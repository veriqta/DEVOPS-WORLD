# Part 17: Bash for System Administration and Server Automation

System administration is one of the places where Bash becomes genuinely powerful.

A Linux administrator or DevOps engineer constantly needs answers to questions such as:

* What server am I connected to?
* Which Linux distribution is running?
* How long has the server been online?
* Is memory running low?
* Is a filesystem nearly full?
* Is a service running?
* Is the application listening on the expected port?
* Does a required user exist?
* Does a required group exist?
* Are important files using safe permissions?
* Is a required package installed?
* Is a process alive?
* Are logs showing recent failures?
* Can a service be restarted safely?
* Did a maintenance operation actually succeed?

You could answer each question manually.

But when you manage:

```text
1 server
10 servers
100 servers
1,000 servers
```

manual inspection becomes slow, inconsistent, and error-prone.

Bash allows you to turn repeatable operational checks into controlled automation.

The important word is:

```text
controlled
```

System-administration scripts can:

* restart services
* modify files
* change permissions
* install packages
* delete data
* affect production traffic

A mistake can therefore have real consequences.

Throughout Part 17, we will follow this operational principle:

```text
Observe
   |
   v
Validate
   |
   v
Decide
   |
   v
Act only when necessary
   |
   v
Verify
   |
   v
Report
```

Never begin with the destructive action.

# 5. Privileges Matter

Many inspection commands work as a normal user.

Some administrative operations require elevated privileges.

For example:

```bash
systemctl restart nginx
```

may require root privileges.

You may need:

```bash
sudo systemctl restart nginx
```

But:

```text
sudo
```

is not a universal solution.

Before using elevated privileges, ask:

```text
Why does this operation require root?

Should this script be allowed to perform it?

What exact command needs elevation?

Can the operation be performed more safely without root?
```

Avoid running an entire large script with root privileges when only one controlled operation needs them.

# 11. Reading `/etc/os-release`

Because `/etc/os-release` uses shell-like assignments, you may encounter:

```bash
source /etc/os-release
```

followed by:

```bash
printf 'OS: %s\n' "$PRETTY_NAME"
```

However, remember the rule from Part 8:

> `source` executes shell syntax in the current shell.

On a trusted Linux system, `/etc/os-release` is normally a system-controlled file designed for machine-readable OS identification, but scripts should still understand that sourcing a file is code execution.

A simple controlled approach can instead extract the required value.

For example:

```bash
grep '^PRETTY_NAME=' /etc/os-release
```

Later you can parse it more carefully.

---

# 12. Safe OS Information Function

```bash
get_os_name() {
    if [[ -r /etc/os-release ]]; then
        local os_name

        os_name="$(
            awk -F= '
                $1 == "PRETTY_NAME" {
                    value = substr($0, index($0, "=") + 1)
                    gsub(/^"/, "", value)
                    gsub(/"$/, "", value)
                    print value
                    exit
                }
            ' /etc/os-release
        )"

        printf '%s\n' "${os_name:-Unknown Linux}"
    else
        printf '%s\n' "Unknown"
    fi
}
```

This demonstrates how the text-processing skills from Part 11 can support system administration.

# 15. CPU Load

A simple command:

```bash
uptime
```

often shows load averages.

Example:

```text
10:30:00 up 15 days, 2:14, 2 users, load average: 0.42, 0.31, 0.27
```

The three load averages generally represent approximately:

```text

```

---

# 16. Load Average Is Not CPU Percentage

This is an important beginner distinction.

A load average of:

```text
4.0
```

does not mean:

```text
4% CPU
```

Linux load average represents runnable or certain uninterruptible tasks over time.

Its meaning should be interpreted relative to system capacity.

For example, a load of approximately:

```text
4
```

on a system with:

```text
4 CPUs
```

means something very different from the same load on a system with:

```text
64 CPUs
```

Do not write scripts that treat load average as a percentage.

# 19. Understanding Linux Memory

Beginners often see low:

```text
free
```

memory and assume the server is out of memory.

Linux intentionally uses available RAM for caching.

A more useful field for many operational checks is:

```text
available
```

rather than only:

```text
free
```

because available memory estimates how much memory can be used without swapping heavily.

# 21. Calculate Memory Usage Percentage

A simple Linux calculation:

```bash
read -r mem_total mem_available < <(
    awk '
        /^MemTotal:/ {
            total = $2
        }

        /^MemAvailable:/ {
            available = $2
        }

        END {
            print total, available
        }
    ' /proc/meminfo
)
```

Then:

```bash
mem_used=$((mem_total - mem_available))
mem_used_percent=$((mem_used * 100 / mem_total))
```

Print:

```bash
printf 'Memory used: %d%%\n' "$mem_used_percent"
```

---

# 22. Validate Before Arithmetic

Do not assume parsing succeeded.

Better:

```bash
if [[ ! "$mem_total" =~ ^[0-9]+$ ]] ||
   [[ ! "$mem_available" =~ ^[0-9]+$ ]] ||
   (( mem_total == 0 )); then
    printf 'ERROR: unable to read memory information\n' >&2
    return 1
fi
```

Then calculate.

Operational scripts should validate the data they depend on.

# 26. Extract Disk Usage Percentage

Example:

```bash
disk_usage="$(
    df -P / |
        awk 'NR == 2 {gsub(/%/, "", $5); print $5}'
)"
```

Then:

```bash
printf 'Root filesystem usage: %s%%\n' "$disk_usage"
```

Before using it numerically:

```bash
if [[ ! "$disk_usage" =~ ^[0-9]+$ ]]; then
    printf 'ERROR: unable to determine disk usage\n' >&2
    exit 1
fi
```

---

# 27. Disk-Space Alert

Suppose you want a warning at:

```text
80%
```

and a critical alert at:

```text
90%
```

You can write:

```bash
if (( disk_usage >= 90 )); then
    printf 'CRITICAL: disk usage is %s%%\n' "$disk_usage"
elif (( disk_usage >= 80 )); then
    printf 'WARNING: disk usage is %s%%\n' "$disk_usage"
else
    printf 'OK: disk usage is %s%%\n' "$disk_usage"
fi
```

This is a basic health-check pattern.

---

# 28. Thresholds Should Be Configurable

Hardcoding:

```text
80
90
```

may be acceptable for a learning exercise.

A reusable script should allow configuration.

Example:

```bash
warning_threshold="${DISK_WARNING_THRESHOLD:-80}"
critical_threshold="${DISK_CRITICAL_THRESHOLD:-90}"
```

Then validate them.

---

# 29. Validate Thresholds

```bash
validate_percentage() {
    local value="$1"
    local name="$2"

    if [[ ! "$value" =~ ^[0-9]+$ ]]; then
        printf 'ERROR: %s must be an integer\n' "$name" >&2
        return 1
    fi

    if (( value < 0 || value > 100 )); then
        printf 'ERROR: %s must be between 0 and 100\n' \
            "$name" >&2
        return 1
    fi
}
```

Then:

```bash
validate_percentage "$warning_threshold" "warning threshold"
validate_percentage "$critical_threshold" "critical threshold"
```

Also verify:

```bash
if (( warning_threshold >= critical_threshold )); then
    printf 'ERROR: warning threshold must be lower than critical threshold\n' >&2
    exit 2
fi
```

# 34. `pgrep`

If you need to find a process by name:

```bash
pgrep nginx
```

may print matching PIDs.

For process name and PID:

```bash
pgrep -a nginx
```

```text

```

```text
application health
```

---

# 35. Process Check Function

```bash
check_process() {
    local process_name="$1"

    if pgrep -x "$process_name" >/dev/null 2>&1; then
        printf 'OK: process %s is running\n' "$process_name"
        return 0
    fi

    printf 'CRITICAL: process %s is not running\n' \
        "$process_name" >&2
    return 1
}
```

The:

```text
-x
```

option asks `pgrep` for an exact process-name match on implementations supporting it.

This is usually safer than loose substring matching.

---

# 36. Why `ps | grep` Is Often a Weak Pattern

Beginners commonly write:

```bash
ps aux | grep nginx
```

Problems include:

* the `grep` command may match itself
* substring matches can be misleading
* output parsing becomes fragile

When available, use purpose-built tools such as:

```bash
pgrep
```

or service managers such as:

```bash
systemctl
```

depending on what you are actually checking.

# 37. Services

A service is typically a long-running system process managed by a service manager.

Examples:

```text
nginx
sshd
docker
postgresql
```

On many modern Linux distributions, the service manager is:

```text
systemd
```

and its primary command-line interface is:

```text
systemctl
```

---

# 38. Check Whether systemd Is Available

Do not assume every Linux environment uses systemd.

Check:

```bash
command -v systemctl
```

But even if the command exists, systemd may not be PID 1 in containers or special environments.

A stronger Linux check might include:

```bash
if [[ "$(ps -p 1 -o comm= 2>/dev/null)" == "systemd" ]]; then
    printf 'systemd appears to be PID 1\n'
fi
```

Environment matters.

---

# 39. `systemctl status`

To inspect a service:

```bash
systemctl status nginx
```

This provides human-readable information such as:

* loaded state
* active state
* PID
* recent logs

It is excellent for interactive investigation.

But scripts should prefer machine-oriented status commands when possible.

---

# 40. `systemctl is-active`

Instead of parsing:

```bash
systemctl status nginx
```

use:

```bash
systemctl is-active nginx
```

Possible output:

```text
active
```

The command also returns an exit status.

That means you can write:

```bash
if systemctl is-active --quiet nginx; then
    printf 'OK: nginx is active\n'
else
    printf 'CRITICAL: nginx is not active\n' >&2
fi
```

This is much better than grepping the human-readable `status` output.

---

# 41. `systemctl is-enabled`

To determine whether a service is configured to start automatically according to systemd enablement state:

```bash
systemctl is-enabled nginx
```

Possible output might include:

```text
enabled
disabled
static
masked
```

Do not assume every valid unit must report:

```text
enabled
```

Some units are static or activated differently.

Understand the service architecture.

---

# 42. Service Active vs Enabled

These are different questions.

```text
ACTIVE
Is it running now?

ENABLED
Is it configured for startup/activation in a particular way?
```

A service can be:

```text
active but disabled
```

or:

```text
enabled but currently failed
```

Do not confuse the two.

---

# 43. Starting a Service

Command:

```bash
sudo systemctl start nginx
```

This asks systemd to start the service.

Do not immediately assume success.

Verify:

```bash
systemctl is-active --quiet nginx
```

Then, depending on the service:

```text
Check port
Check application health endpoint
Check logs
```

A successful `systemctl start` is not necessarily the same as a healthy application.

---

# 44. Stopping a Service

Command:

```bash
sudo systemctl stop nginx
```

This can cause an outage.

Before stopping a service, understand:

```text
What traffic depends on it?

Is redundancy available?

Is this the correct host?

Is maintenance authorized?

Will it restart automatically?

Are there dependent services?

How will success be verified?
```

Never turn service stop/restart into a casual automation action.

---

# 45. Restarting a Service

Command:

```bash
sudo systemctl restart nginx
```

A restart normally stops and starts the service.

This can interrupt traffic.

A safer operational sequence is:

```text
Confirm target
   |
   v
Check current state
   |
   v
Validate configuration
   |
   v
Confirm restart is necessary
   |
   v
Restart
   |
   v
Check service state
   |
   v
Check port
   |
   v
Check application health
   |
   v
Check logs
```

That is much safer than:

```text
Something looks wrong
   |
   v
restart everything
```

---

# 46. Reload vs Restart

Some services support:

```bash
systemctl reload service
```

A reload asks the service to reload configuration without a full restart when supported.

This may reduce disruption.

But not every service supports reload.

You can inspect capabilities or service documentation before relying on it.

For nginx, configuration should usually be validated before reload or restart.

Example:

```bash
nginx -t
```

Then:

```bash
sudo systemctl reload nginx
```

if validation succeeds and reload is appropriate.

---

# 47. Never Restart to Hide the Root Cause

A service restart can temporarily make a symptom disappear.

For example:

```text
memory leak
connection exhaustion
deadlock
bad deployment
disk full
dependency outage
```

may appear fixed after restart.

But the root cause remains.

Operational reasoning:

```text
Observe failure
   |
   v
Gather evidence
   |
   v
Preserve useful logs
   |
   v
Understand likely cause
   |
   v
Restart only if justified
   |
   v
Verify recovery
   |
   v
Investigate root cause
```

# 48. Safe Service Restart Function

A reusable function might begin:

```bash
restart_service() {
    local service_name="$1"

    if [[ -z "$service_name" ]]; then
        printf 'ERROR: service name is required\n' >&2
        return 2
    fi

    if ! command -v systemctl >/dev/null 2>&1; then
        printf 'ERROR: systemctl is unavailable\n' >&2
        return 1
    fi

    if ! systemctl cat "$service_name" >/dev/null 2>&1; then
        printf 'ERROR: service does not exist: %s\n' \
            "$service_name" >&2
        return 1
    fi

    printf 'Restarting service: %s\n' "$service_name"

    if ! sudo systemctl restart "$service_name"; then
        printf 'ERROR: restart failed: %s\n' \
            "$service_name" >&2
        return 1
    fi

    if ! systemctl is-active --quiet "$service_name"; then
        printf 'ERROR: service is not active after restart: %s\n' \
            "$service_name" >&2
        return 1
    fi

    printf 'OK: service restarted and is active: %s\n' \
        "$service_name"
}
```

But this still does not prove application health.

---

# 49. Why Arbitrary Service Names Are Dangerous

Imagine a privileged script accepts:

```bash
./restart-service.sh "$user_input"
```

and restarts whatever service name is provided.

That may give callers too much operational power.

For controlled automation, use an allowlist where appropriate.

Example:

```bash
case "$service_name" in
    nginx|myapp|redis)
        ;;
    *)
        printf 'ERROR: service is not approved for automated restart: %s\n' \
            "$service_name" >&2
        return 2
        ;;
esac
```

Least privilege applies to automation interfaces.

# 53. `getent`

On many Linux systems:

```bash

```

can query user information through the system's configured name-service mechanisms.

This can include users from sources beyond only:

```text
/etc/passwd
```

depending on system configuration.

For example:

```bash
getent passwd nginx
```

This is often preferable to directly grepping `/etc/passwd`.

---

# 54. Why Not Just `grep /etc/passwd`?

You may see:

```bash
grep '^nginx:' /etc/passwd
```

But systems can obtain account information through mechanisms such as:

* local files
* LDAP
* other NSS sources

`getent` asks the configured name-service database.

Use the system interface that matches the question you are asking.

# 55. Group Checks

```bash
groups
```


For a specific user:


# 56. Check Whether a Group Exists

```bash
check_group() {
    local group_name="$1"

    if getent group "$group_name" >/dev/null 2>&1; then
        printf 'OK: group exists: %s\n' "$group_name"
        return 0
    fi

    printf 'CRITICAL: required group does not exist: %s\n' \
        "$group_name" >&2
    return 1
}
```

```bash
command -v getent
```

# 57. Check User Membership in a Group

You might need to know whether:

```text
deploy
```

belongs to:

```text
docker
```

One useful approach is:

```bash
id -nG deploy
```

Example:

```text
deploy sudo docker
```

A safe Bash check can split the output into an array:

```bash
user_in_group() {
    local username="$1"
    local required_group="$2"
    local group
    local -a groups=()

    if ! id "$username" >/dev/null 2>&1; then
        printf 'ERROR: user does not exist: %s\n' \
            "$username" >&2
        return 1
    fi

    read -r -a groups <<< "$(id -nG "$username")"

    for group in "${groups[@]}"; do
        if [[ "$group" == "$required_group" ]]; then
            return 0
        fi
    done

    return 1
}
```

This uses arrays from Part 12.

# 58. Permission Validation

System automation frequently depends on files having correct:

```text
owner
group
permissions
```

Examples:

```text
SSH private keys
application configuration
TLS private keys
service files
deployment scripts
backup directories
```

You learned Linux permissions in Part 10.

Now we apply them operationally.

---

# 59. Inspect Permissions

Run:

```bash
ls -l file
```

For more precise scripting:

```bash
stat file
```

On GNU/Linux:

```bash
stat -c '%a %U %G %n' file
```

may produce:

```text
600 ann ann secret.conf
```

Meaning:

```text
permissions = 600
owner = ann
group = ann
file = secret.conf
```

Be aware that `stat` options differ across operating systems.

This part focuses primarily on Linux.

---

# 60. Validate Exact Permissions

Suppose a sensitive file must be:

```text
600
```

Check:

```bash
permissions="$(stat -c '%a' "$file")"
```

Then:

```bash
if [[ "$permissions" != "600" ]]; then
    printf 'WARNING: %s permissions are %s, expected 600\n' \
        "$file" "$permissions"
fi
```

---

# 61. Validate Owner and Group

```bash
owner="$(stat -c '%U' "$file")"
group="$(stat -c '%G' "$file")"
```

Then:

```bash
if [[ "$owner" != "$expected_owner" ]]; then
    printf 'ERROR: wrong owner for %s\n' "$file" >&2
fi
```

Similarly for group.

---

# 62. Do Not Automatically Fix Every Permission Problem

This is dangerous:

```bash
chmod -R 777 "$directory"
```

It may make the immediate error disappear while creating a serious security problem.

A safer workflow:

```text
Identify required permission
   |
   v
Inspect current owner/group/mode
   |
   v
Understand which process needs access
   |
   v
Change the minimum required permission
   |
   v
Verify
```

Least privilege applies to filesystem permissions.

# 63. Disk-Space Alerts Across Filesystems

A server may have multiple mounted filesystems.

Example:

```text
/
 /var
 /data
 /backup
```

Checking only:

```text
/
```

may miss:

```text
/data = 99%
```

A broader script can inspect multiple filesystems.

But parsing `df` safely requires care because filesystems and mount points can vary.

For a beginner project, explicitly checking known mount points is often safer.

---

# 64. Check Known Mount Points

Example:

```bash
mount_points=(
    "/"
    "/var"
    "/data"
)
```

Then:

```bash
for mount_point in "${mount_points[@]}"; do
    if [[ ! -e "$mount_point" ]]; then
        printf 'SKIP: path does not exist: %s\n' "$mount_point"
        continue
    fi

    usage="$(
        df -P "$mount_point" |
            awk 'NR == 2 {gsub(/%/, "", $5); print $5}'
    )"

    printf '%s: %s%%\n' "$mount_point" "$usage"
done
```

In production, also consider whether multiple paths map to the same filesystem.

---

# 65. Inodes Can Fill Up Too

A filesystem can report available disk space but still fail to create files because it has exhausted inodes.

Inspect:

```bash
df -i
```

Example:

```text
Filesystem      Inodes   IUsed   IFree IUse% Mounted on
...
```

A server with millions of tiny files can run out of inodes before running out of storage bytes.

This is an important operational check.

---

# 66. Disk Troubleshooting Workflow

Problem:

```text
Application cannot write files.
```

Do not immediately delete random data.

Check:

```bash

```

Then investigate relevant directories:

```bash

```

or another known location.

Reasoning:

```text
Write failure
   |
   +--> disk bytes full?
   |
   +--> inodes full?
   |
   +--> permissions?
   |
   +--> filesystem read-only?
   |
   +--> quota?
```

Disk-full is only one possible cause.

* contact repositories
* modify package state
* require privileges

# 81. `ss`

On modern Linux systems:

```bash

```

```text

```

# 82. Inspect a Port

You might interactively run:

```bash
ss -lnt | grep ':8080'
```

But loose matching can produce false positives.

For example:

```text
:8080
```

should not accidentally match:

```text
:80801
```

Parsing socket output deserves care.

---

# 83. Basic Listening-Port Function

A Linux-focused beginner function:

```bash
check_tcp_port() {
    local port="$1"

    if [[ ! "$port" =~ ^[0-9]+$ ]] ||
       (( port < 1 || port > 65535 )); then
        printf 'ERROR: invalid TCP port: %s\n' "$port" >&2
        return 2
    fi

    if ss -lntH |
        awk -v expected_port="$port" '
            {
                address = $4
                sub(/^.*:/, "", address)

                if (address == expected_port) {
                    found = 1
                    exit
                }
            }

            END {
                exit(found ? 0 : 1)
            }
        '
    then
        printf 'OK: TCP port %s is listening\n' "$port"
        return 0
    fi

    printf 'CRITICAL: TCP port %s is not listening\n' \
        "$port" >&2
    return 1
}
```

This is still Linux-tool-specific and should be tested against your actual `ss` output.

---

# 84. Port Listening Does Not Prove Application Health

Suppose:

```text
TCP 8080 is listening
```

The application may still:

* return HTTP 500
* reject authentication
* fail database connections
* be stuck
* serve stale data
* fail only certain requests

Health checking should be layered.

---

# 85. Layered Service Health

A better model:

```text
Service manager
      |
      v
Is process active?
      |
      v
Is expected port listening?
      |
      v
Does application respond?
      |
      v
Does health endpoint report healthy?
      |
      v
Are dependencies healthy?
```

Each layer answers a different question.

# 86. HTTP Health Checks

Suppose an application exposes:

```text
http://127.0.0.1:8080/health
```

You can use:

```bash
curl -fsS http://127.0.0.1:8080/health
```

Useful options include:

```text
-f    fail on HTTP error status
-s    silent progress
-S    still show errors
```

But production health checks should also consider timeouts.

---

# 87. Add Timeouts

Avoid allowing a health-check script to hang indefinitely.

Example:

```bash
curl \
    --connect-timeout 3 \
    --max-time 5 \
    -fsS \
    http://127.0.0.1:8080/health
```

Now the check has bounded waiting time.

Timeout values should match the operational context.

---

# 88. Health Function

```bash
check_http_health() {
    local url="$1"

    if curl \
        --connect-timeout 3 \
        --max-time 5 \
        -fsS \
        "$url" \
        >/dev/null
    then
        printf 'OK: health endpoint responded successfully: %s\n' \
            "$url"
        return 0
    fi

    printf 'CRITICAL: health endpoint failed: %s\n' \
        "$url" >&2
    return 1
}
```

Do not place credentials directly into diagnostic output.

# 91. Basic Inventory Function

```bash
print_server_inventory() {
    printf 'SERVER INVENTORY\n'
    printf '================\n'

    printf 'Hostname: %s\n' "$(hostname)"
    printf 'OS: %s\n' "$(get_os_name)"
    printf 'Kernel: %s\n' "$(uname -r)"
    printf 'Architecture: %s\n' "$(uname -m)"
```

# 92. Inventory Should Be Read-Only

A server inventory script should normally observe.

It should not unexpectedly:

* install packages
* restart services
* delete logs
* change permissions

Keep:

```text
inventory
```

separate from:

```text
maintenance
```

unless the user explicitly selects a maintenance operation.

This separation reduces risk.

---

# 93. Automated Maintenance

Maintenance scripts can perform repetitive tasks such as:

```text
cleaning controlled temporary files
rotating application-generated artifacts
checking backups
validating services
checking package state
checking disk space
restarting approved services
```

But maintenance is more dangerous than inventory.

A maintenance script should include:

```text
validation
dry-run where appropriate
allowlists
logging
clear exit statuses
verification
```

---

# 94. Maintenance Should Be Idempotent

From earlier parts:

```text
idempotent
```

means repeated execution should produce a predictable safe result.

For example:

```bash
mkdir -p "$directory"
```

is usually more rerunnable than:

```bash
mkdir "$directory"
```

when the directory may already exist.

For system administration, ask:

```text
What happens if this automation runs twice?

What happens if the previous run failed halfway?

What happens if the server is already in the desired state?
```

---

# 95. Do Not Restart a Healthy Service Without Reason

Bad maintenance logic:

```text
Every hour:
restart application
```

Better:

```text
Check health
   |
   +--> healthy
   |      |
   |      +--> do nothing
   |
   +--> unhealthy
          |
          +--> gather evidence
          +--> validate restart policy
          +--> restart if appropriate
          +--> verify recovery
```

Automatic restarts can hide recurring defects.

---

# 96. Safe Restart Logic

A controlled restart function should consider:

```text
Is restart allowed?

Is service approved?

Is systemctl available?

Does service exist?

Is restart actually necessary?

Should configuration be validated first?

Can evidence be captured before restart?

Did restart command succeed?

Is service active afterward?

Is expected port listening?

Does application health succeed?

If not, what should happen?
```

This is much more than:

```bash
systemctl restart app
```

---

# 97. Pre-Restart Evidence

Before restarting an unhealthy service, capture useful evidence.

Example:

```bash
systemctl status "$service_name" --no-pager
```

and:

```bash
journalctl -u "$service_name" -n 50 --no-pager
```

But be mindful:

* logs may contain secrets
* output may be large
* permissions may restrict access

Evidence should be captured deliberately.

---

# 98. Configuration Validation Before Restart

Some services provide configuration-test commands.

Examples:

```bash
nginx -t
```

or service-specific equivalents.

A restart after invalid configuration can turn:

```text
currently running service
```

into:

```text
service that cannot start
```

Therefore:

```text
validate configuration
before
restart/reload
```

when the service supports it.

---

# 99. Example Nginx Safe Restart Logic

A Linux/nginx-specific example:

```bash
restart_nginx_safely() {
    if ! command -v nginx >/dev/null 2>&1; then
        printf 'ERROR: nginx command not found\n' >&2
        return 1
    fi

    if ! command -v systemctl >/dev/null 2>&1; then
        printf 'ERROR: systemctl command not found\n' >&2
        return 1
    fi

    printf 'Validating nginx configuration...\n'

    if ! sudo nginx -t; then
        printf 'ERROR: nginx configuration validation failed\n' >&2
        return 1
    fi

    printf 'Configuration is valid.\n'
    printf 'Restarting nginx...\n'

    if ! sudo systemctl restart nginx; then
        printf 'ERROR: nginx restart failed\n' >&2
        return 1
    fi

    if ! systemctl is-active --quiet nginx; then
        printf 'ERROR: nginx is not active after restart\n' >&2
        return 1
    fi

    printf 'OK: nginx restarted successfully\n'
}
```

For a production load balancer, you may prefer a reload or orchestrated instance rotation depending on architecture.

# 100. Why `sudo` Inside Scripts Requires Thought

A script containing:


may:

* prompt for a password
* fail in non-interactive automation
* work for one user but not another
* have broader privilege implications

Production automation should have an intentional privilege model.

Examples include:

```text
restricted sudo policy
service account
orchestration platform
configuration-management system
systemd permissions
```

Do not assume interactive `sudo` is suitable for unattended automation.

# 101. Root Detection

You can inspect the effective user ID:

```bash

```

Root normally has:

```text
0
```

# 102. Service Health Check Function

```bash
check_systemd_service() {
    local service_name="$1"

    if ! command -v systemctl >/dev/null 2>&1; then
        printf 'ERROR: systemctl is unavailable\n' >&2
        return 2
    fi

    if ! systemctl cat "$service_name" >/dev/null 2>&1; then
        printf 'ERROR: service not found: %s\n' \
            "$service_name" >&2
        return 2
    fi

    if systemctl is-active --quiet "$service_name"; then
        printf 'OK: service is active: %s\n' "$service_name"
        return 0
    fi

    printf 'CRITICAL: service is not active: %s\n' \
        "$service_name" >&2
    return 1
}
```

This reports state without changing anything.

---

# 103. Multiple Service Checks

Using arrays from Part 12:

```bash
services=(
    "nginx"
    "ssh"
    "cron"
)
```

Then:

```bash
for service in "${services[@]}"; do
    check_systemd_service "$service" || true
done
```

But there is an important issue.

If you use:

```bash
|| true
```

you suppress failure for the loop.

That may be appropriate for continuing checks, but you must record the failures separately.

---

# 104. Aggregate Health Status

Suppose you want to inspect every service even if one fails.

Use:

```bash
overall_status=0

for service in "${services[@]}"; do
    if ! check_systemd_service "$service"; then
        overall_status=1
    fi
done

exit "$overall_status"
```

Now:

* all checks run
* the final script still reports failure if any service failed

This is much better than exiting after the first failed health check when you want a complete report.

---

# 105. Warning vs Critical Status

A useful health model:

```text
OK
WARNING
CRITICAL
UNKNOWN/ERROR
```

You might represent them internally as:

```text
0 = OK
1 = WARNING
2 = CRITICAL
3 = UNKNOWN
```

But if integrating with an external monitoring system, use that system's documented exit-code expectations.

For a standalone script, document your own scheme clearly.

---

# 106. Do Not Accidentally Downgrade Severity

Suppose:

```text
disk = CRITICAL
memory = WARNING
```

Your overall result should remain:

```text
CRITICAL
```

not become:

```text
WARNING
```

because the warning happened later.

You need severity aggregation.

---

# 107. Severity Aggregation Function

```bash
overall_status=0

update_status() {
    local new_status="$1"

    if (( new_status > overall_status )); then
        overall_status="$new_status"
    fi
}
```

Then:

```bash
update_status 1
update_status 2
update_status 1
```

Final:

```text
2
```

This preserves the highest severity.

---

# 108. Disk Check Function

```bash
check_disk_usage() {
    local path="$1"
    local warning="$2"
    local critical="$3"
    local usage

    if [[ ! -e "$path" ]]; then
        printf 'UNKNOWN: path does not exist: %s\n' "$path" >&2
        return 3
    fi

    if ! usage="$(
        df -P "$path" 2>/dev/null |
            awk 'NR == 2 {gsub(/%/, "", $5); print $5}'
    )"; then
        printf 'UNKNOWN: unable to inspect disk usage: %s\n' \
            "$path" >&2
        return 3
    fi

    if [[ ! "$usage" =~ ^[0-9]+$ ]]; then
        printf 'UNKNOWN: invalid disk usage value for %s\n' \
            "$path" >&2
        return 3
    fi

    if (( usage >= critical )); then
        printf 'CRITICAL: disk %s is %s%% used\n' \
            "$path" "$usage"
        return 2
    fi

    if (( usage >= warning )); then
        printf 'WARNING: disk %s is %s%% used\n' \
            "$path" "$usage"
        return 1
    fi

    printf 'OK: disk %s is %s%% used\n' "$path" "$usage"
    return 0
}
```

# 109. Memory Check Function

```bash
check_memory_usage() {
    local warning="$1"
    local critical="$2"

    local mem_total
    local mem_available
    local mem_used
    local usage

    if [[ ! -r /proc/meminfo ]]; then
        printf 'UNKNOWN: /proc/meminfo is unavailable\n' >&2
        return 3
    fi

    read -r mem_total mem_available < <(
        awk '
            /^MemTotal:/ {
                total = $2
            }

            /^MemAvailable:/ {
                available = $2
            }

            END {
                print total, available
            }
        ' /proc/meminfo
    )

    if [[ ! "$mem_total" =~ ^[0-9]+$ ]] ||
       [[ ! "$mem_available" =~ ^[0-9]+$ ]] ||
       (( mem_total == 0 )); then
        printf 'UNKNOWN: unable to parse memory information\n' >&2
        return 3
    fi

    mem_used=$((mem_total - mem_available))
    usage=$((mem_used * 100 / mem_total))

    if (( usage >= critical )); then
        printf 'CRITICAL: memory usage is %d%%\n' "$usage"
        return 2
    fi

    if (( usage >= warning )); then
        printf 'WARNING: memory usage is %d%%\n' "$usage"
        return 1

    printf 'OK: memory usage is %d%%\n' "$usage"
```

A naive script may calculate:

```text
used = total - free
```

But Linux uses memory for caches.

Using:

```text
MemAvailable
```

provides a more useful estimate for many operational checks.

This does not mean every monitoring system calculates memory pressure exactly this way.

Production monitoring may use more sophisticated metrics.

# 129. Run a Check Without Stopping the Script

We want every check to run.

A helper:

```bash
run_check() {
    local status

    set +e
    "$@"
    status=$?
    set -e

    record_result "$status"
}
```

However, toggling `set -e` repeatedly can become difficult to reason about.

A cleaner design is to run checks inside an `if`, because commands tested by conditional constructs are handled differently by `errexit`.

Use:

```bash
run_check() {
    local status

    if "$@"; then
        status=0
    else
        status=$?
    fi

    record_result "$status"
}
```

This is clearer.

---

# 130. Why Capture `$?` Immediately?

This is wrong:

```bash
if ! check_something; then
    printf 'Check failed\n'
    status=$?
fi
```

After:

```text
!
```

the status has been inverted.

And after another command, `$?` may refer to that later command.

Instead:

```bash
if check_something; then
    status=0
else
    status=$?
fi
```

captures the original check status safely.

This continues the exit-status lessons from Parts 5 and 14.

# 138. Memory Check

```bash
check_memory() {
    local mem_total
    local mem_available
    local mem_used
    local usage

    if [[ ! -r /proc/meminfo ]]; then
        printf 'UNKNOWN: /proc/meminfo unavailable\n'
        return "$STATUS_UNKNOWN"
    fi

    read -r mem_total mem_available < <(
        awk '
            /^MemTotal:/ {
                total = $2
            }

            /^MemAvailable:/ {
                available = $2
            }

            END {
                print total, available
            }
        ' /proc/meminfo
    )

    if [[ ! "$mem_total" =~ ^[0-9]+$ ]] ||
       [[ ! "$mem_available" =~ ^[0-9]+$ ]] ||
       (( mem_total == 0 )); then
        printf 'UNKNOWN: unable to parse memory information\n'
        return "$STATUS_UNKNOWN"
    fi

    mem_used=$((mem_total - mem_available))
    usage=$((mem_used * 100 / mem_total))

    if (( usage >= MEMORY_CRITICAL )); then
        printf 'CRITICAL: memory usage is %d%%\n' "$usage"
        return "$STATUS_CRITICAL"
    fi

    if (( usage >= MEMORY_WARNING )); then
        printf 'WARNING: memory usage is %d%%\n' "$usage"
        return "$STATUS_WARNING"
    fi

    printf 'OK: memory usage is %d%%\n' "$usage"
    return "$STATUS_OK"
}
```

# 150. A Severity Design Problem

Our numeric scheme is:

```text
0 OK
1 WARNING
2 CRITICAL
3 UNKNOWN
```

Using:

```bash
if (( status > overall_status ))
```

means:

```text
UNKNOWN
```

has higher severity than:

```text
CRITICAL
```

Is that what we want?

Maybe.

Maybe not.

This is a design decision.

If:

```text
UNKNOWN
```

means:

```text
the check could not be performed
```

you might consider it operationally serious.

But you may want:

```text
CRITICAL
```

to outrank unknown.

This demonstrates why exit-code numbers and business severity are not always the same concept.

---

# 151. Better Severity Ranking

Keep exit codes:

```text
0 OK
1 WARNING
2 CRITICAL
3 UNKNOWN
```

but define explicit severity ranking.

Example:

```bash
status_rank() {
    local status="$1"

    case "$status" in
        "$STATUS_OK")
            printf '0\n'
            ;;

        "$STATUS_WARNING")
            printf '1\n'
            ;;

        "$STATUS_UNKNOWN")
            printf '2\n'
            ;;

        "$STATUS_CRITICAL")
            printf '3\n'
            ;;

        *)
            return 1
            ;;
    esac
}
```

Now:

```text
CRITICAL
```

can outrank:

```text
UNKNOWN
```

without changing external status codes.

```bash
            ;;
        "$STATUS_WARNING")
            printf '1\n'

            ;;
        "$STATUS_WARNING")

    printf '\n%s\n' "$title"
    printf '%*s\n' "${#title}" '' | tr ' ' '-'

load_configuration() {

        printf 'ERROR: configuration file is not readable: %s\n' \

validate_percentage() {
    local value="$1"
    local name="$2"

    if [[ ! "$value" =~ ^[0-9]+$ ]]; then
        printf 'ERROR: %s must be an integer\n' "$name" >&2
        return 1
    fi

    if (( value < 0 || value > 100 )); then
        printf 'ERROR: %s must be between 0 and 100\n' \
            "$name" >&2
        return 1
    fi
}

validate_configuration() {
    : "${DISK_WARNING:?DISK_WARNING is required}"
    : "${DISK_CRITICAL:?DISK_CRITICAL is required}"
    : "${MEMORY_WARNING:?MEMORY_WARNING is required}"
    : "${MEMORY_CRITICAL:?MEMORY_CRITICAL is required}"
    : "${INODE_WARNING:?INODE_WARNING is required}"
    : "${INODE_CRITICAL:?INODE_CRITICAL is required}"

    validate_percentage "$DISK_WARNING" "DISK_WARNING"
    validate_percentage "$DISK_CRITICAL" "DISK_CRITICAL"

    validate_percentage "$MEMORY_WARNING" "MEMORY_WARNING"
    validate_percentage "$MEMORY_CRITICAL" "MEMORY_CRITICAL"

    validate_percentage "$INODE_WARNING" "INODE_WARNING"
    validate_percentage "$INODE_CRITICAL" "INODE_CRITICAL"

    if (( DISK_WARNING >= DISK_CRITICAL )); then
        printf 'ERROR: DISK_WARNING must be lower than DISK_CRITICAL\n' >&2
        return 1
    fi

    if (( MEMORY_WARNING >= MEMORY_CRITICAL )); then
        printf 'ERROR: MEMORY_WARNING must be lower than MEMORY_CRITICAL\n' >&2
        return 1
    fi

    if (( INODE_WARNING >= INODE_CRITICAL )); then
        printf 'ERROR: INODE_WARNING must be lower than INODE_CRITICAL\n' >&2

    if [[ ! -r /etc/os-release ]]; then
        printf 'Unknown\n'

check_command() {
    local command_name="$1"

    if command -v "$command_name" >/dev/null 2>&1; then
        printf 'OK: command available: %s\n' "$command_name"
        return "$STATUS_OK"
    fi

    printf 'CRITICAL: required command missing: %s\n' \
        "$command_name"
    return "$STATUS_CRITICAL"
}

check_memory() {
    local mem_total
    local mem_available
    local mem_used
    local usage

    if [[ ! -r /proc/meminfo ]]; then
        printf 'UNKNOWN: /proc/meminfo unavailable\n'
        return "$STATUS_UNKNOWN"
    fi

    read -r mem_total mem_available < <(
        awk '
            /^MemTotal:/ {
                total = $2
            }

            /^MemAvailable:/ {
                available = $2
            }

            END {
                print total, available
            }
        ' /proc/meminfo
    )

    if [[ ! "$mem_total" =~ ^[0-9]+$ ]] ||
       [[ ! "$mem_available" =~ ^[0-9]+$ ]] ||
       (( mem_total == 0 )); then
        printf 'UNKNOWN: unable to parse memory information\n'
        return "$STATUS_UNKNOWN"
    fi

    mem_used=$((mem_total - mem_available))
    usage=$((mem_used * 100 / mem_total))

    if (( usage >= MEMORY_CRITICAL )); then
        printf 'CRITICAL: memory usage is %d%%\n' "$usage"
        return "$STATUS_CRITICAL"
    fi

    if (( usage >= MEMORY_WARNING )); then
        printf 'WARNING: memory usage is %d%%\n' "$usage"
        return "$STATUS_WARNING"
    fi

    printf 'OK: memory usage is %d%%\n' "$usage"
    return "$STATUS_OK"
}

check_disk() {
    local path="$1"
    local usage

    if [[ ! -e "$path" ]]; then
        printf 'UNKNOWN: disk path does not exist: %s\n' "$path"
        return "$STATUS_UNKNOWN"
    fi

    usage="$(
        df -P "$path" 2>/dev/null |
            awk 'NR == 2 {gsub(/%/, "", $5); print $5}'
    )"

    if [[ ! "$usage" =~ ^[0-9]+$ ]]; then
        printf 'UNKNOWN: unable to parse disk usage: %s\n' "$path"
        return "$STATUS_UNKNOWN"
    fi

    if (( usage >= DISK_CRITICAL )); then
        printf 'CRITICAL: disk %s usage is %s%%\n' \
            "$path" "$usage"
        return "$STATUS_CRITICAL"
    fi

    if (( usage >= DISK_WARNING )); then
        printf 'WARNING: disk %s usage is %s%%\n' \
            "$path" "$usage"
        return "$STATUS_WARNING"
    fi

    printf 'OK: disk %s usage is %s%%\n' "$path" "$usage"
    return "$STATUS_OK"
}

check_inodes() {
    local path="$1"
    local usage

    usage="$(
        df -Pi "$path" 2>/dev/null |
            awk 'NR == 2 {gsub(/%/, "", $5); print $5}'
    )"

    if [[ ! "$usage" =~ ^[0-9]+$ ]]; then
        printf 'UNKNOWN: unable to parse inode usage: %s\n' "$path"
        return "$STATUS_UNKNOWN"
    fi

    if (( usage >= INODE_CRITICAL )); then
        printf 'CRITICAL: inode usage for %s is %s%%\n' \
            "$path" "$usage"
        return "$STATUS_CRITICAL"
    fi

    if (( usage >= INODE_WARNING )); then
        printf 'WARNING: inode usage for %s is %s%%\n' \
            "$path" "$usage"
        return "$STATUS_WARNING"
    fi

    printf 'OK: inode usage for %s is %s%%\n' \
        "$path" "$usage"
    return "$STATUS_OK"
}

check_user() {
    local username="$1"

    if id "$username" >/dev/null 2>&1; then
        printf 'OK: user exists: %s\n' "$username"
        return "$STATUS_OK"
    fi

    printf 'CRITICAL: required user missing: %s\n' "$username"
    return "$STATUS_CRITICAL"
}

check_group() {
    local group_name="$1"

    if ! command -v getent >/dev/null 2>&1; then
        printf 'UNKNOWN: getent unavailable; cannot check group %s\n' \
            "$group_name"
        return "$STATUS_UNKNOWN"
    fi

    if getent group "$group_name" >/dev/null 2>&1; then
        printf 'OK: group exists: %s\n' "$group_name"
        return "$STATUS_OK"
    fi

    printf 'CRITICAL: required group missing: %s\n' "$group_name"
    return "$STATUS_CRITICAL"
}

check_file_permissions() {
    local file="$1"
    local expected_mode="$2"
    local actual_mode

    if [[ ! -f "$file" ]]; then
        printf 'CRITICAL: required file missing: %s\n' "$file"
        return "$STATUS_CRITICAL"
    fi

    actual_mode="$(stat -c '%a' "$file" 2>/dev/null)" || {
        printf 'UNKNOWN: unable to inspect permissions: %s\n' "$file"
        return "$STATUS_UNKNOWN"
    }

    if [[ "$actual_mode" == "$expected_mode" ]]; then
        printf 'OK: permissions for %s are %s\n' \
            "$file" "$actual_mode"
        return "$STATUS_OK"
    fi

    printf 'WARNING: permissions for %s are %s, expected %s\n' \
        "$file" "$actual_mode" "$expected_mode"
    return "$STATUS_WARNING"
}

check_service() {
    local service_name="$1"

    if ! command -v systemctl >/dev/null 2>&1; then
        printf 'UNKNOWN: systemctl unavailable; cannot check %s\n' \
            "$service_name"
        return "$STATUS_UNKNOWN"
    fi

    if ! systemctl cat "$service_name" >/dev/null 2>&1; then
        printf 'UNKNOWN: systemd unit not found: %s\n' \
            "$service_name"
        return "$STATUS_UNKNOWN"
    fi

    if systemctl is-active --quiet "$service_name"; then
        printf 'OK: service is active: %s\n' "$service_name"
        return "$STATUS_OK"
    fi

    printf 'CRITICAL: service is not active: %s\n' "$service_name"
    return "$STATUS_CRITICAL"
}

check_process() {
    local process_name="$1"

    if ! command -v pgrep >/dev/null 2>&1; then
        printf 'UNKNOWN: pgrep unavailable\n'
        return "$STATUS_UNKNOWN"
    fi

    if pgrep -x "$process_name" >/dev/null 2>&1; then
        printf 'OK: process is running: %s\n' "$process_name"
        return "$STATUS_OK"
    fi

    printf 'CRITICAL: process is not running: %s\n' "$process_name"
    return "$STATUS_CRITICAL"
}

check_tcp_port() {
    local port="$1"

    if [[ ! "$port" =~ ^[0-9]+$ ]] ||
       (( port < 1 || port > 65535 )); then
        printf 'UNKNOWN: invalid TCP port: %s\n' "$port"
        return "$STATUS_UNKNOWN"
    fi

    if ! command -v ss >/dev/null 2>&1; then
        printf 'UNKNOWN: ss unavailable; cannot check port %s\n' \
            "$port"
        return "$STATUS_UNKNOWN"
    fi

    if ss -lntH |
        awk -v expected_port="$port" '
            {
                address = $4
                sub(/^.*:/, "", address)

                if (address == expected_port) {
                    found = 1
                    exit
                }
            }

            END {
                exit(found ? 0 : 1)
            }
        '
    then
        printf 'OK: TCP port is listening: %s\n' "$port"
        return "$STATUS_OK"
    fi

    printf 'CRITICAL: TCP port is not listening: %s\n' "$port"
    return "$STATUS_CRITICAL"
}

check_http() {
    local url="$1"

    if ! command -v curl >/dev/null 2>&1; then
        printf 'UNKNOWN: curl unavailable; cannot check %s\n' "$url"
        return "$STATUS_UNKNOWN"
    fi

    if curl \
        --connect-timeout 3 \
        --max-time 5 \
        -fsS \
        "$url" \
        >/dev/null
    then
        printf 'OK: HTTP health check passed: %s\n' "$url"
        return "$STATUS_OK"
    fi

    printf 'CRITICAL: HTTP health check failed: %s\n' "$url"
    return "$STATUS_CRITICAL"
}

print_summary() {
    printf '\nSUMMARY\n'
    printf '%s\n' '-------'

    printf 'OK: %d\n' "$ok_count"
    printf 'WARNING: %d\n' "$warning_count"
    printf 'CRITICAL: %d\n' "$critical_count"
    printf 'UNKNOWN: %d\n' "$unknown_count"

    printf 'Overall status: '

    case "$overall_status" in
        "$STATUS_OK")
            printf 'OK\n'
            ;;
        "$STATUS_WARNING")
            printf 'WARNING\n'
            ;;
        "$STATUS_CRITICAL")
            printf 'CRITICAL\n'
            ;;
        "$STATUS_UNKNOWN")
            printf 'UNKNOWN\n'
            ;;
    esac
}

    load_configuration
```

# 162. Adding Log Inspection

A health script can inspect recent application logs, but log interpretation is application-specific.

For example:

```bash
check_recent_errors() {
    local log_file="$1"
    local line_count="${2:-100}"
    local error_count

    if [[ ! -r "$log_file" ]]; then
        printf 'UNKNOWN: log file unreadable: %s\n' "$log_file"
        return "$STATUS_UNKNOWN"
    fi

    error_count="$(
        tail -n "$line_count" "$log_file" |
            grep -ci 'error' || true
    )"

    if [[ ! "$error_count" =~ ^[0-9]+$ ]]; then
        printf 'UNKNOWN: unable to inspect log: %s\n' "$log_file"
        return "$STATUS_UNKNOWN"
    fi

    if (( error_count > 0 )); then
        printf 'WARNING: found %d error-like lines in recent %s lines of %s\n' \
            "$error_count" "$line_count" "$log_file"
        return "$STATUS_WARNING"
    fi

    printf 'OK: no error-like lines found in recent log sample: %s\n' \
        "$log_file"
    return "$STATUS_OK"
}
```

# 163. Why `grep ... || true` Appears There

`grep` returns:

```text
0 = match found
1 = no match found
```

No match is not necessarily an operational error.

With:

```bash
set -e
```

you must understand command statuses carefully.

However, the pipeline above can be designed more clearly without relying on `|| true`.

For example, `awk` could count matching lines and always print a number.

This demonstrates why strict mode requires deliberate scripting.

# 164. Better Log Error Count

Example:

```bash
error_count="$(
    tail -n "$line_count" "$log_file" |
        awk '
            BEGIN {
                IGNORECASE = 1
            }

            /error/ {
                count += 1
            }

            END {
                print count + 0
            }
        '
)"
```

This avoids treating "no matches" as a special failure status.

But note:

```text
IGNORECASE
```

is supported by common awk implementations but portability details can vary.

For maximum portability, normalize text another way.

```bash
    printf 'ERROR: refusing operation on unexpected host: %s\n' \

    exit 1
fi
```

This is useful in tightly controlled environments.

But hostnames alone should not be treated as a perfect security boundary.

Use multiple safeguards for dangerous operations.

# 170. Validate Environment Too

If the server has:

```bash

```

a destructive maintenance operation can require explicit production authorization.

For example:

```bash
if [[ "${APP_ENV:-}" == "production" ]] &&
   [[ "${ALLOW_PRODUCTION_MAINTENANCE:-}" != "yes" ]]; then
    printf 'ERROR: production maintenance not explicitly authorized\n' >&2
    exit 1
fi
```

But environment variables themselves can be changed.

They are guardrails, not authorization systems.

# 172. Automated Restart Loops Can Be Dangerous

Never create:

```bash

    if ! health_check; then
        restart_service
    fi
done
```

without controls.

A permanently broken application could enter:

```text

restart
fail
restart
fail
restart
```

This creates a restart storm.

You need:

* retry limits
* backoff
* cooldown
* escalation
* evidence preservation
* failure thresholds

Conceptually:


Then:

```text

    if restart_count >= max_restarts:
        stop automatic remediation
        alert human/operator
```

Production systems such as systemd and orchestration platforms often already provide restart policies.

Possible cause:

The process accepted the socket but the application is unhealthy.

# 184. Troubleshooting: Disk Shows 100%

Problem:

```text
Use% = 100%
```

Investigate:

```bash

df -i
```

Then identify large relevant directories:

```bash

    sort -h |
    tail
```

Be cautious on large filesystems because recursive `du` can be expensive.

Do not delete before identifying:


# 185. Troubleshooting: `du` and `df` Disagree

Possible causes can include:

* deleted files still held open by processes
* filesystem metadata/reserved space
* mount boundaries
* sparse files
* permissions preventing `du` from seeing everything

One important Linux investigation for deleted-but-open files is:

```bash
lsof +L1
```

if `lsof` is installed.

A process can keep disk blocks allocated after a file has been deleted until the file descriptor is closed.

# 186. Troubleshooting: Memory Usage Is High

Do not immediately restart the server.

```bash

```

Then:

```bash

```

* available memory
* swap activity
* application behavior
* memory leaks
* workload growth
* cache behavior
* container memory limits

High memory usage alone does not always mean failure.

# 192. Verification Window

A simple controlled approach:

```bash
sleep 2
```

then recheck.

But arbitrary sleeps are imperfect.

Better systems may poll:

```text
up to 30 seconds
every 2 seconds
until healthy
```

with a timeout.

You learned polling and retries in Part 7.

---

# 193. Health Polling Example

```bash
wait_for_health() {
    local url="$1"
    local attempts="${2:-10}"
    local delay="${3:-2}"
    local attempt

    for ((attempt = 1; attempt <= attempts; attempt++)); do
        if curl \
            --connect-timeout 2 \
            --max-time 3 \
            -fsS \
            "$url" \
            >/dev/null
        then
            printf 'Health check passed on attempt %d\n' "$attempt"
            return 0
        fi

        if (( attempt < attempts )); then
            sleep "$delay"
        fi
    done

    printf 'ERROR: health check did not recover\n' >&2
    return 1
}
```

This has a finite retry limit.

---

# 194. Avoid Infinite Health Polling

Bad:

```bash
while ! curl ...; do
    sleep 1
done
```

If the service never recovers, the script never finishes.

Always define:

```text
timeout
attempt limit
failure behavior
```

for production automation.

# 195. Maintenance Logging

A maintenance script should record important actions.

Example:

```bash
log() {
    local level="$1"
    shift

    printf '%s [%s] %s\n' \
        "$(date '+%Y-%m-%d %H:%M:%S')" \
        "$level" \
        "$*"
}
```

Then:

```bash
log INFO "Checking nginx configuration"
log INFO "Restarting nginx"
log ERROR "nginx failed health verification"
```

Do not log secrets.
