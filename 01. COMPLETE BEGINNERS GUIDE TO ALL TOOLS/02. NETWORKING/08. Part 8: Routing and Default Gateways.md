# Part 8: Routing and Default Gateways

## Learn How Packets Move Between Different Networks

In Part 7, you learned that switches move Ethernet frames inside Layer 2 networks, while communication between different IP networks requires Layer 3 routing.

Now we will focus on that Layer 3 process.

Consider this simple network:

```text
Laptop
192.168.10.50/24
     |
     v
Switch
     |
     v
Router
     |
     v
Internet
```

The laptop can communicate directly with devices inside `192.168.10.0/24`.

But what happens when it wants to reach:

```text
8.8.8.8
```

That address is not part of its local network.

The laptop needs another device to move the packet toward the remote network.

That device is normally its default gateway.

By the end of this part, you should understand how a host makes this decision:

```text
Destination IP
      |
      v
Check routing table
      |
      v
Which route matches?
      |
      v
Choose most specific route
      |
      +------------------+
      |                  |
      v                  v
Local network        Remote network
      |                  |
      v                  v
Send locally         Send to next hop
```

You will also learn how Linux routing tables work, how static and default routes are created, what route metrics mean, why routing loops occur, and how to troubleshoot routing failures systematically.

---

# 1. What Is Routing?

Routing is the process of determining where an IP packet should be sent so that it can reach its destination network.

Suppose your computer has:

```text
IP address:
192.168.10.50/24
```

and wants to communicate with:

```text
192.168.20.100
```

These addresses belong to different networks:

```text
192.168.10.0/24

192.168.20.0/24
```

A normal Layer 2 switch cannot simply move the packet from one IP network into the other.

A Layer 3 device must make a routing decision.

Conceptually:

```text
192.168.10.0/24
       |
       v
    Router
       |
       v
192.168.20.0/24
```

The router receives the packet, examines its destination IP address, consults its routing table, and determines where to send it next.

---

# 2. Why Routing Exists

Imagine three networks:

```text
Engineering
10.10.10.0/24

Finance
10.10.20.0/24

Servers
10.10.30.0/24
```

Without routing, each network is isolated at Layer 3.

```text
Engineering       Finance         Servers

10.10.10.0/24   10.10.20.0/24   10.10.30.0/24

      X                X                X
```

Routing creates paths between them:

```text
10.10.10.0/24
      |
      v
+-------------+
|   Router    |
+-------------+
   |       |
   v       v
10.10.20   10.10.30
.0/24      .0/24
```

Routing therefore allows separate IP networks to communicate.

---

# 3. Why Separate Networks in the First Place?

If routing is required to connect networks, why divide networks at all?

Because one enormous network is often undesirable.

Separate networks can help with:

* Organization
* Broadcast containment
* Security segmentation
* Department separation
* Cloud architecture
* Failure isolation
* Address management
* Network policy
* Geographic separation
* Scaling

For example:

```text
Users
10.0.10.0/24

Application Servers
10.0.20.0/24

Databases
10.0.30.0/24

Management
10.0.40.0/24
```

Routing provides controlled communication between these networks.

---

# 4. Routers vs Switches

You already learned that switches commonly operate at Layer 2.

A traditional Layer 2 switch primarily examines:

```text
Destination MAC address
```

A router primarily makes forwarding decisions using:

```text
Destination IP address
```

A simplified comparison:

| Device         | Primary Layer  | Main Information        | Main Job                         |
| -------------- | -------------- | ----------------------- | -------------------------------- |
| Layer 2 switch | Layer 2        | MAC addresses           | Forward Ethernet frames          |
| Router         | Layer 3        | IP addresses and routes | Forward packets between networks |
| Layer 3 switch | Layers 2 and 3 | MAC and IP information  | Switching plus routing           |

Remember that modern networking devices can perform many functions, so real products are not always limited to one simple category.

---

# 5. Switch Packet Flow

Suppose:

```text
Host A
192.168.10.10/24

Host B
192.168.10.20/24
```

Both belong to:

```text
192.168.10.0/24
```

Host A can communicate with Host B through Layer 2 switching.

```text
Host A
   |
   v
Switch
   |
   v
Host B
```

The switch does not need to route the packet into another IP network.

---

# 6. Router Packet Flow

Now suppose:

```text
Host A
192.168.10.10/24
```

wants:

```text
Host C
192.168.20.20/24
```

The destination belongs to another network.

The path becomes:

```text
Host A
   |
   v
Switch
   |
   v
Router
   |
   v
Switch
   |
   v
Host C
```

Routing occurs between:

```text
192.168.10.0/24
```

and:

```text
192.168.20.0/24
```

---

# 7. Local vs Remote Destinations

Before sending a packet, a host needs to answer an important question:

```text
Is this destination local or remote?
```

Suppose your Linux machine has:

```text
IP:
192.168.10.50

Prefix:
/24
```

Its local network is:

```text
192.168.10.0/24
```

The normal host range is:

```text
192.168.10.1
through
192.168.10.254
```

Now consider:

```text
192.168.10.100
```

That is local.

But:

```text
192.168.20.100
```

is remote.

The subnet mask or prefix helps the host determine this.

---

# 8. Local Destination Flow

Suppose:

```text
Host A
192.168.10.50/24
```

wants:

```text
192.168.10.100
```

The destination belongs to the same subnet.

Conceptually:

```text
192.168.10.50
      |
      | Local destination
      v
Resolve destination MAC
      |
      v
Send Ethernet frame
directly toward destination
```

For IPv4 Ethernet networks, ARP may be used to resolve the destination MAC address.

The default gateway is not required for this local communication.

---

# 9. Remote Destination Flow

Now Host A wants:

```text
10.20.30.40
```

Host A determines that this address is outside:

```text
192.168.10.0/24
```

It therefore needs a route.

Often that route says:

```text
For destinations I do not know more specifically,
send traffic to 192.168.10.1
```

`192.168.10.1` is the default gateway in this example.

---

# 10. What Is a Default Gateway?

A default gateway is the next-hop Layer 3 device a host normally uses when it needs to reach destinations outside its directly connected networks and has no more specific route.

Example:

```text
Laptop:
192.168.10.50/24

Gateway:
192.168.10.1
```

Network:

```text
Laptop
192.168.10.50
     |
     v
Switch
     |
     v
Router
192.168.10.1
     |
     v
Other Networks
```

The gateway provides a way out of the local network.

---

# 11. The Gateway Must Normally Be Reachable Locally

This is an important beginner concept.

If the host has:

```text
192.168.10.50/24
```

and its gateway is:

```text
192.168.10.1
```

the gateway belongs to the host's local subnet.

The host can therefore resolve its MAC address and send Ethernet frames to it.

Conceptually:

```text
Remote destination
        |
        v
Need gateway
        |
        v
Gateway must be reachable
through local interface
```

A badly configured gateway can prevent remote connectivity.

---

# 12. Destination IP vs Destination MAC

This is one of the most important concepts in networking.

Suppose:

```text
Laptop:
192.168.10.50

Gateway:
192.168.10.1

Remote Server:
10.50.20.100
```

The laptop wants to reach the remote server.

The IP packet contains:

```text
Source IP:
192.168.10.50

Destination IP:
10.50.20.100
```

But the Ethernet frame on the laptop's local network is addressed to the gateway's MAC:

```text
Source MAC:
Laptop MAC

Destination MAC:
Gateway MAC
```

So:

```text
Ethernet destination
=
Next local hop

IP destination
=
Final Layer 3 destination
```

This distinction explains much of routing.

---

# 13. Packet and Frame View

Conceptually:

```text
Ethernet Frame
+----------------------------------+
| Destination MAC: Router MAC      |
| Source MAC: Laptop MAC           |
|                                  |
|   IP Packet                      |
|   +--------------------------+   |
|   | Source: 192.168.10.50    |   |
|   | Destination: 10.50.20.100|   |
|   | Data                     |   |
|   +--------------------------+   |
+----------------------------------+
```

The frame gets the packet to the next Layer 2 hop.

The IP destination identifies where the packet ultimately needs to go.

---

# 14. What Happens at the Router?

The router receives the Ethernet frame.

It processes the Layer 2 framing addressed to it and examines the enclosed IP packet.

It sees:

```text
Destination:
10.50.20.100
```

The router asks:

```text
Which route should I use for 10.50.20.100?
```

It consults its routing table.

Then it forwards the packet toward the appropriate next hop or outgoing interface.

---

# 15. MAC Addresses Change Hop by Hop

Suppose the path is:

```text
Laptop
 |
 v
Router A
 |
 v
Router B
 |
 v
Server
```

The Layer 2 framing is rebuilt as the packet moves between Layer 3 hops.

Conceptually:

```text
Laptop -> Router A

Source MAC:
Laptop

Destination MAC:
Router A
```

Next link:

```text
Router A -> Router B

Source MAC:
Router A outgoing interface

Destination MAC:
Router B
```

Final local link:

```text
Router B -> Server

Source MAC:
Router B

Destination MAC:
Server
```

The IP packet still identifies the original source and final destination, unless something such as NAT changes addressing.

---

# 16. What Is a Routing Table?

A routing table contains information about where packets should be sent.

A simplified routing table might look like:

```text
Destination        Next Hop         Interface
------------------------------------------------
192.168.10.0/24    directly         eth0
10.20.0.0/16       192.168.10.2     eth0
0.0.0.0/0          192.168.10.1     eth0
```

The system compares the destination IP against these routes.

---

# 17. Understanding a Route

A route generally contains information such as:

```text
Destination network
Prefix length
Next hop
Outgoing interface
Metric or preference information
```

For example:

```text
10.20.0.0/16 via 192.168.10.2 dev eth0
```

Let's break it down.

```text
10.20.0.0/16
```

Destination network.

```text
via 192.168.10.2
```

Next-hop router.

```text
dev eth0
```

Outgoing interface.

---

# 18. Destination Networks

A route usually represents a network rather than one individual destination.

For example:

```text
10.20.0.0/16
```

can match addresses such as:

```text
10.20.1.5
10.20.20.100
10.20.200.50
```

This allows one route to represent many destinations.

Without prefixes, routers might need enormous tables containing individual entries for every possible host.

---

# 19. Prefixes in Routing

You learned CIDR in Part 5.

Routing uses the same concept.

Examples:

```text
10.0.0.0/8

10.20.0.0/16

10.20.30.0/24

10.20.30.50/32
```

A larger prefix length represents a more specific route.

For example:

```text
/8
```

is less specific than:

```text
/24
```

and:

```text
/32
```

identifies one IPv4 address.

---

# 20. What Is a Next Hop?

The next hop is the next Layer 3 device toward the destination.

Suppose:

```text
Host
 |
 v
Router A
 |
 v
Router B
 |
 v
Server
```

From the host's perspective:

```text
Next hop = Router A
```

From Router A's perspective:

```text
Next hop may = Router B
```

The host does not necessarily need to know the complete path.

It only needs an appropriate next step.

---

# 21. Routing Is a Series of Decisions

Imagine traveling from New York to a small town in another country.

You do not need to know every road before starting.

You may first know:

```text
Go to the airport.
```

Then another system determines the next step.

Routing works similarly.

```text
Packet
  |
  v
Router A
  |
  | Where next?
  v
Router B
  |
  | Where next?
  v
Router C
  |
  v
Destination
```

Each router makes its own forwarding decision.

---

# 22. Outgoing Interfaces

A router can have several network interfaces.

For example:

```text
              Router
        +----------------+
        |                |
 eth0 --|                |-- eth1
        |                |
        |                |-- eth2
        +----------------+
```

Perhaps:

```text
eth0 -> 10.0.10.0/24

eth1 -> 10.0.20.0/24

eth2 -> ISP
```

The routing table helps determine which interface should carry a packet.

---

# 23. Connected Routes

A connected route represents a network directly attached to an interface.

Suppose:

```text
eth0:
192.168.10.1/24
```

The router knows that:

```text
192.168.10.0/24
```

is directly reachable through `eth0`.

Similarly:

```text
eth1:
192.168.20.1/24
```

provides direct connectivity to:

```text
192.168.20.0/24
```

Conceptually:

```text
192.168.10.0/24
       |
      eth0
       |
     Router
       |
      eth1
       |
192.168.20.0/24
```

---

# 24. Why Connected Routes Matter

If a router is directly connected to:

```text
192.168.20.0/24
```

it does not need another router to reach that network.

It can deliver packets directly through the appropriate interface.

The next step may involve resolving the destination's Layer 2 address.

So:

```text
Connected route
=
Destination network is directly reachable
through one of my interfaces
```

---

# 25. Static Routes

A static route is manually configured.

Suppose Router A knows:

```text
10.10.10.0/24
```

but needs to reach:

```text
10.20.20.0/24
```

through Router B:

```text
10.10.10.2
```

An administrator can create a route conceptually saying:

```text
To reach 10.20.20.0/24,
send packets to 10.10.10.2.
```

On Linux, that could look like:

```bash
sudo ip route add 10.20.20.0/24 via 10.10.10.2
```

---

# 26. Understanding the Static Route Command

Command:

```bash
sudo ip route add 10.20.20.0/24 via 10.10.10.2
```

Breakdown:

```text
sudo
```

Run the command with elevated privileges.

```text
ip
```

Linux networking utility.

```text
route
```

Work with the routing table.

```text
add
```

Add a new route.

```text
10.20.20.0/24
```

Destination network.

```text
via
```

Specify the next hop.

```text
10.10.10.2
```

Next-hop router.

The command means:

```text
For 10.20.20.0/24,
forward traffic toward 10.10.10.2.
```

---

# 27. Important Warning About Temporary Routes

Commands such as:

```bash
sudo ip route add ...
```

normally modify the running Linux networking state.

They do not necessarily survive a reboot.

Persistent routing configuration depends on the Linux distribution and network management system, such as:

* NetworkManager
* Netplan
* systemd-networkd
* Distribution-specific networking configuration

Do not assume an `ip route add` command permanently configures the server.

---

# 28. Verifying a Static Route

After adding a route:

```bash
ip route
```

You may see:

```text
10.20.20.0/24 via 10.10.10.2 dev eth0
```

Then ask Linux exactly which route it would use:

```bash
ip route get 10.20.20.50
```

Example:

```text
10.20.20.50 via 10.10.10.2 dev eth0 src 10.10.10.10
```

This is extremely useful for troubleshooting.

---

# 29. Removing a Temporary Route

If you added:

```bash
sudo ip route add 10.20.20.0/24 via 10.10.10.2
```

you can remove the matching route with:

```bash
sudo ip route del 10.20.20.0/24 via 10.10.10.2
```

Be careful when changing routes on remote systems.

Removing the route used by your SSH connection can disconnect you from the server.

---

# 30. Default Routes

A default route is used when no more specific route matches the destination.

For IPv4:

```text
0.0.0.0/0
```

represents the default route.

On Linux:

```text
default via 192.168.10.1 dev eth0
```

is effectively equivalent to:

```text
0.0.0.0/0 via 192.168.10.1
```

It means:

```text
If I do not have a more specific route,
send the packet to 192.168.10.1.
```

---

# 31. Why `/0` Means Default

IPv4 addresses contain 32 bits.

A `/0` prefix fixes zero destination bits.

Therefore it can match every IPv4 address.

Examples:

```text
8.8.8.8
```

matches:

```text
0.0.0.0/0
```

So does:

```text
1.1.1.1
```

and:

```text
172.20.50.100
```

But if a more specific matching route exists, that route normally wins through longest prefix matching.

---

# 32. Longest Prefix Match

Suppose the routing table contains:

```text
10.0.0.0/8
10.20.0.0/16
10.20.30.0/24
0.0.0.0/0
```

A packet is destined for:

```text
10.20.30.50
```

All four routes match.

But which should be selected?

The most specific matching prefix:

```text
10.20.30.0/24
```

This is called:

```text
Longest Prefix Match
```

---

# 33. Why Longest Prefix Match Matters

Consider:

```text
10.0.0.0/8
via Router A

10.20.0.0/16
via Router B
```

Destination:

```text
10.20.50.25
```

Both routes match.

But:

```text
/16
```

is more specific than:

```text
/8
```

Therefore the `/16` route is preferred based on prefix specificity.

---

# 34. Another Longest Prefix Example

Routing table:

```text
192.168.0.0/16     via Router A
192.168.10.0/24    via Router B
192.168.10.50/32   via Router C
default            via Router D
```

Destination:

```text
192.168.10.50
```

Matches:

```text
192.168.0.0/16
192.168.10.0/24
192.168.10.50/32
0.0.0.0/0
```

The winner is:

```text
192.168.10.50/32
```

because `/32` is the longest matching prefix.

---

# 35. Route Metrics

What if multiple routes exist for the same destination prefix?

Example:

```text
default via 192.168.10.1 metric 100

default via 192.168.20.1 metric 500
```

Both are default routes.

Metrics can help determine preference between otherwise comparable routes.

Generally, a lower metric is preferred within the relevant routing context.

So:

```text
metric 100
```

would normally be preferred over:

```text
metric 500
```

Do not confuse metrics with prefix length.

Prefix specificity is evaluated before a metric comparison between equivalent route choices.

---

# 36. Multiple Routes

A host may have several routes.

Example:

```text
10.0.0.0/8 via 192.168.1.1
172.16.0.0/12 via 192.168.1.2
192.168.1.0/24 dev eth0
default via 192.168.1.254
```

Traffic for:

```text
10.50.20.30
```

uses:

```text
10.0.0.0/8
```

Traffic for:

```text
172.20.50.10
```

uses:

```text
172.16.0.0/12
```

Traffic for:

```text
8.8.8.8
```

uses the default route.

Suppose:

```text
10.0.0.0/8 via Router A

10.20.0.0/16 via Router B

10.20.30.0/24 via Router C

default via Router D
```

Where does this go?

```text
10.20.30.100
```

Router C.


Router B.

```text
10.100.50.20
```

Router A.

What about:

```text
8.8.8.8
```

Router D.

# 38. Viewing Linux Routing Tables

The modern Linux command is:

```bash
ip route
```

You may also use:

```bash
ip route show
```

Example output:


Let's interpret it carefully.

---

# 39. Understanding `ip route` Output

First line:

```text
default via 192.168.1.1 dev eth0 proto dhcp metric 100
```

Meaning:

```text
default
```

This is the default route.

```text
via 192.168.1.1
```

Use `192.168.1.1` as the next hop.

```text
dev eth0
```

Send through `eth0`.

```text
proto dhcp
```

This route was learned or installed through DHCP-related configuration.

```text
metric 100
```

Route preference information.

---

# 40. Connected Route Output

Second line:

```text
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.50 metric 100
```

Important pieces:

```text
192.168.1.0/24
```

Destination network.

```text
dev eth0
```

Use `eth0`.

```text
proto kernel
```

The kernel installed the route because of interface addressing.

```text
scope link
```

The destination is directly reachable on that link.

```text
src 192.168.1.50
```

Preferred source address associated with that route.

# 41. `ip route get`

One of the best beginner troubleshooting commands is:

```bash
ip route get 8.8.8.8
```

Instead of reading the entire routing table yourself, you ask Linux:

```text
How would you route traffic to 8.8.8.8?
```

Example:

```text
8.8.8.8 via 192.168.1.1 dev eth0 src 192.168.1.50
```

This immediately tells you:

* Next hop
* Outgoing interface
* Selected source address

---

# 42. Why `ip route get` Is So Useful

Suppose a server has:

```text
eth0
eth1
eth2
```

and dozens of routes.

Instead of guessing:

```text
Which route should this packet use?
```

run:

```bash
ip route get 10.50.20.100
```

You can inspect the kernel's route selection directly.

This is much safer than making configuration changes before understanding the current behavior.

---

# 43. The Older `route` Command

You may encounter:

```bash
route
```

or:

```bash
route -n
```

Example:

```bash
route -n
```

Historically, this displayed the kernel routing table using the `net-tools` package.

However, modern Linux administration generally prefers:

```bash
ip route
```

from the `iproute2` tooling.

You should still recognize `route` because older tutorials, systems, scripts, and troubleshooting documentation may use it.

---

# 44. Why `route -n` Was Common

The `-n` option requests numeric output rather than resolving addresses into names.

That avoids unnecessary name-resolution behavior and can make troubleshooting clearer.

But for modern work, learn:

```bash
ip route
```

first.

Treat:

```bash
route
```

as legacy knowledge you should recognize.

---

# 45. Adding a Route Through an Interface

Some routes can specify an outgoing interface.

For example:

```bash
sudo ip route add 10.30.0.0/16 dev eth1
```

This tells Linux that traffic for:

```text
10.30.0.0/16
```

should use:

```text
eth1
```

Whether such a route is appropriate depends on the network type and topology.

Do not blindly replace next-hop routes with interface-only routes.

The forwarding behavior must match the actual network.

---

# 46. Adding a Route With a Next Hop and Interface

You may also see:

```bash
sudo ip route add 10.30.0.0/16 via 192.168.20.1 dev eth1
```

Meaning:

```text
Destination:
10.30.0.0/16

Next hop:
192.168.20.1

Interface:
eth1
```

This is explicit and easy to reason about.

---

# 47. Adding a Temporary Default Route

A command might look like:

```bash
sudo ip route add default via 192.168.10.1
```

Or explicitly:

```bash
sudo ip route add default via 192.168.10.1 dev eth0
```

Be extremely careful with default routes on remote servers.

Changing the default route can immediately disrupt:

* SSH
* Monitoring
* Package downloads
* API communication
* Database connections
* Cloud management agents

Always inspect the current routing table before changing it.

---

# 48. Safer Routing Workflow

Before modifying a route:

```bash
ip addr
```

Then:

```bash
ip route
```

Then:

```bash
ip route get <destination>
```

For example:

```bash
ip route get 8.8.8.8
```

Understand the current path before changing anything.

A good workflow is:

```text
Observe
   |
   v
Understand existing route
   |
   v
Identify desired route
   |
   v
Make smallest necessary change
   |
   v
Verify
   |
   v
Make persistent only when correct
```

---

# 49. Dynamic Routing

Static routes are manually configured.

But imagine a network containing:

```text
10 routers
100 routers
1,000 routers
```

Manually maintaining every possible route can become difficult.

Networks can instead use dynamic routing protocols.

Dynamic routing allows routers to exchange information and adapt their routing knowledge.

Conceptually:

```text
Router A <----> Router B
   ^               |
   |               v
Router D <----> Router C
```

Routers exchange reachability information according to the routing protocol being used.

---

# 50. Static vs Dynamic Routing

Static routing:

```text
Administrator
      |
      v
Manually configures routes
```

Dynamic routing:

```text
Routers
   |
   v
Exchange routing information
   |
   v
Build and update route knowledge
```

Static routes are still extremely useful.

Dynamic routing does not replace static routing everywhere.

Real networks often use both.

---

# 51. Why Dynamic Routing Exists

Suppose:

```text
Router A ----- Router B ----- Router C
```

Router A needs to reach networks behind Router C.

With static routing, administrators manually configure the necessary paths.

Now imagine hundreds of routers and thousands of networks.

Dynamic routing helps with:

* Learning routes
* Responding to topology changes
* Choosing paths
* Scaling route management
* Advertising network reachability

---

# 52. Routing Protocol Overview

Three important protocols beginners should recognize are:

```text
RIP
OSPF
BGP
```

They do not all solve exactly the same problem or operate at the same scale.

A very simplified view:

| Protocol | Common Context                                                                      |
| -------- | ----------------------------------------------------------------------------------- |
| RIP      | Simple or legacy routing environments, education                                    |
| OSPF     | Internal routing within organizations                                               |
| BGP      | Routing between autonomous systems, Internet-scale and large policy-driven networks |

We will introduce them without trying to turn this part into an advanced routing course.

---

# 53. RIP

RIP stands for:

```text
Routing Information Protocol
```

RIP is a distance-vector routing protocol.

One important concept in RIP is:

```text
Hop count
```

A route passing through fewer routers can be considered preferable under RIP's basic metric.

Conceptually:

```text
Network X

Path A:
R1 -> R2 -> X

Path B:
R1 -> R3 -> R4 -> R5 -> X
```

Path A has fewer hops.

---

# 54. RIP Limitations

RIP has significant limitations for modern large networks.

Its maximum usable hop count is small.

A hop count of 16 represents unreachable in RIP.

This severely limits scalability.

RIP also converges more slowly than modern alternatives in many situations.

You should understand RIP because it teaches important routing concepts, but you are much more likely to encounter protocols such as OSPF and BGP in serious modern infrastructure discussions.

---

# 55. OSPF

OSPF stands for:

```text
Open Shortest Path First
```

OSPF is a link-state routing protocol commonly used inside organizations.

Routers participating in OSPF exchange topology information and calculate paths.

OSPF uses a concept called:

```text
Cost
```

when selecting routes.

Conceptually:

```text
          R2
        /    \
      /        \
    R1          R4
      \        /
        \    /
          R3
```

OSPF builds knowledge about the topology and calculates appropriate paths.

---

# 56. OSPF and Areas

OSPF networks can be divided into:

```text
Areas
```

This helps structure larger OSPF deployments.

A particularly important area is:

```text
Area 0
```

called the backbone area.

At beginner level, remember:

```text
OSPF
 |
 +-- Link-state routing protocol
 |
 +-- Common inside organizations
 |
 +-- Uses cost
 |
 +-- Supports areas
 |
 +-- Area 0 is the backbone
```

Detailed OSPF neighbor states, LSAs, DR/BDR elections, SPF calculations, and area types belong in more advanced networking material.

---

# 57. BGP Introduction

BGP stands for:

```text
Border Gateway Protocol
```

BGP is fundamental to Internet routing.

The Internet is not one giant organization running one internal routing protocol.

It consists of many independently administered networks.

These networks can be organized as:

```text
Autonomous Systems
```

or:

```text
ASes
```

BGP allows autonomous systems to exchange routing information.

---

# 58. Autonomous Systems

An autonomous system is a collection of IP networks and routers under a defined administrative routing policy, identified for BGP purposes by an Autonomous System Number.

Conceptually:

```text
+----------------+
|      AS 1      |
| Organization A |
+----------------+
        |
        | BGP
        |
+----------------+
|      AS 2      |
| Organization B |
+----------------+
```

BGP helps these networks exchange reachability information.

---

# 59. Why BGP Is Different

BGP is heavily policy-oriented.

It is not simply:

```text
Find the physically shortest path.
```

Organizations may choose routes based on:

* Business relationships
* Routing policy
* AS path information
* Traffic engineering
* Reachability
* Attributes attached to routes

This is one reason Internet routing is much more complex than simply counting routers.

---

# 60. RIP vs OSPF vs BGP

A beginner mental model:

```text
RIP
 |
 +-> Distance vector
 +-> Hop-count metric
 +-> Limited scalability
```

```text
OSPF
 |
 +-> Link state
 +-> Cost-based path selection
 +-> Common internal routing protocol
```

```text
BGP
 |
 +-> Path-vector protocol
 +-> Policy-driven
 +-> Connects autonomous systems
 +-> Fundamental to Internet routing
```

Do not try to memorize every detail yet.

First understand why different routing protocols exist.

---

# 61. What Is Packet Forwarding?

A Linux system normally processes traffic addressed to itself.

But Linux can also be configured to forward packets between interfaces.

For example:

```text
Network A
   |
 eth0
   |
Linux Router
   |
 eth1
   |
Network B
```

If forwarding is enabled and routing/security configuration permits it, Linux can act as a router.

---

# 62. Linux IPv4 Forwarding

You can inspect IPv4 forwarding with:

```bash
sysctl net.ipv4.ip_forward
```

Possible output:

```text
net.ipv4.ip_forward = 0
```

`0` means IPv4 forwarding is disabled.

```text
net.ipv4.ip_forward = 1
```

means IPv4 forwarding is enabled.

You can also inspect:

```bash
cat /proc/sys/net/ipv4/ip_forward
```

---

# 63. Temporarily Enabling IPv4 Forwarding

In a disposable lab, you could temporarily enable forwarding with:

```bash
sudo sysctl -w net.ipv4.ip_forward=1
```

This changes the running kernel setting.

Warning:

Do not enable forwarding blindly on production machines.

Turning a host into a forwarding device can change its security exposure and traffic behavior.

Routing also depends on:

* Routes
* Firewall rules
* Interface configuration
* Network policy
* Reverse paths
* Potential NAT requirements

Forwarding alone does not create a complete router configuration.

---

# 64. Linux Router Example

Suppose:

```text
eth0:
192.168.10.1/24

eth1:
192.168.20.1/24
```

Topology:

```text
Host A
192.168.10.10
     |
     v
192.168.10.1
 Linux Router
192.168.20.1
     |
     v
Host B
192.168.20.10
```

If forwarding and appropriate policies are enabled, Linux can route between:

```text
192.168.10.0/24
```

and:

```text
192.168.20.0/24
```

Host A might use:

```text
192.168.10.1
```

as its gateway.

Host B might use:

```text
192.168.20.1
```

as its gateway.

---

# 65. Return Routing Matters

Suppose Host A sends:

```text
192.168.10.10
      |
      v
Linux Router
      |
      v
192.168.20.10
```

Host B receives the packet.

Communication is not complete.

Host B must know how to send the reply back to:

```text
192.168.10.10
```

A path working in one direction is not enough.

This is the:

```text
Return path
```

concept.

---

# 66. Forward Path and Return Path

A successful conversation requires:

```text
Forward:

A -> B
```

and:

```text
Return:

B -> A
```

If B does not know how to reach A:

```text
A --------> B
             |
             X
       Cannot return
```

A user may report:

```text
The server is not responding.
```

But the incoming packet may actually reach the server.

The reply is what fails.

This is a common networking troubleshooting pattern.

---

# 67. Asymmetric Routing

Asymmetric routing occurs when the forward and return traffic use different paths.

For example:

```text
Forward:

Host A
  |
  v
Router 1
  |
  v
Server
```

Return:

```text
Server
  |
  v
Router 2
  |
  v
Host A
```

Different paths are not automatically wrong.

Large networks can intentionally use asymmetric routing.

However, asymmetry can cause problems with devices or systems that expect to observe both directions of a connection.

---

# 68. Why Asymmetric Routing Can Cause Problems

Suppose a stateful firewall tracks a connection.

Forward traffic:

```text
Client
  |
  v
Firewall A
  |
  v
Server
```

Return traffic:

```text
Server
  |
  v
Firewall B
  |
  v
Client
```

Firewall B may not have the connection state established by Firewall A.

Depending on the architecture, return traffic could be dropped.

Asymmetric routing can therefore complicate:

* Stateful firewalls
* NAT
* Load balancers
* Packet captures
* Troubleshooting
* Connection tracking

---

# 69. Multiple Default Routes

A machine might have:

```text
eth0
Wi-Fi
VPN
```

Each can potentially install routes.

For example:

```text
default via 192.168.1.1 dev eth0 metric 100

default via 192.168.50.1 dev wlan0 metric 600
```

The lower-metric default route may be preferred.

But a more specific route can still override both.

For example:

```text
10.50.0.0/16 via VPN
```

Traffic for:

```text
10.50.20.10
```

uses the `/16` route because it is more specific than `/0`.

---

# 70. VPN Routing Example

Before connecting to a VPN:

```text
default via home-router
```

After connecting:

```text
10.50.0.0/16 via VPN
10.60.0.0/16 via VPN
default via home-router
```

Now:

```text
8.8.8.8
```

may still use the home router.

But:

```text
10.50.20.100
```

uses the VPN.

This is called a form of split routing or, in VPN contexts, commonly split tunneling when only selected traffic uses the VPN.

---

# 71. Routing Loops

A routing loop occurs when routers repeatedly forward a packet in a cycle.

Suppose:

```text
Router A:
To reach Network X -> Router B
```

Router B says:

```text
To reach Network X -> Router A
```

Now:

```text
Packet
  |
  v
Router A
  |
  v
Router B
  |
  v
Router A
  |
  v
Router B
  |
  v
...
```

Without a stopping mechanism, the packet could circulate indefinitely.

---

# 72. TTL Prevents Endless IP Loops

IPv4 packets contain a field called:

```text
TTL
```

which stands for:

```text
Time To Live
```

Despite the name, in normal IP forwarding it effectively limits how many Layer 3 hops the packet can survive.

Each router decreases the TTL.

For example:

```text
Host sends:
TTL 64

Router 1:
TTL 63

Router 2:
TTL 62

Router 3:
TTL 61
```

Eventually, if the packet loops long enough:

```text
TTL -> 0
```

The router discards it.

This prevents routing loops from circulating packets forever.

---

# 73. TTL Expiration

When a router discards a packet because TTL expires, it may return an ICMP:

```text
Time Exceeded
```

message.

This behavior is also fundamental to how tools such as `traceroute` can reveal Layer 3 hops.

We will study ICMP and diagnostic tools more deeply later in the networking series.

---

# 74. Recognizing a Routing Loop

A routing loop might produce symptoms such as:

* Destination unreachable
* TTL exceeded messages
* Repeated routers in traceroute
* High unnecessary traffic
* Applications timing out

Conceptually:

```text
1  Router A
2  Router B
3  Router A
4  Router B
5  Router A
6  Router B
```

That repeated pattern strongly suggests a routing problem.

---

# 75. "No Route to Host"

You may encounter:

```text
No route to host
```

A beginner might interpret this literally as:

```text
My routing table definitely has no route.
```

Do not make that assumption.

The error can arise in situations involving:

* Missing routes
* Unreachable next hops
* Network unreachable conditions
* Neighbor resolution failures
* Firewall or ICMP rejection behavior
* Other lower-level reachability problems

Investigate rather than relying solely on the wording.

---

# 76. First Check for "No Route to Host"

Suppose:

```bash
ssh user@10.50.20.10
```

returns a reachability-related error.

Start with:

```bash
ip route get 10.50.20.10
```

If Linux says:

```text
10.50.20.10 via 192.168.1.1 dev eth0
```

then Linux does have a selected route.

Now investigate the next stages.

---

# 77. Check the Interface

Run:

```bash
ip addr
```

and:

```bash
ip link
```

Ask:

```text
Is the expected interface present?

Is it UP?

Does it have the correct IP?

Does it have the correct prefix?
```

A perfect route cannot help if the required interface is unavailable.

---

# 78. Check the Next Hop

Suppose:

```bash
ip route get 10.50.20.10
```

shows:

```text
via 192.168.1.1 dev eth0
```

Now ask:

```text
Can I reach 192.168.1.1?
```

You can inspect neighbor resolution:

```bash
ip neigh show 192.168.1.1
```

Possible healthy state:

```text
192.168.1.1 dev eth0 lladdr aa:bb:cc:dd:ee:ff REACHABLE
```

Possible problem:

```text
192.168.1.1 dev eth0 FAILED
```

If the gateway itself cannot be reached locally, investigate Layer 2 before blaming a remote router.

# 79. Routing Troubleshooting Methodology

Use a structured process.

```text
1. Identify source
       |
       v
2. Identify destination
       |
       v
3. Check source IP/prefix
       |
       v
4. Ask kernel which route wins
       |
       v
5. Identify next hop
       |
       v
6. Verify outgoing interface
       |
       v
7. Verify next-hop reachability
       |
       v
8. Trace forward path
       |
       v
9. Verify destination
       |
       v
10. Verify return route
       |
       v
11. Check filtering/policy
       |
       v
12. Verify after fix
```

This is far more reliable than randomly adding routes.

# 80. Troubleshooting Scenario 1: Wrong Default Gateway

Host:

```text
IP:
192.168.10.50/24

Gateway:
192.168.20.1
```

Expected gateway:

```text
192.168.10.1
```

The configured gateway is not in the expected local subnet.

The host may fail to use it as intended.

Check:

```bash
ip route
```

Then inspect the default route.

Correct the network configuration rather than adding unrelated routes.

---

# 81. Troubleshooting Scenario 2: Missing Default Route

Host:

```text
192.168.10.50/24
```

Routing table:

```text
192.168.10.0/24 dev eth0
```

There is no:

```text
default via ...
```

The host can reach:

```text
192.168.10.x
```

but may not know where to send traffic for:

```text
8.8.8.8
```

unless another specific route covers it.

This produces a classic symptom:

```text
Local network works.
Remote networks do not.
```

---

# 82. Troubleshooting Scenario 3: Wrong Static Route

Suppose:

```text
10.50.0.0/16 via 192.168.10.2
```

but the correct next hop should be:

```text
192.168.10.3
```

Packets are being sent to the wrong router.

Check:

```bash
ip route get 10.50.20.100
```

The output exposes the selected next hop.

This is why checking the actual route decision is more useful than simply testing connectivity repeatedly.

---

# 83. Troubleshooting Scenario 4: More Specific Wrong Route

Suppose:

```text
10.0.0.0/8 via 192.168.1.1

10.50.0.0/16 via 192.168.1.200
```

You expect:

```text
10.50.20.10
```

to use `192.168.1.1`.

But it uses:

```text
192.168.1.200
```

Why?

Because:

```text
10.50.0.0/16
```

is more specific than:

```text
10.0.0.0/8
```

This is not Linux behaving incorrectly.

It is longest prefix match behaving exactly as designed.

---

# 84. Troubleshooting Scenario 5: Return Route Missing

Topology:

```text
Client
10.10.10.10
     |
     v
Router
     |
     v
Server
10.20.20.10
```

The client's packet reaches the server.

But the server has no route back to:

```text
10.10.10.0/24
```

Result:

```text
Client --------> Server
Client <----X--- Server
```

The application times out.

The forward route works.

The return route does not.

Always investigate both directions.

---

# 85. Troubleshooting Scenario 6: Interface Down

Route:

```text
10.50.0.0/16 dev eth1
```

But:

```bash
ip link show eth1
```

reveals that the interface is down.

The routing table alone does not guarantee successful forwarding.

You need:

```text
Correct route
+
Working interface
+
Working Layer 2 path
+
Reachable next hop
+
Correct downstream routing
```

---

# 86. Troubleshooting Scenario 7: Routing vs DNS

User reports:

```text
google.com does not work.
```

Do not immediately conclude:

```text
Routing is broken.
```

First separate name resolution from IP connectivity.

For example, if:

```text
8.8.8.8
```

is reachable but names fail, the problem may be DNS rather than routing.

A good engineer separates:

```text
Can I resolve the name?
```

from:

```text
Can I reach the resulting IP?
```

We will cover DNS deeply later.

---

# 87. Troubleshooting Scenario 8: Routing vs Port Failure

Suppose:

```text
ping server
```

works, but:

```text
ssh server
```

fails.

Routing may be perfectly functional.

The problem could involve:

* SSH service
* TCP port 22
* Firewall rules
* Application binding
* Authentication

Do not interpret every application failure as a routing failure.

# 92. Exercise 4 Solution

Host A examines:

```text
192.168.20.10
```

and determines it is remote.

It sends the packet toward:

```text
192.168.10.1
```

The router receives it.

The router has a connected route:

```text
192.168.20.0/24
```

through its second interface.

It forwards the packet toward Host B.

Host B replies to:

```text
192.168.10.10
```

which is remote from Host B's perspective.

Host B therefore sends the reply to:

```text
192.168.20.1
```

The router forwards the reply into:

```text
192.168.10.0/24
```

Complete path:

```text
Host A
192.168.10.10
      |
      v
192.168.10.1
    Router
192.168.20.1
      |
      v
Host B
192.168.20.10
```

# 100. Common Beginner Routing Mistakes

### Mistake 1: Assuming the default gateway handles local traffic

It normally does not.

Same-subnet traffic can be delivered directly.

### Mistake 2: ARPing for every remote server

A host normally resolves the MAC address of its local next hop, not the MAC of a server several routed networks away.

### Mistake 3: Thinking switches and routers perform the same job

Layer 2 switching and Layer 3 routing solve different problems.

### Mistake 4: Assuming the default route always wins

A more specific route wins through longest prefix matching.

### Mistake 5: Thinking the lowest metric always beats everything

Prefix specificity matters first.

### Mistake 6: Checking only the forward route

Replies need a return path.

### Mistake 7: Adding routes without inspecting existing ones

This can make the network worse.

### Mistake 8: Assuming `ip route add` is persistent

It normally changes running state only.

### Mistake 9: Treating every connectivity problem as routing

DNS, firewalls, applications, ports, interfaces, Layer 2, and authentication can also fail.

### Mistake 10: Changing a remote server's default route casually

You can disconnect yourself immediately.

# 105. Final Routing Troubleshooting Lab

You are the DevOps engineer responsible for this environment:

```text
Developer Laptop
192.168.10.50/24
Gateway: 192.168.10.1
        |
        v
+----------------+
|    Router A    |
| 192.168.10.1   |
| 10.0.0.1       |
+----------------+
        |
        |
   10.0.0.0/30
        |
        |
+----------------+
|    Router B    |
| 10.0.0.2       |
| 172.16.20.1    |
+----------------+
        |
        v
Application Server
172.16.20.50/24
Gateway: 172.16.20.1
```

The developer reports:

```text
I cannot SSH to 172.16.20.50.
```

Do not immediately modify routes.

## Step 1: Verify the source

On the laptop:

```bash
ip addr
```

Confirm:

```text
192.168.10.50/24
```

## Step 2: Inspect routes

```bash
ip route
```

Confirm the expected default route:

```text
default via 192.168.10.1
```

## Step 3: Ask Linux about the server

```bash
ip route get 172.16.20.50
```

You expect the first hop to be:

```text
192.168.10.1
```

## Step 4: Verify the local gateway

Inspect:

```bash
ip neigh show 192.168.10.1
```

If neighbor resolution fails, investigate the local network first.

## Step 5: Examine Router A

Router A must know how to reach:

```text
172.16.20.0/24
```

A possible route could conceptually be:

```text
172.16.20.0/24 via 10.0.0.2
```

Without it, Router A may not know that Router B provides the path.

## Step 6: Examine Router B

Router B is directly connected to:

```text
172.16.20.0/24
```

so it should be able to forward the packet toward the application server.

## Step 7: Verify the return route

This is critical.

Router B must also know how to reach:

```text
192.168.10.0/24
```

Perhaps:

```text
192.168.10.0/24 via 10.0.0.1
```

Without a return path:

```text
Laptop
   |
   | Request
   v
Server

Laptop
   X
   | Reply
   |
Server
```

SSH still fails.

## Step 8: Separate routing from SSH

If basic IP reachability works but TCP port 22 does not, investigate:

```text
SSH service
Firewall
Security policy
Port 22
Server listening address
```

Do not keep modifying routes once the evidence shows routing works.

# What You Should Now Understand

You should now be able to explain the complete routing decision:

```text
Application generates traffic
          |
          v
Destination IP identified
          |
          v
Kernel checks routing table
          |
          v
Matching routes found
          |
          v
Longest prefix match
          |
          v
Preferred route selected
          |
          v
Next hop and interface selected
          |
          v
Layer 2 next-hop address resolved
          |
          v
Frame transmitted
          |
          v
Router receives packet
          |
          v
Router performs another
routing-table lookup
          |
          v
Packet moves toward destination
          |
          v
Destination receives packet
          |
          v
Return routing occurs
```

The most important routing relationships to remember are:

```text
MAC address
-> Gets a frame to the next Layer 2 destination

IP address
-> Identifies the Layer 3 destination

Subnet/prefix
-> Defines address ranges and route specificity

Routing table
-> Contains available paths

Next hop
-> Next router toward the destination

Interface
-> Where the packet leaves

Default gateway
-> Common next hop when no more specific route exists

Longest prefix match
-> Chooses the most specific matching route

Metric
-> Helps choose between comparable route candidates

Static route
-> Manually configured path

Dynamic routing
-> Routers exchange reachability information

Packet forwarding
-> Allows a system to route traffic between interfaces

Return route
-> Allows replies to get back

TTL
-> Prevents packets from circulating forever
```

The central troubleshooting principle for routing is simple:

```text
Do not ask only:

"Can I reach the destination?"

Ask:

"What route should this packet take,
which route did the system actually select,
can it reach the next hop,
and can the reply get back?"
```

That shift from testing blindly to tracing the routing decision is one of the foundations of real network troubleshooting.
