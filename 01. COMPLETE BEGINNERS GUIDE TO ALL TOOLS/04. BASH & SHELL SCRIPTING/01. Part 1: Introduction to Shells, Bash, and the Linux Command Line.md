# Part 1: Introduction to Shells, Bash, and the Linux Command Line

Before learning Bash scripting, you need to understand the environment in which Bash operates.

A common beginner mistake is to jump directly into `.sh` files, variables, loops, and `if` statements without understanding what the terminal is, what the shell does, how Linux receives commands, or why Bash exists in the first place.

This part builds that foundation.

By the end, you should understand the path from:

```text
You
 ↓
Terminal
 ↓
Shell / Bash
 ↓
Linux Kernel
 ↓
Hardware and System Resources
```

You will also run your first Bash commands and create a very small shell script.

---

## 1. What Is a Shell?

A shell is a program that allows you to communicate with an operating system.

You give the shell instructions such as:

```bash
pwd
```

or:

```bash
ls
```

or:

```bash
mkdir project
```

The shell interprets what you typed and determines what should happen.

For example:

```bash
mkdir devops-lab
```

means:

> Run the `mkdir` command and give it `devops-lab` as the directory name.

The shell processes that instruction and arranges for the appropriate operating-system operation to happen.

### Why is it called a shell?

Think about an operating system as layers:

```text
+-----------------------------+
|          User               |
+-----------------------------+
              |
              v
+-----------------------------+
|          Shell              |
+-----------------------------+
              |
              v
+-----------------------------+
|          Kernel             |
+-----------------------------+
              |
              v
+-----------------------------+
| CPU | Memory | Disk | NIC   |
+-----------------------------+
```

The kernel is the central component of the operating system.

The shell provides an interface through which users and scripts can request work from the system.

### What can a shell do?

A shell can help you:

* navigate directories
* create and delete files
* launch programs
* manage processes
* inspect system information
* redirect output
* connect commands together
* work with environment variables
* automate repetitive tasks
* execute scripts
* manage servers
* interact with cloud tools
* run deployment commands
* troubleshoot systems

This is why shell knowledge is fundamental for Linux and DevOps work.

---

# 2. What Is Bash?

Bash stands for:

**Bourne Again Shell**

Bash is a shell and a scripting language.

It was created as a free-software successor compatible with ideas from the earlier Bourne shell.

The name is a play on:

```text
Bourne Shell
     ↓
Bourne Again Shell
     ↓
Bash
```

Bash can operate interactively, where you type commands manually, and it can execute commands stored in scripts.

For example, interactively you might run:

```bash
pwd
```

Then:

```bash
ls
```

Then:

```bash
whoami
```

A Bash script can store those instructions:

```bash
#!/usr/bin/env bash

pwd
ls
whoami
```

Instead of manually entering each command every time, Bash can execute the sequence for you.

That is the beginning of automation.

# 3. Shell vs Terminal vs Command Line

These terms are related, but they do not mean exactly the same thing.

Understanding the distinction now prevents a lot of confusion later.

## Terminal

The terminal is the interface through which you interact with a shell.

On modern computers, what people usually call a terminal is actually a **terminal emulator**.

Examples include:

* GNOME Terminal
* Konsole
* Windows Terminal
* iTerm2
* Terminal.app

The terminal provides the window in which text input and output are displayed.

---

## Shell

The shell is the program running inside that terminal environment that interprets commands.

Examples:

```text
Bash
Zsh
Fish
Dash
```

So when you open a terminal and see:

```text
user@server:~$
```

the terminal is displaying the interface, while a shell such as Bash may be waiting for your command.

---

## Command line

The command line is the text-based way of entering commands.

For example:

```bash
ls -l /var/log
```

That line is a command line.

### Simple mental model

```text
Terminal
   |
   | provides the interface
   v
Shell
   |
   | interprets commands
   v
Operating System
```

A useful analogy is:

```text
Terminal = conversation window

Shell = interpreter processing your instructions

Command line = the instructions you type
```

The analogy is imperfect, but it is useful for getting started.

---

# 4. What Is a Terminal Emulator?

Historically, terminals were physical devices used to communicate with larger computers.

Modern computers normally use software that imitates the behavior of those terminals.

That software is called a **terminal emulator**.

For example, when you open Terminal on macOS or GNOME Terminal on Linux, you are opening a terminal emulator.

The terminal emulator handles things such as:

* displaying text
* accepting keyboard input
* showing command output
* managing terminal sessions
* colors
* fonts
* window dimensions
* keyboard shortcuts

The shell running through it handles command interpretation.

This means changing your terminal application does not necessarily change your shell.

You could use:

```text
Terminal Emulator A
        ↓
       Bash
```

or:

```text
Terminal Emulator B
        ↓
       Bash
```

The terminal changed.

The shell did not.

# 5. Kernel vs Shell

The kernel and shell have very different responsibilities.

## Kernel

The kernel is the core component of the operating system.

It manages resources such as:

* CPU
* memory
* devices
* storage
* processes
* networking
* system calls

Programs generally do not directly control hardware however they want.

They request services from the operating system.

The kernel manages those requests.

---

## Shell

The shell provides a user-oriented command environment.

You might type:

```bash
cat app.log
```

Bash interprets the command and runs the appropriate program. That program ultimately relies on operating-system services to access the file.

A simplified model is:

```text
You
 |
 | cat app.log
 v
Terminal Emulator
 |
 v
Bash
 |
 | launches cat
 v
cat process
 |
 | requests file access
 v
Linux Kernel
 |
 v
Filesystem / Storage
```

So Bash is not the Linux kernel.

And Linux itself is not Bash.

Bash is one program that can run on a Linux system.

**Command-Line Interface**

Imagine needing to perform the same operation on 100 Linux servers.

Clicking through a GUI 100 times is usually impractical.

A script can automate repeated operations.

# 7. Why Do Shells Exist?

An operating system needs ways for users and programs to request actions.

The shell provides a powerful command-oriented interface.

Without a shell, you would need another interface or program every time you wanted to interact with the operating system.

Shells provide:

```text
Human-readable commands
        ↓
Command interpretation
        ↓
Programs and operating-system operations
```

More importantly, shells allow commands to be combined.

For example:

```bash
grep "ERROR" app.log
```

searches for lines containing `ERROR`.

You could then combine commands:

```bash
grep "ERROR" app.log | wc -l
```

Now you are asking the system to:

```text
Read app.log
     ↓
Find ERROR lines
     ↓
Send those lines through a pipe
     ↓
Count them
```

This ability to combine small tools is one reason Unix and Linux command-line environments are so powerful.

# 13. Common Linux Shells

Bash is not the only shell.

Several shells exist.

## Bash

```text
Bash = Bourne Again Shell
```

Bash is widely used on Linux and remains extremely important for scripting, server administration, DevOps, and automation.

This series focuses primarily on Bash.

---

## sh

`sh` historically refers to the Bourne shell, but on modern Unix-like systems `/bin/sh` often refers to a shell providing a more portable, POSIX-oriented shell environment rather than necessarily the original Bourne shell.

For example:

```bash
/bin/sh
```

may point to different implementations depending on the operating system.

On some Linux distributions, it may point to Dash.

On others, it may point to Bash operating in a compatibility-oriented mode.

Therefore, do not automatically assume:

```text
sh = Bash
```

---

## Zsh

Zsh means:

**Z Shell**

It offers many interactive features and customization options.

For example:

* advanced completion
* powerful globbing
* interactive customization
* plugin ecosystems

Recent macOS versions use Zsh as the default interactive shell for new user accounts.

Zsh and Bash share many concepts, but they are not identical languages.

---

## Dash

Dash is a lightweight POSIX-oriented shell.

It is designed to be relatively small and fast.

Some Linux systems use Dash for `/bin/sh`.

A script written specifically for Bash may therefore fail if someone executes it with `sh`.

We will return to this distinction shortly.

---

## Fish

Fish stands for:

**Friendly Interactive Shell**

It emphasizes interactive usability and provides features such as:

* convenient completion
* syntax highlighting
* suggestions

Fish can provide an excellent interactive experience, but its scripting syntax differs significantly from traditional Bourne-style shells.

A Bash script should not be assumed to work as a Fish script.

---

# 14. Bash vs sh

This distinction is extremely important.

You will sometimes see scripts beginning with:

```bash
#!/bin/sh
```

and others:

```bash
#!/bin/bash
```

They do not necessarily mean the same thing.

A script written for `/bin/sh` should generally avoid Bash-specific language features if portability is the goal.

Bash provides additional features beyond basic POSIX shell syntax.

For example, Bash supports features such as:

* arrays
* `[[ ... ]]`
* associative arrays
* Bash-specific parameter expansions
* various extended pattern features

Therefore:

```text
Portable POSIX-style shell script
            ↓
           sh
```

while:

```text
Script intentionally using Bash features
            ↓
          Bash
```

### Beginner rule

If you are learning Bash and intentionally writing Bash scripts, execute them with Bash rather than assuming `sh` means Bash.

For example:

```bash
bash script.sh
```

We will study shebangs and script execution properly in Part 2.

# 15. How to Find Your Current Shell

Try:

```bash
echo "$SHELL"
```

### What does this do?

`echo` displays text.

`$SHELL` refers to the value of the `SHELL` environment variable, which commonly records the user's configured login shell.

You might see:

```text
/bin/bash
```

or:

```text
/bin/zsh
```

Important nuance: `$SHELL` does **not always prove which shell process is executing the command right now**.

For example, your login shell could be Zsh and you could manually start Bash inside it.

For Bash specifically, you can check:

```bash
echo "$BASH_VERSION"
```

If you are currently running Bash, you may see something similar to:

```text
5.2.15(1)-release
```

The exact version depends on your system.

Another useful command is:

```bash
ps -p $$ -o comm=
```

We will understand processes and `$$` much more deeply later in the series.

For now, just know that this can help identify the current shell process.

# 16. Interactive Shells

An **interactive shell** accepts commands directly from a user.

You open a terminal and see a prompt:

```text
user@server:~$
```

You type:

```bash
pwd
```

The shell executes it and displays the result.

Then it waits for another command.

```text
Prompt
 ↓
Command
 ↓
Result
 ↓
Prompt
 ↓
Next command
```

This is interactive usage.

You and the shell are effectively having an ongoing command-response session.

---

# 17. Non-Interactive Shells

A non-interactive shell does not need to wait for you to manually type each command.

This commonly happens when executing scripts.

Suppose `check.sh` contains:

```bash
pwd
whoami
date
```

You run:

```bash
bash check.sh
```

Bash reads the commands from the file and executes them.

Conceptually:

```text
check.sh
   |
   | commands
   v
Bash
   |
   v
Execute commands
```

This distinction becomes important because shell startup behavior and configuration can differ between interactive and non-interactive environments.

It also explains a common production problem:

> The command works when I type it manually, but it fails inside my script or CI/CD pipeline.

Environment differences are often part of the reason.

---

# 18. Login vs Non-Login Shells

This is a separate concept from interactive vs non-interactive.

A **login shell** is a shell started as part of a login session or explicitly instructed to behave as one.

A **non-login shell** is started without that login behavior.

Why does this matter?

Because Bash can read different startup files depending on how it was started.

Files you will encounter later include:

```text
/etc/profile
~/.bash_profile
~/.bash_login
~/.profile
~/.bashrc
```

Do not memorize all of this yet.

For Part 1, remember:

> Interactive/non-interactive describes whether the shell is interacting with a user.

> Login/non-login describes how the shell was started and which startup behavior applies.

These are different dimensions.

A shell can, for example, be interactive and login, or interactive and non-login.

We will examine Bash startup configuration in detail in Part 16.

# 19. How a Command Travels Through the System

Now let's understand what actually happens when you type:

```bash
ls
```

A simplified flow is:

```text
You type: ls
      |
      v
Terminal Emulator
      |
      v
Bash receives "ls"
      |
      v
Bash parses the command
      |
      v
Is it something Bash handles itself?
      |
      +------ Yes ------> Bash executes it
      |
      +------ No -------> Bash searches for a program
                              |
                              v
                           $PATH
                              |
                              v
                      Finds executable
                              |
                              v
                     Starts new process
                              |
                              v
                         Linux Kernel
                              |
                              v
                     System resources
                              |
                              v
                       Output produced
                              |
                              v
                       Terminal displays
```

Real shell execution contains additional details, but this is the correct beginner mental model.

# 20. The Bash Prompt

When using Bash, you may see something similar to:

```text
ann@dev-server:~$
```

A prompt can contain useful information.

For example:

```text
ann@dev-server:~$
 |       |      |
 |       |      +---- location indicator
 |       |
 |       +----------- hostname
 |
 +------------------- username
```

The `$` is commonly used for a normal user's prompt.

A root shell often uses:

```text
#
```

For example:

```text
root@server:~#
```

### Important safety warning

Do not treat `#` as merely cosmetic.

A root shell has extremely powerful permissions.

Commands run as root can potentially:

* delete system files
* change critical permissions
* stop important services
* modify networking
* damage an operating system

Use elevated privileges only when required and when you understand the command.

# 25. Understanding Command Syntax

A typical command can be represented as:

```text
command [options] [arguments]
```

For example:

```bash
ls -l /var/log
```

Break it apart:

```text
ls       -l       /var/log
|        |           |
command  option      argument
```

### Command

```text
ls
```

The program or shell operation you want to execute.

### Option

```text
-l
```

Changes how the command behaves.

For `ls`, `-l` requests a long listing format.

### Argument

```text
/var/log
```

The object the command should operate on.

In this case, it tells `ls` which directory to list.

---

# 26. Options and Flags

You will often hear the words **option** and **flag**.

They are frequently used loosely or interchangeably, although technically an option can sometimes take a value while a flag commonly acts like an on/off switch.

For example:

```bash
ls -a
```

`-a` tells `ls` to include entries that would normally be hidden from a basic listing.

You may also encounter long options:

```bash
ls --all
```

Many commands support both short and long forms.

But not every command follows exactly the same option convention.

That is why reading documentation matters.

---

# 27. Arguments

Arguments provide information to a command.

Consider:

```bash
mkdir devops-lab
```

Breakdown:

```text
mkdir       devops-lab
  |             |
command       argument
```

The command is:

```text
mkdir
```

The argument is:

```text
devops-lab
```

It tells `mkdir` what directory to create.

You can think of the command as the **action** and its arguments as the **targets or data associated with that action**.

# 28. Built-In Commands vs External Programs

Not every command you type is executed the same way.

Some commands are built directly into Bash.

These are called **shell builtins**.

Others are separate executable programs stored somewhere on the filesystem.

---

## Built-in command example

```bash
cd
```

`cd` changes Bash's current working directory.

It needs to affect the shell process itself, so implementing it as a shell builtin makes sense.

Try:

```bash
type cd
```

You may see:

```text
cd is a shell builtin
```

---

## External command example

Try:

```bash
type ls
```

Depending on your environment and aliases, you may see output identifying an executable location or possibly an alias.

For example:

```text
ls is /usr/bin/ls
```

That means an external executable exists at:

```text
/usr/bin/ls
```

---

# 29. Why the Difference Matters

Imagine that every command were automatically assumed to be an external program.

The shell would have to locate and execute a program for every operation.

But shells also have internal operations that need to modify the shell itself.

Examples of common Bash builtins include:

```text
cd
echo
printf
read
export
unset
alias
type
help
```

You do not need to memorize them now.

Instead, learn how to investigate.

# 30. Investigating Commands with `type`

One of the most useful Bash commands for understanding another command is:

```bash
type
```

Try:

```bash
type cd
```

Then:

```bash
type ls
```

Then:

```bash
type echo
```

Then:

```bash
type pwd
```

`type` tells you how Bash would interpret a command name.

A command name might resolve to something such as:

* alias
* function
* builtin
* executable file

This makes `type` particularly useful when troubleshooting surprising shell behavior.

---

# 31. Using `which`

You will also encounter:

```bash
which ls
```

Possible output:

```text
/usr/bin/ls
```

`which` is commonly used to locate an executable that would be found through the current command search path.

However, beginners often rely on `which` for questions it does not answer as completely as Bash's own `type` command.

For Bash troubleshooting, prefer:

```bash
type command_name
```

when you want to understand how Bash resolves that command.

---

# 32. Using `command`

Bash also provides the `command` builtin.

One useful form is:

```bash
command -v ls
```

Possible output:

```text
/usr/bin/ls
```

Try:

```bash
command -v cd
```

You may get:

```text
cd
```

`command -v` is useful for determining whether a command can be found and how it resolves in the shell environment.

For example:

```bash
command -v git
```

If Git is available, you may receive a path such as:

```text
/usr/bin/git
```

If it produces no result, Git may not be available through the current command search environment.

---

# 33. `type` vs `which` vs `command -v`

For now, use this mental model:

| Tool         | Useful question                                                  |
| ------------ | ---------------------------------------------------------------- |
| `type`       | How does Bash interpret this command?                            |
| `which`      | Where is an executable found in the command search path?         |
| `command -v` | Can the shell resolve this command, and what does it resolve to? |

For Bash scripts, `command -v` is commonly useful for dependency checks.

Later, you could write logic conceptually like:

```text
Does docker exist?
       |
   +---+---+
   |       |
  Yes      No
   |       |
Continue   Stop with useful error
```

That is much safer than blindly assuming every required program is installed.

# 39. Introduction to Exit Status

Commands do more than print output.

They also report whether they succeeded or failed.

This is called an **exit status** or **exit code**.

The fundamental convention is:

```text
0       success

non-zero
        some kind of failure or other non-success status
```

The exact meaning of non-zero values depends on the command.

# 41. Why Exit Status Matters

Exit codes are one of the foundations of automation.

Imagine a deployment:

```text
Build application
       |
       v
Did build succeed?
   /         \
 Yes          No
  |            |
  v            v
Deploy      Stop pipeline
```

A CI/CD system cannot simply look at the screen and think:

> That error message looks bad.

Instead, programs communicate success or failure through machine-readable mechanisms such as exit codes.

Later you will write Bash logic such as:

```bash
if some_command; then
    echo "Command succeeded"
else
    echo "Command failed"
fi
```

You do not need to learn the `if` syntax yet.

For now remember:

> Output is information intended to be consumed or displayed.

> Exit status communicates the result of command execution.

They are related, but not the same thing.

# 48. Common Beginner Mistakes

## Mistake 1: Thinking the terminal is Bash

It is not necessarily.

Your terminal emulator can run Bash, Zsh, or another shell.

---

## Mistake 2: Thinking Bash is Linux

Bash is a shell.

Linux refers to the kernel at the core of Linux-based operating systems.

They are not the same thing.

---

## Mistake 3: Assuming `sh` always means Bash

It does not.

On some systems `/bin/sh` may point to another shell implementation.

---

## Mistake 4: Copying commands without understanding the current directory

Before manipulating files, check:

```bash
pwd
```

This simple habit can prevent mistakes.

---

## Mistake 5: Ignoring the current user

Before administrative operations, know which user you are:

```bash
whoami
```

Permissions depend on identity.

---

## Mistake 6: Ignoring the hostname

When multiple remote servers are involved, verify where you are:

```bash
hostname
```

Never assume you are on development when you might actually be on production.

---

## Mistake 7: Assuming visible output determines success

A command's exit status is a separate and important signal.

Check:

```bash
echo $?
```

when learning how a command behaves.

---

## Mistake 8: Using root for everything

Root access is powerful and dangerous.

Do not use elevated privileges simply because a command failed.

First determine **why** it failed.

# 49. Beginner Troubleshooting Lab

Let's deliberately create a harmless failure.

Run:

```bash
ls /definitely-not-a-real-veriqta-directory
```

You should see an error similar to:

```text
ls: cannot access '/definitely-not-a-real-veriqta-directory': No such file or directory
```

## Problem

`ls` could not list the requested directory.

## What did you see?

A “No such file or directory” message.

## Possible cause

The supplied path does not exist.

## How do we investigate?

Check your current location:

```bash
pwd
```

List available files/directories:

```bash
ls
```

Check the exit status of the failed command immediately after rerunning it:

```bash
ls /definitely-not-a-real-veriqta-directory
echo $?
```

The second command should display a non-zero status.

## Correct lesson

Do not respond to every Linux error by adding `sudo`.

This error is not telling you:

```text
You need more privileges.
```

It is telling you that the requested path could not be found.

Understanding the error matters more than blindly changing permissions.

# What You Should Now Understand

After Part 1, you should understand that:

* A shell is a program that provides a command-oriented interface to the operating system.
* Bash is both a shell and a scripting language.
* The terminal emulator and shell are different components.
* The command line is the text-based interface through which commands are entered.
* The kernel manages fundamental operating-system resources.
* CLI and GUI are different interaction models.
* Shells are powerful because commands can be repeated, combined, automated, and executed remotely.
* Bash is widely used across Linux, DevOps, Cloud, SRE, and Platform Engineering.
* Bash, `sh`, Zsh, Dash, and Fish are different shells.
* `sh` should not automatically be treated as another name for Bash.
* Interactive shells accept commands directly from users.
* Non-interactive shells commonly execute scripts or automated commands.
* Login/non-login and interactive/non-interactive describe different shell characteristics.
* The Bash prompt can provide clues about user, hostname, location, and privilege.
* `whoami` identifies the effective user.
* `hostname` identifies the machine.
* `pwd` displays the current working directory.
* Commands can have options and arguments.
* Bash contains built-in commands while other commands may be external executables.
* `type`, `which`, and `command -v` help investigate commands in different ways.
* `help`, `--help`, and `man` provide documentation.
* Successful commands conventionally return exit status `0`.
* Non-zero exit statuses indicate failure or another non-success condition defined by the command.
* Bash scripts turn sequences of shell commands into repeatable automation.
