# Part 10: Building a Production-Style Multi-Tier VPC

Parts 5 through 9 introduced the main building blocks of AWS networking:

* VPCs
* CIDR ranges
* Availability Zones
* Public and private subnets
* Route tables
* Internet Gateways
* NAT Gateways
* Security Groups
* Network ACLs

Now we are going to stop looking at these components separately.

We will combine them into one production-style architecture.

The goal is to understand how an engineer plans, builds, secures, verifies, and troubleshoots a VPC that supports a real application.

The architecture will contain:

* One VPC
* Two Availability Zones
* Two public subnets
* Two private application subnets
* Two private database subnets
* One Internet Gateway
* A public Application Load Balancer
* NAT connectivity for private application servers
* Two application EC2 instances
* Private Amazon RDS
* Separate route tables
* Purpose-specific Security Groups
* Network ACL considerations
* High availability across Availability Zones

AWS itself uses a similar two-AZ pattern in its production VPC guidance, with public load-balancer subnets, private application subnets, NAT connectivity, and resilient workloads distributed across zones.

# 1. The Architecture We Are Building

At a high level:

```text
                              INTERNET
                                 |
                                 v
                        Internet Gateway
                                 |
                                 v
                   Application Load Balancer
                       /                  \
                      /                    \
                     v                      v
             Public Subnet A        Public Subnet B
                 AZ-A                   AZ-B
                     |                      |
                     |                      |
                     v                      v
          Private App Subnet A    Private App Subnet B
                App EC2 A               App EC2 B
                     |                      |
                     \                      /
                      \                    /
                       \                  /
                            Amazon RDS
                     Private DB Subnets
```

But a real design contains more detail.

The complete traffic architecture looks closer to this:

```text
                                  INTERNET
                                     |
                                     |
                              Internet Gateway
                                     |
                    +----------------+----------------+
                    |                                 |
                    v                                 v

             AVAILABILITY ZONE A               AVAILABILITY ZONE B

          +---------------------+             +---------------------+
          | Public Subnet A     |             | Public Subnet B     |
          | 10.0.1.0/24         |             | 10.0.2.0/24         |
          |                     |             |                     |
          | ALB node            |             | ALB node            |
          | NAT Gateway A       |             | NAT Gateway B       |
          +----------+----------+             +----------+----------+
                     |                                   |
                     |                                   |
                     v                                   v
          +---------------------+             +---------------------+
          | Private App A       |             | Private App B       |
          | 10.0.11.0/24        |             | 10.0.12.0/24        |
          |                     |             |                     |
          | EC2 App A           |             | EC2 App B           |
          +----------+----------+             +----------+----------+
                     |                                   |
                     |                                   |
                     +----------------+------------------+
                                      |
                                      v
                          +-----------------------+
                          | Amazon RDS            |
                          | Private DB Subnets    |
                          |                       |
                          | DB Subnet A           |
                          | DB Subnet B           |
                          +-----------------------+
```

This is not the only valid AWS architecture.

It is a strong beginner architecture because it teaches the main production networking patterns clearly.

---

# 2. What Makes This "Production-Style"?

Production-style does not mean:

"This exact diagram must be copied into every company."

It means the architecture follows several principles that are commonly important in production:

* Avoid a single Availability Zone dependency
* Separate internet-facing resources from application workloads
* Keep databases private
* Expose only the load balancer publicly
* Use controlled outbound internet access
* Restrict communication between tiers
* Design routing intentionally
* Understand failure domains
* Verify every traffic path
* Plan for failure before failure happens
* Make the design understandable to other engineers

The architecture should answer:

```text
Who can reach what?
Through which path?
On which port?
Through which route?
What happens if one AZ fails?
What happens if one route is wrong?
What happens if one Security Group changes?
```

If you cannot answer those questions, you do not fully understand the network yet.

# 3. Do Not Start by Clicking "Create VPC"

One of the most important engineering habits is planning before creating resources.

A beginner often does this:

```text
Create VPC
Create subnet
Create another subnet
Create EC2
Create route table
Create NAT
```

Then eventually asks:

```text
Why did I create this?
Which subnet is this?
Which route table belongs here?
```

A better approach is:

```text
Requirements
    |
    v
Architecture
    |
    v
Address plan
    |
    v
Availability design
    |
    v
Security design
    |
    v
Routing design
    |
    v
Resources
```

Infrastructure should be designed before it is deployed.

# 4. Begin With Requirements

Suppose the application requirements are:

* Users access the application over HTTPS
* Users must never connect directly to EC2 instances
* Application servers need outbound internet access
* Application servers connect to PostgreSQL
* Database must not be public
* Application should continue working if one Availability Zone fails
* Database should support high availability
* Administrative access should not require exposing SSH publicly

These requirements drive the network design.

---

# 5. Convert Requirements Into Architecture Decisions

Requirement:

```text
Users need public HTTPS access.
```

Decision:

```text
Use an internet-facing Application Load Balancer.
```

Requirement:

```text
Application EC2 instances should not be directly public.
```

Decision:

```text
Place EC2 in private application subnets.
```

Requirement:

```text
Private EC2 instances need package updates and external API access.
```

Decision:

```text
Provide controlled outbound connectivity through NAT.
```

Requirement:

```text
Database should not be reachable from the internet.
```

Decision:

```text
Place RDS in private database subnets.
```

Requirement:

```text
Application should tolerate an AZ failure.
```

Decision:

```text
Deploy across at least two Availability Zones.
```

Requirement:

```text
Only the application should reach the database.
```

Decision:

```text
Use Security Group references.
```

This is infrastructure reasoning.

# 6. Choose a Region

Before building the VPC, choose an AWS Region.

Example:

```text
us-east-1
```

A Region is a geographic AWS location containing multiple isolated Availability Zones.

Your VPC exists within one Region.

It does not span multiple AWS Regions.

---

# 7. Choose Two Availability Zones

For this architecture:

```text
Availability Zone A
Availability Zone B
```

Conceptually:

```text
us-east-1a
us-east-1b
```

Remember that AZ letter mappings can differ between AWS accounts.

The important architectural idea is:

```text
Two independent Availability Zones
```

rather than the literal letters.

AWS recommends distributing workloads across multiple Availability Zones because each subnet exists entirely within one AZ, and multi-AZ placement helps protect applications from a single-zone failure.

---

# 8. Understanding Failure Domains

An Availability Zone is an important failure domain.

A failure domain is a portion of infrastructure that could fail together.

If everything runs in:

```text
AZ-A
```

then an AZ-A failure may take everything down.

Example:

```text
AZ-A

ALB
EC2
Database
NAT
```

This is a large shared failure dependency.

Instead:

```text
AZ-A                   AZ-B

ALB node               ALB node
EC2 A                  EC2 B
NAT A                  NAT B
DB infrastructure      DB infrastructure
```

A failure affecting one zone should not necessarily destroy the complete service.

---

# 9. High Availability Does Not Mean "Two Servers"

This is an important misconception.

Suppose you run:

```text
EC2 A
EC2 B
```

but both exist in:

```text
AZ-A
```

You have two servers.

You do not have meaningful AZ-level redundancy.

Better:

```text
EC2 A
AZ-A
```

and:

```text
EC2 B
AZ-B
```

Now one Availability Zone can fail while the other remains available.




```text

```

Good IP planning improves operations and troubleshooting.

# 13. Subnet Plan

Our network plan:

| Tier        | Availability Zone A | Availability Zone B |
| ----------- | ------------------- | ------------------- |
| Public      | 10.0.1.0/24         | 10.0.2.0/24         |
| Application | 10.0.11.0/24        | 10.0.12.0/24        |

---

# 14. Public Subnets

The public subnets will contain internet-facing networking resources.

For this design:

```text
Application Load Balancer nodes
NAT Gateway
```

The public subnet route table will include:

```text
0.0.0.0/0 → Internet Gateway
```

That is what gives the subnet a direct route toward the Internet Gateway.

---

# 15. Private Application Subnets

Application EC2 instances will live here.

They will:

* Have private IPv4 addresses
* Not require public IPv4 addresses
* Receive application traffic from the ALB
* Connect to RDS
* Reach the internet through NAT when required

Their route tables will contain:

```text
0.0.0.0/0 → NAT Gateway
```

not:

```text
0.0.0.0/0 → Internet Gateway
```

---

# 16. Private Database Subnets

RDS will use separate database subnets.

Database subnets should not need a default route to the public internet for normal application connectivity.

Their purpose is to provide isolated placement for database infrastructure.

AWS requires RDS DB subnet groups to cover at least two Availability Zones for normal DB instance deployments, which is why we create DB subnet A and DB subnet B.

---

# 17. Why Separate App and Database Subnets?

You could technically place:

```text
EC2
RDS
```

inside the same private subnet.

But separation provides clearer architecture.

It helps you apply different:

* Routing policies
* NACL policies
* Operational controls
* Security expectations
* IP planning

Conceptually:

```text
Application Zone
```

and:

```text
Database Zone
```

have different purposes.

---

# 18. Internet Gateway

The Internet Gateway connects the VPC to the public internet routing environment.

Create one Internet Gateway and attach it to the VPC.

Conceptually:

```text
Internet
   |
   v
Internet Gateway
   |
   v
VPC
```

An Internet Gateway attaches to the VPC, not individually to every subnet.

Subnets gain internet routing through route-table entries.

---

# 19. Public Route Table

Create a public route table.

Example:

```text
Name:
prod-public-rt
```

Routes:

```text
Destination       Target

10.0.0.0/16       local
0.0.0.0/0         Internet Gateway
```

Associate:

```text
Public Subnet A
Public Subnet B
```

The local route allows communication within the VPC.

The default route provides the public internet path.

---

# 20. NAT Gateway Design

Private application servers need outbound connectivity.

For production resilience using zonal NAT Gateways, AWS recommends deploying a NAT Gateway in each active Availability Zone and routing each private subnet through the NAT Gateway in the same AZ.

Therefore:

```text
Public Subnet A
    |
NAT Gateway A
```

and:

```text
Public Subnet B
    |
NAT Gateway B
```

---

# 21. Why Two NAT Gateways?

Suppose both private application subnets use:

```text
NAT Gateway A
```

Architecture:

```text
App A ----\
           \
            NAT A
           /
App B ----/
```

If AZ-A becomes unavailable:

```text
NAT A
```

may become unavailable.

Then App B in AZ-B could lose outbound internet connectivity even though App B itself remains healthy.

AWS specifically warns about this zonal dependency.

A stronger zonal design:

```text
App A → NAT A

App B → NAT B
```

# 26. Application Load Balancer

The Application Load Balancer will be the application's public entry point.

It should be internet-facing.

It spans public subnets across at least two Availability Zones.

Architecture:

```text
Internet
   |
   v
Application Load Balancer
   |
   +--------+
   |        |
 AZ-A      AZ-B
```

The ALB distributes application requests to registered targets.

---

# 27. Why Put EC2 Behind the Load Balancer?

Without a load balancer:

```text
Internet
   |
EC2 public IP
```

Users become dependent on one server.

With an ALB:

```text
Internet
   |
ALB
 / \
EC2 A
EC2 B
```

The load balancer can:

* Distribute traffic
* Perform health checks
* Stop routing to unhealthy targets
* Support multiple Availability Zones
* Terminate HTTPS
* Provide a stable application endpoint
* Support future Auto Scaling

---

# 28. Application EC2 Placement

Launch:

```text
App EC2 A
```

inside:

```text
Private App Subnet A
```

and:

```text
App EC2 B
```

inside:

```text
Private App Subnet B
```

Do not assign public IPv4 addresses.

Conceptually:

```text
Internet
   |
ALB
   |
Private EC2
```

The EC2 instances do not need to be internet-facing.

# 29. Database Placement

Amazon RDS should use:

```text
Private DB Subnet A
Private DB Subnet B
```

through a DB subnet group.

A DB subnet group is a collection of subnets RDS can use for database placement.

AWS requires a DB subnet group for a DB instance to contain subnets in at least two Availability Zones.

---

# 30. RDS High Availability

For stronger availability, configure an RDS Multi-AZ deployment where appropriate.

A standard Multi-AZ DB instance deployment maintains a standby in another Availability Zone for failover.

The standby is not simply another application read server in the traditional Multi-AZ DB instance design. Its primary role is availability and failover.

Conceptually:

```text
AZ-A                      AZ-B

Primary RDS      <---->   Standby RDS
```

If the primary experiences certain failures, RDS can fail over.

---

# 31. Do Not Confuse Multi-AZ With Read Scaling

High availability and read scaling are different goals.

Traditional RDS Multi-AZ:

```text
Primary
   |
Standby
```

primarily improves availability.

Read replica:

```text
Primary
   |
   +---- Read Replica
```

primarily supports read scaling and other use cases.

Always understand the service behavior rather than assuming:

```text
more database copies = same purpose
```

# 33. ALB Security Group

Example inbound rules:

```text
HTTPS
TCP 443
Source:
0.0.0.0/0
```

Optional:

```text
HTTP
TCP 80
Source:
0.0.0.0/0
```

if HTTP redirects to HTTPS.

The ALB is intentionally public.

---

# 34. Application Security Group

Suppose the application listens on:

```text
8080
```

Inbound:

```text
Custom TCP
TCP 8080
Source:
prod-alb-sg
```

This means only traffic from the ALB tier can reach the application port.

Not:

```text
8080 from 0.0.0.0/0
```

The application tier does not need direct public exposure.

---

# 35. Database Security Group

For PostgreSQL:

```text
PostgreSQL
TCP 5432
Source:
prod-app-sg
```

For MySQL:

```text
MySQL
TCP 3306
Source:
prod-app-sg
```

The database accepts application traffic only from the application tier.

---

# 36. Administrative Access

Avoid this:

```text
SSH 22
Source:
0.0.0.0/0
```

for private EC2 administration.

Possible production approaches include:

* AWS Systems Manager Session Manager
* VPN
* Controlled bastion host
* Private enterprise connectivity

For this architecture, Session Manager is a useful approach because EC2 does not need a public IP simply for administration.

---

# 37. Network ACL Considerations

Do not automatically create highly restrictive custom NACLs simply because this is a production-style architecture.

Security Groups should remain the primary fine-grained network control.

NACLs can provide additional subnet-level guardrails.

Possible groups:

```text
public-nacl
app-nacl
database-nacl
```

But complexity must be justified.

---

# 38. Public NACL Considerations

Public subnets may require:

* HTTPS inbound
* Optional HTTP inbound
* ALB return traffic
* NAT traffic
* Ephemeral ports
* Appropriate outbound traffic

Remember:

NACLs are stateless.

Every connection must be considered in both directions.

---

# 39. Application NACL Considerations

Application subnets need communication from:

```text
ALB
```

toward the application port.

They may also need outbound access to:

```text
RDS
NAT
AWS services
external APIs
```

Return traffic must also work.

---

# 40. Database NACL Considerations

Database subnets can be more restrictive.

Conceptually:

```text
Application subnets
       |
       | database port
       v
Database subnets
```

A database NACL might restrict broad network ranges.

But Security Group references provide the more precise workload-level rule.

---

# 41. Defense in Depth

The database is protected through several layers.

First:

```text
No public route
```

Second:

```text
Private database subnets
```

Third:

```text
Security Group:
5432 only from app-sg
```

Potential fourth layer:

```text
NACL restrictions
```

Fifth:

```text
Database authentication
```

Sixth:

```text
TLS
```

Seventh:

```text
Secrets management
```

This is defense in depth.

# 42. Build Order

Do not create resources randomly.

A logical build order is:

1. VPC
2. Subnets
3. Internet Gateway
4. Route tables
5. NAT Gateways
6. Security Groups
7. DB subnet group
8. Application EC2 instances
9. RDS
10. Target group
11. Application Load Balancer
12. DNS later with Route 53
13. Monitoring later with CloudWatch

Each resource depends on previous networking decisions.

# 75. Complete Inbound Traffic Flow

Now follow one user request.

User opens:

```text
https://app.example.com
```

Traffic:

```text
User
 |
 | HTTPS 443
 v
Internet
 |
 v
Internet Gateway
 |
 v
Public ALB
 |
 | App port 8080
 v
Private App EC2
```

Let's examine each step.

---

# 76. Step 1: User Reaches the Public Endpoint

The user resolves the application's public hostname.

The destination eventually leads to the internet-facing ALB.

The ALB's Security Group checks:

```text
TCP 443 from internet?
```

Rule matches:

```text
443 from 0.0.0.0/0
```

Traffic is allowed.

---

# 77. Step 2: ALB Selects a Healthy Target

The load balancer checks the target group.

Suppose:

```text
App A = Healthy
App B = Healthy
```

The ALB selects a healthy application target.

---

# 78. Step 3: ALB Connects to Application

The ALB sends:

```text
TCP 8080
```

to App A or App B.

The application Security Group checks:

```text
Source = prod-alb-sg?
Port = 8080?
```

Yes.

Traffic is allowed.

---

# 79. Step 4: Application Processes the Request

The application may need database information.

It connects to:

```text
RDS endpoint
```

on:

```text
5432
```

for PostgreSQL.

---

# 80. Step 5: Database Security Group Checks

The DB Security Group asks:

```text
Source = prod-app-sg?
Port = 5432?
```

Yes.

The database connection is allowed.

---

# 81. Step 6: Response Travels Back

RDS responds to the application.

Application responds to ALB.

ALB responds to the user.

Security Groups are stateful, so established response traffic is automatically handled according to that connection state.

---

# 82. Outbound Application Traffic

Suppose App A needs:

```bash
sudo apt update
```

Traffic path:

```text
App EC2 A
   |
Private App Subnet A
   |
App Route Table A
   |
0.0.0.0/0 → NAT A
   |
NAT Gateway A
   |
Public Subnet A
   |
Internet Gateway
   |
Internet
```

App B uses NAT B.

---

# 83. Database Traffic Does Not Need NAT

Suppose App A connects to RDS:

```text
10.0.11.x
    |
    v
RDS private address
10.0.21.x
```

Both addresses are within:

```text
10.0.0.0/16
```

The route:

```text
10.0.0.0/16 → local
```

matches.

Traffic stays inside the VPC.

NAT is not involved.

---

# 84. Internet Gateway Is Not Used for App-to-Database Traffic

Another critical point:

```text
App EC2
  |
  v
RDS
```

does not travel through:

```text
Internet Gateway
```

because both resources are inside the VPC.

The VPC-local route handles the path.

---

# 85. NAT Is Not Used for Inbound User Requests

User traffic:

```text
Internet
   |
ALB
   |
Application
```

does not enter through NAT.

NAT serves the outbound path for private workloads.

The ALB handles public application ingress.

These are separate functions.

# 87. High Availability Analysis

Now ask:

What happens if:

```text
App EC2 A
```

fails?

The ALB health check marks it unhealthy.

Traffic can continue to:

```text
App EC2 B
```

Assuming B remains healthy.

---

# 88. What Happens If AZ-A Fails?

Potentially unavailable:

```text
Public Subnet A
NAT A
App Subnet A
App EC2 A
DB resources in AZ-A
```

Still available:

```text
Public Subnet B
NAT B
App Subnet B
App EC2 B
other healthy DB resources
```

This is the reason for spreading infrastructure across failure domains.

---

# 89. Why NAT Per AZ Matters Here

If App B depended on:

```text
NAT A
```

an AZ-A outage could break outbound connectivity for App B.

AWS recommends same-AZ NAT routing to avoid this dependency.

---

# 90. High Availability Has Multiple Layers

Application availability includes:

```text

```

plus:

```text
Compute across AZs
```

plus:

```text

```

plus:

```text
Outbound connectivity
```

plus:

```text
DNS
```

plus:

```text
Application design
```

Two EC2 instances alone do not make the complete system highly available.

---

# 91. Stateless Application Design

Suppose:

```text
User session
```

exists only in memory on App A.

The next request goes to App B.

App B does not know about the session.

Now load balancing causes application problems.

This is why scalable application tiers often aim to be stateless or store shared state externally.

Examples:

* Database
* Redis
* Shared session service
* Object storage

Networking can distribute traffic.

The application must still support distributed operation.

# 107. Breaking the Architecture Intentionally

A good engineer should not only know how to create a working system.

You should understand how it fails.

We will intentionally break several components.

Then troubleshoot without guessing.

---

# 108. Failure 1: Remove the Public Default Route

Remove:

```text
0.0.0.0/0 → IGW
```

from:

```text
prod-public-rt
```

Expected effects:

* Public internet path breaks
* ALB internet accessibility may fail
* NAT internet connectivity fails

Why?

Both public ingress and traditional public NAT egress depend on the Internet Gateway path.

Restore the route afterward.

---

# 109. Failure 2: Break App A NAT Route

Change:

```text
0.0.0.0/0 → NAT A
```

or remove it.

From App A:

```bash
curl https://example.com
```

fails.

But internal communication to:

```text
10.0.0.0/16
```

may still work because the local VPC route remains.

This distinction is important.

---

# 110. Failure 3: Verify App B Still Works

If App B uses its own NAT Gateway:

```text
App B → NAT B
```

its internet access should remain unaffected when only App A's NAT path is broken.

This demonstrates failure isolation.

---

# 111. Failure 4: Remove ALB-to-App Security Rule

Remove:

```text
TCP 8080
Source:
prod-alb-sg
```

from `prod-app-sg`.

Expected:

```text
Targets become unhealthy
```

User requests eventually fail.

The route tables are still correct.

This demonstrates the difference between:

```text
routing
```

and:

```text
security filtering
```

---

# 112. Failure 5: Restore the Security Group

Add:

```text
TCP 8080
Source:
prod-alb-sg
```

back.

Watch target health recover.

Do not stop at:

```text
rule restored
```

Verify:

```text
Target:
Healthy
```

and:

```text
Application request:
Successful
```

---

# 113. Failure 6: Stop the Application

On App A:

```bash
sudo systemctl stop myapp
```

or stop the appropriate container/process.

Now the Security Group remains correct.

Networking remains correct.

But the health check fails.

This teaches:

```text
Network reachable
```

does not mean:

```text
Application healthy
```

---

# 114. Failure 7: Bind the Application to localhost

Suppose the application listens only on:

```text
127.0.0.1:8080
```

The ALB cannot reach it through the EC2 private network interface.

Check:

```bash
sudo ss -ltnp
```

If you see:

```text
127.0.0.1:8080
```

instead of an appropriate interface:

```text
0.0.0.0:8080
```

or private address,

the problem is application binding.

Opening more Security Group rules does not fix it.

---

# 115. Failure 8: Break the Database Security Group

Remove:

```text
TCP 5432
Source:
prod-app-sg
```

Application logs may show:

```text
database connection timeout
```

Restore the rule.

Verify application-to-database connectivity again.

---

# 116. Failure 9: Use Wrong Database Credentials

Now deliberately use a wrong password.

You may see:

```text
authentication failed
```

Do not change Security Groups.

This demonstrates:

```text
Network failure
```

versus:

```text
Authentication failure
```

The error message provides evidence.

---

# 117. Failure 10: Wrong Route Table Association

Associate:

```text
prod-app-a
```

with the wrong route table in a controlled lab.

For example:

```text
prod-db-rt
```

Now App A loses its NAT route.

This is one of the most realistic AWS networking errors.

The route itself may exist in AWS.

The problem is:

```text
Wrong subnet association
```

---

# 118. Failure 11: Wrong NAT Gateway

Point App B to:

```text
NAT A
```

instead of:

```text
NAT B
```

The connection may still work.

But the architecture has lost zonal independence and may incur cross-AZ traffic.

Not every architectural error creates an immediate outage.

Some create hidden resilience and cost problems.

---

# 119. Failure 12: Restrictive NACL

Create a controlled NACL rule that blocks application traffic.

Security Groups remain correct.

Routes remain correct.

Application stops receiving connections.

This teaches why NACLs must be checked when Security Groups look correct.

---

# 120. Failure 13: Break Return Traffic

Create a restrictive NACL that permits the request but blocks appropriate return traffic.

The connection fails because NACLs are stateless.

This is especially useful for understanding ephemeral ports.

---

# 121. Failure 14: Bad Health Check Path

Suppose ALB checks:

```text
/health
```

but your application only responds on:

```text
/
```

The target becomes unhealthy even though:

```text
curl http://localhost:8080/
```

works.

Check health-check configuration before changing network security.

---

# 122. Failure 15: Wrong Target Port

Target group:

```text
Port 8080
```

Application:

```text
Port 3000
```

Targets fail.

Again, networking architecture may be correct.

The target configuration is wrong.

# 135. Architecture Review

Before calling this production-ready, ask:

## Network

* Is the CIDR plan documented?
* Are subnets correctly separated?
* Are two AZs used?
* Are route-table associations correct?

## Security

* Is only the ALB public?
* Are application instances private?
* Is RDS private?
* Are Security Group references used?
* Are administrative ports restricted?
* Are NACLs justified?

## Availability

* Are app instances in two AZs?

* Does each application subnet have a resilient outbound path?

* Are logs enabled?
* Is monitoring configured?
* Are backups configured?
* Is there a recovery plan?
* Are resources tagged?
* Is cost monitoring enabled?

# 141. Answers

## Answer 1

Planning defines the address space, subnet structure, security boundaries, availability model, routing, and dependencies before resources are created. This reduces accidental complexity and design mistakes.

## Answer 2

Two Availability Zones reduce dependency on a single AZ and allow workloads to remain available when one zone or resources inside it fail.

## Answer 3

A failure domain is a portion of infrastructure that may fail together.

## Answer 4

They do not need direct public exposure. Users should reach the application through the load balancer.

## Answer 5

The internet-facing ALB requires public network connectivity.

## Answer 6

Their associated route table contains a direct route to the Internet Gateway.

## Answer 7

Private application servers may still need outbound access for software updates, dependencies, external APIs, and similar operations.

## Answer 8

It reduces cross-AZ dependency and improves zonal resilience for outbound connectivity.

## Answer 9

No.

RDS traffic remains inside the VPC.

## Answer 10

No.

Internal VPC routing handles the connection.

## Answer 11

The VPC `local` route.

## Answer 12

Separation creates clearer security, routing, operational, and address-management boundaries.

## Answer 13

RDS requires subnet coverage across multiple Availability Zones and can use that placement for multi-AZ designs.

## Answer 14

The intended public application ports, usually HTTPS 443 and optionally HTTP 80.

## Answer 15

Only the application port from the ALB Security Group, plus any other justified communication.

## Answer 16

Only the required database port from the application Security Group.

## Answer 17

That would unnecessarily expose the database port to all IPv4 internet sources if a public path also existed.

## Answer 18

The load balancer can continue routing requests to App B if it remains healthy.

## Answer 19

The ALB uses health information to decide which targets should receive traffic.

## Answer 20

Remote systems such as the ALB cannot normally connect through the server's private interface because the application only listens on local loopback.

## Answer 21

Security Groups control network permission. They cannot start an application process or make it respond correctly.

## Answer 22

Those four properties define the network flow you are actually trying to troubleshoot.

## Answer 23

Routes belong to subnet associations. A perfect route table is useless to a subnet that is not actually associated with it.

## Answer 24

NACLs are stateless, so requests and responses must independently satisfy appropriate rules.

## Answer 25

Infrastructure as code makes the architecture repeatable, reviewable, version-controlled, consistent, and automatable.

# 142. Final Mental Model

Do not think of the VPC as:

```text
VPC
Subnets
NAT
Routes
Security Groups
```

as unrelated AWS resources.

Think of it as a system.

```text
                          INTERNET
                             |
                             v
                       PUBLIC ENTRY
                             |
                             v
                         LOAD BALANCER
                             |
                    +--------+--------+
                    |                 |
                    v                 v
                 APP A             APP B
                  AZ-A               AZ-B
                    |                 |
                    +--------+--------+
                             |
                             v
                         DATABASE
```

Now add routing:

```text
Internet
   |
IGW
   |
Public Route Table
   |
ALB
```

Private egress:

```text
App A
   |
App Route A
   |
NAT A
   |
IGW
```

and:

```text
App B
   |
App Route B
   |
NAT B
   |
IGW
```

Internal database path:

```text
App
   |
VPC Local Route
   |
RDS
```

Now add security:

```text
Internet
   |
443
   |
ALB SG
   |
8080
   |
App SG
   |
5432
   |
DB SG
```

Now add availability:

```text
AZ-A                     AZ-B

Public A                 Public B
NAT A                    NAT B
App A                    App B
DB subnet A              DB subnet B
```

This is the point where AWS networking starts to become architecture rather than memorization.

You should no longer see:

```text
VPC
Subnet
Route Table
Internet Gateway
NAT Gateway
Security Group
RDS
ALB
```

as isolated services.

You should see a packet.

You should be able to ask:

```text
Where did it originate?
Where is it going?
What route will match?
Which security rule must allow it?
Which subnet does it cross?
Which Availability Zone owns the dependency?
Does NAT participate?
Does the Internet Gateway participate?
What happens on the return path?
What fails if this component disappears?
```

That is the thinking pattern a DevOps, cloud, platform, infrastructure, or SRE engineer needs.
