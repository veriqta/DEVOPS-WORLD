# Part 5: Working With Files and the Staging Area

In Part 4, you learned Git’s internal workflow:

```text
HEAD
Current committed snapshot
        |
        v
INDEX / STAGING AREA
Proposed next snapshot
        |
        v
WORKING TREE
Current files on disk
```

You also learned that a file can be:

```text
Untracked
Modified
Staged
Committed
```

Now we will work directly with those states.

This part is where the staging area becomes practical.

You will learn how to:

* Track new files
* Modify tracked files
* Stage one file
* Stage several files
* Use `git add .`
* Use `git add -A`
* Understand partial staging
* Inspect unstaged changes with `git diff`
* Inspect staged changes with `git diff --staged`
* Read Git diff output
* Remove tracked files
* Use `git rm`
* Rename and move files
* Use `git mv`
* Unstage changes
* Restore working-tree files
* Understand when data may be recoverable
* Avoid common staging mistakes

The goal is not to stage everything quickly.

The goal is to learn how to control exactly what enters your next commit.

---

# 1. Start With the Core Mental Model

Before doing anything, remember:

```text
HEAD
Last committed state

INDEX
What you plan to commit next

WORKING TREE
What currently exists on disk
```

Most commands in this part affect one of these relationships.

For example:

```text
git add
```

updates the staging area.

```text
git diff
```

normally compares the working tree against the staging area.

```text
git diff --staged
```

compares the staging area against the current commit.

```text
git restore
```

can restore content into the working tree.

This is why understanding Git state matters more than memorizing commands.

# 3. Tracking New Files

A newly created file is normally untracked.

Example:

```text
Untracked files:
  README.md
  app.py
  config.yml
```

This means:

```text
File exists
+
Git can see it
+
It has not entered tracked history
```

At this stage, Git will not automatically include the file in a commit.

You must stage it.

---

# 4. Stage Your First New File

Run:

```bash
git add README.md
```

Then:

```bash
git status
```

You should now see something similar to:

```text
Changes to be committed:
  new file: README.md

Untracked files:
  app.py
  config.yml
```

The file has moved conceptually from:

```text
Untracked
```

to:

```text
Staged
```

The current content of `README.md` is now prepared for the next commit.

---

# 5. Tracking Does Not Mean "Git Watches Every Future Edit Automatically"

Once a file has been committed, Git considers it tracked.

But later modifications still need to be staged if you want them included in a new commit.

Think:

```text
New file
   |
   | git add
   v
Staged
   |
   | git commit
   v
Tracked
   |
   | edit
   v
Modified
   |
   | git add
   v
Staged again
```

So "tracked" does not mean:

```text
every future change is automatically committed
```

It means Git knows this file as part of repository history.

Expected:

# 7. Modifying a Tracked File

Edit:

```text
app.py
```

Change:

```python
print("Application started")
```

to:

```python
print("VERIQTA application started")
```

Save it.

Now run:

```bash
git status
```

You should see something resembling:

```text
Changes not staged for commit:
  modified: app.py
```

Why?

Because Git already has a committed version of `app.py`.

The working-tree version now differs from the staged and committed versions.

Conceptually:

```text
HEAD
old app.py

INDEX
old app.py

WORKING TREE
new app.py
```

Therefore:

```text
Modified
```

---

# 8. What Does Modified Really Mean?

Modified means:

> A tracked file in the working tree differs from the version currently represented in the index.

At this moment:

```text
HEAD        A
INDEX       A
WORKING     B
```

Git can detect that:

```text
A != B
```

The change exists, but it has not been prepared for a commit.

# 9. Staging an Individual File

Stage only:

```text
app.py
```

using:

```bash
git add app.py
```

Then:

```bash
git status
```

Now:

```text
Changes to be committed:
  modified: app.py
```

Conceptually:

```text
HEAD        A
INDEX       B
WORKING     B
```

The new version has been copied into the index.

# 10. Why Stage Individual Files?

Imagine you modify:

```text
app.py
README.md
config.yml
```

but the changes serve different purposes.

For example:

```text
app.py
Fix application startup

README.md
Document setup steps

config.yml
Experimental configuration
```

You may want to commit only the application fix.

Then:

```bash
git add app.py
```

lets you prepare only that change.

This creates cleaner commits.

# 11. Staging Multiple Files Explicitly

You can stage multiple files in one command:

```bash
git add README.md app.py
```

This means:

> Stage the current content of both of these paths.

You can include more:

```bash
git add README.md app.py config.yml
```

This is useful when you know exactly which files belong together.

---

# 12. Why Explicit Staging Is Good for Beginners

Compare:

```bash
git add README.md app.py
```

with:

```bash
git add .
```

The first command is very explicit.

You know exactly what you are staging.

The second command may stage more than you expect depending on what changed beneath the current directory.

For beginners, explicit staging builds good habits.

---

# 13. Understanding git add .

You will use this command frequently:

```bash
git add .
```

The dot:

```text
.
```

represents the current directory.

So conceptually:

```bash
git add .
```

means:

> Update the staging area using relevant changes under the current path.

If your current directory contains:

```text
app.py
README.md
config.yml
src/
```

then changes under that current directory may be staged.

This includes new and modified files, and modern Git behavior also accounts for removals within the path scope.

---

# 14. The Current Directory Matters

Suppose your repository is:

```text
project/
├── README.md
├── app.py
└── config/
    ├── dev.yml
    └── prod.yml
```

If you are at:

```text
project/
```

and run:

```bash
git add .
```

Git considers changes under the whole project path.

But if you first run:

```bash
cd config
```

and then:

```bash
git add .
```

you are staging changes under:

```text
config/
```

not necessarily every change elsewhere in the repository.

This is why:

```bash
pwd
```

and:

```bash
git status
```

matter before broad staging.

---

# 15. Example of git add .

Suppose:

```text
README.md      modified
app.py         modified
config.yml     new
```

You run:

```bash
git add .
```

from the repository root.

Then:

```bash
git status
```

may show all relevant changes as staged.

Conceptually:

```text
WORKING TREE

README.md      B
app.py         B
config.yml     new

      |
      | git add .
      v

INDEX

README.md      B
app.py         B
config.yml     new
```

---

# 16. The Danger of git add .

Imagine your working tree also contains:

```text
.env
debug.log
temp.txt
credentials.txt
```

If those files are not ignored, broad staging may include them.

That can be dangerous.

For example:

```text
.env
```

might contain:

```text
DATABASE_PASSWORD=...
API_TOKEN=...
```

If you stage and commit those values, they may enter repository history.

This is why the correct habit is:

```text
git status
```

before:

```bash
git add .
```

and again afterward.

---

# 17. Understanding git add -A

Another common command is:

```bash
git add -A
```

`-A` means:

```text
--all
```

Conceptually, this tells Git to update the index to reflect changes across the repository.

That includes:

```text
new files
modified files
deleted tracked files
```

Think:

```text
Working tree state
        |
        | git add -A
        v
Index updated comprehensively
```

---

# 18. git add . vs git add -A

For many everyday operations, especially when run at the repository root, the results may appear similar.

But there is an important conceptual distinction.

```bash
git add .
```

is path-based.

The dot means:

```text
current directory
```

while:

```bash
git add -A
```

asks Git to update the index across the repository.

A useful beginner rule is:

```text
git add specific-file
```

for precise staging.

```text
git add .
```

for changes beneath your current location.

```text
git add -A
```

when you deliberately want all repository changes reflected in the index.

---

# 19. Which Should You Use?

For careful work:

```bash
git add app.py
```

is safest and clearest.

For a small, well-understood repository:

```bash
git add .
```

may be convenient.

For intentionally staging every repository change:

```bash
git add -A
```

is explicit.

But no matter which one you use:

```bash
git status
```

should verify the result before committing.

---

# 20. Practical Comparison

Suppose the repository contains:

```text
README.md       modified
app.py          modified
old.conf        deleted
new.conf        untracked
```

Running:

```bash
git add -A
```

is intended to update the index to reflect all of those changes.

Then:

```bash
git status
```

might show:

```text
Changes to be committed:
  modified: README.md
  modified: app.py
  deleted: old.conf
  new file: new.conf
```

The index now represents the proposed next project state.

---

# 21. Partial Staging Introduction

Sometimes one file contains several unrelated changes.

Suppose:

```text
app.py
```

contains:

```text
Change A:
Fix login error

Change B:
Add new debug logging
```

You might not want both changes in the same commit.

Staging the entire file with:

```bash
git add app.py
```

would stage both.

Git supports partial staging.

One common command is:

```bash
git add -p
```

The `-p` means:

```text
patch
```

This allows you to review groups of changes and choose which ones to stage.

---

# 22. Why Partial Staging Exists

Imagine one file contains:

```text
Bug fix
+
Documentation cleanup
+
Experimental code
```

Instead of creating one messy commit, partial staging can help separate them.

Conceptually:

```text
app.py

Change A
Change B
Change C

      |
      | partial staging
      v

INDEX

Change A
Change B

WORKING TREE STILL HAS

Change C
```

This gives you much more control over commit quality.

---

# 23. Basic git add -p Experience

Run:

```bash
git add -p
```

Git may display a section of changes and ask something similar to:

```text
Stage this hunk [y,n,q,a,d,...]?
```

A **hunk** is a grouped section of changes.

At the beginner level:

```text
y
```

means stage this hunk.

```text
n
```

means do not stage this hunk.

```text
q
```

means stop.

There are more options, but you do not need to memorize them yet.

Use:

```text
?
```

when offered to see help.

---

# 24. Partial Staging Is Powerful but Requires Attention

Do not use:

```bash
git add -p
```

blindly.

Read each change carefully.

Partial staging can create commits containing only some modifications from a file.

This is useful, but if changes depend on each other, you could create a commit that does not work independently.

Always consider:

> Does this staged subset still represent a valid change?

---

# 25. Inspecting Changes Before Staging

Now we introduce one of Git's most useful commands:

```bash
git diff
```

Suppose you edit `app.py`.

Before staging, run:

```bash
git diff
```

Git shows differences between the working tree and the staging area.

Conceptually:

```text
INDEX
   |
   | compare
   v
WORKING TREE
```

This means:

```text
What have I changed but not staged yet?
```

---

# 26. git diff in the Three-State Model

Remember:

```text
HEAD
 |
 v
INDEX
 |
 v
WORKING TREE
```

Default:

```bash
git diff
```

compares:

```text
INDEX
vs
WORKING TREE
```

So if:

```text
HEAD        A
INDEX       A
WORKING     B
```

`git diff` shows:

```text
A -> B
```

because that is the unstaged change.

---

# 27. Example of git diff

Suppose `config.yml` was:

```yaml
port: 8080
```

You change it to:

```yaml
port: 9090
```

Run:

```bash
git diff
```

You may see output resembling:

```diff
-port: 8080
+port: 9090
```

This tells you:

```text
old line removed
new line added
```

The change is currently unstaged.

---

# 28. What Happens After git add?

Run:

```bash
git add config.yml
```

Then:

```bash
git diff
```

You may now see no output for that change.

Why?

Because:

```text
INDEX
```

and:

```text
WORKING TREE
```

now match.

Conceptually:

```text
HEAD        A
INDEX       B
WORKING     B
```

Default `git diff` compares:

```text
B vs B
```

so there is nothing to show.

But the change has not disappeared.

It is staged.

---

# 29. Inspecting Staged Changes

To inspect staged changes, use:

```bash
git diff --staged
```

You may also encounter:

```bash
git diff --cached
```

For beginner purposes, they serve the same common use case here.

`git diff --staged` compares:

```text
HEAD
vs
INDEX
```

Conceptually:

```text
HEAD
   |
   | git diff --staged
   v
INDEX
```

This answers:

> What will my next commit change compared with the current commit?

---

# 30. The Two Most Important Diff Comparisons

Remember:

```bash
git diff
```

means:

```text
What is changed but not staged?
```

while:

```bash
git diff --staged
```

means:

```text
What is staged for the next commit?
```

The model:

```text
HEAD
  |
  | git diff --staged
  v
INDEX
  |
  | git diff
  v
WORKING TREE
```

This diagram is extremely important.

---

# 31. Recommended Pre-Commit Workflow

Before committing:

```bash
git status
```

Then inspect unstaged changes:

```bash
git diff
```

Inspect staged changes:

```bash
git diff --staged
```

Then, only when satisfied:

```bash
git commit -m "Meaningful message"
```

This produces a strong habit:

```text
Change
 |
 v
Inspect
 |
 v
Stage
 |
 v
Inspect staged result
 |
 v
Commit
```

---

# 32. Reading a Git Diff

Git diff output can look intimidating.

Example:

```diff
diff --git a/config.yml b/config.yml
index 12ab345..67cd890 100644
--- a/config.yml
+++ b/config.yml
@@ -1,2 +1,2 @@
 environment: development
-port: 8080
+port: 9090
```

Let's break it down.

---

# 33. diff --git

The line:

```text
diff --git a/config.yml b/config.yml
```

identifies the file being compared.

Git often prefixes versions with:

```text
a/
b/
```

These are comparison labels.

Do not interpret them as necessarily being real top-level folders in your project.

---

# 34. --- and +++

You may see:

```text
--- a/config.yml
+++ b/config.yml
```

Conceptually:

```text
---
old side
```

and:

```text
+++
new side
```

This introduces the two file states being compared.

---

# 35. Reading Removed and Added Lines

Lines beginning with:

```text
-
```

represent content removed from the old version.

Lines beginning with:

```text
+
```

represent content added in the new version.

Example:

```diff
-port: 8080
+port: 9090
```

means:

```text
Old:
port: 8080

New:
port: 9090
```

---

# 36. Context Lines

Lines with no `+` or `-` at the beginning are context.

Example:

```diff
 environment: development
-port: 8080
+port: 9090
```

The line:

```text
environment: development
```

did not change.

Git includes it to help you understand where the change occurred.

---

# 37. What Is @@?

You may see:

```text
@@ -1,2 +1,2 @@
```

This describes the location of the hunk in the old and new file.

At a beginner level, you do not need to memorize its exact syntax.

Just understand:

```text
@@ ... @@
```

introduces a section of related changes.

That section is called a:

```text
hunk
```

---

# 38. Why Diff Reading Matters

Before committing production infrastructure, you should know exactly what changed.

For example:

```diff
-allow_public_access: false
+allow_public_access: true
```

That is not a trivial change.

A quick glance at:

```bash
git diff --staged
```

could prevent a serious mistake.

Diff review is a core engineering habit.

---

# 39. Real DevOps Diff Example

Suppose Terraform contains:

```hcl
instance_type = "t3.small"
```

You change it to:

```hcl
instance_type = "m7i.4xlarge"
```

A staged diff may show:

```diff
-instance_type = "t3.small"
+instance_type = "m7i.4xlarge"
```

That change could significantly affect infrastructure cost.

Before committing:

```bash
git diff --staged
```

helps you catch it.

---

# 40. Real Kubernetes Diff Example

Before:

```yaml
replicas: 3
```

After:

```yaml
replicas: 30
```

Diff:

```diff
-replicas: 3
+replicas: 30
```

Maybe `30` was intentional.

Maybe it was a typo.

Reviewing the diff before committing gives you a chance to decide.

# 41. Removing Files Normally

Suppose Git tracks:

```text
old-config.yml
```

You remove it using the operating system:

```bash
rm old-config.yml
```

Now:

```bash
git status
```

may show:

```text
deleted: old-config.yml
```

Git recognizes that a tracked file was removed from the working tree.

The deletion itself still needs to be staged before it becomes part of the next commit.

---

# 42. Stage a Deletion

If you remove a tracked file using:

```bash
rm old-config.yml
```

you can stage the repository state using commands such as:

```bash
git add -A
```

or by staging the relevant path.

The goal is for the index to represent:

```text
This file should no longer exist in the next commit.
```

---

# 43. Using git rm

Git provides:

```bash
git rm filename
```

Example:

```bash
git rm old-config.yml
```

This performs two related actions:

```text
Remove file from working tree
+
Stage the removal
```

Conceptually:

```text
Tracked File
   |
   | git rm
   v
Removed from working tree
+
Removal staged
```

Then:

```bash
git status
```

should show the deletion under changes to be committed.

---

# 44. Why Use git rm?

Compare:

```bash
rm old-config.yml
```

with:

```bash
git rm old-config.yml
```

The first only removes the working-tree file.

The second integrates the removal directly into Git's staging workflow.

For a tracked file that you truly intend to remove and commit as deleted:

```bash
git rm
```

can be convenient.

---

# 45. Be Careful With File Removal

Before deleting a file, ask:

* Is this file tracked?
* Do I still need its current uncommitted changes?
* Is it present in a previous commit?
* Is it generated or irreplaceable?
* Is this deletion intentional?

If a file has committed history, recovery may be possible.

If it contains important uncommitted work that Git never recorded, recovery may be much harder or impossible.

---

# 46. Removing a File From Git but Keeping It Locally

Sometimes you want Git to stop tracking a file but still keep it on your computer.

A common example is a file that should have been ignored.

Git supports:

```bash
git rm --cached filename
```

Conceptually:

```text
Remove from index
but
keep working-tree file
```

Example:

```bash
git rm --cached local-settings.conf
```

This does **not** mean the file automatically becomes permanently ignored.

You would normally also define an appropriate ignore rule if that is the goal.

Ignore files will be covered later in the series.

# 47. Renaming Files

Suppose you have:

```text
application.py
```

and want:

```text
app.py
```

At the operating-system level, you could use:

```bash
mv application.py app.py
```

Git can often detect the rename based on content similarity when comparing repository states.

Git does not need to permanently store a special "rename object" for every rename.

From the user's perspective, Git may display the change as a rename when it determines that interpretation fits.

---

# 48. Using git mv

Git also provides:

```bash
git mv old-name new-name
```

Example:

```bash
git mv application.py app.py
```

Conceptually, this combines:

```text
Move/rename file
+
Stage resulting change
```

Then:

```bash
git status
```

may show something resembling:

```text
renamed: application.py -> app.py
```

---

# 49. Moving a File Into a Directory

Suppose:

```text
app.py
```

should be moved into:

```text
src/
```

First create:

```bash
mkdir src
```

Then:

```bash
git mv app.py src/app.py
```

Now:

```bash
git status
```

may show the move as a rename.

The working-tree structure becomes:

```text
project/
└── src/
    └── app.py
```

and Git stages the resulting change.

---

# 50. git mv Is a Convenience

You do not absolutely need:

```bash
git mv
```

for Git to understand file moves.

You could use:

```bash
mv app.py src/app.py
```

and then stage the resulting changes.

But:

```bash
git mv
```

is convenient because the move and staging happen together.

---

# 51. Git Tracks Content, Not "File Identity" the Way Beginners Imagine

Beginners sometimes imagine Git permanently attaches an identity tag to a file and follows it everywhere.

Git works differently.

It records snapshots and later detects similarities between states.

That is why a move may be displayed as:

```text
rename
```

even though Git's underlying storage model is based on content and trees.

You do not need to master rename detection yet.

Just remember:

```text
Git records snapshots.
Rename display is derived from comparing snapshots.
```

---

# 52. Unstaging Changes

Suppose you accidentally run:

```bash
git add config.yml
```

but decide:

> I do not want this change in the next commit.

You want to remove it from the staging area without deleting your working-tree changes.

A modern command for this is:

```bash
git restore --staged config.yml
```

Conceptually:

```text
Before

HEAD       A
INDEX      B
WORKING    B
```

After:

```bash
git restore --staged config.yml
```

conceptually:

```text
HEAD       A
INDEX      A
WORKING    B
```

The file remains modified.

The change is simply no longer staged.

---

# 53. Unstaging Is Not the Same as Discarding

This distinction is critical.

```bash
git restore --staged config.yml
```

means:

```text
Remove this change from the proposed next commit
```

It does **not** mean:

```text
Delete my current working changes
```

Your working-tree modification remains.

Run:

```bash
git status
```

and the file should move from:

```text
Changes to be committed
```

to:

```text
Changes not staged for commit
```

---

# 54. Older Tutorials May Use git reset

You will often encounter:

```bash
git reset HEAD file
```

as an older/common method for unstaging.

It is still important to recognize because many tutorials and existing workflows use it.

However, for a beginner learning modern Git, this series will generally prefer:

```bash
git restore --staged file
```

when the goal is simply:

```text
unstage this change
```

We will study `git reset` properly in Part 7 because it has broader and potentially more dangerous behavior depending on how it is used.

# 55. Restoring a Working-Tree File

Suppose you modify:

```text
config.yml
```

from:

```yaml
port: 8080
```

to:

```yaml
port: 9999
```

Then you decide:

> I do not want this modification. Restore the previously staged or committed content.

You can use:

```bash
git restore config.yml
```

This can overwrite the unstaged working-tree modification.

That makes it more dangerous than simple unstaging.

---

# 56. Important Warning Before git restore

Before running:

```bash
git restore filename
```

ask:

> Do I need the current unstaged changes?

Because this command can discard the current working-tree version in favor of Git's source version.

If your current work has not been staged, committed, copied elsewhere, or otherwise saved, it may be difficult or impossible for Git to recover it.

Do not use restoration commands casually.

---

# 57. Unstage vs Restore

This difference is worth memorizing conceptually.

### Unstage

```bash
git restore --staged file
```

changes:

```text
INDEX
```

while preserving your working-tree change.

### Restore working file

```bash
git restore file
```

changes:

```text
WORKING TREE
```

and may discard current unstaged edits.

Think:

```text
--staged
=
change staging state
```

while:

```text
without --staged
=
change working-tree content
```

---

# 58. Example: Unstage Safely

Suppose:

```text
HEAD        version A
INDEX       version B
WORKING     version B
```

You run:

```bash
git restore --staged app.py
```

Afterward:

```text
HEAD        version A
INDEX       version A
WORKING     version B
```

Nothing was lost from your current file.

It simply became unstaged.

---

# 59. Example: Discard Working Change

Suppose:

```text
HEAD        version A
INDEX       version A
WORKING     version B
```

You run:

```bash
git restore app.py
```

Afterward, conceptually:

```text
HEAD        version A
INDEX       version A
WORKING     version A
```

Version B may be gone from the working tree.

This is why the command should be used intentionally.

---

# 60. Restoring From Another Source

Git restore can work with different sources, but do not jump into advanced forms yet.

For beginner purposes, the key distinction is:

```text
git restore --staged
```

for unstaging.

```text
git restore
```

for restoring working-tree content.

Later, once you understand commits and references more deeply, you will restore from specific commits safely.

# 61. Understanding Recoverability

Git recovery depends heavily on whether Git ever stored the data.

This is one of the most important safety lessons in the entire series.

Think of three categories.

---

# 62. Category 1: Committed Data

If data exists in a commit, Git usually has a strong record of it.

Example:

```text
Commit A:
app.py version 1
```

You later change or delete the file.

Because version 1 was committed, Git can usually retrieve that committed state.

Conceptually:

```text
Committed
=
strong recoverability
```

assuming repository history itself has not been destroyed.

---

# 63. Category 2: Staged but Not Committed Data

If content was staged, Git may have created internal objects representing that content.

This can sometimes make recovery possible.

But recovery is less straightforward than simply retrieving a committed version.

Do not treat staging as a replacement for committing important work.

Think:

```text
Staged
=
Git may have object data
but no durable named history point
```

---

# 64. Category 3: Never Staged or Committed

Suppose you type two hours of work into:

```text
app.py
```

but never stage or commit it.

Then you run a command that discards the working-tree changes.

Git may have no record of those edits.

Conceptually:

```text
Working tree only
+
never staged
+
never committed
+
discarded
=
Git may not be able to recover it
```

This is why destructive restore operations require caution.

---

# 65. Git Is Not an Autosave System

Git does not record every keystroke.

It is not equivalent to:

```text
editor autosave
```

or:

```text
cloud backup
```

or:

```text
filesystem snapshots
```

Git records states when you interact with its workflow.

Important work should be committed at sensible points.

---

# 66. What Is Safest?

A practical safety hierarchy is:

```text
Committed
   |
   v
Generally easiest to recover

Staged
   |
   v
May be recoverable internally

Working-tree only
   |
   v
More vulnerable
```

This does not mean you should commit broken work constantly without thought.

It means you should understand where your work exists.

# 67. Common Staging Mistake 1: Staging Everything Without Looking

Command:

```bash
git add .
```

Problem:

You never checked:

```bash
git status
```

Possible result:

```text
debug.log
.env
temporary files
credentials
unrelated configuration
```

all become staged.

Better:

```bash
git status
```

then intentionally stage.

---

# 68. Common Staging Mistake 2: Forgetting New Edits After Staging

Workflow:

```text
Edit app.py
git add app.py
Edit app.py again
git commit
```

Only the staged version is committed.

The newest working-tree edit may remain.

Always check:

```bash
git status
```

and:

```bash
git diff
```

before committing.

---

# 69. Common Staging Mistake 3: Assuming git add Means "Remember This File Forever"

You stage:

```bash
git add app.py
```

then edit it again.

Git does not automatically update the staged copy.

You must stage again if you want the new content included.

Think:

```text
git add
=
snapshot current content into index
```

not:

```text
keep watching every future change
```

---

# 70. Common Staging Mistake 4: Mixing Unrelated Changes

Suppose you modify:

```text
app.py
terraform/main.tf
README.md
```

for three separate reasons.

Then run:

```bash
git add -A
git commit -m "Updates"
```

This produces an unclear commit.

Better:

```text
Stage related files
Commit

Stage next related change
Commit

Stage documentation
Commit
```

Clean commits improve:

* Review
* Debugging
* Reverting
* Auditability
* Incident investigation

---

# 71. Common Staging Mistake 5: Staging Secrets

Never blindly stage files such as:

```text
.env
credentials.json
private-key.pem
aws-credentials
production-secrets.yml
```

If sensitive values enter commit history, simply deleting them later may not remove the secret from history.

If real credentials are exposed, they should generally be treated as compromised and rotated.

Prevention is much better.

---

# 72. Common Staging Mistake 6: Confusing git diff With git diff --staged

You stage a change.

Then:

```bash
git diff
```

shows nothing.

You assume:

> My change disappeared.

It did not.

You are simply asking Git to compare:

```text
INDEX
vs
WORKING TREE
```

If they match, there is no unstaged difference.

Run:

```bash
git diff --staged
```

to inspect the staged change.

---

# 73. Common Staging Mistake 7: Restoring Instead of Unstaging

You accidentally staged a file.

You want:

```text
keep my changes
but remove from staging
```

Correct conceptual action:

```bash
git restore --staged file
```

But you accidentally run:

```bash
git restore file
```

Now you may discard working-tree changes.

Always identify which area you want to change:

```text
Index?
or
Working Tree?
```

before using restore.

---

# 74. Common Staging Mistake 8: Removing a File Without Understanding Its State

Before:

```bash
git rm file
```

ask whether the file contains uncommitted work.

If Git believes removal would destroy changes, Git may protect you in some cases.

Do not fight Git's warning by adding force options unless you understand exactly why it is refusing.

Warnings are often protecting data.

---

# 75. Common Staging Mistake 9: Running Commands From the Wrong Directory

Remember:

```bash
git add .
```

depends on your current path.

Always check:

```bash
pwd
```

if the results are surprising.

Then:

```bash
git status
```

This is especially important in repositories with many nested directories.

---

# 76. Common Staging Mistake 10: Committing Without Reviewing the Staged Diff

A professional-quality workflow should not stop at:

```text
git status says staged
```

You should also inspect what is actually staged.

Use:

```bash
git diff --staged
```

This can catch:

* Debug statements
* Wrong configuration
* Accidental secrets
* Huge unexpected changes
* Formatting mistakes
* Production-impacting values

---

# 77. Strong Pre-Commit Workflow

A disciplined local workflow can look like this:

```bash
git status
```

Inspect unstaged changes:

```bash
git diff
```

Stage intentionally:

```bash
git add app.py
```

Inspect status again:

```bash
git status
```

Inspect exact staged content:

```bash
git diff --staged
```

Then commit:

```bash
git commit -m "Fix application startup message"
```

Then verify:

```bash
git status
```

This is far safer than:

```text
edit
git add .
git commit
hope
```

# 92. Data Recovery Decision Model

Before any destructive operation, ask:

```text
Was this data committed?
        |
        +-- Yes
        |    |
        |    v
        |  Strong recovery options usually exist
        |
        +-- No
             |
             v
        Was it staged?
             |
             +-- Yes
             |    |
             |    v
             |  Some Git object data may exist
             |
             +-- No
                  |
                  v
             Working-tree only
             Higher risk of permanent loss
```

This is not a guarantee of recovery.

It is a risk model.

---

# 93. Safe Rule for Destructive Commands

Before commands that may overwrite or remove data:

1. Run `git status`.
2. Run the relevant `git diff`.
3. Understand whether the change is staged or unstaged.
4. Decide whether you need the current content.
5. Make a backup if uncertain.
6. Only then run the destructive command.

Never use a destructive Git command only because an online answer says:

```text
Run this and it will fix it.
```

Understand what area it changes.

```bash
git mv old new
```

unstaging:

```bash
git restore --staged file
```

and working-tree restoration:

```bash
git restore file
```

with an important warning:

```text
Unstaging
does not mean
discarding.

Restoring a working file
may discard
unstaged work.
```

Finally, you learned the most important safety principle from this part:

```text
The more completely Git has recorded your data,
the easier recovery usually becomes.
```

Conceptually:

```text
COMMITTED
Most protected by Git history

STAGED
May have recoverable object data

WORKING TREE ONLY
Most vulnerable
```

The correct staging workflow is therefore not:

```text
Change
Add everything
Commit immediately
```

It is:

```text
CHANGE
   |
   v
git status
   |
   v
git diff
   |
   v
STAGE INTENTIONALLY
   |
   v
git status
   |
   v
git diff --staged
   |
   v
VERIFY
   |
   v
COMMIT
```
