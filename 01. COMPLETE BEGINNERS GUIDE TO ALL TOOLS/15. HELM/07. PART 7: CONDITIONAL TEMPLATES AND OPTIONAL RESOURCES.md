# 1. Why conditional templates exist

Imagine maintaining a Kubernetes application deployed into three environments.

Development requires:

- Deployment
- Service
- One replica
- No public Ingress
- No autoscaling
- No PodDisruptionBudget

Staging requires:

- Deployment
- Service
- Ingress
- Two replicas
- Optional autoscaling
- Basic availability protection

Production requires:

- Deployment
- Service
- Ingress
- HPA
- PDB
- Dedicated ServiceAccount
- NetworkPolicy
- Monitoring integration

Without Helm conditionals, teams may maintain multiple manifest collections:

```
kubernetes/
├── development/
│   ├── deployment.yaml
│   └── service.yaml
├── staging/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── ingress.yaml
└── production/
    ├── deployment.yaml
    ├── service.yaml
    ├── ingress.yaml
    ├── hpa.yaml
    ├── pdb.yaml
    ├── serviceaccount.yaml
    ├── networkpolicy.yaml
    └── servicemonitor.yaml
```

As the application evolves, these directories may drift apart.

Helm provides a different model:

```
One Helm Chart
      +
Environment Values
      +
Conditional Templates
      ↓
Environment-Specific
Kubernetes Resources
```

The important distinction is that the chart contains the available deployment capabilities, while values determine which capabilities are enabled for a particular release.

# 2. The conditional rendering mental model

VALUES

## ingress.enabled: true

HELM CONDITIONAL

## {{ if .Values.ingress.enabled }}

True

Render Ingress manifest

False

Omit Ingress manifest

FINAL OUTPUT

Rendered Kubernetes YAML

The Helm template engine evaluates the condition before sending resources to Kubernetes.

Kubernetes does not understand:

```
{{ if .Values.ingress.enabled }}
```

Kubernetes receives only the final YAML.

This means Helm conditionals are render-time decisions, not Kubernetes runtime feature switches.

# 3. The `if` statement

The basic syntax is:

```
{{- if CONDITION }}
CONTENT
{{- end }}
```

Helm evaluates `CONDITION`.

If it is true or nonempty, the content inside the block is rendered.

Otherwise, the content is omitted.

## 3.1 First example

`values.yaml`:

```
feature:
  enabled: true
```

Template:

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: feature-demo
data:
  {{- if .Values.feature.enabled }}
  FEATURE_STATUS: "enabled"
  {{- end }}
```

Rendered:

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: feature-demo
data:
  FEATURE_STATUS: "enabled"
```

If the value changes to:

```
feature:
  enabled: false
```

the conditional entry disappears.

However, the surrounding ConfigMap may still be rendered with an empty `data` map or a null-like `data` field, depending on the template layout.

That distinction matters.

If the entire resource is optional, wrap the whole manifest, not merely its contents.

# 4. Conditional resources versus conditional fields

Helm conditionals are commonly used in two ways.

## 4.1 Conditional resource

```
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: example
spec:
  ...
{{- end }}
```

When disabled, Helm does not render the Ingress resource.

## 4.2 Conditional field

```
spec:
  template:
    spec:
      {{- if .Values.serviceAccount.create }}
      serviceAccountName: my-service-account
      {{- end }}
      containers:
        - name: web
          image: nginx:1.27
```

When disabled, only the `serviceAccountName` field disappears.

## 4.3 Comparison

| Aspect            | Conditional resource          | Conditional field                      |
| ----------------- | ----------------------------- | -------------------------------------- |
| Controls          | Entire Kubernetes object      | Portion of an object                   |
| Typical use       | Ingress, HPA, PDB             | Annotations, probes, security settings |
| Disabled behavior | No manifest for that resource | Field or section omitted               |
| Main risk         | Missing dependent resources   | Invalid YAML or unexpected defaults    |

A common production mistake is disabling a resource while leaving another resource configured to reference it.

For example, disabling ServiceAccount creation while keeping a Pod's `serviceAccountName` pointed at the missing ServiceAccount.

You will solve that problem later in the chapter.

# 5. The `else` statement

Use `else` to render one of two alternatives.

Syntax:

```
{{- if CONDITION }}
TRUE CONTENT
{{- else }}
FALSE CONTENT
{{- end }}
```

Example:

```
data:
  {{- if .Values.debug.enabled }}
  LOG_LEVEL: "DEBUG"
  {{- else }}
  LOG_LEVEL: "INFO"
  {{- end }}
```

If:

```
debug:
  enabled: true
```

the output is:

```
data:
  LOG_LEVEL: "DEBUG"
```

Otherwise:

```
data:
  LOG_LEVEL: "INFO"
```

## 5.1 When to use `else`

Use `else` when exactly one of two behaviors should apply.

Good examples include:

- Choosing a default logging mode.
- Selecting a ServiceAccount name.
- Enabling a development-only setting.
- Selecting one of two mutually exclusive configuration blocks.

Avoid `else` when omission is the correct behavior.

For an optional Ingress, there is usually no reason to render a different resource merely because Ingress is disabled.

# 6. The `else if` statement

Use `else if` when several mutually exclusive conditions must be evaluated.

Example:

```
{{- if eq .Values.environment "production" }}
LOG_LEVEL: "WARN"
{{- else if eq .Values.environment "staging" }}
LOG_LEVEL: "INFO"
{{- else }}
LOG_LEVEL: "DEBUG"
{{- end }}
```

This demonstrates the concept, but it assumes all other environments should use debug logging.

For production engineering, validate supported environment names instead of silently treating unexpected values as development.

A better design may simply expose:

```
config:
  logLevel: info
```

and let each environment override the value.

Use conditional logic for structural differences. Use values for ordinary configuration differences.

That principle prevents charts from accumulating unnecessary conditions.

# 7. Boolean values and YAML typing

Boolean values are usually written as:

```
ingress:
  enabled: true

autoscaling:
  enabled: false
```

These are YAML booleans.

Compare:

```
enabled: true
```

with:

```
enabled: "true"
```

The first is a boolean.

The second is a string.

A nonempty string such as `"false"` is truthy in Go-template conditions.

Therefore:

```
enabled: "false"
```

can unexpectedly enable a resource when used with:

```
{{- if .Values.feature.enabled }}
```

## 7.1 Recommended practice

Use actual YAML booleans and validate them through `values.schema.json`.

For CLI overrides:

```
helm template demo ./my-chart \
  --set ingress.enabled=false
```

For a deliberately string-typed setting, `--set-string` may be appropriate, but it should not be used for a boolean feature flag.

# 8. Empty values and truthiness

Helm's `if` condition evaluates whether an expression is empty.

The following are generally considered false or empty:

| Value           | `if` result |
| --------------- | ----------- |
| `false`         | False       |
| `0`             | False       |
| `""`            | False       |
| `null`          | False       |
| Empty list `[]` | False       |
| Empty map `{}`  | False       |
| Nonempty string | True        |
| Nonzero number  | True        |
| Nonempty list   | True        |
| Nonempty map    | True        |

For example:

```
{{- if .Values.extraAnnotations }}
metadata:
  annotations:
    {{- toYaml .Values.extraAnnotations | nindent 4 }}
{{- end }}
```

If `extraAnnotations` is an empty map, the block is omitted.

This is often desirable.

## 8.1 Missing versus explicitly false

A missing value and an explicitly configured `false` both cause a simple `if` block to be skipped.

If your logic must distinguish them, use `hasKey`.

Example:

```
{{- if hasKey .Values.feature "enabled" }}
{{ .Values.feature.enabled }}
{{- else }}
false
{{- end }}
```

This checks whether the key exists, not whether its value is truthy.

# 9. Equality and comparison operators

Helm provides comparison functions through the Go-template engine.

| Function | Meaning               | Example                                |
| -------- | --------------------- | -------------------------------------- |
| `eq`     | Equal                 | `eq .Values.environment "production"`  |
| `ne`     | Not equal             | `ne .Values.environment "development"` |
| `lt`     | Less than             | `lt .Values.replicaCount 3`            |
| `le`     | Less than or equal    | `le .Values.replicaCount 3`            |
| `gt`     | Greater than          | `gt .Values.replicaCount 1`            |
| `ge`     | Greater than or equal | `ge .Values.replicaCount 2`            |

## 9.1 Equality

```
{{- if eq .Values.environment "production" }}
...
{{- end }}
```

## 9.2 Inequality

```
{{- if ne .Values.environment "development" }}
...
{{- end }}
```

## 9.3 Numeric comparison

```
{{- if gt .Values.replicaCount 1 }}
...
{{- end }}
```

Numeric comparisons require compatible operand types.

A value such as:

```
replicaCount: "three"
```

should be rejected through schema validation rather than silently converted.

# 10. Logical `and`, `or`, and `not`

These functions combine conditions.

## 10.1 `and`

Both conditions must be truthy.

```
{{- if and .Values.ingress.enabled (eq .Values.environment "production") }}
...
{{- end }}
```

This renders only when Ingress is enabled and the environment is production.

## 10.2 `or`

At least one condition must be truthy.

```
{{- if or .Values.monitoring.enabled .Values.debug.enabled }}
...
{{- end }}
```

## 10.3 `not`

Negates a condition.

```
{{- if not .Values.autoscaling.enabled }}
replicas: {{ .Values.replicaCount }}
{{- end }}
```

This is a common pattern for a Deployment that may be controlled by an HPA.

## 10.4 Combining conditions

```
{{- if and .Values.networkPolicy.enabled (ne .Values.environment "development") }}
...
{{- end }}
```

The expression is valid, but consider whether the environment check belongs in the template.

A cleaner alternative is to configure `networkPolicy.enabled` separately for each environment.

That reduces hidden behavior.

# 12. Whitespace and conditional blocks

Helm templates combine YAML with Go-template control statements.

Whitespace handling matters because YAML uses indentation to define structure.

Consider:

```
{{ if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
...
{{ end }}
```

This may leave extra blank lines in the rendered output.

Whitespace trimming can improve readability:

```
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
...
{{- end }}
```

The leading hyphen trims whitespace to the left of the template action.

A trailing hyphen trims whitespace to the right:

```
{{- if CONDITION -}}
```

## 12.1 Important caution

Aggressive trimming can join YAML tokens unexpectedly.

For example:

```
food: "PIZZA"
{{- if .Values.favorite.drink -}}
drink: "coffee"
{{- end }}
```

may concatenate text into an invalid YAML line.

The correct use of trimming depends on surrounding whitespace.

Always inspect the rendered manifest.

# 13. Conditional resources in production charts

A production-oriented chart may have this structure:

```
templates/
├── _helpers.tpl
├── deployment.yaml
├── service.yaml
├── ingress.yaml
├── hpa.yaml
├── pdb.yaml
├── serviceaccount.yaml
├── networkpolicy.yaml
└── servicemonitor.yaml
```

Each optional resource can have a dedicated feature flag.

```
ingress:
  enabled: false

autoscaling:
  enabled: false

pdb:
  enabled: false

serviceAccount:
  create: false

networkPolicy:
  enabled: false

monitoring:
  serviceMonitor:
    enabled: false
```

The chart can render different resource combinations without duplicating its templates.

The challenge is ensuring that enabled resources have valid configuration and disabled resources do not leave broken references.

# 14. Conditional Ingress

Ingress routes HTTP and HTTPS traffic to Kubernetes Services.

Example values:

```
ingress:
  enabled: true
  className: nginx
  host: app.example.com
  path: /
  pathType: Prefix
```

Template:

```
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: {{ .Release.Name }}-ingress
spec:
  ingressClassName: {{ .Values.ingress.className | quote }}
  rules:
    - host: {{ required "ingress.host is required" .Values.ingress.host | quote }}
      http:
        paths:
          - path: {{ .Values.ingress.path | quote }}
            pathType: {{ .Values.ingress.pathType }}
            backend:
              service:
                name: {{ .Release.Name }}-service
                port:
                  name: http
{{- end }}
```

When enabled, Helm renders an Ingress.

When disabled, it renders nothing from this template.

Important: An Ingress resource alone does not provide traffic routing. The cluster needs an appropriate Ingress controller, and DNS must resolve correctly.

# 15. Conditional HPA

An HPA automatically adjusts the number of replicas based on metrics.

Values:

```
autoscaling:
  enabled: true
  minReplicas: 2
  maxReplicas: 6
  targetCPUUtilizationPercentage: 70
```

Template:

```
{{- if .Values.autoscaling.enabled }}
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: {{ .Release.Name }}-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: {{ .Release.Name }}-deployment

  minReplicas: {{ .Values.autoscaling.minReplicas }}
  maxReplicas: {{ .Values.autoscaling.maxReplicas }}

  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: {{ .Values.autoscaling.targetCPUUtilizationPercentage }}
{{- end }}
```

## 15.1 HPA and Deployment interaction

When HPA is enabled, the Deployment commonly omits its manually configured replica field:

```
spec:
  {{- if not .Values.autoscaling.enabled }}
  replicas: {{ .Values.replicaCount }}
  {{- end }}
```

This avoids repeatedly managing the replica count through Helm while HPA is managing scaling.

There are nuances around HPA ownership and transitions between manual and automatic scaling, so production changes should be tested carefully.

## 15.2 HPA prerequisites

CPU-based autoscaling requires appropriate resource requests and a working metrics pipeline, commonly Metrics Server.

A valid HPA manifest does not guarantee that autoscaling will function.

# 16. Conditional PodDisruptionBudget

A PodDisruptionBudget limits how many matching Pods may be voluntarily disrupted.

Example:

```
pdb:
  enabled: true
  minAvailable: 1
```

Template:

```
{{- if .Values.pdb.enabled }}
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: {{ .Release.Name }}-pdb
spec:
  minAvailable: {{ .Values.pdb.minAvailable }}
  selector:
    matchLabels:
      app.kubernetes.io/instance: {{ .Release.Name | quote }}
      app.kubernetes.io/name: {{ .Chart.Name | quote }}
{{- end }}
```

The selector must match the intended Pods.

## 16.1 Important production considerations

A PDB does not protect against every type of Pod failure. It applies to supported voluntary disruptions, such as certain eviction operations.

For a single-replica application, a strict PDB can prevent routine voluntary eviction and interfere with node maintenance.

A PDB should reflect the application's actual availability requirements and replica strategy.

# 17. Conditional ServiceAccount

A chart may either create its own ServiceAccount or use an existing one.

Values:

```
serviceAccount:
  create: true
  name: ""
  automountServiceAccountToken: false
```

Template:

```
{{- if .Values.serviceAccount.create }}
apiVersion: v1
kind: ServiceAccount
metadata:
  name: {{ .Values.serviceAccount.name | default (printf "%s-sa" .Release.Name) | quote }}
automountServiceAccountToken: {{ .Values.serviceAccount.automountServiceAccountToken }}
{{- end }}
```

The Deployment must reference the correct account.

Conceptually:

```
serviceAccount.create = true
           ↓
Create chart-managed ServiceAccount
           ↓
Deployment references it
```

Versus:

```
serviceAccount.create = false
           ↓
Do not create ServiceAccount
           ↓
Use existing account or Kubernetes default
```

## 17.1 Avoiding broken references

A simple design can calculate the ServiceAccount name in one helper.

For this chapter's lab, you will use a shared helper that chooses the configured name or a generated name when creation is enabled, and otherwise uses the configured existing name or `default`.

That avoids creating a Pod that references a ServiceAccount the chart never created.

# 18. Conditional NetworkPolicy

NetworkPolicy controls allowed network traffic for selected Pods when the cluster's networking implementation supports policy enforcement.

Values:

```
networkPolicy:
  enabled: true
```

Template concept:

```
{{- if .Values.networkPolicy.enabled }}
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: {{ .Release.Name }}-network-policy
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/instance: {{ .Release.Name | quote }}

  policyTypes:
    - Ingress

  ingress:
    - from:
        - podSelector:
            matchLabels:
              access: allowed
{{- end }}
```

This example permits selected same-namespace Pods to reach the targeted Pods.

It is not a complete production network policy.

NetworkPolicy behavior depends on the CNI/networking implementation. A cluster can accept NetworkPolicy objects without enforcing them if the network plugin lacks support.

Be particularly careful with egress restrictions: they can block DNS, telemetry, external APIs, and other required dependencies.

# 19. Conditional monitoring resources

Some Kubernetes environments use Prometheus Operator custom resources such as `ServiceMonitor`.

A `ServiceMonitor` is not a built-in Kubernetes resource.

It requires the relevant CRD to be installed.

Values:

```
monitoring:
  serviceMonitor:
    enabled: false
    interval: 30s
```

Template concept:

```
{{- if .Values.monitoring.serviceMonitor.enabled }}
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: {{ .Release.Name }}-monitor
spec:
  selector:
    matchLabels:
      app.kubernetes.io/instance: {{ .Release.Name | quote }}

  endpoints:
    - port: metrics
      interval: {{ .Values.monitoring.serviceMonitor.interval | quote }}
{{- end }}
```

The Service must expose a named `metrics` port, and the monitoring operator must select the ServiceMonitor.

## 19.1 CRD availability

Enabling a custom resource before installing its CRD causes installation failures.

A chart may use `.Capabilities.APIVersions.Has` to check whether an API is advertised:

```
{{- if and .Values.monitoring.serviceMonitor.enabled (.Capabilities.APIVersions.Has "monitoring.coreos.com/v1/ServiceMonitor") }}
...
{{- end }}
```

However, silently omitting a requested monitoring resource can conceal misconfiguration.

For a required integration, it may be better to fail with an explicit error when the CRD is unavailable.

Also note that offline `helm template` capabilities may not reflect a real cluster unless supplied explicitly.

# 20. Environment-specific behavior

You can use conditionals directly against the environment name:

```
{{- if eq .Values.environment "production" }}
...
{{- end }}
```

But overusing environment-name checks makes a chart rigid.

Compare two designs.

## 20.1 Environment hardcoded into templates

```
{{- if eq .Values.environment "production" }}
...
{{- end }}
```

## 20.2 Behavior controlled by values

```
{{- if .Values.pdb.enabled }}
...
{{- end }}
```

The second is generally more reusable.

It allows a staging environment to enable a PDB when needed without changing template logic.

A good chart exposes capabilities; environment values select those capabilities.

# 21. Avoiding conditional explosion

Conditional explosion occurs when a chart contains too many interacting conditions.

For example:

```
{{- if and
    .Values.ingress.enabled
    (or .Values.monitoring.enabled .Values.debug.enabled)
    (ne .Values.environment "development")
    (not .Values.maintenanceMode)
}}
...
{{- end }}
```

This may be technically valid, but it is difficult to reason about.

Problems include:

- Hidden dependencies between settings.
- Unexpected combinations of enabled resources.
- Difficult testing.
- Repeated environment-specific branches.
- Increased risk of invalid manifests.
- Unclear behavior for chart consumers.

## 21.1 Better approaches

Use independent feature flags. Give optional resources clear `enabled` settings.

Validate dependencies. Fail clearly if enabling one feature requires another.

Use helpers. Move repeated naming and label logic into `_helpers.tpl`.

Use values files. Keep ordinary environment differences out of templates.

Keep one responsibility per template. Avoid enormous templates that render many unrelated resources.

Test combinations. Verify that important feature combinations render valid Kubernetes manifests.

Split charts when necessary. If one chart is managing unrelated applications or independently released components, separate charts may be easier to maintain.

# 25. Lab 3: Create reusable helpers

Create `conditional-lab/templates/_helpers.tpl`:

```
{{- define "conditional-lab.name" -}}
{{- .Chart.Name | trunc 63 | trimSuffix "-" -}}
{{- end -}}

{{- define "conditional-lab.fullname" -}}
{{- printf "%s-%s" .Release.Name .Chart.Name | trunc 63 | trimSuffix "-" -}}
{{- end -}}

{{- define "conditional-lab.selectorLabels" -}}
app.kubernetes.io/name: {{ include "conditional-lab.name" . }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end -}}

{{- define "conditional-lab.labels" -}}
{{ include "conditional-lab.selectorLabels" . }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
helm.sh/chart: {{ printf "%s-%s" .Chart.Name .Chart.Version | replace "+" "_" }}
{{- end -}}

{{- define "conditional-lab.serviceAccountName" -}}
{{- if .Values.serviceAccount.create -}}
{{- default (printf "%s-sa" (include "conditional-lab.fullname" .)) .Values.serviceAccount.name -}}
{{- else -}}
{{- default "default" .Values.serviceAccount.name -}}
{{- end -}}
{{- end -}}
```

These helpers centralize names and labels so all resources use consistent selectors.

The naming helpers are introductory and assume sensible release names. A production chart should also validate any user-provided names and account for suffix lengths.

### Security exercise

Explain which Pods may reach the application when this policy is enforced.

The policy permits ingress from same-namespace Pods carrying:

```

```

It does not automatically permit traffic from every Ingress controller.

# 46. Troubleshooting conditional templates

| Symptom                          | Likely cause                                | Recommended fix                             |
| -------------------------------- | ------------------------------------------- | ------------------------------------------- |
| Optional resource always renders | String `"false"` instead of boolean `false` | Use native boolean and schema               |
| Optional resource never renders  | Incorrect `.Values` path                    | Inspect values and template expression      |
| `unexpected EOF`                 | Missing `end`                               | Close every control block                   |
| Template parse error             | Missing braces or malformed expression      | Check delimiters and function syntax        |
| YAML parse error                 | Whitespace trimming or indentation          | Render with `--debug`                       |
| Resource rejected by API         | Field in wrong YAML location                | Validate rendered manifest                  |
| HPA exists but does not scale    | Metrics unavailable or requests missing     | Inspect HPA conditions and metrics          |
| PDB blocks node drain            | Availability constraints too strict         | Revisit replicas and disruption budget      |
| Pod cannot start                 | Referenced ServiceAccount missing           | Check account creation and naming           |
| NetworkPolicy blocks traffic     | Missing ingress/egress allowances           | Review selected Pods and permitted peers    |
| ServiceMonitor rejected          | CRD missing                                 | Install supported operator/CRD first        |
| Monitoring finds no targets      | Wrong labels or metrics port                | Verify Service and ServiceMonitor selectors |
| Wrong resources in environment   | Incorrect values-file precedence            | Inspect effective values and overrides      |

```

Check YAML type

     ↓

     ↓
```

# 47. Production design patterns

## Pattern 1: Independent resource flags

```
ingress:
  enabled: true

autoscaling:
  enabled: true

pdb:
  enabled: true
```

This is generally clear and maintainable.

## Pattern 2: Configuration rather than environment branching

Prefer:

```
pdb:
  enabled: true
```

over:

```
{{- if eq .Values.environment "production" }}
```

unless the environment name itself is genuinely part of the chart's intended behavior.

## Pattern 3: Explicit dependencies

If a feature requires another resource, document and validate the dependency.

For example, a ServiceMonitor requires a compatible Service and monitoring CRD.

## Pattern 4: Safe defaults

Default optional integrations to disabled when they depend on external cluster components.

Do not assume every Kubernetes cluster has an Ingress controller, metrics system, or monitoring operator.

## Pattern 5: Stable selectors

Keep Deployment, Service, HPA, PDB, and NetworkPolicy selectors aligned.

Changing selectors carelessly can disconnect traffic or cause Kubernetes to reject immutable-field updates.

## Pattern 6: Minimal conditional nesting

Use one condition around a whole resource when possible.

Prefer:

```
{{- if .Values.ingress.enabled }}
...
{{- end }}
```

over many repeated checks inside the same resource.

## Pattern 7: Test combinations, not only individual flags

A chart with six independent boolean feature flags has up to:

\\[ 2^6=64 \\]

possible combinations.

Not all combinations need identical testing, but the important supported combinations must be validated.

For example:

- HPA enabled, Ingress disabled.
- HPA disabled, PDB enabled.
- ServiceAccount creation disabled with an existing account name.
- NetworkPolicy enabled with Ingress enabled.
- Monitoring enabled with and without its required CRD.

## 48.1 Automation concept

You can automate rendering checks in CI:

```
set -e

helm lint ./conditional-lab

helm template test ./conditional-lab \
  -f environments/dev.yaml \
  > /tmp/conditional-dev.yaml

helm template test ./conditional-lab \
  -f environments/staging.yaml \
  > /tmp/conditional-staging.yaml

helm template test ./conditional-lab \
  -f environments/production.yaml \
  > /tmp/conditional-production.yaml
```

For robust CI, go further than checking command success.

Parse the YAML and assert that expected resource kinds exist, forbidden kinds are absent, and important fields have the correct values.

```
       │
```

The central engineering principle is:

Conditional templates should make a Helm chart configurable without making its behavior unpredictable.

The objective is not to create the maximum possible number of feature flags.

The objective is to expose a clear, maintainable deployment interface that produces valid resources for supported configurations.
