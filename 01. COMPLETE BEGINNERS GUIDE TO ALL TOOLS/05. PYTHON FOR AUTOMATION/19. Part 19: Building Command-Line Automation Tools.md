# Part 19: Building Command-Line Automation Tools

Turn Python scripts into tools another engineer can actually use.

Up to this point, you have learned how to write Python that can:

* Work with variables and collections.
* Make decisions.
* Loop through resources.
* Organize logic into functions and modules.
* Manage dependencies.
* Handle exceptions.
* Work with files and directories.
* Interact with the operating system.
* Run Linux commands.
* Parse JSON.
* Read and modify YAML.
* Understand HTTP and APIs.
* Communicate with APIs using `requests`.
* Log operational events.
* Work with dates and time.
* Parse text with regular expressions.
* Read configuration from environment variables.

Now we need to solve another problem:

```text
How does another engineer actually use the automation?
```

A Python script may work perfectly internally, but if using it requires opening the source code and editing variables like:

```python
host = "web01"
port = 443
environment = "production"
```

then it is not yet a very usable tool.

A better interface is:

```bash
python server_check.py --host web01 --port 443
```

Or:

```bash
python server_check.py --config servers.yaml
```

Or:

```bash
python server_check.py \
  --config servers.yaml \
  --dry-run \
  --verbose
```

This is a command-line interface.

By the end of this part, you should be able to design and build Python CLI tools that another engineer can discover, understand, configure, run safely, troubleshoot, and automate from shell scripts or CI/CD systems.

# 2. What Is a Command-Line Interface?

A command-line interface, or CLI, is a way for a user to interact with software by typing commands into a terminal or shell.

Examples you already know include:

```bash
git status
```

```bash
kubectl get pods
```

```bash
docker ps
```

```bash
terraform plan
```

```bash
python script.py
```

Each command exposes an interface.

---

* Infrastructure tooling.

A well-designed CLI can serve both:


# 17. Why `argparse` Is Better

Python provides:

```python
import argparse
```

`argparse` helps build command-line interfaces.

It can automatically handle:

* Argument parsing.
* Required arguments.
* Optional arguments.
* Flags.
* Defaults.
* Type conversion.
* Choices.
* Help text.
* Usage messages.
* Many input errors.

# 43. Dry-Run Flag

A very important infrastructure flag is:

```text
--dry-run
```

Create:

```python
parser.add_argument(
    "--dry-run",
    action="store_true",
    help=(
        "Show intended actions "
        "without changing anything"
    )
)
```

---

# 44. Why Dry Run Matters

Suppose a tool will restart failed services.

Without dry run:

```text
Detect service
     |
     v
Restart immediately
```

With dry run:

```text
Detect service
     |
     v
Show intended restart
     |
     v
No mutation
```

This reduces risk.

---

# 45. Dry Run Is More Than a Print Statement

Good dry-run mode should avoid the actual mutation.

Bad:

```python
restart_service(
    service
)

if dry_run:
    print(
        "Would restart service"
    )
```

The service has already been restarted.

---

# 46. Correct Dry-Run Structure

Better:

```python
if dry_run:

    logger.info(
        "DRY RUN would restart "
        "service=%s",
        service
    )

else:

    restart_service(
        service
    )
```

Check the mode before the action.

---

# 47. Dry Run Should Still Validate

A useful dry run may still:

* Read configuration.
* Validate input.
* Discover resources.
* Calculate intended changes.
* Check permissions where safe.
* Generate a plan.

But it should avoid the state-changing operation.

# 51. Input Validation

Argument parsing and input validation are related but different.

`argparse` can ensure:

```text
port is an integer
```

But your application still needs to check:

```text
port is between 1 and 65535
```

---

# 52. Port Validation

```python
def validate_port(
    port: int
) -> int:

    if not 1 <= port <= 65535:
        raise ValueError(
            "Port must be between "
            "1 and 65535"
        )

    return port
```

---

# 53. Why Type Is Not Enough

This:

```text
99999
```

is a valid integer.

It is not a valid TCP port.

Validation often has layers:

```text
Correct type?
    |
    v
Correct range?
    |
    v
Allowed for this operation?
```

---

# 54. Validation Through an `argparse` Type Function

You can integrate validation directly.

```python
def port_value(
    value: str
) -> int:

    try:
        port = int(
            value
        )

    except ValueError as error:
        raise argparse.ArgumentTypeError(
            "Port must be an integer"
        ) from error

    if not 1 <= port <= 65535:
        raise argparse.ArgumentTypeError(
            "Port must be between "
            "1 and 65535"
        )

    return port
```

---

# 55. Use the Custom Type

```python
parser.add_argument(
    "--port",
    type=port_value,
    default=443
)
```

Now validation happens during parsing.

---

# 56. `argparse.ArgumentTypeError`

This exception lets your custom validation produce a friendly CLI parsing error.

It is preferable to exposing an internal Python traceback for a normal user input mistake.

# 60. User Error vs Program Bug

A CLI should distinguish:

```text
User supplied bad input
```

from:

```text

```

Normal user mistakes should usually receive clean messages without Python tracebacks.

Unexpected internal bugs should preserve debugging evidence.

# 61. Exit Codes

A command-line tool returns an exit status to the shell.

Conventionally:

```text
0
Success

nonzero
Some form of failure
```

---

# 62. Why Exit Codes Matter

A human can read output.

A CI/CD system may primarily inspect:

```text
exit code
```

Example:

```text
Tool prints:
"Server unreachable"

but exits:
0
```

A pipeline may incorrectly report success.

---

# 63. Returning from `main()`

Example:

```python
def main() -> int:

    success = run_check()

    if success:
        return 0

    return 1
```

Then:

```python
if __name__ == "__main__":
    raise SystemExit(
        main()
    )
```

---

# 64. `SystemExit`

Passing:

```text
0
```

signals success.

Passing:

```text
1
```

signals failure.

The shell receives the resulting exit status.

---

# 65. Check Exit Code in a Shell

On Bash-like shells:

```bash

  --host web01

```

You may see:

```text

```

or:

```text

```

depending on the tool's result.

---

# 66. Design an Exit-Code Policy

A simple tool might use:

```text
0
Check passed

1
Check failed

2
Configuration/input problem
```

A more detailed internal tool could use additional codes.

Keep the policy documented and understandable.

---

# 67. Do Not Create Meaningless Exit Codes

This:

```text
73
server timeout

74
DNS failure

75
port closed

76
config missing
```

may become unnecessarily complicated.

Use detail in logs and output.

Use exit codes for useful machine-level classification.

---

# 68. `argparse` Has Its Own Error Exit Behavior

When parsing fails, `argparse` normally prints usage information and exits with a nonzero status.

That is useful.

You do not need to reinvent every parsing error path.

# 69. CLI Configuration Sources


# 70. Configuration Precedence

A common design is:

```text
CLI argument
highest priority

        ↓

Environment variable

        ↓

Configuration file

        ↓

Built-in default
lowest priority
```

But this is a design decision.

Document it clearly.

---

# 71. Why Precedence Matters

Suppose:

YAML contains:

```yaml

```

Environment says:

```text

```

CLI says:

```bash
--port 443
```

Which port should be used?

If precedence is undocumented, operators cannot predict behavior.

# 77. Mutually Exclusive Inputs

If the tool should accept either:

```text
--host
```

or:

```text
--config
```

but not both, `argparse` supports mutually exclusive groups.

---

# 78. Create a Mutually Exclusive Group

```python
target_group = (
    parser.add_mutually_exclusive_group(
        required=True
    )
)
```

Then:

```python
target_group.add_argument(
    "--host"
)

target_group.add_argument(
    "--config",
    type=Path
)
```

---

# 79. What This Enforces

The user must supply exactly one of:

```text
--host
--config
```

So:

```bash
python server_check.py
```

fails.

And:

```bash
python server_check.py \
  --host web01 \
  --config servers.yaml
```

also fails.

That makes the interface predictable.

---

# 80. Port with Config Mode

If:

```text
--host
```

is used, a CLI:

```text
--port
```

makes sense.

But if:

```text
--config
```

is used, each server may already contain its own port.

You need to define whether:

```text
--port
```

overrides config ports.

---

# 81. Avoid Ambiguous Overrides

For a beginner tool, a simple rule might be:

```text
Host mode:
--port applies

Config mode:
port comes from YAML
```

Then reject:

```bash
--config servers.yaml --port 443
```

if that combination would be ambiguous.

# 82. Cross-Argument Validation

`argparse` handles individual values well.

But sometimes you need validation involving several arguments.

Example:

```python
if (
    args.config is not None

        "with --config"
    )
```

# 83. `parser.error()`

This produces a user-friendly parsing error and usage information.

Use it for invalid combinations of otherwise valid arguments.

# 84. Environment Variables

Suppose:

```text

```

# 85. Environment Variables as Defaults

You can use an environment variable as the argparse default.

Example:

```python
default_timeout = int(
    os.getenv(
        "SERVER_CHECK_TIMEOUT",
        "5"

)
```

Then:

```python
parser.add_argument(
    "--timeout",
    type=int,
    default=default_timeout
)
```

---

# 86. CLI Overrides Environment

If:

```text
SERVER_CHECK_TIMEOUT=5
```

and user runs:

```bash
python server_check.py \
  --host web01 \
```

```python
def get_positive_env_int(
    name: str,
    default: int
) -> int:

    raw = os.getenv(
        name,
        str(default)
    )

    try:
        value = int(
            raw
        )

    except ValueError as error:
        raise RuntimeError(
            f"{name} must be "
            f"an integer"

    if value <= 0:
        raise RuntimeError(
            f"{name} must be "
            f"greater than zero"
        )

    return value
```

# 102. Network Check Function

In:

```text

```

write:

```python
import socket


def check_tcp_port(
    host: str,
    port: int,
    timeout: float
) -> dict:

    try:
        with socket.create_connection(
            (
                host,
                port
            ),
            timeout=timeout
        ):
            return {
                "host": host,
                "port": port,
                "reachable": True,
                "error": None
            }

    except OSError as error:
        return {
            "host": host,
            "port": port,
            "reachable": False,
            "error": str(
                error
            )
        }
```

# 118. Load YAML

```python
def load_server_config(
    path: Path
) -> list[dict]:

    try:
        with path.open(
            "r",
            encoding="utf-8"
        ) as file:

            data = yaml.safe_load(
                file
            )

    except FileNotFoundError as error:
        raise RuntimeError(
            f"Configuration file "
            f"not found: {path}"
        ) from error

    except PermissionError as error:
        raise RuntimeError(
            f"Permission denied: "
            f"{path}"
        ) from error

    except yaml.YAMLError as error:
        raise RuntimeError(
            f"Invalid YAML: {path}"
        ) from error
```

# 187. Host Validation

# 189. Fail-Fast Configuration

# 190. Partial Processing Policy


```python
def load_targets(

) -> list[Target]:

    try:
        with path.open(

            f"Permission denied: "
```

```python
    args

            args.config
```

# 249. When to Use `sys.argv`

You should still understand:

```python
sys.argv
```

because:

* It explains how command-line arguments reach Python.
* Simple scripts may use it.
* Libraries and tooling ultimately interact with argument arrays.


is usually a much better beginner choice.

# 250. When `argparse` May Eventually Not Be Enough

Large professional CLI ecosystems may use other frameworks.

But do not rush there.

`argparse` can build substantial, production-quality command-line tools and is part of Python itself.

The important skill is CLI design, not collecting frameworks.
