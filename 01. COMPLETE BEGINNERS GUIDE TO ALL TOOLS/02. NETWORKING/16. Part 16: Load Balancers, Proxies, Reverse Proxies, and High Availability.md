# Part 16: Load Balancers, Proxies, Reverse Proxies, and High Availability

## Understand How Production Traffic Reaches Applications

In the previous parts, you learned how packets move through networks, how TCP connections are established, how DNS resolves names, how firewalls control traffic, and how packet capture reveals what is happening on the wire.

Now we can combine those concepts into a typical production architecture.

A beginner may imagine a website like this:

```text
User
  |
  v
Web Server
```

Real production systems frequently look more like this:

```text
                         Internet
                            |
                            v
                           DNS
                            |
                            v
                    Public Load Balancer
                            |
              +-------------+-------------+
              |             |             |
              v             v             v
           App-01         App-02         App-03
              |             |             |
              +-------------+-------------+
                            |
                            v
                         Database
```

The client may never communicate directly with `App-01`, `App-02`, or `App-03`.

Instead, the client connects to a load balancer or reverse proxy.

That component decides where the request should go.

This architecture allows systems to:

* handle more traffic
* survive server failures
* distribute requests
* perform maintenance with less disruption
* scale horizontally
* centralize TLS handling
* perform health checks
* route traffic based on application information
* provide highly available services

The central mental model for this part is:

> A production request often passes through one or more intermediaries before reaching the application that actually processes it.

---

# 1. Why One Server Is Often Insufficient

Imagine an online store running on one server:

```text
Users
  |
  v
App-01
```

At first, this might work perfectly.

Suppose `App-01` can comfortably process:

```text
1,000 requests per second
```

Traffic eventually increases to:

```text
3,000 requests per second
```

Now the server may experience:

```text
High CPU
High memory usage
Slow responses
Connection queues
Timeouts
Application failures
```

There is another problem.

What happens if `App-01` crashes?

```text
Users
  |
  v
App-01
  X
```

The entire application may become unavailable.

The server has become a:

```text
Single Point of Failure
```

or:

```text
SPOF
```

---

# 2. What Is a Single Point of Failure?

A single point of failure is a component whose failure can make the entire service unavailable.

Example:

```text
Internet
   |
   v
Load Balancer
   |
   v
App-01
```

Even though a load balancer exists, there is still only one application server.

If `App-01` fails:

```text
Internet
   |
   v
Load Balancer
   |
   X
 App-01
```

there is nowhere else to send requests.

Redundancy is one of the fundamental principles of high availability.

---

# 3. Scaling Applications

When a server reaches its limits, you generally have two broad scaling approaches:

```text
Vertical scaling
Horizontal scaling
```

These solve capacity problems differently.

---

# 4. Vertical Scaling

Vertical scaling means making one machine more powerful.

For example:

```text
Before

4 CPU
8 GB RAM

        |
        v

After

16 CPU
64 GB RAM
```

You may hear this called:

```text
Scaling up
```

---

# 5. Advantages of Vertical Scaling

Vertical scaling can be relatively simple.

You may not need to redesign the application immediately.

Instead of managing multiple application instances:

```text
App-01
App-02
App-03
```

you continue running:

```text
App-01
```

but on stronger infrastructure.

---

# 6. Limitations of Vertical Scaling

Machines have limits.

Eventually:

```text
More CPU
More RAM
More storage
```

becomes:

```text
Expensive
Unavailable
Operationally difficult
```

More importantly, making one server enormous does not automatically eliminate its role as a single point of failure.

```text
Very Powerful Server
         X
```

is still failed infrastructure.

---

# 7. Horizontal Scaling

Horizontal scaling means adding more application instances.

```text
             +--> App-01
             |
Traffic -----+--> App-02
             |
             +--> App-03
```

You may hear this called:

```text
Scaling out
```

Instead of making one machine increasingly powerful, workload is distributed across multiple machines or instances.

---

# 8. Horizontal Scaling Example

Suppose each application server can process approximately:

```text
1,000 requests/second
```

You might deploy:

```text
App-01
App-02
App-03
App-04
```

to increase aggregate capacity.

This is simplified because real capacity does not always scale perfectly linearly.

Applications can also be constrained by:

```text
Database capacity
Shared storage
External APIs
Network bandwidth
Locks
Queues
Caches
```

Adding application servers does not automatically remove every bottleneck.

---

# 9. Horizontal Scaling Creates a New Question

Suppose you have:

```text
App-01 = 10.0.1.10
App-02 = 10.0.1.11
App-03 = 10.0.1.12
```

Which server should the user contact?

You do not normally want every client manually deciding:

```text
Maybe App-01.

Maybe App-02.

Maybe App-03.
```

You need a traffic distribution mechanism.

That leads us to load balancing.

---

# 10. What Is Load Balancing?

Load balancing distributes network connections or application requests across multiple backend systems.

Architecture:

```text
                    Users
                      |
                      v
                Load Balancer
                 203.0.113.20
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
       App-01       App-02       App-03
      10.0.1.10    10.0.1.11    10.0.1.12
```

Clients connect to the load balancer.

The load balancer selects an appropriate backend.

---

# 11. Frontend vs Backend

Load-balancing terminology can initially be confusing.

A simplified model is:

```text
Client
  |
  v
Frontend / Listener
  |
  v
Load Balancer
  |
  v
Backend Pool
  |
  +--> Backend-01
  +--> Backend-02
  +--> Backend-03
```

The frontend side accepts client traffic.

The backend side contains systems that actually process requests.

Terminology varies between products.

You may encounter terms such as:

```text
Listener
Frontend
Virtual server
Target group
Backend pool
Origin
Upstream
Target
```

Learn the concept rather than memorizing one vendor's vocabulary.

---

# 12. Load Balancers Do More Than Distribute Traffic

Modern load balancers can provide functions such as:

```text
Traffic distribution
Health checking
TLS termination
Routing
Session persistence
Connection draining
Backend failover
Logging
Metrics
Security integration
```

Some Layer 7 load balancers can even route requests based on:

```text
Hostname
Path
Headers
Methods
Cookies
```

depending on the product.

---

# 13. Layer 4 Load Balancing

Layer 4 load balancing operates primarily using transport/network information.

Think:

```text
IP addresses
TCP
UDP
Ports
Connections
```

Example:

```text
Client
  |
  | TCP 443
  v
L4 Load Balancer
  |
  +--> Server A:443
  |
  +--> Server B:443
```

The load balancer does not necessarily need to understand the HTTP request itself.

---

# 14. Layer 4 Decision Example

Suppose traffic arrives for:

```text
203.0.113.20:443
```

The L4 load balancer may select:

```text
10.0.1.10:443
```

or:

```text
10.0.1.11:443
```

based on connection-level information and its balancing algorithm.

It primarily deals with transport-level traffic rather than application semantics such as:

```text
/api/orders
```

or:

```text
Host: shop.example.com
```

---

# 15. Why Use Layer 4 Load Balancing?

Potential advantages include:

```text
Protocol flexibility
High throughput
Lower application-layer processing
TCP/UDP support
TLS passthrough possibilities
```

Layer 4 load balancing is useful when application-layer inspection is unnecessary.

---

# 16. Layer 7 Load Balancing

Layer 7 load balancing understands application-layer protocols, commonly HTTP and HTTPS.

Example:

```text
Client
  |
  v
HTTPS Request
  |
  v
Layer 7 Load Balancer
```

It may inspect information such as:

```text
Hostname
Path
Headers
Cookies
HTTP method
```

and make routing decisions accordingly.

---

# 17. Path-Based Routing

Suppose the application consists of multiple services.

```text
shop.example.com/products
shop.example.com/orders
shop.example.com/payments
```

A Layer 7 load balancer might route:

```text
/products/*
      |
      v
Product Service
```

```text
/orders/*
      |
      v
Order Service
```

```text
/payments/*
      |
      v
Payment Service
```

One public entry point can therefore route traffic to multiple backend services.

---

# 18. Host-Based Routing

Suppose:

```text
api.example.com
shop.example.com
admin.example.com
```

all resolve to the same load-balancer infrastructure.

The load balancer can inspect the requested hostname and route:

```text
api.example.com
      |
      v
API Pool
```

```text
shop.example.com
      |
      v
Web Pool
```

```text
admin.example.com
      |
      v
Admin Pool
```

This is common in modern web architectures.

---

# 19. Layer 4 vs Layer 7

| Feature                 | Layer 4           | Layer 7                      |
| ----------------------- | ----------------- | ---------------------------- |
| Main awareness          | IP/transport      | Application protocol         |
| TCP                     | Yes               | Often                        |
| UDP                     | Commonly possible | Product/protocol dependent   |
| HTTP path routing       | No                | Yes                          |
| HTTP header inspection  | No                | Yes                          |
| Host-based HTTP routing | No                | Yes                          |
| TLS passthrough         | Common use case   | Possible depending on design |
| TLS termination         | Product dependent | Very common                  |

Do not interpret this table as saying every product behaves identically.

Load-balancer capabilities vary.

---

# 20. Load-Balancing Algorithms

Once multiple healthy backends exist, the load balancer must decide:

> Which backend should receive this traffic?

That decision is made according to a balancing algorithm or routing policy.

Common examples include:

```text
Round robin
Least connections
Weighted routing
Hash-based methods
Randomized methods
```

We will focus on the core methods.

---

# 21. Round Robin

Round robin distributes traffic across backends in sequence.

Suppose:

```text
Backend A
Backend B
Backend C
```

Requests might be assigned:

```text
Request 1 -> A
Request 2 -> B
Request 3 -> C
Request 4 -> A
Request 5 -> B
Request 6 -> C
```

Then the cycle continues.

---

# 22. Round Robin Is Simple

Round robin works well when backend servers have roughly similar capabilities and workloads.

But requests are not necessarily equal.

Consider:

```text
Request A:
GET /health
Processing time: 5 ms
```

versus:

```text
Request B:
Generate financial report
Processing time: 20 seconds
```

Sending an equal number of requests to each backend does not necessarily produce equal workload.

---

# 23. Least Connections

Least-connections balancing considers how many active connections backends currently have.

Example:

```text
App-01 = 100 active connections
App-02 = 40 active connections
App-03 = 75 active connections
```

A new connection may be directed toward:

```text
App-02
```

because it currently has fewer active connections.

---

# 24. Why Least Connections Can Help

Imagine some connections last:

```text
50 milliseconds
```

while others last:

```text
30 seconds
```

Simple round robin may create uneven concurrent load.

Least-connections strategies can sometimes distribute long-lived connection workloads more effectively.

Again, exact implementations differ.

---

# 25. Weighted Routing

Sometimes backends have different capacities.

Example:

```text
App-01
4 CPU
Weight: 1

App-02
16 CPU
Weight: 4
```

You might intentionally direct more traffic toward `App-02`.

Conceptually:

```text
App-01 -> 20%
App-02 -> 80%
```

The exact relationship between weight and traffic depends on the balancing implementation.

---

# 26. Why Weighted Routing Is Useful

Weighted routing can help with:

```text
Different server capacities
Gradual migrations
Canary releases
Controlled traffic shifts
Mixed instance sizes
```

Example:

```text
Old Version
Weight: 90

New Version
Weight: 10
```

This can support gradual rollout strategies where the platform supports appropriate weighted routing.

---

# 27. Health Checks

Load balancing becomes much more useful when the load balancer knows whether a backend is healthy.

Suppose:

```text
App-01 = healthy
App-02 = healthy
App-03 = crashed
```

Without health checks:

```text
Load Balancer
   |
   +--> App-01
   +--> App-02
   +--> App-03 X
```

Some requests may continue going to the failed backend.

---

# 28. What Is a Health Check?

A health check is a periodic test used to determine whether a backend should receive traffic.

Examples include:

```text
TCP connection check
HTTP request
HTTPS request
Application-specific endpoint
```

For a web application, the load balancer might request:

```text
GET /health
```

and expect:

```text
HTTP 200
```

---

# 29. Healthy Backends

If:

```text
App-01 -> health check succeeds
App-02 -> health check succeeds
App-03 -> health check fails
```

the load balancer may maintain:

```text
Healthy Pool

App-01
App-02
```

and stop sending normal traffic to:

```text
App-03
```

until it becomes healthy again.

---

# 30. Healthy Does Not Mean Perfect

A health check only proves whatever the health check actually tested.

Suppose:

```text
GET /health
```

returns:

```text
200 OK
```

but the application's database is unavailable.

If `/health` does not test critical dependencies, the load balancer may consider the backend healthy even though real user requests fail.

---

# 31. Health Checks Can Also Be Too Strict

Imagine `/health` checks:

```text
Application
Database
Redis
External payment API
Email provider
Analytics service
```

A temporary analytics outage could make every application instance report unhealthy.

The load balancer might remove all of them.

Now a non-critical dependency has caused complete application unavailability.

Health-check design matters.

---

# 32. Health Check Parameters

Health checks commonly have configurable properties such as:

```text
Protocol
Port
Path
Interval
Timeout
Healthy threshold
Unhealthy threshold
Expected response
```

For example:

```text
Protocol: HTTP
Port: 8080
Path: /health
Interval: 10 seconds
Timeout: 3 seconds
Unhealthy threshold: 3
```

Exact capabilities depend on the load balancer.

---

# 33. Health Check Failure Does Not Always Mean Application Failure

Suppose users can reach:

```text
App-01:8080
```

directly.

But the load balancer reports:

```text
App-01 unhealthy
```

Possible causes include:

```text
Wrong health-check port
Wrong health-check path
Firewall blocks health-check source
Application bound to wrong interface
Health check expects wrong status
TLS mismatch
Health endpoint dependency failure
Network routing problem
```

Always troubleshoot the health-check path separately.

---

# Proxies

# 34. What Is a Proxy?

A proxy is an intermediary in communication.

Instead of:

```text
Client ------------------> Server
```

you may have:

```text
Client ------> Proxy ------> Server
```

The proxy participates in communication between the two sides.

But "proxy" covers several different architectural roles.

Two important categories are:

```text
Forward proxy
Reverse proxy
```

---

# 35. Forward Proxy

A forward proxy primarily represents clients.

Architecture:

```text
Client
  |
  v
Forward Proxy
  |
  v
Internet
  |
  v
Destination Server
```

The destination server may see the proxy as the immediate network peer rather than the original client.

---

# 36. Forward Proxy Example

Corporate network:

```text
Employee Laptop
       |
       v
Corporate Proxy
       |
       v
Internet
```

The organization may use the proxy for purposes such as:

```text
Outbound access control
Logging
Policy enforcement
Content filtering
Caching
Security inspection
```

depending on configuration.

---

# 37. Who Knows About a Forward Proxy?

In an explicit forward-proxy architecture, the client is configured to use the proxy.

For example:

```text
Browser
   |
   | "Send outbound requests through proxy.company.local"
   v
Forward Proxy
```

There are also transparent/intercepting proxy architectures, so do not assume every forward proxy requires explicit client configuration.

---

# Reverse Proxies

# 38. What Is a Reverse Proxy?

A reverse proxy primarily represents servers.

Architecture:

```text
Internet Client
      |
      v
Reverse Proxy
      |
      +--> App-01
      |
      +--> App-02
      |
      +--> App-03
```

The client connects to the reverse proxy.

The reverse proxy communicates with backend servers.

---

# 39. Why Use a Reverse Proxy?

Reverse proxies can provide:

```text
TLS termination
Load balancing
Routing
Caching
Compression
Header manipulation
Access control
Logging
Rate limiting
Backend abstraction
```

depending on the software and configuration.

---

# 40. Forward Proxy vs Reverse Proxy

A useful mental model:

```text
Forward Proxy
represents/protects clients.

Reverse Proxy
represents/protects servers.
```

Architecture comparison:

```text
FORWARD PROXY

Clients
   |
   v
Proxy
   |
   v
Internet Servers
```

```text
REVERSE PROXY

Internet Clients
   |
   v
Proxy
   |
   v
Backend Servers
```

---

# 41. Proxy vs Reverse Proxy

"Proxy" is the broader concept.

A reverse proxy is a specific proxy role.

Therefore:

```text
All reverse proxies are proxies.

Not all proxies are reverse proxies.
```

When someone simply says "proxy," determine which direction and purpose they mean.

---

# 42. Reverse Proxy vs Load Balancer

These concepts overlap.

A reverse proxy can often load balance.

A load balancer can often behave as a reverse proxy.

For example:

```text
Client
  |
  v
NGINX
  |
  +--> App-01
  +--> App-02
```

NGINX is acting as:

```text
Reverse proxy
+
Load balancer
```

Do not treat these terms as mutually exclusive product categories.

Think about the function being performed.

---

# NGINX Concepts

# 43. What Is NGINX?

NGINX is widely used as:

```text
Web server
Reverse proxy
Load balancer
TLS endpoint
HTTP gateway
```

A common architecture:

```text
Internet
   |
   v
NGINX
   |
   +--> App-01:8080
   |
   +--> App-02:8080
```

NGINX receives client requests and proxies them to upstream applications.

---

# 44. Basic NGINX Reverse Proxy Concept

A simplified configuration might look like:

```nginx
server {
    listen 80;

    location / {
        proxy_pass http://127.0.0.1:8080;
    }
}
```

Conceptually:

```text
Client -> NGINX:80 -> Application:8080
```

The client does not need to connect directly to port `8080`.

---

# 45. NGINX Upstream Concept

For multiple backend servers, NGINX can define an upstream group.

Simplified:

```nginx
upstream backend {
    server 10.0.1.10:8080;
    server 10.0.1.11:8080;
}

server {
    listen 80;

    location / {
        proxy_pass http://backend;
    }
}
```

Traffic flow:

```text
Client
  |
  v
NGINX
  |
  +--> 10.0.1.10:8080
  |
  +--> 10.0.1.11:8080
```

This is a conceptual beginner example. Production configuration requires additional security, timeout, logging, TLS, header, health, and operational considerations.

---

# 46. Proxy Headers

When a reverse proxy creates a new connection to a backend, the backend may otherwise see information associated with the proxy connection rather than the original client connection.

HTTP proxy architectures commonly use headers to preserve relevant request context.

Examples include concepts such as:

```text
Host
X-Forwarded-For
X-Forwarded-Proto
```

and standardized `Forwarded` headers.

---

# 47. Why Original Client Information Matters

Suppose:

```text
Client IP:
198.51.100.25

Reverse Proxy:
10.0.1.5

Backend:
10.0.2.10
```

At the network layer, the backend may see a connection from:

```text
10.0.1.5
```

because that is the proxy.

But application logs may need to know the original client address.

Trusted proxy metadata can help preserve this information.

---

# 48. Never Blindly Trust Forwarded Headers

A client may be able to send its own:

```text
X-Forwarded-For
```

header.

Applications should only trust forwarding information according to a properly configured trusted-proxy architecture.

Otherwise, attackers may spoof client-address metadata.

---

# HAProxy Concepts

# 49. What Is HAProxy?

HAProxy is widely used for:

```text
Load balancing
Reverse proxying
TCP proxying
HTTP proxying
High-availability traffic distribution
```

It is common in infrastructure where high-performance Layer 4 or Layer 7 traffic management is required.

---

# 50. HAProxy Frontend and Backend Concepts

A simplified mental model:

```text
HAProxy

Frontend
   |
   v
Traffic rules
   |
   v
Backend
   |
   +--> Server 1
   +--> Server 2
```

A frontend defines where/how traffic enters.

A backend defines where traffic can be sent.

Exact HAProxy configuration details become more important when you operate it directly.

---

# 51. Simplified HAProxy Example

Conceptually:

```text
Frontend:
listen on :443

Backend:
10.0.1.10:8080
10.0.1.11:8080
```

Traffic:

```text
Client
   |
   v
HAProxy:443
   |
   +--> App-01:8080
   |
   +--> App-02:8080
```

HAProxy can operate at both TCP and HTTP levels depending on configuration.

# Cloud Load Balancers

# 52. Managed Cloud Load Balancers

Cloud providers offer managed load-balancing services.

Instead of operating:

```text
Your own NGINX/HAProxy VM cluster
```

you can use a cloud-managed service.

The provider manages much of the load-balancer infrastructure itself.

---

# 53. Why Managed Load Balancers Are Popular

Managed services can reduce the need to manually manage:

```text
Load-balancer servers
Redundancy
Software upgrades
Capacity
Failover infrastructure
```

You still need to configure:

```text
Listeners
Backends
Health checks
Routing
Security
TLS
Networking
```

Managed does not mean configuration-free.

---

# 54. Cloud Load Balancer Architecture

Example:

```text
Internet
   |
   v
Cloud Load Balancer
   |
   +-------------------+
   |                   |
   v                   v
Availability Zone A   Availability Zone B
   |                   |
   v                   v
App-01                App-02
```

This can form part of a highly available architecture.

---

# 55. Public Load Balancer

A public or internet-facing load balancer provides an entry point reachable according to its public networking configuration.

Example:

```text
Internet
   |
   v
Public Load Balancer
   |
   v
Private Application Servers
```

The backend servers do not necessarily need public addresses.

This is an important architecture pattern.

---

# 56. Public Does Not Mean "Allow Everything"

A public load balancer may still be protected by:

```text
Firewalls
Security groups
WAF policies
Authentication
TLS
Access-control rules
```

"Public" describes network reachability characteristics, not the absence of security.

---

# 57. Internal Load Balancer

An internal/private load balancer is intended for private network access.

Example:

```text
Frontend Service
       |
       v
Internal Load Balancer
       |
       v
Backend API Servers
```

It might be reachable only from:

```text
VPC
Private network
VPN
Connected corporate network
```

depending on architecture.

---

# 58. Public and Internal Load Balancers Together

A production environment may contain both:

```text
Internet
   |
   v
Public LB
   |
   v
Web Tier
   |
   v
Internal LB
   |
   v
Application Tier
```

This avoids exposing internal services directly to the Internet.

# Backend Pools

# 59. What Is a Backend Pool?

A backend pool is a collection of systems eligible to receive traffic.

Example:

```text
Backend Pool: payments-api

10.0.2.10:8080
10.0.2.11:8080
10.0.3.10:8080
10.0.3.11:8080
```

The load balancer chooses among healthy eligible backends according to its configuration.

---

# 60. Backend Registration

A backend generally must be registered or discoverable by the load-balancing system.

Depending on the platform, a backend might be:

```text
VM
IP address
Container
Kubernetes workload
Instance group
Service
Serverless target
```

The exact target types vary.

---

# 61. Backend Port Can Differ From Frontend Port

Example:

```text
Client
  |
  | HTTPS 443
  v
Load Balancer
  |
  | HTTP 8080
  v
Application
```

The frontend listener port does not have to match the backend application port.

This is common when TLS terminates at the load balancer.

# TLS Termination

# 62. What Is TLS Termination?

Suppose:

```text
Client
  |
  | HTTPS
  v
Load Balancer
  |
  | HTTP
  v
Backend
```

The TLS connection ends at the load balancer.

The load balancer:

1. receives the encrypted connection
2. performs TLS negotiation
3. decrypts the HTTP traffic
4. forwards a request toward the backend

This is TLS termination.

---

# 63. Why Terminate TLS at a Load Balancer?

Possible benefits include:

```text
Centralized certificate management
Reduced certificate management on every backend
Layer 7 request inspection
Host/path routing
Centralized TLS policy
```

It can simplify application-server configuration.

---

# 64. TLS Termination Does Not Require Plaintext Backend Traffic

This is an important distinction.

You can have:

```text
Client
  |
  | HTTPS
  v
Load Balancer
  |
  | HTTPS
  v
Backend
```

The load balancer terminates the client TLS connection and establishes another TLS connection to the backend.

This is often called:

```text
TLS re-encryption
```

or similar terminology depending on the product.

---

# 65. Two TLS Connections

With termination and re-encryption:

```text
Client
  |
  | TLS Connection 1
  v
Load Balancer
  |
  | TLS Connection 2
  v
Backend
```

These are separate connections.

The backend is not participating directly in the client's original TLS session.

---

# TLS Passthrough

# 66. What Is TLS Passthrough?

With TLS passthrough, the load-balancing/proxy layer forwards encrypted TLS traffic without terminating the client TLS session at that layer.

Conceptually:

```text
Client
  |
  | Encrypted TLS
  v
L4 Load Balancer
  |
  | Encrypted TLS
  v
Backend
```

The backend performs TLS termination.

---

# 67. Why Use TLS Passthrough?

Possible reasons include:

```text
End-to-end client-to-backend TLS requirement
Backend-controlled certificates
Application-specific TLS behavior
Reduced TLS awareness at intermediary
```

But passthrough also reduces the intermediary's ability to inspect HTTP-layer information.

---

# 68. Termination vs Passthrough

TLS termination:

```text
Client
   |
 HTTPS
   |
   v
Load Balancer
   |
 decrypted/possibly re-encrypted
   |
   v
Backend
```

TLS passthrough:

```text
Client
   |
 HTTPS
   |
   v
Load Balancer
   |
 encrypted stream
   |
   v
Backend
```

This difference is extremely important when troubleshooting certificates and Layer 7 routing.

---

# 69. Which Certificate Does the Client See?

With TLS termination at the load balancer:

```text
Client
   |
   v
Load Balancer Certificate
```

The client validates the certificate presented by the load balancer.

With TLS passthrough:

```text
Client
   |
   v
Backend Certificate
```

because the TLS session continues to the backend.

This distinction helps locate certificate failures.

# SNI and Load Balancing

# 70. SNI Can Matter

As learned in TLS, Server Name Indication can tell the TLS endpoint which hostname the client is requesting.

This enables architectures where multiple hostnames share an IP/listener.

Example:

```text
api.example.com
shop.example.com
admin.example.com
        |
        v
Shared Load Balancer
```

The load balancer may select appropriate TLS configuration based on hostname information.

Exact behavior depends on termination/passthrough architecture and product capabilities.

# Sticky Sessions

# 71. The Session Problem

Suppose:

```text
Request 1 -> App-01
Request 2 -> App-02
Request 3 -> App-03
```

This works beautifully if the application is stateless.

But suppose user session information exists only in memory on `App-01`.

```text
App-01:
User Ann session exists

App-02:
No session

App-03:
No session
```

Request 1 succeeds.

Request 2 reaches `App-02`.

The application may think the user is no longer logged in.

---

# 72. What Are Sticky Sessions?

Sticky sessions attempt to keep a client's requests associated with the same backend.

Example:

```text
User A
  |
  +--> App-01
  +--> App-01
  +--> App-01
```

User B:

```text
User B
  |
  +--> App-02
  +--> App-02
  +--> App-02
```

This is also called:

```text
Session persistence
```

or:

```text
Session affinity
```

---

# 73. How Sticky Sessions Can Work

Depending on the product, affinity may use mechanisms such as:

```text
Cookies
Source-address hashing
Application-generated information
Load-balancer-generated identifiers
```

Implementation varies.

---

# 74. Sticky Sessions Have Tradeoffs

Sticky sessions can create uneven distribution.

Suppose many heavy users become attached to:

```text
App-01
```

while:

```text
App-02
App-03
```

remain lightly loaded.

Sticky sessions can also complicate backend failure because the preferred server may disappear.

---

# 75. Stateless Applications Scale More Easily

A common scalable design stores session state outside individual application instances.

Example:

```text
                  +--> App-01
                  |
Load Balancer ----+--> App-02
                  |
                  +--> App-03
                         |
                         v
                    Shared Redis
```

Now any application instance can retrieve session information.

This reduces the need for strong backend affinity.

---

# 76. Stateless Does Not Mean "No Data"

A stateless application instance can still use:

```text
Database
Redis
Object storage
Queues
External state stores
```

The important idea is that the application instance itself does not need to retain unique local session state between requests.

---

# Connection Draining

# 77. The Deployment Problem

Suppose:

```text
App-01
App-02
App-03
```

are serving production traffic.

You need to remove `App-02` for deployment.

If you immediately terminate it:

```text
App-02 X
```

existing requests or connections may be interrupted.

---

# 78. What Is Connection Draining?

Connection draining allows a backend to stop receiving new traffic while existing connections or in-flight requests are given time to finish.

Conceptually:

```text
App-02 state:

New traffic: NO

Existing traffic:
Allow to complete
```

After the drain period:

```text
App-02
can be safely removed
```

within the limits of the configured timeout and application behavior.

---

# 79. Why Connection Draining Matters

Without graceful draining, deployments can cause:

```text
Dropped requests
Connection resets
502 errors
User-visible failures
Incomplete operations
```

Proper draining supports safer:

```text
Deployments
Autoscaling
Maintenance
Instance replacement
```

---

# 80. Draining Is Not Infinite

A load balancer generally cannot wait forever.

There may be a configured timeout.

For example:

```text
Drain timeout:
60 seconds
```

If a connection exceeds that behavior, it may eventually be terminated depending on implementation.

Long-lived connections require special consideration.

---

# High Availability

# 81. What Is High Availability?

High availability means designing a system to remain available despite expected component failures.

It does not mean:

```text
Nothing ever fails.
```

It means:

```text
Failures occur,
but the architecture reduces their impact.
```

---

# 82. Redundancy

Consider:

```text
App-01
```

versus:

```text
App-01
App-02
App-03
```

Multiple instances provide redundancy.

But only if traffic can be redirected when one fails.

That is why:

```text
Redundancy
+
Health checks
+
Traffic management
```

work together.

---

# 83. High Availability Across Failure Domains

Suppose all three servers are in one physical or logical failure domain:

```text
Zone A

App-01
App-02
App-03
```

If Zone A fails:

```text
App-01 X
App-02 X
App-03 X
```

all redundancy disappears simultaneously.

A stronger design may distribute workloads:

```text
Zone A               Zone B

App-01               App-03
App-02               App-04
```

The exact failure domains depend on the infrastructure.

---

# 84. High Availability Is End-to-End

Having redundant application servers is not enough.

Consider:

```text
Internet
   |
   v
Load Balancer
   |
   +--> App-01
   +--> App-02
   +--> App-03
           |
           v
        Database
```

If there is only one database and it fails:

```text
Database X
```

the application may still fail.

High availability must consider the complete dependency chain.

---

# 85. Hidden Single Points of Failure

Potential SPOFs include:

```text
DNS
Load balancer
Firewall
Router
Application server
Database
Cache
Storage
Identity service
Certificate infrastructure
Network connection
Availability zone
```

A production architecture review should repeatedly ask:

> What happens if this component disappears?

---

# Active-Active

# 86. What Is Active-Active?

In active-active architecture, multiple systems actively serve traffic at the same time.

Example:

```text
               Load Balancer
                    |
            +-------+-------+
            |               |
            v               v
         App-01           App-02
         ACTIVE           ACTIVE
```

Both process production requests.

---

# 87. Advantages of Active-Active

Potential benefits include:

```text
Better resource utilization
Traffic distribution
Fast failure response
Horizontal scaling
```

If one backend fails:

```text
App-01 X
App-02 ACTIVE
```

the surviving backend can continue handling traffic, assuming sufficient capacity and healthy dependencies.

---

# 88. Active-Active Capacity Planning

Suppose:

```text
App-01 capacity = 1,000 req/s
App-02 capacity = 1,000 req/s
```

Normal traffic:

```text
1,800 req/s
```

Everything works when both are healthy.

If `App-01` fails:

```text
App-02 receives 1,800 req/s
```

but can only handle:

```text
1,000 req/s
```

Your architecture was redundant but lacked sufficient failure capacity.

High availability requires capacity planning.

---

# Active-Passive

# 89. What Is Active-Passive?

In active-passive architecture:

```text
Primary
ACTIVE

Secondary
PASSIVE/STANDBY
```

The active system serves normal traffic.

The passive system waits to take over if necessary.

---

# 90. Failover

If the active system fails:

```text
Primary
X

Secondary
   |
   v
BECOMES ACTIVE
```

This process is called failover.

---

# 91. Active-Passive Tradeoffs

Advantages can include:

```text
Simpler state management in some architectures
Clear primary ownership
Standby recovery path
```

Potential disadvantages:

```text
Unused standby capacity
Failover delay
Failover complexity
Risk that standby is not actually ready
```

A standby that is never tested is not automatically reliable.

---

# 92. Active-Active vs Active-Passive

```text
ACTIVE-ACTIVE

Node A -> serving
Node B -> serving
```

```text
ACTIVE-PASSIVE

Node A -> serving
Node B -> waiting
```

Neither is universally superior.

The correct design depends on:

```text
Application architecture
State
Consistency requirements
Cost
Failure objectives
Operational complexity
```

---

# Load Balancer High Availability

# 93. The Load Balancer Can Become the SPOF

Suppose:

```text
Internet
   |
   v
LB-01
   |
   +--> App-01
   +--> App-02
```

If `LB-01` fails:

```text
Internet
   |
   X
 LB-01
```

both application servers become unreachable through that path.

You solved backend redundancy but introduced a load-balancer SPOF.

---

# 94. Redundant Load Balancers

Self-managed load-balancer architectures may use:

```text
LB-01
LB-02
```

with some form of failover, shared/virtual addressing, routing, DNS, or other HA mechanism.

Managed cloud load balancers generally abstract much of this infrastructure, but you still need to understand the service's availability model.

---

# 95. Do Not Assume "Managed" Means Immune to Failure

Managed services can still experience:

```text
Misconfiguration
Regional incidents
Dependency failures
Quota problems
Certificate problems
Routing problems
Backend failures
Operator mistakes
```

High availability still requires architectural understanding.

# HTTP Errors at Load Balancers

# 96. Why 502, 503, and 504 Matter

When using reverse proxies and load balancers, three HTTP status codes appear frequently during incidents:

```text
502 Bad Gateway

503 Service Unavailable

504 Gateway Timeout
```

These codes can provide clues about where a request failed.

But they should not be interpreted too rigidly because exact behavior depends on the proxy/load balancer/application.

---

# 502 Bad Gateway

# 97. What Does 502 Generally Mean?

A `502 Bad Gateway` generally means a gateway/proxy received an invalid or unsuccessful response while communicating with an upstream system.

Architecture:

```text
Client
   |
   v
Reverse Proxy
   |
   X
Backend
```

The proxy is reachable.

The problem occurs while it tries to interact with the upstream/backend.

---

# 98. Common 502 Causes

Possible causes include:

```text
Backend connection reset
Backend closed connection unexpectedly
Wrong backend protocol
Malformed upstream response
Backend unavailable
TLS problem between proxy and backend
Proxy/backend configuration mismatch
```

Example:

```text
Load Balancer
     |
     | expects HTTP
     v
Backend
     |
     | expects HTTPS
     X
```

Protocol mismatch can cause gateway failures.

---

# 99. 502 Does Not Mean "The Load Balancer Is Broken"

This is a common beginner mistake.

If the load balancer returns:

```text
502
```

the load balancer itself is clearly capable of returning an HTTP response to the client.

Investigate the load balancer's communication with its upstreams.

---

# 503 Service Unavailable

# 100. What Does 503 Generally Mean?

`503 Service Unavailable` indicates the service is currently unable to handle the request.

In load-balancing environments, common situations include:

```text
No healthy backends
Backend capacity exhausted
Application unavailable
Maintenance state
Overload
```

But exact semantics depend on the component generating the response.

---

# 101. No Healthy Backends

Suppose:

```text
App-01 unhealthy
App-02 unhealthy
App-03 unhealthy
```

The load balancer has:

```text
0 healthy targets
```

It may return an error such as `503`, depending on the product.

Therefore:

```text
503
```

should prompt you to inspect backend health and availability.

---

# 504 Gateway Timeout

# 102. What Does 504 Generally Mean?

A `504 Gateway Timeout` usually means a gateway/proxy did not receive the required response from an upstream service within its allowed time.

Example:

```text
Client
   |
   v
Proxy
   |
   | request
   v
Backend

Backend takes too long

   X

Proxy timeout reached
```

The proxy may return:

```text
504 Gateway Timeout
```

---

# 103. Common 504 Causes

Potential causes include:

```text
Slow backend
Database delay
External API delay
Network timeout
Packet loss
Backend deadlock
Overloaded server
Incorrect timeout configuration
```

A 504 is often about timing, but you still need evidence to determine why the upstream response did not arrive in time.

---

# 104. 502 vs 503 vs 504 Mental Model

Simplified:

```text
502
"I reached upstream territory,
but the upstream interaction/response was bad."

503
"The service cannot currently handle you."

504
"I waited for upstream,
but it did not complete in time."
```

These are useful mental models, not universal root-cause rules.

---

# 105. Find Who Generated the Error

Suppose the user sees:

```text
503 Service Unavailable
```

Possible generators include:

```text
CDN
WAF
Load balancer
NGINX
API gateway
Application
```

Do not assume the application produced the status code.

Check:

```text
Response headers
Proxy logs
Load-balancer logs
Application logs
Request IDs
```

where available.

# Load-Balancer Troubleshooting

# 106. Troubleshoot the System as Separate Connections

One of the most important concepts in this part is that a reverse-proxy architecture may contain multiple separate connections.

Example:

```text
Client
  |
  | Connection 1
  v
Load Balancer
  |
  | Connection 2
  v
Backend
```

If TLS is re-encrypted:

```text
Client
  |
  | TCP + TLS #1
  v
Load Balancer
  |
  | TCP + TLS #2
  v
Backend
```

Do not treat this as one uninterrupted TCP connection.

---

# 107. Troubleshooting Question 1: Can the Client Resolve the Load Balancer?

Check:

```bash
dig app.example.com
```

Ask:

```text
Does DNS return the expected endpoint?

Public or private address?

IPv4 or IPv6?

Correct environment?
```

---

# 108. Question 2: Can the Client Reach the Listener?

For HTTPS:

```bash
curl -v https://app.example.com
```

You may also test transport connectivity where appropriate:

```bash
nc -vz app.example.com 443
```

This separates basic TCP connectivity from HTTP/TLS behavior.

---

# 109. Question 3: Is the Listener Configured?

Check whether the load balancer actually accepts:

```text
Protocol: HTTPS
Port: 443
```

A load balancer existing does not automatically mean it has the correct listener.

---

# 110. Question 4: Is TLS Working?

For TLS inspection:

```bash
openssl s_client -connect app.example.com:443 -servername app.example.com
```

Check:

```text
Certificate presented
Hostname
Certificate chain
Handshake result
```

If TLS terminates at the load balancer, this primarily tests the client-facing TLS endpoint.

---

# 111. Question 5: Is the Routing Rule Correct?

Suppose:

```text
Host: api.example.com
Path: /payments
```

Expected backend:

```text
Payments Pool
```

But a routing rule sends:

```text
/payments
```

to:

```text
Default Web Pool
```

Network connectivity can be perfect while application routing is wrong.

---

# 112. Question 6: Are There Healthy Backends?

Inspect:

```text
Backend registration
Health status
Health-check failures
Ports
Health-check paths
Thresholds
```

If all targets are unhealthy, determine why.

Do not simply disable health checks.

---

# 113. Question 7: Can the Load Balancer Reach the Backend?

This is separate from:

```text
Can my laptop reach the backend?
```

The load balancer's network path matters.

Check:

```text
Firewall rules
Security groups
Network ACLs
Routes
Backend listening port
Backend binding
```

---

# 114. Backend Binding Problem

Suppose the backend application listens only on:

```text
127.0.0.1:8080
```

Check:

```bash
ss -lntp
```

You see:

```text
127.0.0.1:8080
```

The application works locally:

```bash
curl http://127.0.0.1:8080
```

But the load balancer cannot connect to the server's network address.

Why?

Because the application is listening only on loopback.

---

# 115. Do Not Blindly Change to `0.0.0.0`

The solution is not automatically:

```text
Bind everything publicly.
```

Choose an appropriate interface/binding and enforce network access controls.

The principle is:

> The application must listen on an address reachable through the intended backend path, while remaining appropriately protected.

---

# 116. Backend Port Mismatch

Load balancer expects:

```text
Backend port 8080
```

Application actually listens:

```text
8443
```

Health checks fail.

User requests fail.

Check:

```bash
sudo ss -lntp
```

and compare actual listener configuration with the load-balancer backend configuration.

---

# 117. Backend Protocol Mismatch

Load balancer sends:

```text
HTTP
```

Backend expects:

```text
HTTPS
```

or vice versa.

You may see:

```text
Health-check failure
502
TLS errors
Connection termination
```

depending on the implementation.

Verify:

```text
Frontend protocol
Backend protocol
Backend port
Health-check protocol
Health-check port
```

separately.

---

# 118. Health-Check Path Mismatch

Configured:

```text
/health
```

Application provides:

```text
/healthz
```

Result:

```text
404
```

The application is running, but the load balancer marks it unhealthy.

This tiny configuration error can remove every backend from service.

---

# 119. Authentication on Health Endpoints

Suppose:

```text
GET /health
```

requires authentication.

The load balancer sends no credentials.

Response:

```text
401 Unauthorized
```

The backend may be marked unhealthy even though the application itself is running.

Health endpoints need deliberate design.

---

# 120. Firewall Blocking Health Checks

Architecture:

```text
Load Balancer
     |
     | Health Check
     v
Firewall
     X
     |
Backend
```

The application is healthy.

But the load balancer cannot verify it.

Result:

```text
Backend marked unhealthy
```

Then production traffic may stop reaching it.

---

# 121. Health Check Works but User Traffic Fails

This can also happen.

Suppose health checks use:

```text
TCP 8080
```

They only verify:

```text
Can a TCP connection be established?
```

But actual application requests fail with:

```text
HTTP 500
```

The backend can pass a basic TCP health check while the application is unhealthy at Layer 7.

---

# 122. Packet Capture at the Backend

Suppose the load balancer says:

```text
Backend timeout
```

Capture on the backend:

```bash
sudo tcpdump -nn -i any 'tcp port 8080'
```

Reproduce the request.

Possible patterns provide different clues.

---

# 123. Pattern A: Nothing Arrives

Backend capture:

```text
No matching packets
```

Investigate:

```text
Load-balancer routing
Backend registration
Firewall
Security group
Network ACL
Routing
Wrong IP
Wrong port
Wrong capture interface
```

---

# 124. Pattern B: SYN Arrives, Backend Sends RST

```text
Load Balancer -> Backend    SYN
Backend -> Load Balancer    RST
```

Possible explanation:

```text
Nothing listening on expected backend port
```

or another active rejection.

Check:

```bash
ss -lntp
```

---

# 125. Pattern C: TCP Handshake Completes

```text
SYN
SYN-ACK
ACK
```

Now basic backend TCP connectivity works.

Move upward:

```text
TLS
HTTP
Application
```

---

# 126. Pattern D: Request Arrives, Response Is Slow

```text
TCP established
HTTP request arrives

... 30 seconds ...

Response
```

If the load balancer has a:

```text
10-second upstream timeout
```

the client may receive a gateway timeout before the backend eventually responds.

The problem may be application latency rather than network connectivity.

---

# 127. Pattern E: Backend Resets Connection

```text
Handshake succeeds
Request arrives
RST
```

Investigate:

```text
Application crash
Application/proxy behavior
Protocol mismatch
Timeouts
Backend resource exhaustion
```

Use packet capture together with application logs.

---

# 128. Compare Proxy and Backend Logs

A powerful production investigation uses multiple evidence sources:

```text
Client result
      |
      v
Load-balancer access log
      |
      v
Load-balancer error log
      |
      v
Backend access log
      |
      v
Backend application log
      |
      v
Packet capture
```

The goal is to determine where the request stopped.

---

# 129. Request IDs

Distributed systems often attach request or correlation IDs.

Example:

```text
X-Request-ID: abc123
```

You can search:

```text
Load balancer logs
NGINX logs
Application logs
Tracing systems
```

for:

```text
abc123
```

This can connect one user's failure across multiple components.

---

# 130. Client IP Troubleshooting

Suppose application logs show every request coming from:

```text
10.0.1.5
```

That may be the reverse proxy.

If the application needs the original client address, inspect trusted forwarding configuration.

Do not assume NAT or networking is broken merely because the backend sees the proxy as its immediate peer.

# 131. Timeouts Exist at Multiple Layers

Consider:

```text
Client
  |
  v
CDN
  |
  v
Load Balancer
  |
  v
NGINX
  |
  v
Application
  |
  v
Database
```

Each component may have its own timeout.

For example:

```text
Client timeout
CDN timeout
Load-balancer timeout
NGINX upstream timeout
Application timeout
Database timeout
```

The shortest relevant timeout may determine what the user experiences.

---

# 132. Timeout Mismatch

Suppose:

```text
Application can take:
60 seconds

Load balancer timeout:
30 seconds
```

The application may successfully finish after:

```text
45 seconds
```

but the client already received a timeout at 30 seconds.

The application log may even show:

```text
Request completed successfully
```

while the user saw:

```text
504
```

This is why timestamps matter.

---

# 133. Long-Lived Connections

Applications may use long-lived connections such as:

```text
WebSockets
Streaming connections
Long polling
Persistent TCP connections
```

Load-balancer configuration must account for them.

Timeouts designed for short HTTP requests can disrupt legitimate long-lived communication.

---

# 134. Persistent Connections and Load Balancing

Remember from HTTP:

```text
One TCP connection
```

can potentially carry multiple HTTP requests depending on protocol and connection behavior.

Therefore:

```text
10 requests
```

does not necessarily mean:

```text
10 independent load-balancing decisions
```

The exact behavior depends on:

```text
HTTP version
Connection reuse
Load-balancer architecture
Backend connection reuse
```

---

# 135. HTTP/2 Adds More Complexity

HTTP/2 can multiplex multiple streams over one connection.

Therefore, reasoning about:

```text
requests
connections
backend selections
```

requires understanding where the load balancer terminates and creates connections.

Do not assume one HTTP request always equals one TCP connection.

---

# 136. HTTP/3 Adds Another Transport Model

HTTP/3 uses QUIC over UDP.

Therefore, a load-balancing architecture supporting HTTP/3 may have:

```text
Client
  |
  | QUIC / UDP 443
  v
Load Balancer
```

The backend side may use the same or a different protocol depending on the platform.

Always distinguish:

```text
Client-facing protocol
```

from:

```text
Backend-facing protocol
```

---

# 137. Load Balancers and NAT

Depending on architecture and product, traffic reaching a backend may have undergone:

```text
Address translation
Proxy connection creation
Source-address preservation
Destination translation
```

Do not assume the backend always sees the client's original Layer 3 source address.

This is why understanding NAT, proxies, and forwarding metadata together matters.

---

# 138. Load Balancer vs DNS Load Distribution

DNS itself can sometimes return multiple endpoints.

Example:

```text
app.example.com

A -> 192.0.2.10
A -> 192.0.2.20
```

This can contribute to traffic distribution.

But DNS-based distribution differs from a traditional proxy/load-balancer architecture because:

```text
DNS answers can be cached.

Clients may choose addresses differently.

DNS does not observe every application request.
```

DNS balancing and proxy balancing solve related but different problems.

---

# 139. Load Balancer vs CDN

A CDN may also sit in front of an application.

Example:

```text

  |
  v

  |
  v

  |
  v

```

The CDN may:

```text

```

The load balancer then distributes origin traffic among backends.

Production systems may therefore contain several proxy-like layers.

# 140. Load Balancer vs API Gateway


and may also distribute requests.

```text

```

rather than only:

```text

```


# 142. The Wrong Troubleshooting Approach

Suppose users report:

```text
502 Bad Gateway
```

Weak approach:

```text
Restart NGINX.
```

Why is this weak?

Because you have not established:

```text
Which component generated 502
Whether backend is healthy
Whether TCP works
Whether TLS works
Whether the correct backend is selected
Whether the backend returned something invalid
```

Restarting destroys evidence and may temporarily hide the root cause.

# 160. High Availability Failure Scenario

Architecture:

```text
                    Internet
                       |
                       v
                 Load Balancer
                       |
            +----------+----------+
            |                     |
            v                     v
          Zone A                Zone B
            |                     |
            v                     v
         App-01                 App-02
```

Everything looks redundant.

But both applications connect to:

```text
DB-01
```

in Zone A.

Architecture:

```text
App-01 -----+
            |
            +----> DB-01
            |
App-02 -----+
```

If `DB-01` fails:

```text
App-01 cannot function
App-02 cannot function
```

The application tier was redundant.

The complete service was not.


```text
Redundancy
```

but not enough:

```text

```

High availability is more than duplicating servers.

# 163. High Availability and Deployments

A safer deployment can conceptually look like:

```text

App-03 v1
```

Remove/drain:

```text

```

Deploy:

```text

```

Validate health.

Then proceed gradually.

# 164. Load Balancers and Autoscaling

Load balancing is often combined with autoscaling.

Example:

```text

      |
      v

      |
      v

      |
      v
```

# 165. Do Not Send Traffic Before Readiness

An application process starting does not necessarily mean it is ready.

Startup may require:

```text

Loading caches
Running initialization
```

This leads to the broader distinction between:

```text

and

```

Health/readiness mechanisms help manage this.


The distinction is especially important in orchestration systems.

# Complete Client-to-Backend Traffic Flow

# 171. Production Architecture

Now combine everything.

```text
User Browser
     |
     v
Recursive DNS
     |
     v
Public DNS
     |
     v
Internet
     |
     v
Firewall / Security Controls
     |
     v
Public Load Balancer
     |
     v
Backend Pool
     |
     +--------+--------+
     |                 |
     v                 v
  App-01             App-02
     |                 |
     +--------+--------+
              |
              v
           Database
```

The user enters:

```text
https://shop.example.com/orders
```

Let us follow the request.

---

# 172. Step 1: URL Processing

Browser identifies:

```text
Scheme:
https

Hostname:
shop.example.com

Port:
443 by default

Path:
/orders
```

---

# 173. Step 2: DNS Resolution

The client needs an address for:

```text
shop.example.com
```

DNS eventually returns the load-balancer endpoint/address according to the architecture.

Conceptually:

```text
shop.example.com
        |
        v
203.0.113.20
```

---

# 174. Step 3: Routing

Client determines:

```text
203.0.113.20 is remote
```

It selects a route through its default gateway.

At Layer 2, the next-hop MAC is typically the gateway's MAC.

At Layer 3, the destination remains:

```text
203.0.113.20
```

subject to any later address translation in the path.

---

# 175. Step 4: TCP or QUIC

For a TCP-based HTTPS connection:

```text
Client
  |
  | SYN
  v
Load Balancer

Client
  ^
  | SYN-ACK
  |
Load Balancer

Client
  |
  | ACK
  v
Load Balancer
```

TCP is established.

If HTTP/3 is used, QUIC over UDP changes this transport flow.

---

# 176. Step 5: TLS

Assume TLS terminates at the load balancer.

```text
Client
  |
  | TLS handshake
  v
Load Balancer
```

The load balancer presents the certificate for:

```text
shop.example.com
```

The client validates it.

Encrypted application communication can then proceed.

---

# 177. Step 6: HTTP Request

The client sends something conceptually like:

```http
GET /orders HTTP/1.1
Host: shop.example.com
```

Actual protocol representation differs for HTTP/2 and HTTP/3, but the application semantics remain recognizable.

---

# 178. Step 7: Layer 7 Routing

The load balancer sees:

```text
Hostname:
shop.example.com

Path:
/orders
```

Routing policy:

```text
/orders/*
    |
    v
Orders Backend Pool
```

---

# 179. Step 8: Health-Aware Backend Selection

Backend pool:

```text
Orders-01: healthy
Orders-02: healthy
Orders-03: unhealthy
```

Eligible:

```text
Orders-01
Orders-02
```

Not eligible:

```text
Orders-03
```

The load balancer applies its balancing policy.

Suppose it selects:

```text
Orders-02
```

---

# 180. Step 9: New Backend Connection

If the load balancer operates as a reverse proxy, it may create a separate connection:

```text
Load Balancer
      |
      | TCP
      v
Orders-02
```

If backend TLS is enabled:

```text
Load Balancer
      |
      | TCP + TLS
      v
Orders-02
```

This is independent from the original client-side connection.

---

# 181. Step 10: Backend Receives Request

The backend may receive:

```text
GET /orders
```

plus forwarding information configured by the proxy.

The immediate network peer may be the load balancer.

---

# 182. Step 11: Backend Processes Request

Orders service may contact:

```text
Database
Redis
Queue
Payment service
```

Any of these dependencies can affect response time.

---

# 183. Step 12: Backend Response

Backend returns:

```text
200 OK
```

with application data.

Flow:

```text
Orders-02
    |
    v
Load Balancer
```

---

# 184. Step 13: Load Balancer Returns Response

The load balancer sends the response over the client-facing connection:

```text
Load Balancer
     |
     v
Client
```

If TLS terminates at the load balancer, the client-facing response is encrypted through that TLS session.

# Complete Failure Investigation

# 186. Scenario

Users report:

```text
https://shop.example.com/orders
```

returns:

```text
504 Gateway Timeout
```

Architecture:

```text
Browser
   |
   v
Public Load Balancer
   |
   v
Orders API
   |
   v
PostgreSQL
```

Where is the problem?

You do not know yet.

---

# 187. Check DNS

```bash
dig shop.example.com
```

Correct load-balancer endpoint is returned.

DNS is not the immediate failure.

---

# 188. Check Frontend Connectivity

```bash
curl -v https://shop.example.com/orders
```

You observe:

```text
TCP succeeds
TLS succeeds
HTTP request sent
504 returned
```

Therefore:

```text
Client -> Load Balancer
```

is functioning well enough to establish HTTPS and receive an HTTP response.

Move deeper.

---

# 189. Check Load-Balancer Logs

Suppose they indicate:

```text
Selected backend:
10.0.2.20:8080

Upstream timeout:
30 seconds
```

Now investigate:

```text
Load Balancer -> Backend
```

---

# 190. Capture on Backend

Run:

```bash
sudo tcpdump -nn -i any 'tcp port 8080'
```

Reproduce.

You observe:

```text
SYN
SYN-ACK
ACK

HTTP request

... 45 seconds ...

HTTP response
```

This is critical evidence.

The network connection works.

The request reaches the backend.

The backend takes approximately:

```text
45 seconds
```

to respond.

Load balancer waits only:

```text
30 seconds
```

The client therefore receives:

```text
504
```

---

# 191. Do Not Immediately Increase the Timeout

A beginner might say:

```text
Change timeout from 30 to 60 seconds.
```

But why is the backend taking 45 seconds?

Investigate application dependencies.

Application logs reveal:

```text
Database query:
43 seconds
```

The root cause is now closer to:

```text
Slow database query
```

rather than:

```text
Broken load balancer
```

Increasing the timeout might only hide the real performance problem.

---

# 192. Another Scenario: 503

Users receive:

```text
503
```

Load balancer reports:

```text
Healthy backends: 0
```

Backend application is running.

Check health configuration:

```text
Configured:
GET /health

Application provides:
GET /healthz
```

The load balancer receives:

```text
404
```

and marks every backend unhealthy.

Root cause:

```text
Incorrect health-check path
```

Not:

```text
Application outage
```

---

# 193. Another Scenario: 502

Client receives:

```text
502 Bad Gateway
```

Backend:

```bash
sudo ss -lntp
```

shows:

```text
127.0.0.1:8080
```

Load balancer tries:

```text
10.0.2.20:8080
```

Application is listening only on loopback.

The proxy cannot reach that listener through the server's network interface.

Again, the error becomes understandable when you follow the traffic.

---

# 194. Another Scenario: One Backend Causes Intermittent Failures

Backend pool:

```text
App-01 healthy
App-02 healthy
App-03 healthy
```

Users report:

```text
About one-third of requests fail.
```

Suppose round robin is used.

Investigate each backend separately.

You discover:

```text
App-01 -> works
App-02 -> works
App-03 -> returns 500
```

The load balancer is successfully distributing traffic.

The problem is backend-specific.

This is why intermittent failures often require checking whether failures correlate with a particular target.

---

# 195. Another Scenario: Only Logged-In Users Fail

Anonymous requests work.

Logged-in users fail intermittently.

Architecture:

```text
Load Balancer
   |
   +--> App-01
   +--> App-02
```

Session state exists only in local application memory.

Login request:

```text
User -> App-01
```

Next request:

```text
User -> App-02
```

App-02 has no session.

The networking infrastructure may be functioning perfectly.

The architectural problem is state management.

Possible approaches include:

```text
Session affinity
```

or preferably where appropriate:

```text
External/shared session state
```

depending on application design.

---

# 196. Another Scenario: Deployment Causes 502 Spikes

Normal:

```text
App-01
App-02
App-03
```

Deployment process:

```text
Terminate App-01 immediately
```

But App-01 still has active requests.

Those requests fail.

Metrics show:

```text
502 spike during every deployment
```

Investigate:

```text
Connection draining
Graceful shutdown
Readiness
Deployment sequencing
```

The problem may be lifecycle management rather than basic networking.

---

# 197. Another Scenario: Certificate Works Directly but Fails Through Load Balancer

Backend direct connection presents:

```text
Valid certificate
```

But public endpoint presents:

```text
Expired certificate
```

If TLS terminates at the load balancer, the client sees the load balancer's certificate.

Updating only the backend certificate does not fix the public endpoint.

You must know where TLS terminates.

---

# 198. Another Scenario: Backend TLS Fails

Client-facing certificate is valid.

But load balancer connects to backend using HTTPS and fails certificate validation.

Architecture:

```text
Client
   |
   | TLS #1 works
   v
Load Balancer
   |
   | TLS #2 fails
   X
Backend
```

Users may see a gateway error even though:

```bash
openssl s_client -connect public.example.com:443
```

shows a perfectly valid client-facing certificate.

There are two separate TLS relationships.

---

# 199. The Four Paths You Should Mentally Separate

In many production incidents, think about:

```text
1. Client -> DNS

2. Client -> Load Balancer

3. Load Balancer -> Backend

4. Backend -> Dependencies
```

Each can fail independently.

---

# 200. Add the Return Paths

Do not forget:

```text
Backend -> Load Balancer

Load Balancer -> Client
```

and for dependencies:

```text
Database -> Backend
```

Successful forward traffic does not guarantee successful return traffic.

# Common Beginner Mistakes

# 212. Mistake: Thinking the Client Connects Directly to the Backend

With a reverse proxy:

```text
Client -> Proxy

Proxy -> Backend
```

These are usually separate relationships.

---

# 213. Mistake: Treating 502 as Proof the Load Balancer Failed

A 502 often points you toward upstream communication.

Find the actual generator and investigate the backend path.

---

# 214. Mistake: Treating 503 as Proof the Application Is Down

It might mean:

```text
No healthy targets
Overload
Maintenance
Proxy policy
```

Determine who generated it and why.

---

# 215. Mistake: Treating 504 as Proof of a Network Problem

The network might work perfectly while the application spends 60 seconds on a database query.

Measure where the delay occurs.

---

# 216. Mistake: Ignoring Health Checks

Direct backend access works, so the engineer concludes:

```text
Load balancer must be broken.
```

But health check:

```text
GET /health
```

returns:

```text
404
```

The load balancer is behaving according to configuration.

---

# 217. Mistake: Using the Wrong Health-Check Port

Application:

```text
8080
```

Health check:

```text
8000
```

Every target becomes unhealthy.

Always compare configuration with actual listeners.

---

# 218. Mistake: Assuming Healthy Means Application Fully Works

A TCP health check may pass while HTTP requests return 500.

Health means only what you defined it to mean.

---

# 219. Mistake: Assuming Direct Backend Access Proves Load-Balancer Access

Your laptop may have a different:

```text
Route
Firewall rule
Source address
Security policy
```

than the load balancer.

Test the actual path.

---

# 220. Mistake: Forgetting Backend Return Traffic

The load balancer's SYN may reach the backend.

The backend's SYN-ACK may fail to return.

Check both directions.

---

# 221. Mistake: Confusing TLS Termination With Passthrough

Always ask:

```text
Where does the client's TLS connection terminate?
```

That tells you which system presents the certificate and which system can inspect HTTP.

---

# 222. Mistake: Assuming Backend Traffic Is Unencrypted After Termination

The load balancer may establish a second HTTPS connection to the backend.

Termination does not automatically mean plaintext backend communication.

---

# 223. Mistake: Blindly Trusting X-Forwarded-For

Only trust forwarding metadata from properly configured trusted proxies.

---

# 224. Mistake: Using Sticky Sessions to Hide Poor State Design

Session affinity may solve certain requirements, but it can also hide an application architecture that cannot tolerate backend changes.

Understand why persistence is needed.

---

# 225. Mistake: Killing Instances Without Draining

This can terminate active connections during:

```text
Deployments
Autoscaling
Maintenance
```

Use graceful lifecycle management where supported.

---

# 226. Mistake: Putting All Redundant Servers in One Failure Domain

Three servers in one zone may all fail together.

Redundancy should consider shared failure domains.

---

# 227. Mistake: Forgetting the Database SPOF

Three application servers do not make a system highly available if every request depends on one fragile database.

Think end-to-end.

Some requests return:

Others:

```text

```

DNS, frontend TCP, and frontend TLS clearly work at least some of the time.

# 244. Correlate Requests

Load-balancer logs reveal:

```text
Successful requests -> App-01

Failed requests -> App-02
```

Now the failure domain is dramatically smaller.

# 245. Inspect App-02

Run:


Application is listening on:

```text
0.0.0.0:8080
```

TCP listener exists.

# 246. Capture Traffic

Run:

```bash
sudo tcpdump -nn -i any 'tcp port 8080'
```

Reproduce a failed request.

You observe:

```text
Load Balancer -> App-02    SYN

App-02 -> Load Balancer    SYN-ACK

Load Balancer -> App-02    ACK

Load Balancer -> App-02    HTTP request

App-02 -> Load Balancer    RST
```

TCP connectivity exists.

The connection is reset after application traffic begins.

# 247. Check Application Logs

App-02 logs show:

```text
Application worker crashes
when processing /checkout
```

App-01 does not.

Further inspection reveals:

```text
App-01:
Version 2.4.1

App-02:
Version 2.4.0
```

A deployment left one backend running an older faulty version.

# 248. Root Cause

The root cause is not:

```text
DNS
Load-balancer algorithm
Firewall
Routing
TLS
```

The load balancer actually helped expose the issue because failures correlated with one backend.

Root cause:

```text
App-02 was running an outdated application version
that crashed while processing /checkout.
```

A controlled response could be:

```text
Remove/drain App-02 from production traffic
        |
        v

        |
        v

        |
        v
Verify application
        |
        v
Verify health
        |
        v
Return App-02 to backend pool
```

Then investigate why deployment consistency failed so it does not recur.

The most important production principle from this part is:

> **Do not troubleshoot a load-balanced application as one connection. Break the request into individual network and application relationships, then identify the first point where expected behavior stops.**

Once you can do that, errors such as **502, 503, 504, unhealthy targets, TLS failures, intermittent backend failures, and deployment-related outages** stop being vague "load balancer problems." They become specific failures that you can isolate with DNS checks, routing information, health status, logs, `curl`, `ss`, `openssl`, and packet captures.
