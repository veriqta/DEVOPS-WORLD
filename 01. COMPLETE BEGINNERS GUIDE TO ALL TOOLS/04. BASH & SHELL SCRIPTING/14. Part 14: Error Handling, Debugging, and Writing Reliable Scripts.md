# Part 14: Error Handling, Debugging, and Writing Reliable Scripts

A Bash script can look correct and still be dangerous.

It may:

* contain invalid syntax
* call a command that fails
* use the wrong variable
* continue after a critical failure
* hide an error inside a pipeline
* operate on an empty path
* delete or overwrite the wrong file
* behave differently in production
* report success when part of the work failed
* leave temporary files behind
* fail only for certain inputs
* depend on commands that are not installed

This is why reliable Bash engineering is not just about writing commands.

You must also know how to answer:

```text
What failed?

Where did it fail?

Why did it fail?

What was the exit status?

What input caused it?

Should the script continue?

What evidence can I collect?

Can I reproduce the problem safely?

How do I prevent the same failure?
```

Guessing is not debugging.

A useful troubleshooting model is:

```text
Observe
   |
   v
Understand the symptom
   |
   v
Check the simplest cause
   |
   v
Gather evidence
   |
   v
Form a hypothesis
   |
   v
Test the hypothesis
   |
   v
Fix the cause
   |
   v
Verify the fix
   |
   v
Prevent recurrence
```

By the end of Part 14, you should understand:

* why Bash scripts fail
* syntax errors
* runtime errors
* logic errors
* exit-code checking
* `set -e`
* limitations of `set -e`
* `set -u`
* `set -o pipefail`
* `set -x`
* `set +x`
* `set -E`
* the common `set -Eeuo pipefail` pattern
* strict-mode advantages
* strict-mode surprises
* `trap ERR`
* error-handling functions
* debug logging
* `LINENO`
* `BASH_SOURCE`
* assertions
* input validation
* dependency validation
* defensive scripting
* temporary-resource cleanup
* safe production testing
* `bash -n`
* ShellCheck
* execution tracing
* a systematic Bash debugging workflow
* how to troubleshoot a deliberately broken production-style script

# 1. Why Bash Scripts Fail

Bash scripts fail for many different reasons.

Consider:

```bash
#!/usr/bin/env bash

backup_dir="/backups"

cp /important/data "$backup_dir"

rm -rf /important/data
```

At first glance, the intention might be:

```text
Copy data
   |
   v
Delete original
```

But what happens if `cp` fails?

Perhaps:

* `/backups` does not exist
* permission is denied
* disk is full
* source does not exist
* filesystem is read-only
* destination is unavailable

Unless the script handles the failure correctly, it may continue to:

```bash
rm -rf /important/data
```

That turns a simple backup failure into a potentially destructive incident.

The important lesson is:

> A reliable script must define what should happen when operations fail.

---

# 2. Failure Is Normal

Do not design scripts as though every command will succeed.

Real systems experience:

```text
missing files
bad permissions
full disks
network failures
DNS failures
API errors
timeouts
authentication failures
invalid input
missing commands
unexpected output
process termination
concurrent changes
configuration mistakes
```

Reliable automation expects failure.

The goal is not:

```text
Make failure impossible
```

That is unrealistic.

The goal is:

```text
Detect failure
   |
   v
Understand failure
   |
   v
Respond safely
   |
   v
Expose useful evidence
   |
   v
Prevent incorrect continuation
```

---

# 3. Three Important Failure Categories

For beginners, it is useful to classify script problems into three broad categories:

```text
Syntax errors
Runtime errors
Logic errors
```

They are not identical.

Understanding which category you are dealing with helps you choose the right debugging method.

---

# 4. Syntax Errors

A syntax error means Bash cannot correctly parse the script according to shell grammar.

Example:

```bash
if [[ -f "/tmp/test" ]]
    echo "File exists"
fi
```

This is missing:

```bash
then
```

Correct:

```bash
if [[ -f "/tmp/test" ]]; then
    echo "File exists"
fi
```

---

# 5. Another Syntax Error

Broken:

```bash
for server in web01 web02 web03
    echo "$server"
done
```

Correct:

```bash
for server in web01 web02 web03; do
    echo "$server"
done
```

The missing `do` breaks the loop syntax.

---

# 6. Unclosed Quotes

Broken:

```bash
name="production
echo "$name"
```

Bash may report something involving:

```text
unexpected EOF
```

or another parsing error.

The actual mistake may have occurred several lines earlier than the line Bash reports.

This is an important debugging lesson:

> The reported line is not always where the mistake began.

---

# 7. Missing `fi`

Broken:

```bash
if [[ "$environment" == "production" ]]; then
    echo "Production environment"
```

The conditional was never closed with:

```bash
fi
```

This can produce an error near the end of the file.

---

# 8. Missing `done`

Broken:

```bash
for file in *.log; do
    echo "$file"
```

The loop needs:

```bash
done
```

---

# 9. Syntax Checking Without Running the Script

Bash provides:

```bash
bash -n script.sh
```

The:

```text
-n
```

option tells Bash to read commands and check syntax without executing them.

Example:

```bash
bash -n deploy.sh
```

If no syntax errors are found, Bash normally produces no output.

Check the status:

```bash
echo "$?"
```

A status of:

```text
0
```

means the syntax check succeeded.

---

# 10. Why `bash -n` Matters

Suppose a script contains:

```bash
rm -rf -- "$target"
```

You do not want to execute the script merely to discover whether an unrelated `if` statement has a syntax error.

Instead:

```bash
bash -n cleanup.sh
```

performs parsing without running the commands.

This should become one of your basic Bash checks.

---

# 11. What `bash -n` Does Not Prove

This is critical.

If:

```bash
bash -n script.sh
```

succeeds, it does not mean the script is correct.

It only means Bash did not detect a syntax problem while parsing.

This can pass:

```bash
#!/usr/bin/env bash

source_file="/does/not/exist"

cp "$source_file" "/tmp/backup"
```

The syntax is valid.

But the script can still fail at runtime.

---

# 12. Runtime Errors

A runtime error occurs while the script is executing.

Example:

```bash
cp "/missing/file.txt" "/tmp/file.txt"
```

The command syntax is valid.

But if the source file does not exist, `cp` fails.

You might see:

```text
cp: cannot stat '/missing/file.txt': No such file or directory
```

This is a runtime failure.

---

# 13. Runtime Failure Examples

Common runtime failures include:

```text
Permission denied
No such file or directory
Command not found
Connection refused
Authentication failed
Disk full
Read-only filesystem
Timeout
DNS resolution failure
Invalid command option
API returns error
```

The script was valid enough to start.

Something failed while it was running.

---

# 14. Logic Errors

Logic errors are often more dangerous.

A logic error means the script runs, but does the wrong thing.

Example:

```bash
if [[ "$environment" == "development" ]]; then
    deploy_to_production
fi
```

The syntax may be valid.

The function may run successfully.

The exit status may even be 0.

But the logic is wrong.

---

# 15. Another Logic Error

Suppose:

```bash
disk_usage=95

if (( disk_usage < 80 )); then
    echo "Disk usage is critical"
fi
```

The condition is reversed.

At 95 percent usage, the warning does not appear.

No syntax checker can automatically understand every business rule.

This is why testing matters.

---

# 16. Successful Execution Does Not Mean Correct Behavior

A script can return:

```text
0
```

and still be wrong.

For example:

```bash
echo "Deleting staging files"

rm -rf -- "$production_dir"

exit 0
```

If the wrong variable was used, every command might technically succeed.

But the outcome is disastrous.

Therefore:

```text
Exit status 0
       ≠
Business logic is correct
```

Exit codes detect command-level success or failure.

Tests and validation help detect logic problems.

---

# 17. Checking Exit Codes

You learned earlier that:

```bash
$?
```

contains the exit status of the most recently completed foreground pipeline or command context.

Example:

```bash
cp source.txt backup.txt

echo "$?"
```

Common convention:

```text
0     success
nonzero failure or another command-specific result
```

---

# 18. Capture Exit Codes Immediately

Correct:

```bash
cp source.txt backup.txt
status=$?

printf 'cp returned: %s\n' "$status"
```

Incorrect:

```bash
cp source.txt backup.txt

echo "Copy finished"

status=$?
```

Now `$?` belongs to:

```bash
echo "Copy finished"
```

not `cp`.

---

# 19. Prefer Direct Conditional Testing

Instead of:

```bash
cp source.txt backup.txt
status=$?

if (( status == 0 )); then
    echo "Success"
else
    echo "Failure"
fi
```

you can often write:

```bash
if cp source.txt backup.txt; then
    echo "Success"
else
    echo "Failure"
fi
```

This directly uses the command's exit status as the condition.

---

# 20. Explicit Failure Handling

Suppose backup is mandatory.

```bash
if ! cp -a -- "$source" "$backup"; then
    printf 'ERROR: backup failed\n' >&2
    exit 1
fi
```

Now the script deliberately refuses to continue.

This is safer than hoping Bash automatically knows the backup was critical.

---

# 21. Error Handling Is a Design Decision

For every important operation, ask:

```text
If this fails:

Should the script stop?

Should it retry?

Should it continue?

Should it log a warning?

Should it clean up?

Should it return a specific status?

Should it roll back?
```

Different failures require different responses.

---

# 22. `set -e`

Bash provides:

```bash
set -e
```

You may also see:

```bash
set -o errexit
```

This enables the `errexit` shell option.

The simplified beginner explanation is:

> Exit when an unhandled command failure occurs.

Example:

```bash
#!/usr/bin/env bash

set -e

echo "Step 1"

false

echo "Step 2"
```

You may expect:

```text
Step 1
```

and then the script exits before `Step 2`.

In this simple case, that happens.

---

# 23. Why `set -e` Looks Attractive

Without it:

```bash
#!/usr/bin/env bash

cp important.file /missing/directory/

echo "Continuing deployment..."
```

the script may continue.

With:

```bash
set -e
```

some failures automatically terminate execution.

This can prevent accidental continuation.

But there is a major warning:

> `set -e` is not simply "exit whenever anything returns nonzero."

Its behavior depends on shell syntax and context.

---

# 24. The Limitations of `set -e`

Bash intentionally suppresses or modifies `errexit` behavior in several contexts because nonzero statuses are often used for control flow.

Examples include commands used in:

* `if` tests
* `while` conditions
* `until` conditions
* parts of `&&` and `||` lists
* pipelines, depending on position and `pipefail`
* commands whose status is inverted with `!`
* other context-sensitive constructs

This is why blindly relying on `set -e` can create surprises.

---

# 25. `set -e` Inside `if`

Consider:

```bash
set -e

if grep -q "ERROR" app.log; then
    echo "Errors found"
fi

echo "Continuing"
```

`grep -q` returns:

```text
0 → match found
1 → no match
```

A status of 1 here is not necessarily a script failure.

It is being used as the condition of `if`.

Bash understands that nonzero is part of control flow.

The script can continue.

---

# 26. Why This Is Necessary

If `set -e` terminated every time a conditional command returned nonzero, this would be almost unusable:

```bash
if [[ -f "$file" ]]; then
    ...
fi
```

A false condition is not automatically an error.

Shell scripting uses exit statuses both for:

```text
failure
```

and:

```text
boolean-style control flow
```

That creates complexity.

---

# 27. `set -e` and `||`

Consider:

```bash
set -e

some_command || echo "Command failed"

echo "Continuing"
```

Because the command is part of an OR list, its nonzero result is being handled by shell control flow.

The script does not necessarily exit where a beginner might expect.

---

# 28. `set -e` and `&&`

Similarly:

```bash
set -e

some_test && perform_action
```

A nonzero result from `some_test` may simply mean:

```text
Do not run perform_action.
```

Again, context matters.

---

# 29. `set -e` Is Not a Replacement for Error Handling

Do not write:

```bash
set -e
```

and conclude:

```text
My script now handles all errors.
```

It does not.

Reliable scripts still need:

* validation
* explicit conditionals
* meaningful errors
* cleanup
* tests
* careful pipeline handling
* knowledge of expected nonzero statuses

Use `set -e` as one tool, not as your entire reliability strategy.

---

# 30. `set -u`

Bash provides:

```bash
set -u
```

also known as:

```bash
set -o nounset
```

It treats many expansions of unset variables as errors.

Example:

```bash
#!/usr/bin/env bash

set -u

echo "$server_name"
```

If `server_name` was never set, Bash reports an error instead of silently expanding it to an empty string.

---

# 31. Why `set -u` Helps

Consider:

```bash
backup_dir="/backups"

cp -a -- "$source_dir" "$bakcup_dir"
```

Notice the typo:

```text
bakcup_dir
```

Without nounset, depending on context, an unset variable may become an empty string.

With:

```bash
set -u
```

Bash can expose the mistake immediately.

This is extremely useful for catching misspelled variables.

---

# 32. Unset vs Empty

These are different:

```bash
unset name
```

versus:

```bash
name=""
```

The first variable is unset.

The second exists but contains an empty string.

With `set -u`, this matters.

---

# 33. Safe Defaults with `set -u`

Suppose a variable may legitimately be unset.

Instead of:

```bash
echo "$OPTIONAL_VALUE"
```

you can use:

```bash
echo "${OPTIONAL_VALUE:-}"
```

This means:

> Use the value if it is set and non-empty; otherwise use an empty default.

Or:

```bash
environment="${ENVIRONMENT:-development}"
```

This provides a deliberate default.

---

# 34. Required Variables with Parameter Expansion

You can also require a value:

```bash
database_url="${DATABASE_URL:?DATABASE_URL must be set}"
```

If `DATABASE_URL` is unset or empty, Bash prints the message and stops that expansion.

This is useful for mandatory configuration.

Example:

```bash
api_endpoint="${API_ENDPOINT:?API_ENDPOINT is required}"
```

---

# 35. Do Not Use Defaults Carelessly

This might hide a configuration mistake:

```bash
environment="${ENVIRONMENT:-production}"
```

If the user forgets to specify the environment, the script defaults to production.

That is usually an unsafe default.

Safer:

```bash
environment="${ENVIRONMENT:-development}"
```

or require explicit selection for sensitive operations.

Defensive scripting includes safe defaults.

---

# 36. `set -o pipefail`

Consider:

```bash
cat missing.log | grep ERROR | sort
```

Without `pipefail`, the pipeline's status normally comes from the last command.

Suppose:

```text
cat fails
grep receives no useful input
sort exits successfully
```

The pipeline may appear successful because the final command returned 0.

That can hide failures.

---

# 37. Enable `pipefail`

Use:

```bash
set -o pipefail
```

Now a pipeline returns failure when a command within it fails, according to Bash's pipefail rules, rather than blindly using only the final command's success.

Example:

```bash
set -o pipefail

cat missing.log | grep ERROR | sort

echo "$?"
```

The failure is now visible.

---

# 38. Why `pipefail` Matters for DevOps

DevOps scripts often use pipelines:

```bash
kubectl logs ... | grep ERROR
```

```bash
curl ... | jq ...
```

```bash
grep ... | awk ... | sort
```

```bash
command | tee deployment.log
```

If an early command fails but the final command succeeds, automation may incorrectly report success.

`pipefail` helps expose these failures.

---

# 39. `pipefail` Can Also Expose Expected Nonzero Statuses

Remember from Part 11:

```bash
grep -q "pattern" file
```

can return 1 when no match is found.

Depending on your logic, that may be expected.

With strict error handling, you need to distinguish:

```text
Expected non-match
```

from:

```text
Unexpected command failure
```

This is another reason error handling requires understanding, not memorization.

---

# 40. Inspect Pipeline Statuses

Bash provides:

```bash
PIPESTATUS
```

an array containing exit statuses from commands in the most recently executed foreground pipeline.

Example:

```bash
false | true | false

printf '%s\n' "${PIPESTATUS[@]}"
```

You may see:

```text
1 0 1
```

This can be useful when debugging pipeline behavior.

Capture or inspect it immediately because later commands replace it.

---

# 41. `set -x`

Bash provides execution tracing:

```bash
set -x
```

When enabled, Bash prints expanded commands as it executes them.

Example:

```bash
#!/usr/bin/env bash

set -x

name="web01"

echo "Checking $name"

set +x
```

The trace shows what Bash is actually executing after expansions.

---

# 42. Why `set -x` Helps

Suppose:

```bash
target="$backup_root/$environment"

cp -a -- "$source" "$target"
```

You think:

```text
target=/backups/production
```

but the script actually produces:

```text
target=/backups/
```

Tracing can reveal the expanded command.

Instead of guessing, you see what Bash executed.

---

# 43. `set +x`

Use:

```bash
set +x
```

to disable execution tracing.

Example:

```bash
set -x

echo "Debugging normal operations"

set +x

echo "Tracing disabled"
```

---

# 44. Security Warning: Tracing Can Expose Secrets

This is critical.

Do not casually enable:

```bash
set -x
```

around commands containing:

* passwords
* API tokens
* access keys
* authorization headers
* private URLs containing credentials
* secrets from environment variables

Example:

```bash
set -x

curl -H "Authorization: Bearer $API_TOKEN" "$url"
```

could expose the token in logs.

This is dangerous in:

* CI/CD logs
* shared terminals
* centralized logging
* support bundles
* build artifacts

---

# 45. Disable Tracing Around Sensitive Commands

If tracing is required elsewhere:

```bash
set +x

perform_sensitive_operation

set -x
```

But be careful.

The command used to re-enable tracing can itself appear depending on tracing state and execution.

More importantly, design scripts so secret-bearing commands are not unnecessarily exposed.

Debugging must not create a security incident.

---

# 46. Trace Prefixes

Bash uses:

```text
PS4
```

to control the prefix displayed for traced commands.

The default often begins with:

```text
+
```

You can make tracing more useful:

```bash
PS4='+ ${BASH_SOURCE}:${LINENO}:${FUNCNAME[0]:-main}: '
```

Then:

```bash
set -x
```

may produce trace lines containing:

```text
script name
line number
function name
```

This is extremely useful for larger scripts.

---

# 47. `BASH_SOURCE`

`BASH_SOURCE` is a Bash array containing source-file information associated with the current execution context.

At the simplest level:

```bash
echo "${BASH_SOURCE[0]}"
```

often identifies the current script file.

Example:

```text
./deploy.sh
```

or:

```text
/home/ann/scripts/deploy.sh
```

depending on how the script was invoked.

---

# 48. Why `BASH_SOURCE` Is Useful

Imagine:

```text
deploy.sh
   |
   v
source lib/common.sh
   |
   v
function fails
```

You want an error message showing which file contains the failing function.

`BASH_SOURCE` helps provide that context.

This becomes increasingly valuable when scripts use shared libraries.

---

# 49. `LINENO`

Bash provides:

```bash
echo "$LINENO"
```

which expands to the current line number in the script context.

Example:

```bash
printf 'Currently near line %s\n' "$LINENO"
```

This helps create useful diagnostic messages.

---

# 50. Why Line Numbers Matter

Bad error:

```text
Something failed.
```

Better:

```text
ERROR: deployment failed.
```

Much better:

```text
ERROR: deploy.sh:87: deployment failed.
```

The engineer now knows where to investigate.

---

# 51. Debug Logging

A reliable script should support meaningful logging.

Example:

```bash
log() {
    local level="$1"
    shift

    printf '[%s] [%s] %s\n' \
        "$(date '+%Y-%m-%d %H:%M:%S')" \
        "$level" \
        "$*"
}
```

Use:

```bash
log INFO "Starting deployment"
log WARN "Using fallback configuration"
log ERROR "Health check failed"
```

---

# 52. Add Source and Line Context

You can create:

```bash
debug() {
    printf '[DEBUG] %s:%s: %s\n' \
        "${BASH_SOURCE[1]}" \
        "${BASH_LINENO[0]}" \
        "$*" >&2
}
```

Here we use caller-related Bash metadata.

This is more useful inside a function than simply printing the line inside the logging function itself.

---

# 53. Why `$LINENO` Inside a Logging Function Can Mislead

Consider:

```bash
debug() {
    printf 'Line: %s\n' "$LINENO"
}
```

When `debug` runs, `$LINENO` refers to execution within the function context.

It may not be the caller line you wanted.

For caller information, Bash provides additional arrays such as:

```text
BASH_SOURCE
BASH_LINENO
FUNCNAME
```

These can be combined for more useful diagnostics.

---

# 54. A Practical Debug Function

Example:

```bash
debug() {
    local message="$*"
    local source="${BASH_SOURCE[1]:-${BASH_SOURCE[0]}}"
    local line="${BASH_LINENO[0]:-unknown}"
    local function="${FUNCNAME[1]:-main}"

    printf '[DEBUG] %s:%s:%s: %s\n' \
        "$source" \
        "$line" \
        "$function" \
        "$message" >&2
}
```

Call:

```bash
debug "Resolved backup path: $backup_dir"
```

Possible output:

```text
[DEBUG] ./backup.sh:74:main: Resolved backup path: /backups/prod
```

---

# 55. Conditional Debug Logging

You do not always want debug messages.

Use:

```bash
DEBUG="${DEBUG:-false}"
```

Then:

```bash
debug() {
    [[ "$DEBUG" == "true" ]] || return 0

    local message="$*"
    local source="${BASH_SOURCE[1]:-${BASH_SOURCE[0]}}"
    local line="${BASH_LINENO[0]:-unknown}"
    local function="${FUNCNAME[1]:-main}"

    printf '[DEBUG] %s:%s:%s: %s\n' \
        "$source" \
        "$line" \
        "$function" \
        "$message" >&2
}
```

Run normally:

```bash
./script.sh
```

Run with debugging:

```bash
DEBUG=true ./script.sh
```

---

# 56. Do Not Log Secrets

This is unsafe:

```bash
debug "API token: $API_TOKEN"
```

Avoid exposing:

* tokens
* passwords
* credentials
* private keys
* session cookies
* secret headers

Instead:

```bash
debug "API token is configured"
```

if that information is sufficient.

---

# 57. `set -E`

You may encounter:

```bash
set -E
```

also known as:

```bash
set -o errtrace
```

This affects inheritance of the `ERR` trap in functions, command substitutions, and subshell-related contexts.

It is commonly used with:

```bash
trap ... ERR
```

and explains the `E` in:

```bash
set -Eeuo pipefail
```

---

# 58. The Common Strict-Mode Pattern

You will frequently see:

```bash
set -Eeuo pipefail
```

This combines:

```text
-E
ERR trap inheritance in important Bash contexts

-e
errexit

-u
nounset

-o pipefail
pipeline failure propagation
```

It is often called:

```text
strict mode
```

although Bash itself does not officially define one single feature named "strict mode."

It is a community convention.

---

# 59. Expanded Form

This:

```bash
set -Eeuo pipefail
```

roughly combines:

```bash
set -E
set -e
set -u
set -o pipefail
```

The compact form is common in production Bash scripts.

But do not use it without understanding each option.

---

# 60. When Strict Mode Helps

Strict settings can expose:

* ignored command failures
* misspelled variables
* unset variables
* hidden pipeline failures
* failures inside nested execution contexts when combined carefully with traps

This can make scripts fail earlier instead of continuing with corrupted assumptions.

---

# 61. When Strict Mode Creates Surprises

Strict mode can surprise beginners when:

* a command returns nonzero as normal control flow
* an optional variable is unset
* `grep` finds no match
* arithmetic expressions produce status 1
* pipeline commands intentionally terminate early
* functions are used in conditional contexts
* command substitutions behave differently than expected
* cleanup commands fail
* `ERR` traps interact with shell grammar

The solution is not necessarily:

```text
Never use strict mode.
```

Nor is it:

```text
Always use strict mode everywhere.
```

The solution is:

> Understand the semantics and explicitly handle expected failures.

---

# 62. Arithmetic Surprise

Remember from Part 7:

```bash
((count++))
```

returns a status based on the arithmetic expression's value.

If `count` initially equals 0, the expression evaluates to 0 before incrementing, so its command status is 1.

Under `set -e`, this can cause surprising behavior in some contexts.

Safer when you only want incrementing:

```bash
((count += 1))
```

or:

```bash
((++count))
```

when appropriate.

Understanding command status matters.

---

# 63. `grep` Surprise

Suppose:

```bash
set -e

grep -q "ERROR" app.log

echo "Finished"
```

If no match exists, `grep` returns 1.

Under `set -e`, that may terminate the script because the command is not being used in a conditional context.

But "no ERROR line exists" might actually be good.

Better:

```bash
if grep -q "ERROR" app.log; then
    echo "Errors found"
else
    echo "No error pattern found"
fi
```

Now the expected nonzero result is explicitly handled.

---

# 64. Pipelines and Early Termination

Some pipelines can produce surprising statuses with `pipefail`.

For example, a downstream command may intentionally stop reading early after obtaining enough data.

An upstream command may then receive a broken pipe.

The exact behavior depends on the commands involved.

The lesson:

> Do not treat strict-mode rules as magic. Test important pipelines under the actual shell and commands you use.

---

# 65. `trap ERR`

Bash supports the special:

```text
ERR
```

trap.

Example:

```bash
trap 'echo "A command failed"' ERR
```

When qualifying command failures occur, Bash runs the trap.

This can provide useful diagnostics.

---

# 66. Basic ERR Trap

Example:

```bash
#!/usr/bin/env bash

set -E

trap 'printf "ERROR near line %s\n" "$LINENO" >&2' ERR

false
```

The trap runs when `false` fails.

But there are important limitations.

---

# 67. `ERR` Follows Similar Context Rules to `errexit`

The `ERR` trap is not invoked for every possible nonzero status.

Its behavior is related to shell contexts where failures are considered handled or part of conditional logic.

For example, commands in:

* conditional tests
* certain `&&`/`||` contexts
* inverted commands
* other exempt contexts

may not trigger it as a beginner expects.

Do not treat `trap ERR` as universal exception handling.

Bash is not Python, Java, or another language with a conventional exception model.

---

# 68. A Better Error Function

Create:

```bash
error_handler() {
    local status=$?
    local line="$1"
    local command="$2"

    printf 'ERROR: status=%s line=%s command=%s\n' \
        "$status" \
        "$line" \
        "$command" >&2

    return "$status"
}
```

Then:

```bash
trap 'error_handler "$LINENO" "$BASH_COMMAND"' ERR
```

This can produce much more useful evidence.

---

# 69. `BASH_COMMAND`

Bash provides:

```text
BASH_COMMAND
```

which can help identify the command being executed around the time an error trap fires.

Example diagnostic:

```text
ERROR: status=1 line=52 command=cp "$source" "$destination"
```

This is far better than:

```text
ERROR
```

---

# 70. Capture Status First

Inside an error handler:

```bash
error_handler() {
    local status=$?
```

should happen immediately.

If you first run:

```bash
echo "Failure"
```

then:

```bash
local status=$?
```

you capture `echo`'s status instead of the original failure.

This is the same `$?` principle you learned earlier.

---

# 71. Error Handler with Source Information

A more useful handler:

```bash
error_handler() {
    local status=$?
    local line="$1"
    local command="$2"
    local source="$3"

    printf 'ERROR: %s:%s: command failed with status %s: %s\n' \
        "$source" \
        "$line" \
        "$status" \
        "$command" >&2

    return "$status"
}
```

Register:

```bash
trap 'error_handler "$LINENO" "$BASH_COMMAND" "${BASH_SOURCE[0]}"' ERR
```

---

# 72. Avoid Overcomplicated Error Traps

It is tempting to build an enormous trap that:

* sends Slack messages
* deletes resources
* rolls back infrastructure
* restarts services
* uploads logs
* kills processes
* changes deployments

Avoid putting too much logic directly into error traps.

Error handlers should usually focus on:

```text
Capture evidence
Report failure
Preserve status
Trigger carefully designed cleanup
```

Complex remediation deserves explicit functions and tests.

---

# 73. Assertions

An assertion verifies that an assumption required by the script is true.

Example:

```bash
assert_file_exists() {
    local file="$1"

    if [[ ! -f "$file" ]]; then
        printf 'ERROR: required file does not exist: %s\n' "$file" >&2
        return 1
    fi
}
```

Use:

```bash
assert_file_exists "$config_file"
```

---

# 74. Why Assertions Help

Without validation:

```text
Assume config exists
      |
      v
Start deployment
      |
      v
Several operations succeed
      |
      v
Config read fails
      |
      v
Partial deployment
```

With early assertion:

```text
Validate config
      |
      +--> missing
      |      |
      |      v
      |     stop
      |
      +--> valid
             |
             v
         continue
```

Fail early before side effects.

---

# 75. Assert a Directory

Example:

```bash
assert_directory() {
    local directory="$1"

    if [[ ! -d "$directory" ]]; then
        printf 'ERROR: required directory does not exist: %s\n' \
            "$directory" >&2
        return 1
    fi
}
```

---

# 76. Assert a Command Exists

Example:

```bash
require_command() {
    local command_name="$1"

    if ! command -v "$command_name" > /dev/null 2>&1; then
        printf 'ERROR: required command not found: %s\n' \
            "$command_name" >&2
        return 1
    fi
}
```

Then:

```bash
require_command curl
require_command jq
```

Do this before starting work that depends on those tools.

---

# 77. Assert a Variable Is Non-Empty

Example:

```bash
require_nonempty() {
    local name="$1"
    local value="$2"

    if [[ -z "$value" ]]; then
        printf 'ERROR: %s must not be empty\n' "$name" >&2
        return 1
    fi
}
```

Use:

```bash
require_nonempty "environment" "$environment"
```

---

# 78. Validation Is Better Than Hope

Do not write:

```bash
rm -rf -- "$target"
```

while merely assuming `$target` is correct.

Validate first:

```bash
if [[ -z "$target" ]]; then
    printf 'ERROR: target is empty\n' >&2
    exit 1
fi
```

Then validate expected boundaries.

---

# 79. Validate Sensitive Paths

Suppose a cleanup script should only operate inside:

```text
/var/tmp/myapp/
```

A defensive check might be:

```bash
if [[ "$target" != /var/tmp/myapp/* ]]; then
    printf 'ERROR: refusing unexpected target: %s\n' "$target" >&2
    exit 1
fi
```

But path safety can become more complex with:

* symbolic links
* `..`
* relative paths
* normalization
* mount points

For destructive production scripts, path validation deserves careful design and testing.

---

# 80. Never Let an Empty Variable Become a Destructive Target

This is one of the most important Bash safety habits.

Suppose:

```bash
target="$CLEANUP_DIR"
```

and `CLEANUP_DIR` is unset.

Then badly written commands may operate on something unintended.

Use:

```bash
target="${CLEANUP_DIR:?CLEANUP_DIR is required}"
```

and further validate the path.

For destructive operations, one check is rarely enough.

---

# 81. Defensive Scripting

Defensive scripting means writing code that assumes inputs, environments, and dependencies can be wrong.

A defensive script asks:

```text
Is the input present?

Is the input valid?

Does the file exist?

Is this really a directory?

Is the path inside the allowed location?

Does the required command exist?

Do I have permission?

Is there enough disk space?

Am I operating in the expected environment?

Has the prerequisite step succeeded?

Can this action be retried safely?

What happens if interrupted?
```

---

# 82. Validate Before Side Effects

Prefer:

```text
Parse
   |
   v
Validate
   |
   v
Check dependencies
   |
   v
Check environment
   |
   v
Show plan
   |
   v
Perform changes
```

Avoid:

```text
Modify system
   |
   v
Discover bad argument
```

Validation should happen as early as possible.

---

# 83. Use Meaningful Exit Codes

A simple CLI contract might use:

```text
0   success
1   operational failure
2   invalid usage
```

For a more specialized tool, you might deliberately define additional statuses.

Document them.

Do not randomly return different codes with no meaning.

---

# 84. Error Messages Should Be Actionable

Bad:

```text
Failed.
```

Better:

```text
ERROR: backup failed.
```

Better still:

```text
ERROR: unable to copy /srv/app/config.yml to /backups/app/config.yml
```

Even better when appropriate:

```text
ERROR: backup destination is not writable: /backups/app
```

Useful errors reduce troubleshooting time.

---

# 85. Send Errors to stderr

Use:

```bash
printf 'ERROR: configuration missing\n' >&2
```

Why?

Because stdout may be used for actual data.

Example:

```bash
result="$(./script.sh)"
```

If error messages are printed to stdout, they may contaminate captured output.

Separate:

```text
stdout → intended data/output
stderr → diagnostics/errors
```

---

# 86. Temporary File Cleanup

From Parts 10 and 13, you already know:

```bash
mktemp
```

is useful for safe temporary resources.

Example:

```bash
temp_file="$(mktemp)" || {
    printf 'ERROR: failed to create temporary file\n' >&2
    exit 1
}
```

Then register cleanup.

---

# 87. Cleanup Function

Example:

```bash
temp_file=""

cleanup() {
    local status=$?

    if [[ -n "$temp_file" && -f "$temp_file" ]]; then
        rm -f -- "$temp_file"
    fi

    return "$status"
}

trap cleanup EXIT
```

The cleanup function preserves the original exit status.

---

# 88. Temporary Directory Cleanup

Example:

```bash
work_dir=""

cleanup() {
    local status=$?

    if [[ -n "$work_dir" &&
          -d "$work_dir" &&
          "$work_dir" == /tmp/myapp.* ]]; then
        rm -rf -- "$work_dir"
    fi

    return "$status"
}

work_dir="$(mktemp -d '/tmp/myapp.XXXXXX')" || exit 1

trap cleanup EXIT
```

The path restriction gives another safety layer.

---

# 89. Cleanup Can Fail Too

Suppose:

```bash
rm -rf -- "$work_dir"
```

fails during cleanup.

Should cleanup failure replace the original error?

Sometimes yes.

Sometimes no.

For example:

```text
Deployment failed with status 7
Cleanup failed with status 1
```

The original deployment failure may be the more important root cause.

A mature script should decide how cleanup failures are reported.

---

# 90. Report Cleanup Failure Without Hiding Original Failure

Example:

```bash
cleanup() {
    local original_status=$?

    if [[ -n "$work_dir" &&
          -d "$work_dir" &&
          "$work_dir" == /tmp/myapp.* ]]; then

        if ! rm -rf -- "$work_dir"; then
            printf 'WARN: failed to remove temporary directory: %s\n' \
                "$work_dir" >&2
        fi
    fi

    return "$original_status"
}
```

Now cleanup problems are visible without replacing the original status.

---

# 91. Testing Before Production

Never make production the first environment where you test a destructive script.

Prefer:

```text
Local lab
   |
   v
Test data
   |
   v
Development
   |
   v
Staging
   |
   v
Controlled production rollout
```

The exact environments vary, but the principle remains:

> Reduce uncertainty before touching important systems.

---

# 92. Test with Fake Data

Suppose you are building:

```text
cleanup-old-logs.sh
```

Do not begin with:

```text
/var/log/production-app/
```

Create:

```bash
mkdir -p "$HOME/bash-lab/log-cleanup"
```

Then create fake files:

```bash
touch "$HOME/bash-lab/log-cleanup/app-1.log"
touch "$HOME/bash-lab/log-cleanup/app-2.log"
touch "$HOME/bash-lab/log-cleanup/app-3.log"
```

Test against those first.

---

# 93. Dry-Run Mode

A dry-run mode shows what would happen without making the destructive change.

Example:

```bash
if [[ "$dry_run" == "true" ]]; then
    printf 'DRY RUN: would delete %s\n' "$file"
else
    rm -f -- "$file"
fi
```

This is useful for:

* deletion
* deployment
* bulk rename
* permission changes
* infrastructure operations

---

# 94. A Fake Dry Run Is Dangerous

This is not a dry run:

```bash
rm -f -- "$file"

if [[ "$dry_run" == "true" ]]; then
    echo "Would delete $file"
fi
```

The destructive operation already happened.

Dry-run logic must prevent the side effect itself.

---

# 95. Back Up Before Destructive Changes

Where appropriate:

```text
Validate
   |
   v
Backup
   |
   v
Verify backup
   |
   v
Modify
   |
   v
Verify modification
```

Do not write:

```bash
cp "$file" "$backup"
rm "$file"
```

and assume the backup worked.

Check it.

Example:

```bash
if ! cp -a -- "$file" "$backup"; then
    printf 'ERROR: backup failed; refusing deletion\n' >&2
    exit 1
fi
```

Only then consider the destructive step.

---

# 96. Verify Outcomes

A command returning 0 may be sufficient for some operations.

For critical workflows, additional verification may be appropriate.

Example:

```bash
if ! cp -a -- "$source" "$backup"; then
    printf 'ERROR: copy failed\n' >&2
    exit 1
fi

if [[ ! -f "$backup" ]]; then
    printf 'ERROR: backup file not found after copy\n' >&2
    exit 1
fi
```

The exact verification depends on the operation.

For directories or critical data, stronger verification may be needed.

---

# 97. Assertions vs User Input Validation

These concepts overlap but have different intentions.

User validation asks:

```text
Did the user provide valid input?
```

Assertions often ask:

```text
Is an internal assumption required by the script true?
```

Example user validation:

```bash
case "$environment" in
    development|staging|production)
        ;;
    *)
        printf 'ERROR: invalid environment\n' >&2
        exit 2
        ;;
esac
```

Example assertion:

```bash
[[ -d "$work_dir" ]] || {
    printf 'ERROR: internal workspace missing\n' >&2
    exit 1
}
```

# 98. ShellCheck

ShellCheck is a static-analysis tool for shell scripts.

It can detect many common problems, including:

* quoting mistakes
* suspicious expansions
* incorrect test syntax
* unused variables
* portability concerns
* common command-substitution problems
* problematic loops
* shell-specific mistakes

It is one of the most valuable tools for Bash development.

---

# 99. Check Whether ShellCheck Is Installed

Run:

```bash
command -v shellcheck
```

If installed, you may see a path such as:

```text
/usr/bin/shellcheck
```

If nothing is returned, it may not be installed.

Installation depends on your operating system and package manager.

---

# 100. Run ShellCheck

Use:

```bash
shellcheck script.sh
```

Example:

```bash
shellcheck deploy.sh
```

ShellCheck may report findings with codes such as:

```text
SC2086
SC2046
SC2164
```

These codes correspond to documented explanations.

Do not blindly suppress warnings.

Understand why the warning exists.

---

# 101. Example ShellCheck Problem

Consider:

```bash
rm $file
```

ShellCheck may warn about unquoted variable expansion.

Better:

```bash
rm -- "$file"
```

Why?

Because quoting prevents unwanted word splitting and pathname expansion.

The:

```text
--
```

also protects against filenames beginning with `-` being interpreted as options by commands that support the convention.

---

# 102. ShellCheck Is Not a Proof of Correctness

A script can pass ShellCheck and still:

* contain wrong business logic
* delete the wrong directory
* call the wrong server
* use incorrect thresholds
* expose secrets
* make unsafe architectural decisions

Static analysis is one layer.

Think:

```text
bash -n
   +
ShellCheck
   +
tests
   +
review
   +
safe environment
   +
runtime validation
```

---

# 103. `bash -n` and ShellCheck Solve Different Problems

`bash -n` primarily checks:

```text
Can Bash parse this script?
```

ShellCheck asks many questions like:

```text
Does this code contain suspicious shell patterns?
```

Testing asks:

```text
Does this script actually behave correctly?
```

You need all three perspectives.

---

# 104. Tracing an Entire Script

Instead of modifying the script with:

```bash
set -x
```

you can invoke:

```bash
bash -x script.sh
```

This enables execution tracing for that run.

Useful when debugging without permanently editing the script.

---

# 105. Syntax Check from the Command Line

Similarly:

```bash
bash -n script.sh
```

checks syntax.

You can combine workflow steps:

```bash
bash -n script.sh
shellcheck script.sh
bash -x script.sh
```

But do not automatically run a dangerous script with `-x`.

Inspect and test it safely first.

---

# 106. Trace Only a Section

Instead of tracing everything:

```bash
set -x

problematic_function

set +x
```

This reduces noise.

It also reduces the chance of exposing unrelated sensitive information.

---

# 107. Trace Functions Individually

Suppose:

```bash
deploy_application() {
    ...
}
```

is failing.

Instead of tracing a 2,000-line script, isolate the problem.

You may temporarily arrange a safe test that runs only:

```bash
set -x
deploy_application
set +x
```

with non-production inputs.

Debug the smallest reproducible unit.

---

# 108. Reduce the Problem

This is one of the strongest debugging techniques.

Suppose:

```text
1,500-line deployment script fails
```

Do not stare at all 1,500 lines.

Ask:

```text
Which phase failed?
```

Perhaps:

```text
Configuration
Dependency validation
Artifact download
Extraction
Deployment
Health check
Cleanup
```

Then isolate that phase.

---

# 109. Add Evidence, Not Random Changes

Bad debugging:

```text
Maybe add sudo.

Maybe add sleep 10.

Maybe remove set -e.

Maybe chmod 777.

Maybe run as root.
```

This changes the system without understanding the cause.

Better:

```text
What exact command failed?

What status did it return?

What arguments did it receive?

What file exists?

Who owns it?

What are its permissions?

What environment variable is set?

What output did the command produce?
```

Collect evidence first.

---

# 110. Never Use `chmod 777` as a Generic Debugging Fix

Permission errors often cause beginners to try:

```bash
chmod -R 777 something
```

This can create security problems and may not address the actual cause.

Instead inspect:

```bash
ls -ld path
stat path
```

Ask:

```text
Who owns it?

Which user is running the script?

Which permission is actually required?
```

Fix the minimum necessary permission.

---

# 111. Never Use `sudo` as a Generic Debugging Fix

If:

```text
Permission denied
```

appears, do not automatically prepend:

```bash
sudo
```

Determine:

* who should own the resource
* whether the script should require privilege
* whether permissions are misconfigured
* whether the path is wrong

Least privilege matters.

---

# 112. Debugging Variables

If you suspect a variable:

```bash
printf 'DEBUG target=<%s>\n' "$target" >&2
```

Using delimiters:

```text
<...>
```

helps expose empty values and whitespace.

Example:

```text
DEBUG target=<>
```

immediately reveals an empty string.

---

# 113. Inspect Variables with `declare -p`

For Bash variables:

```bash
declare -p variable_name
```

Example:

```bash
declare -p servers
```

For an array, this can reveal its actual structure.

This is often more informative than:

```bash
echo "$servers"
```

---

# 114. Inspect Quoting Problems

Suppose:

```bash
files="/tmp/a file.txt /tmp/b file.txt"
```

Then:

```bash
for file in $files; do
    ...
done
```

splits on spaces.

Tracing may reveal unexpected arguments.

This is not a random runtime problem.

It is a data-structure and quoting problem.

Use arrays for collections:

```bash
files=(
    "/tmp/a file.txt"
    "/tmp/b file.txt"
)
```

Then:

```bash
for file in "${files[@]}"; do
    ...
done
```

---

# 115. Debugging Pipelines

Suppose:

```bash
generate_data | grep ERROR | sort > report.txt
```

fails unexpectedly.

Break it apart.

Step 1:

```bash
generate_data > raw.txt
```

Inspect:

```bash
less raw.txt
```

Step 2:

```bash
grep ERROR raw.txt > matches.txt
```

Inspect status:

```bash
status=$?
printf 'grep status=%s\n' "$status"
```

Step 3:

```bash
sort matches.txt > report.txt
```

Reducing the pipeline helps identify which stage fails.

---

# 116. Debugging Conditional Logic

Suppose:

```bash
if [[ "$environment" = "production" ]]; then
    ...
fi
```

does not run.

Print:

```bash
printf 'environment=<%s>\n' "$environment"
```

You may discover:

```text
environment=<Production>
```

instead of:

```text
production
```

The problem is not the `if` syntax.

It is the input value.

---

# 117. Debugging Filesystem Assumptions

Suppose:

```bash
cp "$config" "$destination"
```

fails.

Inspect:

```bash
printf 'config=<%s>\n' "$config"
printf 'destination=<%s>\n' "$destination"

ls -ld -- "$config" "$destination"
```

If appropriate:

```bash
stat -- "$config"
```

Do not assume paths are what you think they are.

---

# 118. Debugging Current Directory Problems

A script may work when run from:

```text
/home/ann/project
```

but fail from:

```text
/tmp
```

because it uses relative paths.

Inspect:

```bash
pwd
```

and:

```bash
printf 'script source: %s\n' "${BASH_SOURCE[0]}"
```

Then consider resolving paths relative to the script location where appropriate.

---

# 119. Debugging Environment Differences

A script may work interactively but fail in:

* cron
* CI/CD
* systemd
* Docker
* Kubernetes
* SSH automation

because environment variables differ.

Inspect safely:

```bash
printf 'PATH=%s\n' "$PATH"
```

But do not dump every environment variable into logs if secrets may be present.

---

# 120. Debugging `PATH`

Suppose:

```text
kubectl: command not found
```

but `kubectl` works in your interactive terminal.

Check:

```bash
command -v kubectl
```

and:

```bash
printf 'PATH=%s\n' "$PATH"
```

The automated environment may have a different `PATH`.

Part 16 will examine environment and Bash configuration more deeply.

# 121. Common Bash Debugging Workflow

Use this workflow rather than random edits:

```text
1. Reproduce the failure safely
        |
        v
2. Read the exact error
        |
        v

        |
        v

        |
        v

        |

        |

        |
```

# 122. Practical Broken-Script Troubleshooting Lab

Now we will troubleshoot a deliberately broken Bash script.

The scenario:

A junior engineer created a cleanup script intended to:

1. accept an environment
2. locate an application directory
3. back up old logs
4. remove old logs
5. generate a report
6. clean temporary files

But the script contains multiple problems.

Some are syntax-related.

Some are runtime failures.

Some are logic errors.

Some are safety problems.

Some are strict-mode problems.

Your job is not merely to make the errors disappear.

Your job is to understand why each problem exists.

---

# 123. Create a Safe Lab

Do not use production logs.

Create:

```bash
mkdir -p "$HOME/bash-lab/part14/app/logs"
mkdir -p "$HOME/bash-lab/part14/backups"

cd "$HOME/bash-lab/part14"
```

Create test files:

```bash
printf 'INFO application started\n' > app/logs/app-1.log
printf 'ERROR database timeout\n' > app/logs/app-2.log
printf 'WARN memory high\n' > app/logs/app-3.log
```

Verify:

```bash
find "$HOME/bash-lab/part14" -maxdepth 3 -type f -print
```

---

# 124. The Deliberately Broken Script

Create:

```text
broken-cleanup.sh
```

with:

```bash
#!/usr/bin/env bash

set -eu

environment=$1

base_dir="$HOME/bash-lab/part14"
log_dir="$base_dir/app/logs"
backup_dir="$base_dir/backups/$enviroment"

echo "Environment: $environment"
echo "Log directory: $log_dir"
echo "Backup directory: $backup_dir"

mkdir -p $backup_dir

temp_file="/tmp/report.txt"

grep ERROR "$log_dir"/*.log | sort > "$temp_file"

echo "Errors found:"
cat "$temp_file"

for file in "$log_dir/*.log"; do
    cp $file "$backup_dir/"
    rm -f $file
done

echo "Cleanup complete"
```

Make it executable:

```bash
chmod +x broken-cleanup.sh
```

Do not immediately start randomly editing it.

Troubleshoot systematically.

---

# 125. Step 1: Syntax Check

Run:

```bash
bash -n broken-cleanup.sh
```

The script may pass.

That tells us:

```text
The script is syntactically valid.
```

It does not tell us:

```text
The script is correct.
```

This is already an important finding.

---

# 126. Step 2: Run ShellCheck

If ShellCheck is installed:

```bash
shellcheck broken-cleanup.sh
```

Review the findings.

# 144. Critical Logic Problem: Delete After Unverified Backup

# 145. Safe Backup Before Deletion

Only then:

```bash

```

# 150. Complete Corrected Script

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

shopt -s nullglob

DEBUG="${DEBUG:-false}"

base_dir="$HOME/bash-lab/part14"

environment=""
log_dir=""
backup_dir=""
work_dir=""
raw_report=""
report=""

log_files=()

debug() {
    [[ "$DEBUG" == "true" ]] || return 0

    local message="$*"
    local source="${BASH_SOURCE[1]:-${BASH_SOURCE[0]}}"
    local line="${BASH_LINENO[0]:-unknown}"
    local function="${FUNCNAME[1]:-main}"

    printf '[DEBUG] %s:%s:%s: %s\n' \
        "$source" \
        "$line" \
        "$function" \
        "$message" >&2
}

error_handler() {
    local status=$?
    local line="$1"
    local command="$2"
    local source="$3"

    printf 'ERROR: %s:%s: status=%s command=%s\n' \
        "$source" \
        "$line" \
        "$status" \
        "$command" >&2

    return "$status"
}

cleanup() {
    local original_status=$?

    if [[ -n "${work_dir:-}" &&
          -d "$work_dir" &&
          "$work_dir" == /tmp/veriqta-cleanup.* ]]; then

        if ! rm -rf -- "$work_dir"; then
            printf 'WARN: failed to remove temporary workspace: %s\n' \
                "$work_dir" >&2
        fi
    fi

    return "$original_status"
}

usage() {
    printf 'Usage: %s ENVIRONMENT\n' "$0"
    printf '\n'
    printf 'Allowed environments:\n'
    printf '  development\n'
    printf '  staging\n'
}

parse_args() {
    if (( $# != 1 )); then
        usage >&2
        return 2
    fi

    environment="$1"
}

validate_environment() {
    case "$environment" in
        development|staging)
            return 0
            ;;
        *)
            printf 'ERROR: unsupported environment: %s\n' \
                "$environment" >&2
            return 2
            ;;
    esac
}

validate_paths() {
    log_dir="$base_dir/app/logs"
    backup_dir="$base_dir/backups/$environment"

    if [[ ! -d "$log_dir" ]]; then
        printf 'ERROR: log directory does not exist: %s\n' \
            "$log_dir" >&2
        return 1
    fi

    if ! mkdir -p -- "$backup_dir"; then
        printf 'ERROR: unable to create backup directory: %s\n' \
            "$backup_dir" >&2
        return 1
    fi
}

create_workspace() {
    work_dir="$(mktemp -d '/tmp/veriqta-cleanup.XXXXXX')" || {
        printf 'ERROR: unable to create temporary workspace\n' >&2
        return 1
    }

    if [[ -z "$work_dir" ||
          ! -d "$work_dir" ||
          "$work_dir" != /tmp/veriqta-cleanup.* ]]; then

        printf 'ERROR: invalid temporary workspace\n' >&2
        return 1
    fi

    raw_report="$work_dir/raw-errors.txt"
    report="$work_dir/error-report.txt"
}

collect_log_files() {
    log_files=("$log_dir"/*.log)

    if (( ${#log_files[@]} == 0 )); then
        printf 'INFO: no log files found in %s\n' "$log_dir"
        return 1
    fi

    return 0
}

build_error_report() {
    local grep_status=0

    grep -H "ERROR" "${log_files[@]}" > "$raw_report" || \
        grep_status=$?

    case "$grep_status" in
        0)
            if ! sort "$raw_report" > "$report"; then
                printf 'ERROR: unable to sort error report\n' >&2
                return 1
            fi
            ;;

        1)
            : > "$report"
            ;;

        *)
            printf 'ERROR: grep failed with status %s\n' \
                "$grep_status" >&2
            return 1
            ;;
    esac
}

print_error_report() {
    printf '\nERROR REPORT\n'
    printf '============\n'

    if [[ -s "$report" ]]; then
        cat -- "$report"
    else
        printf 'No ERROR entries found.\n'
    fi
}

backup_and_remove() {
    local file="$1"
    local filename
    local backup_file

    filename="$(basename -- "$file")"
    backup_file="$backup_dir/$filename"

    debug "Backing up <$file> to <$backup_file>"

    if ! cp -a -- "$file" "$backup_file"; then
        printf 'ERROR: failed to back up: %s\n' "$file" >&2
        return 1
    fi

    if [[ ! -f "$backup_file" ]]; then
        printf 'ERROR: backup verification failed: %s\n' \
            "$backup_file" >&2
        return 1
    fi

    if ! rm -f -- "$file"; then
        printf 'ERROR: unable to remove original: %s\n' \
            "$file" >&2
        return 1
    fi

    printf 'Processed: %s\n' "$file"
}

process_logs() {
    local file

    for file in "${log_files[@]}"; do
        backup_and_remove "$file"
    done
}

main() {
    parse_args "$@"
    validate_environment
    validate_paths
    create_workspace

    trap cleanup EXIT
    trap 'error_handler "$LINENO" "$BASH_COMMAND" "${BASH_SOURCE[0]}"' ERR

    debug "environment=<$environment>"
    debug "log_dir=<$log_dir>"
    debug "backup_dir=<$backup_dir>"
    debug "work_dir=<$work_dir>"

    if ! collect_log_files; then
        return 0
    fi

    build_error_report
    print_error_report

    process_logs

    printf '\nCleanup completed successfully.\n'
}

main "$@"
```

If your script depends on newer features, document the minimum Bash version.

This is particularly important across:

* Linux distributions
* macOS
* CI images
* containers

# Part 14 Summary

Reliable Bash is not created by adding one line such as:

```bash
set -e
```

Reliability comes from layers.

Start with syntax validation:

```bash
bash -n script.sh
```

Use static analysis:

```bash
shellcheck script.sh
```

Understand command exit statuses.

Handle critical failures explicitly.

Use strict options deliberately:

```bash
set -Eeuo pipefail
```

but understand what each option does.

Use:

```bash
set -x
```

or:

```bash
bash -x script.sh
```

when tracing is useful, while protecting secrets.

Use diagnostic information such as:

```text
BASH_SOURCE
BASH_LINENO
LINENO
FUNCNAME
BASH_COMMAND
```

to answer:

```text
Where did this fail?
What command failed?
What was the status?
Which function was running?
```

Use assertions and validation to fail before side effects.

Use:

```bash
mktemp
```

for temporary resources.

Use:

```bash
trap cleanup EXIT
```

for controlled cleanup.

Treat destructive operations as safety-critical.

Prefer:

```text
Validate
   |
   v
Backup
   |
   v
Verify
   |
   v
Modify
   |
   v
Verify again
```

Test:

```text
success paths
failure paths
missing input
invalid input
permissions
missing files
empty results
interruptions
unexpected filenames
```

And when something fails, do not begin with:

```text
sudo
chmod 777
sleep 10
remove set -e
add || true
```

Begin with evidence.

The core debugging loop is:

```text
Observe
   |
   v
Understand symptom
   |
   v
Check simplest cause
   |
   v
Gather evidence
   |
   v
Form hypothesis
   |
   v
Test
   |
   v
Fix root cause
   |
   v
Verify
   |
   v
Prevent recurrence
```

That is the difference between merely writing Bash scripts and being able to troubleshoot Bash automation when real systems behave differently from your assumptions.
