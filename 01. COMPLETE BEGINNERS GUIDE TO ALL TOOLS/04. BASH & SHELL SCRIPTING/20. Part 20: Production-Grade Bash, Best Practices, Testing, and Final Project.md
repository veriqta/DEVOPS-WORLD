# 1. A Quick Script vs Production Automation

Consider:

```bash
df -h
systemctl status nginx
curl https://example.com/health
```

This may be perfectly useful when you are investigating a server manually.

Now imagine putting similar commands into automation that:

* runs every five minutes
* executes on 100 servers
* has access to production
* writes reports
* restarts services
* calls APIs
* runs from CI/CD
* is maintained by several engineers

The requirements change.

A production-quality script should usually consider:

```text
Correctness
Security
Predictability
Failure handling
Input validation
Logging
Observability
Testing
Maintainability
Idempotency
Concurrency
Cleanup
Documentation
Portability assumptions
Exit codes
Operational safety
```

Production quality does not mean making every script enormous.

It means matching engineering rigor to operational risk.

---

# 2. Production Quality Is Context Dependent

A five-line script that lists files does not need the architecture of a deployment system.

For example:

```bash
#!/usr/bin/env bash

find "$HOME/logs" -type f -name '*.log'
```

This may already be sufficient.

But a script that can restart production services requires stronger safeguards.

Think in terms of risk:

```text
Low-risk local helper
        |
        v
Moderate operational utility
        |
        v
Shared infrastructure automation
        |
        v
Production-changing automation
```

As risk increases, so should:

```text
validation
testing
logging
review
permissions
failure handling
observability
change control
```

Do not overengineer tiny scripts.

Do not underengineer dangerous ones.

# 3. The Production Bash Mindset

A production script should answer several questions before doing anything important.

```text
Who am I?
Where am I running?
What was requested?
Is the request valid?
Do I have the required dependencies?
Do I have permission?
Is the target correct?
What is the current state?
What will change?
Can the operation be repeated safely?
What happens if it fails halfway?
Can temporary resources be cleaned?
Can another copy run simultaneously?
How long may an operation wait?
Should a temporary failure be retried?
How will success be verified?
How will failure be reported?
Will secrets remain protected?
```

This mindset matters more than memorizing syntax.

# 4. Recommended Script Structure

A substantial Bash utility benefits from predictable organization.

A useful structure is:

```bash
#!/usr/bin/env bash

# Shell behavior

# Constants

# Runtime defaults

# Logging functions

# Utility functions

# Configuration functions

# Argument parsing

# Validation functions

# Operational functions

# Reporting functions

# Cleanup

# main()

main "$@"
```

This allows another engineer to understand the script quickly.

---

# 5. Example Structural Skeleton

```bash
#!/usr/bin/env bash

set -o pipefail

readonly SCRIPT_NAME="${0##*/}"

config_file=""
environment=""
dry_run=0
debug=0

log_info() {
    :
}

log_error() {
    :
}

usage() {
    :
}

parse_args() {
    :
}

load_config() {
    :
}

validate_inputs() {
    :
}

validate_dependencies() {
    :
}

perform_checks() {
    :
}

generate_report() {
    :
}

cleanup() {
    :
}

main() {
    parse_args "$@"
    load_config
    validate_inputs
    validate_dependencies
    perform_checks
    generate_report
}

trap cleanup EXIT

main "$@"
```

The functions are initially empty.

But the structure tells you where responsibilities belong.

---

# 6. Why main() Is Valuable

Without `main`, scripts often become:

```text
variable
command
function
command
loop
function
command
condition
command
```

Execution flow becomes difficult to understand.

With:

```bash
main() {
    parse_args "$@"
    load_config
    validate
    run_checks
    generate_report
}
```

you can understand the high-level workflow immediately.

Think of `main()` as the script's table of contents.

---

# 7. Keep Top-Level Execution Minimal

A useful convention is:

```bash
main "$@"
```

as the primary top-level execution statement.

Why?

Because functions become easier to:

* test
* reuse
* inspect
* reason about
* call independently

It also reduces unexpected side effects when sourcing files for testing.

---

# 8. Naming Conventions

Bash does not enforce one naming style.

Consistency matters more than choosing one universal convention.

A useful approach is:

```text
Variables:
snake_case

Functions:
snake_case

Constants:
UPPER_SNAKE_CASE
```

Example:

```bash
server_name="web01"
retry_count=3

readonly DEFAULT_TIMEOUT=10
readonly REPORT_DIRECTORY="/var/tmp/reports"

check_disk_usage() {
    :
}
```

---

# 9. Use Descriptive Names

Weak:

```bash
x=90
d="/var/log"
f() {
    :
}
```

Better:

```bash
disk_threshold=90
log_directory="/var/log"

check_disk_usage() {
    :
}
```

Production code is read more often than it is written.

Optimizing names for typing speed is usually a poor trade.

---

# 10. Avoid Reusing Variables for Unrelated Meanings

Bad:

```bash
value="$1"

value="$(df -P /)"

value=90
```

The meaning of `value` keeps changing.

Better:

```bash
target_host="$1"
disk_output="$(df -P /)"
disk_threshold=90
```

Clear state makes debugging easier.

---

# 11. Local Variables

Inside functions, prefer:

```bash
local
```

where appropriate.

Example:

```bash
check_file() {
    local file_path="$1"

    [[ -f "$file_path" ]]
}
```

Without `local`, assignments can accidentally modify global state.

Remember Bash uses dynamic scoping, so variable design still requires care.

---

# 12. Constants with readonly

For values that should not change:

```bash
readonly DEFAULT_TIMEOUT=10
readonly DEFAULT_RETRIES=3
readonly SCRIPT_NAME="${0##*/}"
```

Attempting to modify a readonly variable causes an error.

This communicates intent:

```text
this value is configuration for the program itself
not mutable runtime state
```

---

# 13. Comments vs Self-Explanatory Code

Bad comments repeat obvious syntax:

```bash
# Set x to 5
x=5

# Check if file exists
if [[ -f "$file" ]]; then
```

These comments add little value.

Prefer readable names:

```bash
max_retries=5

if [[ -f "$config_file" ]]; then
```

Then use comments to explain:

* why something unusual is necessary
* assumptions
* external constraints
* security decisions
* compatibility workarounds
* intentionally non-obvious behavior

---

# 14. Good Comment Example

```bash
# Production health checks may briefly fail while the load balancer
# updates its backend targets. Retry only connection/server failures
# and stop after the configured attempt limit.
```

This explains reasoning.

That is more useful than:

```bash
# Retry loop
```

---

# 15. Do Not Let Comments Become False

Suppose:

```bash
# Retry three times
max_retries=5
```

Now the comment contradicts the code.

Comments require maintenance too.

Where possible, make the code communicate the behavior.

---

# 16. Functions Should Have Clear Responsibilities

Weak:

```bash
do_everything() {
    # validate config
    # check disk
    # check memory
    # call API
    # restart service
    # create report
    # send report
}
```

Better:

```bash
load_config
validate_config
check_disk
check_memory
check_services
check_endpoint
generate_report
```

Smaller functions are easier to:

* test
* debug
* reuse
* review

---

# 17. Functions Should Have Clear Contracts

A function should make it clear:

```text
What input does it receive?
What output does it produce?
What status does it return?
Does it change external state?
```

For example:

```bash
file_exists() {
    local path="$1"
    [[ -f "$path" ]]
}
```

Contract:

```text
Input:
file path

stdout:
nothing

status:
0 if regular file exists
nonzero otherwise

side effects:
none
```

That is easy to reason about.

---

# 18. Separate Data from Status

Suppose a function returns data:

```bash
get_hostname() {
    hostname
}
```

Capture:

```bash
server_hostname="$(get_hostname)"
```

The function's stdout is its data channel.

Errors should normally go to stderr:

```bash
printf 'ERROR: Could not determine hostname\n' >&2
```

The exit status communicates success or failure.

Conceptually:

```text
stdout -> data
stderr -> diagnostics
status -> success/failure
```

Keeping these roles clear improves composition.

# 19. Configuration

Hard-coding every operational value makes scripts difficult to reuse.

Instead of:

```bash
disk_threshold=90
api_url="https://api.example.com/status"
service_name="nginx"
```

you may support configuration through:

* command-line arguments
* environment variables
* configuration files
* safe defaults

A common precedence model is:

```text
Built-in default
      |
      v
Configuration file
      |
      v
Environment variable
      |
      v
Command-line argument
```

The most explicit input wins.

Your project should document whatever precedence model it uses.

---

# 20. Do Not Turn Configuration into Arbitrary Code Execution

A common Bash technique is:

```bash
source "$config_file"
```

This executes the file as shell code.

If the file contains:

```bash
rm -rf ...
```

Bash executes it.

Therefore:

> Sourcing a configuration file means trusting that file as executable code.

For trusted internal configuration this may be acceptable.

For untrusted configuration it is dangerous.

---

# 21. Safer Simple Configuration Format

For this project, we can use a controlled key-value format:

```text
DISK_THRESHOLD=85
MEMORY_THRESHOLD=90
SERVICE=sshd
PORT=22
ENDPOINT=https://example.com/health
```

Then parse only supported keys rather than executing the file.

This reduces risk.

# 22. Logging

Production logs should be:

* consistent
* timestamped
* useful
* searchable
* free of secrets

Example:

```bash
timestamp() {
    date '+%Y-%m-%dT%H:%M:%S%z'
}

log_info() {
    printf '%s [INFO] %s\n' "$(timestamp)" "$*"
}

log_warn() {
    printf '%s [WARN] %s\n' "$(timestamp)" "$*" >&2
}

log_error() {
    printf '%s [ERROR] %s\n' "$(timestamp)" "$*" >&2
}
```

---

# 23. Debug Logging

Debug mode should provide extra information without automatically exposing secrets.

Example:

```bash
debug=0

log_debug() {
    if (( debug )); then
        printf '%s [DEBUG] %s\n' "$(timestamp)" "$*" >&2
    fi
}
```

Then:

```bash
log_debug "Checking service: $service_name"
```

Do not write:

```bash
log_debug "API token: $API_TOKEN"
```

Debug mode does not cancel security requirements.

---

# 24. Verbose Mode vs Debug Mode

Organizations use these terms differently.

A useful distinction is:

```text
Normal:
important operational messages

Verbose:
more execution detail

Debug:
developer/troubleshooting information
```

You might support:

```text
-v
--verbose

--debug
```

For the final beginner project, we will keep one:

```text
--debug
```

mode.

# 25. Error Handling

Production error handling requires intentional decisions.

For every important command, ask:

```text
If this fails:

Should the script stop?
Should it retry?
Should it warn and continue?
Should it mark the report unhealthy?
Should it clean up first?
Should it return a special exit code?
```

Not every failure has the same meaning.

# 26. Strict Mode

A commonly seen header is:

```bash
set -Eeuo pipefail
```

As you learned in Part 14, this is useful but not magical.

It can introduce surprising behavior around:

* expected nonzero commands
* arithmetic expressions
* pipelines
* conditionals
* functions
* command substitutions

Production engineering means understanding these options rather than copying them blindly.

For the final project, we will use:

```bash
set -o pipefail
```

and explicit error handling around important operations.

That makes failure behavior easier for a beginner to inspect.

# 27. Meaningful Exit Codes

You can define a small exit-code contract.

Example:

```bash
readonly EXIT_OK=0
readonly EXIT_CHECK_FAILED=1
readonly EXIT_USAGE=2
readonly EXIT_DEPENDENCY=3
readonly EXIT_CONFIG=4
readonly EXIT_RUNTIME=5
```

Then:

```bash
exit "$EXIT_USAGE"
```

when arguments are invalid.

Document these values.

Do not create dozens of arbitrary codes unless consumers genuinely need them.

---

# 28. Input Validation

Never assume:

```text
argument exists
number is numeric
file exists
directory is writable
hostname is safe
port is valid
URL is valid enough for your use
service exists
```

Validate before side effects.

---

# 29. Numeric Validation

Suppose:

```bash
disk_threshold="$1"
```

Validate:

```bash
if [[ ! "$disk_threshold" =~ ^[0-9]+$ ]]; then
    log_error "Disk threshold must be an integer"
    return 1
fi
```

Then range:

```bash
if (( disk_threshold < 1 || disk_threshold > 100 )); then
    log_error "Disk threshold must be between 1 and 100"
    return 1
fi
```

Syntax validation and semantic validation are separate.

---

# 30. Port Validation

```bash
validate_port() {
    local port="$1"

    if [[ ! "$port" =~ ^[0-9]+$ ]]; then
        return 1
    fi

    (( port >= 1 && port <= 65535 ))
}
```

This checks:

* numeric format
* valid TCP/UDP port-number range

It does not prove a service is listening.

That requires a separate check.

---

# 31. Dependency Validation

If your script requires:

```text
curl
jq
ss
ssh
```

check them before reaching the middle of the workflow.

Example:

```bash
require_command() {
    local command_name="$1"

    if ! command -v "$command_name" >/dev/null 2>&1; then
        log_error "Required command missing: $command_name"
        return 1
    fi
}
```

Then:

```bash
for command_name in curl jq ss; do
    require_command "$command_name" || exit "$EXIT_DEPENDENCY"
done
```

Fail early.

---

# 32. Optional Dependencies

Not every feature needs every dependency.

Suppose remote checking requires SSH.

Do not fail local-only operation because `ssh` is missing if the remote feature was not requested.

Instead:

```text
Core dependencies -> always validate
Feature dependencies -> validate when feature enabled
```

This keeps the tool flexible.

---

# 33. Secure Defaults

A secure default reduces risk when configuration is absent or ambiguous.

Examples:

```text
Do not default to production.
Do not default to destructive mode.
Do not disable TLS verification by default.
Do not expose secrets in debug logs.
Do not use world-writable permissions by default.
Do not automatically run as root.
Do not automatically retry destructive requests.
```

A safe default should usually prefer:

```text
stop
warn
require explicit intent
```

over dangerous convenience.

---

# 34. Least Privilege

Least privilege means giving a process only the permissions required to perform its task.

If a script only reads:

```text
disk usage
memory
service status
logs readable by current user
```

it may not need root.

Do not begin every operational script with:

```bash
if [[ "$EUID" -ne 0 ]]; then
    echo "Run as root"
    exit 1
fi
```

unless root is genuinely required.

---

# 35. Elevate Only Where Necessary

A better architecture may allow:

```text
read-only checks
      |
      +--> normal user

specific administrative action
      |
      +--> controlled sudo permission
```

This reduces the blast radius if the script has a bug.

# 36. Secrets Handling

Secrets may include:

* API tokens
* passwords
* private keys
* cloud credentials
* database credentials
* signing keys

Avoid:

```bash
API_TOKEN="secret-value"
```

inside committed source.

Possible mechanisms include:

* CI secret stores
* environment injection
* secret managers
* workload identity
* protected files
* short-lived credentials

The correct method depends on your environment.

---

# 37. Never Dump the Entire Environment During Debugging

This can be dangerous:

```bash
env
```

or:

```bash
export -p
```

inside CI logs.

The environment may contain secrets.

Instead inspect only specific safe variables:

```bash
printf 'PATH=%s\n' "$PATH"
printf 'HOME=%s\n' "$HOME"
```

when needed.

---

# 38. Quoting Discipline

One of the most important Bash habits is:

```bash
"$variable"
```

rather than:

```bash
$variable
```

unless you intentionally want word splitting or glob expansion.

Example:

```bash
rm -- "$file"
```

not:

```bash
rm $file
```

---

# 39. Quote Array Expansions Correctly

Use:

```bash
"${servers[@]}"
```

not:

```bash
${servers[@]}
```

when iterating safely:

```bash
for server in "${servers[@]}"; do
    printf '%s\n' "$server"
done
```

This preserves each element as one argument.

---

# 40. Use -- Where Supported

If a filename begins with:

```text
-
```

a command may interpret it as an option.

Use:

```bash
rm -- "$file"
cp -- "$source" "$destination"
mv -- "$source" "$destination"
```

where supported.

This is particularly important when filenames come from external input.

---

# 41. Temporary Resources

Avoid predictable temporary files:

```bash
temp_file="/tmp/report.txt"
```

Another process could interfere with that path.

Use:

```bash
temp_file="$(mktemp)"
```

or:

```bash
temp_dir="$(mktemp -d)"
```

Check success.

---

# 42. Cleanup

Temporary resources should be cleaned even when the script fails.

Example:

```bash
temp_dir=""

cleanup() {
    local status=$?

    if [[ -n "$temp_dir" && -d "$temp_dir" ]]; then
        rm -rf -- "$temp_dir"
    fi

    return "$status"
}

trap cleanup EXIT
```

Capturing:

```bash
local status=$?
```

at the beginning preserves the original exit status.

---

# 43. Be Careful in Cleanup Functions

This is dangerous:

```bash
rm -rf -- "$temp_dir"
```

if `temp_dir` is not validated.

For temporary directories created by `mktemp`, you can add guards:

```bash
if [[ -n "$temp_dir" &&
      "$temp_dir" == /tmp/* &&
      -d "$temp_dir" ]]
then
    rm -rf -- "$temp_dir"
fi
```

Exact temporary paths differ between operating systems, so production code should design the guard around its actual environment.

---

# 44. Idempotency

A production utility may run repeatedly.

Ask:

> What happens if this operation runs twice?

Bad:

```bash
echo "server=web01" >> config
```

Repeated execution duplicates configuration.

Better approaches include:

* check before adding
* replace deterministically
* generate the whole file
* use an idempotent target tool

---

# 45. Idempotent Directory Creation

```bash
mkdir -p "$report_directory"
```

Running it repeatedly keeps the desired state:

```text
directory exists
```

This is a simple example of idempotency.

---

# 46. Idempotent Service Logic

Suppose you need a service running.

Weak approach:

```bash
systemctl restart "$service"
```

every time.

Better:

```bash
if systemctl is-active --quiet "$service"; then
    log_info "Service already active: $service"
else
    systemctl start "$service"
fi
```

Now the script changes state only when necessary.

Whether automatically starting a service is appropriate depends on your operational policy.

---

# 47. Concurrency Awareness

Suppose a maintenance script runs every hour.

The first execution becomes slow.

Before it finishes, the next scheduled execution starts.

Now:

```text
Process A
   |
   +--> modifies report

Process B
   |
   +--> modifies same report
```

Potential problems include:

* duplicate work
* corrupted files
* conflicting service operations
* duplicate API requests
* misleading reports

Production scripts should consider concurrent execution.

---

# 48. Lock Files

One approach is a lock.

On Linux, `flock` is commonly useful.

Example:

```bash
exec 9>"/tmp/my-script.lock"

if ! flock -n 9; then
    printf 'Another instance is already running\n' >&2
    exit 1
fi
```

The open file descriptor remains locked while the script runs.

---

# 49. How flock Works Conceptually

```text
Process A
   |
   v
Acquire lock
   |
   v
Run work
   |
   v
Exit
   |
   v
Lock released
```

Meanwhile:

```text
Process B
   |
   v
Try lock
   |
   v
Lock unavailable
   |
   v
Exit safely
```

This prevents duplicate execution when designed correctly.

---

# 50. Do Not Implement Naive Locks Carelessly

A naive approach:

```bash
if [[ -f /tmp/script.lock ]]; then
    exit 1
fi

touch /tmp/script.lock
```

has problems.

Two processes can both check before either creates the file.

This is a race condition.

Stale lock files can also remain after crashes.

Use proper locking primitives when available.

---

# 51. Lock Scope Matters

Do you want to prevent:

```text
all instances of script
```

or only:

```text
two instances targeting the same server/environment
```

You might use:

```text
toolkit.lock
```

or:

```text
toolkit-production.lock
```

or:

```text
toolkit-web01.lock
```

depending on the resource being protected.

Lock design should match the operation.

# 52. Timeouts

Any external operation can potentially hang.

Examples:

```text
HTTP request
SSH connection
DNS query
remote command
service operation
cloud API
```

Use timeouts where supported.

Example:

```bash
curl \
    --connect-timeout 5 \
    --max-time 15 \
    "$url"
```

---

# 53. timeout Command

GNU systems often provide:

```bash
timeout 30 command
```

Example:

```bash
timeout 30 ssh "$server" "hostname"
```

If the command exceeds the limit, `timeout` terminates it according to its behavior.

Portability matters.

Do not assume every environment has GNU `timeout`.

Dependency-check it if your script requires it.

---

# 54. Retries

Some failures are temporary.

Examples:

* brief network interruption
* temporary API 503
* DNS delay
* service starting
* load balancer propagation

Retrying may help.

But retries should not become:

```text
repeat everything until something happens
```

---

# 55. Bounded Retry

A basic retry function:

```bash
retry() {
    local max_attempts="$1"
    local delay="$2"

    shift 2

    local attempt=1

    while (( attempt <= max_attempts )); do
        if "$@"; then
            return 0
        fi

        if (( attempt == max_attempts )); then
            break
        fi

        sleep "$delay"
        ((attempt++))
    done

    return 1
}
```

Usage:

```bash
retry 3 5 curl -fsS "$endpoint"
```

---

# 56. Retry Only Appropriate Operations

Do not blindly retry:

```text
payment creation
user deletion
resource creation
database mutation
email sending
```

unless the operation has appropriate idempotency guarantees.

Otherwise:

```text
attempt 1 succeeds remotely
response is lost
        |
        v
script thinks it failed
        |
        v
attempt 2 repeats side effect
```

You may create duplicate effects.

---

# 57. Backoff

Instead of waiting the same amount each time:

```text
2 seconds
2 seconds
2 seconds
```

you can increase the delay:

```text
1 second
2 seconds
4 seconds
8 seconds
```

This is exponential backoff.

It reduces pressure on a struggling dependency.

---

# 58. Simple Exponential Backoff

```bash
retry_with_backoff() {
    local max_attempts="$1"
    shift

    local attempt=1
    local delay=1

    while (( attempt <= max_attempts )); do
        if "$@"; then
            return 0
        fi

        if (( attempt == max_attempts )); then
            break
        fi

        log_warn \
            "Attempt $attempt failed. Retrying in ${delay}s."

        sleep "$delay"

        delay=$((delay * 2))
        ((attempt++))
    done

    return 1
}
```

---

# 59. Backoff Limits

Unlimited exponential growth is not useful.

You may cap the delay:

```bash
if (( delay > 30 )); then
    delay=30
fi
```

A more mature retry policy might include:

```text
maximum attempts
maximum delay
total timeout
retryable error classification
jitter
```

Jitter adds randomness so many clients do not retry simultaneously.

---

# 60. Dry-Run Mode

Dry-run mode lets users inspect intended state-changing operations.

Example:

```bash
dry_run=0
```

Function:

```bash
run_mutation() {
    if (( dry_run )); then
        printf '[DRY RUN]'
        printf ' %q' "$@"
        printf '\n'
        return 0
    fi

    "$@"
}
```

Then:

```bash
run_mutation systemctl restart nginx
```

In dry-run:

```text
[DRY RUN] systemctl restart nginx
```

No restart occurs.

# 61. Dry-Run Has Limits

Suppose the script does:

```text

then query resource ID
then modify resource
```

If dry-run skips creation, later stages cannot query the nonexistent resource.

Therefore dry-run may require different control flow.

Do not pretend every complex workflow can be accurately simulated merely by printing commands.

Document what dry-run does and does not validate.

# 70. Bats Introduction

```bash
#!/usr/bin/env bash

readonly EXIT_OK=0
readonly EXIT_CHECK_FAILED=1
readonly EXIT_USAGE=2
readonly EXIT_DEPENDENCY=3
readonly EXIT_CONFIG=4
readonly EXIT_RUNTIME=5

debug=0
dry_run=0

timestamp() {
    date '+%Y-%m-%dT%H:%M:%S%z'
}

log_info() {
    printf '%s [INFO] %s\n' "$(timestamp)" "$*"
}

log_warn() {
    printf '%s [WARN] %s\n' "$(timestamp)" "$*" >&2
}

log_error() {
    printf '%s [ERROR] %s\n' "$(timestamp)" "$*" >&2
}

log_debug() {
    if (( debug )); then
        printf '%s [DEBUG] %s\n' "$(timestamp)" "$*" >&2
    fi
}

require_command() {
    local command_name="$1"

    if ! command -v "$command_name" >/dev/null 2>&1; then
        log_error "Required command missing: $command_name"
        return 1
    fi
}

validate_percentage() {
    local value="$1"

    [[ "$value" =~ ^[0-9]+$ ]] || return 1

    (( value >= 0 && value <= 100 ))
}

validate_port() {
    local port="$1"

    [[ "$port" =~ ^[0-9]+$ ]] || return 1

    (( port >= 1 && port <= 65535 ))
}

retry_with_backoff() {
    local max_attempts="$1"
    shift

    local attempt=1
    local delay=1

    while (( attempt <= max_attempts )); do
        if "$@"; then
            return 0
        fi

        if (( attempt == max_attempts )); then
            break
        fi

        log_warn \
            "Attempt $attempt failed. Retrying in ${delay}s."

        sleep "$delay"

        delay=$((delay * 2))

        if (( delay > 16 )); then
            delay=16
        fi

        ((attempt++))
    done

    return 1
}

run_mutation() {
    if (( dry_run )); then
        printf '%s [DRY RUN]' "$(timestamp)"

        printf ' %q' "$@"

        printf '\n'

        return 0
    fi

    "$@"
}
```

# 101. Memory Usage

Linux exposes memory information through:

```text
/proc/meminfo
```

We can calculate approximate memory utilization.

```bash
get_memory_usage() {
    local total
    local available
    local used_percent

    total="$(
        awk '/^MemTotal:/ {print $2}' /proc/meminfo
    )"

    available="$(
        awk '/^MemAvailable:/ {print $2}' /proc/meminfo
    )"

    [[ "$total" =~ ^[0-9]+$ ]] || return 1
    [[ "$available" =~ ^[0-9]+$ ]] || return 1

    (( total > 0 )) || return 1

    used_percent=$(
        (
            (total - available) * 100
        ) / total
    )

    printf '%s\n' "$used_percent"
}
```

This uses `MemAvailable`, which is more useful than simply subtracting free memory on modern Linux.

# 112. Handle No Log Matches Correctly

Improved:

```bash
inspect_log() {
    local log_file="$1"
    local pattern="$2"
    local max_lines="${3:-20}"
    local matches
    local grep_status

    if [[ ! -r "$log_file" ]]; then
        log_warn "Log file is not readable: $log_file"
        return 1
    fi

    matches="$(
        grep -E "$pattern" "$log_file"
    )"

    grep_status=$?

    case "$grep_status" in
        0)
            printf '%s\n' "$matches" |
                tail -n "$max_lines"
            return 0
            ;;

        1)
            log_info \
                "No log entries matched pattern: $pattern"
            return 0
            ;;

        *)
            log_error \
                "Log search failed for: $log_file"
            return 1
            ;;
    esac
}
```

This applies the exit-code reasoning from earlier parts.

```bash
#!/usr/bin/env bash

get_hostname_value() {
    hostname
}

get_os_name() {
    if [[ ! -r /etc/os-release ]]; then
        printf 'unknown\n'
        return 1
    fi

    local pretty_name=""

    while IFS='=' read -r key value; do
        if [[ "$key" == "PRETTY_NAME" ]]; then
            pretty_name="${value%\"}"
            pretty_name="${pretty_name#\"}"

            printf '%s\n' "$pretty_name"
            return 0
        fi
    done < /etc/os-release

    printf 'unknown\n'
    return 1
}

get_disk_usage() {
    local mount_point="${1:-/}"
    local usage

    usage="$(
        df -P "$mount_point" |
        awk 'NR==2 {gsub(/%/, "", $5); print $5}'
    )" || return 1

    [[ "$usage" =~ ^[0-9]+$ ]] || return 1

    printf '%s\n' "$usage"
}

check_disk_usage() {
    local mount_point="$1"
    local threshold="$2"
    local usage

    usage="$(get_disk_usage "$mount_point")" || {
        log_error \
            "Could not determine disk usage for $mount_point"
        return 1
    }

    log_debug \
        "Disk usage for $mount_point: ${usage}%"

    if (( usage >= threshold )); then
        log_warn \
            "Disk usage is ${usage}% on $mount_point; threshold is ${threshold}%"
        return 1
    fi

    log_info \
        "Disk usage OK: ${usage}% on $mount_point"

    return 0
}

get_memory_usage() {
    local total
    local available
    local used_percent

    total="$(
        awk '/^MemTotal:/ {print $2}' /proc/meminfo
    )"

    available="$(
        awk '/^MemAvailable:/ {print $2}' /proc/meminfo
    )"

    [[ "$total" =~ ^[0-9]+$ ]] || return 1
    [[ "$available" =~ ^[0-9]+$ ]] || return 1

    (( total > 0 )) || return 1

    used_percent=$(
        (
            (total - available) * 100
        ) / total
    )

    printf '%s\n' "$used_percent"
}

check_memory_usage() {
    local threshold="$1"
    local usage

    usage="$(get_memory_usage)" || {
        log_error "Could not calculate memory usage"
        return 1
    }

    log_debug "Memory usage: ${usage}%"

    if (( usage >= threshold )); then
        log_warn \
            "Memory usage is ${usage}%; threshold is ${threshold}%"
        return 1
    fi

    log_info "Memory usage OK: ${usage}%"

    return 0
}

check_process() {
    local process_name="$1"

    if pgrep -x "$process_name" >/dev/null 2>&1; then
        log_info "Process running: $process_name"
        return 0
    fi

    log_warn "Process not running: $process_name"
    return 1
}

check_service() {
    local service_name="$1"

    if systemctl is-active --quiet "$service_name"; then
        log_info "Service active: $service_name"
        return 0
    fi

    log_warn "Service inactive: $service_name"
    return 1
}

restart_service() {
    local service_name="$1"

    log_warn \
        "Restart requested for service: $service_name"

    run_mutation systemctl restart "$service_name"
}

check_port() {
    local port="$1"

    if ss -ltn |
        awk 'NR > 1 {print $4}' |
        grep -Eq "(^|:)$port$"
    then
        log_info "TCP port listening: $port"
        return 0
    fi

    log_warn "TCP port not listening: $port"
    return 1
}

check_endpoint_once() {
    local endpoint="$1"

    curl \
        -fsS \
        --connect-timeout 5 \
        --max-time 10 \
        "$endpoint" \
        >/dev/null
}

check_endpoint() {
    local endpoint="$1"

    if retry_with_backoff \
        3 \
        check_endpoint_once \
        "$endpoint"
    then
        log_info "Endpoint healthy: $endpoint"
        return 0
    fi

    log_warn "Endpoint unhealthy: $endpoint"
    return 1
}

call_status_api() {
    local api_url="$1"
    local response

    if ! response="$(
        curl \
            -fsS \
            --connect-timeout 5 \
            --max-time 10 \
            "$api_url"
    )"
    then
        log_warn "API request failed: $api_url"
        return 1
    fi

    if ! jq -e . >/dev/null 2>&1 <<< "$response"; then
        log_warn "API returned invalid JSON"
        return 1
    fi

    printf '%s\n' "$response"
}

check_api_status() {
    local api_url="$1"
    local response
    local status

    response="$(call_status_api "$api_url")" ||
        return 1

    status="$(
        jq -r '.status // empty' <<< "$response"
    )"

    if [[ "$status" == "healthy" ]]; then
        log_info "API reports healthy status"
        return 0
    fi

    log_warn \
        "API status is '${status:-missing}'"

    return 1
}

inspect_log() {
    local log_file="$1"
    local pattern="$2"
    local max_lines="${3:-20}"
    local matches
    local grep_status

    if [[ ! -r "$log_file" ]]; then
        log_warn \
            "Log file is not readable: $log_file"
        return 1
    fi

    matches="$(
        grep -E "$pattern" "$log_file"
    )"

    grep_status=$?

    case "$grep_status" in
        0)
            printf '%s\n' "$matches" |
                tail -n "$max_lines"
            return 0
            ;;

        1)
            log_info \
                "No log entries matched pattern: $pattern"
            return 0
            ;;

        *)
            log_error \
                "Log search failed for: $log_file"
            return 1
            ;;
    esac
}

check_remote_host() {
    local remote_host="$1"

    ssh \
```

```bash
load_config() {
    if [[ ! -r "$config_file" ]]; then
        log_error \
            "Configuration file is not readable: $config_file"
        return "$EXIT_CONFIG"
    fi

    local line
    local key
    local value

    while IFS= read -r line || [[ -n "$line" ]]; do
        [[ -z "$line" ]] && continue
        [[ "$line" == \#* ]] && continue

        if [[ "$line" != *=* ]]; then
            log_error \
                "Invalid configuration line: $line"
            return "$EXIT_CONFIG"
        fi

        key="${line%%=*}"
        value="${line#*=}"

        case "$key" in
            DISK_THRESHOLD)
                DISK_THRESHOLD="$value"
                ;;

            MEMORY_THRESHOLD)
                MEMORY_THRESHOLD="$value"
                ;;

            SERVICE)
                SERVICE="$value"
                ;;

            PORT)
                PORT="$value"
                ;;

            ENDPOINT)
                ENDPOINT="$value"
                ;;

            LOG_PATTERN)
                LOG_PATTERN="$value"
                ;;

            LOG_FILE)
                LOG_FILE="$value"
                ;;

            API_URL)
                API_URL="$value"
                ;;

            *)
                log_error \
                    "Unsupported configuration key: $key"
                return "$EXIT_CONFIG"
                ;;
        esac
    done < "$config_file"

    return "$EXIT_OK"
}
```

# 146. Log Inspection Output

We do not want arbitrary log lines directly embedded into JSON without processing.

# 147. Separate Data-Producing Functions from Logging

A cleaner data function:

```bash
get_log_matches() {
    local log_file="$1"
    local pattern="$2"
    local max_lines="${3:-20}"
    local grep_status

    [[ -r "$log_file" ]] || return 2

    grep -E "$pattern" "$log_file" |
        tail -n "$max_lines"

    grep_status=${PIPESTATUS[0]}

    case "$grep_status" in
        0|1)
            return 0
            ;;

        *)
            return 1
            ;;
    esac
}
```

Now:

```text

status -> operation result
```

Logging belongs to the caller.

This is cleaner architecture.

# 155. Important Command Substitution Problem

There is a subtle architecture issue with:

```bash
report_file="$(generate_report)"
```

Functions executed in command substitution run in a subshell environment.

Also, anything `generate_report` writes to stdout becomes captured.

Our `log_info` function currently writes to stdout.

Therefore:

```bash
report_file
```

could accidentally contain log messages plus the filename.

This is exactly the kind of problem production engineering should catch.

```bash
set -o pipefail

readonly SCRIPT_NAME="${0##*/}"

fi

usage() {
    cat <<EOF

  $SCRIPT_NAME [options]

Options:
  -c, --config FILE
      Configuration file.

  --process NAME
      Check whether a process is running.

  --remote HOST
      Perform a read-only SSH connectivity check.

  --restart-service
      Restart the configured service if it is inactive.
      Requires appropriate permissions.

  -d, --dry-run
      Show state-changing commands without executing them.

  --debug
      Enable additional diagnostic logging.

  -h, --help

parse_args() {
    while (( $# > 0 )); do
        case "$1" in
            -c|--config)
                if (( $# < 2 )); then
                    log_error "$1 requires a file path"
                    return "$EXIT_USAGE"
                fi

                config_file="$2"
                shift 2
                ;;

            --process)
                if (( $# < 2 )); then
                    log_error "$1 requires a process name"
                    return "$EXIT_USAGE"
                fi

                process_name="$2"
                shift 2
                ;;

            --remote)
                if (( $# < 2 )); then
                    log_error "$1 requires a host"
                    return "$EXIT_USAGE"
                fi

                remote_host="$2"
                shift 2
                ;;

            --restart-service)
                restart_requested=1
                shift
                ;;

            -d|--dry-run)
                dry_run=1
                shift
                ;;

            --debug)
                debug=1
                shift
                ;;

            -h|--help)
                usage
                exit "$EXIT_OK"
                ;;

            *)
                log_error "Unknown argument: $1"
                usage >&2
                return "$EXIT_USAGE"
                ;;
        esac
    done
}

load_config() {
    if [[ ! -r "$config_file" ]]; then
        log_error \
            "Configuration file is not readable: $config_file"
        return "$EXIT_CONFIG"
    fi

    local line
    local key
    local value

    while IFS= read -r line || [[ -n "$line" ]]; do
        [[ -z "$line" ]] && continue
        [[ "$line" == \#* ]] && continue

        if [[ "$line" != *=* ]]; then
            log_error \
                "Invalid configuration line: $line"
            return "$EXIT_CONFIG"
        fi

        key="${line%%=*}"
        value="${line#*=}"

        case "$key" in
            DISK_THRESHOLD)
                DISK_THRESHOLD="$value"
                ;;

            MEMORY_THRESHOLD)
                MEMORY_THRESHOLD="$value"
                ;;

            SERVICE)
                SERVICE="$value"
                ;;

            PORT)
                PORT="$value"
                ;;

            ENDPOINT)
                ENDPOINT="$value"
                ;;

            LOG_PATTERN)
                LOG_PATTERN="$value"
                ;;

            LOG_FILE)
                LOG_FILE="$value"
                ;;

            API_URL)
                API_URL="$value"
                ;;

            *)
                log_error \
                    "Unsupported configuration key: $key"
                return "$EXIT_CONFIG"
                ;;
        esac
    done < "$config_file"

    return "$EXIT_OK"
}

validate_config() {
    if ! validate_percentage "$DISK_THRESHOLD"; then
        log_error \
            "Invalid DISK_THRESHOLD: $DISK_THRESHOLD"
        return "$EXIT_CONFIG"
    fi

    if ! validate_percentage "$MEMORY_THRESHOLD"; then
        log_error \
            "Invalid MEMORY_THRESHOLD: $MEMORY_THRESHOLD"
        return "$EXIT_CONFIG"
    fi

    if [[ -n "$PORT" ]] &&
       ! validate_port "$PORT"
    then
        log_error "Invalid PORT: $PORT"
        return "$EXIT_CONFIG"
    fi

    return "$EXIT_OK"
}

validate_dependencies() {
    local command_name

    for command_name in hostname df awk date mktemp; do
        require_command "$command_name" ||
            return "$EXIT_DEPENDENCY"
    done

    if [[ ! -r /proc/meminfo ]]; then
        log_error \
            "/proc/meminfo unavailable; Linux is required"
        return "$EXIT_DEPENDENCY"
    fi

    if [[ -n "$SERVICE" ]]; then
        require_command systemctl ||
            return "$EXIT_DEPENDENCY"
    fi

    if [[ -n "$PORT" ]]; then
        require_command ss ||
            return "$EXIT_DEPENDENCY"

        require_command grep ||
            return "$EXIT_DEPENDENCY"
    fi

    if [[ -n "$ENDPOINT" || -n "$API_URL" ]]; then
        require_command curl ||
            return "$EXIT_DEPENDENCY"
    fi

    if [[ -n "$API_URL" ]]; then
        require_command jq ||
            return "$EXIT_DEPENDENCY"
    fi

    if [[ -n "$LOG_FILE" ]]; then
        require_command grep ||
            return "$EXIT_DEPENDENCY"

        require_command tail ||
            return "$EXIT_DEPENDENCY"
    fi

    if [[ -n "$process_name" ]]; then
        require_command pgrep ||
            return "$EXIT_DEPENDENCY"
    fi

    if [[ -n "$remote_host" ]]; then
        require_command ssh ||
            return "$EXIT_DEPENDENCY"
    fi

    require_command flock ||
        return "$EXIT_DEPENDENCY"

    require_command jq ||
        return "$EXIT_DEPENDENCY"

    return "$EXIT_OK"
}

prepare_directories() {

acquire_lock() {
    exec 9>"$lock_file" || {
        log_error \
            "Could not open lock file: $lock_file"
        return "$EXIT_RUNTIME"
    }

    if ! flock -n 9; then
        log_error \
            "Another toolkit instance is already running"
        return "$EXIT_RUNTIME"
    fi

    log_debug "Execution lock acquired"

    return "$EXIT_OK"
}
```

# 195. Troubleshooting: Lock Never Clears

With `flock` on an open file descriptor, the lock normally releases when the process exits.

The lock file itself may remain.

That does not necessarily mean the lock is still held.

This is an important distinction:

```text
lock file exists
```

does not equal:

```text
lock currently active
```

This is one reason proper advisory locking is preferable to checking only file existence.

# 210. Final Conclusion

Bash begins with something as simple as:

```bash
echo "Hello"
```

But the shell sits at the intersection of operating systems, processes, files, networks, APIs, cloud platforms, containers, CI/CD systems, and infrastructure tools.

That makes it extraordinarily useful.

It also means Bash scripts can acquire enormous operational power.

The mature Bash engineer therefore does not measure script quality by how clever or short the code looks.

They measure it by whether the automation is:

```text
understandable
predictable
testable
secure
observable
recoverable
maintainable
safe to operate
```

The progression from Part 1 to Part 20 has taken you from:

```text
"What is Bash?"
```

to:

```text
"How do I design Bash automation that can participate safely in real infrastructure operations?"
```

That is the real goal of this learning path.

You now have a complete Bash/Shell Scripting foundation for Linux administration, DevOps, SRE, platform engineering, cloud operations, CI/CD, containers, Kubernetes workflows, troubleshooting, and production automation.

The next step is no longer to memorize more Bash syntax.

The next step is to build, test, break, troubleshoot, review, and improve real automation.
