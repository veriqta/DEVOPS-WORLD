# Part 6: Loops and Repetitive Automation

Infrastructure work is repetitive.

An engineer rarely manages only one server, one file, one URL, one container, or one cloud resource.

You may need to:

* Check 50 servers.
* Test 20 application endpoints.
* Read hundreds of log files.
* Inspect every EC2 instance returned by an API.
* Validate multiple configuration files.
* Check several services on every server.
* Process every Kubernetes workload.
* Repeat a health check until a service becomes available.

Writing the same Python code repeatedly would be inefficient.

Instead of:

```python
print("Checking web01")
print("Checking web02")
print("Checking web03")
print("Checking web04")
```

Python allows:

```python
servers = ["web01", "web02", "web03", "web04"]

for server in servers:
    print(f"Checking {server}")
```

Output:

```text
Checking web01
Checking web02
Checking web03
Checking web04
```

This is a loop.

A loop allows Python to repeat work.

The basic automation idea is:

```text
Collection of resources
        |
        v
     Start loop
        |
        v
   Select one item
        |
        v
   Perform operation
        |
        v
   More items?
     /     \
   Yes      No
    |        |
    +--------> Finish
```

Loops are one of the most important foundations of automation.

# 1. Why Loops Exist

Imagine you manage three servers:

```text
web01
web02
web03
```

Without a loop:

```python
print("Checking web01")
print("Checking web02")
print("Checking web03")
```

This works.

But imagine 500 servers.

Writing 500 separate statements would be impractical.

It would also be difficult to maintain.

If the operation changed, you might have to modify hundreds of lines.

A loop solves this.

```python
servers = ["web01", "web02", "web03"]

for server in servers:
    print(f"Checking {server}")
```

Now the operation is written once.

Python applies it to every server.

Think:

```text
Data changes
Code stays reusable
```

That is a major principle of automation.

# 3. The Two Main Python Loops

Python provides two primary loop structures:

```python
for
```

and:

```python
while
```

They solve different kinds of repetition.

A `for` loop is generally used when you want to process items from something iterable.

Examples:

* Servers in a list
* Keys in a dictionary
* Characters in a string
* Files in a directory
* Numbers in a range
* Resources returned by an API

A `while` loop is generally used when repetition should continue while a condition remains true.

Examples:

* Retry while a service is unavailable.
* Wait while deployment status is pending.
* Repeat a health check while an application is starting.
* Continue polling until a condition changes.

A useful beginner distinction is:

```text
for
Process these items.

while
Keep doing this while this condition remains true.
```

# 14. Do Not Modify a List Carelessly While Iterating

Suppose:

```python
servers = ["web01", "web02", "db01"]

for server in servers:
    if server == "web02":
        servers.remove(server)
```

Changing the collection you are actively iterating through can produce unexpected behavior.

A safer beginner approach is to build another list.

Example:

```python
servers = ["web01", "web02", "db01"]
remaining_servers = []

for server in servers:
    if server != "web02":
        remaining_servers.append(server)

print(remaining_servers)
```

Output:

```text
['web01', 'db01']
```

Later you will learn additional patterns for filtering collections.


# 41. Understanding `zip()`

Conceptually:

```text
servers            ports

web01   <--------> 80
web02   <--------> 443
api01   <--------> 8080
```

Python combines corresponding positions.

---

# 42. Important `zip()` Behavior

Suppose:

```python
servers = ["web01", "web02", "api01"]
ports = [80, 443]
```

Then:

```python
for server, port in zip(servers, ports):
    print(server, port)
```

processes only:

```text
web01 80
web02 443
```

The extra `api01` has no matching port.

By default, `zip()` stops when the shortest input is exhausted.

This matters when you expect collections to have matching lengths.

---

# 43. When a Dictionary May Be Better Than `zip()`

If a server permanently belongs to a port, this may be clearer:

```python
servers = {
    "web01": 80,
    "web02": 443,
    "api01": 8080
}
```

Then:

```python
for server, port in servers.items():
    print(f"{server}:{port}")
```

Choose a data structure that represents the relationship clearly.

Do not use `zip()` simply because it exists.

# 44. Nested Loops

A loop can exist inside another loop.

This is called a nested loop.

Suppose you have:

```python
servers = ["web01", "web02"]
ports = [80, 443]
```

You want to check every port on every server.

```python
for server in servers:
    for port in ports:
        print(f"Checking {server}:{port}")
```

Output:

```text
Checking web01:80
Checking web01:443
Checking web02:80
Checking web02:443
```

---

# 45. Understanding Nested Loop Execution

The outer loop selects:

```text
web01
```

Then the inner loop processes every port:

```text
80
443
```

Only then does the outer loop move to:

```text
web02
```

Flow:

```text
web01
  |
  +--> 80
  |
  +--> 443

web02
  |
  +--> 80
  |
  +--> 443
```

---

# 48. `break`

`break` immediately stops the current loop.

Example:

```python
servers = ["web01", "web02", "db01", "web03"]

for server in servers:
    print(f"Checking {server}")

    if server == "db01":
        print("Database server found")
        break
```

Output:

```text
Checking web01
Checking web02
Checking db01
Database server found
```

`web03` is never processed.

---

# 49. Why `break` Exists

Sometimes continuing is unnecessary.

Examples:

* Stop searching after finding the required resource.
* Stop retries after success.
* Stop processing when a critical condition occurs.
* Stop waiting when a service becomes healthy.
* Stop scanning after locating a target file.

Conceptually:

```text
Loop
 |
 v
Condition satisfied?
   |
 +---+
 |Yes|
 v
break
 |
 v
Exit loop
```

---

# 50. `break` in a Search

```python
servers = ["web01", "web02", "db01", "api01"]
target = "db01"

for server in servers:
    if server == target:
        print(f"Found {target}")
        break
```

Once the target is found, there is no reason to keep searching.

# 51. `continue`

`continue` does not terminate the loop.

Instead, it skips the rest of the current iteration and moves to the next one.

Example:

```python
servers = ["web01", "maintenance01", "web02"]

for server in servers:
    if server == "maintenance01":
        continue

    print(f"Checking {server}")
```

Output:

```text
Checking web01
Checking web02
```

---

# 52. Understanding `continue`

Flow:

```text
Get server
    |
    v
Should skip?
   / \
 Yes  No
 |     |
 v     v
continue
 |   process
 v
next item
```

`maintenance01` is skipped.

The entire loop does not stop.

---

# 53. Practical Maintenance Example

```python
servers = [
    "web01",
    "web02",
    "db-maintenance",
    "api01"
]

for server in servers:
    if server == "db-maintenance":
        print(f"Skipping {server}")
        continue

    print(f"Running health check on {server}")
```

This pattern is useful when certain resources should temporarily be excluded.

---

# 54. `break` vs `continue`

Remember:

```text
break
Stop the loop completely.

continue
Skip this iteration and move to the next.
```

Example:

```text
100 servers

continue
Skip server 23.
Continue with server 24.

break
Stop processing entirely at server 23.
```

# 55. `pass`

`pass` means:

```text
Do nothing.
```

It is a placeholder.

Example:

```python
for server in ["web01", "web02"]:
    pass
```

The loop is syntactically valid but performs no operation.

---

# 56. Why `pass` Exists

Python requires an indented block after statements such as:

```python
if
for
while
```

During development you may not have implemented that block yet.

Example:

```python
environment = "production"

if environment == "production":
    pass
else:
    print("Non-production environment")
```

`pass` lets the code remain syntactically valid.

---

# 57. `pass` Is Not the Same as `continue`

This distinction matters.

```python
for server in servers:
    if server == "web02":
        pass

    print(server)
```

`web02` still gets printed.

`pass` does nothing.

But:

```python
for server in servers:
    if server == "web02":
        continue

    print(server)
```

`web02` is skipped.

Remember:

```text
pass
Do nothing and continue normal execution.

continue
Immediately jump to the next iteration.
```

# 58. `while` Loops

A `while` loop repeats while a condition remains true.

Example:

```python
attempt = 1

while attempt <= 3:
    print(f"Attempt {attempt}")
    attempt += 1
```

Output:

```text
Attempt 1
Attempt 2
Attempt 3
```

---

# 59. Understanding the `while` Loop

Start:

```python
attempt = 1
```

Then:

```python
while attempt <= 3:
```

means:

```text
Keep running this block while attempt is less than or equal to 3.
```

Inside:

```python
attempt += 1
```

changes the condition over time.

Eventually:

```text
attempt = 4
```

Then:

```text
4 <= 3
```

is false.

The loop ends.

---

# 60. `while` Loop Flow

```text
Initialize value
      |
      v
Check condition
   /      \
 True     False
  |         |
  v         v
Run body   Exit
  |
  v
Update value
  |
  +-------> Check condition again
```

A `while` loop needs a way for its condition to eventually become false, unless an intentional `break` is used.

# 61. Loop Conditions

The condition after `while` can use the same Boolean logic learned in Part 5.

Example:

```python
service_healthy = False
attempt = 1

while not service_healthy and attempt <= 3:
    print(f"Health check attempt {attempt}")
    attempt += 1
```

The loop continues while:

```text
service is NOT healthy

AND

attempt is at most 3
```

# 62. Simulating Service Recovery

Consider:

```python
attempt = 1
service_healthy = False

while attempt <= 5:
    print(f"Checking service: attempt {attempt}")

    if attempt == 3:
        service_healthy = True

    if service_healthy:
        print("Service is healthy")
        break

    attempt += 1
```

Output:

```text
Checking service: attempt 1
Checking service: attempt 2
Checking service: attempt 3
Service is healthy
```

This simulates a service becoming healthy on the third check.

# 63. Why `while` Is Useful for Health Checks

Infrastructure systems often change over time.

A newly deployed application might initially be:

```text
Starting
```

then:

```text
Initializing
```

then:

```text
Healthy
```

An automation script may need to check repeatedly.

Conceptually:

```text
Deploy application
       |
       v
Check health
       |
       v
Healthy?
 /       \
No       Yes
|         |
wait      continue
|
v
check again
```

A `while` loop fits this pattern.

# 64. Infinite Loops

An infinite loop is a loop that never naturally ends.

Example:

```python
while True:
    print("Checking service")
```

`True` never becomes false.

Therefore the loop continues indefinitely.

---

# 65. Why Infinite Loops Can Be Dangerous

This:

```python
while True:
    print("Checking")
```

may run continuously until manually stopped.

A badly designed infinite loop can:

* Consume CPU.
* Generate huge log files.
* Flood an API.
* Trigger rate limits.
* Send repeated alerts.
* Repeatedly execute commands.
* Create unnecessary cloud requests.
* Overload another service.

Never create an infinite operational loop without understanding how it will stop or wait.

---

# 66. Intentional Infinite Loops

Some long-running programs intentionally use:

```python
while True:
```

For example:

```python
while True:
    # perform periodic work
    ...
```

But production programs normally include controls such as:

* Sleep intervals
* Shutdown signals
* Timeouts
* Retry limits
* Error handling
* Rate limiting
* Logging
* External orchestration

As a beginner, prefer bounded loops unless continuous operation is specifically required.

---

# 67. Breaking an Infinite Loop

An intentional loop can use `break`.

Example:

```python
attempt = 0

while True:
    attempt += 1
    print(f"Attempt {attempt}")

    if attempt == 3:
        break
```

Output:

```text
Attempt 1
Attempt 2
Attempt 3
```

Although the condition is always `True`, `break` provides an exit.

---

# 68. Common Infinite Loop Mistake

Wrong:

```python
attempt = 1

while attempt <= 3:
    print(attempt)
```

What is missing?

`attempt` never changes.

It remains:

```text
1
```

Therefore:

```text
1 <= 3
```

is always true.

The loop never ends.

Correct:

```python
attempt = 1

while attempt <= 3:
    print(attempt)
    attempt += 1
```

# 69. Retry Limits

Infrastructure automation should usually have bounded retries.

Instead of:

```python
while True:
    print("Retrying")
```

consider:

```python
max_attempts = 5
attempt = 1

while attempt <= max_attempts:
    print(f"Attempt {attempt} of {max_attempts}")
    attempt += 1
```

This guarantees a stopping point.

---

# 70. Why Retry Limits Matter

Imagine an API is unavailable.

Without limits:

```text
Request
  |
failed
  |
retry
  |
failed
  |
retry
  |
failed
  |
retry forever...
```

This can make the problem worse.

A bounded design is safer:

```text
Request
   |
failure
   |
retry 1
   |
retry 2
   |
retry 3
   |
still failing?
   |
stop and report
```

Later, we will add timeouts, exception handling, and retry delays.

# 72. `for` vs `while`

Suppose you know you want exactly five attempts.

A `for` loop is often straightforward:

```python
for attempt in range(1, 6):
    print(f"Attempt {attempt}")
```

Suppose instead you want to continue until a changing condition becomes false:

```python

    ...
```

A useful rule:

```text
Known collection or bounded sequence
        |
        v
       for

Condition-controlled repetition
        |
        v
      while
```

This is a guideline, not an absolute law.

# 82. Safety When Processing Many Files

Be especially careful when a loop modifies or deletes files.

This:

```text
for every file
    delete file
```

can affect hundreds or thousands of files very quickly.

Before destructive automation:

1. Verify the directory.
2. Verify the file-selection pattern.
3. Print targets first.
4. Consider a dry-run mode.
5. Use narrow conditions.
6. Test with disposable files.
7. Verify backups where appropriate.

Never blindly copy a deletion loop into an important directory.

```text
5
```

# 110. Common Mistake: Retrying Without Waiting

Imagine:

```python
for attempt in range(1000):
    check_service()
```

If the real check happens immediately 1,000 times, you may overwhelm the service.

Real retry systems often need a delay.

Python provides:

```python
time.sleep()
```

Example:

```python
import time

for attempt in range(1, 4):
    print(f"Attempt {attempt}")

    if attempt < 3:
        time.sleep(2)
```

`time.sleep(2)` pauses execution for approximately two seconds.

Do not use aggressive retry loops against real production systems.

---

# 111. Retry Delay Example

```python
import time

max_attempts = 3

for attempt in range(1, max_attempts + 1):
    print(f"Health check {attempt}/{max_attempts}")

    if attempt < max_attempts:
        print("Waiting before next attempt...")
        time.sleep(2)
```

This demonstrates:

```text
Check
 |
failed
 |
wait
 |
retry
```

Later, production retry design can include techniques such as increasing delays and jitter.

For now, remember:

```text
Retrying faster is not automatically better.
```

# 123. Why `continue` Is Used

This section:

The important lesson is that `continue` expresses:

# 129. Production Thinking: Sequential Loops Have Limits

# 132. Production Thinking: Idempotency

Suppose a loop processes the same server twice.

Should that cause damage?

Good infrastructure automation often aims for idempotent behavior.

At beginner level, think of idempotency as:

```text
Running the same intended automation again should not create unnecessary or harmful repeated changes.
```

For example, a script should ideally check:

```text
Does directory already exist?
```

before blindly trying to recreate or modify it.

Loops magnify mistakes because one operation may run across many resources.

# 133. Production Thinking: Blast Radius

Blast radius means the scope of systems affected when something goes wrong.

Compare:

```text
Manual mistake on one test server
```

with:

```text
Automation mistake inside a loop over 2,000 production servers
```

The second has a much larger potential impact.

Therefore:

```text
More automation
does not mean
less caution
```

It often requires stronger safeguards.

# 139. Part 6 Summary

Before loops, your automation could evaluate one resource:

```python
hostname = "web01"
disk_usage = 92

if disk_usage >= 90:
    print(f"{hostname}: critical disk usage")
```

Now the same decision can be applied repeatedly:

```python
servers = [
    {"hostname": "web01", "disk_usage": 61},
    {"hostname": "web02", "disk_usage": 92},
    {"hostname": "api01", "disk_usage": 84}
]

for server in servers:
    if server["disk_usage"] >= 90:
        print(
            f"{server['hostname']}: "
            "critical disk usage"
        )
```

Your automation progression is now:

```text
Part 2
Store values
    |
    v
Part 3
Process text
    |
    v
Part 4
Organize collections
    |
    v
Part 5
Make decisions
    |
    v
Part 6
Repeat decisions across resources
```

This creates one of the most important automation patterns:

```text
Discover resources
       |
       v
Loop through resources
       |
       v
Inspect current item
       |
       v
Evaluate conditions
       |
       v
Skip / Continue / Act / Stop
       |
       v
Collect results
       |
       v
Process next item
       |
       v
Generate summary
```

You can now reason about automation across:

* Multiple servers
* Multiple services
* Multiple URLs
* Multiple files
* Multiple cloud instances
* Multiple regions
* Nested infrastructure inventories
* Repeated health checks
* Bounded retries

But there is now another problem.

Our scripts are beginning to contain reusable pieces of logic.

For example:

```text
check disk
classify CPU
evaluate HTTP status
check server
format result
```

We do not want to rewrite these operations every time we need them.

Part 7 solves that problem with functions.

Instead of repeatedly writing:

```python
if disk_usage >= 90:
    print("CRITICAL")
elif disk_usage >= 80:
    print("WARNING")
else:
    print("OK")
```

we will be able to create reusable logic conceptually like:

```python
check_disk_usage(92)
check_disk_usage(71)
check_disk_usage(45)
```

The next progression is therefore:

```text
Loops
Repeat work
   |
   v
Functions
Package repeated logic into reusable operations
   |
   v
Larger automation programs
```

That is the next major step toward building maintainable Python infrastructure automation.
