# 1. What Does Merging Mean?

A merge combines development history from another branch into your current branch.

Suppose `main` contains:

```text
A -> B -> C
```

You create:

```text
feature/login
```

and make two commits:

```text
A -> B -> C -> D -> E
          ^         ^
          |         |
         main   feature/login
```

The login feature now exists on `feature/login`.

But `main` still points to C.

If the feature is complete, tested, and approved, you may want `main` to include it.

That is where merging comes in.

---

# 2. A Simple Mental Model

Think:

```text
BRANCH A
   +
BRANCH B
   |
   v
COMBINED HISTORY
```

More specifically, if you are on `main` and run:

```bash
git merge feature/login
```

you are asking Git:

> Integrate the history reachable from `feature/login` into my current branch, `main`.

The direction matters.

---

# 3. Merge Into the Current Branch

This is one of the most important Git merge rules for beginners:

```text
git merge <branch>
```

means:

```text
MERGE <branch>
INTO
THE BRANCH I AM CURRENTLY ON
```

Suppose:

```bash
git status
```

shows:

```text
On branch main
```

Then:

```bash
git merge feature/login
```

means:

```text
feature/login
      |
      v
     main
```

You are bringing `feature/login` into `main`.

---

# 4. Why Merge Direction Matters

Suppose you accidentally remain on:

```text
feature/login
```

and run:

```bash
git merge main
```

You are not merging the feature into `main`.

You are doing the opposite:

```text
main
 |
 v
feature/login
```

This may be a legitimate operation in some workflows, but it is not the same thing.

Before merging, always ask:

```text
Which branch should receive the changes?
```

Then switch to that branch.

---

# 5. Safe Pre-Merge Habit

Before every merge:

```bash
git status
```

Confirm:

```text
On branch main
```

or whichever branch should receive the changes.

Then inspect your branches:

```bash
git branch
```

For example:

```text
  feature/login
* main
```

The `*` confirms that `main` is current.

Only then run:

```bash
git merge feature/login
```

---

# 6. Why Teams Merge Code

Modern projects rarely have one engineer making every change directly on one branch.

Imagine three engineers:

```text
Engineer A
feature/login

Engineer B
feature/payment

Engineer C
fix/api-timeout
```

They may work independently:

```text
                  L1 -> L2
                 /
A -> B -> C -----+
                 \
                  P1 -> P2
                   \
                    T1
```

Eventually, approved work needs to become part of the project's shared development history.

Merging allows teams to integrate those separate lines.

---

# 7. Why Not Just Work Directly on main?

Technically, a small team could make every commit directly on `main`.

But feature branches provide useful separation.

A feature can be:

* Developed
* Tested
* Reviewed
* Changed
* Rejected
* Reworked

before being integrated.

A typical workflow is:

```text
main
 |
 v
Create feature branch
 |
 v
Develop
 |
 v
Commit
 |
 v
Test
 |
 v
Review
 |
 v
Merge
 |
 v
main contains feature
```

# 9. The git merge Command

The basic syntax is:

```bash
git merge <branch>
```

Break it down.

```text
git
```

runs Git.

```text
merge
```

requests history integration.

```text
<branch>
```

identifies the branch whose history you want to integrate into your current branch.

Example:

```bash
git merge feature/login
```

Again, the receiving branch is determined by HEAD.

---

# 10. Check HEAD Before Merging

Suppose:

```text
HEAD -> main
```

Then:

```bash
git merge feature/login
```

merges into `main`.

But if:

```text
HEAD -> develop
```

the same command merges into `develop`.

The command does not inherently mean:

```text
Merge into main
```

It means:

```text
Merge into current branch
```

This is why understanding HEAD from earlier parts matters.

# 14. Fast-Forward Merge

Switch to `main`:

```bash
git switch main
```

Verify:

```bash
git status
```

Then:

```bash
git merge feature/login
```

Git may report something similar to:

```text
Updating abc1234..def5678
Fast-forward
 app.py | 3 +++
 1 file changed, 3 insertions(+)
```

The important phrase is:

```text
Fast-forward
```

---

# 15. What Is a Fast-Forward Merge?

Before:

```text
A -> B -> C
     ^     ^
     |     |
   main  feature/login
```

`main` points to B.

The feature branch points to C.

There are no separate commits on `main` after B.

Git does not need to combine two divergent histories.

It can simply move `main` forward.

After:

```text
A -> B -> C
          ^
         / \
      main  feature/login
```

The `main` branch pointer moved from B to C.

---

# 16. Why It Is Called Fast-Forward

Think of `main` as being behind:

```text
main
 |
 v
B
 \
  C
  ^
  |
feature/login
```

Git can move:

```text
main
```

directly forward to C.

No new merge commit is required by the normal fast-forward operation.

Conceptually:

```text
BEFORE

main -> B
feature -> C

AFTER

main -> C
feature -> C
```

---

# 17. Fast-Forward Requirements

A fast-forward is possible when the current branch tip is an ancestor of the branch being merged.

Beginner version:

> The receiving branch has not developed its own separate commits since the feature branch split from it.

Example:

```text
A -> B -> C -> D
     ^         ^
     |         |
   main      feature
```

`main` can move directly from B to D.

---

# 18. Fast-Forward Does Not Create a New Merge Commit

Suppose the feature contains:

```text
C
D
```

After fast-forwarding:

```text
A -> B -> C -> D
               ^
               |
              main
```

Git does not need:

```text
M = merge commit
```

because there was no divergent history to reconcile.

The existing commits already form a valid linear path.

---

# 19. Verify the Fast-Forward Merge

After:

```bash
git merge feature/login
```

run:

```bash
git status
```

Then:

```bash
git log --oneline --graph --decorate --all
```

You should see `main` and `feature/login` pointing at the same latest commit.

Also inspect:

```bash

```

Verify that the login function exists.

Never assume a merge succeeded simply because Git did not show an obvious error.

Verify the project.

# 20. Merging Is About History, Not Copying Files

A beginner may imagine:

```text
Copy files from feature/login
Paste them into main
```

That is incomplete.

Git is integrating commit history.

This distinction becomes clearer when branches diverge.

---

# 21. When Fast-Forward Is Not Possible

Suppose both branches gain commits after separating.

Start:

```text
A -> B
```

Create feature branch.

Feature gets:

```text
C
```

Meanwhile `main` gets:

```text
D
```

Now:

```text
        C
       /
A -> B
       \
        D
```

Neither branch is simply behind the other.

The histories have diverged.

A simple pointer movement cannot combine them.

Git needs another strategy.

---

# 22. Three-Way Merge

A three-way merge is commonly used when two branches have diverged.

Suppose:

```text
        C
       /
A -> B
       \
        D
```

We want to merge C's branch into D's branch.

Git considers three important points:

1. The common ancestor
2. The current branch tip
3. The branch being merged

Here:

```text
Common ancestor = B
Current branch = D
Other branch = C
```

---

# 23. Why It Is Called Three-Way

Git effectively needs to understand:

```text
            C
           /
          B
           \
            D
```

It considers:

```text
B = common starting point
C = one line of development
D = other line of development
```

Then it determines how the project changed from:

```text
B -> C
```

and:

```text
B -> D
```

and tries to combine those changes.

---

# 24. The Common Ancestor Matters

Suppose B contains:

```python
print("Application started")
```

Feature branch changes it by adding:

```python
def login():
    pass
```

Meanwhile `main` changes another file:

```text
README.md
```

Git can compare both branches to B.

It can see:

```text
Feature changed app.py
Main changed README.md
```

These changes do not interfere.

Git can normally combine them automatically.

# 28. What Is a Merge Commit?

After a successful divergent merge, history may look like:

```text
        C
       / \
A -> B   M
       \ /
        D
```

`M` is the merge commit.

More clearly:

```text
             C
            / \
A -> B ----    M
            \ /
             D
```

The merge commit represents the point where the two histories were integrated.

---

# 29. Merge Commits Have Multiple Parents

A normal commit usually has one parent.

Example:

```text
A -> B -> C
```

C has parent B.

A merge commit commonly has two parents.

Conceptually:

```text
C ----\
       M
D ----/
```

M has parents:

```text
C
D
```

This is how Git records that two development lines came together.

---

# 30. Why Parent Commits Matter

You learned in Part 6 that parent relationships form Git history.

A normal chain:

```text
D
|
v
C
|
v
B
|
v
A
```

A merge introduces multiple ancestry paths:

```text
       C
      / \
     B   M
      \ /
       D
```

The exact drawing varies, but the key idea is:

```text
Merge commit
    |
    +--> Parent 1
    |
    +--> Parent 2
```

Git can preserve both lines of development.

# 33. Fast-Forward vs Three-Way Merge

Fast-forward:

```text
BEFORE

A -> B -> C
     ^     ^
     |     |
   main  feature

AFTER

A -> B -> C
          ^
         main
```

No divergent main-side commit existed.

Three-way:

```text
BEFORE

        C
       /
A -> B
       \
        D
```

After:

```text
        C
       / \
A -> B   M
       \ /
        D
```

A merge commit records the integration.

---

# 34. A Merge Commit Is Not Automatically a Conflict

This is important.

A three-way merge can create a merge commit without producing a merge conflict.

For example:

Feature branch modifies:

```text
profile.py
```

Main modifies:

```text
README.md
```

Git can combine both automatically.

You still get a merge commit because histories diverged, but no human conflict resolution is required.

Therefore:

```text
merge commit ≠ merge conflict
```

---

# 35. What Is a Merge Conflict?

A merge conflict occurs when Git cannot safely determine how to combine certain competing changes automatically.

Git stops the merge and asks you to decide what the final content should be.

A conflict is not Git failing.

It is Git refusing to guess.

---

# 36. Why Merge Conflicts Happen

Imagine a common ancestor contains:

```python
timeout = 30
```

Feature branch changes it to:

```python
timeout = 60
```

Main changes the same line to:

```python
timeout = 10
```

Now Git sees:

```text
Original:
timeout = 30

Feature:
timeout = 60

Main:
timeout = 10
```

What should the final value be?

Git cannot know your engineering intention.

Should it be:

```python
timeout = 10
```

or:

```python
timeout = 60
```

or perhaps:

```python
timeout = 45
```

Only a human or higher-level project decision can determine that.

---

# 37. Conflicts Are About Ambiguous Intent

Git understands file content and history.

Git does not understand your business requirement.

Suppose:

```text
main:
replicas: 3
```

Feature:

```text
replicas: 5
```

Another branch:

```text
replicas: 2
```

Git cannot decide whether production needs:

```text
2
3
5
```

replicas.

That is an engineering decision.

---

# 38. Common Causes of Merge Conflicts

Conflicts commonly happen when:

* Two branches modify the same line differently
* One branch deletes a file another branch modifies
* Two branches restructure related content
* Files are renamed and changed in incompatible ways
* Long-lived branches drift significantly apart
* Large refactors overlap with feature development
* Multiple engineers modify the same configuration section

Not every simultaneous edit creates a conflict.

Git often merges non-overlapping changes automatically.

---

# 39. DevOps Conflict Example

Suppose a Kubernetes manifest originally contains:

```yaml
resources:
  limits:
    memory: "512Mi"
```

Feature branch changes:

```yaml
memory: "1Gi"
```

Main changes:

```yaml
memory: "768Mi"
```

Which limit should production use?

Git cannot know.

This is exactly the type of conflict where blindly choosing one side could create operational problems.

---

# 40. Another DevOps Conflict Example

Original Terraform:

```hcl

```

Feature branch:

```hcl

```

Main:

```hcl

```

Choosing incorrectly can affect:

* Cost
* Capacity
* Performance
* Infrastructure behavior

Conflict resolution should therefore be treated as an engineering decision, not merely a Git task.

# 45. What Git May Report

You may see output similar to:

```text
Auto-merging config.txt
CONFLICT (content): Merge conflict in config.txt
Automatic merge failed; fix conflicts and then commit the result.
```

This tells you:

1. Git attempted the merge.
2. It found incompatible content.
3. It stopped.
4. You must resolve the conflict.
5. The merge has not been completed.

---

# 46. Do Not Panic During a Conflict

A conflict does not mean your repository is destroyed.

Git has intentionally paused.

Your repository is in a special merge-in-progress state.

Start with:

```bash
git status
```

This should always be one of your first commands during troubleshooting.

---

# 47. Reading git status During a Conflict

You may see something similar to:

```text
On branch main
You have unmerged paths.

Unmerged paths:
  both modified:   config.txt
```

Git is telling you which file needs attention.

Do not immediately run random reset, checkout, restore, or force commands.

First inspect the conflict.

---

# 48. Open the Conflicted File

Run:

```bash
cat config.txt
```

or open it in your editor.

You may see:

```text
PORT=8080
<<<<<<< HEAD
TIMEOUT=15
=======
TIMEOUT=60
>>>>>>> feature/timeout
LOG_LEVEL=info
```

Git inserted conflict markers.

These markers show the competing content.

---

# 49. Understanding <<<<<<<

This marker:

```text
<<<<<<< HEAD
```

starts one side of the conflict.

In this merge, HEAD refers to your current branch.

You are on:

```text
main
```

So:

```text
<<<<<<< HEAD
TIMEOUT=15
```

represents the current branch's version.

---

# 50. Understanding =======

The marker:

```text
=======
```

separates the two competing versions.

Everything above it belongs to one side.

Everything below it, until the closing marker, belongs to the other side.

---

# 51. Understanding >>>>>>>

This marker:

```text
>>>>>>> feature/timeout
```

marks the end of the other branch's conflicting content.

So:

```text
<<<<<<< HEAD
TIMEOUT=15
=======
TIMEOUT=60
>>>>>>> feature/timeout
```

means:

Current branch:

```text
TIMEOUT=15
```

Other branch:

```text
TIMEOUT=60
```

Git wants you to choose or construct the final result.

---

# 52. Conflict Marker Diagram

Think:

```text
<<<<<<< HEAD

CURRENT BRANCH CONTENT

=======

OTHER BRANCH CONTENT

>>>>>>> feature/timeout
```

These lines are temporary markers.

They are not supposed to remain in the finished configuration or source code.

---

# 53. Never Commit Conflict Markers Accidentally

A dangerous mistake is resolving nothing and committing a file containing:

```text
<<<<<<<
=======
>>>>>>>
```

If such markers enter application code or configuration, they can cause:

* Syntax errors
* Broken builds
* Invalid YAML
* Invalid JSON
* Application crashes
* Deployment failures
* CI failures

Always verify that all conflict markers have been removed.

---

# 54. Resolving the Conflict Manually

You must decide what the final file should contain.

Suppose after discussing the requirement you determine:

```text
TIMEOUT=45
```

is correct.

Edit the file to:

```text
PORT=8080
TIMEOUT=45
LOG_LEVEL=info
```

Notice that you did not necessarily choose either original side exactly.

You created the correct final state.

This is a crucial point.

---

# 55. Conflict Resolution Is Not Always “Choose Ours or Theirs”

Beginners sometimes think:

```text
I must choose one entire side.
```

No.

You can:

* Keep the current branch's content
* Keep the other branch's content
* Combine both
* Rewrite the section completely
* Use a third value
* Refactor the final result

The goal is not to make Git happy.

The goal is to produce the correct project state.

---

# 56. Example: Combining Both Changes

Suppose:

Current branch:

```python
def greet():
    print("Welcome")
```

Feature branch:

```python
def greet():
    print("Hello, user")
```

After understanding the requirement, you might resolve it as:

```python
def greet(username):
    print(f"Welcome, {username}")
```

Neither branch contained that exact final version.

That is perfectly valid.

# 58. git add Has a Special Role During Conflict Resolution

Earlier you learned that:

```bash
git add file
```

stages content.

That remains true.

During a conflict, it also has an important workflow meaning.

Before:

```text
config.txt
=
unmerged
```

After you resolve and run:

```bash
git add config.txt
```

Git can treat that path as resolved for the pending merge.

The staging area again becomes central to Git's workflow.

Run:

You may now see something similar to:

```text
All conflicts fixed but you are still merging.
```

This means:

* Conflict resolution is staged
* Git no longer sees unresolved paths
* The merge still needs to be completed

Do not stop here.

Run:


Save and close the editor.

# 61. Why git merge Did Not Finish Automatically

When there was no conflict, Git could create the merge result automatically.

But during the conflict, Git stopped because human input was required.

The sequence became:

```text
git merge
   |
   v
CONFLICT
   |
   v
Inspect
   |
   v
Edit
   |
   v
git add
   |
   v
git commit
   |
   v
MERGE COMPLETE
```

# 65. Search for Leftover Conflict Markers

Before completing an important merge, search the files you resolved for markers such as:

```text
<<<<<<<
=======
>>>>>>>
```

Be careful with broad searches because `=======` can legitimately appear in some files.

The most distinctive markers are usually:

```text
<<<<<<<
>>>>>>>
```

In a Unix-like shell, for example:

```bash
grep -R "<<<<<<<" .
```

and:

```bash
grep -R ">>>>>>>" .
```

can help identify accidentally retained conflict markers.

Do not blindly run recursive searches across enormous repositories without understanding their scope.

# 66. What If You Want to Cancel the Merge?

Sometimes you begin a merge and realize:

* You are on the wrong branch
* You chose the wrong source branch
* There are too many conflicts
* You need more information
* You want to return to the pre-merge state

Git provides:

```bash
git merge --abort
```

---

# 67. What git merge --abort Means

Suppose:

```bash
git merge feature/timeout
```

creates conflicts.

Before resolving them, run:

```bash
git merge --abort
```

Git attempts to reconstruct the state that existed before the merge began.

Conceptually:

```text
BEFORE MERGE
    |
    v
START MERGE
    |
    v
CONFLICT
    |
    v
git merge --abort
    |
    v
RETURN TOWARD
PRE-MERGE STATE
```

---

# 68. Abort Is Not the Same as Resolving

If you abort:

```bash
git merge --abort
```

you are saying:

> Do not complete this merge now.

You are not saying:

> Accept one side.

You are cancelling the merge attempt.

# 70. Important Warning About Pre-Existing Changes

The safest situation for beginning a merge is usually a clean working tree.

Why?

Because if you already have unrelated uncommitted changes, reasoning about:

* Pre-existing work
* Merge changes
* Conflict changes
* Recovery

becomes harder.

Before merging:


Understand everything that is not committed.

Do not begin complex merges while carrying mysterious unrelated changes.

# 76. Step 5: If There Is a Conflict, Run git status

# 77. Step 6: Inspect Every Conflict

```text
=======
```

# 78. Step 7: Resolve Based on Requirements

Investigate the intended deployment capacity.


# 86. Common Mistake: Merging From the Wrong Branch

You intend:

```text
feature/login -> main
```

but you are on `feature/login`.

You run:

```bash
git merge main
```

Now you merged `main` into the feature.

Prevent this with:

```bash
git status
```

before every merge.

Think:

```text
CURRENT BRANCH RECEIVES THE MERGE
```

---

# 87. Common Mistake: Resolving Without Understanding

Conflict:

```text
<<<<<<< HEAD
timeout = 15
=======
timeout = 60
>>>>>>> feature/timeout
```

Beginner chooses:

```text
timeout = 60
```

only because it is below `=======`.

That is not proper conflict resolution.

The correct value depends on the requirement.

---

# 88. Common Mistake: Deleting Only the Markers

Suppose:

```text
<<<<<<< HEAD
timeout = 15
=======
timeout = 60
>>>>>>> feature/timeout
```

You remove only markers and produce:

```text
timeout = 15
timeout = 60
```

The conflict markers are gone, but the configuration may now be invalid or contradictory.

Resolution means producing correct final content, not merely deleting special symbols.

---

# 89. Common Mistake: Forgetting git add

You manually fix:

```text
config.txt
```

but:

```bash
git status
```

still reports it as unmerged.

Why?

You did not stage the resolution.

Run:

```bash
git add config.txt
```

Then:

```bash
git status
```

again.

---

# 90. Common Mistake: Staging Before the Conflict Is Truly Resolved

You can stage a file that is logically wrong.

Git does not understand your application's requirements.

Before:

```bash
git add conflicted-file
```

inspect the final file carefully.

After staging:

```bash
git diff --staged
```

and run relevant validation.

---

# 91. Common Mistake: Forgetting to Complete the Merge

You resolve every conflict.

You stage everything.

Then you stop.

Later:

```bash
git status
```

says:

```text
All conflicts fixed but you are still merging.
```

The merge still needs to be completed.

Follow Git's instructions, commonly with:

```bash
git commit
```

---

# 92. Common Mistake: Using Hard Reset During a Conflict

A beginner becomes uncomfortable and runs:

```bash
git reset --hard
```

without understanding what will be lost.

This can discard work.

If your goal is simply:

```text
Cancel this merge
```

the purpose-built command is normally:

```bash
git merge --abort
```

Use the tool that matches your intention.

---

# 93. Common Mistake: Assuming Every Merge Creates a Merge Commit

Fast-forward merges normally do not require a merge commit.

Example:

```text
A -> B -> C
     ^     ^
     |     |
   main  feature
```

can become:

```text
A -> B -> C
          ^
          |
         main
```

No separate merge commit is necessary.

---

# 94. Common Mistake: Assuming Every Three-Way Merge Conflicts

Three-way merge:

```text
        C
       /
A -> B
       \
        D
```

can often be combined automatically.

If C and D changed unrelated content, Git may create the merge result without conflict.

Conflict only occurs where Git cannot safely reconcile certain changes automatically.

---

# 95. Common Mistake: Treating Conflict as Failure

Conflicts are normal in collaborative development.

A conflict means:

```text
Git found competing changes
and needs human intent.
```

A strong engineer does not panic.

They:

```text
Observe
Understand
Compare
Decide
Edit
Stage
Validate
Commit
Verify
```

---

# 96. Common Mistake: Huge Long-Lived Branches

Imagine:

```text
main:
500 new commits

feature:
300 independent commits
```

The longer branches evolve independently, the more differences can accumulate.

That can make integration harder.

Teams often reduce risk by:

* Keeping changes focused
* Integrating regularly
* Avoiding unnecessary long-lived branches
* Communicating about overlapping work
* Keeping commits understandable

Workflow choices depend on the team, but uncontrolled drift makes merging harder.

---

# 97. Common Mistake: Mixing Unrelated Changes

Suppose a feature branch contains:

```text
Login feature
Database migration
README rewrite
Terraform refactor
Kubernetes upgrade
Logging changes
```

Merging and reviewing that branch becomes harder.

Focused branches and atomic commits improve:

* Review
* Testing
* Troubleshooting
* Rollback reasoning
* Conflict resolution

This connects directly to the atomic-commit lessons from Part 6.

# 100. Troubleshooting: “I Don't Know Which Side Is Mine”

During:


But do not reduce conflict resolution to “mine vs theirs.”

Understand the content and desired final result.

# 101. Troubleshooting: “I Resolved the File but Git Still Says Unmerged”

# 102. Troubleshooting: “I Want to Start Over”


# 103. Troubleshooting: “The Merge Succeeded but the Application Broke”

This is not necessarily a Git failure.

Git may have combined the text correctly while producing incompatible application behavior.

Example:

One branch changes:

```text
API function signature
```

while another branch changes:

```text
code that calls the function
```

Git may see no textual conflict.

But the application can still fail.

This is called a logical or semantic conflict.

---

# 104. Text Conflict vs Logical Conflict

Textual conflict:

```text
Both branches change same lines incompatibly
        |
        v
Git stops
```

Logical conflict:

```text
Git combines files successfully
        |
        v
Code interactions are wrong
        |
        v
Application/test fails
```

Git cannot detect every logical problem.

This is why testing after merges is essential.

---

# 105. Example of a Logical Conflict

Original:

```python
def connect():
    return "connected"
```

Feature branch changes function:

```python
def connect(host):
    return f"connected to {host}"
```

Another branch adds:

```python
status = connect()
```

The textual changes may occur in different files or lines.

Git may merge automatically.

But:

```python
connect()
```

may now be invalid because the function expects:

```text
host
```

The Git merge succeeded.

The software integration failed.

```text
   +--> Unit tests
   |
   +--> Integration tests
   |
   +--> Lint
   |
   +--> Security scan
```

# 127. Part 9 Final Recap

You began Part 8 with separate branches:

```text
             D -> E
            /
A -> B -> C
            \
             F -> G
```

Part 9 answers:

```text
How do those histories come back together?
```

The answer is:

```bash
git merge
```

The first rule to remember is:

```text
THE CURRENT BRANCH
RECEIVES THE MERGE.
```

So:

```bash
git switch main
git merge feature/login
```

means:

```text
feature/login
      |
      v
     main
```

If the history looks like:

```text
A -> B -> C
     ^     ^
     |     |
   main  feature
```

Git can often fast-forward:

```text
A -> B -> C
          ^
          |
         main
```

No separate merge commit is required.

But if branches diverge:

```text
        C
       /
A -> B
       \
        D
```

Git performs a three-way merge using:

```text
COMMON ANCESTOR
      +
CURRENT BRANCH
      +
OTHER BRANCH
```

and may produce:

```text
        C
       / \
A -> B   M
       \ /
        D
```

where:

```text
M = merge commit
```

If Git cannot safely determine how competing content should be combined, it stops with a conflict.

You may see:

```text
<<<<<<< HEAD
TIMEOUT=15
=======
TIMEOUT=60
>>>>>>> feature/timeout
```

Your job is not simply to delete the markers.

Your job is to determine:

```text
WHAT SHOULD THE FINAL PROJECT STATE BE?
```

The correct resolution could be:

```text
TIMEOUT=15
```

or:

```text
TIMEOUT=60
```

or:

```text
TIMEOUT=45
```

depending on the actual requirement.

The safe workflow is:

```text
MERGE
  |
  v
READ OUTPUT
  |
  v
git status
  |
  v
INSPECT CONFLICTS
  |
  v
UNDERSTAND BOTH CHANGES
  |
  v
DECIDE CORRECT RESULT
  |
  v
EDIT
  |
  v
REMOVE MARKERS
  |
  v
git add
  |
  v
REVIEW
  |
  v
TEST
  |
  v
git commit
  |
  v
VERIFY HISTORY
  |
  v
VERIFY APPLICATION
```

And if you determine that the merge should not continue:

```bash
git merge --abort
```

The deeper lesson is:

```text
Git can understand history.

Git can compare content.

Git can automatically combine many changes.

But Git cannot always understand
engineering intent.
```

That responsibility belongs to the engineer.

You now understand the essential local Git workflow:

```text
CREATE REPOSITORY
      |
      v
TRACK FILES
      |
      v
STAGE
      |
      v
COMMIT
      |
      v
CREATE BRANCH
      |
      v
DEVELOP
      |
      v
COMMIT
      |
      v
DIVERGE
      |
      v
MERGE
      |
      v
RESOLVE CONFLICTS
      |
      v
VERIFY
```

So far, however, everything has primarily happened on your own computer.

Real engineering teams need something else:

```text
Your laptop
     |
     v
Shared repository
     |
     v
Other engineers
```

That introduces remote repositories.
