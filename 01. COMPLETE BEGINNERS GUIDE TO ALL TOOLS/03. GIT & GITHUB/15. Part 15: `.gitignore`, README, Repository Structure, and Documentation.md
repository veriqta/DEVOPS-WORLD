# 1. Why Repository Structure Matters

Imagine you clone a repository and see this:

```text
project/
├── file1
├── test2
├── random.txt
├── final.py
├── final2.py
├── final-real.py
├── temp/
├── old/
├── config123
├── notes.txt
├── password.txt
└── stuff/
```

You immediately have questions.

What starts the application?

What is:

```text
final-real.py
```

Is:

```text
final2.py
```

still used?

Is:

```text
old/
```

safe to delete?

Does:

```text
password.txt
```

contain a real password?

Where are the tests?

Where is the documentation?

How do you install dependencies?

How do you run the project?

This repository may technically contain working code, but it communicates poorly.

Now compare it with:

```text
server-monitor/
├── README.md
├── LICENSE
├── CONTRIBUTING.md
├── .gitignore
├── .env.example
├── requirements.txt
├── src/
│   └── monitor.py
├── tests/
│   └── test_monitor.py
├── config/
│   └── default.yaml
├── docs/
│   └── troubleshooting.md
└── .github/
    ├── ISSUE_TEMPLATE/
    │   ├── bug_report.md
    │   └── feature_request.md
    └── pull_request_template.md
```

Even before opening a file, you can begin forming a mental model.

```text
src/
```

probably contains application source code.

```text
tests/
```

contains tests.

```text
config/
```

contains configuration.

```text
docs/
```

contains extended documentation.

```text
README.md
```

introduces the project.

```text
.gitignore
```

defines files Git should normally leave untracked.

```text
CONTRIBUTING.md
```

explains how to contribute.

```text
LICENSE
```

explains the project's licensing terms.

```text
.github/
```

contains GitHub-specific project configuration and community files.

Good repository structure reduces confusion.

# 4. What Should Git Track?

Before discussing `.gitignore`, we need a stronger mental model.

Git should generally track files that are part of the project's meaningful, reproducible history.

Examples include:

```text
Source code

Infrastructure code

Configuration templates

Dependency manifests

Tests

Documentation

Build definitions

CI/CD configuration

Scripts

Database migrations

Kubernetes manifests

Terraform configuration

Dockerfiles
```

For example:

```text
app.py
requirements.txt
Dockerfile
README.md
terraform/main.tf
k8s/deployment.yaml
.github/workflows/test.yml
```

These files describe the project.

They normally belong in version control.

---

# 5. What Should Git Usually Not Track?

Some files exist in your project directory but should not normally become part of repository history.

Examples include:

```text
Secrets

Local environment configuration

Generated build output

Dependency directories that can be recreated

Temporary files

Editor-specific files

Operating-system metadata

Cache files

Logs

Runtime files
```

For example:

```text
.env
node_modules/
dist/
build/
.DS_Store
*.log
__pycache__/
.idea/
.vscode/
```

Whether a particular file should be ignored can depend on the project.

For example, some teams intentionally commit selected editor configuration under `.vscode/`.

The important question is:

```text
Is this file part of the project,
or is it local/generated/private machine state?
```

# 6. The Problem With Unwanted Untracked Files

Imagine:

```text
server-monitor/
├── app.py
├── README.md
├── app.log
├── debug.log
├── .env
├── .DS_Store
└── __pycache__/
```

Run:

```bash
git status
```

You might see several untracked files.

But perhaps only:

```text
app.py
README.md
```

should be committed.

The others create noise.

Worse, you might accidentally run:

```bash
git add .
```

and stage:

```text
.env
```

containing credentials.

We need a way to tell Git:

```text
These paths may exist in my working directory,
but I do not want Git to treat them as normal
untracked project content.
```

That is the purpose of:

```text
.gitignore
```

---

# 7. What Is `.gitignore`?

`.gitignore` is a file containing patterns describing intentionally untracked files that Git should ignore.

A simple `.gitignore` might contain:

```gitignore
.env
*.log
__pycache__/
dist/
```

This tells Git to ignore matching untracked paths.

For example:

```text
.env
```

matches a file named `.env` according to the pattern's location and scope.

```text
*.log
```

can match log files such as:

```text
app.log
error.log
debug.log
```

```text
__pycache__/
```

matches directories named `__pycache__` under the applicable scope.

```text
dist/
```

matches a `dist` directory and its contents under the applicable scope.

---

# 8. `.gitignore` Does Not Delete Files

This is extremely important.

If you add:

```gitignore
.env
```

Git does not delete:

```text
.env
```

from your computer.

The file remains there.

Conceptually:

```text
Working Directory

.env
 |
 | still exists
 v

Your application can still read it
```

Git is simply being told:

```text
Do not normally treat this untracked path
as something to add to version control.
```

---

# 9. `.gitignore` Is Not a Security Vault

Another critical rule:

```text
.gitignore
!=
secret manager
```

Adding:

```text
.env
```

to `.gitignore` can help prevent an untracked `.env` file from being accidentally staged during normal Git operations.

But it does not encrypt the file.

It does not protect the file from:

* Malware
* Other users with filesystem access
* Backups
* Misconfigured applications
* Manual copying
* Shell history
* Screenshots
* Other secret-exposure paths

And most importantly:

```text
If a secret has already been committed,
adding it to .gitignore does not remove it
from existing Git history.
```

We will return to this.

---

# 10. Creating a `.gitignore`

From the repository root:

```bash
touch .gitignore
```

On systems where `touch` is available, this creates an empty file if it does not already exist.

You can then edit it.

Example:

```gitignore
# Environment configuration
.env

# Python cache
__pycache__/
*.pyc

# Logs
*.log

# Build output
dist/
build/
```

Comments begin with:

```text
#
```

So:

```gitignore
# Logs
```

is a comment.

It does not define an ignore pattern.

---

# 11. `.gitignore` Should Usually Be Committed

This surprises some beginners.

You normally do want Git to track:

```text
.gitignore
```

because the ignore rules are often part of the project's shared repository behavior.

For example:

```bash
git add .gitignore
git commit -m "Add Git ignore rules"
```

Now someone cloning the repository also receives those project-specific ignore rules.

Conceptually:

```text
Developer A
     |
     | commits .gitignore
     v
Repository
     |
     | clone
     v
Developer B

Developer B receives the same
project-level ignore rules.
```

# 12. Understanding Ignore Patterns

A `.gitignore` file is not simply a list of exact filenames.

It supports patterns.

Understanding those patterns prevents many mistakes.

Let's start with simple examples.

---

# 13. Ignore One File Name

```gitignore
debug.log
```

This ignores matching `debug.log` paths within the pattern's applicable scope.

Examples may include:

```text
debug.log
logs/debug.log
```

depending on where the `.gitignore` containing the pattern is located.

If you want to anchor a pattern relative to the directory containing that `.gitignore`, a leading slash becomes important.

---

# 14. Ignore Files by Extension

```gitignore
*.log
```

The:

```text
*
```

acts as a wildcard.

This pattern can match:

```text
app.log
debug.log
server.log
```

This is useful for generated log files.

Another example:

```gitignore
*.tmp
```

can match:

```text
cache.tmp
session.tmp
build.tmp
```

---

# 15. Ignore a Directory

```gitignore
build/
```

The trailing:

```text
/
```

indicates a directory pattern.

This can ignore the matching directory and paths beneath it.

Example:

```text
build/
├── app
├── output.bin
└── reports/
```

If `build/` is generated by your build system, it often does not belong in Git.

---

# 16. Root-Anchored Patterns

Suppose your root `.gitignore` contains:

```gitignore
/config.json
```

The leading slash anchors the match relative to the directory containing that `.gitignore`.

For a root `.gitignore`, this means the root-level:

```text
config.json
```

is matched.

A nested file such as:

```text
examples/config.json
```

is not matched by that root-anchored pattern.

Compare:

```gitignore
config.json
```

which can match `config.json` at multiple levels under the applicable directory.

This distinction is useful when the same filename may legitimately exist elsewhere.

---

# 17. Ignore Everything Matching a Pattern

Suppose:

```gitignore
*.log
```

You have:

```text
logs/
├── app.log
├── error.log
└── README.md
```

Git can ignore:

```text
app.log
error.log
```

while:

```text
README.md
```

can remain trackable.

---

# 18. Negation With `!`

Sometimes you want:

```text
Ignore a broad pattern
but keep one specific file.
```

You can use:

```text
!
```

to negate a previous matching rule.

Example:

```gitignore
*.log
!important.log
```

Conceptually:

```text
*.log
    ignore log files

!important.log
    make important.log eligible again
```

However, negation has important directory rules.

If Git has excluded an entire parent directory, simply negating a file inside that excluded directory may not be enough because Git does not traverse excluded directories in the same way.

For beginners, remember:

```text
Negation works best when you understand
the parent directory patterns too.
```

Do not create extremely complicated ignore rules when a simpler repository structure would solve the problem.

---

# 19. Pattern Examples

Consider:

```gitignore
# Environment files
.env
.env.local

# Logs
*.log

# Python
__pycache__/
*.pyc

# Build output
build/
dist/

# OS files
.DS_Store
Thumbs.db
```

This is much more useful than randomly adding files only after they appear in `git status`.

---

# 20. Testing Ignore Rules

Suppose you expect:

```text
.env
```

to be ignored.

Run:

```bash
git check-ignore .env
```

If `.env` is ignored, Git can print:

```text
.env
```

For more useful debugging:

```bash
git check-ignore -v .env
```

The verbose output can show:

* Which ignore source matched
* The relevant line number
* The matching pattern
* The path being tested

This is extremely useful when you do not understand why a file is being ignored.

---

# 21. Example: Debugging an Ignore Rule

Suppose:

```bash
git check-ignore -v app.log
```

returns conceptually:

```text
.gitignore:5:*.log    app.log
```

This tells you:

```text
Source:
.gitignore

Line:
5

Pattern:
*.log

Matched path:
app.log
```

Now you know exactly why Git is ignoring it.

# 22. Files That Should Not Normally Be Committed

There is no universal list for every project, but several categories deserve special attention.

We will cover:

1. Environment files
2. Secret files
3. Build artifacts
4. Dependency directories
5. IDE/editor files
6. Operating-system files
7. Cache files
8. Logs
9. Temporary files
10. Runtime-generated data

---

# 23. Environment Files

Applications often need environment-specific values.

For example:

```text
DATABASE_HOST
DATABASE_PORT
API_URL
LOG_LEVEL
```

Developers commonly store local values in files such as:

```text
.env
```

Example:

```text
DATABASE_HOST=localhost
DATABASE_PORT=5432
LOG_LEVEL=debug
```

This may be local configuration.

But `.env` files often also contain secrets.

Example:

```text
DATABASE_PASSWORD=super-secret-password
API_TOKEN=abc123
```

That should not be committed.

---

# 24. Ignoring Environment Files

A project might use:

```gitignore
.env
.env.local
.env.*.local
```

But be careful.

Do not blindly use:

```gitignore
.env*
```

if your project intentionally tracks something such as:

```text
.env.example
```

because a broad pattern could also ignore the example file.

---

# 25. `.env` vs `.env.example`

A strong pattern is:

```text
.env
```

for real local values and:

```text
.env.example
```

for documentation.

Example `.env`:

```text
DATABASE_HOST=db.internal.example
DATABASE_USER=appuser
DATABASE_PASSWORD=REAL_SECRET
API_TOKEN=REAL_TOKEN
```

Do not commit this.

Example `.env.example`:

```text
DATABASE_HOST=localhost
DATABASE_USER=your_username
DATABASE_PASSWORD=your_password
API_TOKEN=your_token
```

This contains placeholders rather than real credentials.

It can be committed.

---

# 26. Why `.env.example` Is Useful

A new developer clones the project.

They read:

```text
README.md
```

and see:

```bash
cp .env.example .env
```

Then they edit their local:

```text
.env
```

with actual values.

Conceptually:

```text
Repository

.env.example
     |
     | copy
     v

Local machine

.env
     |
     | fill in local values
     v

Application configuration
```

This documents required variables without publishing secrets.

---

# 27. Secret Files

Never intentionally commit real secrets such as:

```text
API tokens
Passwords
Database passwords
Private SSH keys
Cloud access keys
Service-account credentials
Private certificates
Signing keys
Encryption keys
Production secrets
```

Potentially dangerous filenames include:

```text
.env
credentials.json
service-account.json
id_rsa
id_ed25519
*.pem
*.key
```

But filenames alone are not enough.

A secret can exist in:

```text
app.py
README.md
config.yaml
terraform.tfvars
shell scripts
CI configuration
```

Security requires reviewing content, not merely filenames.

---

# 28. Dangerous Example

Never commit something like:

```python
API_KEY = "real-production-api-key"
```

Even if you later change it to:

```python
API_KEY = os.environ["API_KEY"]
```

the original secret may still exist in Git history.

If a real credential is exposed:

```text
Do not only delete it from the latest file.
```

Treat it as compromised.

Depending on the credential:

```text
Revoke it
Rotate it
Replace it
Investigate usage
Remove sensitive history where appropriate
```

The exact incident response depends on the system.

# 29. `.gitignore` Is Preventive, Not Retroactive

This deserves its own rule:

```text
.gitignore prevents normal tracking of
matching untracked files.

It does not erase tracked history.
```

Remember that sentence.

# 33. Dependency Directories

```text
node_modules/
```

can contain many generated/downloaded dependency files.

Projects commonly commit:

```text

```

```text

```

Conceptually:

```text

      |
```

# 34. Python Virtual Environments

```text

```

These directories contain a local Python environment.

They should generally not be committed.

Example:


# 35. IDE Files

Integrated development environments can create project-specific metadata.

Examples include:

```text
.idea/
.vscode/
*.iml
```

Should all of them always be ignored?

No.

This is where judgment matters.

For example:

```text
.vscode/
```

might contain:

```text
Personal editor settings
```

or:

```text
Useful shared workspace configuration
```

A team may intentionally commit selected files such as:

```text
.vscode/extensions.json
```

while ignoring personal settings.

The rule is:

```text
Do not blindly ignore or commit editor metadata.

Decide whether it represents
shared project configuration
or personal machine configuration.
```

# 36. Operating-System Files

Operating systems may create metadata files that have nothing to do with your project.

Common examples include:

```text
.DS_Store
Thumbs.db
Desktop.ini
```

For example, macOS may create:

```text
.DS_Store
```

to store Finder-related metadata.

Your application does not need that file.

It normally does not belong in repository history.

# 37. Logs

Applications generate logs such as:

```text
app.log
error.log
access.log
debug.log
```

These may contain:

* Runtime information
* Machine-specific paths
* User data
* Tokens
* Error details
* Large amounts of changing text

Logs are usually runtime artifacts.

A common pattern is:

```gitignore
*.log
```

But production logging should be managed by your application's logging and observability systems, not by committing live log files into Git.

# 38. Cache Files

```text

```

# 42. The Already-Tracked File Problem

This is one of the most common beginner mistakes.

Suppose you accidentally commit:

```text
debug.log
```

Then you add:

```gitignore
*.log
```

You expect:

```text
debug.log disappears from Git tracking
```

But it does not.

Why?

Because `.gitignore` is designed primarily for intentionally untracked files.

Files already tracked by Git are not made untracked simply because they later match `.gitignore`.

---

# 43. Demonstration

Create:

```bash
echo "debug information" > debug.log
```

Stage:

```bash
git add debug.log
```

Commit:

```bash
git commit -m "Add debug log"
```

Now add:

```gitignore
*.log
```

to `.gitignore`.

Modify:

```text
debug.log
```

Run:

```bash
git status
```

Git can still report changes to `debug.log`.

Why?

Because Git is already tracking it.

---

# 44. Stop Tracking While Keeping the Local File

If a file is tracked but should remain on your local filesystem, you can use:

```bash
git rm --cached debug.log
```

Breakdown:

```text
git
    run Git

rm
    remove a path from Git's index

--cached
    remove it from the index while
    leaving the working-tree file
```

Then:

```bash
git status
```

may show the tracked deletion that will be recorded in the next commit.

If `.gitignore` now matches `debug.log`, the local file can remain without appearing as a normal untracked file.

Commit the repository change:

```bash
git add .gitignore
git commit -m "Stop tracking generated log files"
```

---

# 45. Important `git rm --cached` Warning

Do not confuse:

```bash
git rm --cached file
```

with:

```bash
git rm file
```

The first is used when you want Git to stop tracking the file while keeping the working copy.

The second normally removes the path from both the index and working tree.

Before running file-removal commands:

```text
Know whether you want to:

Stop tracking the file

or

Delete the local file too
```

---

# 46. What If a Secret Was Already Committed?

Suppose:

```text
.env
```

contained:

```text
API_TOKEN=REAL_TOKEN
```

and was committed.

You then run:

```bash
git rm --cached .env
```

and add:

```gitignore
.env
```

This prevents future normal tracking of the local `.env`.

But the secret may still exist in earlier commits.

Therefore:

```text
git rm --cached
+
.gitignore
```

is not complete secret incident response.

The credential should normally be considered exposed and rotated or revoked as appropriate.

History cleanup may also be necessary depending on the situation.

---

# 47. Ignoring Files Only for Yourself

Suppose your team wants to track:

```text
project-notes/
```

but you personally use:

```text
scratch.txt
```

inside the repository.

You do not want to modify the project's shared `.gitignore` just for your personal workflow.

Git provides:

```text
.git/info/exclude
```

for repository-specific ignore rules that do not need to be shared with other clones.

You might add:

```text
scratch.txt
```

there.

That rule remains local to that Git repository.

---

# 48. Three Useful Ignore Locations

A beginner should understand three major levels.

### Shared project ignore

```text
.gitignore
```

Use for rules the project should share.

Example:

```text
build/
```

### Repository-local personal ignore

```text
.git/info/exclude
```

Use for local rules for this repository that should not be committed.

Example:

```text
my-notes.txt
```

### User-wide global ignore

Configured through:

```text
core.excludesFile
```

Use for patterns you personally want ignored across repositories.

Example:

```text
.DS_Store
```

---

# 49. Global Git Ignore

Suppose every repository on your Mac eventually gets:

```text
.DS_Store
```

Instead of adding:

```gitignore
.DS_Store
```

to every project, you can maintain a global ignore file.

Git supports a global excludes file through:

```text
core.excludesFile
```

You can inspect the configured value with:

```bash
git config --global --get core.excludesFile
```

If you choose a custom location, you might configure:

```bash
git config --global core.excludesFile ~/.gitignore_global
```

Then create:

```bash
touch ~/.gitignore_global
```

and add personal global patterns such as:

```gitignore
.DS_Store
*.swp
```

The exact choice of global patterns is personal.

---

# 50. Project Ignore vs Global Ignore

Ask:

```text
Should everyone working on this project ignore this?
```

If yes:

```text
.gitignore
```

may be appropriate.

Ask:

```text
Is this only related to my operating system,
editor, or personal workflow?
```

Then a global ignore or repository-local exclude may be better.

Example:

```text
Project generates dist/
```

Use project `.gitignore`.

Example:

```text
Your personal editor creates *.swp
```

A global ignore may make sense.

# 51. Debugging Ignore Problems

Suppose a file is missing from:

```bash
git status
```

and you do not know why.

Do not guess.

Run:

```bash
git check-ignore -v path/to/file
```

Example:

```bash
git check-ignore -v config/local.yaml
```

This can tell you which ignore rule matched it.

Your troubleshooting flow becomes:

```text
File not appearing
      |
      v
Is it already tracked?
      |
      v
git status
git ls-files
      |
      v
Check ignore rules
      |
      v
git check-ignore -v <path>
      |
      v
Identify matching rule
      |
      v
Decide whether rule is correct
```

# 82. Public Does Not Mean Unrestricted

A common beginner misconception is:

```text
The source code is public on GitHub,
therefore anyone can do anything with it.
```

Do not make that assumption.

Repository visibility and software licensing are different concepts.

A public repository means people can access the repository according to GitHub's platform rules.

A software license defines important permissions and conditions regarding use, modification, and distribution.

---

# 83. Common Open-Source Licenses

You may encounter licenses such as:

```text

BSD licenses
```

These licenses have different terms.

```text
Everyone seems to use MIT.
```

Choose licensing intentionally.

For business, legal, or unusual licensing situations, obtain appropriate legal guidance.

# 108. Step 7: Add a Simple Application

`src/monitor.py`:

```python
import urllib.request


def check_endpoint(url: str) -> bool:
    try:
        with urllib.request.urlopen(url, timeout=5) as response:
            return 200 <= response.status < 400
    except Exception:
        return False


if __name__ == "__main__":
    endpoint = "https://example.com"

    if check_endpoint(endpoint):
        print(f"{endpoint} is reachable")
    else:
        print(f"{endpoint} is unavailable")
```

# 126. Infrastructure Repositories Need Extra Security Care

A Terraform repository might contain:

```text
terraform.tfstate
terraform.tfstate.backup
*.tfvars
```

Some of these can contain sensitive infrastructure information or credentials depending on configuration.

Do not blindly commit Terraform state files.

A `.gitignore` for a Terraform project commonly needs rules appropriate to Terraform's generated/local state.

But remember:

```text
Ignoring a state file is not a complete
Terraform state-management strategy.
```

Production teams often use secured remote state backends with appropriate access controls, locking, encryption, and operational procedures.

`.gitignore` merely helps prevent local files from entering Git.

# 127. Kubernetes Repositories Also Need Care

A Kubernetes manifest might accidentally contain:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: database
stringData:
  password: real-password
```

Do not assume:

```text
It's YAML, so it belongs in Git.
```

The file format is irrelevant.

The content matters.

Production GitOps environments need an intentional secrets-management strategy.

Never commit plaintext production secrets simply because Kubernetes manifests are stored in Git.

# 142. Troubleshooting: `.gitignore` Is Not Working

Problem:

```text
I added .env to .gitignore,
but Git still shows changes to .env.
```

First check:

```bash
git ls-files .env
```

If output shows:

```text
.env
```

the file is already tracked.

That explains the behavior.

If it should no longer be tracked:

```bash
git rm --cached .env
```

Then ensure:

```gitignore
.env
```

exists.

Review:

```bash
git status
```

Before committing, remember:

```text
If .env contained real secrets and was already committed,
rotate/revoke them as appropriate.
```

# 143. Troubleshooting: File Is Ignored Unexpectedly

Problem:

```text
config/example.yaml does not appear in git status.
```

Run:

```bash
git check-ignore -v config/example.yaml
```

Suppose output indicates:

```text
.gitignore:8:config/ config/example.yaml
```

Now you know the rule:

```gitignore
config/
```

is too broad for your intended structure.

Adjust the rule deliberately.

# 144. Troubleshooting: Ignore Rule Does Not Match

Suppose:

```gitignore
/build
```

but you expected all nested `build` directories to be ignored.

Your root-anchored rule may only target the root-level path.

Understand whether you actually want:

```gitignore
/build/
```

or a broader:

```gitignore
build/
```

depending on your desired matching behavior.

Use:

```bash
git check-ignore -v <path>
```

to verify rather than guessing.

# 145. Troubleshooting: `.gitignore` Itself Is Not Showing

Check:

```bash
ls -la
```

on Unix-like systems.

Because `.gitignore` begins with:

```text
.
```

it is a hidden file on many systems.

Then:

```bash
git status
```

If `.gitignore` is untracked and not itself excluded by another rule, Git should normally show it.

# 158. Part 15 Final Recap

A professional repository is not:

```text
Code
+
Random files
+
Git history
```

It is an organized engineering workspace.

A strong repository looks conceptually like:

```text
                     REPOSITORY
                         |
       +-----------------+-----------------+
       |                 |                 |
       v                 v                 v
      CODE          DOCUMENTATION      CONFIGURATION
       |                 |                 |
       v                 v                 v
     src/            README.md          config/
    tests/             docs/          .env.example
       |
       |
       +-----------------+-----------------+
                         |
                         v
                   COLLABORATION
                         |
              +----------+----------+
              |                     |
              v                     v
       CONTRIBUTING.md           .github/
                                      |
                            +---------+---------+
                            |                   |
                            v                   v
                     Issue Templates      PR Template
```

And surrounding all of this is repository hygiene:

```text
.gitignore
    |
    +--> Environment files
    |
    +--> Generated artifacts
    |
    +--> Logs
    |
    +--> Caches
    |
    +--> Local machine files
```

The critical `.gitignore` rule is:

```text
Untracked + matching ignore rule
            |
            v
       normally ignored


Already tracked + matching ignore rule
            |
            v
        still tracked
```

If you need Git to stop tracking a local file:

```bash
git rm --cached <file>
```

But if that file contained a secret:

```text
Stopping tracking
!=
removing historical exposure
```

Treat the secret as compromised and respond appropriately.

The critical documentation model is:

```text
README
   |
   v
Start here
   |
   +--> Installation
   +--> Configuration
   +--> Usage
   +--> Testing
   +--> Troubleshooting
   |
   v
docs/
   |
   v
Detailed knowledge
```

The collaboration model is:

```text
CONTRIBUTING.md
      |
      v
How contributors work

Issue Templates
      |
      v
How problems are reported

PR Template
      |
      v
How changes are proposed
```

And the licensing model is:

```text
Public repository
      |
      X
      |
      v
"Anyone can do anything"

That assumption is wrong.


LICENSE
      |
      v
Defines important permissions
and conditions
```

The goal is not to fill a repository with every possible community file.

The goal is to make the repository:

```text
Understandable

Reproducible

Safe

Navigable

Maintainable

Contributor-friendly
```

A new engineer should not need a private phone call with the original developer just to discover how the project works.

The repository itself should teach them how to begin.
