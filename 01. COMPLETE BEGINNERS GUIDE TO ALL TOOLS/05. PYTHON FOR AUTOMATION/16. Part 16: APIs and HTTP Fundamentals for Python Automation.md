
# Part 16: APIs and HTTP Fundamentals for Python Automation

Understand APIs before trying to automate them.

In Part 14, you learned how Python works with JSON.

In Part 15, you learned how Python can read, validate, modify, and safely write YAML configuration.

Now we move from data stored in files to communication between systems.

Modern DevOps automation frequently needs to communicate with:

* Cloud platforms
* Git hosting platforms
* CI/CD systems
* Monitoring platforms
* Kubernetes APIs
* Incident-management systems
* Ticketing systems
* Security platforms
* Container registries
* Internal company services

These systems commonly expose APIs.

Before writing Python code that calls an API, you need to understand what actually happens when one system communicates with another.

The basic model is:

```text
Python Automation
       |
       | HTTP Request
       v
      API
       |
       | HTTP Response
       v
Python Automation
```

The response frequently contains JSON:

```text
Python
   |
   | HTTP Request
   v
API Server
   |
   | HTTP Response
   v
JSON
   |
   v
Python dictionary/list
   |
   v
Automation decision
```

By the end of this part, you should understand the language and mechanics behind API communication well enough to inspect, test, troubleshoot, and reason about an API before automating it with Python.

---

# 1. What Are We Trying to Accomplish?

Imagine your automation needs to check whether a production service is healthy.

An API provides:

```text
https://api.example.com/services/payments
```

When queried, it returns:

```json
{
  "name": "payments",
  "status": "running",
  "replicas": 5
}
```

Your future Python script might use this information to decide:

```text
status == running
        |
        +---- YES ---> Continue
        |
        +---- NO ----> Alert / Fail
```

But before writing Python code, you should understand:

* What is the API?
* Who is the client?
* Who is the server?
* What is the URL?
* What is the endpoint?
* What HTTP method should be used?
* Does authentication exist?
* What headers are required?
* Does the request need a body?
* What status code indicates success?
* What happens if the request times out?
* What happens if the API limits your requests?
* What if there are 10,000 results?
* What if the server returns an error?

That is the foundation of reliable API automation.

---

# 2. What Is an API?

API stands for:

```text
Application Programming Interface
```

An API is an interface that allows software systems to communicate with each other according to defined rules.

For example:

```text
Your Python Script
       |
       v
Cloud API
       |
       v
Cloud Resources
```

Your Python script does not need to know the internal implementation of the cloud platform.

It communicates through the interface the platform provides.

---

# 3. Think of an API as a Contract

Suppose an API documentation says:

```text
GET /servers/123
```

returns information about server `123`.

That creates a contract.

Your client agrees to send the request in the expected format.

The server agrees to respond according to its API behavior.

Conceptually:

```text
CLIENT
"I will send a valid request."
        |
        v
API CONTRACT
        |
        v
SERVER
"I will return a defined response."
```

The contract may specify:

* Available endpoints
* HTTP methods
* Required headers
* Authentication
* Request-body format
* Query parameters
* Path parameters
* Response format
* Status codes
* Rate limits
* Error responses

---

# 4. APIs Hide Internal Complexity

Imagine a cloud platform containing:

```text
Databases
Load balancers
Authentication systems
Schedulers
Virtual machines
Networks
Storage systems
Logging systems
Internal microservices
```

You normally do not communicate directly with every internal component.

Instead:

```text
Automation
    |
    v
Public / Internal API
    |
    v
Platform internals
```

The API provides a controlled interface.

# 5. APIs Are Everywhere in DevOps

A DevOps engineer might use APIs to:


# 6. APIs Are Not Only Web APIs

The general idea of an API is broader than HTTP.

Software libraries also expose APIs.

Operating systems expose programming interfaces.

Databases expose interfaces.

But in this part, our focus is primarily:

```text
HTTP-based web APIs
```

because they are extremely common in modern infrastructure automation.

# 7. Client and Server

HTTP communication commonly involves two roles:

```text
CLIENT
   |
   | Request
   v
SERVER
   |
   | Response
   v
CLIENT
```

The client initiates the request.

The server receives the request and returns a response.

---

# 8. What Is a Client?

A client is software that sends a request to another system.

Examples:

```text
Browser
curl
Python script
Mobile application
CLI tool
Monitoring agent
CI/CD job
```

If your Python script calls an API:

```text
Python script = client
```

---

# 9. What Is a Server?

The server is the system receiving the request and providing a response.

Example:

```text
Python Script
     |
     | GET /servers
     v
Cloud API Server
```

The API server may then communicate with databases or internal services before returning a response.

---

# 10. Client-Server Flow

A simplified request:

```text
Client
  |
  | "Give me server 123"
  v
Server
  |
  | Processes request
  |
  v
Response
```

More realistically:

```text
Python Client
      |
      | HTTPS Request
      v
API Gateway
      |
      v
Authentication
      |
      v
Application Service
      |
      v
Database / Platform
      |
      v
Application Service
      |
      v
HTTPS Response
      |
      v
Python Client
```

You do not always see those internal layers.

From the client's perspective:

```text
Request
   |
   v
API
   |
   v
Response
```

# 11. What Is REST?

REST stands for:

```text
Representational State Transfer
```

REST is an architectural style commonly used for web APIs.

You will frequently hear:

```text
REST API
RESTful API
REST endpoint
REST service
```

For beginner automation, focus on the practical pattern:

```text
Resource
+
URL
+
HTTP method
+
request data
+
response data
```

---

# 12. Resources in REST APIs

REST APIs often organize operations around resources.

Examples:

```text
users
servers
deployments
repositories
incidents
clusters
projects
containers
pipelines
```

A URL might represent a collection:

```text
/api/servers
```

while:

```text
/api/servers/123
```

may represent one particular server.

---

# 13. Collection vs Individual Resource

Think:

```text
/servers
```

as:

```text
Collection of servers
```

and:

```text
/servers/123
```

as:

```text
Server 123
```

This pattern appears frequently in REST APIs.

---

# 14. REST Is an Architectural Style, Not a Strict Universal Format

Not every API that uses HTTP follows REST principles perfectly.

Real APIs vary.

You may encounter:

* REST-style APIs
* RPC-style APIs
* GraphQL APIs
* Webhooks
* Vendor-specific APIs

Do not assume every HTTP API behaves identically.

Always read its documentation.

---

# 15. What Is an Endpoint?

An endpoint is a specific API location through which a client interacts with a resource or operation.

Example:

```text
GET /servers
```

might list servers.

Another endpoint:

```text
GET /servers/123
```

might retrieve one server.

Another:

```text
DELETE /servers/123
```

might delete it.

---

# 16. Endpoint Includes More Than Just a Path

Engineers sometimes use "endpoint" informally to refer to the URL.

But when working with APIs, the operation often depends on both:

```text
HTTP method
+
URL/path
```

For example:

```text
GET /servers/123
```

and:

```text
DELETE /servers/123
```

use the same path but perform completely different operations.

---

# 17. What Is a URL?

URL stands for:

```text
Uniform Resource Locator
```

A URL identifies where a resource can be accessed.

Example:

```text
https://api.example.com/v1/servers/123
```

---

# 18. Breaking Down a URL

Consider:

```text
https://api.example.com:443/v1/servers/123?details=true
```

Conceptually:

```text
https
  |
  +--> scheme/protocol

api.example.com
  |
  +--> hostname

443
  |
  +--> port

/v1/servers/123
  |
  +--> path

?details=true
  |
  +--> query string
```

---

# 19. URL Scheme

The beginning:

```text
https://
```

indicates how the client should communicate with the server.

Common schemes include:

```text
http
https
```

For APIs carrying credentials or sensitive infrastructure information, HTTPS should normally be expected.

---

# 20. Hostname

In:

```text
https://api.example.com/v1/servers
```

the hostname is:

```text
api.example.com
```

DNS normally resolves this hostname to an IP address.

The networking concepts underneath may involve:

```text
DNS
TCP
TLS
HTTP
```

You do not need to implement these protocols manually to use an API, but understanding the layers helps troubleshooting.

---

# 21. Port

HTTP commonly uses:

```text
80
```

HTTPS commonly uses:

```text
443
```

When the standard port is used, it is usually omitted from the URL.

Therefore:

```text
https://api.example.com:443
```

and:

```text
https://api.example.com
```

commonly refer to HTTPS on the standard port.

---

# 22. Path

In:

```text
https://api.example.com/v1/servers/123
```

the path is:

```text
/v1/servers/123
```

The server uses this path to determine which resource or operation is being requested.

---

# 23. API Versions in URLs

You may see:

```text
/v1/
/v2/
/api/v1/
```

Example:

```text
https://api.example.com/v1/servers
```

Versioning allows an API provider to evolve its interface.

A newer version may change:

* Fields
* Behavior
* Authentication
* Endpoints
* Error formats
* Capabilities

Never casually replace:

```text
v1
```

with:

```text
v2
```

without reading the migration documentation.

---

# 24. What Is a URI?

URI stands for:

```text
Uniform Resource Identifier
```

A URI identifies a resource.

A URL is a type of URI that also tells you how and where the resource can be accessed.

A useful beginner model is:

```text
URI
 |
 +--> identifies a resource

URL
 |
 +--> identifies resource
      and provides location/access information
```

In everyday API discussions, engineers frequently say URL when referring to API addresses.

You do not need to obsess over the terminology difference to begin automating APIs.

---

# 25. What Is HTTP?

HTTP stands for:

```text
Hypertext Transfer Protocol
```

HTTP defines rules for communication between clients and servers.

A simplified HTTP interaction is:

```text
Client
  |
  | HTTP Request
  v
Server
  |
  | HTTP Response
  v
Client
```

---

# 26. HTTP Is a Protocol

A protocol is an agreed set of communication rules.

HTTP defines concepts such as:

* Methods
* Headers
* Request bodies
* Response bodies
* Status codes

This gives different systems a common way to communicate.

---

# 27. What Is HTTPS?

HTTPS means HTTP communication protected using TLS.

Conceptually:

```text
HTTP
+
TLS encryption/security
=
HTTPS
```

HTTPS provides important protections such as:

* Encryption in transit
* Server authentication through certificates
* Integrity protection

---

# 28. Why HTTPS Matters for APIs

API requests may contain:

```text
Passwords
Tokens
API keys
Personal data
Infrastructure information
Deployment information
Configuration
```

Sending sensitive information over unencrypted HTTP can expose it to interception.

For real API automation, prefer HTTPS whenever the service supports it.

---

# 29. HTTPS Does Not Make Everything Automatically Safe

HTTPS protects data in transit.

It does not protect you from:

* Leaking tokens into logs
* Hardcoding secrets
* Sending credentials to the wrong host
* Weak authorization
* Malicious API responses
* Application vulnerabilities
* Unsafe automation decisions

Security has multiple layers.

---

# 30. What Is an HTTP Request?

A request is a message sent by the client to the server.

It can contain:

```text
HTTP method
URL
Headers
Query parameters
Path parameters
Request body
Authentication information
```

Not every request contains all of these.

---

# 31. What Is an HTTP Response?

The server returns a response.

It commonly contains:

```text
Status code
Headers
Response body
```

Example:

```text
HTTP/1.1 200 OK
Content-Type: application/json
```

with a body:

```json
{
  "status": "running"
}
```

---

# 32. Request and Response Flow

```text
CLIENT
  |
  | REQUEST
  |
  | Method: GET
  | URL: /servers/123
  | Headers: ...
  |
  v
SERVER
  |
  | Process request
  |
  v
RESPONSE
  |
  | Status: 200
  | Headers: ...
  | Body: JSON
  |
  v
CLIENT
```

---

# 33. HTTP Methods

HTTP methods describe the intended operation.

The methods we will focus on are:

```text
GET
POST
PUT
PATCH
DELETE
```

These are sometimes called HTTP verbs.

---

# 34. GET

GET is commonly used to retrieve information.

Example:

```text
GET /servers
```

might retrieve all servers.

```text
GET /servers/123
```

might retrieve server 123.

---

# 35. GET Example

Request:

```text
GET /api/v1/servers/123
```

Response:

```json
{
  "id": 123,
  "name": "web01",
  "status": "running"
}
```

The client asked for information.

---

# 36. GET Should Normally Be Read-Oriented

GET is intended for retrieving a representation of a resource.

You should not assume that every real-world API perfectly follows this principle, but well-designed APIs generally avoid using GET for destructive state changes.

Always check the API documentation.

---

# 37. POST

POST is commonly used to create a resource or trigger an operation.

Example:

```text
POST /servers
```

with:

```json
{
  "name": "web03",
  "region": "us-east-1"
}
```

might create a new server.

---

# 38. POST Request Body

Conceptually:

```text
POST /servers

Body:
{
  "name": "web03",
  "region": "us-east-1"
}
```

The body provides data required for the operation.

---

# 39. POST Is Not Always "Create"

Although resource creation is common, POST can also represent operations such as:

```text
Trigger deployment
Start pipeline
Rotate credential
Send notification
Perform search
Execute action
```

The documentation defines the actual behavior.

---

# 40. PUT

PUT is commonly used to replace or fully update a resource representation.

Conceptually:

```text
Current server
{
  "name": "web01",
  "region": "us-east-1",
  "size": "small"
}
```

PUT may send the desired complete representation:

```json
{
  "name": "web01",
  "region": "us-east-1",
  "size": "large"
}
```

---

# 41. PUT Can Have Replacement Semantics

A common conceptual difference is:

```text
PUT
 |
 +--> Replace/update full resource

PATCH
 |
 +--> Modify selected fields
```

But actual APIs can differ.

Never assume missing PUT fields will automatically remain unchanged.

Read the API documentation.

---

# 42. PATCH

PATCH is commonly used for partial updates.

Example:

```text
PATCH /servers/123
```

Body:

```json
{
  "size": "large"
}
```

The intent is:

```text
Change size
without resending every field
```

---

# 43. PUT vs PATCH

Simplified model:

```text
PUT

Current:
name = web01
region = us-east-1
size = small

Send full desired representation
        |
        v
Updated resource
```

Compared with:

```text
PATCH

Change:
size = large

        |
        v
Only requested field changes
```

Again, documentation wins over assumptions.

---

# 44. DELETE

DELETE is commonly used to remove a resource.

Example:

```text
DELETE /servers/123
```

This may delete server 123.

---

# 45. DELETE Is Potentially Destructive

Automation using DELETE deserves strong safeguards.

Before sending destructive requests, consider:

* Is the target correct?
* Is the environment correct?
* Is the resource ID correct?
* Is deletion allowed?
* Is confirmation required?
* Is there a dry-run mechanism?
* Can the resource be recovered?
* Are dependencies affected?
* Does the API support soft deletion?

Never experiment with destructive API operations against important infrastructure.

---

# 46. HTTP Methods Summary

```text
GET
Retrieve information

POST
Create or trigger operation

PUT
Replace/full update

PATCH
Partial update

DELETE
Remove resource
```

This is a useful starting model, not a substitute for documentation.

---

# 47. Safe vs Destructive Operations

A beginner should distinguish:

```text
READ
 |
 +--> GET
```

from operations that may change state:

```text
WRITE / ACTION
 |
 +--> POST
 +--> PUT
 +--> PATCH
 +--> DELETE
```

When learning an unfamiliar API, begin with read-only operations where possible.

---

# 48. Idempotency and HTTP Methods

An operation is idempotent when repeating the same request has the same intended effect as performing it once.

Conceptually:

```text
Set replicas to 5
Set replicas to 5
Set replicas to 5

Final desired state:
replicas = 5
```

This differs from:

```text
Create a new deployment
Create a new deployment
Create a new deployment
```

which could potentially create multiple resources.

---

# 49. Why Idempotency Matters in Automation

Networks fail.

Clients retry.

Responses get lost.

Suppose:

```text
Client sends request
        |
        v
Server completes operation
        |
        X
Response never reaches client
```

The client may not know whether the operation succeeded.

If it blindly retries a non-idempotent operation, it might create duplicate effects.

Reliable automation must understand retry behavior.

---

# 50. Headers

HTTP headers provide metadata about a request or response.

Conceptually:

```text
Request
 |
 +-- Method
 +-- URL
 +-- Headers
 +-- Body
```

Headers can describe:

* Authentication
* Content type
* Accepted response format
* User agent
* Caching behavior
* Correlation IDs
* API versions
* Request tracing

---

# 51. Example Request Headers

```text
Authorization: Bearer TOKEN
Content-Type: application/json
Accept: application/json
```

Each header usually follows:

```text
Header-Name: value
```

---

# 52. `Content-Type`

Example:

```text
Content-Type: application/json
```

This tells the receiver:

```text
The body is JSON.
```

If you send:

```json
{
  "name": "web01"
}
```

the server may need the correct `Content-Type` to interpret it properly.

---

# 53. `Accept`

Example:

```text
Accept: application/json
```

This tells the server:

```text
I prefer/expect a JSON response.
```

The exact behavior depends on the API.

---

# 54. `Authorization`

Example:

```text
Authorization: Bearer TOKEN
```

This carries authentication information.

Never print or expose this header carelessly.

---

# 55. Response Headers

Servers also return headers.

Examples may include:

```text
Content-Type
Content-Length
Date
Retry-After
RateLimit-related headers
Request IDs
Cache-Control
```

These can provide important information for automation and troubleshooting.

---

# 56. Request IDs

Many production APIs return a request or correlation ID.

Example:

```text
X-Request-ID: abc123
```

If a request fails, this identifier can help support teams or engineers trace the request through logs.

Good automation records useful request IDs without exposing credentials.

---

# 57. Request Body

The request body contains data sent to the server.

Example:

```text
POST /servers
```

Body:

```json
{
  "name": "web03",
  "region": "us-east-1"
}
```

---

# 58. Not Every Request Has a Body

GET requests commonly send parameters through the URL rather than relying on a request body.

POST, PUT, and PATCH commonly use request bodies.

But APIs vary.

Follow the documentation.

---

# 59. JSON Request Bodies

Many modern APIs expect:

```text
Content-Type: application/json
```

and a JSON body.

Example:

```json
{
  "service": "payments",
  "replicas": 5
}
```

This connects directly to Part 14.

---

# 60. JSON Is Data, HTTP Is Transportation

This distinction is fundamental.

```text
JSON
 |
 +--> represents structured data

HTTP
 |
 +--> transports requests/responses
```

Together:

```text
HTTP Request
    |
    +--> JSON body
```

or:

```text
HTTP Response
    |
    +--> JSON body
```

Do not confuse the data format with the communication protocol.

---

# 61. Query Parameters

Query parameters provide additional information through the URL.

Example:

```text
GET /servers?region=us-east-1
```

Here:

```text
region
```

is the parameter name.

```text
us-east-1
```

is the value.

---

# 62. Multiple Query Parameters

Example:

```text
GET /servers?region=us-east-1&status=running
```

This might mean:

```text
Return servers where:

region = us-east-1
AND
status = running
```

---

# 63. Query String

The portion beginning with:

```text
?
```

is the query string.

Example:

```text
?region=us-east-1&status=running
```

Multiple parameters are commonly separated with:

```text
&
```

---

# 64. Common Uses of Query Parameters

Query parameters are frequently used for:

```text
Filtering
Sorting
Pagination
Search
Selecting fields
Date ranges
Result limits
```

Examples:

```text
?status=failed

?limit=100

?page=2

?sort=created_at

?environment=production
```

---

# 65. Query Parameters Should Be Encoded Properly

Suppose a search value contains spaces:

```text
production server
```

You should not manually construct URLs carelessly.

Characters may require URL encoding.

Tools such as `curl` and Python HTTP libraries provide safer mechanisms for handling parameters.

Part 17 will show how Python handles this.

---

# 66. Path Parameters

A path parameter is part of the URL path.

Example:

```text
/servers/123
```

Here:

```text
123
```

may be the server ID.

Documentation may describe the route as:

```text
/servers/{server_id}
```

---

# 67. Another Path Parameter Example

Documentation:

```text
/projects/{project_id}/deployments/{deployment_id}
```

Actual request:

```text
/projects/42/deployments/901
```

Values:

```text
project_id = 42
deployment_id = 901
```

---

# 68. Path Parameters vs Query Parameters

Path parameter:

```text
/servers/123
```

usually identifies a particular resource.

Query parameter:

```text
/servers?status=running
```

usually modifies, filters, or controls the request.

A useful model:

```text
Path:
Which resource?

Query:
How should the request be filtered
or modified?
```

---

# 69. Status Codes

HTTP responses include status codes.

Example:

```text
200
```

or:

```text
404
```

or:

```text
500
```

Status codes help the client understand what happened.

---

# 70. Status Code Families

The first digit gives a broad category:

```text
1xx
Informational

2xx
Success

3xx
Redirection

4xx
Client-side/request problem

5xx
Server-side problem
```

For API automation, you will frequently reason about:

```text
2xx
4xx
5xx
```

---

# 71. Do Not Check Only for `200`

Beginners often write logic equivalent to:

```text
if status == 200:
    success
else:
    failure
```

But HTTP has multiple successful 2xx codes.

Depending on the operation, success may be:

```text
200
201
202
204
```

Always understand what the endpoint documents.

---

# 72. 200 OK

```text
200 OK
```

means the request succeeded in a general sense.

Common example:

```text
GET /servers/123
```

Response:

```text
200 OK
```

with JSON data.

---

# 73. 201 Created

```text
201 Created
```

commonly indicates that a new resource was successfully created.

Example:

```text
POST /servers
```

might return:

```text
201 Created
```

---

# 74. 202 Accepted

```text
202 Accepted
```

usually means:

```text
The request was accepted,
but processing may not be complete.
```

This is extremely important in infrastructure APIs.

---

# 75. Asynchronous Operations

Imagine:

```text
POST /clusters
```

Creating a cluster may take 20 minutes.

The API cannot necessarily keep the HTTP request open until completion.

Instead:

```text
Client
  |
  | POST /clusters
  v
API
  |
  | 202 Accepted
  | operation_id = 789
  v
Client
```

The client may need to check operation status later.

---

# 76. Accepted Does Not Mean Completed

This distinction matters:

```text
202 Accepted
!=
Operation completed successfully
```

Your automation may need to poll a status endpoint.

Example:

```text
POST create cluster
      |
      v
202 Accepted
      |
      v
GET /operations/789
      |
      v
status = running
      |
      v
wait
      |
      v
GET /operations/789
      |
      v
status = completed
```

---

# 77. 204 No Content

```text
204 No Content
```

means the request succeeded but there is no response body.

This may occur with:

```text
DELETE
PUT
PATCH
```

depending on the API.

Do not assume every successful response contains JSON.

---

# 78. Common 2xx Codes

```text
200 OK
Request succeeded

Resource created

Request accepted for processing

```

# 79. 400 Bad Request

```text

```

usually indicates that the request is invalid.

* Malformed JSON
* Missing field
* Invalid parameter
* Wrong data type

# 81. 401 Unauthorized

Despite the name, `401` commonly means authentication is missing, invalid, or expired.

Possible causes:



# 82. 403 Forbidden

```text

```

commonly means the server understood the identity but the caller does not have permission for the requested operation.

Conceptually:

```text

Authentication problem

403
Authorization/permission problem
```

Real implementations can vary, but this is a useful starting distinction.

---

# 83. Authentication vs Authorization

Authentication asks:

```text
Who are you?
```

Authorization asks:

```text
What are you allowed to do?
```

Example:

```text
Token proves:
You are automation-service

Permission policy says:
automation-service may read servers
but may not delete servers
```

Then:

```text
GET /servers
```

may succeed.

But:

```text
DELETE /servers/123
```

may return:

```text
403 Forbidden
```

# 84. 404 Not Found

```text

```

means the requested resource or route could not be found.

Possible causes:

* Wrong endpoint
* Wrong resource ID
* Resource deleted
* Typo
* Wrong API version
* Some APIs intentionally hide unauthorized resources using 404

Do not automatically conclude:

```text
"The server is down."
```

A 404 response proves you received an HTTP response.

---

# 85. 405 Method Not Allowed


means the path may exist, but the HTTP method is not allowed there.

```text

```

when the endpoint only supports:

```text

PATCH
```

# 86. 409 Conflict

can indicate that the request conflicts with the current state.

Examples:

```text

Version conflict
Concurrent update conflict
State does not permit operation
```

This can matter in automation where multiple processes modify the same resources.

Not every API uses 422 the same way.

# 104. Authentication Basics

Many APIs are not public.

Before returning data or allowing changes, the server needs to identify the caller.

Authentication answers:

```text
Who is making this request?
```

Common API authentication mechanisms include:

* API keys
* Tokens
* Bearer tokens
* Basic authentication
* OAuth-based access tokens
* Signed requests
* Client certificates

This part focuses on basic token concepts.

---

# 105. What Is a Token?

A token is a credential or credential-like value used to represent authenticated access.

Example conceptually:

```text
token:
abc123-secret-value
```

The client sends it with the request.

The server validates it.

---

# 106. Token Flow

```text
Client
  |
  | Request + Token
  v
API
  |
  | Validate token
  |
  +---- invalid ---> Reject
  |
  +---- valid -----> Check permissions
                        |
                        v
                     Process request
```

---

# 107. Tokens Are Secrets

Treat tokens like passwords.

Do not:

* Commit them to Git.
* Hardcode them into public scripts.
* Print them in logs.
* Put them into screenshots.
* Share them in tickets.
* Expose them in error messages.

---

# 108. What Is an API Key?

An API key is a value issued by a service that a client includes with requests.

The API may expect it:

```text
In a header
```

or sometimes:

```text
In another documented location
```

Example conceptually:

```text
X-API-Key: SECRET_VALUE
```

---

# 109. API Keys Are Not All Implemented the Same Way

One service may expect:

```text
X-API-Key: value
```

Another may use a different header.

Another may use query parameters.

Do not guess.

Read the documentation.

For secrets, headers are generally preferable to exposing credentials in URLs because URLs can appear in logs and histories.

---

# 110. What Is a Bearer Token?

A common pattern is:

```text
Authorization: Bearer TOKEN
```

Example:

```text
Authorization: Bearer eyJ...
```

The word:

```text
Bearer
```

describes the authentication scheme.

The credential follows it.

---

# 111. Bearer Token Structure

The header is conceptually:

```text
Authorization
      |
      v
Bearer <token>
```

Example:

```text
Authorization: Bearer abc123
```

Do not omit the space between:

```text
Bearer
```

and the token.

---

# 112. Why "Bearer"?

Conceptually, possession of the bearer token grants the associated access.

That makes token protection extremely important.

If an attacker obtains a valid bearer token, they may be able to use it until it expires or is revoked, depending on the system.

---

# 113. Token Permissions

A token should ideally have only the permissions required.

Example:

```text
Monitoring script
```

probably needs:

```text
Read metrics
Read service status
```

It probably does not need:

```text
Delete clusters
Create administrators
Rotate production credentials
```

This is least privilege.

---

# 114. Token Scope

Some systems allow tokens to be restricted by scope.

Conceptually:

```text
Token A
 |
 +--> read:servers
 +--> read:metrics

Token B
 |
 +--> read:servers
 +--> write:servers
 +--> delete:servers
```

Use the narrowest appropriate permissions.

---

# 115. Token Expiration

Tokens may expire.

A script that worked yesterday may suddenly receive:

```text
401 Unauthorized
```

Possible cause:

```text
Expired token
```

Automation needs a credential-management strategy rather than assuming credentials last forever.

---

# 116. Token Rotation

Organizations may periodically replace credentials.

This is token rotation.

Good automation should avoid embedding tokens directly in code so credentials can change without rewriting the program.

---

# 117. Where Should Python Get Secrets?

Common approaches include:

```text
Environment variables
Secret managers
CI/CD secret stores
Cloud secret services
Workload identity
Protected runtime configuration
```

The exact choice depends on the environment.

Part 17 will use safe patterns when building API clients.

---

# 118. Do Not Put Secrets Directly in URLs

Avoid patterns such as:

```text
https://api.example.com/data?token=SECRET
```

unless a specific API absolutely requires that mechanism.

URLs can be recorded in:

* Browser history
* Proxy logs
* Server logs
* Monitoring systems
* Shell history
* Debug output

Prefer the documented secure authentication mechanism.

# 119. Authentication Failure Troubleshooting

If you receive:

```text

```

investigate:

```text
Is the token present?
Is it expired?
Is the header formatted correctly?
Is the credential for the correct environment?
Is the API hostname correct?
Is the authentication scheme correct?
```

Do not immediately regenerate credentials before understanding the cause.

---

# 120. Authorization Failure Troubleshooting

If you receive:

```text

```

investigate:

```text

What permissions does it have?
What operation is being attempted?
Is the resource protected?
Is there an organization/project policy?

```

Do not solve every 403 by granting administrator access.

Apply least privilege.

# 121. Pagination

Suppose an API contains:

```text
50,000 servers
```

Returning all 50,000 in one response may be inefficient.

Instead, the API may divide results into pages.

This is pagination.

---

# 122. Simple Page-Based Pagination

Request:

```text
GET /servers?page=1&limit=100
```

returns the first 100 results.

Then:

```text
GET /servers?page=2&limit=100
```

returns the next group.

---

# 123. Pagination Flow

```text
Page 1
  |
  v
100 results
  |
  v
More pages?
  |
  +---- YES ---> Page 2
  |
  +---- NO ----> Finish
```

---

# 124. Why Pagination Matters

If your script reads only the first response, it might process:

```text
100 resources
```

while believing it processed:

```text
10,000 resources
```

That creates incomplete automation.

---

# 125. Pagination Metadata

An API might return:

```json
{
  "items": [
    {
      "id": 1
    },
    {
      "id": 2
    }
  ],
  "page": 1,
  "total_pages": 20
}
```

Your automation can inspect:

```text
page
total_pages
```

to determine whether more requests are required.

---

# 126. Cursor-Based Pagination

Not every API uses page numbers.

Some use a cursor.

Example response:

```json
{
  "items": [
    {
      "id": "srv-1"
    }
  ],
  "next_cursor": "abc123"
}
```

The next request may use:

```text
?cursor=abc123
```

---

# 127. Cursor Flow

```text
Request
  |
  v
Results + next_cursor
  |
  v
cursor exists?
  |
  +---- YES ---> Request next page
  |
  +---- NO ----> Finished
```

---

# 128. Do Not Invent Pagination Logic

Different APIs use:

```text
page
offset
limit
cursor
next
continuation_token
links
```

Read the documentation.

Do not assume:

```text
?page=2
```

works everywhere.

---

# 129. Pagination Can Interact with Changing Data

Imagine resources are being created and deleted while you paginate.

The result set may change between requests.

Depending on the API, this can create:

* Duplicates
* Missing items
* Changed ordering

Cursor-based pagination can sometimes help provide more stable traversal, but behavior depends on the API.

For important automation, understand the API's pagination guarantees.

---

# 130. Rate Limiting

APIs have finite capacity.

Providers may restrict how many requests a client can make.

This is rate limiting.

Example:

```text
100 requests per minute
```

---

# 131. Why APIs Use Rate Limits

Rate limits can protect:

* Service availability
* Infrastructure capacity
* Other customers
* Databases
* Upstream systems
* Security boundaries

They can also enforce product or account limits.

---

# 132. What Happens When You Exceed a Rate Limit?

A common response is:

```text
429 Too Many Requests
```

The server may also provide information about when to retry.

---

# 133. `Retry-After`

An API may return:

```text
Retry-After: 30
```

Conceptually:

```text
Wait 30 seconds before retrying.
```

The exact interpretation of the header can vary according to HTTP rules and API behavior, so use the documentation.

---

# 134. Rate-Limit Headers

Some APIs provide headers containing information such as:

```text
Limit
Remaining
Reset time
```

Names differ between APIs.

Never hardcode assumptions about header names without checking documentation.

---

# 135. Bad Rate-Limit Handling

Dangerous logic:

```text
Request
 |
 v
429
 |
 v
Immediately retry
 |
 v
429
 |
 v
Immediately retry
 |
 v
429
 |
 v
Repeat forever
```

This makes the situation worse.

---

# 136. Better Rate-Limit Handling

Conceptually:

```text
Request
 |
 v
429?
 |
 +---- NO ----> Continue
 |
 +---- YES
        |
        v
Read retry guidance
        |
        v
Wait
        |
        v
Retry within limit
```

Retries should be bounded.

---

# 137. Exponential Backoff

When temporary failures occur, automation may increase the delay between retries.

Example:

```text
Attempt 1
wait 1 second

Attempt 2
wait 2 seconds

Attempt 3
wait 4 seconds

Attempt 4
wait 8 seconds
```

This is exponential backoff.

---

# 138. Why Backoff Helps

If a service is overloaded, thousands of clients retrying immediately can worsen the outage.

Backoff reduces pressure.

A small randomized delay called jitter is often added in distributed systems so many clients do not retry at exactly the same time.

---

# 139. Retry Safety Comes Before Retry Speed

Before retrying, ask:

```text
Is the failure temporary?

Is the operation safe to repeat?

Could the original request have succeeded?

Could a retry create duplicate state?
```

This is especially important for POST and other state-changing operations.

---

# 140. Timeouts

A timeout limits how long the client is willing to wait for an operation.

Without timeouts:

```text
Request
 |
 v
Server never responds
 |
 v
Client waits...
 |
 v
waits...
 |
 v
waits...
```

Automation can hang indefinitely or much longer than intended.

---

# 141. Why Timeouts Matter in Automation

Imagine a CI/CD pipeline calling ten APIs.

If one request hangs indefinitely:

```text
Pipeline
 |
 v
API request
 |
 X
Never finishes
```

the entire pipeline may stall.

Timeouts create operational boundaries.

---

# 142. Timeout Is Not the Same as HTTP 504

This distinction matters.

Your client may time out because it waited too long.

That is a client-side timeout.

A:

```text
504 Gateway Timeout
```

is an HTTP response generated by a gateway/proxy.

Conceptually:

```text
Client timeout
=
client stopped waiting

504
=
client received an HTTP response
saying a gateway timed out
```

---

# 143. Different Timeout Phases

HTTP clients may distinguish different timeout phases, such as:

```text
Connection timeout
Read timeout
```

Connection timeout:

```text
How long should I wait to establish
the connection?
```

Read timeout:

```text
How long should I wait for data
after communication begins?
```

Part 17 will show practical timeout configuration.

---

# 144. Timeout Does Not Prove the Server Did Nothing

This is critical for state-changing APIs.

Imagine:

```text
Client sends POST
      |
      v
Server creates resource
      |
      X
Response delayed
      |
      v
Client times out
```

The client knows:

```text
"I did not receive the response."
```

It does not necessarily know:

```text
"The server did not perform the operation."
```

Do not blindly retry destructive or non-idempotent operations after timeouts.

---

# 145. Network Failure vs HTTP Error

Suppose DNS fails.

You receive no HTTP status code.

Suppose connection is refused.

You receive no HTTP status code.

Suppose TLS negotiation fails.

You may receive no HTTP status code.

Compare:

```text

Connection failure
TLS failure
Client timeout

        vs

400
401
404
429
500
503
```

The first group may prevent an HTTP response entirely.

The second group means an HTTP response was received.

# 211. Idempotency Keys

Some APIs support an idempotency key for state-changing requests.

Conceptually:

```text
POST /payments-or-resources

Idempotency-Key: unique-request-123
```

If the client retries the same logical request with the same key, the server may be able to recognize it as the same operation.

Not all APIs support this.

Read the documentation.

---

# 212. Why Idempotency Keys Matter

Consider:

```text
POST create resource
      |
      v
Resource created
      |
      X
Response lost
      |
      v
Client retries
```

Without protection:

```text
Resource 1
Resource 2
```

might be created.

With properly implemented idempotency support:

```text
Same logical request
        |
        v
One resulting operation
```

may be preserved.

203. False healthy results can hide real monitoring or data failures.

204. Understand the operation, read the contract, construct the request, test it, inspect the response, classify the result, decide the appropriate action, and verify the actual outcome.
