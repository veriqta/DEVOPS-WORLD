# Part 20: Complete Networking Troubleshooting and Final Production Lab

## Bring the Entire Networking Series Together

Networking troubleshooting is not about memorizing hundreds of commands.

It is not about randomly changing:

```text
DNS
Routes
Firewalls
Security groups
NAT
Application settings
```

until the problem disappears.

Professional troubleshooting is a process of turning a vague symptom into a precise technical failure.

A user may report:

```text
"The application is down."
```

Your job is to transform that statement into questions such as:

```text
What exact client is affected?

What exact destination is it trying to reach?

Which hostname?

Which IP address?

Which protocol?

Which port?

What path should the traffic take?

What actually happens?

How far does communication get?

What should happen next?

What evidence proves where it stops?
```

Throughout this series, you have learned individual networking components.

You learned:

```text
Ethernet
MAC addresses
ARP
IPv4
Subnetting
Routing
TCP
UDP
DNS
DHCP
NAT
HTTP
TLS
Firewalls
Linux networking
Packet capture
Load balancers
Cloud networking
Containers
Kubernetes
IPv6
```

Part 20 connects all of them.

The central principle of this final part is:

> **Do not troubleshoot the entire network at once. Follow one specific communication flow and identify the first point where expected behavior stops.**

---

# 1. The Networking Troubleshooting Mindset

Suppose the architecture is:

```text
User
 |
 v
DNS
 |
 v
Internet
 |
 v
Firewall
 |
 v
Load Balancer
 |
 v
Application
 |
 v
Database
```

A checkout request fails.

There could be problems involving:

```text
DNS
Client routing
Internet routing
Firewall policy
Load balancer
TLS
HTTP routing
Application listener
Application process
Database DNS
Database routing
Database firewall
Database listener
Authentication
Application logic
```

If you begin changing random components, you can easily create a second problem before understanding the first.

Instead:

```text
Observe
   |
   v
Form hypothesis
   |
   v
Test
   |
   v
Collect evidence
   |
   v
Narrow failure domain
   |
   v
Identify root cause
   |
   v
Apply smallest justified fix
   |
   v
Verify
```

---

# 2. Troubleshooting Is Evidence-Driven

Weak troubleshooting:

```text
"The network is probably down."

"Let's restart the server."

"Open the firewall."

"Flush DNS."

"Restart Kubernetes."

"Increase the timeout."
```

Strong troubleshooting:

```text
DNS resolves api.example.com to 10.20.2.30.

The client selects eth0 and gateway 10.20.1.1.

TCP SYN leaves the client.

The server receives the SYN.

The server sends RST because nothing is listening on TCP 8080.

Therefore routing and firewall transport delivery are functioning.

The immediate failure is the missing backend listener.
```

Notice the difference.

The second explanation tells you:

```text
What happened
Where it happened
What evidence proves it
What did not fail
```

That is the standard you should aim for.

---

# 3. Start With the Symptom

Never start troubleshooting with:

```text
"Networking problem."
```

That is too broad.

Instead, record the exact symptom.

Examples:

```text
SSH to 10.20.1.50:22 times out.

api.example.com does not resolve.

curl to https://shop.example.com returns 502.

App-01 cannot reach DB-01 on TCP 5432.

Only Pods on Node-B cannot reach the payments Service.

IPv4 works but IPv6 fails.

Only large HTTPS downloads stall.
```

Each symptom points toward a different investigation.

---

# 4. Convert User Language Into Technical Language

User says:

```text
"The website isn't working."
```

Translate it.

Ask:

```text
Does DNS resolve?

Does TCP 443 connect?

Does TLS complete?

What HTTP status is returned?

Does every page fail?

Does one path fail?

Does every user fail?

Does IPv4 fail?

Does IPv6 fail?
```

"The website isn't working" is not yet a technical diagnosis.

---

# 5. Scope the Failure

Determine:

```text
One user?
One device?
One subnet?
One office?
One availability zone?
One server?
One container?
One Kubernetes node?
One application version?
Everyone?
```

Scope provides powerful clues.

For example:

```text
Only one laptop fails
```

suggests a different investigation from:

```text
Every customer worldwide fails
```

---

# 6. Identify Source and Destination

Every network investigation should establish a flow.

Write:

```text
Source:
Destination:
Protocol:
Destination port:
```

Example:

```text
Source:
App-01
10.20.11.25

Destination:
DB-01
10.20.21.50

Protocol:
TCP

Port:
5432
```

Now you are troubleshooting something concrete.

---

# 7. Hostnames Are Not Destinations Until Resolved

If the application connects to:

```text
db.internal.example
```

record both:

```text
Hostname:
db.internal.example

Resolved IP:
10.20.21.50
```

A DNS problem and a routing problem are different failures.

Do not blur them together.

---

# 8. Determine Expected Communication

Ask:

```text
Should these systems communicate at all?

Which direction?

Which protocol?

Which port?

Through which device?

Which firewall rule should permit it?

Which route should carry it?
```

Example:

```text
Frontend
   |
   | TCP 443
   v
API
```

not:

```text
Frontend
   |
   | everything
   v
API
```

Troubleshooting is easier when the intended architecture is known.

---

# 9. Draw the Expected Packet Path

Even a rough diagram helps.

```text
Client
10.20.1.25
   |
   v
Gateway
10.20.1.1
   |
   v
Firewall
   |
   v
Load Balancer
10.20.10.10
   |
   v
App
10.20.20.20:8080
```

For each boundary ask:

```text
Should the packet reach here?

What address does this component see?

What route does it use next?

What security policy applies?
```

---

# 10. Troubleshoot From Known Good Toward Failure

Suppose:

```text
Client -> Load Balancer = works
Load Balancer -> App = fails
```

Then you have already eliminated large parts of:

```text
Client DNS
Client Internet connectivity
Frontend TLS
Frontend firewall
```

Do not continue changing them.

Focus where evidence points.

A useful order is:

```text
Physical/interface
      |
      v
IP configuration
      |
      v
Subnet/local-link logic
      |
      v
Neighbor discovery
      |
      v
Routing
      |
      v
DNS
      |
      v
Transport
      |
      v
Firewall/NAT
      |
      v
TLS
      |
      v
HTTP/application
      |
      v

```

This is not a rigid rule.

Sometimes the symptom immediately points to a higher layer.

But it gives you a disciplined structure.

# Check Physical and Interface State

# 12. Is the Interface Up?

Linux:

```bash
ip link
```

or:

```bash
ip link show
```

Look for the relevant interface.

Example:

```text
2: ens5: <BROADCAST,MULTICAST,UP,LOWER_UP>
```

If the interface is down, higher-layer troubleshooting is premature.

---

# 13. Interface Down Means Everything Above It Can Fail

If:

```text
ens5 DOWN
```

you may observe:

```text
No DHCP
No ARP
No routing through interface
No DNS connectivity
No TCP
No HTTP
```

One Layer 1/2 failure can create many higher-level symptoms.

---

# 14. Check Ethernet Link Information

Where applicable:

```bash
sudo ethtool eth0
```

or:

```bash
sudo ethtool ens5
```

You may inspect:

```text
Link detected
Speed
Duplex
Autonegotiation
```

Example:

```text
Link detected: yes
Speed: 1000Mb/s
Duplex: Full
```

---

# 15. Slow Network May Be a Link Problem

Suppose an interface unexpectedly negotiates:

```text
100 Mb/s
```

instead of:

```text
1 Gb/s
```

or has duplex problems.

Applications may appear:

```text
Slow
Intermittent
Lossy
```

Do not assume every performance issue is an application problem.

---

# Check Local Configuration

# 16. Inspect All Addresses

```bash
ip addr
```

Ask:

```text
Is expected interface present?

Does it have expected IPv4?

Does it have IPv6?

Correct prefix?

Unexpected addresses?

Duplicate-looking configuration?
```

---

# 17. Check Only One Interface

```bash
ip addr show dev eth0
```

or:

```bash
ip addr show dev ens5
```

This reduces noise.

---

# 18. IP Addressing Checklist

Verify:

```text
Correct address
Correct prefix length
Correct interface
Correct address family
No unintended link-local-only state
No stale configuration
```

Example expected:

```text
10.20.1.25/24
```

but actual:

```text
10.20.1.25/16
```

That prefix error can dramatically change local/remote routing decisions.

---

# Check Subnetting

# 19. Determine Whether Destination Is Local or Remote

Source:

```text
10.20.1.25/24
```

Destination:

```text
10.20.1.50
```

Same `/24`.

Source considers destination local.

It will try direct Layer 2 resolution.

---

# 20. Remote Example

Source:

```text
10.20.1.25/24
```

Destination:

```text
10.20.2.50
```

Different subnet.

Traffic needs routing.

Likely:

```text
Client
   |
   v
Default Gateway
   |
   v
10.20.2.50
```

---

# 21. Wrong Subnet Mask Can Break Communication

Suppose:

```text
Host A:
10.20.1.25/16

Host B:
10.20.2.50/24
```

Host A thinks:

```text
10.20.2.50 is local.
```

Host B may think:

```text
10.20.1.25 is remote.
```

This creates inconsistent assumptions.

Host A might ARP directly for Host B instead of sending to the router.

---

# 22. Subnet Problems Can Look Like Routing Problems

Symptoms may include:

```text
Some local addresses work
Others fail
Gateway appears correct
ARP requests occur unexpectedly
Asymmetric communication
```

Always verify prefixes.

---

# Check ARP and Neighbors

# 23. IPv4 Neighbor Table

```bash
ip neigh
```

Example:

```text
10.20.1.1 dev eth0 lladdr aa:bb:cc:dd:ee:ff REACHABLE
```

This tells you the kernel has neighbor information for the gateway.

---

# 24. ARP Failure

Suppose:

```text
10.20.1.1 dev eth0 FAILED
```

Capture:

```bash
sudo tcpdump -nn -i eth0 arp
```

You see:

```text
Who has 10.20.1.1?
Who has 10.20.1.1?
Who has 10.20.1.1?
```

No reply.

The failure is local-link neighbor resolution.

Do not troubleshoot remote HTTPS yet.

---

# 25. Possible ARP Failure Causes

Investigate:

```text
Wrong VLAN
Wrong subnet
Gateway offline
Switching problem
Incorrect gateway
Interface issue
Layer 2 isolation
```

---

# 26. IPv6 Neighbor Table

```bash
ip -6 neigh
```

IPv6 uses Neighbor Discovery rather than ARP.

The same troubleshooting principle applies:

> Can the host resolve/reach its local next hop?

---

# Check Routing

# 27. Inspect the Routing Table

```bash
ip route
```

For IPv6:

```bash
ip -6 route
```

Ask:

```text
Is destination directly connected?

Is a specific route present?

Is there a default route?

Which interface?

Which next hop?
```

# 28. Use `ip route get`

One of the most valuable Linux commands:

```bash
ip route get 10.20.2.50
```

Example:

```text
10.20.2.50 via 10.20.1.1 dev eth0 src 10.20.1.25
```

This tells you what Linux actually intends to do.

---

# 29. IPv6 Route Selection

```bash
ip -6 route get 2001:db8:20::50
```

Again, inspect:

```text
Gateway
Interface
Selected source
```

---

# 30. Wrong Default Gateway

Expected:

```text
default via 10.20.1.1
```

Actual:

```text
default via 10.20.1.254
```

Possible symptoms:

```text
Local subnet works
Remote networks fail
Internet fails
DNS may fail if resolver is remote
```

---

# 31. Missing Default Route

Local communication can work:

```text
10.20.1.25 -> 10.20.1.50
```

while:

```text
10.20.1.25 -> 8.8.8.8
```

fails.

Check:

```bash
ip route show default
```

---

# 32. Longest Prefix Match

Suppose:

```text
10.0.0.0/8 -> Gateway A
10.20.0.0/16 -> Gateway B
0.0.0.0/0 -> Gateway C
```

Destination:

```text
10.20.5.10
```

The `/16` route wins.

Do not assume the default route is used merely because it exists.

---

# 33. Return Route Matters

Forward path:

```text
Client -> Server
```

works only if the response can return.

Ask:

```text
What route does the server use back to the client?
```

On Linux:

```bash
ip route get <client-ip>
```

A missing return route can cause:

```text
Timeouts
Asymmetric paths
Stateful firewall failures
```

# Check DNS

# 34. DNS Is a Separate Layer

If:

```bash
ping 10.20.1.50
```

works but:

```bash
ping server.example.com
```

fails with:

```text
Name or service not known
```

you likely have a name-resolution issue rather than basic IP reachability.

---

# 35. Inspect DNS Configuration

Linux:

```bash
cat /etc/resolv.conf
```

But remember it may be dynamically managed.

Also consider:

```text
NetworkManager
systemd-resolved
VPN configuration
Containers
Kubernetes DNS
```

---

# 36. Query DNS Directly

```bash
dig example.com
```

IPv4:

```bash
dig A example.com
```

IPv6:

```bash
dig AAAA example.com
```

Short:

```bash
dig +short example.com
```

---

# 37. Query a Specific Resolver

```bash

```

This helps compare:

```text
Configured resolver
Corporate resolver
Cloud resolver
Public resolver
```

---

# 38. `nslookup`

```bash
nslookup example.com
```

Still common in many environments.

---

# 39. `host`

```bash
host example.com
```

Useful for quick resolution checks.

---

# 40. System Resolver vs Direct DNS

Remember:

```bash
dig example.com
```

and:

```bash
getent hosts example.com
```

can produce different results.

Why?

The system resolver can consider:

```text
/etc/hosts
DNS
NSS configuration
Other configured name services
```

---

# 41. DNS Name Does Not Resolve

Possible symptoms:

```text
NXDOMAIN
SERVFAIL
Timeout
Could not resolve host
```

These mean different things.

---

# 42. NXDOMAIN

The resolver responded that the name does not exist in that DNS view.

Investigate:

```text
Spelling
Missing record
Wrong private/public DNS zone
Wrong resolver
Search domain
```

---

# 43. SERVFAIL

The resolver attempted resolution but could not successfully complete it.

Possible causes:

```text
Upstream failure
Authoritative failure
DNSSEC issue
Resolver misconfiguration
```

---

# 44. DNS Timeout

No acceptable response arrived in time.

Possible causes:

```text
Resolver unreachable
Firewall blocks DNS
Routing
Resolver down
Return path
```

---

# 45. DNS Resolves to Wrong Address

Suppose:

```text
api.example.com
```

should return:

```text
10.20.2.50
```

but returns:

```text
10.20.3.50
```

The network may be functioning correctly.

The application is simply being directed to the wrong destination.

---

# 46. Server Reachable by IP but Not Hostname

This is one of the strongest DNS clues.

Example:

```bash
curl http://10.20.2.50:8080
```

works.

But:

```bash
curl http://api.internal.example:8080
```

fails to resolve.

Focus on:

```text
DNS
/etc/hosts
Resolver selection
Private DNS
Search domains
```

not routing.

---

# Check Ports and Listening Services

# 47. IP Reachability Does Not Prove Application Reachability

Suppose:

```bash
ping 10.20.2.50
```

works.

But:

```bash
curl http://10.20.2.50:8080
```

fails.

Ping proves something about ICMP reachability.

It does not prove:

```text
TCP 8080 listening
Firewall allows TCP 8080
Application healthy
```

---

# 48. Inspect Listeners

```bash
sudo ss -lntp
```

For UDP:

```bash
sudo ss -lunp
```

Combined:

```bash
sudo ss -lntup
```

---

# 49. Listener Binding Matters

Compare:

```text
127.0.0.1:8080
```

with:

```text
0.0.0.0:8080
```

and:

```text
10.20.2.50:8080
```

A process bound only to loopback cannot normally accept remote traffic.

---

# 50. IPv6 Listener

You may see:

```text
[::]:443
```

or:

```text
[::1]:8080
```

The second is IPv6 loopback only.

Again, remote reachability requires appropriate binding.

# Test TCP and UDP

# 51. Test TCP Port

```bash
nc -vz 10.20.2.50 443
```

or:

```bash
nc -vz api.example.com 443
```

This tests TCP connection establishment.

It does not prove:

```text
TLS validity
HTTP health
Authentication
Application logic
```

---

# 52. UDP Testing Is Different

UDP has no TCP three-way handshake.

Therefore success/failure interpretation with simple tools is less definitive.

Use protocol-specific testing and packet capture where necessary.

---

# 53. TCP Handshake

Expected:

```text
Client                     Server

SYN ---------------------->

    <--------------- SYN-ACK

ACK ---------------------->

Established
```

This simple sequence tells you a great deal.

---

# 54. TCP Timeout Pattern

Capture:

```text
SYN
SYN
SYN
```

No response.

Possible causes:

```text
Firewall drop
Routing issue
Host down
Wrong IP
Return path failure
Packet loss
```

Not enough evidence yet to identify which.

---

# 55. TCP Refused Pattern

Capture:

```text
SYN
RST
```

Something actively responded.

Common possibilities:

```text
No listener
Active rejection
Wrong port
Service stopped
```

---

# 56. TCP Established but Application Fails

If:

```text
SYN
SYN-ACK
ACK
```

completes, stop troubleshooting basic TCP establishment.

Move upward:

```text
TLS
HTTP
Authentication
Application
Dependencies
```

# Firewalls

# 57. Firewall Troubleshooting Questions

Ask:

```text
Which firewall?

Where?

Inbound or outbound?

Stateful or stateless?

What source does it actually see?

What destination?

Protocol?

Port?

Rule order?

Default policy?
```

---

# 58. Host Firewall

Inspect according to system.

nftables:

```bash
sudo nft list ruleset
```

UFW:

```bash
sudo ufw status verbose
```

Legacy iptables view:

```bash
sudo iptables -L -n -v
```

Do not flush or disable production firewalls blindly.

---

# 59. Cloud Firewalls

Cloud traffic may pass through:

```text
Security groups
NSGs
Network ACLs
Cloud firewalls
Load-balancer policies
Kubernetes NetworkPolicies
```

One allow rule does not prove all other controls allow the flow.

---

# 60. Source Address Matters

Suppose backend firewall allows:

```text
10.20.1.0/24
```

but actual source after proxy/NAT is:

```text
10.20.5.10
```

The intended traffic is blocked.

Always ask:

> What source address does this firewall actually see?

---

# 61. Stateful vs Stateless

Stateful firewall:

```text
Tracks connection state
```

Stateless ACL:

```text
Evaluates packets independently
```

With stateless rules, return traffic must be explicitly considered.

Ephemeral ports matter.

# NAT

# 62. NAT Troubleshooting Questions

Ask:

```text
Where does translation happen?

Which address is translated?

Source or destination?

Which port?

What does the external service see?

Is translation state created?

Can return traffic find the same state/path?
```

```text

      |
      v
NAT

      |
      v

```

External server sees:

```text
203.0.113.20
```

not:

```text

```

---

# 64. NAT Misconfiguration

Possible failures:

```text
Missing NAT route
Wrong NAT gateway
No public egress
Port exhaustion
Translation rule mismatch
Asymmetric return path
```

---

# 65. NAT Is Not Firewall and Not Routing

Keep these concepts separate.

```text
Routing:
Where does the packet go?

Firewall:
Is it allowed?

NAT:
How are addresses/ports translated?
```

# 68. HTTP 502

Usually think:

```text
Gateway/proxy had a problem communicating successfully with upstream.
```

Investigate:

```text
Wrong port
Wrong protocol
Reset
No backend listener
Backend TLS failure
Invalid upstream response
```

---

# 69. HTTP 503

Often points toward:

```text
No healthy backends
Overload
Service unavailable
Maintenance
```

depending on the component generating it.

Always identify the response source.

---

# 70. HTTP 504

Think:

```text
Gateway waited for upstream and timed out.
```

Possible root causes:

```text

Slow database
Packet loss
Network timeout
External dependency
Timeout mismatch
```

Do not immediately increase the timeout.

```text
Certificate
Chain
Hostname context
TLS version
Verification
```

```text

Hostname mismatch
```

Use packet capture when you need to answer:

# 80. Basic tcpdump

```bash
sudo tcpdump -nn -i any
```

Better when possible:

```bash
sudo tcpdump -nn -i eth0 \

```

# 81. Capture Both Ends

A powerful method:

```text
Client capture
+
Server capture
```

Client:

```text
SYN leaves
```

Server:

```text
No SYN arrives
```

Now the failure is between those points.

---

# 82. Server Sees SYN and Sends SYN-ACK

Server capture:

```text
SYN
SYN-ACK
```

Client:

```text
SYN
No SYN-ACK
```

Investigate the return path.

---

# 83. Wireshark

Use Wireshark to analyze:

```text

Set security group to all traffic
```

just to see whether it works.

That can create a security incident.

---

# 344. Never Change Remote Routes Casually

A bad route can terminate your SSH connection.

Before modifying:

```text
Default route
Management route
VPN path
Cloud route table
```

know how you will recover.

---

# 345. Never Restart Before Capturing Evidence When Evidence Matters

Restarting can erase:

```text
Connection state
Logs
Counters
Failure conditions
Memory state
```

Sometimes restart is appropriate.

But do not use it as a substitute for diagnosis.

---

# 346. Do Not Trust Error Messages as Complete Diagnoses

Examples:

```text
No route to host
Connection timeout
502
503
504
```

are clues.

They do not tell the entire root cause.

# 347. Never Assume One Successful Layer Proves the Next

Examples:

```text
DNS works
!= TCP works

TCP works
!= TLS works

TLS works
!= HTTP works

HTTP 200 /health
!= checkout works

Pod Running
!= Service reachable

Container Up
!= published port correct
```

# 348. Always Ask About Return Traffic

Every successful request-response flow needs a return path.

Especially with:

```text
Routing
VPNs
NAT
Stateful firewalls
Stateless ACLs
Load balancers
Multi-homed systems
```

# 349. Use Comparison as a Troubleshooting Tool

Compare:

```text
Working host vs failing host

Working subnet vs failing subnet

App-01 vs App-02

Node-A vs Node-B

IPv4 vs IPv6

Pod IP vs ClusterIP

Internal vs external request

Before vs after deployment
```

Differences often reveal the root cause faster than inspecting one failing system in isolation.

# 350. Use the Narrowest Test Possible

Instead of:

```text
"The website fails."
```

test:

```text

```

Narrow tests reveal which layer is responsible.

# 351. Build a Hypothesis

```text

DB firewall blocks App-02.
```

Prediction:

```text

```

Test.

If evidence matches, confidence increases.

This is far better than random configuration changes.
