# 1. Start With the Problem

Imagine you have built a web application.

It runs on one EC2 instance:

```text
Internet
   |
   v
EC2
```

The EC2 instance has:

```text
Public IP:
203.0.113.10
```

Your application listens on:

```text
TCP 8080
```

Users connect directly to the server.

Initially, everything works.

Then your application becomes popular.

You now have:

```text
10 users
100 users
1,000 users
10,000 users
```

Eventually the server becomes overloaded.

You have another problem.

What happens if the EC2 instance fails?

```text
Internet
   |
   v
EC2
   X
 FAILED
```

Your entire application becomes unavailable.

You have created a single point of failure.

---

# 2. Scaling Beyond One Server

One solution is to add more application servers.

Instead of:

```text
App Server A
```

you create:

```text
App Server A
App Server B
App Server C
```

But this creates a new problem.

Which server should users connect to?

Should you tell some users:

```text
Connect to Server A
```

and others:

```text
Connect to Server B
```

No.

Users should not need to understand your backend architecture.

They should access one application endpoint.

For example:

```text
https://app.example.com
```

Something needs to receive those requests and distribute them across the available servers.

That component is a:

```text
Load Balancer
```

---

# 3. What Is a Load Balancer?

A load balancer sits between clients and backend systems.

Conceptually:

```text
                 Client Requests
                       |
                       v
                 Load Balancer
                  /    |    \
                 /     |     \
                v      v      v
             Server A Server B Server C
```

Instead of users connecting directly to individual servers, they connect to the load balancer.

The load balancer decides which backend target should receive each request.

---

# 4. What Problem Does a Load Balancer Solve?

Load balancers help solve several problems.

## Traffic distribution

Traffic can be distributed among multiple servers.

## Availability

If one server fails, traffic can be sent to healthy servers.

## Scaling

Additional servers can be added without changing the public application endpoint.

## Health awareness

The load balancer can continuously test whether backend servers are functioning.

## Centralized public entry point

Backend application servers can remain private.

## TLS termination

HTTPS certificates can be managed at the load balancer.

## Advanced routing

Different requests can be routed to different applications or services.

For example:

```text
/api/*
```

could go to API servers.

While:

```text
/images/*
```

could go to another application.

---

# 5. Load Balancing Is Not the Same as Auto Scaling

Beginners frequently confuse these concepts.

Load balancing answers:

```text
Where should this request go?
```

Auto Scaling answers:

```text
How many application instances should exist?
```

They often work together:

```text
                  Internet
                     |
                     v
                     ALB
                /     |     \
               v      v      v
             EC2    EC2    EC2
                \     |     /
                     ASG
```

The ALB distributes requests.

The Auto Scaling Group manages the number of EC2 instances.

Part 12 will study Auto Scaling.

---

# 6. Vertical Scaling vs Horizontal Scaling

Suppose one EC2 instance cannot handle your workload.

You have two broad approaches.

## Vertical scaling

Make the existing server larger.

Example:

```text
Small EC2
   |
   v
Larger EC2
```

You increase:

* CPU
* Memory
* Instance size

This is called scaling vertically.

## Horizontal scaling

Add more servers.

```text
Server A
Server B
Server C
Server D
```

This is called scaling horizontally.

Load balancers are particularly important for horizontal scaling because traffic must be distributed among those servers.

---

# 7. What Is Elastic Load Balancing?

Elastic Load Balancing, commonly abbreviated ELB, is AWS's managed load-balancing service.

ELB can distribute incoming traffic across targets such as:

* EC2 instances
* Containers
* IP addresses
* Lambda functions in supported ALB configurations

It monitors target health and can route traffic to healthy targets.

AWS manages the underlying load-balancer infrastructure.

---

# 8. ELB Is the Service, ALB Is a Load Balancer Type

This naming causes confusion.

Think:

```text
Elastic Load Balancing
        |
        +-- Application Load Balancer
        |
        +-- Network Load Balancer
        |
        +-- Gateway Load Balancer
        |
        +-- Classic Load Balancer
```

ELB is the overall AWS service.

ALB is one type of load balancer provided by ELB.

---

# 9. Main Modern AWS Load Balancer Types

The three types beginners should understand first are:

```text
ALB
NLB
GWLB
```

They solve different problems.

---

# 10. Application Load Balancer

ALB means:

```text
Application Load Balancer
```

It operates primarily at:

```text
OSI Layer 7
Application Layer
```

It understands application-level protocols and request information.

For example:

```text
HTTP
HTTPS
```

Because ALB understands HTTP requests, it can make routing decisions based on things such as:

```text
Hostname
URL path
HTTP headers
HTTP methods
Query strings
Source IP
```

This makes ALB particularly useful for:

* Websites
* Web applications
* REST APIs
* Microservices
* Containerized HTTP applications

---

# 11. Network Load Balancer

NLB means:

```text
Network Load Balancer
```

It operates primarily at:

```text
OSI Layer 4
Transport Layer
```

It is designed for network-level traffic and supports protocols such as TCP, TLS, UDP, TCP_UDP, QUIC, and TCP_QUIC depending on configuration.

NLB is useful when you need capabilities such as:

* TCP or UDP load balancing
* Very high network performance
* Static IP requirements
* Preserving client source IP in supported configurations
* Network-level services

---

# 12. Gateway Load Balancer

GWLB means:

```text
Gateway Load Balancer
```

Its purpose is different.

It is designed primarily for distributing network traffic through virtual network appliances.

Examples include:

```text
Firewalls
Intrusion detection systems
Intrusion prevention systems
Deep packet inspection appliances
```

Conceptually:

```text
Traffic
   |
   v
GWLB
   |
   +---- Firewall A
   |
   +---- Firewall B
```

Gateway Load Balancer uses GENEVE for traffic between the GWLB and its appliance targets.

---

# 13. ALB vs NLB vs GWLB

| Feature        | ALB                                                                 | NLB              | GWLB                              |
| -------------- | ------------------------------------------------------------------- | ---------------- | --------------------------------- |
| Main purpose   | Web/application traffic                                             | Network traffic  | Network appliances                |
| Main OSI layer | Layer 7                                                             | Layer 4          | Network gateway/appliance traffic |
| HTTP aware     | Yes                                                                 | Not like ALB     | No application routing focus      |
| Path routing   | Yes                                                                 | No               | No                                |
| Host routing   | Yes                                                                 | No               | No                                |
| TCP workloads  | Through supported application protocols, not general L4 replacement | Yes              | Appliance use                     |
| UDP workloads  | No                                                                  | Yes              | Appliance traffic                 |
| Typical use    | Websites, APIs, microservices                                       | TCP/UDP services | Firewalls/security appliances     |

For our application architecture, we need:

```text
Application Load Balancer
```

because we are serving a web application.


# 16. Internet-Facing vs Internal ALB

An ALB can be created with different schemes.

Two important ones are:

```text
Internet-facing
```

and:

```text
Internal
```

---

# 17. Internet-Facing ALB

An internet-facing ALB accepts requests from internet clients when networking and security rules permit them.

Example:

```text
Internet
   |
   v
Public ALB
   |
   v
Private Application
```

This is the design from Part 10.

Typical use:

```text
Public website
Public API
Public SaaS application
```

---

# 18. Internal ALB

An internal ALB is intended for private access.

Example:

```text
Private Application A
       |
       v
 Internal ALB
       |
       v
Private Service B
```

Possible uses include:

* Internal company applications
* Private APIs
* Service-to-service routing
* Internal platform services

An application does not need to be public simply because it uses a load balancer.

---

# 19. ALB Subnets

An ALB is associated with subnets in enabled Availability Zones.

For our internet-facing architecture:

```text
AZ-A                       AZ-B

Public Subnet A            Public Subnet B
       \                       /
        \                     /
         +--------ALB---------+
```

The application targets remain in private subnets:

```text
ALB
 |
 +---- Private App A
 |
 +---- Private App B
```

Do not confuse:

```text
ALB subnet
```

with:

```text
Target subnet
```

They do not need to be the same subnet.

---

# 20. What Is a Listener?

A listener is the ALB component that checks for incoming connection requests using a configured protocol and port.

Example:

```text
HTTP : 80
```

or:

```text
HTTPS : 443
```

AWS describes a listener as checking for connection requests using the protocol and port you configure. Listener rules then determine how those requests are routed.

---

# 21. Understanding Ports

Suppose the ALB has:

```text
HTTPS listener
Port 443
```

Users connect:

```text
Client
   |
   | TCP 443
   v
ALB
```

The backend application does not necessarily need to listen on 443.

It could listen on:

```text
8080
```

So the complete path could be:

```text
Client
   |
HTTPS :443
   |
   v
ALB
   |
HTTP :8080
   |
   v
EC2
```

This distinction is extremely important.

---

# 22. Listener Port vs Target Port

These are different concepts.

Listener:

```text
443
```

Target group:

```text
8080
```

Application:

```text
8080
```

Therefore:

```text
Browser
   |
443
   v
ALB
   |
8080
   v
Application
```

The public-facing port and backend application port do not have to match.

# 23. HTTP Listener

For a beginner lab, you may start with:

```text
HTTP
Port 80
```

Flow:

```text
Client
   |
HTTP 80
   |
   v
ALB
```

This is easy for testing.

But production internet applications normally should use HTTPS where appropriate.

---

# 24. HTTPS Listener

For HTTPS:

```text
HTTPS
Port 443
```

The ALB needs a certificate.

A common AWS architecture uses a certificate managed through AWS Certificate Manager.

Conceptually:

```text
Client
   |
Encrypted HTTPS
   |
   v
ALB
   |
TLS certificate
```

The ALB proves the identity associated with the certificate and establishes the encrypted connection.

---

# 25. TLS Termination

One common architecture is:

```text
Client
   |
HTTPS 443
   |
   v
ALB
   |
HTTP 8080
   |
   v
Application
```

TLS terminates at the ALB.

This means the ALB handles the client-side TLS connection.

The backend connection is then separately established between ALB and target.

---

# 26. Backend Encryption

You can also configure:

```text
Client
   |
HTTPS
   |
   v
ALB
   |
HTTPS
   |
   v
Application
```

This provides encryption on the backend connection as well.

Whether you need this depends on:

* Security requirements
* Compliance requirements
* Architecture
* Threat model
* Organizational standards

Do not assume that TLS termination automatically means all traffic behind the ALB must be HTTP.

---

# 27. HTTP-to-HTTPS Redirect

A common configuration is:

```text
HTTP :80
   |
   v
Redirect
   |
   v
HTTPS :443
```

Instead of serving the application over HTTP, the port 80 listener redirects users to HTTPS.

Conceptually:

```text
http://example.com
        |
        v
ALB :80
        |
     Redirect
        |
        v
https://example.com
        |
        v
ALB :443
```

# 28. What Is a Listener Rule?

A listener rule tells the ALB:

```text
When this condition matches,
perform this action.
```

A rule consists of concepts such as:

* Priority
* Conditions
* Actions

Every listener has a default rule.

Additional rules can be created for more advanced routing.

---

# 29. Simple Default Rule

Suppose:

```text
Listener:
HTTPS :443
```

Default rule:

```text
Forward to:
web-target-group
```

Then:

```text
Client
   |
443
   v
ALB
   |
Default rule
   |
   v
web-target-group
```

All requests handled by that listener that do not match a higher-priority rule go to the default action.

---

# 30. What Is a Target Group?

A target group is a logical group of backend destinations that can receive traffic.

Example:

```text
web-target-group
```

contains:

```text
EC2 A
EC2 B
EC2 C
```

Conceptually:

```text
ALB
 |
Listener
 |
Rule
 |
Target Group
 |
+---- EC2 A
|
+---- EC2 B
|
+---- EC2 C
```

AWS configures health checks on a per-target-group basis.

# 31. Target Group Configuration

A target group includes important settings such as:

```text

Port
Protocol version
Health check configuration
```

Example:

```text

prod-app-tg

Protocol:
HTTP

Port:
8080

Target type:
Instances
```

# 32. What Is a Registered Target?

Creating a target group does not automatically mean your application servers belong to it.

You register targets.

Example:

```text
prod-app-tg

Registered targets:

i-01abcdef
i-02abcdef
```

Those EC2 instances can now participate in traffic distribution after they satisfy the required conditions, including health checks.

---

# 33. Target Types

ALB target groups support different target types depending on the workload.

Important examples include:

```text
Instance
IP
Lambda
```

For our beginner EC2 architecture:

```text
Instance
```

is appropriate.

---

# 34. Instance Target

With target type:

```text
instance
```

you register EC2 instances.

Example:

```text
Target Group
 |
 +---- i-012345
 |
 +---- i-067890
```

The ALB routes requests toward those registered instances.

---

# 35. IP Target

With target type:

```text
ip
```

you register IP addresses.

This is useful for architectures where the target is represented by an IP rather than directly by an EC2 instance ID.

Containerized architectures frequently make use of IP-based targets.

---

# 36. Lambda Target

ALB can also invoke Lambda functions through supported Lambda target-group configurations.

Conceptually:

```text
HTTP Request
    |
    v
   ALB
    |
    v
Lambda
```

This is not required for our EC2 application lab, but you should know that ALB targets are not limited to EC2 instances.

---

# 37. Registered Does Not Mean Healthy

This is critical.

Suppose you register:

```text
EC2 A
EC2 B
```

That does not automatically mean:

```text
EC2 A = ready for traffic
EC2 B = ready for traffic
```

The load balancer needs to determine target health.

That is the purpose of:

```text
Health Checks
```

---

# 38. What Is a Health Check?

A health check is a periodic request sent by the load balancer to determine whether a target can serve traffic.

Example:

```text
ALB
 |
 | GET /health
 |
 v
EC2
```

The application might respond:

```text
HTTP 200 OK
```

The load balancer interprets that response according to its configured health-check matcher.

ALB health checks are configured on the target group.

---

# 39. Why Health Checks Matter

Imagine:

```text
EC2 A = working
EC2 B = application crashed
```

Without health awareness:

```text
ALB
 / \
A   B
    X
```

Some users could still be sent to B.

With health checks:

```text
A = healthy
B = unhealthy
```

The load balancer can stop normally routing traffic to B.

---

# 40. Health Check Components

Important health-check settings include:

* Protocol
* Port
* Path
* Interval
* Timeout
* Healthy threshold
* Unhealthy threshold
* Success response codes

A beginner should understand every one.

---

# 41. Health Check Protocol

For ALB target groups, health checks can use:

```text
HTTP
HTTPS
```

depending on configuration.

Example:

```text
Health check protocol:
HTTP
```

---

# 42. Health Check Port

Suppose the application listens on:

```text
8080
```

The health check can use:

```text
Traffic port
```

which means it checks the target using the port through which the target receives load-balanced traffic.

Example:

```text
ALB
 |
 | HTTP :8080
 v
Application
```

---

# 43. Health Check Path

The health check needs a path.

Example:

```text
/health
```

The ALB sends something conceptually like:

```http
GET /health
```

The application might respond:

```text
200 OK
```

---

# 44. Designing a Health Endpoint

A useful health endpoint could be:

```text
/health
```

For a simple application:

```text
GET /health

200 OK
```

Avoid designing health checks without thinking about what "healthy" actually means.

A process being alive does not necessarily mean the application is capable of doing useful work.

---

# 45. Health Check Interval

The interval controls approximately how often health checks occur.

Conceptually:

```text
Check
 |
wait
 |
Check
 |
wait
 |
Check
```

A shorter interval can detect changes faster, but health-check behavior should be chosen deliberately rather than simply minimizing every timer.

---

# 46. Health Check Timeout

Timeout answers:

```text
How long should the ALB wait for this health-check response?
```

If the target does not respond within the configured timeout, that check fails.

---

# 47. Healthy Threshold

Suppose:

```text
Healthy threshold = N
```

The target must achieve the required consecutive successful checks before transitioning back to healthy according to the configured health-check behavior.

This helps avoid rapidly switching state because of one successful request.

---

# 48. Unhealthy Threshold

The unhealthy threshold determines how many consecutive failed checks are required before a target is considered unhealthy.

Conceptually:

```text
Success
Success
Failure
Failure
...
```

AWS evaluates these checks according to the target group's configured thresholds.

---

# 49. Healthy vs Unhealthy Targets

A healthy target is one that satisfies the configured health checks.

An unhealthy target has failed them.

AWS exposes additional states as well, including:

```text
initial
healthy
unhealthy
unused
draining
unavailable
```

depending on target and configuration state.

---

# 50. Initial State

A newly registered target may initially show:

```text
initial
```

This means registration or initial health checking is still in progress.

Do not immediately assume something is broken.

---

# 51. Draining State

When a target is being deregistered, it may enter:

```text
draining
```

This allows existing connections or requests to be handled according to deregistration behavior while new traffic is moved away from the target.

This becomes particularly important during deployments and Auto Scaling operations.

---

# 52. Unused State

A target may show as unused when, for example:

* It is not registered correctly
* Its target group is not used by a listener rule
* Its Availability Zone is not enabled
* Its underlying instance is stopped or terminated

The target-health reason should be inspected instead of guessing.

---

# 53. Health Check Example

Suppose:

```text
Target group:
prod-app-tg

Protocol:
HTTP

Port:
8080

Health path:
/health
```

App A:

```text
GET /health
→ 200
```

App B:

```text

→ timeout
```

```text

Healthy
```

---

# 54. Common Health Check Failure: Application Not Running

Check:

```bash
sudo ss -ltnp
```

You expect:

```text
:8080
```

If nothing listens on 8080, the ALB cannot reach the application.

Fix the application.

Do not blindly change the Security Group.

---

# 55. Common Health Check Failure: Wrong Port

Target group:

```text
8080
```

Application:

```text
3000
```

Result:

```text
Unhealthy
```

The ALB is checking the wrong destination.

Verify:

```bash
sudo ss -ltnp
```

Then compare the listening port with target-group configuration.

---

# 56. Common Health Check Failure: Wrong Path

Configured:

```text
/health
```

Application only provides:

```text
/
```

Testing:

```bash
curl http://localhost:8080/health
```

might return:

```text
404 Not Found
```

while:

```bash
curl http://localhost:8080/
```

returns:

```text
200 OK
```

The network works.

The health-check path is wrong.

---

# 57. Common Health Check Failure: Security Group

Suppose:

```text
ALB SG:
prod-alb-sg
```

App SG should allow:

```text
TCP 8080
Source:
prod-alb-sg
```

If that rule is missing, the ALB cannot reach the application on the target port.

---

# 58. Common Health Check Failure: Localhost Binding

Application:

```text
127.0.0.1:8080
```

This means only the local machine can access it through loopback.

Test:

```bash
curl http://localhost:8080
```

works.

But ALB health checks fail.

Check:

```bash
sudo ss -ltnp
```

You may need the application to listen appropriately, for example:

```text
0.0.0.0:8080
```

depending on the application and security design.

---

# 59. Common Health Check Failure: OS Firewall

Even when AWS Security Groups are correct, the operating system may have its own firewall.

Examples:

```text
ufw
firewalld
nftables
iptables
```

A host firewall can block the target port.

Never assume Security Groups are the only filtering layer.

---

# 60. Common Health Check Failure: NACL

A restrictive Network ACL can block:

* ALB-to-target traffic
* Return traffic
* Ephemeral-port traffic

Because NACLs are stateless, both directions must be considered.

---

# 61. Host-Based Routing

One of ALB's powerful Layer 7 features is host-based routing.

Suppose you own:

```text
api.example.com
admin.example.com
shop.example.com
```

You can configure:

```text
api.example.com
      |
      v
API Target Group
```

```text
admin.example.com
      |
      v
Admin Target Group
```

```text
shop.example.com
      |
      v
Shop Target Group
```

All can use the same ALB.

---

# 62. Host-Based Routing Flow

```text
                      ALB
                       |
          +------------+------------+
          |            |            |
          v            v            v
 api.example.com admin.example.com shop.example.com
          |            |            |
          v            v            v
       API TG        Admin TG      Shop TG
```

The ALB inspects the host information in the HTTP request and applies the appropriate listener rule.

---

# 63. Example Host Rules

Listener:

```text
HTTPS :443
```

Rule:

```text
IF
Host = api.example.com

THEN
Forward → api-tg
```

Another:

```text
IF
Host = admin.example.com

THEN
Forward → admin-tg
```

Default:

```text
Forward → web-tg
```

---

# 64. Path-Based Routing

ALB can also route based on URL paths.

Example:

```text
example.com/
```

goes to:

```text
Frontend Target Group
```

While:

```text
example.com/api/*
```

goes to:

```text
API Target Group
```

And:

```text
example.com/admin/*
```

goes to:

```text
Admin Target Group
```

---

# 65. Path Routing Architecture

```text
                     example.com
                          |
                          v
                         ALB
                          |
          +---------------+---------------+
          |               |               |
          v               v               v
          /             /api/*          /admin/*
          |               |               |
          v               v               v
       Web TG           API TG         Admin TG
```

One public load balancer can therefore route requests to multiple backend applications.

---

# 66. Why This Matters for Microservices

Imagine:

```text
/users/*
```

belongs to:

```text
User Service
```

and:


Conceptually:

```text
Priority 20

Default
```

The default rule catches traffic that does not match earlier applicable rules.

You must design rules carefully to avoid unexpected routing.

# 79. Cross-Zone Load Balancing Concept

Suppose:

```text
AZ-A
ALB node
EC2 A
```

and:

```text
AZ-B
ALB node
EC2 B
EC2 C
```

Without cross-zone behavior, a load-balancer node may primarily distribute traffic among targets associated with its own zone.

With cross-zone load balancing, traffic received by a load-balancer node can be distributed across healthy targets in enabled Availability Zones according to the service's cross-zone behavior.

For Application Load Balancers, cross-zone load balancing is an important part of understanding how targets across enabled zones participate in request distribution.

---

# 80. Why Cross-Zone Concepts Matter

Imagine:

```text
AZ-A:
1 target

AZ-B:
4 targets
```

Traffic arriving through different load-balancer nodes does not necessarily correspond neatly to the number of targets in each zone.

Cross-zone behavior affects how load is distributed across those backend targets.

You should therefore understand both:

```text
Load balancer Availability Zones
```

and:

```text
Target placement
```

when analyzing traffic distribution.

---

# 81. Balanced Target Placement Still Matters

Even when cross-zone load balancing helps distribute requests, you should still design workloads across multiple Availability Zones.

Prefer:

```text
AZ-A:
App A
App B

AZ-B:
App C
App D
```

over:

```text
AZ-A:
App A
App B
App C
App D

AZ-B:
App E
```

when your availability requirements call for balanced zonal capacity.

Cross-zone routing does not eliminate the need for good capacity planning.

# 82. What Happens When a Target Becomes Unhealthy?

Suppose:

```text
App A = healthy
App B = unhealthy
```

The ALB normally sends application traffic to:

```text
App A
```

rather than the unhealthy App B.

When App B passes the required successful health checks again, it can return to service.

---

# 83. Important Edge Case: All Targets Unhealthy

Do not assume:

```text
All unhealthy = ALB always sends traffic nowhere.
```

AWS documents fail-open behavior for ALB target groups if all registered targets are unhealthy across enabled Availability Zones. In that situation, requests may be routed to targets regardless of health status.

This is an important production detail.

Health checks are not a substitute for monitoring the application itself.

---

# 84. ALB Is Not Application Monitoring

A health check answers a narrow question:

```text
Can this target satisfy this configured health check?
```

It does not automatically answer:

```text
Are users happy?
```

or:

```text
Is every dependency working correctly?
```

or:

```text
Is application latency acceptable?
```

You still need monitoring.

Later, CloudWatch will help with that.

# 86. HTTP 502: Bad Gateway

A 502 generally indicates that the load balancer attempted to communicate with a target but received an invalid or problematic response at the backend connection/application layer.

AWS documents possible ALB 502 causes including:

* Target TCP resets
* Unexpected target/network responses
* Target closing connections unexpectedly
* Malformed HTTP responses
* Invalid response headers
* Oversized response headers
* Deregistration timing issues
* Backend SSL handshake errors
* Certain Lambda target errors

---

# 87. 502 Troubleshooting Model

Start with:

```text
Client
   |
   v
ALB
   |
   X
Target
```

Ask:

```text
Can the ALB establish a valid connection to the target?
```

Then investigate:

1. Is the application running?
2. Is it listening on the correct port?
3. Is the target-group port correct?
4. Does the Security Group allow ALB traffic?
5. Does the application produce valid HTTP responses?
6. Is the connection being reset?
7. Are backend TLS settings correct?
8. Are application logs showing crashes or malformed responses?

# 92. HTTP 503: Service Unavailable

A 503 means something different.

For ALB-generated 503 responses, AWS documents conditions including target groups with no registered targets or targets that are not usable for routing in relevant configurations.

A useful beginner mental model is:

```text
502:
The ALB reached toward the backend,
but backend communication failed.

503:
The ALB does not have a usable service target
for the request.
```

This is simplified, but useful for initial troubleshooting.

---

# 93. Troubleshooting 503

Check:

```text
Target group exists?
```

Then:

```text
Targets registered?
```

Then:

```text
Target group attached to listener rule?
```

Then:

```text
Targets in usable state?
```

Then:

```text
Correct Availability Zones enabled?
```

Then inspect target-health reason codes.

# 94. HTTP 504: Gateway Timeout

Although the curriculum specifically highlights 502 and 503, you should understand 504 too.

A 504 commonly indicates that the ALB could not establish or complete backend communication within required timing limits.

AWS lists possible causes including connection timeouts, target response timeouts, NACL return-path problems, incomplete response bodies, and backend SSL handshake timeouts.

Think:

```text
ALB
 |
 | waiting...
 |
Target
```

---

# 95. 502 vs 503 vs 504

| Error | Beginner mental model                                            |
| ----- | ---------------------------------------------------------------- |
| 502   | Backend returned or caused an invalid/broken gateway interaction |
| 503   | No usable service target for the request                         |
| 504   | Backend interaction took too long                                |

Always confirm using:

* ALB metrics
* Access logs where enabled
* Target health
* Application logs
* Network evidence

Do not rely only on the HTTP code.

```text
Health path       /health        ?
Application       same version   ?
```

When two supposedly identical systems behave differently, compare their state.

That often exposes the root cause quickly.

# 138. Troubleshooting Scenario 8: Target Goes Unhealthy During Deployment

```text
      |
```

* Deployment process
* Readiness behavior
* Deregistration timing
* Auto Scaling health configuration

A listener accepts connection requests using a configured protocol and port and applies its rules.

Yes. The frontend listener and backend target port can be different.

A listener rule defines conditions and actions that determine how matching requests are handled.

## Answer 10

A target group is a logical collection and configuration through which the ALB routes traffic to registered backend targets.

## Answer 11

A registered target is a backend destination, such as an EC2 instance, that has been added to a target group.

## Answer 12

No. The target must satisfy the applicable health-check and routing requirements.

It tests whether a registered target can respond according to configured health criteria.

The application may be bound only to loopback, or a Security Group, NACL, host firewall, or target-group configuration may prevent remote access.

It limits backend application access to traffic originating from the intended ALB tier instead of broadly exposing the application port.

Routing requests according to the requested hostname.

The ALB can normally continue routing application traffic to healthy targets.

Auto Scaling manages how many application instances exist. The ALB distributes requests among the instances registered with its target group.

# 148. Final Mental Model

Do not memorize:

```text
ALB = AWS load balancer
```

Understand the complete system:

```text
                    CLIENT
                       |
                       v
                      DNS
                       |
                       v
                      ALB
                       |
                       v
                   LISTENER
                       |
                       v
                 LISTENER RULE
                       |
                       v
                  TARGET GROUP
                       |
                 HEALTH CHECKS
                       |
             +---------+---------+
             |                   |
             v                   v
          TARGET A            TARGET B
           Healthy             Healthy
```

When a request fails, walk the same path:

```text
Can DNS resolve?
       |
       v
Can the client reach the ALB?
       |
       v
Is the listener correct?
       |
       v
Which rule matched?
       |
       v
Which target group was selected?
       |
       v
Are targets registered?
       |
       v
Are targets healthy?
       |
       v
Can ALB reach the target port?
       |
       v
Is the application listening?
       |
       v
Does the application respond correctly?
       |
       v
Are its dependencies healthy?
```

That is the important skill.

A DevOps engineer should not respond to:

```text
The ALB is returning 502.
```

by randomly opening ports.

The engineer should ask:

```text
Which listener received the request?

Which rule matched?

Which target group received it?

Which target was selected?

What is the target health?

Can the ALB establish the backend connection?

What address and port is the application listening on?

What does the application return?

What do the ALB and application logs show?
```

Once you think this way, the Application Load Balancer stops being another AWS service to memorize.

It becomes a request-routing system that you can reason about and troubleshoot.
