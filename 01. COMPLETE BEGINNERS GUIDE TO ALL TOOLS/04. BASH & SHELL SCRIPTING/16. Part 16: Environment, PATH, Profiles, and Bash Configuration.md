# 1. What Is a Shell Environment?

When Bash runs, it does not operate in isolation.

It has information describing the context in which commands execute.

Examples include:

```text
Current user
Home directory
Current working directory
Command search path
Locale
Terminal type
Shell settings
Environment variables
```

You can inspect some common values:

```bash
printf 'User: %s\n' "$USER"
printf 'Home: %s\n' "$HOME"
printf 'Shell: %s\n' "$SHELL"
printf 'Working directory: %s\n' "$PWD"
printf 'PATH: %s\n' "$PATH"
```

Example:

```text
User: ann
Home: /home/ann
Shell: /bin/bash
Working directory: /home/ann/projects
PATH: /usr/local/bin:/usr/bin:/bin
```

The environment influences what your commands can find and how programs behave.

---

# 2. Shell Variables vs Environment Variables

You learned variables earlier in this series.

Example:

```bash
application="payments"
```

This creates a Bash variable.

But that does not automatically mean programs launched by Bash receive that variable.

This distinction gives us two important concepts:

```text
Shell variable

Environment variable
```

A shell variable belongs to the current Bash process.

An exported variable becomes part of the environment passed to child processes.

---

# 3. Creating a Normal Shell Variable

Run:

```bash
application="payments"
```

Verify:

```bash
printf '%s\n' "$application"
```

Output:

```text
payments
```

Bash knows the variable.

Now start another Bash process:

```bash
bash -c 'printf "<%s>\n" "$application"'
```

You may see:

```text
<>
```

The child Bash did not receive the ordinary shell variable.

---

# 4. Exporting a Variable

Use:

```bash
export application
```

Now:

```bash
bash -c 'printf "<%s>\n" "$application"'
```

should print:

```text
<payments>
```

The variable was exported into the environment inherited by the child process.

---

# 5. Create and Export in One Command

Instead of:

```bash
application="payments"
export application
```

you can write:

```bash
export application="payments"
```

This assigns and exports the variable.

Uppercase names are conventionally used for environment variables:

```bash
export APP_ENV="staging"
export LOG_LEVEL="INFO"
export APP_PORT="8080"
```

This is a convention rather than a Bash requirement.

---

# 6. What Does `export` Actually Mean?

Think of the current Bash process as having two related collections:

```text
Current Bash
    |
    +--> Shell variables
    |
    +--> Exported variables
             |
             v
      Passed to child processes
```

For example:

```bash
project="VERIQTA"
export APP_ENV="production"
```

Conceptually:

```text
Current Bash
--------------------------------
project=VERIQTA
APP_ENV=production

Exported environment
--------------------------------
APP_ENV=production
```

When Bash launches another process:

```text
Current Bash
    |
    | starts
    v
Child process
    |
    +--> receives APP_ENV
    |
    +--> does not automatically receive project
```

---

# 7. Parent and Child Processes

From Part 13, processes have parent-child relationships.

Suppose:

```text
Terminal
   |
   v
Bash
   |
   +--> script
   |
   +--> grep
   |
   +--> curl
   |
   +--> another Bash
```

When Bash starts a child process, exported environment variables can be inherited.

This is one reason environment variables are widely used for configuration.

---

# 8. Inheritance Is Primarily Downward

A child process can inherit exported values from its parent.

But a child cannot normally change its parent's environment.

Example:

Create:

```bash
cat > child.sh <<'EOF'
#!/usr/bin/env bash

export MESSAGE="changed by child"

printf 'Child MESSAGE: %s\n' "$MESSAGE"
EOF
```

Run:

```bash
chmod +x child.sh
export MESSAGE="parent value"

./child.sh

printf 'Parent MESSAGE: %s\n' "$MESSAGE"
```

You should see something like:

```text
Child MESSAGE: changed by child
Parent MESSAGE: parent value
```

The child changed its own environment.

It did not rewrite the parent shell's variable.

---

# 9. Why a Script Cannot Normally Change Your Current Shell

Suppose:

```text
set-env.sh
```

contains:

```bash
#!/usr/bin/env bash

export APP_ENV="production"
```

Running:

```bash
./set-env.sh
```

starts a child process.

That child exports `APP_ENV`, then exits.

Your parent shell does not receive the change.

So afterward:

```bash
printf '<%s>\n' "${APP_ENV:-}"
```

may still be empty.

---

# 10. Sourcing Changes the Current Shell

If you intentionally run:

```bash
source set-env.sh
```

or:

```bash
. set-env.sh
```

the file executes inside the current shell.

Then:

```bash
export APP_ENV="production"
```

affects your current shell.

But remember the Part 8 security lesson:

> Sourcing executes shell code.

Do not source untrusted files simply because you want their variables.

---

# 11. Environment Inheritance Diagram

```text
Login/session process
        |
        v
      Bash
        |
        +--> export APP_ENV=production
        |
        +--> ./deploy.sh
        |        |
        |        +--> receives APP_ENV
        |
        +--> curl
        |        |
        |        +--> receives APP_ENV
        |
        +--> bash
                 |
                 +--> receives APP_ENV
```

But:

```text
Child
  |
  +--> changes APP_ENV
         |
         X
         |
Parent does not receive change
```

This parent-child model explains many shell-environment problems.

env

Another is:

```bash
printenv
```

Example:

```bash

```

Possible output:

```text

```

You can also use:

```bash

```

inside Bash.

# 13. `env` vs `printenv`

Both are commonly used for inspecting environments.

Examples:

```bash
env
```

prints the environment.

```bash
printenv
```

also prints environment values.

To inspect one variable:

```bash
printenv PATH
```

# 14. Inspect Shell Variables

Bash has many variables that may not all be exported.

You can inspect shell variables with:

```bash
set
```

But `set` can produce a large amount of output, including shell functions and variables.

For one known variable:

```bash
declare -p variable_name
```

can be more focused.

Example:

```bash
declare -p APP_ENV
```

---

# 15. Check Whether a Variable Is Exported

Example:

```bash
APP_ENV="staging"

declare -p APP_ENV
```

You might see:

```text
declare -- APP_ENV="staging"
```

Now:

```bash
export APP_ENV
declare -p APP_ENV
```

may show:

```text
declare -x APP_ENV="staging"
```

The:

```text
-x
```

indicates the export attribute.

---

# 16. `export -p`

You can inspect exported variables using:

```bash
export -p
```

This can be useful when debugging environment inheritance.

Be careful when sharing output from commands that display environments.

Environment variables may contain sensitive information.

---

# 17. Removing Variables

Use:

```bash
unset APP_ENV
```

Now:

```bash
printf '<%s>\n' "${APP_ENV:-}"
```

prints:

```text
<>
```

`unset` removes the shell variable.

---

# 18. Temporary Environment Variables for One Command

Suppose you want:

```text
APP_ENV=staging
```

for only one command.

You can write:

```bash
APP_ENV="staging" ./deploy.sh
```

This does not necessarily persist `APP_ENV` in your current shell.

It supplies the value to that command's environment.

This is extremely useful.

---

# 19. Temporary Environment Example

Create:

```bash
cat > show-env.sh <<'EOF'
#!/usr/bin/env bash

printf 'APP_ENV=%s\n' "${APP_ENV:-not-set}"
EOF

chmod +x show-env.sh
```

Run:

```bash
APP_ENV="staging" ./show-env.sh
```

Expected:

```text
APP_ENV=staging
```

Then:

```bash
printf '<%s>\n' "${APP_ENV:-}"
```

may still show:

```text
<>
```

if it was not previously set in the parent shell.

---

# 20. Why This Is Useful in DevOps

You can test different configurations:

```bash
APP_ENV="development" ./deploy.sh
```

then:

```bash
APP_ENV="staging" ./deploy.sh
```

without permanently changing your current shell.

CI/CD systems also frequently inject environment variables for individual jobs or processes.

# 21. Running with a Clean Environment

The `env` command can help create controlled tests.

Example:

```bash
env -i bash --noprofile --norc
```

`-i` tells `env` to begin with an empty environment.

The additional Bash options avoid loading normal user startup files.

Your shell may still establish some Bash variables internally, but this gives you a much cleaner environment for troubleshooting.

Exit when finished:

```bash
exit
```

```text
Custom PATH

Shell function
SDK setup

```

Testing in a reduced environment can expose those hidden dependencies.

This is especially useful when preparing scripts for:

* CI/CD
* servers
* containers
* cron
* other engineers

# 23. What Is `$PATH`?

`PATH` is one of the most important environment variables on Unix-like systems.

Inspect it:

```bash
printf '%s\n' "$PATH"
```

You may see:

```text
/usr/local/bin:/usr/bin:/bin
```

`PATH` contains directories separated by:

```text
:
```

Bash uses these directories to search for commands.

---

# 24. Understanding PATH Entries

Given:

```text
/usr/local/bin:/usr/bin:/bin
```

the search order is approximately:

```text
1. /usr/local/bin
2. /usr/bin
3. /bin
```

If Bash needs to locate an external executable called:

```text
mytool
```

these directories are searched in order.

Order matters.

---

# 25. PATH Is Not a List of Commands

`PATH` contains directories.

Not command names.

Correct:

```text
/usr/local/bin
```

Incorrect concept:

```text
/usr/local/bin/curl
```

as an entry intended specifically for `curl`.

You add the directory containing executable commands.

---

# 26. How Bash Finds a Command

Suppose you type:

```bash
deployctl
```

Bash needs to determine what `deployctl` means.

Command resolution can involve more than just `PATH`.

A useful simplified model is:

```text
Command entered
      |
      v
Is it a shell keyword/reserved construct?
      |
      v
Is it an alias?       [interactive alias expansion context]
      |
      v
Is it a function?
      |
      v
Is it a Bash builtin?
      |
      v
Search command locations / PATH
      |
      v
Execute
```

The exact parsing and lookup details are more nuanced, but this model is useful for troubleshooting.

---

# 27. `type` Shows What Bash Will Use

Run:

```bash
type cd
```

You may see:

```text
cd is a shell builtin
```

Run:

```bash
type ls
```

Depending on configuration, you might see:

```text
ls is aliased to ...
```

or an executable path.

Run:

```bash
type -a ls
```

to see multiple ways the command may be resolved.

---

# 28. `command -v`

A portable and useful command lookup technique is:

```bash
command -v curl
```

Possible output:

```text
/usr/bin/curl
```

You can use it in scripts:

```bash
if ! command -v curl >/dev/null 2>&1; then
    printf 'ERROR: curl is required\n' >&2
    exit 1
fi
```

This is the dependency-check pattern introduced earlier.

---

# 29. Why `which` Is Often Not the Best Script Check

You may see:

```bash
which curl
```

used to locate commands.

For Bash scripts, prefer:

```bash
command -v curl
```

because command resolution includes shell concepts that an external `which` implementation may not represent consistently.

For interactive investigation:

```bash
type -a command_name
```

is also extremely useful.

---

# 30. Command Lookup Example

Suppose:

```bash
command -v python
```

returns:

```text
/home/ann/bin/python
```

but:

```bash
type -a python
```

shows:

```text
python is /home/ann/bin/python
python is /usr/bin/python
```

That tells you multiple executables exist.

The first matching resolution wins.

This can explain why different environments execute different software versions.

---

# 31. PATH Search Order

Suppose:

```text
/home/ann/bin:/usr/local/bin:/usr/bin:/bin
```

and both:

```text
/home/ann/bin/tool
```

and:

```text
/usr/bin/tool
```

exist.

When you type:

```bash
tool
```

the earlier PATH entry normally wins.

That means PATH order is behavior, not merely configuration.

---

# 32. Inspect PATH One Entry Per Line

Instead of:

```bash
printf '%s\n' "$PATH"
```

you can make it easier to read.

One approach:

```bash
printf '%s\n' "$PATH" | tr ':' '\n'
```

You learned `tr` in Part 11.

Example:

```text
/usr/local/bin
/usr/bin
/bin
```

This makes duplicate or suspicious entries easier to spot.

---

# 33. Adding a Directory to PATH

Suppose your custom commands are stored in:

```text
$HOME/bin
```

You could prepend it:

```bash
export PATH="$HOME/bin:$PATH"
```

Now Bash searches:

```text
$HOME/bin
```

before the existing PATH directories.

---

# 34. Append vs Prepend

Prepend:

```bash
export PATH="$HOME/bin:$PATH"
```

Search your directory first.

Append:

```bash
export PATH="$PATH:$HOME/bin"
```

Search your directory after existing entries.

This difference matters.

---

# 35. When Should You Prepend?

Prepending may be appropriate when you intentionally want your version of a tool to override system versions.

For example:

```text
Custom developer tools
Version manager shims
User-installed utilities
```

But overriding system commands unintentionally can create confusing or dangerous behavior.

---

# 36. When Should You Append?

Appending may be safer when your custom directory contains commands that do not need to override system utilities.

Example:

```bash
export PATH="$PATH:$HOME/bin"
```

Then normal system directories are searched first.

There is no universal rule.

Understand what precedence you want.

---

# 37. Avoid Destroying the Existing PATH

Wrong:

```bash
export PATH="$HOME/bin"
```

unless you intentionally want to replace the entire search path.

After this, Bash may fail to find commands such as:

```text
ls
grep
sed
awk
curl
```

because directories such as:

```text
/usr/bin
/bin
```

may no longer be present.

Usually you want:

```bash
export PATH="$HOME/bin:$PATH"
```

or:

```bash
export PATH="$PATH:$HOME/bin"
```

---

Run:

Expected:

# 40. Temporary vs Persistent PATH Changes

This:

```bash
export PATH="$HOME/bin:$PATH"
```

changes the current shell environment and future child processes.

When the shell session ends, that modification is normally lost unless a startup/configuration mechanism recreates it.

To persist it, you typically place appropriate configuration in a shell startup file.

This leads us to:

```text
.bashrc
.bash_profile
.profile
```

---

# 41. Shell Startup Files

Bash can read configuration files when it starts.

Which files it reads depends on how Bash was started.

Important questions include:

```text
Is this shell interactive?

Is this shell a login shell?

Is it non-interactive?

Was Bash invoked as sh?

Was a special startup option used?
```

This is why shell initialization can initially feel confusing.

---

# 42. What Is an Interactive Shell?

An interactive shell is generally a shell where a person interacts with the command prompt.

Example:

```text
You open terminal
      |
      v
Prompt appears
      |
      v
You type commands
      |
      v
Bash responds
```

You can test whether the current Bash shell is interactive using:

```bash
case $- in
    *i*)
        printf 'Interactive shell\n'
        ;;
    *)
        printf 'Non-interactive shell\n'
        ;;
esac
```

The special parameter:

```text
$-
```

contains current shell option flags.

The presence of:

```text
i
```

indicates interactive mode.

---

# 43. What Is a Non-Interactive Shell?

When Bash executes a script:

```bash
bash deploy.sh
```

that Bash process is normally non-interactive.

There is no person typing commands into its prompt.

Examples include many scripts launched by:

* CI/CD
* automation systems
* cron
* system services
* other programs

Non-interactive environments are one major reason your interactive shell configuration should not be assumed to exist in scripts.

---

# 44. What Is a Login Shell?

Historically, a login shell is the shell associated with logging into a system.

Today it can also be created explicitly.

Check:

```bash
shopt -q login_shell
```

Then inspect the status:

```bash
if shopt -q login_shell; then
    printf 'Login shell\n'
else
    printf 'Not a login shell\n'
fi
```

Another useful inspection:

```bash
printf 'argv0: %s\n' "$0"
```

But `shopt -q login_shell` directly asks Bash about its login-shell state.

---

# 45. Interactive and Login Are Separate Concepts

A shell can conceptually be:

```text
Interactive login shell

Interactive non-login shell

Non-interactive shell
```

Do not assume:

```text
interactive = login
```

They describe different properties.

---

# 46. Common Startup Behavior

For Bash, a useful simplified model is:

```text
Login shell
    |
    +--> /etc/profile
    |
    +--> first available of:
           ~/.bash_profile
           ~/.bash_login
           ~/.profile
```

For an interactive non-login Bash shell:

```text
Interactive non-login Bash
    |
    +--> ~/.bashrc
```

There are additional details and special cases, but this is the essential beginner model.

---

# 47. `~/.bashrc`

`.bashrc` is commonly used for configuration intended for interactive Bash sessions.

Examples:

* aliases
* prompt customization
* interactive shell functions
* completion setup
* interactive tool initialization

Typical location:

```text
/home/user/.bashrc
```

or:

```text
~/.bashrc
```

---

# 48. Why `.bashrc` Is Commonly Interactive

A typical `.bashrc` may contain:

```bash
alias ll='ls -alF'
```

or prompt configuration:

```bash
PS1='...'
```

These features are primarily useful when a human is using the shell.

A CI job does not need a colorful prompt.

A production deployment script should not depend on your personal alias definitions.

---

# 49. `.bash_profile`

`~/.bash_profile` is commonly read by Bash for an interactive login shell.

Many users configure it to load `.bashrc`.

Example:

```bash
if [[ -f "$HOME/.bashrc" ]]; then
    source "$HOME/.bashrc"
fi
```

This allows login shells to reuse interactive Bash configuration.

---

# 50. `.profile`

`~/.profile` is a more general login-profile file commonly used by Bourne-compatible shells and desktop/session environments.

Bash login-shell behavior checks login startup files in a specific order.

A key detail:

> Bash does not simply read `.bash_profile` and then `.profile`.

For an interactive login Bash, it searches for:

```text
~/.bash_profile
~/.bash_login
~/.profile
```

and reads the first readable one it finds.

Therefore, if `.bash_profile` exists, `.profile` is not automatically read afterward by Bash.

---

# 51. Why This Causes Confusion

Suppose you add:

```bash
export APP_ENV="development"
```

to:

```text
~/.profile
```

but your Bash login shell uses:

```text
~/.bash_profile
```

and `.bash_profile` does not source `.profile`.

Your variable may not appear where you expected.

The solution is not:

```text
Add the same export everywhere.
```

The solution is:

```text
Understand which startup files your shell actually reads.
```

---

# 52. A Clean Startup Strategy

One possible arrangement is:

```text
~/.profile
    |
    +--> login/session environment

~/.bash_profile
    |
    +--> Bash login-specific setup
    |
    +--> source ~/.bashrc when appropriate

~/.bashrc
    |
    +--> interactive Bash setup
```

But the correct layout depends on:

* operating system
* terminal application
* desktop environment
* remote-login behavior
* installed tooling

Do not blindly copy startup-file structures from another machine.

---

# 53. Example `.bash_profile`

A simple Bash login profile might contain:

```bash
if [[ -f "$HOME/.bashrc" ]]; then
    source "$HOME/.bashrc"
fi
```

This means:

```text
Login Bash starts
      |
      v
Reads ~/.bash_profile
      |
      v
.bash_profile sources ~/.bashrc
      |
      v
Interactive Bash configuration becomes available
```

---

# 54. Guard Interactive Configuration

If `.bashrc` might be sourced in contexts where you only want interactive features, use an interactive guard.

Example:

```bash
case $- in
    *i*)
        ;;
    *)
        return
        ;;
esac
```

Then place interactive-only configuration after it.

This prevents aliases and prompt setup from running unnecessarily in non-interactive contexts where `.bashrc` happens to be sourced.

Be careful with `return`: it is appropriate in a sourced file such as `.bashrc`, but not at arbitrary top-level locations in a normally executed script.

---

# 55. System-Wide Configuration

Shell configuration can also exist outside the user's home directory.

Common examples on Linux systems include:

```text
/etc/profile
/etc/bash.bashrc
/etc/bashrc
/etc/profile.d/
```

Exact files vary by distribution.

Do not assume every Linux distribution has identical Bash startup configuration.

---

# 56. `/etc/profile`

`/etc/profile` is commonly involved in login-shell initialization.

Administrators may use it to establish system-wide settings.

Examples might include:

* system PATH changes
* organization-wide environment setup
* scripts from `/etc/profile.d/`

But distribution behavior can vary.

Always inspect the target system rather than assuming.

---

# 57. `/etc/profile.d/`

Many Linux distributions use:

```text
/etc/profile.d/
```

for modular system-wide shell initialization scripts.

Example:

```text
/etc/profile.d/company-tools.sh
```

might configure:

```bash
export COMPANY_TOOLS="/opt/company-tools"
export PATH="$PATH:$COMPANY_TOOLS/bin"
```

This can be cleaner than placing all system configuration into one large file.

---

# 58. System Configuration Requires Caution

Changes under:

```text
/etc/
```

can affect many users.

Do not modify system-wide shell configuration simply to fix a personal PATH problem.

First determine whether the requirement is:

```text
One user
One project
One service
All users
```

Then choose the correct scope.

---

# 59. Configuration Scope

Think:

```text
Need setting for one command?
    |
    +--> VAR=value command

Need setting for one script?
    |
    +--> set it inside script / inject it

Need setting for one terminal session?
    |
    +--> export VAR=value

Need interactive Bash customization?
    |
    +--> ~/.bashrc

Need Bash login initialization?
    |
    +--> ~/.bash_profile or appropriate login file

Need broader login environment?
    |
    +--> ~/.profile where appropriate

Need all users?
    |
    +--> carefully designed system configuration
```

Choose the narrowest scope that solves the problem.

---

# 60. Aliases

An alias gives a shorter or alternative command name.

Example:

```bash
alias ll='ls -alF'
```

Then:

```bash
ll
```

expands to the configured command in an interactive shell where alias expansion is active.

Inspect:

```bash
alias
```

or:

```bash
alias ll
```

Remove:

```bash
unalias ll
```

---

# 61. Good Alias Use

Aliases are useful for interactive convenience.

Examples:

```bash
alias ll='ls -alF'
alias gs='git status'
alias k='kubectl'
```

These reduce typing for humans.

They should not become hidden dependencies in automation scripts.

---

# 62. Do Not Depend on Aliases in Scripts

Suppose your `.bashrc` contains:

```bash
alias k='kubectl'
```

Your terminal accepts:

```bash
k get pods
```

Then you put:

```bash
k get pods
```

inside:

```text
check-cluster.sh
```

The script may fail:

```text
k: command not found
```

Why?

Because your non-interactive script should not be assumed to load or expand your interactive aliases.

Use the real command:

```bash
kubectl get pods
```

Scripts should be explicit.

---

# 63. Dangerous Aliases

Some people create:

```bash
alias rm='rm -i'
```

This may make interactive deletion ask for confirmation.

But never write a script assuming:

```text
rm will always ask me first.
```

On another machine, that alias may not exist.

Automation should not depend on personal safety aliases.

Build safety into the script itself.

---

# 64. Shell Functions in Configuration

You can define functions in `.bashrc`.

Example:

```bash
mkcd() {
    mkdir -p -- "$1" &&
        cd -- "$1"
}
```

Then:

```bash
mkcd project
```

creates and enters the directory.

This is useful for interactive workflows.

---

# 65. Functions vs Aliases

Aliases work well for simple command substitutions.

Functions are better when you need:

* arguments
* conditions
* multiple commands
* local variables
* return statuses
* reusable logic

Example alias:

```bash
alias gs='git status'
```

Example function:

```bash
cproj() {
    local project="$1"

    cd -- "$HOME/projects/$project"
}
```

---

# 66. Do Not Make Scripts Depend on Personal Functions

Suppose your `.bashrc` defines:

```bash
deploy_prod() {
    ...
}
```

A script calling:

```bash
deploy_prod
```

may work interactively but fail in CI.

Why?

Because that function belongs to your interactive shell configuration.

Production automation should contain its dependencies explicitly or load controlled libraries deliberately.

---

# 67. Exporting Functions

Bash can export functions with:

```bash
export -f function_name
```

and some child Bash processes may inherit them through Bash-specific mechanisms.

However, do not use exported shell functions as the foundation of portable deployment automation.

They:

* are Bash-specific
* create hidden environmental dependencies
* may not cross execution boundaries you expect
* can complicate debugging

For reusable automation, explicit scripts or libraries are usually clearer.

---

# 68. Prompt Customization

When you see something like:

```text
ann@server:~/projects$
```

that prompt is controlled partly by:

```text
PS1
```

Inspect:

```bash
printf '%s\n' "$PS1"
```

The value may contain special Bash prompt escape sequences.

---

# 69. What Is `PS1`?

`PS1` is the primary interactive prompt string.

A simple prompt:

```bash
PS1='$ '
```

might display:

```text
$
```

Another:

```bash
PS1='\u@\h:\w\$ '
```

may display something like:

```text
ann@web01:~/projects$
```

---

# 70. Common PS1 Escape Sequences

You may encounter:

```text
\u    username

\h    hostname

\w    current working directory

\W    current directory basename

\$    $ for normal user, # for root
```

Example:

```bash
PS1='\u@\h:\w\$ '
```

This is only an introduction.

Prompt customization can become much more advanced.

---

# 71. Why the Prompt Matters Operationally

A useful prompt can remind you:

```text
Which user am I?

Which host am I on?

Which directory am I in?
```

This can reduce operational mistakes.

For example:

```text
ann@staging-web01:/srv/app$
```

contains useful context.

But do not rely on prompt appearance as a security control.

Always verify important production targets explicitly.

---

# 72. Avoid Fragile Prompt Commands

Some prompts execute commands every time the prompt appears.

For example, a sophisticated prompt may query:

* Git status
* Kubernetes context
* cloud account
* Python environment

This can be useful.

But expensive prompt commands can make the terminal slow.

Broken prompt commands can also make interactive shell troubleshooting harder.

Start simple.

---

# 73. Environment-Specific Variables

Applications and scripts often use environment variables to describe execution context.

Examples:

```bash
export APP_ENV="staging"
export LOG_LEVEL="INFO"
export APP_PORT="8080"
export API_BASE_URL="https://staging-api.example.internal"
```

A script might read:

```bash
environment="${APP_ENV:?APP_ENV is required}"
```

Then make decisions based on that validated value.

---

# 74. Environment Variables Are Strings

Remember:

```text
Environment variables are fundamentally string data.
```

If:

```bash
export APP_PORT="8080"
```

and your script needs numeric behavior, validate it before arithmetic.

Example:

```bash
if [[ ! "$APP_PORT" =~ ^[0-9]+$ ]]; then
    printf 'ERROR: APP_PORT must be numeric\n' >&2
    exit 1
fi
```

Then validate its range.

---

# 75. Do Not Trust an Environment Variable Because It Exists

This is unsafe reasoning:

```text
APP_ENV exists
therefore it must be valid
```

Instead:

```bash
environment="${APP_ENV:?APP_ENV is required}"

case "$environment" in
    development|staging|production)
        ;;
    *)
        printf 'ERROR: invalid APP_ENV: %s\n' \
            "$environment" >&2
        exit 1
        ;;
esac
```

Environment variables are inputs.

Validate inputs.

---

# 76. Environment Variables and Secrets

Environment variables are often used to pass:

* API tokens
* database credentials
* cloud credentials
* passwords
* private configuration

But this does not mean:

```text
environment variable = perfectly secret storage
```

Environment variables can leak through:

* debugging output
* CI logs
* crash reports
* process inspection under some circumstances
* accidental `env` output
* shell history if assigned carelessly
* child processes
* application diagnostics

Treat secrets deliberately.

---

# 77. Avoid Printing the Entire Environment in CI

A debugging command such as:

```bash
env
```

may seem harmless.

In a CI/CD environment, it can expose injected secrets if masking is incomplete or misconfigured.

Instead of:

```bash
env
```

prefer targeted inspection:

```bash
printf 'APP_ENV=%s\n' "${APP_ENV:-not-set}"
```

For sensitive values, verify presence without printing the value:

```bash
if [[ -n "${API_TOKEN:-}" ]]; then
    printf 'API_TOKEN is set\n'
else
    printf 'API_TOKEN is not set\n'
fi
```

---

# 78. Never Print Secrets Just to Debug Them

Avoid:

```bash
printf 'TOKEN=%s\n' "$API_TOKEN"
```

Instead:

```bash
if [[ -z "${API_TOKEN:-}" ]]; then
    printf 'ERROR: API_TOKEN is missing\n' >&2
    exit 1
fi

printf 'API_TOKEN is configured\n'
```

You can verify existence without exposing contents.

---

# 79. Shell History

Interactive Bash can store command history.

Try:

```bash
history
```

You may see:

```text
501 pwd
502 ls
503 git status
504 kubectl get pods
```

History is convenient.

It is also a potential source of accidental secret exposure.

---

# 80. `.bash_history`

A common Bash history file is:

```text
~/.bash_history
```

Inspect its configured location:

```bash
printf '%s\n' "${HISTFILE:-}"
```

A common result:

```text
/home/ann/.bash_history
```

Do not assume every Bash session writes history identically or immediately.

History behavior depends on Bash settings and session lifecycle.

---

# 81. Why History Can Be Sensitive

This is dangerous:

```bash
curl -H 'Authorization: Bearer SUPER_SECRET_TOKEN' \
    https://api.example.com
```

The token is directly present in the command line you typed.

Depending on shell configuration and other system behavior, it may be exposed through history or other mechanisms.

Likewise:

```bash
export DATABASE_PASSWORD='my-secret-password'
```

typed interactively may become part of history.

---

# 82. Better Secret Handling

Prefer dedicated secret-management mechanisms appropriate to your environment.

Examples include:

* CI/CD secret stores
* cloud secret managers
* Kubernetes Secrets with appropriate controls
* credential helpers
* protected files with restrictive permissions
* interactive secure prompting where appropriate

A Bash script should not encourage developers to paste long-lived production credentials directly into commands.

---

# 83. Reading a Secret Interactively

For some local interactive workflows:

```bash
read -r -s -p 'Password: ' password
printf '\n'
```

The:

```text
-s
```

option prevents normal terminal echo while typing.

But the secret now exists in a shell variable, so you must still handle it carefully.

Example:

```bash
unset password
```

after use.

This is not a complete secrets-management system.

---

# 84. `HISTSIZE`

Inspect:

```bash
printf '%s\n' "${HISTSIZE:-}"
```

`HISTSIZE` controls how many history entries Bash keeps in the in-memory history list.

Example:

```bash
HISTSIZE=5000
```

This affects the current shell history list.

---

# 85. `HISTFILESIZE`

Another related variable is:

```bash
printf '%s\n' "${HISTFILESIZE:-}"
```

`HISTFILESIZE` controls the maximum number of lines stored in the history file.

Example:

```bash
HISTFILESIZE=10000
```

Do not confuse:

```text
HISTSIZE
```

with:

```text
HISTFILESIZE
```

One relates to the in-memory history list, while the other relates to the history file size.

---

# 86. `HISTCONTROL`

Inspect:

```bash
printf '%s\n' "${HISTCONTROL:-}"
```

Common values include:

```text
ignorespace
ignoredups
ignoreboth
```

Conceptually:

```text
ignorespace
ignore commands beginning with a space

ignoredups
avoid storing consecutive duplicate commands

ignoreboth
combine ignorespace and ignoredups
```

---

# 87. Do Not Treat `ignorespace` as a Security Boundary

You may hear advice such as:

```text
Put a space before commands containing secrets.
```

If `HISTCONTROL` includes `ignorespace`, Bash may avoid storing that command in normal history.

But this is not a robust secret-management strategy.

Why?

Because:

* the configuration may differ
* other logging mechanisms may exist
* process arguments may still be visible
* terminal recording may exist
* command auditing may exist
* users can forget the leading space

Use proper secret handling instead.

---

# 88. `HISTCONTROL=ignoreboth`

A common interactive setting is:

```bash
HISTCONTROL=ignoreboth
```

This can reduce duplicate history entries and ignore commands beginning with a space.

Again:

```text
convenience feature
```

not:

```text
secret protection system
```

---

# 89. `HISTIGNORE`

Another Bash variable is:

```text
HISTIGNORE
```

It can define patterns for commands that should not be saved to history.

Example concepts may include repetitive commands such as:

```text
ls
pwd
history
```

But using history filtering to protect secrets is fragile.

The correct solution is to avoid placing secrets directly into command text where possible.

---

# 90. History Is Usually an Interactive Concern

Non-interactive scripts do not behave like your normal interactive shell history session.

This is another example of:

```text
Interactive shell behavior
```

being different from:

```text
script behavior
```

Do not assume `.bash_history` explains every command executed on a machine.

System auditing, application logs, CI logs, and service logs are separate mechanisms.

---

# 91. Persisting Variables

Suppose you run:

```bash
export EDITOR="vim"
```

It exists in the current shell and descendants.

Close the shell.

Open a new one.

The value may disappear unless it is recreated by startup configuration.

To persist an interactive environment variable, you may place an appropriate export in a startup file.

Example:

```bash
export EDITOR="vim"
```

But which startup file is correct depends on where you need the variable.

---

# 92. Do Not Put Everything in `.bashrc`

Ask:

```text
Who needs this value?

Only interactive Bash?

Login sessions?

Scripts?

A service?

A CI job?

A single project?
```

For example, a systemd service should generally receive service configuration through its service environment/configuration mechanisms rather than depending on your personal `.bashrc`.

Similarly, a CI job should receive variables through its CI configuration rather than relying on your laptop's profile.

---

# 93. Project Configuration vs Personal Shell Configuration

Suppose a project requires:

```text
APP_ENV
APP_PORT
DATABASE_URL
```

Do not force every developer to place those values permanently into:

```text
~/.bashrc
```

Project-specific configuration should generally remain project-specific.

Personal shell configuration should not become an undocumented application dependency.

---

# 94. Environment Configuration by Scope

A useful architecture:

```text
Personal terminal convenience
    |
    +--> ~/.bashrc

Personal login environment
    |
    +--> login profile

Project configuration
    |
    +--> project-controlled configuration mechanism

CI configuration
    |
    +--> CI environment / secrets

systemd service
    |
    +--> service configuration

Container
    |
    +--> container/runtime configuration

Kubernetes workload
    |
    +--> workload configuration / Secrets / ConfigMaps where appropriate
```

The shell is only one layer.

---

# 95. Why “Works in My Terminal” Happens

Imagine your terminal contains:

```bash
export PATH="$HOME/tools/bin:$PATH"
export APP_ENV="staging"

alias k='kubectl'
```

Your script contains:

```bash
k get pods
```

and:

```bash
my-deploy-tool
```

When you test manually, everything works.

In CI:

```text
No ~/.bashrc
No alias k
Different PATH
No APP_ENV
No custom tool
```

The script fails.

The problem is not necessarily Bash itself.

The script had undocumented environment dependencies.

---

# 96. The Environment Dependency Problem

Conceptually:

```text
Developer terminal
--------------------------------
Custom PATH
Aliases
Functions
Exported variables
Cloud credentials
Tool managers
Current directory
Personal config

              VS

Automation environment
--------------------------------
Minimal PATH
No aliases
No interactive functions
Different HOME
Different user
Different working directory
Injected variables only
```

Reliable automation should minimize assumptions about the first environment.

# 97. First Troubleshooting Question: Which User?

Run:

```bash
whoami
```

or:

```bash
id
```

A script running as:

```text
ann
```

may have access to different:

* files
* home directories
* permissions
* credentials
* PATH configuration

than a service running as:

```text
jenkins
```

or:

```text
www-data
```

---

# 98. Check HOME

Run:

```bash
printf 'HOME=<%s>\n' "${HOME:-}"
```

Your terminal may have:

```text
/home/ann
```

while automation may have:

```text
/var/lib/jenkins
```

or another value.

Therefore:

```text
$HOME/bin
```

may refer to completely different directories.

---

# 99. Check the Working Directory

Run:

```bash
pwd
```

Your terminal may be:

```text
/home/ann/project
```

while cron or a service may run from another directory.

Then:

```bash
./config/app.conf
```

may fail.

This is why robust scripts often determine their own location rather than assuming the current directory.

From Part 8:

```bash
script_dir="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)"
```

Then:

```bash
config_file="$script_dir/config/app.conf"
```

---

# 100. Check PATH

Print:

```bash
printf 'PATH=<%s>\n' "$PATH"
```

Then:

```bash
command -v required_tool || true
```

For example:

```bash
command -v kubectl || true
command -v terraform || true
command -v aws || true
```

Compare the output between:

```text
working terminal
```

and:

```text
failing environment
```

---

# 101. Check Variables Explicitly

Instead of dumping everything:

```bash
env
```

inspect only relevant variables:

```bash
printf 'APP_ENV=<%s>\n' "${APP_ENV:-}"
printf 'HOME=<%s>\n' "${HOME:-}"
printf 'PATH=<%s>\n' "${PATH:-}"
```

For secrets:

```bash
if [[ -n "${API_TOKEN:-}" ]]; then
    printf 'API_TOKEN=set\n'
else
    printf 'API_TOKEN=missing\n'
fi
```

Do not print the token.

---

# 102. Check Whether the Shell Is Interactive

Use:

```bash
case $- in
    *i*)
        printf 'interactive=yes\n'
        ;;
    *)
        printf 'interactive=no\n'
        ;;
esac
```

If your code depends on:

```text
aliases
prompt setup
interactive shell functions
```

this may explain the failure.

---

# 103. Check Whether It Is a Login Shell

Use:

```bash
if shopt -q login_shell; then
    printf 'login_shell=yes\n'
else
    printf 'login_shell=no\n'
fi
```

This helps determine which Bash startup files may have been read.

---

# 104. Check Bash Version

Run:

```bash
bash --version
```

or inside Bash:

```bash
printf '%s\n' "$BASH_VERSION"
```

Different systems may have different Bash versions.

This matters for features introduced in newer Bash releases.

---

# 105. Check the Actual Executable

Do not assume:

```bash
python
```

or:

```bash
terraform
```

means the same executable everywhere.

Run:

```bash
command -v terraform
type -a terraform
```

Then:

```bash
terraform version
```

The path and version are both important.

---

# 106. Bash Command Hashing

Bash can remember locations of commands it previously found.

Suppose you change PATH or install a different executable.

Sometimes it is useful to clear remembered command locations:

```bash
hash -r
```

Then Bash performs fresh command searches.

You can inspect remembered commands with:

```bash
hash
```

This is a useful troubleshooting detail when PATH has recently changed.

---

# 107. Why `hash -r` Can Matter

Suppose Bash previously resolved:

```text
mytool
```

to:

```text
/usr/local/bin/mytool
```

Then you modify PATH so a different version should win.

If behavior seems inconsistent, inspect:

```bash
type -a mytool
```

and clear command hashing:

```bash
hash -r
```

Do not use `hash -r` as a random fix.

Understand why you are using it.

---

# 108. PATH Security

PATH controls which executable may run when you type a command without an absolute path.

That makes PATH security-sensitive.

Suppose:

```text
/tmp:/usr/bin:/bin
```

and an attacker can create:

```text
/tmp/ls
```

Then typing:

```bash
ls
```

could potentially run the attacker's executable before `/usr/bin/ls`, depending on the environment and command resolution.

Writable directories early in PATH can therefore be dangerous.

---

# 109. Never Add `.` Casually to PATH

You may see:

```bash
export PATH=".:$PATH"
```

This means:

```text
Search the current directory before other PATH entries.
```

That is dangerous.

Suppose you enter an untrusted directory containing a malicious executable named:

```text
ls
```

Typing:

```bash
ls
```

could execute it.

Avoid placing:

```text
.
```

early in PATH.

---

# 110. Empty PATH Components

Be careful with malformed PATH values such as:

```text
/usr/local/bin::/usr/bin
```

An empty component may be interpreted as the current directory in relevant PATH-search behavior.

Similarly:

```text
:/usr/bin:/bin
```

or:

```text
/usr/bin:/bin:
```

can create current-directory search behavior.

Avoid accidental empty PATH entries.

---

# 111. PATH Construction Mistake

Suppose:

```bash
TOOLS_DIR=""
export PATH="$TOOLS_DIR:$PATH"
```

This can produce:

```text
:/usr/local/bin:/usr/bin:/bin
```

That leading empty component is undesirable.

Validate before adding:

```bash
if [[ -n "${TOOLS_DIR:-}" ]]; then
    export PATH="$TOOLS_DIR:$PATH"
fi
```

Better:

```bash
if [[ -d "${TOOLS_DIR:-}" ]]; then
    export PATH="$TOOLS_DIR:$PATH"
fi
```

depending on your requirement.

---

# 112. Validate a PATH Directory

Example:

```bash
tools_dir="$HOME/bin"

if [[ -d "$tools_dir" ]]; then
    export PATH="$tools_dir:$PATH"
fi
```

This avoids adding a nonexistent path accidentally.

You may also want to verify permissions and ownership for security-sensitive environments.

---

# 113. Avoid Repeated PATH Entries

If `.bashrc` repeatedly runs:

```bash
export PATH="$HOME/bin:$PATH"
```

and the file is sourced multiple times, you can end up with:

```text
/home/ann/bin:/home/ann/bin:/home/ann/bin:/usr/bin:/bin
```

Usually this is not catastrophic, but it is messy.

You can guard against duplicates.

---

# 114. Simple PATH Duplicate Guard

Example:

```bash
add_to_path() {
    local directory="$1"

    [[ -d "$directory" ]] || return 0

    case ":$PATH:" in
        *":$directory:"*)
            ;;
        *)
            PATH="$directory:$PATH"
            ;;
    esac
}
```

Then:

```bash
add_to_path "$HOME/bin"
export PATH
```

---

# 115. Why Add Colons Around PATH?

This:

```bash
case ":$PATH:" in
```

helps compare complete PATH entries.

Suppose you search for:

```text
/home/ann/bin
```

without separators.

You might accidentally match part of:

```text
/home/ann/bin-old
```

Adding delimiters makes entry boundaries clearer:

```text
:/home/ann/bin:
```

---

# 116. Validate Before Exporting

You can write:

```bash
PATH="$directory:$PATH"
export PATH
```

or simply:

```bash
export PATH="$directory:$PATH"
```

For more complex configuration, separating construction and export can make debugging easier.

---

# 117. Practical `.bashrc` Structure

A clean personal `.bashrc` might be organized like:

```bash
# ~/.bashrc

# Stop interactive-only setup when not interactive.
case $- in
    *i*)
        ;;
    *)
        return
        ;;
esac

# History configuration.
HISTCONTROL=ignoreboth
HISTSIZE=5000
HISTFILESIZE=10000

# PATH helpers.
add_to_path() {
    local directory="$1"

    [[ -d "$directory" ]] || return 0

    case ":$PATH:" in
        *":$directory:"*)
            ;;
        *)
            PATH="$directory:$PATH"
            ;;
    esac
}

add_to_path "$HOME/bin"
export PATH

# Aliases.
alias ll='ls -alF'
alias gs='git status'

# Interactive functions.
mkcd() {
    if (( $# != 1 )); then
        printf 'Usage: mkcd DIRECTORY\n' >&2
        return 2
    fi

    mkdir -p -- "$1" &&
        cd -- "$1"
}

# Prompt.
PS1='\u@\h:\w\$ '
```

This is an example, not a universal `.bashrc`.

---

# 118. Why Organize `.bashrc`?

A `.bashrc` can grow for years.

Without structure it becomes:

```text
PATH change
alias
SDK initialization
another PATH change
function
cloud setup
old commented code
another alias
language manager
duplicate export
```

Then troubleshooting becomes difficult.

Organize configuration into sections.

For example:

```text
Interactive guard
History
PATH
Aliases
Functions
Tool initialization
Prompt
```

---

# 119. Do Not Turn `.bashrc` Into a Deployment System

Your personal shell startup file should not perform heavy operational actions such as:

```text
Deploy application
Restart production services
Run Terraform apply
Delete temporary resources
Authenticate automatically to sensitive systems
```

Startup files execute when shells start.

Keep side effects minimal and predictable.

---

# 120. Avoid Slow Startup Files

Suppose `.bashrc` runs:

```bash
kubectl get pods
```

every time a shell starts.

If the cluster is slow or unreachable, opening your terminal becomes slow.

Similarly, network calls inside startup files can create fragile interactive environments.

Prefer initialization that is:

* local
* fast
* predictable

---

# 121. Avoid Unconditional Tool Initialization

Some development tools ask you to add large initialization snippets to `.bashrc`.

Understand what they do.

Ask:

```text
Does this change PATH?

Does it define functions?

Does it run subprocesses?

Does it perform network access?

Does it modify environment variables?

Does it need to run in every shell?
```

Do not blindly paste shell initialization code from untrusted sources.

---

# 122. Shell Configuration Is Code

This is important.

Files such as:

```text
~/.bashrc
~/.bash_profile
~/.profile
```

can contain executable shell commands.

Treat modifications as code changes.

Before editing:

```bash
cp -- "$HOME/.bashrc" "$HOME/.bashrc.backup"
```

if the file exists and you want a simple local backup.

After editing:

```bash
bash -n "$HOME/.bashrc"
```

can catch many syntax errors.

---

# 123. Test Before Replacing Your Environment

If you make a significant `.bashrc` change, do not immediately close every terminal.

Keep one working shell open.

Open another shell and test the new configuration.

If the new configuration is broken, your original shell gives you a recovery path.

This is a practical operational habit.

---

# 124. Reloading `.bashrc`

After editing:

```bash
source "$HOME/.bashrc"
```

can reload it into the current shell.

But remember:

```text
Reloading does not perfectly reproduce starting a completely new shell.
```

Existing variables, functions, and state may remain.

For reliable testing, also open a fresh shell.

---

# 125. Testing a Fresh Interactive Bash

You can start:

```bash
bash
```

which typically creates another interactive Bash when run from a terminal.

You can explicitly request an interactive shell:

```bash
bash -i
```

Exit:

```bash
exit
```

For login behavior:

```bash
bash --login
```

Use these deliberately when testing startup files.

---

# 126. Start Bash Without Startup Files

For troubleshooting:

```bash
bash --noprofile --norc
```

# 129. Troubleshooting “Works in Terminal but Not in Script”

# 130. Why Sourcing `.bashrc` in Scripts Is Usually a Bad Fix

inside the script.

* prompt configuration
* interactive functions
* shell options

# 131. Better Script Dependency Handling

Example:

```bash
require_command() {

    fi

```

Then:

# 135. CI/CD Environments

# 145. Avoid Ambiguous Boolean Environment Variables

Suppose:

```bash
DEBUG="false"
```

This is a non-empty string.

So:

```bash
if [[ -n "$DEBUG" ]]; then
    printf 'Debug enabled\n'

```

incorrectly treats:

```text
false
```

as enabled.

Validate the actual value:

```bash
case "${DEBUG,,}" in
    true|1|yes)
        debug_enabled=true
        ;;

    false|0|no|'')
        debug_enabled=false
        ;;

    *)
        printf 'ERROR: invalid DEBUG value\n' >&2
        exit 1
        ;;
esac
```

# 148. `SHELL` Does Not Necessarily Tell You the Current Shell Process

This is an important subtlety.

You may inspect:

```bash
printf '%s\n' "$SHELL"
```

and see:

```text

```

while currently running:

```bash

```

`SHELL` commonly represents the user's login shell, not necessarily the executable currently interpreting the script.

To confirm Bash:

```bash

```

or inspect process information appropriately.

Do not use `$SHELL` as proof that a script is currently running under Bash.

after validating that the execution environment provides the intended HOME.

For system services, even `$HOME` may not mean what you expect.

Scope matters.

when constructing paths in variables.

# 164. Build a Script That Does Not Depend on `.bashrc`

Create:

```text
check-runtime.sh
```

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

require_command() {
    local command_name="$1"

    if ! command -v "$command_name" >/dev/null 2>&1; then
        printf 'ERROR: required command not found: %s\n' \
            "$command_name" >&2
        return 1
    fi
}

print_runtime() {
    printf 'Runtime Information\n'
    printf '===================\n'

    printf 'User: %s\n' "${USER:-unknown}"
    printf 'Home: %s\n' "${HOME:-unknown}"
    printf 'PWD: %s\n' "$PWD"
    printf 'Bash: %s\n' "$BASH_VERSION"
    printf 'PATH: %s\n' "$PATH"
}

check_environment() {
    local environment="${APP_ENV:-}"

    if [[ -z "$environment" ]]; then
        printf 'ERROR: APP_ENV is required\n' >&2
        return 1
    fi

    environment="${environment,,}"

    case "$environment" in
        development|staging|production)
            ;;
        *)
            printf 'ERROR: invalid APP_ENV: %s\n' \
                "$environment" >&2
            return 1
            ;;
    esac

    printf 'Application environment: %s\n' "$environment"
}

main() {
    print_runtime

    require_command grep
    require_command sed
    require_command awk

    check_environment

    printf 'Runtime validation passed.\n'
}

main "$@"
```

Make executable:

```bash
chmod +x check-runtime.sh
```

# 185. Common Mistake: Using `$SHELL` to Detect Current Interpreter

This:

```bash
if [[ "$SHELL" == */bash ]]; then
    ...
fi
```

does not reliably prove that the current script is being interpreted by Bash.

Use Bash-specific information such as:

```bash
BASH_VERSION
```

when appropriate.

---

# 186. Common Mistake: Editing the Wrong Startup File

You add configuration to:

```text
~/.profile
```

but your actual shell path reads:

```text
~/.bash_profile
```

instead.

Or you add aliases to `.bash_profile`, but your common terminal launches interactive non-login Bash and reads `.bashrc`.

Do not guess.

Identify:

```text
shell type
login status
interactive status
startup files
```

---

# 187. Common Mistake: Duplicating Configuration Everywhere

Avoid putting:

```bash
export PATH=...
```

into:

```text
.bashrc
.bash_profile
.profile
/etc/profile
```

just because you are unsure which one works.

This creates:

* duplication
* conflicting order
* debugging difficulty
* unexpected environment differences

Understand startup behavior first.

---

# 188. Common Mistake: Assuming Shell Startup Is Identical on Every OS

macOS, Ubuntu, Fedora, Debian, containers, remote hosts, and other Unix-like systems may differ in:

* default shell
* Bash version
* startup configuration
* system-wide files
* PATH defaults
* terminal behavior

Inspect the environment you actually operate.

---

# 189. Common Mistake: Unquoted PATH Assignment

Prefer:

```bash
export PATH="$HOME/bin:$PATH"
```

rather than relying on unquoted expansion.

Consistent quoting improves clarity and prevents unwanted shell transformations in many contexts.

---

# 190. Common Mistake: Using PATH to Hide Dependency Problems

If a script requires:

```text
terraform 1.x
```

checking only:

```bash
command -v terraform
```

does not prove the correct version is installed.

For important dependencies:

```text
Check command exists
        |
        v
Check version
        |
        v
Check configuration
        |
        v
Run
```

Dependency validation can include more than PATH lookup.

---

# 191. Common Mistake: Assuming HOME Is Correct

A service may have:

```text
HOME=/var/lib/service
```

or no meaningful user home for your intended configuration.

Do not blindly load:

```bash
"$HOME/.config/mytool"
```

without understanding the execution context.

---

# 192. Common Mistake: Relying on Current Directory

Your terminal may start a script from:

```text
~/project
```

while CI runs it from:

```text
/builds/project
```

and cron runs it from somewhere else.

Resolve project paths deliberately.

---

# 193. Common Mistake: Persisting Project Variables Globally

Avoid filling `.bashrc` with:

```bash
export PROJECT_A_ENV=...
export PROJECT_B_ENV=...
export PROJECT_C_ENV=...
```

unless that is genuinely the intended configuration architecture.

Project configuration should normally travel with or be managed for the project environment.

---

# 194. Common Mistake: Assuming Environment Variables Are Secure

Environment variables are convenient configuration channels.

They are not magical encrypted containers.

Avoid:

* logging them blindly
* exposing them in debug traces
* exporting secrets unnecessarily
* passing secrets to children that do not need them

Least privilege applies to process environments too.

---

# 195. `set -x` and Secrets

From Part 14:

```bash
set -x
```

prints command tracing.

Suppose:

```bash
API_TOKEN="super-secret"
curl -H "Authorization: Bearer $API_TOKEN" ...
```

With tracing enabled, the expanded secret may appear in logs.

Before secret-sensitive operations:

```bash
set +x
```

may be necessary.

But the best solution is to design secret handling deliberately, not merely toggle tracing and hope.

---

# 196. Environment Variables and Child Process Exposure

If you:

```bash
export SECRET_TOKEN="..."
```

every child process launched afterward can potentially receive that variable unless you remove or override it.

Do not export sensitive values more broadly than necessary.

For one command, a narrower environment can sometimes be better:

```bash
SECRET_TOKEN="$secret" command
```

But understand that the target process still receives the secret.

---

# 197. Remove Sensitive Variables After Use

When practical:

```bash
unset SECRET_TOKEN
```

after the secret is no longer needed.

This does not erase every possible historical copy from memory or logs, but it reduces continued exposure in later child environments.

Security requires layers.

# Part 16 Summary

A Bash script does not run in a vacuum.

Every process has an execution context.

That context includes:

```text
User
HOME
Working directory
Environment variables
PATH
Available executables
Permissions
Shell mode
Startup configuration
```

A Bash variable:

```bash
APP_ENV="staging"
```

belongs to the current shell.

An exported variable:

```bash
export APP_ENV="staging"
```

can be inherited by child processes.

Environment inheritance generally flows:

```text
Parent
   |
   v
Child
```

not backward.

`PATH` determines where commands are searched:

```bash
printf '%s\n' "$PATH"
```

Useful command-resolution tools include:

```bash
command -v
type
type -a
```

Adding a user command directory may look like:

```bash
export PATH="$HOME/bin:$PATH"
```

but PATH order and security must be understood.

Avoid dangerous PATH configurations involving:

```text
.
empty components
untrusted writable directories
```

Bash startup behavior depends on shell type.

The core beginner model is:

```text
Interactive non-login Bash
        |
        v
~/.bashrc
```

and:

```text
Login Bash
    |
    v
/etc/profile
    |
    v
first readable user login file
```

including:

```text
~/.bash_profile
~/.bash_login
~/.profile
```

Aliases and interactive functions belong primarily to human shell convenience.

Production scripts should not depend on them.

`PS1` controls the interactive prompt and can display useful context such as:

```text
username
hostname
working directory
```

Bash history is convenient, but commands can contain sensitive information.

Understand:

```text
.bash_history
HISTCONTROL
HISTSIZE
HISTFILESIZE
```

without treating history controls as secret-management mechanisms.

Most importantly, when you encounter:

```text
It works in my terminal but not in the script.
```

do not guess.

Inspect:

```text
Who is running it?

What is HOME?

What is PWD?

What is PATH?

Which command is actually resolved?

Which version is running?

Which variables exist?

Are they exported?

Is the shell interactive?

Is it a login shell?

Which startup configuration was loaded?

What permissions exist?
```

Then reproduce the difference in a controlled environment.

That is the shift from:

```text
trying random fixes
```

to:

```text
debugging the execution environment.
```
