# Part 16: Tags, Releases, and Software Versioning

In Part 15, you learned how to organize a professional repository.

You learned how files such as:

```text
README.md
.gitignore
LICENSE
CONTRIBUTING.md
```

and directories such as:

```text
src/
tests/
docs/
.github/
```

help make a repository understandable, maintainable, and safe.

You also learned that Git history contains the evolution of a project.

For example:

```text
A---B---C---D---E---F---G
                        ^
                       main
```

Every commit represents a point in project history.

But this creates a new problem.

Imagine your project has:

```text
2,847 commits
```

and someone asks:

```text
Which exact commit is version 1.0.0?
```

Or:

```text
Which version is currently running in production?
```

Or:

```text
Which source code produced the application
customers downloaded last month?
```

A commit hash can answer this technically:

```text
9f2a6d31...
```

But humans generally do not want to remember hundreds of commit hashes.

We want meaningful names such as:

```text
v1.0.0

v1.1.0

v1.1.1

v2.0.0
```

Git tags solve this problem.

# 1. The Problem Tags Solve

Consider this history:

```text
A---B---C---D---E---F---G---H---I---J
                                    ^
                                   main
```

Suppose commit:

```text
D
```

was the first production release.

Commit:

```text
G
```

was the second release.

Commit:

```text
J
```

is the latest release.

Without tags, someone investigating the system might need to know:

```text
D = 5c71e42
G = b80e197
J = 91ad703
```

That works technically.

But this is much easier:

```text
A---B---C---D---E---F---G---H---I---J
            ^           ^           ^
          v1.0.0      v1.1.0      v1.2.0
```

Now important points in history have human-readable names.

That is one of the primary purposes of Git tags.

---

# 2. What Is a Git Tag?

A Git tag is a reference used to give a meaningful name to a specific point or object in repository history.

Tags are commonly used to identify:

```text
Software releases

Production versions

Milestones

Stable versions

Important historical points
```

For example:

```text
v1.0.0
```

might identify the commit containing the first stable public release.

Conceptually:

```text
Commit A
   |
   v
Commit B
   |
   v
Commit C  <--- v1.0.0
   |
   v
Commit D
```

The tag:

```text
v1.0.0
```

identifies commit C.

---

# 3. Tags Are References

You learned earlier that branches are references.

For example:

```text
main
```

may point to:

```text
Commit D
```

A tag is also a Git reference.

Internally, tag references live under:

```text
refs/tags/
```

For example:

```text
refs/tags/v1.0.0
```

But branches and tags have very different intended behavior.

Understanding that difference is essential.

---

# 4. Branches vs Tags

Consider:

```text
A---B---C
        ^
       main
```

You create another commit:

```text
A---B---C---D
            ^
           main
```

The branch:

```text
main
```

moves.

That is what branches are designed to do.

A branch represents an evolving line of development.

Now suppose commit C has a tag:

```text
A---B---C---D
        ^   ^
     v1.0.0 main
```

You create commit E:

```text
A---B---C---D---E
        ^       ^
     v1.0.0    main
```

The tag stays on C.

That is the key difference.

---

# 5. Branches Move

A branch is expected to move as new commits are created.

For example:

```text
Before commit:

A---B---C
        ^
       main
```

After commit:

```text
A---B---C---D
            ^
           main
```

The `main` branch reference moved from C to D.

Branches are used for ongoing development.

Examples:

```text
main

feature/login

fix/database-timeout

release/2.0
```

---

# 6. Tags Normally Stay Put

A release tag is normally intended to identify one particular historical point.

Example:

```text
A---B---C---D---E
        ^       ^
     v1.0.0    main
```

New commits do not cause:

```text
v1.0.0
```

to move.

That stability is precisely why tags are useful for releases.

If someone says:

```text
Deploy v1.0.0
```

the team should be able to identify the same code later.

---

# 7. Branch vs Tag Mental Model

Think:

```text
BRANCH

"Where development is currently going"

main
 |
 v
latest commit
 |
 moves as new commits appear
```

versus:

```text
TAG

"Remember this exact point"

v1.0.0
 |
 v
specific historical point
 |
 normally remains there
```

Or:

```text
Branch = moving pointer

Tag = historical marker
```

This is simplified, but it is an excellent beginner mental model.

---

# 8. Why Tags Exist

Imagine your team deploys on Friday.

The production deployment uses commit:

```text
74e291a
```

Three weeks later, `main` contains another 40 commits.

Production still runs the Friday version.

Someone reports:

```text
Production is failing.
```

Which source code should you inspect?

Not necessarily today's `main`.

You need the exact version deployed.

If the deployed commit was tagged:

```text
v2.4.0
```

you now have a stable human-readable reference.

```text
Production
    |
    v
  v2.4.0
    |
    v
74e291a
```

This improves:

* Traceability
* Incident response
* Release management
* Rollback decisions
* Auditing
* CI/CD automation
* Communication

---

# 9. A Tag Is Not a Copy of the Repository

Do not imagine a tag as:

```text
another folder containing the project
```

Git does not create:

```text
project-v1.0.0/
project-v1.1.0/
project-v1.2.0/
```

A tag identifies Git history.

Conceptually:

```text
Repository history

A---B---C---D---E
        ^
        |
      v1.0.0
```

The same underlying Git objects are used.

---

# 10. Two Important Types of Git Tags

Git supports two major tag styles beginners should understand:

```text
Lightweight tags

Annotated tags
```

They both provide names for points or objects in Git history.

But they contain different information.

---

# 11. Lightweight Tags

A lightweight tag is essentially a simple named reference to an object, usually a commit.

Example:

```bash
git tag v1.0.0
```

If your current history is:

```text
A---B---C
        ^
       HEAD
```

then:

```bash
git tag v1.0.0
```

creates:

```text
A---B---C
        ^
        |
     v1.0.0
```

The tag points directly at the object.

---

# 12. What a Lightweight Tag Contains

At a beginner level, think:

```text
Lightweight Tag

Name
 |
 v
Commit
```

For example:

```text
v1.0.0
   |
   v
Commit C
```

A lightweight tag does not create the richer tag object that annotated tags create.

---

# 13. When Lightweight Tags Are Useful

Lightweight tags can be useful for:

```text
Temporary markers

Personal labels

Simple internal references

Short-lived development markers
```

For formal releases, annotated tags are often preferable because they contain additional metadata.

Git's own documentation describes annotated tags as intended for releases, while lightweight tags are more suitable for temporary or private labels.

---

# 14. Annotated Tags

An annotated tag creates a tag object containing additional information.

It can include:

```text
Tag name

Tagger identity

Tag creation date

Tag message

Optional cryptographic signature
```

Conceptually:

```text
v1.0.0
   |
   v
Annotated Tag Object
   |
   +--> Tagger
   +--> Date
   +--> Message
   |
   v
Commit C
```

This provides more release context than a simple lightweight tag.

---

# 15. Creating an Annotated Tag

Use:

```bash
git tag -a v1.0.0 -m "Release version 1.0.0"
```

Breakdown:

```text
git
    Run Git

tag
    Work with tags

-a
    Create an annotated tag

v1.0.0
    Tag name

-m
    Supply a tag message

"Release version 1.0.0"
    Annotation message
```

If the target commit is omitted, Git normally tags the current `HEAD`.

---

# 16. Lightweight vs Annotated Tags

Compare:

```text
LIGHTWEIGHT TAG

v1.0.0
   |
   v
Commit
```

with:

```text
ANNOTATED TAG

v1.0.0
   |
   v
Tag object
   |
   +--> Tagger
   +--> Date
   +--> Message
   +--> Optional signature
   |
   v
Commit
```

For important releases, annotated tags provide useful metadata.

---

# 17. Signed Tags

Git also supports cryptographically signed tags.

For example:

```bash
git tag -s v1.0.0 -m "Release version 1.0.0"
```

Signing can provide additional verification about who created the tag.

However, signing requires signing-key configuration and introduces concepts beyond our immediate beginner release workflow.

The important thing to understand now is:

```text
Lightweight tag
    Simple reference

Annotated tag
    Tag object + metadata

Signed tag
    Annotated tag + cryptographic verification
```

```bash
mkdir release-lab
cd release-lab
git init -b main
```

```bash
echo "Server Monitor" > README.md
```

```bash
git add README.md
```

```bash
git commit -m "Create Server Monitor project"
```

```bash
mkdir src
echo 'print("Server Monitor 0.1")' > src/app.py
```

Commit:

```bash
git add src/app.py

```

```bash
echo "timeout=5" > config.txt
git add config.txt

```

Inspect:

```bash

```

You may see something conceptually similar to:

```text

```

Your hashes will be different.

# 19. Creating Your First Lightweight Tag

Run:

```bash
git tag v0.1.0
```

Then:

```bash
git tag
```

Expected:

```text
v0.1.0
```

You have created a lightweight tag pointing at your current commit.

# 20. Listing Tags

The simplest command is:

```bash
git tag
```

or explicitly:

```bash
git tag --list
```

Short form:

```bash
git tag -l
```

If the repository contains:

```text
v0.1.0
v0.2.0
v0.2.1
v1.0.0
```

Git can list those tag names.

---

# 21. Filtering Tags

Suppose your repository contains:

```text
v1.0.0
v1.1.0
v1.2.0
v2.0.0
experiment
```

You can filter:

```bash
git tag --list "v1.*"
```

This can return:

```text
v1.0.0
v1.1.0
v1.2.0
```

The pattern helps find matching tag names.

---

# 22. Creating an Annotated Tag

Let's create another commit:

```bash
echo "health_check=true" >> config.txt
git add config.txt
git commit -m "Enable health checks"
```

Now create:

```bash
git tag -a v0.2.0 -m "Release version 0.2.0"
```

List:

```bash
git tag
```

You should now have:

```text
v0.1.0
v0.2.0
```

But they are not the same kind of tag.

`v0.1.0` was lightweight.

`v0.2.0` is annotated.

---

# 23. Inspecting a Tag

Use:

```bash
git show v0.2.0
```

For an annotated tag, you can see information including:

```text
Tag name

Tagger

Date

Tag message

Tagged commit

Commit details

Commit changes
```

Conceptually:

```text
tag v0.2.0
Tagger: Ann Developer
Date: ...

Release version 0.2.0

commit abc123...
Author: ...
Date: ...

    Enable health checks
```

The exact output depends on your repository.

---

# 24. Inspecting a Lightweight Tag

Run:

```bash
git show v0.1.0
```

Because a lightweight tag points directly to the target object, you will primarily see information about that object rather than separate annotated-tag metadata.

This difference becomes easier to understand after seeing both outputs.

---

# 25. Finding Which Commit a Tag Identifies

You can use:

```bash
git rev-parse v0.2.0^{commit}
```

This resolves the tag to its commit.

Or inspect:

```bash
git log --oneline --decorate
```

You might see:

```text
9ad42fe (HEAD -> main, tag: v0.2.0) Enable health checks
7bd20ac (tag: v0.1.0) Add default timeout configuration
8f72b18 Add initial monitoring application
41e95af Create Server Monitor project
```

Now the relationship is visible.

---

# 26. Tags Do Not Need to Point to HEAD

Suppose history is:

```text
A---B---C---D---E
                ^
               HEAD
```

But commit C should have been:

```text
v1.0.0
```

You can tag a specific commit:

```bash
git tag -a v1.0.0 <commit-id> -m "Release version 1.0.0"
```

Example:

```bash
git tag -a v1.0.0 7bd20ac -m "Release version 1.0.0"
```

Now:

```text
A---B---C---D---E
        ^       ^
        |      HEAD
     v1.0.0
```

Always verify the target commit before creating an important release tag.

---

# 27. Verify Before Tagging

Before creating a release tag:

```bash
git status
```

Then:

```bash
git log --oneline --decorate -10
```

Then inspect the intended commit:

```bash
git show <commit-id>
```

Ask:

```text
Is this the exact commit we tested?

Did CI pass?

Does this commit contain the expected version?

Are all required fixes included?

Are there unrelated changes?

Is this actually the release candidate?
```

A tag should identify deliberate history.

Do not tag blindly.

---

# 28. Creating a Tag Does Not Push It

This is a major beginner mistake.

You create:

```bash
git tag -a v1.0.0 -m "Release version 1.0.0"
```

Then assume GitHub has the tag.

Not necessarily.

The tag initially exists in your local repository.

Conceptually:

```text
LOCAL

main
v1.0.0

          X

REMOTE

main
```

You must publish the tag to the remote.

---

# 29. Pushing One Tag

Use:

```bash
git push origin v1.0.0
```

Breakdown:

```text
git
    Run Git

push
    Send references and necessary objects to a remote

origin
    Remote name

v1.0.0
    Tag being pushed
```

Afterward:

```text
LOCAL                     GITHUB

v1.0.0  ----------------> v1.0.0
```

---

# 30. Pushing All Tags

You can use:

```bash
git push origin --tags
```

This pushes tags that are missing from the remote.

But be careful.

If your local repository contains temporary tags such as:

```text
test
experiment
before-refactor
old-demo
```

you may not want to publish all of them.

For beginners, deliberately pushing the specific release tag is often safer:

```bash
git push origin v1.0.0
```

---

# 31. `--follow-tags`

Git also supports:

```bash
git push --follow-tags
```

This can push annotated tags that are reachable from the commits being pushed, subject to Git's rules.

This can be useful in release workflows.

But do not confuse:

```text
--tags
```

with:

```text
--follow-tags
```

They are not identical.

For your first release workflow, explicit tag pushes are easier to reason about.

---

# 32. Verifying a Remote Tag

After pushing:

```bash
git ls-remote --tags origin
```

This asks the remote for tag references.

You can also inspect the repository's Tags or Releases area on GitHub.

The important habit is:

```text
Create
   |
   v
Verify locally
   |
   v
Push
   |
   v
Verify remotely
```

---

# 33. Deleting a Local Tag

Suppose you accidentally create:

```text
v1.0.00
```

instead of:

```text
v1.0.0
```

If it has not been published, remove it locally:

```bash
git tag -d v1.0.00
```

Then verify:

```bash
git tag
```

If necessary, create the correct tag.

---

# 34. Deleting a Remote Tag

If a tag was already pushed, deleting it locally does not automatically delete the remote tag.

You can request deletion from the remote:

```bash
git push origin --delete v1.0.00
```

Then verify:

```bash
git ls-remote --tags origin
```

But remote tag deletion deserves more caution than local cleanup.

---

# 35. Why Published Tag Changes Are Dangerous

Suppose:

```text
v1.0.0
```

points to commit C.

Users download it.

CI builds it.

Production deploys it.

Another developer clones it.

Later you silently move:

```text
v1.0.0
```

to commit E.

Now:

```text
Developer A:

v1.0.0 -> C
```

while:

```text
Developer B:

v1.0.0 -> E
```

Both people say:

```text
I have version 1.0.0.
```

But they do not have the same code.

That destroys one of the most valuable properties of release tags:

```text
Stable identity.
```

---

# 36. Do Not Casually Move Published Release Tags

Git can force replacement of a tag.

For example:

```bash
git tag -f ...
```

But technical possibility does not mean good release practice.

For an unpublished local mistake:

```text
Fixing the tag may be reasonable.
```

For a published release tag:

```text
Prefer a new version.
```

For example, if:

```text
v1.2.0
```

is wrong and has already been distributed, release a corrected version such as:

```text
v1.2.1
```

when the change fits your versioning policy.

The important principle is:

```text
Published release identifiers should be trustworthy.
```

---

# 37. Safe Tag Deletion Decision

Before deleting a tag, ask:

```text
Is it only local?

Has it been pushed?

Has a GitHub Release been created from it?

Has CI/CD built artifacts from it?

Has production deployed it?

Have customers downloaded it?

Does another repository depend on it?

Is it referenced in documentation?
```

The wider the tag has been distributed, the more carefully changes should be handled.

---

# 38. Tag Deletion Does Not Delete the Commit

Suppose:

```text
A---B---C---D
        ^
     v1.0.0
```

Delete:

```bash
git tag -d v1.0.0
```

You now have:

```text
A---B---C---D
```

Commit C still exists as part of branch history.

The tag reference was deleted.

This is another reminder:

```text
Tag
!=
Commit
```

---

# 39. Tags and Software Versions

So far, we have used names such as:

```text
v1.0.0
v1.1.0
v1.1.1
```

Why this pattern?

One widely used versioning specification is:

```text
Semantic Versioning
```

often abbreviated:

```text
SemVer
```

Its core format is:

```text
MAJOR.MINOR.PATCH
```

Example:

```text
2.7.4
```

means:

```text
MAJOR = 2

MINOR = 7

PATCH = 4
```

---

# 40. What Semantic Versioning Tries to Communicate

Version numbers should communicate information.

Instead of:

```text
release-final

release-final2

release-final-real

new-version

latest-fixed

final-final
```

you can have:

```text
1.0.0

1.1.0

1.1.1

2.0.0
```

When a project follows SemVer correctly, version changes communicate compatibility information about its public API.

---

# 41. MAJOR.MINOR.PATCH

The core rule is:

```text
MAJOR.MINOR.PATCH
```

At a beginner level:

```text
MAJOR
    incompatible public API changes

MINOR
    backward-compatible functionality

PATCH
    backward-compatible bug fixes
```

Example:

```text
1.4.7
```

contains:

```text
Major: 1
Minor: 4
Patch: 7
```

---

# 42. Patch Version

Suppose current version:

```text
1.4.7
```

contains a bug.

You fix the incorrect behavior without breaking compatibility.

The next version may be:

```text
1.4.8
```

Conceptually:

```text
1.4.7
   |
   | backward-compatible bug fix
   v
1.4.8
```

The patch number increased.

---

# 43. Minor Version

Suppose:

```text
1.4.8
```

is current.

You add backward-compatible functionality.

The next version may become:

```text
1.5.0
```

Notice:

```text
MINOR

4 -> 5
```

and:

```text
PATCH

8 -> 0
```

Conceptually:

```text
1.4.8
   |
   | backward-compatible functionality
   v
1.5.0
```

---

# 44. Major Version

Suppose:

```text
1.5.0
```

is current.

You introduce an incompatible change to the public API.

The next version may become:

```text
2.0.0
```

Conceptually:

```text
1.5.0
   |
   | incompatible public API change
   v
2.0.0
```

Minor and patch reset:

```text
1.5.0
   |
   v
2.0.0
```

---

# 45. Semantic Versioning Table

| Change | Example           | Meaning                           |
| ------ | ----------------- | --------------------------------- |
| Patch  | `1.4.7` → `1.4.8` | Backward-compatible bug fix       |
| Minor  | `1.4.8` → `1.5.0` | Backward-compatible functionality |
| Major  | `1.5.0` → `2.0.0` | Incompatible public API change    |

Do not choose the number merely based on:

```text
How much code changed.
```

A one-line change could be breaking.

A thousand-line internal refactor might not change the public API.

SemVer communicates compatibility, not effort.

---

# 46. What Is a Public API?

Semantic Versioning depends heavily on the idea of:

```text
public API
```

Do not interpret API as only:

```text
REST API
```

A project's public API is the documented interface consumers depend on.

Depending on the project, that might include:

```text
Functions

Classes

Command-line arguments

Configuration formats

Network endpoints

Library methods

File formats

Protocols

Module interfaces
```

The project should define what its public API is.

Without that understanding, Semantic Versioning becomes difficult to apply consistently.

---

# 47. What Does `1.0.0` Mean?

Under Semantic Versioning:

```text
1.0.0
```

is important.

Version:

```text
1.0.0
```

defines the public API.

Before that, versions may use:

```text
0.y.z
```

for initial development.

For example:

```text
0.1.0
0.2.0
0.9.0
```

Major version zero indicates initial development, where the public API should not yet be treated as stable.

---

# 48. Why Git Tags Often Use `v`

Semantic Versioning itself describes versions such as:

```text
1.0.0
```

Git repositories frequently name tags:

```text
v1.0.0
```

The leading:

```text
v
```

means:

```text
version
```

So:

```text
v1.0.0
```

means:

```text
version 1.0.0
```

This is a common Git tag naming convention.

Your team should use a consistent convention.

# 49. Version Progression Example

Imagine Server Monitor evolves like this:

```text
v0.1.0
    Initial development

v0.2.0
    Add configurable endpoints

v0.3.0
    Add health reporting

v1.0.0
    Stable public interface

v1.1.0
    Add backward-compatible JSON output

v1.1.1
    Fix timeout bug

v1.1.2
    Fix status-code handling bug

v2.0.0
    Introduce incompatible configuration format
```

This tells a much clearer story than:

```text
release1
release2
new
new-fixed
final
final2
```

# 50. Pre-Release Versions

Semantic Versioning also supports pre-release identifiers.

Examples:

```text
1.0.0-alpha

1.0.0-beta

1.0.0-rc.1
```

These indicate versions that come before the normal release.

For example:

```text
1.0.0-beta
```

might represent a beta version.

```text
1.0.0-rc.1
```

might represent release candidate 1.

Pre-release versions have lower precedence than the corresponding normal version.

For beginners, the main sequence to understand is:

```text
Development
   |
   v
1.0.0-alpha
   |
   v
1.0.0-beta
   |
   v
1.0.0-rc.1
   |
   v
1.0.0
```

Exact organizational naming practices vary.

---

# 51. Build Metadata

Semantic Versioning also supports build metadata.

Example:

```text
1.0.0+build.42
```

or:

```text
1.0.0+20260901
```

Build metadata follows:

```text
+
```

It can provide additional build information.

It does not change version precedence in the same way major, minor, patch, and pre-release identifiers do.

For beginner Git release workflows, you may not need build metadata immediately.

But you should recognize the syntax.

---

# 52. Version Numbers Are Policy

Git does not look at your code and decide:

```text
This should be v2.0.0.
```

Git has no understanding of:

```text
Breaking API change

Feature

Bug fix
```

Your project or team decides the version according to its versioning policy.

Then Git records the chosen version as a tag.

Conceptually:

```text
Engineering change
       |
       v
Versioning decision
       |
       v
Version number
       |
       v
Git tag
```

---

# 53. Git Tag vs Software Version

These are related but not identical concepts.

```text
Software version
    Logical release identity

Git tag
    Git reference identifying repository history
```

A common mapping is:

```text
Software version 1.4.0
        |
        v
Git tag v1.4.0
        |
        v
Commit 7f1a92c
```

This creates traceability.

---

# 54. What Is a Software Release?

A release is a packaged, identifiable version of software made available for use or deployment.

A release may include:

```text
Version number

Source code

Compiled binaries

Container images

Packages

Release notes

Checksums

Installation files

Documentation
```

The exact contents depend on the project.

For a Python library, a release may publish a package.

For a Go application, it might publish compiled binaries.

For a containerized service, it may produce a container image.

For infrastructure code, the release may identify the exact Git revision approved for deployment.

---

# 55. Git Tag vs GitHub Release

These are not the same thing.

A Git tag exists in Git.

Example:

```text
v1.0.0
   |
   v
Commit C
```

A GitHub Release is a GitHub feature built around a tag.

Conceptually:

```text
Git History
    |
    v
Tag v1.0.0
    |
    v
GitHub Release
    |
    +--> Release title
    +--> Release notes
    +--> Source archives
    +--> Optional binary assets
```

GitHub Releases are based on Git tags.

---

# 56. Why GitHub Releases Exist

A raw tag tells us:

```text
This point in Git history is v1.0.0.
```

A GitHub Release can provide users with more context:

```text
What changed?

What was fixed?

What is new?

Are there breaking changes?

How do I upgrade?

Who contributed?

What files can I download?
```

This makes a release more useful to humans.

# 59. What Are Release Notes?

Release notes explain what changed in a release.

They are communication between:

```text
Engineering
```

and:

```text
Users
Operators
Developers
Customers
Other teams
```

Good release notes should answer:

```text
What changed?

Why does it matter?

Is anything breaking?

Do I need to change configuration?

Are there upgrade steps?

Were important bugs fixed?

Are there security implications?
```

---

# 60. Weak Release Notes

Bad:

```text
Various fixes and improvements.
```

This communicates very little.

Also weak:

```text
Merged PR #44
Merged PR #51
Merged PR #53
```

Those references may help maintainers, but users may not understand what actually changed.

---

# 61. Better Release Notes

```text
Server Monitor v1.4.0

New

- Added configurable retry limits for endpoint checks.
- Added JSON output for automation workflows.

Improved

- Health checks now report DNS failures separately from HTTP failures.
- Startup validation now detects missing configuration earlier.

Fixed

- Fixed a timeout bug affecting slow HTTPS endpoints.

Upgrade Notes

- No configuration changes are required.
```

This communicates user-visible impact.

---

# 62. Release Notes for Breaking Changes

Suppose:

```text
v2.0.0
```

changes configuration from:

```yaml
timeout: 5
```

to:

```yaml
request:
  timeout_seconds: 5
```

Release notes should not hide this.

Example:

```text
Breaking Change

The timeout configuration format has changed.

Old:

timeout: 5

New:

request:
  timeout_seconds: 5

Existing configuration files must be updated before upgrading.
```

Breaking changes deserve prominent documentation.

# 63. Automatically Generated Release Notes

GitHub can generate release notes based on repository activity such as merged pull requests and contributors.

This can save time.

But automatically generated notes should still be reviewed.

Why?

Because a useful release note is not merely:

```text
Everything GitHub detected.
```

It should communicate what matters to users.

A human may need to add:

```text
Breaking changes

Migration steps

Security notes

Operational warnings
```

# 64. Source Archives

GitHub automatically provides source-code archives for releases/tags.

Common formats include:

```text
.zip

.tar.gz
```

These archives contain the repository contents corresponding to the tag.

Conceptually:

```text
v1.2.0
   |
   v
Repository state
   |
   +--> Source code (zip)
   |
   +--> Source code (tar.gz)
```

This lets users obtain the source for a specific tagged version without performing a normal Git clone.

---

# 65. Source Archive vs Git Clone

A source archive is not the same as cloning the repository.

When you:

```bash
git clone ...
```

you receive a Git repository containing Git metadata and history according to the clone operation.

When someone downloads:

```text
Source code (zip)
```

they primarily receive a snapshot of repository contents for that tag.

They do not receive the normal `.git` history database as part of that archive.

Think:

```text
Clone
    Repository + Git history/metadata

Archive
    Files from a particular repository state
```

# 68. Hotfix Concepts

Suppose production runs:

```text
v1.4.0
```

Then a serious bug appears.

Meanwhile development on `main` has continued:

```text
v1.4.0
   |
   v
Production

main
   |
   v
unfinished v1.5.0 work
```

You may need to fix production without releasing all unfinished work.

This is where a hotfix workflow can be useful.

---

# 69. What Is a Hotfix?

A hotfix is an urgent correction to a released version, often for:

```text
Production failure

Critical bug

Security issue

Data corruption risk

Major customer-impacting defect
```

Suppose:

```text
v1.4.0
```

contains a timeout bug.

You fix only that problem.

The next patch version might be:

```text
v1.4.1
```

Conceptually:

```text
v1.4.0
   |
   | critical bug fix
   v
v1.4.1
```

---

# 70. Hotfix Branch Example

Suppose history:

```text
A---B---C---D---E---F
        ^           ^
     v1.4.0        main
```

Commits D, E, and F contain unfinished work for the next release.

You may create a hotfix branch from:

```text
v1.4.0
```

For example:

```bash
git switch -c hotfix/timeout v1.4.0
```

Now:

```text
A---B---C---D---E---F
        ^           ^
     v1.4.0        main
        \
         H
         ^
  hotfix/timeout
```

Commit H contains the production fix.

---

# 71. Tagging the Hotfix

After testing and approval:

```bash
git tag -a v1.4.1 -m "Release version 1.4.1"
```

Then:

```bash
git push origin v1.4.1
```

The exact branch integration strategy depends on the team's workflow.

The fix should generally also be integrated into the continuing development line so the same bug does not reappear later.

---

# 72. Do Not Treat Every Bug as a Hotfix

A hotfix usually implies urgency around an already released version.

A typo in a development branch that has never been released is simply normal development.

Use release terminology meaningfully.

# 74. Step 1: Confirm the Working Tree

Before a release:


```text
Untracked files

Unexpected staged changes
```

Depending on your team workflow:

```bash

```

```bash

```


```text

Remote-tracking branch

Release target
```

For example:

```text

Integration tests

Linting

Security scanning

Build validation

Configuration validation

Infrastructure plan

Container image scan
```

The exact checks depend on the project.

For our beginner project:

```bash

```

might be one validation step.

A production project may require much more.

---

# 77. Step 4: Identify the Exact Commit

```text
72bd920 Fix timeout handling
```

Inspect:

```bash
git show 91ad703
```

Verify that this is the intended release commit.

# 78. Step 5: Choose the Version

```text

```

and the team has decided the public API is ready.

The release might become:

```text
v1.0.0
```

This is a versioning decision.

Git does not make the decision for you.

```text
Correct annotation
```

# 80. Step 7: Push the Tag


# 86. GitHub Actions Tag Trigger Example

Much clearer.

# 96. Release Branches vs Release Tags

Some teams use branches such as:

```text
release/1.5
```

Do not confuse that with:

```text
v1.5.0
```

A release branch may continue receiving commits.

For example:

```text
release/1.5
```

could later contain fixes for:

```text
v1.5.0
v1.5.1
v1.5.2
```

Conceptually:

```text
release/1.5
      |
      +--> v1.5.0
      |
      +--> v1.5.1
      |
      +--> v1.5.2
```

The branch moves.

Each release tag normally remains fixed.

# 97. Common Mistake: Using a Branch as a Release Identifier

Someone says:

```text
Production runs main.
```

That is weak version identification because `main` moves.

Better:

```text
Production runs commit 91ad703,
released as v2.3.1.
```

Now the version is precise.

---

# 98. Common Mistake: Creating a Tag on the Wrong Commit

You intend:

```text
v1.0.0 -> C
```

but accidentally tag:

```text
D
```

because your working branch was ahead.

Prevention:

```bash
git status
git log --oneline --decorate
git show <target>
```

before tagging.

Never assume HEAD is automatically the correct release commit.

---

# 99. Common Mistake: Forgetting to Push the Tag

Local:

```text
v1.0.0 exists
```

GitHub:

```text
v1.0.0 missing
```

Fix:

```bash
git push origin v1.0.0
```

Then verify remotely.

---

# 100. Common Mistake: Assuming `git push` Always Pushes Tags

A normal branch push such as:

```bash
git push origin main
```

does not mean every local tag is automatically published.

Treat branch publishing and tag publishing as distinct operations unless your chosen push options/workflow explicitly handle tags.

---

# 101. Common Mistake: Tagging Uncommitted Work

Suppose:

```bash
git status
```

shows:

```text
modified: src/app.py
```

You create:

```bash
git tag v1.0.0
```

The tag identifies a Git object, usually the current commit.

Your uncommitted working-tree changes are not part of that tagged commit.

This is another reason to verify:

```bash
git status
```

before releasing.

---

# 102. Common Mistake: Moving a Published Tag

Do not casually turn:

```text
v1.0.0 -> C
```

into:

```text
v1.0.0 -> E
```

after people have consumed the original tag.

Create a new release identifier instead when appropriate.

Release tags should provide confidence.

---

# 103. Common Mistake: Version Numbers Based on Emotion

Bad versioning:

```text
This update feels huge.

Let's call it 5.0.
```

Semantic Versioning is about compatibility with a defined public API.

Ask:

```text
Did we introduce an incompatible public API change?

Did we add backward-compatible functionality?

Did we make a backward-compatible bug fix?
```

Then choose the version according to your documented policy.

---

# 104. Common Mistake: Thinking Patch Means Small Code Change

A patch release means:

```text
Backward-compatible bug fix
```

under SemVer.

It does not mean:

```text
Only five lines changed.
```

Version meaning is about compatibility, not line count.

---

# 105. Common Mistake: Thinking Major Means Big Project

Version:

```text
10.0.0
```

does not mean:

```text
This application is enormous.
```

Major versions communicate incompatible public API changes under SemVer.

A small library could reach:

```text
8.0.0
```

after several generations of breaking API changes.

---

# 106. Common Mistake: Poor Release Notes

Bad:

```text
Fixed things.
```

Better:

```text
Fixed a timeout bug that caused endpoint checks
to fail after 30 seconds.
```

Good release notes communicate impact.

---

# 107. Common Mistake: Rebuilding an Old Version From New Source

Suppose:

```text
v1.0.0 -> Commit C
```

Do not build current `main` and simply name the resulting artifact:

```text
1.0.0
```

That breaks provenance.

Release artifacts should correspond to the source revision they claim to represent.

---

# 108. Common Mistake: Assuming a Tag Means Tests Passed

A Git tag itself does not guarantee:

```text
Tests passed

Security scan passed

Build succeeded

Release was approved

Production deployment succeeded
```

A tag is a Git reference.

Your release process provides the quality gates around it.

---

# 109. Troubleshooting: `git tag` Shows Nothing

Problem:

```bash
git tag
```

returns nothing.

Possible cause:

```text
No tags exist locally.
```

Investigate:

```bash
git log --oneline --decorate
```

If you expected remote tags:

```bash
git fetch --tags
```

Then:

```bash
git tag
```

---

# 110. Troubleshooting: Tag Already Exists

You run:

```bash
git tag v1.0.0
```

and Git reports that the tag already exists.

Do not immediately force it.

Inspect:

```bash
git show v1.0.0
```

Ask:

```text
Does this existing tag already identify the correct release?

Was it published?

Is someone using it?
```

If it is an established release, do not casually replace it.

---

# 111. Troubleshooting: Tag Points to Wrong Commit

First determine whether the tag has been published.

If it is purely local and unused, correcting it may be straightforward.

If it is already published and consumed, prefer creating a new version rather than silently changing history.

The safe principle is:

```text
Distribution increases the cost of rewriting identity.
```

# 134. Part 16 Final Recap

The central Git model is:

```text
BRANCH

A---B---C---D---E
                ^
               main

main moves.
```

Compared with:

```text
TAG

A---B---C---D---E
        ^       ^
     v1.0.0    main

v1.0.0 stays associated with C.
```

The two main tag types are:

```text
Lightweight
    |
    v
Simple reference to an object
```

and:

```text
Annotated
    |
    v
Tag object
    |
    +--> Tagger
    +--> Date
    +--> Message
    +--> Optional signature
    |
    v
Target object
```

A basic release workflow becomes:

```text
Develop
   |
   v
Review
   |
   v
Test
   |
   v
Approve exact commit
   |
   v
Choose version
   |
   v
Create annotated tag
   |
   v
Verify tag
   |
   v
Push tag
   |
   v
CI/CD build
   |
   v
Release artifacts
   |
   v
GitHub Release
   |
   v
Deploy
   |
   v
Verify
```

Semantic Versioning provides the model:

```text
MAJOR.MINOR.PATCH
```

For example:

```text
1.4.7
```

A backward-compatible bug fix can become:

```text
1.4.8
```

A backward-compatible feature can become:

```text
1.5.0
```

An incompatible public API change can become:

```text
2.0.0
```

A Git tag can then connect that logical software version to exact history:

```text
Software Version
      |
      v
     2.0.0
      |
      v
Git Tag v2.0.0
      |
      v
Commit 91ad703
```

GitHub can build another layer around that tag:

```text
Commit
   |
   v
Tag
   |
   v
GitHub Release
   |
   +--> Release notes
   +--> Source archive
   +--> Binary assets
```

And DevOps automation can extend the chain:

```text
Git Commit
    |
    v
Git Tag
    |
    v
CI/CD Pipeline
    |
    v
Build Artifact
    |
    v
Container / Package / Binary
    |
    v
Deployment
    |
    v
Production
```

That gives engineers one of the most important properties of a mature release process:

```text
TRACEABILITY
```

When production fails, the question should not be:

```text
Which code do we think is running?
```

The team should be able to establish:

```text
Production version
      |
      v
Artifact
      |
      v
Release
      |
      v
Git tag
      |
      v
Commit
      |
      v
Exact source
```

That is why tags are much more than convenient labels.

They connect Git history to software versions, releases, CI/CD pipelines, deployment systems, incident investigation, and production operations.
