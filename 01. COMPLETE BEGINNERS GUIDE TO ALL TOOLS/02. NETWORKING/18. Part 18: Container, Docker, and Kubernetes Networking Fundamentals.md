# Part 18: Container, Docker, and Kubernetes Networking Fundamentals

## Understand Networking When Applications Run Inside Containers

Container networking can initially feel like networking has changed completely.

Suddenly you see:

```text
Containers
Namespaces
veth interfaces
Bridges
Container IPs
Pod IPs
Services
ClusterIP
NodePort
Ingress
CNI
NetworkPolicy
```

But the fundamentals from the previous parts still apply:

```text
IP addresses
Interfaces
Routes
MAC addresses
ARP / Neighbor Discovery
TCP and UDP
Ports
DNS
NAT
Firewalls
Load balancing
Packet flow
```

Containers add **additional virtual networking layers**.

The most important mindset for this part is:

> Do not memorize Docker and Kubernetes networking as magic. Follow the packet from one network namespace to another.

A traditional application might look like:

```text
Physical/Virtual Server
10.20.1.10
     |
     +--> Application :8080
```

Docker introduces another networking environment:

```text
Host
10.20.1.10
     |
     +--> Docker Bridge
             |
             +--> Container
                  172.17.0.2:8080
```

Kubernetes adds another abstraction:

```text
Node
10.20.1.10
     |
     +--> Pod
     |    10.244.1.20
     |
     +--> Pod
          10.244.1.21

Service
10.96.20.50
     |
     +--> Pod 10.244.1.20
     +--> Pod 10.244.2.30
```

Understanding those layers is the goal of Part 18.

---

# 1. Why Container Networking Is Different

Before containers, imagine an application running directly on a Linux server:

```text
Server
10.20.1.10
     |
     v
Application
TCP 8080
```

The application uses the host's networking stack.

You inspect it with:

```bash
ip addr
ip route
ss -lntp
```

Now run the application inside a container.

The application may see:

```text
eth0
172.17.0.2
```

while the host sees:

```text
eth0
10.20.1.10

docker0
172.17.0.1
```

These are different network environments.

---

# 2. Containers Need Network Isolation

Containers are isolated processes.

Linux can isolate resources including:

```text
Processes
Filesystems
Users
Hostnames
Networking
```

Network isolation is largely provided through:

```text
Network namespaces
```

This is one of the most important Linux concepts behind container networking.

---

# 3. What Is a Network Namespace?

A Linux network namespace provides an isolated network stack.

A namespace can have its own:

```text
Network interfaces
IP addresses
Routing table
ARP/neighbor table
Firewall state/rules
Sockets
Loopback interface
```

Conceptually:

```text
Host Network Namespace
|
+-- eth0
|   10.20.1.10
|
+-- routes
|
+-- sockets


Container Network Namespace
|
+-- eth0
|   172.17.0.2
|
+-- routes
|
+-- sockets
```

The container does not simply inherit every host network object.

---

# 4. Network Namespace Mental Model

Imagine two Linux computers:

```text
Computer A             Computer B

eth0                   eth0
192.168.1.10            192.168.1.20
```

Now imagine both network stacks exist inside one Linux machine:

```text
Linux Host
|
+-- Namespace A
|      |
|      +-- interfaces
|      +-- routes
|      +-- sockets
|
+-- Namespace B
       |
       +-- interfaces
       +-- routes
       +-- sockets
```

They still need some mechanism to communicate.

That is where virtual Ethernet interfaces become useful.

---

# Virtual Ethernet Interfaces

# 5. What Is a veth Pair?

Linux provides virtual Ethernet devices commonly called:

```text
veth pairs
```

A veth pair consists of two connected virtual interfaces.

Think of it as a virtual cable:

```text
veth-A <================> veth-B
```

A packet entering one side appears on the other.

---

# 6. Connecting a Container Namespace

One end can remain in the host namespace:

```text
Host
|
+-- veth123
```

The other end can be moved into the container namespace:

```text
Container
|
+-- eth0
```

Conceptually:

```text
Container Namespace            Host Namespace

eth0
 |
 | virtual Ethernet pair
 |
 +-------------------------- veth123
```

Container runtimes normally hide much of this setup from you.

---

# 7. Why the Container Calls It `eth0`

Inside a typical container, you may run:

```bash
ip addr
```

and see something like:

```text
1: lo
2: eth0
```

The interface presented inside the container may be named:

```text
eth0
```

while its peer on the host has another generated name.

These interfaces are connected through the veth pair.

---

# Bridges

# 8. What Is a Linux Bridge?

A Linux bridge is a software Layer 2 networking construct.

Conceptually, it behaves similarly to an Ethernet switch.

```text
                Linux Bridge
              +--------------+
              |              |
              +--+--------+--+
                 |        |
                 |        |
               veth1    veth2
                 |        |
                 v        v
             Container A Container B
```

This allows multiple virtual interfaces to participate in the same Layer 2 network.

---

# 9. Bridge Networking Mental Model

Think:

```text
Physical Ethernet:

PC-A
 |
Switch
 |
PC-B
```

Virtualized:

```text
Container-A
 |
veth
 |
Linux Bridge
 |
veth
 |
Container-B
```

The same Layer 2 principles still matter.

---

# Docker Bridge Networking

# 10. Docker's Default Bridge Concept

A typical Docker installation creates a bridge network.

Historically, the host-side bridge commonly appears as:

```text
docker0
```

Inspect it with:

```bash
ip addr show docker0
```

You might see:

```text
172.17.0.1/16
```

The exact configuration can differ.

---

# 11. Docker Container Addresses

Containers connected to that network may receive addresses such as:

```text
Container A
172.17.0.2

Container B
172.17.0.3

Container C
172.17.0.4
```

Conceptually:

```text
                docker0
              172.17.0.1
             /     |      \
            /      |       \
           v       v        v

       172.17.0.2  .3       .4
       Container A B         C
```

---

# 12. Container IP Addresses

A container IP is an address assigned to the container's network interface within the relevant container network.

Inspect a Docker container:

```bash
docker inspect <container>
```

You can also inspect a network:

```bash
docker network inspect <network>
```

Do not assume container IP addresses are permanent application identities.

Containers can be destroyed and recreated.

Their addresses can change.

---

# 13. Why Hard-Coding Container IPs Is Usually a Mistake

Suppose:

```text
frontend -> 172.18.0.5
```

works today.

Then the backend container is recreated and receives:

```text
172.18.0.7
```

The hard-coded configuration fails.

Prefer service names and appropriate discovery mechanisms where available.

---

# 14. User-Defined Docker Networks

Docker can create user-defined networks.

Example:

```bash
docker network create app-network
```

Run containers on it:

```bash
docker run -d \
  --name backend \
  --network app-network \
  nginx
```

Another:

```bash
docker run -it \
  --name client \
  --network app-network \
  alpine
```

Containers on an appropriate user-defined network can use Docker-provided name resolution.

---

# 15. List Docker Networks

```bash
docker network ls
```

Typical output may include network drivers such as:

```text
bridge
host
none
```

plus user-created networks.

---

# 16. Inspect a Docker Network

```bash
docker network inspect app-network
```

This can reveal information such as:

```text
Subnet
Gateway
Connected containers
Container addresses
Network driver
```

This is one of the first commands to use when troubleshooting Docker networking.

---

# 17. Connect a Container to a Network

Existing containers can be connected to suitable Docker networks:

```bash
docker network connect app-network my-container
```

Disconnect:

```bash
docker network disconnect app-network my-container
```

Do not randomly change production container networks during troubleshooting.

Inspect the existing architecture first.

# Host Networking

# 18. What Is Host Networking?

With host networking, a container uses the host's network namespace rather than receiving the normal isolated network stack used by bridge networking.

Conceptually, instead of:

```text
Host
 |
 +--> Bridge
       |
       +--> Container 172.17.0.2
```

you have:

```text
Host Network Namespace
10.20.1.10
 |
 +--> Host processes
 |
 +--> Container process
```

---

# 19. Host Networking Changes Port Behavior

Suppose a container application listens on:

```text
TCP 8080
```

using host networking.

It is effectively using the host networking stack.

This means port conflicts become important.

If another process already uses:

```text
0.0.0.0:8080
```

the containerized application cannot simply claim the same socket.

---

# 20. Host Networking Reduces Isolation

Host networking can be useful in particular architectures.

But it reduces network isolation between the container and host.

Do not use it simply because bridge networking is not understood.

Fix the networking problem instead of bypassing the networking model.

---

# Port Publishing

# 21. The Container Reachability Problem

Suppose your Docker host is:

```text
10.20.1.10
```

and the container is:

```text
172.17.0.2
```

with NGINX listening on:

```text
172.17.0.2:80
```

A remote client knows:

```text
10.20.1.10
```

not necessarily how to directly reach:

```text
172.17.0.2
```

Docker can publish the container service through a host port.

---

# 22. Docker Port Publishing

Example:

```bash
docker run -d -p 8080:80 nginx
```

Conceptually:

```text
Client
   |
   | TCP 8080
   v
Docker Host
10.20.1.10:8080
   |
   | Docker forwarding/NAT behavior
   v
Container
:80
```

---

# 23. Understanding `8080:80`

In:

```bash
-p 8080:80
```

think:

```text
HOST PORT : CONTAINER PORT
```

Therefore:

```text
8080 -> 80
```

A client connects to:

```text
10.20.1.10:8080
```

while the application inside the container listens on:

```text
:80
```

---

# 24. Port Mapping Does Not Change the Application's Listening Port

If NGINX listens inside the container on:

```text
80
```

publishing:

```text
8080:80
```

does not make NGINX itself listen internally on 8080.

The mapping occurs outside the application.

---

# 25. Inspect Published Ports

Run:

```bash
docker ps
```

You might see:

```text
0.0.0.0:8080->80/tcp
```

You can also use:

```bash
docker port <container>
```

---

# 26. Binding Published Ports Carefully

Consider:

```bash
docker run -d -p 8080:80 nginx
```

versus:

```bash
docker run -d -p 127.0.0.1:8080:80 nginx
```

The second explicitly binds the published port to host loopback.

That can be useful when the service should only be reachable locally through the host.

Do not publish services broadly unless required.

---

# 27. Container Port vs Published Port

This distinction is critical.

```text
Container port:
Where the application listens inside the container.

Published host port:
Where external clients reach that container through the host.
```

Example:

```text
Browser
 |
 | 8080
 v
Host
 |
 | mapping
 v
Container
 |
 | 80
 v
NGINX
```

---

# Container-to-Container Communication

# 28. Containers on the Same Network

Suppose:

```text
frontend
backend
```

are connected to:

```text
app-network
```

The frontend can often communicate directly with the backend using its container-network address or, preferably, an appropriate Docker DNS name.

Conceptually:

```text
Frontend
   |
   v
Docker Network
   |
   v
Backend
```

You do not normally need to publish the backend port to the host merely for containers on the same network to communicate.

---

# 29. Publishing Is Not Required for Every Container

Suppose:

```text
Frontend -> Backend -> Database
```

Only the frontend may need external exposure.

Conceptually:

```text
Internet
   |
   | Published port
   v
Frontend
   |
   | Internal Docker network
   v
Backend
   |
   | Internal Docker network
   v
Database
```

Publishing every container port increases unnecessary exposure.

---

# 30. Docker Network Isolation

Containers on different Docker networks may not communicate directly unless the architecture connects them appropriately.

Example:

```text
Network A                Network B

Frontend                 Database
   |                        |
   X------------------------X
```

A container can also be attached to multiple networks when deliberately required.

---

# Container-to-Host Communication

# 31. Container Reaching the Host

This can be confusing because:

```text
127.0.0.1
```

inside the container normally means:

```text
The container itself
```

not the host.

This is the same principle you learned earlier:

> Loopback belongs to the current network namespace.

---

# 32. Classic `localhost` Mistake

Suppose PostgreSQL runs directly on the Docker host:

```text
Host
10.20.1.10
PostgreSQL :5432
```

Inside a container, the application is configured:

```text
DB_HOST=127.0.0.1
```

The application tries:

```text
Container -> Container's own loopback
```

not:

```text
Container -> Host PostgreSQL
```

The connection fails.

---

# 33. Container-to-Host Access Is Platform-Dependent

The appropriate mechanism for reaching host services from containers depends on:

```text
Operating system
Docker environment
Network driver
Host configuration
```

For example, Docker environments may provide special hostnames such as `host.docker.internal` in supported configurations.

Do not assume the same host-access mechanism exists identically everywhere.

---

# Docker DNS

# 34. Why Docker Needs DNS

Suppose:

```text
frontend
```

needs:

```text
backend
```

Hard-coding:

```text
172.18.0.5
```

is fragile.

Docker networking can provide name resolution for containers on appropriate user-defined networks.

The frontend can use:

```text
backend
```

instead.

---

# 35. Example Docker Service Discovery

```text
Docker Network: app-network

frontend
172.18.0.2

backend
172.18.0.3
```

Frontend application connects to:

```text
http://backend:8080
```

Docker's networking/DNS mechanisms resolve:

```text
backend
```

to the appropriate container-network address.

---

# 36. Test Docker DNS

Inside a suitable container:

```bash
getent hosts backend
```

or, if DNS tools are installed:

```bash
nslookup backend
```

You can also test the application directly:

```bash
curl http://backend:8080
```

Remember that minimal container images may not include common diagnostic commands.

---

```bash
docker network ls
```

```bash

```

```bash

```

```bash

```




# 38. Minimal Images Complicate Troubleshooting

A production container may not contain:

```text
ping
curl
dig
ip
ss
tcpdump
```

This does not mean networking is broken.

It may simply be a minimal image.

Avoid permanently bloating production images with troubleshooting packages merely for convenience.

Use appropriate debugging mechanisms.

# Docker Packet Flow

# 39. External Client to Docker Container

Suppose:

```bash
docker run -d -p 8080:80 nginx
```

Host:

```text
10.20.1.10
```

Container:

```text
172.17.0.2
```

Client requests:

```text
10.20.1.10:8080
```

Simplified flow:

```text
Client
192.168.1.50
     |
     | TCP destination 10.20.1.10:8080
     v
Docker Host
10.20.1.10
     |
     | Docker networking/port publishing
     v
Container
172.17.0.2:80
     |
     v
NGINX
```

Return traffic is handled according to the host/container networking and connection-tracking behavior.

---

# 40. Container Outbound Internet Flow

Container:

```text
172.17.0.2
```

requests:

```text
https://example.com
```

Simplified:

```text
Container
172.17.0.2
     |
     v
Docker Bridge
     |
     v
Host routing/NAT
     |
     v
Host interface
10.20.1.10
     |
     v
Default Gateway
     |
     v
Internet
```

There can be multiple layers of NAT.

For example, a cloud VM running Docker might produce:

```text
Container
172.17.0.2
     |
     v
Docker Host
10.20.11.25
     |
     v
Cloud NAT

     |
     v
Internet
```

# Kubernetes Networking

# 41. Why Kubernetes Networking Is More Complex

Docker on one machine is already virtualized networking.

Kubernetes introduces:

```text
Multiple nodes
Pods
Pod IPs
Services
Cluster DNS
Load balancing
Ingress
Network policies
CNI plugins
```

A packet may travel:

```text
Internet
   |
   v
Cloud Load Balancer
   |
   v
Kubernetes Node
   |
   v
Service
   |
   v
Pod
```

Understanding each layer separately makes Kubernetes networking much easier.

---

# 42. Kubernetes Networking Model

At a conceptual level, Kubernetes networking aims to provide connectivity so Pods can communicate using their Pod addresses according to the cluster's networking implementation and policy.

A simplified model:

```text
Node A                         Node B

Pod A                          Pod C
10.244.1.10                    10.244.2.10

Pod B                          Pod D
10.244.1.11                    10.244.2.11
```

Pod A should be able to communicate with Pod C through the cluster network without the application needing to manually understand which node hosts Pod C.

The implementation is provided by the cluster networking system.

---

# Pods and Pod IPs

# 43. What Is a Pod?

A Pod is Kubernetes' basic workload scheduling unit.

A Pod can contain:

```text
One container
```

or:

```text
Multiple closely related containers
```

Containers inside the same Pod share important namespaces, including the Pod's network namespace.

---

# 44. Containers in the Same Pod Share Networking

Suppose:

```text
Pod
10.244.1.20
 |
 +--> Application container
 |
 +--> Sidecar container
```

Both share the Pod's network namespace.

Therefore they share:

```text
Pod IP
Network interfaces
Port space
Loopback
```

---

# 45. Same-Pod Communication

Two containers in the same Pod can communicate through:

```text
localhost
```

Example:

```text
Application Container
localhost:15000
       |
       v
Sidecar Container
```

This is very different from two separate Docker containers with separate network namespaces.

---

# 46. Same-Pod Port Conflicts

Because containers in the same Pod share the network namespace, they cannot independently bind the same IP/port combination.

If Container A already listens on:

```text
0.0.0.0:8080
```

Container B in the same Pod cannot normally bind the same socket.

---

# 47. Pod IP

A Pod typically receives an IP address from the cluster networking system.

Example:

```text
Pod-A
10.244.1.20
```

Inspect:

```bash
kubectl get pods -o wide
```

You may see:

```text
NAME        IP            NODE
frontend    10.244.1.20   node-a
backend     10.244.2.15   node-b
```

---

# 48. Pod IPs Are Ephemeral

Suppose:

```text
backend
10.244.2.15
```

is deleted.

A replacement Pod might receive:

```text
10.244.1.37
```

Therefore applications should not generally hard-code Pod IP addresses.

Kubernetes Services solve this problem.

---

# Node Networking

# 49. What Is a Kubernetes Node?

A node is a machine that runs Kubernetes workloads.

It may be:

```text
Physical server
Virtual machine
Cloud instance
```

Example:

```text
Node A
10.20.11.10

Node B
10.20.12.10
```

Pods run on those nodes.

---

# 50. Node IP vs Pod IP

Do not confuse them.

Example:

```text
Node A
10.20.11.10
 |
 +--> Pod A
      10.244.1.20
```

The node and Pod have different networking identities.

---

# 51. Node-to-Pod Relationship

Conceptually:

```text
Cloud / Physical Network
          |
          v
Node
10.20.11.10
          |
          v
CNI Networking
          |
          v
Pod
10.244.1.20
```

The exact implementation depends heavily on the CNI and infrastructure.

---

# Pod-to-Pod Communication

# 52. Same-Node Communication

Suppose:

```text
Node A
 |
 +--> Pod A
 |    10.244.1.20
 |
 +--> Pod B
      10.244.1.21
```

The node's container networking implementation provides the path between them.

Conceptually:

```text
Pod A
 |
 v
Virtual networking
 |
 v
Pod B
```

---

# 53. Cross-Node Communication

Now:

```text
Node A                     Node B

Pod A                      Pod B
10.244.1.20                10.244.2.30
```

Communication requires the cluster network to provide a path across nodes.

Conceptually:

```text
Pod A
10.244.1.20
   |
   v
Node A
   |
   v
Cluster/underlay/overlay network
   |
   v
Node B
   |
   v
Pod B
10.244.2.30
```

---

# 54. How Cross-Node Networking Is Implemented

Different CNI implementations may use approaches involving:

```text
Native routing
Overlay networks
Encapsulation
Cloud-native routing
eBPF
Linux bridges
Virtual interfaces
```

Do not assume every Kubernetes cluster moves Pod traffic the same way.

The Kubernetes networking model defines desired connectivity behavior.

The CNI implementation helps provide it.

# Services

# 55. Why Kubernetes Services Exist

Imagine a Deployment with three backend Pods:

```text
backend-1
10.244.1.20

backend-2
10.244.2.21

backend-3
10.244.3.22
```

Pods are replaced frequently.

A client should not need to track all Pod IPs manually.

Instead:

```text
Client
   |
   v
Service
   |
   +--> backend-1
   +--> backend-2
   +--> backend-3
```

---

# 56. What Is a Kubernetes Service?

A Service provides a stable network abstraction for a set of matching backend endpoints.

The Service typically uses labels/selectors to identify appropriate Pods, depending on Service configuration.

Example:

```yaml
selector:
  app: payments
```

Pods:

```yaml
labels:
  app: payments
```

become eligible backend endpoints.

---

# 57. Service IP vs Pod IP

Suppose:

```text
Service:
10.96.20.50

Pods:
10.244.1.20
10.244.2.21
10.244.3.22
```

The application connects to:

```text
10.96.20.50
```

rather than tracking every Pod address.

---

# 58. A ClusterIP Is Usually Virtual

This is important.

A Service ClusterIP is generally not an ordinary IP assigned to a physical interface like:

```text
eth0
```

Kubernetes networking components implement the Service forwarding abstraction.

Depending on the environment, this may involve technologies such as:

```text
iptables
IPVS
eBPF
```

or other implementations.

Do not troubleshoot ClusterIP as though it were simply another server NIC.

---

# ClusterIP

# 59. What Is ClusterIP?

`ClusterIP` is the default Kubernetes Service type.

It provides an address reachable within the cluster according to cluster networking.

Example:

```text
payments Service
10.96.20.50:8080
```

Clients inside the cluster can use the Service rather than individual Pod addresses.

---

# 60. ClusterIP Flow

```text
Frontend Pod
10.244.1.10
      |
      | payments:8080
      v
ClusterIP
10.96.20.50:8080
      |
      v
Service forwarding
      |
      +--> 10.244.2.20:8080
      |
      +--> 10.244.3.20:8080
```

The Service gives clients a stable destination.

---

# 61. ClusterIP Is Normally Internal

A normal ClusterIP is not designed as a direct public Internet entry point.

For external exposure, other mechanisms may be used, including:

```text
NodePort
LoadBalancer
Ingress
Gateway-related architectures
```

depending on requirements.

---

A NodePort Service exposes a Service through a port on cluster nodes.

Conceptually:

```text
Client
   |
   v
Node IP : NodePort
   |
   v
Service
   |
   v
Pod
```

---

# 63. NodePort Example

Suppose:

```text
Node:
10.20.11.10

NodePort:
32080

Pod:
10.244.1.20:8080
```

Conceptually:

```text
10.20.11.10:32080
        |
        v
Kubernetes Service
        |
        v
10.244.1.20:8080
```

---

# 64. NodePort Is Not the Same as `containerPort`

This distinction causes many beginner mistakes.

You may have:

```text
containerPort:
8080

Service port:
80

targetPort:
8080

nodePort:
32080
```

Flow:

```text
Client
   |
   | 32080
   v
Node
   |
   v
Service port 80
   |
   v
targetPort 8080
   |
   v
Pod application :8080
```

---

# 65. `containerPort` Does Not Publish the Application

A Kubernetes Pod specification may declare:

```yaml
ports:
  - containerPort: 8080
```

This does not, by itself, create an externally reachable listener or Service.

The application must actually listen on the port.

And exposure requires appropriate networking resources.

# LoadBalancer Services

# 66. What Is `LoadBalancer`?

A Kubernetes Service of type:

```text
LoadBalancer
```

requests external load-balancing integration where the environment supports it.

This is especially common in cloud Kubernetes environments.

Conceptually:

```text
Internet
   |
   v
Cloud Load Balancer
   |
```

# 82. What Is Ingress?

Kubernetes Ingress is an API resource for describing HTTP/HTTPS routing rules.

For example:

```text
shop.example.com -> shop-service

api.example.com -> api-service
```

or path-based:


# 83. Ingress Resource Does Not Process Packets by Itself

This is extremely important.

Creating an Ingress object does not mean the Ingress API object itself becomes a reverse proxy.

You need an implementation that processes the configuration.

Traditionally this is an:

```text
Ingress Controller
```


The exact implementation matters greatly for troubleshooting.

# CNI

# 90. What Is CNI?

CNI stands for:

```text
Container Network Interface
```

CNI defines specifications/interfaces used by container runtimes and orchestration systems for configuring container networking.

In Kubernetes environments, CNI plugins provide critical Pod networking functionality.

---

# 91. What Does a CNI Plugin Help Do?

Depending on implementation, the CNI networking system may help:

```text
Create/configure Pod interfaces
Assign Pod addresses
Configure routes
Connect Pod namespaces
Enable cross-node communication
Integrate with cloud networking
Enforce network policy
```

Not every plugin implements every capability identically.

---

# 92. CNI Examples

Common Kubernetes networking implementations include projects such as:

```text
Calico
Cilium
Flannel
AWS VPC CNI
Azure CNI
```

They use different networking approaches and feature sets.

Do not assume troubleshooting steps for one CNI automatically apply to another.

---

# 93. Overlay Networking

Some implementations use overlay networking.

Conceptually:

```text

   |
   v
Encapsulation
   |
   v
Physical/Cloud Network
   |
   v
Decapsulation
   |
   v

```

The underlying network carries an encapsulated representation of the Pod traffic.

# 94. Native or Underlay-Aware Routing

Other architectures integrate Pod networking more directly with the underlying cloud or routed network.

Conceptually:

```text

   |
   v

   |
   v
Destination
```

```text

```

# 95. CNI Failure Impact

```text
Pods cannot obtain networking
Pods cannot communicate across nodes
New Pods remain unhealthy

Network policies behave unexpectedly
```

A CNI failure can therefore appear as many different application failures.

A Pod CIDR is address space used for Pod networking.

Example:


Individual nodes might receive portions:

```text

Node B:
10.244.2.0/24

Node C:
```

This is one conceptual model.

Exact allocation depends on the cluster networking implementation.

```text

10.244.0.0/16
```

and Kubernetes also uses:

```text
Pod CIDR
```

```text

```

```text

```

These addresses play different roles.

# 101. Default Pod Connectivity Can Be Too Permissive

Suppose:

```text
Frontend Pod
Backend Pod
Database Pod
Monitoring Pod
Unknown Pod
```

Without restrictive network policy and depending on cluster implementation, Pods may have broad ability to communicate.

Production environments often need more control.

---

# 102. What Is a NetworkPolicy?

Kubernetes NetworkPolicy is an API for describing allowed network communication for selected Pods.

Conceptually:

```text
Frontend
   |
   | allowed
   v
Backend
   |
   | allowed
   v
Database

Unknown Pod
   |
   X
Database
```

---

# 103. NetworkPolicy Requires Implementation Support

Creating NetworkPolicy resources only helps if the cluster networking implementation enforces them.

This is important.

Do not assume:

```text
NetworkPolicy object exists
```

therefore:

```text
Traffic is definitely being filtered.
```

Verify your CNI/network implementation supports the required policy behavior.

---

# 104. Ingress and Egress in NetworkPolicy

In NetworkPolicy terminology:

```text
Ingress
```

means traffic entering selected Pods.

```text
Egress
```

means traffic leaving selected Pods.

Do not confuse Kubernetes NetworkPolicy ingress traffic with the Kubernetes Ingress API resource.

They are different concepts.

# 105. Least-Privilege Pod Communication

Imagine:

```text
Frontend
Backend
Database
```

Desired:

```text

Backend  -> Database:5432
```

Undesired:

```text
Frontend -> Database:5432
```

A network policy architecture can help enforce this segmentation.

# 106. NetworkPolicy and DNS

Be careful with restrictive egress policies.

Suppose you deny nearly all egress from a Pod.

The application suddenly reports:

```text

```

Why?

Its DNS traffic may also have been blocked.

Network policies must account for required infrastructure dependencies such as DNS.

# Packet-Flow Walkthrough 1: Docker Client to Container

# 143. Architecture

```text
Laptop
192.168.1.50
     |
     v
Docker Host
10.20.1.10
     |
     v
Container
172.17.0.2
```

Docker:

```bash
docker run -d -p 8080:80 nginx
```

Client requests:

```text
http://10.20.1.10:8080
```

---

# 144. Flow

```text
1. Client determines 10.20.1.10 is destination.

2. Client routing selects appropriate next hop.

3. TCP connection targets:
   10.20.1.10:8080

4. Packet reaches Docker host.

5. Host Docker networking recognizes published port.

6. Traffic is forwarded/transformed toward:
   172.17.0.2:80

7. Container network receives packet.

8. NGINX listening on :80 processes request.

9. Response returns through container/host networking.

10. Client receives HTTP response.
```

---

# 145. Where Can It Fail?

```text
Client routing
External firewall
Host firewall
Port not published
Wrong host port
Container stopped
Wrong container port
Application not listening
Application bound incorrectly
Docker network failure
```

# Common Beginner Mistakes

# 187. Mistake: Thinking a Container Is a Tiny VM

Containers use operating-system isolation mechanisms and share the host kernel rather than behaving exactly like independent virtual machines.

This distinction matters for networking.

---

# 188. Mistake: Thinking Container `localhost` Means Host

It usually means the container's own network namespace.

---

# 189. Mistake: Thinking Pod `localhost` Means Node

It means the Pod's network namespace.

Containers within that same Pod share it.

---

# 190. Mistake: Hard-Coding Container IPs

Containers are replaceable.

Use appropriate name/service discovery mechanisms.

---

# 191. Mistake: Hard-Coding Pod IPs

Pods are ephemeral.

Use Kubernetes Services where appropriate.

---

# 192. Mistake: Publishing Every Docker Port

Internal container communication does not require every service to be exposed through the host.

Expose only what needs exposure.

---

# 193. Mistake: Confusing Host Port and Container Port

Remember:

```text
-p 8080:80

Host 8080
     |
     v
Container 80
```

---

# 194. Mistake: Thinking `containerPort` Exposes a Pod

It does not create a Service or public endpoint.

---

# 195. Mistake: Confusing Service `port` and `targetPort`

Remember:

```text
Client
 |
 v
Service port
 |
 v
targetPort
 |
 v
Pod application
```

---

# 196. Mistake: Thinking ClusterIP Is a Normal Interface Address

It is typically a virtual Service address implemented by cluster networking mechanisms.

---

# 197. Mistake: Thinking a Service Guarantees Backends

A Service can exist with:

```text
zero endpoints
```

Always inspect the endpoint relationship.

---

# 198. Mistake: Ignoring Pod Readiness

A Pod may exist but not be considered ready for normal Service traffic.

Check:

```bash
kubectl get pods
```

and inspect readiness.

---

# 199. Mistake: Confusing Kubernetes Ingress With NetworkPolicy Ingress

They are different.

```text
Ingress resource:
HTTP/HTTPS application routing.

NetworkPolicy ingress:
Traffic entering selected Pods.
```

---

# 200. Mistake: Thinking Ingress Works Without an Implementation

Ingress configuration requires an appropriate controller/implementation.

---

# 201. Mistake: Assuming All CNIs Work the Same Way

They do not.

Always identify the cluster networking implementation.

---

# 202. Mistake: Ignoring CIDR Overlap

Check:

```text
Cloud CIDR
Corporate CIDR
Pod CIDR
Service CIDR
VPN CIDR
Other cluster CIDRs
```

before connecting environments.

---

# 203. Mistake: Assuming NetworkPolicy Is Enforced Everywhere

The networking implementation must support the policy behavior.

---

# 204. Mistake: Blocking DNS With Egress Policies

A restrictive policy can unintentionally break name resolution.

---

# 205. Mistake: Blaming Kubernetes Before Testing the Node

If the node itself cannot reach the destination, a Pod may not be able to either.

Understand the complete infrastructure.

---

# 206. Mistake: Blaming the Application Before Testing Cross-Node Networking

If every application fails only when communicating across nodes, investigate the networking infrastructure.

---

# 207. Mistake: Restarting Everything

Restarting:

```text
Pods
Deployments
CoreDNS
CNI components
Nodes
```

without evidence can temporarily hide the issue and destroy useful diagnostic state.

Collect evidence first.

---

# 208. Mistake: Installing Debugging Tools Into Production Containers

Prefer disposable debugging containers/Pods or approved operational tooling where possible.

Keep production images minimal and controlled.

---

# 209. Mistake: Disabling Network Policies to Fix Production

Do not remove security controls blindly.

Determine which exact flow should be allowed.

Then make the narrowest justified change.

---

# 210. Mistake: Treating Every Timeout as NetworkPolicy

A timeout could involve:

```text
Routing
CNI
Node firewall
Cloud firewall
NetworkPolicy
Service forwarding
Application
Return path
```

Investigate before modifying policy.

# 223. What Have We Learned?

The problem is not simply:

```text
checkout-svc does not exist
```

because one backend works.

It is not simply:

```text
wrong targetPort
```

because Pod 1 works on 8080.

It is not simply:

```text
all checkout Pods are broken
```

because Pod 1 works.

The failure correlates with:

```text
Pod 2
Node-B
Cross-node path
```

# 224. Compare Same-Node and Cross-Node Traffic

Further tests reveal:

```text
Pods on Node-A
-> can communicate with each other.

Pods on Node-B
-> can communicate locally.

Node-A Pods
-> cannot reach Node-B Pods.

Node-B Pods
-> cannot reach Node-A Pods.
```

This changes the investigation dramatically.

---

# 225. Move Below the Service Layer

Now investigate:

```text
CNI
Node routes
Cross-node encapsulation/routing
Cloud firewall
Security groups
Network ACLs
MTU
Node interfaces
```

Do not rewrite the checkout application.

The evidence points toward cross-node networking.

---

# 226. Inspect Node Networking

Suppose the cluster uses an overlay CNI.

Node-A and Node-B must exchange encapsulated networking traffic through a specific protocol/port according to that CNI's architecture.

A recent infrastructure change modified the node security rules.

The required node-to-node CNI traffic is no longer permitted.

---

# 227. Explain the Intermittent 502

When ingress sends traffic to:

```text
checkout-pod-1
```

on the reachable path:

```text
Request succeeds.
```

When traffic is sent toward:

```text
checkout-pod-2
```

across the broken node-network path:

```text
Backend connection fails.
```

Ingress eventually returns:

```text
502
```

or another implementation-specific upstream failure response.

---

# 228. Root Cause

The application is healthy.

The Service selector is correct.

The Service ports are correct.

DNS is healthy.

The Pods are running.

The root cause is:

```text
Cross-node CNI traffic blocked
by an infrastructure security change.
```

This is why restarting the Pods would not solve the underlying problem.

---

# 229. Fix Philosophy

Do not solve it with:

```text
Allow all traffic from everywhere
```

Determine the exact node-to-node communication required by the CNI.

Then restore only the required connectivity according to the cluster's security design.

That preserves least privilege.

# 230. Final Container and Kubernetes Networking Mental Model

For Docker, think:

```text
CLIENT
   |
   v
HOST IP
   |
   v
PUBLISHED PORT
   |
   v
HOST NETWORKING
   |
   v
LINUX BRIDGE / CONTAINER NETWORK
   |
   v
VETH
   |
   v
CONTAINER NETWORK NAMESPACE
   |
   v
CONTAINER IP
   |
   v
APPLICATION PORT
```

For Kubernetes internal traffic:

```text
SOURCE POD
   |
   v
POD NETWORK NAMESPACE
   |
   v
DNS
   |
   v
SERVICE NAME
   |
   v
CLUSTERIP
   |
   v
SERVICE FORWARDING
   |
   v
ENDPOINT
   |
   v
CNI NETWORK
   |
   v
DESTINATION NODE
   |
   v
DESTINATION POD
   |
   v
APPLICATION PORT
```

For an Internet-facing Kubernetes application:

```text
USER
 |
 v
PUBLIC DNS
 |
 v
CLOUD LOAD BALANCER
 |
 v
INGRESS CONTROLLER
 |
 v
KUBERNETES SERVICE
 |
 v
SERVICE ENDPOINT
 |
 v
CNI
 |
 v
POD
 |
 v
APPLICATION
 |
 v
DEPENDENCIES
```

The most important principle from Part 18 is:

> **Containers and Kubernetes add networking abstractions, but they do not remove networking fundamentals.**

When something fails, translate the abstraction back into concrete questions:

```text
What is the source?

What is the destination?

Which namespace am I in?

Which IP is being used?

Which port?

What does DNS return?

Which route is selected?

Which Service is involved?

Does it have endpoints?

Which Pod was selected?

Which node is that Pod on?

Can the nodes communicate?

Is NetworkPolicy allowing the flow?

Is the CNI providing the path?

Is the application actually listening?

Can the response return?
```

Once you learn to follow that path, Kubernetes networking stops looking like magic and becomes a series of ordinary networking decisions layered together.
