# Part 6: ARP, Neighbor Discovery, and Local Network Communication

In Part 5, you learned how an IPv4 address and subnet prefix allow a host to answer a critical question:

```text
Is the destination on my local network,
or must I send the traffic to a router?
```

Now we need to solve the next problem.

Suppose your Linux computer has:

```text
IP address:
192.168.10.20/24
```

and wants to communicate with:

```text
192.168.10.50
```

The destination is local.

But Ethernet does not deliver a local Ethernet frame using an IPv4 address alone. The sender needs a Layer 2 destination address.

It needs the destination's MAC address.

How does it discover it?

For IPv4 over Ethernet, this is where ARP becomes essential.

By the end of this part, you should understand the complete process:

```text
Destination IP
      |
      v
Local or remote?
      |
      +--- Local
      |      |
      |      v
      |   Resolve destination MAC
      |      |
      |      v
      |     ARP
      |
      +--- Remote
             |
             v
        Find gateway
             |
             v
      Resolve gateway MAC
             |
             v
            ARP
```

You will also learn how to inspect and troubleshoot this process on Linux, why duplicate IP addresses cause strange failures, what ARP spoofing means, and how IPv6 solves the same general problem using Neighbor Discovery instead of ARP.

---

# 1. Start With the Layer 2 and Layer 3 Relationship

Before learning ARP commands, you need to understand why ARP exists.

Remember the OSI model:

```text
Layer 7  Application
Layer 6  Presentation
Layer 5  Session
Layer 4  Transport
Layer 3  Network
Layer 2  Data Link
Layer 1  Physical
```

For this discussion, focus on:

```text
Layer 3
IP addressing and routing

Layer 2
Ethernet frames and MAC addresses
```

An IPv4 address might look like:

```text
192.168.10.20
```

A MAC address might look like:

```text
00:1a:2b:3c:4d:5e
```

These addresses serve different purposes.

IP addresses help identify hosts and networks at Layer 3 and allow traffic to be routed across networks.

MAC addresses are used for local Layer 2 Ethernet frame delivery.

That distinction is fundamental.

---

# 2. A Simple Network

Imagine:

```text
Computer A
IP: 192.168.10.20
MAC: AA:AA:AA:AA:AA:AA
        |
        |
      Switch
        |
        |
Computer B
IP: 192.168.10.50
MAC: BB:BB:BB:BB:BB:BB
```

Both computers use:

```text
192.168.10.0/24
```

Computer A wants to communicate with:

```text
192.168.10.50
```

From the `/24`, Computer A determines that Computer B is local.

But Computer A still needs to construct an Ethernet frame.

Conceptually:

```text
Ethernet frame

Destination MAC: ?
Source MAC: AA:AA:AA:AA:AA:AA
Payload: IP packet
```

Computer A knows the destination IP:

```text
192.168.10.50
```

but initially may not know its MAC address.

That is the problem ARP solves.

---

# 3. Why IP Alone Is Not Enough on Ethernet

Suppose an application wants to send data to:

```text
192.168.10.50
```

Eventually, the network stack creates an IP packet containing information such as:

```text
Source IP:
192.168.10.20

Destination IP:
192.168.10.50
```

But that IP packet must be carried inside a Layer 2 frame on an Ethernet network.

This is encapsulation.

Conceptually:

```text
Ethernet Frame
+---------------------------------------------+
| Destination MAC                             |
| Source MAC                                  |
|                                             |
|   IP Packet                                 |
|   +-------------------------------------+   |
|   | Source IP: 192.168.10.20           |   |
|   | Destination IP: 192.168.10.50      |   |
|   |                                     |   |
|   | Transport data and application data |   |
|   +-------------------------------------+   |
+---------------------------------------------+
```

The sender therefore needs both Layer 3 and Layer 2 information.

---

# 4. What Is ARP?

ARP stands for:

```text
Address Resolution Protocol
```

ARP is used in IPv4 local networks to determine the Layer 2 address associated with an IPv4 address.

In simple terms, ARP helps answer:

```text
I know the IPv4 address.

Which MAC address should receive the Ethernet frame?
```

For example:

```text
Known:

192.168.10.50

Need:

BB:BB:BB:BB:BB:BB
```

ARP provides the mapping.

---

# 5. Do Not Think of ARP as "Converting" an IP Address

A common beginner explanation says:

```text
ARP converts IP addresses into MAC addresses.
```

That wording can be misleading.

There is no mathematical conversion such as:

```text
192.168.10.50
        |
        v
some calculation
        |
        v
BB:BB:BB:BB:BB:BB
```

The MAC address cannot generally be calculated from the IPv4 address.

Instead, ARP performs discovery.

A better mental model is:

```text
Who currently owns this IPv4 address
on my local Layer 2 network?
```

---

# 6. The Basic ARP Process

Suppose:

```text
Computer A

IP:
192.168.10.20

MAC:
AA:AA:AA:AA:AA:AA
```

wants to reach:

```text
Computer B

IP:
192.168.10.50

MAC:
BB:BB:BB:BB:BB:BB
```

Computer A does not know Computer B's MAC address.

The basic process is:

```text
Computer A
    |
    | ARP Request
    | "Who has 192.168.10.50?"
    v
Local network
    |
    v
Computer B
    |
    | ARP Reply
    | "192.168.10.50 is at
    |  BB:BB:BB:BB:BB:BB"
    v
Computer A
```

Computer A can now construct the Ethernet frame.

---

# 7. ARP Requests

An ARP request essentially asks:

```text
Who has 192.168.10.50?

Tell 192.168.10.20.
```

The sender knows:

```text
Destination IPv4 address:
192.168.10.50
```

but does not know:

```text
Destination MAC address:
?
```

So it cannot send an ordinary unicast Ethernet frame directly to the destination yet.

Instead, the ARP request is sent using Ethernet broadcast.

---

# 8. Ethernet Broadcast

The Ethernet broadcast MAC address is:

```text
ff:ff:ff:ff:ff:ff
```

It means:

```text
Deliver this frame to everyone
in this Layer 2 broadcast domain.
```

Therefore the ARP request is carried in a frame resembling:

```text
Destination MAC:
ff:ff:ff:ff:ff:ff

Source MAC:
AA:AA:AA:AA:AA:AA
```

Conceptually:

```text
                  ARP Request
       "Who has 192.168.10.50?"

                     |
                     v

                 Switch
               /    |    \
              /     |     \
             v      v      v

         Host B   Host C   Host D
```

Every relevant device in the broadcast domain can receive the broadcast.

But only the device that owns the requested IPv4 address should answer normally.

---

# 9. Why the Switch Cannot Simply Solve This

You learned earlier that an Ethernet switch maintains a MAC address table.

For example:

```text
MAC Address              Port

AA:AA:AA:AA:AA:AA        1
BB:BB:BB:BB:BB:BB        4
CC:CC:CC:CC:CC:CC        7
```

But Computer A is asking:

```text
Who has 192.168.10.50?
```

The switch's ordinary Layer 2 forwarding table maps:

```text
MAC address -> switch port
```

It does not normally provide the host with:

```text
IPv4 address -> MAC address
```

ARP solves that mapping problem for the host.

After the host learns the MAC address, the switch can use its own MAC table to forward Ethernet frames toward the correct port.

These are two separate mechanisms.

---

# 10. ARP Replies

Computer B receives the request and recognizes:

```text
192.168.10.50
```

as its own IPv4 address.

It sends an ARP reply.

Conceptually:

```text
192.168.10.50
is at
BB:BB:BB:BB:BB:BB
```

Unlike the original broadcast request, the reply can normally be sent directly back to Computer A.

Conceptually:

```text
Computer A
AA:AA:AA:AA:AA:AA

        ^
        |
        | ARP Reply
        |
Computer B
BB:BB:BB:BB:BB:BB
```

Computer A now knows:

```text
192.168.10.50
        |
        v
BB:BB:BB:BB:BB:BB
```

---

# 11. The ARP Cache

Imagine having to perform ARP before every single packet.

That would create unnecessary broadcast traffic.

Operating systems therefore temporarily remember discovered mappings.

This stored information is commonly called the:

```text
ARP cache
```

On modern Linux systems, it is generally exposed through the neighbor table.

It might contain information conceptually like:

```text
192.168.10.1
-> 00:11:22:33:44:55

192.168.10.50
-> BB:BB:BB:BB:BB:BB

192.168.10.80
-> CC:CC:CC:CC:CC:CC
```

The next time the host needs one of those neighbors, it may be able to use the cached mapping without immediately broadcasting another ARP request.

---

# 12. ARP Tables and Neighbor Tables

Older terminology often refers to an:

```text
ARP table
```

Modern Linux commonly uses the broader concept:

```text
neighbor table
```

Why broader?

Because Linux networking supports more than IPv4 ARP.

For example, IPv6 uses Neighbor Discovery.

The `ip` command therefore provides:

```bash
ip neigh
```

rather than being limited to an ARP-specific command.

---

# 13. Viewing the Neighbor Table on Linux

Run:

```bash
ip neigh
```

You might see:

```text
192.168.1.1 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE
192.168.1.20 dev eth0 lladdr aa:bb:cc:dd:ee:ff STALE
```

Let's break down the first entry.

```text
192.168.1.1
```

This is the neighbor's Layer 3 address.

```text
dev eth0
```

This means the neighbor is reachable through:

```text
eth0
```

```text
lladdr 00:11:22:33:44:55
```

`lladdr` means link-layer address.

In this Ethernet example, that is the MAC address.

```text
REACHABLE
```

This is the current neighbor state.

We will examine these states shortly.

---

# 14. The Older arp Command

Some Linux systems also provide:

```bash
arp
```

or:

```bash
arp -n
```

You might see something similar to:

```text
Address          HWaddress             Iface
192.168.1.1      00:11:22:33:44:55     eth0
```

However, `arp` belongs to the older `net-tools` family.

Modern Linux administration generally favors:

```bash
ip neigh
```

from `iproute2`.

You should recognize both because older tutorials, systems, scripts, and troubleshooting documentation may still use `arp`.

---

# 15. What Happens When You Ping a Local Host?

Let's follow the process carefully.

Host A:

```text
IP:
192.168.1.10/24

MAC:
AA:AA:AA:AA:AA:AA
```

Host B:

```text
IP:
192.168.1.20/24

MAC:
BB:BB:BB:BB:BB:BB
```

You run:

```bash
ping 192.168.1.20
```

The operating system does not immediately say:

```text
Send Ethernet frame to BB:BB:BB:BB:BB:BB
```

It may not know that MAC address yet.

First it determines whether:

```text
192.168.1.20
```

is local.

---

# 16. How a Host Decides Whether a Destination Is Local

Host A has:

```text
192.168.1.10/24
```

Its connected network is:

```text
192.168.1.0/24
```

Destination:

```text
192.168.1.20
```

belongs to:

```text
192.168.1.0/24
```

Therefore:

```text
Destination is local
```

The host can attempt direct Layer 2 delivery.

Conceptually:

```text
My network:
192.168.1.0/24

Destination:
192.168.1.20

Inside my connected network?

YES

Resolve destination's MAC.
```

---

# 17. Local Destination Communication

The full process looks like this:

```text
Application wants:
192.168.1.20
       |
       v
Routing decision
       |
       v
Destination is local
       |
       v
Check neighbor table
       |
       +--- Mapping exists and usable
       |          |
       |          v
       |     Use known MAC
       |
       +--- Mapping unavailable
                  |
                  v
             Send ARP request
                  |
                  v
              ARP reply
                  |
                  v
             Learn MAC
                  |
                  v
           Build Ethernet frame
                  |
                  v
               Switch
                  |
                  v
           Destination host
```

This is the mental model you should remember.

---

# 18. What If the Destination Is Remote?

Now change the destination.

Host A:

```text
192.168.1.10/24
```

wants:

```text
8.8.8.8
```

Host A calculates its local network:

```text
192.168.1.0/24
```

Is:

```text
8.8.8.8
```

inside that network?

No.

Therefore the host cannot directly deliver the packet to `8.8.8.8` over its local Ethernet network.

It needs a route.

Often, that means using the default gateway.

---

# 19. What Is the Default Gateway?

A default gateway is typically a router that a host uses when no more specific route matches a remote destination.

For example:

```text
Host:
192.168.1.10/24

Gateway:
192.168.1.1
```

The topology might be:

```text
Host
192.168.1.10
      |
      v
Switch
      |
      v
Router
192.168.1.1
      |
      v
Other networks
      |
      v
Internet
```

The router provides the next Layer 3 step toward remote destinations.

---

# 20. The Critical Remote-Traffic Rule

Suppose Host A wants:

```text
8.8.8.8
```

A common beginner mistake is thinking:

```text
Host A must ARP for 8.8.8.8.
```

Normally, no.

`8.8.8.8` is not on the local subnet.

Host A instead needs the Layer 2 address of its local next hop.

If the route uses:

```text
192.168.1.1
```

as the gateway, Host A resolves:

```text
192.168.1.1
        |
        v
Gateway MAC address
```

It does not normally ARP across the Internet for the final destination.

---

# 21. Why the Default Gateway's MAC Address Matters

Suppose:

```text
Host:
IP 192.168.1.10
MAC AA:AA:AA:AA:AA:AA

Gateway:
IP 192.168.1.1
MAC GG:GG:GG:GG:GG:GG

Remote server:
IP 203.0.113.50
```

The host creates an IP packet:

```text
Source IP:
192.168.1.10

Destination IP:
203.0.113.50
```

But the first Ethernet frame is addressed to:

```text
Destination MAC:
GG:GG:GG:GG:GG:GG
```

Why?

Because the router is the next Layer 2 recipient.

So the frame and packet contain different destination concepts:

```text
Ethernet destination:
Gateway MAC

IP destination:
Remote server IP
```

This distinction is one of the most important concepts in networking.

---

# 22. Frame vs Packet for Remote Traffic

Consider:

```text
Host
192.168.1.10
        |
        v
Gateway
192.168.1.1
        |
        v
Internet
        |
        v
203.0.113.50
```

On the first Ethernet link:

```text
Ethernet frame:

Source MAC:
Host MAC

Destination MAC:
Gateway MAC


Inside that frame:

IP packet:

Source IP:
192.168.1.10

Destination IP:
203.0.113.50
```

Notice:

```text
Layer 2 destination != Layer 3 destination
```

for remote traffic.

That is normal.

---

# 23. What the Router Does Next

The router receives the Ethernet frame because the destination MAC belongs to its local interface.

It removes the incoming Layer 2 framing and examines the IP packet.

It sees:

```text
Destination IP:
203.0.113.50
```

The router consults its routing table.

It then forwards the packet toward the next hop.

On another Ethernet segment, it constructs a new Layer 2 frame appropriate for that link.

Conceptually:

```text
Original host
      |
      | Frame 1
      v
Router
      |
      | Frame 2
      v
Next device
      |
      v
...
```

The Layer 2 header can change from hop to hop.

The Layer 3 destination generally remains the ultimate destination as the packet is routed, although technologies such as NAT can intentionally modify IP addressing.

---

# 24. Local vs Remote Side by Side

Local destination:

```text
Host A
192.168.1.10
      |
      | ARP for 192.168.1.20
      v
Host B
192.168.1.20
```

Remote destination:

```text
Host A
192.168.1.10
      |
      | ARP for gateway
      | 192.168.1.1
      v
Router
      |
      v
Remote networks
```

The rule is:

```text
Local destination
-> resolve destination neighbor

Remote destination
-> resolve local next-hop neighbor
```

---

# 25. How the Routing Table Participates

ARP does not decide whether a destination is local or remote.

Routing logic does.

On Linux:

```bash
ip route
```

might show:

```text
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 scope link src 192.168.1.10
```

The second route says:

```text
192.168.1.0/24
is directly connected through eth0
```

The first says:

```text
For destinations without a more specific matching route,
send traffic via 192.168.1.1.
```

This is why routing and ARP must be understood together.

---

# 26. Ask Linux Which Route It Will Use

Instead of guessing, use:

```bash
ip route get 192.168.1.20
```

For a local destination, you may see output indicating direct use of the interface.

For a remote destination:

```bash
ip route get 8.8.8.8
```

you may see something resembling:

```text
8.8.8.8 via 192.168.1.1 dev eth0 src 192.168.1.10
```

This tells you the next hop.

Now you know which neighbor mapping matters.

For this example:

```text
192.168.1.1
```

---

# 27. A Practical Troubleshooting Workflow

Suppose:

```bash
ping 8.8.8.8
```

fails.

Do not immediately blame DNS.

You are already using an IP address.

Start lower in the path.

Check:

```bash
ip addr
```

Then:

```bash
ip route
```

Then:

```bash
ip route get 8.8.8.8
```

If the route says:

```text
via 192.168.1.1
```

inspect:

```bash
ip neigh
```

Ask:

```text
Can my machine resolve and reach
192.168.1.1 at Layer 2?
```

That is a much more structured troubleshooting process.

---

# 28. ARP Cache Expiration

Neighbor mappings are not necessarily permanent.

Why?

Networks change.

A device might:

* Disconnect
* Reboot
* Change interfaces
* Move
* Receive a different address
* Be replaced
* Fail over to another system

If hosts remembered every dynamic ARP mapping forever, stale information could remain indefinitely.

Operating systems therefore maintain dynamic neighbor entries and update, probe, or eventually remove them according to their neighbor-cache logic.

---

# 29. Why ARP Expiration Is Useful

Suppose:

```text
192.168.1.50
```

previously belonged to:

```text
AA:AA:AA:AA:AA:AA
```

Later the device is replaced.

The new device has:

```text
BB:BB:BB:BB:BB:BB
```

If another machine permanently believed:

```text
192.168.1.50
=
AA:AA:AA:AA:AA:AA
```

traffic could be sent to an obsolete destination.

Dynamic neighbor management allows the mapping to be refreshed.

---

# 30. Neighbor States on Linux

Linux neighbor entries can have states such as:

```text
INCOMPLETE
REACHABLE
STALE
DELAY
PROBE
FAILED
PERMANENT
NOARP
```

You do not need to memorize every internal transition immediately.

But you should understand what the common states tell you during troubleshooting.

---

# 31. REACHABLE

Example:

```text
192.168.1.1 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE
```

`REACHABLE` means the kernel has relatively recent confirmation that the neighbor is reachable.

This is generally a healthy state.

---

# 32. STALE

Example:

```text
192.168.1.20 dev eth0 lladdr aa:bb:cc:dd:ee:ff STALE
```

A beginner may see:

```text
STALE
```

and immediately assume:

```text
The network is broken.
```

That is not necessarily true.

`STALE` means the mapping exists, but its reachability has not been recently confirmed.

Linux can still use it and perform further reachability detection as needed.

So:

```text
STALE != automatically broken
```

This distinction prevents unnecessary troubleshooting.

---

# 33. INCOMPLETE

You might see:

```text
192.168.1.50 dev eth0 INCOMPLETE
```

This is much more interesting during a connectivity failure.

It means address resolution has started, but Linux does not yet have a usable link-layer address for that neighbor.

Possible reasons include:

* Target host is offline
* Wrong subnet configuration
* Wrong VLAN
* Layer 2 connectivity failure
* ARP replies are not returning
* Interface problems
* Security controls are blocking communication
* Target IP does not exist

This state gives you evidence.

---

# 34. FAILED

You may see:

```text
192.168.1.50 dev eth0 FAILED
```

This indicates neighbor resolution has failed.

Instead of randomly changing configurations, investigate why the host cannot resolve the neighbor.

Ask:

```text
Should this destination really be local?

Is the interface up?

Are both systems in the same VLAN?

Does the destination exist?

Is the prefix correct?

Can ARP requests and replies cross the Layer 2 path?
```

---

# 35. DELAY and PROBE

`DELAY` and `PROBE` are associated with neighbor reachability detection.

Conceptually:

```text
We have a mapping,
but we need to confirm whether
the neighbor remains reachable.
```

During troubleshooting, these states tell you the kernel is actively managing neighbor reachability rather than simply holding a permanent static mapping.

---

# 36. PERMANENT

A `PERMANENT` entry does not age like a normal dynamically learned neighbor entry.

Static neighbor entries can be created administratively.

They can be useful in specialized situations, but beginners should not use static ARP entries as a general fix for unexplained networking problems.

If normal ARP is failing, first determine why.

---

# 37. Inspect a Specific Neighbor

Instead of displaying the entire table:

```bash
ip neigh
```

you can inspect a particular destination.

For example:

```bash
ip neigh show 192.168.1.1
```

This is useful when you are troubleshooting the gateway.

You can also inspect entries associated with an interface:

```bash
ip neigh show dev eth0
```

Replace:

```text
eth0
```

with the actual interface name on your system.

Modern Linux interface names may look like:

```text
ens33
enp0s3
ens5
eth0
```

Never assume the interface is named `eth0`.

Check first:

```bash
ip link
```

or:

```bash
ip addr
```

---

# 38. Creating ARP Activity Safely

Suppose you have a lab network and know that:

```text
192.168.1.1
```

is your gateway.

Check:

```bash
ip neigh show 192.168.1.1
```

Then generate traffic:

```bash
ping -c 1 192.168.1.1
```

Check again:

```bash
ip neigh show 192.168.1.1
```

You may observe the neighbor entry appear or change state.

This is a simple way to connect theory to the operating system.

---

# 39. Capturing ARP Traffic

If `tcpdump` is installed and you have appropriate permissions, you can inspect ARP packets.

Run:

```bash
sudo tcpdump -n -i eth0 arp
```

Breakdown:

```text
sudo
```

runs the command with elevated privileges where required.

```text
tcpdump
```

captures network traffic.

```text
-n
```

prevents name resolution, which often makes troubleshooting output clearer.

```text
-i eth0
```

selects the interface.

```text
arp
```

filters for ARP traffic.

Use your actual interface name.

---

# 40. What an ARP Capture May Look Like

You might see:

```text
ARP, Request who-has 192.168.1.20 tell 192.168.1.10
ARP, Reply 192.168.1.20 is-at aa:bb:cc:dd:ee:ff
```

Read it as:

```text
Request:

Who owns 192.168.1.20?
Tell 192.168.1.10.
```

Then:

```text
Reply:

192.168.1.20 is associated with
aa:bb:cc:dd:ee:ff.
```

Now ARP is no longer an abstract concept.

You can watch the exchange happen.

---

# 41. Clearing a Neighbor Entry in a Lab

Sometimes you may want to remove a neighbor entry so you can observe resolution again.

For example:

```bash
sudo ip neigh del 192.168.1.20 dev eth0
```

This tells Linux to remove that neighbor entry for the specified interface.

Then generate traffic again:

```bash
ping -c 1 192.168.1.20
```

and inspect:

```bash
ip neigh
```

Warning:

Do this only in a safe lab or on a system where you understand the impact.

Do not randomly delete neighbor entries on production systems.

---

# 42. Gratuitous ARP

Normally ARP asks:

```text
Who has this IPv4 address?
```

But a device can also send ARP information about its own address without first receiving the usual request.

This behavior is commonly called:

```text
Gratuitous ARP
```

Conceptually:

```text
Host announces:

"I am 192.168.1.50,
and this is my MAC information."
```

The exact packet form and behavior can vary, but the important beginner concept is that the host is proactively advertising or checking information about its own address.

---

# 43. Why Gratuitous ARP Is Useful

Gratuitous ARP can help with situations such as:

* Updating neighbor caches
* IP address changes
* Failover
* High-availability systems
* Duplicate address detection
* Moving an IP between systems

Imagine:

```text
Server A
owns virtual IP
192.168.1.100
```

Server A fails.

Server B takes over:

```text
Server B
now owns
192.168.1.100
```

But neighboring devices may still remember:

```text
192.168.1.100
        |
        v
Server A's old MAC
```

A gratuitous ARP announcement can help neighbors learn the updated mapping.

---

# 44. High-Availability Example

Before failure:

```text
Virtual IP:
192.168.1.100

        |
        v

Server A MAC
AA:AA:AA:AA:AA:AA
```

After failover:

```text
Virtual IP:
192.168.1.100

        |
        v

Server B MAC
BB:BB:BB:BB:BB:BB
```

Neighboring systems need to learn:

```text
192.168.1.100
is now associated with
BB:BB:BB:BB:BB:BB
```

Without that update, some systems could temporarily continue sending frames toward the old MAC address.

---

# 45. Duplicate IP Addresses

Now imagine two devices are accidentally configured with:

```text
192.168.1.50
```

Device A:

```text
IP:
192.168.1.50

MAC:
AA:AA:AA:AA:AA:AA
```

Device B:

```text
IP:
192.168.1.50

MAC:
BB:BB:BB:BB:BB:BB
```

This is an IP address conflict.

Both systems claim the same Layer 3 identity.

---

# 46. Why Duplicate IPs Create Strange Symptoms

Another host asks:

```text
Who has 192.168.1.50?
```

Now more than one device may claim the address.

Neighbor mappings can become inconsistent.

A client might learn:

```text
192.168.1.50
-> AA:AA:AA:AA:AA:AA
```

and later:

```text
192.168.1.50
-> BB:BB:BB:BB:BB:BB
```

Possible symptoms include:

* Intermittent connectivity
* Connections reaching the wrong host
* Ping working and then failing
* SSH sessions behaving strangely
* Duplicate-address warnings
* Neighbor entries changing unexpectedly
* Services appearing and disappearing

Intermittent problems are often harder to diagnose than complete failures.

---

# 47. Investigating a Suspected Duplicate Address

Suppose:

```text
192.168.1.50
```

behaves inconsistently.

Check:

```bash
ip neigh show 192.168.1.50
```

Record the MAC address.

Generate traffic.

Check again.

If the same IPv4 address repeatedly appears with different MAC addresses unexpectedly, that is evidence worth investigating.

Do not immediately conclude malicious activity.

Possible explanations include:

* Duplicate static IP configuration
* DHCP problems
* High-availability failover
* Virtual machines
* Containers
* Network appliances
* Legitimate IP movement
* ARP spoofing

Context matters.

# 48. arp-scan and arping

Some environments provide diagnostic utilities such as:

```text
arping
```

or:

```text
arp-scan
```

They can help investigate local Layer 2 and ARP behavior.

For example, `arping` can send ARP requests toward an IPv4 neighbor on the local network.

The exact syntax and package availability vary by operating system.

These tools can be useful in a lab, but understand the basic mechanism before relying on them.

Your reasoning should still be:

```text
Which interface?

Which subnet?

Should the target be local?

What MAC responds?

Does that MAC remain consistent?
```

# 49. Stale ARP Entries

Suppose a server was:

```text
192.168.1.50
-> AA:AA:AA:AA:AA:AA
```

The server is replaced.

Now:

```text
192.168.1.50
-> BB:BB:BB:BB:BB:BB
```

A host may temporarily have old neighbor information.

This is one example of what people informally mean when they talk about a stale ARP entry.

But remember that Linux's formal `STALE` neighbor state does not automatically mean the entry is incorrect.

These are related but not identical ideas.

# 50. Troubleshooting Stale Neighbor Information

Suppose traffic appears to be going to an old MAC address.

First inspect:

```bash
ip neigh show 192.168.1.50
```

Compare the MAC with what you expect.

If you control the destination, inspect its interface:

```bash
ip link
```

or:

```bash
ip addr
```

Confirm its actual MAC address.

Then determine whether the mismatch is caused by:

* Old cache information
* Duplicate IP
* Failover
* Wrong interface
* Incorrect network design
* Security issue

Only after understanding the situation should you consider manually deleting the neighbor entry.

# 51. Problem: ARP Resolution Fails

Scenario:

```text
Host A:
192.168.10.20/24

Host B:
192.168.10.50/24
```

You run:

```bash
ping 192.168.10.50
```

and communication fails.

`ip neigh` shows:

```text
192.168.10.50 dev eth0 INCOMPLETE
```

What does that tell you?

Host A believes the destination is local and has attempted neighbor resolution, but it has not learned a usable MAC address.

That dramatically narrows the problem.

# 52. ARP Failure Troubleshooting

Start with the local host.

### Step 1: Check the interface

```bash
ip addr
```

Confirm:

* Correct interface
* Correct IPv4 address
* Correct prefix
* Interface is up

### Step 2: Check the route

```bash
ip route get 192.168.10.50
```

Does Linux treat it as directly connected?

### Step 3: Check neighbor state

```bash
ip neigh show 192.168.10.50
```

### Step 4: Capture ARP

```bash
sudo tcpdump -n -i eth0 arp
```

### Step 5: Generate traffic

```bash
ping -c 1 192.168.10.50
```

Now ask:

```text
Do I see the ARP request?

Do I see an ARP reply?
```

Those two questions are powerful.

# 53. Request Seen, No Reply

Suppose `tcpdump` shows:

```text
ARP, Request who-has 192.168.10.50 tell 192.168.10.20
```

repeatedly.

But no reply appears.

Possible causes include:

* Destination is powered off
* Destination does not own that IP
* Destination interface is down
* Hosts are actually in different VLANs
* Layer 2 path is broken
* Incorrect switch configuration
* Wrong subnet assumptions
* Security controls interfere
* Cabling or virtual networking problem

You now know the sender is attempting ARP.

The investigation moves outward.

---

# 54. No ARP Request Seen

Suppose you expect the host to ARP for:

```text
192.168.10.50
```

but no request appears.

Ask:

```text
Does the operating system actually think
192.168.10.50 is directly connected?
```

Check:

```bash
ip route get 192.168.10.50
```

Perhaps the subnet mask is wrong.

Perhaps a more specific route sends the traffic elsewhere.

Perhaps you captured on the wrong interface.

This demonstrates why packet captures should be interpreted together with routing information.

# 55. Problem: Gateway Cannot Be Resolved

Host:

```text
192.168.1.20/24
```

Gateway:

```text
192.168.1.1
```

You can see:

```bash
ip route
```

showing:

```text
default via 192.168.1.1 dev eth0
```

But:

```bash
ip neigh show 192.168.1.1
```

eventually shows:

```text
FAILED
```

This is a major clue.

The host has a route telling it to use the gateway, but it cannot establish the local Layer 2 neighbor relationship required to send frames to that gateway.

Investigate:

* Interface state
* VLAN
* Cabling
* Virtual switch configuration
* Gateway availability
* IP and prefix configuration
* Layer 2 security controls

Changing DNS will not solve this problem.

# 56. Why This Matters for Troubleshooting Internet Failures

A beginner may say:

```text
The Internet isn't working.
```

That symptom is too broad.

Break the path down:

```text
My application
     |
     v
My IP configuration
     |
     v
Routing table
     |
     v
Default gateway
     |
     v
Gateway neighbor resolution
     |
     v
Upstream routing
     |
     v
Internet
     |
     v

```

If you cannot resolve your gateway's MAC address, there is little value in immediately investigating a remote web server.

Troubleshoot from the nearest dependency outward.

# 57. ARP and Switches

Remember that ARP and switch MAC learning are not the same process.

Host ARP table:

```text
IP
|
v
MAC
```

Switch MAC table:

```text
MAC
|
v
Port
```

Together:

```text
Host knows:
192.168.1.50
        |
        v
BB:BB:BB:BB:BB:BB

Switch knows:
BB:BB:BB:BB:BB:BB
        |
        v
Port 7
```

That is how Layer 3 identity and Layer 2 forwarding cooperate on a typical Ethernet LAN.

---

# 58. ARP Does Not Cross Routers Normally

Suppose:

```text
Network A:
192.168.1.0/24

Network B:
192.168.2.0/24
```

with a router between them.

Host A:

```text
192.168.1.10
```

wants:

```text
192.168.2.20
```

Host A does not broadcast:

```text
Who has 192.168.2.20?
```

across the router under normal routing.

Instead:

```text
Host A
   |
   | ARP for local gateway
   v
Router
   |
   | Local resolution on Network B
   v
Host B
```

Broadcast domains are normally separated by routers.

---

# 59. Packet Flow Across a Router

Let's make this concrete.

Host A:

```text
IP:
192.168.1.10

MAC:
AA:AA:AA:AA:AA:AA
```

Router interface A:

```text
IP:
192.168.1.1

MAC:
11:11:11:11:11:11
```

Router interface B:

```text
IP:
192.168.2.1

MAC:
22:22:22:22:22:22
```

Host B:

```text
IP:
192.168.2.20

MAC:
BB:BB:BB:BB:BB:BB
```

Host A wants Host B.

---

# 60. First Link

Host A determines:

```text
192.168.2.20
```

is remote.

It resolves the gateway:

```text
192.168.1.1
->
11:11:11:11:11:11
```

The frame becomes:

```text
Source MAC:
AA:AA:AA:AA:AA:AA

Destination MAC:
11:11:11:11:11:11
```

Inside:

```text
Source IP:
192.168.1.10

Destination IP:
192.168.2.20
```

---

# 61. Second Link

The router receives the packet and determines that:

```text
192.168.2.20
```

is reachable through its interface on:

```text
192.168.2.0/24
```

If needed, the router resolves:

```text
192.168.2.20
->
BB:BB:BB:BB:BB:BB
```

Then it creates a new Ethernet frame:

```text
Source MAC:
22:22:22:22:22:22

Destination MAC:
BB:BB:BB:BB:BB:BB
```

The IP packet still targets:

```text
192.168.2.20
```

This demonstrates a core rule:

```text
MAC addresses are relevant to each local link.

IP addresses support end-to-end Layer 3 forwarding.
```

# 62. ARP Spoofing Introduction

ARP was designed for local network address resolution.

Traditional ARP itself does not provide strong authentication proving:

```text
This device is definitely
the legitimate owner of this IP.
```

That creates a security weakness.

An attacker on an applicable local network may attempt to send false ARP information.

This is commonly called:

```text
ARP spoofing
```

or:

```text
ARP poisoning
```

---

# 63. Conceptual ARP Spoofing Example

Normal mapping:

```text
Gateway:
192.168.1.1
        |
        v
11:11:11:11:11:11
```

An attacker attempts to convince another host:

```text
192.168.1.1
        |
        v
AA:AA:AA:AA:AA:AA
```

where:

```text
AA:AA:AA:AA:AA:AA
```

belongs to the attacker's system.

The victim could then send frames intended for the gateway toward the wrong device.

---

# 64. Why ARP Spoofing Matters

Depending on the environment and other security controls, ARP spoofing can contribute to:

* Traffic interception
* Man-in-the-middle attacks
* Traffic redirection
* Denial of service
* Session disruption

At beginner level, remember:

```text
ARP provides useful local address resolution,
but classic ARP does not inherently authenticate
the claimed IPv4-to-MAC mapping.
```

We will not turn this section into an attack tutorial.

The important goal here is understanding the security limitation and recognizing suspicious symptoms.

---

# 65. Defensive Awareness

Network defenses vary by environment.

Managed switches and enterprise networks may provide protections such as:

* DHCP snooping
* Dynamic ARP Inspection
* Port security
* Network segmentation
* Monitoring for unexpected IP-to-MAC changes

Host monitoring may also detect suspicious neighbor changes.

The exact security design depends on the infrastructure.

Do not treat static ARP entries as a universal security solution.

---

# 66. IPv6 Does Not Use ARP

This is important.

ARP is associated with IPv4.

IPv6 does not use ARP for neighbor address resolution.

Instead, IPv6 uses:

```text
Neighbor Discovery
```

commonly abbreviated:

```text
ND
```

or:

```text
NDP
```

Neighbor Discovery is part of ICMPv6.

---

# 67. IPv6 Neighbor Discovery

IPv6 Neighbor Discovery performs several important local-network functions.

These include concepts such as:

* Neighbor discovery
* Link-layer address resolution
* Router discovery
* Prefix discovery
* Neighbor reachability detection
* Duplicate Address Detection
* Redirects

So IPv6 Neighbor Discovery does more than simply replace one ARP message with another.

It forms a broader local-network discovery mechanism.

---

# 68. Neighbor Solicitation

For IPv6 address resolution, a host can send a:

```text
Neighbor Solicitation
```

Often abbreviated:

```text
NS
```

Conceptually, it asks:

```text
Who owns this IPv6 address?
```

This serves a role comparable to an IPv4 ARP request for address resolution.

However, the actual IPv6 mechanism is different.

---

# 69. Neighbor Advertisement

The target can respond with a:

```text
Neighbor Advertisement
```

often abbreviated:

```text
NA
```

Conceptually:

```text
That IPv6 address is mine,
and here is relevant neighbor information.
```

For beginner understanding:

```text
IPv4:
ARP Request
ARP Reply

IPv6:
Neighbor Solicitation
Neighbor Advertisement
```

But do not assume the protocols are identical internally.

---

# 70. IPv6 Uses Multicast Rather Than ARP Broadcast

IPv4 ARP requests commonly use Ethernet broadcast.

IPv6 Neighbor Discovery makes extensive use of multicast.

This is an important architectural difference.

Conceptually:

```text
IPv4 ARP:
Broadcast-based local discovery

IPv6 ND:
ICMPv6 and multicast-based discovery
```

You will learn IPv6 addressing and multicast behavior in greater depth later in the networking series.

---

# 71. Viewing IPv6 Neighbors

The same Linux command can display neighbor information:

```bash
ip neigh
```

You may see IPv4 and IPv6 entries.

To focus on IPv6:

```bash
ip -6 neigh
```

This is another reason modern Linux uses the generic term:

```text
neighbor
```

rather than treating everything as an ARP table.

---

# 72. Duplicate Address Detection in IPv6

IPv6 includes a process called:

```text
Duplicate Address Detection
```

or:

```text
DAD
```

Before normally using certain IPv6 addresses, a host can check whether another device already appears to be using that address on the link.

This helps detect duplicate-address situations.

Do not confuse:

```text
DAD
```

with DHCP.

They solve different problems.

# 90. Common Beginner Mistakes

Avoid these assumptions.

### Mistake 1

```text
Ping failed, therefore the host is down.
```

Not necessarily.

The problem could exist anywhere along the path.

### Mistake 2

```text
STALE means broken.
```

No.

A `STALE` Linux neighbor entry can be perfectly normal.

### Mistake 3

```text
I need the remote server's MAC address.
```

Normally not across routed networks.

You need the MAC address of the local next hop.

### Mistake 4

```text
ARP decides routing.
```

No.

Routing determines the next hop. ARP helps resolve an IPv4 next hop on the local Ethernet network.

### Mistake 5

```text
The switch's MAC table and my ARP table are the same.
```

No.

They solve different mapping problems.

### Mistake 6

```text
IPv6 uses ARP too.
```

No.

IPv6 uses Neighbor Discovery.

# 96. Final Packet-Flow Challenge

You have:

```text
Linux Server

IP:
10.20.30.50/24

MAC:
AA:AA:AA:AA:AA:AA

Default gateway:
10.20.30.1
```

The gateway has:

```text
MAC:
11:11:11:11:11:11
```

The server wants to communicate with:

```text
203.0.113.100
```

Walk through the process.

### Step 1: Examine the destination

```text
203.0.113.100
```

### Step 2: Compare it with the local connected network

Local network:

```text
10.20.30.0/24
```

The destination is not local.

### Step 3: Consult routing

Assume the route says:

```text
default via 10.20.30.1
```

The next hop is:

```text
10.20.30.1
```

### Step 4: Resolve the next hop

The server checks its neighbor table.

If no usable entry exists, it performs ARP for:

```text
10.20.30.1
```

not:

```text
203.0.113.100
```

### Step 5: Learn the gateway's MAC

```text
10.20.30.1
->
11:11:11:11:11:11
```

### Step 6: Build the Ethernet frame

```text
Source MAC:
AA:AA:AA:AA:AA:AA

Destination MAC:
11:11:11:11:11:11
```

### Step 7: Place the IP packet inside

```text
Source IP:
10.20.30.50

Destination IP:
203.0.113.100
```

### Step 8: Send the frame

```text
Server
   |
   | Ethernet frame
   v
Switch
   |
   v
Gateway
```

### Step 9: Router processes the packet

The gateway removes the incoming Layer 2 framing, examines the IP destination, checks its routing table, and forwards the packet toward the next hop.

The process continues until the packet reaches its destination or is dropped somewhere along the path.

# Part 6 Final Takeaway

The most important lesson from this part is not simply:

```text
ARP finds MAC addresses.
```

The more useful mental model is:

```text
Application wants to send data
            |
            v
      Destination IP
            |
            v
      Routing decision
            |
      +-----+-----+
      |           |
      v           v
    Local       Remote
      |           |
      v           v
Destination    Next-hop
neighbor       gateway
      |           |
      +-----+-----+
            |
            v
   Need link-layer address
            |
            v
    IPv4 Ethernet?
            |
            v
           ARP
            |
            v
      Neighbor table
            |
            v
     Ethernet frame
            |
            v
          Switch
            |
            v
      Local next hop
```

For IPv6, replace the ARP portion of that mental model with Neighbor Discovery.

When troubleshooting, do not ask only:

```text
Why can't I ping this IP?
```

Ask more precise questions:

```text
What route will my host use?

Does it think the destination is local or remote?

Which next hop must it reach?

Does it know that neighbor's link-layer address?

Is ARP being sent?

Is an ARP reply returning?

Is the neighbor entry REACHABLE, STALE,
INCOMPLETE, or FAILED?

Is the prefix correct?

Could there be a duplicate IP?

Could the hosts actually be in different VLANs?
```

Once you can answer those questions, ARP becomes more than a definition. It becomes a practical tool for understanding exactly where local network communication is succeeding or failing.
