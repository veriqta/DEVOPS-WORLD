# Part 7: Switches, VLANs, Trunks, and Layer 2 Segmentation

In Part 6, you learned how devices communicate with neighbors on a local network. You learned how ARP maps an IPv4 address to a MAC address, how switches use MAC addresses, and why a host sends remote traffic to its default gateway.

Now we need to examine the network in the middle.

Consider this office:

```text
Engineering PCs
Finance PCs
Security PCs
Servers
Printers
Wi-Fi access points
IP phones
Cameras
```

They might all connect to switches.

But should every device belong to one enormous Layer 2 network?

Usually, no.

Modern networks divide Layer 2 environments into smaller logical networks using VLANs.

By the end of this part, you should understand this complete path:

```text
Host
 |
 v
Access Port
 |
 v
VLAN
 |
 v
Switch
 |
 v
Trunk
 |
 v
Another Switch
 |
 v
Same VLAN Host
```

And when communication must cross VLANs:

```text
VLAN 10
   |
   v
Layer 3 Device
   |
   v
VLAN 20
```

You will also understand why switching loops are dangerous, what Spanning Tree does, what link aggregation solves, and how to troubleshoot common VLAN and trunk failures.

---

# 1. What Is a Network Switch?

A network switch connects devices within a network and forwards Ethernet frames between them.

A simple network might look like:

```text
Laptop A
   |
   |
+--------+
| Switch |
+--------+
   |
   |
Laptop B
```

A larger switch might connect:

```text
             +----------------+
             |     Switch     |
             +----------------+
              |   |   |   |   |
              |   |   |   |   |
              v   v   v   v   v

             PC  PC  AP Server Printer
```

At Layer 2, the switch primarily makes forwarding decisions using MAC addresses.

Remember from Part 3:

```text
Ethernet frame
+--------------------------------+
| Destination MAC                |
| Source MAC                     |
| EtherType                      |
| Payload                        |
| FCS                            |
+--------------------------------+
```

The switch examines information such as the destination MAC address and determines where the frame should go.

---

# 2. Why Do We Need Switches?

Imagine an office with 40 computers.

Each computer needs to communicate with:

* Other computers
* Printers
* Servers
* Routers
* Wireless infrastructure
* Other network devices

You cannot practically connect every computer directly to every other computer.

A switch provides a central Layer 2 connectivity point.

Instead of:

```text
PC1 -------- PC2
 | \          |
 |  \         |
 |   \        |
PC3 -------- PC4
```

you can use:

```text
PC1 ----+
        |
PC2 ----+
        |
      Switch
        |
PC3 ----+
        |
PC4 ----+
```

The switch then decides where Ethernet frames should be forwarded.

---

# 3. Switches vs Hubs

Before modern Ethernet switching became standard, Ethernet hubs were common.

A hub is much simpler than a switch.

Suppose four computers connect to a hub:

```text
PC A
  |
  |
+-----+
| Hub |
+-----+
 | | |
 | | |
 B C D
```

If PC A sends traffic into the hub, the hub essentially repeats the electrical signal out its other ports.

Conceptually:

```text
A sends frame
     |
     v
    Hub
  /  |  \
 v   v   v
 B   C   D
```

Even if the frame is intended only for B, C and D may also receive the transmitted signal.

---

# 4. How a Switch Is Different

A switch learns which MAC addresses are reachable through which ports.

Suppose:

```text
PC A
MAC: AA:AA:AA:AA:AA:AA
Port 1

PC B
MAC: BB:BB:BB:BB:BB:BB
Port 2

PC C
MAC: CC:CC:CC:CC:CC:CC
Port 3
```

The switch can build a table:

```text
MAC Address               Port
--------------------------------
AA:AA:AA:AA:AA:AA        1
BB:BB:BB:BB:BB:BB        2
CC:CC:CC:CC:CC:CC        3
```

If A sends a unicast frame to B, the switch can forward it toward port 2 rather than blindly transmitting it everywhere.

Conceptually:

```text
A
|
v
Switch
|
| Port 2
v
B
```

This is one of the fundamental differences between switching and old hub-based Ethernet.

---

# 5. Collision Domains

A collision domain is an Ethernet segment where simultaneous transmissions could interfere with one another under older shared, half-duplex Ethernet behavior.

With a hub:

```text
A ----\
B ----- Hub
C ----/
```

the connected devices share the medium.

With a modern switch:

```text
A ---- Port 1
B ---- Port 2     Switch
C ---- Port 3
```

each switch port forms a separate collision domain.

Modern switched Ethernet normally operates full duplex, so traditional Ethernet collisions are largely not part of normal switched Ethernet operation.

This is one reason switches replaced hubs.

---

# 6. Full Duplex and Switching

Full duplex means both sides can transmit and receive simultaneously.

For example:

```text
Host
  <-------->
Switch
```

Traffic can move in both directions at the same time.

Compare that with half duplex:

```text
Host
   <---->
Shared medium

One side effectively transmits
at a time.
```

Modern Ethernet switch links are normally full duplex.

---

# 7. MAC Address Tables

You already encountered MAC address tables in Part 3.

Now we need to connect them to VLANs.

A switch learns source MAC addresses.

Suppose a frame enters port 5:

```text
Source MAC:
AA:AA:AA:AA:AA:AA

Destination MAC:
BB:BB:BB:BB:BB:BB
```

The switch learns:

```text
AA:AA:AA:AA:AA:AA
is reachable through port 5
```

This information is stored in its MAC address table.

Depending on vendor terminology, you may also hear names such as:

```text
MAC table
CAM table
forwarding table
bridge table
```

---

# 8. How MAC Learning Works

Imagine an empty switch table.

```text
MAC Address     Port
--------------------
```

Host A sends a frame into port 1.

Source MAC:

```text
AA:AA:AA:AA:AA:AA
```

The switch learns:

```text
AA:AA:AA:AA:AA:AA -> Port 1
```

Later Host B sends through port 4:

```text
BB:BB:BB:BB:BB:BB -> Port 4
```

Now:

```text
MAC Address               Port
--------------------------------
AA:AA:AA:AA:AA:AA        1
BB:BB:BB:BB:BB:BB        4
```

When A sends to B, the switch knows where B is located.

---

# 9. Unknown Unicast Traffic

What happens if A sends to a MAC address the switch has not learned yet?

Suppose:

```text
Destination:
CC:CC:CC:CC:CC:CC
```

but there is no matching entry.

The switch cannot determine one specific destination port from its MAC table.

It therefore floods the frame through appropriate ports in that VLAN, except the port on which the frame arrived.

This is called:

```text
Unknown unicast flooding
```

Once the destination communicates and its source MAC is learned, future unicast forwarding can become more specific.

---

# 10. Broadcast Traffic

Some Ethernet traffic intentionally targets everyone within the Layer 2 broadcast domain.

The Ethernet broadcast address is:

```text
ff:ff:ff:ff:ff:ff
```

ARP requests are a classic IPv4 example.

Suppose:

```text
Host A:
192.168.10.10

Target:
192.168.10.50
```

Host A may ask:

```text
Who has 192.168.10.50?
```

That ARP request is broadcast within the relevant Layer 2 broadcast domain.

---

# 11. What Is a Broadcast Domain?

A broadcast domain is the group of Layer 2 devices that can receive a Layer 2 broadcast from one another.

Imagine:

```text
PC1 ----+
        |
PC2 ----+
        |
      Switch
        |
PC3 ----+
        |
PC4 ----+
```

Without VLAN segmentation, these devices may all belong to the same broadcast domain.

An ARP broadcast from PC1 can be flooded toward the other relevant ports.

As networks grow, having every device in one enormous broadcast domain becomes undesirable.

This leads us to VLANs.

---

# 12. Why VLANs Exist

VLAN stands for:

```text
Virtual Local Area Network
```

A VLAN logically divides Layer 2 networks.

Without VLANs:

```text
Engineering
Finance
HR
Servers
Printers
Cameras
Phones

        |
        v

One large Layer 2 network
```

With VLANs:

```text
Engineering -> VLAN 10
Finance     -> VLAN 20
HR          -> VLAN 30
Servers     -> VLAN 40
Phones      -> VLAN 50
```

Each VLAN can form a separate Layer 2 broadcast domain.

---

# 13. VLANs Are Logical Segmentation

This point is important.

You do not necessarily need a separate physical switch for every department.

One physical switch can support multiple logical Layer 2 networks.

For example:

```text
+--------------------------------+
|            Switch              |
|                                |
| Ports 1-8   -> VLAN 10         |
| Ports 9-16  -> VLAN 20         |
| Ports 17-20 -> VLAN 30         |
+--------------------------------+
```

Physically:

```text
One switch
```

Logically:

```text
Three separate VLANs
```

This gives administrators much more flexibility.

---

# 14. VLANs and Broadcast Domains

Suppose:

```text
VLAN 10
PC A
PC B

VLAN 20
PC C
PC D
```

A broadcast from PC A is normally contained within VLAN 10.

Conceptually:

```text
PC A
 |
 | Broadcast
 v

+------------------+
|     VLAN 10      |
|                  |
| PC A      PC B   |
+------------------+

        X

+------------------+
|     VLAN 20      |
|                  |
| PC C      PC D   |
+------------------+
```

The VLAN boundary separates the Layer 2 broadcast domains.

---

# 15. Why Organizations Use VLANs

VLANs are useful for several reasons.

Common examples include:

* Separating departments
* Separating user devices from servers
* Separating guest Wi-Fi
* Separating voice traffic
* Separating cameras and IoT devices
* Creating management networks
* Reducing Layer 2 broadcast scope
* Applying different network policies
* Supporting network organization and troubleshooting

For example:

```text
VLAN 10  Employees
VLAN 20  Servers
VLAN 30  Guest Wi-Fi
VLAN 40  IP Phones
VLAN 50  Cameras
VLAN 99  Network Management
```

But VLANs alone are not a complete security architecture.

They create segmentation. Security controls still need to be applied where traffic crosses boundaries.

---

# 16. VLAN IDs

VLANs are identified using VLAN IDs.

A common configuration might use:

```text
VLAN 10
VLAN 20
VLAN 30
VLAN 100
```

With IEEE 802.1Q, the VLAN ID field is 12 bits.

That gives values from:

```text
0 through 4095
```

However, not all of those values are available as ordinary configurable VLAN IDs.

In normal Ethernet VLAN discussions, usable VLAN IDs are generally:

```text
1 through 4094
```

with some values potentially treated specially or reserved depending on the technology and platform.

A VLAN ID identifies the Layer 2 VLAN.

It is not an IP subnet mask and not an IP address.

---

# 17. VLAN IDs Are Not IP Networks

A common beginner mistake is assuming:

```text
VLAN 10 = 10.0.0.0/24
```

There is no automatic relationship.

You could design:

```text
VLAN 10
192.168.50.0/24
```

or:

```text
VLAN 10
10.20.30.0/24
```

The VLAN ID belongs to Layer 2.

The IP subnet belongs to Layer 3.

Administrators often choose matching numbers because they are easier to remember.

For example:

```text
VLAN 10 -> 10.0.10.0/24
VLAN 20 -> 10.0.20.0/24
VLAN 30 -> 10.0.30.0/24
```

That is a design convention, not a technical requirement.

---

# 18. One Subnet per VLAN

A common network design is:

```text
VLAN 10
10.0.10.0/24

VLAN 20
10.0.20.0/24

VLAN 30
10.0.30.0/24
```

This keeps Layer 2 and Layer 3 boundaries aligned.

Conceptually:

```text
Layer 2                   Layer 3

VLAN 10      <------>     10.0.10.0/24

VLAN 20      <------>     10.0.20.0/24

VLAN 30      <------>     10.0.30.0/24
```

This makes routing and troubleshooting much easier to understand.

---

# 19. What Is an Access Port?

An access port is a switch port normally assigned to one VLAN for endpoint traffic.

Suppose:

```text
Port 1 -> VLAN 10
Port 2 -> VLAN 10
Port 3 -> VLAN 20
Port 4 -> VLAN 20
```

Then:

```text
PC A --- Port 1
          |
        VLAN 10

PC B --- Port 2
          |
        VLAN 10
```

and:

```text
PC C --- Port 3
          |
        VLAN 20
```

Access ports are commonly used for end devices such as:

* PCs
* Printers
* Some servers
* Cameras
* Other endpoints

Exact behavior depends on switch configuration and platform.

---

# 20. Access Port Example

Imagine:

```text
Switch

Port 1 -> Access VLAN 10
Port 2 -> Access VLAN 10
Port 3 -> Access VLAN 20
Port 4 -> Access VLAN 20
```

Connected devices:

```text
Port 1 -> Engineering-PC-1
Port 2 -> Engineering-PC-2
Port 3 -> Finance-PC-1
Port 4 -> Finance-PC-2
```

Logically:

```text
VLAN 10

Engineering-PC-1
        |
        +------+
               |
             Switch
               |
        +------+
        |
Engineering-PC-2
```

Separate from:

```text
VLAN 20

Finance-PC-1
        |
        +------+
               |
             Switch
               |
        +------+
        |
Finance-PC-2
```

They share hardware but not the same Layer 2 VLAN.

---

# 21. What Happens When an Untagged Frame Enters an Access Port?

Suppose port 1 is configured as an access port for VLAN 10.

A PC sends an ordinary Ethernet frame into port 1.

The endpoint usually does not need to know:

```text
I belong to VLAN 10.
```

The switch associates traffic arriving on that access port with VLAN 10.

Conceptually:

```text
PC
 |
 | Ordinary Ethernet frame
 v
Port 1
 |
 | Port configured for VLAN 10
 v
Switch internally treats frame
as belonging to VLAN 10
```

This is one reason VLANs can be transparent to ordinary endpoint devices.

---

# 22. Communication Within the Same VLAN

Suppose:

```text
PC A
IP: 10.0.10.10/24
VLAN: 10

PC B
IP: 10.0.10.20/24
VLAN: 10
```

Both connect to the same switch.

PC A determines:

```text
10.0.10.20
```

is local.

If necessary, it sends ARP:

```text
Who has 10.0.10.20?
```

The ARP broadcast stays within VLAN 10.

PC B replies.

PC A learns PC B's MAC.

Then unicast frames can flow:

```text
PC A
 |
 v
Switch
 |
 v
PC B
```

No router is required simply because the hosts communicate through a switch within the same VLAN and IP subnet.

---

# 23. Same VLAN Across Multiple Switches

Now imagine PC A and PC B are connected to different switches.

```text
PC A
 |
Switch 1
 |
 |
Switch 2
 |
PC B
```

Both should belong to VLAN 10.

How can VLAN 10 travel between the switches?

You could theoretically dedicate a separate physical link to each VLAN:

```text
VLAN 10 link
VLAN 20 link
VLAN 30 link
```

But that becomes inefficient.

Instead, networks commonly use trunk links.

---

# 24. What Is a Trunk Port?

A trunk port can carry traffic for multiple VLANs across one physical link.

Example:

```text
             Trunk
Switch 1 ================= Switch 2

Carries:

VLAN 10
VLAN 20
VLAN 30
```

Instead of requiring:

```text
Three VLANs
=
Three physical switch-to-switch links
```

a trunk can transport traffic for several VLANs over one link.

---

# 25. Access vs Trunk

The basic beginner distinction is:

```text
Access port
-----------
Usually carries endpoint traffic
for one VLAN.

Trunk port
----------
Carries traffic for multiple VLANs.
```

Example:

```text
PC A
 |
 | Access VLAN 10
 v
Switch 1
 |
 | Trunk
 | VLAN 10,20,30
 v
Switch 2
 |
 | Access VLAN 10
 v
PC B
```

This allows PC A and PC B to remain in the same logical VLAN even though they connect to different switches.

---

# 26. The Problem a Trunk Must Solve

Imagine a frame crosses this link:

```text
Switch 1
    |
    | one physical cable
    |
Switch 2
```

The link carries:

```text
VLAN 10 traffic
VLAN 20 traffic
VLAN 30 traffic
```

When Switch 2 receives a frame, it needs to know:

```text
Which VLAN does this frame belong to?
```

That is where VLAN tagging becomes important.

---

# 27. IEEE 802.1Q

The standard mechanism commonly used for Ethernet VLAN tagging is:

```text
IEEE 802.1Q
```

Often pronounced:

```text
802 dot 1 Q
```

802.1Q allows VLAN information to be inserted into Ethernet frames.

Conceptually:

```text
Normal Ethernet frame

+-------------+
| Destination |
| Source      |
| EtherType   |
| Data        |
+-------------+
```

802.1Q-tagged frame:

```text
+-------------+
| Destination |
| Source      |
| 802.1Q Tag  |
| EtherType   |
| Data        |
+-------------+
```

The tag contains information including the VLAN identifier.

---

# 28. The 802.1Q Tag

The 802.1Q tag is four bytes.

It includes fields used for purposes such as:

* Identifying the frame as VLAN-tagged
* Carrying priority information
* Carrying the VLAN ID

At beginner level, the most important information is:

```text
This frame belongs to VLAN X.
```

For example:

```text
Frame
 |
 +-- 802.1Q VLAN ID: 20
```

A receiving switch can use that information to keep VLAN 20 traffic associated with VLAN 20.

---

# 29. Tagged Traffic

Tagged traffic contains VLAN identification information in the Ethernet frame.

For example:

```text
Switch 1
    |
    | Frame tagged VLAN 10
    v
Switch 2
```

Switch 2 receives the frame and understands:

```text
This belongs to VLAN 10.
```

Another frame might arrive:

```text
Frame tagged VLAN 20
```

The switches can therefore distinguish multiple logical Layer 2 networks on the same physical link.

---

# 30. Untagged Traffic

An untagged Ethernet frame does not carry an 802.1Q VLAN tag.

Ordinary endpoint devices connected to access ports commonly send and receive untagged Ethernet traffic.

Conceptually:

```text
PC
 |
 | Untagged
 v
Access Port
 |
 | Switch associates it
 | with VLAN 10
 v
Internal switching
```

If that frame must cross a trunk, the switch can send it with the appropriate VLAN tagging according to its configuration.

---

# 31. Complete Access-to-Trunk Flow

Suppose:

```text
PC A
Switch 1 Port 1
Access VLAN 10

PC B
Switch 2 Port 8
Access VLAN 10
```

Between the switches:

```text
Trunk carrying VLAN 10
```

PC A sends an ordinary frame.

### Step 1

PC A sends:

```text
Untagged Ethernet frame
```

### Step 2

Switch 1 receives it on:

```text
Access port VLAN 10
```

Therefore the switch associates the frame with VLAN 10.

### Step 3

The frame must cross the trunk.

Switch 1 sends it across the trunk as VLAN 10 traffic, normally using an 802.1Q tag where appropriate.

### Step 4

Switch 2 receives:

```text
Tagged VLAN 10 frame
```

### Step 5

Switch 2 knows the destination is reachable through an access port in VLAN 10.

### Step 6

It forwards the traffic toward PC B in the form appropriate for that access port, normally untagged.

Conceptually:

```text
PC A
 |
 | Untagged
 v
Access VLAN 10
 |
 v
Switch 1
 |
 | Tagged VLAN 10
 v
====================
       Trunk
====================
 |
 v
Switch 2
 |
 | Untagged
 v
Access VLAN 10
 |
 v
PC B
```

This packet flow is essential.

---

# 32. What Is the Native VLAN?

On an 802.1Q trunk, there can be a concept called the:

```text
Native VLAN
```

Traditionally, traffic belonging to the native VLAN may cross the trunk without an 802.1Q tag, depending on the platform and configuration.

Conceptually:

```text
Trunk

VLAN 10 -> tagged
VLAN 20 -> tagged
VLAN 30 -> tagged
Native VLAN -> potentially untagged
```

The exact behavior and configuration commands depend on the network vendor.

---

# 33. Why the Native VLAN Matters

Suppose two switches disagree.

Switch 1:

```text
Native VLAN 10
```

Switch 2:

```text
Native VLAN 20
```

Now untagged traffic crossing the trunk may be interpreted differently on each side.

This is called a native VLAN mismatch.

It can cause:

* Incorrect VLAN placement
* Connectivity problems
* Security concerns
* Network warnings on some platforms

A trunk should be configured consistently on both sides.

---

# 34. Do Not Confuse Native VLAN With Access VLAN

These concepts are related to VLAN membership but apply in different contexts.

Access port:

```text
Endpoint-facing port
usually associated with one VLAN
```

Native VLAN:

```text
Special handling of untagged traffic
on an 802.1Q trunk
```

They are not interchangeable terms.

---

# 35. Allowed VLANs on a Trunk

A trunk does not necessarily need to carry every VLAN that exists on the switches.

Administrators can restrict which VLANs are allowed across the trunk.

For example:

```text
Trunk between Switch 1 and Switch 2

Allowed:
VLAN 10
VLAN 20
VLAN 30

Not allowed:
VLAN 40
VLAN 50
```

This matters enormously during troubleshooting.

A VLAN may exist correctly on both switches but still fail across the link because that VLAN is not permitted on the trunk.

---

# 36. Practical Trunk Failure

Suppose:

```text
PC A
Switch 1
VLAN 30
```

needs to communicate with:

```text
PC B
Switch 2
VLAN 30
```

The trunk allows:

```text
VLAN 10
VLAN 20
```

but not:

```text
VLAN 30
```

Then VLAN 30 traffic cannot traverse that trunk as intended.

The PCs may have:

* Correct IP addresses
* Correct subnet masks
* Correct access VLANs
* Working interfaces

and still fail to communicate.

The missing trunk VLAN is the actual problem.

---

# 37. Communication Between VLANs

Now consider:

```text
PC A
VLAN 10
10.0.10.10/24
```

and:

```text
PC B
VLAN 20
10.0.20.20/24
```

Can the Layer 2 switch simply forward PC A's Ethernet frame directly into VLAN 20?

No.

The VLANs represent separate Layer 2 broadcast domains.

Communication between different IP networks requires Layer 3 routing.

This is called:

```text
Inter-VLAN routing
```

---

# 38. Why Routing Is Needed Between VLANs

PC A wants:

```text
10.0.20.20
```

Its own address is:

```text
10.0.10.10/24
```

PC A calculates:

```text
My network:
10.0.10.0/24

Destination network:
10.0.20.0/24
```

The destination is remote from PC A's perspective.

Therefore PC A sends the traffic toward a router or Layer 3 gateway.

This connects directly to what you learned in Part 6.

---

# 39. Inter-VLAN Routing

Conceptually:

```text
VLAN 10
10.0.10.0/24
     |
     |
     v
+-------------+
| Layer 3     |
| Device      |
+-------------+
     |
     |
     v
VLAN 20
10.0.20.0/24
```

The Layer 3 device has connectivity to both VLANs and can route between their IP networks.

That Layer 3 device could be:

* A router
* A Layer 3 switch
* A firewall
* Another routing-capable network device

---

# 40. Default Gateways for VLANs

Suppose:

```text
VLAN 10:
10.0.10.0/24

Gateway:
10.0.10.1
```

and:

```text
VLAN 20:
10.0.20.0/24

Gateway:
10.0.20.1
```

PC A:

```text
10.0.10.10/24
Gateway: 10.0.10.1
```

PC B:

```text
10.0.20.20/24
Gateway: 10.0.20.1
```

When PC A wants PC B, it does not ARP directly for:

```text
10.0.20.20
```

It determines the destination is remote and sends the frame toward the MAC address of:

```text
10.0.10.1
```

Its local gateway.

---

# 41. Inter-VLAN Packet Flow

Let's walk through it.

```text
PC A
IP: 10.0.10.10
VLAN 10

PC B
IP: 10.0.20.20
VLAN 20
```

### Step 1

PC A examines:

```text
10.0.20.20
```

and determines it is remote.

### Step 2

PC A chooses:

```text
10.0.10.1
```

as the gateway.

### Step 3

PC A uses ARP if necessary to learn the gateway's MAC.

### Step 4

PC A creates:

```text
Ethernet frame

Source MAC:
PC A

Destination MAC:
VLAN 10 gateway
```

Inside:

```text
IP packet

Source IP:
10.0.10.10

Destination IP:
10.0.20.20
```

### Step 5

The Layer 3 device receives the frame.

### Step 6

It examines:

```text
Destination IP:
10.0.20.20
```

### Step 7

It determines VLAN 20's network is reachable.

### Step 8

If necessary, it resolves PC B's MAC on VLAN 20.

### Step 9

It constructs a new Ethernet frame for VLAN 20.

### Step 10

PC B receives the packet.

This is inter-VLAN routing.

---

# 42. Router-on-a-Stick

One method of performing inter-VLAN routing is commonly called:

```text
Router-on-a-stick
```

Instead of using one physical router interface for every VLAN, a single physical link can carry several VLANs between a switch and router.

Conceptually:

```text
VLAN 10 ----\
             \
VLAN 20 ------ Switch ===== Router
             /        trunk
VLAN 30 ----/
```

The router uses logical subinterfaces associated with different VLANs.

---

# 43. Router Subinterfaces

Conceptually, a router might have:

```text
Physical interface:
GigabitEthernet0/0
```

with logical subinterfaces:

```text
GigabitEthernet0/0.10
VLAN 10
10.0.10.1/24

GigabitEthernet0/0.20
VLAN 20
10.0.20.1/24

GigabitEthernet0/0.30
VLAN 30
10.0.30.1/24
```

The physical switch-router link operates as a trunk.

Tagged frames allow the router to distinguish which VLAN each frame belongs to.

# 44. Router-on-a-Stick Packet Flow

Suppose PC A in VLAN 10 wants PC B in VLAN 20.

```text
PC A
 |
 | VLAN 10
 v

 |
 | Tagged VLAN 10
 v
Router
 |
 | Routing decision
 |
 | Tagged VLAN 20
 v
Switch
 |
 | VLAN 20
 v
PC B
```

The packet goes:

```text
VLAN 10
   |
   v
Router
   |
   v
VLAN 20
```

Even though both VLANs may physically use the same switch.

---

# 45. Why Router-on-a-Stick Is Useful

It allows one router physical interface to support routing for several VLANs.

This can be useful in:

* Small networks
* Training labs
* Branch environments
* Simple network designs

However, the trunk to the router can become a shared traffic path.

Larger or higher-performance networks often perform inter-VLAN routing directly on Layer 3 switches.

# 46. Layer 2 vs Layer 3 Switches

A Layer 2 switch primarily performs Ethernet switching.

Conceptually:

```text

     |
     v

     |
     v

```

A Layer 3 switch can additionally perform IP routing.

Conceptually:

```text

+

IP-based routing
```

This allows the device to route between VLANs without requiring a separate external router for every inter-VLAN flow.

```text
Allowed
```

Do not assume:

```text

```

by itself.

# 53. Why Network Loops Are Dangerous

Now consider this topology:

```text
Switch A
 |      \
 |       \
 |        \
Switch B---Switch C
```

There are redundant paths between switches.

Redundancy can be useful because a second path may remain available if one link fails.

But Layer 2 Ethernet has a serious problem.

Ethernet frames do not have the same hop-count mechanism that IP uses through TTL to ensure packets cannot circulate indefinitely.

If a Layer 2 loop exists, certain traffic can circulate repeatedly.

---

# 54. A Simple Layer 2 Loop

Imagine:

```text
+----------+
| Switch A |
+----------+
 |        |
 |        |
 |        |
+----------+
| Switch B |
+----------+
```

There are two active Layer 2 links connecting the same switching environment.

A broadcast enters.

Switch A forwards it.

Switch B receives it and forwards it.

Copies can return through the redundant path.

More copies can be created.

The problem can grow extremely quickly.

---

# 55. Broadcast Storms

A broadcast storm occurs when broadcast traffic is repeatedly replicated through a Layer 2 loop, consuming network resources.

Conceptually:

```text
Broadcast
   |
   v
Switch A
 |     |
 v     v
Switch B
 |     |
 +-----+
   |
   v
More copies
   |
   v
More copies
   |
   v
Network overwhelmed
```

Symptoms may include:

* Very high link utilization
* Switch CPU pressure
* Severe packet loss
* Network latency
* Hosts losing connectivity
* Management access becoming difficult
* Large amounts of broadcast traffic

A Layer 2 loop can take down a network surprisingly quickly.

---

# 56. MAC Address Table Instability

Loops can create another problem.

Suppose the same source MAC is seen arriving through different switch ports repeatedly.

The switch may learn:

```text
AA:AA:AA:AA:AA:AA -> Port 1
```

then:

```text
AA:AA:AA:AA:AA:AA -> Port 5
```

then back to:

```text
AA:AA:AA:AA:AA:AA -> Port 1
```

This rapid movement can cause MAC address table instability.

You may hear terms such as:

```text
MAC flapping
MAC address flapping
```

Unexpected MAC flapping can be evidence of a Layer 2 loop or another topology problem.

---

# 57. Spanning Tree Protocol

To support redundant Layer 2 links without allowing uncontrolled loops, Ethernet networks can use:

```text
Spanning Tree Protocol
```

abbreviated:

```text
STP
```

STP allows switches to logically prevent certain redundant paths from forwarding normal traffic so that the active Layer 2 topology is loop-free.

Conceptually:

```text
        Switch A
        /      \
       /        \
      /          \
Switch B -------- Switch C
          X

X = path not forwarding normal traffic
    to prevent a loop
```

If an active path fails, STP can allow an alternate path to become active.

---

# 58. Why STP Exists

We want:

```text
Physical redundancy
```

without:

```text
Logical Layer 2 loops
```

So:

```text
Multiple physical paths
        |
        v
       STP
        |
        v
Loop-free forwarding topology
```

This is the core purpose.

---

# 59. STP Does Not Remove the Cable

Suppose:

```text
Switch A -------- Switch B
   |                  |
   |                  |
   +------------------+
```

STP does not physically disconnect a redundant cable.

Instead, it controls forwarding behavior.

A port or path can be prevented from forwarding ordinary user traffic as part of loop prevention.

If topology conditions change, STP can recalculate which paths should forward.

---

# 60. STP Root Bridge Introduction

Spanning Tree needs a reference point for calculating the loop-free topology.

A switch is elected as the:

```text
Root Bridge
```

Other switches calculate paths toward the root and determine which ports should forward or not forward according to STP rules.

At this stage, remember:

```text
Root Bridge
     |
     v
Reference point for STP topology
```

Detailed root election, bridge IDs, path costs, port roles, STP states, RSTP, and related concepts deserve deeper study later.

---

# 61. STP Troubleshooting Mindset

If a redundant link appears physically connected but does not forward ordinary traffic, do not immediately assume the link is broken.

STP may intentionally be preventing forwarding to avoid a loop.

Ask:

```text
Is the interface physically up?

Is the VLAN allowed?

What is the STP state?

What is the port role?

Is STP intentionally blocking this path?
```

A port being physically up and a port forwarding traffic are not the same thing.

---

# 62. Link Aggregation Introduction

Suppose two switches need more bandwidth and redundancy.

You might think:

```text
Connect four cables between them.
```

But simply adding parallel Layer 2 links can create loops.

Instead, multiple physical links can be logically bundled into one logical connection.

This is called:

```text
Link aggregation
```

---

# 63. Link Aggregation Concept

Instead of:

```text
Switch A ---- Link 1 ---- Switch B
Switch A ---- Link 2 ---- Switch B
Switch A ---- Link 3 ---- Switch B

Three unrelated Layer 2 paths
```

we can logically combine them:

```text
Switch A
   ||
   || Link 1
   || Link 2
   || Link 3
   ||
Switch B

       |
       v

One logical aggregated link
```

Benefits can include:

* Increased aggregate bandwidth
* Link redundancy
* Better utilization of multiple physical links

---

# 64. LACP Introduction

A common standard protocol used to negotiate and manage link aggregation is:

```text
LACP
```

which stands for:

```text
Link Aggregation Control Protocol
```

LACP is associated with IEEE link aggregation standards.

Depending on vendor terminology, aggregated links may be called things such as:

```text
Port channel
EtherChannel
Bond
Team
LAG
```

These terms are not always perfectly interchangeable across every platform, but they describe closely related concepts.

---

# 65. Important Link Aggregation Limitation

Do not assume that combining four 1 Gbps links means one single network flow automatically becomes:

```text
4 Gbps
```

Traffic is typically distributed across member links using a hashing mechanism based on information such as:

* Source MAC
* Destination MAC
* Source IP
* Destination IP
* Transport ports

depending on platform and configuration.

A single flow may remain on one physical member.

The aggregate benefits become more apparent across multiple flows.

# 70. Wrong VLAN and DHCP

Suppose VLAN 10 has:

```text

```

```text

```

```text

```

instead of:

```text

```

# 74. Missing VLAN on a Trunk

Suppose:

```text
Switch A trunk allows:
10,20,30
```

Switch B expects:

```text
10,20,30,40
```

A VLAN 40 device behind Switch A tries to communicate with a VLAN 40 device behind Switch B.

Traffic fails.

Why?

Because VLAN 40 is not carried correctly across the trunk.

The physical link can still be:

```text
UP
```

Other VLANs may work perfectly.

This creates an important troubleshooting clue:

```text
Only one VLAN is broken.
```

That often points toward VLAN-specific configuration rather than complete physical failure.

# 75. Native VLAN Mismatch

Suppose:

```text
Switch A
Native VLAN: 10

Switch B
Native VLAN: 20
```

Untagged traffic sent across the trunk can be classified differently by the two switches.

Possible symptoms can include:

* Unexpected connectivity
* VLAN leakage concerns
* Control-protocol warnings
* Traffic appearing in the wrong VLAN
* Difficult-to-understand intermittent behavior

The solution is not to randomly change VLAN IDs.

Verify both ends of the trunk and make their intended configuration consistent.

# 76. Troubleshooting Same-VLAN Communication

```text
VLAN 10

VLAN 10
```

They cannot communicate.

```text

2. Are the IP addresses correct?

3. Are the prefixes correct?

4. Does each host believe the other is local?

5. Are both access ports actually in VLAN 10?

6. If different switches are involved,
   is VLAN 10 carried across the trunk?

7. Is STP preventing the expected path?

8. Can ARP requests and replies be observed?
```

This is structured troubleshooting.

# 77. Troubleshooting Inter-VLAN Communication

Scenario:

```text
Host A:
10.0.10.10/24
Gateway: 10.0.10.1

Host B:
10.0.20.20/24
Gateway: 10.0.20.1
```

They cannot communicate.

First determine:

```text
Can Host A reach 10.0.10.1?
```

Then:

```text
Can Host B reach 10.0.20.1?
```

Then verify:

```text
Does the Layer 3 device have both networks?

Is IP routing enabled where required?

Are the VLAN interfaces operational?

Are security policies blocking the traffic?

Are return routes available?
```

Do not treat every inter-VLAN failure as a VLAN problem.

The VLANs may work perfectly while routing or policy fails.

# 78. Practical Packet Flow 1: Same Switch, Same VLAN

Network:

```text
Host A
10.0.10.10/24
VLAN 10
Port 1

Host B
10.0.10.20/24
VLAN 10
Port 2
```

Host A wants Host B.

### Step 1

Host A calculates that:

```text
10.0.10.20
```

is local.

### Step 2

If necessary:

```text
ARP:
Who has 10.0.10.20?
```

### Step 3

The switch floods the ARP broadcast within VLAN 10.

### Step 4

Host B replies.

### Step 5

Host A learns Host B's MAC.

### Step 6

Host A sends a unicast Ethernet frame.

### Step 7

The switch uses its MAC table to forward the frame toward port 2.

No router is needed.

# 79. Practical Packet Flow 2: Same VLAN, Different Switches

Network:

```text

 |

 |
Switch A
 |
Trunk
 |

 |
Access VLAN 10
 |
```

Switch A receives the broadcast in VLAN 10.

It sends VLAN 10 traffic across the trunk.

Switch B recognizes VLAN 10 from the trunk's VLAN handling.

It floods the ARP to appropriate VLAN 10 access ports.

Host B replies.

The reply crosses the trunk as VLAN 10 traffic.

Both hosts remain in the same Layer 2 broadcast domain even though they use different physical switches.

Instead of installing one physical NIC for every network, a trunk-like VLAN-aware connection can carry multiple VLANs.

```text
             Linux Host
        +------------------+
        | Management       |
        | Application      |
        | Storage          |
        +------------------+
                 |
                 |
            VLAN trunk
                 |
                 v
               Switch
```

The exact implementation depends on the operating system, hypervisor, switch, and architecture.

# 98. Common Beginner Mistakes

### Mistake 1: VLAN ID equals subnet

No.

```text
VLAN = Layer 2 segmentation

Subnet = Layer 3 addressing
```

They are often associated by design, but they are not the same thing.

### Mistake 2: Different VLANs can communicate through ordinary Layer 2 switching

No.

Inter-VLAN communication requires Layer 3 forwarding.

### Mistake 3: A trunk is just a faster port

No.

A trunk's defining purpose is carrying traffic for multiple VLANs.

### Mistake 4: All trunk traffic must always be tagged

Be careful.

Native VLAN handling can involve untagged traffic depending on configuration.

### Mistake 5: VLANs automatically provide complete security

No.

Routing and security policies determine what cross-VLAN communication is permitted.

### Mistake 6: Physically connected means forwarding

No.

STP may intentionally prevent a link from forwarding normal traffic.

### Mistake 7: More parallel cables always mean more bandwidth

Not safely without proper network design.

Uncontrolled redundant Layer 2 links can create loops.

### Mistake 8: Four 1 Gbps aggregated links guarantee one 4 Gbps flow

No.

A single flow may remain on one member depending on the load-balancing mechanism.

# 102. Final Troubleshooting Challenge

Consider this network:

```text
Developer PC
10.10.10.50/24
Gateway: 10.10.10.1
VLAN 10
      |
      v
Switch A
      |
      | Trunk
      |
      v
Switch B
      |
      v
Layer 3 Switch
      |
      +-------------------+
      |                   |
      v                   v
VLAN 10                VLAN 20
10.10.10.0/24          10.10.20.0/24
                      |
                      v
                   Server
                   10.10.20.50
```

The developer reports:

```text
I cannot reach the server.
```

Do not start by changing configuration.

Work through the layers.

### Step 1: Check the developer PC

```bash
ip addr
```

Confirm:

```text
10.10.10.50/24
```

### Step 2: Check its route

```bash
ip route
```

Confirm the expected gateway:

```text
10.10.10.1
```

### Step 3: Check the route toward the server

```bash
ip route get 10.10.20.50
```

The host should select its gateway.

### Step 4: Inspect the gateway neighbor

```bash
ip neigh show 10.10.10.1
```

Can the developer PC resolve its gateway's MAC address?

If not, investigate VLAN 10's Layer 2 path first.

### Step 5: Check the access port

Is the developer connected to:

```text
VLAN 10?
```

### Step 6: Check the trunk

Does the Switch A to Switch B trunk carry:

```text
VLAN 10?
```

### Step 7: Check STP

Is VLAN 10's intended path forwarding?

### Step 8: Check the VLAN 10 gateway

Is:

```text
10.10.10.1
```

operational?

### Step 9: Check Layer 3 routing

Does the Layer 3 switch know:

```text
10.10.10.0/24
```

and:

```text
10.10.20.0/24
```

### Step 10: Check VLAN 20

Is the server actually connected to VLAN 20?

### Step 11: Check the server

Does it have:

```text
10.10.20.50/24
```

and the correct gateway?

### Step 12: Check security policy

If switching and routing work, determine whether an ACL, firewall, or another policy prevents the developer network from reaching the server.

Notice what you did not do.

You did not randomly change:

```text
DNS
VLAN IDs
routes
firewall rules
switch ports
```

You followed the packet.
