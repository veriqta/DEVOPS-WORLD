# 1. What Is Observability?

Observability is the ability to understand what is happening inside a system by examining the signals the system produces.

Imagine a production application.

You cannot physically look inside every:

* EC2 process
* ALB request
* Database connection
* Network interface
* Application thread
* User request

Instead, the system produces evidence.

Examples:

```text
CPU utilization
Request count
HTTP error rate
Database connections
Application logs
Latency
Target health
Disk usage
Memory usage
Deployment events
```

You use those signals to understand the internal state of the system.

That is the foundation of observability.

# 2. Observability Is About Answering Questions

A good observability system helps answer questions such as:

```text
Why is the website slow?
```

```text
Why did errors start at 14:32?
```

```text
Which service is failing?
```

```text
Did the database run out of connections?
```

```text
Did the new deployment cause the problem?
```

```text
Are users affected in one path or the whole application?
```

```text
Did Auto Scaling respond to the traffic spike?
```

```text
Is the problem CPU, memory, disk, database, network, or application code?
```

Observability is not simply:

```text
We have a dashboard.
```

A dashboard that cannot help answer useful questions is not enough.

# 3. Monitoring vs Observability

Monitoring usually focuses on known conditions.

For example:

```text
CPU > 80%
```

or:

```text
Healthy targets < 2
```

or:

```text
Free storage < 10 GB
```

You already know the condition you want to watch.

Observability goes further.

It helps investigate questions you did not predict beforehand.

For example:

```text
Why are only checkout requests slow?
```

or:

```text
Why did latency increase even though CPU stayed normal?
```

or:

```text
Why are only one Availability Zone's targets unhealthy?
```

Monitoring is part of observability.

Observability is the broader ability to understand system behavior.

* Metrics

# 5. What Is a Metric?

A metric is a numerical measurement recorded over time.

Examples:

```text
CPU utilization = 72%
```

```text
Request count = 4,500
```

```text
Database connections = 85
```

```text
Target response time = 0.42 seconds
```

A metric has:

```text
Name
Value
Timestamp
```

and often:

```text
Dimensions
Namespace
Unit
Statistic
```

# 6. Metrics Are Time Series

A metric becomes useful when you observe it over time.

Example:

```text
12:00  CPU 20%
12:05  CPU 25%
12:10  CPU 31%
12:15  CPU 65%
12:20  CPU 92%
```

Now you can see a trend.

One number tells you:

```text
Current value
```

A time series tells you:

```text
Behavior
```

That distinction is important.

# 7. Why Metrics Are Useful

Metrics are useful for:

* Trends
* Thresholds
* Capacity planning
* Alerts
* Performance analysis
* Scaling
* Availability monitoring

For example:

```text
CPU steadily rising for 30 minutes
```

may suggest capacity pressure.

But:

```text
CPU briefly spikes to 95% for 10 seconds
```

may not indicate a serious problem.

Context matters.

# 8. What Is a Log?

A log is a record describing something that happened.

Example application log:

```text
2026-09-06T14:20:15Z INFO User login successful user_id=1042
```

Error:

```text
2026-09-06T14:22:33Z ERROR Database connection timeout
```

Web server:

```text
203.0.113.5 GET /api/orders 500 1.482s
```

System log:

```text
nginx.service entered failed state
```

Logs provide detail that metrics often cannot.

# 9. Metrics vs Logs

Suppose:

```text
HTTP 5xx error count = 300
```

That metric tells you:

```text
Many errors occurred.
```

But it may not tell you why.

Logs may show:

```text
ERROR database connection pool exhausted
```

Now you have the likely cause.

Metrics tell you:

```text
Something changed.
```

Logs often help explain:

```text
What happened?
```

# 10. What Is an Event?

An event represents something that happened at a specific point in time.

Examples:

```text
EC2 instance launched
```

```text
Auto Scaling instance terminated
```

```text
RDS failover started
```

```text
Deployment completed
```

```text
CloudWatch alarm changed to ALARM
```

```text
Security Group changed
```

Events are useful because many incidents begin after a change.

# 11. The Importance of Timeline Correlation

Imagine:

```text
14:00 Deployment completed
14:02 Error rate increases
14:03 CPU normal
14:04 Database connections spike
14:05 Users report checkout failures
```

These signals together tell a story.

Observability often means building a timeline from:

```text
Metrics
+
Logs
+
Events
```

instead of looking at each in isolation.

# 14. Metrics Have Namespaces

CloudWatch organizes metrics into namespaces.

A namespace groups related metrics.

Examples include namespaces associated with AWS services such as:

```text
AWS/EC2
```

```text
AWS/ApplicationELB
```

```text
AWS/RDS
```

```text
AWS/AutoScaling
```

You can also publish custom metrics into your own namespace.

Example:

```text
VERIQTA/Application
```

The namespace prevents unrelated metrics from being mixed together.

# 15. Example Namespace

Suppose you look inside:

```text
AWS/EC2
```

You may find metrics such as:

```text
CPUUtilization
NetworkIn
NetworkOut
DiskReadBytes
DiskWriteBytes
```

Inside:

```text
AWS/RDS
```

you may find:

```text
CPUUtilization
DatabaseConnections
FreeStorageSpace
ReadLatency
WriteLatency
```

Same metric name can exist in different namespaces.

The namespace provides context.

# 16. What Is a Dimension?

A dimension identifies a particular characteristic associated with a metric.

For example:

```text
InstanceId = i-0123456789
```

This tells CloudWatch which EC2 instance the metric belongs to.

Another example:

```text
DBInstanceIdentifier = prod-db
```

Another:

```text
LoadBalancer = app/prod-alb/...
```

Dimensions allow CloudWatch to distinguish one resource from another.

# 17. Namespace + Metric + Dimension

Think:

```text
Namespace:
AWS/EC2

Metric:
CPUUtilization

Dimension:
InstanceId=i-0123456789
```

Together this means:

```text
CPU utilization
for this specific EC2 instance
```

Without dimensions, a metric may not have enough context.

# 18. Statistics

Metrics are collected as data points.

CloudWatch can calculate statistics over a time period.

Common examples include:

```text
Average
Minimum
Maximum
Sum
SampleCount
```

Suppose CPU values during five minutes are:

```text
20
30
40
80
90
```

Average:

```text
52%
```

Maximum:

```text
90%
```

These tell very different stories.

# 19. Why Statistic Selection Matters

Suppose latency is usually:

```text
100 ms
```

but one request takes:

```text
10 seconds
```

Average latency may still look acceptable.

If you only inspect averages, you may miss bad user experiences.

Later you may work with percentiles such as:

```text
p95
p99
```

For now, understand:

```text
Average
```

does not always represent the worst experience.

# 20. Periods

CloudWatch metrics are evaluated over periods.

For example:

```text
1 minute
5 minutes
15 minutes
```

A period controls how data points are grouped for a graph or alarm.

Example:

```text
Average CPU over 5 minutes
```

means something different from:

```text
Maximum CPU over 1 minute
```

Alarm design depends on choosing the correct period and statistic.

# 21. EC2 Metrics

EC2 automatically publishes several infrastructure metrics to CloudWatch.

Important examples include:

```text

NetworkIn
NetworkOut
DiskReadOps
DiskWriteOps
DiskReadBytes
DiskWriteBytes
StatusCheckFailed
```

Exact available metrics depend on configuration and resource type.

# 22. CPUUtilization

This metric measures EC2 CPU utilization.

Example:

```text
CPUUtilization = 92%
```

Possible reasons:

* Heavy legitimate traffic
* CPU-intensive application
* Infinite loop
* Background process
* Compression
* Encryption workload
* Poor code
* Excessive requests

Do not immediately conclude:

```text
Need larger EC2.
```

Ask why CPU increased.

# 23. CPU Troubleshooting Example

Observed:

```text
14:00 CPU = 20%
14:05 CPU = 24%
14:10 Deployment
14:15 CPU = 93%
```

This timeline suggests:

```text
Deployment may have changed CPU behavior.
```

Now inspect:

* Application logs
* Process CPU
* Request volume
* Deployment changes

Metrics provide the clue.

Logs provide detail.

# 24. NetworkIn and NetworkOut

These metrics show network data flowing into and out of the EC2 instance.

A sudden increase could mean:

* Traffic spike
* Large downloads
* Backup process
* Replication
* Unexpected network activity

Again:

```text
High NetworkOut
```

is not automatically bad.

Context determines whether the value is expected.

# 25. EC2 Status Checks

EC2 performs status checks.

Failures can indicate problems involving:

```text
Underlying AWS infrastructure
```

or:

```text
The EC2 instance itself
```

These can help distinguish:

```text
Application failure
```

from:

```text
Instance/infrastructure failure
```

# 26. Important Limitation: Memory Is Not a Standard EC2 Metric

A very important beginner lesson:

CloudWatch does not automatically provide operating-system memory usage for ordinary EC2 instances through the standard EC2 metric set.

Why?

AWS can observe the virtual machine infrastructure.

But memory utilization exists inside the guest operating system.

To collect metrics such as:

```text
Memory usage
Disk filesystem usage
Swap usage
```

you generally need an agent or another monitoring method.

This is where the CloudWatch Agent becomes important.

# 27. CPU Normal Does Not Mean Server Healthy

Suppose:

```text
CPU = 20%
```

but:

```text
Memory = 99%
```

The application could be near failure.

If you only watch default CPU metrics, you may completely miss the problem.

Observability requires selecting the correct signals.

# 28. What Is the CloudWatch Agent?

The CloudWatch Agent is software that can run on supported servers to collect additional metrics and logs.

For example:

```text
Linux EC2
   |
   v
CloudWatch Agent
   |
   +---- Memory metrics
   +---- Disk metrics
   +---- Log files
   |
   v
CloudWatch
```

It can also be used in environments beyond EC2 depending on setup.

# 29. CloudWatch Agent Use Cases

You might use the agent to collect:

```text
Memory utilization
Disk usage
Swap usage
Process-related measurements
Application log files
System logs
```

This fills important gaps left by default infrastructure metrics.

# 30. CloudWatch Agent Architecture

Conceptually:

```text
Linux Server
 |
 +---- /var/log/messages
 +---- /var/log/nginx/access.log
 +---- /var/log/nginx/error.log
 +---- memory metrics
 +---- disk metrics
 |
 v
CloudWatch Agent
 |
 v
CloudWatch
```

The agent needs:

* Correct installation
* Configuration
* IAM permissions
* Network connectivity
* Correct log paths

# 31. IAM Permissions for the Agent

The agent must be authorized to send data to CloudWatch.

If the agent runs on EC2, a good approach is to use an IAM role attached to the instance.

Conceptually:

```text
EC2
 |
 v
IAM Role
 |
 v
CloudWatch permissions
 |
 v
CloudWatch
```

Do not place long-lived AWS access keys inside the agent configuration.

# 32. Installing the CloudWatch Agent

The installation process varies by Linux distribution and environment.

Before installation, identify the operating system:

```bash
cat /etc/os-release
```

Then use the supported installation method for that distribution.

Do not blindly copy an Amazon Linux package command onto Ubuntu or vice versa.

# 33. Agent Configuration

The CloudWatch Agent uses configuration describing what should be collected.

Conceptually:

```json
{
  "metrics": {
    "metrics_collected": {
      "mem": {},
      "disk": {}
    }
  }
}
```

A real configuration may contain additional settings.

The important concept is:

```text
You explicitly define
what the agent should collect.
```

# 34. Memory Metrics

After the agent is configured correctly, you can collect metrics such as memory utilization.

Conceptually:

```text
mem_used_percent = 78%
```

This gives visibility unavailable from the standard EC2 metric set.

# 35. Disk Usage

The agent can also monitor filesystem usage.

Example:

```text
/ filesystem
92% used
```

This is different from EC2 disk I/O metrics.

Understand the distinction:

```text
DiskReadBytes
```

means:

```text
How much disk I/O occurred.
```

While:

```text
Disk used percent
```

means:

```text
How full the filesystem is.
```

These are completely different questions.

# 36. Why Disk Usage Matters

Suppose:

```text
/var
100% full
```

Your application may fail to:

* Write logs
* Create temporary files
* Save uploads
* Start services
* Write application state

CPU may remain completely normal.

Without disk monitoring, the failure may seem mysterious.

# 37. CloudWatch Logs

CloudWatch Logs is the CloudWatch capability for collecting, storing, and analyzing logs.

Conceptually:

```text
Application logs
Linux logs
Nginx logs
       |
       v
CloudWatch Logs
       |
       v
Centralized log storage
```

This is important because your EC2 instances may be temporary.

# 38. Why Centralize Logs?

Imagine an Auto Scaling instance fails.

```text
EC2 A
  X
terminated
```

If all logs existed only in:

```text
/var/log/myapp.log
```

on EC2 A, you may lose important incident evidence.

Instead:

```text
EC2 A
 |
 v
CloudWatch Logs
```

allows logs to survive beyond the individual instance.

This is essential for replaceable infrastructure.

# 39. What Is a Log Group?

A log group is a logical container for related log streams.

Example:

```text
/aws/ec2/veriqta-app
```

or:

```text
/veriqta/production/application
```

A log group can contain logs from multiple instances.

Think:

```text
Log Group
   |
   +---- Log Stream A
   +---- Log Stream B
   +---- Log Stream C
```

# 40. What Is a Log Stream?

A log stream represents a sequence of log events from a particular source.

Example:

```text
Log Group:
/veriqta/prod/app

Streams:
i-abc123
i-def456
i-ghi789
```

Each EC2 instance could send its application logs into a separate stream.

Conceptually:

```text
EC2 A
 |
 v
Stream A
     \
      \
       > Log Group
      /
     /
EC2 B
 |
 v
Stream B
```

# 41. Log Event

Inside a stream, you have individual events.

Example:

```text
2026-09-06T14:31:22Z INFO Request completed status=200
```

```text
2026-09-06T14:31:24Z ERROR DB connection timeout
```

Each event generally includes:

```text
Timestamp
Message
```

# 42. Log Group Design

Avoid creating random log groups such as:

```text

```

Use a naming strategy.

Example:

```text

```


# 43. Log Retention

Do not keep every log forever by accident.

CloudWatch Logs supports retention settings.

You might choose:

```text

30 days
90 days
```

* Troubleshooting needs
* Compliance
* Security
* Cost
* Audit requirements

If no expiration is configured, logs can remain indefinitely.

Retention should be intentional.

# 45. Application Logs

Applications should produce useful logs.

Poor:

```text

```

```text

```

Useful logs provide context.

But do not log:

* Passwords
* Access tokens
* Secrets
* Credit card data
* Sensitive personal information unnecessarily

Observability must not create a data-leak problem.

Common application log levels include:

```text

WARN
ERROR

```

Exact names vary by framework.

A reasonable mental model:

```text

Normal operational events
```

Do not run extremely verbose debug logging indefinitely in production without understanding cost and security implications.

# 47. Structured Logging

Structured logs are easier for systems to analyze.

Instead of:

```text

```

use structured data conceptually like:

```json
{
  "level": "ERROR",
  "user_id": 42,
  "operation": "checkout",
  "error": "database_unavailable"

```

This makes filtering and analysis easier.

# 48. Request IDs

A useful application pattern is assigning a unique request or correlation ID.

Example:

```text

```

Then logs across services may include the same identifier.

Example:

```text

```

```text

```


# 49. Metric Filters

CloudWatch Logs can turn matching log patterns into metrics.

This is a powerful concept.

Suppose application logs contain:

```text
ERROR payment_failed
```

You can define a metric filter that counts occurrences.

Conceptually:

```text
Logs
 |
 | pattern: payment_failed
 v
Metric Filter
 |
 v
Custom Metric
 |
 v
PaymentFailures
```

Now a text event becomes a numerical time series.

# 50. Why Metric Filters Matter

Logs contain rich detail.

Metrics are easier to:

* Graph
* Alarm on
* Trend

Metric filters let you bridge the two.

Example:

```text
Application log:
ERROR database_timeout
```

Metric filter:

```text
Count database_timeout
```

Metric:

```text
DatabaseTimeoutCount
```

Alarm:

```text
DatabaseTimeoutCount > 20 in 5 minutes
```

Now operationally important log events become alertable.

# 54. CloudWatch Alarms

A CloudWatch alarm watches a metric and evaluates it against defined conditions.

Example:

```text
Metric:
CPUUtilization

Threshold:
Greater than 80%

Period:
5 minutes

Evaluation:
3 consecutive periods
```

Conceptually:

```text
Metric
 |
 v
Alarm condition
 |
 v
State changes
```

# 55. Alarm States

CloudWatch alarms have states such as:

```text
OK
```

```text
ALARM
```

```text
INSUFFICIENT_DATA
```

Understand each one.

# 56. OK

`OK` means the metric is currently not breaching the configured alarm condition according to the evaluation rules.

It does not necessarily mean:

```text
The entire system is healthy.
```

It only means:

```text
This alarm condition is not currently triggered.
```

# 57. ALARM

`ALARM` means the metric has breached the configured condition according to the evaluation rules.

Example:

```text
DatabaseConnections > 180
for 3 evaluation periods
```

Alarm transitions to:

```text
ALARM
```

# 58. INSUFFICIENT_DATA

This means CloudWatch does not currently have enough usable data to determine whether the alarm should be OK or ALARM.

Possible reasons:

* New resource
* Metric not publishing
* Agent stopped
* Incorrect dimensions
* Sparse metric
* Resource terminated

Do not ignore `INSUFFICIENT_DATA`.

It may indicate a monitoring gap.

# 59. Alarm Design Matters

Bad alarm:

```text
CPU > 50% for 1 minute
```

for every server.

This might produce constant noise.

If engineers receive dozens of meaningless alarms every day, they stop trusting alerts.

This is:

```text
Alert fatigue
```

Good alarms should represent conditions that require attention or action.

# 60. Alert on Symptoms and Causes

A strong monitoring strategy may include both.

Symptom:

```text
HTTP 5xx rate high
```

Cause:

```text
Database connections exhausted
```

If you alert only on causes, you may miss unexpected failure modes.

If you alert only on symptoms, investigation can take longer.

Use a balanced approach.


```text

```

```text

```

```text

```

# 68. RequestCount

This tells you how much request traffic the ALB is handling.

Example:

```text
12:00  10,000 requests
12:05  11,500
12:10  25,000
```

Now CPU increases.

You can correlate:

```text
Traffic increase
+
CPU increase
```

This is far more useful than looking at CPU alone.

# 69. TargetResponseTime

This measures how long targets take to begin responding to requests through the ALB.

If:

```text
TargetResponseTime
```

increases significantly, investigate:

* Application
* Database
* Downstream services
* Resource saturation

It may not be an ALB problem.

The ALB may simply be observing slow targets.

# 70. ALB 5xx vs Target 5xx

This distinction is very useful.

ALB-generated 5xx errors may point toward:

```text
Load balancer/backend communication problems
```

Target 5xx errors indicate:

```text
Application targets returned 5xx responses
```

Example:

```text
HTTPCode_ELB_5XX_Count increases
```

may suggest a different investigation than:

```text
HTTPCode_Target_5XX_Count increases
```

Always identify who produced the error.

# 71. HealthyHostCount

This metric tells you how many targets are healthy.

Suppose:

```text
Desired ASG capacity = 4
```

but:

```text
HealthyHostCount = 2
```

Something is wrong.

Possible causes:

* Bootstrap failure
* Health check failure
* Application crash
* Security Group problem
* Deployment failure

This metric connects the load-balancer and Auto Scaling layers.

# 72. UnHealthyHostCount

If unhealthy targets increase after a deployment:

```text
14:00 deployment
14:02 UnHealthyHostCount rises
```

that is strong evidence.

Now investigate:

* Application startup
* Health endpoint
* Port
* Security Group
* New configuration

But do not wait for the alarm to understand growth.




# 85. Verify Logs Locally First

Before blaming CloudWatch, verify the application is actually writing logs.

Run:

```bash
sudo tail -f /var/log/veriqta/app.log
```

If the file does not exist, CloudWatch cannot collect it.

Check:

```bash
ls -l /var/log/veriqta/
```

Then:

```bash
sudo tail -n 50 /var/log/veriqta/app.log
```

First validate the source.

# 86. `tail` Command

Example:

```bash
tail -n 50 app.log
```

Breakdown:

```text
tail
```

shows the end of a file.

```text
-n 50
```

shows the last 50 lines.

Useful for recent events.

# 87. Following Logs

Run:

```bash
tail -f app.log
```

`-f` means follow.

New lines appear as the application writes them.

This is useful during troubleshooting.

Press:

```text
Ctrl+C
```

to stop following.

# 88. `journalctl`

For systemd-managed services:

```bash
sudo journalctl -u myapp
```

shows logs for:

```text
myapp.service
```

Follow:

```bash
sudo journalctl -u myapp -f
```

Recent entries:

```bash
sudo journalctl -u myapp -n 100
```

This is often critical for debugging failed Linux services.

# 89. CloudWatch Log Collection Failure

Suppose the log group is empty.

Do not immediately reinstall the agent.

Investigate systematically.

Ask:

1. Is the application writing logs locally?
2. Is the configured path correct?
3. Can the agent read the file?
4. Is the agent running?
5. Does the instance role allow CloudWatch Logs actions?
6. Can the instance reach required AWS endpoints?
7. Is the agent configuration valid?
8. Are logs going to a different group or stream?

# 90. Check Agent Status

For example:

```bash

```

If the service is stopped, logs will not be shipped.

# 92. File Permission Problem

Suppose application log:

```text

```

# 96. Troubleshooting From Evidence

Now we reach the most important part.

Suppose a user reports:

```text
The website is slow.
```

Poor troubleshooting:

```text

```

Then:

```text
Restart RDS.
```

Then:

```text
Increase instance size.
```

Then:

```text
Open Security Groups.
```

This is guessing.

A stronger process is:

```text
Observe
→ Define symptom
→ Check metrics
→ Check logs
→ Check recent events
→ Form hypothesis
→ Test
→ Fix
→ Verify
```

# 97. Step 1: Define the Symptom

Instead of:

```text
Website slow
```

ask:

```text
Which URL?
```

```text
All users or some?
```

```text
When did it start?
```

```text
Slow or completely failing?
```

```text
What HTTP status?
```

```text
Does it affect reads, writes, or both?
```

The more precise the symptom, the faster the investigation.


Then inspect application logs.

```text

```

Then inspect RDS.

Maybe:

```text

```

Now your evidence chain is:

```text

   |

   |

   |

RDS connections extremely high
   |
   v
Connection pool exhaustion
```

That is observability-driven troubleshooting.

# 101. Scenario: EC2 CPU High

Check traffic first.

If:

```text

```

and:



* Metric

* Warmup
* Scaling activities

# 102. Scenario: CPU High but Traffic Normal

This suggests something else.

Check:

* Deployment
* Background job
* Runaway process
* Infinite loop
* Malware/security issue
* Batch processing

On Linux:

```bash

```

or:

```bash

```

Now identify which process is using CPU.

# 103. Scenario: Memory Exhaustion

CloudWatch Agent shows:

```text

```

Application logs show:

```text
Out of memory
```

Now you have evidence.

Investigate:

* Memory leak
* Too-large cache
* Too many worker processes
* Too many connections
* Incorrect heap configuration

Do not solve every memory incident by permanently increasing instance size.

Find the growth pattern.

# 104. Scenario: Disk Full

Agent metric:

```text

```

Application log:

```text
No space left on device
```

Now inspect:

```bash

```

Then:

```bash
du -sh /var/log/*
```

or appropriate directories.

Possible root cause:

```text
Application logs grew without rotation.
```

The infrastructure is not mysteriously broken.

The filesystem is full.

# 105. Scenario: Auto Scaling Is Launching Instances but Service Still Slow

Check:

```text

```

but:

```text

```

That tells you new instances are not becoming healthy.

Inspect:

```text
Pending capacity
```

then:

```text
Bootstrap logs
```

then:

```text
CloudWatch Agent logs
```

then:

```text
Application health endpoint
```

Possible root cause:

```text

```

Auto Scaling itself may be functioning perfectly.

# 106. Scenario: RDS Connections Spike After Scaling

```text
12:10 ASG desired = 10
12:12 DB connections rise from 80 to 500
```

```text

```


* Pool size per instance
* RDS Proxy
* Database connection limit
* Application connection behavior

This is a system-level incident.

# 107. Scenario: Only One AZ Is Failing

* Route table
* NACL
* Security Groups

# 108. Scenario: Users Report Errors but Dashboard Looks Fine

# 136. Do Not Log Secrets

Never intentionally log:

```text
Passwords
API keys
Session tokens
AWS credentials
Private keys
Full payment data
```

Example of bad logging:

```text
Login failed username=ann password=Secret123
```

Better:

```text
Login failed username=ann reason=invalid_credentials
```

Observability must respect security and privacy.

# 137. Log Volume and Cost

More logs are not automatically better.

If every request produces:

```text
100 KB of debug output
```

and you process millions of requests, logging cost can become substantial.

Design:

* Log levels
* Retention
* Sampling
* Structured fields
* Useful events

Observability should be informative, not wasteful.

# 138. Metric Cardinality Introduction

Custom metrics with many unique dimension combinations can become expensive and difficult to manage.

For example:

Bad idea:

```text
Dimension:
user_id = every individual user
```

for millions of users.

This creates huge metric cardinality.

Metrics should generally aggregate useful operational dimensions.

Use logs or another system for highly detailed per-entity data.

# 141. Example Complete Investigation

```text

```



```text
DatabaseConnections increased from 80 to 400.
```

Step 4:

Auto Scaling:

```text
Desired capacity changed from 2 to 10.
```

Step 5:

Application configuration:

```text
Pool size = 50 connections per instance.
```

Calculation:

```text
10 x 50
=
500 possible connections
```

Root cause:

```text
Application scale-out multiplied database connection pools beyond safe database capacity.
```

Possible remediation:

* Reduce pool size
* Improve connection reuse
* Consider RDS Proxy
* Review database capacity
* Adjust application scaling

This is observability connecting multiple services.

# 146. Answers

## Answer 1

Observability is the ability to understand the internal state and behavior of a system using the signals the system produces.

## Answer 2

Monitoring focuses mainly on known conditions and thresholds. Observability is broader and helps investigate both expected and unexpected questions about system behavior.

## Answer 3

A metric is a numerical measurement recorded over time.

## Answer 4

A log is a timestamped record describing something that happened inside a system or application.

## Answer 5

An event represents a specific change or occurrence at a point in time.

## Answer 6

Because trends and changes over time provide more context than one isolated value.

## Answer 7

Amazon CloudWatch is AWS's monitoring and observability service for metrics, logs, alarms, dashboards, and related monitoring capabilities.

## Answer 8

A namespace groups related CloudWatch metrics.

## Answer 9

A dimension identifies a characteristic of a metric, such as a specific EC2 instance or RDS database.

## Answer 10

Because different statistics reveal different behavior. An average can hide a short but severe spike that a maximum would reveal.

## Answer 11

Average summarizes the mean value over the selected period. Maximum shows the highest value observed during that period.

## Answer 12

`CPUUtilization`.

## Answer 13

Because memory utilization exists inside the guest operating system and is not directly available from the standard EC2 infrastructure metrics.

## Answer 14

The CloudWatch Agent can collect additional operating-system metrics and log files from servers and send them to CloudWatch.

## Answer 15

A log group is a logical container holding related CloudWatch log streams.

## Answer 16

A log stream is an ordered sequence of log events from a particular source.

## Answer 17

Because application servers may be terminated or replaced, and centralized logs preserve evidence beyond the lifecycle of individual instances.

## Answer 18

A metric filter matches patterns in CloudWatch Logs and converts matching events into numerical metrics.

## Answer 19

A CloudWatch alarm evaluates a metric against configured conditions and changes state when those conditions are met.

## Answer 20

`OK` means the alarm condition is not currently breached. `ALARM` means it is breached according to the evaluation rules. `INSUFFICIENT_DATA` means CloudWatch lacks enough valid data to determine the state.

## Answer 21

SNS can receive CloudWatch alarm notifications and deliver them to configured subscribers or downstream systems.

## Answer 22

A CloudWatch dashboard is a visual collection of metrics and widgets used to monitor a system.

## Answer 23

Because an application can fail from memory exhaustion, disk pressure, database problems, dependencies, logic errors, or other issues while CPU remains normal.

## Answer 24

`RequestCount`.

## Answer 25

It helps show how long backend targets are taking to respond through the load balancer.

## Answer 26

It shows how many backend targets are currently healthy and available for traffic.

## Answer 27

ALB-generated 5xx errors indicate errors generated by the load-balancing layer or backend communication. Target 5xx errors indicate the application target itself returned the 5xx response.

## Answer 28

`DatabaseConnections`.

## Answer 29

It shows how much database storage remains before capacity becomes critically low.

## Answer 30

Because the ASG may want a certain amount of capacity while fewer instances are actually available and ready to serve traffic.

## Answer 31

They reveal whether the application is accomplishing its real work, such as successful checkouts, jobs, logins, or requests.

## Answer 32

Alert fatigue occurs when engineers receive too many low-value or noisy alerts and begin ignoring them.

## Answer 33

Because changes such as deployments or configuration updates often explain why metrics changed at a particular time.

## Answer 34

Because restarting can destroy useful evidence that would help identify the root cause.

## Answer 35

Use:

```text
Observe
→ Define symptom
→ Gather metrics
→ Inspect logs
→ Check events
→ Form hypothesis
→ Test
→ Fix
→ Verify
→ Prevent recurrence
```
