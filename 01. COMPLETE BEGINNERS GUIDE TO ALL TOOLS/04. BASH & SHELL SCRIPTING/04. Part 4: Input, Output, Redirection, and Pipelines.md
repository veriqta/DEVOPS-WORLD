# Part 4: Input, Output, Redirection, and Pipelines

In Part 3, you learned how Bash stores and transforms data using variables, quoting, parameter expansion, command substitution, arithmetic expansion, and environment variables.

Now you need to understand how data moves **between commands, files, scripts, and users**.

When you run:

```bash
ls
```

where does the output go?

When a command fails:

```bash
ls /directory-that-does-not-exist
```

why can the error be redirected separately from normal output?

When you run:

```bash
grep "ERROR" app.log | wc -l
```

how does the output from `grep` become the input to `wc`?

Why does:

```bash
command > output.txt
```

replace a file, while:

```bash
command >> output.txt
```

adds to it?

And what exactly does this mean?

```bash
command > output.log 2>&1
```

These questions are fundamental to Bash.

The central model for this part is:

```text
                    Command
                 +-----------+
Standard Input → |           | → Standard Output
      0          |  Process  |         1
                 |           |
                 +-----------+
                       |
                       ↓
                Standard Error
                       2
```

By the end of this part, you should understand how to:

* work with standard input
* distinguish standard output from standard error
* understand file descriptors `0`, `1`, and `2`
* print data with `echo` and `printf`
* collect user input with `read`
* redirect output into files
* append instead of overwrite
* redirect errors separately
* combine output and errors
* discard unwanted output with `/dev/null`
* connect commands using pipes
* understand pipeline exit behavior
* use `tee`
* create here documents
* use here strings
* build command-processing pipelines
* create basic script logs
* separate normal output from errors
* process realistic application logs

# 1. Commands Need Ways to Receive and Produce Data

Consider:

```bash
cat app.log
```

The `cat` command reads data and writes data.

Or:

```bash
grep "ERROR" app.log
```

`grep` reads information and produces matching information.

Or:

```bash
sort names.txt
```

`sort` reads lines and produces sorted lines.

Linux and Unix-like systems provide standard data channels that allow programs to communicate consistently.

The three fundamental streams are:

```text
Standard Input
Standard Output
Standard Error
```

Often abbreviated:

```text
stdin
stdout
stderr
```

---

# 2. What Is Standard Input?

**Standard input**, or `stdin`, is the default input stream from which a program can read data.

Its file descriptor number is:

```text
0
```

So:

```text
stdin = file descriptor 0
```

When working interactively, standard input is often connected to your terminal.

For example:

```bash
read name
```

Bash waits for you to type something.

You enter:

```text
Ann
```

and press Enter.

Conceptually:

```text
Keyboard
   |
   v
Terminal
   |
   v
Standard Input
FD 0
   |
   v
read
```

But standard input does not have to come from your keyboard.

It can come from:

* a file
* another command
* a pipe
* a here document
* a here string
* another process

That flexibility is extremely important.

---

# 3. What Is Standard Output?

**Standard output**, or `stdout`, is the normal output stream produced by a program.

Its file descriptor is:

```text
1
```

So:

```text
stdout = file descriptor 1
```

For example:

```bash
echo "Deployment complete"
```

normally displays:

```text
Deployment complete
```

in your terminal.

Conceptually:

```text
echo
 |
 v
Standard Output
FD 1
 |
 v
Terminal
```

But standard output does not have to go to the terminal.

You can redirect it into:

* a file
* another command
* a log
* `tee`
* `/dev/null`

---

# 4. What Is Standard Error?

**Standard error**, or `stderr`, is a separate output stream intended for errors, warnings, and diagnostic information.

Its file descriptor is:

```text
2
```

So:

```text
stderr = file descriptor 2
```

Suppose you run:

```bash
ls /this-directory-does-not-exist
```

You may see:

```text
ls: cannot access '/this-directory-does-not-exist': No such file or directory
```

That message is normally written to standard error rather than standard output.

This separation is extremely useful.

It means you can say:

> Save normal results here, but save errors somewhere else.

---

# 5. The Three Standard Streams

The model is:

```text
             +----------------+
FD 0 ------> |                |
stdin        |    COMMAND     |
             |                |
             +----------------+
                |          |
                |          |
                v          v
              FD 1       FD 2
              stdout     stderr
```

Remember:

```text
0 = standard input
1 = standard output
2 = standard error
```

This is worth memorizing.

You will use these numbers constantly in shell scripting.

---

# 6. What Is a File Descriptor?

A file descriptor is a small integer used by a process to refer to an open input/output resource.

For beginners, focus on:

```text
0
1
2
```

When a process starts, it normally has:

```text
0 → standard input
1 → standard output
2 → standard error
```

The operating system and shell connect these descriptors to appropriate destinations.

In a terminal session:

```text
FD 0 → terminal input
FD 1 → terminal display
FD 2 → terminal display
```

That is why both normal output and error messages often appear on the same screen even though they are different streams.

---

# 7. Same Terminal Does Not Mean Same Stream

This is an important beginner concept.

Run:

```bash
echo "Normal output"
```

Then:

```bash
ls /not-a-real-directory
```

Both messages appear in your terminal.

But internally:

```text
"Normal output"
      |
      v
    stdout
     FD 1
```

while the `ls` diagnostic normally travels through:

```text
Error message
      |
      v
    stderr
     FD 2
```

They appear in the same terminal because both descriptors are currently connected there.

Later, we will send them to different files.


# 9. Using `printf`

Another important output tool is:

```bash
printf
```

Example:

```bash
printf '%s\n' "Hello from Bash"
```

Output:

```text
Hello from Bash
```

The first argument:

```text
%s\n
```

is a format string.

Here:

```text
%s = print a string
\n = newline
```

The next argument:

```text
Hello from Bash
```

is inserted where `%s` appears.

---

# 10. Basic `printf` Syntax

A simplified form is:

```text
printf FORMAT ARGUMENTS
```

Example:

```bash
name="Ann"

printf 'Hello, %s\n' "$name"
```

Output:

```text
Hello, Ann
```

Another:

```bash
environment="production"
port=8080

printf 'Environment: %s\nPort: %s\n' "$environment" "$port"
```

Output:

```text
Environment: production
Port: 8080
```

---

# 11. Why `printf` Is Often Safer Than `echo`

`echo` is convenient, but behavior around some options, backslashes, and strings can vary between shell implementations and environments.

For predictable formatted output, `printf` is generally a better choice.

For example:

```bash
printf '%s\n' "$message"
```

clearly means:

> Print this value as a string followed by a newline.

Another advantage is that `printf` separates the format from the data.

For example:

```bash
value="-n"

printf '%s\n' "$value"
```

predictably prints:

```text
-n
```

Some `echo` implementations can interpret values beginning with option-like characters in special ways.

For serious scripts, especially when printing variable data, develop the habit of using:

```bash
printf '%s\n' "$variable"
```

when predictable behavior matters.

`echo` is still perfectly useful for many simple messages.

---

# 12. Format Specifiers

Common `printf` format specifiers include:

```text
%s    string
%d    integer
\n    newline
\t    tab
```

Example:

```bash
app="api"
replicas=3

printf 'Application: %s\nReplicas: %d\n' "$app" "$replicas"
```

Output:

```text
Application: api
Replicas: 3
```

You will not need advanced formatting yet.

The main lesson is:

> `printf` gives you more deliberate control over output.

```bash

```

The shell waits.

Type:

```text
Ann
```

and press Enter.

Then:

```bash
printf 'Hello, %s\n' "$name"
```

Output:

```text
Hello, Ann
```

`read` received a line from standard input and stored it in the variable `name`.

# 14. Understanding `read`

The basic pattern is:

```bash
read variable
```

For example:

```bash
read environment
```

If the user enters:

```text
production
```

then:

```bash
echo "$environment"
```

prints:

```text
production
```

Conceptually:

```text
User types
"production"
     |
     v
Standard Input
FD 0
     |
     v
read
     |
     v
environment="production"
```

# 15. Creating a Prompt

Instead of making the user guess what to type, you can display a prompt.

One approach:

```bash
printf 'Enter environment: '
read environment
```

The user sees:

```text
Enter environment:
```

and enters a value.

Bash `read` also supports:

```bash
read -p "Enter environment: " environment
```

This displays the prompt and reads the value.

Example:

```bash
read -p "Enter your name: " name

printf 'Hello, %s\n' "$name"
```

---

# 16. Reading Input Safely with `read -r`

A useful habit is:

```bash
read -r variable
```

The `-r` option prevents backslashes in the input from being treated as escape characters by `read`.

For example:

```bash
read -r file_path
```

is usually preferable when reading arbitrary text or paths.

For many scripts, you will see:

```bash
read -r -p "Enter file path: " file_path
```

This makes input behavior more predictable.

---

# 17. Silent Input

Sometimes you do not want the user's input displayed while they type.

Bash `read` supports:

```bash
read -s
```

For example:

```bash
read -r -s -p "Enter secret: " secret
printf '\n'
```

The typed characters are not echoed to the terminal.

This is useful for sensitive interactive values.

However, an important security warning:

> Hiding input from the screen does not automatically make your entire secret-handling process secure.

The value may still exist in memory, be passed incorrectly later, or accidentally be logged.

Do not print it afterward.

Bad:

```bash
printf 'Your secret is %s\n' "$secret"
```

Better:

```bash
printf 'Secret received.\n'
```

---

# 18. Reading Multiple Values

You can read several values at once.

Example:

```bash
read -r first_name last_name
```

If the user enters:

```text
Ann Felix
```

Bash can assign:

```text
first_name = Ann
last_name  = Felix
```

Then:

```bash
printf 'First: %s\n' "$first_name"
printf 'Last: %s\n' "$last_name"
```

---

# 19. What Happens with Extra Words?

Suppose:

```bash
read -r first second
```

and the input is:

```text
one two three four
```

The first variable receives:

```text
one
```

and the final variable receives the remaining words according to `read`'s field-splitting behavior:

```text
two three four
```

This is why input handling should be designed carefully rather than assuming users always enter exactly what you expect.

# 20. Input Validation Introduction

Receiving input is only the first step.

Suppose:

```bash
read -r -p "Enter environment: " environment
```

What if the user presses Enter without typing anything?

What if they enter:

```text
banana
```

when your script only supports:

```text
development
staging
production
```

A robust script should validate input before using it.

Conceptually:

```text
Receive input
     |
     v
Is it empty?
     |
     v
Is it allowed?
     |
     v
Use it
```

We will learn conditional statements properly in Part 6.

For now, understand the principle:

> User input is data and should not automatically be trusted.

# 21. Output Redirection

Normally:

```bash
echo "Deployment complete"
```

writes to your terminal.

But you can redirect that output into a file.

Use:

```text
>
```

Example:

```bash
echo "Deployment complete" > deployment.log
```

Now the message may not appear in your terminal.

Instead, it is written into:

```text
deployment.log
```

Check:

```bash
cat deployment.log
```

Output:

```text
Deployment complete
```

---

# 22. What `>` Means

The operator:

```text
>
```

redirects standard output.

Conceptually:

```text
echo "Deployment complete"
             |
             v
           stdout
            FD 1
             |
             X terminal
             |
             v
      deployment.log
```

More explicitly:

```bash
echo "Deployment complete" 1> deployment.log
```

The `1` represents standard output.

Because standard output is the default for `>`, we usually omit it:

```bash
echo "Deployment complete" > deployment.log
```

---

# 23. Warning: `>` Can Overwrite Files

This is extremely important.

Run in your safe lab:

```bash
echo "Line one" > test.log
```

Check:

```bash
cat test.log
```

You see:

```text
Line one
```

Now:

```bash
echo "Line two" > test.log
```

Check again:

```bash
cat test.log
```

You now see:

```text
Line two
```

`Line one` is gone.

Why?

Because:

```text
>
```

opens the target for replacement/truncation before writing.

Do not use `>` against important files unless overwriting is intentional.

---

# 24. Appending with `>>`

If you want to add output to the end of an existing file, use:

```text
>>
```

Example:

```bash
echo "Line one" > test.log
```

Then:

```bash
echo "Line two" >> test.log
```

Then:

```bash
echo "Line three" >> test.log
```

Check:

```bash
cat test.log
```

Output:

```text
Line one
Line two
Line three
```

The first command created or replaced the file.

The later commands appended.

---

# 25. `>` vs `>>`

Remember:

```text
>     redirect and overwrite/truncate

>>    redirect and append
```

Example:

```bash
date > latest-run.txt
```

means:

> Replace the file with the latest date output.

While:

```bash
date >> history.log
```

means:

> Add another date entry to the end of the history.

---

# 26. Input Redirection with `<`

The operator:

```text
<
```

redirects a file into standard input.

Suppose:

```bash
printf '%s\n' "production" > environment.txt
```

Now run:

```bash
read -r environment < environment.txt
```

Then:

```bash
printf 'Environment: %s\n' "$environment"
```

Output:

```text
Environment: production
```

Conceptually:

```text
environment.txt
       |
       v
       <
       |
       v
Standard Input
FD 0
       |
       v
read
```

---

# 27. Commands Can Read Files Through Standard Input

Suppose:

```bash
cat < environment.txt
```

The file is connected to `cat` through standard input.

You may wonder:

> Why not just run `cat environment.txt`?

You can.

The purpose here is understanding the mechanism.

These are not conceptually identical:

```bash
cat environment.txt
```

Here, `environment.txt` is a command-line argument.

But:

```bash
cat < environment.txt
```

Here, Bash opens the file and connects it to `cat`'s standard input.

That distinction becomes useful with programs designed to process standard input.

---

# 28. Redirecting Standard Error with `2>`

Remember:

```text
2 = stderr
```

Run:

```bash
ls /directory-that-does-not-exist 2> errors.log
```

The error may disappear from the terminal.

Check:

```bash
cat errors.log
```

You should see the error message.

Conceptually:

```text
ls failure
    |
    v
stderr
FD 2
    |
    v
errors.log
```

---

# 29. Redirecting Normal Output and Errors Separately

Create a small test:

```bash
ls "$HOME" /directory-that-does-not-exist > output.log 2> errors.log
```

This command asks `ls` to process:

```text
a valid location
an invalid location
```

Normal output goes to:

```text
output.log
```

Errors go to:

```text
errors.log
```

Inspect:

```bash
cat output.log
```

Then:

```bash
cat errors.log
```

This is a major advantage of having stdout and stderr as separate streams.

---

# 30. Appending Standard Error with `2>>`

Just as:

```text
>>
```

appends standard output, you can append standard error using:

```text
2>>
```

Example:

```bash
ls /missing-one 2>> errors.log
```

Then:

```bash
ls /missing-two 2>> errors.log
```

Both errors are added to the file rather than replacing each other.

This is useful for persistent error logs.

---

# 31. Understanding `2>&1`

You will frequently encounter:

```bash
command > output.log 2>&1
```

This looks confusing until you understand file descriptors.

Break it down.

First:

```text
> output.log
```

means:

```text
stdout → output.log
```

Then:

```text
2>&1
```

means:

> Redirect file descriptor 2 to the destination currently used by file descriptor 1.

So:

```bash
command > output.log 2>&1
```

results in:

```text
stdout ───┐
          |
          v
      output.log
          ^
          |
stderr ───┘
```

Both normal output and errors end up in the same file.

---

# 32. Why the `&` Appears in `2>&1`

Without the `&`, Bash could interpret `1` as a filename.

The syntax:

```text
2>&1
```

means:

```text
redirect FD 2
to the destination represented by FD 1
```

It is descriptor duplication/redirection, not:

```text
write errors into a file literally named 1
```

---

# 33. Redirection Order Matters

This is an important concept.

Consider:

```bash
command > output.log 2>&1
```

First:

```text
stdout → output.log
```

Then:

```text
stderr → wherever stdout currently goes
```

Result:

```text
stdout → output.log
stderr → output.log
```

But:

```bash
command 2>&1 > output.log
```

is processed from left to right.

First:

```text
stderr → current stdout
```

At that moment stdout may still point to the terminal.

Then:

```text
stdout → output.log
```

Result can effectively be:

```text
stdout → output.log
stderr → terminal
```

The two commands are therefore not equivalent.

This is a common source of confusion.

---

# 34. A Modern Bash Shortcut

Bash also supports:

```bash
command &> output.log
```

to redirect both stdout and stderr to the same file.

And:

```bash
command &>> output.log
```

to append both.

However, you should still understand:

```bash
> output.log 2>&1
```

because you will encounter it constantly in shell scripts, CI/CD systems, Docker-related scripts, service wrappers, and production automation.

---

# 35. What Is `/dev/null`?

Linux provides a special device:

```text
/dev/null
```

Data written to `/dev/null` is discarded.

Think of it as a data sink.

```text
Output
   |
   v
/dev/null
   |
   v
discarded
```

Example:

```bash
echo "You will not see this" > /dev/null
```

Nothing useful is stored.

---

# 36. Suppressing Normal Output

Suppose a command is noisy but you only care whether it succeeds.

You can write:

```bash
command > /dev/null
```

This discards standard output.

Errors still appear because stderr has not been redirected.

Conceptually:

```text
stdout → /dev/null

stderr → terminal
```

---

# 37. Suppressing Errors

You can discard only errors:

```bash
command 2> /dev/null
```

Now:

```text
stdout → terminal

stderr → /dev/null
```

Use this carefully.

Errors often contain important troubleshooting information.

Do not hide errors simply because you do not understand them.

---

# 38. Suppressing Everything

You may encounter:

```bash
command > /dev/null 2>&1
```

This discards both stdout and stderr.

Or in Bash:

```bash
command &> /dev/null
```

This can be useful when output truly does not matter.

But it can also make troubleshooting difficult.

A better engineering question is:

> Do I really want to discard this information, or should I log it?

---

# 39. What Is a Pipe?

The pipe operator is:

```text
|
```

A pipe connects the standard output of one command to the standard input of another command.

Example:

```bash
printf '%s\n' "ERROR database unavailable" | grep "ERROR"
```

Conceptually:

```text
printf
   |
   | stdout
   v
  pipe
   |
   | stdin
   v
 grep
```

Instead of writing output to a temporary file and making another command read it, the data flows directly between processes.

---

# 40. Your First Useful Pipeline

Suppose:

```bash
printf '%s\n' \
  "INFO application started" \
  "ERROR database unavailable" \
  "INFO retrying" \
  "ERROR connection timeout"
```

You can send this output into `grep`:

```bash
printf '%s\n' \
  "INFO application started" \
  "ERROR database unavailable" \
  "INFO retrying" \
  "ERROR connection timeout" |
grep "ERROR"
```

Output:

```text
ERROR database unavailable
ERROR connection timeout
```

`grep` received the previous command's stdout through its stdin.

---

# 41. How a Pipeline Works

Consider:

```bash
cat app.log | grep "ERROR"
```

A simplified model:

```text
app.log
   |
   v
 cat
   |
   | stdout
   v
 pipe
   |
   | stdin
   v
 grep "ERROR"
   |
   v
terminal
```

The output from `cat` does not need to appear on the screen first.

It flows directly into `grep`.

For this specific example, you could more simply write:

```bash
grep "ERROR" app.log
```

because `grep` can open the file itself.

The pipeline example is useful for understanding data flow.

---

# 42. Pipelines Can Have Multiple Stages

Suppose you want to count errors:

```bash
grep "ERROR" app.log | wc -l
```

Flow:

```text
app.log
   |
   v
grep "ERROR"
   |
   | matching lines
   v
wc -l
   |
   | count
   v
terminal
```

If there are 12 matching lines:

```text
12
```

is displayed.

You have transformed raw log data into a useful metric.

---

# 43. A Three-Stage Pipeline

Suppose a log contains:

```text
ERROR database timeout
INFO request complete
ERROR disk full
ERROR database timeout
WARNING memory high
ERROR authentication failed
```

You could run:

```bash
grep "ERROR" app.log | sort | uniq
```

Conceptually:

```text
app.log
   |
   v
Find ERROR lines
   |
   v
Sort them
   |
   v
Remove adjacent duplicates
   |
   v
Display result
```

Later, text-processing commands will be covered in much greater depth.

For now, focus on how data moves.

---

# 44. Pipelines Are Not Just Visual Chaining

Each stage of a pipeline is normally a separate command/process connected through operating-system pipes.

Conceptually:

```text
Process A
 stdout
   |
   v
Kernel pipe
   |
   v
 stdin
Process B
 stdout
   |
   v
Kernel pipe
   |
   v
 stdin
Process C
```

This is why Unix-style tools are often designed to:

```text
read text
transform text
write text
```

They can then be combined into larger workflows.

---

# 45. Standard Error Does Not Automatically Enter the Pipe

Consider:

```bash
some_command | grep "something"
```

Normally, the pipe connects:

```text
some_command stdout
        |
        v
      grep
```

But `some_command`'s stderr remains separate.

Conceptually:

```text
                stdout
some_command -------------> grep
     |
     |
     +---- stderr ---------> terminal
```

This is important.

If you need errors to enter the pipeline too, you must redirect them appropriately.

For example:

```bash
some_command 2>&1 | grep "something"
```

Now both streams can flow into `grep`.

Only do this when combining them is actually what you want.

---

# 46. Pipeline Exit Behavior

Every command has an exit status.

But what is the exit status of:

```bash
command1 | command2
```

By default in Bash, the pipeline's status is generally the exit status of the **last command** in the pipeline.

This can hide failures in earlier stages.

For example, conceptually:

```text
command1 → fails
      |
      v
command2 → succeeds
```

The overall pipeline may still report success because the last command succeeded.

This matters in automation.

---

# 47. Demonstrating Pipeline Exit Behavior

Try:

```bash
false | true
```

Then:

```bash
echo "$?"
```

You will normally see:

```text
0
```

Why?

`false` returns failure.

`true` returns success.

The last command is `true`.

Therefore the default pipeline status is success.

Now:

```bash
true | false
```

Then:

```bash
echo "$?"
```

You should see non-zero because the last command failed.

---

# 48. `pipefail`

Bash provides an option called:

```bash
set -o pipefail
```

With `pipefail` enabled, a pipeline can report failure when a command in the pipeline fails rather than blindly relying only on the final command.

Try:

```bash
set -o pipefail
```

Then:

```bash
false | true
```

Immediately check:

```bash
echo "$?"
```

You should now receive a non-zero result.

This makes pipeline failures easier to detect in automation.

We will study reliable script settings and their caveats properly in Part 14.

For now, remember:

> Without `pipefail`, an earlier pipeline failure can be hidden by a successful final command.

# 49. What Is `tee`?

Normally, redirection makes a choice:

```text
display output
```

or:

```text
write output to file
```

But sometimes you want both.

That is where:

```bash
tee
```

is useful.

Example:

```bash
echo "Deployment started" | tee deployment.log
```

The message is:

1. displayed in the terminal
2. written to `deployment.log`

---

# 50. How `tee` Works

Conceptually:

```text
Command
   |
   | stdout
   v
 tee
 / \
/   \
v   v
File Terminal
```

This is useful for:

* deployment logs
* CI/CD output
* troubleshooting
* audit trails
* long-running scripts

You can watch what is happening while keeping a copy.

---

# 51. Appending with `tee`

By default:

```bash
tee file.log
```

writes/replaces the file.

To append:

```bash
tee -a file.log
```

Example:

```bash
echo "Deployment started" | tee -a deployment.log
```

Then:

```bash
echo "Deployment finished" | tee -a deployment.log
```

The file contains both lines.

---

# 52. Logging Both stdout and stderr with `tee`

Suppose:

```bash
some_command 2>&1 | tee -a application.log
```

First:

```text
2>&1
```

combines stderr with stdout.

Then the combined stream enters `tee`.

Conceptually:

```text
stdout ───┐
          |
stderr ───┤
          v
         tee
        /   \
       v     v
 terminal   application.log
```

This is a common logging pattern.

Remember the pipeline exit-status issue from the previous section. In production scripts, `pipefail` may matter if you need to detect failures from the command before `tee`.

# 53. Here Documents

Sometimes you need to provide multiple lines of input to a command.

A **here document**, often called a **heredoc**, provides multi-line input.

The general form is:

```bash
command <<EOF
line one
line two
line three
EOF
```

`EOF` is a delimiter.

It is not a required keyword.

It simply marks where the input ends.

---

# 54. Basic Here Document Example

Try:

```bash
cat <<EOF
VERIQTA Bash Lab
Environment: development
Status: ready
EOF
```

Output:

```text
VERIQTA Bash Lab
Environment: development
Status: ready
```

Conceptually:

```text
Here-document text
       |
       v
standard input
       |
       v
      cat
       |
       v
standard output
       |
       v
terminal
```

---

# 55. Variables Inside Here Documents

Suppose:

```bash
app_name="orders-api"
environment="production"
```

Then:

```bash
cat <<EOF
Application: $app_name
Environment: $environment
EOF
```

Bash performs expansions in this ordinary unquoted heredoc.

Output:

```text
Application: orders-api
Environment: production
```

This makes heredocs useful for generating:

* configuration files
* reports
* multi-line messages
* templates
* command input

---

# 56. Writing a Here Document to a File

You can combine a heredoc with redirection:

```bash
cat > app.conf <<EOF
APP_NAME=orders-api
APP_ENV=production
APP_PORT=8080
EOF
```

Now:

```bash
cat app.conf
```

shows:

```text
APP_NAME=orders-api
APP_ENV=production
APP_PORT=8080
```

Be careful:

```text
>
```

will replace an existing file.

Do not generate configuration files over important production files while practicing.

---

# 57. Preventing Expansion in a Here Document

Sometimes you want literal `$variable` text rather than expansion.

Quote the delimiter:

```bash
cat <<'EOF'
$HOME
$USER
$(hostname)
EOF
```

Output:

```text
$HOME
$USER
$(hostname)
```

The quoted delimiter tells Bash not to perform the usual parameter, command, and arithmetic expansions within the heredoc body.

Compare:

```bash
cat <<EOF
$HOME
EOF
```

with:

```bash
cat <<'EOF'
$HOME
EOF
```

The first expands `$HOME`.

The second preserves it literally.

```bash
command <<< "data"
```

Example:

```bash
grep "ERROR" <<< "ERROR database unavailable"
```

Output:

The string is supplied to the command's standard input.

Suppose:

You can write:

The variable's value becomes input to `grep`.

Conceptually:

```text
$message
   |
   v
Here string
   |
   v
stdin
   |
   v
grep
```

# 60. Here Document vs Here String

Use a here string for small, single-value input:

```bash

```

```bash

```

Mental model:

```text
<<<    small string as stdin

<<     multi-line document as stdin
```

# 61. Combining Commands into Processing Pipelines

Now let's combine several ideas.

Suppose `app.log` contains:

```text
2026-09-02 09:00:01 INFO Application started

2026-09-02 09:01:12 ERROR Payment service timeout

2026-09-02 09:03:41 ERROR Database connection lost
2026-09-02 09:03:45 ERROR Database connection lost
2026-09-02 09:04:02 INFO Database connected
```

Find errors:

```bash
grep "ERROR" app.log
```

Count errors:

```bash
grep "ERROR" app.log | wc -l
```

Find unique error lines:

```bash
grep "ERROR" app.log | sort | uniq
```

You are turning raw operational data into information.

# 62. A Better Log Pipeline

The previous unique-error example includes timestamps, so otherwise-identical messages may still be considered different.

Suppose you want to remove the date and time first.

You might eventually use:

```bash
grep "ERROR" app.log | cut -d' ' -f3-
```

This tells `cut` to work with fields separated by spaces and keep fields from the third onward.

Result:

```text
ERROR Payment service timeout
ERROR Payment service timeout
ERROR Database connection lost
ERROR Database connection lost
```

Now:

```bash
grep "ERROR" app.log |
cut -d' ' -f3- |
sort |
uniq -c
```

might produce:

```text
      2 ERROR Database connection lost
      2 ERROR Payment service timeout
```

Do not worry about mastering `cut`, `sort`, or `uniq` yet. They will be covered later.

Focus on the flow:

```text
Raw log
   |
   v
Filter errors
   |
   v
Remove timestamp
   |
   v
Sort messages
   |
   v
Count duplicates
   |
   v
Useful summary
```

---

# 63. Pipelines Should Have a Purpose

Avoid building pipelines merely because they look impressive.

Bad learning:

```text
Memorize:
cat file | grep x | awk ... | sed ... | cut ... | sort ...
```

Better:

```text
What data do I have?

What result do I need?

Which command performs the first transformation?

What should its output look like?

Which command performs the next transformation?

How will I verify each stage?
```

Build pipelines one stage at a time.

---

# 64. Debugging Pipelines One Stage at a Time

Suppose:

```bash
grep "ERROR" app.log |
cut -d' ' -f3- |
sort |
uniq -c
```

does not produce what you expected.

Do not immediately rewrite everything.

Start with:

```bash
grep "ERROR" app.log
```

Inspect it.

Then:

```bash
grep "ERROR" app.log | cut -d' ' -f3-
```

Inspect it.

Then:

```bash
grep "ERROR" app.log | cut -d' ' -f3- | sort
```

Inspect it.

Then add:

```bash
uniq -c
```

This follows the engineering principle:

```text
Break complex workflow
        ↓
Inspect each stage
        ↓
Find where output becomes wrong
        ↓
Fix that stage
        ↓
Verify complete workflow
```

# 70. Why Separate Error Logs?

Imagine a production automation job generates 10,000 lines of normal output but only five errors.

# 71. Writing Your Own Message to stderr

You can explicitly send a message to standard error.

For example:

```bash

```

The syntax:

```text
>&2
```

redirects the command's stdout to file descriptor 2.

So although `printf` normally writes to stdout, this particular message is sent to stderr.

This is useful when your own script needs to distinguish:

```text
normal information
```

from:

```text
errors
```

# 73. A Practical Logging Pattern


# 90. Common Beginner Mistake: Confusing `>` and `>>`

This:

```bash
echo "new entry" > production.log
```

can replace existing contents.

This:

```bash
echo "new entry" >> production.log
```

appends.

Before redirecting into an important file, ask:

> Do I intend to replace it or add to it?

---

# 91. Common Beginner Mistake: Assuming Errors Are stdout

This:

```bash
command > output.log
```

does not automatically capture stderr.

If the command fails, errors may still appear in the terminal.

To capture them separately:

```bash
command > output.log 2> errors.log
```

To combine them:

```bash
command > output.log 2>&1
```

---

# 92. Common Beginner Mistake: Hiding Every Error

Do not automatically use:

```bash
2> /dev/null
```

whenever an error appears.

That does not solve the error.

It hides it.

Correct troubleshooting is:

```text
Observe error
    ↓
Understand error
    ↓
Investigate cause
    ↓
Fix cause
    ↓
Verify
```

Use `/dev/null` only when discarding the stream is intentional.

---

# 93. Common Beginner Mistake: Assuming a Pipeline Fully Succeeded

Consider:

```bash
command1 | command2 | command3
```

If `command1` fails but `command3` succeeds, the default pipeline status may still look successful.

This matters in:

* deployments
* backups
* CI/CD
* production automation

Learn to recognize where `pipefail` may eventually be necessary.

---

# 94. Common Beginner Mistake: Unnecessary `cat`

You will often see:

```bash
cat application.log | grep "ERROR"
```

This works.

But because `grep` can open a file itself:

```bash
grep "ERROR" application.log
```

is simpler.

This does not mean `cat` is bad.

The lesson is:

> Use each command when it contributes something useful.

Avoid adding pipeline stages that do nothing necessary.

---

# 95. Common Beginner Mistake: Ignoring Quoting in Redirections

Prefer:

```bash
printf '%s\n' "$message" >> "$log_file"
```

instead of:

```bash
printf '%s\n' "$message" >> $log_file
```

If a variable contains unexpected spaces or special characters, unquoted use can cause problems.

The quoting rules from Part 3 still apply.

# 96. Common Beginner Mistake: Logging Secrets

# 97. Common Beginner Mistake: Trusting User Input

Suppose:

```bash

```

Then immediately:

```bash

```


# 100. Troubleshooting: `tee` Makes a Failed Command Look Successful

Suppose:

```bash
failing_command 2>&1 | tee output.log
```

The last command in the pipeline is `tee`.

If `tee` succeeds, the default pipeline status can hide the earlier failure.

## Investigation

Understand the pipeline:

```text
failing_command
       |
       v
      tee
```

## Production consideration

Bash can enable:

```bash
set -o pipefail
```

so earlier pipeline failures affect the pipeline's result.

We will study the full reliability implications later rather than blindly enabling options without understanding them.

# What You Should Now Understand

After Part 4, you should understand that:

* Linux commands commonly communicate through standard streams.
* Standard input is called `stdin`.
* Standard output is called `stdout`.
* Standard error is called `stderr`.
* File descriptor `0` represents standard input.
* File descriptor `1` represents standard output.
* File descriptor `2` represents standard error.
* stdout and stderr may both appear in the terminal while remaining separate streams.
* `echo` provides simple output.
* `printf` provides more predictable and controlled formatting.
* `read` receives input from standard input.
* `read -r` is a useful default for arbitrary text.
* `read -p` can display a prompt.
* `read -s` can hide interactive input from the screen.
* User input should be validated before sensitive use.
* `>` redirects stdout and normally replaces the target file contents.
* `>>` appends stdout.
* `<` redirects a file into stdin.
* `2>` redirects stderr.
* `2>>` appends stderr.
* `2>&1` redirects stderr to stdout's current destination.
* Redirection order matters.
* `/dev/null` discards data written to it.
* `|` connects one command's stdout to another command's stdin.
* stderr does not automatically enter a normal pipe.
* pipelines can contain multiple processing stages.
* Bash normally uses the final command's status as the pipeline status.
* `set -o pipefail` changes how failures in pipelines are reported.
* `tee` displays output while also writing it to a file.
* `tee -a` appends.
* heredocs provide multi-line standard input.
* quoted heredoc delimiters can suppress expansion.
* here strings provide a short string as standard input.
* complex pipelines should be built and verified one stage at a time.
* script logs can preserve execution history.
* stdout and stderr can be logged separately.
* your own script can send error messages to stderr using `>&2`.
* redirection can overwrite important data, so target paths must be handled carefully.
* logs should never casually expose secrets.

# Part 4 Summary

You now understand one of the most important ideas in Unix and Linux:

**commands communicate through streams.**

The basic model is:

```text
             COMMAND
          +-----------+
stdin --->|           |---> stdout
 FD 0     |  Process  |      FD 1
          |           |
          +-----------+
                |
                v
              stderr
               FD 2
```

You can redirect stdout:

```text
command > file
```

append it:

```text
command >> file
```

redirect stdin:

```text
command < file
```

redirect errors:

```text
command 2> errors.log
```

append errors:

```text
command 2>> errors.log
```

combine streams:

```text
command > output.log 2>&1
```

or discard unwanted data:

```text
command > /dev/null
```

You also understand pipelines:

```text
Command A
   |
   | stdout
   v
   |
   | pipe
   v
Command B
   |
   | stdout
   v
Command C
```

and how `tee` can split a stream:

```text
Command
   |
   v
  tee
 /   \
v     v
screen file
```

You can now provide input through:

```text
Keyboard
   |
   v
read
```

files:

```text
file
 |
 <
 |
 v
command
```

here documents:

```text
multi-line data
      |
      v
    <<EOF
      |
      v
   command
```

and here strings:

```text
"$value"
    |
    v
   <<<
    |
    v
 command
```

Most importantly, you should now think about Bash commands as data-processing components:

```text
Input
  ↓
Command
  ↓
Output
  ↓
Filter
  ↓
Transform
  ↓
Count
  ↓
Log
  ↓
Report
```

The engineering habits to keep from Part 4 are:

```text
Know which stream contains your data.

Remember 0, 1, and 2.

Do not confuse stdout with stderr.

Use printf when predictable output matters.

Treat user input as untrusted data.

Quote filenames and variable expansions.

Know whether > will destroy existing contents.

Use >> when history should be preserved.

Do not hide errors without a reason.

Build pipelines one stage at a time.

Understand pipeline exit behavior.

Use tee when output must be visible and recorded.

Keep secrets out of logs.

Separate errors when it improves troubleshooting.

Verify that a generated report came from successful commands.
```

You will learn exit statuses in greater depth, `$?`, `exit`, custom exit codes, `;`, `&&`, `||`, `!`, fallback behavior, command lists, grouping with `{ }`, subshells with `( )`, and how CI/CD systems use exit codes to determine whether automation succeeded or failed.
