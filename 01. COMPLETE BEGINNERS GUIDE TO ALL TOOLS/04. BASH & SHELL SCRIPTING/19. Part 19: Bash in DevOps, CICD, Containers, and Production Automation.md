# Part 19: Bash in DevOps, CI/CD, Containers, and Production Automation

Bash becomes especially valuable when separate DevOps tools need to work together.

A production delivery workflow might involve:

```text
Git
 |
 v
CI/CD Platform
 |
 v
Bash Scripts
 |
 +--> Build
 |
 +--> Test
 |
 +--> Security Checks
 |
 +--> Container Build
 |
 +--> Container Registry
 |
 +--> Terraform
 |
 +--> Kubernetes
 |
 +--> Deployment
 |
 +--> Health Verification
 |
 +--> Rollback
```

Bash frequently acts as the glue between these systems.

It may not be the application language.

It may not provision infrastructure by itself.

It may not schedule containers.

But it can coordinate the commands that do those things.

That makes Bash extremely useful and potentially dangerous.

A badly designed local script may inconvenience one engineer.

A badly designed production deployment script can affect thousands of users.

This part therefore focuses on more than syntax.

You will learn how to design Bash automation that behaves predictably inside CI/CD pipelines, containers, Kubernetes environments, infrastructure workflows, and production deployments.

# 4. Why Pipeline Scripts Should Be Separate Files

You may be tempted to place large scripts directly inside CI configuration.

For example:

```yaml
script:
  - command1
  - command2
  - command3
  - command4
  - command5
```

This is reasonable for a few simple commands.

But large inline scripts become difficult to:

* test locally
* lint
* reuse
* review
* debug
* version independently from pipeline structure

A better structure for substantial logic may be:

```text
project/
├── app/
├── tests/
├── scripts/
│   ├── build.sh
│   ├── test.sh
│   ├── deploy.sh
│   └── rollback.sh
└── pipeline-config
```

Then the CI platform invokes:

```bash
./scripts/build.sh
./scripts/test.sh
./scripts/deploy.sh
```

Now the automation logic is normal version-controlled code.

# 5. Pipeline Exit Codes

One of the most important concepts in CI/CD is extremely simple:

```text
0       success
nonzero failure
```

Suppose your pipeline executes:

```bash
./scripts/test.sh
```

If the script exits:

```text
0
```

the CI platform normally interprets that as success.

If it exits:

```text
1
```

or another nonzero value, the step normally fails.

Conceptually:

```text
Bash Script
    |
    v
Exit Status
    |
    +--> 0 ------> pipeline continues
    |
    +--> nonzero -> pipeline fails/stops according to configuration
```

Your scripts therefore communicate with CI/CD systems through exit statuses.

---

# 6. The Dangerous False-Success Script

Consider:

```bash
#!/usr/bin/env bash

run_tests

echo "Tests completed"
```

Suppose:

```text
run_tests
```

returns status `1`.

Then:

```bash
echo "Tests completed"
```

succeeds.

If no other handling exists, the script's final status may become `0`.

The pipeline can incorrectly report success.

That is a serious automation bug.

Better:

```bash
#!/usr/bin/env bash

if ! run_tests; then
    printf 'ERROR: Tests failed\n' >&2
    exit 1
fi

printf 'Tests passed\n'
```

Now failure is explicit.

---

# 7. Preserve Important Exit Codes

Suppose:

```bash
run_tests
status=$?
```

You must capture `$?` immediately.

This is wrong:

```bash
run_tests
printf 'Tests finished\n'
status=$?
```

Now `status` belongs to:

```text
printf
```

not `run_tests`.

Correct:

```bash
run_tests
status=$?

printf 'Tests finished with status %d\n' "$status"

if (( status != 0 )); then
    exit "$status"
fi
```

This builds directly on Part 5.

# 8. Pipeline Stages and Failure Propagation

Imagine:

```text
Build
  |
  v
Test
  |
  v
Package
  |
  v
Deploy
```

If testing fails, deployment should usually not continue.

Your Bash logic should preserve that behavior.

For example:

```bash
build_application || exit 1
run_tests || exit 1
create_artifact || exit 1
deploy_application || exit 1
```

Or use explicit blocks to provide better diagnostics.

The important principle is:

> Never hide a failure that should stop delivery.

# 9. Environment Variables in CI

CI/CD platforms frequently expose information through environment variables.

Examples might conceptually include:

```text
CI=true
BRANCH_NAME=main
COMMIT_SHA=abc123...
BUILD_NUMBER=184
ENVIRONMENT=staging
```

The exact variable names depend on the CI/CD platform.

A Bash script can inspect them:

```bash
printf 'Environment: %s\n' "${ENVIRONMENT:-unknown}"
```

For required variables:

```bash
: "${ENVIRONMENT:?ENVIRONMENT must be set}"
```

This uses parameter expansion from Part 15.

If the variable is absent or empty, Bash reports an error.

---

# 10. Never Assume CI Variables Exist

A script may run:

```text
locally
in GitHub Actions
in Jenkins
in GitLab CI
in another CI platform
```

If your script assumes:

```bash
echo "$CI_BRANCH"
```

exists everywhere, portability suffers.

Instead, define a script interface.

For example:

```bash
branch="${BRANCH_NAME:-}"
```

Then validate:

```bash
if [[ -z "$branch" ]]; then
    printf 'ERROR: BRANCH_NAME is required\n' >&2
    exit 2
fi
```

Better still, allow explicit arguments when appropriate.

---

# 11. Environment Variables Are Inputs

Treat CI environment variables like other external inputs.

Do not blindly trust them.

Suppose:

```bash
environment="$DEPLOY_ENVIRONMENT"
```

Before using it:

```bash
case "$environment" in
    development|staging|production)
        ;;
    *)
        printf 'ERROR: Invalid environment: %s\n' "$environment" >&2
        exit 2
        ;;
esac
```

This prevents unexpected values from reaching deployment logic.

# 12. Secrets in CI/CD

CI pipelines often require:

* API tokens
* registry credentials
* cloud credentials
* signing credentials
* deployment keys
* database credentials

These should not be hard-coded into:

```text
scripts
Git repositories
Dockerfiles
pipeline configuration committed as plaintext
```

CI/CD systems usually provide protected secret mechanisms.

Conceptually:

```text
CI Secret Store
      |
      v
Pipeline Runtime
      |
      v
Environment/File/Identity
      |
      v
Command That Needs Secret
```

The script should consume the secret without exposing it.

---

# 13. Never Print CI Secrets

Bad:

```bash
printf 'Using token: %s\n' "$DEPLOY_TOKEN"
```

Also dangerous:

```bash
set -x

curl \
    -H "Authorization: Bearer $DEPLOY_TOKEN" \
    "$api_url"
```

The expanded token may appear in pipeline logs.

Remember from Part 14:

```bash
set -x
```

prints command traces.

That can be valuable for debugging but dangerous around secrets.

---

# 14. Secret Validation Without Secret Exposure

You can validate existence:

```bash
if [[ -z "${DEPLOY_TOKEN:-}" ]]; then
    printf 'ERROR: DEPLOY_TOKEN is not set\n' >&2
    exit 2
fi
```

Or:

```bash
: "${DEPLOY_TOKEN:?DEPLOY_TOKEN must be set}"
```

Do not validate by printing the value.

If you must log something:

```bash
printf 'Deployment credential is configured\n'
```

That tells the operator enough without exposing it.

---

# 15. Prefer Workload Identity Where Available

Long-lived credentials create operational risk.

Modern cloud and CI systems may support mechanisms such as:

* workload identity
* temporary credentials
* role assumption
* identity federation
* managed identities
* service accounts

Conceptually:

```text
CI Job
  |
  v
Trusted Identity Relationship
  |
  v
Temporary Credential
  |
  v
Cloud API
```

This can be safer than storing a long-lived cloud secret in the CI system.

Bash should work with the identity model rather than inventing its own credential storage.

# 16. Build Scripts

A build script transforms source code into something usable for later stages.

Examples:

```text
source code
    |
    v
compile
    |
    v
package
    |
    v
artifact
```

Depending on the project, Bash may invoke:

```bash
mvn package
npm run build
go build
make
docker build
```

The specific tool is less important than the script's responsibilities.

A good build script should:

* validate prerequisites
* fail when the build fails
* produce predictable output
* place artifacts in known locations
* avoid hidden side effects
* print useful logs

---

# 17. Example Build Script

```bash
#!/usr/bin/env bash

set -o pipefail

artifact_dir="dist"

log() {
    printf '[BUILD] %s\n' "$*"
}

main() {
    if ! command -v npm >/dev/null 2>&1; then
        printf 'ERROR: npm is required\n' >&2
        return 2
    fi

    log "Installing dependencies"

    if ! npm ci; then
        printf 'ERROR: Dependency installation failed\n' >&2
        return 1
    fi

    log "Building application"

    if ! npm run build; then
        printf 'ERROR: Build failed\n' >&2
        return 1
    fi

    if [[ ! -d "$artifact_dir" ]]; then
        printf 'ERROR: Expected artifact directory missing: %s\n' \
            "$artifact_dir" >&2
        return 1
    fi

    log "Build completed successfully"
}

main "$@"
```

Notice that the script does not assume success simply because the build command finished executing.

It verifies the expected artifact.

Production automation should frequently follow this pattern:

```text
Perform operation
       |
       v

       |
       v
Verify expected state
```

For example:

```bash
npm run build
```

returning `0` is useful.

But if you expect:

```text

```

you can verify:

```bash
if [[ ! -f dist/application.js ]]; then
    printf 'ERROR: Build succeeded but expected artifact is missing\n' >&2
    exit 1
fi
```

Command success and desired state are related but not always identical.

# 19. Test Scripts

A CI test script might coordinate:

```text
unit tests
integration tests
linting
security checks
```

Example:

```bash
#!/usr/bin/env bash

run_step() {
    local name="$1"
    shift

    printf '[TEST] %s\n' "$name"

    if "$@"; then
        printf '[PASS] %s\n' "$name"
        return 0
    fi

    printf '[FAIL] %s\n' "$name" >&2
    return 1
}

main() {
    run_step "Lint" npm run lint || return 1
    run_step "Unit tests" npm test || return 1

    printf 'All required tests passed\n'
}

main "$@"
```

The function:

```bash
"$@"
```

executes the command passed to it while preserving argument boundaries.

---

# 20. Fail Fast vs Collect All Failures

There are two useful testing strategies.

## Fail fast

```text
Test 1 fails
   |
   v
Stop immediately
```

Useful when later tests depend on earlier success.

## Collect failures

```text
Test 1 -> fail
Test 2 -> pass
Test 3 -> fail
      |
      v
Report all failures
```

Useful when you want maximum feedback from one CI run.

Example:

```bash
failures=0

if ! npm run lint; then
    ((failures++))
fi

if ! npm test; then
    ((failures++))
fi

if (( failures > 0 )); then
    printf 'ERROR: %d test stage(s) failed\n' "$failures" >&2
    exit 1
fi
```

Choose intentionally.

# 22. Never Deploy an Ambiguous Version

Bad:

```bash
deploy latest
```

Why?

Because `latest` does not clearly identify what is being deployed.

A better production artifact identifier might be:

```text
v2.8.4
```

or:

```text
commit SHA
```

or an immutable image digest.

For example:

```text
registry.example.com/payments:abc123def
```

The goal is reproducibility.

You should be able to answer:

> Exactly what version is running?

# 23. Release Scripts

An organization may distinguish:

```text
Deploy
  |
  +--> put software into environment

Release
  |
  +--> make capability available to users
```

A release script may:

* generate version numbers
* create Git tags
* package artifacts
* publish artifacts
* generate release metadata
* promote an existing artifact
* trigger deployment
* update release records

Avoid rebuilding the application separately for every environment if your delivery model expects artifact promotion.

A common principle is:

```text
Build once
   |
   v
Artifact
   |
   +--> staging
   |
   +--> production
```

# 25. Determine the Current Git Branch

A useful command is:

```bash
git branch --show-current
```

Capture:

```bash
branch="$(git branch --show-current)"
```

But CI pipelines may operate in detached HEAD state.

In that case, the result may be empty.

Another useful command is:

```bash
git rev-parse --abbrev-ref HEAD
```

In detached HEAD state, it may return:

```text
HEAD
```

Therefore production scripts should understand their Git execution environment.

---

# 26. CI Branch Information

CI/CD platforms often provide branch information themselves.

That can be more reliable than asking Git in certain pipeline states.

A generic approach might be:

```bash
branch="${CI_BRANCH_NAME:-}"

if [[ -z "$branch" ]]; then
    branch="$(git branch --show-current 2>/dev/null || true)"
fi
```

Then validate:

```bash
if [[ -z "$branch" ]]; then
    printf 'ERROR: Could not determine branch\n' >&2
    exit 1
fi
```

Do not invent a branch if you cannot determine one.

---

# 27. Branch-Based Deployment Logic

You may encounter logic such as:

```text
feature/* -> development
develop   -> staging
main      -> production
```

A Bash implementation:

```bash
case "$branch" in
    main)
        environment="production"
        ;;
    develop)
        environment="staging"
        ;;
    feature/*)
        environment="development"
        ;;
    *)
        printf 'ERROR: Branch is not deployable: %s\n' "$branch" >&2
        exit 1
        ;;
esac
```

This is an example.

Your organization may use completely different branching and deployment policies.

---

# 28. Be Careful with Branch-Controlled Production Deployment

Automatically assuming:

```text
main = deploy immediately to production
```

may be inappropriate.

Production may require:

* approval
* change controls
* deployment windows
* automated policy checks
* protected environments
* separation of duties

Bash should implement or respect organizational deployment policy, not bypass it.

```bash
git rev-parse --short HEAD
```

```bash
commit_sha="$(git rev-parse --short HEAD)"
```

* release records
* debugging

```text
payments:7f93a2c
```

# 30. Version and Tag Generation

A simple artifact version might combine:

```text
semantic version
commit SHA
build number
```

For example:

```text
2.4.1-7f93a2c
```

Or:

```text
build-184-7f93a2c
```

A script could generate:

```bash
commit_sha="$(git rev-parse --short HEAD)"
build_number="${BUILD_NUMBER:-local}"

version="build-${build_number}-${commit_sha}"

printf '%s\n' "$version"
```

The exact strategy depends on your release process.

---

# 31. Validate Generated Versions

Do not blindly use generated strings as:

* Docker tags
* filenames
* Git tags
* cloud resource names

Validate the format expected by the destination system.

For example:

```bash
if [[ ! "$version" =~ ^[A-Za-z0-9._-]+$ ]]; then
    printf 'ERROR: Invalid generated version: %s\n' "$version" >&2
    exit 1
fi
```

The exact allowed characters depend on the target.

# 32. Creating Git Tags

Example:

```bash
git tag "v$version"
```

Before doing that, check whether the tag already exists.

```bash
if git rev-parse "refs/tags/v$version" >/dev/null 2>&1; then
    printf 'ERROR: Tag already exists: v%s\n' "$version" >&2
    exit 1
fi
```

Then:

```bash
git tag "v$version"
```

Potentially push:

```bash
git push origin "v$version"
```

Tag creation is a state-changing operation.

Validate carefully before automating it.

# 34. Verify an Artifact

Example:

```bash
artifact="dist/application.tar.gz"
```

# 38. Bash Inside Containers

Containers frequently execute shell scripts.

Examples:

```text
startup scripts
entrypoint scripts
migration scripts
configuration rendering
health-check helpers
one-time initialization
```

But remember:

A container may not contain Bash.

Minimal images might have:

```text
/bin/sh
```

but not:

```text
/bin/bash
```

If your script requires Bash features such as:

```text
arrays
[[ ]]
BASH_SOURCE
associative arrays
```

then the image must actually provide Bash.

Do not assume.

---

# 39. Check the Interpreter

If your script begins:

```bash
#!/usr/bin/env bash
```

then `bash` must be discoverable through the container's environment.

If the container intentionally uses POSIX shell, write a POSIX-compatible script instead.

Do not write Bash-specific syntax and then execute it with:

```bash
sh script.sh
```

That may fail or behave differently.

# 40. Docker Entrypoint Scripts

An entrypoint script runs when a container starts.

Example:

```bash
#!/usr/bin/env bash

set -e

printf 'Preparing application...\n'

exec "$@"
```

This small script contains an extremely important command:

```bash
exec "$@"
```

Why?

Because it replaces the shell process with the application command.

---

# 41. Why exec Matters in Containers

Without `exec`:

```text
PID 1
 |
 v
Bash entrypoint
 |
 v
Application child process
```

With:

```bash
exec "$@"
```

the application replaces Bash:

```text
PID 1
 |
 v
Application
```

This can improve signal handling and shutdown behavior.

Containers depend heavily on correct process behavior.

You learned about signals in Part 13.

---

# 42. A Better Entrypoint Example

```bash
#!/usr/bin/env bash

set -e

log() {
    printf '[ENTRYPOINT] %s\n' "$*"
}

main() {
    log "Starting container initialization"

    if [[ -n "${APP_CONFIG:-}" ]]; then
        log "Application configuration detected"
    fi

    log "Launching application"

    exec "$@"
}

main "$@"
```

Do not log sensitive configuration values.

---

# 43. ENTRYPOINT vs CMD Concepts

In Docker, `ENTRYPOINT` and `CMD` influence what executes when a container starts.

A simplified mental model:

```text
ENTRYPOINT
    |
    +--> main executable/startup behavior

CMD
    |
    +--> default command or default arguments
```

For example:

```dockerfile
ENTRYPOINT ["/usr/local/bin/entrypoint.sh"]
CMD ["my-application", "serve"]
```

Conceptually Docker starts:

```text
/usr/local/bin/entrypoint.sh my-application serve
```

Then the script can:

```bash
exec "$@"
```

resulting in:

```text
my-application serve
```

The exact behavior depends on whether shell-form or exec-form instructions are used.

---

# 44. Prefer Exec Form in Dockerfiles

Compare:

```dockerfile
CMD my-application serve
```

with:

```dockerfile
CMD ["my-application", "serve"]
```

The second is exec form.

It avoids an unnecessary shell interpretation layer and usually gives clearer argument and signal behavior.

Similarly:

```dockerfile
ENTRYPOINT ["/usr/local/bin/entrypoint.sh"]
```

is commonly preferable to shell form when you want predictable process execution.

---

# 45. Entrypoint Mistake: Swallowing Signals

Suppose:

```bash
#!/usr/bin/env bash

my-application
```

Bash remains the parent process.

Container stop signals may require correct forwarding/reaping behavior.

Using:

```bash
exec my-application
```

makes the application replace the shell.

This is often the correct final action for simple entrypoint scripts.

---

# 46. Entrypoint Mistake: Infinite Initialization

An entrypoint script might wait for a dependency:

```bash
while ! dependency_ready; do
    sleep 2
done
```

Without a limit, the container may remain stuck forever.

Better:

```text
maximum attempts
timeout
clear logs
nonzero failure
```

The orchestrator can then respond appropriately.

# 47. Containers Should Not Hide Application Failure

Bad:

```bash
my-application || true
sleep infinity
```

Now the application dies but the container remains alive.

Monitoring may see:

```text
container running
```

while the actual application is dead.

Do not hide failures merely to keep a container alive.


```bash

```

or:


# 57. Health Checks

A deployment should not be declared successful merely because commands returned `0`.

You need to define application health.

Possible signals:

```text
Kubernetes rollout complete
HTTP health endpoint returns 200
JSON status == healthy
critical dependency available
expected version running
```

A strong deployment check might verify several of these.

---

# 58. Verify the Deployed Version

Suppose your health endpoint returns:

```json
{
  "status": "healthy",
  "version": "7f93a2c"
}
```

You can verify:

```bash
response="$(curl -fsS "$health_url")" || {
    printf 'ERROR: Health endpoint failed\n' >&2
    exit 1
}

running_version="$(
    jq -r '.version // empty' <<< "$response"
)"
```

Then:

```bash
if [[ "$running_version" != "$expected_version" ]]; then
    printf 'ERROR: Expected version %s but found %s\n' \
        "$expected_version" \
        "${running_version:-missing}" >&2
    exit 1
fi
```

This provides stronger evidence that the intended release is actually serving.

---

# 59. Health Checks Need Timeouts

Use:

```bash
curl \
    --connect-timeout 5 \
    --max-time 10 \
    ...
```

Without timeouts, deployment jobs can become stuck.

Combine timeouts with bounded retry logic.

---

# 60. Deployment Health Retry

Example:

```bash
wait_for_health() {
    local url="$1"
    local expected_version="$2"
    local max_attempts="${3:-10}"
    local delay="${4:-5}"
    local attempt=1
    local response
    local status
    local version

    while (( attempt <= max_attempts )); do
        printf '[INFO] Health check %d/%d\n' \
            "$attempt" "$max_attempts"

        if response="$(
            curl \
                -fsS \
                --connect-timeout 5 \
                --max-time 10 \
                "$url"
        )"
        then
            status="$(jq -r '.status // empty' <<< "$response")"
            version="$(jq -r '.version // empty' <<< "$response")"

            if [[ "$status" == "healthy" &&
                  "$version" == "$expected_version" ]]
            then
                printf '[OK] Application healthy\n'
                return 0
            fi
        fi

        if (( attempt < max_attempts )); then
            sleep "$delay"
        fi

        ((attempt++))
    done

    printf '[ERROR] Application failed health verification\n' >&2
    return 1
}
```

# 61. Health Check Failure Is Evidence

Suppose deployment health verification fails.

Do not immediately run:

```bash

```

without understanding your rollback policy.

Depending on the system, you may need to:

* capture logs
* capture Kubernetes events
* inspect rollout state
* record failed version
* preserve evidence
* determine whether rollback is safe
* trigger automated rollback according to policy

# 62. Rollback

Rollback means returning to a previously known acceptable state.

A simplified deployment model:

```text
Version A healthy
      |
      v
Deploy Version B
      |
      v
Health fails
      |
      v
Rollback
      |
      v
Version A restored
```

Rollback sounds simple.

In reality, it can be complicated by:

* database migrations
* schema compatibility
* message formats
* caches
* external side effects
* irreversible operations
* data changes

Never assume every deployment can safely roll back.

---

# 63. Kubernetes Rollback

For a Deployment, Kubernetes provides:

```bash
kubectl rollout undo deployment/myapp
```

In automation:

```bash
if ! kubectl \
    --context "$kube_context" \
    -n "$namespace" \
    rollout undo deployment/myapp
then
    printf 'CRITICAL: Rollback command failed\n' >&2
    return 1
fi
```

Then verify rollback:

```bash
kubectl \
    --context "$kube_context" \
    -n "$namespace" \
    rollout status deployment/myapp \
    --timeout=120s
```

Rollback itself requires verification.

---

# 64. Do Not Hide Rollback Failure

Bad:

```bash
rollback || true
```

followed by:

```text
Deployment completed
```

That can hide a severe production problem.

If rollback fails, your script should make that unmistakable.

For example:

```bash
if ! rollback; then
    printf 'CRITICAL: Deployment failed and rollback also failed\n' >&2
    return 2
fi
```

Your organization may define different status codes, but the important point is visibility.

# 68. Terraform Environment Safety

Suppose:

```bash
environment="$1"
```

Do not build dangerous paths or commands without validation.

Use:

```bash
case "$environment" in
    development|staging|production)
        ;;
    *)
        printf 'ERROR: Invalid environment\n' >&2
        exit 2
        ;;
esac
```

Then map explicitly:

```bash
case "$environment" in
    development)
        terraform_dir="infra/environments/development"
        ;;
    staging)
        terraform_dir="infra/environments/staging"
        ;;
    production)
        terraform_dir="infra/environments/production"
        ;;
esac
```

Explicit mappings are often safer than constructing critical production paths from arbitrary strings.

# 69. Terraform Helper Example

```bash
#!/usr/bin/env bash
```

# 70. Git Automation and Dirty Working Trees

A release script may require a clean repository.

Check:

```bash
git status --porcelain
```

If output exists, there are working-tree changes.

Example:

```bash
if [[ -n "$(git status --porcelain)" ]]; then
    printf 'ERROR: Working tree is not clean\n' >&2
    exit 1
fi
```

Why?

Because creating releases from uncommitted local changes can make the result difficult to reproduce.

CI environments may have different assumptions, so apply this check where it makes sense.

# 71. Verify the Expected Branch

For a production release:

```bash
branch="$(git branch --show-current)"

if [[ "$branch" != "main" ]]; then
    printf 'ERROR: Production release requires main branch\n' >&2
    exit 1
fi
```

But remember detached HEAD environments.

A robust CI release process may rely on CI-provided metadata instead.

The important principle is target validation, not a specific Git command.

# 72. Artifact Promotion

Imagine:

```text
Build
 |
 v
Image: payments:abc123
 |
 +--> Staging
 |
 +--> Production
```

The same artifact should ideally be promoted.

Avoid:

```text
Build for staging
Build again for production
```

because the second build could differ.

A strong release process often prefers:

```text
Build once
Test once
Identify immutable artifact
Promote same artifact
```

Bash can enforce that by requiring an explicit artifact identifier.

# 73. Idempotency

Idempotency means that repeating an operation produces the same desired state without creating unintended duplicate effects.

Consider:

```bash
mkdir /opt/myapp
```

The second run may fail because the directory exists.

Better:

```bash
mkdir -p /opt/myapp
```

Now repeated execution can still achieve:

```text
directory exists
```

without treating existing state as an error.

---

# 74. Idempotency in Deployment Automation

Bad:

```bash
echo "CONFIG=true" >> app.env
```

Every run adds another line.

After three runs:

```text
CONFIG=true
CONFIG=true
CONFIG=true
```

That is not idempotent.

A better design might replace or manage the setting deterministically.

For example, generate the entire file from known configuration rather than repeatedly appending.

---

# 75. Create Only When Missing

Example:

```bash
if [[ ! -d "$directory" ]]; then
    mkdir -p "$directory"
fi
```

Sometimes `mkdir -p` alone is sufficient.

For resources with side effects:

```bash
if resource_exists; then
    printf 'Resource already exists\n'
else
    create_resource
fi
```

But remember race conditions.

Another actor could change the resource after your check.

Use the target tool's idempotent APIs where available.

---

# 76. Desired State Beats Procedural Guessing

Compare:

```text
Procedural:
create
then edit
then append
then restart
then hope
```

with:

```text
Desired state:
configuration should equal X
deployment should run version Y
replicas should equal 3
```

Tools such as Kubernetes and Terraform are strongly oriented toward desired state.

Bash should avoid fighting that model.

Use Bash to coordinate declarative tools, not recreate them poorly.

---

# 77. Dangerous Production Automation

Production scripts become dangerous when they combine:

```text
powerful credentials
+
unvalidated input
+
destructive commands
+
wrong environment
+
weak error handling
```

Examples include:

```bash
rm -rf "$path"
kubectl delete ...
terraform destroy ...
cloud-cli delete ...
database-drop-command ...
```

A single empty or incorrect variable can become catastrophic.

---

# 78. Validate Before Destructive Operations

Suppose:

```bash
namespace="$1"
```

Before deletion:

```bash
if [[ -z "$namespace" ]]; then
    printf 'ERROR: Namespace cannot be empty\n' >&2
    exit 2
fi
```

Then whitelist if appropriate:

```bash
case "$namespace" in
    dev-*|test-*)
        ;;
    *)
        printf 'ERROR: Refusing destructive action on namespace: %s\n' \
            "$namespace" >&2
        exit 1
        ;;
esac
```

This is stronger than trusting arbitrary input.

---

# 79. Production Should Require Stronger Guards

A production deployment might require:

```text
explicit environment
explicit version
verified identity
verified cluster
verified namespace
clean artifact
approved pipeline context
health-check URL
rollback information
```

Do not let:

```text
missing environment
```

silently become:

```text
production
```

Safe defaults should fail closed.

---

# 80. Fail Closed

Bad:

```bash
environment="${ENVIRONMENT:-production}"
```

If CI configuration breaks, you deploy to production.

Safer:

```bash
environment="${ENVIRONMENT:-}"

if [[ -z "$environment" ]]; then
    printf 'ERROR: ENVIRONMENT must be explicitly set\n' >&2
    exit 2
fi
```

For high-risk operations:

> Missing information should stop execution rather than choose the most dangerous target.

# 81. Dry-Run Mode

A useful deployment script can support:

```bash
--dry-run
```

Conceptually:

```text
Normal:
validate -> execute -> verify

Dry run:
validate -> show intended actions -> stop
```

Example:

```bash
if (( dry_run )); then
    printf '[DRY RUN] Would deploy %s to %s\n' \
        "$version" "$environment"
    return 0
fi
```

But a dry run must truly avoid side effects.

Do not perform:

```text
Git tag creation
registry push
kubectl apply
Terraform apply
file deletion
```

before checking dry-run mode.

# 82. Logging

Production scripts need useful logs.

A basic logging system:

```bash
timestamp() {
    date '+%Y-%m-%dT%H:%M:%S%z'
}

log_info() {
    printf '%s [INFO] %s\n' "$(timestamp)" "$*"
}

log_warn() {
    printf '%s [WARN] %s\n' "$(timestamp)" "$*" >&2
}

log_error() {
    printf '%s [ERROR] %s\n' "$(timestamp)" "$*" >&2
}
```

Example:

```text
2026-09-03T14:20:11+0000 [INFO] Deploying payments version abc123
```

---

# 83. What Good Deployment Logs Should Answer

Useful logs help answer:

```text
What script ran?
Which environment?
Which application?
Which version?
Which cluster?
Which namespace?
When did it start?
Which stage is running?
What failed?
How long did it take?
Was rollback attempted?
Did rollback succeed?
What was the final result?
```

Logs should not answer:

```text
What is the production password?
What is the API token?
What is the private key?
```

Observability and secrecy must coexist.

# 88. Production-Safe Script Structure

A useful production pattern is:

```text

2. Validate syntax/input
3. Validate dependencies
4. Validate credentials/identity

6. Validate target
```

# 89. Validation Should Precede Side Effects

Bad:

```bash

    echo "Missing environment"
    exit 1

```

The validation happened too late.

Correct structure:

```bash

validate_namespace
validate_artifact

deploy
```

The earlier a script can safely reject invalid execution, the better.

# 90. Avoid eval

Do not build deployment commands like:

```bash
command="kubectl $user_input"
eval "$command"
```

This creates command-injection risks and quoting problems.

Instead, use arrays.

Example:

```bash
cmd=(
    kubectl
    --context "$kube_context"
    -n "$namespace"
    get
    deployment
    "$deployment"
)

"${cmd[@]}"
```

Each argument remains separate.

This is one of the safest ways to construct commands dynamically in Bash.

---

# 91. Command Arrays

Suppose:

```bash
cmd=(
    kubectl
    --context "$kube_context"
    -n "$namespace"
    rollout
    status
    "deployment/$deployment"
    "--timeout=${rollout_timeout}s"
)
```

Preview safely:

```bash
printf 'Command:'

printf ' %q' "${cmd[@]}"

printf '\n'
```

Execute:

```bash
"${cmd[@]}"
```

This avoids dangerous string-based command construction.

# 92. Locking and Concurrent Deployments

Imagine two pipelines deploy the same application simultaneously.

```text
Pipeline A -> version A
Pipeline B -> version B
```

Their actions may overlap.

Possible consequences:

* confusing rollout status
* incorrect rollback target
* conflicting migrations
* misleading health checks

Concurrency should often be controlled by the CI/CD platform.

Bash can also use locks where appropriate, but deployment concurrency is usually best addressed at the workflow/platform level.

Do not assume your script is the only actor changing production.

# 93. Temporary Files

Production scripts may create:

* rendered configuration
* temporary manifests
* API responses
* metadata files

Use:

```bash

```

rather than predictable filenames.

Example:

```bash
temp_file="$(mktemp)" || exit 1
```

Then:

```bash
cleanup() {
    rm -f -- "${temp_file:-}"

```

# 94. Cleanup Must Not Destroy Evidence Accidentally

Temporary files should be cleaned.

But logs or diagnostic artifacts needed after failure may need to be preserved or uploaded.

For example:

```text

test report -> upload as CI artifact
deployment diagnostic -> preserve on failure
```

Design cleanup according to the purpose of the file.

```bash
    printf 'Deployment:    %s\n' "$deployment"
    printf 'Container:     %s\n' "$container_name"
    printf 'Health URL:    %s\n' "$health_url"

    if (( dry_run )); then
        printf 'Mode:          DRY RUN\n'
    else
        printf 'Mode:          EXECUTE\n'
    fi

    printf '%s\n' '========================================'
    printf '\n'
}

deploy_image() {
    log_info "Updating deployment image to $image"

    if ! kubectl \
        --context "$kube_context" \
        -n "$namespace" \
        set image \
        "deployment/$deployment" \
        "${container_name}=${image}"
    then
        log_error "Failed to update deployment image"
        return 1
    fi

    log_ok "Deployment image update accepted"
}

wait_for_rollout() {
    log_info "Waiting for Kubernetes rollout"

    if kubectl \
        --context "$kube_context" \
        -n "$namespace" \
        rollout status \
        "deployment/$deployment" \
        "--timeout=${rollout_timeout}s"
    then
        log_ok "Kubernetes rollout completed"
        return 0
    fi

    log_error "Kubernetes rollout failed or timed out"
    return 1
}

check_health_once() {
    local expected_version="$1"
    local response
    local status
    local running_version

    if ! response="$(
        curl \
            -fsS \
            --connect-timeout 5 \
            --max-time 10 \
            "$health_url"
    )"
    then
        return 1
    fi

    if ! jq -e . >/dev/null 2>&1 <<< "$response"; then
        log_warn "Health endpoint returned invalid JSON"
        return 1
    fi

    status="$(jq -r '.status // empty' <<< "$response")"
    running_version="$(jq -r '.version // empty' <<< "$response")"

    if [[ "$status" != "healthy" ]]; then
        log_warn "Application status is '${status:-missing}'"
        return 1
    fi

    if [[ "$running_version" != "$expected_version" ]]; then
        log_warn \
            "Expected version '$expected_version', received '${running_version:-missing}'"
        return 1
    fi

    return 0
}

wait_for_health() {
    local expected_version="$1"
    local attempt=1

    while (( attempt <= health_attempts )); do
        log_info \
            "Application health check $attempt/$health_attempts"

        if check_health_once "$expected_version"; then
            log_ok \
                "Application health passed for version $expected_version"
            return 0
        fi

        if (( attempt < health_attempts )); then
            sleep "$health_delay"
        fi

        ((attempt++))
    done

    log_error \
        "Application failed health verification for version $expected_version"

    return 1
}

perform_deployment() {
    deploy_image || return 1
    wait_for_rollout || return 1
    wait_for_health "$version" || return 1

    return 0
}

rollback_deployment() {
    log_warn "Starting Kubernetes rollback"

    if ! kubectl \
        --context "$kube_context" \
        -n "$namespace" \
        rollout undo \
        "deployment/$deployment"
    then
        log_critical "Rollback command failed"
        return 1
    fi

    log_info "Waiting for rollback rollout"

    if ! kubectl \
        --context "$kube_context" \
        -n "$namespace" \
        rollout status \
        "deployment/$deployment" \
        "--timeout=${rollout_timeout}s"
    then
        log_critical "Rollback rollout did not complete successfully"
        return 1
    fi

    log_ok "Rollback rollout completed"
}

verify_rollback_image() {
    local current_image

    current_image="$(get_current_image)" || {
        log_critical "Could not inspect image after rollback"
        return 1
    }

    if [[ "$current_image" != "$previous_image" ]]; then
        log_critical \
            "Rollback image mismatch. Expected '$previous_image', found '$current_image'"
        return 1
    fi

    log_ok "Previous image restored: $previous_image"
}

handle_deployment_failure() {
    log_error "Deployment verification failed"

    if ! rollback_deployment; then
        log_critical \
            "Deployment failed and rollback could not be completed"
        return 2
    fi

    if ! verify_rollback_image; then
        log_critical \
            "Rollback completed but previous image was not verified"
        return 2
    fi

    log_warn "Deployment failed. Previous image was restored."
    return 1
}

print_summary() {
    local result="$1"
    local end_time
    local duration

    end_time="$(date +%s)"
    duration=$((end_time - start_time))

    printf '\n'
    printf '%s\n' '========================================'
    printf '%s\n' 'DEPLOYMENT SUMMARY'
    printf '%s\n' '========================================'
    printf 'Application:   %s\n' "$application"
    printf 'Environment:   %s\n' "$environment"
    printf 'Version:       %s\n' "$version"
    printf 'Context:       %s\n' "$kube_context"
    printf 'Namespace:     %s\n' "$namespace"
    printf 'Duration:      %d seconds\n' "$duration"
    printf 'Result:        %s\n' "$result"
    printf '%s\n' '========================================'
}

main() {
    start_time="$(date +%s)"

    parse_args "$@"

    validate_environment || return 2
    validate_version || return 2

    configure_environment
    build_image_reference

    check_dependencies || return 2
    validate_production_policy || return 2

    verify_kube_context || return 1
    verify_cluster_access || return 1
    verify_deployment || return 1
    capture_current_image || return 1

    print_plan

    if (( dry_run )); then
        log_ok "Dry run completed. No changes were made."
        print_summary "DRY RUN"
        return 0
    fi

    if perform_deployment; then
        log_ok "Deployment completed successfully"
        print_summary "SUCCESS"
        return 0
    fi

    handle_deployment_failure
    failure_status=$?

    if (( failure_status == 2 )); then
        print_summary "CRITICAL FAILURE"
        return 2
    fi

    print_summary "FAILED - ROLLED BACK"
    return 1
}

main "$@"
```

# 141. Critical Limitation: Database Migrations

Suppose version B changes a database schema.

```text
Version A
   |
   v
Migration
   |
   v
Database Schema B
   |
   v
Version B
```

If you simply restore Version A:

```text
Version A
   |
   v
Database Schema B
```

Version A may no longer work.

Therefore application rollback and database rollback are separate concerns.

Production release design should consider:

* backward-compatible migrations
* expand/contract migration patterns
* migration sequencing
* rollback compatibility
* data transformations

Do not assume `kubectl rollout undo` reverses database changes.

It does not.

---

# 142. Critical Limitation: External Side Effects

Suppose the new version:

* sends emails
* processes payments
* publishes messages
* modifies external systems

Rolling back the application does not reverse those actions.

This is another reason why:

```text
rollback
```

does not mean:

```text
time travel
```

Automation must understand system side effects.

---

# 143. Critical Limitation: Kubernetes Rollout History

`kubectl rollout undo` depends on available rollout history and the state of the Deployment.

A production deployment system should understand:

* revision history
* previous version
* deployment strategy
* rollout history limits

For critical systems, explicitly recording release metadata outside the immediate shell process is valuable.

# 144. Better Rollback Design

A more advanced deployment system may deploy explicitly:

```text
new image:
registry.example.com/payments-api:abc123
```

and retain:

```text
previous image:
registry.example.com/payments-api:def456
```

If rollback is required, it could explicitly restore:

```text
def456
```

rather than relying only on generic rollout history.

That gives stronger control over the intended rollback target.

# 145. Production-Safe Pattern: Verify Before Mutating

```text
Arguments valid?
       |
       v

       |
       v

       |

       |

       |

       |
```

# 146. Production-Safe Pattern: Verify After Mutating

```text
   |
   v

   |

   |
```

# 147. Production-Safe Pattern: Make Failure Loud

A production script should not quietly continue after critical failures.

Bad:

```bash

```

Better:

```bash
if ! kubectl apply -f deployment.yaml; then
    log_error "Deployment configuration failed"
```

The operator and pipeline need accurate state.

# 149. Diagnostic Function

A simple educational function:

```bash
collect_diagnostics() {
    log_info "Collecting Kubernetes diagnostics"

    kubectl \
        --context "$kube_context" \
        -n "$namespace" \
        get deployment "$deployment" \
        -o wide || true

    kubectl \
        --context "$kube_context" \
        -n "$namespace" \
        get pods \
        -o wide || true

    kubectl \
        --context "$kube_context" \
        -n "$namespace" \
        get events \
        --sort-by='.lastTimestamp' || true
}
```

Here `|| true` is intentional.

Why?

Diagnostics should attempt to continue even if one diagnostic command fails.

This is very different from hiding deployment failure.

Context determines whether failure should stop execution.

---

# 150. `|| true` Is Not Always Bad

Earlier you learned that:

```bash
critical_command || true
```

can hide important failures.

But:

```bash
optional_diagnostic || true
```

may be reasonable.

The question is:

> Is failure of this command fatal to the primary operation?

Examples:

```text
deployment command fails
    -> fatal

health verification fails
    -> fatal

optional diagnostic command fails
    -> perhaps nonfatal

best-effort cleanup fails
    -> maybe warning, depending on resource
```

Reliable Bash requires reasoning, not rigid rules.

# 151. Logging vs Observability

Logging:

```text

```

Metrics:

```text

```

Deployment events:

```text
what changed and when?
```

Tracing:

```text
how did a request move through distributed components?
```

Your Bash deployment script may primarily produce logs and events.

The deployed application and infrastructure observability stack provide broader telemetry.

* avoid tracing sensitive operations
* use secret mechanisms
* avoid echoing credentials
* review logs

# 155. Common Mistake: Using latest in Production

Problem:

```text

```

Fix:

Use immutable version identifiers.

Verify:

Inspect the running workload and map it to a specific build/commit.

# 156. Common Mistake: Wrong Kubernetes Context

Problem:

A staging script modifies production.

Investigate:

```bash

```

Fix:

Use explicit context and namespace mappings.

Verify target before mutation.

# 157. Common Mistake: Sleep Instead of Readiness

Problem:

```bash

```

assumes deployment readiness after one minute.

Fix:

Use:

```bash

```

or:

```bash

```

# 158. Common Mistake: Rollout Success Equals Application Success

A Deployment may become available while an external dependency is failing.

Fix:

Check application health after rollout.

Better still, ensure Kubernetes readiness probes themselves represent meaningful readiness.

---

# 159. Common Mistake: Blind Automatic Rollback

Problem:

Every health failure triggers rollback without considering database or external side effects.

Fix:

Define rollback policy before deployment.

Understand what is reversible.

# 160. Common Mistake: Rebuilding for Production

Problem:

Staging tested artifact A.

Production receives separately rebuilt artifact B.

Fix:

Build once and promote the same immutable artifact when your delivery architecture supports it.

# 161. Common Mistake: Parsing Human Git Output


for automation.

# 163. Common Mistake: Defaulting Missing Environment to Production

# 164. Common Mistake: Ignoring Artifact Verification

# 165. Common Mistake: Unbounded Deployment Waiting

Problem:

Script waits forever.

Fix:

Use:

```text

```

Every waiting loop should have a termination policy.

# 166. Common Mistake: No Final Exit Status

```text
what it is changing

whether the resulting system became healthy
whether the intended version is actually running
whether rollback is safe
whether rollback succeeded
what should be logged
what must never be logged
what status should be returned
```

