
# 1. What Is a Module?

A Python module is usually a Python file containing reusable Python code.

Suppose you create:

```text
disk_utils.py
```

Inside:

```python
def classify_disk_usage(
    disk_usage: int
) -> str:
    """Classify disk usage."""

    if disk_usage >= 90:
        return "CRITICAL"
    elif disk_usage >= 80:
        return "WARNING"
    else:
        return "OK"
```

That file is a Python module.

Conceptually:

```text
disk_utils.py
     |
     +--> classify_disk_usage()
```

Another Python file can import and use that function.

---

Without modules:

```text
automation.py
```

```text

```

Each file has a clearer responsibility.

This improves:

* Organization

* Maintenance

# 3. A Module Is Still a Normal Python File

There is nothing mysterious about a basic module.

This:

```text
server_utils.py
```

is simply a `.py` file.

For example:

```python
def format_server_name(
    hostname: str
) -> str:
    return hostname.strip().lower()
```

The important difference is how we intend to use the file.

Instead of only executing it directly, another Python file can import functionality from it.

```text
        v

        |
        v
```

means:

# 8. Why There Is No `.py` in the Import

The file is:

```text
server_utils.py
```

But normally you write:

```python
import server_utils
```

not:

```python
import server_utils.py
```

Python's import system works with module names.

For a simple `.py` module, the filename without `.py` becomes the module name.

So:

```text
server_utils.py
      |
      v
server_utils
```

---

# 9. Module Namespace

When you write:

```python
import server_utils
```

the module gets its own namespace.

Suppose `server_utils.py` contains:

```python
def check_server():
    print("Checking server")
```

You call:

```python
server_utils.check_server()
```

This tells the reader exactly where the function came from.

That can be valuable in larger projects.

---

# 10. Why Namespaces Matter

Suppose two modules both contain:

```python
check_status()
```

You could have:

```python
import server_utils
import database_utils
```

Then:

```python
server_utils.check_status()
database_utils.check_status()
```

There is no ambiguity.

The module name provides context.

---

# 11. Importing Multiple Modules

You may write:

```python
import os
import sys
import json
```

This is generally clearer than:

```python
import os, sys, json
```

Both may work, but separate lines are easier to read and maintain.

---

# 12. `from ... import`

Sometimes you want a specific object from a module.

Instead of:

```python
import server_utils

server_utils.format_hostname(" WEB01 ")
```

you can write:

```python
from server_utils import format_hostname
```

Then:

```python
hostname = format_hostname(
    " WEB01 "
)

print(hostname)
```

Now you do not need:

```text
server_utils.
```

before the function name.

---

# 13. Comparing the Two Import Styles

Style 1:

```python
import server_utils

server_utils.format_hostname("web01")
```

Style 2:

```python
from server_utils import format_hostname

format_hostname("web01")
```

Both are valid.

The difference is how the imported name becomes available.

---

# 14. When `import module` Is Useful

This:

```python
import server_utils
```

can be useful when:

* You use several functions from the module.
* You want the source of each function to remain obvious.
* You want to avoid name collisions.

Example:

```python
server_utils.check_server()
server_utils.format_hostname()
server_utils.validate_hostname()
```

The source remains clear.

---

# 15. When `from module import name` Is Useful

This:

```python
from server_utils import format_hostname
```

can be useful when:

* You need only a small number of objects.
* Their names are already clear.
* Repeating the module name adds little value.

Example:

```python
from pathlib import Path
```

Then:

```python
path = Path("/var/log")
```

instead of:

```python
import pathlib

path = pathlib.Path("/var/log")
```

Both styles are common.

---

# 16. Importing Multiple Names

Suppose:

```text
server_utils.py
```

contains:

```python
def format_hostname(hostname):
    return hostname.strip().lower()


def is_production(environment):
    return environment == "production"
```

You can write:

```python
from server_utils import (
    format_hostname,
    is_production,
)
```

Then:

```python
print(format_hostname(" WEB01 "))
print(is_production("production"))
```

---

# 17. Avoid `import *`

You may encounter:

```python
from server_utils import *
```

This means roughly:

```text
Import many available names from server_utils
directly into the current namespace.
```

For beginner and production automation, generally avoid this style.

Why?

It becomes difficult to know:

* Which names were imported.
* Where a function came from.
* Whether imported names conflict.
* Which dependencies the file actually uses.

Prefer explicit imports.

---

# 18. Aliases with `as`

Python allows imported objects to have aliases.

Example:

```python
import datetime as dt
```

Now:

```python
dt.datetime.now()
```

uses the alias:

```text
dt
```

instead of:

```text
datetime
```

---

# 19. Aliasing Your Own Module

Suppose:

```python
import server_utils as su
```

Then:

```python
su.format_hostname(" WEB01 ")
```

works.

But aliases should improve readability.

Do not shorten names merely because you can.

This:

```python
import server_utils as s
```

may save typing but make the code less obvious.

---

# 20. Aliasing Imported Objects

You can also write:

```python
from pathlib import Path as FilePath
```

Then:

```python
path = FilePath("/var/log")
```

This is technically possible.

But aliases are most useful when they:

* Avoid naming conflicts.
* Follow established conventions.
* Make a long name easier to use.
* Clarify meaning.

Do not create unnecessary aliases.

# 28. What `os.getenv()` Does

This:

```python
os.getenv("APP_ENV")
```

means:

```text
Ask the operating system environment
for a variable named APP_ENV.
```

If it exists, Python returns its value.

If it does not exist, the result is normally:

```python

```

# 29. Default Value with `os.getenv()`


If `APP_ENV` does not exist, the value becomes:

```text
development
```

# 30. Why Environment Variables Matter

Automation often receives configuration from the environment.

For example:


Environment variables are also frequently used by:

* Kubernetes workloads.

But environment variables are not automatically secure merely because they are environment variables.

Sensitive values still require careful handling.

# 41. `pathlib`

Import:

```python
from pathlib import Path
```

`pathlib` provides an object-oriented way to work with filesystem paths.

For modern Python code, it is often clearer than manually manipulating path strings.

---

# 42. Creating a Path Object

```python
from pathlib import Path

log_file = Path("/var/log/app.log")

print(log_file)
```

Output:

```text
/var/log/app.log
```

`log_file` is not merely being treated as arbitrary text.

It is a `Path` object representing a filesystem path.

---

# 43. Why `pathlib` Helps

Without `pathlib`, beginners often build paths manually:

```python
directory = "/var/log"
filename = "app.log"

full_path = directory + "/" + filename
```

With `pathlib`:

```python
from pathlib import Path

directory = Path("/var/log")
full_path = directory / "app.log"
```

This:

```python
directory / "app.log"
```

constructs the child path.

The `/` here is an operator provided by `Path`.

It is not mathematical division.

---

# 44. Checking Whether a Path Exists

```python
from pathlib import Path

if path.exists():
    print("Configuration exists")
else:
    print("Configuration not found")
```

This is a common automation operation.

---

# 45. File or Directory?

These return Boolean values.

# 46. Creating a Directory with `pathlib`

The method:

The option:

# 47. Parent Directories

Suppose you want:

```text

```

but the parent directories may not exist.

You can write:

```python

path = Path(
    "reports/2026/september"

    parents=True,
    exist_ok=True
)
```

`parents=True` allows missing parent directories to be created.

# 51. Copying a File with `shutil`

Suppose:

```text
config.yaml
```

should be copied to:

```text

```

Example:

```python
import shutil

shutil.copy(
    "config.yaml",
    "backup/config.yaml"
)
```

This performs a real filesystem operation.

Use a safe test directory while learning.

---

# 52. Copying Metadata with `copy2()`

You may also encounter:

```python
shutil.copy2(
    "config.yaml",
    "backup/config.yaml"
)
```

`copy2()` attempts to preserve more filesystem metadata than basic `copy()`.

You do not need to memorize every difference now.

Remember:

```text
shutil
handles high-level file operations.
```

---

# 53. Moving Files

Example:

```python
import shutil

shutil.move(
    "report.txt",
    "archive/report.txt"
)
```

This moves the file.

Again, this changes the filesystem.

Test using disposable files before automating important production data.

---

# 54. Dangerous Filesystem Operations

`shutil` also supports operations capable of deleting directory trees.

For example, you may encounter:

```python
shutil.rmtree(...)
```

Do not experiment with recursive deletion against real directories.

Before destructive automation:

1. Verify the target.
2. Print or log the target.
3. Consider a dry-run mode.
4. Test in a disposable directory.
5. Confirm that path construction is correct.
6. Avoid broad root-level paths.
7. Use least privilege.

A path bug combined with recursive deletion can cause serious damage.

---

# 55. Disk Usage with `shutil`

Example:

```python
import shutil

usage = shutil.disk_usage("/")

print(usage)
```

This can return values representing:

```text
total
used
free
```

You can unpack them:

```python
total, used, free = shutil.disk_usage("/")
```

These values are normally measured in bytes.

---

# 56. Converting Bytes to GiB

A simple conversion:

```python
total, used, free = shutil.disk_usage("/")

gib = 1024 ** 3

print(f"Total: {total / gib:.2f} GiB")
print(f"Used: {used / gib:.2f} GiB")
print(f"Free: {free / gib:.2f} GiB")
```

This turns raw byte values into more readable binary gigabytes, or GiB.

---

# 57. Calculating Disk Percentage

```python
import shutil

total, used, free = shutil.disk_usage("/")

used_percentage = (
    used / total
) * 100

print(
    f"Disk usage: "
    f"{used_percentage:.2f}%"
)
```

Now you can pass that value to a reusable function from Part 7.

For example:

```python
status = classify_disk_usage(
    used_percentage
)
```

This is where standard-library modules and your own functions begin working together.

# 59. Running a Command

Example:

```python
import subprocess

result = subprocess.run(
    ["python3", "--version"],
    capture_output=True,
    text=True
)

print(result.stdout)
```

Depending on the system and Python version, version information may be available in standard output or another output stream.

The important concept is the structure.

---

# 60. Why Commands Are Passed as a List

We used:

```python
[
    "python3",
    "--version"
]
```

instead of one large shell string.

Conceptually:

```text
Program:
python3

Argument:
--version
```

Passing arguments as a list is generally safer and more predictable than constructing shell command strings.

---

# 61. `capture_output=True`

Normally, an external command can write directly to the terminal.

With:

```python
capture_output=True
```

Python captures standard output and standard error so your program can inspect them.

You can then use:

```python
result.stdout
```

and:

```python
result.stderr
```

---

# 62. `text=True`

Without text mode, subprocess output may be returned as bytes.

Using:

```python
text=True
```

asks Python to provide decoded text strings.

That makes operations such as:

```python
result.stdout.strip()
```

more convenient.

---

# 63. Return Codes from Commands

Example:

```python
import subprocess

result = subprocess.run(
    ["python3", "--version"],
    capture_output=True,
    text=True
)

print(result.returncode)
```

A return code of:

```text
0
```

usually indicates successful command execution.

A non-zero code usually indicates some kind of failure or special condition.

---

# 64. Do Not Assume Output Means Success

A command may produce text and still fail.

Check:

```python
result.returncode
```

Do not write automation that assumes:

```text
Output exists
=
Command succeeded
```

The return code matters.

---

# 65. `shell=True` Warning

You may encounter:

```python
subprocess.run(
    "some command",
    shell=True
)
```

Do not use `shell=True` casually, especially when any part of the command comes from:

* Users.
* APIs.
* Files.
* Environment variables.
* External systems.

Untrusted values combined with shell interpretation can create command-injection vulnerabilities.

Prefer argument lists when possible:

```python
subprocess.run(
    ["program", "argument"]
)
```

# 93. What Happens When Python Imports a Module?

This is important.

Suppose:

```text
health.py
```

```python

    print("Checking health")
```

Then `main.py` contains:

```python

```


```python
    print("Inside function")
```

```text

```

executes.

But the body of:


does not execute until the function is called.

# 102. Why Use the Main Guard?

Suppose:

```text
health.py
```

contains:

```python
def classify_disk_usage(
    disk_usage
):
    if disk_usage >= 90:
        return "CRITICAL"

    return "OK"


def main():
    print(
        classify_disk_usage(92)
    )


if __name__ == "__main__":
    main()
```

If you run:

```bash
python3 health.py
```

`main()` executes.

But if another file does:

```python
import health
```

the imported module does not automatically run `main()`.

Its functions become available without executing the direct-run workflow.

---

# 103. Understanding the Main Guard Visually

```text
health.py starts
      |
      v
Define functions
      |
      v
Check __name__
      |
      +----------------------+
      |                      |
      v                      v
"__main__"                "health"
      |                      |
      v                      v
Run main()               Do not run main()
Direct execution         Imported module
```

---

# 104. Is `main()` Special?

No.

This:

```python
def main():
```

is a naming convention.

Python does not require a function named `main`.

The special part is:

```python
__name__
```

and the value:

```python
"__main__"
```

---

# 105. Is the Main Guard Mandatory?

No.

Small scripts may not need it.

But it becomes very useful when:

* A file can be imported.
* You want reusable functions.
* You also want direct execution.
* You want to avoid import-time side effects.
* You are organizing a larger application.

`health.py`:

```python
def main() -> None:
```

# 123. Imports Are Cached

When Python imports a module, it normally records it in:

```python
sys.modules
```

If the same module is imported again during the same process, Python normally reuses the already-loaded module rather than executing it from scratch each time.

You do not need to manipulate `sys.modules` as a beginner.

But this explains why importing the same module several times does not normally rerun all its top-level code repeatedly.

---

# 124. Why Import-Time Side Effects Are Still Bad

Even though modules are normally cached, import-time actions remain problematic.

Avoid modules that immediately:

* Delete files.
* Restart services.
* Send alerts.
* Modify cloud resources.
* Deploy applications.

An import should not surprise the caller with major infrastructure changes.

Prefer explicit functions:

```python

```

```python
delete_backup()
```

```python
deploy_application()
```

Then the caller chooses when those actions happen.

```text

```

A better design might extract shared logic:

```text

    |
    +--> common.py
    |

    |
    +--> common.py
```

You do not need to master circular-import resolution now.

Remember:

```text

```

```python
) -> str:
    """Classify a percentage using two thresholds."""

    if value >= critical_threshold:
        return "CRITICAL"

    if value >= warning_threshold:
        return "WARNING"

    return "OK"


def classify_disk_usage(
    disk_usage: float
) -> str:
    """Classify disk usage."""

    return classify_percentage(
        value=disk_usage,
        warning_threshold=80,
        critical_threshold=90
    )

    cpu_usage: float
) -> str:
    """Classify CPU usage."""

    return classify_percentage(

    )
```

```python
    create_report_directory,
    create_report_filename,
    write_json_report,
)

    level=logging.INFO,
    format=(
        "%(asctime)s "
        "%(levelname)s "
        "%(message)s"
    )
)

    """Run the infrastructure reporting workflow."""

    logging.info(
        "Infrastructure report started"
    )

    environment = os.getenv(
        "APP_ENV",
        "development"
    )

    hostname = os.getenv(
        "HOSTNAME",
        "local-machine"
    )

    disk_usage = get_disk_usage("/")

    disk_status = classify_disk_usage(
        disk_usage
    )

    alert = format_alert(
        severity=disk_status,
        resource=hostname,
        message=(
            f"Disk usage is "

        )
    )

    report_data = {
        "environment": environment,
        "hostname": hostname,
        "disk": {
            "usage_percentage": round(

                2
            ),

        },

    }

    report_directory = (
        create_report_directory()
    )

    filename = (
        create_report_filename()
    )

    report_path = (
        report_directory / filename
    )

    write_json_report(
        report_path,
        report_data
    )

    print(alert)

    print(
        f"Report written to: "
        f"{report_path}"
    )

    logging.info(
        "Infrastructure report completed"
    )


if __name__ == "__main__":
    main()
```

# 191. What Is Idempotent Behavior?

At a beginner level, an operation is idempotent when repeating it leads to the same intended state rather than repeatedly causing unwanted changes.

For example:

```python

    exist_ok=True
)
```


```text
reports1
reports2
reports3
```

This idea becomes very important in infrastructure automation.

# 193. Break It: Invalid JSON Data

Most ordinary Python strings, numbers, booleans, lists, dictionaries, and `None` can map naturally to JSON-compatible data.

But some Python objects cannot be directly serialized by default.

For example, if you put a `Path` object directly into JSON data:

```python
report_data = {
    "path": report_path
}
```

then:

```python
json.dumps(report_data)
```

may raise a serialization error.

A simple fix may be:

```python
report_data = {
    "path": str(report_path)
}
```

Part 14 will explain JSON serialization properly.

# 195. Security: Imports Are Code Execution

Remember that importing a Python module can execute its top-level code.

Therefore, installing or importing untrusted Python code can be dangerous.

Do not assume:

```text
It's only a Python package.
```

means:

```text
It cannot harm the system.
```

Code can:

* Read files.
* Access environment variables.
* Make network connections.
* Start processes.
* Modify files.
* Perform actions allowed by your user permissions.

Use trusted dependencies and understand what you install.

---

# 196. Security: Least Privilege

If your automation only needs to read:

```text
/var/log/app.log
```

it should not automatically run with unrestricted root access.

If it only needs to write:

```text
./reports/
```

give it appropriate access there.

Higher privileges increase the impact of:

* Bugs.
* Path mistakes.
* Malicious dependencies.
* Command injection.
* Accidental deletion.

---

# 197. Security: Environment Variables

Environment variables are useful for configuration.

But do not assume they are a secret vault.

A process with appropriate access may be able to inspect environment information.

Avoid:

```python
print(os.environ)
```

in real systems.

That could expose:

* Tokens.
* Passwords.
* Service credentials.
* Cloud keys.

---

# 198. Security: Subprocess Input

Never blindly build shell commands from untrusted values.

Dangerous conceptual pattern:

```text
user input
    |
    v
string concatenation
    |
    v
shell=True
    |
    v
shell interprets input
```

Safer default:

```text
program
+
separate arguments
```

using:

```python
subprocess.run(
    ["program", "argument"]
)
```

Even then, validate what operations your automation allows.

# 199. Security: Filesystem Paths

Suppose a script receives a path from an external source.

Do not blindly assume it points where you expect.

Validate:

* Allowed directory.
* File type.
* Whether the path exists.
* Whether it is a file or directory.
* Whether symbolic links matter.
* Whether the operation is destructive.

Filesystem automation can cause real damage when paths are wrong.

# 201. Production Thinking: Standard Library Before Dependency

Before installing another package, ask:

```text
Does Python's standard library already solve this problem well enough?
```

Advantages of standard-library solutions can include:

* No extra installation.
* Fewer dependencies.
* Less version-management complexity.
* Smaller attack surface.
* Easier deployment.

But this does not mean:

```text
Never use third-party packages.
```

Many third-party libraries solve important problems better than the standard library alone.

The correct principle is:

```text
Add a dependency because it provides meaningful value,
not because installing packages is easy.
```

# 205. Production Thinking: Reusable Modules Should Avoid Hidden Assumptions


* A particular user.

* A particular directory.
* A particular machine.

```python
def write_report(
    file_path,
    content

    ...
```

Reusable modules should avoid unnecessary machine-specific assumptions.
