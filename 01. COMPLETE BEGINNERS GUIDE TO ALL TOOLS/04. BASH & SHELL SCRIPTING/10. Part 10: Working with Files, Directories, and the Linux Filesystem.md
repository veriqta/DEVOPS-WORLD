# Part 10: Working with Files, Directories, and the Linux Filesystem

In Part 9, you learned how to turn Bash scripts into command-line tools using positional parameters, options, `getopts`, validation, help messages, and meaningful exit codes.

Now we move into one of the most important areas of Bash automation: working with the Linux filesystem.

Almost every real Bash automation task interacts with files or directories.

A deployment script may copy configuration files.

A backup script may archive application data.

A CI/CD pipeline may create build artifacts.

A monitoring script may inspect log files.

A cleanup job may remove old temporary files.

A server-administration script may change permissions or ownership.

These operations are powerful.

They can also be destructive.

A mistake such as:

```bash
rm -rf "$target"
```

can be catastrophic if `$target` contains the wrong value.

So Part 10 is not simply about learning `cp`, `mv`, and `rm`.

You will learn how to manipulate filesystem data safely.

By the end of this part, you should understand:

* how the Linux filesystem is organized
* absolute and relative paths
* `pwd`
* `cd`
* `ls`
* `mkdir`
* `touch`
* `cp`
* `mv`
* `rm`
* `rmdir`
* recursive filesystem operations
* checking whether files and directories exist
* Linux permissions
* ownership
* `chmod`
* `chown`
* `chgrp`
* file metadata
* `stat`
* disk usage with `du`
* filesystem capacity with `df`
* temporary files
* `mktemp`
* wildcards
* shell globbing
* hidden files
* safe deletion practices
* backups before destructive operations
* looping through files
* bulk rename concepts
* how to build a practical backup and cleanup utility

# 1. Why Filesystem Automation Matters

Linux systems store enormous amounts of operational information as files and directories.

Examples include:

```text
Application code
Configuration files
Logs
SSH keys
Certificates
Temporary files
Build artifacts
Backups
System configuration
User data
Container configuration
Service definitions
Scripts
Deployment manifests
```

A DevOps engineer might need to automate:

```text
Copy 50 configuration files

Back up application data

Clean logs older than a certain age

Check whether a configuration file exists

Create deployment directories

Inspect available disk space

Change permissions

Move build artifacts

Process every .log file in a directory

Create temporary working files
```

Doing these manually becomes repetitive and error-prone.

Bash allows you to automate them.

But filesystem automation requires discipline because commands can modify or permanently delete data.

# 2. Linux Filesystem Recap

Linux uses a hierarchical filesystem.

At the top is:

```text
/
```

called the **root directory**.

A simplified filesystem might look like:

```text
/
├── bin
├── boot
├── dev
├── etc
├── home
│   ├── ann
│   │   ├── projects
│   │   ├── scripts
│   │   └── logs
├── opt
├── tmp
├── usr
└── var
    ├── log
    └── lib
```

Everything begins underneath `/`.

---

# 3. Important Linux Directories

You do not need to memorize the entire Linux filesystem immediately.

But several directories appear frequently in DevOps work.

| Directory  | Common purpose                                                      |
| ---------- | ------------------------------------------------------------------- |
| `/`        | Root of the filesystem                                              |
| `/home`    | User home directories                                               |
| `/etc`     | System and application configuration                                |
| `/var`     | Variable application/system data                                    |
| `/var/log` | Logs                                                                |
| `/tmp`     | Temporary files                                                     |
| `/opt`     | Optional/additional software                                        |
| `/usr`     | User-space programs, libraries, and shared data                     |
| `/dev`     | Device interfaces                                                   |
| `/proc`    | Process and kernel information exposed through a virtual filesystem |

For example:

```bash
ls /var/log
```

may show system logs.

Do not modify unfamiliar system directories simply because you have permission to do so.

# 4. Your Home Directory

Your user's home directory is normally represented by:

```bash
$HOME
```

or:

```text
~
```

Check:

```bash
printf '%s\n' "$HOME"
```

Example:

```text
/home/ann
```

On another machine it could be different.

This is why scripts often prefer:

```bash
"$HOME/scripts"
```

instead of hardcoding:

```bash
/home/ann/scripts
```

# 5. What Is a Path?

A **path** describes the location of a file or directory.

Example:

```text
/home/ann/projects/api/config.yaml
```

This identifies:

```text
/
└── home
    └── ann
        └── projects
            └── api
                └── config.yaml
```

The final component may be a file or directory depending on the path.

---

# 6. Absolute Paths

An **absolute path** begins from the root directory `/`.

Example:

```text
/home/ann/projects/api
```

Another:

```text
/var/log/syslog
```

Absolute paths begin with:

```text
/
```

They do not depend on your current working directory.

---

# 7. Relative Paths

A **relative path** is interpreted relative to your current working directory.

Suppose you are in:

```text
/home/ann/projects
```

and have:

```text
api/config.yaml
```

You can refer to it as:

```text
api/config.yaml
```

That is a relative path.

The equivalent absolute path is:

```text
/home/ann/projects/api/config.yaml
```

---

# 8. Why Current Directory Matters

Suppose your current directory is:

```text
/home/ann/projects
```

Then:

```bash
cat api/config.yaml
```

means:

```text
/home/ann/projects/api/config.yaml
```

But if you move to:

```text
/tmp
```

the same relative path:

```text
api/config.yaml
```

now means:

```text
/tmp/api/config.yaml
```

This is why scripts that rely heavily on unknown working directories can fail.

# 16. Always Check `cd` in Scripts

Consider:

```bash
cd "$project_dir"
rm -rf build
```

What happens if:

```bash
cd "$project_dir"
```

fails?

The script may remain in the previous directory.

Then:

```bash
rm -rf build
```

might remove the wrong `build` directory.

Safer:

```bash
cd "$project_dir" || exit 1
```

or:

```bash
if ! cd "$project_dir"; then
    printf 'ERROR: cannot enter directory: %s\n' "$project_dir" >&2
    exit 1
fi
```

Never assume a directory change succeeded before running destructive relative-path operations.

Syntax:


```bash

```

Verify:

```bash
ls -l
```

# 29. Copying into a Directory

Suppose:

```text
config.yaml
backups/
```

You can run:

```bash

```

```text
backups/config.yaml
```

You can also run:

# 31. Copying Multiple Files

Example:

```bash
cp app.conf database.conf nginx.conf backups/
```

---

# 32. Recursive Copying

By default, `cp` does not copy an entire directory tree as an ordinary file.

For directories, use recursive copying.

Example:

```bash
cp -r app app-backup
```

The:

```text
-r
```

means:

**recursive**

The command descends through the directory and its contents.

---

# 33. What Does Recursive Mean?

Suppose:

```text
app/
├── config/
│   └── app.conf
├── logs/
│   └── app.log
└── scripts/
    └── start.sh
```

Running:

```bash
cp -r app app-backup
```

copies the tree.

Conceptually:

```text
app/
 |
 +--> config/
 |      |
 |      +--> app.conf
 |
 +--> logs/
 |      |
 |      +--> app.log
 |
 +--> scripts/
        |
        +--> start.sh
```

Recursive operations continue through nested directories.

---

# 34. Preserve Metadata When Appropriate

For backup-like copies, you may encounter:

```bash
cp -a source destination
```

`-a` is archive mode.

It is commonly used when you want to preserve important attributes while recursively copying.

It generally attempts to preserve things such as:

* permissions
* timestamps
* symbolic links
* ownership where permitted
* directory structure

For simple beginner copies, `cp -r` demonstrates recursion.

For filesystem backups, understand whether metadata preservation matters.

---

# 35. Be Careful with Existing Destinations

Suppose:

```bash
cp config.yaml backups/config.yaml
```

and the destination already exists.

It may be overwritten.

Before replacing important files, inspect:

```bash
ls -l backups/config.yaml
```

or explicitly create a backup first.

For interactive manual use, some systems support:

```bash
cp -i source destination
```

which asks before overwrite.

Do not depend on interactive prompts inside unattended automation unless that is intentionally part of the design.

# 36. `mv`

`mv` moves or renames files and directories.

Rename:

```bash
mv old-name.txt new-name.txt
```

Move into another directory:

```bash
mv app.log logs/
```

---

# 37. Moving Directories

You can also move directories.

Example:

```bash
mv old-project archive/
```

Depending on destination state, this may place the directory inside `archive` or rename it.

Always inspect your source and destination paths before large moves.

---

# 38. `mv` Can Overwrite

Like `cp`, `mv` can replace an existing destination under some conditions.

Before automation:

```text
Verify source
Verify destination
Check whether destination already exists
Decide overwrite policy
```

Do not let overwrite behavior be accidental.

---

# 39. `rm`

`rm` removes files.

Example:

```bash
rm old.log
```

This is a destructive operation.

Unlike moving a file into a desktop Trash folder, command-line deletion usually does not provide an easy built-in undo.

Treat `rm` seriously.

---

# 40. Removing Multiple Files

Example:

```bash
rm old1.log old2.log old3.log
```

Every listed file is targeted.

Before doing this with important files, preview them:

```bash
ls -l old1.log old2.log old3.log
```

---

# 41. `rm -r`

To remove a directory and its contents recursively:

```bash
rm -r old-directory
```

This traverses the directory tree and removes its contents.

This is substantially more dangerous than deleting one known file.

---

# 42. `rm -f`

The:

```text
-f
```

option means:

**force**

It suppresses certain prompts/errors for nonexistent files and attempts removal without interactive confirmation.

You will frequently see:

```bash
rm -rf directory
```

This combines:

```text
-r = recursive
-f = force
```

This is powerful and dangerous.

Do not develop the habit of automatically adding `-rf` to every deletion command.

---

# 43. Dangerous Deletion Pattern

Consider:

```bash
rm -rf "$target"
```

If:

```bash
target="/home/ann/project/build"
```

the intended target may be reasonable.

But what if a bug causes:

```bash
target="/"
```

?

Or:

```bash
target=""
```

and the command is constructed differently?

Filesystem scripts must validate destructive targets.

---

# 44. Never Blindly Copy Destructive Commands

Before running commands that:

* recursively delete directories
* overwrite configuration
* change permissions recursively
* change ownership recursively
* clean system directories

understand:

```text
What exactly is the target?

Is the path absolute or relative?

Does it contain the expected value?

Could a variable be empty?

Could a wildcard match more than expected?

Is there a backup?

Can I preview the operation first?
```

---

# 45. `rmdir`

`rmdir` removes **empty directories**.

Example:

```bash
mkdir empty-dir
rmdir empty-dir
```

If the directory contains files:

```bash
rmdir project
```

will normally fail.

This makes `rmdir` safer for situations where you only intend to remove empty directories.

---

# 46. `rmdir` vs `rm -r`

Think:

```text
rmdir
 |
 +--> empty directory only
```

```text
rm -r
 |
 +--> directory and contents recursively
```

If you only intend to remove an empty directory, `rmdir` communicates that intention more safely.

# 48. File Existence Checks

From Part 6, you learned test expressions.

To check whether a path exists:

```bash
[[ -e "$path" ]]
```

Example:

```bash
file="project/config/app.conf"

if [[ -e "$file" ]]; then
    printf 'Path exists: %s\n' "$file"
else
    printf 'Path does not exist: %s\n' "$file"
fi
```

---

# 49. Regular File Check

Use:

```bash
[[ -f "$file" ]]
```

to test whether a path exists and is a regular file.

Example:

```bash
if [[ -f "project/config/app.conf" ]]; then
    printf 'Configuration file exists.\n'
fi
```

This is more specific than:

```bash
[[ -e ... ]]
```

---

# 50. Directory Existence Check

Use:

```bash
[[ -d "$directory" ]]
```

Example:

```bash
backup_dir="project/backups"

if [[ -d "$backup_dir" ]]; then
    printf 'Backup directory exists.\n'
else
    printf 'Creating backup directory.\n'
    mkdir -p "$backup_dir"
fi
```

---

# 51. Why Check Path Type?

Suppose you expect:

```text
project/backups
```

to be a directory.

A path with that name might exist but be a regular file.

This:

```bash
[[ -e "$path" ]]
```

would succeed.

But:

```bash
[[ -d "$path" ]]
```

would correctly detect that it is not a directory.

Validate the property you actually require.

# 53. File Tests and Permissions Are Related but Different

Suppose:

```bash
[[ -w "$file" ]]
```

succeeds.

That asks whether the file is writable in the current execution context.

It is not merely displaying the permission bits.

Factors such as the current user and filesystem behavior matter.

For metadata inspection, use tools such as:

```bash
ls -l
```

and:

```bash
stat
```

# 54. Linux Permissions

Linux permissions commonly control three operations:

```text
r = read
w = write
x = execute
```

They are evaluated for categories such as:

```text
user
group
others
```

You may also hear the user category called the **owner**.

---

# 55. Reading `ls -l`

Example:

```text
-rwxr-x---
```

Break it into:

```text
-  rwx  r-x  ---
|   |    |    |
|   |    |    +--> others
|   |    +-------> group
|   +------------> owner/user
+----------------> file type
```

The first character:

```text
-
```

typically means regular file.

A:

```text
d
```

means directory.

---

# 56. Permission Meaning for Regular Files

For a regular file:

```text
r = read file contents
w = modify file contents
x = execute file as a program/script when other requirements are met
```

Example:

```text
rw-
```

means read and write, but not execute.

---

# 57. Permission Meaning for Directories

Directory permissions behave differently.

Simplified:

```text
r = list directory entries
w = create/remove/rename entries, subject to other permissions/rules
x = traverse/access entries through the directory
```

Directory execute permission does not mean:

> execute the directory.

It controls traversal.

This distinction is important.

---

# 58. Numeric Permissions

Permissions can be represented numerically.

Values:

```text
r = 4
w = 2
x = 1
```

Add them for each category.

Examples:

```text
7 = 4 + 2 + 1 = rwx
6 = 4 + 2     = rw-
5 = 4 + 1     = r-x
4             = r--
0             = ---
```

---

# 59. Understanding `chmod 600`

Consider:

```bash
chmod 600 secret.txt
```

Break down:

```text
6 = owner = read + write
0 = group = no permissions
0 = others = no permissions
```

Result:

```text
rw-------
```

This is often appropriate for sensitive files that only the owner should read and modify.

---

# 60. Understanding `chmod 644`

```bash
chmod 644 config.txt
```

means:

```text
owner  = rw-
group  = r--
others = r--
```

Result:

```text
rw-r--r--
```

Whether this is appropriate depends on what the file contains.

A secrets file should not automatically receive world-readable permissions.

---

# 61. Understanding `chmod 755`

```bash
chmod 755 script.sh
```

means:

```text
owner  = rwx
group  = r-x
others = r-x
```

Result:

```text
rwxr-xr-x
```

This is common for executable scripts intended to be readable and executable by others.

But permissions should match actual requirements.

---

# 62. `chmod`

`chmod` means:

**change mode**

It changes filesystem permission bits.

Numeric example:

```bash
chmod 600 secret.txt
```

Symbolic example:

```bash
chmod u+x deploy.sh
```

Here:

```text
u = user/owner
+ = add
x = execute
```

---

# 63. Symbolic `chmod`

Examples:

```bash
chmod u+x script.sh
```

add execute for owner.

```bash
chmod g-w file.txt
```

remove write from group.

```bash
chmod o-r secret.txt
```

remove read from others.

```bash
chmod a+r documentation.txt
```

add read for all categories.

Where:

```text
u = user
g = group
o = others
a = all
```

---

# 64. Recursive Permission Changes

You may encounter:

```bash
chmod -R 755 directory
```

This recursively changes permissions throughout the directory tree.

Be careful.

Files and directories often should not have identical permission modes.

For example, making every file executable simply because directories require execute/traverse permission may be inappropriate.

Do not blindly use recursive `chmod`.

---

# 65. Ownership

Linux files usually have:

```text
owner
group
```

Inspect:

```bash
ls -l
```

Example:

```text
-rw-r----- 1 ann developers 2048 Sep 2 10:00 config.ini
```

Here:

```text
owner = ann
group = developers
```

---

# 66. Why Ownership Matters

Permissions answer questions such as:

```text
What can the owner do?
What can the group do?
What can everyone else do?
```

Ownership answers:

```text
Who is the owner?
Which group is associated with this file?
```

Both determine access.

---

# 67. `chown`

`chown` means:

**change owner**

Example:

```bash
sudo chown appuser app.conf
```

This changes the owner to:

```text
appuser
```

Changing ownership normally requires appropriate privileges.

Do not use `sudo` simply because a command failed.

First understand why ownership needs to change.

---

# 68. Change Owner and Group Together

You may use:

```bash
sudo chown appuser:appgroup app.conf
```

This sets:

```text
owner = appuser
group = appgroup
```

---

# 69. Recursive Ownership

You may encounter:

```bash
sudo chown -R appuser:appgroup /opt/myapp
```

This changes ownership recursively.

Before doing this, inspect:

```bash
ls -ld /opt/myapp
```

and relevant contents.

# 82. Temporary Files

# 83. `mktemp`

`mktemp` creates unique temporary files or directories safely.

Example:

```bash
temp_file=$(mktemp)
```

Then:

```bash
printf 'Temporary file: %s\n' "$temp_file"
```

Example result:

```text
/tmp/tmp.XYZ123abc
```

The exact name varies.

---

# 84. Create a Temporary Directory

Use:

```bash
temp_dir=$(mktemp -d)
```

Verify:

```bash
printf 'Temporary directory: %s\n' "$temp_dir"
```

Now your script has a unique workspace.

---

# 85. Always Clean Temporary Resources

If a script creates:

```bash
temp_dir=$(mktemp -d)
```

it should normally clean it up.

Example:

```bash
rm -rf "$temp_dir"
```

But what happens if the script fails before reaching that line?

This is where `trap`, introduced in earlier discussions and covered more deeply later, becomes useful.

Example:

```bash
temp_dir=$(mktemp -d)

cleanup() {
    rm -rf "$temp_dir"
}

trap cleanup EXIT
```

When the script exits, Bash runs `cleanup`.

---

# 86. Validate Temporary Variables Too

Even when using `mktemp`, do not assume success.

Safer:

```bash
temp_dir=$(mktemp -d) || {
    printf 'ERROR: failed to create temporary directory\n' >&2
    exit 1
}
```

Then:

```bash
[[ -d "$temp_dir" ]] || exit 1
```

This matters before later destructive cleanup.

# 87. Wildcards

The shell supports patterns commonly called wildcards.

Important ones include:

```text
*     zero or more characters
?     exactly one character
[...] one character from a set/range
```

Example:

```bash
ls *.log
```

may match:

```text

error.log
audit.log
```

---

# 88. What Is Globbing?

**Globbing** is the shell's filename pattern expansion.

Suppose the directory contains:

```text
app.log
error.log
notes.txt
```

You type:

```bash
printf '%s\n' *.log
```

Bash expands:

```text
*.log
```

before `printf` runs.

Conceptually:

```text
You type:

*.log
   |
   v
Bash searches matching filenames
   |
   v
app.log error.log
   |
   v
Command receives filenames
```

---

# 89. `*`

The pattern:

```text
*
```

matches zero or more characters in filenames, subject to shell globbing rules.

Example:

```bash
ls *.txt
```

could match:

```text
notes.txt
users.txt
report.txt
```

---

# 90. `?`

The pattern:

```text
?
```

matches exactly one character.

Suppose:

```text
log1.txt
log2.txt
log10.txt
```

Then:

```text
log?.txt
```

matches:

```text
log1.txt
log2.txt
```

but not:

```text
log10.txt
```

because `10` contains two characters.

---

# 91. Character Sets

Example:

```text
file[123].txt
```

can match:

```text
file1.txt
file2.txt
file3.txt
```

Another example:

```text
log[0-9].txt
```

matches a single digit in that position.

---

# 92. Hidden Files and Globbing

By default:

```text
*
```

does not normally match filenames beginning with `.`.

Suppose:

```text
config.txt
.env
.gitignore
```

Then:

```bash
printf '%s\n' *
```

normally includes:

```text
config.txt
```

but not:

```text
.env
.gitignore
```

This matters during copies, backups, and cleanup operations.

---

# 93. The Hidden-File Backup Problem

Suppose you run:

```bash
cp -r project/* backup/
```

You may assume:

> Everything in project was copied.

But hidden entries may be excluded.

That can matter if the project contains:

```text
.env
.gitignore
.github/
```

Do not casually assume `*` means literally every directory entry.

---

# 94. Better Directory Copy Semantics

If you intend to copy the contents of a directory, including hidden entries, one useful pattern is:

```bash
cp -a project/. backup/
```

The exact behavior of copy commands and metadata preservation should be understood before using them for critical backups.

For serious backup systems, dedicated backup tools may be more appropriate than a simple `cp`.

---

# 95. Quoting and Globbing

This:

```bash
printf '%s\n' "*.log"
```

does not normally expand the wildcard because it is quoted.

Bash passes the literal string:

```text
*.log
```

This:

```bash
printf '%s\n' *.log
```

allows glob expansion.

So quoting decisions affect wildcard behavior.

---

# 96. But Quote Variables Containing Paths

Suppose:

```bash
file="application logs/app.log"
```

Use:

```bash
rm "$file"
```

not:

```bash
rm $file
```

The second can split the value into multiple words.

The lesson is not:

> Never quote.

The lesson is:

> Understand when you want shell pattern expansion and when you want a literal variable value.

---

# 97. A Dangerous Wildcard Example

Consider:

```bash
rm *.log
```

This deletes every matching `.log` file in the current directory.

Before deletion, preview:

```bash
printf '%s\n' *.log
```

or:

```bash
ls -l -- *.log
```

Then confirm that the matches are what you intended.

# 98. Why `--` Can Matter

Suppose a filename is:

```text
-important.log
```

A command may interpret it as an option.

Many Unix commands support:

```text
--
```

to mark the end of options.

Example:

```bash
rm -- "-important.log"
```

Now the filename is treated as an operand rather than another option.

This becomes important when processing arbitrary filenames.

---

# 99. Safe Deletion Principle 1: Know the Target

Before:

```bash
rm "$file"
```

verify:

```bash
[[ -f "$file" ]]
```

if a regular file is expected.

Before:

```bash
rm -rf "$directory"
```

verify:

```bash
[[ -d "$directory" ]]
```

But existence checks alone are not enough for high-risk deletion.

You should also validate that the path is an expected target.

---

# 100. Safe Deletion Principle 2: Reject Empty Variables

Example:

```bash
if [[ -z "$target" ]]; then
    printf 'ERROR: deletion target is empty\n' >&2
    exit 1
fi
```

Never allow a destructive operation to depend on an unchecked variable.

---

# 101. Safe Deletion Principle 3: Reject Dangerous Targets

Example:

```bash
case "$target" in
    ""|"/"|"/home"|"/etc"|"/var")
        printf 'ERROR: refusing dangerous deletion target: %s\n' "$target" >&2
        exit 1
        ;;
esac
```

This is not a complete universal deletion-security system.

It demonstrates defensive thinking.

A real cleanup tool should be even more narrowly scoped.

---

# 102. Safe Deletion Principle 4: Restrict the Allowed Parent

Suppose your script should only delete from:

```text
/home/ann/app/backups
```

Do not accept arbitrary filesystem paths.

A stronger design is:

```text
cleanup root
    |
    v
/home/ann/app/backups
    |
    +--> backup-001
    +--> backup-002
    +--> backup-003
```

The script should operate only inside its known cleanup root.

---

# 103. Safe Deletion Principle 5: Preview

Before deleting:

```bash
printf 'Would remove: %s\n' "$target"
```

A dry-run option is even better.

For example:

```bash
if [[ "$dry_run" == "true" ]]; then
    printf 'DRY RUN: would remove %s\n' "$target"
else
    rm -- "$target"
fi
```

---

# 104. Safe Deletion Principle 6: Back Up Important Data

If a file is important and you are about to replace it:

```bash
cp config.yaml config.yaml.backup
```

Better, include a timestamp:

```bash
timestamp=$(date '+%Y%m%d-%H%M%S')
cp config.yaml "config.yaml.$timestamp.bak"
```

Example:

```text
config.yaml.20260902-103015.bak
```

Now multiple backups do not overwrite each other.

---

# 105. Backup Before Modification

Suppose your script changes:

```text
app.conf
```

A safer flow is:

```text
Validate original
      |
      v
Create backup
      |
      v
Verify backup
      |
      v
Modify original
      |
      v
Validate new configuration
      |
      v
Restart/reload if appropriate
      |
      v
Verify service
```

This is safer than:

```text
modify first
hope later
```

---

# 106. Verify the Backup

Do not merely run:

```bash
cp "$source" "$backup"
```

and assume success.

Check:

```bash
if ! cp "$source" "$backup"; then
    printf 'ERROR: backup failed\n' >&2
    exit 1
fi
```

Then, where appropriate:

```bash
[[ -f "$backup" ]] || {
    printf 'ERROR: backup verification failed\n' >&2
    exit 1
}
```

Only proceed with destructive modification after backup success.

---

# 107. Backups Are Not Automatically Good Backups

A copied file is not automatically a complete backup strategy.

Ask:

```text
Can it be restored?

Does it preserve required metadata?

Is it stored separately from the failure domain?

Could the cleanup script delete the backup too?

Are backups rotated?

Are they tested?

Are sensitive backups protected?
```

Production backup engineering goes far beyond `cp`.

But Bash can help automate pieces of the workflow.

# 108. Looping Through Files

From Part 7, you learned loops.

Now combine loops with globbing.

Suppose:

```text
app.log
error.log
audit.log
```

Run:

```bash
for file in *.log; do
    printf 'Processing: %s\n' "$file"
done
```

Bash expands the pattern, and the loop processes each match.

---

# 109. Always Quote the Loop Variable

Correct:

```bash
for file in *.log; do
    printf 'Processing: %s\n' "$file"
done
```

If you later use:

```bash
cp "$file" "$backup_dir/"
```

the quotes protect filenames containing spaces.

Avoid:

```bash
cp $file $backup_dir/
```

---

# 110. What If No Files Match?

This is subtle.

Suppose no `.log` files exist.

Depending on Bash settings, the unmatched pattern:

```text
*.log
```

may remain literal.

Then the loop may process:

```text
*.log
```

as if it were a filename.

One simple defensive check is:

```bash
for file in *.log; do
    [[ -e "$file" ]] || continue

    printf 'Processing: %s\n' "$file"
done
```

Now an unmatched literal pattern is skipped.

---

# 111. `nullglob`

Bash has an option called:

```bash
shopt -s nullglob
```

With `nullglob` enabled, a glob that matches nothing expands to nothing rather than remaining literal.

Example:

```bash
shopt -s nullglob

files=(*.log)

for file in "${files[@]}"; do
    printf 'Processing: %s\n' "$file"
done
```

Arrays are covered more deeply in Part 12.

For now, understand why no-match behavior matters.

---

# 112. Looping Through Directories

Example:

```bash
for directory in */; do
    [[ -d "$directory" ]] || continue

    printf 'Directory: %s\n' "$directory"
done
```

The pattern:

```text
*/
```

commonly matches directories in the current directory.

---

# 113. Processing Files with Spaces

Suppose:

```text
application log.txt
database log.txt
```

This loop is safe:

```bash
for file in *.txt; do
    [[ -e "$file" ]] || continue
    printf '<%s>\n' "$file"
done
```

Because each glob result becomes an individual shell word, and:

```bash
"$file"
```

preserves it when used.

---

# 114. Do Not Parse `ls`

A common bad pattern is:

```bash
for file in $(ls *.log); do
    ...
done
```

This is unnecessary and can break on filenames containing whitespace or other unusual characters.

Prefer direct globbing:

```bash
for file in *.log; do
    ...
done
```

or more robust `find`-based techniques when recursion or complex matching is needed.

# 115. Bulk Operations

A bulk operation performs the same action across multiple files.

Examples:

```text
Copy every log file

Rename every .txt file

Compress every backup

Change permissions on selected scripts

Move all reports

Inspect every configuration file
```

Loops make bulk operations possible.

But bulk operations amplify mistakes.

If your logic is wrong once, it may be wrong 10,000 times.

---

# 116. Preview Bulk Operations First

Before:

```bash
for file in *.log; do
    rm -- "$file"
done
```

first run:

```bash
for file in *.log; do
    [[ -e "$file" ]] || continue
    printf 'Would delete: %s\n' "$file"
done
```

Only after verifying the list should deletion be enabled.

This is the same dry-run principle from Part 9.

---

# 117. Bulk Rename Concepts

Suppose:

```text
report1.txt
report2.txt
report3.txt
```

You want:

```text
report1.txt.bak
report2.txt.bak
report3.txt.bak
```

You could write:

```bash
for file in *.txt; do
    [[ -e "$file" ]] || continue

    mv -- "$file" "$file.bak"
done
```

But production bulk renaming requires more thought.

---

# 118. Detect Destination Collisions

Suppose:

```text
report1.txt.bak
```

already exists.

Then:

```bash
mv report1.txt report1.txt.bak
```

could overwrite or otherwise conflict with existing data depending on command/platform/options.

Safer:

```bash
destination="$file.bak"

if [[ -e "$destination" ]]; then
    printf 'SKIP: destination exists: %s\n' "$destination" >&2
    continue
fi

mv -- "$file" "$destination"
```

---

# 119. Preview Rename Mapping

Before bulk renaming:

```bash
for file in *.txt; do
    [[ -e "$file" ]] || continue

    destination="$file.bak"

    printf '%s -> %s\n' "$file" "$destination"
done
```

Inspect the mapping.

Then enable `mv`.

This simple habit prevents many mistakes.

---

# 120. Filename Transformation

Suppose:

```text
application.log
```

You want:

```text
application.log.backup
```

Easy:

```bash
new_name="${file}.backup"
```

Suppose instead you want:

```text
application.backup
```

from:

```text
application.log
```

You can use parameter expansion:

```bash
base="${file%.log}"
new_name="${base}.backup"
```

`${file%.log}` removes the shortest matching `.log` suffix.

Advanced parameter expansion receives deeper coverage later.

# 121. Filesystem Automation and Race Conditions

Imagine:

```text
Check file exists
     |
     v
Another process changes/removes file
     |
     v
Your script operates
```

Filesystem state can change between checking and acting.

This is one reason checks are useful but not magical guarantees.

Robust scripts should also handle failure from the actual command.

Do not write:

```bash
if [[ -f "$file" ]]; then
    cp "$file" "$backup"
fi
```

and assume `cp` cannot fail.

Instead:

```bash
if [[ -f "$file" ]]; then
    if ! cp "$file" "$backup"; then
        printf 'ERROR: copy failed: %s\n' "$file" >&2
    fi
fi
```

---

# 122. Validate Commands, Not Just Preconditions

Think:

```text
Check expected state
       |
       v
Attempt operation
       |
       v
Check operation status
       |
       v
Verify resulting state
```

Example:

```bash
if [[ ! -f "$source" ]]; then
    printf 'ERROR: source missing\n' >&2
    exit 1
fi

if ! cp "$source" "$destination"; then
    printf 'ERROR: copy failed\n' >&2
    exit 1
fi

if [[ ! -f "$destination" ]]; then
    printf 'ERROR: copied file not found\n' >&2
    exit 1
fi
```

# 129. Argument Parsing

```bash
parse_args() {

    OPTIND=1

    while getopts ":s:b:k:dh" option; do

        case "$option" in
            s)
                source_dir="$OPTARG"
                ;;

            b)
                backup_root="$OPTARG"
                ;;

            k)
                keep_days="$OPTARG"
                ;;

            d)
                dry_run=true
                ;;

            h)
                usage
                exit 0
                ;;

            :)
                printf 'ERROR: option -%s requires a value\n' "$OPTARG" >&2
                return 2
                ;;

            \?)
                printf 'ERROR: invalid option: -%s\n' "$OPTARG" >&2
                return 2
                ;;
        esac

    done

    shift "$((OPTIND - 1))"

    if (( $# > 0 )); then
        printf 'ERROR: unexpected argument: %s\n' "$1" >&2
        return 2
    fi

    return 0
}
```

# 130. Validate the Source Directory

Add:

```bash
validate_source() {

    if [[ -z "$source_dir" ]]; then
        printf 'ERROR: source directory is required\n' >&2
        return 2
    fi

    if [[ ! -d "$source_dir" ]]; then
        printf 'ERROR: source directory does not exist: %s\n' "$source_dir" >&2
        return 2
    fi

    if [[ ! -r "$source_dir" ]]; then
        printf 'ERROR: source directory is not readable: %s\n' "$source_dir" >&2
        return 1
    fi

    return 0
}
```

---

# 131. Validate the Backup Root

Add:

```bash
validate_backup_root() {

    if [[ -z "$backup_root" ]]; then
        printf 'ERROR: backup directory is required\n' >&2
        return 2
    fi

    if [[ -e "$backup_root" && ! -d "$backup_root" ]]; then
        printf 'ERROR: backup path exists but is not a directory: %s\n' \
            "$backup_root" >&2
        return 2
    fi

    return 0
}
```

Notice the logic:

```text
Does path exist?
       |
       +--> No: can create directory later
       |
       +--> Yes
             |
             v
          Is directory?
```

# 136. Understanding the Copy Command



copy.


# 140. The `find` Command

A basic form is:

```bash

```

For example:


---

# 141. Restricting Search Depth

We can use:

```bash
find "$backup_root" -mindepth 1 -maxdepth 1
```

This means:

```text
-mindepth 1
    do not return backup_root itself

-maxdepth 1
    inspect only direct children
```

This is an important safety boundary.

We do not want cleanup recursively discovering arbitrary nested directories.

---

# 142. Match Backup Directories Only

Add:

```bash
-type d
```

and:

```bash
-name 'backup-*'
```

Now:

```bash

    -mindepth 1 \
    -maxdepth 1 \
    -type d \
    -name 'backup-*'
```

matches only direct child directories named like:

```text
backup-20260901-100000
backup-20260830-140000
```

---

# 143. Match by Age

GNU/Linux `find` supports:

```bash

```

to match based on modification time in day-sized units.

There are boundary details to how `find -mtime` rounds elapsed time, so do not treat it as an exact hour-level retention policy.

For a simple daily backup cleanup, it is sufficient for this exercise.

---

# 144. Why the Pattern Is Quoted

We write:

```bash
-name 'backup-*'
```

not:

```bash
-name backup-*
```

because we want:

```text
find
```

to receive the pattern.

If the shell expands `backup-*` before `find` runs, the command may behave incorrectly.

This is an important distinction:

```text
Shell globbing
vs
pattern interpreted by another command
```

# 146. Cleanup Function

Add:

```bash
cleanup_old_backups() {

    if ! find "$backup_root" \
        -mindepth 1 \
        -maxdepth 1 \
        -type d \
        -name 'backup-*' \
        -mtime "+$keep_days" \
        -print > "$temp_file"; then

        printf 'ERROR: failed to inspect old backups\n' >&2
        return 1
    fi

    while IFS= read -r old_backup; do

        [[ -n "$old_backup" ]] || continue

        case "$old_backup" in
            "$backup_root"/backup-*)
                ;;
            *)
                printf 'ERROR: refusing unexpected cleanup target: %s\n' \
                    "$old_backup" >&2
                return 1
                ;;
        esac

        if [[ "$dry_run" == "true" ]]; then
            printf 'DRY RUN: would remove old backup: %s\n' "$old_backup"
            continue
        fi

        printf 'Removing old backup: %s\n' "$old_backup"

        if ! rm -rf -- "$old_backup"; then
            printf 'ERROR: failed to remove backup: %s\n' \
                "$old_backup" >&2
            return 1
        fi

    done < "$temp_file"

    return 0
}
```

---

# 147. Why `IFS= read -r`?

The loop:

```bash
while IFS= read -r old_backup; do
```

is the safer standard pattern for reading lines.

```text
IFS=
```

prevents leading/trailing whitespace from being stripped through normal field splitting.

```text
-r
```

prevents backslashes from being treated as escapes by `read`.

For ordinary generated backup names this may seem unnecessary.

But learning the robust pattern now is valuable.

---

# 148. Important Filename Limitation

Our temporary file stores one path per line.

That means a filename containing a literal newline would make line-based processing ambiguous.

Our own generated backup directory names:

```text
backup-YYYYMMDD-HHMMSS
```

cannot contain newlines, so this project is safe under its naming contract.

For arbitrary Unix filenames, production scripts often use NUL-delimited processing such as `find -print0` with compatible readers.

This is an example of understanding your input contract instead of assuming all filenames are simple.

# 157. Complete Backup and Cleanup Script

```bash
#!/usr/bin/env bash

source_dir=""
backup_root=""
keep_days=7
dry_run=false
temp_file=""

usage() {
    cat <<EOF
VERIQTA Backup and Cleanup Utility

Usage:
  $0 -s SOURCE -b BACKUP_DIR [options]

Required:
  -s SOURCE       Directory to back up
  -b BACKUP_DIR   Directory where backups are stored

Optional:
  -k DAYS         Keep backups for DAYS days (default: 7)
  -d              Dry-run mode
  -h              Show this help message

Examples:
  $0 -s ./project/data -b ./project/backups
  $0 -s ./project/data -b ./project/backups -k 14
  $0 -s ./project/data -b ./project/backups -k 7 -d

Exit codes:
  0   Success
  1   Operational failure
  2   Invalid command-line usage
EOF
}

parse_args() {

    OPTIND=1

    while getopts ":s:b:k:dh" option; do

        case "$option" in
            s)
                source_dir="$OPTARG"
                ;;

            b)
                backup_root="$OPTARG"
                ;;

            k)
                keep_days="$OPTARG"
                ;;

            d)
                dry_run=true
                ;;

            h)
                usage
                exit 0
                ;;

            :)
                printf 'ERROR: option -%s requires a value\n' "$OPTARG" >&2
                return 2
                ;;

            \?)
                printf 'ERROR: invalid option: -%s\n' "$OPTARG" >&2
                return 2
                ;;
        esac

    done

    shift "$((OPTIND - 1))"

    if (( $# > 0 )); then
        printf 'ERROR: unexpected argument: %s\n' "$1" >&2
        return 2
    fi

    return 0
}

validate_source() {

    if [[ -z "$source_dir" ]]; then
        printf 'ERROR: source directory is required\n' >&2
        return 2
    fi

    if [[ ! -d "$source_dir" ]]; then
        printf 'ERROR: source directory does not exist: %s\n' \
            "$source_dir" >&2
        return 2
    fi

    if [[ ! -r "$source_dir" ]]; then
        printf 'ERROR: source directory is not readable: %s\n' \
            "$source_dir" >&2
        return 1
    fi

    return 0
}

validate_backup_root() {

    if [[ -z "$backup_root" ]]; then
        printf 'ERROR: backup directory is required\n' >&2
        return 2
    fi

    if [[ -e "$backup_root" && ! -d "$backup_root" ]]; then
        printf 'ERROR: backup path exists but is not a directory: %s\n' \
            "$backup_root" >&2
        return 2
    fi

    return 0
}

validate_keep_days() {

    if [[ ! "$keep_days" =~ ^[0-9]+$ ]]; then
        printf 'ERROR: keep days must be a non-negative integer: %s\n' \
            "$keep_days" >&2
        return 2
    fi

    return 0
}

prepare_backup_root() {

    if [[ "$dry_run" == "true" ]]; then

        if [[ ! -d "$backup_root" ]]; then
            printf 'DRY RUN: would create backup directory: %s\n' \
                "$backup_root"
        fi

        return 0
    fi

    if ! mkdir -p "$backup_root"; then
        printf 'ERROR: failed to create backup directory: %s\n' \
            "$backup_root" >&2
        return 1
    fi

    if [[ ! -d "$backup_root" ]]; then
        printf 'ERROR: backup directory verification failed\n' >&2
        return 1
    fi

    if [[ ! -w "$backup_root" ]]; then
        printf 'ERROR: backup directory is not writable: %s\n' \
            "$backup_root" >&2
        return 1
    fi

    return 0
}

create_temp_file() {

    temp_file=$(mktemp) || {
        printf 'ERROR: failed to create temporary file\n' >&2
        return 1
    }

    return 0
}

cleanup_temp() {

    if [[ -n "$temp_file" && -f "$temp_file" ]]; then
        rm -f -- "$temp_file"
    fi
}

create_backup() {
    local timestamp
    local backup_dir

    timestamp=$(date '+%Y%m%d-%H%M%S') || {
        printf 'ERROR: failed to generate timestamp\n' >&2
        return 1
    }

    backup_dir="$backup_root/backup-$timestamp"

    if [[ "$dry_run" == "true" ]]; then
        printf 'DRY RUN: would copy %s to %s\n' \
            "$source_dir" "$backup_dir"
        return 0
    fi

    if ! mkdir "$backup_dir"; then
        printf 'ERROR: failed to create backup destination: %s\n' \
            "$backup_dir" >&2
        return 1
    fi

    if ! cp -a "$source_dir"/. "$backup_dir"/; then
        printf 'ERROR: failed to copy source data\n' >&2
        return 1
    fi

    if [[ ! -d "$backup_dir" ]]; then
        printf 'ERROR: backup verification failed: %s\n' \
            "$backup_dir" >&2
        return 1
    fi

    printf 'Backup created: %s\n' "$backup_dir"

    printf 'Backup size: '
    du -sh "$backup_dir" 2>/dev/null || printf 'unavailable\n'

    return 0
}

show_disk_usage() {

    printf '\nBackup root usage:\n'
    du -sh "$backup_root" 2>/dev/null || true

    printf '\nFilesystem usage:\n'
    df -h "$backup_root" 2>/dev/null || true
}

cleanup_old_backups() {

    if [[ ! -d "$backup_root" ]]; then

        if [[ "$dry_run" == "true" ]]; then
            printf 'DRY RUN: backup root does not exist yet; no old backups to inspect.\n'
            return 0
        fi

        printf 'ERROR: backup root does not exist: %s\n' \
            "$backup_root" >&2
        return 1
    fi

    if ! find "$backup_root" \
        -mindepth 1 \
        -maxdepth 1 \
        -type d \
        -name 'backup-*' \
        -mtime "+$keep_days" \
        -print > "$temp_file"; then

        printf 'ERROR: failed to inspect old backups\n' >&2
        return 1
    fi

    while IFS= read -r old_backup; do

        [[ -n "$old_backup" ]] || continue

        case "$old_backup" in
            "$backup_root"/backup-*)
                ;;
            *)
                printf 'ERROR: refusing unexpected cleanup target: %s\n' \
                    "$old_backup" >&2
                return 1
                ;;
        esac

        if [[ "$dry_run" == "true" ]]; then
            printf 'DRY RUN: would remove old backup: %s\n' \
                "$old_backup"
            continue
        fi

        printf 'Removing old backup: %s\n' "$old_backup"

        if ! rm -rf -- "$old_backup"; then
            printf 'ERROR: failed to remove backup: %s\n' \
                "$old_backup" >&2
            return 1
        fi

    done < "$temp_file"

    return 0
}

main() {
    local status

    parse_args "$@"
    status=$?

    if (( status != 0 )); then
        usage >&2
        return "$status"
    fi

    validate_source
    status=$?

    if (( status != 0 )); then
        return "$status"
    fi

    validate_backup_root
    status=$?

    if (( status != 0 )); then
        return "$status"
    fi

    validate_keep_days
    status=$?

    if (( status != 0 )); then
        return "$status"
    fi

    if ! prepare_backup_root; then
        return 1
    fi

    if ! create_temp_file; then
        return 1
    fi

    if ! create_backup; then
        return 1
    fi

    if [[ -d "$backup_root" ]]; then
        show_disk_usage
    fi

    if ! cleanup_old_backups; then
        return 1
    fi

    printf '\nBackup and cleanup operation completed successfully.\n'

    return 0
}

trap cleanup_temp EXIT

main "$@"
status=$?

exit "$status"
```

# 165. Production Improvement: Source Inside Backup Root

There is another dangerous configuration.

Imagine:

```text
source_dir = /data
backup_root = /data/backups
```

The backup destination exists inside the source tree.

Depending on the copy strategy, this can create undesirable recursion, backup-of-backup growth, or unexpected data inclusion.

A production backup tool should detect path relationships before copying.

For this beginner project, use separate source and backup locations.

Remember:

> A path can be individually valid while the relationship between two paths is unsafe.

---

# 166. Production Improvement: Canonical Paths

Paths can be written in different ways:

```text
./data
/home/ann/project/data
/home/ann/project/./data
```

They may refer to the same place.

Production safety checks often normalize or canonicalize paths before comparing them.

Tools such as:

```bash
realpath
```

or:

```bash
readlink
```

may help on supported systems.

Do not build high-risk path validation purely from string appearance if canonical path relationships matter.

---

# 167. Production Improvement: Symlinks

A symbolic link can make path reasoning more complicated.

Example:

```text
current -> /srv/releases/v2
```

A path may appear to be inside one directory while ultimately referencing another location.

This is another reason filesystem security is deeper than:

```bash
[[ -e "$path" ]]
```

For ordinary beginner scripts, recognize symlinks.

For security-sensitive deletion, investigate them deliberately.

# 168. Production Improvement: Backups Need Restore Testing

A backup that has never been restored is only assumed to work.

A real operational process should periodically test:

```text
Can the backup be read?

Are expected files present?

Are permissions correct?

Can the application restore from it?

Is the restored data valid?
```

Backup success should ultimately mean recoverability, not merely:

```text
cp returned 0
```


Then inspect the path.

# 170. Common Beginner Mistake: Confusing Relative and Absolute Paths

You expect:

```text
project/config.yaml
```

to work everywhere.

It does not.

That is relative to the current directory.

Use an absolute path when location must not depend on where the user launched the script.

# 171. Common Beginner Mistake: Ignoring Failed `cd`

Dangerous:

```bash
cd "$directory"
rm -rf build
```

Safer:

```bash
cd "$directory" || {
    printf 'ERROR: cannot enter %s\n' "$directory" >&2
    exit 1
}
```

Then perform the operation.

# 172. Common Beginner Mistake: Using `rm -rf` for Everything

If removing one known file:

```bash
rm -- "$file"
```

is clearer.

If removing an empty directory:

```bash
rmdir "$directory"
```

may be more appropriate.

Use recursive force only when recursion and force are actually required.

# 173. Common Beginner Mistake: Assuming `*` Includes Hidden Files

It usually does not.

This can produce incomplete:

* copies
* backups
* loops
* cleanup operations

Always understand the pattern being expanded.

# 174. Common Beginner Mistake: Quoting a Glob You Wanted Expanded

This:

```bash
ls "*.log"
```

asks `ls` for a file literally named:

```text
*.log
```

This:

```bash
ls -- *.log
```

allows Bash to expand matching files.

Know whether the pattern should be interpreted by Bash or passed literally to another program.

# 175. Common Beginner Mistake: Not Quoting Variables

Risky:

```bash
cp $source $destination
```

Better:

```bash
cp "$source" "$destination"
```

A path containing spaces can otherwise become multiple arguments.

# 176. Common Beginner Mistake: Parsing `ls`

Avoid:

```bash
for file in $(ls)
```

File names are data, not formatted `ls` output.

Use direct globbing or appropriate filesystem tools.

# 177. Common Beginner Mistake: Changing Permissions to 777

Beginners sometimes respond to:

```text
Permission denied
```

with:

```bash
chmod 777 file
```

without understanding the problem.

`777` means:

```text
owner  = rwx
group  = rwx
others = rwx
```

This can grant far more access than required.

Instead ask:

```text
Who needs access?

What operation do they need?

Who owns the file?

Which group should have access?

Is execute permission actually necessary?
```

Apply least privilege.

# 178. Common Beginner Mistake: Using `sudo` as a Universal Fix

If:

```bash
cp file /some/path
```

fails, do not immediately prepend:

```bash

```

```bash

```

```bash

```

```bash

```

Understand the permission model first.

Unnecessary root privileges increase risk.

# 179. Common Beginner Mistake: Recursive `chmod` Without Thought

Running:

```bash
chmod -R 777 project
```

is rarely a thoughtful solution.

Directories and files may need different permissions.

Secrets may need stricter access.

Executables may need execute permission while ordinary data files do not.

Recursive permission changes require planning.

# 180. Common Beginner Mistake: Backing Up to the Same Filename

This:

```bash
cp config.yaml config.yaml.bak
```

works once.

Next time, it may overwrite the previous backup.

Timestamped backups provide history:

```bash
timestamp=$(date '+%Y%m%d-%H%M%S')
cp config.yaml "config.yaml.$timestamp.bak"
```

# 181. Common Beginner Mistake: Backup Without Verification

Do not do:

```bash
cp important.db backup.db
rm important.db
```

without checking whether the backup succeeded.

Better:

```bash
if cp important.db backup.db; then
    printf 'Backup completed.\n'
else
    printf 'ERROR: backup failed. Original will not be removed.\n' >&2
    exit 1
fi
```

# 182. Common Beginner Mistake: Deleting During Disk Investigation

If disk space is low, investigate first.

Do not delete logs without understanding:

* whether application still writes to them
* whether retention requirements exist
* whether logs are needed for incident investigation
* whether log rotation is broken
* whether deleting an open file will actually recover expected space immediately
* whether another directory is the real problem

Disk cleanup is an operational decision, not merely an `rm` command.

# 192. What You Should Now Understand

After Part 10, you should understand:

* Linux uses a hierarchical filesystem rooted at `/`
* paths identify files and directories
* absolute paths begin at `/`
* relative paths depend on the current working directory
* `$HOME` identifies the current user's home directory
* `~` commonly represents the home directory interactively
* `pwd` displays the current working directory
* `cd` changes the current directory
* `.` means current directory
* `..` means parent directory
* `cd -` commonly returns to the previous directory
* failed `cd` operations must not be ignored before destructive commands
* `ls` lists directory contents
* `ls -l` shows detailed information
* `ls -a` includes hidden entries
* `mkdir` creates directories
* `mkdir -p` creates required parent directories
* `touch` creates an empty file if it does not exist and can update timestamps
* `cp` copies files
* `cp -r` recursively copies directories
* `cp -a` is useful when preserving filesystem attributes matters
* `mv` moves and renames files/directories
* `rm` deletes files
* `rm -r` recursively deletes directories
* `rm -f` forces removal behavior and should not be added casually
* `rmdir` removes empty directories
* recursive operations multiply both power and risk
* `[[ -e path ]]` checks existence
* `[[ -f path ]]` checks for a regular file
* `[[ -d path ]]` checks for a directory
* `-r`, `-w`, and `-x` test access capabilities
* Linux permissions use read, write, and execute concepts
* permissions apply to owner/user, group, and others
* directory permissions have different practical meaning from file permissions
* numeric permissions use values 4, 2, and 1
* `600` means owner read/write only
* `644` means owner read/write and group/others read
* `755` means owner read/write/execute and group/others read/execute
* `chmod` changes permissions
* symbolic `chmod` can add or remove individual permissions
* recursive `chmod` should not be used blindly
* files have owners and groups
* `chown` changes ownership
* `chgrp` changes group ownership
* ownership changes should follow least privilege
* `stat` displays detailed file metadata
* metadata includes permissions, ownership, size, and timestamps
* `du` measures file/directory disk usage
* `du -sh` provides a human-readable summary
* `df` reports filesystem capacity and availability
* `du` and `df` answer different disk-space questions
* `mktemp` creates safer unique temporary resources
* temporary resources should be cleaned up
* `trap` can help ensure cleanup
* wildcards are patterns used in shell filename expansion
* `*` matches zero or more characters
* `?` matches one character
* bracket expressions match characters from a set/range
* globbing happens before the command receives arguments
* quoted glob patterns generally do not expand
* hidden filenames are normally not matched by `*`
* backup operations must account for hidden files
* `--` can protect filenames beginning with `-` for commands that support it
* deletion variables should be validated
* dangerous deletion roots should be rejected
* cleanup scripts should operate inside tightly controlled directories
* dry-run behavior is valuable for destructive automation
* important files should be backed up before destructive modification
* backup creation must be checked for failure
* backups should ultimately be restore-tested
* loops can process multiple files
* loop variables representing paths should be quoted
* unmatched globs require consideration
* `nullglob` can change Bash's no-match glob behavior
* parsing `ls` output is a poor way to iterate over files
* bulk operations should be previewed before execution
* bulk renaming should detect destination collisions
* filesystem checks do not eliminate the possibility of state changing between check and operation
* the operation's own exit status must also be checked
* filesystem automation should follow Observe → Validate → Preview → Protect → Act → Verify
