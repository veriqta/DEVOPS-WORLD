# Part 18: Bash for Networking, APIs, Remote Servers, and Cloud Operations

Modern infrastructure is rarely limited to one Linux server.

A Bash script may need to:

* check whether another server is reachable
* resolve a hostname through DNS
* verify that a TCP port is listening
* call an HTTP API
* inspect a JSON response
* authenticate using a token
* copy files to another machine
* execute commands over SSH
* synchronize directories between servers
* perform the same check across many hosts
* retry operations when a network connection temporarily fails
* interact with AWS, Azure, Google Cloud, Kubernetes, or another platform through a command-line interface

This is where Bash begins to move from local system administration into infrastructure automation.

In Part 17, you used Bash to inspect and administer a Linux server.

Now you will extend those skills across networks.

By the end of this part, you should understand how Bash can communicate with network services, APIs, remote Linux systems, and cloud command-line tools while handling failures safely.

---

# 1. The Networking Model a Bash User Needs

You do not need to become a network engineer before writing useful networking scripts.

But you do need a mental model of what happens when one machine communicates with another.

Imagine your server wants to call an application API:

```text
Your Bash Script
      |
      v
Hostname
api.example.com
      |
      v
DNS Resolution
      |
      v
IP Address
203.0.113.25
      |
      v
Network Route
      |
      v
TCP Connection
Port 443
      |
      v
HTTPS Request
      |
      v
Application/API
```

Several different things can fail.

For example:

```text
DNS failure
    |
    +--> hostname cannot be resolved

Routing failure
    |
    +--> destination cannot be reached

TCP failure
    |
    +--> port closed/firewall/service unavailable

TLS failure
    |
    +--> certificate or encryption problem

HTTP failure
    |
    +--> server responds with 4xx or 5xx

Application failure
    |
    +--> API responds but application data is wrong
```

This distinction is extremely important in troubleshooting.

A successful `ping` does not prove that an application works.

A successful DNS lookup does not prove that port 443 is open.

A successful TCP connection does not prove that the API returns HTTP 200.

Good infrastructure scripts test the correct layer.

---

# 2. IP Addresses

An IP address identifies an interface on an IP network.

IPv4 addresses commonly look like:

```text
192.168.1.10
10.0.4.25
172.16.8.12
```

IPv6 addresses look different:

```text
2001:db8::10
```

In cloud environments, a server may have multiple addresses.

For example:

```text
EC2 instance

Private IP:
10.0.2.15

Public IP:
203.0.113.40
```

The private address may be used between systems inside a virtual network.

The public address may be reachable from the Internet, depending on routing, firewall, and security rules.

Do not assume that every server has a public IP.

Production infrastructure often intentionally keeps application and database servers private.

---

# 3. Hostnames

Humans usually prefer names over IP addresses.

Instead of:

```text
10.20.4.17
```

you might use:

```text
app01
database01
api.example.com
```

Check the current system hostname with:

```bash
hostname
```

Example output:

```text
web-prod-01
```

You can also use:

```bash
hostnamectl
```

On systems using systemd, this may provide more information.

Example:

```text
 Static hostname: web-prod-01
 Operating System: Ubuntu 24.04 LTS
 Kernel: Linux 6.x
 Architecture: x86-64
```

For scripts that simply need the hostname:

```bash
server_name="$(hostname)"
printf 'Server: %s\n' "$server_name"
```

The command substitution:

```bash
$(hostname)
```

runs `hostname` and stores its stdout in the variable.

---

# 4. DNS

DNS stands for Domain Name System.

DNS translates names such as:

```text
api.example.com
```

into IP addresses.

Conceptually:

```text
api.example.com
      |
      v
DNS resolver
      |
      v
203.0.113.25
```

Without working DNS, many applications appear to have "network problems" even when the network itself is functioning.

---

# 5. Testing DNS with dig

`dig` is one of the most useful DNS troubleshooting commands.

Example:

```bash
dig example.com
```

The output contains several sections.

For scripting, shorter output is often better:

```bash
dig +short example.com
```

Example:

```text
93.184.216.34
```

You can capture the result:

```bash
ip_address="$(dig +short example.com | head -n 1)"
```

Then:

```bash
printf 'Resolved IP: %s\n' "$ip_address"
```

You should validate the result:

```bash
if [[ -z "$ip_address" ]]; then
    printf 'ERROR: DNS resolution failed\n' >&2
    exit 1
fi
```

This is better than assuming the lookup succeeded.

---

# 6. nslookup

Another common DNS utility is:

```bash
nslookup example.com
```

It may display:

```text
Server:         192.168.1.1
Address:        192.168.1.1#53

Name:   example.com
Address: 93.184.216.34
```

`nslookup` is useful for interactive troubleshooting.

For scripts, `dig +short` is often easier to parse.

However, do not assume either tool exists.

A production script can check dependencies:

```bash
if ! command -v dig >/dev/null 2>&1; then
    printf 'ERROR: dig is required\n' >&2
    exit 1
fi
```

# 7. Ports

An IP address identifies a network interface.

A port identifies a service endpoint on that host.

For example:

```text
Server: 10.0.1.20

22    SSH
80    HTTP
443   HTTPS
5432  PostgreSQL
3306  MySQL
6379  Redis
```

Think of it like:

```text
IP address = building
Port       = specific door
```

The analogy is not technically perfect, but it is useful for beginners.

A server being reachable does not mean every port is reachable.

For example:

```text
10.0.1.20 responds to network traffic
```

but:

```text
10.0.1.20:443
```

may still fail because:

* nothing is listening on port 443
* a host firewall blocks it
* a cloud firewall/security group blocks it
* routing is wrong
* the service crashed
* the service is bound only to localhost
* a network policy blocks traffic

# 8. TCP Basics

TCP stands for Transmission Control Protocol.

Many important services use TCP.

Examples include:

```text
SSH
HTTP/HTTPS
PostgreSQL
MySQL
Redis
many internal APIs
```

Before data is exchanged, TCP normally establishes a connection.

Simplified:

```text
Client                    Server
  |                         |
  | ---- SYN -------------> |
  | <--- SYN-ACK ---------- |
  | ---- ACK -------------> |
  |                         |
  | Connection established  |
```

This is called the TCP three-way handshake.

For Bash automation, the important question is often:

> Can this machine establish a TCP connection to that host and port?

That is different from:

> Does the application itself work correctly?

---

# 9. Testing Connectivity with ping

`ping` sends ICMP echo requests.

Example:

```bash
ping example.com
```

On Linux, it normally continues until interrupted.

For automation, limit the number of packets:

```bash
ping -c 3 example.com
```

`-c 3` means:

```text
send 3 echo requests
```

You can suppress normal output:

```bash
ping -c 1 example.com >/dev/null 2>&1
```

Then test the exit status:

```bash
if ping -c 1 example.com >/dev/null 2>&1; then
    printf 'Host responded to ping\n'
else
    printf 'Ping failed\n'
fi
```

But there is an important warning.

## Ping failure does not necessarily mean the server is down

ICMP may be intentionally blocked.

A production server might reject ping while still serving HTTPS perfectly.

Therefore:

```text
ping failure
```

does not automatically mean:

```text
server unavailable
```

If your real requirement is HTTPS availability, test HTTPS.

If your requirement is SSH, test SSH or TCP port 22.

Always test the service you actually care about.

---

# 10. The ip Command

Modern Linux systems commonly use the `ip` command for network inspection.

Display addresses:

```bash
ip address
```

Short form:

```bash
ip addr
```

Even shorter:

```bash
ip a
```

Display routes:

```bash
ip route
```

Example:

```text
default via 10.0.1.1 dev eth0
10.0.1.0/24 dev eth0 proto kernel scope link src 10.0.1.20
```

This tells you how the system decides where packets should go.

Display a specific interface:

```bash
ip addr show eth0
```

Interfaces may have names such as:

```text
eth0
ens5
ens33
enp0s3
```

Do not hard-code `eth0` unless your environment guarantees it.

---

# 11. Finding the Route to a Destination

A useful troubleshooting command is:

```bash
ip route get 8.8.8.8
```

The system may show something like:

```text
8.8.8.8 via 10.0.1.1 dev eth0 src 10.0.1.20
```

This can help answer:

* which interface will be used?
* which gateway will be used?
* which source address will be selected?

This is often more useful than blindly restarting networking.

---

# 12. Inspecting Listening Ports with ss

`ss` displays socket information.

A very useful command is:

```bash
ss -lnt
```

The options mean approximately:

```text
-l   listening sockets
-n   numeric addresses and ports
-t   TCP sockets
```

Example:

```text
LISTEN 0 4096 0.0.0.0:22
LISTEN 0 511  0.0.0.0:80
```

To include process information when permissions allow:

```bash
ss -lntp
```

Suppose your web application should listen on port 8080.

You can inspect:

```bash
ss -lnt | grep ':8080'
```

A more careful script could be:

```bash
if ss -lnt | grep -q ':8080 '; then
    printf 'Port 8080 appears to be listening\n'
else
    printf 'Port 8080 was not found in listening TCP sockets\n'
fi
```

For serious production checks, remember that text parsing should account for IPv4/IPv6 and exact matching.

---

# 13. Listening Address Matters

Suppose `ss` shows:

```text
127.0.0.1:8080
```

That usually means the application listens only on the local loopback interface.

Another machine may not be able to connect.

Compare:

```text
127.0.0.1:8080
```

with:

```text
0.0.0.0:8080
```

The second commonly indicates listening on all IPv4 interfaces.

For IPv6, you may see:

```text
[::]:8080
```

Binding behavior can vary by operating system and application configuration, so verify rather than making assumptions.

This explains an important production problem:

```text
Application is running
        |
        v
Port is listening
        |
        v
But only on localhost
        |
        v
Remote clients cannot connect
```

# 14. Networking Troubleshooting by Layer

Suppose:

```text
https://api.example.com
```

does not work.

Do not immediately restart the application.

Investigate systematically.

```text
1. Resolve hostname
        |
        v
2. Check route/connectivity
        |
        v
3. Check TCP connection
        |
        v
4. Check TLS/HTTPS
        |
        v
5. Check HTTP status
        |
        v
6. Check response
        |
        v
7. Check application logs
```

For example:

```bash
dig +short api.example.com
```

Then:

```bash
ip route get <resolved-ip>
```

Then test the actual service:

```bash
curl -v https://api.example.com/
```

This layered approach produces evidence instead of guesses.

# 15. curl

`curl` is one of the most important commands for DevOps and infrastructure engineers.

It transfers data using network protocols.

It is heavily used for:

* HTTP
* HTTPS
* APIs
* health checks
* downloads
* authentication tests
* debugging headers
* service-to-service testing

Basic example:

```bash
curl https://example.com
```

By default, the response body is written to stdout.

That means it can be:

* displayed
* redirected
* piped
* captured in a variable
* processed by another command

---

# 16. HTTP Basics

HTTP is an application-layer protocol used for communication between clients and servers.

Simplified:

```text
Client
  |
  | HTTP request
  v
Server
  |
  | HTTP response
  v
Client
```

A request may contain:

```text
method
URL
headers
body
```

A response may contain:

```text
status code
headers
body
```

Understanding these components is essential when scripting APIs.

---

# 17. HTTP Methods

Common HTTP methods include:

```text
GET
POST
PUT
PATCH
DELETE
HEAD
```

Typical meaning:

| Method | Common purpose                                |
| ------ | --------------------------------------------- |
| GET    | Retrieve data                                 |
| POST   | Create or submit data                         |
| PUT    | Replace/update a resource                     |
| PATCH  | Partially update a resource                   |
| DELETE | Remove a resource                             |
| HEAD   | Retrieve headers without normal response body |

These are conventions.

The API itself determines exact behavior.

---

# 18. Making a GET Request

A normal curl request is usually GET:

```bash
curl https://api.example.com/status
```

You can explicitly specify it:

```bash
curl -X GET https://api.example.com/status
```

But `-X GET` is usually unnecessary because GET is already the default for a normal request.

Avoid unnecessary options when the default behavior is clear.

---

# 19. HTTP Status Codes

HTTP responses include status codes.

Important groups are:

```text
1xx   informational
2xx   success
3xx   redirection
4xx   client-side request problem
5xx   server-side problem
```

Common examples:

```text
200 OK
201 Created
204 No Content
301 Moved Permanently
302 Found
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
429 Too Many Requests
500 Internal Server Error
502 Bad Gateway
503 Service Unavailable
504 Gateway Timeout
```

Do not treat every HTTP response as success.

An API can return a valid HTTP response containing:

```text
500
```

The network worked.

The application did not.

---

# 20. Retrieving Only the HTTP Status Code

With curl:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://example.com
```

Important options:

```text
-s
```

silent mode.

```text
-o /dev/null
```

discard the response body.

```text
-w
```

write formatted information after the request.

```text
%{http_code}
```

the HTTP response status code.

Capture it:

```bash
status_code="$(curl -s -o /dev/null -w '%{http_code}' https://example.com)"
```

Then:

```bash
if [[ "$status_code" == "200" ]]; then
    printf 'Service healthy\n'
else
    printf 'Unexpected HTTP status: %s\n' "$status_code"
fi
```

But there is another problem.

What if curl cannot connect at all?

You must distinguish:

```text
curl execution failure
```

from:

```text
HTTP non-200 response
```

---

# 21. Checking curl Itself

Example:

```bash
response_file="$(mktemp)"

if ! curl -sS -o "$response_file" https://example.com; then
    printf 'ERROR: curl request failed\n' >&2
    rm -f -- "$response_file"
    exit 1
fi
```

`-sS` combines:

```text
-s   silent progress output
-S   still show errors
```

This is often useful in scripts.

Remember:

```text
HTTP 404
```

does not necessarily cause curl itself to fail.

The HTTP server successfully responded.

If you want curl to treat HTTP error responses as failures, investigate options such as:

```bash
--fail
```

or:

```bash
--fail-with-body
```

depending on your installed curl version and your desired behavior.

Always understand what "failure" means for your script.

---

# 22. Headers

HTTP headers carry metadata.

Examples include:

```text
Content-Type
Authorization
Accept
User-Agent
Cache-Control
```

Inspect response headers:

```bash
curl -I https://example.com
```

`-I` requests headers using HTTP HEAD where supported.

For detailed debugging:

```bash
curl -v https://example.com
```

`-v` means verbose.

It may show:

* DNS information
* connection attempts
* TLS negotiation
* request headers
* response headers

Be careful.

Verbose output can expose sensitive headers such as authentication information.

Do not blindly save verbose output to shared logs.

---

# 23. Sending Request Headers

Use:

```bash
-H
```

Example:

```bash
curl \
    -H 'Accept: application/json' \
    https://api.example.com/status
```

Multiple headers can be supplied:

```bash
curl \
    -H 'Accept: application/json' \
    -H 'User-Agent: infrastructure-check/1.0' \
    https://api.example.com/status
```

# 24. Sending JSON with POST

Suppose an API accepts:

```json
{
  "server": "web01",
  "status": "healthy"
}
```

You might send:

```bash
curl \
    -X POST \
    -H 'Content-Type: application/json' \
    -d '{"server":"web01","status":"healthy"}' \
    https://api.example.com/report
```

`-d` supplies request data.

When `-d` is used, curl normally uses POST automatically, so explicitly writing:

```bash
-X POST
```

is often optional.

For larger payloads, avoid building complicated JSON manually in shell strings.

Use `jq`.

---

# 25. JSON

JSON stands for JavaScript Object Notation.

Despite the name, it is widely used independently of JavaScript.

Example:

```json
{
  "service": "payments",
  "status": "healthy",
  "instances": 4
}
```

JSON contains structures such as:

* objects
* arrays
* strings
* numbers
* booleans
* null

APIs frequently return JSON.

Trying to parse JSON using `grep`, `cut`, or fragile string manipulation is usually a mistake.

Use a JSON-aware tool.

---

# 26. jq

`jq` is a command-line JSON processor.

Example input:

```json
{
  "service": "payments",
  "status": "healthy",
  "instances": 4
}
```

Pipe it into:

```bash
jq '.'
```

This parses and formats the JSON.

Extract one field:

```bash
jq '.status'
```

Output:

```text
"healthy"
```

The quotes are JSON string syntax.

For raw text:

```bash
jq -r '.status'
```

Output:

```text
healthy
```

That is usually easier for Bash variables.

---

# 27. curl and jq Together

Example:

```bash
curl -sS https://api.example.com/status | jq '.'
```

Extract a field:

```bash
status="$(
    curl -sS https://api.example.com/status |
    jq -r '.status'
)"
```

Then:

```bash
if [[ "$status" == "healthy" ]]; then
    printf 'API reports healthy\n'
else
    printf 'API reports status: %s\n' "$status"
fi
```

But this version has a reliability problem.

If curl fails, the pipeline behavior must be handled correctly.

Part 14 introduced:

```bash
set -o pipefail
```

With `pipefail`, a pipeline can report failure when an earlier command fails.

For critical scripts:

```bash
set -o pipefail
```

can help prevent network failures from being hidden by later commands.

---

# 28. Validating JSON

Suppose:

```bash
response="$(curl -sS https://api.example.com/status)"
```

Before assuming it is JSON:

```bash
if ! jq -e . >/dev/null 2>&1 <<< "$response"; then
    printf 'ERROR: API returned invalid JSON\n' >&2
    exit 1
fi
```

Then extract:

```bash
status="$(jq -r '.status // empty' <<< "$response")"
```

The:

```text
// empty
```

expression prevents a missing or null field from becoming an unexpected literal value for this use case.

Then validate:

```bash
if [[ -z "$status" ]]; then
    printf 'ERROR: status field missing\n' >&2
    exit 1
fi
```

This is defensive API scripting.

---

# 29. Creating JSON Safely with jq

Suppose:

```bash
server_name="$(hostname)"
service_status="healthy"
```

Avoid:

```bash
payload="{\"server\":\"$server_name\",\"status\":\"$service_status\"}"
```

It may work for simple values, but becomes fragile when values contain quotes, newlines, backslashes, or other special characters.

Instead:

```bash
payload="$(
    jq -n \
        --arg server "$server_name" \
        --arg status "$service_status" \
        '{
            server: $server,
            status: $status
        }'
)"
```

Now `jq` performs proper JSON escaping.

Display:

```bash
printf '%s\n' "$payload"
```

This is much safer.

# 30. wget

`wget` is another network download tool.

Example:

```bash
wget https://example.com/file.tar.gz
```

It commonly downloads the resource into a file.

Specify output filename:

```bash
wget -O package.tar.gz https://example.com/file.tar.gz
```

Quiet mode:

```bash
wget -q -O package.tar.gz https://example.com/file.tar.gz
```

In scripts, check the status:

```bash
if wget -q -O package.tar.gz "$url"; then
    printf 'Download successful\n'
else
    printf 'Download failed\n' >&2
fi
```

# 31. curl vs wget

Both can download network resources.

A simplified distinction:

```text
curl
    Excellent for APIs, HTTP inspection,
    request construction and data transfer.

wget
    Commonly convenient for downloading files
    and recursive retrieval use cases.
```

This is not an absolute rule.

Both tools have many capabilities.

For DevOps API automation, `curl` is especially common.

# 32. Authentication Tokens

Many APIs require authentication.

A common pattern is:

```text
Authorization: Bearer TOKEN
```

For example:

```bash
curl \
    -H "Authorization: Bearer $API_TOKEN" \
    https://api.example.com/resources
```

The token proves that the caller is authorized according to the API's authentication system.

Tokens must be treated as secrets.

---

# 33. Do Not Hard-Code Secrets

Bad:

```bash
API_TOKEN="abc123-real-secret-token"
```

inside a script committed to Git.

Why?

Because the secret may leak through:

* source control
* pull requests
* backups
* logs
* copied scripts
* screenshots
* build artifacts

A better pattern is to receive the secret from the environment:

```bash
: "${API_TOKEN:?API_TOKEN must be set}"
```

Then:

```bash
curl \
    -H "Authorization: Bearer $API_TOKEN" \
    https://api.example.com/resources
```

The script does not contain the secret itself.

But environment variables are not magically secure.

Depending on the environment, they may still be exposed through:

* debugging
* process inspection
* CI/CD configuration
* accidental logging
* crash reports
* child processes

Use your platform's secret-management mechanism when available.

---

# 34. Avoid Secrets in Command History

Typing:

```bash
curl -H 'Authorization: Bearer my-real-secret-token' ...
```

may place the token in shell history.

Safer approaches include retrieving secrets from:

* CI/CD secret stores
* cloud secret managers
* protected files
* environment injection
* dedicated credential helpers

Do not print secrets:

```bash
printf 'Token: %s\n' "$API_TOKEN"
```

Avoid debugging modes around secret-bearing commands.

For example:

```bash
set -x
```

can expose expanded commands and variables.

If tracing is enabled, disable it before sensitive operations:

```bash
set +x
```

But the better design is to ensure secrets are not unnecessarily expanded into debug output at all.

---

# 35. HTTP Authentication Failure

Suppose the API returns:

```text
401 Unauthorized
```

Possible causes:

* token missing
* token expired
* token malformed
* wrong authentication scheme
* wrong audience/scope
* credential not accepted

A:

```text
403 Forbidden
```

often means the server understood the identity but refuses the requested action.

Do not automatically interpret every 403 exactly the same way. Authorization systems vary.

Troubleshooting should inspect the API's documented authentication model.

---

# 36. Capturing HTTP Body and Status Separately

Production scripts often need both.

One approach is to write the body to a temporary file:

```bash
response_file="$(mktemp)"

http_code="$(
    curl \
        -sS \
        -o "$response_file" \
        -w '%{http_code}' \
        https://api.example.com/status
)"
curl_status=$?
```

Now you have:

```text
curl_status
```

for the command itself,

```text
http_code
```

for HTTP,

and:

```bash
cat "$response_file"
```

for the body.

Always clean temporary files.

For example:

```bash
cleanup() {
    rm -f -- "$response_file"
}

trap cleanup EXIT
```

This is much more reliable than treating networking as a single success/failure condition.

# 37. Timeouts

A network operation can hang longer than your automation should tolerate.

Automation needs time boundaries.

With curl:

```bash
curl --connect-timeout 5 https://example.com
```

This limits connection establishment time.

You can also limit the entire operation:

```bash
curl \
    --connect-timeout 5 \
    --max-time 15 \
    https://example.com
```

Conceptually:

```text
connect timeout
    |
    +--> how long to establish connection

max time
    |
    +--> maximum total operation duration
```

Timeout values should reflect your environment.

A health check might need aggressive limits.

A large file transfer may legitimately need much longer.

---

# 38. Why Timeouts Matter

Consider:

```text
CI/CD Pipeline
      |
      v
Bash deployment script
      |
      v
API call hangs
      |
      v
Job waits indefinitely
```

This can consume:

* CI runners
* deployment windows
* automation workers
* operator attention

Reliable automation should decide how long it is willing to wait.

---

# 39. Retry Logic

Networks experience temporary failures.

Examples:

* brief DNS failure
* transient connection reset
* temporary 503
* rate limiting
* service startup delay
* load balancer target transition

Sometimes retrying is appropriate.

But retries must be controlled.

Do not write:

```bash
while true; do
    curl "$url"
done
```

That can create an infinite request storm.

Use:

* maximum attempts
* delay
* timeout
* clear logging
* final failure status

---

# 40. Basic Retry Function

Example:

```bash
retry_curl() {
    local url="$1"
    local max_attempts="${2:-3}"
    local delay="${3:-2}"
    local attempt=1

    while (( attempt <= max_attempts )); do
        printf 'Attempt %d/%d: %s\n' \
            "$attempt" "$max_attempts" "$url"

        if curl \
            -fsS \
            --connect-timeout 5 \
            --max-time 15 \
            "$url"
        then
            return 0
        fi

        if (( attempt < max_attempts )); then
            sleep "$delay"
        fi

        ((attempt++))
    done

    printf 'ERROR: Request failed after %d attempts\n' \
        "$max_attempts" >&2

    return 1
}
```

Call:

```bash
retry_curl "https://example.com" 3 2
```

Here:

```text
3 = maximum attempts
2 = seconds between attempts
```

---

# 41. Exponential Backoff

A more advanced retry strategy increases the delay after each failure.

For example:

```text
Attempt 1
wait 1 second

Attempt 2
wait 2 seconds

Attempt 3
wait 4 seconds

Attempt 4
wait 8 seconds
```

Example:

```bash
retry_with_backoff() {
    local url="$1"
    local max_attempts="${2:-4}"
    local attempt=1
    local delay=1

    while (( attempt <= max_attempts )); do
        if curl \
            -fsS \
            --connect-timeout 5 \
            --max-time 15 \
            "$url"
        then
            return 0
        fi

        if (( attempt == max_attempts )); then
            break
        fi

        printf 'Attempt %d failed. Retrying in %d seconds...\n' \
            "$attempt" "$delay" >&2

        sleep "$delay"

        delay=$((delay * 2))
        ((attempt++))
    done

    printf 'ERROR: All attempts failed\n' >&2
    return 1
}
```

This reduces aggressive repeated requests.

Production systems may also use:

* maximum backoff
* random jitter
* retry-after headers
* different rules for different failures

---

# 42. Not Every Failure Should Be Retried

This is extremely important.

Suppose an API returns:

```text
401 Unauthorized
```

Retrying the same invalid credential ten times probably accomplishes nothing.

Similarly:

```text
400 Bad Request
```

may indicate that your request itself is wrong.

Failures such as:

```text
429 Too Many Requests
503 Service Unavailable
temporary connection timeout
```

may be more reasonable retry candidates.

Retry policy should depend on the operation and failure.

Blind retries can:

* increase outages
* overload services
* hide configuration problems
* duplicate operations
* trigger rate limits

---

# 43. Idempotency and API Retries

Imagine this request:

```text
POST /payments
```

The server processes the payment, but the network connection breaks before your script receives the response.

Your script sees failure and retries.

The result could be:

```text
payment #1
payment #2
```

This demonstrates why retry safety matters.

Before retrying state-changing API operations, understand whether the operation is idempotent or whether the API supports an idempotency mechanism.

For infrastructure automation:

```text
GET health status
```

is usually much safer to retry than an operation that creates, deletes, or modifies resources.

# 44. SSH

SSH stands for Secure Shell.

It provides encrypted remote access to systems.

Basic syntax:

```bash
ssh user@server
```

Example:

```bash
ssh admin@10.0.1.20
```

Or:

```bash
ssh ubuntu@app01.example.com
```

SSH is heavily used for:

* remote administration
* command execution
* automation
* file transfer
* tunneling
* configuration tasks

---

# 45. SSH Host Verification

The first time you connect to a server, SSH may ask whether you trust its host key.

This protects against connecting to an unexpected machine.

You may see something like:

```text
The authenticity of host ... can't be established.
Are you sure you want to continue connecting?
```

Do not teach yourself to blindly bypass host-key verification.

A production automation system should have a controlled method for trusting and verifying hosts.

Avoid insecure patterns such as globally disabling host-key checking simply because automation becomes easier.

Convenience is not a substitute for authentication.

---

# 46. SSH Keys

Passwordless automation commonly uses SSH key pairs.

A key pair includes:

```text
private key
public key
```

Conceptually:

```text
Client
  |
  | owns private key
  |
  v
SSH authentication
  |
  v
Server
  |
  | recognizes corresponding public key
```

The private key must remain protected.

Never send your private key to someone simply because they need to give you access.

The public key is the part intended to be installed on authorized systems.

---

# 47. Generating an SSH Key

A modern example:

```bash
ssh-keygen -t ed25519
```

The command asks where to store the key and whether to use a passphrase.

Common files may be:

```text
~/.ssh/id_ed25519
~/.ssh/id_ed25519.pub
```

The first is private.

The second is public.

Do not expose:

```text
id_ed25519
```

Treat it as a credential.

---

# 48. SSH Private-Key Permissions

SSH may reject a private key that is accessible too broadly.

A commonly required permission is:

```bash
chmod 600 ~/.ssh/id_ed25519
```

This means:

```text
owner: read + write
group: none
others: none
```

For a downloaded cloud key, you may sometimes see:

```bash
chmod 400 key.pem
```

The exact acceptable permissions depend on the SSH implementation and environment, but private keys should never be broadly readable.

---

# 49. Connecting with a Specific SSH Key

Example:

```bash
ssh -i ~/.ssh/production.pem ubuntu@server.example.com
```

`-i` specifies the identity file.

Quote paths when appropriate:

```bash
ssh -i "$HOME/.ssh/production.pem" ubuntu@server.example.com
```

---

# 50. Remote Command Execution

SSH can execute a command without opening a normal interactive shell.

Example:

```bash
ssh ubuntu@server.example.com 'hostname'
```

The command:

```text
hostname
```

runs remotely.

You could run:

```bash
ssh ubuntu@server.example.com 'uptime'
```

Or:

```bash
ssh ubuntu@server.example.com 'df -h'
```

This is the foundation of simple remote Bash automation.

---

# 51. Local vs Remote Expansion

This concept causes many Bash mistakes.

Compare:

```bash
ssh server "echo $HOME"
```

with:

```bash
ssh server 'echo $HOME'
```

In the first command, your local shell may expand:

```text
$HOME
```

before SSH receives the command.

In the second, the remote shell receives:

```text
echo $HOME
```

and expands it remotely.

Conceptually:

```text
Double quotes
    |
    +--> local expansion can occur

Single quotes
    |
    +--> literal text sent through local shell
         then remote shell may expand it
```

Remote quoting can become complex very quickly.

For substantial remote logic, it may be cleaner to deploy a script and execute it remotely rather than constructing enormous nested SSH command strings.

---

# 52. Checking SSH Command Status

Example:

```bash
if ssh server.example.com 'systemctl is-active nginx'; then
    printf 'Remote check succeeded\n'
else
    printf 'Remote check failed\n' >&2
fi
```

The local `ssh` command returns a status related to the SSH operation and, when a remote command executes normally, the remote command's exit status.

This makes SSH useful in automation.

But you still need to distinguish:

```text
SSH connection failed
```

from:

```text
SSH worked, remote command failed
```

For sophisticated automation, logs and specific diagnostics become important.

---

# 53. Non-Interactive SSH Automation

Automation should not unexpectedly stop waiting for user input.

Useful SSH options include:

```bash
-o BatchMode=yes
```

This tells SSH not to prompt for password-style interactive authentication.

Example:

```bash
ssh \
    -o BatchMode=yes \
    server.example.com \
    'hostname'
```

If key authentication is unavailable, the command fails instead of waiting for a human.

This is useful for CI/CD and unattended scripts.

---

# 54. SSH Connection Timeout

Use:

```bash
-o ConnectTimeout=5
```

Example:

```bash
ssh \
    -o BatchMode=yes \
    -o ConnectTimeout=5 \
    ubuntu@server.example.com \
    'hostname'
```

Now the script does not wait indefinitely just to establish the SSH connection.

---

# 55. scp

`scp` securely copies files using SSH.

Local to remote:

```bash
scp file.txt user@server:/tmp/
```

Remote to local:

```bash
scp user@server:/var/log/app.log .
```

Using a key:

```bash
scp \
    -i "$HOME/.ssh/production.pem" \
    report.txt \
    ubuntu@server:/tmp/
```

Copy a directory recursively:

```bash
scp -r config/ user@server:/opt/application/
```

Always confirm destination paths before automating file deployment.

---

# 56. rsync

`rsync` is powerful for synchronizing files and directories.

Example:

```bash
rsync -av source/ user@server:/opt/application/
```

Common options:

```text
-a   archive mode
-v   verbose
```

Archive mode preserves useful metadata and recursively transfers directory contents.

The trailing slash matters.

Compare:

```bash
rsync -av source/ destination/
```

with:

```bash
rsync -av source destination/
```

They can produce different directory structures.

Always test synchronization behavior before using it on production paths.

---

# 57. rsync Dry Run

One of the most useful safety features is:

```bash
--dry-run
```

Example:

```bash
rsync -av --dry-run source/ user@server:/opt/application/
```

This previews intended changes.

For risky synchronization tasks, preview first.

Especially be careful with:

```bash
--delete
```

because it can remove destination files that do not exist in the source.

Never add destructive synchronization options casually.

---

# 58. rsync with SSH Options

You can specify the SSH command:

```bash
rsync \
    -av \
    -e "ssh -i $HOME/.ssh/production.pem" \
    source/ \
    ubuntu@server:/opt/application/
```

For complex automation, quoting SSH options carefully becomes important.

You can also centralize SSH settings in:

```text
~/.ssh/config
```

when appropriate.

---

# 59. SSH Configuration

Instead of repeatedly writing:

```bash
ssh -i ~/.ssh/production.pem ubuntu@203.0.113.20
```

you can configure an SSH host alias.

Example:

```text
Host production-web
    HostName 203.0.113.20
    User ubuntu
    IdentityFile ~/.ssh/production.pem
```

Then:

```bash
ssh production-web
```

Scripts can also use:

```bash
ssh production-web 'hostname'
```

This can improve maintainability.

But automation still depends on the configuration existing on the machine where the script runs.

Document that dependency.

---

# 60. Looping Across Multiple Servers

Suppose:

```bash
servers=(
    "web01.example.com"
    "web02.example.com"
    "web03.example.com"
)
```

You can loop:

```bash
for server in "${servers[@]}"; do
    printf 'Checking %s...\n' "$server"

    ssh \
        -o BatchMode=yes \
        -o ConnectTimeout=5 \
        "$server" \
        'hostname && uptime'
done
```

This allows one script to inspect many systems.

---

# 61. Do Not Stop Understanding Failure

A naive loop:

```bash
for server in "${servers[@]}"; do
    ssh "$server" 'uptime'
done
```

may print errors, but the script does not clearly summarize which systems failed.

A better approach tracks results.

```bash
failed_servers=()

for server in "${servers[@]}"; do
    if ssh \
        -o BatchMode=yes \
        -o ConnectTimeout=5 \
        "$server" \
        'uptime'
    then
        printf '[OK] %s\n' "$server"
    else
        printf '[FAIL] %s\n' "$server" >&2
        failed_servers+=("$server")
    fi
done
```

Then:

```bash
if (( ${#failed_servers[@]} > 0 )); then
    printf '\nFailed servers:\n' >&2

    for server in "${failed_servers[@]}"; do
        printf '  %s\n' "$server" >&2
    done

    exit 1
fi
```

Now the script communicates overall failure correctly.

---

# 62. Server Inventory Files

Instead of hard-coding servers:

```bash
servers=(
    web01
    web02
    web03
)
```

you may maintain:

```text
servers.txt
```

Example:

```text
web01.example.com
web02.example.com
web03.example.com
```

Read safely:

```bash
while IFS= read -r server || [[ -n "$server" ]]; do
    [[ -z "$server" ]] && continue
    [[ "$server" == \#* ]] && continue

    printf 'Checking %s\n' "$server"
done < servers.txt
```

This supports:

* blank lines
* comments
* final lines without newline

You learned this pattern in Part 7.

---

# 63. Validate Inventory Input

An inventory file should not automatically be trusted.

A malicious or malformed server value could cause unexpected behavior depending on how it is later used.

At minimum, validate expected formats.

For a controlled environment, you might restrict hostnames:

```bash
if [[ ! "$server" =~ ^[A-Za-z0-9.-]+$ ]]; then
    printf 'Invalid server name: %s\n' "$server" >&2
    continue
fi
```

This is only a simplified hostname validation rule.

The exact validation should reflect your inventory format and infrastructure.

Never use:

```bash
eval
```

to construct SSH commands from inventory values.

---

# 64. Sequential vs Parallel Remote Operations

This loop:

```bash
for server in "${servers[@]}"; do
    ssh "$server" 'uptime'
done
```

runs sequentially.

For 100 servers, that may be slow.

Parallel execution is possible, but it introduces complexity:

* output interleaving
* concurrency limits
* resource consumption
* API rate limits
* SSH connection pressure
* failure aggregation
* logging
* ordering

Do not introduce uncontrolled parallelism simply because it is faster.

Correctness and observability matter more.

For beginner automation, sequential execution is often the safest starting point.

---

# 65. Failed Connections

A remote operation can fail because:

```text
DNS fails
host unreachable
SSH port blocked
SSH service down
wrong username
wrong key
key permissions incorrect
host key mismatch
authentication denied
remote command missing
remote command lacks permission
remote command itself fails
timeout
```

Do not report all of these as:

```text
Server down
```

That diagnosis may be completely wrong.

Good scripts report what they actually know.

Better:

```text
SSH command failed for web02
```

Not:

```text
web02 is down
```

unless you have enough evidence to prove that.

# 66. SSH Retry Logic

Temporary SSH failures can sometimes be retried.

Example:

```bash
retry_ssh() {
    local server="$1"
    local remote_command="$2"
    local max_attempts="${3:-3}"
    local delay="${4:-2}"
    local attempt=1

    while (( attempt <= max_attempts )); do
        printf 'SSH attempt %d/%d to %s\n' \
            "$attempt" "$max_attempts" "$server"

        if ssh \
            -o BatchMode=yes \
            -o ConnectTimeout=5 \
            "$server" \
            "$remote_command"
        then
            return 0
        fi

        if (( attempt < max_attempts )); then
            sleep "$delay"
        fi

        ((attempt++))
    done

    printf 'ERROR: SSH failed for %s\n' "$server" >&2
    return 1
}
```

Use:

```bash
retry_ssh web01.example.com 'uptime' 3 2
```

Again, not every failure should be blindly retried.

An invalid key will not become valid because you tried it five times.

---

# 67. Remote Commands and sudo

Suppose you need:

```bash
sudo systemctl restart nginx
```

remotely.

You might try:

```bash
ssh server 'sudo systemctl restart nginx'
```

But unattended automation becomes problematic if `sudo` asks for a password.

Do not solve this by embedding the sudo password in the script.

Instead, design permissions appropriately.

Possible approaches include:

* dedicated automation users
* carefully restricted sudo rules
* configuration-management systems
* cloud-native management tools
* service-specific permissions

Least privilege matters.

An automation account should not automatically receive unrestricted root access simply because it is convenient.

# 68. Remote Script Execution

For more complex logic, a remote script may be cleaner.

Suppose:

```text
health-check.sh
```

exists locally.

You can copy it:

```bash
scp health-check.sh server:/tmp/
```

Then execute:

```bash
ssh server 'bash /tmp/health-check.sh'
```

This is often easier to understand and test than:

```bash
ssh server 'very long command with many nested quotes ...'
```

For production systems, also consider:

* deployment location
* ownership
* permissions
* integrity
* cleanup
* versioning
* auditability

# 69. Running a Local Script Through SSH Standard Input

Another pattern is:

```bash
ssh server 'bash -s' < script.sh
```

Here:

```text
script.sh
```

is read locally and sent to the remote Bash process through stdin.

This can be convenient for temporary automation.

But remember:

* relative files referenced by the script are not automatically transferred
* secrets must still be handled safely
* the remote system must have required commands
* the remote environment may differ from your local environment

# 70. Remote Environment Differences

A script that works locally may fail remotely because:

```text
different PATH
different shell
different Bash version
missing commands
different permissions
different environment variables
different working directory
different OS
different package versions
```

This connects directly to Part 16.

Do not assume SSH receives the same interactive environment you see after manually logging in.

For example:

```bash
ssh server 'command -v jq'
```

may fail even though you remember using `jq` during an interactive session.

Investigate:

```bash
ssh server 'printf "%s\n" "$PATH"'
```

and:

```bash
ssh server 'command -v jq || true'
```

Understand the environment rather than randomly editing `.bashrc`.

# 71. API Health Checks

Suppose your API provides:

```text
https://api.example.com/health
```

returning:

```json
{
  "status": "healthy"
}
```

A basic check might be:

```bash
response="$(
    curl \
        -fsS \
        --connect-timeout 5 \
        --max-time 10 \
        https://api.example.com/health
)" || {
    printf 'ERROR: API request failed\n' >&2
    exit 1
}
```

Then:

```bash
status="$(jq -r '.status // empty' <<< "$response")"
```

Then:

```bash
if [[ "$status" != "healthy" ]]; then
    printf 'ERROR: API status is %s\n' "$status" >&2
    exit 1
fi
```

Then:

```bash
printf 'API is healthy\n'
```

This checks both transport and application-level data.

---

# 72. Health Endpoint vs Real Dependency Health

Be careful with simplistic health endpoints.

An application might return:

```json
{"status":"healthy"}
```

while its database is unavailable.

A mature health model may distinguish:

```text
process health
readiness
database connectivity
cache connectivity
queue connectivity
external dependencies
```

Bash can automate these checks, but your script is only as meaningful as the signals it inspects.

# 73. HTTP Redirects

A URL may redirect.

Example:

```text
HTTP 301
Location: https://new.example.com/
```

curl does not automatically follow every redirect unless instructed.

Use:

```bash
curl -L https://example.com
```

`-L` follows redirects.

Whether you should follow redirects depends on the check.

For example, if:

```text
http://example.com
```

is expected to redirect to:

```text
https://example.com
```

then redirect behavior may itself be part of what you want to test.

---

# 74. TLS and HTTPS

HTTPS is HTTP protected by TLS.

When curl connects to:

```text
https://example.com
```

it normally verifies the server's certificate.

Do not casually disable verification with:

```bash
-k
```

or:

```bash
--insecure
```

because a certificate error is inconvenient.

Certificate verification protects against connecting securely to the wrong or untrusted endpoint.

If verification fails, investigate:

* expired certificate
* wrong hostname
* incomplete certificate chain
* missing CA certificate
* incorrect system clock
* proxy/TLS interception
* wrong endpoint

Fix the cause.

# 75. Port Checks

Sometimes you only need to determine whether a TCP connection can be established.

Tools vary by system.

One common tool is `nc`, also known as netcat.

Example:

```bash
nc -z -w 3 server.example.com 443
```

Options commonly mean:

```text
-z   scan/check without normal data exchange
-w 3 timeout
```

Then:

```bash
if nc -z -w 3 server.example.com 443; then
    printf 'TCP port reachable\n'
else
    printf 'TCP port check failed\n'
fi
```

But availability of `nc` and option behavior can vary across implementations.

Always verify the version available on your environment.

---

# 76. TCP Success Is Not Application Success

Suppose:

```bash
nc -z server 443
```

succeeds.

You have learned:

```text
TCP connection to port 443 succeeded
```

You have not proven:

```text
HTTPS certificate valid
HTTP server healthy
API healthy
database healthy
application healthy
```

This distinction prevents false conclusions.

Cloud CLI commands often support:

* filters
* queries
* resource IDs

* instance/service roles

* secret stores
* protected credential configuration

```text
    |

    |

    |
```

# 85. Polling Cloud Resource State

* maximum attempts

# 101. Remote Server Check Function

```bash
check_server() {
    local server="$1"

    log_info "Checking remote server: $server"

    if ssh \
        -o BatchMode=yes \
        -o ConnectTimeout="$connect_timeout" \
        "$server" \
        '
            printf "Hostname: "
            hostname

            printf "Uptime: "
            uptime -p 2>/dev/null || uptime

            printf "Root filesystem: "
            df -h / | awk "NR==2 {print \$3 \"/\" \$2 \" used, \" \$5 \" utilization\"}"

            printf "Memory: "
            if command -v free >/dev/null 2>&1; then
                free -h | awk "/^Mem:/ {print \$3 \"/\" \$2 \" used\"}"
            else
                printf "free command unavailable\n"
            fi
        '
    then
        log_ok "$server passed remote check"
        return 0
    fi

    log_error "$server remote check failed"
    return 1
}
```

Notice the quoting.

The remote script is enclosed in single quotes so that variables such as:

```text
$3
$2
$5
```

inside `awk` are not expanded by the local shell.

Inside the awk program, dollar signs are escaped for the remote shell so that `awk` receives them correctly.

Remote quoting deserves careful testing.

# 104. API Request Function

We want to distinguish:

```text
transport failure
HTTP failure
invalid JSON
application health failure
```

Create:

```bash
check_api_once() {
    local response_file
    local http_code
    local curl_status
    local api_status

    response_file="$(mktemp)" || {
        log_error "Could not create temporary response file."
        return 1
    }

    http_code="$(
        curl \
            -sS \
            --connect-timeout "$connect_timeout" \
            --max-time "$((connect_timeout * 3))" \
            -o "$response_file" \
            -w '%{http_code}' \
            "$api_url"
    )"

    curl_status=$?

    if (( curl_status != 0 )); then
        log_error "API transport request failed."
        rm -f -- "$response_file"
        return 1
    fi

    if [[ ! "$http_code" =~ ^2[0-9][0-9]$ ]]; then
        log_error "API returned HTTP $http_code"
        rm -f -- "$response_file"
        return 1
    fi

    if ! jq -e . "$response_file" >/dev/null 2>&1; then
        log_error "API response is not valid JSON."
        rm -f -- "$response_file"
        return 1
    fi

    api_status="$(
        jq -r '.status // empty' "$response_file"
    )"

    rm -f -- "$response_file"

    if [[ "$api_status" != "healthy" ]]; then
        log_error "API health status is '${api_status:-missing}'"
        return 1
    fi

    log_ok "API is healthy"
    return 0
}
```

# 105. Why We Save the Response to a File

You could store the entire response in a variable.

But a temporary file provides a clean separation:

```text
curl response body
        |
        v
temporary file

HTTP code
        |
        v
shell variable
```

This becomes useful when responses are larger or need several processing steps.

The temporary file is removed after use.

For more complex scripts, use a cleanup trap to guarantee cleanup even when interrupted.

```text
REMOTE_COMMAND_FAILED
API_TIMEOUT
HTTP_503
INVALID_JSON
UNHEALTHY_APPLICATION
```

Why?

Because operators need actionable information.

Compare:

```text

```

with:

```text
web02: SSH connection timed out after 5 seconds
```

The second gives you somewhere to start.

# 119. Production Improvement: Timestamp Logs

You could create:

```bash
timestamp() {
    date '+%Y-%m-%dT%H:%M:%S%z'
}
```

Then:

```bash
log_info() {
    printf '%s [INFO] %s\n' "$(timestamp)" "$*"
}
```

Example:

```text

```

Timestamps become important when correlating:

* application logs
* load balancer logs
* cloud events
* monitoring alerts
* deployment events

Human-readable output is useful interactively.

For example:

```json
  "servers_ok": 2,
```

As scripts grow, avoid scattering configuration throughout the code.

Possible structure:

# 122. Production Improvement: Consider the Right Tool

Bash is excellent for:

* orchestrating commands
* small infrastructure utilities
* health checks
* CI/CD glue
* deployment helpers
* server administration
* simple API interactions

Bash becomes increasingly difficult when you need:

* complex nested data
* sophisticated API clients
* heavy concurrency
* large application architecture
* complicated error models
* extensive testing frameworks
* advanced object manipulation

At that point, Python, Go, or another language may be more appropriate.

Choosing Bash because the file started as a shell script is not always the right engineering decision.

Bad reasoning:

```text

therefore application is healthy
```

Correct reasoning:

```text
ping works
therefore ICMP echo succeeded
```

That is all you know.

Continue checking the relevant service.

# 124. Common Mistake: Assuming Ping Failure Means Down

ICMP may be blocked.

Instead of only:

```bash
ping server
```

test what matters:

```bash
curl https://server/health
```

or:

```bash
ssh server 'hostname'
```

depending on your requirement.

# 125. Common Mistake: Ignoring DNS

Suppose:

```bash
curl https://api.example.com
```

fails.

Do not immediately restart the API.

First determine whether:

```bash
dig +short api.example.com
```

works.

The application cannot serve a client that cannot resolve its hostname.

# 126. Common Mistake: Treating Every curl Response as Success

This:

```bash
response="$(curl -s https://api.example.com)"
```

does not prove success.

You must consider:

```text
Did curl execute successfully?

Was the body valid?
Does the body contain expected data?
```

# 127. Common Mistake: Parsing JSON with grep

Bad:

```bash
curl -s "$url" | grep '"status":"healthy"'
```

Why fragile?

The server may return:

```json
{
  "status": "healthy"
}
```

with whitespace or formatting changes.

Use:

```bash
jq -r '.status'
```

Bad:

```bash

```

Better:

```bash
: "${API_TOKEN:?API_TOKEN must be set}"
```

# 129. Common Mistake: Logging Secrets

```bash

```

Sensitive automation must be designed with logging in mind.

# 130. Common Mistake: Disabling TLS Verification

Bad troubleshooting habit:

```bash
curl -k https://production-api.example.com
```

followed by:

```text

```

You have not fixed the certificate problem.

You have disabled a security check.

# 131. Common Mistake: Disabling SSH Host Verification

Another dangerous shortcut is disabling host-key verification everywhere.

That weakens SSH's protection against connecting to an unexpected system.

Use controlled host-key management instead.

# 132. Common Mistake: Infinite Retries

Bad:

```bash
while true; do
    curl "$url"
done
```

If the service remains unavailable, the script may run forever.

Use:

```text

delay
final failure
```

If:


retrying the same request probably does not help.

# 134. Common Mistake: No Timeout

Bad:

inside critical unattended automation without considering time limits.

# 135. Common Mistake: SSH Without BatchMode

* review

# 138. Common Mistake: Uncontrolled Parallel SSH

# 140. Troubleshooting: curl Says Could Not Resolve Host

Problem:

```text
Could not resolve host
```

What the beginner sees:

```bash
curl https://api.example.com
```

fails before receiving an HTTP response.

Possible cause:

* DNS failure
* misspelled hostname
* DNS configuration issue
* unavailable resolver

Investigate:

```bash
dig +short api.example.com
```

or:

```bash
nslookup api.example.com
```

Inspect resolver configuration where appropriate.

Fix:

Correct the hostname or DNS problem.

Verify:

```bash
dig +short api.example.com
```

then:

```bash
curl -v https://api.example.com
```

# 141. Troubleshooting: Connection Refused

Problem:

```text
Connection refused
```

This often means the destination was reachable enough to reject the connection, but no acceptable service is listening on that port or a device actively rejected it.

Investigate on the server:

```bash
ss -lnt
```

Check the expected port.

Check the service:

```bash
systemctl status service-name
```

Check binding address.

Fix the actual service/listening configuration.

Verify from the client again.

---

# 142. Troubleshooting: Connection Timeout

Problem:

```text
connection timed out
```

Possible causes:

* firewall
* security group
* network ACL
* routing
* destination unavailable
* wrong IP
* service path blocked

Investigate:

```bash
dig +short hostname
```

```bash
ip route get destination-ip
```

Then test the required TCP service.

Do not immediately conclude that the application crashed.

---

# 143. Troubleshooting: HTTP 401

Problem:

```text
401 Unauthorized
```

Possible causes:

* token absent
* token invalid
* token expired
* wrong authentication header

Investigate whether the variable exists without printing the secret:

```bash
if [[ -n "${API_TOKEN:-}" ]]; then
    printf 'API_TOKEN is set\n'
else
    printf 'API_TOKEN is not set\n'
fi
```

Do not debug by printing the actual token.

Fix credential delivery or authentication configuration.

Verify the request again.

# 144. Troubleshooting: HTTP 403

Problem:

```text
403 Forbidden
```

Possible cause:

The authenticated identity may lack permission.

Investigate:

* identity
* role
* scope
* resource policy
* endpoint requirements

Do not assume "authentication is broken."

Authentication and authorization are different concepts.

# 145. Troubleshooting: HTTP 500

Problem:

```text
500 Internal Server Error
```

The network and HTTP path may be functioning.

The server application encountered an internal error.

Investigate:

* application logs
* recent deployment
* dependencies
* database
* configuration
* resource exhaustion

Do not troubleshoot a 500 by changing local DNS unless evidence points there.

Possible architecture:

Investigate:

* DNS

# 147. Troubleshooting: HTTP 503

A:

```text
503 Service Unavailable
```

may indicate temporary inability to serve requests.

Possible causes:

* service starting
* overloaded application
* no healthy load balancer targets
* maintenance
* dependency failure

This may be a reasonable retry candidate depending on the system.

But retries should still be bounded.

# 148. Troubleshooting: SSH Permission Denied

Problem:

```text
Permission denied (publickey)
```

Possible causes:

* wrong username
* wrong private key
* corresponding public key missing
* key permissions incorrect
* SSH configuration wrong
* server authorization changed

Investigate:

```bash
ssh -v user@server
```

Verbose SSH output can help determine which identities are attempted.

Be careful when sharing verbose logs because they may reveal infrastructure information.

Fix the authentication configuration.

Verify with a normal SSH command.

# 149. Troubleshooting: SSH Timeout

Problem:

```text
Connection timed out
```

Possible causes:

* port 22 blocked
* wrong address
* routing problem
* SSH service unavailable
* cloud firewall/security group

Investigate DNS and network path.

Then test the expected SSH endpoint.

Do not immediately replace the SSH key. A key cannot authenticate if the TCP connection is never established.

# 150. Troubleshooting: Host Key Changed

SSH may warn that a host key has changed.

Do not automatically delete the old key and continue.

A changed host key can be legitimate:

* server rebuilt
* instance replaced
* host reinstalled

But it can also indicate that you are connecting to a different machine than expected.

Verify the new host identity through a trusted process before updating your known-host information.

```text
parse error
```

Possible cause:

The response is not valid JSON.

Inspect the response safely.

It might actually be:

```html

  <h1>502 Bad Gateway</h1>
</html>
```

This is why HTTP status should be checked before assuming JSON.

Possible causes:

* different user
* different PATH
* missing environment variable
* different working directory

# 160. Part 18 Summary

You have moved beyond automating a single Linux machine.

You can now think about infrastructure as connected layers:

```text
Bash
 |
 +--> Linux commands
 |
 +--> DNS
 |
 +--> Network
 |
 +--> TCP ports
 |
 +--> HTTP/HTTPS
 |
 +--> APIs
 |
 +--> JSON
 |
 +--> SSH
 |
 +--> Remote servers
 |
 +--> Cloud CLI
 |
 +--> Cloud APIs
 |
 +--> Infrastructure
```

The most important lesson is not simply learning commands such as:

```bash
ping
ip
ss
dig
curl
wget
jq
ssh
scp
rsync
```

The important skill is understanding what each command actually proves.

A DNS lookup proves something different from a TCP connection.

A TCP connection proves something different from HTTP 200.

HTTP 200 proves something different from application readiness.

A cloud instance in a `running` state proves something different from a healthy production service.

Reliable Bash automation follows evidence through those layers.

Your scripts should therefore:

```text
validate input
      |
      v
validate dependencies
      |
      v
verify identity and target
      |
      v
attempt operation
      |
      v
enforce timeout
      |
      v
inspect exit status
      |
      v
inspect protocol response
      |
      v
validate returned data
      |
      v
retry only when appropriate
      |
      v
record failures
      |
      v
verify final state
      |
      v
return meaningful exit status
```

That is the difference between a shell command that happens to work and infrastructure automation that can be trusted.

In Part 19, you will take these Bash skills directly into DevOps workflows: CI/CD pipelines, build and deployment scripts, Docker, container entrypoints, Kubernetes and `kubectl`, Terraform helper scripts, Git automation, release workflows, health checks, rollback logic, idempotency, logging, and production deployment automation.
