# Part 13: Processes, Jobs, Signals, and Background Execution

Every time Bash runs a command, something important happens behind the scenes.

When you type:

```bash
sleep 30
```

Bash does not simply "run some text."

The operating system creates or manages a running instance of a program called a process.

That process receives an identity.

It has a parent.

It consumes resources.

It can run in the foreground or background.

It can finish successfully.

It can fail.

It can receive signals.

It can be stopped.

It can be terminated.

It can create other processes.

Your Bash script itself is also part of this process world.

Understanding processes is essential for DevOps engineers because production systems are full of running programs:

```text
Web servers
Application servers
Databases
Monitoring agents
Container runtimes
CI/CD workers
Backup jobs
Cron jobs
Log collectors
SSH sessions
Deployment scripts
Background workers
Kubernetes processes
System services
```

When something goes wrong, engineers frequently ask questions such as:

```text
Is the process running?

What PID does it have?

Who started it?

Is it stuck?

Is it consuming CPU?

Did the parent process disappear?

Should I terminate it?

Which signal should I send?

Did my script leave temporary resources behind?

How do I wait for several background jobs?

```

These are process-management questions.

# 1. What Is a Process?

A process is a running instance of a program.

Suppose you have a program:

```text
/usr/bin/sleep
```

That file exists on disk.

When you run:

```bash
sleep 30
```

the operating system creates a running process associated with that program.

Think:

```text
Program on disk
      |
      | executed
      v
Running process
      |
      +--> PID
      +--> parent
      +--> memory
      +--> environment
      +--> open files
      +--> current directory
      +--> permissions
      +--> execution state
```

A program and a process are therefore related but not identical.

The program is executable code.

The process is a running instance of that code.

---

# 2. One Program Can Have Multiple Processes

Run:

```bash
sleep 300 &
sleep 300 &
sleep 300 &
```

You now have three separate `sleep` processes.

They execute the same program but have different process IDs.

You might see:

```text
PID 4101 → sleep 300
PID 4102 → sleep 300
PID 4103 → sleep 300
```

This is common in production.

For example, multiple processes may run:

* worker programs
* web server workers
* application instances
* CI runners
* SSH sessions
* monitoring agents

---

# 3. What Is a Process ID?

Every running process has a numeric identifier called a:

```text
PID
```

PID means:

```text
Process ID
```

Example:

```text
PID 4281
```

The operating system uses the PID to identify a particular running process.

You can then perform operations such as:

```bash
ps -p 4281
```

or:

```bash
kill 4281
```

The PID identifies a process at that moment.

---

# 4. PIDs Are Temporary

A PID is not a permanent identity.

Suppose:

```text
PID 4281
```

belongs to a process.

When that process exits, PID 4281 eventually becomes available for reuse.

Later, an entirely different process could receive PID 4281.

This creates an important production safety rule:

> Do not assume an old PID still identifies the process you originally intended to manage.

If your automation stores PIDs, validate what you are acting on whenever appropriate.

---

# 5. Your Shell Is a Process

Open a Bash terminal.

Run:

```bash
echo "$$"
```

You may see:

```text
3950
```

That number represents the process ID associated with the current Bash shell context.

The special Bash parameter:

```text
$$
```

expands to the shell's process ID.

---

# 6. Inspect Your Shell PID

Run:

```bash
echo "$$"
```

Then:

```bash
ps -p "$$"
```

You might see something similar to:

```text
PID TTY          TIME CMD
3950 pts/0    00:00:00 bash
```

Your Bash shell is itself a running process.

---

# 7. Parent and Child Processes

Processes often create other processes.

The process that creates another process is called the:

```text
parent process
```

The created process is called the:

```text
child process
```

Conceptually:

```text
Terminal
   |
   v
Bash
   |
   +------> sleep
   |
   +------> grep
   |
   +------> curl
```

Bash may act as the parent of commands it launches.

---

# 8. Process Trees

Processes naturally form relationships.

Example:

```text
system manager
      |
      +--> sshd
             |
             +--> bash
                    |
                    +--> deployment.sh
                           |
                           +--> curl
                           |
                           +--> kubectl
```

Understanding these relationships helps answer questions such as:

```text
Who launched this process?

What will happen if the parent exits?

Which processes belong to this script?

Why did this worker remain after the script finished?
```

---

# 9. Parent Process ID

A process can have a:

```text
PPID
```

meaning:

```text
Parent Process ID
```

In Bash:

```bash
echo "$PPID"
```

prints the parent process ID associated with the current shell.

Try:

```bash
printf 'Shell PID: %s\n' "$$"
printf 'Parent PID: %s\n' "$PPID"
```

Possible output:

```text
Shell PID: 3950
Parent PID: 3921
```

---

# 10. Inspect the Parent

Run:

```bash
ps -p "$PPID"
```

Depending on your environment, the parent might be:

* a terminal-related process
* SSH daemon/session
* another shell
* container process
* IDE terminal process
* process supervisor

The exact result depends on how Bash was launched.

---

# 11. Inspect PID and PPID Together

Run:

```bash
ps -o pid,ppid,stat,cmd -p "$$"
```

Possible output:

```text
PID   PPID STAT CMD
3950  3921 Ss   bash
```

Here:

```text
PID  = process itself
PPID = parent
STAT = process state
CMD  = command
```

---

# 12. Child Processes from Bash

Run:

```bash
sleep 300 &
```

Bash may display something like:

```text
[1] 4105
```

Here:

```text
[1]
```

is the shell job number.

And:

```text
4105
```

is the process ID of the background command Bash started.

These are different concepts.

---

# 13. Job Number vs PID

Do not confuse:

```text
[1]
```

with:

```text
4105
```

The first is a shell job identifier.

The second is an operating-system process identifier.

Think:

```text
Shell job table

Job 1
  |
  v
PID 4105
```

Job IDs are primarily managed by the shell.

PIDs belong to the operating system's process model.

---

# 14. Foreground Processes

Normally, when you run:

```bash
sleep 30
```

the command runs in the foreground.

Your shell waits for it to finish.

During those 30 seconds, you do not get the normal interactive Bash prompt back.

Conceptually:

```text
Bash
 |
 | launch
 v
sleep 30
 |
 | Bash waits
 v
sleep finishes
 |
 v
Bash prompt returns
```

---

# 15. Try a Foreground Process

Run:

```bash
sleep 10
```

Notice:

* the prompt disappears
* Bash waits
* after approximately 10 seconds, the prompt returns

This is foreground execution.

---

# 16. Background Processes

Sometimes you do not want Bash to wait immediately.

You can place a command in the background using:

```text
&
```

Example:

```bash
sleep 30 &
```

Bash returns the prompt while the command continues running.

---

# 17. What `&` Does

Compare:

```bash
sleep 30
```

with:

```bash
sleep 30 &
```

Foreground:

```text
Bash
 |
 v
sleep
 |
 Bash waits
 |
 v
prompt
```

Background:

```text
Bash
 |
 +----> sleep
 |
 +----> prompt continues
```

The shell and the background command can now progress independently.

---

# 18. Why Background Execution Matters

Background execution is useful when:

* running independent tasks
* performing multiple checks
* starting temporary workers
* launching long-running operations
* running multiple downloads
* processing several files
* performing independent infrastructure checks
* executing controlled parallel work

But background execution also creates new responsibilities.

You need to know:

```text
Which jobs did I start?

Are they still running?

Did they succeed?

Did they fail?

How do I wait for them?

How do I stop them?

What happens if my script is interrupted?
```

---

# 19. `$!`: PID of the Most Recent Background Process

After:

```bash
sleep 60 &
```

run:

```bash
echo "$!"
```

`$!` contains the process ID associated with the most recently started asynchronous/background command.

Example:

```text
4210
```

This is extremely useful.

---

# 20. Capture Background PIDs Immediately

A common pattern is:

```bash
sleep 60 &
pid=$!
```

Then:

```bash
printf 'Started PID: %s\n' "$pid"
```

Do this immediately after launching the intended background job.

Why?

Because starting another background command changes `$!`.

---

# 21. `$!` Changes

Example:

```bash
sleep 100 &
first_pid=$!

sleep 200 &
second_pid=$!
```

Now:

```text
first_pid  → first background job
second_pid → second background job
```

If you waited until after both launches and only used `$!`, you would only have the most recent one.

---

# 22. Store Several Background PIDs in an Array

Part 12 now becomes very useful.

```bash
pids=()

sleep 30 &
pids+=("$!")

sleep 40 &
pids+=("$!")

sleep 50 &
pids+=("$!")
```

Now:

```bash
printf '%s\n' "${pids[@]}"
```

shows the PIDs you recorded.

This is the foundation for controlled concurrent Bash work.

# 23. Shell Job Control

Interactive Bash maintains information about jobs it has started.

Run:

```bash
sleep 300 &
sleep 400 &
```

Then:

```bash
jobs
```

You may see:

```text
[1]-  Running    sleep 300 &
[2]+  Running    sleep 400 &
```

---

# 24. What `jobs` Shows

The `jobs` command reports jobs known to the current shell.

It may show states such as:

```text
Running
Stopped
Done
```

Example:

```text
[1] Running sleep 300 &
```

This is shell job control.

---

# 25. `jobs` Is Not a System-Wide Process Viewer

This is important.

`jobs` does not show every process on the machine.

It shows jobs associated with the current shell's job table.

For system-wide process inspection, tools such as:

```text
ps
pgrep
top
```

are more appropriate.

---

# 26. Job Specifications

Bash can refer to jobs using job specifications such as:

```text
%1
%2
```

For example:

```bash
fg %1
```

means:

> Bring job 1 into the foreground.

Do not confuse:

```text
%1
```

with PID 1.

They are completely different identifiers.

---

# 27. Bringing a Background Job to the Foreground

Start:

```bash
sleep 300 &
```

Run:

```bash
jobs
```

Suppose it is job 1.

Run:

```bash
fg %1
```

Now the process becomes the foreground job.

Your prompt waits again.

---

# 28. Stopping a Foreground Job

While a foreground command is running, pressing:

```text
Ctrl+Z
```

usually sends a terminal-generated stop signal to suspend it.

For example:

```bash
sleep 300
```

Press:

```text
Ctrl+Z
```

You may see:

```text
[1]+ Stopped sleep 300
```

The process is stopped, not necessarily terminated.

---

# 29. Resume a Stopped Job in the Background

Run:

```bash
bg %1
```

The job continues in the background.

Then:

```bash
jobs
```

may show:

```text
[1]+ Running sleep 300 &
```

---

# 30. Resume a Stopped Job in the Foreground

Instead of:

```bash
bg %1
```

you can use:

```bash
fg %1
```

The job resumes as the foreground job.

---

# 31. `fg` and `bg` Are Mainly Interactive Job-Control Tools

In production automation, you will more commonly use:

* `&`
* `$!`
* arrays of PIDs
* `wait`
* `kill`
* `trap`

rather than scripting around interactive `fg` and `bg`.

Still, understanding `fg` and `bg` is important because engineers frequently use them in terminal sessions.

---

# 32. Waiting for Background Processes

Suppose:

```bash
sleep 5 &
```

Bash immediately continues.

But sometimes you want to do other work and later wait for the background process.

Use:

```bash
wait
```

---

# 33. Basic `wait`

Example:

```bash
sleep 5 &

printf 'Background task started\n'

wait

printf 'Background task finished\n'
```

The shell starts the task, continues, then waits before printing the final message.

---

# 34. Wait for a Specific PID

Better control:

```bash
sleep 10 &
pid=$!

printf 'Started PID %s\n' "$pid"

wait "$pid"

printf 'PID %s finished\n' "$pid"
```

Now you are explicitly waiting for one known process.

---

# 35. `wait` Returns the Job's Exit Status

This is extremely important.

Example:

```bash
bash -c 'exit 7' &
pid=$!

wait "$pid"
status=$?

printf 'Exit status: %s\n' "$status"
```

Output:

```text
Exit status: 7
```

This allows a parent script to discover whether background work succeeded.

---

# 36. Why `wait` Matters in Automation

Suppose you launch:

```text
backup A
backup B
backup C
```

in parallel.

Starting them successfully does not mean they completed successfully.

You need:

```text
Launch
  |
  v
Capture PIDs
  |
  v
Wait
  |
  v
Collect exit statuses
  |
  v
Report failures
```

Without `wait`, your script might finish while work is still running or fail to notice background errors.

---

# 37. Waiting for Multiple PIDs

Example:

```bash
pids=()

sleep 2 &
pids+=("$!")

sleep 3 &
pids+=("$!")

sleep 4 &
pids+=("$!")

for pid in "${pids[@]}"; do
    wait "$pid"
done
```

The parent waits for every recorded process.

---

# 38. Collect Background Failures

Example:

```bash
pids=()

bash -c 'sleep 1; exit 0' &
pids+=("$!")

bash -c 'sleep 2; exit 4' &
pids+=("$!")

failed=0

for pid in "${pids[@]}"; do

    if wait "$pid"; then
        printf 'PID %s succeeded\n' "$pid"
    else
        status=$?
        printf 'PID %s failed with status %s\n' \
            "$pid" "$status" >&2
        ((failed += 1))
    fi

done
```

This is far more reliable than simply starting processes with `&` and forgetting them.

---

# 39. Be Careful When Capturing `$?`

This works:

```bash
if wait "$pid"; then
    printf 'Success\n'
else
    status=$?
    printf 'Failed: %s\n' "$status"
fi
```

Inside the `else` branch, `$?` is the failure status returned by `wait`.

But if you run another command first:

```bash
if wait "$pid"; then
    ...
else
    printf 'Failure detected\n'
    status=$?
fi
```

you have lost the original status because `printf` changed `$?`.

Capture statuses immediately.

```bash
ps
```

Run:

```bash
sleep 300 &

```

Possible output:

```text
PID TTY          TIME CMD
4501 pts/0    00:00:00 sleep
```

# 42. Select Useful `ps` Columns

Try:

```bash
ps -o pid,ppid,user,stat,etime,cmd -p "$pid"
```

Possible output:

```text
PID  PPID USER STAT ELAPSED CMD
4501 3950 ann  S      00:05 sleep 300
```

Important fields:

```text
PID      Process ID
PPID     Parent process ID
USER     Process owner

CMD      Command
```

---

# 43. Process States

`ps` may display state letters.

Common examples include:

```text
R    running or runnable
S    interruptible sleep
D    uninterruptible sleep
T    stopped/traced
Z    zombie
```

You may see additional characters depending on the `ps` implementation.

Do not assume every state letter means "broken."

For example, many healthy processes spend much of their time sleeping while waiting for work.

---

# 44. What Is a Zombie Process?

A zombie is a process that has finished execution but still has an entry in the process table because its parent has not yet collected its termination status.

Conceptually:

```text
Child finishes
     |
     v
Exit information remains
     |
Parent has not reaped it yet
     |
     v
Zombie state
```

You do not normally "fix" zombies by repeatedly sending stronger kill signals to the zombie itself.

The underlying issue concerns parent-child process handling.

---

# 45. Search for Processes with `pgrep`

`pgrep` searches running processes.

Example:

```bash
pgrep bash
```

It may print PIDs of processes whose names match `bash`.

---

# 46. Exact Process Matching

Use:

```bash
pgrep -x nginx
```

The:

```text
-x
```

means exact process-name matching.

This is safer than a loose match when you know the exact process name.

---

# 47. Show PID and Process Name

Depending on your implementation:

```bash
pgrep -a nginx
```

can display matching PIDs with command information.

For broader process inspection, you can also combine tools appropriately.

---

# 48. Why `pgrep` Is Better Than `ps | grep` for Many Checks

You may see:

```bash
ps aux | grep nginx
```

This has several problems.

The `grep` command itself can appear in results, and text matching may be broader than intended.

When you need to find processes by name, prefer a process-aware tool such as:

```bash
pgrep
```

when available.

---

# 49. Do Not Blindly Kill `pgrep` Results

This is dangerous:

```bash
kill $(pgrep some_name)
```

Why?

Because:

* the match may be broader than expected
* several processes may match
* the process set may change between lookup and action
* you may terminate processes you did not intend to affect

Inspect first.

Validate ownership and identity.

Then act deliberately.

---

# 50. Process Inspection with `top`

Run:

```bash
top
```

`top` provides an interactive view of running processes and system resource usage.

Depending on the system, it may display:

* CPU usage
* memory usage
* load
* process IDs
* users
* process states
* command names
* running time

It is commonly used during troubleshooting.

---

# 51. Why `top` Matters for DevOps

Suppose an application becomes slow.

You might ask:

```text
Is CPU saturated?

Is one process consuming most CPU?

Is memory pressure high?

Are many processes running?

Is a particular process stuck?
```

`top` can provide quick operational visibility.

Other tools may provide deeper analysis, but `top` is a useful starting point.

# 53. Killing Processes

Linux provides the:

```bash
kill
```

command.

Despite its name, `kill` is fundamentally a tool for sending signals to processes.

For example:

```bash
kill "$pid"
```

normally sends:

```text
SIGTERM
```

to the process.

---

# 54. Signals

A signal is a notification sent to a process to indicate that an event has occurred.

Signals can request or cause behaviors such as:

* termination
* interruption
* stopping
* continuation
* reloading
* other process-specific behavior

Different signals have different meanings.

---

# 55. List Signals

Run:

```bash
kill -l
```

Your system will display supported signal names and/or numbers.

You may see names such as:

```text
HUP
INT
KILL
TERM
STOP
CONT
```

Signal numbering can have platform details, so using symbolic names often makes scripts easier to understand.

---

# 56. SIGTERM

`SIGTERM` means a termination request.

Send it using:

```bash
kill -TERM "$pid"
```

or commonly:

```bash
kill "$pid"
```

because `SIGTERM` is the normal default signal for `kill`.

Think:

```text
Please terminate cleanly.
```

A program may handle `SIGTERM` and perform cleanup before exiting.

---

# 57. Why SIGTERM Is Usually the Better First Choice

A well-designed service receiving `SIGTERM` may have an opportunity to:

* stop accepting new work
* finish or abandon work safely
* flush buffers
* close files
* close network connections
* release locks
* remove temporary files
* notify child processes
* shut down cleanly

The exact behavior depends on the application.

But `SIGTERM` gives the process a chance to respond.

---

# 58. SIGKILL

`SIGKILL` forcibly terminates a process.

Send:

```bash
kill -KILL "$pid"
```

or:

```bash
kill -9 "$pid"
```

You will frequently see the numeric form:

```text
-9
```

But the symbolic form:

```text
-KILL
```

is often clearer to readers.

---

# 59. Why SIGKILL Is Different

`SIGKILL` cannot be caught, blocked, or ignored by the target process.

The kernel terminates the process.

Conceptually:

```text
SIGTERM

Process receives request
      |
      v
Process may clean up
      |
      v
Process exits


SIGKILL

Kernel
  |
  v
Process terminated immediately
```

---

# 60. Why SIGKILL Should Not Be Your First Option

If you immediately use:

```bash
kill -9 "$pid"
```

the process cannot run normal signal cleanup.

Depending on the program, this can leave:

* incomplete work
* stale lock files
* temporary files
* partially written application data
* interrupted transactions or workflows
* child-process complications
* difficult operational states

This does not mean SIGKILL should never be used.

It means it should normally be an escalation mechanism.

---

# 61. A Safer Termination Pattern

Conceptually:

```text
Identify correct process
      |
      v
Send SIGTERM
      |
      v
Wait for graceful exit
      |
      +--> exited
      |      |
      |      v
      |     done
      |
      +--> still running
             |
             v
      investigate/escalate
             |
             v
        SIGKILL if justified
```

---

# 62. Check Whether a PID Still Exists

One useful pattern is:

```bash
kill -0 "$pid"
```

This does not send a terminating signal.

It asks the system to perform signal-related validity/permission checking.

Example:

```bash
if kill -0 "$pid" 2>/dev/null; then
    printf 'Process appears to exist and is signalable\n'
else
    printf 'Process does not exist or cannot be signaled\n'
fi
```

Important:

A failed `kill -0` does not always mean simply "not running."

It can also involve permission issues.

Interpret it carefully.

---

# 63. Graceful Termination Example

Start:

```bash
sleep 300 &
pid=$!
```

Then:

```bash
kill -TERM "$pid"
```

Wait:

```bash
wait "$pid"
status=$?
```

The exit status may indicate that the process ended because of a signal.

Exact shell-visible status behavior follows signal conventions.

---

# 64. Signal-Related Exit Statuses

Shells commonly represent signal termination using:

```text
128 + signal number
```

For example, `SIGTERM` is commonly signal 15:

```text
128 + 15 = 143
```

So you may see:

```text
143
```

for a process terminated by SIGTERM.

Similarly, SIGINT is commonly signal 2:

```text
130
```

But when writing portable logic, understand the signal meaning rather than memorizing every number without context.

---

# 65. SIGINT

`SIGINT` means interrupt.

A familiar source is:

```text
Ctrl+C
```

When you press Ctrl+C while a foreground process is running, the terminal typically causes `SIGINT` to be delivered to the foreground process group.

This requests interruption.

---

# 66. Ctrl+C Is Not the Same as SIGKILL

This matters.

Ctrl+C does not mean:

```text
Forcefully destroy process immediately
```

It generally results in:

```text
SIGINT
```

Processes can handle SIGINT.

That makes graceful cleanup possible.

---

# 67. SIGHUP

`SIGHUP` historically means:

```text
hangup
```

It is associated with terminal/session disconnection history.

Some long-running programs also use SIGHUP by convention as a request to reload configuration.

For example, a daemon may interpret:

```bash
kill -HUP "$pid"
```

as:

```text
Reload configuration
```

But this is application-specific.

Do not assume every program interprets SIGHUP as reload.

Check the program's documentation.

# 68. Important Signal Summary

```text
SIGTERM
Request graceful termination.

SIGKILL
Force immediate termination.
Cannot be caught or ignored.

SIGINT
Interactive interruption.
Often associated with Ctrl+C.

SIGHUP
Historically terminal/session hangup.
Some daemons use it for configuration reload.
```

---

# 69. Signals Are Not Commands

A signal does not contain a Bash script telling the process exactly what to do.

The operating system delivers the signal.

The process may:

* use default behavior
* catch it
* ignore some signals
* run a handler
* perform application-specific behavior

Not all signals are catchable.

---

# 70. Bash Can React to Signals

Bash provides:

```bash
trap
```

This allows a script to arrange commands or functions to run when certain signals or shell events occur.

Example:

```bash
trap 'echo "Interrupted"' INT
```

Now pressing Ctrl+C can trigger the specified action.

---

# 71. Basic `trap`

Create:

```bash
#!/usr/bin/env bash

trap 'printf "Caught SIGINT\n"' INT

printf 'Running. Press Ctrl+C.\n'

while true; do
    sleep 1
done
```

Run it.

Press Ctrl+C.

Instead of immediately ending due solely to the default SIGINT behavior, the trap runs.

Depending on your handler, the script may continue.

---

# 72. Why the Previous Script May Keep Running

The trap was:

```bash
trap 'printf "Caught SIGINT\n"' INT
```

It prints a message.

But it does not explicitly exit.

So the loop can continue.

If you want interruption to terminate the script:

```bash
trap 'printf "Interrupted\n"; exit 130' INT
```

---

# 73. Prefer Functions for Nontrivial Traps

Instead of:

```bash
trap 'command1; command2; command3; command4' INT
```

define a function:

```bash
handle_interrupt() {
    printf 'Interrupted\n' >&2
    exit 130
}
```

Then:

```bash
trap handle_interrupt INT
```

This is easier to read and maintain.

---

# 74. Trap SIGTERM

Example:

```bash
handle_term() {
    printf 'Termination requested\n' >&2
    exit 143
}

trap handle_term TERM
```

Now the script can react when receiving SIGTERM.

---

# 75. Trap Multiple Signals

You can associate one handler with several signals:

```bash
trap handle_shutdown INT TERM
```

Example:

```bash
handle_shutdown() {
    printf 'Shutdown requested\n' >&2
    exit 1
}

trap handle_shutdown INT TERM
```

However, you may want different exit statuses depending on the signal.

---

# 76. Different Handlers for Different Signals

Example:

```bash
handle_int() {
    printf 'Interrupted by user\n' >&2
    exit 130
}

handle_term() {
    printf 'Termination requested\n' >&2
    exit 143
}

trap handle_int INT
trap handle_term TERM
```

This preserves clearer semantics.

---

# 77. The `EXIT` Trap

Bash also allows:

```bash
trap cleanup EXIT
```

`EXIT` is not an ordinary operating-system signal.

It is a Bash trap condition that runs when the shell is exiting.

This is extremely useful for cleanup.

---

# 78. Cleanup Handlers

Suppose your script creates:

```bash
temp_file="$(mktemp)"
```

If the script completes normally, you can remove it:

```bash
rm -f -- "$temp_file"
```

But what happens if someone presses Ctrl+C halfway through?

Without cleanup handling, the temporary file may remain.

---

# 79. Temporary Resource Problem

Imagine:

```text
Script starts
   |
   v
Create temp directory
   |
   v
Create temp files
   |
   v
Begin work
   |
   v
Ctrl+C
   |
   v
Script exits
   |
   v
Temporary resources remain
```

Repeated runs may leave:

```text
/tmp/app.XYZ1
/tmp/app.ABC2
/tmp/app.KLM3
```

This is resource leakage.

---

# 80. Cleanup with `trap`

Example:

```bash
#!/usr/bin/env bash

temp_dir="$(mktemp -d)"

cleanup() {
    rm -rf -- "$temp_dir"
}

trap cleanup EXIT

printf 'Temporary directory: %s\n' "$temp_dir"

sleep 30
```

Whether the script exits normally or through many common controlled exit paths, the `EXIT` trap can remove the directory.

---

# 81. Warning About `rm -rf`

This command:

```bash
rm -rf -- "$temp_dir"
```

is destructive.

Never use it with an unvalidated or potentially empty path.

The variable should be created safely and validated.

A safer cleanup function can check it.

---

# 82. Safer Temporary Directory Cleanup

Example:

```bash
temp_dir=""

cleanup() {

    if [[ -n "$temp_dir" && -d "$temp_dir" ]]; then
        rm -rf -- "$temp_dir"
    fi
}
```

Then:

```bash
temp_dir="$(mktemp -d)" || exit 1
trap cleanup EXIT
```

Now cleanup does not blindly operate on an empty variable.

---

# 83. Even Better: Restrict the Expected Path

If appropriate:

```bash
cleanup() {

    if [[ -n "$temp_dir" &&
          -d "$temp_dir" &&
          "$temp_dir" == /tmp/veriqta-job.* ]]; then

        rm -rf -- "$temp_dir"
    fi
}
```

Then create:

```bash
temp_dir="$(mktemp -d '/tmp/veriqta-job.XXXXXX')" || exit 1
```

This adds another safety boundary.

---

# 84. Why Cleanup Functions Matter

A cleanup handler can remove:

* temporary files
* temporary directories
* lock files
* FIFOs
* local scratch resources

It can also stop child processes your script deliberately created.

Good automation considers:

```text
What resources do I create?

Who owns them?

What happens on success?

What happens on failure?

What happens on interruption?
```

# 85. Preserve the Original Exit Status During Cleanup

This is a subtle but important technique.

Suppose your script fails with status:

```text
7
```

Then the `EXIT` trap runs cleanup commands.

You generally do not want cleanup to accidentally change the intended final result.

Use:

```bash
cleanup() {
    local status=$?

    # cleanup operations here

    return "$status"
}
```

The first command captures the status that existed when the trap began.

---

# 86. Cleanup Example with Status Preservation

```bash
cleanup() {
    local status=$?

    if [[ -n "$temp_dir" &&
          -d "$temp_dir" &&
          "$temp_dir" == /tmp/veriqta-job.* ]]; then
        rm -rf -- "$temp_dir"
    fi

    return "$status"
}

trap cleanup EXIT
```

This is a stronger pattern than cleanup code that ignores exit semantics.

---

# 87. Do Not Put Untrusted Values into Trap Strings

Avoid constructing trap code from untrusted input.

Risky design:

```bash
trap "rm -f $user_supplied_value" EXIT
```

The trap string is shell code.

Prefer:

```bash
cleanup() {
    rm -f -- "$validated_file"
}

trap cleanup EXIT
```

Functions are easier to reason about and safer to maintain.

---

# 88. Ctrl+C Handling

Suppose a script starts several background workers.

If the user presses Ctrl+C, simply exiting the parent may not produce the cleanup behavior you want for every child.

A controlled script should know which children it owns.

That is why we captured:

```bash
pids+=("$!")
```

---

# 89. Track Only Processes You Started

This is an important safety principle.

Prefer:

```text
Start process
     |
     v
Capture PID
     |
     v
Store PID
     |
     v
Manage that PID
```

over:

```text
Search machine broadly
     |
     v
Kill everything with matching text
```

The first approach has clearer ownership.

---

# 90. Terminating Tracked Children

Suppose:

```bash
pids=()
```

contains child PIDs.

A cleanup function might inspect them:

```bash
terminate_children() {
    local pid

    for pid in "${pids[@]}"; do

        if kill -0 "$pid" 2>/dev/null; then
            kill -TERM "$pid" 2>/dev/null || true
        fi

    done
}
```

This sends SIGTERM only to tracked processes that still appear signalable.

---

# 91. Do Not Immediately Send SIGKILL

After SIGTERM, give children time to exit.

Conceptually:

```text
Send TERM
   |
   v
Wait
   |
   +--> exited
   |
   +--> still running
          |
          v
        escalate
```

---

# 92. Waiting for Children During Cleanup

After sending termination:

```bash
for pid in "${pids[@]}"; do
    wait "$pid" 2>/dev/null || true
done
```

This allows the parent shell to collect termination statuses for children it can wait on.

# 93. Why Child Cleanup Matters

Imagine a deployment script starts:

```text

test server
background log collector
health-check worker
```

Then the deployment fails.

Without cleanup:

```text
Parent exits
   |
   +--> port-forward still running?
   +--> test server still running?
   +--> temporary files remain?
   +--> lock remains?
```

This creates confusing future failures.

# 94. Orphan Processes

An orphan process is a process whose original parent exits while the child remains running.

On Unix-like systems, such processes are adopted/reparented according to the operating system's process-management behavior, commonly to a system process or subreaper.

The important operational lesson is:

> Do not assume child work automatically disappears just because your Bash script exits.

Design lifecycle management deliberately.

---

# 95. Orphaned Resources vs Orphan Processes

These are related but different.

An orphan process is a process whose original parent has exited.

An orphaned resource might be something your script leaves behind, such as:

```text
temporary directory
lock file
PID file
socket
background worker
```

Good cleanup logic prevents unnecessary leftovers.

# 96. PID Files

Some long-running applications store a PID in a file.

Example:

```text

```

or for user-level scripts:

```text

```

The file might contain:

```text

```

But a PID file by itself does not prove the original process is still running.

# 97. Never Trust a PID File Blindly

Dangerous pattern:


without validation.

* stale PID file
* invalid content
* PID reused by another process
* maliciously modified file
* unexpected permissions

PID-based control requires careful ownership and validation.

# 109. Race Conditions

Background execution introduces concurrency.

Concurrency introduces race conditions.

A race condition occurs when behavior depends on timing between operations.

Example:

```bash
generate_file &
process_file
```

If `process_file` expects the generated file to be complete, it may run too early.

Correct synchronization might require:

```bash
generate_file &
pid=$!

wait "$pid"

process_file
```

# 110. Another Race Condition Example

Two background processes both write:

```text

```

at the same time.

You may get:

* overwritten data
* mixed output
* incomplete results
* unpredictable behavior

Parallel tasks should not casually share writable resources without coordination.

# 140. Complete Controlled Background-Job Script

```bash
#!/usr/bin/env bash

jobs_to_run=(
    "configuration-check"
    "dependency-check"
    "health-check"
)

declare -A job_pids=()
declare -A job_logs=()
declare -A job_statuses=()

failed_jobs=()

work_dir=""

log() {
    local level="$1"
    shift

    printf '[%s] [%s] %s\n' \
        "$(date '+%Y-%m-%d %H:%M:%S')" \
        "$level" \
        "$*"
}

run_configuration_check() {
    printf 'Checking configuration...\n'
    sleep 2
    printf 'Configuration valid\n'
    return 0
}

run_dependency_check() {
    printf 'Checking dependencies...\n'
    sleep 3

    if command -v bash > /dev/null 2>&1; then
        printf 'Required dependency found\n'
        return 0
    fi

    printf 'Required dependency missing\n' >&2
    return 1
}

run_health_check() {
    printf 'Running health check...\n'
    sleep 4
    printf 'Health check passed\n'
    return 0
}

run_job() {
    local job="$1"

    case "$job" in
        configuration-check)
            run_configuration_check
            ;;

        dependency-check)
            run_dependency_check
            ;;

        health-check)
            run_health_check
            ;;

        *)
            printf 'ERROR: unknown job: %s\n' "$job" >&2
            return 2
            ;;
    esac
}

start_job() {
    local job="$1"
    local log_file
    local pid

    log_file="$work_dir/$job.log"

    run_job "$job" > "$log_file" 2>&1 &
    pid=$!

    job_pids[$job]="$pid"
    job_logs[$job]="$log_file"

    log INFO "Started $job with PID $pid"
}

start_all_jobs() {
    local job

    for job in "${jobs_to_run[@]}"; do
        start_job "$job"
    done
}

wait_for_job() {
    local job="$1"
    local pid
    local status

    pid="${job_pids[$job]}"

    if wait "$pid"; then
        status=0
    else
        status=$?
    fi

    job_statuses[$job]="$status"

    if (( status == 0 )); then
        log INFO "$job completed successfully"
    else
        log ERROR "$job failed with status $status"
        failed_jobs+=("$job")
    fi
}

wait_for_all_jobs() {
    local job

    for job in "${jobs_to_run[@]}"; do
        wait_for_job "$job"
    done
}

terminate_children() {
    local job
    local pid

    for job in "${jobs_to_run[@]}"; do

        if [[ ! -v 'job_pids[$job]' ]]; then
            continue
        fi

        pid="${job_pids[$job]}"

        if kill -0 "$pid" 2>/dev/null; then
            log WARN "Sending SIGTERM to $job PID $pid"
            kill -TERM "$pid" 2>/dev/null || true
        fi

    done
}

reap_children() {
    local job
    local pid

    for job in "${jobs_to_run[@]}"; do

        if [[ ! -v 'job_pids[$job]' ]]; then
            continue
        fi

        pid="${job_pids[$job]}"

        wait "$pid" 2>/dev/null || true

    done
}

cleanup() {
    local status=$?

    if [[ -n "${work_dir:-}" &&
          -d "$work_dir" &&
          "$work_dir" == /tmp/veriqta-bg.* ]]; then

        rm -rf -- "$work_dir"
    fi

    return "$status"
}

handle_interrupt() {
    trap - INT TERM

    printf '\n' >&2
    log WARN "Interrupt received. Stopping background jobs."

    terminate_children
    reap_children

    exit 130
}

handle_term() {
    trap - INT TERM

    log WARN "SIGTERM received. Stopping background jobs."

    terminate_children
    reap_children

    exit 143
}

print_job_logs() {
    local job
    local log_file

    printf '\nJOB LOGS\n'
    printf '========\n'

    for job in "${jobs_to_run[@]}"; do

        log_file="${job_logs[$job]}"

        printf '\n--- %s ---\n' "$job"

        if [[ -f "$log_file" ]]; then
            cat -- "$log_file"
        else
            printf 'No log file available.\n'
        fi

    done
}

print_summary() {
    local job
    local status

    printf '\nJOB SUMMARY\n'
    printf '===========\n'

    for job in "${jobs_to_run[@]}"; do

        status="${job_statuses[$job]:-unknown}"

        printf '%-24s %s\n' "$job" "$status"

    done

    if (( ${#failed_jobs[@]} == 0 )); then
        printf '\nAll background jobs succeeded.\n'
        return 0
    fi

    printf '\nFailed jobs: %s\n' "${#failed_jobs[@]}"
    printf '  %s\n' "${failed_jobs[@]}"

    return 1
}

main() {
    local final_status

    work_dir="$(mktemp -d '/tmp/veriqta-bg.XXXXXX')" || {
        printf 'ERROR: failed to create temporary workspace\n' >&2
        return 1
    }

    if [[ -z "$work_dir" || ! -d "$work_dir" ]]; then
        printf 'ERROR: temporary workspace is invalid\n' >&2
        return 1
    fi

    trap cleanup EXIT
    trap handle_interrupt INT
    trap handle_term TERM

    log INFO "Starting controlled background jobs"

    start_all_jobs

    wait_for_all_jobs

    print_job_logs

    if print_summary; then
        final_status=0
    else
        final_status=1
    fi

    log INFO "Background job runner finished"

    return "$final_status"
}

main "$@"
exit "$?"
```

# 148. Critical Limitation: A Background Function May Create Descendants

Suppose:

```bash
run_job "$job" &
pid=$!
```

The PID you capture represents the asynchronous job Bash created.

But that job may itself launch additional processes.

Terminating only the recorded PID does not automatically guarantee every descendant disappears in every scenario.

This becomes especially important with:

* pipelines
* wrappers
* shell scripts launching programs
* process trees
* long-running subprocesses

Advanced production lifecycle management may require process groups, supervisors, cgroups, containers, or service managers.

Do not assume one PID always represents an entire workload tree.

# 149. Process Groups

Unix-like systems also organize processes into process groups.

A terminal foreground job may consist of more than one process.

For example:

```bash

```

may involve multiple processes participating in one pipeline.

This helps explain why terminal signals such as Ctrl+C are often associated with a foreground process group rather than only one arbitrary PID.

Process-group management is more advanced than the core beginner requirements here, but you should know the concept exists.

# 150. Production Principle: Use the Right Supervisor

Bash can manage background work.

That does not mean Bash should replace every workload manager.

For a persistent Linux service, consider proper service management.

For containers, use container lifecycle mechanisms.

For Kubernetes workloads, let Kubernetes manage workload lifecycle.

For CI/CD jobs, use the CI platform's job model.

For one-off shell automation, Bash background management may be completely appropriate.

The engineering question is:

> Who should own the lifecycle of this process?

# 168. Troubleshooting: Background Job Disappeared

Problem:

```text
You started a job with &
but cannot find it.
```

Investigate:

```bash

```

Then inspect captured PID:

```bash
ps -p "$pid"
```

Possible causes:

* job completed quickly
* job failed immediately
* PID was not captured
* process terminated
* command never started successfully
* you are looking from another shell and expecting `jobs` to know about it

# 169. Troubleshooting: `wait` Says PID Is Not a Child

`wait` is designed around jobs/children the current shell can wait for.

You cannot generally use Bash `wait` as a universal system-wide process waiter for arbitrary unrelated PIDs.

If you obtained a PID belonging to an unrelated process, `wait "$pid"` may fail.

Track processes you launch.

# 170. Troubleshooting: Ctrl+C Leaves Something Running

Possible causes include:

* child did not receive expected signal
* script did not track child PID
* child created descendants
* signal handler exited without cleanup
* external program changed signal behavior
* process group behavior differs from assumptions

Investigate:

```bash
ps -o pid,ppid,pgid,stat,cmd
```

where supported.

Understand the process tree before blindly killing processes.

# 171. Troubleshooting: SIGTERM Does Nothing

* wrong PID
* process ignores or handles SIGTERM differently
* insufficient permission
* process is in an unusual kernel wait state
* process is not the workload you thought it was

Investigate before escalating.

Check:

```bash

```

Then determine the correct next action.

# 172. Troubleshooting: Temporary Files Remain

* cleanup trap was registered
* cleanup function path validation is correct
* script did not receive SIGKILL
* cleanup itself did not fail
* temporary path matches expected pattern

> SIGKILL cannot be trapped.

If the script receives SIGKILL, its Bash cleanup handler cannot run.

# 177. Security: Process Permissions Matter

You cannot necessarily signal every process on a system.

Linux permissions and privileges matter.

A normal user should not be able to arbitrarily terminate processes owned by unrelated users.

Avoid solving every permission problem with:

```bash
sudo
```

First determine:

```text
Who owns the process?

Why does my script need to manage it?

Should this automation have that privilege?
```

Apply least privilege.

# 178. Security: Validate PIDs

If a PID comes from:

* user input
* file
* network response
* external command

validate it.

Basic numeric validation:

```bash
if [[ ! "$pid" =~ ^[0-9]+$ ]]; then
    printf 'ERROR: invalid PID\n' >&2
    return 2
fi
```

But numeric validation alone does not prove identity.

# 179. Security: Never Treat PID 1 Casually

PID 1 is special on Unix-like systems and especially significant in containers.

Do not write destructive process logic that could accidentally target:

```text
1
```

A safety check might reject unexpected low or critical PIDs depending on the script's purpose.

But do not invent arbitrary PID thresholds without understanding the environment.

Identity validation is more important than simplistic numeric rules.

# 180. Security: Avoid Command Injection in Process Management

Dangerous:

```bash
eval "kill $user_input"
```

Do not use `eval` for ordinary PID handling.

Validate:

```bash
[[ "$pid" =~ ^[0-9]+$ ]]
```

Then pass as a quoted argument:

```bash
kill -TERM "$pid"
```

No `eval` is required.

# Part 13 Summary

You now understand that Bash does not operate in isolation.

Every command exists within the operating system's process model.

Your Bash shell is a process:

```bash
echo "$$"
```

It has a parent:

```bash
echo "$PPID"
```

When Bash launches commands, it can create child processes.

Foreground execution:

```bash
command
```

normally causes Bash to wait.

Background execution:

```bash
command &
```

allows Bash to continue.

The most recent background PID can be captured with:

```bash
pid=$!
```

Multiple PIDs can be tracked using arrays:

```bash
pids+=("$!")
```

Shell jobs can be inspected with:

```bash
jobs
```

and interactively managed with:

```bash
fg
bg
```

Background work should eventually be synchronized with:

```bash
wait "$pid"
```

because:

```text
Process started
      ≠
Process succeeded
```

Processes can be inspected with:

```bash
ps
pgrep
top
```

Signals provide process-control mechanisms.

The core signals from this part are:

```text
SIGTERM
    graceful termination request

SIGKILL
    immediate forced termination

SIGINT
    interactive interruption

SIGHUP
    hangup signal with possible application-specific behavior
```

The normal escalation model is:

```text
Observe
   |
   v
Identify
   |
   v
SIGTERM
   |
   v
Wait
   |
   v
Verify
   |
   v
SIGKILL only if necessary
```

Bash can respond to signals using:

```bash
trap
```

Cleanup can be attached to script exit:

```bash
trap cleanup EXIT
```

This allows scripts to remove temporary resources and perform controlled shutdown.

But SIGKILL cannot be trapped.

Therefore:

```text
SIGKILL
   |
   v
No Bash cleanup opportunity
```

You also learned that background processes create concurrency concerns:

```text
race conditions
shared resources
unlimited parallelism
mixed logs
uncollected failures
orphaned work
```

A reliable background workflow therefore looks like:

```text
Define work
   |
   v
Launch controlled jobs
   |
   v
Capture $!
   |
   v
Store PIDs
   |
   v
Separate logs
   |
   v
wait
   |
   v
Collect statuses
   |
   v
Handle signals
   |
   v
Terminate owned children gracefully
   |
   v
Cleanup
   |
   v
Return meaningful status
```

> Starting a background process is easy. Owning its complete lifecycle is the real engineering work.
