# Part 6: Commit History and Understanding Project Changes

In Part 5, you learned how to control what enters a commit.

Your workflow became:

```text
Change files
    |
    v
git status
    |
    v
git diff
    |
    v
Stage intentionally
    |
    v
git diff --staged
    |
    v
git commit
```

But creating commits is only half of Git.

You also need to understand the history those commits create.

A Git repository is not simply a collection of current files. It is also a record of how the project reached its current state.

That history can answer questions such as:

* Who changed this?
* When was it changed?
* Why was it changed?
* What exactly changed?
* What did the project look like before this change?
* Which commit introduced a problem?
* What was the previous commit?
* How do two commits differ?
* Which commit is HEAD currently referring to?

In this part, you will learn:

* Why commit history matters
* How to use `git log`
* How to read commit history
* What commit IDs are
* How authors and timestamps appear
* How to use `git log --oneline`
* How to use `git show`
* How to inspect specific commits
* How to compare commits
* How HEAD relates to history
* How relative references work
* What `HEAD~1` means
* What `HEAD^` means
* How to write useful commit messages
* What atomic commits are
* Why giant commits create problems
* How to build meaningful project history

# 1. Why Commit History Matters

Imagine a production application has been running successfully for six months.

Then an engineer deploys the latest version.

Suddenly:

```text
Users
  |
  v
Application
  |
  v
500 Internal Server Error
```

The team needs answers.

They may ask:

```text
What changed?

Who changed it?

When?

Why?

Which files changed?

What was the previous configuration?

Can we identify the commit that introduced the problem?
```

Without useful history, answering these questions becomes much harder.

With Git history, engineers can investigate the sequence of changes.

---

# 2. Git History Is More Than Backup

Beginners sometimes think Git history exists mainly so they can recover deleted files.

Recovery is important, but history does much more.

Good commit history provides:

* Change tracking
* Context
* Accountability
* Troubleshooting evidence
* Collaboration history
* Reviewability
* Release information
* Rollback reference points
* Audit information
* Debugging clues

A useful history tells the story of the project.

For example:

```text
Create application structure
        |
        v
Add database connection
        |
        v
Add health check endpoint
        |
        v
Configure production logging
        |
        v
Fix database connection timeout
```

That is much more useful than:

```text
update
   |
   v
changes
   |
   v
fix
   |
   v
stuff
```

# 3. Commit History as an Engineering Timeline

Suppose a project has these commits:

```text
A
Create application

|
v

B
Add PostgreSQL configuration

|
v

C
Add health check endpoint

|
v

D
Increase database connection pool

|
v

E
Fix connection timeout handling
```

Each commit represents a recorded project state.

Together, they create a timeline.

You can inspect:

```text
E
```

to understand the current state.

Or inspect:

```text
C
```

to understand an earlier state.

You can also compare:

```text
C
vs
E
```

to determine what changed between those points.

# 7. What git log Does

The command:

```bash
git log
```

displays commit history reachable from your current position.

At this stage, think:

```text
HEAD
 |
 v
Latest commit
 |
 v
Parent
 |
 v
Parent
 |
 v
First commit
```

`git log` walks backward through this history.

By default, the newest commit appears first.

---

# 8. Reading git log

A normal log entry contains several important pieces of information.

Example:

```text
commit 8f47a28...
Author: Ann <ann@example.com>
Date:   Tue Sep 1 20:30:00 2026

    Update application startup message
```

Break it into:

```text
Commit ID
Author
Timestamp
Commit message
```

Each answers a different question.

---

# 9. Commit ID

The line:

```text
commit 8f47a28...
```

contains the commit's object identifier.

You learned in Part 4 that Git objects have content-derived identifiers.

For everyday Git work, engineers commonly call this:

```text
commit ID
commit hash
SHA
commit SHA
```

The commit ID lets you identify a specific commit.

This matters because commit messages are not guaranteed to be unique.

You could have:

```text
Fix application
Fix application
Fix application
```

But each commit still has a different identifier.

---

# 10. Why Commit IDs Matter

Suppose someone tells you:

> The application broke after commit `8f47a28`.

You can inspect that exact commit.

For example:

```bash
git show 8f47a28
```

The identifier removes ambiguity.

Commit IDs are used when:

* Inspecting commits
* Comparing commits
* Reverting changes
* Creating branches
* Checking out historical states
* Troubleshooting
* Identifying deployed versions
* Discussing changes with teammates

---

# 11. Full and Abbreviated Commit IDs

Git may display a full identifier in:

```bash
git log
```

while:

```bash
git log --oneline
```

usually displays an abbreviated version.

For example:

```text
Full:
8f47a28b14c...

Short:
8f47a28
```

Git can often resolve a sufficiently unique prefix.

That is why you can commonly run:

```bash
git show 8f47a28
```

instead of typing the complete identifier.

---

# 12. Authors

A log entry may contain:

```text
Author: Ann <ann@example.com>
```

This tells you who authored the change according to the commit metadata.

Git gets this information from configuration such as:

```bash
git config user.name
git config user.email
```

This is one reason configuring Git identity correctly matters.

In collaborative projects, author information helps answer:

> Who originally created this change?

---

# 13. Author vs Committer

Git can distinguish between:

```text
Author
```

and:

```text
Committer
```

The **author** is the person who originally wrote the change.

The **committer** is the person who created or applied that particular commit object.

In simple beginner workflows, these are often the same person.

But they can differ.

For example:

```text
Developer creates patch
        |
        v
Maintainer applies patch
```

The developer may be recorded as the author while the maintainer is the committer.

You do not need to manage this manually yet.

Just understand that Git has both concepts.

---

# 14. Timestamps

Git commits also contain time information.

A standard log may show:

```text
Date: Tue Sep 1 20:30:00 2026
```

This helps answer:

```text
When was this commit created?
```

Time information is useful for:

* Incident timelines
* Release investigation
* Auditing
* Understanding development sequence
* Correlating code changes with operational events

But remember something from Part 4:

> Git history structure is not based only on timestamps.

Parent relationships form the commit graph.

---

# 15. Commit Messages

The final visible part of a basic log entry is the commit message.

Example:

```text
Update application startup message
```

The message should explain the purpose of the commit clearly enough that another engineer can understand it later.

Compare:

```text
update
```

with:

```text
Increase API request timeout
```

The second gives useful context immediately.

Suppose:



# 19. Why git log --oneline Is Useful


For quick history inspection:

# 20. Newest Commit First

Suppose:

```bash
git log --oneline
```

returns:

```text

B Add configuration
A Create application
```

The newest commit is shown first.

Conceptually, history is:

```text
A
|
v
B
|
v
C
```

But `git log` displays:

```text
C
B
A
```

because you normally want to inspect recent changes first.

# 21. Introducing git show

`git log` tells you that a commit exists.

But what if you want to inspect the commit itself?

Use:

```bash
git show
```

With no explicit commit supplied:

```bash
git show
```

Git normally shows the commit referred to by HEAD.

In a simple repository, this is usually your latest commit on the current branch.

---

# 22. What git show Displays

Run:

```bash
git show
```

You may see:

```text
commit 8f47a28...
Author: Ann <ann@example.com>
Date: ...

    Update application startup message

diff --git a/app.py b/app.py
...
-print("Application started")
+print("VERIQTA application started")
```

This combines:

```text
Commit metadata
+
Commit message
+
Changes introduced by the commit
```

That makes `git show` extremely useful for investigation.

---

# 23. git log vs git show

Think:

```text
git log
=
Show me the history
```

while:

```text
git show
=
Show me details about a particular Git object, commonly a commit
```

In everyday beginner work:

```bash
git log --oneline
```

helps you find a commit.

Then:

```bash
git show <commit-id>
```

helps you inspect it.

---

# 24. Inspecting a Specific Commit

Run:

```bash
git log --oneline
```

Suppose you see:

```text
8f47a28 Update application startup message
6d291c4 Add application configuration
1ab39f7 Create application entry point
```

To inspect:

```text
6d291c4
```

run:

```bash
git show 6d291c4
```

Git shows information for that specific commit.

This allows you to investigate historical changes without changing your current files.

---

# 25. Inspecting Is Not the Same as Checking Out

This distinction matters.

Running:

```bash
git show 6d291c4
```

does not normally move your working tree to that commit.

It displays information.

Think:

```text
git show
=
inspect
```

not:

```text
git show
=
switch project version
```

This makes it a safe and useful investigation command.

---

# 26. Inspecting Only Commit Metadata

Sometimes you do not want the entire patch.

You can use:

```bash
git show --no-patch <commit-id>
```

Example:

```bash
git show --no-patch 6d291c4
```

This can show commit information without displaying the file differences.

The option:

```text
--no-patch
```

means:

> Do not display the patch/diff portion.

# 27. Inspecting Which Files Changed

A useful summary form is:

```bash
git show --stat <commit-id>
```

Example:

```bash
git show --stat 6d291c4
```

You may see a summary of:

* Files changed
* Insertions
* Deletions

This is useful when you want to understand the size of a change before reading every line.

Suppose production failed shortly after a deployment.

Your release system reports:

```text

```

You can run:

```bash

```

You discover:


# 29. Comparing Commits

Sometimes inspecting one commit is not enough.

You may want to ask:

> What changed between these two points in history?

Git can compare commits using:

```bash
git diff <commit-A> <commit-B>
```

Example:

```bash
git diff 1ab39f7 8f47a28
```

Conceptually:

```text
Commit A
   |
   | compare
   v
Commit C
```

Git displays the differences between the two snapshots.

---

# 30. Why Compare Commits?

Imagine:

```text
Commit A
Known-good production release

Commit B
Current broken release
```

You can compare them:

```bash
git diff <good-commit> <bad-commit>
```

This helps answer:

> What changed between the known-good version and the broken version?

That is a powerful troubleshooting technique.

---

# 31. Example Commit Comparison

Suppose Commit A contains:

```yaml
replicas: 3
image: api:v1.2
```

Commit B contains:

```yaml
replicas: 5
image: api:v1.3
```

Running:

```bash
git diff <A> <B>
```

may show:

```diff
-replicas: 3
-image: api:v1.2
+replicas: 5
+image: api:v1.3
```

You now know both the scaling value and image version changed.

---

# 32. Direction Matters When Comparing

Suppose you run:

```bash
git diff A B
```

Git shows the changes required to move conceptually from A to B.

If you reverse them:

```bash
git diff B A
```

the additions and removals appear reversed.

Example:

```bash
git diff A B
```

might show:

```diff
-port: 8080
+port: 9090
```

while:

```bash
git diff B A
```

may show:

```diff
-port: 9090
+port: 8080
```

The comparison direction matters.

# 33. Understanding HEAD Again

You first learned HEAD in Part 4.

Now we will use it actively with history.

In normal branch-based work:

```text
HEAD
 |
 v
main
 |
 v
Commit C
```

HEAD represents your current checked-out position through the current branch.

If:

```text
main -> Commit C
```

and:

```text
HEAD -> main
```

then HEAD ultimately resolves to Commit C.

---

# 34. Using HEAD as a Commit Reference

Instead of manually copying the latest commit ID, you can often use:

```text
HEAD
```

For example:

```bash
git show HEAD
```

means:

> Show the commit currently identified by HEAD.

Likewise:

```bash
git diff <older-commit> HEAD
```

means:

> Compare that older commit with my current commit.

---

# 35. HEAD Is a Symbolic Reference in Normal Work

Remember:

```text
HEAD
 |
 v
main
 |
 v
C
```

HEAD normally points to a branch reference.

The branch points to the commit.

This is useful because when you create another commit:

```text
A -> B -> C
```

becomes:

```text
A -> B -> C -> D
```

and:

```text
main
```

moves from C to D.

HEAD remains associated with `main`.

---

# 36. What Are Relative References?

Commit IDs are precise, but they can be inconvenient.

Suppose your history is:

```text
A
|
v
B
|
v
C
|
v
D
```

and HEAD is at D.

You want to refer to C.

You could find C's hash.

Or you can describe it relative to HEAD.

Git supports relative references.

For example:

```text
HEAD~1
```

means, in this simple history:

> One first-parent generation before HEAD.

---

# 37. Understanding HEAD~1

Suppose:

```text
A -> B -> C -> D
                   ^
                   |
                  HEAD
```

Then:

```text
HEAD
=
D
```

```text
HEAD~1
=
C
```

```text
HEAD~2
=
B
```

```text
HEAD~3
=
A
```

This gives you a convenient way to navigate backward conceptually.

---

# 38. Using HEAD~1

Run:

```bash
git show HEAD~1
```

This shows the commit one first-parent step before HEAD.

You can also compare:

```bash
git diff HEAD~1 HEAD
```

This asks:

> What changed between the previous first-parent commit and the current commit?

In a simple linear history, that effectively shows the changes introduced by the latest commit.

---

# 39. HEAD~2

If history is:

```text
A -> B -> C -> D
                   ^
                   HEAD
```

then:

```text
HEAD~2
```

means:

```text
B
```

You can inspect it:

```bash
git show HEAD~2
```

Or compare it:

```bash
git diff HEAD~2 HEAD
```

This compares the project state two first-parent generations ago with the current state.

---

# 40. What Does the Tilde Mean?

At a beginner-friendly level:

```text
~N
```

means:

> Follow the first-parent relationship backward N times.

So:

```text
HEAD~1
```

follows one first-parent step.

```text
HEAD~2
```

follows two.

```text
HEAD~3
```

follows three.

The phrase **first parent** becomes important when merges appear later.

---

# 41. Introducing the Caret: HEAD^

Git also supports:

```text
HEAD^
```

In a simple linear history:

```text
HEAD^
```

refers to HEAD's first parent.

Therefore, in a simple history:

```text
HEAD^
```

and:

```text
HEAD~1
```

usually identify the same commit.

---

# 42. HEAD^ vs HEAD~1

Suppose:

```text
A -> B -> C
              ^
              HEAD
```

Then:

```text
HEAD^
=
B
```

and:

```text
HEAD~1
=
B
```

So why have both?

Because they become different in meaning when a commit has multiple parents.

That happens with merge commits.

---

# 43. Why the Caret Exists

A normal commit usually has one parent:

```text
C
|
v
B
```

But a merge commit can have multiple parents.

Conceptually:

```text
A---B------M
     \    /
      C--D
```

The merge commit:

```text
M
```

may have:

```text
Parent 1
Parent 2
```

Caret syntax can select a particular parent.

For example:

```text
M^1
```

means first parent.

```text
M^2
```

means second parent.

You do not need to master merge-parent navigation yet.

Merging comes later.

For now, understand why `^` exists.

---

# 44. Tilde vs Caret Mental Model

A useful beginner model:

```text
~
walk backward through first parents
```

while:

```text
^
select a parent
```

In a straight history:

```text
A -> B -> C -> D
```

these can appear similar.

But in a branching history, their purpose becomes clearer.

---

# 45. Useful Relative Reference Examples

Show current commit:

```bash
git show HEAD
```

Show previous first-parent commit:

```bash
git show HEAD~1
```

Equivalent in a simple linear history:

```bash
git show HEAD^
```

Show two first-parent generations back:

```bash
git show HEAD~2
```

Compare previous first-parent commit to current:

```bash
git diff HEAD~1 HEAD
```

Compare two first-parent generations ago to current:

```bash
git diff HEAD~2 HEAD
```

---

# 46. Relative References Prevent Copying Hashes Constantly

Without relative references:

```bash
git log --oneline
```

find:

```text
6d291c4
```

then:

```bash
git show 6d291c4
```

With relative references:

```bash
git show HEAD~1
```

This can be faster when you know the commit's relationship to your current position.

---

# 47. Do Not Guess Relative References

Before using something such as:

```text
HEAD~5
```

make sure the history actually contains enough first-parent generations.

You can inspect:

```bash
git log --oneline
```

first.

Git will report an error if the reference cannot be resolved.

Do not interpret that as repository corruption.

It may simply mean the requested ancestor does not exist.

# 48. Commit Messages Are Part of History

Now we move from inspecting history to improving it.

Consider:

```text
3a12b91 update
8c71f22 fix
10ac430 changes
62b831d stuff
```

Technically, this is Git history.

But it is poor engineering history.

Months later, these messages provide almost no useful context.

---

# 49. What Should a Commit Message Do?

A useful commit message should help answer:

> What meaningful change does this commit introduce?

For example:

Bad:

```text
fix
```

Better:

```text
Fix API timeout handling
```

Bad:

```text
update config
```

Better:

```text
Increase worker timeout to 60 seconds
```

Bad:

```text
changes
```

Better:

```text
Add health check endpoint
```

---

# 50. Write Messages for Future Readers

Do not write only for yourself right now.

Write for:

```text
You six months later

A teammate

A reviewer

An incident responder

A future maintainer
```

Imagine seeing:

```text
Fix stuff
```

during a production incident at 2 AM.

It tells you almost nothing.

Now compare:

```text
Prevent API crash when Redis connection times out
```

That immediately gives useful context.

---

# 51. Useful Commit Subject Style

A common convention is to write concise imperative-style subjects.

Examples:

```text
Add health check endpoint

Fix Redis timeout handling

Remove obsolete deployment script

Update production logging configuration

Document local development setup
```

These read naturally as:

> This commit will...

```text
Add health check endpoint

Fix Redis timeout handling

Remove obsolete deployment script
```

This style is clear and widely used.

---

# 52. Avoid Meaningless Messages

Avoid messages such as:

```text
update
updates
changes
fix
fixes
stuff
work
final
final2
working
test
new
misc
```

They provide almost no explanation.

The commit ID tells Git which commit it is.

The message should help humans understand why they care.

---

# 53. Commit Subject vs Detailed Message

So far you have used:

```bash
git commit -m "Add application configuration"
```

This creates a short commit message.

For more significant changes, a commit message can contain:

```text
Short subject

Longer explanation
```

For example:

```text
Fix API timeout handling

Return a controlled 504 response when the upstream payment
service exceeds the configured timeout instead of allowing the
request worker to fail unexpectedly.
```

The subject summarizes.

The body provides context.

---

# 54. When a Longer Message Helps

A longer commit message can be useful when the change needs explanation.

For example:

```text
Why was this unusual configuration chosen?

What production problem was being solved?

Why was the previous approach unsafe?

What tradeoff was accepted?
```

Do not write long commit messages simply to make them look professional.

Add detail when it improves understanding.

---

# 55. Explain Why, Not Just What the Diff Already Shows

Suppose the diff clearly shows:

```diff
-timeout: 30
+timeout: 60
```

A weak message is:

```text
Change timeout from 30 to 60
```

The diff already tells us that.

A more useful message might be:

```text
Increase API timeout for slow payment responses
```

Now the history tells us why the value changed.

---

# 56. What Is an Atomic Commit?

An **atomic commit** represents one logical change.

Think:

```text
One commit
=
One coherent purpose
```

For example:

```text
Fix API timeout handling
```

might involve:

```text
api.py
timeout.py
tests/test_timeout.py
```

Multiple files can still belong to one atomic commit if they all support the same logical change.

Atomic does not mean:

```text
one file per commit
```

It means:

```text
one logical unit of work per commit
```

---

# 57. Example of an Atomic Commit

Suppose a feature requires:

```text
app.py
Add /health endpoint

tests/test_health.py
Add health endpoint test

README.md
Document health endpoint
```

These changes all support:

```text
Add health check endpoint
```

They may reasonably belong in one commit.

The commit is still atomic because all changes serve one purpose.

---

# 58. Example of a Non-Atomic Commit

Suppose one commit contains:

```text
Fix login bug

Upgrade database version

Rewrite README

Change Kubernetes replicas

Add new monitoring dashboard

Rename unrelated files
```

These changes have unrelated purposes.

The commit is not logically atomic.

If something goes wrong, it becomes harder to identify or reverse only the relevant change.

---

# 59. Why Atomic Commits Matter

Atomic commits improve:

* Code review
* Troubleshooting
* Reverting
* History readability
* Collaboration
* Release investigation
* Cherry-picking
* Auditing

Imagine an incident is caused by:

```text
Change Kubernetes memory limit
```

If that change has its own commit, it is easy to identify.

If it is buried inside:

```text
Massive Friday update
```

with 47 unrelated changes, investigation becomes harder.

---

# 60. Atomic Does Not Mean Tiny for the Sake of Tiny

Do not misunderstand atomic commits.

Bad extreme:

```text
Commit 1:
Add one line

Commit 2:
Add another line

Commit 3:
Rename variable

Commit 4:
Add comment
```

when all four actions are inseparable parts of one simple change.

The goal is not maximum commit count.

The goal is logical separation.

Ask:

> Does this commit represent one coherent reason for change?

---

# 61. Why Giant Commits Cause Problems

Imagine a commit changes:

```text
82 files
4,000 lines
Terraform
Kubernetes
Application code
Documentation
CI/CD
Monitoring
```

Maybe that size is necessary for a major migration.

But often it indicates unrelated work was bundled together.

Giant commits create several problems.

---

# 62. Problem 1: Difficult Review

A reviewer sees:

```text
4,000 changed lines
```

It becomes harder to understand:

* What matters
* What is unrelated
* What introduces risk
* What should be tested
* What might be wrong

Smaller logical commits can make review easier.

---

# 63. Problem 2: Difficult Troubleshooting

Suppose production fails after:

```text
Commit X
```

and Commit X changed:

```text
Database settings
Kubernetes resources
API code
DNS configuration
Monitoring
```

Which change caused the incident?

The investigation surface is huge.

Compare that with separate commits:

```text
A Update database connection pool

B Increase API memory limit

C Add readiness probe

D Update Grafana dashboard
```

History gives much better clues.

---

# 64. Problem 3: Difficult Reverts

Suppose one giant commit contains:

```text
Useful feature
+
Dangerous infrastructure change
+
Documentation
```

You want to reverse only the dangerous infrastructure change.

But the commit bundles everything.

Reverting it may reverse useful work too.

Atomic commits make selective reversal easier.

---

# 65. Problem 4: Poor Collaboration

Teammates reviewing a giant commit may struggle to understand intent.

Useful history should allow another engineer to scan:

```bash
git log --oneline
```

and quickly understand how the project evolved.

---

# 66. Problem 5: Weak Incident Evidence

During an incident, engineers often ask:

```text
What changed recently?
```

A history like:

```text
a123 Add readiness probe
b456 Increase Redis timeout
c789 Update worker memory limit
```

is useful.

A history like:

```text
a123 updates
b456 stuff
c789 changes
```

is not.

# 67. Build Commits Intentionally With the Staging Area

Part 5 taught you why the staging area matters.

Suppose you modify:

```text
app.py
README.md
terraform/database.tf
```

for three unrelated reasons.

Do not automatically run:

```bash
git add -A
```

and create:

```text
Update project
```

Instead, inspect:

```bash
git status
git diff
```

Then stage logically related work.

Example:

```bash
git add app.py
git commit -m "Fix application startup validation"
```

Then:

```bash
git add README.md
git commit -m "Document local startup requirements"
```

Then, after verifying the infrastructure change:

```bash
git add terraform/database.tf
git diff --staged
git commit -m "Increase database connection limit"
```

Now history has structure.

---

# 68. Partial Staging Helps Build Atomic Commits

Sometimes unrelated changes exist inside the same file.

Suppose:

```text
app.py
```

contains:

```text
Change A:
Fix authentication bug

Change B:
Add unrelated debug logging
```

You can use:

```bash
git add -p
```

to stage selected hunks.

This lets you build an atomic commit even when your working tree became messy.

The staging area is therefore not merely:

```text
the place before commit
```

It is a tool for designing history.

# 69. Meaningful History Is Designed

Good history usually does not happen accidentally.

A disciplined engineer asks:

```text
What logical change did I make?

Which files belong to it?

Which changes do not belong?

What message explains the purpose?

Does the staged diff match that purpose?
```

Then:

```bash
git diff --staged
```

provides the final check.

---

# 70. A Strong Commit Workflow

A useful workflow is:

```text
1. Make changes

2. Run git status

3. Inspect git diff

4. Identify one logical change

5. Stage only that change

6. Run git diff --staged

7. Verify the staged content

8. Write a meaningful commit message

9. Commit

10. Verify git status

11. Inspect history when useful
```

Commands might look like:

```bash
git status
git diff
git add app.py tests/test_app.py
git diff --staged
git commit -m "Fix startup configuration validation"
git status
git log --oneline
```

# 90. Security and History

Commit history deserves security awareness.

Never assume:

> I can commit a secret now and delete it in the next commit.

If a secret enters committed history, deleting the file later does not necessarily erase the old commit containing that secret.

Examples include:

```text
API keys
Passwords
Private keys
Cloud credentials
Database credentials
Tokens
```

If a real secret is committed and exposed, treat it as potentially compromised and rotate/revoke it.

Good history should not contain secrets.

# 101. Part 6 Final Recap

You now know how to move backward through Git history instead of thinking only about the current files.

Your project history can be visualized as:

```text
Commit A
Create project
    |
    v
Commit B
Add configuration
    |
    v
Commit C
Add health check
    |
    v
Commit D
Fix timeout handling
```

You can inspect that history using:

```bash
git log
```

or the compact form:

```bash
git log --oneline
```

You can inspect the current commit:

```bash
git show HEAD
```

or a specific commit:

```bash
git show <commit-id>
```

You can compare snapshots:

```bash
git diff <commit-A> <commit-B>
```

And you can navigate history relative to your current position:

```text
HEAD
Current commit

HEAD~1
One first-parent generation back

HEAD~2
Two first-parent generations back

HEAD^
First parent of HEAD
```

In a simple linear history:

```text
A -> B -> C -> D
                   ^
                   HEAD
```

you can think:

```text
HEAD    = D
HEAD~1  = C
HEAD^   = C
HEAD~2  = B
HEAD~3  = A
```

But the technical distinction matters:

```text
~
walks through first-parent ancestry

^
selects a parent
```

That distinction becomes important once merges enter your history.

Most importantly, you learned that creating commits is not simply about saving work.

You are building a historical record.

A poor history looks like:

```text
update
  |
  v
fix
  |
  v
stuff
  |
  v
changes
```

A meaningful history looks like:

```text
Create application structure
        |
        v
Add database configuration
        |
        v
Add health check endpoint
        |
        v
Configure production logging
        |
        v
Fix Redis timeout handling
```

To build that history:

```text
MAKE CHANGES
      |
      v
INSPECT
git status
git diff
      |
      v
IDENTIFY ONE LOGICAL CHANGE
      |
      v
STAGE INTENTIONALLY
      |
      v
REVIEW
git diff --staged
      |
      v
COMMIT WITH A USEFUL MESSAGE
      |
      v
VERIFY
      |
      v
BUILD MEANINGFUL HISTORY
```

That is the shift from simply knowing Git commands to using Git as an engineering tool.
