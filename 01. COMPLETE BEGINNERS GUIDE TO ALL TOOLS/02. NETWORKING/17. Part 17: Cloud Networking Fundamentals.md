# Part 17: Cloud Networking Fundamentals

## Translate Traditional Networking Into AWS, Azure, and Modern Cloud Environments

By this point, you already understand the fundamental building blocks of networking:

```text
IP addresses
Subnets
CIDR
Routing
Default gateways
DNS
NAT
Firewalls
TCP/UDP
HTTP/HTTPS
Load balancers
```

Cloud networking does **not** replace these concepts.

Instead, cloud platforms virtualize and automate them.

A traditional environment might look like:

```text
Internet
   |
   v
Physical Router
   |
   v
Physical Firewall
   |
   v
Physical Switch
   |
   +--> Web Server
   +--> Application Server
   +--> Database Server
```

A cloud environment may look like:

```text
Internet
   |
   v
Cloud Edge
   |
   v
Virtual Network
   |
   +--> Public Subnet
   |       |
   |       v
   |   Load Balancer
   |
   +--> Private App Subnet
   |       |
   |       v
   |   Application
   |
   +--> Private DB Subnet
           |
           v
        Database
```

The underlying networking principles remain familiar.

The implementation changes.

That is the central idea of this part:

> Cloud networking is traditional networking implemented through software-defined, provider-managed infrastructure.

---

# 1. What Changes in Cloud Networking?

In a physical data center, you may work directly with:

```text
Routers
Switches
Firewalls
Cables
VLANs
Physical interfaces
```

In cloud environments, much of that infrastructure is abstracted.

Instead, you configure logical resources such as:

```text
Virtual networks
Subnets
Route tables
Security groups
Network ACLs
Gateways
Load balancers
Private endpoints
Public IP resources
VPN gateways
```

You may never see the physical router carrying your packet.

But routing still happens.

---

# 2. What Does Not Change?

These concepts still matter:

```text
Source IP
Destination IP
CIDR
Subnet boundaries
Routes
Next hops
Ports
Protocols
TCP state
DNS
NAT
Firewalls
Return paths
```

If an application cannot connect to a database in AWS or Azure, you still ask:

```text
What source is connecting?

What destination?

What port?

What route should the packet take?

What security controls exist?

Can the destination respond?

Can the response return?
```

Cloud networking changes the interface, not the underlying logic.

---

# 3. Software-Defined Networking

Cloud networking relies heavily on software-defined networking.

Instead of physically connecting:

```text
Server A
   |
Cable
   |
Switch
```

you define network relationships through cloud configuration and APIs.

Conceptually:

```text
Cloud Control Plane
       |
       v
Virtual Network Configuration
       |
       +--> Subnets
       +--> Routes
       +--> Security
       +--> Gateways
```

The provider implements those configurations using its infrastructure.

---

# 4. Cloud Networking Is API-Driven

Cloud networks can be created through:

```text
Web console
CLI
SDK
Terraform
CloudFormation
Bicep
ARM templates
Other infrastructure-as-code tools
```

This changes network operations significantly.

A network configuration becomes something you can:

```text
Version
Review
Automate
Deploy
Audit
Reproduce
```

This is one reason networking knowledge is extremely valuable in DevOps and platform engineering.

---

# 5. Cloud Networking Introduces Shared Responsibility

The cloud provider manages much of the physical infrastructure.

You manage your logical configuration.

For example, the provider may manage:

```text
Physical routers
Physical switches
Data-center cabling
Hardware redundancy
Underlying virtualization
```

You may be responsible for:

```text
CIDR design
Subnets
Routes
Security groups
Network ACLs
Public exposure
Private connectivity
DNS
Firewall policy
Application architecture
```

The exact responsibility boundary depends on the service.

# Virtual Networks

# 6. What Is a Virtual Network?

A virtual network is a logically isolated network environment inside a cloud platform.

Think of it as:

```text
Your private networking space
inside the cloud provider.
```

You normally choose an IP address range for it.

Example:

```text
10.20.0.0/16
```

Then divide that address space into smaller subnets.

---

# 7. Traditional Network vs Cloud Virtual Network

Traditional:

```text
Physical Network
10.20.0.0/16
```

Cloud:

```text
Virtual Network
10.20.0.0/16
```

Both use:

```text
IP addressing
CIDR
Subnets
Routes
Network policies
```

The cloud implementation is virtualized.

---

# AWS VPC

# 8. What Is an AWS VPC?

In AWS, the fundamental virtual networking construct is the:

```text
VPC
```

which stands for:

```text
Virtual Private Cloud
```

A VPC provides a logically isolated network in which AWS resources can operate.

Example:

```text
AWS VPC

10.20.0.0/16
```

Inside it, you might create:

```text
10.20.1.0/24
10.20.2.0/24
10.20.11.0/24
10.20.12.0/24
```

---

# 9. VPC Mental Model

Think:

```text
AWS Account
    |
    v
VPC
10.20.0.0/16
    |
    +--> Subnet A
    |
    +--> Subnet B
    |
    +--> Route Tables
    |
    +--> Security Controls
    |
    +--> Gateways
```

The VPC defines a networking boundary.

It does not automatically mean every resource inside it should communicate freely.

# Azure VNet

# 10. What Is an Azure VNet?

Azure's comparable fundamental construct is the:

```text
Virtual Network
```

commonly called:

```text
VNet
```

Example:

```text
Azure VNet

10.30.0.0/16
```

You divide the VNet into subnets and attach resources according to your architecture.

---

# 11. AWS VPC vs Azure VNet

At a beginner conceptual level:

```text
AWS
VPC
```

and:

```text
Azure
VNet
```

both represent logically isolated cloud networking environments.

They are not identical products.

Their:

```text
Routing behavior
Security controls
Gateway architecture
Private connectivity
DNS integration
Service capabilities
```

have provider-specific differences.

Learn the common networking principles first, then learn provider-specific implementation.

# Cloud CIDR Planning

# 12. CIDR Planning Still Matters

Suppose you create:

```text
VPC A
10.0.0.0/16
```

and later create:

```text
VPC B
10.0.0.0/16
```

Everything appears fine while they remain isolated.

Later you want:

```text
VPC A <----> VPC B
```

Now you have overlapping address spaces.

That can make straightforward routing between them difficult or impossible without redesign, translation, or other architecture.

---

# 13. Plan Before Creating Networks

Before assigning CIDRs, consider:

```text
Current workloads
Future growth
Other cloud networks
Corporate networks
VPN networks
Kubernetes Pod CIDRs
Kubernetes Service CIDRs
Acquisitions
Development environments
Testing environments
Disaster-recovery networks
```

Do not choose `10.0.0.0/16` everywhere simply because it is familiar.

---

# 14. Example Address Plan

Suppose the organization reserves:

```text
10.0.0.0/8
```

internally.

You might allocate:

```text
AWS Production
10.10.0.0/16

AWS Development
10.20.0.0/16

Azure Production
10.30.0.0/16

Azure Development
10.40.0.0/16

Corporate Network
10.50.0.0/16
```

This is only an example.

Real enterprise IP address management requires more careful planning.

---

# 15. Why Overlap Becomes Painful

Suppose:

```text
AWS VPC
10.10.0.0/16
```

and:

```text
Corporate Network
10.10.0.0/16
```

A server in AWS needs to reach:

```text
10.10.20.50
```

Which network contains it?

The destination could appear to be local to the cloud network even though you intended it to exist across the VPN.

This is fundamentally a routing ambiguity.

---

# 16. Cloud CIDRs Should Leave Room for Growth

Suppose your VPC is:

```text
10.20.0.0/24
```

You only have 256 total IPv4 addresses in that CIDR before provider-specific reservations and architecture are considered.

If your environment later requires:

```text
Web subnets
Application subnets
Database subnets
Load balancers
Container nodes
Private endpoints
Additional zones
Management resources
```

you may discover that the original address plan was too small.

# Subnets

# 17. Cloud Subnets

A cloud subnet divides part of the virtual network's address space.

Example:

```text
VPC
10.20.0.0/16

        |
        +--> 10.20.1.0/24
        |
        +--> 10.20.2.0/24
        |
        +--> 10.20.11.0/24
        |
        +--> 10.20.12.0/24
```

Subnets help organize:

```text
Address allocation
Routing
Availability-zone placement
Security architecture
Workload tiers
```

---

# 18. AWS Subnets and Availability Zones

In AWS, a subnet belongs to one Availability Zone.

Conceptually:

```text
VPC 10.20.0.0/16
       |
       +--> AZ-A
       |     |
       |     +--> Subnet 10.20.1.0/24
       |
       +--> AZ-B
             |
             +--> Subnet 10.20.2.0/24
```

If you want workloads across multiple Availability Zones, you create subnets in those zones.

---

# 19. Azure Subnets

Azure VNets are regional resources, and subnets are defined within the VNet's address space.

Azure's failure-domain and availability architecture differs from AWS.

Do not assume an AWS subnet-to-AZ rule applies identically to Azure.

This is an important cloud-learning habit:

> Transfer networking concepts between providers, but verify provider-specific implementation.

---

# Public Subnets

# 20. What Is a Public Subnet?

The phrase "public subnet" is commonly used to describe a subnet whose routing and surrounding configuration allow appropriate resources to communicate with the Internet directly through the cloud's Internet-facing gateway architecture.

In AWS, a typical conceptual public-subnet route table contains:

```text
10.20.0.0/16 -> local

0.0.0.0/0 -> Internet Gateway
```

But this route alone does not magically make every resource publicly reachable.

---

# 21. Public Subnet Does Not Mean Every Instance Is Public

Suppose an EC2 instance exists in a subnet with:

```text
0.0.0.0/0 -> Internet Gateway
```

For direct IPv4 Internet communication, other requirements may include:

```text
Public IPv4 address
Security-group permissions
Network ACL permissions
Correct routing
Application listener
```

So:

```text
Public subnet
```

does not mean:

```text
Everything is exposed.
```

---

# Private Subnets

# 22. What Is a Private Subnet?

A private subnet generally describes a subnet whose workloads do not have a direct Internet-facing route for direct inbound/outbound Internet communication through an Internet gateway.

Example:

```text
Private App Subnet
10.20.11.0/24
```

A server may have only:

```text
10.20.11.25
```

as its normal workload address.

It can still communicate with other private resources.

---

# 23. Private Does Not Mean Isolated

A private subnet may communicate with:

```text
Other subnets
Databases
Internal load balancers
NAT gateways
VPN-connected networks
Peered networks
Private endpoints
Transit networks
```

depending on routes and security policies.

"Private" does not mean "cannot communicate."

---

# 24. Public vs Private Mental Model

Simplified:

```text
PUBLIC SUBNET

Workload
   |
   v
Route Table
   |
   v
Internet Gateway
   |
   v
Internet
```

Private:

```text
PRIVATE SUBNET

Workload
   |
   v
Route Table
   |
   v
Private destinations
```

Private outbound Internet access may be added through NAT.

# Route Tables

# 25. Cloud Route Tables

Cloud route tables contain rules describing where packets should go.

Conceptually:

```text
Destination          Next Hop

10.20.0.0/16         Local
0.0.0.0/0            Internet Gateway
```

or:

```text
Destination          Next Hop

10.20.0.0/16         Local
0.0.0.0/0            NAT Gateway
10.50.0.0/16         VPN
```

The exact route-table model varies by cloud provider.

---

# 26. Longest Prefix Match Still Matters

Suppose:

```text
10.50.0.0/16 -> VPN
0.0.0.0/0    -> NAT Gateway
```

Destination:

```text
10.50.20.10
```

The `/16` route is more specific than `/0`.

Therefore the VPN route is selected.

The existence of a default route does not override more-specific routes.

---

# 27. Cloud Route Tables Are Not Firewalls

This is critical.

A route says:

```text
Where should this traffic go?
```

A firewall/security policy says:

```text
Should this traffic be permitted?
```

You can have a perfect route and still have blocked traffic.

You can also have permissive firewall rules and no valid route.

---

# 28. Route Association Matters

Suppose you modify:

```text
Route Table A
```

but your failing subnet uses:

```text
Route Table B
```

Nothing changes.

Always verify which route table actually applies to the source or destination architecture.

---

# Internet Gateways

# 29. Internet Gateway Concept

An Internet gateway connects a virtual cloud network to Internet-facing connectivity according to the provider's architecture.

In AWS, the Internet Gateway is commonly abbreviated:

```text
IGW
```

Conceptually:

```text
VPC
 |
 v
Internet Gateway
 |
 v
Internet
```

---

# 30. AWS Public Route Example

A public AWS subnet may have:

```text
Destination       Target

10.20.0.0/16      local
0.0.0.0/0         igw-xxxx
```

The default route sends non-more-specific IPv4 traffic toward the Internet Gateway.

---

# 31. An Internet Gateway Is Not a NAT Gateway

These are different components.

Conceptually:

```text
Internet Gateway
```

provides Internet connectivity for appropriately configured VPC resources.

A:

```text
NAT Gateway
```

is commonly used to provide outbound connectivity for private IPv4 resources while avoiding direct unsolicited inbound initiation toward those private resources through that NAT mapping.

Do not use the terms interchangeably.

---

# NAT Gateways

# 32. Why Private Workloads May Need NAT

Suppose:

```text
Private App Server
10.20.11.25
```

needs to download:

```text
Operating-system updates
Application packages
Container images
External API data
```

It needs outbound Internet connectivity.

But you do not want to assign it a public IPv4 address.

A NAT architecture can solve this.

---

# 33. NAT Gateway Flow

Conceptually:

```text
Private App Server
10.20.11.25
      |
      v
Private Route Table
      |
      | 0.0.0.0/0
      v
NAT Gateway
      |
      v
Internet-facing path
      |
      v
Internet
```

The external destination sees the translated public source rather than:

```text
10.20.11.25
```

---

# 34. AWS NAT Gateway Architecture

A common AWS IPv4 pattern is:

```text
Private Subnet
     |
     | 0.0.0.0/0
     v
NAT Gateway
     |
     v
Public Subnet
     |
     v
Internet Gateway
     |
     v
Internet
```

The NAT gateway itself is placed in a public subnet for public Internet egress in this architecture.

---

# 35. NAT Gateway Does Not Make Private Instances Public

This is an important distinction.

A private server can initiate:

```text
Private Server -> Internet
```

and receive responses associated with those translated connections.

But an arbitrary Internet client cannot normally initiate:

```text
Internet -> NAT Gateway -> Private Server
```

as though the NAT gateway were a public load balancer.

NAT is not an inbound application publishing mechanism.

---

# 36. NAT Is Not a Load Balancer

A NAT gateway primarily solves address translation/connectivity requirements.

A load balancer primarily distributes traffic to backend targets.

Do not confuse:

```text
NAT Gateway
```

with:

```text
Application Load Balancer
```

or other load-balancing services.

---

```text
10.20.21.50
```

Remember:


# Elastic and Static Public IP Concepts

# 40. Dynamic Public Address Problem

Some cloud resources can receive public addresses that may change as resources are stopped, recreated, or reconfigured, depending on service behavior.

If an external partner requires:

```text
Allow traffic only from 203.0.113.50
```

a changing public IP can be problematic.

---

# 41. Static Public Address Concept

Cloud platforms provide mechanisms for reserving or assigning stable public addresses.

AWS commonly uses the concept:

```text
Elastic IP address
```

Azure provides:

```text
Public IP
```

resources that can be configured with appropriate allocation behavior.

Exact lifecycle and billing rules are provider-specific.

---

# 42. Why Stable Public IPs Matter

Examples:

```text
Partner allowlists
VPN endpoints
Legacy integrations
Fixed DNS requirements
Controlled outbound egress
```

But do not assign static public IPs to every server without architectural justification.

# Security Groups

# 43. AWS Security Groups

AWS security groups are stateful virtual firewall controls associated with supported resources/network interfaces.

Rules can consider:

```text
Protocol
Port
Source
Destination for outbound rules
```

Example inbound rule:

```text
TCP 443
Source: 0.0.0.0/0
```

might be appropriate for a deliberately public HTTPS endpoint.

---

# 44. Security Groups Are Stateful

Suppose inbound traffic is permitted:

```text
Client -> Server:443
```

The return traffic associated with that allowed connection is handled through stateful behavior.

You do not generally create a separate inbound-style reverse rule merely for the response traffic.

This is different from stateless filtering.

---

# 45. Security Groups and Least Privilege

Bad application-tier rule:

```text
TCP 8080
Source: 0.0.0.0/0
```

if only the load balancer should reach the application.

Better architecture may restrict the application to the load-balancer security context.

Conceptually:

```text
Internet
   |
   v
LB Security Group
Allows 443 from Internet
   |
   v
App Security Group
Allows 8080 only from LB tier
```

This is much closer to least privilege.

---

# 46. Database Security

Suppose PostgreSQL listens on:

```text
5432
```

Do not automatically allow:

```text
0.0.0.0/0 -> TCP 5432
```

A better architecture might be:

```text
Database Security Group

Allow TCP 5432
Source:
Application Security Group
```

Conceptually:

```text
Internet
   X
Database

Application
   |
   | TCP 5432
   v
Database
```

---

# Network ACLs

# 47. AWS Network ACL Concept

AWS Network ACLs, commonly:

```text
NACLs
```

provide subnet-level stateless filtering.

They differ from security groups.

Simplified:

```text
Security Group
-> resource/interface-oriented
-> stateful

Network ACL
-> subnet boundary-oriented
-> stateless
```

---

# 48. Stateless Filtering Changes Troubleshooting

Because NACLs are stateless, you need to consider traffic in both directions.

For a TCP connection:

```text
Client
   |
   | SYN
   v
Server
```

the response:

```text
Server
   |
   | SYN-ACK
   v
Client
```

must also be permitted according to applicable rules.

Ephemeral ports therefore become relevant.

---

# 49. Security Group vs NACL

| Feature             | AWS Security Group                 | AWS NACL                             |
| ------------------- | ---------------------------------- | ------------------------------------ |
| Scope               | Supported resource/interface level | Subnet level                         |
| Stateful            | Yes                                | No                                   |
| Allow rules         | Yes                                | Yes                                  |
| Explicit deny rules | No                                 | Yes                                  |
| Rule processing     | Provider-specific SG semantics     | Numbered/order-based NACL evaluation |

Do not transfer this exact model blindly to Azure.

Azure has its own security constructs and behavior.

---

# 50. Azure Network Security Groups

Azure Network Security Groups, or NSGs, provide network traffic filtering for supported Azure networking scopes such as network interfaces and subnets.

Rules consider concepts such as:

```text
Source
Destination
Protocol
Port
Priority
Action
```

Again, learn Azure's own implementation rather than assuming an AWS security group and Azure NSG are identical.

```text
Managed databases

Private endpoints
Service discovery
Hybrid connectivity
```

You should avoid building architectures that depend unnecessarily on hard-coded IP addresses.

---

# 52. Public Cloud DNS

Public DNS might map:

```text
app.example.com
```

to a cloud load-balancing endpoint.

Conceptually:

```text
app.example.com
      |
      v
Cloud Load Balancer
      |
      v
Application
```

AWS provides Route 53.

Azure provides Azure DNS.

---

# 53. Private DNS

Cloud platforms also support private DNS scenarios.

Example:

```text
db.internal.example
```

might resolve only from inside:

```text
VPC
VNet
Connected network
VPN
```

Public Internet users may receive no useful record.

That is intentional.

---

# 54. Split DNS in Cloud

You may have:

```text
api.example.com
```

resolve publicly to:

```text
203.0.113.20
```

but internally to:

```text
10.20.10.20
```

depending on DNS architecture.

When DNS results differ between:

```text
Laptop
VPN
Cloud VM
Container
```

do not immediately assume DNS is broken.

Check which DNS view each client uses.

# VPC and VNet Peering

# 55. Why Connect Virtual Networks?

Suppose:

```text
VPC A
10.10.0.0/16
```

contains the web application.

Another network:

```text
VPC B
10.20.0.0/16
```

contains analytics services.

They need private communication.

One possible solution is:

```text
Peering
```

---

# 56. Peering Concept

Conceptually:

```text
VPC A
10.10.0.0/16
   |
   | Peering
   |
VPC B
10.20.0.0/16
```

Traffic can use private connectivity according to routing and security configuration.

---

# 57. Peering Requires More Than Creating the Relationship

A common beginner mistake is:

```text
Peering exists.

Therefore connectivity must work.
```

Not necessarily.

You may still need correct:

```text
Routes
Security rules
DNS configuration
Non-overlapping address space
Service listeners
```

---

# 58. Peering and CIDR Overlap

Suppose:

```text
VPC A
10.10.0.0/16

VPC B
10.10.0.0/16
```

Traditional routing cannot cleanly distinguish the identical destination ranges.

This is another reason CIDR planning should happen early.

---

# 59. Peering Is Commonly Non-Transitive

Consider:

```text
VPC A <----> VPC B <----> VPC C
```

Do not automatically assume:

```text
VPC A <----> VPC C
```

works through B.

Peering implementations commonly do not provide general transitive routing.

This becomes important as environments grow.

---

# Transit Networking

# 60. The Peering Mesh Problem

Suppose you have:

```text
VPC A
VPC B
VPC C
VPC D
VPC E
```

Connecting everything directly can create many relationships.

Conceptually:

```text
A <--> B
A <--> C
A <--> D
A <--> E
B <--> C
B <--> D
...
```

Management becomes increasingly complex.

---

# 61. Transit Networking Concept

Instead of every network connecting directly to every other network:

```text
          VPC A
            |
            v
          Transit
         Network Hub
        /    |     \
       /     |      \
      v      v       v
   VPC B   VPC C   VPC D
```

The hub provides centralized routing connectivity.

---

# 62. AWS Transit Gateway

AWS provides:

```text
Transit Gateway
```

for hub-style connectivity among supported networks and attachments.

Conceptually:

```text
             VPC A
               |
               v
        Transit Gateway
          /    |    \
         /     |     \
        v      v      v
     VPC B   VPC C   VPN
```

---

# 63. Azure Transit Architectures

Azure environments may use hub-and-spoke architectures with components such as:

```text
Hub VNets
VNet peering
VPN gateways
Azure Virtual WAN
Private connectivity services
```

depending on architecture.

Again, the concept is centralized/transit connectivity.

Implementation differs.

# VPN Connectivity

# 64. Why VPNs Matter in Cloud

Organizations often need to connect:

```text
Office
Data center
Remote network
Other cloud
```

to cloud resources privately.

A VPN can create an encrypted communication path across an untrusted network such as the Internet.

---

# 65. Site-to-Site VPN

A site-to-site VPN connects networks rather than just one individual user.

Example:

```text
Corporate Network
10.50.0.0/16
      |
      v
VPN Device
      |
      | Encrypted Tunnel
      |
      v
Cloud VPN Gateway
      |
      v
Cloud VPC/VNet
10.20.0.0/16
```

Hosts can then communicate according to routing and security policies.

---

# 66. Site-to-Site VPN Still Needs Routes

Creating a VPN tunnel is not enough.

Cloud side may need:

```text
10.50.0.0/16 -> VPN
```

Corporate side may need:

```text
10.20.0.0/16 -> VPN
```

Without return routing, connectivity can fail.

---

# 67. VPN Troubleshooting

Ask:

```text
Is the tunnel up?

Does the source have a route?

Does the cloud have a return route?

Do CIDRs overlap?

Are firewall rules correct?

Are security groups/NSGs correct?

Are NACLs correct?
```

```text

     |
```

```text
     |
```

# Multi-AZ Networking

# 96. Why Multiple Availability Zones?

Suppose everything runs in:

```text
Availability Zone A
```

If that zone experiences a major failure, the entire application may become unavailable.

Instead:

```text
Zone A                  Zone B

Public A                Public B
App A                   App B
DB A                    DB B
```

This distributes resources across failure domains.

---

# 97. Multi-AZ Does Not Automatically Mean Highly Available

You can deploy application servers across two zones but still depend on:

```text
One NAT gateway
One database
One internal service
One misconfigured route
One DNS component
```

High availability requires examining the complete architecture.

---

# 98. NAT and Availability Zones

In AWS production designs, NAT gateway placement and routing should consider Availability Zone failure domains, resilience requirements, and cross-AZ traffic/cost implications.

A simplistic design:

```text
Private A -----+
               |
               v
            NAT-A
               ^
               |
Private B -----+
```

may create undesirable dependence on the NAT path in one zone.

A more resilient architecture may use per-zone NAT paths:

```text
Private A -> NAT-A

Private B -> NAT-B
```

with appropriate routing.

Architecture should be chosen according to availability and cost requirements.

---

# 99. Failure Domains Matter More Than Resource Count

Four servers:

```text
App-01
App-02
App-03
App-04
```

sound redundant.

But if all four depend on:

```text
One zone
```

you still have a shared failure domain.

Always ask:

```text
What can fail together?
```

# Cloud Network Troubleshooting

# 121. The Biggest Cloud Networking Mistake

A beginner sees:

```text
Connection timed out
```

and immediately changes:

```text
Security group
```

Then:

```text
NACL
```

Then:

```text
Route
```

Then:

```text
DNS
```

randomly.

This destroys evidence and creates configuration drift.

Instead, follow the packet.

---

# 122. Cloud Troubleshooting Framework

For every failed connection, identify:

```text
Source
Destination
Protocol
Destination port
Expected route
Security controls
Listener
Return path
```

Example:

```text
Source:
10.20.11.25

Destination:
10.20.21.50

Protocol:
TCP

Port:
5432
```

Now troubleshoot this specific flow.

---

# 123. Step 1: Is DNS Correct?

If connecting using:

```text
db.internal.example
```

check:

```bash
dig db.internal.example
```

Does it resolve to the expected private address?

If not, investigate DNS before changing routes or firewalls.

---

# 124. Step 2: Inspect Source IP Configuration

On Linux:

```bash
ip addr
```

Verify:

```text
Expected private IP
Expected interface
Expected subnet
```

---

# 125. Step 3: Inspect Source Routing

```bash
ip route
```

and:

```bash
ip route get 10.20.21.50
```

Understand what the operating system intends to do.

Remember that cloud networking also has provider-side routing outside the guest OS.

---

# 126. Step 4: Check Cloud Route Tables

Ask:

```text
Which subnet is the source in?

Which route table applies?

What route matches the destination?

What is the next hop?

Is there a more-specific route?
```

Do not inspect an unrelated subnet's route table.

---

# 127. Step 5: Check Security Controls

Depending on platform:

```text
Security group
NSG
NACL
Cloud firewall
Network policy
```

Ask:

```text
Is the source permitted?

Is the destination port permitted?

Does the return path require explicit stateless rules?
```

---

# 128. Step 6: Check the Destination Listener

On the destination:

```bash
sudo ss -lntp
```

Suppose PostgreSQL should listen on:

```text
10.20.21.50:5432
```

but actually listens:

```text
127.0.0.1:5432
```

Cloud networking may be perfectly configured.

The application is bound incorrectly for remote access.

---

# 129. Step 7: Test the Port

From an authorized source:

```bash
nc -vz 10.20.21.50 5432
```

Possible result:

```text
Connection succeeded
```

This proves TCP connectivity to the port, not database authentication or query correctness.

---

# 130. Step 8: Interpret Refused vs Timeout

If you receive:

```text
Connection refused
```

possible causes include:

```text
No listener
Wrong port
Active rejection
Service stopped
```

If you receive:

```text
Timeout
```

investigate possibilities such as:

```text
Firewall drop
NACL
Route
Return route
Host unavailable
Network path
```

These are clues, not absolute proof.

---

# 131. Step 9: Packet Capture

On the destination:

```bash
sudo tcpdump -nn -i any 'tcp port 5432'
```

Reproduce.

If you see:

```text
Nothing
```

the traffic may be blocked or misrouted before reaching the host.

If you see:

```text
SYN
```

but no SYN-ACK:

```text
Investigate destination host/listener/firewall.
```

If you see:

```text
SYN
SYN-ACK
ACK
```

basic TCP connectivity exists.

Move upward.

---

# 132. Cloud Provider Flow Evidence

Cloud platforms may provide network logging and diagnostic capabilities that can help answer:

```text
Was traffic accepted?

Was it rejected?

Which network interface was involved?

Which policy may have applied?
```

Examples include cloud flow-log technologies.

Use them alongside:

```text
Application logs
OS tools
Packet captures
Cloud configuration
```

No single evidence source answers everything.

# Common Beginner Mistakes

# 172. Mistake: Thinking Cloud Networking Is Completely Different

It still uses:

```text
IP
CIDR
Routing
TCP
UDP
DNS
Firewalls
NAT
```

Your networking fundamentals transfer directly.

---

# 173. Mistake: Choosing CIDRs Randomly

Today's isolated VPC may become tomorrow's:

```text
Peered VPC
VPN-connected network
Kubernetes environment
Hybrid cloud
```

Plan for connectivity.

---

# 174. Mistake: Using Overlapping CIDRs Everywhere

This makes future routing and hybrid connectivity significantly harder.

---

# 175. Mistake: Thinking a Public Subnet Makes Everything Public

Public reachability still depends on:

```text
Addressing
Routes
Gateway architecture
Security rules
Listeners
```

---

# 176. Mistake: Thinking a Private Subnet Has No Internet Access

Private resources can have controlled outbound Internet access through NAT.

---

# 177. Mistake: Putting Application Servers Directly on the Internet Without Need

Often:

```text
Internet
   |
   v
Load Balancer
   |
   v
Private Application
```

is preferable.

---

# 178. Mistake: Giving Databases Public Exposure

Database services should generally have narrowly controlled network access.

Do not publish a database simply because connectivity is easier.

---

# 179. Mistake: Confusing Routes and Firewall Rules

Remember:

```text
Route:
Where?

Firewall:
Allowed?
```

You need both.

---

# 180. Mistake: Confusing NAT Gateway and Internet Gateway

They serve different purposes.

Do not interchange them.

---

# 181. Mistake: Assuming NAT Enables Inbound Access

NAT gateway egress architecture does not function like a public application load balancer.

---

# 182. Mistake: Treating Security Groups and NACLs as Identical

In AWS:

```text
Security groups:
Stateful

NACLs:
Stateless
```

Their scope and rule behavior differ.

---

# 183. Mistake: Forgetting Ephemeral Ports With Stateless Filtering

Return TCP traffic can use client-side ephemeral ports.

Stateless ACL design must account for the complete traffic flow.

---

# 184. Mistake: Creating Peering but Forgetting Routes

A peering relationship alone does not guarantee traffic has routes to use it.

---

# 185. Mistake: Assuming Peering Is Automatically Transitive

Do not assume:

```text
A <-> B
B <-> C
```

means:

```text
A <-> C
```

---

# 186. Mistake: Ignoring DNS With Private Endpoints

Private connectivity often depends on correct private name resolution.

---

# 187. Mistake: Assuming VPN "UP" Means Applications Work

Tunnel state is only one component.

Routes, security rules, DNS, listeners, and return paths still matter.

---

# 188. Mistake: Opening SSH to the Entire Internet

Avoid broad management-port exposure.

Use restricted, auditable administrative paths.

---

# 189. Mistake: Building All Resources in One Zone

This creates a shared failure domain.

---

# 190. Mistake: Using One NAT Path Without Considering Failure Domains

Your application can be multi-zone while Internet egress still depends on one zone.

Think end-to-end.

---

# 191. Mistake: Troubleshooting Only in the Cloud Console

Also use the operating system.

Commands such as:

```bash
ip addr
ip route
ip route get
ip neigh
ss
curl
dig
nc
tcpdump
```

remain extremely valuable.

---

# 192. Mistake: Troubleshooting Only Inside the VM

The guest operating system cannot show you every provider-side control.

Also inspect:

```text
Cloud routes
Security groups/NSGs
NACLs
Load balancer configuration
NAT
VPN
Peering
Private endpoints
DNS
```

Cloud troubleshooting requires both perspectives.

---

# 193. Mistake: Changing Everything Until It Works

Do not simultaneously:

```text
Open security group
Open NACL
Change route
Change DNS
Restart server
Disable firewall
```

If it suddenly works, you may not know why.

Change one evidence-backed thing at a time.

# 217. Root Cause

The database security policy permits only the application subnet in AZ-A:

```text
10.20.11.0/24
```

but not the application tier in AZ-B:

```text
10.20.12.0/24
```

The application was deployed across multiple zones.

The security design was not updated correctly.

# 218. Better Security Design

Where supported and appropriate, instead of tying database access unnecessarily to individual application subnet CIDRs, use identity-aware cloud security relationships.

Conceptually:

```text

Allow TCP 5432
from APP-SG
```

Then both authorized application instances can reach the database according to the intended security-group relationship.

Do not broaden access beyond what the application requires.

```text
LISTENING SERVICE
   |
   v
APPLICATION
   |
   v
RETURN PATH
```

The most important lesson from this part is:

> **Do not memorize cloud networking as a collection of AWS or Azure product names. Translate every cloud component back into the networking problem it solves.**

A **VPC or VNet** gives you a virtual network.

A **subnet** divides address space.

A **route table** decides where traffic goes.

A **security group, NSG, NACL, or firewall** controls whether traffic is permitted.

An **Internet gateway** provides an Internet-facing path.

A **NAT gateway** gives private workloads translated outbound connectivity.

A **load balancer** provides a traffic entry and distribution layer.

**Peering, transit, VPN, Direct Connect, and ExpressRoute** connect networks.

**Private endpoints** provide private paths to services.

**DNS** tells applications where those services are.

And underneath all of them are the same networking fundamentals you have already learned:

```text
Source
Destination
IP
CIDR
Route
Protocol
Port
State
Security
Return path
```

Once you can translate cloud services into those fundamentals, AWS, Azure, hybrid cloud, Kubernetes, and multi-cloud networking become much easier to reason about.
