# Part 9: Python Environments, pip, and Dependency Management

In Part 8, you learned that Python already includes a large standard library.

You used modules such as:

```text
os
sys
pathlib
shutil
subprocess
datetime
time
json
logging
```

These normally come with Python.

But real DevOps, SRE, cloud, security, and platform automation frequently needs capabilities that are not included in the standard library.

For example, you may want Python to:

* Call HTTP APIs conveniently.
* Read YAML configuration.
* Interact with AWS.
* Work with Kubernetes.
* Connect to databases.
* Communicate with monitoring platforms.
* Use cloud SDKs.

Instead of building every capability yourself, you can install external Python packages.

Examples you will encounter later include:

```text
requests
PyYAML
boto3
```

That introduces a new problem.

Suppose Project A needs:

```text
package version 1
```

while Project B needs:

```text
package version 2
```

Or suppose you install 40 packages globally and six months later cannot remember which ones your automation actually requires.

Or your script works on your laptop but fails on a CI runner because the required package is missing.

Dependency management exists to solve these problems.

The progression is:

```text
Python
   |
   v
Standard library
   |
   v
External packages
   |
   v
pip
   |
   v
Virtual environments
   |
   v
Dependency files
   |
   v
Reproducible automation project
```

By the end of this part, you should understand how to create an isolated Python project, install packages safely, record its dependencies, reproduce the environment, and avoid many common dependency mistakes.

---

# 1. What Is a Python Package?

Before learning `pip`, we need to clarify the word **package**.

In Part 8, you learned that a Python package can organize related Python modules.

For example:

```text
automation/
|
+-- __init__.py
+-- health.py
+-- alerts.py
```

That is a package inside your project.

But engineers also use the word **package** to refer to distributable Python software that can be installed into a Python environment.

Examples include:

```text
requests
PyYAML
boto3
```

These packages may contain:

* Python modules.
* Subpackages.
* Metadata.
* Version information.
* Dependencies.
* Command-line tools.
* Other resources.

So context matters.

In this part, when we discuss installing packages, we mean installable Python distributions and their importable code.

---

# 2. Standard Library vs External Package

Consider:

```python
import json
```

`json` belongs to Python's standard library.

You normally do not need:

```bash
pip install json
```

But later you may use:

```python
import requests
```

`requests` is not part of Python's standard library.

It must normally be installed separately.

Conceptually:

```text
Python installation
|
+-- Standard library
|   |
|   +-- json
|   +-- pathlib
|   +-- logging
|   +-- subprocess
|
+-- Installed external packages
    |
    +-- requests
    +-- PyYAML
    +-- boto3
```

# 3. What Is `pip`?

`pip` is Python's widely used package installer.

It allows you to install and manage Python packages from package indexes and other supported sources.

A basic command looks like:

```bash
python3 -m pip install requests
```

This tells Python's package-management tooling to install the `requests` distribution into the Python environment associated with that interpreter.

---

# 4. Why `pip` Exists

Without a package installer, using an external library could require manually:

1. Finding its source code.
2. Downloading it.
3. Finding the correct version.
4. Copying files into appropriate locations.
5. Finding its dependencies.
6. Installing those dependencies manually.
7. Keeping track of upgrades.

Package-management tools automate much of this process.

Conceptually:

```text
Your project
    |
    v
Needs package
    |
    v
pip
    |
    v
Package source/index
    |
    v
Download package
    |
    v
Resolve/install dependencies
    |
    v
Install into environment
```

---

# 5. What Is PyPI?

PyPI stands for:

```text
Python Package Index
```

It is the primary public repository used for publishing and distributing Python packages.

Many packages installed with `pip` are retrieved from PyPI by default.

Conceptually:

```text
Developer publishes package
          |
          v
         PyPI
          |
          v
pip retrieves package
          |
          v
Your Python environment
```

PyPI contains a huge ecosystem of packages.

That is powerful.

It also means you should not blindly trust every package simply because it is available there.

We will discuss dependency security later.

---

# 6. Package Name vs Import Name

This can confuse beginners.

The name you install is not always identical to the name you import.

For example, a distribution might be installed using one package name but expose another Python import name.

A common example you will encounter later is:

```bash
python3 -m pip install PyYAML
```

but Python code typically uses:

```python
import yaml
```

Therefore:

```text
Installation name
and
import name

are not guaranteed to be identical.
```

Do not assume a package is wrong merely because these names differ.

Check the package's official documentation.

# 9. Why Use `python -m pip`?

You will frequently see:

```bash
pip install requests
```

or:

```bash
pip3 install requests
```

These may work.

But a useful habit is:

```bash
python3 -m pip install requests
```

or, inside an activated virtual environment:

```bash
python -m pip install requests
```

Why?

Because it makes the relationship between the Python interpreter and `pip` clearer.

Consider a machine containing:

```text
Python A
Python B
Python C
```

A standalone command named:

```text
pip
```

might not always be associated with the Python interpreter you think it is.

Using:

```text
python -m pip
```

means:

```text
Use this Python interpreter
        |
        v
Run its pip
```

This can prevent a common class of environment mistakes.

# 11. Do Not Blindly Install Packages Yet

Before installing external packages, ask:

```text

```

For learning, we are going to create a virtual environment first.

This is safer than filling your global Python installation with project dependencies.

# 12. What Is a Global Python Installation?

Suppose your machine has Python installed at the system or user level.

Conceptually:

```text
Computer
|
+-- Python
    |
    +-- standard library
    +-- globally/user-installed packages
```

If every project installs packages into the same environment:

```text
Global Python
|
+-- Project A dependencies
+-- Project B dependencies
+-- Project C dependencies
+-- Random experiments
+-- Old packages
```

Eventually, it becomes difficult to determine which project requires what.

---

# 13. The Global Dependency Problem

Imagine:

```text
Project A
requires Package X version 1
```

But:

```text
Project B
requires Package X version 2
```

If both use one shared global environment:

```text
Global Python
      |
      v
Package X
      |
      +--> version 1?
      |
      +--> version 2?
```

You can create compatibility problems.

---

# 14. Another Global Install Problem

Suppose today you install:

```text
requests
PyYAML
boto3
```

Next week:

```text
kubernetes
some-monitoring-sdk
another-library
```

Six months later, your environment contains dozens of packages.

You open one project and ask:

```text
Which of these packages does this project actually need?
```

A shared environment makes that harder to answer.

---

# 15. Global Installs Can Affect System Tools

On some operating systems, the system Python environment may be used by operating-system tooling.

Changing packages in that environment can create problems.

Modern Linux distributions may deliberately prevent or discourage direct modifications to externally managed Python installations.

You may encounter an error referring to an:

```text
externally-managed-environment
```

That is not necessarily a broken Python installation.

It may be the operating system protecting its managed Python environment.

---

# 16. Do Not Solve Environment Protection with `sudo pip`

A dangerous beginner reaction is:

```bash
sudo pip install package
```

or:

```bash
sudo pip3 install package
```

Avoid using elevated privileges merely to force a package installation into the system Python environment.

Why?

You may:

* Modify system-managed Python files.
* Create ownership problems.
* Conflict with operating-system packages.
* Make future troubleshooting harder.
* Increase the impact of a malicious package.

For project dependencies, use a virtual environment.

---

# 17. What Is a Virtual Environment?

A virtual environment is an isolated Python environment created for a particular project or purpose.

Instead of:

```text
One global Python
shared by everything
```

you can have:

```text
Project A
|
+-- its environment
    +-- Package X 1.x

Project B
|
+-- its environment
    +-- Package X 2.x
```

Each project gets its own dependency space.

---

# 18. Virtual Environment Mental Model

Think of it like this:

```text
Base Python installation
        |
        +-------------------+
        |                   |
        v                   v
Project A venv          Project B venv
        |                   |
        +-- requests         +-- boto3
        +-- PyYAML           +-- requests
```

The environments are separate.

Installing a package in Project A's virtual environment does not normally install it into Project B's virtual environment.

---

# 19. What Virtual Environments Solve

Virtual environments help with:

* Project isolation.
* Version conflicts.
* Reproducibility.
* Cleaner development systems.
* Safer dependency management.
* CI/CD consistency.
* Easier troubleshooting.

They do not solve every dependency problem, but they provide an essential boundary.

Because `venv` belongs to the standard library, you can invoke it using:


On some Linux distributions, additional operating-system packaging may be required before the `venv` functionality is available.

# 28. Activating on Linux or macOS

---

# 29. Understanding `source`

On common Unix-like shells, `source` executes the activation script within the current shell environment.

Why does that matter?

Activation needs to modify the environment of your current shell.

If it ran only in a separate child process, those changes would disappear when that process ended.

---

# 30. Windows PowerShell Activation

A common PowerShell activation command is:

```powershell
.venv\Scripts\Activate.ps1
```

Windows Command Prompt commonly uses:

```text
.venv\Scripts\activate.bat
```

Your shell matters.

Do not blindly use a Linux activation command in PowerShell or a PowerShell command in Bash.

---

# 31. What Activation Actually Does

A common misconception is:

```text
Activation starts a separate Python server.
```

It does not.

Activation primarily modifies your shell environment so commands such as:

```text
python
pip
```

resolve to the virtual environment's tools first.

Conceptually:

```text
Before activation

python
   |
   v
system/base Python
```

After:

```text
source .venv/bin/activate
```

you get:

```text
python
   |
   v
project/.venv Python
```

# 37. Direct vs Transitive Dependencies

Suppose you explicitly install:

```text
Package A
```

but Package A requires:

```text
Package B
Package C
```

Then:

```text
Your project
    |
    v
Package A
   / \
  v   v
B     C
```

Package A is a **direct dependency** because your project requested it.

B and C are **transitive dependencies** because another dependency requires them.

This distinction becomes important when reading dependency lists.

# 43. Package Versions

Software packages change over time.

A package may have versions such as:

```text
1.0.0
1.1.0
1.2.0
2.0.0
```

Versions help identify which release is installed.

You should not assume every package uses version numbers with exactly the same release policy.

But many projects use conventions influenced by semantic versioning.

---

# 44. Semantic Versioning at a Beginner Level

A common version format is:

```text
MAJOR.MINOR.PATCH
```

For example:

```text
3.4.7
```

Conceptually:

```text
3
|
+--> major version

4
|
+--> minor version

7
|
+--> patch version
```

Under semantic versioning conventions, projects generally intend:

* Major changes for incompatible API changes.
* Minor changes for backward-compatible functionality.
* Patch changes for backward-compatible fixes.

But not every Python package follows semantic versioning perfectly.

Always check the specific project's release policy.

---

# 45. Installing a Specific Version

Instead of:

```bash
python -m pip install requests
```

you can specify a version:

```bash
python -m pip install "requests==2.32.5"
```

This means:

```text
Install exactly version 2.32.5.
```

The version shown here is only an example for learning syntax. In a real project, choose a version based on compatibility, security, and project requirements.

---

# 46. What `==` Means in Package Requirements

In:

```text
requests==2.32.5
```

`==` means:

```text
exactly this version
```

This is called exact version pinning.

---

# 47. Other Version Specifiers

You may encounter:

```text
package>=1.5
package<=2.0
package>1.5
package<3.0
package~=2.4
package>=2.0,<3.0
```

At a beginner level:

```text
>=
at least this version

<=
no greater than this version

>
greater than

<
less than

==
exactly
```

The `~=` compatible-release operator has more specific packaging semantics and should be checked carefully before use.

---

# 48. Why Version Constraints Exist

Suppose your automation was tested with:

```text
Package X 2.x
```

but a future:

```text
Package X 3.x
```

changes an API your script uses.

If you always install the newest version without constraints:

```text
Working project today
        |
        v
New package release
        |
        v
Fresh deployment tomorrow
        |
        v
Different dependency version
        |
        v
Possible failure
```

Version constraints help control this uncertainty.

---

# 49. But Pinning Has Trade-Offs

Pinning everything forever is not a complete solution.

Suppose you pin:

```text
package==1.0.0
```

and never update it.

Later:

* Security vulnerabilities may be discovered.
* Bugs may be fixed.
* Python compatibility may change.
* Other dependencies may stop supporting that version.

So dependency management requires both:

```text
stability
```

and:

```text
maintenance
```

# 53. Does Uninstall Remove Everything?

Not necessarily in the way you might expect.

Suppose:

```text
Package A
|
+--> depends on Package B
```

If you remove Package A, dependency-management behavior may not automatically clean every package that became unused.

Do not assume an environment is perfectly cleaned simply because one package was uninstalled.

For disposable project environments, recreating the environment can sometimes be simpler and more reliable than trying to manually clean a heavily changed one.

---

# 54. Upgrade a Package

You may encounter:

```bash

```

The:

```text
--upgrade
```

option asks `pip` to upgrade the requested package according to applicable constraints.

Do not automatically upgrade production dependencies without testing.

An upgrade can change behavior.

---

# 55. Dependency Changes Should Be Tested

A safer workflow is:

```text

        |
        v

        |
        v
Upgrade dependency
        |
        v
Run tests
        |
        v
Run automation safely
        |
        v

        |
        v

```

Not:

```text

        |
        v
Upgrade everything randomly
```

```bash

```

```text

```

Exact output depends on your environment.

---

# 63. Freezing Dependencies to a File

On common shells, you can redirect the output:

```bash
python -m pip freeze > requirements.txt
```

The:

```text
>
```

is shell redirection.

It sends command output into:

```text
requirements.txt
```

instead of displaying it only in the terminal.

---

# 64. Be Careful with `>`

This command:

```bash
python -m pip freeze > requirements.txt
```

can overwrite the existing contents of:

```text
requirements.txt
```

Do not use output redirection blindly against an important file.

Before overwriting dependency files:

* Check your current environment.
* Review Git changes afterward.
* Confirm that the environment contains only intended project dependencies.

---

# 65. `pip freeze` Records the Environment

This distinction is extremely important.

`pip freeze` answers approximately:

```text
What installed Python distributions are currently represented in this environment in requirement-style output?
```

It does not necessarily answer:

```text
Which packages did my source code intentionally choose as top-level dependencies?
```

Suppose you installed:

```text
requests
```

and it required several dependencies.

`pip freeze` may include both the direct dependency and its transitive dependencies.

---

Conceptually:

```text
Direct project requirements
```

may resolve into:

```text

|
+-- dependency A
+-- dependency B
+-- dependency C

PyYAML
```

A freeze can capture the larger resolved environment.

This can improve reproducibility but may also make it less obvious which packages were directly chosen by your project.

Modern dependency workflows often distinguish between:

```text
Declared direct dependencies
```

and:

```text
Resolved/locked dependency versions
```

# 67. Create a Clean Practice Environment

# 80. What Is a Dependency Conflict?

A dependency conflict occurs when dependency requirements cannot be satisfied together, or when installed versions are incompatible with what packages require.

Example:

```text
Your project
|
+-- Package A
|   |
|   +-- requires X >= 2
|
+-- Package B
    |
    +-- requires X < 2
```

Now:

```text
X must be >= 2
```

and:

```text
X must be < 2
```

cannot both be true.

That is an incompatible constraint.

---

# 81. Visualizing a Conflict

```text
Package A
    |
    v
X >= 2
    |
    X
    |
    ^
X < 2
    |
Package B
```

There is no version of X satisfying both constraints.

A resolver cannot invent one.

---

# 82. Another Conflict Type

Suppose your requirements say:

```text
package-x==1.5
```

but another dependency requires:

```text
package-x>=2.0
```

Again:

```text
1.5
```

cannot satisfy:

```text
>=2.0
```

You must change the dependency combination or constraints.

---

# 83. What Should You Do During a Dependency Conflict?

Do not randomly uninstall packages until the error disappears.

Investigate:

1. Which packages are conflicting?
2. What versions do they require?
3. Are newer compatible versions available?
4. Is one dependency outdated?
5. Did you over-pin a version?
6. Does the project's Python version affect compatibility?
7. Is the package still maintained?

Then change constraints intentionally.

# 84. `pip check`

```bash
python -m pip check
```

This checks whether installed packages have compatible declared dependencies.

Healthy output may resemble:

```text
No broken requirements found.
```

If there are problems, it can report them.

This is a useful verification command.

# 85. Dependency Resolver

Modern `pip` includes dependency-resolution behavior.

When installing packages, it attempts to choose versions satisfying declared requirements.

Conceptually:

```text
Your requirements
       |
       v
pip resolver
       |
       +--> inspect dependency A
       +--> inspect dependency B
       +--> inspect version constraints
       |
       v
Find compatible set
```

If no compatible set exists, installation may fail.

That failure is useful.

It prevents some invalid combinations from being silently installed.

---

# 86. Do Not Fight the Resolver Blindly

If `pip` says requirements conflict, the correct response is not:

```text
How do I force it?
```

The first question should be:

```text
Why are these requirements incompatible?
```

Dependency errors often contain important evidence.

Read them.

not only package versions.

```text
       +
```

# 90. Virtual Environment vs Container

Do not confuse:

```text
virtual environment
```

with:

```text
container
```

A Python virtual environment isolates Python packages.

It does not create a fully isolated operating system.

Conceptually:

```text
Virtual environment
|
+-- Python packages
+-- Python executable context
```

A container can isolate much more of the application runtime, including filesystem and operating-system-level dependencies.

You will encounter both in DevOps.

They solve different problems.

---

# 91. Virtual Environment vs Virtual Machine

They are also different.

```text
Python virtual environment
```

is not a virtual machine.

A virtual machine virtualizes an entire computer environment.

A Python virtual environment mainly isolates Python dependencies.

# 94. Dependency Bloat

Dependency bloat happens when a project accumulates unnecessary packages.

Problems include:

* Larger installation size.
* Slower setup.
* More potential conflicts.
* More updates to manage.
* More security exposure.
* More transitive dependencies.
* Harder troubleshooting.

Do not install a package for every tiny operation.

# 97. Safe Package Selection

Before adding a dependency, investigate:

* Who maintains it?
* Is the project active?
* Is its documentation legitimate?
* Does it have a healthy release history?
* Does it support your Python version?
* Does it have known security issues?
* Is the package name correct?
* Is it actually the package you intended?

# 98. Typosquatting

Suppose the legitimate package is named:

```text
important-package
```

An attacker might publish something with a confusingly similar name.

A user mistypes:

```bash
pip install imporant-package
```

and accidentally installs something malicious.

This type of attack is commonly associated with **typosquatting**.

Always verify package names.

---

# 99. Packages Are Executable Code

Installing a package is not equivalent to downloading a harmless text document.

Package installation and imported code can involve executable behavior.

A malicious dependency may potentially:

* Read accessible files.
* Read environment variables.
* Make network requests.
* Modify files.
* Access credentials available to your process.
* Execute commands with your permissions.

Treat dependency installation as a security decision.

---

# 100. Least Privilege During Installation

Do not install random packages with administrator/root privileges.

If malicious code executes with:

```text
your normal user permissions
```

the impact is already serious.

If it executes with:

```text
root/administrator permissions
```

the potential impact can be much larger.

Virtual environments help reduce the need for privileged package installation.

---

# 101. Never Put Secrets in `requirements.txt`

Bad:

```text
API_KEY=my-secret-key
requests==...
```

A dependency file is not a secret store.

Do not place:

* Passwords.
* API tokens.
* Private keys.
* Cloud credentials.

inside ordinary dependency files.

* Organization-specific tooling.

Authentication may be required.

Be careful not to hardcode credentials into:

```text

```

or commit them into Git.

The exact secure configuration depends on your organization's package infrastructure.

# 105. Locking Dependencies


# 142. Dependency Version Strategy

There is no single versioning strategy appropriate for every project.

You may see:

```text

Compatible ranges
Minimum versions
Lock files
Generated requirements
```

The right approach depends on whether you are building:

* An application.
* A reusable library.
* A CLI tool.
* Internal automation.
* A production service.
* A container image.
* A distributable package.

For beginner infrastructure automation, prioritize:

```text

+

+
```

# 143. Applications and Libraries Have Different Needs

An application controls its runtime environment more directly.

Therefore, exact resolved versions can be valuable.

A reusable Python library may need broader dependency constraints so it can coexist with other libraries in a user's environment.

Conceptually:

```text
Application
|
+-- "This is the environment I run."

Library
|
+-- "I must coexist inside someone else's environment."
```

This distinction affects dependency strategy.

# 144. Infrastructure Automation Is Often Application-Like

Many DevOps scripts and automation tools are deployed as controlled applications:

You want:

```text

        |
```

# 145. Dependency Drift

Dependency drift occurs when environments gradually differ.

Example:

```text
Developer laptop
requests A

CI
requests B

Production
requests C
```

Even if all versions are nominally compatible, differences make troubleshooting harder.

Version controls and reproducible builds reduce drift.

# 146. Environment Drift

```text

Different environment variables
Different command versions
Different configuration
```

DevOps engineers care about reproducibility because inconsistent environments create inconsistent behavior.

# 147. Why Containers Often Pin Dependencies

Suppose a Docker build contains:

```text

```

If every build downloads whatever happens to be newest that day:

```text

    |
    +--> dependency A

Build Friday
    |
    +--> newer dependency B
```

The same source code can produce behaviorally different images.

Controlling versions improves build predictability.

# 148. But Containers Do Not Remove Dependency Management

Wrong.

* Which versions?
* Which base image?

Containers make reproducibility easier when used properly, but they do not make dependency decisions disappear.

# 174. Dependency Trees

# 175. Shared Transitive Dependency

Notice:

```text

B -> D
```

Both A and B depend on D.

Now imagine:

```text

```

The shared dependency becomes the conflict point.

Dependency resolution is therefore a graph problem, not merely a list of package names.

```python
        f"{sys.executable}"

    url: str

    show_environment()

    check_endpoint(
        "https://example.com"
    )

    main()
```
