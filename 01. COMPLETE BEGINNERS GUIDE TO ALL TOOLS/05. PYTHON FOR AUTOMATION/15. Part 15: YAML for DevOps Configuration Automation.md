# Part 15: YAML for DevOps Configuration Automation

Work with the format used throughout modern infrastructure.

In Part 14, you learned how Python works with JSON from APIs, cloud platforms, Kubernetes, Docker, command-line tools, and automation systems.

Now we move to another structured-data format that appears constantly in DevOps:

YAML.

If you work with Kubernetes, CI/CD, Ansible, application configuration, GitOps, monitoring, or infrastructure tooling, you will encounter YAML.

Examples include:

```text
Kubernetes manifests
GitHub Actions workflows
GitLab CI/CD pipelines
Ansible playbooks
Docker Compose files
Helm values files
Prometheus configuration
Application configuration
Cloud-native tools
GitOps repositories
```

By the end of this part, you should be able to read YAML, understand its data types and indentation rules, load YAML into Python, validate it, modify it safely, write YAML files, and build automation that updates infrastructure configuration without blindly editing text.

---

# 1. What Are We Trying to Accomplish?

Imagine a Kubernetes configuration contains:

```yaml
app:
  name: payments
  replicas: 3
  image: company/payments:v1.4.0
```

Your deployment automation needs to change:

```text
replicas: 3
```

to:

```text
replicas: 5
```

You could treat the file as ordinary text and perform:

```text
replace "replicas: 3"
with "replicas: 5"
```

But that approach is fragile.

What if several sections contain:

```yaml
replicas: 3
```

What if spacing changes?

What if the configuration is nested?

A stronger approach is:

```text
YAML file
    |
    v
YAML parser
    |
    v
Python dictionary/list
    |
    v
Find exact configuration field
    |
    v
Validate current value
    |
    v
Modify Python object
    |
    v
Write YAML
    |
    v
Validate result
```

That is what this part teaches.

---

# 2. What Is YAML?

YAML is a human-readable data serialization format.

It is used to represent structured data.

A simple example:

```yaml
service: payments
port: 8080
replicas: 3
enabled: true
```

This represents several named values.

Conceptually:

```text
service  ---> payments
port     ---> 8080
replicas ---> 3
enabled  ---> true
```

---

# 3. What Does YAML Stand For?

YAML is commonly expanded as:

```text
YAML Ain't Markup Language
```

The recursive name emphasizes that YAML is primarily intended for representing data rather than marking up documents.

For a beginner, the important thing to remember is simpler:

```text
YAML
=
structured data written in a
human-friendly text format
```

---

# 4. Why YAML Is Popular in DevOps

Infrastructure engineers frequently need configuration that is:

* Human-readable.
* Easy to edit.
* Easy to store in Git.
* Structured.
* Machine-readable.
* Suitable for nested configuration.

YAML fits those requirements well.

For example:

```yaml
application:
  name: checkout
  environment: production
  replicas: 4

database:
  host: db.internal
  port: 5432
```

A human can read this relatively easily.

A program can also parse it.

---

# 5. YAML Is Data, Not Instructions by Itself

Consider:

```yaml
replicas: 5
```

YAML itself does not create five application replicas.

The program reading the YAML decides what that value means.

For example:

```text
YAML
 |
 v
Kubernetes API
 |
 v
Interprets desired state
 |
 v
Creates/maintains workloads
```

Likewise:

```text
YAML
 |
 v
CI/CD platform
 |
 v
Interprets workflow configuration
 |
 v
Runs pipeline jobs
```

The meaning comes from the system consuming the YAML.

# 7. YAML Syntax vs Tool Schema

This:

```yaml
replicas: 3
```

may be valid YAML.

But that does not automatically mean it is valid Kubernetes configuration.

There are two separate questions:

```text
Is the YAML syntactically valid?

          ↓

Does the application understand
this structure and these fields?
```

Exactly as with JSON:

```text
Valid data syntax
!=
Valid application configuration
```

---

# 8. YAML vs JSON

YAML and JSON can represent similar structured data.

JSON:

```json
{
    "service": "payments",
    "port": 8080,
    "enabled": true
}
```

YAML:

```yaml
service: payments
port: 8080
enabled: true
```

Both represent essentially the same data.

---

# 9. YAML Is Often More Compact

JSON uses explicit punctuation:

```json
{
    "server": {
        "name": "web01",
        "port": 443
    }
}
```

YAML can express the same structure as:

```yaml
server:
  name: web01
  port: 443
```

YAML relies heavily on indentation.

This makes it visually clean, but also creates an important source of errors.

---

# 10. JSON Uses More Delimiters

JSON commonly uses:

```text
{
}
[
]
,
"
```

YAML often uses indentation and:

```text
:
-
```

For example:

JSON:

```json
{
    "servers": [
        "web01",
        "web02"
    ]
}
```

YAML:

```yaml
servers:
  - web01
  - web02
```

---

# 11. YAML Can Contain Comments

JSON does not support ordinary comments in its standard syntax.

YAML does.

Example:

```yaml
# Production application configuration
replicas: 3
```

This is one reason YAML is attractive for configuration maintained by humans.

---

# 12. YAML Supports Multiple Styles

YAML can sometimes express the same data in different ways.

For example:

```yaml
servers:
  - web01
  - web02
```

and a flow-style representation:

```yaml
servers: [web01, web02]
```

Both can represent a sequence.

For beginner DevOps configuration, block-style YAML is usually easier to read.

# 14. Key-Value Pairs

The most basic YAML structure is a key-value pair.

Example:

```yaml
service: payments
```

The key is:

```text
service
```

The value is:

```text
payments
```

The colon separates them.

---

# 15. Multiple Key-Value Pairs

```yaml
service: payments
port: 8080
replicas: 3
environment: production
```

After parsing, Python can represent this as:

```python
{
    "service": "payments",
    "port": 8080,
    "replicas": 3,
    "environment": "production"
}
```

This is a dictionary.

---

# 16. Space After the Colon

Write:

```yaml
service: payments
```

not:

```text
service:payments
```

A space after the colon makes the key-value relationship clear and is the normal style for configuration mappings.

Spacing matters in YAML.

---

# 17. YAML Mappings

A collection of key-value pairs is often called a mapping.

Example:

```yaml
name: api
port: 8080
healthy: true
```

Conceptually:

```text
mapping
 |
 +-- name ----> api
 +-- port ----> 8080
 +-- healthy -> true
```

In Python, this normally becomes a dictionary.

---

# 18. Lists

YAML lists are commonly written using hyphens.

Example:

```yaml
servers:
  - web01
  - web02
  - web03
```

The value of:

```text
servers
```

is a list.

---

# 19. Lists Become Python Lists

After parsing:

```python
{
    "servers": [
        "web01",
        "web02",
        "web03"
    ]
}
```

You can then use:

```python
for server in data["servers"]:
    print(server)
```

Your existing loop knowledge applies.

---

# 20. List Items Can Be Objects

Example:

```yaml
servers:
  - name: web01
    status: running
  - name: web02
    status: stopped
```

Conceptually:

```text
servers
 |
 +-- item 0
 |    |
 |    +-- name --> web01
 |    +-- status --> running
 |
 +-- item 1
      |
      +-- name --> web02
      +-- status --> stopped
```

---

# 21. Python Representation

The YAML above becomes approximately:

```python
{
    "servers": [
        {
            "name": "web01",
            "status": "running"
        },
        {
            "name": "web02",
            "status": "stopped"
        }
    ]
}
```

This should look familiar from JSON.

---

# 22. Nested Structures

YAML uses indentation to express nesting.

Example:

```yaml
server:
  name: web01
  network:
    private_ip: 10.0.1.10
    port: 443
```

Structure:

```text
server
 |
 +-- name --> web01
 |
 +-- network
      |
      +-- private_ip --> 10.0.1.10
      +-- port -------> 443
```

---

# 23. Nested YAML Becomes Nested Dictionaries

Python representation:

```python
{
    "server": {
        "name": "web01",
        "network": {
            "private_ip": "10.0.1.10",
            "port": 443
        }
    }
}
```

Access:

```python
data["server"]["network"]["private_ip"]
```

---

# 24. Lists Inside Nested Structures

Example:

```yaml
application:
  name: api
  ports:
    - 8080
    - 8443
```

Python:

```python
{
    "application": {
        "name": "api",
        "ports": [
            8080,
            8443
        ]
    }
}
```

---

# 25. Nested Objects Inside Lists

Example:

```yaml
applications:
  - name: frontend
    replicas: 3
    ports:
      - 80
      - 443

  - name: backend
    replicas: 5
    ports:
      - 8080
```

This is common in infrastructure configuration.

---

# 26. Strings

YAML supports strings.

Example:

```yaml
service: payments
environment: production
region: us-east-1
```

These values are strings.

Quotes are often optional for simple strings.

---

# 27. Quoted Strings

You can explicitly quote strings:

```yaml
service: "payments"
environment: "production"
```

or:

```yaml
service: 'payments'
```

Unlike JSON, YAML supports both single and double quoted strings.

---

# 28. Why Quote a YAML String?

Quotes can help when:

* A value could be interpreted as another data type.
* The value contains special characters.
* Leading or trailing spaces matter.
* You want to make string intent explicit.
* A value contains characters meaningful to YAML.

Example:

```yaml
version: "1.0"
```

This explicitly communicates that the value is intended as text.

---

# 29. Numbers

YAML can represent integers:

```yaml
replicas: 3
port: 8080
```

After parsing:

```python
type(data["replicas"])
```

should normally be:

```text
int
```

---

# 30. Floating-Point Numbers

Example:

```yaml
threshold: 75.5
```

Python normally receives a float.

This matters when performing calculations or comparisons.

---

# 31. Numbers vs Numeric Strings

Compare:

```yaml
port: 443
```

with:

```yaml
port: "443"
```

The first is intended as a number.

The second is explicitly a string.

That can change your Python logic.

---

# 32. Booleans

Modern YAML configuration commonly uses:

```yaml
enabled: true
maintenance: false
```

Python typically receives:

```python
True
False
```

after safe parsing.

---

# 33. Be Careful with YAML Type Interpretation

YAML parsers apply YAML's type-resolution rules.

This means values that look simple may not always become the Python type you expected.

For configuration where type matters, validate the parsed Python value.

Do not rely only on how the YAML visually looks.

---

# 34. Null Values

YAML can represent null values.

Common forms include:

```yaml
public_ip: null
```

or:

```yaml
public_ip: ~
```

After parsing, Python normally receives:

```python
None
```

For beginner infrastructure configuration, explicitly writing:

```yaml
public_ip: null
```

is usually clearer.

---

# 35. Missing vs Null

These are different.

Example 1:

```yaml
public_ip: null
```

The key exists.

Its value is null.

Example 2:

```yaml
name: worker01
```

The key:

```text
public_ip
```

does not exist.

Your automation may need to distinguish these situations.

---

# 36. Indentation Is Fundamental

YAML uses indentation to represent hierarchy.

Correct:

```yaml
server:
  name: web01
  port: 443
```

The fields:

```text
name
port
```

belong to:

```text
server
```

because they are indented beneath it.

---

# 37. Indentation Changes Meaning

Compare:

```yaml
server:
  name: web01
  port: 443
```

with:

```yaml
server:
  name: web01
port: 443
```

In the second example:

```text
port
```

is no longer inside:

```text
server
```

The YAML may still be syntactically valid.

But its structure has changed.

This can be more dangerous than a simple syntax error.

---

# 38. Think in Trees

For:

```yaml
application:
  name: checkout
  deployment:
    replicas: 4
    strategy: rolling
```

visualize:

```text
application
 |
 +-- name --> checkout
 |
 +-- deployment
      |
      +-- replicas --> 4
      +-- strategy --> rolling
```

Indentation tells you which branch a value belongs to.

---

# 39. Use Spaces for Indentation

Use spaces, not tabs, for YAML indentation.

A common convention is two spaces per nesting level:

```yaml
application:
  deployment:
    replicas: 3
```

Consistency is more important than trying to make the file visually elaborate.

---

# 40. Why Tabs Are a Problem

YAML indentation is based on spaces.

Tabs can lead to parsing problems and confusing editor behavior.

Configure your editor to insert spaces when working with YAML.

---

# 41. Consistent Indentation

Bad:

```text
application:
   name: api
  replicas: 3
```

The indentation is inconsistent.

Correct:

```yaml
application:
  name: api
  replicas: 3
```

---

# 42. List Indentation

Correct:

```yaml
services:
  - nginx
  - docker
  - ssh
```

The list belongs to:

```text
services
```

because the items are indented under it.

---

# 43. Nested List Objects

Correct:

```yaml
servers:
  - name: web01
    port: 443

  - name: web02
    port: 443
```

Notice that:

```text
port
```

aligns with:

```text
name
```

inside each list item.

---

# 44. A Common List Indentation Mistake

Incorrect structure:

```text
servers:
  - name: web01
  port: 443
```

The intended relationship is broken.

Correct:

```yaml
servers:
  - name: web01
    port: 443
```

---

# 45. Comments

YAML comments begin with:

```text
#
```

Example:

```yaml
# Production replica count
replicas: 5
```

Comments help explain configuration to humans.

---

# 46. Inline Comments

Example:

```yaml
replicas: 5  # Minimum production capacity
```

This can be useful.

But avoid turning every line into a paragraph.

Comments should explain important intent, constraints, or non-obvious decisions.

---

# 47. Comments Are Not Data

A YAML parser normally does not treat:

```yaml
# Production environment
```

as part of the resulting Python dictionary.

The parsed data might simply be:

```python
{
    "environment": "production"
}
```

This matters when rewriting YAML with a library.

---

# 48. Rewriting YAML Can Affect Comments

If Python loads YAML into ordinary dictionaries and writes it back, comments and original formatting may not necessarily be preserved.

This is extremely important for configuration automation.

Your data may remain correct while the human formatting changes.

---

# 49. Data Preservation vs Formatting Preservation

There are two different goals:

```text
Preserve configuration meaning

vs

Preserve exact original text,
comments, spacing and style
```

PyYAML is primarily concerned with YAML data, not perfect round-trip preservation of every formatting detail.

For files where comments and formatting must remain intact, specialized round-trip YAML tools may be more appropriate.

---

# 50. Multi-Line Values

Configuration sometimes needs multi-line text.

Example:

```yaml
message: |
  Deployment completed.
  All health checks passed.
  Monitoring remains active.
```

The:

```text
|
```

indicates a literal block scalar.

---

# 51. Literal Block Style

Example:

```yaml
script: |
  echo "Starting deployment"
  kubectl get pods
  echo "Deployment check complete"
```

Line breaks are preserved.

Conceptually, the value contains:

```text
echo "Starting deployment"
kubectl get pods
echo "Deployment check complete"
```

with line breaks.

---

# 52. Folded Block Style

YAML also supports:

```text
>
```

Example:

```yaml
description: >
  This application handles
  customer payment requests
  in the production environment.
```

Folded style generally turns many line breaks into spaces according to YAML's folding rules.

This is useful for long prose.

---

# 53. `|` vs `>`

A useful beginner rule:

```text
|
Preserve line structure

>
Fold lines into flowing text
```

Use the style that matches the meaning of the value.

---

# 54. Multi-Line Shell Commands

CI/CD configuration frequently contains:

```yaml
run: |
  python -m pytest
  python -m compileall .
  echo "Checks complete"
```

The line structure matters because these are separate shell commands.

Literal block style is therefore common.

---

# 55. Multi-Line Values Still Require Correct Indentation

Correct:

```yaml
script: |
  echo "one"
  echo "two"
```

The content belongs to:

```text
script
```

because it is indented underneath it.

---

# 56. Common YAML Mistake: Wrong Indentation

Bad:

```text
application:
  name: api
    replicas: 3
```

The parser cannot interpret the intended hierarchy correctly.

Fix:

```yaml
application:
  name: api
  replicas: 3
```

---

# 57. Common YAML Mistake: Tabs

Do not use tabs for YAML indentation.

Use spaces.

---

# 58. Common YAML Mistake: Missing Colon

Wrong:

```text
service nginx
```

Correct:

```yaml
service: nginx
```

---

# 59. Common YAML Mistake: Broken List Structure

Wrong:

```text
servers:
  web01
  web02
```

Correct:

```yaml
servers:
  - web01
  - web02
```

# 60. Common YAML Mistake: Misaligned List Object

Wrong:

```text
servers:
  - name: web01
  port: 443
```

Correct:

```yaml
servers:
  - name: web01

```

---

# 61. Common YAML Mistake: Unexpected Type

Suppose you intended:

```yaml
version: "1.20"
```

but wrote an unquoted scalar and your parser resolves it as a number.

Your program may receive a different type than expected.

Validate important fields.

---

# 62. Common YAML Mistake: Duplicate Keys

Consider:

```yaml
service:
  port: 8080
  port: 9090
```

Duplicate keys are dangerous.

Depending on parser behavior and configuration, one value may replace another or the duplicate may be rejected.

Avoid duplicate keys entirely.

A configuration should have one unambiguous value for a mapping key.

---

# 63. Common YAML Mistake: Editing by Blind String Replacement

Suppose:

```yaml
replicas: 3
```

appears in five deployments.

This is dangerous:

```python
text.replace(
    "replicas: 3",
    "replicas: 5"
)
```

You may change all five.

Instead:

```text
Parse YAML
   |
   v
Navigate exact structure
   |
   v
Modify intended field
```

---

# 64. Common YAML Mistake: Assuming Valid YAML Means Valid Kubernetes

This may be valid YAML:

```yaml
banana: production
replicas: 3
```

But Kubernetes does not accept arbitrary fields simply because YAML parses.

The consumer's schema matters.

---

# 65. Common YAML Mistake: Mixing Data and Secrets

Example:

```yaml
database:
  username: admin
  password: super-secret-password
```

YAML is plain text.

This is not encrypted.

Do not commit secrets to Git merely because they are inside YAML.

---

# 66. Common YAML Mistake: Treating YAML as Harmless

YAML parsing has security implications.

Some YAML libraries and loading modes can construct more than simple data structures.

When reading configuration from files, APIs, repositories, or users, use safe loading methods.

This is one of the most important rules in this part.

# 75. Why `safe_load()`?

Use:

```python
yaml.safe_load()
```

for ordinary configuration data.

It restricts loading to standard YAML data types rather than allowing arbitrary Python object construction.

For normal DevOps configuration, safe loading should be your default.

---

# 76. Safe Loading Rule

Remember:

```text

      |

```

Do not casually replace it with unsafe loading mechanisms.

External configuration is input.

Treat it as untrusted until validated.

# 88. Safe YAML File Loader

```python
from pathlib import Path

import yaml


def load_yaml_file(
    path: Path
):
    try:
        with path.open(
            "r",
            encoding="utf-8"
        ) as file:
            data = yaml.safe_load(file)

    except FileNotFoundError as error:
        raise RuntimeError(
            f"YAML file not found: "
            f"{path}"
        ) from error

    except PermissionError as error:
        raise RuntimeError(
            f"Permission denied: "
            f"{path}"
        ) from error

    except yaml.YAMLError as error:
        raise RuntimeError(
            f"Invalid YAML in "
            f"{path}: {error}"
        ) from error

    return data
```

* CI artifacts.
* Generated files.
* External systems.

```text
ERROR:
```


# 211. Production Pattern: Do Not Hide Partial Failure

Suppose your script updates ten YAML files.

Nine succeed.

One fails.

Do not report simply:

```text
Update successful
```

Track:

```text
Succeeded: 9
Failed: 1
```

and return an appropriate exit status.

This becomes important in CI/CD.

# 212. Production Pattern: Backups Are Not the Same as Version Control

A backup such as:

```text
deployment.yaml.bak
```

can help with local recovery.

Git provides history and collaboration.

Neither automatically replaces:

* Validation.
* Review.
* Access controls.
* Deployment controls.
* Disaster recovery.

Use each tool for its intended purpose.

# 213. Production Pattern: Avoid Unnecessary Rewrites

If nothing changed:

```text
Do not rewrite file.
```

Why?

Because unnecessary writes can:

* Change formatting.
* Trigger pipelines.
* Produce Git diffs.
* Update timestamps.
* Create deployment noise.

Check desired state first.

# 217. Image Update Function

```python
def update_container_image(
    manifest: dict,
    container_name: str,
    new_image: str
) -> bool:

    if (
        not isinstance(
            new_image,
            str
        )
        or not new_image.strip()
    ):
        raise ValueError(
            "new_image must be "
            "a non-empty string"
        )

    try:
        containers = (
            manifest["spec"]
            ["template"]
            ["spec"]
            ["containers"]
        )

    except KeyError as error:
        raise ValueError(
            "Manifest does not "
            "contain the expected "
            "Deployment structure"
        ) from error

    if not isinstance(
        containers,
        list
    ):
        raise ValueError(
            "containers must "
            "be a list"
        )

    for container in containers:
        if (
            isinstance(
                container,
                dict
            )
            and container.get(
                "name"
            ) == container_name
        ):
            if (
                container.get("image")
                == new_image
            ):
                return False

            container["image"] = (
                new_image
            )

            return True

    raise ValueError(
        f"Container not found: "
        f"{container_name}"
    )
```
