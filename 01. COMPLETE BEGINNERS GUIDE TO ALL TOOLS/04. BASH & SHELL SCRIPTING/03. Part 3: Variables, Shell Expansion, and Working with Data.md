# Part 3: Variables, Shell Expansion, and Working with Data

In Part 2, you moved from manually entering commands to creating reusable Bash scripts. You learned how to create `.sh` files, use shebangs, add executable permissions, understand `$PATH`, and execute scripts correctly.

Now your scripts need something more important: **data**.

A useful script cannot have every value permanently hardcoded.

Imagine a backup script containing:

```bash
cp /home/ann/app.log /home/ann/backups/
```

What happens when:

* the username changes?
* the source directory changes?
* the backup location changes?
* the environment changes from development to production?
* the server hostname needs to be included in the backup filename?

You could repeatedly rewrite the script.

A better solution is to store changing information in **variables**.

For example:

```bash
source_file="/home/ann/app.log"
backup_dir="/home/ann/backups"
```

Then:

```bash
cp "$source_file" "$backup_dir"
```

Variables allow scripts to work with changing information.

But Bash variables become much more powerful when combined with **shell expansion**.

You will learn how Bash transforms expressions such as:

```bash
"$HOME"
```

```bash
"${environment}"
```

```bash
"$(hostname)"
```

and:

```bash
"$((count + 1))"
```

before executing commands.

By the end of this part, you should understand how Bash stores, expands, quotes, transforms, exports, and safely uses data.

---

# 1. What Is a Variable?

A variable is a named location used by the shell to associate a name with a value.

For example:

```bash
name="Ann"
```

Here:

```text
name    = variable name

Ann     = value
```

You can think of it conceptually as:

```text
Variable name
     |
     v
   name
     |
     v
   "Ann"
```

Later, instead of repeatedly writing:

```text
Ann
```

you can refer to:

```bash
$name
```

Bash expands the variable and uses its value.

---

# 2. Why Variables Exist

Consider:

```bash
echo "Deploying payment-service"
echo "Checking payment-service"
echo "Restarting payment-service"
echo "Deployment of payment-service complete"
```

The application name appears four times.

If it changes, you need to modify four locations.

Instead:

```bash
app_name="payment-service"

echo "Deploying $app_name"
echo "Checking $app_name"
echo "Restarting $app_name"
echo "Deployment of $app_name complete"
```

Now the application name is defined once.

Change:

```bash
app_name="payment-service"
```

to:

```bash
app_name="orders-service"
```

and every reference uses the new value.

This reduces duplication and mistakes.

---

# 3. Creating Variables

The basic syntax is:

```bash
variable_name=value
```

Example:

```bash
environment="development"
```

Another:

```bash
server="web-server-01"
```

Another:

```bash
port=8080
```

Notice something important.

There are no spaces around:

```text
=
```

Correct:

```bash
environment="production"
```

Incorrect:

```bash
environment = "production"
```

The incorrect version is not interpreted as a variable assignment.

Bash sees separate words and may attempt to execute `environment` as a command.

You could receive:

```text
environment: command not found
```

---

# 4. Variable Naming Rules

Bash variable names should generally contain:

* letters
* numbers
* underscores

But they cannot normally begin with a number.

Valid:

```bash
name="Ann"
```

```bash
server1="web01"
```

```bash
server_name="web01"
```

```bash
DEPLOY_ENV="production"
```

Invalid:

```bash
1server="web01"
```

Invalid:

```bash
server-name="web01"
```

The hyphen has other syntactic meanings and is not valid inside a normal Bash variable name.

Invalid:

```bash
server name="web01"
```

Spaces cannot appear in a normal variable name.

---

# 5. Choosing Good Variable Names

Technically:

```bash
x="production"
```

works.

But:

```bash
environment="production"
```

is clearer.

Compare:

```bash
x="/var/log/myapp"
y="production"
z=8080
```

with:

```bash
log_directory="/var/log/myapp"
environment="production"
application_port=8080
```

The second script is easier to understand.

Use names that explain what the data represents.

---

# 6. Variable Naming Style

You will encounter several naming conventions.

Script-local variables often use lowercase:

```bash
app_name="orders-api"
```

```bash
log_directory="/var/log/orders"
```

Environment variables and important exported configuration commonly use uppercase:

```bash
PATH
HOME
USER
APP_ENV
API_URL
```

Bash does not require this convention, but it helps distinguish different kinds of values.

Be especially careful not to accidentally overwrite important existing variables such as:

```text
PATH
HOME
SHELL
PWD
```

---

# 7. Reading Variables with `$`

Creating:

```bash
name="Ann"
```

stores the value.

To retrieve it:

```bash
echo "$name"
```

Output:

```text
Ann
```

The `$` tells Bash to perform variable expansion.

Conceptually:

```text
$name
  |
  v
Find variable "name"
  |
  v
Retrieve value
  |
  v
Ann
```

---

# 8. Assignment vs Expansion

This distinction is fundamental.

Assignment:

```bash
environment="production"
```

Reading:

```bash
echo "$environment"
```

Do not write:

```bash
$environment="production"
```

because `$environment` means:

> Expand the value stored in `environment`.

The left side of a normal assignment uses the variable's **name**, not its expanded value.

---

# 9. Curly Brace Syntax

Variables can also be expanded using:

```bash
${variable}
```

For example:

```bash
name="Ann"

echo "${name}"
```

Output:

```text
Ann
```

For simple cases:

```bash
$name
```

and:

```bash
${name}
```

often produce the same result.

But curly braces become important when Bash needs to know exactly where the variable name ends.

---

# 10. Why `${variable}` Matters

Suppose:

```bash
server="web"
```

You want:

```text
web01
```

You might try:

```bash
echo "$server01"
```

But Bash interprets:

```text
server01
```

as the variable name.

If `server01` is unset, you may get nothing.

Instead:

```bash
echo "${server}01"
```

Bash can clearly see:

```text
variable = server
text     = 01
```

Output:

```text
web01
```

Curly braces remove ambiguity.

---

# 11. Strings in Bash

Bash variables commonly store text.

Example:

```bash
application="payment-api"
```

Another:

```bash
message="Deployment completed successfully"
```

Then:

```bash
echo "$message"
```

Output:

```text
Deployment completed successfully
```

A string is simply a sequence of characters.

Examples include:

```text
production
web-server-01
/var/log/application.log
Deployment completed
https://api.example.com
```

---

# 12. Numbers in Bash

Bash variables can also contain values that look like numbers:

```bash
port=8080
```

```bash
retry_count=3
```

```bash
server_count=5
```

But Bash does not treat variables like strongly typed integer variables in languages such as Java.

For example:

```bash
count=5
```

stores a shell value that can be interpreted numerically when used in arithmetic contexts.

If you run:

```bash
echo "$count"
```

you get:

```text
5
```

Later we will use arithmetic expansion to perform calculations.

---

# 13. A Common Beginner Arithmetic Mistake

Suppose:

```bash
count=5
```

You might try:

```bash
echo "$count + 1"
```

Output:

```text
5 + 1
```

Bash did not calculate anything.

It simply expanded `$count` and printed the text.

For arithmetic, use an arithmetic context such as:

```bash
echo "$((count + 1))"
```

Output:

```text
6
```

We will explore this properly later in this part.

---

# 14. Empty Variables

A variable can exist with an empty value.

For example:

```bash
database_host=""
```

Then:

```bash
echo "$database_host"
```

prints an empty line.

The variable exists, but its value is empty.

Conceptually:

```text
database_host
      |
      v
     ""
```

This is different from a variable that has never been defined.

That distinction becomes important in validation and parameter expansion.

---

# 15. Unset Variables

An unset variable has not been assigned in the current shell environment, or has been removed.

For example:

```bash
echo "$THIS_VARIABLE_PROBABLY_DOES_NOT_EXIST"
```

Under Bash's normal default behavior, this usually produces an empty string.

That can be dangerous.

Imagine:

```bash
backup_directory="$BACKUP_DIR"
```

If `BACKUP_DIR` is unexpectedly unset, your script might behave differently than intended.

Later you will learn defensive techniques for detecting missing variables.

---

# 16. Checking Whether a Variable Is Set

For now, you can experiment with:

```bash
name="Ann"
```

Then:

```bash
declare -p name
```

You may see:

```text
declare -- name="Ann"
```

For a variable that does not exist:

```bash
declare -p definitely_missing_variable
```

Bash should report that it cannot find it.

`declare` is a Bash builtin with many capabilities. We are only using it here to demonstrate the difference between a defined and undefined variable.

---

# 17. Quoting Fundamentals

Quoting is one of the most important subjects in Bash.

Many broken shell scripts are caused by incorrect quoting.

The three situations you need to understand are:

```text
"double quotes"

'single quotes'

unquoted
```

They do not behave the same way.

Consider:

```bash
name="Ann"
```

Now compare:

```bash
echo "$name"
```

```bash
echo '$name'
```

```bash
echo $name
```

These expressions may look similar, but Bash processes them differently.

---

# 18. Double Quotes

Run:

```bash
name="Ann"
```

Then:

```bash
echo "$name"
```

Output:

```text
Ann
```

Double quotes allow variable expansion.

Bash sees:

```text
"$name"
```

and expands `$name`.

Double quotes also protect the expanded result from normal word splitting and filename expansion.

This makes them extremely important for safe variable handling.

---

# 19. Single Quotes

Try:

```bash
echo '$name'
```

Output:

```text
$name
```

Why?

Single quotes preserve characters literally.

Bash does not expand `$name` inside ordinary single quotes.

So:

```bash
echo '$HOME'
```

prints:

```text
$HOME
```

not your home directory.

---

# 20. Double Quotes vs Single Quotes

Suppose:

```bash
environment="production"
```

Double quotes:

```bash
echo "Environment: $environment"
```

Output:

```text
Environment: production
```

Single quotes:

```bash
echo 'Environment: $environment'
```

Output:

```text
Environment: $environment
```

Use double quotes when you want expansions to occur while preserving the resulting value as one shell word where appropriate.

Use single quotes when you want literal text.

---

# 21. Unquoted Variables

You can technically write:

```bash
echo $environment
```

and it may appear to work.

But unquoted expansions can cause surprising behavior.

Consider:

```bash
message="Deployment completed successfully"
```

Then:

```bash
printf '<%s>\n' $message
```

The shell can split the expanded value into multiple words.

Conceptually:

```text
Deployment completed successfully
          |
          v
      word splitting
          |
          v
Deployment
completed
successfully
```

The `printf` command therefore receives multiple arguments.

Now compare:

```bash
printf '<%s>\n' "$message"
```

The expanded value remains one argument:

```text
<Deployment completed successfully>
```

This is one reason the beginner-safe default is:

> Quote variable expansions unless you specifically need the shell's splitting or pattern behavior.

---

# 22. Why Quoting Matters with Paths

Suppose:

```bash
backup_dir="/home/ann/DevOps Backups"
```

This is one path containing a space.

Unsafe:

```bash
cd $backup_dir
```

After expansion and word splitting, Bash may effectively treat it like:

```text
cd
/home/ann/DevOps
Backups
```

That is not what you intended.

Safe:

```bash
cd "$backup_dir"
```

Now the expanded value remains one argument.

This principle applies to commands such as:

```bash
cp "$source" "$destination"
```

```bash
rm "$file"
```

```bash
mkdir "$directory"
```

```bash
cat "$log_file"
```

Correct quoting is not merely style.

It can affect correctness and safety.

---

# 23. Word Splitting

Word splitting is a shell behavior where certain unquoted expansion results can be divided into multiple words.

Suppose:

```bash
servers="web01 web02 web03"
```

Then an unquoted expansion:

```bash
printf '%s\n' $servers
```

can produce separate arguments:

```text
web01
web02
web03
```

But:

```bash
printf '%s\n' "$servers"
```

produces one argument:

```text
web01 web02 web03
```

Neither behavior is automatically “always correct.”

The important point is that **you must understand which behavior you intend**.

Later, arrays will provide a much safer way to store lists.

---

# 24. Filename Expansion

Another important shell behavior is filename expansion, commonly called **globbing**.

Suppose your directory contains:

```text
app.log
database.log
nginx.log
notes.txt
```

Run:

```bash
ls *.log
```

The pattern:

```text
*.log
```

can be expanded by the shell into matching filenames.

Conceptually:

```text
*.log
   |
   v
Shell examines current directory
   |
   v
app.log database.log nginx.log
```

Then `ls` receives those filenames.

---

# 25. Variables Can Accidentally Trigger Filename Expansion

Suppose:

```bash
pattern="*.log"
```

Then:

```bash
printf '%s\n' $pattern
```

may expand matching filenames.

But:

```bash
printf '%s\n' "$pattern"
```

prints:

```text
*.log
```

This demonstrates another reason quoting matters.

Unquoted variable expansion can interact with:

1. word splitting
2. filename expansion

That can dramatically change what a command receives.

---

# 26. A Dangerous Quoting Example

Suppose:

```bash
file="important report.txt"
```

You want:

```bash
rm $file
```

Bash may split this into:

```text
rm
important
report.txt
```

That means `rm` receives two filenames rather than one.

The correct form is:

```bash
rm "$file"
```

Do not run this example against important data.

Practice deletion only with disposable files in your Bash lab.

The lesson is:

> Incorrect quoting can change which files a command operates on.

---

# 27. Parameter Expansion

When Bash processes:

```bash
"$name"
```

it performs a form of **parameter expansion**.

A parameter can include variables and certain special shell parameters.

Basic variable expansion:

```bash
$name
```

Brace form:

```bash
${name}
```

Parameter expansion becomes much more powerful than simply retrieving values.

It can eventually:

* provide defaults
* test for missing values
* remove prefixes
* remove suffixes
* replace text
* calculate string lengths

We will cover advanced forms later.

For now, understand:

```text
${variable}
     |
     v
Bash expands the parameter
     |
     v
value
```

---

# 28. Basic Parameter Expansion Example

Create:

```bash
application="orders-api"
```

Then:

```bash
echo "${application}"
```

Output:

```text
orders-api
```

Now:

```bash
echo "${application}-deployment"
```

Output:

```text
orders-api-deployment
```

The braces clearly identify where the variable name ends.

---

# 29. Default Values with Parameter Expansion

Here is a useful preview.

Suppose:

```bash
environment=""
```

You can write:

```bash
echo "${environment:-development}"
```

Output:

```text
development
```

The syntax:

```text
${variable:-default}
```

means approximately:

> If the variable is unset or empty, use this default value for this expansion.

If:

```bash
environment="production"
```

then:

```bash
echo "${environment:-development}"
```

outputs:

```text
production
```

This becomes extremely useful for configuration scripts.

---

# 30. Command Substitution

Variables can store the output of commands.

Suppose you want the hostname.

You already know:

```bash
hostname
```

Instead of merely printing it, you can capture its output:

```bash
current_host="$(hostname)"
```

Now:

```bash
echo "$current_host"
```

prints the captured hostname.

This feature is called:

**command substitution**

---

# 31. Understanding `$(command)`

The syntax is:

```bash
$(command)
```

Bash:

1. executes the command
2. captures its standard output
3. removes trailing newline characters from that captured output
4. substitutes the resulting text into the surrounding command

For example:

```bash
current_user="$(whoami)"
```

Conceptually:

```text
$(whoami)
    |
    v
Run whoami
    |
    v
ann
    |
    v
Assign result
    |
    v
current_user="ann"
```

---

# 32. Command Substitution Examples

Current user:

```bash
current_user="$(whoami)"
```

Hostname:

```bash
current_host="$(hostname)"
```

Working directory:

```bash
current_directory="$(pwd)"
```

Current date:

```bash
current_date="$(date)"
```

Then:

```bash
echo "User: $current_user"
echo "Host: $current_host"
echo "Directory: $current_directory"
echo "Date: $current_date"
```

Your script now stores command results as reusable data.

---

# 33. Why Command Substitution Is Powerful

Without command substitution:

```bash
echo "Hostname:"
hostname
```

With command substitution:

```bash
host="$(hostname)"
```

you can reuse the value later.

For example:

```bash
echo "Checking $host"
echo "Generating report for $host"
echo "Finished checking $host"
```

Eventually you can create filenames such as:

```bash
report_file="${host}-report.txt"
```

This is where variables begin connecting commands together.

---

# 34. Legacy Backticks

Older shell scripts may use:

```bash
host=`hostname`
```

instead of:

```bash
host="$(hostname)"
```

The backtick form performs command substitution too.

You should understand it because you may encounter it in old scripts.

But for new Bash code, prefer:

```bash
$(command)
```

---

# 35. Why Prefer `$(command)`?

The modern form is easier to:

* read
* identify visually
* nest
* maintain

Compare:

```bash
result="$(command)"
```

with:

```bash
result=`command`
```

Nested command substitution becomes particularly awkward with legacy backticks.

Use:

```bash
$(...)
```

for new scripts.

---

# 36. Arithmetic Expansion

Bash can perform integer arithmetic using:

```bash
$(( expression ))
```

For example:

```bash
echo "$((2 + 3))"
```

Output:

```text
5
```

This is called:

**arithmetic expansion**

---

# 37. Arithmetic with Variables

Create:

```bash
servers=5
```

Then:

```bash
echo "$((servers + 1))"
```

Output:

```text
6
```

Another example:

```bash
successful=8
failed=2
```

Then:

```bash
total="$((successful + failed))"
```

Now:

```bash
echo "$total"
```

Output:

```text
10
```

---

# 38. Common Arithmetic Operators

You will commonly encounter:

```text
+    addition
-    subtraction
*    multiplication
/    integer division
%    remainder
```

Examples:

```bash
echo "$((10 + 5))"
```

```bash
echo "$((10 - 5))"
```

```bash
echo "$((10 * 5))"
```

```bash
echo "$((10 / 5))"
```

```bash
echo "$((10 % 3))"
```

Outputs:

```text
15
5
50
2
1
```

---

# 39. Bash Arithmetic Is Primarily Integer Arithmetic

Be careful with:

```bash
echo "$((5 / 2))"
```

The result is:

```text
2
```

not:

```text
2.5
```

Bash arithmetic expansion operates with integers.

For decimal calculations, engineers typically use another tool or language appropriate for that calculation.

---

# 40. Escape Characters

The backslash:

```text
\
```

is commonly used as an escape character.

It can change how the next character is interpreted.

Suppose:

```bash
echo "The price is \$10"
```

Output:

```text
The price is $10
```

Without the backslash, `$10` could be interpreted according to shell parameter rules rather than as the literal characters you intended.

The backslash tells Bash to treat `$` literally in this context.

---

# 41. Escaping Double Quotes

Suppose you want to print:

```text
The environment is "production"
```

You can write:

```bash
echo "The environment is \"production\""
```

The backslashes prevent the inner quotes from terminating the outer double-quoted string.

---

# 42. Backslash and Newlines

A backslash can also be used to continue a command onto another physical line.

For example:

```bash
echo "This is a very long command" \
     "that continues on another line"
```

Bash treats the escaped newline as continuation.

This can improve readability for long commands.

Be careful not to place unintended characters after the continuation backslash.

---

# 43. Special Characters in Bash

Bash gives special meanings to many characters.

Examples include:

```text
$    expansion
*    wildcard
?    wildcard
#    comment
\    escape
"    double quoting
'    single quoting
|    pipe
>    output redirection
<    input redirection
&    background/control operator
;    command separator
( )  grouping/subshell/arithmetic contexts
{ }  grouping and expansion-related syntax
```

You do not need to master all of them yet.

The important lesson is:

> Bash is not reading every character as ordinary text.

Quoting and escaping tell Bash when special characters should be treated literally.

# 44. Environment Variables

So far, you have created ordinary shell variables:

```bash
app_name="orders-api"
```

But Bash also works with **environment variables**.

Environment variables are values made available in a process's environment and inherited by child processes when they are launched.

Examples commonly include:

```text
HOME
USER
SHELL
PATH
PWD
```

These variables help programs understand their environment.

---

# 45. Shell Variables vs Environment Variables

Create:

```bash
project_name="veriqta-lab"
```

This is a shell variable in your current Bash process.

Now start another Bash process and ask it to print that variable:

```bash
bash -c 'echo "$project_name"'
```

You will normally see an empty line.

Why?

Because ordinary shell variables are not automatically exported into the environment inherited by child processes.

Conceptually:

```text
Current Bash
   |
   | project_name exists here
   |
   +--> Child Bash
            |
            +--> project_name not inherited
```

---

# 46. Exporting a Variable

Use:

```bash
export project_name
```

Now run:

```bash
bash -c 'echo "$project_name"'
```

You should see:

```text
veriqta-lab
```

The variable is now exported and included in the environment passed to child processes.

---

# 47. Assignment and Export Together

Instead of:

```bash
APP_ENV="production"
export APP_ENV
```

you can write:

```bash
export APP_ENV="production"
```

Then a child process can inherit it.

For example:

```bash
bash -c 'echo "$APP_ENV"'
```

Output:

```text
production
```

---

# 48. What `export` Does Not Mean

`export` does not mean:

> Save this variable permanently on my computer.

It means approximately:

> Mark this shell variable so that it is included in the environment of subsequently launched child processes.

If you close the shell, a manually created exported variable normally disappears unless some startup/configuration mechanism recreates it later.

Persistent shell configuration will be covered later in the series.

---

# 49. Parent and Child Processes

This relationship is important.

Suppose:

```text
Terminal
   |
   v
Bash
   |
   +--> Script
   |
   +--> Git
   |
   +--> Python
   |
   +--> Another Bash
```

Programs launched by Bash are child processes.

Exported environment variables can be inherited by those children.

But a child process cannot normally change the parent's environment simply by changing its own variable.

This explains many real-world configuration behaviors.

---

# 50. The `HOME` Variable

Run:

```bash
echo "$HOME"
```

You may see:

```text
/home/ann
```

On macOS, it might resemble:

```text
/Users/ann
```

`HOME` represents the current user's home directory in typical shell environments.

Instead of hardcoding:

```bash
backup_dir="/home/ann/backups"
```

you can write:

```bash
backup_dir="$HOME/backups"
```

This is more portable between users.

---

# 51. Why `$HOME` Is Better Than Hardcoding User Paths

Bad:

```bash
config_file="/home/ann/app/config.ini"
```

If another user runs the script, that path may be wrong.

Better:

```bash
config_file="$HOME/app/config.ini"
```

Now the script adapts to the user's environment.

This is an early example of writing more reusable automation.

---

# 52. The `USER` Variable

Run:

```bash
echo "$USER"
```

You may see:

```text
ann
```

`USER` commonly contains the username associated with the shell environment.

Remember that environment variables can be modified.

For security-sensitive identity checks, do not blindly assume an environment variable is authoritative.

You already know:

```bash
whoami
```

which reports the effective username based on process credentials.

For learning and normal display purposes, `$USER` is still useful.

---

# 53. The `SHELL` Variable

Run:

```bash
echo "$SHELL"
```

You might see:

```text
/bin/bash
```

or:

```text
/bin/zsh
```

As discussed previously, `$SHELL` commonly represents the user's configured login shell.

It does not necessarily prove that the currently executing process is that shell.

For Bash-specific checks, you may inspect:

```bash
echo "$BASH_VERSION"
```

# 54. The `PATH` Variable

Run:

```bash
echo "$PATH"
```

You may see:

```text
/usr/local/bin:/usr/bin:/bin
```

`PATH` contains directories used during command lookup.

The entries are separated by colons:

```text
:
```

Conceptually:

```text
PATH
 |
 +--> /usr/local/bin
 |
 +--> /usr/bin
 |
 +--> /bin
```

When you enter:

```bash
git
```

the shell uses command-resolution rules that include searching these directories for an appropriate executable.

# 55. Why `$PATH` Must Be Handled Carefully

Suppose you accidentally run:

```bash
PATH=""
```

Now many external commands may stop resolving by name in that shell.

For example:

```bash

```

may produce:

```text
bash: ls: No such file or directory
```

or a command-not-found style error depending on the environment.

This demonstrates why overwriting important environment variables carelessly is dangerous.

If you accidentally modify PATH in a disposable lab shell, opening a new terminal may restore the normal environment from startup configuration.

Do not experiment with critical environment variables on production systems.

# 64. Safe Variable Handling Rule 1: Quote Expansions

Prefer:

```bash
echo "$app_name"
```

over:

```bash
echo $app_name
```

Prefer:

```bash
cp "$source_file" "$destination_file"
```

over:

```bash
cp $source_file $destination_file
```

Prefer:

```bash
cd "$directory"
```

over:

```bash
cd $directory
```

This protects values containing spaces and prevents unintended word splitting and filename expansion.

---

# 65. Safe Variable Handling Rule 2: Use Braces When Boundaries Are Ambiguous

Instead of:

```bash
echo "$app_namebackup"
```

if you mean the value of `app_name` followed by `backup`, use:

```bash
echo "${app_name}backup"
```

The braces make the intended variable name explicit.

---

# 66. Safe Variable Handling Rule 3: Validate Important Values

Suppose your script expects:

```bash
backup_dir="$BACKUP_DIR"
```

Do not immediately use it for destructive operations.

First verify it is what you expect.

A simple beginner check could be:

```bash
echo "Backup directory: $backup_dir"
```

Later, you will learn proper conditional validation.

For sensitive automation:

```text
Receive value
    ↓
Validate value
    ↓
Confirm assumptions
    ↓
Perform operation
    ↓
Verify result
```

---

# 67. Safe Variable Handling Rule 4: Avoid Storing Secrets Directly in Scripts

Bad:

```bash
api_key="real-secret-api-key"
```

especially if the script will be committed to Git.

Secrets embedded directly in scripts can leak through:

* source repositories
* backups
* code reviews
* logs
* screenshots

Production systems usually use more appropriate secret-management mechanisms.

Environment variables are sometimes used to pass secrets, but they also have security considerations.

The important beginner rule is:

> Do not hardcode real credentials into scripts that may be shared or committed.

---

# 68. Safe Variable Handling Rule 5: Do Not Print Secrets

Suppose:

```bash
API_TOKEN="secret-value"
```

Do not casually write:

```bash
echo "Token: $API_TOKEN"
```

Production logs may be stored for months and accessed by many systems.

A debugging statement can become a credential leak.

Prefer messages such as:

```bash
echo "API token is configured"
```

without exposing the value.

# 69. Safe Variable Handling Rule 6: Understand Empty vs Unset

Consider:

```bash

```

versus:

```bash

```

These states are different even though:

```bash

```

may appear empty in both cases.

Later, validation logic will distinguish:

```text
Variable does not exist
```

from:

```text

```

This distinction matters for configuration.

# 70. Safe Variable Handling Rule 7: Avoid Accidentally Overwriting Important Variables

Do not casually use names such as:

```text

SHELL
PWD
USER
```

for unrelated data.

Bad:

```bash

```

if you intended it to mean an application path or deployment environment.

Better:

```bash

```

or:

```bash

```

Variable naming affects safety.

# 71. Shell Expansion: Putting the Pieces Together

When Bash reads a command, it may perform several transformations before execution.

Consider:

```bash
echo "$HOME"
```

Bash sees the variable reference and expands it.

Conceptually:

```text
Input
  |
  v
echo "$HOME"
  |
  v
Parameter expansion
  |
  v
echo "/home/ann"
  |
  v
Execute echo
```

Now consider:

```bash
echo "$(hostname)"
```

Conceptually:

```text
Input
  |
  v
Command substitution
  |
  v
Run hostname
  |
  v
web01
  |
  v
echo "web01"
```

And:

```bash
echo "$((2 + 3))"
```

becomes:

```text
Arithmetic expansion
      |
      v
      5
```

These transformations are collectively part of how the shell processes your command line.

# 72. A Combined Expansion Example

Suppose:

```bash
app_name="orders"
instance=2
```

Now:

```bash
echo "${app_name}-web-$((instance + 1))-$(hostname)"
```

Bash performs several operations.

First:

```text
${app_name}
      ↓
orders
```

Then:

```text
$((instance + 1))
      ↓
3
```

Then:

```text
$(hostname)
      ↓
current hostname
```

The final output might be:

```text
orders-web-3-dev-server
```

You are beginning to see how Bash can construct dynamic information from multiple sources.

# 73. Practical Configuration Script

Now we will build a small configuration-aware script.

The goal is to demonstrate:

* variables
* environment variables
* defaults
* parameter expansion
* command substitution
* arithmetic expansion
* quoting
* readable output

Create:

```bash
nano app-config.sh
```

Add:

```bash
#!/usr/bin/env bash

# app-config.sh
# Demonstrates basic Bash configuration and variable handling.

app_name="veriqta-api"

environment="${APP_ENV:-development}"

application_port="${APP_PORT:-8080}"

retry_count="${RETRY_COUNT:-3}"

current_user="$(whoami)"

current_host="$(hostname)"

working_directory="$PWD"

next_retry_count="$((retry_count + 1))"

echo "================================"
echo "APPLICATION CONFIGURATION"
echo "================================"

echo
echo "Application: $app_name"
echo "Environment: $environment"
echo "Port: $application_port"
echo "Retry count: $retry_count"
echo "Next retry count: $next_retry_count"

echo
echo "Runtime information:"
echo "User: $current_user"
echo "Host: $current_host"
echo "Working directory: $working_directory"

echo
echo "Important environment paths:"
echo "Home: $HOME"
echo "Shell: $SHELL"

echo
echo "================================"
echo "CONFIGURATION CHECK COMPLETE"
echo "================================"
```

Save the script.

Make it executable:

```bash
chmod +x app-config.sh
```

Run:

```bash
./app-config.sh
```

# 75. Understanding the Configuration Script

Let's examine the important lines.

## Application variable


is used.

## Another command substitution


# 91. Security Warning: Expansion and Destructive Commands

Imagine:

```bash
target_directory="$BACKUP_DIR"
```

and later:

```bash
rm -rf "$target_directory"
```

If `BACKUP_DIR` is unexpectedly empty or incorrect, the consequences could be serious depending on the complete command and surrounding logic.

This is why production scripts should validate important variables before destructive operations.

A safer engineering model is:

```text
Receive configuration
        ↓
Check variable exists
        ↓
Check value is non-empty
        ↓
Check value matches expected pattern/path
        ↓
Confirm target exists
        ↓
Perform operation
        ↓
Verify
```

We will build these safeguards as the series progresses.

Do not experiment with destructive recursive deletion commands while learning variable expansion.

# 93. What You Should Now Understand

After Part 3, you should understand that:

* Variables associate names with values.
* Bash assignments use `name=value` without spaces around `=`.
* Variable names generally use letters, numbers, and underscores.
* Variable names cannot normally begin with a number.
* `$variable` expands a variable's value.
* `${variable}` makes variable boundaries explicit.
* Bash variables commonly store strings.
* Numeric-looking values can be used in arithmetic contexts.
* Variables can be empty.
* Variables can also be unset.
* Empty and unset are not necessarily the same state.
* Double quotes allow expansion while protecting values from normal word splitting and filename expansion.
* Single quotes preserve literal text.
* Unquoted expansions can trigger word splitting and filename expansion.
* Quoting is a correctness and security concern.
* `*.log` is an example of filename expansion.
* `${variable}` is parameter expansion syntax.
* Parameter expansion can provide default values.
* `$(command)` captures command output.
* Legacy backticks also perform command substitution but should generally be avoided in new scripts.
* `$(( ))` performs integer arithmetic expansion.
* Backslashes can escape special characters.
* Bash gives special meaning to characters such as `$`, `*`, `?`, `#`, `|`, and `>`.
* Shell variables are not automatically inherited by child processes.
* `export` marks variables for inclusion in child-process environments.
* Exported variables are not automatically permanent across new terminal sessions.
* `$HOME` commonly represents the user's home directory.
* `$USER` commonly contains the username from the environment.
* `$SHELL` commonly identifies the configured login shell.
* `$PATH` influences command lookup.
* `$PWD` contains the current working directory.
* `$OLDPWD` contains the previous working directory.
* `env` and `printenv` can inspect environment variables.
* `unset` removes variables.
* Real scripts should quote variable expansions and validate important configuration.
* Secrets should not be hardcoded or casually printed.
* Variables are a major mechanism for making Bash automation reusable and configurable.

Double quotes allow variable expansion.

### Answer 9

# Part 3 Summary

You have moved from scripts containing fixed commands to scripts capable of storing and transforming data.

The basic variable model is:

```text
Create value
    ↓
variable="value"
    ↓
Retrieve value
    ↓
"$variable"
```

You now understand parameter expansion:

```text
${variable}
     ↓
Variable value
```

command substitution:

```text
$(command)
     ↓
Run command
     ↓
Capture output
     ↓
Use as data
```

and arithmetic expansion:

```text
$(( expression ))
       ↓
Perform integer calculation
       ↓
Use result
```

You also understand why quoting is fundamental:

```text
Unquoted expansion
       |
       +--> word splitting
       |
       +--> filename expansion
       |
       +--> unexpected arguments
```

while:

```text
"$variable"
     |
     v
Expansion occurs
     |
     v
Value remains protected as intended
```

And you have learned the relationship between shell variables and environment variables:

```text
Current Bash
    |
    | normal shell variable
    |
    +--> available here
```

versus:

```text
Current Bash
    |
    | export VARIABLE
    |
    +--> Child process
    |       |
    |       +--> receives VARIABLE
    |
    +--> Another child process
            |
            +--> receives VARIABLE
```

Most importantly, you can now see how variables make automation configurable:

```text
Environment / Configuration
          |
          v
       Variables
          |
          v
      Bash Script
          |
          +--> Commands
          +--> Decisions
          +--> Paths
          +--> Tools
          +--> Runtime data
```

The engineering habits to keep from Part 3 are:

```text
Use meaningful variable names.

Quote expansions by default.

Use braces when boundaries are unclear.

Understand where data comes from.

Do not confuse empty with unset.

Export only when child processes need the value.

Do not overwrite important environment variables carelessly.

Never hardcode real secrets into shareable scripts.

Do not print secrets into logs.

Validate important configuration before using it.

Treat command output and external configuration as data that may need validation.
```
