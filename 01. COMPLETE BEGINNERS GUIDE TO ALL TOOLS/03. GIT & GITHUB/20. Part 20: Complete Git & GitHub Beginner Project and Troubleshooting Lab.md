# 15. Create the Application

Open:

```text
src/monitor.py
```

and add:

```python
from pathlib import Path
import urllib.request

import yaml


def load_services(config_path: str) -> list[dict]:
    path = Path(config_path)

    with path.open("r", encoding="utf-8") as file:
        config = yaml.safe_load(file)

    return config.get("services", [])


def check_service(url: str, timeout: int = 5) -> bool:
    try:
        with urllib.request.urlopen(url, timeout=timeout) as response:
            return 200 <= response.status < 400
    except Exception:
        return False


def main() -> None:
    services = load_services("config/services.yaml")

    for service in services:
        name = service["name"]
        url = service["url"]

        if check_service(url):
            print(f"{name}: healthy")
        else:
            print(f"{name}: unavailable")


if __name__ == "__main__":
    main()
```

Do not focus primarily on the Python.

The Git lesson is about managing this project through version control.

# 41. Authentication Choice

GitHub supports multiple authentication approaches.

For command-line Git, two common transports are:

```text
HTTPS

SSH
```

A Git remote can therefore use an HTTPS or SSH-style remote address. GitHub documents both transport types.

Choose one approach and use it consistently.

---

# 42. SSH Authentication Path

If using SSH, you need:

```text
SSH key pair
    |
    +--> Private key stays local
    |
    +--> Public key added to GitHub
```

Check existing keys:

```bash
ls -la ~/.ssh
```

A common key-generation command is:

```bash
ssh-keygen -t ed25519 -C "you@example.test"
```

Do not share the resulting private key.

Typical private-key file:

```text
~/.ssh/id_ed25519
```

Typical public-key file:

```text
~/.ssh/id_ed25519.pub
```

Only the public key is added to the GitHub account.

---

# 43. Test SSH Authentication

After configuring your key:

```bash
ssh -T git@github.com
```

The first connection may ask you to verify the host fingerprint.

Verify it through official GitHub guidance rather than blindly accepting an unexpected fingerprint.

If authentication succeeds, GitHub identifies the account.

GitHub currently documents SSH as a supported secure authentication method.

---

# 44. HTTPS Authentication Path

If using HTTPS, modern GitHub command-line authentication does not use your normal account password as the Git password.

Common methods include:

```text
Git Credential Manager

Personal access tokens

GitHub CLI credential integration
```

Do not store a token inside:

```text
README.md

shell scripts

committed configuration

remote URLs in project documentation
```

Treat access tokens as secrets.

# 79. Authentication Troubleshooting Lab

Do not deliberately expose or destroy real credentials.

Instead, learn the diagnosis process.

First:

```bash
git remote -v
```

Determine whether the remote uses:

```text
SSH
```

```text
HTTPS
```

The troubleshooting path differs.

---

# 80. SSH Troubleshooting Checklist

If the remote uses SSH and Git reports:

```text
Permission denied (publickey)
```

investigate in this order:

```text
1. Is the remote SSH?

2. Does an SSH private key exist?

3. Is the matching public key registered with the correct GitHub account?

4. Is the SSH agent running?

5. Is the key loaded?

6. Is the expected account being used?

7. Does that account have repository access?
```

Useful commands:

```bash
ls -la ~/.ssh
```

```bash
ssh-add -l
```

```bash
ssh -T git@github.com
```

For deeper diagnostics:

```bash
ssh -vT git@github.com
```

Read the verbose output.

Do not randomly delete keys.

---

# 81. HTTPS Troubleshooting Checklist

If the remote uses HTTPS, investigate:

```text
1. Is the remote correct?

2. Which credential helper is configured?

3. Is the correct GitHub account being used?

4. Is the stored token valid?

5. Does it have required repository access?

6. Does the organization require additional authorization?

7. Is the repository private?
```

Never paste a token into a public issue or repository file.

---

# 82. Distinguish Authentication and Authorization

These are different.

Authentication asks:

```text
Who are you?
```

Authorization asks:

```text
Are you allowed to perform this action?
```

You might authenticate successfully but still receive:

```text
permission denied
```

because your account lacks write access.

# 92. Git Rollback vs Operational Rollback

Remember:

```text
git revert
```

creates history that reverses the Git change.

It does not guarantee:

```text
production has safely rolled back
```

For this simple replica change, reversal is conceptually straightforward.

But real production changes may involve:

```text
Database migrations

Storage deletion

Terraform replacement

External systems

Certificates

Persistent data

Irreversible API changes
```

Git recovery and system recovery are not always identical.

# 123. Rebase Mental Model

Before:

```text
A---B---C---F---G
        \
         D---E
```

After rebasing the feature:

```text
A---B---C---F---G---D'---E'
```

D and E were replayed.

They became new commits.

That is why rebasing shared history requires care.

---

# 124. Cherry-Pick Mental Model

Original:

```text

A---B---C---D
            ^
            |
          useful fix
```

Destination:

```text

A---B---X
```

Cherry-pick D:

```text
A---B---X---D'
```

The logical change was applied into a different history.

Stash is temporary local storage.

# 126. Reflog Mental Model

Normal log asks:



That is why reflog can recover commits after:

```text

```

in many local recovery situations.

# 129. Security Mental Model

Never treat Git as a secret manager.

```text

    |
    v
Git
```

is normal.

But:


require secure secret-management practices.

```text

```

Then investigate cleanup.

# 130. Safe Beginner Rules

Keep these rules after finishing the course.

1. Run `git status` frequently.

2. Know your branch before making changes.

3. Inspect `git diff` before staging.

4. Inspect `git diff --staged` before committing.

5. Use meaningful commit messages.

6. Keep commits focused where practical.

7. Use branches for isolated work.

8. Do not push directly to protected production branches.

9. Review pull requests by examining actual diffs.

10. Never commit secrets intentionally.

11. Understand `.gitignore` before trusting it.

12. Fetch before diagnosing remote divergence.

13. Never use force push simply because a push was rejected.

14. Do not rebase shared history casually.

15. Use operation-specific abort commands when appropriate.

16. Use reflog when committed work appears lost.

17. Preserve missing commits with a recovery branch before cleaning history.

18. Do not assume Git success means application success.

19. Test after merge, rebase, cherry-pick, and infrastructure changes.

20. Verify production after deployment.

# 133. Scenario 1 Answer: Push Rejected

Do not assume non-fast-forward.

Read the exact error.

Start:

```bash
git status
git branch --show-current
git remote -v
```

If it is non-fast-forward:

```bash
git fetch origin
git log --oneline --graph --decorate --all
```

Inspect divergence.

Do not force push blindly.

---

# 134. Scenario 2 Answer: Commit Missing After Rebase

Start:

```bash
git status
```

Then:

```bash
git reflog
```

Find candidate commit.

Inspect:

```bash
git show <commit>
```

Preserve:

```bash
git branch recovery/missing-work <commit>
```

Then investigate how the rebase changed history.

---

# 135. Scenario 3 Answer: Script Not Executable

Inspect:

```bash
git diff --summary
ls -l <script>
```

Check whether executable mode changed.

Do not begin rewriting script logic before confirming the actual failure.

---

# 136. Scenario 4 Answer: Secret Exposed

Highest priority:

```text
Revoke or rotate the credential.
```

Then determine:

```text
Where was it pushed?

Who could access it?

Does history contain it?

Did CI or logs expose it elsewhere?
```

Then coordinate repository cleanup if necessary.

Do not merely delete the file from the latest commit and declare the incident solved.

---

# 137. Scenario 5 Answer: Git and Kubernetes Differ

You have configuration drift.

Investigate:

```text
What does Git declare?

What does the cluster actually contain?

Was the difference manual?

Is a GitOps controller running?

Is reconciliation healthy?

Is the controller watching the correct repository/path/revision?
```

Do not immediately overwrite production before understanding whether Git or the runtime state reflects the intended configuration.
