# Part 12: Auto Scaling and Building Resilient EC2 Applications

In Part 11, you built an application behind an Application Load Balancer:

```text
Internet
   |
   v
Application Load Balancer
   |
   v
Target Group
   |
   +----------+
   |          |
   v          v
EC2 A       EC2 B
```

This solved an important problem.

Users no longer connect directly to individual EC2 instances.

The Application Load Balancer provides a single application endpoint and distributes requests among healthy targets.

But there is still a major weakness.

Who created EC2 A and EC2 B?

You did.

Who replaces EC2 A if it fails?

Without additional automation, you do.

Who creates additional instances when traffic suddenly increases?

Again, without additional automation, you do.

That is not a resilient production design.

We need the infrastructure itself to respond.

This is where Amazon EC2 Auto Scaling becomes important.

* A deployment introduces a bad configuration

# 1. Start With the Problem

Suppose your application currently has two EC2 instances:

```text
                 ALB
                /   \
               /     \
              v       v
           EC2 A     EC2 B
```

Both are healthy.

Everything works.

Then EC2 A fails.

Now:

```text
                 ALB
                /   \
               /     \
              v       v
           EC2 A     EC2 B
             X
           FAILED
```

The ALB health check can identify that EC2 A is unhealthy.

It can stop normally sending application traffic to that target.

That is useful.

But ask another question:

Who creates EC2 C to replace EC2 A?

The load balancer does not exist to manage your EC2 fleet.

Load balancing and Auto Scaling solve different problems.

---

# 2. Load Balancing vs Auto Scaling

Remember this distinction.

A load balancer answers:

```text
Where should this request go?
```

Auto Scaling answers:

```text
How much compute capacity should exist?
```

And:

```text
Are the required instances still healthy?
```

And:

```text
Should an unhealthy instance be replaced?
```

Together:

```text
Users
  |
  v
ALB
  |
  | distributes requests
  v
Target Group
  |
  v
Auto Scaling Group
  |
  | manages capacity
  |
  +---- EC2
  +---- EC2
  +---- EC2
```

The ALB manages request distribution.

The Auto Scaling Group manages the EC2 fleet.

---

# 3. What Does Scaling Mean?

Scaling means changing the amount of computing capacity available to an application.

Imagine your application currently needs:

```text
2 CPU cores
4 GB RAM
```

Then traffic increases.

Now it needs more capacity.

There are two fundamental ways to provide that capacity:

1. Vertical scaling
2. Horizontal scaling

---

# 4. Vertical Scaling

Vertical scaling means making an individual machine more powerful.

Suppose you start with:

```text
Small EC2
2 vCPU
4 GB RAM
```

You change to something larger:

```text
Larger EC2
8 vCPU
32 GB RAM
```

Conceptually:

```text
Small Server
     |
     v
Bigger Server
```

You increased the capacity of one machine.

This is sometimes called:

```text
Scaling up
```

The reverse is:

```text
Scaling down
```

---

# 5. Vertical Scaling Example

Imagine an application server is consistently running near its practical resource limit.

You could move from a smaller EC2 instance type to a larger one.

Conceptually:

```text
Before

EC2
2 vCPU
4 GB RAM
```

to:

```text
After

EC2
8 vCPU
32 GB RAM
```

You still have:

```text
1 server
```

but the server is more powerful.

---

# 6. Problems With Vertical Scaling

Vertical scaling can be useful, but it has limitations.

## There is always a maximum machine size

You cannot make one server infinitely powerful.

## One server can remain a failure dependency

Even a very large server can fail.

## Resizing may require operational work

Depending on the workload and change being made, resizing can involve stopping, changing, restarting, validating, and potentially disrupting the instance.

## Capacity is concentrated

You might have:

```text
1 extremely powerful server
```

instead of:

```text
several independent servers
```

That may not provide the resilience your application requires.

---

# 7. Horizontal Scaling

Horizontal scaling means changing the number of machines.

Instead of:

```text
1 EC2
```

you might run:

```text
3 EC2 instances
```

Conceptually:

```text
           ALB
        /   |   \
       v    v    v
     EC2  EC2  EC2
```

When demand increases:

```text
           ALB
      /   / | \   \
     v   v  v  v   v
    EC2 EC2 EC2 EC2 EC2
```

You added instances rather than making one instance larger.

This is:

```text
Scale out
```

When demand decreases, some instances can be removed.

This is:

```text
Scale in
```

---

# 8. Scale Up vs Scale Out

Do not confuse these terms.

```text
Scale up
=
Make one server larger
```

```text
Scale out
=
Add more servers
```

Likewise:

```text
Scale down
=
Make a server smaller
```

```text
Scale in
=
Remove servers
```

For horizontally scalable web applications, Auto Scaling primarily manages scale-out and scale-in.

---

# 9. Why Horizontal Scaling Works Well With ALB

Suppose your application grows from:

```text
2 instances
```

to:

```text
5 instances
```

Users should not need to know.

They continue accessing:

```text
https://app.example.com
```

The architecture changes behind the ALB:

```text
Before

         ALB
        /   \
       v     v
     EC2     EC2
```

After scaling:

```text
             ALB
       /   /  |  \   \
      v   v   v   v   v
    EC2 EC2 EC2 EC2 EC2
```

The public endpoint remains the same.

That is one reason load balancing and horizontal scaling fit together naturally.

---

# 10. What Is Amazon EC2 Auto Scaling?

Amazon EC2 Auto Scaling is an AWS service for automatically managing groups of EC2 instances.

At its core, it helps maintain the amount of EC2 capacity your application requires.

An Auto Scaling Group can:

* Launch EC2 instances
* Maintain a desired number of instances
* Detect certain unhealthy instances
* Replace unhealthy instances
* Increase capacity
* Decrease capacity
* Distribute instances across Availability Zones
* Integrate with load balancer target groups
* Use scaling policies
* Respond to metrics

The central object is called an:

```text
Auto Scaling Group
```

often abbreviated:

```text
ASG
```

---

# 11. What Is an Auto Scaling Group?

An Auto Scaling Group is a logical group of EC2 instances managed together.

Instead of manually thinking:

```text
EC2 A
EC2 B
EC2 C
```

you think:

```text
Application Auto Scaling Group
```

Inside it:

```text
Auto Scaling Group
       |
       +---- EC2 A
       +---- EC2 B
       +---- EC2 C
```

The group manages the instances according to configuration you define.

AWS describes an Auto Scaling Group as a collection of EC2 instances treated as a logical grouping for automatic scaling and management.

---

# 12. The Desired State Idea

This is one of the most important ideas in infrastructure engineering.

Suppose you declare:

```text
Desired capacity = 3
```

The Auto Scaling Group tries to maintain:

```text
3 instances
```

Current:

```text
EC2 A
EC2 B
EC2 C
```

Count:

```text
3
```

Desired:

```text
3
```

No correction is required.

But then:

```text
EC2 B fails
```

Now:

```text
Current healthy/running capacity:
2

Desired:
3
```

The system recognizes the difference.

It launches replacement capacity.

Conceptually:

```text
Desired State
     |
     v
3 instances

Actual State
     |
     v
2 instances

Difference
     |
     v
Launch replacement
```

This is much more powerful than manually watching servers.

---

# 13. Auto Scaling Is Not Only About Traffic

The name sometimes causes beginners to think:

```text
Auto Scaling = add servers when CPU increases
```

That is only part of the story.

Auto Scaling also helps with:

```text
Capacity maintenance
```

and:

```text
Instance replacement
```

Even if you always want exactly three instances:

```text
Min = 3
Desired = 3
Max = 3
```

an Auto Scaling Group can still provide value by helping maintain that capacity and replacing instances it determines are unhealthy.

# 15. What Is a Launch Template?

The Auto Scaling Group needs instructions for creating new EC2 instances.

It needs to know things such as:

```text
Which AMI?

Which instance type?

Which Security Group?

Which IAM instance profile?

Which storage configuration?

Which SSH key, if one is required?

What user data should run?
```

These launch settings are defined through a:

```text
Launch Template
```

---

# 16. Think of a Launch Template as a Server Blueprint

Imagine a blueprint that says:

```text
AMI:
Amazon Linux

Instance type:
t3.micro

Security Group:
prod-app-sg

IAM instance profile:
prod-app-role

Storage:
20 GiB

User data:
Install and start application
```

When Auto Scaling needs another instance, it uses that blueprint.

Conceptually:

```text
Launch Template
      |
      +----> EC2 A
      |
      +----> EC2 B
      |
      +----> EC2 C
```

This promotes consistency.

---

# 17. Why Consistency Matters

Imagine manually creating three servers.

EC2 A:

```text
Correct AMI
Correct SG
Correct application
```

EC2 B:

```text
Correct AMI
Wrong SG
Correct application
```

EC2 C:

```text
Old AMI
Correct SG
Old application
```

Now your fleet is inconsistent.

This is configuration drift.

A launch template helps make instance creation repeatable.

---

# 18. Launch Template Versions

Launch templates can have versions.

Conceptually:

```text
Launch Template

Version 1
Old configuration

Version 2
Updated configuration

Version 3
New configuration
```

This matters when your server configuration changes.

For example:

```text
Version 1
Application v1
```

then:

```text
Version 2
Application v2
```

You need to understand which version your Auto Scaling Group uses.

Changing a template version does not magically mean every existing instance instantly transforms into the new configuration.

Existing and future instance behavior must be managed deliberately.

---

# 19. Launch Template vs Running Instance

A launch template is not an EC2 instance.

It is configuration used to launch instances.

Think:

```text
Blueprint
!=
Building
```

Similarly:

```text
Launch Template
!=
EC2 Instance
```

The template describes how instances should be created.

---

# 20. The Three Capacity Numbers

Every beginner must understand these:

```text
Minimum capacity
Desired capacity
Maximum capacity
```

They control the size boundaries of the Auto Scaling Group.

---

# 21. Minimum Capacity

Minimum capacity means:

```text
Do not scale below this group size.
```

Example:

```text
Minimum = 2
```

Even if traffic becomes very low, dynamic scaling should not reduce the group's desired capacity below 2.

Why might you want this?

Because you may want:

```text
At least two application instances
```

available for resilience.

---

# 22. Maximum Capacity

Maximum capacity means:

```text
Do not scale above this group size.
```

Example:

```text
Maximum = 6
```

Even if a scaling policy determines more capacity would be useful, the group will not increase its desired capacity beyond that configured maximum.

This protects against uncontrolled fleet growth.

But it can also become a bottleneck.

If:

```text
Current capacity = 6
Maximum = 6
```

and demand continues increasing, the ASG cannot scale beyond six until the limit is changed.

---

# 23. Desired Capacity

Desired capacity is the capacity the Auto Scaling Group currently attempts to maintain.

Example:

```text
Minimum = 2
Desired = 3
Maximum = 6
```

The group initially aims for:

```text
3 instances
```

The allowed range is:

```text
2 to 6
```

---

# 24. Understanding the Relationship

Suppose:

```text
Minimum = 2
Desired = 3
Maximum = 6
```

Then:

```text
2 <= 3 <= 6
```

This is valid.

Desired capacity must stay within the configured minimum and maximum boundaries.

---

# 25. Capacity Example

Start:

```text
Min = 2
Desired = 2
Max = 6
```

Current fleet:

```text
EC2 A
EC2 B
```

Traffic increases.

Scaling policy changes desired capacity:

```text
Desired = 4
```

Auto Scaling launches:

```text
EC2 C
EC2 D
```

Now:

```text
EC2 A
EC2 B
EC2 C
EC2 D
```

Traffic later decreases.

Desired capacity becomes:

```text
2
```

The ASG can terminate capacity until the group returns to two instances.

That is dynamic horizontal scaling.

---

# 26. What Is Scale-Out?

Scale-out means adding capacity.

Example:

```text
Before:

EC2 A
EC2 B
```

Demand increases.

After:

```text
EC2 A
EC2 B
EC2 C
EC2 D
```

This is:

```text
Scale-out
```

---

# 27. What Is Scale-In?

Scale-in means removing capacity.

Example:

```text
Before:

EC2 A
EC2 B
EC2 C
EC2 D
```

Demand decreases.

After:

```text
EC2 A
EC2 B
```

This is:

```text
Scale-in
```

Scale-in must be handled carefully because terminating an instance that is serving active users can cause disruption if the application and load-balancing behavior are poorly designed.

---

# 28. Why Maximum Capacity Exists

Imagine a broken scaling configuration.

CPU remains high because the application has a software bug.

The scaling policy keeps requesting more capacity.

Without sensible boundaries, this could create unnecessary infrastructure and cost.

Maximum capacity creates a guardrail.

But do not choose it arbitrarily.

Too low:

```text
Application cannot scale enough.
```

Too high without thought:

```text
Potential unnecessary cost exposure.
```

Capacity planning still matters.

---

# 29. What Is a Scaling Policy?

A scaling policy defines how Auto Scaling should change capacity in response to conditions.

Conceptually:

```text
Metric changes
      |
      v
Scaling Policy
      |
      v
Change desired capacity
      |
      v
Launch or terminate instances
```

Several scaling approaches exist.

For this beginner foundation, understand:

* Target tracking
* Step scaling concept
* Simple scaling concept
* Scheduled scaling concept
* Predictive scaling concept

But focus most deeply on target tracking.

---

# 30. Target Tracking Scaling

Target tracking works similarly to a thermostat.

Imagine:

```text
Desired room temperature:
22°C
```

If the room becomes too warm, the system reacts.

If it becomes too cold, it reacts differently.

Target tracking applies a similar idea to a metric.

Example:

```text
Average CPU target:
50%
```

The Auto Scaling system attempts to adjust capacity so the selected metric stays around the target.

---

# 31. CPU Target Tracking Example

Suppose:

```text
Min = 2
Desired = 2
Max = 6
```

Target:

```text
Average CPU utilization = 50%
```

Current:

```text
EC2 A CPU = 85%
EC2 B CPU = 79%
```

Average CPU is well above the target.

Auto Scaling can increase capacity.

For example:

```text
2 instances
     |
     v
3 instances
```

or more, depending on the policy's calculations and conditions.

With more capacity, the workload may be spread across additional instances.

---

# 32. Do Not Interpret 50% as a Magic Number

A target such as:

```text
50% CPU
```

is only an example.

The right metric and target depend on the application.

A CPU-heavy application may correlate well with CPU.

Another application may become overloaded because of:

* Request volume
* Memory pressure
* Queue depth
* Network throughput
* Database connections
* Worker saturation

before CPU becomes high.

The scaling metric should represent actual application demand.

---

# 33. ALB Request Count Per Target

For an application behind an Application Load Balancer, another useful metric can be:

```text
ALBRequestCountPerTarget
```

Conceptually:

```text
Requests
   |
   v
ALB
   |
   v
Targets
```

Suppose your application performs well when each target handles approximately a certain request volume.

You can create a target tracking policy around request count per target.

This can sometimes reflect application demand more directly than CPU.

Amazon CloudWatch collects and exposes metrics from AWS resources and services.

Examples relevant to Auto Scaling include metrics related to:

* EC2 CPU
* Application Load Balancer activity
* Auto Scaling capacity
* Custom application measurements

Conceptually:

```text
EC2 / ALB / Application
          |
          v
      CloudWatch
          |
          v
   Scaling Decision
          |
          v
Auto Scaling Group
```

---

# 35. CloudWatch-Based Scaling

A simplified scaling path looks like:

```text
Application demand rises
          |
          v
Metric changes
          |
          v
CloudWatch observes metric
          |
          v
Scaling policy responds
          |
          v
Desired capacity changes
          |
          v
```

# 36. Target Tracking Example

Suppose:

```text
Min:
2

Desired:
2

Max:
6

Target:
50% average CPU
```

Normal load:

```text
EC2 A: 45%
EC2 B: 48%
```

No major capacity change may be needed.

Traffic spike:

```text
EC2 A: 88%
EC2 B: 91%
```

The scaling system sees that the metric is above the target.

It can increase desired capacity.

New state:

```text
EC2 A
EC2 B
EC2 C
```

If demand remains high:

```text
EC2 D
```

may eventually be added as the policy continues responding.

# 37. Why Scaling Is Not Instantaneous

A common beginner assumption is:

```text
CPU reaches 80%
        |
        v
New server instantly handles traffic
```

Real life is more complicated.

A new instance must:

1. Be requested.
2. Launch.
3. Boot the operating system.
4. Run initialization.
5. Install or obtain application components if required.
6. Start the application.
7. Register with the target group.
8. Pass health checks.
9. Become ready for traffic.

This can take time.

Therefore:

```text
Scaling is not instantaneous.
```

Your architecture must tolerate the time required for new capacity to become useful.

---

# 38. Instance Warmup

A newly launched instance may need time before it should influence scaling decisions normally.

This is where instance warmup becomes important.

Suppose startup takes:

```text
3 minutes
```

During those three minutes:

```text
Instance exists
```

does not necessarily mean:

```text
Instance is fully ready to carry normal workload
```

Auto Scaling supports instance warmup concepts to account for this behavior.

---

# 39. Why Warmup Matters

Imagine:

```text
2 overloaded instances
```

Auto Scaling launches:

```text
Instance C
```

But C is still:

```text
Installing packages
Starting application
Loading configuration
```

If the scaling system immediately treats C as normal mature capacity, it could misinterpret the group's current performance.

Proper warmup configuration helps prevent unstable scaling behavior.

---

# 40. What Is Step Scaling?

Step scaling adjusts capacity according to how far a metric crosses an alarm threshold.

Conceptually:

```text
CPU 60-70%
Add 1 instance

CPU 70-85%
Add 2 instances

CPU >85%
Add 3 instances
```

The exact policy design can vary.

The important beginner idea is:

```text
Different severity
=
Different scaling adjustment
```

Target tracking is generally easier to begin with because you specify the metric target you want the system to maintain.

---

# 41. Scheduled Scaling

Sometimes demand is predictable.

Imagine an internal application that becomes busy every weekday at:

```text
09:00
```

You may know capacity should increase before the traffic arrives.

Scheduled scaling lets you change capacity based on time.

Conceptually:

```text
08:45
Increase capacity

18:00
Reduce capacity
```

This differs from reactive metric-based scaling.

---

# 42. Predictive Scaling Concept

Predictive scaling uses historical patterns to forecast future capacity needs.

Conceptually:

```text
Historical demand
       |
       v
Forecast
       |
       v
Prepare capacity
```

This can help when demand follows recurring patterns.

For a beginner, understand the concept first.

You do not need predictive scaling to complete this lab.

---

# 43. Scaling and Resilience Are Related but Different

Scaling answers:

```text
Do I have enough capacity for demand?
```

Resilience asks:

```text
Can the system continue functioning when components fail?
```

Auto Scaling contributes to both.

Example:

```text
Traffic increase
→ scale out
```

Failure:

```text
Instance unhealthy
→ replace instance
```

Those are different triggers producing related fleet-management actions.

---

# 44. Instance Health

An Auto Scaling Group monitors the health of its instances.

By default, EC2 health information is used.

Additional health sources can also be configured.

A key distinction for our architecture is:

```text
EC2 health
```

versus:

```text
Elastic Load Balancing health
```

---

# 45. EC2 Health vs Application Health

Imagine an EC2 instance.

The virtual machine itself is running correctly.

From EC2's perspective:

```text
Instance:
Healthy
```

But Nginx has crashed.

The application port:

```text
8080
```

is no longer listening.

From the ALB's perspective:

```text
Target:
Unhealthy
```

These are not contradictory.

They are checking different things.

---

# 46. EC2 Health Check

EC2 health information focuses on the instance's infrastructure and reachability status.

It can detect certain problems involving the instance or underlying AWS infrastructure.

But:

```text
EC2 is running
```

does not necessarily mean:

```text
Application is serving users correctly.
```

That distinction is essential.

---

# 47. Elastic Load Balancing Health Check

The load balancer checks whether the target can satisfy its configured health check.

Example:

```text
GET /health
```

Expected:

```text
200 OK
```

If the application fails that health check:

```text
ALB:
Target unhealthy
```

This gives you application-path health information that basic EC2 health alone may not provide.

---

# 48. Important Default Behavior

Do not assume that attaching an ALB automatically means the Auto Scaling Group will replace every target the ALB marks unhealthy.

By default, EC2 Auto Scaling uses EC2 health checks.

Elastic Load Balancing health checks must be enabled for the Auto Scaling Group if you want Auto Scaling to use those ELB health results when determining whether to replace instances.

This distinction matters enormously.

---

# 49. Why Enable ELB Health Checks?

Imagine:

```text
EC2:
Running

Application:
Broken

ALB health:
Unhealthy
```

Without using ELB health checks for the ASG:

```text
Auto Scaling may still consider
the EC2 instance healthy.
```

With ELB health checks enabled:

```text
ALB reports target unhealthy
          |
          v
Auto Scaling recognizes unhealthy instance
          |
          v
Replacement process
```

This creates much stronger application-level recovery.

---

# 50. Instance Replacement

Suppose:

```text
Desired capacity = 3
```

Current:

```text
EC2 A = healthy
EC2 B = healthy
EC2 C = unhealthy
```

Auto Scaling determines C is unhealthy.

It replaces the unhealthy instance to maintain desired capacity.

Conceptually:

```text
EC2 C
Unhealthy
   |
   v
Terminate
   |
   v
Launch EC2 D
   |
   v
Bootstrap
   |
   v
Register
   |
   v
Health checks
   |
   v
Healthy
```

The desired fleet returns to:

```text
3 healthy instances
```

assuming the replacement can successfully launch and become healthy.

---

# 51. Why Replacement Is Powerful

Without Auto Scaling:

```text
Server dies
   |
Engineer receives alert
   |
Engineer investigates
   |
Engineer launches replacement
   |
Engineer configures server
   |
Engineer adds server to ALB
```

With properly designed automation:

```text
Server unhealthy
   |
Auto Scaling detects state
   |
Replacement launched
   |
Bootstrapping runs
   |
Target registration occurs
   |
Health check passes
   |
Traffic resumes through new target
```

The engineer should still investigate why the failure happened.

Automation restores capacity.

It does not eliminate root-cause analysis.

---

# 52. Self-Healing Does Not Mean "Nothing Can Break"

You may hear Auto Scaling described as:

```text
Self-healing
```

Use that phrase carefully.

Auto Scaling can replace unhealthy instances.

But suppose the launch template contains a broken user-data script.

Every replacement instance may fail identically.

Then:

```text
Bad instance
    |
replace
    |
Bad instance
    |
replace
    |
Bad instance
```

Automation can repeatedly reproduce a bad configuration.

Therefore:

```text
Automation amplifies good configuration
and bad configuration.
```

This is why testing launch templates and bootstrap processes matters.

---

# 53. Health Check Grace Period

A new instance may need time to start its application.

Suppose:

```text
EC2 boot:
30 seconds

Package installation:
60 seconds

Application startup:
45 seconds
```

If health-based replacement reacts before the application has had a reasonable opportunity to initialize, the new instance could be judged unhealthy too early.

The health check grace period gives a newly InService instance time before certain health-check failures are acted on for replacement.

---

# 54. Grace Period Is Not a Fix for Broken Bootstrapping

If your application takes:

```text
2 minutes
```

to initialize, a suitable grace period may be appropriate.

But if your application never starts because:

```text
Package name is wrong
```

changing:

```text
Grace period:
300 seconds
```

to:

```text
3,000 seconds
```

does not fix the root problem.

It merely delays detection.

```text
   +---- manually registered EC2 B
```

```text

      |
```

# 57. Availability Zones

Do not put every application instance in one Availability Zone.

Bad:

```text
AZ-A

EC2 A
EC2 B
EC2 C

AZ-B

Nothing
```

If AZ-A experiences a serious disruption, your application capacity is concentrated there.

Better:

```text
AZ-A               AZ-B

EC2 A              EC2 B
EC2 C              EC2 D
```

Auto Scaling can distribute capacity across selected Availability Zones.

---

# 58. ASG Subnet Selection

When creating the ASG, you select the VPC subnets where instances may launch.

For our architecture:

```text
VPC
|
+-- Private App Subnet A
|
+-- Private App Subnet B
```

The ASG should use both application subnets.

Conceptually:

```text
ASG
 |
 +---- Private App Subnet A
 |          |
 |          +---- EC2
 |
 +---- Private App Subnet B
            |
            +---- EC2
```

The instances do not need public IP addresses.

The ALB is their public application entry point.

---

# 59. Availability Zone Distribution

EC2 Auto Scaling attempts to maintain appropriate capacity distribution across the selected Availability Zones according to its configured distribution behavior.

Why?

Because:

```text
Three instances
```

does not automatically mean:

```text
Highly available
```

if all three exist in one failure domain.

---

# 60. Failure Domains

An Availability Zone represents an important failure-domain boundary within an AWS Region.

Suppose:

```text
AZ-A
EC2 A
EC2 B
```

and:

```text
AZ-B
EC2 C
EC2 D
```

If one instance fails:

```text
small failure
```

If an entire AZ has problems:

```text
larger failure
```

Your architecture should consider both.

---

# 61. Why Minimum Capacity Matters for Availability

Suppose:

```text
Minimum = 1
```

Your scaling policy may eventually reduce the application to:

```text
1 instance
```

Even if the ASG supports multiple Availability Zones, only one running instance cannot simultaneously provide application-server redundancy across two zones.

For a production-style highly available application, you might choose:

```text
Minimum = 2
```

with instances distributed across multiple AZs.

The exact number depends on your requirements.

# 62. Stateless Application Design

Horizontal scaling works much better when application instances are stateless.

This is a critical architecture concept.

What does stateless mean?

In simple terms:

```text
The application server does not depend
on important user-specific state existing
only on that individual server.
```

---

# 63. The Sticky Server Problem

Imagine:

```text
User logs in
     |
     v
EC2 A
```

EC2 A stores the session only in local memory.

Next request:

```text
User
 |
 v
ALB
 |
 v
EC2 B
```

EC2 B does not know about the session.

The user appears logged out.

That is a scaling problem caused by server-local state.

---

# 64. Another Stateful Problem

Suppose users upload images.

EC2 A stores:

```text
/var/www/uploads/photo.jpg
```

locally.

Later:

```text
User
 |
ALB
 |
EC2 B
```

EC2 B does not have that file.

Even worse:

Auto Scaling terminates EC2 A.

The locally stored upload may disappear with the instance.

This is why horizontally scaled application servers should not be treated as permanent storage locations for important application data.

---

# 65. Stateless Application Pattern

Instead:

```text
                  ALB
               /       \
              v         v
           EC2 A       EC2 B
              \         /
               \       /
                v     v
             Shared Services
```

Examples of externalized state can include:

```text
RDS
S3
ElastiCache
other appropriate shared data systems
```

Application servers become more replaceable.

---

# 66. Treat Application Instances as Replaceable

A strong Auto Scaling architecture assumes:

```text
Any application instance may disappear.
```

That should not destroy the application.

Think:

```text
EC2 A dies
```

Response:

```text
Replace it.
```

Not:

```text
Oh no, all the only copies of our uploaded files
were stored on EC2 A.
```

Replaceability is central to resilient infrastructure.

---

# 67. What Is Bootstrapping?

A newly created EC2 instance must become a functioning application server.

That process is called:

```text
Bootstrapping
```

The instance might need to:

1. Install packages.
2. Obtain application code or artifacts.
3. Load configuration.
4. Configure services.
5. Start the application.
6. Expose a health endpoint.
7. Become healthy.

This process must be automated.

---

# 68. Why Manual Configuration Breaks Auto Scaling

Suppose your launch template creates:

```text
Plain Linux server
```

Then you manually SSH into every server and run:

```text
Install Nginx
Install application
Copy config
Start service
```

Now Auto Scaling launches EC2 C at 3:00 AM.

Who SSHs into it?

Nobody.

EC2 C remains:

```text
Empty Linux server
```

Its health check fails.

Your Auto Scaling architecture is incomplete.

# 69. User Data

EC2 user data allows initialization instructions to run when an instance launches.

For Linux instances, this often involves a shell script.

Example:

```bash
#!/bin/bash

systemctl start nginx
```

This is a very simple bootstrap example.

---

# 70. Understanding the Script

First line:

```bash
#!/bin/bash
```

This is called a:

```text
shebang
```

It tells the system to interpret the script using Bash.

Next:

```bash
dnf install -y nginx
```

`dnf` is the package manager on relevant distributions such as current Amazon Linux.

`install` tells it to install a package.

`-y` automatically answers yes to applicable package-manager confirmation prompts.

`nginx` is the package.

Next:

```bash
systemctl enable nginx
```

This configures the service to start automatically at boot.

Next:

```bash
systemctl start nginx
```

This starts Nginx now.

# 72. Do Not Put Secrets in User Data

Do not write:

```bash
DB_PASSWORD=MySecretPassword123
```

into user data.

Do not place:

* Database passwords
* API keys
* Long-lived AWS credentials
* Private tokens

directly in bootstrap scripts.

Use appropriate AWS secret-management and IAM mechanisms.

The instance should retrieve only the secrets it is authorized to access.

# 73. IAM Instance Roles

For example, if an application needs controlled access to S3:

```text

 |
 v

 |
 v
S3 permissions
```

The role should grant only the permissions required.

This follows:

```text
Least privilege
```

```text
      |

      |
      v
```

not:

```text

```

Repeatability is fundamental.


On many cloud-init-based Linux systems, useful locations include:

# 108. What Is Scaling Oscillation?

Imagine:

```text
CPU high
→ add instance

CPU drops
→ remove instance

CPU rises
→ add instance

CPU drops
→ remove instance
```

Repeatedly.

This is undesirable oscillation.

You may also hear this general behavior described as:

```text
thrashing
```

Good scaling design considers:

* Appropriate metrics
* Target values
* Warmup
* Application startup time
* Workload patterns
* Scale-in behavior

---

# 109. Why Scale-Out Is Usually More Urgent

If demand suddenly increases:

```text
Insufficient capacity
```

can immediately hurt users.

So additional capacity may need to arrive quickly.

Removing capacity is usually less urgent.

A system can often tolerate temporarily having:

```text
one extra instance
```

better than:

```text
one too few.
```

This is one reason scaling behavior should not be designed with simplistic symmetry.

# 149. Answers

## Answer 1

Vertical scaling increases or decreases the resources of an individual machine. Horizontal scaling changes the number of machines.

## Answer 2

Scale-out means adding instances or capacity horizontally.

## Answer 3

Scale-in means removing horizontally scaled capacity.

## Answer 4

It manages a logical fleet of EC2 instances, maintains desired capacity, supports health-based replacement, and can dynamically adjust capacity.

## Answer 5

A launch template is a reusable definition containing settings used when launching EC2 instances, such as AMI, instance type, Security Groups, storage, IAM profile, and user data.

## Answer 6

The minimum capacity is the lower size boundary for the Auto Scaling Group.

## Answer 7

Desired capacity is the capacity the group currently attempts to maintain.

## Answer 8

Maximum capacity is the upper size boundary for the group.

## Answer 9

Three.

## Answer 10

No. Dynamic scaling respects the minimum-capacity boundary.

## Answer 11

It adjusts capacity to keep a selected metric near a configured target value.

## Answer 12

Some applications are limited by request volume, memory, database capacity, queues, network activity, or other resources before CPU becomes the limiting factor.

## Answer 13

CloudWatch provides metrics and alarms that can participate in scaling decisions. Target tracking policies use CloudWatch alarms managed by Auto Scaling.

## Answer 14

A new EC2 instance must launch, boot, initialize, start the application, register, and become healthy before it provides useful capacity.

## Answer 15

Instance warmup represents time a newly launched instance needs before it should fully participate in scaling metric calculations.

## Answer 16

Yes. The EC2 infrastructure can be healthy while the application process is stopped or broken.

## Answer 17

It allows Auto Scaling to use load-balancer health results when determining instance health, so application-level failures can lead to replacement.

## Answer 18

Auto Scaling can replace the unhealthy instance with a new one to maintain desired capacity.

## Answer 19

Bootstrapping is the automated process that turns a newly launched machine into a functioning application instance.

## Answer 20

User data can run initialization instructions when an EC2 instance launches, allowing application setup to happen automatically.

## Answer 21

User data is not an appropriate secret store. Credentials and sensitive values should be handled through proper IAM and secret-management mechanisms.

## Answer 22

Because important application state is not tied to one instance. Instances can be added, removed, or replaced more safely.

## Answer 23

It reduces dependency on one Availability Zone and improves resilience against zonal failures.

## Answer 24

Recovery restores capacity lost because of failure. Scaling changes desired capacity because workload or another scaling condition requires more or less capacity.

## Answer 25

Every replacement uses the same bad configuration, so each new instance may fail in the same way and be replaced again.
