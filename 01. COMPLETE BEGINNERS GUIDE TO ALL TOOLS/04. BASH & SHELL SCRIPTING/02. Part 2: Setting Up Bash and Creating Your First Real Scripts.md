# 1. Before Writing Scripts: Confirm That Bash Exists

Before writing a Bash script, first confirm that Bash is available on your system.

Run:

```bash
command -v bash
```

You may see:

```text
/usr/bin/bash
```

or:

```text
/bin/bash
```

The exact path depends on your operating system.

## What does this command mean?

The command is:

```bash
command
```

`command` is a Bash builtin.

The option is:

```text
-v
```

It asks the shell to show how a command name resolves.

The argument is:

```text
bash
```

So:

```bash
command -v bash
```

essentially asks:

> Can this shell find Bash, and if so, where?

If Bash is available, the command usually prints a location.

If Bash cannot be found, it may produce no output and return a non-zero exit status.

---

# 2. Checking Whether Bash Is Actually Running

Finding Bash on the system does not necessarily mean your current shell is Bash.

You can check:

```bash
echo "$BASH_VERSION"
```

If you are running Bash, you may see something like:

```text
5.2.15(1)-release
```

If the variable is empty, you may not currently be running Bash.

You can also run:

```bash
bash
```

This starts a Bash shell if Bash is installed.

You can then verify:

```bash
echo "$BASH_VERSION"
```

---

# 3. Checking the Bash Version

Run:

```bash
bash --version
```

You may see output similar to:

```text
GNU bash, version 5.2.15(1)-release
Copyright (C) Free Software Foundation, Inc.
```

Your exact version will vary.

## Why does the version matter?

Different Bash versions support different features.

For example, some scripts may use features that are unavailable in much older versions.

This matters when a script:

* runs on multiple Linux distributions
* runs on macOS
* runs in CI/CD
* runs inside containers
* runs across older enterprise servers

A script that works perfectly on one machine may fail somewhere else because the Bash version is different.

For beginner scripts, this usually will not be a major problem yet, but checking versions is a good habit.

Bash is commonly available on Linux systems.

Many Linux distributions either use Bash as the default login shell or include it even if another shell is configured.

Examples include environments based on:

* Ubuntu
* Debian
* Red Hat Enterprise Linux
* Rocky Linux
* AlmaLinux
* Amazon Linux
* Fedora

Check Bash:


Then:

Possible output:

# 5. Bash on macOS

macOS includes Bash, but many modern macOS systems use Zsh as the default interactive shell.

You might open Terminal and run:

```bash
echo "$SHELL"
```

and receive:

```text
/bin/zsh
```

That does not mean Bash is unavailable.

Try:

```bash

```

You may see:

```text
/bin/bash
```

Then:

```bash

```

macOS may provide an older Bash version than current Linux distributions.

You can still learn and run many Bash scripts with it.

If you intentionally write Bash scripts, make sure they are executed by Bash rather than assuming your interactive Zsh session will interpret them identically.

For example:

```bash
bash script.sh
```

explicitly tells Bash to execute the file.

# 6. Bash on Windows

Windows does not behave like a standard Linux environment by default.

For modern Bash learning on Windows, one of the most practical approaches is:

**Windows Subsystem for Linux**

commonly called:

**WSL**

WSL provides a Linux environment that runs alongside Windows.

A simplified view is:

```text
Windows
   |
   v
WSL
   |
   v
Linux distribution
   |
   v
Bash
```

For example, a user may install Ubuntu through WSL and then work with Bash inside that Linux environment.

Once inside the WSL terminal, you can check:

```bash
command -v bash
```

and:

```bash
bash --version
```

This makes WSL particularly useful for learners preparing for:

* DevOps
* Cloud Engineering
* Linux administration
* SRE
* Platform Engineering

because most of those roles involve Linux environments.

---

# 7. Why WSL Is Better Than Pretending Windows CMD Is Bash

Windows Command Prompt uses a different command environment.

PowerShell is also a different shell and scripting language.

These are valuable tools, but they are not Bash.

For example:

```text
Windows CMD ≠ Bash

PowerShell ≠ Bash

Bash ≠ PowerShell
```

Some concepts overlap, but syntax and behavior differ.

For this series, if you are on Windows, use a proper Bash environment such as WSL rather than trying to convert every Linux command into Windows CMD equivalents.

# 10. What Is a `.sh` File?

A shell script is usually a plain-text file containing shell commands.

A common filename extension is:

```text
.sh
```

For example:

```text
backup.sh
health-check.sh
deploy.sh
cleanup.sh
```

The `.sh` extension is useful for humans because it immediately suggests:

> This is probably a shell script.

However, Linux does not rely entirely on file extensions the same way some graphical operating systems do.

A Bash script could technically be named:

```text
backup
```

instead of:

```text
backup.sh
```

Both can work.

For learning, we will usually use `.sh` because it makes the file purpose obvious.

---

# 11. Choosing Good Script Names

Bad names:

```text
script1.sh
test2.sh
new.sh
abc.sh
thing.sh
```

These quickly become confusing.

Prefer names that describe the purpose.

Examples:

```text
server-health-check.sh
backup-logs.sh
check-disk-space.sh
deploy-app.sh
cleanup-temp-files.sh
```

A good script name tells another engineer what the script probably does before they even open it.

---

# 12. Filename Conventions

A simple Bash filename convention is:

* lowercase letters
* meaningful words
* hyphens or underscores
* no unnecessary spaces
* `.sh` extension while learning

For example:

```text
check-server.sh
```

or:

```text
check_server.sh
```

Both styles are common.

Avoid:

```text
Check Server Final Version New.sh
```

Spaces create additional quoting and path-handling concerns.

They can be managed, but avoiding them simplifies scripting.

# 18. What Happens with `bash hello.sh`?

When you run:

```bash
bash hello.sh
```

you are executing the `bash` program directly.

The structure is:

```text
bash        hello.sh
 |             |
command      argument
```

You are saying:

> Start Bash and tell Bash to read commands from hello.sh.

Conceptually:

```text
Terminal
   |
   v
Current shell
   |
   v
Starts Bash
   |
   v
Bash reads hello.sh
   |
   v
Executes commands
```

The script file itself does not need executable permission for this method because Bash is the executable program.

Bash simply reads the script file as input.

---

# 19. Try `./hello.sh`

Now try:

```bash
./hello.sh
```

You may get:

```text
bash: ./hello.sh: Permission denied
```

or a similar error.

Why?

Because the file may not currently have executable permission.

This brings us to Linux permissions.

---

# 20. Understanding File Permissions

Linux uses permissions to control what users can do with files.

The three important permission types are:

```text
r = read
w = write
x = execute
```

A file may be readable and writable but not executable.

Check your script:

```bash
ls -l hello.sh
```

You might see:

```text
-rw-r--r-- 1 ann ann 39 Sep 2  hello.sh
```

Focus on:

```text
-rw-r--r--
```

The first character describes the file type.

Then permissions are grouped for:

```text
owner
group
others
```

A simplified breakdown:

```text
-rw-r--r--
 ||| ||| |||
 ||| ||| +++ others
 ||| +++----- group
 +++--------- owner
```

For the owner:

```text
rw-
```

means:

```text
read      yes
write     yes
execute   no
```

The missing `x` is why direct execution may fail.

---

# 21. What Does Execute Permission Mean?

Executable permission means the operating system allows the file to be launched as a program.

For scripts, execute permission is required when you try to invoke the script directly:

```bash
./hello.sh
```

Without execute permission, Linux prevents direct execution.

This is a security feature.

Imagine if every text file were automatically executable.

That could create unnecessary risk.

---

# 22. Add Execute Permission with `chmod`

Run:

```bash
chmod +x hello.sh
```

Now check:

```bash
ls -l hello.sh
```

You may see something like:

```text
-rwxr-xr-x 1 ann ann 39 Sep 2 hello.sh
```

Notice the `x` characters.

The script is now executable.

---

# 23. Understanding `chmod +x`

Let's break down:

```bash
chmod +x hello.sh
```

## `chmod`

`chmod` means:

**change mode**

It modifies file permission bits.

## `+x`

This means:

> Add execute permission.

## `hello.sh`

This is the target file.

So the entire command means:

> Add executable permission to hello.sh.

Later in the series, you will study Linux permissions in much greater depth.

For now, remember:

```bash
chmod +x script.sh
```

makes a script directly executable for the permission classes affected by that form of `chmod`.

---

# 24. Try Running It Again

Now run:

```bash
./hello.sh
```

You may encounter a different error, such as:

```text
./hello.sh: line 1: ...
```

or:

```text
Exec format error
```

depending on your system.

Why?

Because when a script is executed directly, the operating system needs to know which interpreter should execute it.

This is where the shebang becomes important.

---

# 25. What Is a Shebang?

A shebang is a special first line in a script that tells the operating system which interpreter should execute the file.

It begins with:

```text
#!
```

The name “shebang” comes from common nicknames for:

```text
# = hash
! = bang
```

So:

```text
#!
```

became informally known as:

```text
hash-bang
```

or:

```text
shebang
```

---

# 26. Add a Bash Shebang

Open the file:

```bash
nano hello.sh
```

Change it to:

```bash
#!/bin/bash

echo "Hello from my first Bash script"
```

Save and exit.

Now inspect:

```bash
cat hello.sh
```

You should see:

```bash
#!/bin/bash

echo "Hello from my first Bash script"
```

Then run:

```bash
./hello.sh
```

Expected output:

```text
Hello from my first Bash script
```

---

# 27. What Does `#!/bin/bash` Mean?

This line:

```bash
#!/bin/bash
```

means:

> When this file is executed directly, use `/bin/bash` as the interpreter.

Break it down:

```text
#!            interpreter marker

/bin/bash     path to Bash
```

Conceptually:

```text
./hello.sh
     |
     v
Operating system reads first line
     |
     v
#!/bin/bash
     |
     v
Start /bin/bash
     |
     v
Give hello.sh to Bash
     |
     v
Bash executes commands
```

---

# 28. Why the Shebang Matters

Suppose your script contains Bash-specific syntax.

If the operating system does not know which interpreter should run it, direct execution becomes unreliable or impossible.

A shebang makes the intended interpreter explicit.

For example:

```bash
#!/bin/bash
```

says:

> This script is intended for Bash at `/bin/bash`.

A Python script may instead begin with something like:

```text
#!/usr/bin/python3
```

The concept is the same.

---

# 29. Another Bash Shebang: `/usr/bin/env bash`

You will also frequently see:

```bash
#!/usr/bin/env bash
```

This is another common way to specify Bash.

Instead of hardcoding:

```text
/bin/bash
```

it uses:

```text
/usr/bin/env
```

to locate `bash` using the environment's command search path.

Conceptually:

```text
#!/usr/bin/env bash
         |
         v
Find bash using PATH
         |
         v
Use that Bash interpreter
```

---

# 30. `/bin/bash` vs `/usr/bin/env bash`

Both are widely used.

## Option 1

```bash
#!/bin/bash
```

Advantages:

* explicit
* predictable when Bash exists there
* common on Linux

Potential issue:

Bash may exist somewhere else on certain systems.

---

## Option 2

```bash
#!/usr/bin/env bash
```

Advantages:

* searches for Bash using `$PATH`
* can work better across environments where Bash is installed in different locations

Potential issue:

It depends on the environment's `$PATH`.

That means it may select a different Bash installation than you expected.

---

# 31. Which Should a Beginner Use?

For this series, we can commonly use:

```bash
#!/usr/bin/env bash
```

because it expresses:

> Use the Bash available in the current environment.

However, you should understand both forms because you will encounter both in production systems.

The important lesson is not:

> One is always correct and the other is wrong.

The lesson is:

> Know which interpreter you intend to use and why.

---

# 32. What Happens When You Run `bash script.sh`?

Here is an important subtlety.

If you run:

```bash
bash hello.sh
```

you are explicitly selecting Bash yourself.

The shebang is not what selects Bash in this case.

You already selected it by running:

```text
bash
```

But if you run:

```bash
./hello.sh
```

then the operating system uses the shebang to determine the interpreter.

So:

```text
bash hello.sh
```

means:

```text
You selected Bash.
```

while:

```text
./hello.sh
```

means:

```text
The script's shebang selects the interpreter.
```

This distinction matters.

# 33. Script Structure

A basic Bash script commonly looks like this:

```bash
#!/usr/bin/env bash

# Description of what this script does

echo "Starting script"

pwd
whoami

echo "Script complete"
```

You can think of it as:

```text
Shebang
   ↓
Comments
   ↓
Configuration
   ↓
Commands
   ↓
Logic
   ↓
Output
```

As your scripts become more advanced, they may include:

* variables
* functions
* argument parsing
* validation
* logging
* error handling
* cleanup
* main execution logic

But beginner scripts can start very simply.

---

# 34. Comments in Bash

A comment begins with:

```text
#
```

For example:

```bash
# Check the current user
whoami
```

Bash ignores the comment during normal command execution.

Comments help humans understand the script.

For example:

```bash
#!/usr/bin/env bash

# Display basic system identity
whoami
hostname
```

---

# 35. Why the Shebang Is Different from a Normal Comment

The shebang also begins with:

```text
#
```

but:

```bash
#!/usr/bin/env bash
```

has special meaning when it appears as the first line of an executable script.

So although Bash effectively treats it like a comment once the interpreter is already running, the operating system uses it during direct script execution.

That is why it must appear at the beginning.

Do not put something above it like:

```bash
# My script

#!/usr/bin/env bash
```

If you want the shebang to control direct execution, keep it as the first line.

Use:

```bash
#!/usr/bin/env bash

# My script
```

---

# 36. Blank Lines

Blank lines do not normally change the logic of a simple Bash script.

They improve readability.

Compare this:

```bash
#!/usr/bin/env bash
echo "Starting"
whoami
hostname
pwd
date
echo "Complete"
```

with:

```bash
#!/usr/bin/env bash

echo "Starting"

whoami
hostname
pwd
date

echo "Complete"
```

The second version is easier to scan.

As scripts grow, whitespace becomes important for humans even when Bash does not require it.

---

# 37. Script Readability

A script is not good simply because it works.

Other engineers should be able to understand it.

Prefer:

```bash
#!/usr/bin/env bash

# Display system identity
echo "System information:"
whoami
hostname

# Display current location
echo "Current directory:"
pwd
```

instead of:

```bash
#!/usr/bin/env bash
echo info
whoami
hostname
echo place
pwd
```

Clear structure reduces troubleshooting time.

# 39. Relative Paths

A relative path describes a location relative to your current working directory.

Suppose:

```text
/home/ann/bash-lab/scripts/
```

contains:

```text
hello.sh
```

and you are currently inside:

```text
/home/ann/bash-lab/scripts
```

Then:

```text
hello.sh
```

is just the filename.

A relative path could also be:

```text
./hello.sh
```

The `.` means:

```text
current directory
```

So:

```text
./hello.sh
```

means:

> The file hello.sh located in my current directory.

---

# 40. Absolute Paths

An absolute path starts from the filesystem root:

```text
/
```

For example:

```text
/home/ann/bash-lab/scripts/hello.sh
```

This identifies the file independently of your current directory.

You could execute:

```bash
/home/ann/bash-lab/scripts/hello.sh
```

from another directory, assuming the script is executable and its shebang works.

---

# 41. Relative vs Absolute Path Example

Imagine:

```text
/
└── home
    └── ann
        └── bash-lab
            └── scripts
                └── hello.sh
```

If you are inside:

```text
/home/ann/bash-lab/scripts
```

you can refer to the script relatively:

```text
./hello.sh
```

Absolute:

```text
/home/ann/bash-lab/scripts/hello.sh
```

Both point to the same file.

# 42. Current Directory Behavior

A very common beginner question is:

> Why can I see `hello.sh` with `ls`, but typing `hello.sh` says command not found?

Try:

```bash
hello.sh
```

You may see:

```text
hello.sh: command not found
```

Even though:

```bash
ls
```

shows:

```text
hello.sh
```

Why?

Because the shell does not automatically search your current directory for commands.

It searches locations defined in `$PATH`.

---

# 43. What Is `$PATH`?

`PATH` is an environment variable containing directories that the shell searches when you enter a command name.

Display it:

```bash
echo "$PATH"
```

You may see something like:

```text
/usr/local/bin:/usr/bin:/bin:/usr/local/sbin:/usr/sbin
```

These directories are separated by:

```text
:
```

Conceptually:

```text
You type: ls
     |
     v
Shell checks PATH
     |
     +--> /usr/local/bin
     |
     +--> /usr/bin
     |
     +--> /bin
     |
     v
Finds ls
```

---

# 44. Why the Current Directory Is Usually Not Automatically Searched

Suppose the current directory contains a malicious file named:

```text
ls
```

If the shell automatically preferred the current directory, typing:

```bash
ls
```

could accidentally execute that malicious program instead of the trusted system command.

Requiring explicit current-directory execution helps reduce this risk.

So:

```bash
hello.sh
```

means:

> Search for a command named hello.sh through normal command resolution.

While:

```bash
./hello.sh
```

means:

> Execute hello.sh from this exact current directory.

The `./` is intentional.

---

# 45. Understanding `.`

In Linux paths:

```text
.
```

means:

**current directory**

while:

```text
..
```

means:

**parent directory**

For example:

```bash
pwd
```

might show:

```text
/home/ann/bash-lab/scripts
```

Then:

```bash
cd ..
```

takes you to:

```text
/home/ann/bash-lab
```

We will explore paths much more deeply later.

---

# 46. Why `./script.sh` Is Required

Suppose you run:

```bash
./hello.sh
```

Breaking it apart:

```text
.          current directory

/          path separator

hello.sh   file
```

You are giving Bash/the operating system a path.

You are not asking the shell to search `$PATH`.

That is why direct execution works when:

```bash
hello.sh
```

may not.

# 47. First Practical Automation Script

Now let's create something more useful than “Hello World.”

Create:

```bash
nano system-info.sh
```

Enter:

```bash
#!/usr/bin/env bash

# Simple system information script

echo "=============================="
echo "SYSTEM INFORMATION"
echo "=============================="

echo
echo "Current user:"
whoami

echo
echo "Hostname:"
hostname

echo
echo "Current directory:"
pwd

echo
echo "Current date and time:"
date

echo
echo "Bash version:"
bash --version | head -n 1

echo
echo "=============================="
echo "CHECK COMPLETE"
echo "=============================="
```

Save the file.

---

# 48. What This Script Is Trying to Accomplish

The goal is to collect basic environment information automatically.

Instead of manually running:

```bash
whoami
hostname
pwd
date
bash --version
```

the script runs them for you.

This introduces one of the main reasons scripting exists:


# 60. Another Common Problem: Running a Bash Script with `sh`

Suppose your script is designed for Bash.

You might incorrectly run:

```bash
sh script.sh
```

This tells the system:

> Use whatever shell `sh` refers to.

It does not mean:

> Read the shebang and use Bash.

The explicit interpreter command wins.

So if the script uses Bash-only features, this may fail.

If it is a Bash script, use:

```bash
bash script.sh
```

or make it executable and use the appropriate Bash shebang:

```bash
./script.sh
```

# 61. Why Script Execution Method Matters

Consider these three commands:

```bash
bash script.sh
```

```bash
sh script.sh
```

```bash
./script.sh
```

They are not equivalent.

## `bash script.sh`

Explicitly runs the script with Bash.

## `sh script.sh`

Explicitly runs the script with whatever `sh` means on that system.

## `./script.sh`

Executes the file directly and uses its shebang to choose the interpreter.

This difference becomes extremely important as scripts grow more sophisticated.

The important engineering habits from this part are:

```text
Work in a safe lab.

Know which interpreter you are using.

Inspect scripts before running them.

Use clear filenames.

Understand file permissions.

Do not solve every error with sudo.

Verify command locations.

Understand PATH.

Read errors carefully.

Fix the actual cause.

Keep scripts readable.
```

In Part 3, the focus moves to one of the most important Bash concepts: variables and shell expansion. You will learn how Bash stores values, how quoting changes behavior, the difference between shell and environment variables, how `$HOME`, `$USER`, `$PATH`, `$PWD`, and other variables work, and how command substitution, arithmetic expansion, and parameter expansion allow scripts to work with changing data.
