# 1. Why These Commands Exist

Basic Git workflows are straightforward:

```text
Edit
  |
  v
Stage
  |
  v
Commit
  |
  v
Push
```

But development rarely remains that simple.

Imagine you are working on:

```text
feature/metrics
```

You have modified:

```text
src/metrics.py
config.yml
```

but the feature is not ready.

Then production breaks.

Your team tells you:

```text
Switch to main immediately.

We need a hotfix.
```

You do not necessarily want to create a bad commit such as:

```text
WIP unfinished stuff
```

just to switch branches.

Git stash can help.

---

Another situation:

A developer fixes an important timeout bug on:

```text
develop
```

Commit:

```text
7ac419e Fix API timeout handling
```

Production maintenance branch:

```text
release/2.4
```

needs that one fix.

But you do not want every other commit from `develop`.

Cherry-pick can help.

---

Another situation:

Your branch started here:

```text
A---B---C
        \
         D---E
```

while `main` continued:

```text
A---B---C---F---G
        \
         D---E
```

You want your work to appear as if it started from the newest `main`:

```text
A---B---C---F---G---D'---E'
```

Rebase can help.

These tools solve different problems.

Do not treat them as interchangeable.

---

# 2. The Three Tools at a Glance

Think of them like this:

| Tool              | Main Question                                                                      |
| ----------------- | ---------------------------------------------------------------------------------- |
| `git stash`       | Where can I temporarily put unfinished local changes?                              |
| `git cherry-pick` | How can I apply the change introduced by a particular commit here?                 |
| `git rebase`      | How can I replay my commits onto a different base or rewrite local commit history? |

A simple memory aid:

```text
STASH
Temporary unfinished work

CHERRY-PICK
Selected commit changes

REBASE
Replay/reorganize commits
```

---

# 3. `git stash`

Suppose your repository is:

```text
HEAD
 |
 v
Commit C
```

Your working directory contains unfinished changes:

```text
HEAD
 |
 v
Commit C
   |
   +--> Working changes
        app.py modified
        config.yml modified
```

You want those changes saved temporarily while returning the working tree toward the committed state.

This is what `git stash` is designed to help with.

---

# 4. What `git stash` Does

At a beginner level, think:

```text
Before stash

HEAD
 |
 v
Commit C

Working tree:
app.py modified
config.yml modified
```

Run:

```bash
git stash
```

Conceptually:

```text
Git records the local changes
       |
       v
Stash storage

Working tree returns toward:
Commit C
```

Now you can perform another task with a cleaner working tree.

Later, you can reapply the stashed changes.

The official Git documentation describes stash as recording the current state of the working directory and index while returning the working directory to match `HEAD`.

---

# 5. A Stash Is Not a Normal Branch Commit

This distinction matters.

Suppose:

```text
main

A---B---C
```

You stash unfinished work.

You do not normally get:

```text
A---B---C---D
```

where D becomes a normal commit on `main`.

Instead, Git stores the stashed state separately.

This allows you to preserve unfinished work without placing a normal WIP commit into your branch history.

---

# 6. When Stash Is Useful

Typical situations include:

```text
Urgent hotfix arrives

Need to switch branches

Need to pull/rebase but local changes interfere

Need to test another branch

Need to temporarily remove experimental edits

Need to separate unrelated work
```

Example:

You are changing:

```text
Terraform monitoring resources
```

Then a production IAM fix becomes urgent.

Instead of committing:

```text
WIP monitoring maybe works
```

you may stash the unfinished monitoring changes, handle the urgent work, and return later.

---

# 7. When Stash Should Not Replace Commits

Stash is useful temporary storage.

It should not become your permanent project-management system.

Bad habit:

```text
stash@{0}
stash@{1}
stash@{2}
stash@{3}
stash@{4}
stash@{5}
stash@{6}
stash@{7}
stash@{8}
```

with no idea what anything contains.

Important completed work should generally become meaningful commits.

Think:

```text
Commit
    Durable project history

Stash
    Temporary local work storage
```

# 9. Creating Unfinished Work

Modify:

```text
src/app.py
```

so it contains:

```python
def health():
    return "healthy"


def metrics():
    return "metrics pending"
```

Then:

```bash
git status
```

You should see `src/app.py` as modified.

Inspect:

```bash
git diff
```

At this point the change exists only in your working tree.

# 10. Stashing the Change

Run:

```bash
git stash
```

Git may display output similar to:

```text
Saved working directory and index state WIP on main: ...
```

Now:

```bash
git status
```

Your working tree should normally be clean with respect to those tracked changes.

Check:

```bash
cat src/app.py
```

The unfinished `metrics()` work is no longer visible in the working file.

Do not panic.

The work has been stored in the stash.

# 11. `git stash` vs `git stash push`

Modern explicit syntax is:

```bash
git stash push
```

Running:

```bash
git stash
```

without arguments is equivalent to:

```bash
git stash push
```

for this normal use case.

You will often see both forms.

For learning, this is clearer:

```bash
git stash push
```

because it makes the operation explicit.

---

# 12. Give Your Stash a Message

Instead of:

```bash
git stash
```

prefer descriptive temporary labels when useful:

```bash
git stash push -m "WIP metrics endpoint"
```

Breakdown:

```text
git
    Run Git

stash
    Work with stashed states

push
    Create a new stash entry

-m
    Provide a message

"WIP metrics endpoint"
    Human-readable description
```

This becomes especially helpful when you have multiple stashes.

---

# 13. Listing Stashes

Use:

```bash
git stash list
```

Example:

```text
stash@{0}: On main: WIP metrics endpoint
stash@{1}: On feature/logging: Experiment with JSON logs
stash@{2}: On main: Terraform monitoring changes
```

Git stores the newest stash as:

```text
stash@{0}
```

The previous one becomes:

```text
stash@{1}
```

Then:

```text
stash@{2}
```

and so on.

---

# 14. Understanding `stash@{0}`

This syntax:

```text
stash@{0}
```

means:

```text
the newest stash entry
```

Think:

```text
Newest

stash@{0}

stash@{1}

stash@{2}

Older
```

Do not assume stash numbers permanently identify the same work.

If stashes are removed, positions can change.

Use descriptive messages.

---

# 15. Inspecting a Stash

Before restoring an old stash, inspect it.

Use:

```bash
git stash show stash@{0}
```

This normally gives a summary.

For a patch view:

```bash
git stash show -p stash@{0}
```

The `-p` means:

```text
patch
```

You can inspect the actual changes.

This is a strong habit:

```text
List
  |
  v
Inspect
  |
  v
Apply
```

rather than:

```text
Guess
  |
  v
Apply random stash
```

---

# 16. Applying a Stash

Suppose:

```bash
git stash list
```

shows:

```text
stash@{0}: On main: WIP metrics endpoint
```

Apply it:

```bash
git stash apply stash@{0}
```

Git attempts to restore those changes into your current working state.

Check:

```bash
git status
```

Then:

```bash
git diff
```

Your unfinished work should be visible again.

---

# 17. `git stash apply` Keeps the Stash

This is important.

After:

```bash
git stash apply stash@{0}
```

run:

```bash
git stash list
```

The stash normally remains.

Conceptually:

```text
Before apply

Stash:
WIP metrics

Working tree:
clean
```

After apply:

```text
Stash:
WIP metrics

Working tree:
WIP metrics changes
```

The stash still exists.

This can provide an extra safety margin while you verify the restored work.

---

# 18. Popping a Stash

Another command is:

```bash
git stash pop
```

At a beginner level:

```text
apply
    Restore stash but keep stash entry

pop
    Restore stash and, if successfully applied,
    remove it from the stash list
```

The official Git documentation makes this distinction: `apply` does not remove the stash entry, while `pop` removes the applied stash when successful. If applying during `pop` fails because of conflicts, the stash is not automatically removed.

---

# 19. Apply vs Pop

A useful beginner rule:

If the work is important and you are uncertain, use:

```bash
git stash apply
```

Then inspect:

```bash
git status
git diff
```

Once you are satisfied, remove the stash deliberately.

This is often easier to reason about than immediately popping it.

---

# 20. Dropping a Stash

After successfully applying and verifying a stash:

```bash
git stash drop stash@{0}
```

This removes that stash entry.

Before doing this:

```bash
git stash list
git stash show -p stash@{0}
```

Make sure you are deleting the intended stash.

A dropped stash is not something beginners should assume they can easily recover.

---

# 21. Clearing Every Stash

Git supports:

```bash
git stash clear
```

This removes all stash entries.

This is destructive.

Do not use it casually.

Before clearing:

```bash
git stash list
```

Ask:

```text
Do I understand every stash here?

Is any unfinished work still needed?

Has important work been committed elsewhere?
```

Never run cleanup commands merely because a tutorial tells you to.

---

# 22. What Gets Stashed by Default?

This is a common beginner surprise.

By default, a normal stash primarily handles:

```text
Changes to tracked files
```

and staged tracked changes.

Untracked files are not automatically included by the default stash behavior.

Example:

```bash
touch new-script.sh
git status
```

If `new-script.sh` is untracked, a plain:

```bash
git stash
```

may leave it in the working directory.

---

# 23. Including Untracked Files

Use:

```bash
git stash push -u -m "WIP including new script"
```

`-u` means:

```text
--include-untracked
```

Now untracked files can be included in the stash.

But inspect carefully before using broad stash options.

---

# 24. Ignored Files Are Different

Remember Part 15.

A file can be:

```text
Tracked

Untracked

Ignored
```

Using:

```bash
git stash -u
```

includes untracked files but does not mean every ignored file is included.

Git also has:

```bash
git stash -a
```

where `-a` means:

```text
--all
```

and includes ignored files as well.

This is broader.

Use it carefully.

Large build directories, caches, and dependencies may be ignored for good reasons.

---

# 25. Stashing Selected Paths

Suppose you modified:

```text
app.py
config.yml
README.md
```

but only want to stash:

```text
config.yml
```

You can use a pathspec:

```bash
git stash push -m "Config experiment" -- config.yml
```

The:

```text
--
```

helps separate options from paths.

This can be useful when your working directory contains unrelated changes.

---

# 26. Stash Does Not Mean Backup

Do not think:

```text
I stashed it, therefore my work is permanently safe.
```

Stashes are local repository state.

They are not automatically:

```text
Uploaded to GitHub

Shared with teammates

Backed up remotely

Permanent project history
```

For important checkpoints, use meaningful commits and remote collaboration workflows.

---

# 27. Stash Conflicts

A stash can conflict.

Imagine you stash:

```text
TIMEOUT=30
```

Later, the current branch changes the same line to:

```text
TIMEOUT=60
```

Your stash contains a competing change:

```text
TIMEOUT=45
```

When you apply the stash, Git cannot safely decide:

```text
Should the final value be 60?

45?

Something else?
```

So Git may stop with a conflict.

---

# 28. Example Stash Conflict

You may see:

```text
<<<<<<< Updated upstream
TIMEOUT=60
=======
TIMEOUT=45
>>>>>>> Stashed changes
```

The labels may differ depending on operation and Git version/context.

The important point is the same:

Git needs you to decide the final content.

---

# 29. Resolving a Stash Conflict

First:

```bash
git status
```

Identify conflicted files.

Open each file.

Understand both sides.

Decide the correct final content.

For example:

```text
TIMEOUT=45
```

Remove all conflict markers.

Then stage the resolved file:

```bash
git add config.env
```

Verify:

```bash
git status
git diff --staged
```

Then continue your normal workflow.

Do not blindly choose one side merely to make Git stop complaining.

---

# 30. Important `stash pop` Conflict Behavior

Suppose:

```bash
git stash pop
```

produces conflicts.

Do not assume the stash disappeared.

When `pop` fails because of conflicts, Git keeps the stash entry instead of removing it automatically.

Check:

```bash
git stash list
```

before doing anything else.

---

# 31. Stash Safety Workflow

Use this pattern:

```text
git status
    |
    v
Understand local changes
    |
    v
git diff
    |
    v
git stash push -m "descriptive message"
    |
    v
git status
    |
    v
Perform other work
    |
    v
git stash list
    |
    v
git stash show -p
    |
    v
git stash apply
    |
    v
Resolve conflicts if necessary
    |
    v
Verify
    |
    v
Drop stash when truly finished
```

# 32. `git cherry-pick`

Now imagine this history:

```text
main

A---B---C
```

Another branch:

```text
A---B---C
         \
          D---E---F
              ^
              |
         important fix
```

You want the change introduced by E.

You do not want D.

You do not want F.

This is where:

```bash
git cherry-pick
```

becomes useful.

---

# 33. What Cherry-Pick Means

The official Git definition is essentially:

```text
Apply the changes introduced by an existing commit
and record them as a new commit on the current branch.
```

This wording matters.

Cherry-pick does not normally take the exact existing commit object and magically move it.

It applies that commit's change onto your current history and records a new commit.

---

# 34. Cherry-Pick Creates New History

Suppose:

```text
main

A---B---C

feature

A---B---C---D---E
                ^
               fix
```

Switch to `main`:

```bash
git switch main
```

Cherry-pick E:

```bash
git cherry-pick <E-commit-id>
```

Result:

```text
feature

A---B---C---D---E


main

A---B---C---E'
```

Notice:

```text
E != E'
```

E' contains the applied change in the context of `main`, but it is a new commit with a different parent and therefore normally a different commit ID.

---

# 35. Why the Commit ID Changes

Remember Part 4.

A commit contains information including:

```text
Project snapshot

Parent commit

Author information

Committer information

Commit message
```

Original E may have parent:

```text
D
```

Cherry-picked E' has parent:

```text
C
```

Different parent means different commit identity.

Therefore:

```text
E
```

and:

```text
E'
```

are different commits.

---

# 36. Real-World Cherry-Pick Example

Imagine:

```text
develop
```

contains:

```text
A---B---C---D---E---F
                ^
                |
       Fix authentication timeout
```

Production maintenance branch:

```text
release/3.2
```

contains:

```text
A---B---X---Y
```

You need only the authentication timeout fix.

You may cherry-pick commit E onto:

```text
release/3.2
```

Result:

```text
release/3.2

A---B---X---Y---E'
```

This is often called:

```text
backporting a fix
```

when a fix from newer development is applied to an older maintained version.

---

# 37. Basic Cherry-Pick Syntax

Use:

```bash
git cherry-pick <commit>
```

Example:

```bash
git cherry-pick 7ac419e
```

Breakdown:

```text
git
    Run Git

cherry-pick
    Apply changes introduced by selected commit

7ac419e
    Commit whose change you want applied
```

---

# 38. Check Your Current Branch First

This is critical.

Cherry-pick applies the change onto:

```text
your current branch
```

Before running it:

```bash
git status
```

Then:

```bash
git branch --show-current
```

Then inspect:

```bash
git log --oneline --graph --decorate --all
```

Ask:

```text
Am I on the branch that should receive this change?
```

---

# 39. Inspect the Commit Before Cherry-Picking

Before:

```bash
git cherry-pick 7ac419e
```

run:

```bash
git show 7ac419e
```

Understand:

```text
What files changed?

Why did they change?

Does this commit depend on earlier commits?

Does this change make sense on my current branch?

Does it contain unrelated work?
```

Never cherry-pick a commit based only on its message.

---

# 40. Dependency Problem

Suppose commit E contains:

```python
validate_token(token)
```

but the function:

```python
validate_token()
```

was introduced in commit D.

You cherry-pick only E.

Git may apply the text cleanly.

But the application may fail because E depends on D.

This teaches an important lesson:

```text
Git-level success
!=
Application-level correctness
```

Always test after cherry-picking.

# 42. Cherry-Pick Conflicts

Cherry-picking is not guaranteed to apply cleanly.

Suppose original commit changes:

```text
PORT=8080
```

to:

```text
PORT=9090
```

But your current branch has already changed the same area to:

```text
PORT=7070
```

Git cannot automatically know the desired result.

It may stop with a conflict.

---

# 43. What Happens During a Cherry-Pick Conflict

Git leaves you in an in-progress cherry-pick state.

You may see conflict markers in affected files:

```text
<<<<<<< HEAD
PORT=7070
=======
PORT=9090
>>>>>>> 71ac205
```

The exact labels can vary.

Run:

```bash
git status
```

Git tells you which paths need resolution.

The official Git documentation states that when a cherry-pick cannot apply cleanly, conflicting paths are recorded in the index and conflict markers appear in the working tree.

---

# 44. Resolve Cherry-Pick Conflict

Do not immediately choose:

```text
7070
```

or:

```text
9090
```

Ask:

```text
What is the intended configuration on this branch?
```

Suppose correct final result is:

```text
PORT=9090
```

Edit the file to contain only:

```text
PORT=9090
```

Remove conflict markers.

Stage:

```bash
git add config.env
```

Check:

```bash
git status
```

Then continue:

```bash
git cherry-pick --continue
```

---

# 45. Aborting a Cherry-Pick

Suppose you realize:

```text
This commit should never have been applied here.
```

Instead of improvising with reset commands, use:

```bash
git cherry-pick --abort
```

Git attempts to return to the state before the cherry-pick sequence began.

This is an important recovery command.

---

# 46. Cherry-Pick Continue, Abort, Skip

During a sequence, Git provides commands such as:

```bash
git cherry-pick --continue
```

Continue after resolving the current conflict.

```bash
git cherry-pick --abort
```

Cancel the operation and return toward the pre-operation state.

There is also:

```bash
git cherry-pick --skip
```

which skips the current commit in an ongoing sequence.

Do not use `--skip` merely because a conflict looks difficult.

Understand why the commit is being skipped.

---

# 47. Cherry-Pick Safety Workflow

Use:

```text
git status
    |
    v
Confirm destination branch
    |
    v
git show <commit>
    |
    v
Understand dependencies
    |
    v
git cherry-pick <commit>
    |
    +---- clean ----> test
    |
    +---- conflict --> git status
                       |
                       v
                   resolve
                       |
                       v
                   git add
                       |
                       v
             git cherry-pick --continue
                       |
                       v
                      test
```

If the operation is wrong:

```text
git cherry-pick --abort
```

---

# 48. When Cherry-Pick Is Useful

Good use cases include:

```text
Backporting a bug fix

Applying one approved fix to another branch

Recovering useful work from another branch

Moving a small isolated change

Applying a specific hotfix
```

---

# 49. When Cherry-Pick Becomes a Problem

Imagine regularly copying:

```text
A
B
C
D
E
F
G
H
```

one by one between long-lived branches.

Your history may become difficult to understand.

You may create duplicated logical changes with different commit IDs.

If you need an entire branch's development, merging or rebasing may be a better tool.

Use cherry-pick for deliberate selection, not as a substitute for understanding branch integration.

# 50. Rebase Fundamentals

Now we move to the most conceptually challenging tool in this part:

```bash
git rebase
```

Rebase is powerful because it changes how commits are based on history.

It can produce clean, linear histories.

It can also rewrite commits.

That is why beginners need a precise mental model.

---

# 51. What Is a Base?

Suppose:

```text
A---B---C
        \
         D---E
```

Your feature branch began from:

```text
C
```

C is the point from which your branch work diverged.

At a beginner level, you can think of C as the base of D and E's feature-line work.

Meanwhile `main` advances:

```text
A---B---C---F---G
        \
         D---E
```

Your branch is now based on an older point.

---

# 52. What Rebase Tries to Do

You want your feature work to appear on top of G.

Rebase conceptually says:

```text
Find my branch commits that are not in main.

Temporarily set their changes aside.

Move my branch to the newer base.

Replay my commits one by one.
```

Before:

```text
A---B---C---F---G
        \
         D---E
```

After:

```text
A---B---C---F---G---D'---E'
```

Notice:

```text
D became D'

E became E'
```

These are new commits.

---

# 53. Why Rebased Commits Get New IDs

Original:

```text
D parent = C
```

After rebase:

```text
D' parent = G
```

The parent changed.

Therefore the commit identity changes.

Likewise:

```text
E parent = D
```

becomes:

```text
E' parent = D'
```

So E' also receives a new identity.

This is why rebase is called:

```text
history rewriting
```

in many practical discussions.

# 54. Basic Rebase Example

Suppose:

```text
main

A---B---C---F---G

feature

A---B---C---D---E
```

Switch to feature:

```bash
git switch feature
```

Then:

```bash
git rebase main
```

Conceptually Git transforms:

```text
A---B---C---F---G
        \
         D---E
```

into:

```text
A---B---C---F---G---D'---E'
```

The feature branch now appears to have been built on the latest `main`.

# 58. Merge vs Rebase

This is one of the most important comparisons in Git.

Suppose:

```text
A---B---C---F---G
        \
         D---E
```

You want to integrate newer `main` into your feature branch.

One option is merge.

Another is rebase.

They preserve/integrate history differently.

---

# 59. Merge Approach

On the feature branch:

```bash
git merge main
```

might produce:

```text
A---B---C---F---G
        \       \
         D---E---M
```

M is a merge commit.

The graph preserves the fact that development diverged and later merged.

---

# 60. Rebase Approach

Instead:

```bash
git rebase main
```

can produce:

```text
A---B---C---F---G---D'---E'
```

This creates a linear-looking history.

There is no merge commit for this integration.

But D and E have been recreated as D' and E'.

---

# 61. Merge vs Rebase Table

| Question                                   | Merge                             | Rebase                             |
| ------------------------------------------ | --------------------------------- | ---------------------------------- |
| Preserves existing divergent commits?      | Yes                               | Replays/recreates selected commits |
| Can create merge commit?                   | Yes                               | Normally no for simple rebase      |
| Produces linear history?                   | Not necessarily                   | Often                              |
| Rewrites commit IDs?                       | Existing commits generally remain | Replayed commits get new IDs       |
| Safe for already-shared history?           | Generally safer                   | Requires caution                   |
| Useful for cleaning local feature history? | Less focused on rewriting         | Yes                                |

Neither tool is automatically:

```text
good
```

or:

```text
bad
```

The correct choice depends on workflow and team policy.

---

# 62. Why Teams Use Rebase

Common reasons:

```text
Update local feature work onto newer main

Keep a linear project history

Clean up local commits before review

Combine temporary commits

Improve commit messages

Reorder local commits
```

But:

```text
clean-looking history
```

must not come at the cost of damaging shared collaboration.

Suppose:

```text

```

Your feature commit changed:

```text

```

When Git tries to replay your commit on top of the new `main`, it may stop.


```bash
git status
```

# 64. Understanding Rebase Conflict Markers

The file may contain conflict markers.

Do not rely only on labels such as:

```text

```

because those concepts can become confusing during rebase.

Instead ask:

```text
What does the new base contain?

What change is the current replayed commit trying to introduce?

What should the final file contain?
```

That reasoning is safer.

# 65. Resolving a Rebase Conflict

Suppose final intended value is:

```text
TIMEOUT=45
```

Edit the file.

Remove all:

```text
<<<<<<<
=======
>>>>>>>
```

Stage:

```bash
git add config.env
```

Check:

```bash
git status
```

Then:

```bash
git rebase --continue
```

Git continues replaying remaining commits.

# 66. Rebase May Conflict More Than Once

Suppose your branch contains:

```text
D
E
F
G
```

Git replays:

```text
D'
```

Conflict.

You resolve it.

Continue.

Git replays:

```text
E'
```

No conflict.

Then:

```text
F'
```

another conflict.

This is normal.

Rebase processes commits sequentially.

The workflow can become:

```text
rebase
  |
  v
conflict D
  |
  v
resolve
  |
  v
continue
  |
  v
replay E
  |
  v
conflict F
  |
  v
resolve
  |
  v
continue
```

Do not assume resolving one conflict completes the entire rebase.

# 67. Aborting a Rebase

Suppose the rebase becomes confusing.

Maybe:

```text
Too many conflicts

Wrong branch

Wrong upstream

Unexpected changes

You no longer understand the intended result
```

Use:

```bash
git rebase --abort
```

This aborts the rebase and attempts to restore the branch to its state before the rebase began.

This is much safer than randomly running destructive commands.

# 68. Continue vs Abort

During rebase:

```bash
git status
```

is your guide.

If you understand and resolve the conflict:

```bash
git add <resolved-files>
git rebase --continue
```

If the operation is wrong:

```bash
git rebase --abort
```

A good beginner rule:

```text
Confused about intended history?

Abort before improvising.
```

# 69. Interactive Rebase

Normal rebase answers:

```text
Where should these commits be replayed?
```

Interactive rebase adds another question:

```text
What should happen to each commit while replaying it?
```

This enables operations such as:

```text
Reword commit messages

Squash commits

Reorder commits

Drop commits

Edit commits
```

The command is:

```bash
git rebase -i <base>
```

where:

```text
-i
```

means:

```text
--interactive
```

---

# 70. Interactive Rebase Example

Suppose:

```bash
git log --oneline
```

shows:

```text
e821f44 Fix typo again
d912ac1 Fix typo
c712f80 Add metrics tests
b610ca3 Add metrics endpoint
91ab722 Base project
```

Your feature history is messy.

You want to clean the four commits after:

```text
91ab722
```

You could run:

```bash
git rebase -i 91ab722
```

Git opens an editor with a todo list similar to:

```text
pick b610ca3 Add metrics endpoint
pick c712f80 Add metrics tests
pick d912ac1 Fix typo
pick e821f44 Fix typo again
```

Notice the order is oldest to newest in the interactive rebase todo list.

---

# 71. Understanding `pick`

```text
pick b610ca3 Add metrics endpoint
```

means:

```text
Replay this commit normally.
```

If every line remains:

```text
pick
```

Git essentially replays those commits in that order.

Interactive rebase becomes powerful when you change those instructions.

---

# 72. Common Interactive Rebase Commands

You may see commands including:

```text
pick

reword

edit

squash

fixup

drop
```

At beginner level:

```text
pick
    Keep/replay commit

reword
    Keep commit but edit message

edit
    Stop so commit can be amended

squash
    Combine with previous commit
    and edit combined message

fixup
    Combine with previous commit,
    usually discarding this commit's message

drop
    Remove commit from rewritten history
```

This chapter focuses primarily on:

```text
squash

reword

reorder
```

# 73. Squashing Commits

Suppose history contains:

```text
Add metrics endpoint

Fix metrics typo

Fix metrics typo again
```

Logically, these may represent one piece of work.

Instead of keeping:

```text
D---E---F
```

you may want:

```text
X
```

where X represents the combined change.

This is called:

```text
squashing
```

---

# 74. Squash Example

Interactive todo:

```text
pick b610ca3 Add metrics endpoint
pick d912ac1 Fix metrics typo
pick e821f44 Fix metrics typo again
```

Change to:

```text
pick b610ca3 Add metrics endpoint
squash d912ac1 Fix metrics typo
squash e821f44 Fix metrics typo again
```

Git combines the later commits into the previous selected commit.

It may then open an editor for the resulting commit message.

You might choose:

```text
Add metrics endpoint
```

The resulting history contains one new combined commit rather than three old commits.

---

# 75. Squashing Rewrites History

Before:

```text
A---B---C---D
```

After squashing C and D into B's logical work, you may get something conceptually like:

```text
A---X
```

or, depending on selected range:

```text
A---B'---C'
```

The important point is:

```text
Commit identities change.
```

You are not merely hiding commits.

You are constructing new history.

---

# 76. When Squashing Helps

Squashing can be useful when local feature history contains temporary commits such as:

```text
Add health endpoint

Fix typo

Fix test

Oops fix syntax

Actually fix test

Final cleanup
```

Before sharing or merging, you may decide these should become:

```text
Add health endpoint and tests
```

This can make history easier to review.

---

# 77. Do Not Squash Everything Automatically

Atomic commits are valuable.

Suppose:

```text
Commit A
Add health endpoint

Commit B
Add health endpoint tests

Commit C
Document health endpoint
```

These may already be useful independent commits.

Turning everything into:

```text
Big feature
```

may reduce history quality.

The goal is not:

```text
fewest commits possible
```

The goal is:

```text
meaningful commits
```

---

# 78. Rewording Commits

Suppose your commit says:

```text
stuff
```

That is poor history.

You want:

```text
Add timeout validation to API client
```

Interactive rebase can change the message.

Example:

```text
pick b610ca3 Add API client
reword c712f80 stuff
pick d912ac1 Add tests
```

When Git reaches the `reword` commit, it lets you edit the commit message.

---

# 79. Reword Also Changes Commit Identity

This surprises beginners.

You changed only:

```text
commit message
```

But commit metadata contributes to commit identity.

Therefore the rewritten commit receives a new ID.

And descendant commits being replayed afterward may also receive new IDs because their parent chain changed.

History rewriting can cascade.

---

# 80. Reordering Commits

Interactive rebase also lets you reorder lines.

Original:

```text
pick a111111 Add documentation
pick b222222 Add API endpoint
pick c333333 Add API tests
```

You may decide the logical order should be:

```text
pick b222222 Add API endpoint
pick c333333 Add API tests
pick a111111 Add documentation
```

Save and exit.

Git attempts to replay commits in the new order.

---

# 81. Reordering Can Cause Conflicts

Suppose tests in commit C depend on code introduced by commit B.

This order makes sense:

```text
B
|
v
C
```

But if you reorder:

```text
C
|
v
B
```

the test commit may no longer apply correctly.

Interactive rebase is not merely a visual rearrangement.

Each commit is replayed in the chosen sequence.

Dependencies matter.

---

# 82. Safe Interactive Rebase Scope

For beginners, use interactive rebase primarily on:

```text
your own local feature commits
```

before they become shared history.

Example:

```text
origin/main

A---B---C
        \
         D---E---F
                 ^
             local feature
```

If D, E, and F exist only in your local work and nobody else depends on them, rewriting them is usually much easier to reason about.

---

# 83. Why Rebasing Shared History Is Dangerous

This is one of the most important Git safety rules.

Suppose remote history is:

```text
A---B---C---D
```

You and another developer both have D.

You rebase and rewrite:

```text
C---D
```

into:

```text
C---D'
```

Now your history says:

```text
A---B---C---D'
```

Their history says:

```text
A---B---C---D
```

D and D' may contain similar logical changes.

But Git sees different commits.

---

# 84. Shared History Divergence

Developer A:

```text
A---B---C---D
```

Developer B rewrites:

```text
A---B---C---D'
```

Now collaboration can become:

```text
             D
            /
A---B---C
            \
             D'
```

This can lead to:

```text
Duplicate commits

Confusing pull behavior

Unexpected conflicts

Force-push pressure

Broken assumptions

Lost teammate work if handled badly
```

This is why shared-history rebase requires team agreement and understanding.

---

# 85. The Golden Beginner Rebase Rule

Use this rule:

```text
Rebase your own local unpublished work freely enough
to learn and clean it.

Treat already-shared commits as history
other people may depend on.
```

Before rebasing, ask:

```text
Has this branch been pushed?

Is anyone else working from it?

Is there an open PR?

Has CI/CD consumed these commits?

Does team policy expect rebasing?

Would rewriting require a force push?
```

If uncertain, do not casually rewrite.

---

# 86. Rebase and Force Push

After rebasing a branch that was already pushed, your local history may no longer be a simple fast-forward of the remote history.

A normal:

```bash
git push
```

may be rejected.

Some workflows then use a force-style push.

This is exactly where careless history rewriting can damage collaboration.

Do not respond to a rejected push by reflexively running:

```bash
git push --force
```

First understand why the histories differ.

---

# 87. `--force-with-lease`

In workflows where rewriting your own remote feature branch is intentional, teams often prefer:

```bash
git push --force-with-lease
```

over:

```bash
git push --force
```

because `--force-with-lease` adds a safety check against overwriting remote work that changed unexpectedly.

But it is still a history-rewriting operation.

Do not interpret:

```text
safer
```

as:

```text
risk-free
```

For a beginner:

```text
Never force-push main casually.

Never force-push shared branches casually.

Understand the remote state first.
```

# 88. Rebase Before a Pull Request

A team might have:

```text

```

Your feature started at C:

```text
A---B---C
        \
         F---G
```

Before opening or updating a PR, the team may ask you to rebase your feature onto current `main`.

You could:

```bash

```

Then inspect:

```bash
git log --oneline --graph --decorate --all
```

Then, if appropriate:

```bash

```

Result:

```text
A---B---C---D---E---F'---G'
```

But only do this if it matches the team's collaboration policy.

# 89. Why `origin/main` Can Matter

Suppose your local:

```text
main
```

is outdated.

Remote:

```text
origin/main
```

is newer after:

```bash
git fetch origin
```

Rebasing onto:

```bash
git rebase main
```

may use stale local history.

Rebasing onto:

```bash
git rebase origin/main
```

can explicitly use your current knowledge of the fetched remote-tracking branch.

This connects directly to Part 12.

Always understand what your chosen base actually represents.

# 90. Rebase Does Not Fetch Automatically

This is a crucial distinction.

Running:

```bash
git rebase origin/main
```

does not mean:

```text
Contact GitHub and update origin/main first.
```

Your remote-tracking reference may be stale.

A common workflow is:

```bash
git fetch origin
```

then:

```bash
git rebase origin/main
```

Now your `origin/main` reflects the fetch you just performed.


# 100. Rebase vs Reset

Do not confuse these.

`reset` primarily moves a branch reference and may alter the index/working tree depending on mode.

`rebase` replays commits onto a new base or rewrites a selected sequence.

Example:

```text

    Move where branch points

    Reconstruct/replay commit sequence
```

# 101. Rebase vs Revert

Do not confuse:

```bash
git rebase
```

with:

```bash
git revert
```

```text
Create a new commit that reverses
the effect of an earlier commit.
```

Rebase:

```text
Replay/rewrite commits relative
to a different base.
```

For undoing a bad shared production commit:

```text
revert
```

is often the safer conceptual tool.

Do not use rebase merely because you want to "undo something."

# 111. Troubleshooting: Cannot Stash

# 126. Safe Beginner Rules

These rules are worth remembering.

### Rule 1: Run `git status` first

Before:

```text
stash

cherry-pick

rebase
```

understand your current state.

### Rule 2: Know your current branch

Use:

```bash
git branch --show-current
```

### Rule 3: Inspect commits before cherry-picking

Use:

```bash
git show <commit>
```

### Rule 4: Inspect the graph before rebasing

Use:

```bash
git log --oneline --graph --decorate --all
```

### Rule 5: Use descriptive stash messages

Prefer:

```bash
git stash push -m "WIP Terraform monitoring"
```

over piles of unidentified WIP entries.

### Rule 6: Do not assume untracked files were stashed

Check:

```bash
git status
```

after stashing.

### Rule 7: Do not use stash as permanent storage

Important work belongs in durable commits.

### Rule 8: Test after cherry-pick

Text applying cleanly does not prove dependencies are correct.

### Rule 9: Test after rebase

Successful replay does not prove the application works.

### Rule 10: Rebase local unpublished work more freely than shared work

Shared commits may be dependencies for other people.

### Rule 11: Never force-push merely because Git rejected your push

Understand the divergence first.

### Rule 12: Use `--abort` when an operation is wrong

For example:

```bash
git cherry-pick --abort
```

or:

```bash
git rebase --abort
```

### Rule 13: Do not resolve conflicts blindly

Understand the intended final behavior.

### Rule 14: Preserve evidence when confused

Use:

```bash
git reflog
```

and create a recovery branch when appropriate.

### Rule 15: Never practice dangerous history rewriting first on production repositories

Use disposable labs.

# 131. Part 17 Final Recap

The three central tools in this part solve different problems.

## Stash

```text
Working tree
    |
    | unfinished work
    v
git stash
    |
    v
Temporary stash storage
```

Later:

```text
Stash
  |
  v
git stash apply
  |
  v
Working tree
```

Remember:

```text
apply
    Restore + keep stash

pop
    Restore + remove after success
```

---

## Cherry-Pick

Original history:

```text
A---B---C---D---E
            ^
            |
        useful fix
```

Another branch:

```text
A---B---X---Y
```

Cherry-pick D:

```text
A---B---X---Y---D'
```

Remember:

```text
D != D'
```

The logical change is applied in a new history context.

---

## Rebase

Before:

```text
A---B---C---F---G
        \
         D---E
```

After:

```text
A---B---C---F---G---D'---E'
```

Remember:

```text
D != D'

E != E'
```

Rebase recreates commits on a new base.

---

## Merge vs Rebase

Merge:

```text
A---B---C---F---G
        \       \
         D---E---M
```

preserves the divergent structure.

Rebase:

```text
A---B---C---F---G---D'---E'
```

replays feature commits into a linear sequence.

---

## Interactive Rebase

Interactive rebase gives you tools such as:

```text
pick

reword

squash

reorder
```

allowing you to transform:

```text
Add feature
Fix typo
Fix typo again
```

into cleaner history such as:

```text
Add feature
```

when that accurately represents one logical change.

But history cleanliness must never become an excuse for careless rewriting.

The most important distinction is:

```text
LOCAL UNPUBLISHED HISTORY

Usually much safer to rewrite.
```

versus:

```text
SHARED HISTORY

Other people may depend on it.
Treat it carefully.
```

Your operational safety model should now be:

```text

   v

   |
   v

   |
   v

   |
   v

   |

   |
   v

   |

           v

           |
           v

           |
           v
       Stage
           |
           v
       Continue
           |
           v
       Verify
```

And if you lose confidence during an operation:

