# Part 18: Logging, Dates, Time, Regular Expressions, and Useful Automation Tools

Build scripts that are easier to operate and troubleshoot.

A Python automation script can technically work and still be difficult to operate.

Imagine a monitoring script that:

* Checks 50 servers.
* Calls several APIs.
* Reads configuration files.
* Runs Linux commands.
* Retries temporary failures.
* Detects unhealthy services.
* Runs every five minutes.

Something fails at 2:14 AM.

The script prints:

```text
Error
```

That is almost useless.

You need to know:

```text
When did it fail?
What operation was running?
Which server failed?
Was it a warning or serious failure?
What evidence did the script collect?
Did it retry?
Did the retry succeed?
Where can an engineer find the historical record?
```

This is why production automation needs operational visibility.

In this part, you will learn four major areas:

```text
Logging
   |
   +--> What happened?

Date and time
   |
   +--> When did it happen?

Regular expressions
   |
   +--> What useful information
        can we extract from text?

Environment variables
   |
   +--> How should runtime
        configuration and basic
        secret handling work?
```

These skills appear everywhere in DevOps, SRE, cloud automation, infrastructure engineering, platform engineering, CI/CD, monitoring, and security automation.

# 9. Logging Levels

Python logging uses severity levels.

The main levels are:

```text
DEBUG
INFO
WARNING
ERROR
CRITICAL
```

Their standard numeric values are:

```text
DEBUG       10
INFO        20
WARNING     30
ERROR       40
CRITICAL    50
```

Normally, you use the names rather than the numbers.

---

# 10. Severity Hierarchy

Think of the levels approximately like this:

```text
DEBUG
  |
  v
Detailed troubleshooting information

INFO
  |
  v
Normal operational event

WARNING
  |
  v
Something unusual or concerning

ERROR
  |
  v
An operation failed

CRITICAL
  |
  v
Severe failure requiring urgent attention
```

Higher severity does not automatically mean Python terminates the program.

The level classifies the log message.

# 28. Do Not Log Secrets

Never write:

```python

    "Token=%s",
    api_token
)
```

just because the level is DEBUG.

Logs often live much longer than the process.

They may be:

* Stored centrally.
* Copied.
* Backed up.
* Viewed by many engineers.
* Sent to external systems.

# 29. Logging Exceptions

From Part 10, you learned exception handling.

Consider:

```python
try:
    result = 10 / 0

except ZeroDivisionError:
    logger.error(
        "Calculation failed"
    )
```

This records the message, but not necessarily the full traceback.

---

# 30. `logger.exception()`

Inside an exception handler:

```python
try:
    result = 10 / 0

except ZeroDivisionError:
    logger.exception(
        "Calculation failed"
    )
```

This includes exception traceback information.

That can be extremely useful for debugging.

---

# 31. Use `logger.exception()` Inside Exception Handling

Example:

```python
try:
    load_configuration()

except Exception:
    logger.exception(
        "Configuration loading failed"
    )

    raise
```

The error is logged and then re-raised.

Do not automatically use `except Exception` everywhere. The example demonstrates the logging behavior.

---

# 32. Avoid Duplicate Exception Logging

Suppose a low-level function logs:

```text
ERROR API request failed
```

and raises.

Then three higher layers each log the same exception.

You may get four copies of essentially the same failure.

A useful design principle is:

```text
Handle or enrich at lower layers.

Log at the appropriate operational boundary.
```

# 37. Log Rotation

A continuously growing file can eventually consume disk space.

Python supports rotating handlers such as:

```python
from logging.handlers import (
    RotatingFileHandler
)
```

A full production logging design is beyond this beginner section, but you should know the problem exists.

---

# 38. Why Rotation Matters

Without rotation:

```text
automation.log
    |
    v
100 MB
    |
    v
1 GB
    |
    v
10 GB
    |
    v
Disk full
```

Ironically, poor logging can cause an infrastructure incident.

---

# 39. A Simple Rotating File Handler

Example:

```python
import logging

from logging.handlers import (
    RotatingFileHandler
)


logger = logging.getLogger(
    "automation"
)

logger.setLevel(
    logging.INFO
)


handler = RotatingFileHandler(
    "automation.log",
    maxBytes=1_000_000,
    backupCount=3,
    encoding="utf-8"
)


formatter = logging.Formatter(
    "%(asctime)s "
    "%(levelname)s "
    "%(name)s "
    "%(message)s"
)


handler.setFormatter(
    formatter
)

logger.addHandler(
    handler
)
```

---

# 40. What `maxBytes` Means

Here:

```python
maxBytes=1_000_000
```

means the handler begins rotation around the configured file-size limit.

The example is approximately one megabyte.

---

# 41. What `backupCount` Means

```python
backupCount=3
```

means a limited number of rotated backup log files are retained.

The exact naming and rotation behavior is managed by the handler.

---

# 42. Avoid Adding Duplicate Handlers

If setup code runs multiple times:

```python
logger.addHandler(
    handler
)
```

can result in duplicate messages.

Logging configuration should normally happen once at application startup.

---

# 43. Logging Design Principle

Library modules should usually:

```text

Emit logs
```

while the application entry point decides:

```text
Level
Format
Handlers
Destination
```

This keeps configuration centralized.

# 145. Parse Boolean Configuration Explicitly

```python
    value: str

        value.strip().lower()

        "true",
        "1",
        "yes"
    }:
        return True

    if normalized in {
        "false",
        "0",
        "no"
    }:
        return False

    raise ValueError(
        f"Invalid boolean: {value}"
    )
```

```python
def get_positive_int(
```

```python
def extract_ip_addresses(
    text: str

    valid_addresses = []
```

# 190. Full Log Analyzer

```python
from pathlib import Path

from monitor.log_parser import (
    extract_ip_addresses,
    extract_level
)


def analyze_log(
    path: Path
) -> dict:

    counts = {
        "DEBUG": 0,
        "INFO": 0,
        "WARNING": 0,
        "ERROR": 0,
        "CRITICAL": 0
    }

    addresses = set()

    with path.open(
        "r",
        encoding="utf-8"
    ) as file:

        for line in file:

            level = extract_level(
                line
            )

            if level in counts:
                counts[
                    level
                ] += 1

            for address in (
                extract_ip_addresses(
                    line
                )
            ):
                addresses.add(
                    address
                )

    return {
        "levels": counts,
        "ip_addresses": sorted(
            addresses
        )
    }
```
