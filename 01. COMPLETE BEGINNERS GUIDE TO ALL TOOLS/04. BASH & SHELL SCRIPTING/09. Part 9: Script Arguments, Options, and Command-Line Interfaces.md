# Part 9: Script Arguments, Options, and Command-Line Interfaces

In Part 8, you learned how functions receive arguments.

For example:

```bash
deploy_app() {
    local application="$1"
    local environment="$2"

    printf 'Deploying %s to %s\n' "$application" "$environment"
}
```

and:

```bash
deploy_app "api" "production"
```

Inside the function:

```text
$1 = api
$2 = production
```

Entire Bash scripts work in a very similar way.

Suppose you run:

```bash
./deploy.sh api production
```

The script receives:

```text
$0 = ./deploy.sh
$1 = api
$2 = production
```

This is the foundation of a command-line interface, commonly called a **CLI**.

A professional command-line tool should not force users to edit variables inside the script before every execution.

Instead of:

```bash
environment="production"
version="v2.4.1"
```

hardcoded in the script, a user should be able to run something like:

```bash
./deploy.sh api production v2.4.1
```

or:

```bash
./deploy.sh -a api -e production -v v2.4.1
```

A more mature tool may also support:

```bash
./deploy.sh --help
```

and provide clear messages when the user supplies invalid input.

By the end of Part 9, you should understand:

* what positional parameters are
* what `$0` represents
* how `$1` through `$9` work
* how `${10}` and later arguments work
* what `$#` contains
* what `$@` contains
* what `$*` contains
* why `"$@"` is usually preferable to `"$*"`
* how `shift` changes positional parameters
* how to define required arguments
* how to define optional arguments
* how to provide default values
* how to write useful usage messages
* how to implement `--help`
* how to validate user input
* how to detect missing values
* how to parse simple flags manually
* what `getopts` is
* how short options work
* how options accept arguments
* how to handle invalid options
* how to design predictable CLI scripts
* which exit codes to use for bad usage
* how to write useful CLI examples
* how to build a practical command-line deployment utility

# 1. What Is a Command-Line Interface?

A command-line interface allows a user to interact with a program by supplying commands, arguments, and options in a terminal.

You already use CLI tools every day.

Examples:

```bash
ls -la /var/log
```

```bash
grep -i "error" app.log
```

```bash
curl -I https://example.com
```

```bash
docker ps
```

```bash
kubectl get pods -n production
```

Each command has a structure.

For example:

```bash
grep -i "error" app.log
```

can be viewed as:

```text
command
  |
 grep

option
  |
 -i

search argument
  |
 "error"

file argument
  |
 app.log
```

Your Bash scripts can behave the same way.

---

# 2. Why CLI Design Matters

Suppose your script contains:

```bash
environment="production"
application="api"
version="v2.1"
```

Every time you want to deploy something else, you must edit the source code.

That is inconvenient and risky.

A better interface is:

```bash
./deploy.sh api staging v2.2
```

Now the code stays unchanged.

Only the input changes.

Conceptually:

```text
User
 |
 v
Command-line arguments
 |
 v
Script validates them
 |
 v
Script converts them into variables
 |
 v
Script performs requested operation
```

---

# 3. Professional CLI Behavior

A useful command-line tool should behave predictably.

A user should be able to answer:

```text
What arguments are required?

Which arguments are optional?

Which flags are supported?

Which options require values?

What happens if input is invalid?

How do I ask for help?

What exit status represents incorrect usage?
```

A CLI should not require the user to inspect the source code just to learn how to run it.

---

# 4. Positional Parameters

When a Bash script starts, Bash makes command-line arguments available as **positional parameters**.

Suppose:

```bash
./script.sh alpha beta gamma
```

Inside the script:

```text
$1 = alpha
$2 = beta
$3 = gamma
```

They are called positional parameters because their meaning depends on their position.

---

# 5. `$0`

The special parameter:

```bash
$0
```

usually represents the name or path used to invoke the script.

Suppose:

```bash
./deploy.sh production
```

Inside:

```bash
printf 'Script: %s\n' "$0"
```

might print:

```text
Script: ./deploy.sh
```

If invoked differently:

```bash
bash /home/ann/scripts/deploy.sh production
```

`$0` may contain:

```text
/home/ann/scripts/deploy.sh
```

---

# 6. Why `$0` Is Useful

One common use is generating usage messages.

Example:

```bash
printf 'Usage: %s <environment>\n' "$0"
```

If the script is called:

```text
deploy.sh
```

the user sees:

```text
Usage: ./deploy.sh <environment>
```

This is better than hardcoding:

```bash
printf 'Usage: deploy.sh <environment>\n'
```

because the message adapts to how the script was invoked.

---

# 7. `$1` Through `$9`

Bash provides the first nine positional arguments as:

```text
$1
$2
$3
$4
$5
$6
$7
$8
$9
```

Suppose:

```bash
./deploy.sh api production v2.4.1 blue
```

Then:

```text
$1 = api
$2 = production
$3 = v2.4.1
$4 = blue
```

Your script decides what each position means.

---

# 8. Assign Positional Parameters to Meaningful Variables

Instead of repeatedly using:

```bash
"$1"
"$2"
"$3"
```

throughout a script, assign them.

Example:

```bash
application="$1"
environment="$2"
version="$3"
```

Now later code can read:

```bash
printf 'Application: %s\n' "$application"
printf 'Environment: %s\n' "$environment"
printf 'Version: %s\n' "$version"
```

This is much easier to understand.

---

# 9. Argument 10 and Beyond

For arguments beyond `$9`, use braces.

Correct:

```bash
"${10}"
```

```bash
"${11}"
```

```bash
"${12}"
```

Do not write:

```bash
"$10"
```

expecting argument 10.

Bash can interpret that as:

```text
$1
followed by:
0
```

So always use braces for double-digit positional parameters.

---

# 10. Example with Ten Arguments

Suppose:

```bash
./script.sh a b c d e f g h i j
```

Inside:

```bash
printf 'First: %s\n' "$1"
printf 'Ninth: %s\n' "$9"
printf 'Tenth: %s\n' "${10}"
```

Expected:

```text
First: a
Ninth: i
Tenth: j
```

---

# 11. `$#`

The parameter:

```bash
$#
```

contains the number of positional arguments.

Example:

```bash
./script.sh alpha beta gamma
```

Inside:

```bash
printf 'Argument count: %s\n' "$#"
```

prints:

```text
Argument count: 3
```

This is essential for checking whether required arguments were supplied.

---

# 12. Required Argument Validation

Suppose your script requires:

```text
application
environment
version
```

Then exactly three positional arguments are expected.

You can check:

```bash
if (( $# != 3 )); then
    printf 'ERROR: expected 3 arguments\n' >&2
    exit 2
fi
```

Then:

```bash
application="$1"
environment="$2"
version="$3"
```

---

# 13. Why Validate Argument Count First?

Without validation:

```bash
application="$1"
environment="$2"
version="$3"
```

If the user runs:

```bash
./deploy.sh api
```

then:

```text
application = api
environment = empty
version = empty
```

The script may behave unpredictably.

Validate first.

Then use the values.

---

# 14. Minimum Number of Arguments

Sometimes a script requires at least one argument but allows more.

Example:

```bash
if (( $# < 1 )); then
    printf 'ERROR: at least one file is required\n' >&2
    exit 2
fi
```

Then you might process:

```bash
"$@"
```

to support any number of files.

---

# 15. Maximum Number of Arguments

You may also limit arguments:

```bash
if (( $# > 3 )); then
    printf 'ERROR: too many arguments\n' >&2
    exit 2
fi
```

You can combine minimum and maximum checks.

Example:

```bash
if (( $# < 2 || $# > 3 )); then
    printf 'ERROR: expected 2 or 3 arguments\n' >&2
    exit 2
fi
```

---

# 16. `$@`

The parameter:

```bash
"$@"
```

represents all positional arguments while preserving each one as a separate argument.

Suppose:

```bash
./script.sh "server one" "server two" "server three"
```

Then:

```bash
for argument in "$@"; do
    printf '<%s>\n' "$argument"
done
```

prints:

```text
<server one>
<server two>
<server three>
```

The spaces remain inside each original argument.

---

# 17. Why Quoted `"$@"` Matters

Without quotes:

```bash
for argument in $@; do
```

Bash can perform word splitting and filename expansion.

Then:

```text
server one
```

might become:

```text
server
one
```

Prefer:

```bash
"$@"
```

when preserving original arguments matters.

---

# 18. `$*`

Bash also provides:

```bash
"$*"
```

Quoted `"$*"` combines all positional parameters into one string separated by the first character of `IFS`.

Suppose arguments are:

```text
alpha
two words
gamma
```

Quoted `"$@"` acts like:

```text
<alpha>
<two words>
<gamma>
```

Quoted `"$*"` acts more like:

```text
<alpha two words gamma>
```

---

# 19. `$@` vs `$*`

For most script argument processing, prefer:

```bash
"$@"
```

Use `"$*"` only when you intentionally want one combined string.

Mental model:

```text
"$@"
 |
 +--> preserve argument boundaries
```

```text
"$*"
 |
 +--> combine into one string
```

---

# 20. Displaying All Arguments

You can create a debug loop:

```bash
printf 'Received %s argument(s)\n' "$#"

for argument in "$@"; do
    printf 'Argument: <%s>\n' "$argument"
done
```

This is useful while developing command-line tools.

---

# 21. The `shift` Command

`shift` changes positional parameters.

Suppose:

```bash
./script.sh one two three
```

Initially:

```text
$1 = one
$2 = two
$3 = three
$# = 3
```

Run:

```bash
shift
```

Now:

```text
$1 = two
$2 = three
$# = 2
```

The original `$1` is removed.

Everything shifts left.

---

# 22. Shift Again

After the first:

```bash
shift
```

you have:

```text
$1 = two
$2 = three
```

Run:

```bash
shift
```

again.

Now:

```text
$1 = three
$# = 1
```

Shift is very useful when manually parsing command-line options.

---

# 23. `shift 2`

You can shift more than one argument at once.

Example:

```bash
shift 2
```

removes the first two positional parameters.

If:

```text
$1 = -e
$2 = production
$3 = --verbose
```

then after:

```bash
shift 2
```

you get:

```text
$1 = --verbose
```

This is useful for options that consume a value.

---

# 24. Do Not Shift Beyond Available Arguments

If there are not enough positional parameters, `shift` can fail.

Before shifting two values, ensure the option actually has an argument.

For example:

```bash
if (( $# < 2 )); then
    printf 'ERROR: option requires a value\n' >&2
    exit 2
fi
```

Then:

```bash
shift 2
```

---

# 25. Required Arguments

A required argument must be supplied.

Suppose:

```bash
./backup.sh SOURCE DESTINATION
```

Both are required.

Usage:

```text
Usage: ./backup.sh <source> <destination>
```

Validation:

```bash
if (( $# != 2 )); then
    printf 'Usage: %s <source> <destination>\n' "$0" >&2
    exit 2
fi
```

Then:

```bash
source_path="$1"
destination_path="$2"
```

---

# 26. Optional Arguments

An optional argument can be omitted.

Example:

```text
Usage:
    ./deploy.sh <environment> [version]
```

The square brackets in usage documentation conventionally mean:

```text
optional
```

not literal square brackets the user types.

For example:

```bash
./deploy.sh production
```

or:

```bash
./deploy.sh production v2.4.1
```

---

# 27. Default Values

Suppose version is optional.

You can use:

```bash
environment="$1"
version="${2:-latest}"
```

If the user runs:

```bash
./deploy.sh staging
```

then:

```text
environment = staging
version = latest
```

If:

```bash
./deploy.sh staging v2.5
```

then:

```text
version = v2.5
```

---

# 28. Defaults Should Be Safe

Do not choose defaults carelessly.

Potentially dangerous:

```bash
environment="${1:-production}"
```

If the user forgets the environment, the script defaults to production.

Safer possibilities include:

```bash
environment="${1:-development}"
```

or requiring the environment explicitly.

For deployment tools, explicit production targeting is often preferable.

---

# 29. Usage Messages

A usage message tells the user how the program should be invoked.

Basic example:

```bash
usage() {
    printf 'Usage: %s <environment> <version>\n' "$0"
}
```

Then:

```bash
if (( $# != 2 )); then
    usage >&2
    exit 2
fi
```

---

# 30. Better Usage Function

A useful usage message can explain arguments.

```bash
usage() {
    printf 'Usage: %s <application> <environment> [version]\n' "$0"
    printf '\n'
    printf 'Arguments:\n'
    printf '  application   Application name\n'
    printf '  environment   development, staging, or production\n'
    printf '  version       Optional deployment version (default: latest)\n'
}
```

Now the tool teaches the user its interface.

---

# 31. Usage Messages Are Part of the Interface

Do not treat help text as decoration.

A CLI user should be able to understand:

```text
what to type
what each value means
which values are allowed
which options are optional
```

A confusing CLI produces user errors.

---

# 32. Implementing `--help`

Users often expect:

```bash
./tool.sh --help
```

You can detect it early.

Example:

```bash
if [[ "${1:-}" == "--help" ]]; then
    usage
    exit 0
fi
```

Notice:

```bash
"${1:-}"
```

instead of simply:

```bash
"$1"
```

This safely supplies an empty default if no argument exists.

---

# 33. Help Is Usually Successful

If the user deliberately requests:

```bash
--help
```

the program should normally exit:

```text
0
```

because nothing failed.

Example:

```bash
usage
exit 0
```

Bad usage is different.

---

# 34. Bad Usage Should Return Non-Zero

Suppose required arguments are missing.

You can write:

```bash
printf 'ERROR: missing required arguments\n' >&2
usage >&2
exit 2
```

Why not `exit 0`?

Because the invocation was invalid.

Automation should be able to distinguish:

```text
help requested
```

from:

```text
command used incorrectly
```

---

# 35. Exit Code 2 for Usage Errors

Many Unix-style tools use status `2` for command-line usage problems, though conventions vary.

For your own Bash scripts, a simple scheme could be:

```text
0 = success
1 = operational failure
2 = command-line usage error
```

For example:

```text
0 = deployment completed
1 = deployment failed
2 = invalid argument or option
```

Keep it documented and consistent.

---

# 36. Input Validation

Argument count alone is not enough.

Suppose:

```bash
./deploy.sh api banana v2.4
```

The correct number of arguments was supplied.

But:

```text
banana
```

is not a valid environment.

Your script should validate the value.

---

# 37. Validate Allowed Values

Example:

```bash
case "$environment" in
    development|staging|production)
        ;;
    *)
        printf 'ERROR: invalid environment: %s\n' "$environment" >&2
        exit 2
        ;;
esac
```

This is a whitelist.

Only known values are accepted.

---

# 38. Validate Non-Empty Values

Example:

```bash
if [[ -z "$application" ]]; then
    printf 'ERROR: application must not be empty\n' >&2
    exit 2
fi
```

Even if an argument technically exists, it may be empty.

For example:

```bash
./deploy.sh "" staging
```

Bash receives an empty first argument.

Validate values, not only counts.

---

# 39. Validate Format

Suppose version names must follow:

```text
v1
v2
v12
v42
```

You could use:

```bash
if [[ ! "$version" =~ ^v[0-9]+$ ]]; then
    printf 'ERROR: invalid version: %s\n' "$version" >&2
    exit 2
fi
```

This uses regex matching from Part 6.

---

# 40. Validate Paths

Suppose a script receives:

```bash
./process.sh logs/
```

Validate:

```bash
if [[ ! -d "$directory" ]]; then
    printf 'ERROR: directory not found: %s\n' "$directory" >&2
    exit 2
fi
```

If the program requires a file:

```bash
if [[ ! -f "$file" ]]; then
    ...
fi
```

Input validation should reflect actual requirements.

---

# 41. Handling Missing Values

This is especially important with options.

Suppose:

```bash
./deploy.sh --environment
```

The option requires a value.

If your parser blindly does:

```bash
environment="$2"
shift 2
```

there may be no `$2`.

The program needs to detect this.

---

# 42. Manual Missing-Value Check

Example:

```bash
if [[ "${1:-}" == "--environment" ]]; then

    if (( $# < 2 )); then
        printf 'ERROR: --environment requires a value\n' >&2
        exit 2
    fi

    environment="$2"
    shift 2
fi
```

Never assume the next argument exists.

---

# 43. Flags vs Options with Values

A **flag** usually represents an on/off behavior.

Example:

```bash
--verbose
```

It may not require another argument.

An option such as:

```bash
--environment production
```

requires a value.

Conceptually:

```text
--verbose
    |
    +--> boolean behavior
```

```text
--environment production
       |           |
       option      value
```

---

# 44. Parsing Simple Flags Manually

Suppose your script supports:

```text
--verbose
--dry-run
--environment VALUE
```

You can manually parse arguments with a loop.

Example:

```bash
while (( $# > 0 )); do

    case "$1" in
        --verbose)
            verbose=true
            shift
            ;;

        --dry-run)
            dry_run=true
            shift
            ;;

        --environment)
            environment="$2"
            shift 2
            ;;

        *)
            printf 'ERROR: unknown argument: %s\n' "$1" >&2
            exit 2
            ;;
    esac

done
```

This uses `shift` to consume arguments as they are processed.

---

# 45. Why `while (( $# > 0 ))` Works

At the start:

```text
$# = number of unprocessed arguments
```

Each:

```bash
shift
```

reduces the count.

Eventually:

```text
$# = 0
```

and the loop stops.

Conceptually:

```text
Arguments remain?
      |
     Yes
      |
      v
Inspect $1
      |
      v
Process it
      |
      v
shift
      |
      v
Arguments remain?
```

---

# 46. Manual Parser Example

```bash
verbose=false
dry_run=false
environment=""

while (( $# > 0 )); do

    case "$1" in
        --verbose)
            verbose=true
            shift
            ;;

        --dry-run)
            dry_run=true
            shift
            ;;

        --environment)
            if (( $# < 2 )); then
                printf 'ERROR: --environment requires a value\n' >&2
                exit 2
            fi

            environment="$2"
            shift 2
            ;;

        --help)
            usage
            exit 0
            ;;

        *)
            printf 'ERROR: unknown option: %s\n' "$1" >&2
            usage >&2
            exit 2
            ;;
    esac

done
```

---

# 47. Why Manual Parsing Can Be Useful

Manual parsing is useful when:

* supporting long options such as `--environment`
* CLI structure is simple
* you want full control
* only a few flags exist

But as option parsing grows, it becomes easier to make mistakes.

Bash provides another tool:

```bash
getopts
```

---

# 48. What Is `getopts`?

`getopts` is a Bash/shell builtin used for parsing short command-line options.

Example options:

```text
-e production
-v v2.4.1
-d
-h
```

where:

```text
-e = environment
-v = version
-d = dry run
-h = help
```

---

# 49. Short Options

A short option normally begins with one hyphen and one character.

Examples:

```text
-h
-v
-d
-e
```

This resembles many Linux tools.

For example:

```bash
ls -l
```

```bash
grep -i
```

Your script can use similar conventions.

---

# 50. Basic `getopts` Structure

Example:

```bash
while getopts "h" option; do

    case "$option" in
        h)
            usage
            exit 0
            ;;
    esac

done
```

The string:

```text
h
```

tells `getopts` that:

```text
-h
```

is valid.

---

# 51. Multiple Short Options

Suppose valid options are:

```text
-h
-d
```

Use:

```bash
while getopts "hd" option; do
    ...
done
```

The option string:

```text
hd
```

means:

```text
-h valid
-d valid
```

Neither requires an argument.

---

# 52. Options Requiring Arguments

Suppose:

```text
-e
```

requires an environment value.

The `getopts` specification uses:

```text
e:
```

The colon means:

> `-e` requires an argument.

For:

```text
-h
-d
-e VALUE
-v VALUE
```

use:

```bash
while getopts "hde:v:" option; do
```

Breakdown:

```text
h     no argument
d     no argument
e:    requires argument
v:    requires argument
```

---

# 53. `OPTARG`

When an option requires a value, `getopts` stores it in:

```bash
OPTARG
```

Example:

```bash
./deploy.sh -e production
```

Inside the `e)` branch:

```text
OPTARG = production
```

Example:

```bash
e)
    environment="$OPTARG"
    ;;
```

---

# 54. Basic `getopts` Example

```bash
environment=""
version="latest"
dry_run=false

while getopts "e:v:d" option; do

    case "$option" in
        e)
            environment="$OPTARG"
            ;;
        v)
            version="$OPTARG"
            ;;
        d)
            dry_run=true
            ;;
    esac

done
```

Run:

```bash
./deploy.sh -e staging -v v2.4 -d
```

Results:

```text
environment = staging
version = v2.4
dry_run = true
```

---

# 55. `OPTIND`

`getopts` also uses:

```bash
OPTIND
```

to track the next argument to process.

After `getopts` finishes, you commonly run:

```bash
shift "$((OPTIND - 1))"
```

This removes parsed options from the positional parameters.

Any remaining values are ordinary positional arguments.

---

# 56. Example with Options and Positional Arguments

Suppose your CLI is:

```bash
./deploy.sh -e production -v v2.4 api
```

Here:

```text
-e production
-v v2.4
```

are options.

```text
api
```

is a positional argument.

After:

```bash
shift "$((OPTIND - 1))"
```

you can access:

```bash
application="$1"
```

---

# 57. Full Option Parsing Example

```bash
environment=""
version="latest"
dry_run=false

while getopts "e:v:d" option; do

    case "$option" in
        e)
            environment="$OPTARG"
            ;;
        v)
            version="$OPTARG"
            ;;
        d)
            dry_run=true
            ;;
    esac

done

shift "$((OPTIND - 1))"

application="${1:-}"
```

Now options and positional arguments are separated cleanly.

---

# 58. Invalid Options

Suppose the user runs:

```bash
./deploy.sh -z
```

but `z` is unsupported.

Your script should report the problem clearly.

With `getopts`, you can handle:

```bash
?)
```

Example:

```bash
?)
    printf 'ERROR: invalid option: -%s\n' "$OPTARG" >&2
    usage >&2
    exit 2
    ;;
```

---

# 59. Missing Option Arguments

Suppose:

```bash
./deploy.sh -e
```

but `-e` requires a value.

A robust script should detect this.

One useful approach is beginning the option string with:

```text
:
```

Example:

```bash
while getopts ":e:v:dh" option; do
```

The leading colon changes how certain parsing errors are reported so you can handle them yourself.

---

# 60. Handling Missing Values with `getopts`

Example:

```bash
while getopts ":e:v:dh" option; do

    case "$option" in
        e)
            environment="$OPTARG"
            ;;
        v)
            version="$OPTARG"
            ;;
        d)
            dry_run=true
            ;;
        h)
            usage
            exit 0
            ;;
        :)
            printf 'ERROR: option -%s requires an argument\n' "$OPTARG" >&2
            exit 2
            ;;
        \?)
            printf 'ERROR: invalid option: -%s\n' "$OPTARG" >&2
            exit 2
            ;;
    esac

done
```

---

# 61. Why `\?`

Inside a `case` statement:

```bash
\?)
```

matches the literal question-mark result returned by `getopts` for an unknown option.

The backslash prevents `?` from behaving as a shell pattern wildcard.

---

# 62. `getopts` Is Mainly for Short Options

Traditional `getopts` works naturally with:

```text
-e
-v
-d
-h
```

It does not directly provide full GNU-style long-option parsing such as:

```text
--environment
--version
--dry-run
```

For simple long options, manual parsing with `case` and `shift` is often used.

External `getopt` implementations exist, but behavior can vary between systems.

For beginner Bash scripts, learn `getopts` first for predictable short-option parsing.

---

# 63. CLI Design Choice: Positional Arguments vs Options

Suppose:

```bash
./deploy.sh api production v2.4
```

This is concise.

But what does each position mean?

A user must remember:

```text
1 = application
2 = environment
3 = version
```

Compare:

```bash
./deploy.sh -a api -e production -v v2.4
```

This is more verbose, but self-describing.

---

# 64. When Positional Arguments Work Well

Use positional arguments when:

* there are very few
* order is obvious
* values are required
* invocation remains easy to remember

Example:

```bash
cp SOURCE DESTINATION
```

Two positions make sense.

---

# 65. When Options Work Better

Options are useful when:

* there are many settings
* some are optional
* order should not matter
* values need descriptive labels
* flags enable behaviors

Example:

```bash
./deploy.sh \
    -e production \
    -v v2.4 \
    -d
```

---

# 66. Do Not Make CLI Syntax Arbitrarily Complicated

Avoid creating interfaces like:

```bash
./tool.sh application production v2 yes 5 false blue force
```

No one can easily remember what each position means.

Prefer descriptive options.

A good CLI is designed for the user, not merely for the programmer.

# 67. Option Ordering

With proper option parsing, users often expect:

```bash

```

and:

```bash

```

to behave consistently.

That is one benefit of `getopts`.

Do not unnecessarily require a particular option order if the parser can avoid it.

# 80. Why Silent Ignoring Is Dangerous

Suppose a user types:

```bash
./deploy.sh -a api -e production -v v2.4 prodction
```

If the script silently ignores:

```text
prodction
```

the user may believe it affected behavior.

Unknown input should normally be rejected explicitly.

Predictable CLIs do not silently ignore mistakes.

# 81. Duplicate Options

What happens if the user writes:

```bash
./deploy.sh -e staging -e production
```

A simple parser may use the last value:

```text
production
```

You need a policy.

Possibilities:

```text
last value wins
```

or:

```text
duplicate option is an error
```

The important point is consistency.

For beginner scripts, allowing the last value to win may be acceptable if documented.

For high-risk production tools, rejecting duplicates can be safer.

# 82. Case Sensitivity

Should these all work?

```text
production
Production
PRODUCTION
```

You must decide.

A strict CLI may accept only:

```text
production
```

and reject the others.

This reduces ambiguity.

Alternatively, normalize:

```bash
environment="${environment,,}"
```

which converts to lowercase in Bash.

Then validate.

Be deliberate.

---

# 83. Avoid Secret Values in Command-Line Arguments

This is an important security concern.

Do not design interfaces such as:

```bash
./deploy.sh --password SuperSecretPassword
```

when avoidable.

Command-line arguments may be visible in:

* shell history
* process listings
* logs
* monitoring tools

Prefer:

* secure environment-variable mechanisms where appropriate
* secret managers
* file descriptors
* protected configuration
* interactive secret input with `read -s` where suitable

CLI convenience should not override secret safety.

---

# 84. Do Not Log All Arguments Blindly

This looks useful for debugging:

```bash
printf 'Arguments: %s\n' "$*"
```

But if arguments contain secrets, they are now logged.

Before logging CLI input, ask:

```text
Can any option contain:
passwords?
tokens?
keys?
credentials?
sensitive paths?
```

Sanitize appropriately.

# 85. Manual Long-Option Parser

Suppose you want:

```text
--application
--environment
--version
--dry-run
--help
```

You can write:

```bash
application=""
environment=""
version="latest"
dry_run=false

while (( $# > 0 )); do

    case "$1" in
        --application)
            if (( $# < 2 )); then
                printf 'ERROR: --application requires a value\n' >&2
                exit 2
            fi

            application="$2"
            shift 2
            ;;

        --environment)
            if (( $# < 2 )); then
                printf 'ERROR: --environment requires a value\n' >&2
                exit 2
            fi

            environment="$2"
            shift 2
            ;;

        --version)
            if (( $# < 2 )); then
                printf 'ERROR: --version requires a value\n' >&2
                exit 2
            fi

            version="$2"
            shift 2
            ;;

        --dry-run)
            dry_run=true
            shift
            ;;

        --help)
            usage
            exit 0
            ;;

        *)
            printf 'ERROR: unknown option: %s\n' "$1" >&2
            usage >&2
            exit 2
            ;;
    esac

done
```

This is readable for a small set of long options.

---

# 86. Short vs Long Options

Short form:

```bash
./deploy.sh -a api -e production -v v2.4 -d
```

Long form:

```bash
./deploy.sh \
    --application api \
    --environment production \
    --version v2.4 \
    --dry-run
```

Short options are concise.

Long options are more self-explanatory.

Professional tools often support both, but implementing both manually increases complexity.

Learn one predictable design before expanding.

# 87. Combined Short Flags

Many Unix tools support:

```text
-vdh
```

instead of:

```text
-v -d -h
```

`getopts` can parse combined short options when they do not conflict with required arguments.

But do not force this feature if it makes your CLI confusing.

Correctness and clarity matter more than imitation.


Avoid a function that mixes everything:


Instead:

```text

     |
```

* validation becomes clearer
* deployment functions do not care how values were supplied
* future interfaces can change more easily
* errors are easier to diagnose

This builds directly on Part 8's function design principles.

# 94. Syntax Validation vs Semantic Validation

Parsing answers:

```text
Was -e supplied with a value?
```

Semantic validation answers:

```text
Is that value one of:
development
staging
production?
```

Both matter.

Example:

```bash

```

is syntactically valid.

But semantically invalid.

# 95. CLI Error Message Design

Poor:

```text

```

Better:

```text

```

A good error message tells the user:

```text
what was wrong
what value caused it
how to fix it
```

# 96. Usage Output vs Error Output

Help requested:

```bash
./deploy.sh -h
```

Usage goes to stdout:

```bash

```

Bad usage:

```bash
./deploy.sh -e
```

Usage may go to stderr:

```bash
usage >&2
exit 2
```

Why?

Because help is ordinary requested output.

Bad usage is diagnostic output.

```bash
validate_args() {

    if [[ -z "$application" ]]; then
        printf 'ERROR: application is required. Use -a APPLICATION.\n' >&2
        return 2
    fi

    if [[ -z "$environment" ]]; then
        printf 'ERROR: environment is required. Use -e ENVIRONMENT.\n' >&2
        return 2
    fi

    case "$environment" in
        development|staging|production)
            ;;
        *)
            printf 'ERROR: unsupported environment: %s\n' "$environment" >&2
            printf 'Allowed values: development, staging, production\n' >&2
            return 2
            ;;
    esac

    if [[ -z "$version" ]]; then
        printf 'ERROR: version must not be empty\n' >&2
        return 2
    fi

    if [[ "$version" != "latest" && ! "$version" =~ ^v[0-9]+([.][0-9]+)*$ ]]; then
        printf 'ERROR: invalid version format: %s\n' "$version" >&2
        printf 'Examples: latest, v1, v2.4, v2.4.1\n' >&2
        return 2
    fi

    return 0
}

print_plan() {
    printf '\nDEPLOYMENT PLAN\n'
    printf '===============\n'
    printf 'Application: %s\n' "$application"
    printf 'Environment: %s\n' "$environment"
    printf 'Version: %s\n' "$version"
    printf 'Dry run: %s\n' "$dry_run"
}

check_environment_policy() {

    case "$environment" in
        development)
            printf 'Policy: development deployment\n'
            ;;

        staging)
            printf 'Policy: staging validation required\n'
            ;;

        production)
            printf 'Policy: production safeguards enabled\n'

            if [[ "$version" == "latest" ]]; then
                printf 'ERROR: production requires an explicit version\n' >&2
                return 2
            fi
            ;;
    esac

    return 0
}

simulate_deployment() {

    if [[ "$dry_run" == "true" ]]; then
        printf '\nDRY RUN\n'
        printf '=======\n'
        printf 'Would deploy application %s\n' "$application"
        printf 'Would deploy version %s\n' "$version"
        printf 'Would target environment %s\n' "$environment"
        printf 'No deployment changes were made.\n'
        return 0
    fi

    printf '\nDEPLOYMENT\n'
    printf '==========\n'
    printf 'Deploying %s version %s to %s...\n' \
        "$application" "$version" "$environment"

    sleep 1

    printf 'Deployment simulation completed.\n'

    return 0
}

verify_deployment() {

    if [[ "$dry_run" == "true" ]]; then
        printf 'Verification skipped because this was a dry run.\n'
        return 0
    fi

    printf 'Verifying deployment...\n'
    sleep 1
    printf 'Deployment verification simulation passed.\n'

    return 0
}

main() {
    local status

    parse_args "$@"
    status=$?

    if (( status != 0 )); then
        return "$status"
    fi

    if ! validate_args; then
        usage >&2
        return 2
    fi

    if ! check_environment_policy; then
        return 2
    fi

    print_plan

    if ! simulate_deployment; then
        printf 'ERROR: deployment failed\n' >&2
        return 1
    fi

    if ! verify_deployment; then
        printf 'ERROR: deployment verification failed\n' >&2
        return 1
    fi

    printf '\nRESULT: SUCCESS\n'
    return 0
}

main "$@"
status=$?

exit "$status"
```

# 130. Common Beginner Mistake: Using `$10`

Incorrect:

```bash
printf '%s\n' "$10"
```

```bash
printf '%s\n' "${10}"
```

# 131. Common Beginner Mistake: Forgetting to Quote `$@`

Risky:

```bash
for argument in $@; do
```

Better:

```bash
for argument in "$@"; do
```

The quoted form preserves each original argument.

---

# 132. Common Beginner Mistake: Using `$*` as `$@`

These are not interchangeable.

Use:

```bash
"$@"
```

when forwarding separate arguments.

Use:

```bash
"$*"
```

only when you intentionally want one combined string.

---

# 133. Common Beginner Mistake: Using `$#` Without Understanding It

`$#` does not mean:

```text
number of characters
```

It means:

```text
number of positional parameters
```

For:

```bash
./script.sh "two words"
```

`$#` is:

```text
1
```

not 2.

The quoted value is one argument.

---

# 134. Common Beginner Mistake: Shifting Too Early

Suppose:

```text
$1 = -e
$2 = production
```

If you:

```bash
shift
```

before saving `$2`, positional parameters change.

Now:

```text
$1 = production
```

Be deliberate.

Parse and store values before shifting them away.

---

# 135. Common Beginner Mistake: Forgetting `shift`

Manual parser:

```bash
while (( $# > 0 )); do
    case "$1" in
        --verbose)
            verbose=true
            ;;
    esac
done
```

What changes `$#`?

Nothing.

This loop may never terminate.

You need:

```bash
shift
```

after processing the option.

This connects directly to Part 7's infinite-loop lessons.

---

# 136. Common Beginner Mistake: Blind `shift 2`

Problem:

```bash
--environment)
    environment="$2"
    shift 2
    ;;
```

without verifying that `$2` exists.

If the user runs:

```bash
./script.sh --environment
```

there is no value.

Validate first.

---

# 137. Common Beginner Mistake: Treating `--help` as Failure

Help requested:

```bash
./tool.sh -h
```

should usually exit:

```text
0
```

because the user successfully asked for documentation.

Do not return usage-error status for ordinary help requests.

---

# 138. Common Beginner Mistake: Returning 0 for Invalid Usage

If:

```bash
./tool.sh -z
```

is invalid but exits:

```text
0
```

a calling system may believe the command succeeded.

Use a non-zero status for invalid usage.

---

# 139. Common Beginner Mistake: Starting Work Before Parsing Ends

Bad structure:

```text
read -a
start deployment
read -e
validate environment
```

Parse and validate the complete request before making side effects.

Preferred:

```text
parse
validate
plan
act
verify
```

# 140. Common Beginner Mistake: Silent Unknown Options

If the tool receives:

```bash
--prodction
```

do not ignore it.

Return:

```text
ERROR: unknown option: --prodction
```

Silent ignoring is dangerous in operational tools.

---

# 141. Common Beginner Mistake: Ambiguous Short Options

Do not make:

```text
-v = version
```

and also:

```text
-v = verbose
```

Choose one meaning.

A CLI option should have one predictable contract.

---

# 142. Common Beginner Mistake: Unsafe Production Defaults

Avoid:

```bash
environment="${environment:-production}"
```

unless there is an exceptionally strong reason.

A missing input should not casually escalate to the highest-risk environment.

Require explicit production targeting.

---

# 143. Common Beginner Mistake: Passing Secrets as Options

Avoid:

```bash
./deploy.sh -p MyPassword
```

for secrets when safer methods exist.

Command-line arguments may remain visible in places users do not expect.

Treat credentials differently from ordinary CLI configuration.

# 145. Troubleshooting: `getopts` Skips Expected Arguments

Check your option specification.

If:

```text
-e
```

requires a value, it must appear as:

```text
e:
```

in:

```bash
getopts
```

Without the colon, `getopts` treats `-e` as a flag without a value.

# 146. Troubleshooting: `OPTARG` Is Empty

Ask:

```text
Does this option actually require an argument?

Does the getopts string contain : after the option letter?

Did the user supply the value?
```

For:

```bash
-e production
```

you need:

```bash
getopts "...e:..."
```

# 147. Troubleshooting: Remaining Positional Arguments Are Wrong

After parsing, did you run:

```bash
shift "$((OPTIND - 1))"
```

If not, parsed options still occupy positional parameters.

The script may think:

```text
$1 = -e
```

instead of the remaining application argument.

---

# 148. Troubleshooting: Options Work Once but Fail When Function Is Reused

`OPTIND` retains parser state.

If a function containing `getopts` is called multiple times in the same shell, you may need to reset:

```bash
OPTIND=1
```

before parsing again.

Example:

```bash
parse_args() {
    OPTIND=1

    while getopts ":a:e:" option; do
        ...
    done
}
```

For a normal script where parsing occurs only once, this often does not matter.

But reusable parser functions should understand it.

---

# 149. Troubleshooting: Long Options Fail with `getopts`

Traditional `getopts` is designed around short options such as:

```text
-a
-e
-v
```

It does not directly parse:

```text
--application
```

Use a manual `case`/`shift` parser for simple long-option support or choose another deliberate parsing design.

# 151. Security: Validate Target Environments

Deployment CLIs should not allow arbitrary environment strings to become paths, hostnames, cloud resources, or command fragments without validation.

Safer:

```bash
case "$environment" in
    development|staging|production)
        ;;
    *)
        return 2
        ;;
esac
```

Whitelisting known deployment environments reduces accidental targeting.

---

# 152. Security: Avoid Building Commands as Strings

Dangerous design:

```bash
command="deploy --environment $environment"
eval "$command"
```

If user-controlled values contain shell syntax, this can become dangerous.

Prefer:

```bash
deploy --environment "$environment"
```

or arrays later where command construction is necessary.

Avoid `eval` for CLI input.

---

# 153. Security: Dry Run Must Really Be Dry

If a CLI supports:

```text
-d
```

then dry-run mode must not secretly perform the destructive action first and print afterward.

Correct flow:

```text
dry_run?
   |
  Yes
   |
   v
print intended action
   |
   v
return without changing system
```

Test dry-run behavior carefully.

A production CLI may eventually require:

* explicit version
* explicit environment
* correct credentials
* healthy dependencies
* change approval
* backup verification
* restricted user privileges
* confirmation or non-interactive approval policy
* rollback information

Do not treat production like an ordinary default.

# What You Should Now Understand

After Part 9, you should understand that:

* command-line interfaces allow scripts to receive runtime configuration
* script arguments are exposed through positional parameters
* `$0` normally represents the invoked script name or path
* `$1` through `$9` contain the first nine arguments
* `${10}` and braces are required for argument 10 and beyond
* `$#` contains the number of positional arguments
* quoted `"$@"` preserves all original arguments separately
* quoted `"$*"` combines all arguments into one string
* `"$@"` is usually preferable when preserving argument boundaries
* `shift` removes positional parameters from the beginning
* `shift 2` removes two arguments
* required arguments should be validated before use
* optional arguments can use documented defaults
* production-sensitive defaults should be chosen carefully
* usage messages form part of the CLI interface
* help output should explain syntax, required options, optional options, and examples
* deliberate help requests normally exit successfully
* bad CLI usage should return non-zero
* exit code `2` is a reasonable documented choice for usage errors
* argument count validation does not replace value validation
* allowed values should be whitelisted when appropriate
* empty values should be rejected when invalid
* formats can be validated with regex
* file and directory arguments should be validated before use
* flags normally represent on/off behaviors
* options may require values
* manual parsers can use `while`, `case`, and `shift`
* manual parsers must ensure they always make progress
* `getopts` parses short options
* `OPTARG` contains the current option's argument
* `OPTIND` tracks option parsing position
* a colon after an option letter means that option requires an argument
* a leading colon in the `getopts` specification allows custom parsing errors
* invalid options can be handled through the `?` case
* missing option values can be handled through the `:` case
* parsed options can be removed with `shift "$((OPTIND - 1))"`
* extra remaining arguments should usually be rejected
* traditional `getopts` is primarily designed for short options
* simple long options can be parsed manually
* command-line parsing should be separated from operational logic
* syntax validation and semantic validation are different
* dry-run mode should avoid actual changes
* secrets should not casually be passed or logged through CLI arguments
* production deployments should normally require explicit targeting
* predictable CLI behavior reduces operational mistakes

# Part 9 Summary

You can now make a Bash script behave like a real command-line program.

Instead of editing:

```bash
application="api"
environment="production"
version="v2.4"
```

inside source code, users can provide runtime configuration:

```bash
./deploy.sh -a api -e production -v v2.4
```

The core positional parameters are:

```text
$0       script name/path

$1       first argument

$2       second argument

...

$9       ninth argument

${10}    tenth argument

$#       argument count

"$@"     all arguments, preserving boundaries

"$*"     all arguments combined when quoted
```

You learned how:

```bash
shift
```

changes positional parameters.

For example:

```text
Before shift:

$1 = -e
$2 = production
$3 = -d

After shift 2:

$1 = -d
```

This makes manual option parsing possible.

You also learned to distinguish:

```text
Required argument
     |
     +--> must be supplied
```

from:

```text
Optional argument
     |
     +--> may have default
```

and:

```text
Flag
 |
 +--> usually boolean behavior
```

from:

```text
Option with value
 |
 +--> requires another argument
```

A simple CLI can use positional values:

```bash
./deploy.sh api production v2.4
```

while a more descriptive interface can use options:

```bash
./deploy.sh \
    -a api \
    -e production \
    -v v2.4 \
    -d
```

With `getopts`:

```bash
while getopts ":a:e:v:dh" option; do
```

```text

```

```text
OPTARG
   |
   +--> option's value

OPTIND
   |
   +--> parser position
```

After parsing:

```bash
shift "$((OPTIND - 1))"
```

removes processed options.
