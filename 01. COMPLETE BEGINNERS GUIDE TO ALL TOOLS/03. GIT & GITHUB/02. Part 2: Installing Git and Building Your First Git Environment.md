# Part 2: Installing Git and Building Your First Git Environment

In Part 1, you learned what Git is, why version control exists, how Git differs from GitHub, and how changes move conceptually through the working directory, staging area, local repository, and remote repository.

Now it is time to build the environment you will actually use.

This part is important because Git is not something you only understand theoretically. You will spend most of this series typing commands, creating repositories, inspecting files, making commits, troubleshooting errors, and eventually working with GitHub.

Before doing any of that, your system needs a correctly installed and configured Git environment.

By the end of Part 2, you should be able to:

* Install Git on Windows
* Install Git on macOS
* Install Git on common Linux distributions
* Confirm that Git is installed correctly
* Understand what a terminal is
* Understand what a shell is
* Understand a command, option, and argument
* Navigate basic directories from the command line
* Understand Git's configuration system
* Explain system, global, and local Git configuration
* Configure your Git username and email address
* Inspect existing Git configuration
* Understand configuration precedence
* Configure the default branch name
* Configure a text editor for Git
* Understand line endings
* Configure `core.autocrlf`
* Understand the `.gitconfig` file
* Use Git's built-in help system
* Create a safe practice directory for the rest of the series

# 2. Git Is a Command-Line Program

Git can be used through graphical applications, but the command line is the foundation.

You may eventually encounter tools such as:

* GitHub Desktop
* Visual Studio Code Git integration
* IntelliJ Git integration
* SourceTree
* GitKraken

These applications can make Git easier to visualize.

However, they still perform Git operations underneath.

For this series, you will learn Git primarily from the command line.

Why?

Because command-line Git teaches you what Git is actually doing.

It also prepares you for environments where graphical tools may not exist.

For example:

```text
Your Laptop
```

may have a graphical interface.

But:

```text
Linux Server
AWS EC2 Instance
Container
CI/CD Runner
Kubernetes Utility Host
Remote Build Machine
```

may only provide a terminal.

For DevOps, SRE, cloud, infrastructure, and platform engineering, command-line familiarity is essential.

# 3. What Is a Terminal?

A terminal is an application that provides a text-based interface for interacting with your computer.

Instead of clicking icons, you type commands.

A terminal may look something like:

```text
ann@laptop:~$
```

or:

```text
C:\Users\Ann>
```

or:

```text
PS C:\Users\Ann>
```

You type a command after the prompt.

Example:

```bash
git --version
```

The terminal displays the result.

Example:

```text
git version 2.55.0
```

The terminal itself is not Git.

Think of the relationship like this:

```text
You
 |
 v
Terminal
 |
 v
Shell
 |
 v
Command
 |
 v
Operating System / Program
```

Git is one of the programs that your shell can execute.

---

# 4. What Is a Shell?

A shell is a program that reads the commands you type and asks the operating system to perform them.

Common shells include:

```text
Bash
Zsh
PowerShell
Command Prompt
Fish
```

On many Linux systems, you will encounter Bash.

On modern macOS systems, Zsh is commonly the default interactive shell.

On Windows, you may use:

```text
PowerShell
Command Prompt
Git Bash
Windows Terminal
```

Windows Terminal deserves a small clarification.

Windows Terminal is a terminal application.

Inside it, you can run shells such as PowerShell or Command Prompt.

Conceptually:

```text
Windows Terminal
      |
      +-- PowerShell
      |
      +-- Command Prompt
      |
      +-- WSL shell
```

Do not worry if this seems confusing at first.

For now, remember:

```text
Terminal = the interface window

Shell = the program interpreting your commands

Git = a program the shell can run
```

# 5. Understanding a Command Before Using Git

Consider:

```bash
git --version
```

There are two main pieces.

```text
git
```

is the command.

```text
--version
```

is an option.

The command asks the computer to execute Git.

The option tells Git:

> Show me the installed Git version.

Another example:

```bash
mkdir git-practice
```

Here:

```text
mkdir
```

is the command.

```text
git-practice
```

is an argument.

The argument tells `mkdir` which directory to create.

So:

```text
command + option + argument
```

is a pattern you will see repeatedly.

# 6. Short Options and Long Options

Command-line tools often support short and long options.

You may see:

```text

```

or:

```text

```

A single dash often introduces a short option:

```bash

```

Two dashes often introduce a long option:


The exact options depend on the command.

Never assume every program supports the same flags.

# 13. Windows Troubleshooting: git Is Not Recognized

You might see something like:

```text
'git' is not recognized as an internal or external command
```

or PowerShell may report that `git` is not recognized.

This usually means one of the following:

* Git is not installed
* The terminal was already open before installation
* Git's executable directory is not available through your `PATH`
* Installation did not complete correctly

First:

1. Close the terminal
2. Open it again
3. Run:

```bash
git --version
```

If it still fails, confirm that Git for Windows was actually installed.

# 14. What Is PATH?

Your system's `PATH` is a list of directories where the operating system looks for executable programs.

When you type:

```bash
git
```

your shell needs to find the Git executable.

Conceptually:

```text
You type:
git

      |
      v

Shell searches PATH
      |
      v

Finds Git executable
      |
      v

Runs Git
```

If Git exists but its executable cannot be found through the configured search path, the shell may report:

```text
command not found
```

or:

```text
not recognized
```

You do not need to manually modify PATH unless installation troubleshooting requires it.

# 21. Why Run apt update First?

Your system maintains package metadata describing what packages and versions are available.

Running:


It does not normally upgrade all installed software.

That is a different operation.

Then:

```bash
sudo apt install git
```

installs Git using the package information available to your system.

# 27. Do You Need the Absolute Latest Git Version?

Usually, no.

A supported recent Git version is sufficient for this beginner series.

Linux distribution repositories sometimes package a version different from the newest Git source release.

For a beginner, use a supported package from your operating system or the official installation path unless you have a specific reason not to.

# 36. Git Configuration

Installing Git makes the program available.

Configuration tells Git how you want it to behave.

Git includes a command called:

```bash
git config
```

The official Git documentation describes `git config` as the tool used to read and write Git configuration values.

Configuration can include:

* Your name
* Your email address
* Your preferred text editor
* Your default branch name
* Line-ending behavior
* Aliases
* Credential behavior
* Many other Git settings

---

# 37. Git Configuration Uses Key-Value Pairs

A Git configuration setting often looks conceptually like:

```text
key = value
```

For example:

```text
user.name = Ann Felix
```

Another:

```text
user.email = ann@example.com
```

Another:

```text
init.defaultBranch = main
```

Git uses these configuration values to determine behavior.

---

# 38. Git Configuration Levels

Git configuration can exist at different scopes.

The three important beginner levels are:

```text
System
Global
Local
```

Think of them as increasingly specific.

```text
SYSTEM
   |
   v
GLOBAL
   |
   v
LOCAL
```

A more specific configuration can override a broader one.

The official Git documentation describes system-wide configuration, user-specific global configuration, and repository-specific configuration, with more specific repository configuration taking precedence over broader settings.

---

# 39. System Configuration

System configuration applies broadly to users on the machine.

You target it using:

```bash
git config --system
```

Conceptually:

```text
Computer
 |
 +-- User A
 |
 +-- User B
 |
 +-- User C
```

A system-level Git setting can affect Git usage across the machine.

System configuration is typically managed less often by individual beginners.

You may require administrative privileges to modify it.

Do not change system Git configuration unless you understand why the change is necessary.

---

# 40. Global Configuration

Global configuration applies to your user account.

You target it using:

```bash
git config --global
```

Conceptually:

```text
Your User Account
 |
 +-- Project A
 |
 +-- Project B
 |
 +-- Project C
```

For most beginners, identity settings belong here.

For example:

```bash
git config --global user.name "Ann Felix"
```

This tells Git to use that name by default for repositories belonging to your user environment.

---

# 41. Local Configuration

Local configuration applies only to a specific Git repository.

Conceptually:

```text
Project A
 |
 +-- local Git configuration
```

Another repository can have different values:

```text
Project B
 |
 +-- different local Git configuration
```

Local settings are useful when different projects require different identities or behavior.

For example:

```text
Personal Project
user.email = personal@example.com

Work Project
user.email = engineer@company.com
```

The local configuration can override the global configuration for that repository.

---

# 42. Configuration Precedence

Suppose Git finds:

```text
System:
user.name = Default User
```

Then:

```text
Global:
user.name = Ann Felix
```

Then inside a specific repository:

```text
Local:
user.name = A. Felix
```

Inside that repository, the local value wins.

Conceptually:

```text
System
   |
   v
Global overrides System
   |
   v
Local overrides Global
```

The practical rule is:

**More specific configuration generally wins.**

---

# 43. Setting Your Git Username

Configure your global Git name:

```bash
git config --global user.name "Ann Felix"
```

Replace the example with the name you want associated with your commits.

Breakdown:

```text
git
```

runs Git.

```text
config
```

opens Git's configuration functionality.

```text
--global
```

means the setting applies to your user account.

```text
user.name
```

is the configuration key.

```text
"Ann Felix"
```

is the value.

Quotation marks are useful when the value contains spaces.

---

# 44. Git Username Is Not Necessarily Your GitHub Username

This causes beginner confusion.

Suppose your GitHub username is:

```text
ann-devops
```

Your Git configuration can still be:

```bash
git config --global user.name "Ann Felix"
```

`user.name` becomes author information attached to commits.

It does not need to match your GitHub account username.

---

# 45. Setting Your Git Email

Run:

```bash
git config --global user.email "ann@example.com"
```

Replace the example with the email identity you intend to use for your commits.

The official Git setup guidance recommends setting both `user.name` and `user.email` because commit metadata uses these values.

This matters later when working with GitHub because GitHub can associate commits with an account when commit email information matches appropriately configured account information.

---

# 46. Why Git Needs Your Identity

Imagine this project history:

```text
Commit A
Author: Ann

Commit B
Author: David

Commit C
Author: Maria
```

Git records authorship information with commits.

That lets teams understand who created a change.

This contributes to traceability.

For example:

```text
Commit
 |
 +-- Author
 |
 +-- Email
 |
 +-- Date
 |
 +-- Message
 |
 +-- Project Snapshot
```

Your identity is therefore more than cosmetic.

It becomes part of commit metadata.

# 49. Viewing Your Git Configuration

Output may resemble:


# 50. View Configuration With Its Origin

A particularly useful command is:

```bash

```

This helps identify where settings came from.

Output may resemble:

```text

file:/home/ann/.gitconfig    user.email=ann@example.com
```

This is extremely useful for troubleshooting configuration conflicts.

Instead of asking only:

> What value is Git using?

you can also investigate:

> Which configuration file supplied this value?

# 52. Understanding .gitconfig

Your global Git configuration is commonly stored in:

```text
~/.gitconfig
```

or, depending on the environment:

```text
~/.config/git/config
```

The official Git documentation recognizes both user-level locations.

The symbol:

```text
~
```

normally refers to your home directory.

On Linux, your home might be:

```text
/home/ann
```

On macOS:

```text
/Users/ann
```

On Windows Git environments, Git commonly maps your home to something resembling:

```text
C:\Users\Ann
```

Therefore:

```text
~/.gitconfig
```

means:

```text
your home directory
        |
        v
.gitconfig
```

---

# 53. What Does .gitconfig Look Like?

A simple configuration file might resemble:

```ini
[user]
    name = Ann Felix
    email = ann@example.com

[init]
    defaultBranch = main

[core]
    editor = code --wait
```

The file is divided into sections.

For example:

```ini
[user]
```

contains user identity settings.

```ini
[core]
```

contains core Git behavior.

You do not need to manually edit this file for most beginner configuration.

Using:

```bash
git config
```

is safer and easier.

---

# 54. Editing Git Configuration

Git configuration can be changed by running configuration commands again.

For example:

```bash
git config --global user.name "Ann Felix"
```

If the existing global `user.name` was:

```text
Anne Felix
```

the command updates it.

You can also open the configuration file in an editor, but beginners should generally prefer `git config` commands because they reduce syntax mistakes.

---

# 55. Removing a Configuration Setting

Sometimes you may need to remove a configuration key.

Example:

```bash
git config --global --unset user.name
```

This removes that configured global value.

Be careful.

Do not remove settings simply because you do not recognize them.

First understand what the setting controls.

# 56. Configuring the Default Branch

When a new Git repository is initialized, Git creates an initial branch name.

A common modern convention is:

```text
main
```

You can configure Git so new repositories start with:

```text
main
```

using:

```bash
git config --global init.defaultBranch main
```

Breakdown:

```text
init
```

relates to repository initialization.

```text
defaultBranch
```

controls the default initial branch name.

```text
main
```

is the value.

Then verify:

```bash
git config --global init.defaultBranch
```

Expected output:

```text

```

# 57. Why Configure main?

Historically, many Git repositories used:

```text
master
```

as the initial branch name.

Many modern platforms and organizations use:

```text
main
```

instead.

Configuring:

```bash
git config --global init.defaultBranch main
```

creates more predictable behavior for the repositories we will build in this series.

Remember:

This setting affects newly initialized repositories.

It does not automatically rename existing branches.

# 61. Understanding Line Endings

This section is important, particularly when teams use different operating systems.

A text file is made of characters.

Lines need markers indicating where one line ends and the next begins.

Different operating systems historically used different line-ending conventions.

Two common forms are:

```text
LF
```

and:

```text
CRLF
```

---

# 62. LF

LF means:

```text
Line Feed
```

Unix-like systems commonly use LF line endings.

This includes:

* Linux
* macOS

Conceptually:

```text
line 1<LF>
line 2<LF>
line 3<LF>
```

---

# 63. CRLF

CRLF means:

```text
Carriage Return + Line Feed
```

Windows commonly uses CRLF for text files.

Conceptually:

```text
line 1<CR><LF>
line 2<CR><LF>
line 3<CR><LF>
```

You normally do not see these characters in your editor.

They exist in how the text file represents line boundaries.

---

# 64. Why Line Endings Matter to Git

Imagine:

```text
Developer A
Windows
CRLF
```

and:

```text
Developer B
Linux
LF
```

If line-ending changes are handled poorly, Git may appear to show large file changes even though the meaningful text barely changed.

Example:

```text
100 lines removed
100 lines added
```

when the primary difference may be line-ending representation.

This creates noisy diffs and confusing reviews.

---

# 65. core.autocrlf

Git provides configuration related to line-ending conversion.

One commonly encountered setting is:

```text
core.autocrlf
```

Typical values include:

```text
true
input
false
```

Do not blindly change this setting in an existing professional repository.

A team may already have a defined line-ending strategy using repository configuration such as `.gitattributes`.

---

# 66. core.autocrlf on Windows

A common Windows configuration is:

```bash
git config --global core.autocrlf true
```

Conceptually, this allows Git to normalize line endings in repository history while checking files out with Windows-style line endings where applicable.

Think:

```text
Repository
     |
     | checkout
     v
Windows Working Directory
CRLF
```

and:

```text
Windows Working Directory
     |
     | commit path
     v
Normalized Repository Content
```

The exact behavior also depends on Git attributes and other settings.

---

# 67. core.autocrlf on Linux and macOS

A commonly used Unix-like configuration is:

```bash
git config --global core.autocrlf input
```

This helps convert CRLF to LF when appropriate during input to the repository while avoiding automatic conversion to CRLF during checkout.

Conceptually:

```text
CRLF input
   |
   v
Git normalization
   |
   v
LF repository content
```

while normal Unix working files remain LF.

---

# 68. Should You Always Set core.autocrlf?

Not automatically.

For a personal beginner practice environment, the common settings above can be reasonable.

In a professional project, first inspect the repository's conventions.

A project may use:

```text
.gitattributes
```

to explicitly define line-ending behavior.

Repository-specific rules can be more predictable than relying only on each developer's global configuration.

We will discuss `.gitattributes` and repository conventions later where appropriate.

The beginner rule is:

**Do not change line-ending settings in a team repository without understanding the repository's policy.**
