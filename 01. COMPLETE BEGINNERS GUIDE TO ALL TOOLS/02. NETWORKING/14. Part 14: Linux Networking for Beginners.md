# Part 14: Linux Networking for Beginners

## Use Linux as a Practical Networking Workstation and Server

Up to this point, you have learned the major networking concepts individually:

```text
IP addressing
Subnetting
ARP
Switching
VLANs
Routing
TCP and UDP
DNS
DHCP
NAT
HTTP and HTTPS
Firewalls
```

Now you need to operate those concepts on a real system.

Linux is one of the best environments for doing this because networking is visible from the command line. You can inspect an interface, determine its addresses, read its routes, inspect neighbor resolution, identify listening applications, test DNS, follow network paths, examine connection states, and troubleshoot failures without relying on a graphical interface.

The goal of this part is not:

> Memorize 30 Linux commands.

The goal is to develop a repeatable mental model:

```text
Application
    |
    v
Socket
    |
    v
Linux network stack
    |
    +--> DNS
    +--> Routing table
    +--> Neighbor table
    +--> Network interface
    |
    v
Network
```

When something fails, Linux gives you tools for inspecting every stage.

---

## 1. Linux as a Networked System

A Linux computer may act as:

```text
Desktop
Laptop
Server
Cloud VM
Router
Firewall
Container host
Kubernetes node
Load balancer
VPN gateway
DNS server
Web server
Database server
```

Regardless of its role, the basic networking model remains similar.

The Linux kernel maintains information about:

```text
Network interfaces
IP addresses
Routes
Neighbors
Sockets
Packet forwarding
Network statistics
```

User-space programs then interact with this networking stack.

---

## 2. The Linux Networking Mental Model

When a Linux application wants to communicate with another system:

```text
Application
    |
    v
Destination hostname?
    |
    +--> Resolve DNS if required
    |
    v
Destination IP
    |
    v
Routing decision
    |
    v
Choose interface
    |
    v
Choose next hop
    |
    v
Resolve local neighbor if required
    |
    v
Transmit packet
```

For a TCP application, there is also transport-layer behavior:

```text
Application
    |
    v
Socket
    |
    v
TCP connection
    |
    v
IP routing
    |
    v
Interface
```

Most Linux troubleshooting tools inspect one of these stages.

# Linux Network Interfaces

## 3. What Is a Network Interface?

A network interface is the Linux kernel's representation of a networking endpoint through which traffic can be sent or received.

Examples include:

```text
lo
eth0
eth1
ens5
ens33
enp0s3
wlan0
wlp2s0
```

There are also virtual interfaces such as:

```text
docker0
br0
veth...
tun0
wg0
bond0
eth0.10
```

These may represent:

```text
Container networking
Bridges
VPNs
VLANs
Bonded links
Virtual machines
```

---

## 4. Physical vs Virtual Interfaces

A physical Ethernet NIC may appear as:

```text
enp0s3
```

A virtual machine may expose:

```text
ens5
```

Docker might create:

```text
docker0
```

A VPN might create:

```text
tun0
```

Therefore:

```text
Interface in Linux
```

does not always mean:

```text
Physical Ethernet socket on the computer.
```

Linux networking makes extensive use of virtual interfaces.

# Loopback Interface

## 8. What Is `lo`?

Linux normally has a loopback interface:

```text
lo
```

Its familiar IPv4 address is:

```text
127.0.0.1
```

IPv6 commonly uses:

```text
::1
```

The loopback interface represents communication with the local system itself.

---

## 9. Why Loopback Matters

Suppose a web application listens on:

```text
127.0.0.1:8080
```

A local command may work:

```bash
curl http://127.0.0.1:8080
```

But another computer may not be able to connect.

Why?

Because:

```text
127.0.0.1
```

means:

```text
This computer itself.
```

It is not the server's externally reachable interface address.

---

## 10. `localhost`

The hostname:

```text
localhost
```

normally resolves to a loopback address.

You can test:

```bash
ping localhost
```

or:

```bash
getent hosts localhost
```

A common beginner mistake is using `localhost` when trying to reach another server.

If you SSH into Server A and run:

```bash
curl http://localhost:8080
```

you are testing Server A.

You are not testing your laptop.

```bash

```

```bash

```

```text

```


To focus on IPv4:

```bash

```

```bash

```

---

## 19. Reading an IPv4 Address

Suppose:

```text
inet 192.168.10.50/24
```

You should immediately interpret:

```text
Address:
192.168.10.50

Prefix:
/24

Network:
192.168.10.0/24
```

From your subnetting knowledge, you can determine whether another destination is local or remote.

---

## 20. Temporary IP Configuration

In a disposable lab, an IPv4 address can be added temporarily with a command such as:

```bash
sudo ip addr add 192.168.50.10/24 dev ens5
```

And removed with:

```bash
sudo ip addr del 192.168.50.10/24 dev ens5
```

These commands generally affect the running system rather than automatically creating persistent configuration.

Do **not** experiment with the active interface of a remote production server.

You can disconnect yourself.

# Routing

## 21. Why Linux Needs a Routing Table

Once Linux knows the destination IP, it must answer:

> Where should I send this packet?

The kernel consults its routing information.

Run:

```bash
ip route
```

---

# `ip route`

## 22. Example Routing Table

You might see:

```text
default via 192.168.1.1 dev eth0

192.168.1.0/24 dev eth0
    proto kernel
    scope link
    src 192.168.1.50
```

This tells us:

```text
Connected network:
192.168.1.0/24

Interface:
eth0

Local source:
192.168.1.50

Default gateway:
192.168.1.1
```

---

## 23. Connected Route

When Linux has:

```text
192.168.1.50/24
```

on an interface, it commonly creates a connected route for:

```text
192.168.1.0/24
```

Conceptually:

```text
192.168.1.0/24
        |
        v
Directly reachable through eth0
```

No router is needed to reach another host on that local subnet, assuming Layer 2 connectivity exists.

---

# Default Routes

## 24. What Is the Default Route?

Example:

```text
default via 192.168.1.1 dev eth0
```

means:

> If no more specific route matches the destination, send the packet to 192.168.1.1 through eth0.

Equivalent IPv4 CIDR:

```text
0.0.0.0/0
```

---

## 25. Missing Default Route

Suppose:

```bash
ip route
```

shows:

```text
192.168.1.0/24 dev eth0
```

but no default route.

The machine may successfully communicate with:

```text
192.168.1.20
```

but fail to reach:

```text
8.8.8.8
```

because it does not know where to send traffic for remote networks.

---

## 26. Inspect the Actual Routing Decision

One of the most useful Linux networking commands is:

```bash
ip route get 8.8.8.8
```

Example output might resemble:

```text
8.8.8.8 via 192.168.1.1 dev eth0 src 192.168.1.50
```

This answers:

```text
Destination?
8.8.8.8

Next hop?
192.168.1.1

Interface?
eth0

Source address?
192.168.1.50
```

This is often more useful than merely staring at the entire routing table.

---

## 27. Multiple Routes

Linux may have multiple routes.

Example:

```text
10.0.0.0/8 via 192.168.1.10
10.20.0.0/16 via 192.168.1.20
default via 192.168.1.1
```

For destination:

```text
10.20.30.40
```

the more specific `/16` route is preferred over `/8`.

This is longest prefix match.

# Neighbor Tables

## 28. `ip neigh`

After Linux determines that a next hop is locally reachable, it may need its Layer 2 address.

For IPv4 Ethernet, this involves ARP.

Run:

```bash
ip neigh
```

Example:

```text
192.168.1.1 dev eth0 lladdr aa:bb:cc:dd:ee:ff REACHABLE
```

Interpretation:

```text
Neighbor IP:
192.168.1.1

Interface:
eth0

MAC:
aa:bb:cc:dd:ee:ff

State:
REACHABLE
```

---

## 29. Neighbor States

You may encounter:

```text
REACHABLE
STALE
DELAY
PROBE
INCOMPLETE
FAILED
PERMANENT
```

Remember:

```text
STALE
```

does not automatically mean broken.

It means the mapping exists but reachability has not been recently confirmed.

---

## 30. Failed Neighbor Resolution

Suppose:

```text
192.168.1.1 dev eth0 FAILED
```

This can indicate Linux could not resolve or reach the local neighbor at Layer 2.

Possible causes:

```text
Wrong subnet
Wrong VLAN
Gateway unavailable
Interface problem
Layer 2 failure
Incorrect gateway
```

DNS is not the first thing to troubleshoot here.

# `ping`

## 34. What `ping` Does

`ping` commonly sends ICMP Echo Request messages and waits for Echo Replies.

Example:

```bash
ping 8.8.8.8
```

On Linux, it often continues until interrupted.

For a limited test:

```bash
ping -c 4 8.8.8.8
```

---

## 35. What Ping Can Tell You

Ping can help investigate:

```text
Basic IP reachability
Round-trip latency
Packet loss
DNS behavior when using names
```

Example:

```text
64 bytes from 8.8.8.8:
time=18.4 ms
```

---

## 36. What Ping Cannot Prove

Successful ping does **not** prove:

```text
Web server works
SSH works
Database works
Firewall allows TCP 443
Application is healthy
```

Likewise, failed ping does not prove the server is down.

ICMP may be filtered.

Always test the actual application protocol when possible.

---

## 37. A Better Ping Troubleshooting Sequence

Start locally:

```bash
ping -c 3 127.0.0.1
```

Then your own relevant interface address if useful.

Then:

```bash
ping -c 3 <default-gateway>
```

Then a remote IP:

```bash
ping -c 3 8.8.8.8
```

Then a hostname:

```bash
ping -c 3 example.com
```

This helps separate:

```text
Local stack
Local network
Routing
Internet reachability
DNS
```

# `traceroute`

## 38. What Traceroute Does

`traceroute` helps show the sequence of Layer 3 hops toward a destination.

Example:

```bash
traceroute example.com
```

Conceptually:

```text
Linux Host
   |
   v
Router 1
   |
   v
Router 2
   |
   v
Router 3
   |
   v
Destination
```

---

## 39. How Traceroute Works Conceptually

IP packets contain a TTL:

```text
Time To Live
```

Each router forwarding an IPv4 packet decrements the TTL.

Traceroute deliberately sends probes with progressively larger TTL values.

Simplified:

```text
TTL 1 -> Router 1
TTL 2 -> Router 2
TTL 3 -> Router 3
...
```

This helps reveal intermediate hops.

IPv6 has an analogous Hop Limit field.

---

## 40. `* * *` Does Not Necessarily Mean Broken

Traceroute may show:

```text
1  192.168.1.1
2  * * *
3  203.0.113.10
```

The missing response from hop 2 does not automatically mean packets stopped there.

The router may simply not respond to traceroute probes or responses may be filtered/rate-limited.

If later hops respond, traffic clearly continued.

## 47. Reading a Listener

Suppose:

```text
LISTEN 0 4096 0.0.0.0:22 0.0.0.0:*
```

This indicates an IPv4 TCP listener on:

```text
0.0.0.0:22
```

Conceptually, it is listening on all applicable IPv4 local interfaces.

---

## 48. Loopback-Only Listener

Compare:

```text
127.0.0.1:8080
```

with:

```text
0.0.0.0:8080
```

The first is loopback-only.

The second commonly listens on all IPv4 local addresses.

This distinction explains many:

> It works locally but not remotely.

problems.

---

## 49. Specific Address Binding

An application might listen on:

```text
10.0.1.25:8080
```

This means it is bound specifically to that local address.

If the machine has:

```text
10.0.1.25
10.0.2.25
```

the application may not accept connections arriving for:

```text
10.0.2.25:8080
```

depending on its socket configuration.

---

## 50. Established TCP Connections

Run:

```bash
ss -tn
```

You may see:

```text
ESTAB
```

connections.

Example concept:

```text
10.0.1.25:53124
       ->
203.0.113.20:443
```

This tells you which remote endpoint the local system is communicating with.

---

## 51. TCP States

You may encounter:

```text
LISTEN
ESTAB
SYN-SENT
SYN-RECV
TIME-WAIT
CLOSE-WAIT
```

These connect directly to what you learned about TCP.

For example, large numbers of:

```text
SYN-SENT
```

may suggest outgoing connection attempts are not completing.

Large numbers of:

```text
CLOSE-WAIT
```

can point toward application-side connection-closing behavior.

Do not diagnose solely from one state count, but use it as evidence.

# Linux DNS Configuration

## 67. `/etc/resolv.conf`

Traditionally, resolver configuration can be inspected with:

```bash
cat /etc/resolv.conf
```

You might see:

```text
nameserver 10.0.0.2
search internal.example
```

This indicates resolver-related configuration.

However, modern Linux DNS management can be more complex.

---

## 68. Do Not Assume `/etc/resolv.conf` Is Manually Managed

On modern systems, `/etc/resolv.conf` may be generated or managed by:

```text
NetworkManager
systemd-resolved
DHCP client
Cloud networking software
Other network management systems
```

You may see that it is a symbolic link.

Check:

```bash
ls -l /etc/resolv.conf
```

Do not blindly edit it.

Your changes may be overwritten.

---

## 69. systemd-resolved

On systems using `systemd-resolved`, useful inspection may include:

```bash
resolvectl status
```

This can show per-interface DNS information.

Depending on the system:

```text
Global DNS
Interface DNS
Search domains
Current resolver
```

may differ.

---

## 70. `/etc/hosts`

Linux also checks local host mappings according to its configured name-service behavior.

Inspect:

```bash
cat /etc/hosts
```

Example:

```text
127.0.0.1 localhost
10.0.1.20 app.internal.example
```

A local hosts-file entry can override or influence name resolution before DNS depending on the system's name-service configuration.

---

## 71. Why `/etc/hosts` Can Cause Confusion

DNS may correctly say:

```text
app.example.com -> 10.0.2.20
```

but `/etc/hosts` contains:

```text
10.0.1.20 app.example.com
```

An application using the normal system resolver may connect to:

```text
10.0.1.20
```

while:

```bash
dig app.example.com
```

shows:

```text
10.0.2.20
```

This apparent contradiction occurs because `dig` directly performs DNS queries, while normal application name resolution may follow the system's configured name-service order.

# `nc`

## 72. Netcat

`nc`, commonly called Netcat, is an extremely useful connectivity-testing utility.

Test a TCP port:

```bash
nc -vz example.com 443
```

Options vary slightly between implementations, but commonly:

```text
-v
verbose

-z
scan/connectivity mode without normal data transfer
```

# Telnet for Connectivity Testing

## 75. Why Telnet Still Appears in Troubleshooting

Telnet is an old remote terminal protocol and should not be used for secure remote administration across untrusted networks because it does not provide SSH-style encryption.

However, the `telnet` client has historically been used for simple TCP connectivity tests.

Example:

```bash
telnet example.com 80
```

This attempts a TCP connection to port 80.

---

## 76. Telnet Is Not the Preferred General Tool

For modern troubleshooting, prefer tools such as:

```text
nc
curl
openssl s_client
```

depending on the protocol.

For HTTPS, for example:

```bash
curl -v https://example.com
```

or:

```bash
openssl s_client -connect example.com:443
```

provides much more useful information than Telnet.

# Network Configuration Files

## 88. Linux Has No Single Universal Network Configuration File

This is important.

You may encounter:

```text
/etc/netplan/*.yaml
```

on some Ubuntu systems.

You may encounter NetworkManager connection profiles.

Older Debian/Ubuntu environments may use:

```text
/etc/network/interfaces
```

Other distributions and setups use different locations and tools.

Therefore never begin troubleshooting by blindly editing a file copied from an online tutorial.

---

## 89. Runtime State vs Persistent Configuration

This distinction is essential.

Commands such as:

```bash
ip addr
ip route
```

show the current kernel state.

Persistent configuration determines what should be recreated after:

```text
Reboot
Interface restart
Network service restart
```

You can have:

```text
Correct runtime state
but
Incorrect persistent configuration
```

or the reverse.

---

## 90. Example Runtime Change

A command such as:

```bash
sudo ip route add 10.50.0.0/16 via 192.168.1.1
```

can add a runtime route.

But after reboot, it may disappear unless configured through the system's persistent network-management mechanism.

This is why:

> It worked until the server rebooted.

is a common networking incident.

## 92. Multiple Default Routes


This can become important for:


Suppose:

```text

Gateway configured:
192.168.20.1
```

The gateway is not on the host's expected directly connected `/24`.

This is suspicious and, absent special configuration, will not work as a normal directly reachable gateway.

# Linux IP Forwarding

## 106. Host vs Router

Normal workstation:

```text
Network A
   |
Linux Host
```

Traffic is mainly:

```text
To Linux
or
From Linux
```

Router:

```text
Network A
   |
   v
Linux
   |
   v
Network B
```

Traffic also passes:

```text
Through Linux.
```

For Linux to act as an IPv4 router, IP forwarding must be enabled.

---

## 107. Check IPv4 Forwarding

Run:

```bash
sysctl net.ipv4.ip_forward
```

Possible output:

```text
net.ipv4.ip_forward = 0
```

means forwarding is disabled.

```text
net.ipv4.ip_forward = 1
```

means IPv4 forwarding is enabled.

---

## 108. Why Forwarding Matters

Suppose:

```text
Client
10.0.1.50
   |
   v
Linux Router
eth0: 10.0.1.1
eth1: 10.0.2.1
   |
   v
Server
10.0.2.50
```

Even with correct routes, if Linux forwarding is disabled:

```text
Client
   |
   v
Linux
   X
Server
```

the Linux system will not behave as the intended IPv4 router.

---

## 109. Forwarding Is Not Enough

Enabling IP forwarding does not automatically solve everything.

You may still need:

```text
Correct routes
Firewall FORWARD policy
Neighbor resolution
Return routes
NAT where appropriate
```

The complete path matters.

---

## 110. IPv6 Forwarding

IPv6 forwarding is controlled separately.

For example, inspection may involve:

```bash
sysctl net.ipv6.conf.all.forwarding
```

Do not assume enabling IPv4 forwarding automatically configures IPv6 routing.

# Common Linux Network Failures

## 111. Failure 1: Interface Down

Symptoms:

```text
No connectivity
No carrier
Expected address unavailable
```

Check:

```bash
ip link
```

If the interface is:

```text
DOWN
```

investigate why.

Do not immediately bring interfaces up on production systems without understanding the architecture.

---

## 112. Failure 2: No IP Address

Check:

```bash
ip addr
```

Expected interface exists but has no expected:

```text
inet ...
```

Possible causes:

```text
DHCP failure
Persistent configuration problem
NetworkManager issue
Interface not connected
Cloud configuration issue
```

---

## 113. Failure 3: Wrong IP Address

Expected:

```text
10.0.1.25/24
```

Actual:

```text
10.0.5.25/24
```

This can produce:

```text
Gateway failures
Wrong routing
Firewall mismatches
Application failures
```

Never assume the IP is correct.

Inspect it.

---

## 114. Failure 4: Wrong Prefix

Expected:

```text
10.0.1.50/24
```

Configured:

```text
10.0.1.50/16
```

Linux may incorrectly treat many remote destinations as directly connected.

For example:

```text
10.0.20.50
```

appears local under `/16`.

Linux may attempt neighbor resolution instead of sending the packet to the intended router.

---

## 115. Failure 5: No Default Route

Symptoms:

```text
Local subnet works
Remote networks fail
```

Check:

```bash
ip route
```

If no default route exists and no specific route covers the destination, Linux has nowhere appropriate to send the packet.

---

## 116. Failure 6: Wrong Default Gateway

Check:

```bash
ip route show default
```

Then:

```bash
ip route get 8.8.8.8
```

Confirm the selected gateway and interface.

---

## 117. Failure 7: Gateway Neighbor Resolution Fails

Check:

```bash
ip neigh
```

If the gateway appears:

```text
FAILED
```

investigate the local network first.

Possible causes:

```text
Wrong VLAN
Wrong subnet
Gateway unavailable
Layer 2 issue
Incorrect gateway
```

---

## 118. Failure 8: DNS Broken

Symptoms:

```text
ping 8.8.8.8
works

curl https://example.com
fails with name-resolution error
```

Investigate:

```bash
cat /etc/resolv.conf
```

and where appropriate:

```bash
resolvectl status
```

Then:

```bash
dig example.com
```

---

## 119. Failure 9: Wrong DNS Result

Application connects to the wrong server.

Compare:

```bash
dig app.example.com
```

with:

```bash
getent hosts app.example.com
```

Then inspect:

```bash
cat /etc/hosts
```

The normal system resolver and direct DNS queries may not always produce the same result.

---

## 120. Failure 10: Service Not Listening

Remote client reports:

```text
Connection refused
```

On server:

```bash
sudo ss -lntp
```

Expected port is absent.

This is primarily an application/listener issue, not a routing problem.

---

## 121. Failure 11: Service Bound to Loopback

Server shows:

```text
127.0.0.1:8080
```

Local:

```bash
curl http://127.0.0.1:8080
```

works.

Remote:

```text
Connection fails
```

The application is not listening on the external interface.

---

## 122. Failure 12: Firewall Blocks Traffic

Service is listening:

```text
0.0.0.0:443
```

Route is correct.

But remote connections time out.

Inspect applicable controls:

```bash
sudo nft list ruleset
```

and cloud/network firewalls where relevant.

Do not disable the firewall blindly.

---

## 123. Failure 13: Port Is Wrong

Application actually listens on:

```text
8080
```

Client attempts:

```text
80
```

Check:

```bash
sudo ss -lntp
```

Then test the correct port.

---

## 124. Failure 14: Multiple Interfaces Choose Unexpected Route

Server:

```text
eth0 -> 10.0.1.20
eth1 -> 10.0.2.20
```

Traffic unexpectedly leaves:

```text
eth1
```

Check:

```bash
ip route get <destination>
```

Do not guess which interface Linux selected.

Ask the kernel.

---

## 125. Failure 15: IPv6 Path Broken

Symptoms:

```bash
curl https://example.com
```

fails.

But:

```bash
curl -4 https://example.com
```

works.

Investigate:

```bash
ip -6 addr
ip -6 route
```

along with:

```text
AAAA records
IPv6 firewall
IPv6 gateway
Application binding
```

---

## 126. Failure 16: It Worked Until Reboot

This often indicates:

```text
Runtime configuration was changed
but
Persistent configuration was not.
```

For example:

```bash
sudo ip route add ...
```

worked temporarily.

After reboot:

```text
Route disappeared.
```

Determine the correct persistent configuration mechanism.

---

## 127. Failure 17: Configuration File Changed but Runtime Did Not

The reverse can happen.

You modify a persistent configuration file but the running kernel still uses the old state because the change has not been safely applied.

Therefore always distinguish:

```text
What configuration says should exist
```

from:

```text
What the kernel is actually using now.
```

Commands such as:

```bash
ip addr
ip route
ip link
```

show actual runtime state.

---

# A Linux Networking Troubleshooting Methodology

## 128. Start With the Failure Statement

Do not begin with:

```text
"The network is broken."
```

Define the failure precisely.

Example:

```text
Server 10.0.1.25 cannot establish
TCP 443 to api.example.com.
```

Now you have:

```text
Source
Destination
Protocol
Port
```

That is troubleshootable.

---

## 129. Step 1: Identify Interfaces

Run:

```bash
ip link
```

Ask:

```text
Which interfaces exist?

Which are UP?

Which appear operational?
```

---

## 130. Step 2: Inspect Addresses

Run:

```bash
ip addr
```

Ask:

```text
Does the expected interface have the expected IP?

Correct prefix?

IPv4?

IPv6?
```

---

## 131. Step 3: Inspect Routes

Run:

```bash
ip route
```

Then:

```bash
ip route get <destination-ip>
```

Ask:

```text
Which route?

Which gateway?

Which interface?

Which source address?
```

---

## 132. Step 4: Check the Next Hop

If traffic uses a local gateway:

```bash
ip neigh
```

Look for the gateway.

Ask:

```text
Resolved?

REACHABLE?

STALE?

FAILED?

INCOMPLETE?
```

---

## 133. Step 5: Test Local Network Reachability

Where appropriate:

```bash
ping -c 3 <gateway>
```

If the gateway cannot be reached, do not immediately investigate the remote website.

Your failure may be much closer.

---

## 134. Step 6: Test Remote IP Reachability

Example:

```bash
ping -c 3 8.8.8.8
```

If gateway works but remote IP does not, investigate:

```text
Routing
Upstream network
Firewall
NAT
Internet connectivity
```

Remember that ICMP filtering can affect this test.

---

## 135. Step 7: Test DNS Separately

Run:

```bash
dig example.com
```

or:

```bash
host example.com
```

Ask:

```text
Does the name resolve?

Which address?

Which resolver answered?

A or AAAA?
```

---

## 136. Step 8: Test the Actual Port

For TCP:

```bash
nc -vz example.com 443
```

This is more relevant to an HTTPS problem than ping alone.

---

## 137. Step 9: Test the Actual Application Protocol

For HTTPS:

```bash
curl -v https://example.com
```

Now observe:

```text
DNS
TCP
TLS
HTTP
```

---

## 138. Step 10: If You Own the Server, Inspect the Listener

On destination server:

```bash
sudo ss -lntp
```

Ask:

```text
Is the port listening?

Which address?

Which process?
```

---

## 139. Step 11: Inspect Firewall Policy

Where applicable:

```bash
sudo nft list ruleset
```

or:

```bash
sudo ufw status verbose
```

Then inspect cloud or network controls.

---

## 140. Step 12: Inspect Statistics

Run:

```bash
ip -s link
```

Look for rapidly increasing:

```text
Errors
Drops
```

if performance or packet loss is involved.

---

## 141. Step 13: Trace the Path

Use:

```bash
tracepath <destination>
```

or:

```bash
traceroute <destination>
```

when path information may help.

---

## 142. Step 14: Capture Packets When Needed

When basic inspection is insufficient, packet capture can show what actually happens.

Example:

```bash
sudo tcpdump -n -i any host <destination-ip>
```

For a specific TCP port:

```bash
sudo tcpdump -n -i any tcp port 443
```

Now ask:

```text
Does SYN leave?

Does SYN-ACK return?

Does DNS query leave?

Does DNS response return?

Which interface carries traffic?
```

Packet capture converts assumptions into evidence.

# Common Beginner Mistakes

## 185. Mistake: Assuming the Interface Is `eth0`

Always run:

```bash
ip link
```

Your interface might be:

```text
ens5
enp0s3
eno1
```

---

## 186. Mistake: Looking Only at the IP Address

This:

```text
10.0.1.20
```

is incomplete.

You also need:

```text
Prefix
Route
Gateway
Interface
```

---

## 187. Mistake: Assuming Ping Tests Everything

Ping tests ICMP behavior.

It does not prove:

```text
SSH
HTTPS
Database
DNS
```

works.

Test the actual service.

---

## 188. Mistake: Blaming DNS for Every Network Failure

Before DNS:

```bash
ip route get <destination-ip>
```

may reveal a routing problem.

Use IP-based tests to separate name resolution from basic connectivity.

---

## 189. Mistake: Editing `/etc/resolv.conf` Blindly

Modern Linux systems may regenerate this file.

First determine:

```text
Who manages DNS configuration?
```

---

## 190. Mistake: Treating `ip` Changes as Persistent

Commands such as:

```bash
ip addr add ...
ip route add ...
```

normally change runtime kernel state.

They may disappear after reboot.

---

## 191. Mistake: Restarting Networking Too Early

Restarting networking on a remote server can:

```text
Disconnect SSH
Change routes
Change DNS
Remove temporary addresses
Cause application interruption
```

Inspect before restarting.

---

## 192. Mistake: Disabling the Firewall to "Test"

Instead:

```text
Inspect rules
Check counters
Capture packets
Test exact ports
```

Do not create a security incident while troubleshooting a networking incident.

---

## 193. Mistake: Assuming `STALE` Neighbor Means Failure

`STALE` is a normal neighbor state.

More concerning states in the right context include:

```text
INCOMPLETE
FAILED
```

Even then, investigate rather than immediately deleting entries.

---

## 194. Mistake: Confusing Listener Problems With Firewall Problems

If:

```bash
ss -lntp
```

shows no application on port 443, opening port 443 in the firewall will not start the application.

Always verify the listener.

---

## 195. Mistake: Testing From Only One Side

When you control both systems, inspect both.

```text
Client
  |
  | SYN
  v
Network
  |
  v
Server
```

Client:

```bash
ip route get SERVER
nc -vz SERVER PORT
```

Server:

```bash
ss -lntp
tcpdump ...
```

The two perspectives can reveal exactly where communication stops.

# Final Linux Troubleshooting Challenge

## 199. Scenario

You administer this server:

```text
Application Server

Interface:
ens5

Expected IP:
10.20.30.50/24

Expected Gateway:
10.20.30.1

Application:
TCP 8080

Dependency:
api.example.com:443
```

Users report:

```text
"The application is running,
but it cannot reach the external API."
```

Do not restart networking.

Do not disable the firewall.

Do not edit DNS.

First gather evidence.

---

## 200. Inspect the Interface

Run:

```bash
ip link show ens5
```

Then:

```bash
ip addr show ens5
```

Suppose you find:

```text
ens5:
UP

IP:
10.20.30.50/24
```

Interface and address appear correct.

---

## 201. Inspect the Route

Run:

```bash
ip route
```

Output:

```text
10.20.30.0/24 dev ens5
```

But there is no:

```text
default via 10.20.30.1
```

Now ask Linux:

```bash
ip route get 8.8.8.8
```

It reports that no appropriate route exists.

You have found a major problem.

---

## 202. Why Local Services Still Work

Users may still reach the application from:

```text
10.20.30.0/24
```

because Linux has the connected route:

```text
10.20.30.0/24 dev ens5
```

But the external API is on a remote network.

Without a default or more specific route:

```text
Application
10.20.30.50
      |
      | Local subnet works
      |
      X Remote API
```

Linux does not know where to send unmatched remote traffic.

---

## 203. Root Cause

The server's expected default route is missing.

The application itself is not necessarily broken.

DNS is not necessarily broken.

TLS is not necessarily broken.

The external API is not necessarily down.

The failure occurs earlier:

```text
Application
    |
    v
TCP request
    |
    v
Destination IP
    |
    v
Linux routing lookup
    |
    X
No usable route
```

---

When a Linux network problem appears, work outward:

```text
1. What exactly failed?

        |
        v

2. Does the interface exist?
   ip link

        |
        v

3. Is the address correct?
   ip addr

        |
        v

4. What route exists?
   ip route

        |
        v

5. What route will Linux actually use?
   ip route get

        |
        v

6. Can it resolve the local next hop?
   ip neigh

        |
        v

7. Can basic IP connectivity work?
   ping

        |
        v

8. Does DNS work?
   dig / host / nslookup

        |
        v

9. Can the transport port connect?
   nc

        |
        v

10. Is the service listening?
    ss

        |
        v

11. Does the application protocol work?
    curl

        |
        v

12. What path does traffic take?
    tracepath / traceroute

        |
        v

13. Are interfaces showing errors?
    ip -s link / ethtool

        |
        v

14. What do packet captures show?
    tcpdump
```

The most important Linux networking habit is not memorizing commands.

It is learning to ask a precise question before running each command:

```text
ip link
"Does my interface exist and is it operational?"

ip addr
"Does this machine have the correct address?"

ip route
"Does Linux know where networks are?"

ip route get
"Where will this exact packet go?"

ip neigh
"Can Linux reach its local next hop?"

dig
"Can DNS resolve the name?"

ss
"Is the application actually listening?"

nc
"Can I establish transport-layer connectivity?"

curl
"Does the application protocol work?"

ip -s link
"Is the interface showing errors or drops?"
```

Once you learn to move through Linux networking in this order, the terminal stops looking like a collection of unrelated commands. It becomes a **network diagnostic workstation where every command answers a specific question about the packet's journey**.
