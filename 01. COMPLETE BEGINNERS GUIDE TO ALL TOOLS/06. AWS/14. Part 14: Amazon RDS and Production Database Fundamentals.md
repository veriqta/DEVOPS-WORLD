# 1. Start With the Database Problem

Imagine you have one EC2 instance.

You install:

```text
Linux
Nginx
Application
PostgreSQL
```

Everything runs on one server:

```text
EC2
 |
 +---- Nginx
 |
 +---- Application
 |
 +---- PostgreSQL
```

For a small experiment, this can work.

But now imagine the application becomes important.

Users create accounts.

They purchase products.

They upload information.

The database now contains valuable state.

Then your EC2 instance fails.

What happens?

Potentially:

```text
Application unavailable
+
Database unavailable
+
Data at risk
```

Your compute failure and database failure are now the same failure.

---

# 2. Why Putting the Database on the Application Server Creates Problems

Suppose:

```text
EC2 A
 |
 +---- Application
 |
 +---- MySQL
```

You now want to scale your application.

So you add another EC2 instance:

```text
          ALB
         /   \
        v     v
     EC2 A   EC2 B
```

Where does the database live?

If it remains on EC2 A:

```text
          ALB
         /   \
        v     v
     EC2 A   EC2 B
       |
       v
     MySQL
```

EC2 B depends on EC2 A.

If EC2 A disappears:

```text
EC2 A
  X
  |
Database
  X
```

both application servers lose access to the database.

You have created a major single point of failure.

---

# 3. Auto Scaling Makes This Even More Important

Remember the principle from Part 12:

Application EC2 instances should generally be replaceable.

An Auto Scaling Group might:

```text
Launch instance
      |
      v
Serve traffic
      |
      v
Detect failure
      |
      v
Terminate instance
      |
      v
Launch replacement
```

That is excellent for application servers.

It is dangerous if the only copy of your database lives inside one of those replaceable instances.

Imagine:

```text
Auto Scaling Group
       |
       +---- EC2 A
               |
               +---- Application
               |
               +---- Production Database
```

The Auto Scaling Group decides:

```text
EC2 A is unhealthy.
Terminate it.
```

You have mixed:

```text
Replaceable compute
```

with:

```text
Persistent state
```

Those should usually have different lifecycle models.

---

# 4. Separate Compute From Persistent State

A stronger architecture separates them.

Instead of:

```text
EC2
 |
 +---- Application
 |
 +---- Database
```

use:

```text
Application EC2
      |
      v
Database Tier
```

Now:

```text
Application servers
=
replaceable compute
```

while:

```text
Database
=
persistent application state
```

This separation becomes fundamental in production architecture.

# 5. Could You Run a Database on a Dedicated EC2 Instance?

Yes.

You could build:

```text
Application EC2
      |
      v
Database EC2
      |
      v
EBS
```

You could install PostgreSQL or MySQL yourself.

But then you become responsible for much more of the database infrastructure.

You may need to manage:

* Operating system
* Database installation
* Database configuration
* Patching
* Backups
* Backup testing
* Replication
* Failover
* Storage
* Monitoring
* Recovery
* High availability
* Database upgrades
* Security configuration

This is called a self-managed database model.

It provides control, but it also creates operational responsibility.

---

# 6. What Is a Managed Database?

A managed database service handles significant parts of the infrastructure required to operate a database.

Instead of:

```text
You
 |
 +---- Provision server
 +---- Install OS
 +---- Install database
 +---- Configure backups
 +---- Configure replication
 +---- Manage failover
 +---- Replace failed infrastructure
 +---- Patch underlying infrastructure
```

a managed service handles many of those infrastructure responsibilities.

You still remain responsible for important things such as:

* Database schema
* Queries
* Application behavior
* Credentials
* IAM configuration
* Network access
* Database users
* Data classification
* Performance decisions
* Backup requirements
* Retention decisions
* Engine configuration
* Application connection management

Managed does not mean:

```text
AWS does everything.
```

It means:

```text
AWS manages more of the underlying database infrastructure.
```

# 7. What Is Amazon RDS?

Amazon RDS stands for:

```text
Amazon Relational Database Service
```

RDS is AWS's managed relational database service.

It allows you to create and operate relational databases without manually building the entire database infrastructure yourself.

Conceptually:

```text
Application
    |
    v
Amazon RDS
    |
    v
Relational Database
```

---

# 8. What Is a Relational Database?

A relational database organizes structured data into tables.

Imagine:

```text
users
```

| id | name  | email                                         |
| -- | ----- | --------------------------------------------- |
| 1  | Ada   | [ada@example.com](mailto:ada@example.com)     |
| 2  | David | [david@example.com](mailto:david@example.com) |

Another table:

```text
courses
```

| id  | title              | price |
| --- | ------------------ | ----- |
| 101 | Linux Fundamentals | 20    |
| 102 | AWS Fundamentals   | 30    |

Another:

```text
enrollments
```

| user_id | course_id |
| ------- | --------- |
| 1       | 101       |
| 1       | 102       |
| 2       | 101       |

These tables can relate to each other.

That relationship is where the term:

```text
Relational database
```

comes from.

* Microsoft SQL Server

* Features

* Performance requirements

# 13. What Is Amazon Aurora?

Amazon Aurora is an AWS relational database engine designed for cloud environments.

Aurora is compatible with:

```text
MySQL
```

or:

```text
PostgreSQL
```

depending on the Aurora edition selected.

Applications designed for compatible MySQL or PostgreSQL environments can often work with Aurora, although compatibility should never be assumed blindly for every feature or extension.

Aurora has architecture and scaling characteristics that differ from standard RDS DB instances.

For this beginner part, understand Aurora exists, but focus primarily on core RDS concepts.

# 15. Do You SSH Into RDS?

Normally, no.

This is an important difference from EC2.

With EC2:

```text
Administrator
     |
     | SSH
     v
EC2
```

You manage the operating system.

With RDS:

```text
Administrator
     |
     | Database protocol
     v
RDS
```

You interact with the database engine.

For PostgreSQL, you may use:

```text
psql
```

For MySQL:

```text
mysql
```

You do not normally SSH into the underlying RDS host.

AWS manages that infrastructure.

# 17. DB Instance Classes

When creating an RDS DB instance, you select a DB instance class.

This determines compute and memory capacity available to the database.

Conceptually:

```text
DB Instance Class
       |
       +---- CPU
       |
       +---- Memory
       |
       +---- Network capability
```

Different families are designed for different workload characteristics.

---

# 18. Burstable DB Classes

Some smaller database instance classes use burstable performance models.

These may be appropriate for:

* Development
* Testing
* Small applications
* Workloads with variable CPU usage

But burstable instances rely on CPU credit mechanisms.

A production workload with sustained CPU demand may not be a good fit.

Do not select the smallest instance simply because it costs less.

---

# 19. General-Purpose DB Classes

General-purpose instance families provide a balance between:

```text
CPU
Memory
Networking
```

They can be appropriate for many common database workloads.

But database performance often depends heavily on memory.

Databases use memory for things such as:

* Caching
* Query execution
* Sorting
* Connection management

Always monitor real workload behavior.

---

# 20. Memory-Optimized DB Classes

Memory-optimized families provide larger memory capacity relative to compute.

These can be useful for:

* Large working datasets
* Memory-intensive queries
* High connection counts
* Cache-heavy workloads

But larger instances cost more.

Sizing should be based on measurements rather than guessing.

---

# 21. Database Storage

RDS databases also require storage.

Storage contains things such as:

```text
Database data
Indexes
Transaction logs
Temporary database data
```

depending on the engine and operation.

RDS supports different storage types and configuration options.

For many workloads, General Purpose SSD storage is a common choice.

Provisioned IOPS storage can be used where predictable higher I/O performance is required.

---

# 22. Storage Performance Matters

A database can have plenty of CPU but still perform badly because storage is overloaded.

Imagine:

```text
Application
     |
     v
Database CPU: 30%
Database Memory: Healthy
Storage I/O: Saturated
```

The database can still feel slow.

Database performance troubleshooting must consider:

* CPU
* Memory
* Storage IOPS
* Storage throughput
* Storage latency
* Connections
* Locks
* Queries

Never look at CPU alone.

---

# 23. Storage Capacity Matters

Suppose your database has:

```text
100 GB
```

of storage.

Over time:

```text
Users
Orders
Logs
Indexes
Database growth
```

consume more space.

If available storage becomes critically low, the database can experience serious problems.

Monitor:

```text
FreeStorageSpace
```

and understand the database's growth rate.

---

# 24. Storage Autoscaling

RDS can support storage autoscaling for supported configurations.

This allows storage capacity to increase when available storage becomes low, up to a configured maximum threshold.

But storage autoscaling should not replace monitoring.

You still need to know:

```text
Why is the database growing?
```

Maybe:

* Normal customer growth
* Excessive logs
* Unbounded audit tables
* Broken retention
* Unexpected data duplication

Automation can prevent immediate failure without fixing poor data-management practices.

RDS integrates with your VPC networking.

Conceptually:

```text
VPC
 |
 +---- Public Subnets
 |
 +---- Private App Subnets
 |
 +---- Private Database Subnets
```

A common production architecture places application servers in private application subnets and databases in private database subnets.

Example:

```text
Internet
   |
   v
ALB
   |
   v
Private App Subnets
   |
   v
Private Database Subnets
   |
   v

```

The database does not need to accept connections directly from the public internet.

# 26. Why Databases Should Usually Be Private

Ask:

```text
Who actually needs to connect to the production database?
```

Usually:

```text
Application
```

perhaps:

```text
Approved administrative systems
```

and:

```text
Controlled operational tools
```

The entire internet usually does not need direct access.

Therefore:

```text
Internet
   X
   |
   v
RDS
```

is preferable to:

```text
Internet
   |
   v
RDS
```

for most production application architectures.

# 27. Publicly Accessible Setting

When creating RDS, you encounter a setting related to public accessibility.

A beginner may think:

```text
My laptop needs to connect.
Therefore make the database public.
```

That is not a good default production decision.

For production:

```text
Publicly accessible = No
```

is commonly appropriate.

Administrative access can be designed through controlled paths such as:

* VPN
* Bastion architecture
* AWS Systems Manager-based workflows
* Private connectivity
* Controlled administrative hosts

The exact design depends on your environment.

---

# 28. Database Subnet Groups

RDS needs to know which subnets it may use.

This is handled through a:

```text
DB subnet group
```

A DB subnet group is a collection of subnets in your VPC that RDS can use for database placement.

For high availability, these should span multiple Availability Zones.

Example:

```text
DB Subnet Group
     |
     +---- Private DB Subnet A
     |
     +---- Private DB Subnet B
```

---

# 29. Example Multi-AZ Network

Suppose your VPC is:

```text
10.0.0.0/16
```

You create:

```text
Availability Zone A

Public Subnet A
10.0.1.0/24

Private App Subnet A
10.0.11.0/24

Private DB Subnet A
10.0.21.0/24
```

and:

```text
Availability Zone B

Public Subnet B
10.0.2.0/24

Private App Subnet B
10.0.12.0/24

Private DB Subnet B
10.0.22.0/24
```

Then:

```text
DB Subnet Group
 |
 +---- 10.0.21.0/24
 |
 +---- 10.0.22.0/24
```

This gives RDS subnet options across two Availability Zones.

# 31. Security Groups for RDS

Security Groups control network access to RDS.

Suppose you use PostgreSQL.

The database listens on:

```text
TCP 5432
```

A poor database Security Group rule would be:

```text
Type:
PostgreSQL

Port:
5432

Source:
0.0.0.0/0
```

That means:

```text
Allow PostgreSQL traffic from every IPv4 address
```

This is usually inappropriate for a production database.

# 34. The ALB Should Not Normally Connect to the Database

Do not configure:

```text
ALB SG
   |
   v
Database SG
```

unless the architecture has a very unusual reason.

The ALB communicates with the application.

The application communicates with the database.

Correct mental model:

```text
User
 |
 v
ALB
 |
 v
Application
 |
 v
Database
```

Each tier has a specific responsibility.

# 35. Database Endpoints

Applications need a hostname to connect to RDS.

RDS provides an endpoint.

It may look conceptually like:

```text
mydb.abc123xyz.us-east-1.rds.amazonaws.com
```

The exact value is generated by AWS.

Your application uses:

```text
DB_HOST=mydb.abc123xyz.us-east-1.rds.amazonaws.com
```

not a manually remembered database IP address.

---

# 36. Why You Should Use the Endpoint

Do not hardcode the database's underlying IP address.

RDS infrastructure can change.

Failover can move the database service to different underlying infrastructure.

The endpoint provides the stable logical connection name.

Think:

```text
Application
    |
    v
RDS DNS Endpoint
    |
    v
Current Database Infrastructure
```

---

# 37. DNS Resolution Matters

Because applications connect using an endpoint hostname, DNS becomes part of database connectivity.

The application must be able to resolve:

```text
mydb.abc123.rds.amazonaws.com
```

into the appropriate network address.

Therefore a database connection problem can sometimes actually be:

```text
DNS problem
```

rather than:

```text
Database problem
```

Always separate:

```text
Can hostname resolve?
```

from:

```text
Can TCP connection succeed?
```

from:

```text
Can database authentication succeed?
```

---

# 38. Test DNS Resolution

From an authorized application host:

```bash
getent hosts YOUR_RDS_ENDPOINT
```

or:

```bash
nslookup YOUR_RDS_ENDPOINT
```

or:

```bash
dig YOUR_RDS_ENDPOINT
```

depending on which tools are installed.

You are asking:

```text
Can this hostname resolve?
```

This does not prove the database port is reachable.

It only tests one layer.

---

# 39. Test TCP Connectivity

For PostgreSQL:

```bash
nc -vz YOUR_RDS_ENDPOINT 5432
```

For MySQL:

```bash
nc -vz YOUR_RDS_ENDPOINT 3306
```

`nc` means:

```text
netcat
```

Options:

```text
-v
=
verbose
```

```text
-z
=
scan/listening-port test without sending normal application data
```

A successful TCP test means the network path to the port is working.

It does not prove your username and password are correct.

# 40. Database Authentication Is a Separate Layer

Consider:

```text
DNS works
   |
   v
TCP connection works
   |
   v
Authentication fails
```

This means your Security Group may be fine.

The problem may instead involve:

* Username
* Password
* Database user
* Authentication configuration
* Database name
* TLS requirements
* IAM database authentication where used

Troubleshooting must identify the layer where failure occurs.

# 43. Database Credentials

Applications need credentials to authenticate to databases unless using another supported authentication mechanism.

A beginner may place:

```text
DB_PASSWORD=SuperSecretPassword
```

directly inside source code.

For example:

```python
password = "SuperSecretPassword"
```

This is dangerous.

The password may leak through:

* Git
* GitHub
* Build logs
* Container images
* Screenshots
* CI/CD systems
* Shared files

Secrets should not be hardcoded into application source code.

---

# 44. Environment Variables

A better separation is:

```text
Application code
       |
       v
Environment variable
       |
       v
DB_PASSWORD
```

But environment variables are not automatically secure simply because they are environment variables.

They still need to come from a secure source and be protected from inappropriate exposure.

---

# 45. AWS Secrets Manager

AWS Secrets Manager can store and manage secrets such as database credentials.

Conceptually:

```text
Secrets Manager
      |
      v
Database Secret
      |
      v
IAM-authorized Application
      |
      v
RDS
```

Instead of embedding credentials inside the application image, the application can retrieve an authorized secret at runtime.

---

# 46. IAM Access to Secrets

The EC2 application role should receive only the permissions it needs.

Conceptually:

```text
EC2
 |
 v
IAM Role
 |
 | permission
 v
Specific Secret
 |
 v
Database Credentials
```

Do not give:

```text
secretsmanager:*
Resource: *
```

unless there is a genuine administrative reason.

Use least privilege.

---

# 47. Credential Rotation

Passwords should not remain unchanged forever simply because changing them is inconvenient.

Secrets Manager can support credential rotation patterns for supported scenarios.

A production design should consider:

* Rotation frequency
* Application compatibility
* Connection behavior
* Rollback
* Failure handling
* Monitoring

Credential rotation should be tested.

---

# 48. IAM Database Authentication

For supported RDS engines and configurations, IAM database authentication can be used.

Instead of a long-lived database password, the client can use a short-lived authentication token generated through AWS IAM mechanisms.

Conceptually:

```text
Application
    |
    v
IAM identity
    |
    v
Temporary DB auth token
    |
    v
RDS
```

This can reduce reliance on long-lived database passwords for supported use cases.

However, IAM database authentication has requirements and limitations.

Do not adopt it without understanding the engine and workload.

# 49. Backups Are Not Optional Thinking

Imagine your production database contains:

```text
Users
Payments
Orders
Course progress
```

At 14:03, someone runs a destructive operation.

At 14:04, the application is broken.

You need to ask:

```text
Can we recover the database to before the mistake?
```

That is why database backup strategy matters.

---

# 50. Automated Backups

RDS supports automated backups.

When enabled with an appropriate retention period, RDS automatically creates backups and captures transaction logs needed for point-in-time recovery within the retention window.

Conceptually:

```text
Production Database
       |
       v
Automated Backups
       |
       v
Recovery Window
```

You configure a retention period according to your recovery requirements.

---

# 51. Backup Retention

Backup retention determines how long automated backups are retained.

Do not choose retention arbitrarily.

Ask:

```text
How far back might we need to recover?
```

For example:

```text
If corruption is discovered five days later,
do we still have a usable recovery point?
```

Retention is a business and technical requirement.

---

# 52. Point-in-Time Recovery

Point-in-time recovery allows you to restore the database to a specific point within the supported backup retention window.

Imagine:

```text
13:55 Database healthy
14:00 Bad deployment
14:02 Data corrupted
14:10 Problem discovered
```

You may need a recovery point such as:

```text
13:59
```

Conceptually:

```text
Automated backups
+
Transaction logs
        |
        v
Point-in-time restore
```

# 53. Restore Usually Creates Another DB Instance

A beginner may think:

```text
Restore
=
rewind current production database
```

That is not the usual RDS restore model.

Restoring from backup or snapshot generally creates a new DB instance or cluster, depending on the service/configuration.

Conceptually:

```text

     |
     X
Problem

Backup
  |
  v

  |
  v
New DB Instance
```

Then you validate the restored environment and decide how applications should transition to it.

# 54. Manual Snapshots

You can create manual DB snapshots.

Conceptually:

```text
RDS DB Instance
      |
      v
Manual Snapshot
```

A manual snapshot represents a backup you intentionally created.

This can be useful before:

* Major changes
* Migrations
* Engine upgrades
* Risky maintenance
* Environment cloning

But a snapshot should not replace a broader backup strategy.

# 55. Automated Backup vs Manual Snapshot

Simplified:


is managed according to the configured automated backup retention.


is created intentionally and retained until you delete it, subject to service behavior and account lifecycle.

Both can be useful.

They solve related but different operational needs.

For RDS, one important answer is:

# 61. What Is Multi-AZ?

A Multi-AZ RDS deployment provides database infrastructure across multiple Availability Zones for improved availability.

In the traditional Multi-AZ DB instance model, there is typically:

```text
Primary DB
   |
   v
Synchronous standby
```

located in another Availability Zone.

Conceptually:

```text
Availability Zone A
       |
       v
    Primary
       |
       | synchronous replication
       v
    Standby
       |
Availability Zone B
```

The standby exists for high availability.

---

# 62. What Happens During Failure?

Suppose:

```text
AZ A
 |
 v
Primary DB
 |
 X
Failure
```

RDS can fail over to standby infrastructure.

Conceptually:

```text
Before

Endpoint
   |
   v
Primary A
   |
   v
Standby B
```

After failover:

```text
Endpoint
   |
   v
New Primary B
```

The application continues using the database endpoint.

This is one reason you should connect using the RDS endpoint rather than hardcoding infrastructure IP addresses.

---

# 63. Failover Is Not Zero Downtime

Multi-AZ does not mean:

```text
No application ever notices anything.
```

During failover:

* Existing connections may break.
* New connections may temporarily fail.
* DNS resolution may need to reflect the new target.
* Applications may need to retry.
* Connection pools may contain stale connections.

Your application must be designed for transient database failures.

---

# 64. Application Retry Behavior

Suppose:

```text
Application
    |
    v
Database
```

and a failover occurs.

A fragile application does:

```text
Connection failed
      |
      v
Crash permanently
```

A more resilient application can:

```text
Connection failed
      |
      v
Wait appropriately
      |
      v
Retry with backoff
      |
      v
Reconnect
```

Retries must be carefully designed.

Blindly retrying every operation can create duplicate writes or overload a recovering database.

---

# 65. Multi-AZ Is for Availability

Remember:

```text
Multi-AZ
=
High availability
```

Its primary purpose is not:

```text
Read scaling
```

This distinction is extremely important.

---

# 66. What Is a Read Replica?

A read replica is a separate database copy designed primarily to receive read traffic.

Conceptually:

```text
Primary
   |
   +---- Writes
   |
   +---- Reads
   |
   v
Replication
   |
   v
Read Replica
   |
   +---- Reads
```

Applications can send appropriate read-only workloads to the replica.

---

# 67. Why Read Replicas Exist

Suppose the primary handles:

```text
INSERT
UPDATE
DELETE
SELECT
```

Traffic grows.

Most traffic is:

```text
SELECT
```

You may reduce read pressure by adding read replicas.

Architecture:

```text
                 Application
                 /         \
                v           v
           Write Path    Read Path
                |           |
                v           v
             Primary     Replica
```

This is read scaling.

---

# 68. Read Replicas May Lag

Read replicas generally use asynchronous replication.

That means the replica may temporarily be behind the primary.

Example:

```text
12:00:00
Write reaches primary

12:00:00.100
Application queries replica

Replica has not received change yet
```

The application may see stale data.

This is called:

```text
Replication lag
```

Your application architecture must tolerate it if reads are sent to replicas.

---

# 69. Multi-AZ vs Read Replica

This distinction must be clear.

| Feature             | Multi-AZ                                                                                  | Read Replica                                                |
| ------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Primary purpose     | High availability                                                                         | Read scaling                                                |
| Standby/read target | Depends on Multi-AZ architecture, traditional standby is not for normal application reads | Used for read workloads                                     |
| Replication model   | Designed for availability, traditional Multi-AZ uses synchronous replication              | Typically asynchronous                                      |
| Failover            | Managed HA capability                                                                     | Replica promotion can be part of recovery/scaling workflows |
| Read scaling        | Not the primary purpose                                                                   | Yes                                                         |

Do not say:

```text
I need more read capacity, so I will enable traditional Multi-AZ.
```

Use the feature that solves the actual problem.

---

These are different questions.

High availability asks:

```text

```

Read scaling asks:

```text
What happens if read traffic becomes too large?
```

Solutions may include:

```text
Multi-AZ
```

for availability.

And:

```text

```

for read scaling.

A production system may use both.

# 85. DatabaseConnections

One of the most important metrics is:

```text

```

Why?

Because databases have finite resources.

---

# 86. What Is Connection Exhaustion?

Imagine the database can safely handle a certain number of connections.

Your application has:

```text
20 EC2 instances
```

Each instance creates:

```text
100 database connections
```

Potential total:

```text
20 x 100 = 2,000 connections
```

The database may not be able to handle that.

Eventually applications see errors such as:

```text
too many connections
```

or connection timeouts.

---

# 87. Auto Scaling Can Accidentally Attack Your Database

This is an important production lesson.

Suppose:

```text
2 application instances
```

each maintains:

```text
50 DB connections
```

Total:

```text
100
```

Traffic increases.

Auto Scaling launches:

```text
18 more instances
```

Now:

```text
20 x 50 = 1,000
```

database connections.

Your application tier scaled successfully.

Your database may collapse.

Architecture:

```text
Traffic spike
     |
     v
ASG scales out
     |
     v
More EC2 instances
     |
     v
More DB connections
     |
     v
Database connection exhaustion
```

Scaling one tier can overload another.

# 88. Connection Pooling

Applications commonly use connection pools.

Instead of:

```text

Request 2 → Open DB connection → Close
Request 3 → Open DB connection → Close
```

the application maintains a controlled pool:

```text
Application
     |
     v
Connection Pool
 |
 +---- Connection 1
 +---- Connection 2
 +---- Connection 3
 +---- Connection 4
 |
 v
Database
```

Requests borrow connections and return them to the pool.

---

# 89. Pool Size Matters

A connection pool of:

```text

```

may still be disastrous.

Connection pooling is not simply:

```text
Use a pool.
Problem solved.
```

You must configure:

* Maximum pool size
* Minimum pool size
* Connection timeout
* Idle timeout
* Connection lifetime
* Retry behavior

and consider:

```text
Number of application instances
x
connections per instance
```

# 98. Step 1: Read the Exact Error

# 99. Unknown Host or DNS Failure

Problem:

```text
could not translate host name
```

or:

```text
Name or service not known
```

Possible causes:

* Wrong endpoint
* Typing error
* DNS problem
* VPC DNS configuration
* Application configuration error

Investigation:

```bash
getent hosts YOUR_RDS_ENDPOINT
```

Then:

```bash
nslookup YOUR_RDS_ENDPOINT
```

if available.

Fix the endpoint or DNS issue.

Do not modify the database password.

Authentication has not even started yet.

---

# 100. Connection Timeout

Problem:

```text
connection timed out
```

This often suggests the TCP connection cannot complete.

Possible causes:

* Security Group rule missing
* Wrong source Security Group
* NACL problem
* Wrong port
* Wrong endpoint
* Network path problem
* Database unavailable

Test:

```bash
nc -vz YOUR_RDS_ENDPOINT 5432
```

for PostgreSQL.

If it times out, investigate networking before credentials.

---

# 101. Connection Refused

Problem:

```text
connection refused
```

This can indicate that the destination was reached but nothing accepted the connection on that port, or another component actively rejected it.

Check:

* Correct port
* Correct endpoint
* Database status
* Engine configuration
* Whether you are connecting to the intended service

Do not assume `refused` and `timeout` mean the same thing.

---

# 102. Authentication Failure

Problem:

```text
password authentication failed
```

Network connectivity probably succeeded far enough to reach database authentication.

Check:

* Username
* Password
* Secret value
* Database user
* Authentication configuration
* Password rotation
* Application secret cache
* IAM authentication token if used

Do not start changing route tables.

The error has already told you the connection reached the authentication layer.

---

# 103. Wrong Database Name

You may successfully reach PostgreSQL but receive:

```text

```

This is not:

```text
Security Group problem
```

The database server responded.

Check:

```text
DB_NAME
```

in the application configuration.

# 104. Security Group Troubleshooting

Suppose:

```text
App EC2 SG:
sg-app
```

Database:

```text
sg-db
```

```text

Port: 5432
Source: sg-app
```

```text

```

The ALB does not initiate the database connection.

The application EC2 instance does.

The source should represent the application tier.

# 105. Security Group References Are Better Than IP Guessing

A beginner may inspect an EC2 private IP:

```text
10.0.11.25
```

then add:

```text

```

to the database Security Group.

But Auto Scaling may terminate that instance and launch:

```text

```

Now the rule breaks.

Using:

```text

```

ties authorization to the application role in the network architecture rather than a temporary instance IP.

# 106. NACL Troubleshooting

If Security Groups look correct but connections still fail, investigate Network ACLs.

Remember:

```text
Security Groups
=
Stateful
```

```text
Network ACLs
=
Stateless
```

A restrictive NACL must permit the required traffic in both directions, including appropriate ephemeral return-port behavior.

Do not modify NACLs blindly.

First determine whether custom restrictive NACLs are actually part of the environment.

# 107. Route Table Reasoning

Within a VPC, subnets normally have a local route for communication inside the VPC CIDR.

Example:

```text
Destination:
10.0.0.0/16

Target:
local
```

This allows routing between subnets inside the VPC, subject to Security Groups, NACLs, and resource behavior.

Your private app subnet does not need a NAT Gateway simply to communicate with an RDS instance in another subnet of the same VPC.

---

# 108. NAT Is Not Required for Normal Internal RDS Access

This architecture:

```text
Private EC2
     |
     v
RDS
```

inside the same VPC does not normally require:

```text
NAT Gateway
```

for the database connection.

The traffic stays within VPC networking.

NAT solves a different problem:

```text
Private resources initiating connections toward external/public destinations.
```

Do not mix the two concepts.
