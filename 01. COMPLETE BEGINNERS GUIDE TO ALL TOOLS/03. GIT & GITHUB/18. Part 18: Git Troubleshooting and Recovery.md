# Part 18: Git Troubleshooting and Recovery

Git problems often look more frightening than they really are.

A beginner may see:

```text
fatal: not a git repository
```

or:

```text
error: Your local changes would be overwritten by checkout
```

or:

```text
! [rejected] main -> main (non-fast-forward)
```

and immediately think:

```text
I broke Git.

My code is gone.

I need to delete the repository and clone it again.
```

Usually, that is the wrong reaction.

Git stores a large amount of information about your repository state and history. Many situations that look like lost work are recoverable if the work reached Git as a commit, staged object, branch reference, stash, or recent reflog entry.

The dangerous part is often not the original mistake.

The dangerous part is what happens next.

A confused engineer may start running commands such as:

```bash
git reset --hard
git clean -fd
git push --force
```

without understanding the current state.

That can turn a recoverable problem into real data loss.

This chapter teaches a different approach:

```text
Observe
   |
   v
Read the exact error
   |
   v
Inspect repository state
   |
   v
Understand what Git knows
   |
   v
Identify the problem
   |
   v
Choose the least-destructive fix
   |
   v
Verify
   |
   v
Prevent recurrence
```

This is not only a Git skill.

It is an engineering troubleshooting skill.

By the end of this part, you should be able to investigate problems involving:

* Wrong branches
* Wrong directories
* Detached HEAD
* Deleted commits
* Lost branches
* Reflog recovery
* Stuck merges
* Stuck rebases
* Checkout and switch failures
* Rejected pushes
* Non-fast-forward errors
* Unrelated histories
* Authentication failures
* Incorrect remote URLs
* Tracking-branch problems
* File permission changes
* Line-ending changes
* Accidentally committed secrets
* Large files
* Lost work
* Confusing repository states

Most importantly, you will learn how to avoid making the situation worse.

---

# 1. Git Troubleshooting Is State Troubleshooting

Git problems become easier when you stop thinking:

```text
Git is broken.
```

and start asking:

```text
What state is my repository currently in?
```

Remember the major Git states you have already learned:

```text
Working directory
       |
       v
Staging area
       |
       v
Local repository
       |
       v
Remote repository
```

You also have references such as:

```text
HEAD

main

feature/login

origin/main

tags

stash entries
```

A problem often comes from misunderstanding one of these states.

For example:

```text
Wrong file?
    Working-directory problem

Wrong staged content?
    Index problem

Missing commit?
    History/reference problem

Wrong branch?
    HEAD/branch problem

Push rejected?
    Local/remote history problem

Permission denied?
    Authentication/authorization problem

Wrong GitHub repository?
    Remote configuration problem
```

Troubleshooting begins by identifying the layer.

---

# 2. The Systematic Git Troubleshooting Method

Use this sequence whenever Git behaves unexpectedly.

## Step 1: Stop

Do not immediately run another destructive command.

Especially avoid guessing with:

```bash
git reset --hard
```

or:

```bash
git clean -fd
```

or:

```bash
git push --force
```

---

## Step 2: Read the exact error

Do not summarize the error in your head as:

```text
Git won't work.
```

Read the actual message.

Git often tells you:

```text
what failed

why it failed

what state exists

what command may be appropriate next
```

---

## Step 3: Check your location

Run:

```bash
pwd
```

On Windows PowerShell:

```powershell
Get-Location
```

Then inspect the directory:

```bash
ls -la
```

or the appropriate directory-listing command for your shell.

Ask:

```text
Am I inside the repository I think I am?
```

---

## Step 4: Run `git status`

This should become automatic:

```bash
git status
```

---

## Step 5: Check your branch

```bash
git branch --show-current
```

Also:

```bash
git branch
```

---

## Step 6: Inspect history

```bash
git log --oneline --graph --decorate --all
```

---

## Step 7: Inspect remotes when relevant

```bash
git remote -v
```

---

## Step 8: Fetch before diagnosing remote divergence

When the problem involves GitHub or another remote:

```bash
git fetch origin
```

Then inspect the graph again.

---

## Step 9: Use reflog if history appears lost

```bash
git reflog
```

---

## Step 10: Choose the least-destructive correction

Do not ask:

```text
What command will make the error disappear?
```

Ask:

```text
What is the safest command that corrects the actual cause
while preserving as much information as possible?
```

---

## Step 11: Verify

After the fix:

```bash
git status
```

Then inspect whatever is relevant:

```bash
git log --oneline --graph --decorate --all
```

or:

```bash
git diff
```

or:

```bash
git remote -v
```

or run your application's tests.

---

# 3. `git status` Is Your First Diagnostic Tool

If you remember only one troubleshooting command from this chapter, remember:

```bash
git status
```

`git status` compares important repository states and reports information including:

```text
Current branch

Staged changes

Unstaged changes

Untracked files

Merge conflicts

Rebase state

Cherry-pick state

Branch tracking information

Ahead/behind information when available
```

Git's official documentation describes `git status` as showing differences between `HEAD` and the index, differences between the index and working tree, and untracked files.

That makes it one of the most useful diagnostic commands in Git.

---

# 4. Read Status Before Trying to Fix Status

Suppose:

```bash
git status
```

says:

```text
On branch feature/login

Changes not staged for commit:
  modified: app.py
```

That tells you:

```text
Current branch:
feature/login

Working tree:
app.py changed

Index:
does not contain the latest app.py change
```

You now know what problem you are dealing with.

Compare that with:

```text
You are currently rebasing branch 'feature/login' on '...'
```

That is a completely different state.

The correct recovery command may also be completely different.

---

# 5. Reading Git Error Messages

Git messages usually contain clues.

Consider:

```text
fatal: not a git repository
```

Important words:

```text
not a git repository
```

Likely investigation:

```text
Am I in the correct directory?

Does this directory contain .git?

Am I above or outside the project?
```

---

Another example:

```text
error: Your local changes to the following files would be overwritten by checkout
```

Important phrase:

```text
local changes would be overwritten
```

Git is protecting your work.

This is not Git failing.

Git is refusing to destroy changes automatically.

---

Another:

```text
! [rejected] main -> main (non-fast-forward)
```

Important phrase:

```text
non-fast-forward
```

This suggests your local and remote histories are not in a state where Git can simply move the remote branch pointer forward to your local commit without discarding remote history.

Do not solve unrelated problems just because the word:

```text
error
```

appears.

Read the specific error.

---

# 6. Wrong Directory

One of the simplest Git mistakes is working in the wrong directory.

Suppose your structure is:

```text
~/projects/
    api-service/
        .git/
        app.py

    website/
        .git/
        index.html
```

You intend to work on:

```text
api-service
```

but your terminal is inside:

```text
website
```

You run:

```bash
git status
```

and see unexpected files.

Git is not confused.

You are inside a different repository.

---

# 7. Diagnose the Current Directory

Run:

```bash
pwd
```

Then:

```bash
git rev-parse --show-toplevel
```

The second command asks Git for the top-level directory of the current repository.

Example:

```text
/Users/ann/projects/api-service
```

This is extremely useful when you are inside a deep subdirectory such as:

```text
api-service/src/services/auth/
```

and want to know which repository owns your current location.

---

# 8. `fatal: not a git repository`

Suppose:

```bash
git status
```

returns:

```text
fatal: not a git repository (or any of the parent directories): .git
```

Possible causes:

```text
You are in the wrong directory.

The repository has not been initialized.

The .git directory was deleted.

You copied only project files, not Git metadata.

You are running Git outside the repository.
```

Start with:

```bash
pwd
ls -la
```

Then navigate to the expected project:

```bash
cd ~/projects/api-service
```

Then:

```bash
git status
```

Do not immediately run:

```bash
git init
```

inside a random directory.

You could accidentally create a new repository instead of finding the existing one.

---

# 9. Wrong Branch

You modify:

```text
deployment.yml
```

and commit.

Then you realize:

```text
I was supposed to make this change on feature/readiness-probe.

I committed it on main.
```

First:

```bash
git status
```

Then:

```bash
git branch --show-current
```

Then:

```bash
git log --oneline --decorate -5
```

Do not immediately reset.

First determine:

```text
Has the commit been pushed?

Does anyone else depend on it?

Is the working tree clean?

Is this only my local history?
```

---

# 10. Wrong Branch but Change Is Not Committed

Suppose you edited files on `main`, but you intended to work on:

```text
feature/metrics
```

and you have not committed yet.

First:

```bash
git status
git diff
```

You may be able to switch directly:

```bash
git switch feature/metrics
```

if Git determines the changes can safely move with you.

If switching would overwrite files, Git may block it.

Another option is to stash deliberately:

```bash
git stash push -m "Move metrics work to feature branch"
```

Then:

```bash
git switch feature/metrics
git stash apply
```

Verify:

```bash
git status
git diff
```

Do not blindly stash without understanding which files are tracked or untracked.

---

# 11. Wrong Branch and Commit Is Local

Suppose:

```text
main

A---B---C
        ^
        |
   accidental commit
```

You wanted C on:

```text
feature/metrics
```

If C has not been shared, one safe learning workflow is first preserve it:

```bash
git branch recovery-metrics C
```

Now the commit has another branch reference.

You can then deliberately place it where needed.

For example:

```bash
git switch feature/metrics
git cherry-pick C
```

Now verify.

Only after confirming the change exists safely where intended should you consider cleaning the accidental local `main` history.

This illustrates the recovery principle:

```text
Preserve first.

Clean second.
```

---

# 12. Detached HEAD

You run:

```bash
git switch --detach a83c192
```

or inspect an old tag/commit in a way that detaches HEAD.

Then:

```bash
git status
```

may report that HEAD is detached.

What does this mean?

Normally:

```text
HEAD
 |
 v
main
 |
 v
Commit C
```

HEAD points to a branch.

Detached:

```text
HEAD
 |
 v
Commit B
```

HEAD points directly to a commit instead of a local branch name.

This is called:

```text
detached HEAD
```

---

# 13. Detached HEAD Is Not Automatically an Error

Detached HEAD is useful for:

```text
Inspecting an old release

Testing an old commit

Debugging historical behavior

Temporarily examining a tag
```

The important issue is what happens if you start creating new commits.

Suppose:

```text
main

A---B---C
```

You detach at B:

```text
A---B---C
    ^
    |
   HEAD
```

Then create D:

```text
    D
   /
A---B---C
    ^
```

D exists.

But no normal branch necessarily points to D.

If you switch away without preserving it, D can become difficult to find later.

---

# 14. Saving Work From Detached HEAD

Suppose:

```bash
git status
```

shows detached HEAD.

You have created valuable commits.

Create a branch before leaving:

```bash
git switch -c recovered-experiment
```

Now:

```text
recovered-experiment
        |
        v
        D
       /
A---B---C
```

Your commit now has a branch reference.

This is one of the simplest detached-HEAD recoveries.

---

# 15. You Already Left Detached HEAD

Suppose you created commits while detached and then switched back to `main`.

Now you cannot see them in:

```bash
git log
```

Do not panic.

Run:

```bash
git reflog
```

Find the detached commit.

Inspect it:

```bash
git show <commit-id>
```

If correct, preserve it:

```bash
git branch recovered-detached-work <commit-id>
```

Then:

```bash
git switch recovered-detached-work
```

Verify:

```bash
git log --oneline
```

---

# 16. Accidentally Deleted Commits

Imagine:

```text
A---B---C---D
            ^
            |
           main
```

Then you accidentally run something that moves `main` backward:

```text
A---B
        ^
        |
       main

C---D appear gone
```

For example, perhaps you ran a reset to the wrong commit.

The commits may still exist in the local object database.

What disappeared was the branch reference pointing to them.

This is an important distinction:

```text
Commit object disappeared
```

is different from:

```text
Branch no longer points to commit
```

---

# 17. Do Not Immediately Create Lots of New History

When commits appear lost, reduce activity.

Do not start:

```text
resetting repeatedly

rebasing repeatedly

garbage collecting

deleting reflogs

running cleanup commands
```

First:

```bash
git reflog
```

The reflog is one of Git's most important local recovery tools.

---

# 18. What Is `git reflog`?

Reflog means:

```text
reference log
```

Git records movements of references in your local repository.

For example, reflog can record events such as:

```text
commit

checkout/switch

reset

rebase

merge

branch movements
```

The HEAD reflog also records recent HEAD movement.

Think of:

```bash
git log
```

as asking:

```text
What commit history is reachable from this branch?
```

and:

```bash
git reflog
```

as asking something closer to:

```text
Where has this local reference recently been?
```

These are different questions.

---

# 19. `git log` vs `git reflog`

Suppose branch now says:

```text
A---B
    ^
   main
```

But before an accidental reset:

```text
A---B---C---D
            ^
           main
```

`git log` from `main` may show only:

```text
B
A
```

But:

```bash
git reflog
```

may still show something like:

```text
12ab345 HEAD@{0}: reset: moving to HEAD~2
89cd012 HEAD@{1}: commit: Add monitoring dashboard
74ef901 HEAD@{2}: commit: Configure Prometheus scrape job
```

Those entries give you clues to the old commits.

---

# 20. Understanding `HEAD@{1}`

Reflog syntax can include:

```text
HEAD@{0}

HEAD@{1}

HEAD@{2}
```

Conceptually:

```text
HEAD@{0}
    Current/recent HEAD position

HEAD@{1}
    Previous recorded HEAD position

HEAD@{2}
    Earlier recorded position
```

Do not memorize a number and assume it will remain stable forever.

Inspect the reflog and identify the commit by its ID and context.

---

# 21. Recovering a Commit With Reflog

Suppose:

```bash
git reflog
```

shows:

```text
83ac921 HEAD@{1}: commit: Add readiness probe
```

Inspect:

```bash
git show 83ac921
```

Ask:

```text
Is this really the missing work?

Which files changed?

Is the commit complete?
```

If yes, preserve it:

```bash
git branch recovered-readiness 83ac921
```

Now:

```bash
git switch recovered-readiness
```

Verify:

```bash
git status
git log --oneline
```

This is safer than immediately moving `main`.

---

# 22. Why Create a Recovery Branch First?

Suppose you find:

```text
83ac921
```

You could immediately reset something to it.

But a safer approach is often:

```bash
git branch recovered-work 83ac921
```

Why?

Because now the commit has a clear named reference.

You have preserved evidence.

You can inspect and compare without immediately changing your main branch.

Recovery principle:

```text
Find
 |
 v
Inspect
 |
 v
Preserve
 |
 v
Verify
 |
 v
Integrate
```

---

# 23. Reflog Is Local

This is important.

Your reflog belongs to your local repository.

It is not a shared GitHub recovery log.

If Developer A accidentally loses a commit locally, Developer B's reflog does not automatically contain Developer A's local reference history.

Similarly, deleting your repository directory and recloning creates a new local repository and does not magically restore the old clone's reflog.

Do not treat reflog as a cloud backup.

---

# 24. Reflog Is Not Permanent Backup

Reflog entries can expire, and unreachable objects can eventually be pruned.

Therefore:

```text
reflog
```

is a recovery mechanism, not a backup strategy.

Important work should become:

```text
meaningful commits

branches/tags where appropriate

pushed remote history

proper backups when needed
```

---

# 25. Lost Branch

Suppose:

```text
feature/payment
```

was accidentally deleted.

You run:

```bash
git branch
```

and it is gone.

Do not assume the commits vanished.

A branch is a reference.

If its commits still exist, you may be able to recreate the branch.

Run:

```bash
git reflog
```

Find a commit that was at or near the branch tip.

Inspect:

```bash
git show <commit-id>
```

Then recreate:

```bash
git branch feature/payment-recovered <commit-id>
```

Verify:

```bash
git log --oneline feature/payment-recovered
```

---

# 26. Local Branch Gone but Remote Branch Exists

This is easier.

Suppose:

```bash
git branch
```

does not show:

```text
feature/payment
```

but:

```bash
git branch -r
```

shows:

```text
origin/feature/payment
```

Create a local tracking branch:

```bash
git switch --track origin/feature/payment
```

Depending on naming and Git state, Git can create the corresponding local branch.

Verify:

```bash
git branch -vv
```

---

# 27. Merge Stuck in Progress

You run:

```bash
git merge feature/metrics
```

Git reports conflicts.

You edit one file, become confused, close the terminal, and return the next day.

Now:

```bash
git status
```

may tell you that a merge is still in progress.

This is not a new unrelated problem.

The previous merge never finished.

---

# 28. Diagnose an In-Progress Merge

Run:

```bash
git status
```

Look for:

```text
unmerged paths
```

or messages indicating a merge is in progress.

Then inspect conflicted files.

You may also use:

```bash
git diff
```

to inspect unresolved conflict areas.

Do not start another merge on top of an unfinished merge.

---

# 29. Finish the Merge

For each conflicted file:

1. Open it.
2. Understand both versions.
3. Decide correct final content.
4. Remove conflict markers.
5. Test or validate the result.
6. Stage the resolved file.

Example:

```bash
git add config.yml
```

Then:

```bash
git status
```

When all conflicts are resolved, complete the merge:

```bash
git commit
```

or use the completion command appropriate to the workflow.

Then verify:

```bash
git status
git log --oneline --graph --decorate --all
```

---

# 30. Abort the Merge

If you decide:

```text
This merge should not be happening.
```

use:

```bash
git merge --abort
```

This is generally preferable to improvising with:

```bash
git reset --hard
```

during a merge you no longer want.

Important: Git documentation warns that reconstructing the original state can be harder if you started the merge with complicated uncommitted changes.

That is one reason a clean working tree before merging is such a strong practice.

---

# 31. Rebase Stuck in Progress

A rebase can also remain unfinished.

You may run:

```bash
git rebase origin/main
```

Git stops on a conflict.

The next day you run another Git command and see messages about a rebase already being in progress.

First:

```bash
git status
```

Do not restart the rebase.

---

# 32. Understand Rebase State

During a rebase, Git is replaying commits sequentially.

Conceptually:

```text
Original feature commits:

D---E---F

Replay:

D'
 |
 v
E'
 |
 v
F'
```

If E conflicts:

```text
D' created

E' paused

F' not replayed yet
```

The rebase is waiting for your decision.

---

# 33. Continue the Rebase

Resolve the conflicted file.

Then:

```bash
git add <resolved-file>
```

Check:

```bash
git status
```

Then:

```bash
git rebase --continue
```

Git resumes replaying remaining commits.

You may encounter another conflict later.

That does not mean the first resolution failed.

---

# 34. Abort the Rebase

If you determine:

```text
Wrong branch

Wrong base

Too many unexpected conflicts

I no longer understand the intended result
```

use:

```bash
git rebase --abort
```

Then:

```bash
git status
```

and inspect your history.

Do not blindly mix reset commands into an in-progress rebase.

---

# 35. Rebase Recovery With Reflog

Suppose a rebase completed, but afterward you realize:

```text
I rebased the wrong commits.
```

Run:

```bash
git reflog
```

The reflog may show the previous branch position.

Inspect candidate commits:

```bash
git show <commit-id>
```

Preserve the old position:

```bash
git branch before-bad-rebase <commit-id>
```

Now compare safely.

This is one reason reflog knowledge is so valuable when learning rebase.

---

# 36. Uncommitted Changes Blocking Checkout or Switch

Suppose:

```bash
git switch main
```

returns an error indicating local changes would be overwritten.

Git is protecting you.

Imagine:

```text
feature branch working tree:

config.yml
TIMEOUT=45
```

but `main` contains a different version of the same file.

Switching could overwrite your uncommitted change.

Git refuses.

That is safer than silently deleting your work.

---

# 37. Four Questions Before Fixing a Blocked Switch

Ask:

```text
Do I want to keep these changes?

Are they ready to commit?

Are they unfinished?

Do I want to discard them?
```

The correct action depends on your answer.

---

# 38. Option 1: Commit the Work

If the changes belong to the current branch and are ready:

```bash
git status
git diff
git add <files>
git diff --staged
git commit -m "Describe the change"
git switch main
```

This preserves the work as history.

---

# 39. Option 2: Stash the Work

If the work is unfinished:

```bash
git status
git diff
git stash push -m "WIP before switching branches"
git switch main
```

Later:

```bash
git switch feature/my-work
git stash list
git stash apply
```

---

# 40. Option 3: Discard the Work

Only if you are certain the changes are unwanted:

```bash
git diff
```

Inspect first.

Then for a tracked file:

```bash
git restore <file>
```

Warning:

This can destroy unstaged working-tree changes.

Do not use restore merely to make an error disappear.

---

# 41. Push Rejected

You commit locally:

```text
A---B---C
        ^
       main
```

You run:

```bash
git push origin main
```

and Git rejects it.

There are many possible causes:

```text
Remote contains commits you do not have

Authentication failed

You lack permission

Branch protection blocks the push

Remote URL is wrong

Repository does not exist

Large file rejected

Secret scanning/push protection blocked it

History was rewritten
```

Therefore:

```text
push rejected
```

is not one diagnosis.

Read the exact message.

---

# 42. Non-Fast-Forward Error

A common rejected push looks like:

```text
! [rejected] main -> main (non-fast-forward)
```

Imagine your local history:

```text
A---B---C
        ^
       main
```

Remote:

```text
A---B---D
        ^
   origin/main
```

Your push asks the remote to move from D to C.

But C does not contain D.

Doing so could discard remote history.

Git rejects the update.

That rejection protects history.

---

# 43. Why Non-Fast-Forward Happens

Common causes:

```text
Another developer pushed first

You edited through GitHub

You are working from an outdated local branch

A CI/bot updated the branch

History was rewritten

You rebased a branch that already existed remotely
```

Do not assume:

```text
GitHub is broken.
```

---

# 44. Safe Non-Fast-Forward Investigation

First:

```bash
git status
```

Then:

```bash
git fetch origin
```

Then:

```bash
git log --oneline --graph --decorate --all
```

Now inspect:

```bash
git log HEAD..origin/main --oneline
```

This shows commits known on `origin/main` but not reachable from your current `HEAD`.

Then:

```bash
git log origin/main..HEAD --oneline
```

This shows your local-only commits relative to that remote-tracking branch.

Now you understand the divergence.

---

# 45. Integrating Remote Changes

If your team uses merge-based synchronization:

```bash
git merge origin/main
```

Resolve conflicts if needed.

Test.

Then:

```bash
git push origin main
```

If your team uses rebase-based synchronization, the workflow may instead involve rebasing your local commits.

Do not choose merge or rebase randomly.

Follow project policy and understand the history.

---

# 46. Never Treat Force Push as the Default Fix

A beginner sees:

```text
non-fast-forward
```

searches online, and finds:

```bash
git push --force
```

This can overwrite remote history.

Do not use force push as an error-suppression command.

Before any history-rewriting push, determine:

```text
Why did the histories diverge?

Whose commits exist remotely?

Is this my private feature branch?

Has anyone else based work on it?

Does team policy allow rewriting?

Is the branch protected?
```

---

# 47. Unrelated Histories

You may encounter:

```text
fatal: refusing to merge unrelated histories
```

This often happens when two histories were created independently.

Example:

Local repository:

```text
A---B---C
```

GitHub repository was separately initialized:

```text
X---Y
```

There is no common ancestor.

Git sees:

```text
A---B---C

X---Y
```

rather than:

```text
A---B---C---D
```

---

# 48. How Beginners Commonly Create Unrelated Histories

Example:

You create local project:

```bash
git init
git add .
git commit -m "Initial local project"
```

Then you create a GitHub repository and initialize it separately with:

```text
README

LICENSE

.gitignore
```

GitHub creates its own initial commit.

Now you have two roots.

This is why Part 10 recommended creating an empty GitHub repository when connecting an existing local repository.

---

# 49. Do Not Blindly Use `--allow-unrelated-histories`

Git provides an option that can allow merging unrelated histories.

But the existence of an option does not mean you should immediately use it.

First ask:

```text
Why are these histories unrelated?

Did I connect the wrong repository?

Did I accidentally initialize twice?

Is the remote URL wrong?

Do these projects actually belong together?
```

If they genuinely represent the same project and you intentionally want to combine them, then an unrelated-history merge may be appropriate.

But understand the reason first.

Possible:

```text
No repository permission
```

# 52. HTTPS Troubleshooting Workflow

Start:

```bash
git remote -v
```

Confirm the repository.

Then determine:

```text
Is the repository public or private?

Do I have write permission?

Which GitHub account is my credential helper using?

Has the token expired?
```

# 53. SSH Authentication Failure

A common error:

```text
Permission denied (publickey).
```

This does not automatically mean:

```text
The repository is gone.
```

It means SSH authentication did not succeed with an accepted key.

Start:

```bash
git remote -v
```

If using SSH, test GitHub authentication:

```bash
ssh -T git@github.com
```

Then inspect local keys:

```bash
ls -la ~/.ssh
```

Then:

```bash
ssh-add -l
```

if using an SSH agent.

---

# 54. Systematic `Permission denied (publickey)` Investigation

Check:

```text
1. Is the remote actually SSH?

2. Does the private key exist?

3. Is the corresponding public key added to the correct GitHub account?

4. Is the SSH agent running?

5. Is the key loaded?

6. Are private-key permissions appropriate?

7. Is SSH offering the expected key?

8. Are you authenticated as the correct GitHub account?

9. Do you have permission to the repository?
```

For deeper debugging:

```bash
ssh -vT git@github.com
```

The `-v` enables verbose SSH diagnostics.

Read the output rather than randomly regenerating keys.

# 56. Fixing a Remote URL

```bash
git remote set-url origin <correct-url>
```

```bash

```

```bash

```


# 58. Tracking-Branch Problems

You create:

```text
feature/metrics
```

and commit.

Then:

```bash
git push
```

returns an error indicating the current branch has no upstream branch.

Why?

Git does not yet know which remote branch this local branch should normally correspond to.

You can publish and set upstream:

```bash
git push -u origin feature/metrics
```

`-u` means:

```text
--set-upstream
```

Now future:

```bash
git push
```

and:

```bash
git pull
```

have a configured branch relationship to use.

# 59. Inspect Tracking Relationships

```bash
git branch -vv
```

Example:

```text

  main            61bd820 [origin/main] Update README
```

This shows local branches and their upstream information.

Also:

```bash
git status
```

may report:

```text
Your branch is ahead of 'origin/main' by 1 commit.
```

or:

```text

```

or:

```text
Your branch and 'origin/main' have diverged...
```

# 60. Upstream Is Not the Same as Remote

These concepts are related but different.

Remote:

```text
origin
```

is a named repository connection.

Upstream branch:

```text
origin/main
```

may be configured as the branch your local `main` normally tracks.

Think:

```text
origin
    Remote repository nickname

origin/main
    Remote-tracking reference

main -> origin/main
    Possible tracking relationship
```

# 61. File Permission Problems

Git can track an important permission-related property:

```text
the executable bit
```

Suppose:

```bash
git status
```

shows a shell script modified.

But:

```bash
git diff
```

appears to show only something like:

```text
old mode 100644
new mode 100755
```

The file content may be unchanged.

The executable permission changed.

---

# 62. Why File Modes Matter

For a script:

```text
deploy.sh
```

these permissions are operationally different:

```text
-rw-r--r--
```

versus:

```text
-rwxr-xr-x
```

The second is executable.

This matters for:

```text
deployment scripts

CI scripts

entrypoint scripts

automation tools
```

A permission change may be intentional.

Do not automatically suppress it.

---

# 63. Inspect Permission Changes

Run:

```bash
git diff --summary
```

or:

```bash
git diff
```

You may see mode changes.

Also inspect:

```bash
ls -l deploy.sh
```

Ask:

```text
Should this file be executable?
```

If yes, the permission change may be correct.

If no, correct the filesystem permission appropriately.

---

# 64. `core.fileMode`

Git has configuration:

```bash
git config core.fileMode
```

This determines whether Git honors executable-bit differences in the working tree.

On filesystems or environments where executable-bit reporting is unreliable, Git may configure this differently.

Do not automatically set:

```bash
git config core.fileMode false
```

just to hide a change.

First determine whether the executable bit is operationally meaningful.

---

# 65. Permission Problems vs Ownership Problems

Git file-mode tracking is not the same as full Unix ownership tracking.

Git does not normally version:

```text
user owner

group owner

all Unix permission bits
```

as a full filesystem backup would.

If a deployment fails with:

```text
Permission denied
```

you may need operating-system troubleshooting:

```bash
ls -l
id
whoami
```

and possibly directory/ownership analysis.

Do not assume every OS permission problem is a Git problem.

---

# 66. Line-Ending Problems

Two common text line endings are:

```text
LF
```

and:

```text
CRLF
```

Commonly:

```text
Linux/macOS:
LF

Windows:
often CRLF
```

Mixed development environments can cause confusing diffs.

A file may appear changed across many lines even though the visible text looks nearly identical.

---

# 67. Why Line Endings Cause Git Noise

Imagine repository stores:

```text
LF
```

but an editor rewrites the file as:

```text
CRLF
```

Git may detect widespread changes.

This can create:

```text
Huge diffs

Merge conflicts

Noisy pull requests

Scripts failing on Linux

Confusing blame/history
```

---

# 68. Inspect Line-Ending Configuration

Run:

```bash
git config --show-origin --get core.autocrlf
```

Possible values include:

```text
true

input

false
```

At a high level:

```text
true
    Common Windows-oriented behavior:
    checkout can use CRLF while repository normalization uses LF.

input
    Converts CRLF toward LF when adding,
    without converting LF to CRLF on checkout.

false
    No core.autocrlf conversion behavior.
```

Do not change this randomly across a team.

---

# 69. `.gitattributes`

For team repositories, line-ending rules can be defined in the repository using:

```text
.gitattributes
```

Example:

```text
* text=auto
```

You may also define explicit rules such as:

```text
*.sh text eol=lf
*.bat text eol=crlf
```

This makes repository expectations clearer across operating systems.

Before renormalizing a mature repository, coordinate with the team because line-ending changes can create large diffs.

---

# 70. Shell Scripts and Line Endings

A shell script created with inappropriate CRLF endings may produce strange Linux errors.

For example, an interpreter line:

```bash
#!/bin/bash
```

may effectively contain an unexpected carriage-return character.

Symptoms can look unrelated to Git.

Therefore when a script works on one operating system but fails unexpectedly on Linux, investigate:

```text
permissions

line endings

interpreter path
```

not only the script logic.

---

# 71. Accidentally Committed Secrets

This is one of the highest-priority Git incidents.

Examples:

```text
AWS access key

GitHub token

database password

private SSH key

API key

cloud service credential

.env containing production secrets

TLS private key
```

Suppose you commit:

```text
.env
```

containing:

```text
DATABASE_PASSWORD=...
API_KEY=...
```

Then push it.

Removing the file in the next commit does not make the secret safe.

Why?

Because the earlier commit may still contain it.

---

# 72. First Action: Revoke or Rotate the Secret

If a real credential has been committed or pushed, assume exposure.

Priority:

```text
1. Revoke or rotate credential.

2. Replace it where the application legitimately needs it.

3. Investigate exposure.

4. Remove sensitive material from current files.

5. Decide whether history cleanup is required.

6. Coordinate history rewriting if necessary.

7. Prevent recurrence.
```

Do not make history rewriting your first security response while the credential remains valid.

The credential itself must be invalidated.

---

# 73. Why Deleting the File Is Not Enough

History:

```text
A---B---C
    ^
    |
Secret introduced
```

At C you delete:

```text
.env
```

History becomes:

```text
A---B---C
    ^   ^
    |   |
 secret deleted now
```

Commit B may still contain the secret.

Someone able to inspect history may still retrieve it.

---

# 74. If the Secret Was Only Staged

Suppose:

```bash
git status
```

shows:

```text
new file: .env
```

under staged changes, but you have not committed.

Unstage:

```bash
git restore --staged .env
```

Add it to:

```text
.gitignore
```

Then verify:

```bash
git status
```

The situation is much simpler because the secret never entered commit history.

---

# 75. Secret in Latest Unpushed Commit

Suppose you committed the secret locally but have not pushed.

First rotate it anyway if it is a real sensitive credential and there is any concern it may have been exposed elsewhere.

Then remove it from the commit.

For a file that should remain locally but not be tracked:

```bash
git rm --cached .env
```

Add:

```text
.env
```

to `.gitignore`.

Then amend the unpushed commit:

```bash
git add .gitignore
git commit --amend
```

Inspect:

```bash
git show --stat
git status
```

Be careful that the amended commit no longer contains the sensitive file in that commit.

---

# 76. Secret Exists Deeper in History

This is more serious.

If sensitive data exists in earlier history, removing it may require rewriting repository history.

GitHub's current guidance recommends tools such as:

```text
git-filter-repo
```

for purging sensitive data from repository history.

History rewriting can affect:

```text
Commit IDs

Branches

Tags

Open pull requests

Collaborator clones

Forks

CI references
```

Therefore this is not something beginners should perform blindly on a shared production repository.

Coordinate the cleanup.

Most importantly:

```text
Rotating the credential remains mandatory.
```

History cleanup does not make an already stolen credential safe again.

---

# 77. Secret Scanning and Push Protection

GitHub can detect many supported secret types through secret scanning and can block certain pushes through push protection.

This is useful protection.

But do not treat it as proof that:

```text
If GitHub didn't block it, no secret exists.
```

Detection coverage varies by secret type and context.

Your engineering responsibility remains:

```text
Do not commit credentials.
```

---

# 78. Preventing Secret Commits

Use multiple layers:

```text
.gitignore

Environment-variable patterns

Secret managers

CI/CD secret stores

Pre-commit scanning where appropriate

GitHub secret scanning/push protection

Code review

Least privilege

Short-lived credentials where possible
```

For example:

```text
.env
.env.*
*.pem
```

may belong in `.gitignore`, depending on the project.

But be careful:

```text
*.pem
```

could also ignore legitimate public certificates.

Ignore rules should match your actual repository design.

---

# 79. Large-File Problems

Git is optimized primarily for source code and similar versioned content.

Large binary files can make repositories:

```text
slow to clone

large to fetch

expensive to store

difficult to rewrite

slow in CI/CD
```

Examples:

```text
VM images

database dumps

large videos

ISO images

compiled binaries

machine-learning models

large archives
```

---

# 80. GitHub Large-File Limits

For regular Git repositories on GitHub, files above 50 MiB trigger a warning, while files larger than 100 MiB are blocked. GitHub recommends Git LFS for files beyond the normal Git file limit.

These limits are platform behavior, not a universal Git protocol rule.

A local Git repository can contain files that GitHub later refuses to accept.

---

# 81. Push Rejected Because of a Large File

Suppose:

```text
backup.sql
```

is 250 MiB.

You commit it.

Then push.

GitHub rejects the file.

A common beginner mistake is:

```bash
rm backup.sql
git commit -m "Delete backup"
git push
```

This may still fail.

Why?

Because the large file still exists in the earlier commit you are trying to push.

Deleting it in a later commit does not remove the earlier object from the history being pushed.

---

# 82. Large File in Latest Unpushed Commit

If the large file was added in the latest commit and has not been pushed, one approach is:

```bash
git rm --cached backup.sql
```

Add an appropriate ignore rule:

```text
backup.sql
```

Then amend:

```bash
git add .gitignore
git commit --amend
```

Verify:

```bash
git status
git show --stat
```

Then push.

This rewrites the local unpushed commit so the large file is not part of it.

---

# 83. Large File in Older History

If the large file exists deeper in history, simply deleting it now will not remove the old copy.

History cleanup may be necessary.

For large files that genuinely belong under version control, Git LFS may be appropriate.

For generated files, backups, dependencies, or build artifacts, the better answer may be:

```text
Do not version them at all.
```

---

# 84. What Is Git LFS?

Git LFS means:

```text
Git Large File Storage
```

At a simplified level, instead of storing the large file contents directly in normal Git history, Git tracks a small pointer while the large content is handled through LFS storage.

Typical workflow after installing Git LFS may include:

```bash
git lfs install
```

Then:

```bash
git lfs track "*.psd"
```

This updates tracking rules, normally through:

```text
.gitattributes
```

Then commit the relevant `.gitattributes` file so collaborators receive the LFS tracking rules.

Do not use Git LFS blindly for every large-looking file. Understand storage, bandwidth, team workflow, and hosting limits.

---

# 85. Large Files That Usually Should Not Be in Git

Examples often include:

```text
node_modules/

virtual-machine images

database backups

generated archives

temporary build directories

dependency caches

log archives

container images

large exported datasets
```

Better systems may include:

```text
Package registries

Container registries

Artifact repositories

Object storage

Release assets

Database backup systems
```

Git should not become a general file-storage server.

# 86. Diagnosing "My Commit Is Gone"

Use this sequence:

```bash
git status
```

Then:

```bash
git branch --show-current
```

Then:

```bash
git log --oneline --graph --decorate --all
```

If missing:

```bash
git reflog
```

If you find a likely commit:

```bash
git show <commit-id>
```

Then preserve:

```bash
git branch recovered-work <commit-id>
```

Do not immediately reset another branch.

---

# 87. Diagnosing "My File Is Gone"

First determine:

```text
Was the file tracked?

Was it committed?

Was it staged?

Was it never added?

Was it deleted by Git or outside Git?
```

If tracked and committed, you may inspect previous history:

```bash
git log -- <file>
```

Then inspect:

```bash
git show <commit>:<path>
```

If the file existed in `HEAD` and was merely deleted from the working tree:

```bash
git status
```

may show it as deleted.

You may restore it:

```bash
git restore <file>
```

But verify first that restoring is actually what you want.

---

# 88. Untracked Deleted Files Are Different

Suppose:

```text
notes.txt
```

was never:

```text
staged

committed

stashed with untracked inclusion
```

and you delete it from the filesystem.

Git may have no copy.

This is why:

```text
Git is not an autosave system.
```

Git can recover only information it actually recorded or still has in its object/reference machinery.

---

# 89. Diagnosing "My Branch Is Gone"

Use:

```bash
git branch
```

Then:

```bash
git branch -a
```

Then:

```bash
git reflog
```

Possible situations:

```text
Local branch deleted, remote still exists

Remote branch deleted, local still exists

Both references deleted, commits still recoverable locally

Commit history genuinely unavailable
```

Determine which case you have before acting.

---

# 90. Diagnosing "My Push Doesn't Work"

Use a layered approach.

First:

```bash
git status
```

Then:

```bash
git branch --show-current
```

Then:

```bash
git remote -v
```

Then read the exact push error.

Classify it:

```text
Authentication?

Authorization?

Non-fast-forward?

Wrong remote?

No upstream?

Large file?

Secret blocked?

Branch protection?

Network?
```

Do not troubleshoot SSH if your remote is HTTPS.

Do not regenerate tokens for a non-fast-forward error.

Match the fix to the layer.

---

# 91. Diagnosing "Git Says Everything Is Clean but GitHub Is Missing My Work"

Suppose:

```bash
git status
```

says:

```text
nothing to commit, working tree clean
```

but GitHub does not show your latest work.

Remember:

```text
clean working tree
```

does not mean:

```text
remote synchronized
```

Check:

```bash
git log --oneline --decorate -5
```

Then:

```bash
git status
```

Look at tracking information.

Then:

```bash
git remote -v
```

Perhaps you committed but never pushed.

A commit is local until transferred to a remote.

---

# 92. Diagnosing "GitHub Has Changes I Don't Have"

Run:

```bash

```

Then:

```bash
git status
```

Then:

```bash

```

```text

```

updates your knowledge of the remote.

It does not necessarily integrate those commits into your local branch.

If:

```text

```

advanced while:

```text

```

did not, that is normal after fetch.

# 93. Diagnosing "Why Did Every File Change?"

# 95. Diagnosing Tracking Problems

# 96. Recovery Principle: Do Not Destroy Evidence

Imagine an incident investigator receives a broken server.

Would they immediately delete all logs?

No.

Git troubleshooting should follow the same principle.

Evidence includes:

```text
git status

git diff

git log

git reflog

branch references

remote-tracking references

stash entries

error messages

commit IDs
```

Preserve these before running destructive operations.

---

# 97. Dangerous Commands During Confusion

Commands such as these deserve extra caution:

```bash
git reset --hard
git clean -fd
git clean -fdx
git push --force
git branch -D
git stash clear
```

They are legitimate Git commands.

The problem is not that they exist.

The problem is running them without understanding what information they may remove or overwrite.

---

# 98. `git clean` Warning

`git clean` can remove untracked files.

That matters because untracked files may not exist anywhere in Git history.

Before cleaning, use dry-run behavior:

```bash
git clean -n
```

This shows what would be removed.

Do not run destructive cleanup because you want:

```text
a clean git status
```

Your untracked files may contain valuable work.

---

# 99. Safe Recovery Hierarchy

When choosing between possible actions, prefer information-preserving operations.

Conceptually:

```text
Inspect
   |
   v
Preserve reference
   |
   v
Commit/stash if appropriate
   |
   v
Create recovery branch
   |
   v
Use operation-specific abort
   |
   v
Rewrite only when understood
   |
   v
Destructive cleanup only when intentional
```

Use this mental model.


You should now understand that Git troubleshooting begins with:

```bash

```


You should understand detached HEAD and why commits created there should be preserved with a branch if you want to keep them.

You should understand that deleting a branch does not necessarily immediately delete its commits.

You should understand:


as a local record of recent reference movements that can help recover commits after:

You should understand how to recover a commit safely by:

```text

Verify

Integrate
```

You should understand:

```bash

```

for canceling an unwanted in-progress merge.

You should understand:

```bash
git rebase --continue
```

and:

```bash
git rebase --abort
```

for rebase recovery.

You should understand why Git may block a branch switch when uncommitted changes could be overwritten.

You should understand that a rejected push has multiple possible causes and must be classified before fixing.

You should understand non-fast-forward protection.

You should understand why:

```bash
git push --force
```

is not the default answer.

You should understand unrelated histories and why they often indicate independently initialized repositories.

You should understand authentication troubleshooting for both HTTPS and SSH.

You should understand remote URLs and tracking branches.

You should understand executable-bit changes and line-ending problems.

You should understand that accidentally committed credentials require security response, beginning with revocation or rotation.

You should understand that deleting a secret in a later commit does not erase it from older history.

You should understand GitHub's large-file restrictions and why deleting a large file in a later commit may not fix a rejected push.

Most importantly, you should understand this rule:

```text
When Git looks broken,
preserve information before changing information.
```

# 132. Final Troubleshooting Mental Model

When Git behaves unexpectedly, do not begin with:

```text
How do I force Git to do what I want?
```

Begin with:

```text
What state am I actually in?
```

Then:

```text
Where am I?
    |
    v
pwd
git rev-parse --show-toplevel

What is Git doing?
    |
    v
git status

What branch am I on?
    |
    v
git branch --show-current

What does history look like?
    |
    v
git log --oneline --graph --decorate --all

Where does this repository connect?
    |
    v
git remote -v

What changed remotely?
    |
    v
git fetch origin

Where did HEAD recently point?
    |
    v
git reflog
```

Then classify the problem.

```text
Wrong directory
    -> Navigate to correct repository

Wrong branch
    -> Preserve work and move deliberately

Detached HEAD
    -> Create a branch if work matters

Missing commit
    -> log + reflog + recovery branch

Lost branch
    -> remote refs/reflog + recreate reference

Merge stuck
    -> resolve + complete, or merge --abort

Rebase stuck
    -> resolve + continue, or rebase --abort

Switch blocked
    -> commit, stash, or deliberately discard

Push rejected
    -> read exact rejection

Non-fast-forward
    -> fetch + inspect + integrate

Unrelated histories
    -> understand why before combining

Authentication
    -> identify HTTPS vs SSH and test that layer

Wrong remote
    -> inspect remote -v and correct set-url

No upstream
    -> configure tracking deliberately

Permission noise
    -> inspect executable bit/file mode

Line-ending noise
    -> inspect autocrlf and .gitattributes

Secret committed
    -> revoke/rotate first

Large file
    -> remove from relevant history or use appropriate storage/LFS
```

The mature engineering response to a Git incident is not:

```text
Try commands until one works.
```

It is:

```text
Observe
   |
   v
Understand
   |
   v
Preserve
   |
   v
Diagnose
   |
   v
Correct
   |
   v
Verify
   |
   v
Prevent
```

That is the same mindset you will use later when troubleshooting:

```text
Linux servers

Kubernetes clusters

CI/CD pipelines

Terraform

cloud infrastructure

network failures

production incidents
```

Git is therefore teaching you something larger than version control.

It is teaching you how engineers troubleshoot systems.

You should now see those not as one giant category called:

```text
Git problems
```

but as separate state problems.

Your core diagnostic toolkit is:

```bash
git status
git diff
git diff --staged
git branch
git branch -vv
git log --oneline --graph --decorate --all
git reflog
git show
git remote -v
git fetch
git rev-parse --show-toplevel
```

Your recovery philosophy is:

```text
Do not destroy evidence.

Do not guess.

Do not force because you are frustrated.

Do not assume missing means deleted.

Do not assume rejected means broken.

Do not assume clean means synchronized.

Do not assume Git success means application success.
```

Instead:

```text
Inspect first.

Preserve important work.

Use the least-destructive fix.

Verify the result.

Understand why the problem happened.
```
