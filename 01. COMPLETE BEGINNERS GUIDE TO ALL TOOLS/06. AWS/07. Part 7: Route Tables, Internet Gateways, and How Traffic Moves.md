# Part 7: Route Tables, Internet Gateways, and How Traffic Moves

In Part 6, you divided the VPC into public and private subnet tiers across two Availability Zones.

Your architecture currently looks like this:

```text
VPC 10.0.0.0/16
|
├── AZ-A
│   ├── Public A  10.0.1.0/24
│   └── Private A 10.0.11.0/24
│
└── AZ-B
    ├── Public B  10.0.2.0/24
    └── Private B 10.0.12.0/24
```

But there is an important problem.

Calling a subnet `public` does not make it public.

At this point, Public A and Public B are simply subnets that we intend to make public.

To actually give them a path to the internet, we need to understand routing.

This part introduces:

* What routing means
* How AWS decides where network traffic goes
* Destination and target
* VPC local routes
* Main route tables
* Custom route tables
* Route table associations
* Longest-prefix matching
* Internet Gateways
* Public IPv4 requirements
* How an EC2 instance reaches the internet
* Inbound and outbound traffic
* How to build a public subnet correctly
* How to diagnose routing failures
* How engineers read route tables during incidents

By the end, you will turn the subnet architecture from Part 6 into a working public network.

Our main traffic flow will be:

```text
EC2
 |
 v
Subnet
 |
 v
Route Table
 |
 v
Internet Gateway
 |
 v
Internet
```

But the actual process contains several important layers.

---

# 1. Start With the Problem

Suppose you launch an EC2 instance into:

```text
10.0.1.0/24
```

The instance receives:

```text
Private IPv4:
10.0.1.25
```

You install a web server.

Then you try:

```bash
curl https://example.com
```

and the request fails.

Why?

The EC2 instance exists.

The VPC exists.

The subnet exists.

The network interface exists.

The instance has an IP address.

But AWS still needs to answer:

```text
Where should traffic destined for the internet go?
```

That is a routing question.

---

# 2. What Is Routing?

Routing is the process of deciding where network traffic should go next.

When one computer sends data to another IP address, the network needs a path toward that destination.

Imagine:

```text
Source
|
v
Where should this packet go?
|
v
Destination
```

A router uses routing information to answer that question.

In AWS VPC networking, route tables provide these routing instructions.

---

# 3. A Simple Real-World Analogy

Imagine driving from your home to another city.

You reach a junction.

Signs say:

```text
Downtown      -> Left
Airport       -> Right
Highway       -> Straight
```

Your destination determines which direction you take.

A route table performs a similar job for network traffic.

Instead of:

```text
Airport -> Right
```

you might see:

```text
10.0.0.0/16 -> local
```

or:

```text
0.0.0.0/0 -> Internet Gateway
```

The left side describes the destination.

The right side tells AWS where to send matching traffic.

---

# 4. What Is a Route Table?

A route table is a collection of routes used to determine where network traffic should be directed.

A simplified AWS route table might contain:

```text
Destination       Target

10.0.0.0/16       local
0.0.0.0/0         igw-0123456789
```

Read it as:

```text
Traffic for 10.0.0.0/16
stays inside the VPC.

Traffic for other IPv4 destinations
goes toward the Internet Gateway.
```

That simple table is extremely important.

---

# 5. Every Route Has a Destination and a Target

The two concepts beginners must understand first are:

```text
Destination
Target
```

A route answers:

```text
If traffic is going HERE,
send it THERE.
```

---

# 6. What Is the Destination?

The destination describes which IP addresses a route applies to.

Example:

```text
10.0.0.0/16
```

means:

```text
Traffic destined for an address
inside 10.0.0.0/16
```

Another destination:

```text
0.0.0.0/0
```

means:

```text
All IPv4 destinations
```

It is commonly called the default route.

---

# 7. What Is the Target?

The target tells AWS where matching traffic should go.

Targets can represent different AWS networking resources.

Examples include:

```text
local

Internet Gateway

NAT Gateway

Transit Gateway

Virtual Private Gateway

Network Interface

VPC Peering Connection
```

You do not need to understand all of these yet.

For this part, focus on:

```text
local
```

and:

```text
Internet Gateway
```

---

# 8. Reading a Route

Suppose you see:

```text
Destination       Target

10.0.0.0/16       local
```

Read it as:

```text
If the destination belongs to
10.0.0.0/16,

keep the traffic within
the VPC's local routing system.
```

Now consider:

```text
0.0.0.0/0         igw-abc123
```

Read it as:

```text
If traffic needs to go somewhere
covered by the default IPv4 route,

send it to the Internet Gateway
igw-abc123.
```

---

# 9. The VPC Local Route

When AWS creates a route table for a VPC, it includes a route that allows communication within the VPC address space.

For our VPC:

```text
10.0.0.0/16
```

the route table includes a local route representing the VPC CIDR.

Conceptually:

```text
Destination       Target

10.0.0.0/16       local
```

This is called the local route.

---

# 10. Why Does the Local Route Exist?

Our VPC contains:

```text
Public A
10.0.1.0/24

Public B
10.0.2.0/24

Private A
10.0.11.0/24

Private B
10.0.12.0/24
```

All of these are inside:

```text
10.0.0.0/16
```

Suppose:

```text
EC2-A
10.0.1.25
```

needs to communicate with:

```text
EC2-B
10.0.11.40
```

Both addresses belong to the VPC.

The local route provides the VPC-level routing path.

Conceptually:

```text
EC2-A
10.0.1.25
|
v
Destination:
10.0.11.40
|
v
Route Table
|
v
10.0.0.0/16 -> local
|
v
EC2-B
10.0.11.40
```

Routing alone does not guarantee that the connection will succeed.

Security Groups, Network ACLs, operating-system firewalls, and the destination service can still allow or deny traffic.

---

# 11. Local Routing Does Not Mean "Everything Is Allowed"

This distinction is critical.

A route says:

```text
A path exists.
```

It does not necessarily say:

```text
Traffic is permitted.
```

For example:

```text
Routing:
10.0.0.0/16 -> local
```

may provide a route between two EC2 instances.

But a Security Group could still prevent the connection.

Think:

```text
Routing
=
Where can traffic go?
```

```text
Security
=
Is the traffic permitted?
```

These are different questions.

---

# 12. Routing and Security Work Together

Suppose:

```text
EC2-A
10.0.1.25
```

tries to connect to:

```text
EC2-B
10.0.11.40
```

on:

```text
TCP 8080
```

For the application connection to work, several things need to be correct:

```text
Network route
+
Security Group rules
+
Network ACL behavior
+
Operating-system firewall
+
Application listening on TCP 8080
```

If any required layer fails, the connection can fail.

This is why troubleshooting requires checking layers systematically.

---

# 13. What Is the Main Route Table?

Every VPC has a main route table.

The main route table acts as the default route table for subnets that do not have an explicit association with another route table.

Think:

```text
Subnet
|
No explicit custom route table?
|
v
Use main route table
```

When you create a VPC, AWS provides a main route table.

---

# 14. Main Route Table Example

For:

```text
VPC
10.0.0.0/16
```

the main route table initially contains the local route.

Simplified:

```text
Destination       Target

10.0.0.0/16       local
```

That allows local VPC routing.

But there is no:

```text
0.0.0.0/0 -> Internet Gateway
```

yet.

Therefore, this table does not provide a general IPv4 route to the public internet.

---

# 15. What Is a Route Table Association?

A route table association connects a subnet to the route table that should control its subnet-level routing.

Conceptually:

```text
Subnet
|
v
Associated Route Table
|
v
Routes
```

For example:

```text
Public Subnet A
|
v
Public Route Table
```

and:

```text
Private Subnet A
|
v
Private Route Table
```

This distinction allows different subnet tiers to use different network paths.

---

# 16. Explicit vs Implicit Associations

A subnet can use the main route table implicitly if it has not been explicitly associated with another route table.

Conceptually:

```text
Subnet A
|
No explicit association
|
v
Main Route Table
```

Alternatively:

```text
Subnet B
|
Explicit association
|
v
Custom Route Table
```

The explicit association determines the route table used by that subnet.

---

# 17. What Is a Custom Route Table?

A custom route table is a route table you create for a specific routing design.

For example:

```text
veriqta-dev-public-rt
```

could contain:

```text
Destination       Target

10.0.0.0/16       local
0.0.0.0/0         igw-...
```

You could associate:

```text
Public A
Public B
```

with this table.

Now both public subnets share the intended public routing behavior.

---

# 18. Why Create Custom Route Tables?

Custom route tables make network intent clearer.

Instead of modifying the main table and letting many subnets inherit it accidentally, you can explicitly define:

```text
Public Route Table
```

for public subnets and:

```text
Private Route Table
```

for private subnets.

This makes architecture easier to:

* Understand
* Audit
* Troubleshoot
* Change safely
* Automate

---

# 19. Our Route Table Design

For the architecture from Part 6, we will eventually have something like:

```text
VPC 10.0.0.0/16
|
├── Public Route Table
│   |
│   ├── 10.0.0.0/16 -> local
│   └── 0.0.0.0/0   -> Internet Gateway
│
└── Private Routing
    |
    ├── 10.0.0.0/16 -> local
    └── Internet path handled separately
```

For now, our focus is building the public path correctly.

---

# 20. Route Table Association Mistakes Matter

Suppose you create the perfect public route table:

```text
10.0.0.0/16 -> local
0.0.0.0/0   -> igw-123
```

But Public A is associated with a different table.

Traffic from Public A does not magically use the table you intended.

The actual association matters.

A common incident pattern is:

```text
Correct route exists
+
Wrong subnet association
=
Connectivity failure
```

Always ask:

```text
Which route table is this subnet actually using?
```

---

# 21. What Is Longest-Prefix Matching?

Now we need to answer an important question.

Suppose a route table contains:

```text
10.0.0.0/16 -> local

0.0.0.0/0 -> Internet Gateway
```

An EC2 instance wants to reach:

```text
10.0.11.40
```

Both routes technically match.

Why doesn't AWS send the traffic to the Internet Gateway?

Because routing uses the most specific matching route.

This is called longest-prefix matching.

---

# 22. Understanding Prefix Length

Remember CIDR:

```text
/16
/24
/32
```

A larger prefix length describes a more specific range.

For example:

```text
0.0.0.0/0
```

matches all IPv4 addresses.

Very broad.

```text
10.0.0.0/16
```

matches a smaller range.

More specific.

```text
10.0.1.0/24
```

matches an even smaller range.

More specific again.

```text
10.0.1.25/32
```

matches one IPv4 address.

Extremely specific.

---

# 23. Longest-Prefix Matching Example

Route table:

```text
Destination       Target

10.0.0.0/16       local
0.0.0.0/0         igw-123
```

Destination:

```text
10.0.11.40
```

Both routes match.

But:

```text
/16
```

is more specific than:

```text
/0
```

Therefore AWS selects:

```text
10.0.0.0/16 -> local
```

---

# 24. Another Longest-Prefix Example

Suppose a hypothetical route table contains:

```text
10.0.0.0/16       Target A

10.0.10.0/24      Target B

0.0.0.0/0         Target C
```

Destination:

```text
10.0.10.25
```

All three may match.

But:

```text
10.0.10.0/24
```

is the most specific.

Therefore:

```text
Target B
```

wins.

Do not think:

```text
First route listed wins.
```

Routing is not based on visual order.

It is based primarily on route matching rules, including specificity.

---

# 25. Beginner Rule for Route Tables

When investigating routing, ask:

```text
1. What is the destination IP?

2. Which routes match it?

3. Which matching route is most specific?

4. What is that route's target?

5. Is that target available and correctly configured?
```

This reasoning is far more useful than memorizing route table screenshots.

---

# 26. What Is an Internet Gateway?

An Internet Gateway, commonly abbreviated IGW, is an AWS VPC component that enables communication between a VPC and the internet when the rest of the networking requirements are satisfied.

Think:

```text
VPC
|
Internet Gateway
|
Internet
```

The Internet Gateway attaches to the VPC.

It is not created inside one specific subnet.

---

# 27. Internet Gateway Scope

The Internet Gateway is attached to the VPC.

Conceptually:

```text
VPC 10.0.0.0/16
|
+-- Public A
|
+-- Public B
|
+-- Private A
|
+-- Private B
|
+-- Internet Gateway
```

The presence of the Internet Gateway does not automatically give every subnet internet access.

Subnets still need appropriate routing.

---

# 28. Attaching an Internet Gateway Does Not Make Subnets Public

Suppose you:

1. Create an Internet Gateway.
2. Attach it to the VPC.

But your route table remains:

```text
10.0.0.0/16 -> local
```

There is no default route to the IGW.

The public internet path is still missing.

You need:

```text
0.0.0.0/0 -> Internet Gateway
```

in the route table associated with the intended public subnet.

---

# 29. The Public Route

The core IPv4 route for a public subnet is:

```text
Destination:
0.0.0.0/0

Target:
Internet Gateway
```

Example:

```text
Destination       Target

10.0.0.0/16       local
0.0.0.0/0         igw-0abc123
```

This tells AWS:

```text
VPC destinations
-> stay local

Other IPv4 destinations
-> Internet Gateway
```

---

# 30. Why `0.0.0.0/0`?

Suppose the EC2 instance wants to reach:

```text
8.8.8.8
```

That address is not inside:

```text
10.0.0.0/16
```

The local route does not match it.

But:

```text
0.0.0.0/0
```

matches every IPv4 destination.

Therefore:

```text
8.8.8.8
|
v
0.0.0.0/0
|
v
Internet Gateway
```

---

# 31. How an EC2 Instance Reaches the Internet

Suppose an EC2 instance has:

```text
Private IP:
10.0.1.25

Public IPv4:
Example public address
```

It sits in:

```text
Public A
10.0.1.0/24
```

Its associated route table contains:

```text
10.0.0.0/16 -> local
0.0.0.0/0   -> igw-...
```

The VPC has the Internet Gateway attached.

Now the EC2 instance runs:

```bash
curl https://example.com
```

Let's follow the traffic.

---

# 32. Step 1: The Application Generates Traffic

`curl` wants to contact:

```text
https://example.com
```

DNS resolves the hostname to an IP address.

For illustration, suppose the destination becomes:

```text
203.0.113.x
```

The exact real address may differ.

The operating system now needs to send packets toward that destination.

---

# 33. Step 2: The Instance Uses Its Network Interface

The EC2 instance communicates through its Elastic Network Interface.

Conceptually:

```text
curl
|
v
Linux networking stack
|
v
ENI
|
v
VPC network
```

The ENI has the instance's private IPv4 address.

Example:

```text
10.0.1.25
```

---

# 34. Step 3: AWS Evaluates the Subnet's Routing

The destination is outside:

```text
10.0.0.0/16
```

Therefore the local VPC route is not the path for that destination.

AWS finds:

```text
0.0.0.0/0 -> igw-...
```

The packet is directed toward the Internet Gateway.

---

# 35. Step 4: The Internet Gateway Provides the Internet Path

The traffic reaches the Internet Gateway.

For an EC2 instance using an AWS public IPv4 address, AWS handles the address translation between the instance's private address and its public address as part of the Internet Gateway path.

The instance itself still sees its private address on its network interface.

This surprises many beginners.

---

# 36. Public IPv4 Does Not Replace the Private IPv4

Suppose EC2 shows:

```text
Private IPv4:
10.0.1.25

Public IPv4:
198.51.100.x
```

Inside the VPC, the network interface uses:

```text
10.0.1.25
```

The public IPv4 address is mapped for internet communication.

Do not imagine the EC2 network interface as simply replacing:

```text
10.0.1.25
```

with the public address.

---

# 37. Step 5: Traffic Travels Across the Internet

The request travels to the remote destination.

Conceptually:

```text
EC2
|
Subnet
|
Route Table
|
Internet Gateway
|
Internet
|
Remote Server
```

The remote server processes the request.

---

# 38. Step 6: Response Traffic Returns

The remote server sends a response.

Conceptually:

```text
Remote Server
|
Internet
|
Internet Gateway
|
VPC
|
EC2
```

The Internet Gateway participates in delivering the response back to the instance.

Stateful Security Groups also play an important role in allowing response traffic for permitted connections.

We will examine Security Groups deeply in a later part.

---


```text

|

|

|

```

# 40. What Does an EC2 Instance Need for Direct IPv4 Internet Access?

For the normal public-subnet pattern, the EC2 instance needs several things.

## Requirement 1: Publicly usable IPv4 addressing

For example:

```text
Public IPv4 address
```

or:

```text
Elastic IP
```

depending on the design.

## Requirement 2: Public subnet routing

Its subnet must use a route table containing:

```text
0.0.0.0/0 -> Internet Gateway
```

## Requirement 3: Internet Gateway

The Internet Gateway must be attached to the VPC.

## Requirement 4: Security rules

Security Groups and Network ACLs must permit the required traffic.

## Requirement 5: Working host configuration

The operating system and application must also be functioning correctly.

```text

```

exists.

But EC2 has only:

```text

```

and no public IPv4 address.

For the standard direct IPv4 internet pattern, the instance still cannot communicate directly with the public internet through the IGW as though the private address were internet-routable.

The private address:

```text
10.0.1.25
```

is not a public internet address.

---

# 43. Internet Gateway Alone Is Not Enough

Suppose:

```text
Internet Gateway:
Attached
```

but:

```text
Route to IGW:
Missing
```

No public path.

Again:

```text
IGW alone
!=
Internet connectivity
```

---

# 44. Route + Public IP + IGW Still May Not Be Enough

Suppose all three exist:

```text
Public IP
+
IGW
+
0.0.0.0/0 route
```

But the Security Group does not permit the required inbound traffic.

An inbound connection can still fail.

Or perhaps:

```text

```

Then TCP port 80 has nothing listening.

Network troubleshooting requires checking the complete path.

# 45. What Is Outbound Traffic?

Outbound traffic originates from your resource and travels toward another destination.

Example:

```text
EC2
|
v
Internet
```

The EC2 instance runs:

```bash
sudo dnf update
```

or:

```bash
curl https://example.com
```

The EC2 instance initiated the connection.

That is outbound traffic from the EC2 instance's perspective.

---

# 46. What Is Inbound Traffic?

Inbound traffic originates elsewhere and attempts to reach your resource.

Example:

```text
Laptop
|
Internet
|
v
EC2
```

You run:

```bash
ssh -i key.pem ec2-user@PUBLIC_IP
```

Your laptop initiates the connection.

From the EC2 instance's perspective, this is inbound traffic.

---

# 47. Inbound and Outbound Depend on Perspective

Suppose:

```text
EC2-A
->
EC2-B
```

For EC2-A:

```text
Outbound
```

For EC2-B:

```text
Inbound
```

The same network communication can be described differently depending on which resource you are examining.

Always ask:

```text
Inbound to what?

Outbound from what?
```

---

You run:


```text
|

|

|

```

For the EC2 instance:

```text

```

The return traffic goes back toward your laptop.


* Open every Security Group port
* Delete the route table

# 74. Question 1: What Is the Source?

Identify:

```text
Which resource is sending traffic?
```

Example:

```text
EC2
10.0.1.25
```

Then ask:

```text
Which subnet contains it?
```

Example:

```text
10.0.1.0/24
```

---

# 75. Question 2: What Is the Destination?

Examples:

```text
8.8.8.8
```

or:

```text
example.com
```

If a hostname is used, remember DNS must first resolve it.

Routing decisions ultimately operate on destination IP information.

---

# 76. Question 3: Which Route Table Applies?

Do not inspect a random route table.

Find the subnet.

Then find its actual route table association.

Ask:

```text
Subnet:
10.0.1.0/24

Associated route table:
?
```

This is one of the most important incident checks.

---

# 77. Question 4: Which Route Matches?

Suppose destination:

```text
8.8.8.8
```

Route table:

```text
10.0.0.0/16 -> local
0.0.0.0/0   -> igw-123
```

Which route matches?

`8.8.8.8` is not inside:

```text
10.0.0.0/16
```

Therefore:

```text
0.0.0.0/0
```

is used.

Target:

```text
igw-123
```

---

# 78. Question 5: Is the Target Valid?

Suppose the route shows:

```text
0.0.0.0/0 -> igw-123
```

Now inspect the Internet Gateway.

Ask:

```text
Does igw-123 exist?

Is it attached?

Is it attached to this VPC?
```

A route pointing toward an unavailable target does not create working connectivity.

---

# 79. Question 6: Does EC2 Have the Required Address?

For direct public IPv4 internet communication, inspect the EC2 instance.

Does it have:

```text
Public IPv4?
```

If not, the public-subnet IGW pattern is incomplete for direct IPv4 internet communication.

Do not assume:

```text
Public subnet
=
Every instance gets a public IP.
```

---

# 80. Question 7: Is Security Blocking Traffic?

If routing looks correct, inspect:

```text
Security Group

Network ACL

OS firewall
```

Do not confuse:

```text
No route
```

with:

```text
Traffic denied
```

They can produce similar symptoms from a user's perspective.

---

# 81. Question 8: Is the Application Working?

Suppose a website is unreachable.

Networking might be perfect.

But:

```bash
sudo systemctl status nginx
```

shows:

```text
inactive
```

The problem is not routing.

Always test the service itself.

Example:

```bash
curl http://localhost
```

If localhost fails, investigate the application before blaming AWS routing.

# 82. Incident Scenario 1: Missing Default Route

## Problem

EC2 cannot reach:

```text
https://example.com
```

## Investigation

Route table:

```text
10.0.0.0/16 -> local
```

There is no:

```text
0.0.0.0/0 -> IGW
```

## Cause

No internet route.

## Fix

For a subnet intended to be public, add:

```text
0.0.0.0/0 -> correct Internet Gateway
```

to the appropriate public route table.

## Verification

Run:

```bash
curl -I https://example.com
```

---

# 83. Incident Scenario 2: Internet Gateway Not Attached

## Problem

Public route exists:

```text
0.0.0.0/0 -> igw-123
```

but connectivity fails.

## Investigation

Check the Internet Gateway.

It is not correctly attached to the VPC.

## Fix

Attach the correct Internet Gateway to the correct VPC.

## Verification

Recheck the route target and repeat the connectivity test.

---

# 84. Incident Scenario 3: Wrong Route Table Association

## Problem

Public A works.

Public B does not.

Both appear to have similar EC2 configurations.

## Investigation

Public A:

```text
Associated:
veriqta-dev-public-rt
```

Public B:

```text
Associated:
different route table
```

The second table lacks the IGW route.

## Cause

Incorrect route table association.

## Fix

Associate Public B with the intended public route table.

## Verification

Confirm the association and test again.

---

# 85. Incident Scenario 4: No Public IPv4

## Problem

EC2 is in a correctly routed public subnet.

It cannot use the direct public IPv4 internet pattern.

## Investigation

EC2 networking:

```text
Private IPv4:
10.0.1.25

Public IPv4:
None
```

## Cause

No public IPv4 address.

## Fix

Use the appropriate public-address design for the workload.

For a simple beginner lab, launch/configure the instance with a public IPv4 address as appropriate.

For production, consider whether the instance should actually be public at all.

Often it should not be.

# 86. Incident Scenario 5: SSH Fails but Internet Works

## Problem

From EC2:

```bash
curl https://example.com
```

works.

But from your laptop:

```bash
ssh ...
```

times out.

What does this tell you?

The outbound internet path is functioning.

Therefore, investigate the inbound SSH path.

Possible causes include:

* Security Group missing TCP 22
* Wrong source IP in Security Group
* Network ACL
* Wrong public IP
* SSH service issue
* Wrong username
* Host firewall
* Instance not healthy

Do not rebuild the route table simply because SSH fails.

# 87. Incident Scenario 6: SSH Says Permission Denied

Suppose:

```bash
ssh -i veriqta.pem ubuntu@PUBLIC_IP
```

returns:

```text
Permission denied (publickey)
```

This is different from:

```text
Connection timed out
```

`Permission denied` often suggests that network connectivity reached the SSH service but authentication failed.

Investigate:

* Wrong private key
* Wrong username
* Incorrect authorized key
* SSH configuration

Routing may already be working.

Error messages contain clues about which layer failed.

# 88. Incident Scenario 7: Connection Refused

Suppose:

```bash
curl http://PUBLIC_IP
```

returns:

```text
Connection refused
```

This can mean the host is reachable, but nothing is listening on the requested port, or a host-level component is actively rejecting the connection.

Check:

```bash
sudo ss -lntp
```

This shows listening TCP sockets.

Look for:

```text
:80
```

If Nginx should be running:

```bash
sudo systemctl status nginx
```

Again, do not assume every connection failure is routing.

# 89. Incident Scenario 8: DNS Fails

Suppose:

```bash
curl https://example.com
```

fails with a name-resolution error.

Try:

```bash
getent hosts example.com
```

If DNS fails, investigate DNS configuration.

Do not immediately edit:

```text
0.0.0.0/0
```

A DNS problem and routing problem are different categories.

# 90. Incident Scenario 9: Private Subnet Accidentally Made Public

Suppose:

```text
veriqta-dev-private-a
```

is accidentally associated with:

```text
veriqta-dev-public-rt
```

which contains:

```text

```

The subnet now has direct IGW routing behavior.

This violates the intended architecture.

## Fix

Associate the subnet with the correct private route table design.

Then verify that private workloads do not receive unnecessary public addresses.

If the real issue is:

# 95. Architecture Intent Comes Before the Fix

A beginner often sees:

```text

```

and thinks:

```text

```

A DevOps engineer should first ask:

```text
Should this resource be directly internet connected?
```

For:

```text
Public Load Balancer
```

perhaps yes.

For:

```text
Private application server
```

probably not directly.

For:

```text
Database
```

generally no direct internet exposure.

The correct fix depends on architecture.

# 96. Route Tables as Documentation

A well-designed route table tells part of the architecture story.

Example:

```text
veriqta-prod-public-rt

10.0.0.0/16 -> local
0.0.0.0/0   -> igw-prod
```

Immediately suggests:

```text
This is a public routing tier.
```

Another:

```text
veriqta-prod-private-a-rt

10.0.0.0/16 -> local
0.0.0.0/0   -> nat-a
```

suggests:

```text
Private subnet with outbound NAT path.
```

Clear names help humans understand infrastructure.

# 97. Do Not Treat Route Tables as Firewall Rules

This is another beginner mistake.

Route table:

```text
0.0.0.0/0 -> IGW
```

does not mean:

```text
Allow everyone to access everything.
```

The route defines a path.

Security controls determine whether particular traffic is allowed.

Think:

```text
Route Table
=
Where?
```

```text
Security Group
=
Allowed?
```

---

# 98. Routing Does Not Mean the Application Is Listening

Suppose:

```text
Route:
Correct

Security Group:
Correct

Public IP:
Correct
```

but Nginx is configured to listen only on:

```text
127.0.0.1:80
```

External requests may still fail.

The network can deliver traffic to the host, but the application must listen appropriately.

Infrastructure troubleshooting requires both network and host knowledge.

# 99. The Packet Path Mental Model

When something fails, imagine yourself as the packet.

Ask:

```text

What is my destination?

Which route applies?

Where does the target send me?

Can I reach that target?

What security controls do I encounter?

Does the destination know how to respond?

Can the response return?
```

This mental model is extremely useful in networking.

# 100. Public Subnet Checklist

A subnet intended to provide direct IPv4 internet connectivity should be checked for:

```text
[ ] Correct VPC

[ ] Correct CIDR

[ ] Correct Availability Zone

[ ] Correct route table association

[ ] 0.0.0.0/0 route

[ ] Route targets correct IGW

[ ] IGW attached to correct VPC

[ ] Resource has appropriate public IPv4 addressing

[ ] Security Group allows required traffic

[ ] Network ACL permits required traffic

[ ] Host firewall permits required traffic

[ ] Application/service is running

[ ] DNS works where required
```

Do not skip directly to the Security Group.

---

# 101. Security Warning: Public Does Not Mean Open

A public subnet should not mean:

```text
SSH from everywhere

Database from everywhere

All ports from everywhere
```

Public routing only creates the potential network path.

Security Groups should still follow least privilege.

For example, during a temporary SSH lab:

```text
TCP 22
Source:
Your trusted public IP
```

is preferable to:

```text
TCP 22
Source:
0.0.0.0/0
```

when practical.

---

# 102. Security Warning: Databases

Do not place a database in a public subnet simply because it makes connectivity easier.

Avoid designs like:

```text
Internet
|
Public IP
|
Database
```

when the database only needs communication from your application.

Prefer:

```text
Internet
|
Load Balancer
|
Private Application
|
Private Database
```

We will build toward this architecture throughout the AWS series.

# What You Should Now Understand

Before continuing, you should confidently understand:

* Routing means deciding where network traffic should go.
* AWS VPC route tables contain routing rules.
* Routes contain destinations and targets.
* The destination identifies traffic to which the route applies.
* The target identifies where matching traffic should be sent.
* The VPC local route supports routing within the VPC address space.
* Routing does not automatically permit traffic.
* Security controls are separate from routing.
* Every VPC has a main route table.
* Subnets without an explicit custom association use the main route table.
* Custom route tables allow different subnet tiers to have different routing behavior.
* Route table associations determine which route table a subnet uses.
* A correct route in the wrong route table does not help a subnet.
* AWS uses the most specific matching route.
* This behavior is called longest-prefix matching.
* `/24` is more specific than `/16`.
* `/16` is more specific than `/0`.
* `0.0.0.0/0` represents all IPv4 destinations.
* An Internet Gateway connects a VPC to the internet when routing and addressing requirements are satisfied.
* An Internet Gateway attaches to a VPC, not an individual subnet.
* Attaching an IGW does not automatically make subnets public.
* A public subnet needs an appropriate route to an Internet Gateway.
* Direct public IPv4 communication also requires appropriate public addressing.
* Public IP and private IP have different roles.
* EC2 still uses its private IP on its VPC network interface.
* Outbound traffic originates from the resource being examined.
* Inbound traffic arrives at the resource being examined.
* A failed SSH connection does not automatically mean routing is broken.
* A failed website does not automatically mean AWS networking is broken.
* DNS failures should be distinguished from routing failures.
* Application failures should be distinguished from network failures.
* Private subnets should not be made public simply to solve outbound internet requirements.
* NAT provides a different outbound model for private resources.
* Route tables are critical incident-response evidence.
* Engineers troubleshoot networking by following the traffic path.
