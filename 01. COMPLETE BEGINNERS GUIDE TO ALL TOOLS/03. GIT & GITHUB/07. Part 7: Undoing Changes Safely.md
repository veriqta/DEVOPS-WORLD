# Part 7: Undoing Changes Safely

In Part 6, you learned how Git history records the evolution of a project.

You learned to inspect that history with commands such as:

```bash
git log
git log --oneline
git show
git diff
```

You also learned that:

```text
HEAD
```

represents your current position in Git history.

Now we reach one of the most important Git skills:

```text
UNDOING CHANGES SAFELY
```

Git gives you several ways to undo mistakes.

But there is a problem.

The word:

```text
undo
```

can mean many completely different things.

You might mean:

* Discard an edit you have not staged
* Remove a file from the staging area
* Correct the latest commit message
* Add a forgotten file to the latest commit
* Reverse a committed change
* Move your branch backward
* Keep changes while removing commits
* Throw away commits and working files
* Recover a commit you accidentally removed
* Find work that appears to have disappeared

These operations are not interchangeable.

Some are relatively safe.

Some rewrite local history.

Some can destroy uncommitted work.

This part will teach you how to identify exactly what you are trying to undo before choosing a command.

You will learn:

* The different meanings of “undo” in Git
* How to undo working-directory changes
* How to unstage files
* `git restore`
* `git restore --staged`
* How to correct the latest commit
* `git commit --amend`
* `git revert`
* `git reset`
* Soft reset
* Mixed reset
* Hard reset
* When reset becomes dangerous
* Revert vs reset
* How to recover accidentally removed work
* Introduction to `git reflog`
* How to choose the safest recovery method
* Beginner recovery labs

The most important rule for this entire part is:

```text
DO NOT RUN AN UNDO COMMAND
UNTIL YOU KNOW WHICH GIT STATE
YOU WANT TO CHANGE.
```

---

# 1. Start With Git's Three Main Areas

Before learning recovery commands, return to the model you already know:

```text
HEAD / LOCAL REPOSITORY
Current committed state
        |
        v
STAGING AREA / INDEX
Proposed next commit
        |
        v
WORKING TREE
Files currently on disk
```

Suppose `app.py` has three possible versions:

```text
HEAD       Version A

INDEX      Version B

WORKING    Version C
```

That means:

* Version A is committed.
* Version B is staged.
* Version C is currently in your file.

If you say:

> Undo `app.py`.

Git needs more information conceptually.

Which version do you want?

Do you want:

```text
WORKING C -> B
```

or:

```text
INDEX B -> A
```

or:

```text
HEAD moved backward
```

or:

```text
a new commit that reverses an old commit
```

Those are completely different operations.

---

# 2. “Undo” Is Not One Git Operation

Consider these five mistakes.

### Mistake 1

You edit:

```text
app.py
```

but have not staged it.

You want to discard the edit.

### Mistake 2

You accidentally stage:

```text
config.yml
```

but want to keep your edits.

### Mistake 3

You commit with the message:

```text
Fix loggin bug
```

and notice the spelling mistake immediately.

### Mistake 4

You commit a configuration change, then realize the change itself was wrong.

### Mistake 5

You accidentally move your branch backward and think your latest commits disappeared.

All five can be described as:

```text
I need to undo something.
```

But they require different solutions.

---

# 3. The Beginner Undo Decision Model

Before running anything, ask:

```text
What exactly am I trying to undo?
```

Then identify where the problem exists.

```text
Is it only in my working tree?
        |
        +--> Consider git restore

Is it staged?
        |
        +--> Consider git restore --staged

Is it the latest local commit?
        |
        +--> Consider git commit --amend
             or an appropriate reset

Is it an existing commit that should remain in history?
        |
        +--> Consider git revert

Did I move my branch/history incorrectly?
        |
        +--> Inspect git reflog

Do I want to move the branch backward?
        |
        +--> Understand git reset first
```

This decision process is more important than memorizing command names.

# 5. Undoing Working-Directory Changes

Suppose your committed `app.py` contains:

```python
print("Application version 1")
```

You accidentally change it to:

```python
print("BROKEN EXPERIMENT")
```

Run:

```bash
git status
```

You should see:

```text
modified: app.py
```

The change is not staged.

Conceptually:

```text
HEAD
Version 1

INDEX
Version 1

WORKING TREE
BROKEN EXPERIMENT
```

You decide:

> I definitely do not want this experiment.

You can restore the file.

---

# 6. Using git restore

Run:

```bash
git restore app.py
```

Now inspect:

```bash
cat app.py
```

The file should again contain:

```python
print("Application version 1")
```

Check:

```bash
git status
```

The modification should be gone.

---

# 7. What git restore Did

In this example:

```bash
git restore app.py
```

restored the working-tree file using the staging area as the default source.

Before:

```text
HEAD       A
INDEX      A
WORKING    B
```

After:

```text
HEAD       A
INDEX      A
WORKING    A
```

The unstaged working-tree modification was discarded.

---

# 8. Important Warning About git restore

This command:

```bash
git restore app.py
```

can destroy unstaged work.

Suppose `app.py` contains two hours of changes that have never been:

* Committed
* Staged
* Copied elsewhere
* Saved by another recovery mechanism

If you restore over those changes, Git may not have a stored copy of them.

Therefore:

```text
git restore <file>
```

should not be treated as a harmless cleanup command.

Before using it, inspect:

```bash
git status
git diff app.py
```

Only restore when you are sure the current unstaged edits are unwanted.

# 9. Safe Working-Tree Undo Workflow

Suppose:

```bash
git status
```

shows:

```text
modified: config.yml
```

First inspect:

```bash
git diff config.yml
```

You may see:

```diff
-port: 8080
+port: 9999
```

Ask:

> Do I want to permanently discard this unstaged change?

If yes:

```bash
git restore config.yml
```

Then verify:

```bash
git status
```

and:

```bash
cat config.yml
```

The workflow is:

```text
Observe
   |
   v
git status
   |
   v
Inspect
git diff
   |
   v
Decide
   |
   v
git restore
   |
   v
Verify
```

# 10. Unstaging Files

Now consider a different problem.

You modify:

```text
config.yml
```

from:

```yaml
port: 8080
```

to:

```yaml
port: 9090
```

Then stage it:

```bash
git add config.yml
```

Run:

```bash
git status
```

The file appears under:

```text
Changes to be committed
```

Then you realize:

> I want to keep the change, but I do not want it in the next commit.

That is not a working-tree restoration problem.

It is a staging problem.

---

# 11. git restore --staged

Run:

```bash
git restore --staged config.yml
```

Then:

```bash
git status
```

The file should move from:

```text
Changes to be committed
```

to:

```text
Changes not staged for commit
```

Your edited content remains in the working tree.

---

# 12. What git restore --staged Does

Suppose:

```text
HEAD       A
INDEX      B
WORKING    B
```

Running:

```bash
git restore --staged config.yml
```

conceptually changes this to:

```text
HEAD       A
INDEX      A
WORKING    B
```

The staging area is restored to match HEAD for that path.

The working-tree edit remains.

---

# 13. Unstaging vs Discarding

This distinction must become automatic.

### Keep my changes but remove them from staging

```bash
git restore --staged file
```

### Discard my unstaged working-tree changes

```bash
git restore file
```

Think:

```text
git restore --staged
        |
        v
Changes INDEX
```

versus:

```text
git restore
        |
        v
Changes WORKING TREE
```

Do not confuse them.

---

# 14. Example: File Is Both Staged and Modified Again

This is where beginners can become confused.

Suppose:

```text
HEAD
port: 8080
```

You change it to:

```text
port: 9090
```

and stage:

```bash
git add config.yml
```

Then you edit it again:

```text
port: 7070
```

Now:

```text
HEAD       8080
INDEX      9090
WORKING    7070
```

Run:

```bash
git status
```

Git may show the same file as both staged and modified.

That is valid.

---

# 15. What Happens If You Unstage It?

Run:

```bash
git restore --staged config.yml
```

Conceptually:

```text
HEAD       8080
INDEX      8080
WORKING    7070
```

Your current working-tree version remains `7070`.

Now:

```bash
git diff
```

shows the difference between:

```text
8080
```

and:

```text
7070
```

Nothing in your current working file was discarded.

---

# 16. What Happens If You Restore the Working File Instead?

Return conceptually to:

```text
HEAD       8080
INDEX      9090
WORKING    7070
```

If you run:

```bash
git restore config.yml
```

Git restores the working tree from the index.

The result becomes:

```text
HEAD       8080
INDEX      9090
WORKING    9090
```

The `7070` working-tree edit is discarded.

This demonstrates why you must know:

```text
HEAD
INDEX
WORKING TREE
```

before undoing anything.

# 17. Correcting the Latest Commit

Suppose you create:

```bash
git commit -m "Add applicaton configuration"
```

Then immediately notice:

```text
applicaton
```

should be:

```text
application
```

You do not necessarily need to create another commit just to fix the message.

Git provides:

```bash
git commit --amend
```

---

# 18. What Does Amend Mean?

To **amend** means:

> Modify or replace the most recent commit.

This can be used to:

* Correct the latest commit message
* Add forgotten staged changes
* Remove something from the latest commit after preparing the corrected state
* Update the latest commit

But there is an important internal detail:

```text
Amending does not edit the old commit object in place.
```

Git creates a new commit that replaces it at the branch tip.

Because commit content and metadata contribute to the commit identifier, the amended commit gets a new ID.

---

# 19. Correcting the Latest Commit Message

Suppose:

```bash
git log --oneline
```

shows:

```text
a12bc34 Add applicaton configuration
```

You can run:

```bash
git commit --amend -m "Add application configuration"
```

Then:

```bash
git log --oneline
```

may show:

```text
f89de21 Add application configuration
```

Notice:

```text
a12bc34
```

became:

```text
f89de21
```

The commit ID changed.

---

# 20. Why Amend Changes the Commit ID

A commit contains information such as:

* Tree/snapshot
* Parent
* Author information
* Committer information
* Message

Changing the commit creates different commit data.

Therefore:

```text
Old commit
A
```

is replaced at the branch tip by:

```text
New commit
A'
```

Conceptually:

```text
Before:

X -> A
     ^
     main

After amend:

X -> A'
     ^
     main
```

The branch now points to the replacement commit.

---

# 21. Adding a Forgotten File to the Latest Commit

Suppose you intended to commit:

```text
app.py
README.md
```

but only staged:

```text
app.py
```

You commit:

```bash
git commit -m "Add health check"
```

Then notice that `README.md` was forgotten.

If this is still a local commit that is safe to amend:

```bash
git add README.md
git commit --amend --no-edit
```

The option:

```text
--no-edit
```

means:

> Reuse the existing commit message.

The new commit contains the corrected staged snapshot.

---

# 22. Inspect Before Amending

Before:

```bash
git commit --amend
```

run:

```bash
git status
```

and:

```bash
git diff --staged
```

Why?

Because staged changes are candidates for inclusion in the amended commit.

If unrelated files are staged accidentally, they may become part of the replacement commit.

A safe workflow is:

```text
git status
      |
      v
git diff --staged
      |
      v
Confirm intended changes
      |
      v
git commit --amend
      |
      v
git show HEAD
```

---

# 23. When Amend Becomes Risky

Amending rewrites the latest commit.

If the commit exists only locally and nobody else depends on it, this is often manageable.

But suppose you already pushed a commit and teammates built work on top of it.

Then you amend it.

You now have:

```text
Remote/shared history:

A -> B
```

while locally you created:

```text
A -> B'
```

`B` and `B'` are different commits.

This can create collaboration problems.

Beginner rule:

```text
Be cautious about amending commits
that have already been shared.
```

For shared history, creating a new corrective commit is often safer.

---

# 24. Undoing a Commit Without Erasing History

Suppose you have:

```text
A -> B -> C
```

Commit C introduced a bad configuration.

But C has already been shared with your team.

You want to reverse its effect while preserving the fact that C happened.

This is where:

```bash
git revert
```

becomes useful.

---

# 25. What git revert Does

`git revert` creates a new commit that applies the inverse of an earlier commit's changes.

Suppose:

```text
A -> B -> C
```

C changes:

```text
replicas: 3
```

to:

```text
replicas: 30
```

You revert C.

Git creates a new commit:

```text
A -> B -> C -> D
```

where D reverses C's effect.

Conceptually:

```text
C:
3 -> 30

D:
30 -> 3
```

History records both events.

---

# 26. Reverting a Commit

Find the commit:

```bash
git log --oneline
```

Suppose:

```text
7a3bc91 Increase replicas to 30
```

To reverse it:

```bash
git revert 7a3bc91
```

Git prepares and creates a new revert commit, typically opening an editor for the commit message unless configured otherwise or additional options are used.

Afterward:

```bash
git log --oneline
```

may resemble:

```text
d92f011 Revert "Increase replicas to 30"
7a3bc91 Increase replicas to 30
...
```

Both commits remain visible.

---

# 27. Why Revert Is Good for Shared History

Suppose your team already has:

```text
A -> B -> C
```

If you create:

```text
D = revert C
```

everyone can receive:

```text
A -> B -> C -> D
```

You have not pretended C never happened.

Instead, history says:

```text
C happened.
Then D intentionally reversed it.
```

This is useful for:

* Collaboration
* Auditing
* Incident investigation
* Production changes
* Shared branches

---

# 28. Revert Does Not Delete the Original Commit

This is important.

After:

```bash
git revert C
```

C still exists.

You now have:

```text
A -> B -> C -> D
```

where D counteracts C.

Therefore:

```text
git revert
```

is better understood as:

```text
Create a new reversing commit
```

rather than:

```text
Delete an old commit
```

---

# 29. Revert Can Have Conflicts

Suppose C changed:

```text
config.yml
```

but several later commits also modified the same lines.

When you try to revert C, Git may not be able to apply the inverse automatically.

You can encounter a conflict.

The basic reasoning becomes:

```text
Git attempted inverse change
        |
        v
Later content conflicts
        |
        v
Human decision required
```

You will learn conflict resolution deeply in Part 9.

For now, do not panic if a revert conflicts.

Read:

```bash
git status
```

carefully before taking further action.

---

# 30. Introducing git reset

Now we reach a command that requires more caution:

```bash
git reset
```

`git reset` can move the current branch reference to another commit.

Depending on the mode, it can also change:

* The staging area
* The working tree

This is why reset is powerful.

And why reset can be dangerous.

---

# 31. Reset Mental Model

Suppose history is:

```text
A -> B -> C
          ^
          main
          HEAD
```

You run a reset targeting B.

At the branch/history level, Git can move:

```text
main
```

from:

```text
C
```

back to:

```text
B
```

Conceptually:

```text
Before:

A -> B -> C
          ^
          main

After:

A -> B
     ^
     main

     C
```

Commit C may no longer be reachable through `main`.

But what happens to C's changes in the index and working tree depends on the reset mode.

---

# 32. The Three Reset Modes

The three modes beginners need to understand are:

```text
--soft
--mixed
--hard
```

Think of reset as affecting three levels:

```text
1. HEAD / branch
2. INDEX
3. WORKING TREE
```

The modes determine how far reset goes.

---

# 33. Reset Mode Table

A useful mental model:

| Reset Mode | Move HEAD/Branch | Reset Index | Reset Working Tree |
| ---------- | ---------------- | ----------- | ------------------ |
| `--soft`   | Yes              | No          | No                 |
| `--mixed`  | Yes              | Yes         | No                 |
| `--hard`   | Yes              | Yes         | Yes                |

This table is worth understanding, not merely memorizing.

---

# 34. Soft Reset

Suppose:

```text
A -> B -> C
          ^
          HEAD
```

You run:

```bash
git reset --soft HEAD~1
```

HEAD/your current branch moves from C to B.

But C's changes remain staged.

Conceptually:

```text
Before:

HEAD       C
INDEX      C
WORKING    C
```

After soft reset to B:

```text
HEAD       B
INDEX      C
WORKING    C
```

The commit is removed from the current branch history, but its changes remain ready to commit.

---

# 35. Why Use Soft Reset?

Suppose your latest local commit has the wrong logical structure.

Maybe you want to:

* Recommit it differently
* Combine it with another local change
* Change how the commit is organized
* Rebuild the latest local commit

You could use:

```bash
git reset --soft HEAD~1
```

and then inspect:

```bash
git status
git diff --staged
```

The former commit's changes remain staged.

---

# 36. Soft Reset Example

Create a commit:

```bash
echo "debug=true" >> config.yml
git add config.yml
git commit -m "Add debug configuration"
```

Check:

```bash
git log --oneline
```

Now:

```bash
git reset --soft HEAD~1
```

Check:

```bash
git status
```

The changes from the removed commit should appear staged.

Inspect:

```bash
git diff --staged
```

The file contents remain.

---

# 37. Mixed Reset

Mixed reset goes one step further.

Run:

```bash
git reset --mixed HEAD~1
```

or, because mixed is the default mode:

```bash
git reset HEAD~1
```

Conceptually:

```text
Before:

HEAD       C
INDEX      C
WORKING    C
```

After resetting to B:

```text
HEAD       B
INDEX      B
WORKING    C
```

The commit is removed from the current branch.

Its changes remain in your working tree.

But they are no longer staged.

---

# 38. Why Use Mixed Reset?

Suppose you made one messy local commit:

```text
Application fix
Documentation
Configuration experiment
```

You want to rebuild it into several atomic commits.

A mixed reset can return the committed changes to your working tree as unstaged changes.

Then:

```bash
git status
git diff
```

let you reorganize them.

You could stage and commit each logical change separately.

---

# 39. Mixed Reset Example

Suppose:

```text
A -> B -> C
```

C contains changes to:

```text
app.py
README.md
config.yml
```

Run:

```bash
git reset HEAD~1
```

Now C is no longer the current branch tip.

But your files still contain C's changes.

`git status` may show them as modified.

You can then stage:

```bash
git add app.py
```

commit:

```bash
git commit -m "Fix application startup"
```

then stage:

```bash
git add README.md
```

and continue rebuilding cleaner history.

---

# 40. Hard Reset

Now the dangerous one:

```bash
git reset --hard
```

Hard reset changes:

```text
HEAD / branch
INDEX
WORKING TREE
```

Suppose:

```text
HEAD       C
INDEX      C
WORKING    C + additional edits
```

You run:

```bash
git reset --hard HEAD~1
```

Git moves the branch to B and resets the index and tracked working-tree files to match B.

Conceptually:

```text
HEAD       B
INDEX      B
WORKING    B
```

The newer tracked working-tree changes can be lost.

---

# 41. Hard Reset Warning

Treat:

```bash
git reset --hard
```

as a destructive command.

Before running it:

```bash
git status
git diff
git diff --staged
git log --oneline
```

Understand:

* Which commit you are targeting
* Which staged changes exist
* Which unstaged changes exist
* Whether any current work is uncommitted
* Whether you need a backup

Do not run `--hard` simply because an online answer tells you it will “clean” your repository.

---

# 42. Why Hard Reset Is Dangerous

Imagine:

```text
HEAD:
Version A

INDEX:
Version B

WORKING TREE:
Version C
```

Version C contains two hours of unstaged work.

You run:

```bash
git reset --hard HEAD
```

The branch may remain at the same commit, but Git resets the index and tracked working tree to HEAD.

Result:

```text
HEAD       A
INDEX      A
WORKING    A
```

Version C may be gone.

This can happen even though you did not move to an older commit.

That is why:

```bash
git reset --hard HEAD
```

is still destructive.

---

# 43. Reset Does Not Necessarily Remove Untracked Files

A common beginner misconception is:

> `git reset --hard` deletes absolutely everything that is not committed.

Not exactly.

Hard reset resets tracked paths according to the target commit and index behavior.

Untracked files are a separate issue.

Do not use reset as a general mental substitute for:

```text
make my folder clean
```

Git has different commands and rules for untracked files.

We will handle ignored and untracked-file management more carefully later.

---

# 44. Visualizing All Three Reset Modes

Start:

```text
A -> B -> C
          ^
          HEAD

INDEX = C
WORKING = C
```

### Soft

```bash
git reset --soft HEAD~1
```

Result:

```text
HEAD = B
INDEX = C
WORKING = C
```

Meaning:

```text
Remove commit from current branch
Keep changes staged
```

### Mixed

```bash
git reset --mixed HEAD~1
```

Result:

```text
HEAD = B
INDEX = B
WORKING = C
```

Meaning:

```text
Remove commit from current branch
Keep changes unstaged
```

### Hard

```bash
git reset --hard HEAD~1
```

Result:

```text
HEAD = B
INDEX = B
WORKING = B
```

Meaning:

```text
Move branch backward
Reset staging area
Reset tracked working-tree state
```

---

# 45. A Simple Reset Memory Model

Think:

```text
SOFT
HEAD only
```

```text
MIXED
HEAD + INDEX
```

```text
HARD
HEAD + INDEX + WORKING TREE
```

Visual:

```text
             SOFT   MIXED   HARD

HEAD          X       X       X

INDEX                 X       X

WORKING TREE                  X
```

The further right you go, the more state Git changes.

---

# 46. When Reset Becomes Dangerous

Reset becomes especially dangerous when:

### 1. You use `--hard`

because working-tree changes can be overwritten.

### 2. You reset shared history

because teammates may still depend on commits you removed from your branch.

### 3. You do not inspect your current state first

because you may not know what will disappear.

### 4. You target the wrong commit

for example:

```bash
git reset --hard HEAD~5
```

when you intended:

```bash
git reset --hard HEAD~1
```

### 5. You assume commits are permanently deleted

and panic instead of checking the reflog.

---

# 47. Resetting Shared History

Suppose the shared branch contains:

```text
A -> B -> C
```

Your teammates already have C.

You locally run:

```bash
git reset --hard B
```

Your branch becomes:

```text
A -> B
```

But the remote and teammates may still have:

```text
A -> B -> C
```

You now have divergent history.

Fixing this by force-pushing can affect other people's work.

Beginner rule:

```text
Use reset mainly for local history
you control.

Prefer revert for shared history
when you need to reverse a commit safely.
```

---

# 48. Revert vs Reset

These commands solve different problems.

### Revert

```bash
git revert <commit>
```

creates a new commit that reverses an earlier commit.

History remains visible.

### Reset

```bash
git reset <commit>
```

moves the current branch reference and may also change the index and working tree.

History from the branch's perspective is rewritten.

---

# 49. Revert vs Reset Diagram

Suppose:

```text
A -> B -> C
```

### Revert C

```text
A -> B -> C -> D
```

where:

```text
D reverses C
```

History shows both.

### Reset to B

```text
A -> B
```

and C is no longer reachable from that branch.

These are fundamentally different approaches.

---

# 50. When Revert Is Usually Safer

Prefer considering revert when:

* The commit has been pushed
* Teammates may already have it
* The branch is shared
* You want an audit trail
* You want history to show both the mistake and correction
* You are reversing a production change

Example:

```text
Deploy configuration
        |
        v
Production incident
        |
        v
Revert configuration commit
```

History tells the complete operational story.

---

# 51. When Reset Can Be Appropriate

Reset can be useful when:

* The commits are local
* You control the history
* You understand the target commit
* You intentionally want to rebuild recent history
* You understand what will happen to the index
* You understand what will happen to the working tree

For beginners:

```text
soft and mixed reset
```

are usually easier to recover from than careless hard resets because they preserve more working data.

# 52. Recovery Scenario: “My Commit Disappeared”

Suppose history is:

```text
A -> B -> C
```

You accidentally run:

```bash
git reset --hard HEAD~1
```

Now:

```bash
git log --oneline
```

shows:

```text
B
A
```

You panic:

> Commit C has been deleted!

Do not immediately start creating new commits.

Git may still know where HEAD previously pointed.

This is where:

```bash
git reflog
```

becomes extremely useful.

---

# 53. Introduction to git reflog

`reflog` means:

```text
reference log
```

Git records updates to references such as HEAD in your local repository.

Run:

```bash
git reflog
```

You may see output resembling:

```text
8ab921f HEAD@{0}: reset: moving to HEAD~1
5cd771a HEAD@{1}: commit: Add health check
8ab921f HEAD@{2}: commit: Add configuration
...
```

Even though:

```bash
git log
```

may no longer show the lost commit as part of the current branch history, reflog may reveal the earlier HEAD position.

---

# 54. git log vs git reflog

This distinction matters.

### git log

Shows commit history reachable through the commit graph from the selected reference.

### git reflog

Shows recent local movements of references such as HEAD.

Think:

```text
git log
=
Where does project history currently lead?
```

```text
git reflog
=
Where has my local HEAD/reference recently been?
```

This makes reflog extremely useful for recovery.

---

# 55. Reflog Is Local

Reflog is primarily local repository information.

Do not think of it as a shared backup service.

Your teammate's reflog is not automatically your reflog.

A remote hosting platform is not a replacement for your local reflog either.

Also, reflog entries are not intended to be permanent historical records forever.

Git can eventually expire old reflog entries and prune unreachable objects.

Therefore:

```text
reflog is a recovery mechanism,
not permanent backup.
```

---

# 56. Reading git reflog

Example:

```text
5cd771a HEAD@{0}: reset: moving to HEAD~1
a93fc21 HEAD@{1}: commit: Add API health check
5cd771a HEAD@{2}: commit: Add application config
```

This tells you:

```text
HEAD@{0}
Current/recent position after reset

HEAD@{1}
Previous HEAD position

HEAD@{2}
Earlier HEAD position
```

The lost commit may still be identified by:

```text
a93fc21
```

# 57. Inspect Before Recovering

Suppose reflog shows:

```text
a93fc21 HEAD@{1}: commit: Add API health check
```

Do not immediately reset to it.

First inspect:

```bash
git show a93fc21
```

Verify:

* Commit message
* Files
* Diff
* Whether this is actually the commit you want

Recovery should follow:

```text
Find
   |
   v
Inspect
   |
   v
Confirm
   |
   v
Recover
   |
   v
Verify
```

not:

```text
Guess
   |
   v
Reset
```

# 58. Recovering a Lost Commit Safely With a Branch

Suppose:

```bash
git reflog
```

shows the lost commit:

```text
a93fc21
```

A cautious recovery technique is to create a branch pointing to it:

```bash
git branch recovered-work a93fc21
```

Then inspect:

```bash
git log --oneline recovered-work
```

and:

```bash
git show recovered-work
```

Now the commit has a named reference again.

This can be safer for a beginner than immediately moving the current branch.

---

# 59. Why a Recovery Branch Is Useful

Suppose:

```text
Current main:

A -> B
```

and reflog reveals:

```text
C
```

You create:

```bash
git branch recovered-work C
```

Now:

```text
A -> B
     \
      C
      ^
      recovered-work
```

You have preserved access to C.

You can inspect and decide what to do next without immediately rewriting `main` again.

---

# 60. Recovering the Branch Tip With Reset

If you are absolutely certain that your current branch should return to the recovered commit, you could reset the branch.

For example:

```bash
git reset --hard a93fc21
```

But remember:

```text
--hard
```

also affects the index and tracked working tree.

Therefore, inspect your current work first.

If there are valuable uncommitted changes, a hard reset could destroy them.

A recovery command can create a second problem if used carelessly.

# 61. Recovery Scenario: Accidentally Discarded Unstaged Work

Suppose you edit `app.py` for two hours.

You never stage or commit it.

Then run:

```bash
git restore app.py
```

The edits disappear.

Can `git reflog` recover them?

Usually, reflog is not designed to record every working-tree edit.

If Git never stored that content as an object through an operation such as staging or committing, Git may not have the data.

This is one of the hardest Git recovery situations.

---

# 62. Why Reflog Cannot Save Everything

Reflog records reference movement.

It does not record:

```text
every keystroke
every editor save
every working-tree version
```

Suppose:

```text
HEAD       A
INDEX      A
WORKING    B
```

and B has never entered Git's object database.

You discard B.

Reflog may know where HEAD was.

But HEAD never pointed to B.

Therefore, reflog cannot magically reconstruct content Git never recorded.

---

# 63. Recovery Scenario: Staged Work Was Lost

Staged content is different.

When you run:

```bash
git add file
```

Git typically stores the file content as an object and updates the index.

If you later lose the staging reference to that content, recovery may sometimes be possible through lower-level Git investigation.

However, this is not as straightforward as recovering a normal commit.

For beginner work, the lesson is:

```text
Do not depend on object-database archaeology.

Commit important work at sensible checkpoints.
```

We will not turn this beginner part into a low-level object recovery guide.

---

# 64. Recovery Scenario: Deleted Tracked File

Suppose `config.yml` exists in HEAD.

You accidentally run:

```bash
rm config.yml
```

Check:

```bash
git status
```

Git reports it as deleted.

If you want the committed/staged version back and the deletion is unstaged:

```bash

```

The file can be restored because Git already has a recorded version.

Verify:

```bash
ls
cat config.yml
git status
```

---

# 65. Recovery Scenario: Deleted Untracked File

Now suppose:

```text
notes.txt
```

was never tracked.

You delete it with your operating system.

Can Git restore it?

Usually not.

Git never recorded it.

This demonstrates the difference between:

```text
tracked data
```

and:

```text
untracked data
```

Git cannot act as history for files it never stored.

# 68. Recovery Scenario: Bad Shared Commit

Problem:

A commit has already reached the shared branch:

```text
A -> B -> C
```

C introduces a bad production setting.

Instead of deleting C from shared history, consider:

```bash

```

Result:

```text

```

D reverses C.

# 69. Recovery Scenario: Latest Local Commit Should Become Uncommitted Work

Suppose your latest local commit is:

```text
C
```

and you want to remove the commit but keep all its changes staged.

Use:

```bash
git reset --soft HEAD~1
```

Result:

```text

moves backward

Changes
remain staged
```

Then:

```bash

```

---

# 70. Recovery Scenario: Latest Local Commit Should Be Reorganized

Suppose C contains unrelated changes.

You want them back as unstaged working-tree changes.

Use:

```bash
git reset HEAD~1
```

Because mixed reset is the default.

Then:

```bash
git status
git diff
```

Now stage changes intentionally and rebuild atomic commits.

---

# 71. Recovery Scenario: Throw Away Latest Local Commit and Its Changes

This is the dangerous case.

If you deliberately want:

```text
Commit removed
+
Staging state removed
+
Tracked working-tree changes removed
```

you might use:

```bash
git reset --hard HEAD~1
```

But only after confirming that nothing valuable will be destroyed.

Before running it:

```bash
git status
git diff
git diff --staged
git log --oneline
```

If uncertain, do not use `--hard`.

---

# 72. Choosing the Safest Recovery Method

Use this decision process.

### Situation 1

Unstaged edit is unwanted.

Consider:

```bash
git restore file
```

after inspecting `git diff`.

### Situation 2

Staged edit should remain in the file but leave staging.

Consider:

```bash
git restore --staged file
```

### Situation 3

Latest local commit needs correction.

Consider:

```bash
git commit --amend
```

### Situation 4

Shared commit needs to be reversed.

Consider:

```bash
git revert <commit>
```

### Situation 5

Latest local commit should become staged changes.

Consider:

```bash
git reset --soft HEAD~1
```

### Situation 6

Latest local commit should become unstaged changes.

Consider:

```bash
git reset HEAD~1
```

### Situation 7

You think a commit disappeared.

Inspect:

```bash
git reflog
```

before doing anything destructive.

### Situation 8

You want to destroy local commit and working changes.

Only then consider:

```bash
git reset --hard
```

after careful verification.

# 73. Beginner Safety Hierarchy

When several methods could solve a problem, prefer the one that destroys the least information.

Think:

```text
Inspect first
      |
      v
Preserve data if possible
      |
      v
Create reversible correction
      |
      v
Rewrite local history only when appropriate
      |
      v
Destroy data only when absolutely intentional
```

A good recovery strategy is conservative.

# 74. The Recovery Rule: Stop Making the Situation Worse

When something appears lost:

```text
STOP
```

Do not immediately run five commands copied from a search result.

First:

```bash
git status
```

Then:

```bash

```

If history moved unexpectedly:

```bash

```

Inspect relevant commits:

```bash
git show <commit>
```

Only then choose a recovery operation.

Every additional destructive command can make investigation harder.

A sequence such as:

History is not only about having clean-looking commits.

It is also operational evidence.


```bash

```

# 93. Recovery Troubleshooting: “I Committed Too Early”

Ask:

```text
Was the commit shared?
```

If no, you may consider:

```text
git commit --amend
```

or:

```text
git reset --soft
```

or:

```text
git reset --mixed
```

depending on your goal.

If shared, rewriting it may affect collaborators.

A new corrective commit or revert may be safer.

---

# 94. Recovery Troubleshooting: “I Want to Undo an Old Commit”

Do not automatically reset your branch backward.

Suppose:

```text
A -> B -> C -> D -> E
```

and B introduced something you now want to reverse.

Resetting to A would also move away from:

```text
C
D
E
```

That is probably not what you want.

A revert of B may be more appropriate:

```bash
git revert <B>
```

Git attempts to create a new commit reversing B while preserving later history.

Conflicts are possible if later changes overlap.

---

# 95. Recovery Troubleshooting: “I Ran Hard Reset”

Do not panic.

First:

```bash
git reflog
```

If committed work disappeared from branch history, reflog may help locate it.

But understand:

```text
Committed work
```

and:

```text
unstaged working-tree work
```

are different.

Reflog may help recover the former.

It cannot guarantee recovery of unstaged content Git never stored.

| Situation                               | Likely Tool                 | Main Effect                                |
| --------------------------------------- | --------------------------- | ------------------------------------------ |
| Discard unwanted unstaged edit          | `git restore file`          | Changes working tree                       |

| Correct latest local commit             | `git commit --amend`        | Replaces latest commit                     |

| Find lost commit after history movement | `git reflog`                | Shows local reference history              |

This table is a guide.

Always inspect the repository state before executing a recovery command.

# 103. Part 7 Final Recap

Git does not have one universal undo command.

Instead, you must first determine:

```text
WHAT AM I TRYING TO UNDO?
```

Then identify where the problem exists:

```text
HEAD
 |
 v
INDEX
 |
 v
WORKING TREE
```

If you want to discard an unstaged working-tree change:

```bash
git restore file
```

But remember:

```text
This may destroy unstaged work.
```

If you want to keep your edits but remove them from staging:

```bash
git restore --staged file
```

If your latest local commit needs correction:

```bash
git commit --amend
```

If a shared commit needs to be reversed while preserving history:

```bash
git revert <commit>
```

If you intentionally need to move local history backward, understand the three reset modes:

```text
SOFT
HEAD
```

```text
MIXED
HEAD + INDEX
```

```text
HARD
HEAD + INDEX + WORKING TREE
```

Or visually:

```text
                SOFT    MIXED    HARD

HEAD              X       X        X
INDEX                      X        X
WORKING TREE                         X
```

The most dangerous of these is:

```bash
git reset --hard
```

because it can overwrite tracked working-tree changes.

You also learned the crucial difference between:

```text
REVERT
```

and:

```text
RESET
```

Revert:

```text
A -> B -> C
          |
          v
A -> B -> C -> D

D reverses C.
C remains in history.
```

Reset:

```text
A -> B -> C
          ^
          main
```

can become:

```text
A -> B
     ^
     main

C is no longer reached through main.
```

Finally, you learned that apparent history loss is not always permanent.

When a commit seems to disappear after operations such as reset:

```bash
git reflog
```

may reveal where HEAD previously pointed.

A safe recovery process is:

```text
STOP
  |
  v
git status
  |
  v
git log --oneline
  |
  v
git reflog
  |
  v
Find candidate commit
  |
  v
git show <commit>
  |
  v
Verify
  |
  v
Create recovery branch
  |
  v
Decide how to integrate
```

The central principle of Git recovery is:

```text
PRESERVE INFORMATION FIRST.
DESTROY INFORMATION ONLY
WHEN YOU ARE CERTAIN IT IS UNWANTED.
```

When something goes wrong, do not ask only:

```text
What command undoes this?
```

Ask:

```text
What state am I in?

What data does Git currently have?

What exactly do I want to preserve?

What exactly do I want to change?

Has this history been shared?

Which recovery method changes the least information?
```

That reasoning will prevent many of the Git mistakes that happen when engineers blindly copy reset, restore, or force commands.
