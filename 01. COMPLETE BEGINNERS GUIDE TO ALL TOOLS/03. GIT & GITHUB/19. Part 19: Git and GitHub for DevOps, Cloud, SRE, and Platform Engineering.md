## Part 19: Git and GitHub for DevOps, Cloud, SRE, and Platform Engineering

Parts 1 through 18 taught you how Git works.

You learned repositories, commits, branches, merges, pull requests, remotes, rebasing, recovery, troubleshooting, and collaboration.

Now the question changes.

Instead of asking:

> How do I use Git?

we ask:

> How do infrastructure and platform teams use Git to operate real systems safely?

For a DevOps, Cloud, SRE, or Platform Engineer, Git is not simply a place where application developers store source code.

Git may contain the instructions that define:

* Cloud infrastructure
* Kubernetes workloads
* Helm releases
* Configuration management
* CI/CD pipelines
* Monitoring configuration
* Infrastructure policies
* Deployment configuration
* Environment definitions
* Production changes

A commit can therefore represent much more than a code change.

It might represent:

```text
Create an AWS VPC.

Increase a Kubernetes Deployment from 3 to 6 replicas.

Change the production container image.

Add a firewall rule.

Upgrade a Helm chart.

Change an IAM policy.

Modify a CI/CD deployment pipeline.

Update an Ansible role.

Change an alert threshold.
```

That makes Git an important control point in modern infrastructure engineering.

This part teaches how all the Git knowledge you have built so far connects to practical DevOps work.

# 2. Git as the Foundation of Modern DevOps

DevOps is not simply:

```text
Developer writes code
        |
        v
Operations deploys code
```

Modern engineering teams try to make changes:

```text
Repeatable
Reviewable
Automated
Testable
Auditable
Recoverable
Consistent
```

Git supports all of these.

Imagine a team manually configuring servers.

Engineer A connects to Server 1:

```bash
ssh server1
```

and changes a configuration file.

Engineer B connects to Server 2 and makes a slightly different change.

Engineer C changes Server 3 next week.

Eventually:

```text
Server 1
Configuration A

Server 2
Configuration B

Server 3
Configuration C
```

Nobody is completely sure:

```text
Who changed what?

Why was it changed?

Which configuration is correct?

What should a new server look like?

How do we reproduce production?

How do we undo the last change?
```

This is one of the problems modern infrastructure practices try to solve.

Instead of relying entirely on manual configuration, teams increasingly represent infrastructure and operational configuration as files.

Those files can then be stored in Git.

```text
Engineer
   |
   v
Git repository
   |
   +--> Terraform
   |
   +--> Kubernetes YAML
   |
   +--> Helm
   |
   +--> Ansible
   |
   +--> CI/CD
   |
   +--> Monitoring configuration
   |
   +--> Policies
   |
   +--> Documentation
```

Now changes can follow:

```text
Change
   |
   v
Commit
   |
   v
Pull Request
   |
   v
Automated Validation
   |
   v
Human Review
   |
   v
Merge
   |
   v
Deployment/Reconciliation
   |
   v
Verification
```

That is much safer than an undocumented command entered manually on a production server.

# 3. Git Does Not Automatically Make Infrastructure Safe

This distinction matters.

Putting infrastructure files in Git does not automatically produce:

```text
Good DevOps
```

You can still:

* Commit secrets
* Merge dangerous Terraform changes
* Deploy broken Kubernetes manifests
* Give everyone administrator access
* Allow direct pushes to `main`
* Skip reviews
* Ignore failed tests
* Store Terraform state incorrectly
* Create pipelines with excessive permissions
* Roll back to configurations that are no longer compatible

Git provides mechanisms.

Your engineering process determines how safely those mechanisms are used.

# 4. Infrastructure as Code

Infrastructure as Code is commonly abbreviated:

```text
IaC
```

The basic idea is:

> Describe infrastructure using machine-readable configuration or code instead of relying primarily on manual infrastructure creation.

For example, instead of manually creating an AWS network through a web console, Terraform configuration might describe it:

```hcl
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}
```

This file expresses part of the desired infrastructure.

Because it is text, it can be:

```text
Stored
Versioned
Compared
Reviewed
Tested
Automated
Reused
```

with Git.

---

# 5. Why Infrastructure as Code and Git Work Well Together

Suppose version 1 contains:

```hcl
instance_type = "t3.small"
```

A pull request changes it to:

```hcl
instance_type = "t3.large"
```

Git can show:

```diff
- instance_type = "t3.small"
+ instance_type = "t3.large"
```

Now reviewers can ask:

```text
Why are we increasing instance size?

What will it cost?

Is the workload CPU constrained?

Will this replace the instance?

Will downtime occur?

Does autoscaling need adjustment?

Has this been tested?
```

Git gives the team a reviewable record of the proposed infrastructure change.

```text

```

# 7. Monorepository vs Multiple Repositories

You may hear:

```text
monorepo
```

A monorepo stores multiple related projects or infrastructure components in one repository.

Example:

```text
infrastructure/
├── networking/
├── kubernetes/
├── databases/
├── monitoring/
└── iam/
```

Another organization may separate them:

```text
networking-repo

kubernetes-repo

database-repo

monitoring-repo

iam-repo
```

Neither design is automatically correct.

Tradeoffs include:

* Team ownership
* Repository permissions
* Deployment independence
* CI/CD complexity
* Change coordination
* Security boundaries
* Repository size
* Review requirements

As a beginner, understand the principle before arguing about repository architecture:

> Infrastructure configuration should be organized so engineers can understand ownership, review changes, automate validation, and safely operate environments.

# 8. Terraform in Git

Terraform configuration is code and benefits from version control and code review. HashiCorp explicitly recommends storing Terraform configuration in version control, while warning against storing state files, credentials, and sensitive values there. ([HashiCorp Developer][1])

A small Terraform repository might look like:

```text
terraform/
├── README.md
├── .gitignore
├── versions.tf
├── providers.tf
├── variables.tf
├── main.tf
├── outputs.tf
└── .terraform.lock.hcl
```

Larger repositories may use modules and environment directories:

```text
terraform/
├── modules/
│   ├── vpc/
│   ├── eks/
│   └── database/
│
└── environments/
    ├── dev/
    ├── staging/
    └── production/
```

---

# 9. What Should Be Committed in Terraform?

Typically, source configuration belongs in Git.

Examples:

```text
main.tf
variables.tf
outputs.tf
providers.tf
versions.tf
modules/
README.md
.terraform.lock.hcl
```

HashiCorp's current style guidance specifically recommends committing Terraform code and `.terraform.lock.hcl`. ([HashiCorp Developer][2])

---

# 10. What Should Not Be Committed?

Common examples include:

```text
terraform.tfstate
terraform.tfstate.*
.terraform/
saved plan files
sensitive .tfvars files
credentials
```

Why?

Terraform state may contain sensitive infrastructure information and secrets. HashiCorp recommends remote state rather than storing state in version control, in part because normal version-control storage does not provide Terraform state locking and appropriate secure state handling. ([HashiCorp Developer][3])

A `.gitignore` might contain:

```gitignore
.terraform/
*.tfstate
*.tfstate.*
*.tfplan
*.tfvars
```

Do not blindly copy this into every project.

For example, some teams deliberately commit non-sensitive variable files.

The important question is:

> Does this file contain secrets or runtime-generated state that does not belong in Git?

# 11. Terraform Pull-Request Workflow

Imagine you need to add an application subnet.

Start from current `main`:

```bash
git switch main
git pull --ff-only
```

Create a branch:

```bash
git switch -c feature/add-app-subnet
```

Modify Terraform.

Then format:

```bash
terraform fmt -recursive
```

Validate:

```bash
terraform validate
```

Review Git changes:

```bash
git diff
```

Stage:

```bash
git add terraform/
```

Review staged changes:

```bash
git diff --staged
```

Commit:

```bash
git commit -m "Add application subnet"
```

Push:

```bash
git push -u origin feature/add-app-subnet
```

Then open a pull request.

# 12. Terraform Plan During Review

One of the most important Terraform review concepts is:

```bash
terraform plan
```

A pull request might change only a few lines of HCL, but the infrastructure effect could be substantial.

For example:

```text
Plan:
2 to add
1 to change
1 to destroy
```

The reviewer should not merely ask:

```text
Is the HCL syntax valid?
```

They should ask:

```text
Why is a resource being destroyed?

Is replacement expected?

Could this cause downtime?

Does this expose a network port?

Does this alter IAM permissions?

What will this cost?

Is state correctly configured?

Is the provider version appropriate?
```

Infrastructure review is about consequences, not just syntax.

# 13. Kubernetes Manifests in Git

Kubernetes objects can be described declaratively using YAML.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payments-api
  template:
    metadata:
      labels:
        app: payments-api
    spec:
      containers:
        - name: payments-api
          image: example/payments-api:1.4.2
          ports:
            - containerPort: 8080
```

If this lives in Git, a production change can become visible as a diff.

Example:

```diff
- replicas: 3
+ replicas: 6
```

or:

```diff
- image: example/payments-api:1.4.2
+ image: example/payments-api:1.4.3
```

Now you have a versioned record of the desired configuration.

# 15. Kubernetes Review Is Operational Review

Suppose a PR changes:

```diff
resources:
  limits:
-   memory: "512Mi"
+   memory: "128Mi"
```

A syntax validator may accept this.

But an experienced reviewer asks:

```text
How much memory does this workload actually use?

Will 128 MiB cause OOMKilled containers?

What metrics support this change?

What happened in staging?

Are requests also changing?

Could autoscaling behavior be affected?
```

Valid YAML is not necessarily safe production configuration.

# 16. Helm Charts in Git

Helm helps package and configure Kubernetes applications.

A Helm chart commonly contains files such as:

```text
payments-chart/
├── Chart.yaml
├── values.yaml
├── templates/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── ingress.yaml
└── charts/
```

`Chart.yaml` contains chart metadata.

`values.yaml` contains default configuration values.

`templates/` contains Kubernetes templates.

---

# 17. Why Helm Belongs in Git

Git can track changes such as:

```diff
replicaCount:
- 2
+ 4
```

or:

```diff
image:
  repository: company/payments
- tag: "2.4.0"
+ tag: "2.4.1"
```

A pull request now explains:

```text
What release changes?

Which image version?

What resources change?

What environment values change?
```

This becomes especially important in GitOps workflows.

# 18. Helm Validation

Depending on the project, pull-request automation may run commands such as:

```bash
helm lint ./helm/payments
```

and:

```bash
helm template payments ./helm/payments
```

The first can help identify chart problems.

The second renders templates so you can inspect the resulting Kubernetes YAML.

A strong infrastructure pipeline validates not only:

```text
Does the template parse?
```

but also:

```text
What will this template actually produce?
```

# 20. Inventory Does Not Mean Secrets Belong in Git

An inventory may describe systems:

```ini
[webservers]
web01.example.internal
web02.example.internal
```

That does not mean you should write:

```ini
ansible_password=SuperSecretPassword123
```

into a committed public file.

Sensitive data requires appropriate secret handling.

We will return to this later.

# 21. CI/CD Configuration in Git

CI/CD means:

```text
Continuous Integration
Continuous Delivery
Continuous Deployment
```

A modern pipeline is often defined as code.

Examples include:

```text
.github/workflows/*.yml

.gitlab-ci.yml

Jenkinsfile
```

These files describe automation.

Therefore:

```text
Changing the pipeline
```

# 22. Why Pipeline Configuration Belongs in Git

Imagine someone changes production deployment behavior from:

```text
deploy staging
```

to:

```text
deploy production
```

If pipeline configuration is versioned, Git can record:

```text
Who changed it

When

Why

Which PR reviewed it

Which checks ran

Which commit introduced it
```

That gives teams traceability.

But remember:

Pipeline files are powerful.

A malicious or careless pipeline modification could:

```text
Expose secrets

Modify cloud resources

Publish packages

Deploy production

Delete infrastructure

Change permissions
```

Treat CI/CD configuration as sensitive operational code.

# 23. GitHub Actions Introduction

[GitHub Actions workflows documentation](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows?utm_source=chatgpt.com)

GitHub Actions is GitHub's automation platform.

A workflow is a configurable automated process stored as YAML in:

```text
.github/workflows/
```

A workflow contains one or more jobs, and jobs contain steps that execute on runners. Workflows can be triggered by repository events, manual execution, schedules, and other supported events. ([GitHub Docs][4])

Example:

```text
repository/
└── .github/
    └── workflows/
        └── validate.yml
```

# 25. Basic GitHub Actions Workflow

Example:

```yaml
name: Validate Infrastructure

on:
  pull_request:
    branches:
      - main

jobs:
  validate:
    runs-on: ubuntu-latest

    steps:
      - name: Check out repository
        uses: actions/checkout@v4

      - name: Show repository files
        run: ls -la
```

Let's understand it.

---

# 26. `name`

```yaml
name: Validate Infrastructure
```

This gives the workflow a human-readable name.

---

# 27. `on`

```yaml
on:
  pull_request:
    branches:
      - main
```

`on` defines the trigger.

This example says:

> Run this workflow for matching pull-request activity targeting `main`.

GitHub Actions supports triggers such as `push`, `pull_request`, and manual `workflow_dispatch`, among many others. ([GitHub Docs][5])

---

# 28. `jobs`

```yaml
jobs:
```

A workflow contains jobs.

Here:

```yaml
validate:
```

is the job identifier.

---

# 29. `runs-on`

```yaml
runs-on: ubuntu-latest
```

This tells GitHub what runner environment the job requires.

The runner is the machine/environment executing the job.

---

# 30. `steps`

```yaml
steps:
```

Steps are actions performed inside the job.

For example:

```yaml
- name: Show repository files
  run: ls -la
```

runs a shell command.

---

# 31. Why Checkout Is Necessary

A runner does not automatically mean your repository files are ready for your commands.

This step:

```yaml
- name: Check out repository
  uses: actions/checkout@v4
```

uses the checkout action to make repository content available to subsequent workflow steps.

Then:

```yaml
run: ls -la
```

can inspect it.

# 39. Status Checks

GitHub status checks communicate whether commits meet configured conditions. Checks may come from GitHub Actions or other integrations, and protected branches can require selected checks before a PR is mergeable. ([GitHub Docs][6])

Imagine:

```text
Terraform Format       ✓
Terraform Validate     ✓
Terraform Plan         ✓
Security Scan          ✓
Policy Check           ✗
```

The change should not be treated as safe simply because four checks passed.

The failed policy check needs investigation.

# 40. Code Review for Infrastructure

Infrastructure code review deserves a different mindset from reviewing a spelling correction in documentation.

Suppose Terraform changes:

```diff
cidr_blocks = [
- "10.20.0.0/16"
+ "0.0.0.0/0"
]
```

Syntax may be valid.

Terraform may plan successfully.

But the security impact may be severe.

The reviewer needs to understand:

```text
What resource is exposed?

Which port?

Is public access intentional?

What compensating controls exist?

Is authentication present?

What is the business requirement?
```

---

# 41. Infrastructure Review Checklist

When reviewing infrastructure, ask questions in several categories.

### Scope

```text
What is changing?

Which environment?

Which services?

Which cloud account/project/subscription?
```

### Infrastructure effect

```text
Create?

Update?

Replace?

Destroy?
```

### Availability

```text
Could this cause downtime?

Will pods restart?

Will instances be replaced?

Will traffic be interrupted?
```

### Security

```text
Are ports exposed?

Are IAM privileges increased?

Are secrets involved?

Are encryption settings changing?
```

### Data

```text
Could a database or volume be deleted?

Does replacement destroy data?

Is a backup required?
```

### Cost

```text
Does capacity increase?

Are expensive services introduced?

Could autoscaling expand unexpectedly?
```

### Rollback

```text
Can this change be reversed?

Would reverting Git actually restore the previous system?
```

# 42. Never Approve Infrastructure Just Because the Diff Is Small

A one-line change can have a huge effect.

Example:

```diff
- deletion_protection = true
+ deletion_protection = false
```

Another:

```diff
- replicas = 10
+ replicas = 1
```

Another:

```diff
- environment = "staging"
+ environment = "production"
```

Line count does not measure operational risk.

# 43. Environment Branches

Some teams use branches such as:

```text
development

staging

production
```

Conceptually:

```text
development
    |
    v
staging
    |
    v

```

A change is promoted by merging between environment branches.

This seems intuitive because each branch appears to represent an environment.

But there are tradeoffs.

---

# 44. Advantages of Environment Branches

Potential advantages:

```text
Environment state is easy to conceptualize.

Promotion can be represented as merges.

Permissions can differ by branch.

Production can have stricter controls.
```

For beginners, the mental model may seem simple:

```text
What's on production branch
=
what production should run
```

---

# 45. Problems With Environment Branches

Over time, branches may diverge:

```text
development:
A B C D E F

staging:
A B C D

production:
A B
```

Then emergency fixes occur:

```text
production:
A B H
```

Now:

```text
development:
A B C D E F

staging:
A B C D

production:
A B H
```

Promotion becomes harder.

Teams can experience:

```text
Merge conflicts

Environment drift

Hotfix confusion

Different histories

Unclear promotion paths
```

---

# 46. Alternative Environment Designs

Some teams keep a single main branch and represent environments through directories:

```text
environments/
├── dev/
├── staging/
└── production/
```

Others use:

```text
base configuration

overlays

Helm values

Terraform directories

workspaces

separate repositories
```

There is no universal answer.

The key question is:

> Can we clearly determine the desired state of each environment, review changes, promote safely, and avoid uncontrolled drift?

---

# 47. GitOps Fundamentals

GitOps builds on concepts you already know.

OpenGitOps describes four core principles:

1. Desired state is declarative.
2. Desired state is versioned and immutable.
3. Software agents automatically pull desired-state declarations.
4. Agents continuously reconcile actual state toward desired state. ([Open GitOps][7])

This deserves careful explanation.

---

# 48. Declarative Desired State

Suppose Git contains:

```yaml
spec:
  replicas: 5
```

This says:

```text
I want five replicas.
```

It does not necessarily describe every low-level command required to reach five.

That is declarative configuration.

You declare the desired outcome.

---

# 49. Versioned Desired State

Because the configuration lives in Git:

```text
Commit A:
replicas = 3

Commit B:
replicas = 5

Commit C:
replicas = 6
```

Git preserves history.

You can answer:

```text
When did desired capacity change?

Who proposed it?

Why?

Which PR approved it?

What was the previous value?
```

---

# 50. Automatically Pulled

A GitOps-style controller can observe the desired configuration stored in Git and pull it.

Conceptually:

```text
Git repository
      |
      | pull
      v
GitOps controller
      |
      v
Kubernetes cluster
```

This differs from a simplistic push model such as:

```text
CI server
   |
   | kubectl apply
   v
cluster
```

The GitOps agent operates from the environment side and reconciles against the declared source.

---

# 51. Continuous Reconciliation

Suppose Git says:

```text
replicas = 5
```

but someone manually changes the cluster:

```bash
kubectl scale deployment payments --replicas=2
```

Now:

```text
Git desired state:
5

Cluster actual state:
2
```

A reconciler detects:

```text
desired != actual
```

and attempts to restore:

```text
actual -> desired
```

Conceptually:

```text
Git
Desired = 5
     |
     v
Controller
     |
     | compare
     v
Cluster
Actual = 2
     |
     v
Reconcile
     |
     v
Actual = 5
```

That is a core GitOps idea.

---

# 52. Git as a Source of Truth

You will frequently hear:

```text
Git is the source of truth.
```

This does not mean:

```text
Git contains literally everything.
```

It means Git contains the authoritative versioned desired configuration for the system within the defined GitOps scope.

Suppose Git says:

```text
payments replicas = 5
```

but a person manually changes the cluster to:

```text
payments replicas = 8
```

Which is authoritative?

In a properly designed GitOps system:

```text
Git = desired state
```

The manual change represents drift unless Git is updated appropriately.

---

# 53. Why Source of Truth Matters

Without an authoritative source:

```text
Git says 5.

Cluster says 8.

Wiki says 4.

Engineer says 6.

Old deployment script says 3.
```

Which is correct?

A source-of-truth model tries to eliminate that ambiguity.

---

# 54. GitOps Does Not Mean Put Everything in Git

This is critical.

Do not conclude:

```text
Git is source of truth
therefore
passwords should be plain text in Git.
```

No.

Git may store references or encrypted representations depending on architecture, but plain-text credentials should not simply be committed because you are using GitOps.

Source of truth does not override secret-management principles.

---

# 55. Secrets and Infrastructure Repositories

Infrastructure frequently needs credentials:

```text
Cloud credentials

Database passwords

API tokens

TLS private keys

Registry credentials

SSH keys

Third-party tokens
```

The dangerous beginner approach is:

```yaml
database:
  username: admin
  password: SuperSecretPassword123
```

and then:

```bash
git add .
git commit
git push
```

Do not do this.

---

# 56. `.gitignore` Is Helpful but Not a Secret Manager

You can ignore files such as:

```gitignore
.env
*.tfstate
secret.tfvars
credentials.json
```

That reduces accidental commits.

But `.gitignore` does not:

```text
Encrypt secrets

Rotate secrets

Manage access

Remove previously committed secrets

Prevent someone from force-adding an ignored file
```

It is only one preventive layer.

---

# 57. Terraform Secrets Require Extra Care

Terraform deserves particular attention because sensitive values may enter state.

Marking a Terraform value as `sensitive` can hide it from normal CLI/UI display, but that does not necessarily mean the value is absent from state. HashiCorp explicitly warns that state and plan files can contain sensitive information and should be protected accordingly. ([HashiCorp Developer][3])

Therefore:

```text
sensitive = true
```

does not mean:

```text
secret no longer exists anywhere
```

Understand where the value is stored.

---

# 58. Better Secret Sources

Depending on architecture, secrets may come from systems such as:

```text
Cloud secret managers

Vault systems

CI/CD secret stores

GitHub Actions secrets

Kubernetes secret-management integrations

External secret operators

Identity federation
```

A better pattern is often:

```text
Git contains configuration/reference
          |
          v
Runtime obtains credential securely
          |
          v
Application/infrastructure uses secret
```

rather than:

```text
Git contains plaintext password
```

---

# 59. Short-Lived Credentials

A mature pipeline often tries to avoid long-lived cloud credentials.

Conceptually:

```text
GitHub Actions
      |
      v
Identity provider
      |
      v
Temporary cloud credentials
      |
      v
Deployment
```

This can reduce the risk associated with storing permanent credentials.

As a beginner, the key principle is:

> Pipelines need identity, but that does not mean you should hard-code long-lived credentials into repository files.

---

# 60. Repository Permissions

A production infrastructure repository is powerful.

If changing:

```text
terraform/production/
```

can modify a production AWS account, repository write access indirectly carries operational power.

Therefore repository permissions matter.

Ask:

```text
Who can read?

Who can write?

Who can merge?

Who can administer?

Who can modify repository rules?

Who can change workflows?

Who can approve production deployment?

Who can access secrets?
```

---

# 61. Least Privilege

The security principle is:

```text
Give only the access required to perform the job.
```

Not:

```text
Everyone is admin because it is easier.
```

Examples:

```text
Developer needs read access?
Do not automatically grant admin.

Engineer needs PR creation?
Do not automatically allow production bypass.

Automation needs package read access?
Do not automatically grant repository write access.
```

Permissions should match responsibilities.

# 62. Why Direct Pushes to Production Branches Are Risky

Imagine:

```text
main = production source
```

An engineer runs:

```bash
git push origin main
```

and the pipeline automatically deploys.

If direct pushes are unrestricted:

```text
Engineer
   |
   v
main
   |
   v
Production
```

there may be no mandatory:

```text
Peer review

Automated validation

Security check

Approval
```

A protected workflow is safer:

```text
Engineer
   |
   v
Feature branch
   |
   v
Pull Request
   |
   +--> checks
   |
   +--> review
   |
   +--> approval
   |
   v
main
   |
   v
controlled deployment
```

# 63. Branch Protection

[GitHub protected branches documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches?utm_source=chatgpt.com)

GitHub branch protection can enforce controls on important branches. Current protections can include required pull-request reviews, required status checks, conversation resolution, signed commits, linear history, deployment requirements, restrictions on pushes, and controls over force pushes and deletions. ([GitHub Docs][8])

For a production `main` branch, you might require:

```text
Pull request before merge

At least one approval

Infrastructure validation

Security scan

Code-owner approval

Resolved review conversations

No force pushes
```

---

# 64. Rulesets

GitHub also provides repository rulesets.

Rulesets can enforce repository policies such as:

```text
Require pull requests

Require status checks

Block force pushes

Require code scanning

Restrict certain file paths or file sizes
```

and can target branches or tags according to configuration. ([GitHub Docs][9])

For beginners, think of branch protections and rulesets as:

```text
Repository guardrails
```

They move safety from:

```text
Please remember not to do this.
```

toward:

```text
The repository enforces this requirement.
```

Weak:

```text

```

Better:

```text

    |

    |
   fail
    |
```

Weak:

```text

```

Better:

```text

      |

      |

```

Automation reduces dependence on human memory.

# 66. CODEOWNERS

[GitHub CODEOWNERS documentation](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners?utm_source=chatgpt.com)

A `CODEOWNERS` file associates files or paths with people or teams responsible for them.

GitHub can automatically request code-owner reviews when a pull request changes owned files, and repository protections can require code-owner approval. ([GitHub Docs][10])

A common location is:

```text

```

GitHub also supports a `CODEOWNERS` file in the repository root or `docs/`, using its documented lookup order. ([GitHub Docs][10])

```text
        |
```

# 68. Why CODEOWNERS Matters for Infrastructure

Imagine a developer modifies:

```text

```

The application team may understand why they want the permission.

But the security/platform team may understand:

```text

cross-account trust

wildcard actions

resource scoping

service roles
```

CODEOWNERS helps route the change to the people responsible for that infrastructure area.

---

# 69. CODEOWNERS Is Not Automatically an Approval Requirement

This distinction is important.

Defining ownership can trigger review requests.

But if you want code-owner approval to be mandatory before merge, repository protection must be configured accordingly. ([GitHub Docs][8])

Think:

```text
CODEOWNERS
    |
    v
Who should review?

Protection rule
    |
    v
Must they approve?
```

---

# 70. Protect the CODEOWNERS File

There is a subtle security issue.

If someone can freely modify:

```text
.github/CODEOWNERS
```

they might try to weaken ownership requirements.

GitHub recommends protecting the `CODEOWNERS` file itself by assigning an owner to it or its containing directory. ([GitHub Docs][10])

For example:

```text
/.github/ @company/platform-admins
```

Now changes to governance configuration itself have an owner.

# 76. Production Change Workflow

Consider a real change:

> Increase production payments service memory because pods are being OOMKilled.

The production process should not begin with:

```bash
kubectl edit deployment payments
```

unless an incident genuinely requires an emergency manual action under your organization's process.

A normal controlled workflow might begin with evidence.

---

# 77. Step 1: Observe the Problem

Monitoring shows:

```text
payments-api

OOMKilled: 37 times in 2 hours
```

Engineer investigates:

```text
Memory usage approaching limit before termination.
```

Current configuration:

```yaml
resources:
  requests:
    memory: "256Mi"
  limits:
    memory: "512Mi"
```

Evidence suggests the limit needs adjustment.

---

# 78. Step 2: Update Local Repository

```bash
git switch main
git pull --ff-only
```

Why?

You want to start from the latest approved state.

---

# 79. Step 3: Create Change Branch

```bash
git switch -c fix/payments-memory-limit
```

Why?

The production change remains isolated from `main` until validated and reviewed.

---

# 80. Step 4: Modify Configuration

Change:

```diff
resources:
  requests:
    memory: "256Mi"
  limits:
-   memory: "512Mi"
+   memory: "768Mi"
```

Do not blindly assume this value is correct.

It should be supported by observed workload behavior and team capacity policy.

---

# 81. Step 5: Review Locally

```bash
git diff
```

Ask:

```text
Did I modify only the intended deployment?

Did my editor change unrelated formatting?

Did I accidentally change staging?

Did I alter another service?
```

# 82. Step 6: Validate

Depending on the repository:

```text

Kubernetes schema validation

Helm rendering

policy checks

tests
```

may run locally and again in CI.

---

# 83. Step 7: Commit

```bash
git add kubernetes/production/payments/deployment.yaml
```

Review:

```bash
git diff --staged
```

Commit:

```bash
git commit -m "Increase payments memory limit"
```

---

# 84. Step 8: Push

```bash
git push -u origin fix/payments-memory-limit
```

---

# 85. Step 9: Pull Request

A useful PR description might explain:

```text

Change:

Validation:
Manifest validation passed.

Risk:

```

This gives reviewers operational context.

# 86. Step 10: Automated Checks

CI runs:

```text

policy checks

```

If anything fails:

```text

```

Understand the failure.

Only after:


# 91. Rollbacks Using Git

Suppose commit:

```text
a8c291f Increase payments memory limit
```

causes an unexpected problem.

A beginner may think:

```text
Rollback = git reset main backward.
```

That is often the wrong approach for shared history.

For a shared production branch, a safer Git strategy is often to create a new commit that reverses the problematic commit.

For example:

```bash
git revert a8c291f
```

This creates a new commit that attempts to reverse the changes introduced by the target commit.

History remains visible.

---

# 92. Rollback History

Before:

```text
A---B---C
        ^
        |
     bad change
```

After revert:

```text
A---B---C---D
            ^
            |
         revert C
```

History tells the story:

```text
C:
Change introduced

D:
Change reversed
```

This is often much safer for shared production history than erasing C.

---

# 93. Git Revert Does Not Guarantee Operational Rollback

This is one of the most important production lessons in this chapter.

Suppose Terraform changed:

```text
Database engine version 14
->
Database engine version 15
```

You cannot automatically assume reverting the Git commit will safely downgrade the database.

Likewise:

```text
database migration

persistent data change

deleted storage

external API change

irreversible cloud operation

certificate rotation
```

may not be safely reversible by Git alone.

Therefore:

```text
Git rollback
```

and:

```text
system rollback
```

are related but not identical.

---

# 94. Rollback Must Be Designed

Before production deployment, ask:

```text
Can we revert this?

What happens to data?

Will the platform permit downgrade?

Does the old application understand the new schema?

Are old artifacts still available?

Will Terraform recreate resources?

Will Kubernetes accept the previous configuration?

Do we need restore from backup?
```

Rollback is part of change design.

Not an afterthought.

---

# 95. Emergency Production Changes

Sometimes production is actively failing.

The normal process may be too slow.

Organizations may have emergency procedures.

For example:

```text
Incident declared
      |
      v
Authorized emergency change
      |
      v
Mitigation
      |
      v
Verify service recovery
      |
      v
Backfill Git/change record
      |
      v

```

The dangerous approach is:

```text

      |
      v

      |

```

Speed does not require chaos.


# 117. Common Beginner Mistakes

### Mistake 1: Treating infrastructure Git like personal code

```text
I'll just push directly to main.
```

Production infrastructure deserves stronger controls.

### Mistake 2: Committing Terraform state

State can contain sensitive data and requires specialized storage and locking behavior. Do not use ordinary Git version control as the state backend. ([HashiCorp Developer][3])

### Mistake 3: Committing credentials

Never solve automation convenience by hard-coding secrets into Git.

### Mistake 4: Reviewing only syntax

Valid infrastructure can still be dangerous.

### Mistake 5: Ignoring Terraform plan

A small HCL diff can produce destructive infrastructure operations.

### Mistake 6: Approving because CI passed

Automation does not understand every business or operational consequence.

### Mistake 7: Merging because a human approved

Humans miss problems too. Automated checks provide another layer.

### Mistake 8: Giving everyone admin permissions

Use least privilege.

### Mistake 9: Leaving `main` unprotected

Important infrastructure branches should have appropriate guardrails.

### Mistake 10: Using CODEOWNERS without understanding protections

Ownership and mandatory approval are related but separate controls.

### Mistake 11: Assuming GitOps means storing plaintext secrets in Git

It does not.

### Mistake 12: Manually changing production and forgetting Git

This creates drift from the desired state.

### Mistake 13: Assuming a Git revert guarantees infrastructure rollback

Some operational changes are not safely reversible.

### Mistake 14: Deploying without verifying

Pipeline success is not the same as application health.

### Mistake 15: Using environment branches without considering divergence

Environment branches can work, but they have operational tradeoffs.
