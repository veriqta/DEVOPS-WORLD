# Part 12: HTTP, HTTPS, TLS, and Web Networking

## Follow a Request From Browser to Web Server

By this point, you have built most of the networking foundation required to understand what happens when someone opens a website.

You already know that a client may need to:

```text
Receive configuration through DHCP
        |
        v
Resolve a hostname through DNS
        |
        v
Determine whether the destination is local or remote
        |
        v
Use its routing table and default gateway
        |
        v
Resolve the local next-hop MAC address
        |
        v
Possibly pass through NAT/PAT
        |
        v
Establish transport-layer communication
```

But none of that explains what the browser actually says to the web server.

If you enter:

```text
https://www.example.com/products?id=42
```

the network may successfully deliver packets to the server, but the application still needs a protocol that defines things such as:

```text
What resource do I want?

What operation am I requesting?

What information am I sending?

Did the request succeed?

What content is being returned?
```

For the Web, that protocol is primarily:

```text
HTTP
```

When HTTP is protected with TLS, we commonly call it:

```text
HTTPS
```

This part connects DNS, routing, TCP/UDP, ports, encryption, certificates, and application behavior into one complete web request.

---

# 1. Application-Layer Networking

HTTP operates at the application layer.

A simplified networking stack might look like:

```text
Application
HTTP / HTTPS
     |
     v
Transport
TCP or QUIC
     |
     v
Network
IP
     |
     v
Data Link
Ethernet / Wi-Fi
     |
     v
Physical transmission
```

Each layer solves a different problem.

HTTP answers questions such as:

```text
Which resource does the client want?

Which method is being used?

What headers accompany the request?

What status did the server return?

What application data is in the response?
```

TCP, IP, Ethernet, and DNS solve different problems.

---

# 2. HTTP Does Not Replace TCP or IP

A beginner may think:

> The browser sends an HTTP request to the server.

That is correct at the application level.

But underneath, considerably more happens.

For traditional HTTPS over TCP:

```text
HTTP message
    |
    v
TLS
    |
    v
TCP
    |
    v
IP
    |
    v
Ethernet / Wi-Fi
```

Each layer encapsulates the information needed by the layer below it.

When troubleshooting a web application, you need to determine which layer is failing.

---

# 3. What Is HTTP?

HTTP stands for:

```text
Hypertext Transfer Protocol
```

It is an application-layer protocol used for communication between clients and servers.

The basic model is:

```text
Client
   |
   | HTTP Request
   v
Server
   |
   | HTTP Response
   v
Client
```

A browser is a common HTTP client.

But HTTP clients also include:

```text
curl
Mobile applications
API clients
Monitoring systems
Load balancers
Reverse proxies
Other backend services
Command-line tools
```

---

# 4. HTTP Is a Request-Response Protocol

At its core:

```text
Client requests something.

Server responds.
```

For example:

```text
Browser
   |
   | GET /products
   v
Web Server
   |
   | 200 OK
   | HTML / JSON / other content
   v
Browser
```

The client initiates an HTTP request.

The server processes it and returns an HTTP response.

---

# 5. A Simplified HTTP Request

An HTTP/1.1 request might conceptually look like:

```http
GET /products HTTP/1.1
Host: shop.example.com
User-Agent: ExampleBrowser
Accept: text/html
```

This tells the server things such as:

```text
Method:
GET

Resource:
/products

HTTP version:
HTTP/1.1

Target host:
shop.example.com
```

---

# 6. A Simplified HTTP Response

The server might respond:

```http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1234

<html>
...
</html>
```

Conceptually:

```text
Status:
200 OK

Content type:
text/html

Body:
HTML document
```

The browser then interprets the response.

---

# 7. HTTP Is More Than Websites

HTTP is heavily associated with websites, but it is also fundamental to APIs.

For example:

```text
Mobile App
    |
    | HTTPS
    v
API
```

or:

```text
Frontend
    |
    | GET /api/users/42
    v
Backend API
    |
    | JSON
    v
Frontend
```

Modern distributed systems use HTTP extensively for service-to-service communication.

---

# 8. What Is a URL?

URL stands for:

```text
Uniform Resource Locator
```

Consider:

```text
https://shop.example.com:443/products/42?currency=USD
```

We can break it into components:

```text
https
  |
  +-- Scheme

shop.example.com
  |
  +-- Hostname

443
 |
 +-- Port

/products/42
      |
      +-- Path

currency=USD
      |
      +-- Query string
```

Understanding URL structure is extremely useful for web troubleshooting.

---

# 9. URI Basics

URI stands for:

```text
Uniform Resource Identifier
```

A URI identifies a resource.

A URL is a type of URI that also provides information used to locate/access a resource.

For beginner networking work, you will frequently encounter URLs such as:

```text
https://api.example.com/users/42
```

You do not need to become trapped in terminology debates.

The practical goal is to recognize the components and understand how they influence network and application behavior.

---

# 10. The Scheme

In:

```text
https://example.com/products
```

the scheme is:

```text
https
```

It tells the client which protocol or access mechanism should be used.

Examples include:

```text
http
https
```

For HTTP:

```text
http://example.com
```

For HTTPS:

```text
https://example.com
```

The scheme matters because HTTPS introduces TLS.

---

# 11. The Hostname

In:

```text
https://api.example.com/users
```

the hostname is:

```text
api.example.com
```

The client generally needs to determine an IP address for this hostname.

That leads back to DNS.

```text
api.example.com
       |
       v
DNS
       |
       v
203.0.113.20
```

A DNS failure can therefore prevent the HTTP request from ever reaching the HTTP stage.

---

# 12. The Port

A URL can explicitly contain a port.

Example:

```text
https://example.com:8443/app
```

Port:

```text
8443
```

If the port is omitted, the client normally uses the default associated with the scheme.

Common defaults:

```text
HTTP
TCP 80

HTTPS
TCP 443
```

But HTTPS is not technically restricted to port 443.

You could run HTTPS on:

```text
8443
9443
10443
```

or another permitted port.

---

# 13. The Path

Consider:

```text
https://example.com/products/42
```

The path is:

```text
/products/42
```

It identifies the requested resource or application route.

Different paths may be handled differently:

```text
/
/login
/products
/products/42
/api/users
/health
```

A server can be reachable while one particular path is broken.

This distinction is important.

---

# 14. Query Strings

Consider:

```text
https://shop.example.com/search?q=laptop&page=2
```

The query component is:

```text
q=laptop&page=2
```

It contains parameters associated with the request.

Conceptually:

```text
q = laptop
page = 2
```

Applications can use query parameters for:

```text
Search
Filtering
Pagination
Sorting
Feature selection
Other application-specific input
```

---

# 15. URL Example

Consider:

```text
https://api.example.com:8443/v1/users?id=42
```

Breakdown:

```text
Scheme:
https

Hostname:
api.example.com

Port:
8443

Path:
/v1/users

Query:
id=42
```

This simple decomposition already tells you a lot about what the client will attempt.

---

# 16. HTTP Methods

HTTP methods describe the intended semantics of a request.

Common methods include:

```text
GET
POST
PUT
PATCH
DELETE
HEAD
```

There are others, but these are important starting points.

---

# 17. GET

GET is used to retrieve a representation of a resource.

Example:

```http
GET /products/42 HTTP/1.1
Host: shop.example.com
```

Conceptually:

```text
"Give me product 42."
```

A successful response might be:

```text
200 OK
```

with the product data.

---

# 18. GET Should Be Safe

HTTP defines GET as a safe method.

That means the intended semantics are retrieval rather than changing server state.

For example:

```text
GET /account
```

should not conceptually mean:

```text
Delete my account.
```

Application implementations can be badly designed, but understanding the protocol semantics matters.

---

# 19. POST

POST commonly submits data for processing or creates something according to the application's API design.

Example:

```http
POST /orders HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"product_id":42,"quantity":1}
```

Conceptually:

```text
"Process this data as a new order."
```

The exact meaning is defined by the application.

---

# 20. PUT

PUT commonly creates or replaces the state of a resource at the specified target.

Example:

```http
PUT /users/42 HTTP/1.1
Content-Type: application/json

{"name":"Ada","role":"engineer"}
```

Conceptually:

```text
"Make resource /users/42
have this representation."
```

---

# 21. PATCH

PATCH is commonly used for partial modifications.

Example:

```http
PATCH /users/42 HTTP/1.1
Content-Type: application/json

{"role":"manager"}
```

Conceptually:

```text
"Modify this part of user 42."
```

This differs from the typical full-replacement semantics associated with PUT.

---

# 22. DELETE

DELETE requests removal of the target resource according to the application's semantics.

Example:

```http
DELETE /users/42 HTTP/1.1
Host: api.example.com
```

Conceptually:

```text
"Delete user 42."
```

Authorization still determines whether the client is permitted to do this.

---

# 23. HEAD

HEAD behaves similarly to GET but asks for response metadata without the response content body.

Example:

```http
HEAD /large-file.zip HTTP/1.1
Host: downloads.example.com
```

A response may contain:

```text
Content-Type
Content-Length
Last-Modified
ETag
```

without transferring the representation body itself.

This can be useful for testing or metadata inspection.

---

# 24. Method Does Not Automatically Mean Authorization

A server receiving:

```text
DELETE /users/42
```

should not simply conclude:

```text
"Delete it."
```

The application may need to verify:

```text
Authentication
Authorization
Permissions
Business rules
Request validity
```

HTTP describes communication semantics.

Application security determines whether the operation should be allowed.

---

# 25. HTTP Headers

Headers carry metadata about HTTP requests and responses.

Example request:

```http
GET / HTTP/1.1
Host: example.com
Accept: text/html
User-Agent: ExampleBrowser
```

Headers include:

```text
Name: value
```

pairs.

Examples:

```text
Host
Content-Type
Content-Length
Accept
Authorization
User-Agent
Cache-Control
Cookie
Set-Cookie
Location
```

---

# 26. Request Headers

Request headers tell the server information about the request or client preferences/context.

Examples:

```text
Host: api.example.com

Accept: application/json

Authorization: Bearer ...

Content-Type: application/json
```

Each serves a different purpose.

---

# 27. The Host Header

In HTTP/1.1, the `Host` header identifies the target host.

Example:

```http
Host: shop.example.com
```

This is important because one IP address can host many websites.

For example:

```text
203.0.113.20
    |
    +--> shop.example.com
    +--> blog.example.com
    +--> api.example.com
```

The server or reverse proxy can use the hostname to determine which application should handle the request.

---

# 28. Content-Type

`Content-Type` describes the media type of the body.

Examples:

```text
Content-Type: text/html
Content-Type: application/json
Content-Type: text/plain
Content-Type: image/png
```

For an API request:

```http
Content-Type: application/json
```

tells the server that the body contains JSON.

---

# 29. Accept

The `Accept` header indicates response media types the client can accept.

Example:

```http
Accept: application/json
```

Conceptually:

```text
"I would prefer a JSON response."
```

The server determines what representation it can provide according to its application behavior and content negotiation rules.

---

# 30. Authorization Header

APIs frequently use:

```http
Authorization: Bearer <token>
```

for credentials or tokens.

A missing or invalid authorization value may produce:

```text
401
```

or:

```text
403
```

depending on the situation.

This is an application/authentication problem, not necessarily a network connectivity problem.

---

# 31. Request Bodies

Some HTTP requests contain bodies.

Example:

```http
POST /users HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"name":"Ada"}
```

The body is:

```json
{"name":"Ada"}
```

Methods such as POST, PUT, and PATCH commonly carry request bodies.

---

# 32. Response Bodies

HTTP responses can also contain bodies.

Example:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"id":42,"name":"Ada"}
```

The response body contains application data.

Possible body types include:

```text
HTML
JSON
XML
Images
Video
CSS
JavaScript
Plain text
Binary files
```

---

# 33. HTTP Status Codes

HTTP responses include status codes.

Examples:

```text
200
301
404
500
```

The first digit indicates the broad class.

```text
1xx = Informational
2xx = Successful
3xx = Redirection
4xx = Client error
5xx = Server error
```

For this part, focus primarily on:

```text
2xx
3xx
4xx
5xx
```

---

# 34. 2xx: Success

2xx codes indicate that the request was successfully received and handled according to the particular status semantics.

Common examples:

```text
200 OK
201 Created
202 Accepted
204 No Content
```

---

# 35. 200 OK

```text
200 OK
```

is the common general success response.

Example:

```text
GET /products/42
        |
        v
200 OK
```

The response often contains the requested representation.

---

# 36. 201 Created

```text
201 Created
```

commonly indicates that a request resulted in a new resource being created.

Example:

```text
POST /users
      |
      v
201 Created
```

An API may also provide information identifying the created resource.

---

# 37. 204 No Content

```text
204 No Content
```

means the request succeeded but there is no response content body.

For example:

```text
DELETE /users/42
        |
        v
204 No Content
```

depending on the application's API design.

---

# 38. 3xx: Redirection

3xx status codes indicate redirection or related behavior.

Common examples include:

```text
301 Moved Permanently
302 Found
304 Not Modified
307 Temporary Redirect
308 Permanent Redirect
```

---

# 39. HTTP to HTTPS Redirect

A common pattern:

```text
GET http://example.com
```

Server responds:

```text
301 / 308
Location: https://example.com
```

Browser then requests:

```text
https://example.com
```

That is not necessarily a failure.

It can be intentional redirection.

---

# 40. Redirect Chains

Suppose:

```text
http://example.com
        |
        v
https://example.com
        |
        v
https://www.example.com
        |
        v
https://www.example.com/home
```

Multiple redirects increase request latency and can sometimes reveal configuration problems.

With `curl`, you can inspect this behavior.

---

# 41. 4xx: Client-Side Request Errors

4xx means the server believes there is a problem with the request or that the requested action cannot be fulfilled for client-related reasons.

Common examples:

```text
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
405 Method Not Allowed
408 Request Timeout
429 Too Many Requests
```

A 4xx response is important evidence:

```text
You reached an HTTP-speaking server.
```

Therefore basic network connectivity may already be working.

---

# 42. 400 Bad Request

```text
400 Bad Request
```

generally means the server could not properly process the request because it was invalid in some way.

Possible causes include:

```text
Malformed request
Invalid parameters
Invalid body
Application validation
Incorrect syntax
```

---

# 43. 401 Unauthorized

Despite the wording, `401` generally indicates that valid authentication credentials are required.

Example:

```text
GET /private
Authorization: invalid-token
```

Response:

```text
401 Unauthorized
```

Investigate authentication.

Do not immediately troubleshoot routing.

---

# 44. 403 Forbidden

```text
403 Forbidden
```

means the server understood the request but refuses to fulfill it.

Possible causes:

```text
Insufficient permissions
Access policy
WAF rule
IP restriction
Application authorization
```

The server may know who you are but still deny the action.

---

# 45. 404 Not Found

```text
404 Not Found
```

means the server could not find the requested resource, or is intentionally representing the result that way.

Example:

```text
GET /does-not-exist
```

Response:

```text
404 Not Found
```

This usually points you toward:

```text
Path
Routing
Application
Reverse proxy configuration
```

rather than DNS or TCP.

---

# 46. 429 Too Many Requests

```text
429 Too Many Requests
```

commonly indicates rate limiting.

For example:

```text
Client
  |
  | 10,000 API requests
  v
API Gateway
  |
  v
429
```

The network may be functioning perfectly.

The application or gateway is deliberately limiting requests.

---

# 47. 5xx: Server-Side Errors

5xx status codes indicate server-side failure conditions.

Examples:

```text
500 Internal Server Error
502 Bad Gateway
503 Service Unavailable
504 Gateway Timeout
```

These are especially important in DevOps and production troubleshooting.

---

# 48. 500 Internal Server Error

```text
500 Internal Server Error
```

generally indicates that the server encountered an unexpected condition while handling the request.

Possible causes:

```text
Application exception
Unhandled error
Dependency failure
Configuration problem
Database issue
```

Investigate application and server-side logs.

---

# 49. 502 Bad Gateway

```text
502 Bad Gateway
```

commonly appears when a proxy or gateway receives an invalid or unusable response from an upstream server.

Architecture:

```text
Client
   |
   v
Reverse Proxy
   |
   v
Application
```

If the reverse proxy cannot successfully communicate with the application:

```text
Client
   |
   v
Reverse Proxy
   |
   X
Application
```

the client may receive:

```text
502 Bad Gateway
```

---

# 50. 503 Service Unavailable

```text
503 Service Unavailable
```

means the service is currently unavailable.

Possible causes:

```text
Application overloaded
No healthy backend
Maintenance
Dependency unavailable
Service intentionally drained
```

In load-balanced environments, 503 is often an important health and backend-availability clue.

---

# 51. 504 Gateway Timeout

```text
504 Gateway Timeout
```

commonly means a gateway or proxy did not receive a timely response from an upstream service.

Example:

```text
Client
   |
   v
Load Balancer
   |
   v
Backend
   |
   X
Slow database
```

The client may eventually receive:

```text
504 Gateway Timeout
```

The gateway is reachable.

The problem is farther downstream.

---

# 52. Status Codes Are Troubleshooting Evidence

Compare:

```text
Connection timed out
```

with:

```text
HTTP 404
```

These are completely different.

A 404 means:

```text
DNS likely succeeded
Transport likely succeeded
TLS likely succeeded if HTTPS
HTTP request reached a server
Server returned an HTTP response
```

A timeout may mean you never reached that stage.

Always use the highest-layer evidence available.

---

# 53. HTTP/1.1

HTTP/1.1 has been one of the foundational versions of HTTP for decades.

A simplified request:

```http
GET / HTTP/1.1
Host: example.com
```

HTTP/1.1 introduced and standardized important behavior around:

```text
Persistent connections
Host-based virtual hosting
Caching
Transfer mechanisms
Request/response semantics
```

---

# 54. Persistent Connections

Creating a new TCP connection for every small resource would add overhead.

HTTP/1.1 commonly reuses a TCP connection for multiple requests.

Conceptually:

```text
TCP connection established
        |
        +--> Request 1
        |       |
        |       <-- Response 1
        |
        +--> Request 2
        |       |
        |       <-- Response 2
        |
        +--> Request 3
                |
                <-- Response 3
```

This is called a persistent connection.

---

# 55. Why Persistent Connections Matter

Without connection reuse:

```text
TCP handshake
TLS handshake
HTTP request
Response
Close

TCP handshake
TLS handshake
HTTP request
Response
Close
```

Repeated setup adds latency and resource cost.

Connection reuse reduces that overhead.

---

# 56. HTTP/1.1 Limitations

HTTP/1.1 can reuse connections, but its request/response handling has limitations.

Browsers historically worked around some of these limitations by opening multiple connections to the same origin.

HTTP/2 was designed to improve efficiency significantly.

---

# 57. HTTP/2

HTTP/2 introduces features including:

```text
Binary framing
Multiplexing
Header compression
Stream-based communication
```

One major concept is:

```text
Multiple HTTP streams
over one connection.
```

Conceptually:

```text
One TCP Connection
       |
       +--> Stream 1
       +--> Stream 3
       +--> Stream 5
       +--> Stream 7
```

Requests and responses can be interleaved rather than handled only as one simple sequential text exchange.

---

# 58. HTTP/2 Does Not Mean HTTP Semantics Disappear

You still have concepts such as:

```text
GET
POST
Headers
Status codes
URLs
Request bodies
Response bodies
```

HTTP/2 changes how HTTP messages are represented and transported efficiently.

It does not replace the basic application semantics.

---

# 59. HTTP/2 and TCP

HTTP/2 commonly runs over a single TCP connection for a given connection context.

This creates significant efficiency benefits.

But TCP itself still provides an ordered byte stream.

Packet loss affecting that TCP connection can therefore affect delivery for the HTTP/2 streams using it.

This is one motivation behind newer transport designs.

---

# 60. HTTP/3 Introduction

HTTP/3 uses:

```text
QUIC
```

rather than TCP.

QUIC runs over:

```text
UDP
```

So the simplified stack becomes:

```text
HTTP/3
   |
   v
QUIC
   |
   v
UDP
   |
   v
IP
```

This does **not** mean HTTP/3 is unreliable merely because UDP is underneath it.

QUIC implements the reliability, security, congestion-control, and stream functionality required by HTTP/3.

---

# 61. Why HTTP/3 Exists

HTTP/3 and QUIC aim to improve areas including:

```text
Connection establishment
Multiplexed streams
Loss behavior
Connection migration
Modern encrypted transport
```

A particularly important concept is that independent QUIC streams reduce the cross-stream blocking associated with packet loss in a single TCP byte stream.

You do not need to master QUIC internals yet.

Remember:

```text
HTTP/1.1 -> commonly TCP

HTTP/2 -> commonly TCP

HTTP/3 -> QUIC over UDP
```

---

# 62. What Changes With HTTPS?

HTTP alone does not provide the confidentiality and authentication properties expected for modern Internet communication.

HTTPS is:

```text
HTTP protected using TLS
```

Simplified:

```text
HTTP
  |
  v
TLS
  |
  v
TCP
```

for traditional HTTPS using HTTP/1.1 or HTTP/2 over TCP.

For HTTP/3, TLS functionality is integrated into QUIC's design rather than appearing as a completely separate layer in the same way.

---

# 63. HTTP vs HTTPS

HTTP:

```text
http://example.com
```

commonly uses:

```text
TCP 80
```

HTTPS:

```text
https://example.com
```

commonly uses:

```text
TCP 443
```

for HTTP/1.1 and HTTP/2.

HTTP/3 commonly uses QUIC over UDP, generally on port 443.

---

# 64. What TLS Provides

TLS stands for:

```text
Transport Layer Security
```

TLS provides important security properties including:

```text
Confidentiality
Integrity
Authentication
```

Confidentiality:

```text
Others should not be able to
simply read the protected data.
```

Integrity:

```text
Unauthorized modification should
be detectable.
```

Authentication:

```text
The client can authenticate
the server's identity through
the certificate system.
```

Client authentication with certificates is also possible, though ordinary public websites typically authenticate the server rather than requiring client certificates.

---

# 65. TLS Does Not Make an Application Safe

A valid HTTPS connection means:

```text
The transport is protected
and the peer identity was validated
according to the TLS/certificate process.
```

It does not mean:

```text
The application has no vulnerabilities.

The website is trustworthy.

The server cannot be compromised.

The user cannot be phished.

The application has correct authorization.
```

HTTPS solves important transport-security problems, not every security problem.

---

# 66. Certificates

A TLS certificate binds identity information, particularly hostnames, to a public key under a certificate trust system.

A certificate contains information such as:

```text
Subject / identity information
Public key
Issuer
Validity period
Signature
Extensions
Subject Alternative Names
```

For modern hostname validation, the Subject Alternative Name extension is especially important.

---

# 67. Certificate Example

Suppose the browser connects to:

```text
https://shop.example.com
```

The server presents a certificate valid for:

```text
shop.example.com
```

or perhaps a certificate whose Subject Alternative Names include:

```text
shop.example.com
www.example.com
example.com
```

The browser validates whether the requested hostname is covered by the certificate.

---

# 68. Certificate Authorities

A Certificate Authority is commonly abbreviated:

```text
CA
```

A CA participates in the trust system by signing certificates or issuing certificates through a hierarchy.

Simplified:

```text
Trusted Root CA
      |
      v
Intermediate CA
      |
      v
Server Certificate
```

The client maintains a trust store containing trusted roots.

It uses certificate-chain validation to determine whether the server certificate chains to a trusted authority.

---

# 69. Root and Intermediate Certificates

A certificate chain commonly looks like:

```text
Root CA
   |
   v
Intermediate CA
   |
   v
Server Certificate
```

The root is trusted by the client.

The intermediate is signed within the hierarchy.

The server certificate is issued for the website.

The server commonly sends:

```text
Server certificate
Intermediate certificate(s)
```

The root itself is generally already available in the client's trust store rather than needing to be supplied by the server.

---

# 70. Public and Private Keys

Public-key cryptography uses a key pair:

```text
Private Key
Public Key
```

The private key must remain secret.

The public key can be distributed.

Conceptually:

```text
Server
   |
   +--> Private key
   |      KEEP SECRET
   |
   +--> Public key
          Included/bound through certificate
```

The exact TLS cryptographic process is more sophisticated than simply "encrypt everything with the server public key."

---

# 71. A Common TLS Misunderstanding

A simplified but inaccurate explanation sometimes says:

```text
"The browser encrypts all website data
with the server's public key."
```

Modern TLS generally uses public-key cryptography to authenticate and establish shared secrets, while efficient symmetric cryptography protects the actual application traffic.

Conceptually:

```text
Public-key mechanisms
       |
       v
Authentication + key establishment
       |
       v
Shared session keys
       |
       v
Symmetric encryption
for application data
```

This is both faster and appropriate for large volumes of traffic.

---

# 72. The Private Key

The server's private key is highly sensitive.

If an attacker obtains it, the consequences can be serious depending on the TLS configuration, certificate usage, and circumstances.

Private keys should therefore be protected with appropriate:

```text
Access controls
Secret management
File permissions
Key-management systems
Rotation procedures
```

Never commit production private keys to a public Git repository.

---

# 73. TLS Handshake

Before protected HTTP application data can be exchanged, the client and server perform a TLS handshake.

The exact messages differ by TLS version and configuration.

A simplified modern model is:

```text
Client
  |
  | ClientHello
  v
Server
  |
  | ServerHello
  | Certificate
  | Handshake information
  v
Client
  |
  | Validates certificate
  | Establishes shared secrets
  v
Server
  |
  v
Encrypted application traffic
```

---

# 74. ClientHello

The client begins by sending a:

```text
ClientHello
```

It communicates capabilities and information needed to negotiate the connection.

Depending on TLS version, it can contain information such as:

```text
Supported TLS versions
Supported cryptographic parameters
Key-share information
Extensions
SNI
ALPN
```

---

# 75. ServerHello

The server responds with:

```text
ServerHello
```

and selects compatible parameters.

The server also provides the information required to authenticate itself and complete key establishment.

For ordinary public HTTPS, this includes its certificate chain information.

---

# 76. TLS Version Negotiation

Client and server need compatible TLS capabilities.

For example:

```text
Client:
Supports TLS 1.2 and TLS 1.3

Server:
Supports TLS 1.3

Result:
TLS 1.3
```

If no acceptable version can be negotiated, the TLS handshake fails.

This can occur with outdated clients or badly configured legacy servers.

---

# 77. SNI

SNI stands for:

```text
Server Name Indication
```

SNI allows the client to indicate which hostname it is trying to reach during the TLS handshake.

Why is this useful?

One server IP might host:

```text
shop.example.com
api.example.com
blog.example.com
```

Before HTTP is exchanged, the server may need to know which TLS certificate/configuration to use.

SNI provides that hostname information during TLS negotiation.

---

# 78. Host Header vs SNI

These concepts are related but occur at different stages.

SNI:

```text
TLS layer
```

Host/HTTP authority information:

```text
HTTP layer
```

Simplified:

```text
TCP connection
      |
      v
TLS handshake
SNI = shop.example.com
      |
      v
TLS established
      |
      v
HTTP request
Host = shop.example.com
```

Do not confuse them.

---

# 79. SNI and Shared IP Addresses

Suppose:

```text
203.0.113.20
```

hosts:

```text
shop.example.com
api.example.com
admin.example.com
```

The TLS endpoint can inspect SNI and select the appropriate certificate or virtual-host configuration.

Without the correct hostname information, the wrong certificate or default virtual host may be selected.

---

# 80. Certificate Validation

The browser does not simply accept any certificate the server sends.

It performs validation.

Important checks include:

```text
Is the certificate within its validity period?

Does it match the requested hostname?

Does it chain to a trusted root?

Are signatures valid?

Is the chain correctly constructed?

Are certificate constraints/extensions acceptable?
```

If validation fails, the browser may display a security warning or terminate the connection.

---

# 81. Hostname Validation

Suppose the user requests:

```text
https://api.example.com
```

but the certificate is valid only for:

```text
www.example.com
```

The certificate may otherwise be perfectly valid.

But it does not match the requested hostname.

Result:

```text
Certificate hostname mismatch
```

This is a TLS configuration problem.

---

# 82. Expired Certificates

Certificates have validity periods.

Conceptually:

```text
Not Before:
2026-01-01

Not After:
2026-06-01
```

If the current time is after the valid period, certificate validation fails.

This is why certificate expiration monitoring is important in production.

A perfectly healthy application can become inaccessible because its certificate expired.

---

# 83. Not-Yet-Valid Certificates

The opposite can also occur.

Suppose certificate validity begins:

```text
2026-09-01
```

but the client believes the current date is:

```text
2026-08-28
```

The certificate is not yet valid.

Incorrect system clocks can therefore produce TLS failures.

Always consider time synchronization when certificate validity errors appear unexpectedly.

---

# 84. Certificate Chain Problems

Suppose the server sends its leaf certificate but omits a required intermediate certificate.

Some clients may fail to construct a valid trust chain.

Conceptually:

```text
Trusted Root
     |
     v
Intermediate
     |
     v
Server
```

but the client receives insufficient chain information.

This can produce confusing situations where:

```text
Some clients work.

Other clients fail.
```

Different clients may have different cached or available intermediates.

---

# 85. Self-Signed Certificates

A self-signed certificate signs itself rather than chaining through a public CA hierarchy trusted by ordinary clients.

These are often used in:

```text
Labs
Internal systems
Development environments
Private PKI scenarios
```

A browser will not automatically trust an arbitrary self-signed certificate.

Trust must be explicitly established when appropriate.

Do not solve production TLS problems by casually disabling certificate verification.

---

# 86. TLS and DNS Are Separate

Suppose:

```text
api.example.com
```

resolves to:

```text
203.0.113.20
```

DNS succeeded.

But TLS can still fail because:

```text
Certificate expired
Hostname mismatch
Untrusted issuer
Missing intermediate
TLS version mismatch
SNI configuration problem
```

Successful DNS does not prove HTTPS works.

---

# 87. TLS and TCP Are Separate

Suppose:

```text
TCP 443 connection succeeds.
```

That proves transport connectivity to something listening on TCP 443.

It does not prove TLS negotiation succeeds.

Possible sequence:

```text
DNS
  |
  v
Success

TCP 443
  |
  v
Success

TLS
  |
  X
Certificate failure
```

This layered thinking is extremely important.

---

# 88. TLS and HTTP Are Separate

TLS can succeed while HTTP fails.

Example:

```text
DNS:
Success

TCP:
Success

TLS:
Success

HTTP:
503 Service Unavailable
```

The TLS certificate is not the problem.

The server successfully established HTTPS and then returned an application-layer error.

---

# 89. ALPN Introduction

During TLS negotiation, clients and servers can use:

```text
ALPN
```

Application-Layer Protocol Negotiation.

It helps negotiate which application protocol should run over the secured connection.

For example:

```text
h2
```

can indicate HTTP/2.

```text
http/1.1
```

can indicate HTTP/1.1.

This helps modern HTTPS endpoints support multiple HTTP versions.

# 90. Using curl

`curl` is one of the most useful web troubleshooting tools.

Basic request:

This performs the request and prints the response body.

But for troubleshooting, you usually want more information.

# 95. Following Redirects

By default, `curl` does not automatically follow every HTTP redirect as a browser would.

Use:

```bash

```

to follow redirects.

```bash

```

This can expose an entire redirect chain.

# 96. Testing a Specific HTTP Method

GET:

```bash
curl https://api.example.com/users
```

POST:

```bash
curl -X POST https://api.example.com/users
```

For realistic API testing, you may also send headers and data.

Example:

```bash
curl -X POST \
  -H 'Content-Type: application/json' \

```

Use destructive methods such as DELETE only against systems you are authorized to modify.

# 97. Sending Headers With curl

Example:

```bash

  -H 'Accept: application/json' \

```

For authenticated systems:

```bash

```

```text
/
```

This helps isolate port-specific problems.

# 99. Testing a Specific Backend Without Changing DNS

Sometimes you need to test a hostname against a specific IP.

For example:

```bash

  https://example.com/
```

This tells `curl` to use the specified address for that host and port while preserving the hostname needed for HTTPS and HTTP virtual hosting.

```text

Investigating DNS issues
```

# 100. Why `curl https://IP` Can Be Misleading

Suppose:

```text
example.com
```

resolves to:

```text
203.0.113.20
```

You try:

```bash
curl https://203.0.113.20
```

and get a certificate error.

That does not necessarily mean HTTPS is broken.

The certificate may be valid for:

```text
example.com
```

but not:

```text
203.0.113.20
```

Also, using the IP can alter SNI and virtual-host behavior.

For hostname-based HTTPS testing, preserve the hostname.

# 101. `curl -k` Warning

You may encounter:

```bash

```

or:

```bash

```

This disables normal certificate verification.

It can sometimes help prove that certificate validation is the specific failure in a controlled diagnostic situation.

But:

```text
Do not treat -k as the fix.
```

If HTTPS works only with `-k`, investigate why certificate validation fails.

# 102. openssl s_client

`openssl s_client` is extremely useful for inspecting TLS connections.

Example:

```bash
openssl s_client -connect example.com:443
```

For modern virtual hosting, include SNI:

```bash
openssl s_client \
  -connect example.com:443 \
  -servername example.com
```

This allows you to inspect the TLS handshake and certificate information.

# 103. Why `-servername` Matters

Suppose one IP hosts several HTTPS sites.

Without:

```bash
-servername example.com
```

the server may return a default certificate.

You might incorrectly conclude:

```text
"The certificate is wrong."
```

when your test simply omitted SNI.

Use the hostname during realistic TLS testing.

# 104. What to Inspect With openssl s_client

Look for information such as:

```text

Certificate subject
Issuer
Validity
TLS version
Cipher
Verification result
ALPN
```

The exact output varies with OpenSSL version and server configuration.

The goal is not to memorize every line.

Ask:

```text

Which certificate was presented?

Who issued it?

Does verification succeed?

Which TLS version was negotiated?
```

# 105. Checking Certificate Dates

You can inspect certificate information using OpenSSL tools.

For example:

```bash
openssl s_client \
  -connect example.com:443 \
  -servername example.com </dev/null 2>/dev/null |

```

You may see:

```text
notBefore=...
notAfter=...
```

This helps diagnose certificate validity problems.

# 106. Inspecting Certificate Names

You can inspect Subject Alternative Names:

```bash
openssl s_client \
  -connect example.com:443 \
  -servername example.com </dev/null 2>/dev/null |
openssl x509 -noout -ext subjectAltName
```

Then verify whether the requested hostname is covered.

This is useful for hostname-mismatch incidents.

# 113. HTTP Troubleshooting Starts Below HTTP

User reports:

```text
"Website is down."
```

Do not begin by restarting the application.

Work upward.

```text

3. Transport
4. TLS
5. HTTP
6. Proxy/load balancer
7. Application
8. Dependencies
```

The exact order can be adapted based on evidence.


```text
IPv4 or IPv6?
```

```text
Service availability
```

```text
Does the hostname match?

Which TLS version was negotiated?
```

If TLS fails, HTTP application troubleshooting may be premature.

# 118. Step 5: Test HTTP

Now inspect:


Suppose you receive:


# 120. Connection Refused vs HTTP Error

```text

```

```text
Service is bound elsewhere
```

```text

```

```text

```

# 121. Timeout vs 504

```text

```

```text

```

Conceptually:

```text

  |
  | successful connection
  v
Gateway
  |
  | waits...
  X
Backend
  |
  v
504 returned to client
```

This distinction immediately narrows troubleshooting.

# 136. Complete HTTPS Request: Step 1

```text

```

Browser parses:

```text
Scheme:
https

Hostname:
shop.example.com

Port:
443

Path:
/products/42
```

The browser now knows what it needs to reach.

# 137. Complete HTTPS Request: Step 2, DNS

Browser/system resolver needs an address.

Conceptually:

```text
shop.example.com
       |
       v
DNS resolver
       |
       v
203.0.113.20
```

There may be IPv4 and/or IPv6 answers.

Suppose:

```text
A:
203.0.113.20
```

The client now has a destination IP.

# 138. Complete HTTPS Request: Step 3, Routing

The host checks its routing table.

Suppose:

```text
Client:
192.168.1.50/24

Destination:
203.0.113.20
```

Destination is remote.

Route:

```text
default via 192.168.1.1
```

The host will send the packet toward its default gateway.

---

# 139. Complete HTTPS Request: Step 4, ARP

The client needs the gateway's MAC address.

It checks its neighbor table.

If necessary:

```text
ARP Request:
Who has 192.168.1.1?
```

Gateway replies with its MAC.

Now the client can construct the local Ethernet frame.

---

# 140. Complete HTTPS Request: Step 5, NAT

The client's transport connection may begin as:

```text
192.168.1.50:53124
       ->
203.0.113.20:443
```

Home router performs PAT:

```text
192.168.1.50:53124
       <=>
198.51.100.10:41002
```

The translated traffic continues toward the destination.

---

# 141. Complete HTTPS Request: Step 6, TCP

For HTTP/1.1 or HTTP/2 over TCP, the client establishes a TCP connection.

```text
Client                         Server
  |                              |
  |----------- SYN ------------->|
  |                              |
  |<-------- SYN-ACK ------------|
  |                              |
  |----------- ACK ------------->|
  |                              |
```

TCP connection established.

At this point:

```text
HTTP has still not necessarily been sent.
```

TLS comes first for HTTPS.

---

# 142. Complete HTTPS Request: Step 7, TLS

Client sends:

```text
ClientHello
SNI: shop.example.com
```

Server responds with TLS negotiation information and certificate material.

Client validates:

```text
Hostname
Certificate validity
Trust chain
Signatures
Other TLS requirements
```

Shared cryptographic secrets are established.

TLS handshake completes.

---

# 143. Complete HTTPS Request: Step 8, HTTP

Now the browser can send protected HTTP application data.

Conceptually, after decryption at the server:

```http
GET /products/42 HTTP/1.1
Host: shop.example.com
Accept: text/html
```

On the wire, TLS protects this application content.

A passive observer should not simply see the plaintext HTTP request contents.

---

# 144. Complete HTTPS Request: Step 9, Server Processing

The request might pass through:

```text
CDN
  |
  v
WAF
  |
  v
Load Balancer
  |
  v
Reverse Proxy
  |
  v
Application
  |
  v
Cache / Database / Services
```

The application generates a response.

Example:

```text
200 OK
```

with HTML.

---

# 145. Complete HTTPS Request: Step 10, Response

Application response travels back through the infrastructure.

Conceptually:

```http
HTTP/1.1 200 OK
Content-Type: text/html

<html>...</html>
```

TLS protects the data.

TCP transports it reliably.

IP routes the packets.

NAT performs reverse translation where applicable.

The client receives the data.

# 146. Complete HTTPS Request: Step 11, Browser Rendering

# 173. Common Beginner Mistake: Treating Every 5xx as Application Failure

A 5xx may originate from:

```text

API gateway

Application
```

Find who generated the status.

# 174. Common Beginner Mistake: Disabling TLS Verification

When certificate validation fails, beginners often try:

```bash
curl -k
```

and conclude:

```text
"Fixed."
```

No.

You bypassed a security control.

The correct question is:

```text
Why did verification fail?
```

Investigate the root cause.

# 175. Common Beginner Mistake: Testing HTTPS by IP

This can break:

```text
Hostname validation
SNI
Virtual hosting
```

Instead, preserve the hostname.

Tools such as:

```bash

```

are often more appropriate when testing a specific IP behind a hostname.

# 176. Common Beginner Mistake: Confusing 401 and 403

A useful simplified distinction:

```text
401
Authentication required or invalid

403
Request understood but access forbidden
```

Real application behavior can vary, but this is the right starting mental model.

# 177. Common Beginner Mistake: Thinking HTTPS Means Port 443 Only

443 is the standard/default HTTPS port.

But:

```text
https://example.com:8443
```

is perfectly possible.

Always inspect the actual port.

---

# 178. Common Beginner Mistake: Thinking HTTP/3 Is TCP

HTTP/3 uses:

```text
QUIC over UDP
```

not TCP.

Do not apply every TCP-specific troubleshooting assumption directly to HTTP/3.

---

# 179. Common Beginner Mistake: Assuming a Valid Certificate Means the Website Is Healthy

Certificate:

```text
Valid
```

HTTP response:

```text
503
```

Both can be true.

TLS succeeded.

Application/backend availability did not.
