# Part 20: Complete Python for DevOps Automation Project

## Build an Infrastructure Health and Automation Toolkit

Parts 1 through 19 taught individual Python and automation skills.

Now we will combine them.

The goal is to build a small but realistic infrastructure toolkit that can:

```text
Python Automation Toolkit
        |
        +--> Read YAML inventory
        |
        +--> Load environment variables
        |
        +--> Validate configuration
        |
        +--> Check TCP connectivity
        |
        +--> Check HTTP endpoints
        |
        +--> Run Linux health commands
        |
        +--> Check disk usage
        |
        +--> Check memory
        |
        +--> Check services
        |
        +--> Parse JSON/API responses
        |
        +--> Retry temporary failures
        |
        +--> Log operations
        |
        +--> Handle failures
        |
        +--> Generate JSON report
        |
        +--> Exit with meaningful status
```

This is not intended to replace Prometheus, Grafana, Datadog, CloudWatch, Nagios, Zabbix, or another monitoring platform.

The purpose is to teach you how infrastructure automation is assembled.

By the end, you should understand how several small Python skills become one operational tool.

# 1. What We Are Trying to Accomplish

Imagine that you are responsible for several servers and services.

You want one command:

```bash
python main.py --config config/inventory.yaml
```

to perform basic infrastructure checks.

The tool should:

1. Read the server inventory.
2. Validate the configuration.
3. Read runtime settings from environment variables.
4. Check whether configured TCP ports are reachable.
5. Check HTTP endpoints.
6. Run local Linux health commands where appropriate.
7. Inspect disk and memory.
8. Check configured services.
9. Call an optional API.
10. Parse JSON responses.
11. Retry selected temporary failures.
12. Log what happened.
13. Generate a report.
14. Return a useful exit code.

We also want:

```bash
python main.py \
  --config config/inventory.yaml \
  --dry-run
```

and:

```bash
python main.py \
  --config config/inventory.yaml \
  --verbose
```

# 31. Read YAML Safely

```python
def load_yaml(
    path: Path
) -> dict:

    try:
        with path.open(
            "r",
            encoding="utf-8"
        ) as file:

            data = yaml.safe_load(
                file
            )

    except FileNotFoundError as error:
        raise ConfigurationError(
            f"Configuration file "
            f"not found: {path}"
        ) from error

    except PermissionError as error:
        raise ConfigurationError(
            f"Permission denied: "
            f"{path}"
        ) from error

    except yaml.YAMLError as error:
        raise ConfigurationError(
            f"Invalid YAML in "
            f"{path}"
        ) from error

    if not isinstance(
        data,
        dict
    ):
        raise ConfigurationError(
            "Configuration root "
            "must be a mapping"
        )

    return data
```

---

# 32. Why `yaml.safe_load()`?

Use:

```python
yaml.safe_load()
```

for normal configuration data.

Do not casually replace it with unrestricted YAML object loading.

Configuration should be treated as data, not as instructions to construct arbitrary Python objects.

# 33. Validate a Percentage

Create:

```python
def validate_percentage(
    value,
    field_name: str
) -> int:

    if (
        isinstance(value, bool)
        or not isinstance(value, int)
    ):
        raise ConfigurationError(
            f"{field_name} must "
            f"be an integer"
        )

    if not 0 <= value <= 100:
        raise ConfigurationError(
            f"{field_name} must "
            f"be between 0 and 100"
        )

    return value
```

---

# 34. Why Reject Boolean?

In Python:

```python
isinstance(
    True,
    int
)
```

is:

```text
True
```

because `bool` is related to `int`.

But:

```yaml
disk_warning_percent: true
```

should not be accepted as a percentage.

So we explicitly reject Boolean values.

def validate_port(

        raise ConfigurationError(
            f"{field_name} must "

# 60. Why Bound Retries?

Never create:

* Limited.
* Delayed.
* Observable.
* Used only for failures that might be temporary.

# 62. Generic Retry Function

```python
def retry_operation(
    operation,
    retries: int,
    delay_seconds: float = 1.0,
):
    attempts = (
        retries + 1
    )

    last_error = None

    for attempt in range(
        1,
        attempts + 1
    ):

        try:
            return operation()

        except Exception as error:
            last_error = error

            if attempt >= attempts:
                break

            logger.warning(
                "Operation failed. "
                "Retrying attempt=%s/%s "
                "error=%s",
                attempt,
                attempts,
                type(error).__name__,
            )

            time.sleep(
                delay_seconds
            )

    raise last_error
```

---

# 63. Important Retry Warning

This generic helper is educational.

Do not automatically wrap every operation with it.

Retrying can be dangerous.

Imagine:

```text
Create payment
    |
    v
Response lost
    |
    v
Retry
    |
    v
Second payment created
```

Infrastructure mutations can have similar problems.

Retries are safest when operations are:

* Read-only.
* Idempotent.
* Explicitly designed for retry.

Our health checks are mostly read-only.

---

# 64. What Does Idempotent Mean?

An idempotent operation can be repeated without changing the final outcome beyond the first successful application.

For example, repeatedly reading:

```text
GET /health
```

does not normally create additional resources.

A resource-creation operation may not have the same property.

# 86. Safe Command Runner

```python
def run_command(
    command: list[str],
    timeout: float = 10
) -> dict:

    try:
        result = subprocess.run(
            command,
            capture_output=True,
            text=True,
            timeout=timeout,
            check=False,
        )

    except FileNotFoundError as error:
        return {
            "status": "ERROR",
            "returncode": None,
            "stdout": "",
            "stderr": str(
                error
            ),
        }

    except subprocess.TimeoutExpired:
        return {
            "status": "ERROR",
            "returncode": None,
            "stdout": "",
            "stderr": (
                "Command timed out"
            ),
        }

    return {
        "status": (
            "OK"
            if result.returncode == 0
            else "ERROR"
        ),
        "returncode": (
            result.returncode
        ),
        "stdout": (
            result.stdout.strip()
        ),
        "stderr": (
            result.stderr.strip()
        ),
    }
```

# 149. Unexpected Top-Level Failures

# 176. Test Retry Logic Safely

Do not create a destructive operation merely to test retries.

            "Simulated failure"
        )

    return "success"

# 179. Better Retry Design for Real APIs

Production retry logic may consider:

* HTTP method.
* Status code.
* Timeout type.
* `Retry-After`.
* Exponential backoff.
* Jitter.
* Maximum elapsed time.

* Provider guidance.

# 180. Exponential Backoff

Instead of:

```text
1 second
1 second
1 second
```

a system might wait:

```text
1 second
2 seconds
4 seconds
8 seconds
```

This reduces pressure on a struggling dependency.

---

# 181. Jitter

If 1,000 automation workers all retry at exactly:

```text
2 seconds
```

they may create another traffic spike.

Jitter adds small randomness to spread retries.

This is an advanced production improvement.
