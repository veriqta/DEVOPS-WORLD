# Part 13: GitHub Collaboration and Pull Requests

In Part 12, you learned how multiple copies of a Git repository stay synchronized.

You learned the roles of:

```text
git clone
git fetch
git pull
git push
```

You also learned the difference between:

```text
main
```

and:

```text
origin/main
```

and why a rejected push is often Git protecting remote history.

Now we move into one of the most important parts of professional GitHub usage:

```text
Pull Requests
```

A pull request, usually shortened to:

```text
PR
```

is one of the main mechanisms teams use to propose, discuss, review, validate, and merge changes.

The basic workflow looks like this:

```text
main
 |
 +------> feature branch
              |
              v
           commits
              |
              v
            push
              |
              v
        Pull Request
              |
              v
           Review
              |
              v
          Feedback
              |
              v
           Updates
              |
              v
          Approval
              |
              v
            Merge
              |
              v
             main
```

By the end of this part, you should understand not only how to create a pull request, but why professional teams organize development around them.

---

# 1. The Problem Pull Requests Solve

Imagine five engineers working on the same application.

```text
Alice
Bob
Carlos
David
Emma
```

The production code lives in:

```text
main
```

Suppose every developer simply works directly on `main`.

Alice changes authentication.

Bob modifies database configuration.

Carlos updates Kubernetes manifests.

David changes the API.

Emma modifies CI/CD.

Everyone pushes directly:

```text
Alice ----\
Bob -------\
Carlos ------> main
David ------/
Emma ------/
```

Several problems appear.

Who reviewed the changes?

Were automated tests successful?

Did someone accidentally expose a secret?

Did the Kubernetes change break production?

Why was a particular line changed?

Did the security team review the authentication change?

Was the infrastructure change approved?

If everyone directly pushes to `main`, the team loses an important control point before changes enter the shared branch.

Pull requests create that control point.

---

# 2. What a Pull Request Is

A pull request is a proposal to merge changes from one branch into another branch.

For example:

```text
feature/login
      |
      | propose changes
      v
     main
```

You are effectively saying:

```text
I made these changes on feature/login.

I would like these changes to become
part of main.

Please review them first.
```

The pull request creates a place where the team can:

```text
Inspect changes

Discuss implementation

Leave comments

Suggest modifications

Run automated checks

Approve changes

Request changes

Merge approved work
```

The branch contains the actual Git commits.

The pull request provides the GitHub collaboration layer around those commits.

---

# 3. Pull Requests Are a GitHub Feature

This distinction is important.

Git understands:

```text
Branches

Commits

Merges

Remotes

Tags

References
```

Git itself does not provide GitHub pull requests.

Pull requests are a collaboration feature provided by GitHub.

That means:

```text
Git
+
GitHub
=
Git version control
+
collaboration workflow
```

The underlying changes still exist as Git commits and branches.

GitHub adds the review and collaboration experience around them.

---

# 4. Why Teams Use Pull Requests

Pull requests solve several engineering problems.

They provide:

```text
Isolation

Review

Discussion

Testing

Approval

Traceability

Controlled merging
```

Let's examine these individually.

---

# 5. Reason 1: Isolate Work

Suppose production `main` currently contains:

```text
A --- B --- C
```

You need to add login functionality.

Instead of changing `main` directly, create:

```text
feature/login
```

Now:

```text
              feature/login
                    |
                    v
A --- B --- C --- D --- E
          ^
          |
         main
```

Your unfinished work exists separately from `main`.

This allows development to continue without immediately changing the shared branch.

---

# 6. Reason 2: Review Before Integration

Your feature may appear correct to you.

Another engineer may notice:

```text
Missing error handling

Security issue

Incorrect database query

Race condition

Bad variable name

Missing test

Incorrect Terraform configuration

Dangerous Kubernetes setting
```

The pull request gives reviewers an opportunity to catch these problems before the changes enter the target branch.

---

# 7. Reason 3: Discussion

Sometimes the code technically works but the design should change.

For example:

```text
Author:

I added a new database connection here.
```

Reviewer:

```text
We already have a shared connection pool.
Can we reuse it instead?
```

This discussion becomes attached to the proposed change.

That is much more useful than having important engineering decisions scattered across unrelated private messages.

---

# 8. Reason 4: Automated Validation

A pull request can trigger automated systems.

For example:

```text
Pull Request
     |
     +--> Unit tests
     |
     +--> Integration tests
     |
     +--> Linting
     |
     +--> Security scanning
     |
     +--> Terraform validation
     |
     +--> Docker build
     |
     +--> Kubernetes validation
```

GitHub displays these results as checks associated with the pull request.

A repository can also be configured so required checks must succeed before merging.

---

# 9. Reason 5: Approval

Teams may require one or more reviewers to approve a change.

For example:

```text
Developer
    |
    v
Pull Request
    |
    +--> Senior Engineer
    |
    +--> Security Reviewer
    |
    +--> Platform Engineer
    |
    v
Approved
    |
    v
Merge
```

The exact requirements depend on repository rules and team policy.

---

# 10. Reason 6: Traceability

Imagine production breaks.

You find commit:

```text
8a31bc2
```

You can investigate:

```text
Commit
   |
   v
Pull Request
   |
   +--> Why change was made
   |
   +--> Who reviewed it
   |
   +--> Discussion
   |
   +--> Automated checks
   |
   +--> Related issue
```

This context can be extremely useful during incident investigation.

---

# 11. Pull Request Mental Model

A beginner should remember:

```text
Branch
=
Where I develop the change

Commit
=
A recorded snapshot of my change

Push
=
Publish my branch to GitHub

Pull Request
=
Ask to integrate my branch into another branch

Review
=
Evaluate the proposed change

Merge
=
Integrate approved history into the target branch
```

These concepts work together.

---

# 12. The Contributor Workflow

A common contributor workflow looks like:

```text
1. Synchronize local main

2. Create feature branch

3. Make changes

4. Review changes locally

5. Stage changes

6. Commit changes

7. Push feature branch

8. Open pull request

9. Request review

10. Receive feedback

11. Update branch

12. Push updates

13. Pass checks

14. Receive approval

15. Merge

16. Delete feature branch

17. Synchronize local main again
```

This is one of the most important workflows in professional Git development.

---

# 13. Starting From an Updated main

Before creating a feature branch, begin by checking your repository.

```bash
git status
```

Verify:

```text
Correct branch

Clean working tree

No forgotten changes
```

Switch to `main`:

```bash
git switch main
```

Refresh remote information:

```bash
git fetch origin
```

Inspect:

```bash
git status
```

If your local `main` should simply follow `origin/main` and a fast-forward is possible:

```bash
git pull --ff-only
```

Now your starting point is current.

---

# 14. Why Starting From Current main Matters

Suppose your local `main` is:

```text
A --- B --- C
```

But GitHub already has:

```text
A --- B --- C --- D --- E
```

If you create a feature branch from stale `C`:

```text
          F --- G
         /
A --- B --- C --- D --- E
```

your work begins from an older project state.

That can increase the chance of:

```text
Conflicts

Outdated assumptions

Missing dependencies

Broken tests

Duplicated work
```

Synchronizing before branching gives you a cleaner starting point.

---

# 15. Creating a Feature Branch

Suppose you need to add a health endpoint.

Create:

```bash
git switch -c feature/health-endpoint
```

Breakdown:

```text
git
```

runs Git.

```text
switch
```

changes branches.

```text
-c
```

creates a new branch before switching to it.

```text
feature/health-endpoint
```

is the new branch name.

Verify:

```bash
git branch --show-current
```

Expected:

```text
feature/health-endpoint
```

---

# 16. Feature Branch Naming

There is no universal branch naming system that every team must use.

Common patterns include:

```text
feature/user-login
fix/payment-timeout
bugfix/session-expiry
docs/api-guide
chore/update-dependencies
hotfix/security-header
```

A team might instead include issue numbers:

```text
feature/123-user-login
fix/456-payment-timeout
```

The important thing is consistency with the repository's conventions.

Do not invent your own naming standard inside an established team without checking its contribution guidelines.

---

# 17. Feature Branches Should Usually Be Focused

Suppose your task is:

```text
Add health endpoint
```

Your branch should not also contain unrelated changes such as:

```text
Redesign login page

Upgrade database

Change Terraform network

Rename 40 unrelated files

Rewrite README
```

A focused branch generally produces a focused pull request.

Focused pull requests are easier to:

```text
Understand

Review

Test

Approve

Merge

Revert if necessary
```

---

# 18. Make the Change

Suppose the project is:

```text
platform-api/
├── app.py
├── requirements.txt
├── tests/
└── README.md
```

You modify:

```text
app.py
```

and add:

```text
tests/test_health.py
```

Before staging anything:

```bash
git status
```

Then:

```bash
git diff
```

Ask:

```text
Did I change what I intended?

Did I accidentally change something else?

Did I expose credentials?

Are there debug statements?

Are unrelated files included?
```

---

# 19. Stage Intentionally

Instead of automatically running:

```bash
git add .
```

you may stage specific files:

```bash
git add app.py tests/test_health.py
```

Review the staged changes:

```bash
git diff --staged
```

Then commit:

```bash
git commit -m "Add API health endpoint"
```

---

# 20. Multiple Commits Are Allowed

A feature branch can contain multiple commits.

For example:

```text
A --- B --- C
          \
           D --- E --- F
```

Where:

```text
D = Add health endpoint

E = Add health endpoint tests

F = Improve health response validation
```

These commits collectively represent the work proposed by the pull request.

The merge strategy later determines how those commits appear on the base branch.

---

# 21. Publishing the Feature Branch

Your feature branch currently exists only locally.

Conceptually:

```text
YOUR COMPUTER

main
feature/health-endpoint


GITHUB

main
```

Publish it:

```bash
git push -u origin feature/health-endpoint
```

Afterward:

```text
YOUR COMPUTER

feature/health-endpoint
        |
        | tracks
        v
origin/feature/health-endpoint


GITHUB

feature/health-endpoint
```

---

# 22. Why -u Is Useful

Recall from Part 12:

```text
-u
```

means:

```text
--set-upstream
```

After:

```bash
git push -u origin feature/health-endpoint
```

future pushes from that branch can normally be shortened to:

```bash
git push
```

The upstream relationship is already configured.

---

# 23. Publishing a Branch Does Not Merge It

This distinction is critical.

After:

```bash
git push -u origin feature/health-endpoint
```

GitHub now has your feature branch.

But `main` has not changed.

Conceptually:

```text
GitHub

             feature/health-endpoint
                    |
                    v
A --- B --- C --- D --- E
          ^
          |
         main
```

Publishing makes the branch available remotely.

Merging integrates it.

These are different operations.

---

# 24. Creating a Pull Request

Once your branch is on GitHub, you can propose merging it.

On GitHub, you can typically navigate to the repository and create a pull request using the Pull Requests interface or a Compare & pull request prompt when available.

You select:

```text
Base branch

Compare branch
```

Then provide:

```text
Title

Description
```

and create the pull request.

A pull request can also be created as a draft when the work is not ready for final review.

---

# 25. Base vs Compare Branch

This is one of the most important pull request concepts.

Suppose:

```text
main
```

is where you want the change to go.

And:

```text
feature/health-endpoint
```

contains your work.

Then:

```text
Base:
main

Compare:
feature/health-endpoint
```

Think:

```text
COMPARE
   |
   | proposed changes
   v
BASE
```

Or:

```text
feature/health-endpoint
          |
          | merge into
          v
         main
```

---

# 26. What the Base Branch Means

The base branch is the branch you want to change.

For example:

```text
base: main
```

means:

```text
If this PR is merged,
main receives the proposed changes.
```

The base is the destination.

---

# 27. What the Compare Branch Means

The compare branch contains the proposed changes.

For example:

```text
compare: feature/health-endpoint
```

means:

```text
Show the changes introduced
by this feature branch relative
to the base.
```

The compare branch is the source of the proposed change.

---

# 28. Common Base/Compare Mistake

Suppose you accidentally choose:

```text
base:
feature/health-endpoint

compare:
main
```

You have reversed the intended direction.

Instead of proposing:

```text
feature -> main
```

you may be asking GitHub to compare in the opposite direction.

Always pause and read:

```text
base
```

and:

```text
compare
```

before creating the PR.

---

# 29. Inspect the Diff Before Creating the PR

Before submitting the pull request, inspect the changed files.

Ask:

```text
Are only expected files included?

Are there generated files that should not be here?

Did I accidentally commit .env?

Are there credentials?

Are debug logs included?

Are unrelated changes present?

Does the diff match the purpose of the PR?
```

A pull request is easier to review when the diff is focused.

---

# 30. Writing a Good Pull Request Title

A weak title:

```text
Changes
```

Another weak title:

```text
Update
```

Another:

```text
Fix stuff
```

These titles tell reviewers almost nothing.

A better title:

```text
Add API health endpoint
```

Or:

```text
Fix timeout handling in payment service
```

Or:

```text
Increase readiness probe timeout
```

Or:

```text
Add Terraform configuration for staging VPC
```

A good title should quickly communicate the main purpose of the change.

---

# 31. Good PR Titles Are Specific

Compare:

```text
Bad:
Fix bug
```

with:

```text
Better:
Fix session expiration after token refresh
```

Compare:

```text
Bad:
Kubernetes update
```

with:

```text
Better:
Add readiness probe to API deployment
```

Compare:

```text
Bad:
Terraform changes
```

with:

```text
Better:
Add private subnets to staging VPC
```

The reviewer should understand the purpose before opening the PR.

---

# 32. Writing a Useful Pull Request Description

The title answers:

```text
What is this change?
```

The description should provide additional context such as:

```text
Why is this needed?

What changed?

How was it tested?

Are there risks?

Does deployment require anything special?

Is there a related issue?
```

---

# 33. Example Pull Request Description

```text
## Why

The API currently has no dedicated health endpoint for
Kubernetes readiness checks.

## What changed

- Added GET /health endpoint
- Added readiness response validation
- Added automated tests for healthy responses

## Testing

- Ran unit tests locally
- Verified /health returns HTTP 200
- Verified response contains status=healthy

## Deployment notes

No database migration or configuration change is required.
```

This gives reviewers useful context before reading the code.

---

# 34. The Description Should Explain Why

Suppose the diff shows:

```yaml
timeoutSeconds: 10
```

A reviewer can see that `timeoutSeconds` changed.

But the diff may not explain why.

The PR description can say:

```text
The existing 2-second timeout causes readiness checks
to fail during application startup when cache
initialization takes longer than expected.
```

Now the reviewer understands the operational reason.

Good descriptions preserve engineering context.

---

# 35. Do Not Turn the Description Into a Novel

Useful does not mean unnecessarily long.

For a tiny documentation typo:

```text
Correct typo in installation example.
```

may be enough.

For a production infrastructure change, much more context may be appropriate.

Match the description depth to the risk and complexity of the change.

---

# 36. Draft Pull Requests

Sometimes you want collaboration before the work is ready to merge.

You can create a draft pull request.

Think:

```text
Draft PR
=
This work is visible,
but it is not ready for final merging.
```

A draft can be useful when:

```text
You want early architectural feedback

You want CI to run

You want teammates to see progress

You need help with an implementation

The feature is still incomplete
```

When ready, the PR can be marked ready for review.

---

# 37. What Happens After the PR Opens?

A pull request typically gives you several important views.

These include areas for:

```text
Conversation

Commits

Checks

Files changed
```

The exact GitHub interface can evolve, but these concepts remain important.

---

# 38. Conversation

The conversation area contains context around the PR.

This can include:

```text
PR description

General comments

Review summaries

Timeline events

Linked issues

Updates

Merge activity
```

Think of it as the collaboration history around the proposed change.

---

# 39. Commits

The commits view shows commits included in the pull request.

For example:

```text
D Add health endpoint
E Add endpoint tests
F Handle unhealthy dependency response
```

This allows reviewers to inspect how the branch evolved.

---

# 40. Checks

Automated validation may appear as checks.

For example:

```text
Unit Tests               PASS

Integration Tests        PASS

Security Scan            PASS

Terraform Validate       PASS

Docker Build             PASS
```

Or:

```text
Unit Tests               PASS

Integration Tests        FAIL
```

A failed required check may prevent the pull request from being merged.

---

# 41. Files Changed

This is one of the most important review areas.

It displays the diff.

For example:

```diff
- timeoutSeconds: 2
+ timeoutSeconds: 10
```

A reviewer can inspect the actual modifications and leave comments on specific lines.

---

# 42. Reviewing a Pull Request

Suppose another engineer creates:

```text
PR #142

Add Kubernetes readiness probe
```

You are asked to review it.

Do not immediately click:

```text
Approve
```

A useful review process is:

```text
Understand purpose

Read description

Inspect files changed

Check logic

Check tests

Check security implications

Check operational implications

Check automated results

Ask questions

Suggest improvements

Then decide
```

---

# 43. Understand the Purpose First

Before reading individual lines, ask:

```text
What problem is this PR solving?
```

Read:

```text
Title

Description

Related issue

Deployment notes
```

Without context, you may review technically correct code against the wrong objective.

---

# 44. Review the Scope

Suppose the PR title is:

```text
Fix login timeout
```

but the changed files include:

```text
auth.py

database.py

Dockerfile

terraform/main.tf

k8s/deployment.yaml

README.md

payment.py
```

That does not automatically mean the PR is wrong.

But it should make you ask:

```text
Why are all these files required?
```

Unexpected scope deserves investigation.

---

# 45. Review the Diff

Inspect additions and deletions.

Ask:

```text
Does the code do what the description claims?

Are error conditions handled?

Could this break existing behavior?

Are tests included?

Are configuration values correct?

Are secrets exposed?

Are permissions excessive?

Could this create operational risk?
```

---

# 46. Reviewing Infrastructure Code

For Terraform:

```text
Could this destroy a resource?

Could this expose a network publicly?

Is the CIDR correct?

Are production resources affected?

Is encryption enabled?

Are variables correct?
```

For Kubernetes:

```text
Are resource limits reasonable?

Are probes correct?

Are secrets handled securely?

Is the image tag appropriate?

Could replicas drop unexpectedly?

Are ports correct?
```

For CI/CD:

```text
Are credentials exposed?

Does the workflow have excessive permissions?

Can untrusted code access secrets?

Does deployment target the correct environment?
```

Pull request review is not only about syntax.

It is about consequences.

---

# 47. Comments

A reviewer can leave comments on a pull request.

There are two broad types to understand:

```text
General comments

Line-specific comments
```

A general comment might say:

```text
Can you explain why this change requires a new dependency?
```

A line-specific comment might be attached directly to:

```python
timeout = 120
```

and ask:

```text
Why do we need a two-minute timeout here?
```

Line comments connect feedback directly to the relevant code.

---

# 48. Good Review Comments

A poor comment:

```text
Wrong.
```

Another poor comment:

```text
Bad code.
```

These provide little useful guidance.

Better:

```text
Could we validate this value before passing it to the
database client? An empty value currently reaches the query
builder and may produce an invalid request.
```

Or:

```text
This deployment uses the default service account.
Could we use the restricted application service account
instead so the Pod receives only the permissions it needs?
```

Good reviews improve both the code and shared understanding.

---

# 49. Ask Questions When You Are Unsure

Review does not mean pretending to know everything.

You can ask:

```text
What happens if this API call times out?
```

or:

```text
Is this value intentionally different from staging?
```

or:

```text
Could you explain why this resource needs public access?
```

Questions can uncover assumptions before they become production problems.

---

# 50. Review Conversations

A line comment can begin a conversation.

Example:

Reviewer:

```text
Should this retry count be configurable instead of hard-coded?
```

Author:

```text
Good point. Production uses a different retry policy.
I'll move it to configuration.
```

Author updates the branch.

Reviewer:

```text
Looks good now.
```

The conversation can then be resolved when the concern has been addressed.

---

# 51. Resolving a Conversation Does Not Mean Hiding a Problem

Do not click:

```text
Resolve conversation
```

simply to make comments disappear.

Resolve when:

```text
The requested change was implemented

The question was answered

The team agreed no change is necessary

The concern was otherwise addressed
```

The goal is resolution, not cosmetic cleanup.

---

# 52. Review Decisions

When submitting a review, GitHub supports review decisions such as:

```text
Comment

Approve

Request changes
```

These have different meanings.

---

# 53. Comment

Use:

```text
Comment
```

when you want to leave feedback without explicitly approving or requesting changes.

For example:

```text
I have a question about the timeout behavior,
but I am not blocking this change.
```

A comment is discussion.

It is not the same as approval.

---

# 54. Approve

Use:

```text
Approve
```

when you believe the changes are ready from your review perspective.

Approval means approximately:

```text
I reviewed this change and believe it is ready
to proceed, subject to any other repository
requirements.
```

Approval does not necessarily mean the PR can merge immediately.

The repository might still require:

```text
More approvals

Passing checks

Resolved conversations

Updated base branch

Security validation
```

---

# 55. Request Changes

Use:

```text
Request changes
```

when you identify issues that should be addressed before merging.

For example:

```text
The new endpoint logs the authentication token.
Please remove the token from the log output before merging.
```

Or:

```text
This Terraform rule exposes port 22 to 0.0.0.0/0.
Please restrict the source range before merging.
```

These are not cosmetic preferences.

They can represent blocking concerns.

---

# 56. Do Not Treat Request Changes as Personal

Code review evaluates the proposed change.

It should not become:

```text
You are a bad engineer.
```

It should remain:

```text
This implementation creates this risk.

Here is the evidence.

Here is what needs to change.
```

Professional review focuses on engineering outcomes.

---

# 57. Updating a Pull Request

Suppose your PR is open:

```text
feature/health-endpoint
          |
          v
       PR #142
```

A reviewer asks:

```text
Please add a test for an unhealthy dependency.
```

You do not normally need to create another pull request.

Modify the same branch.

---

# 58. Update the Branch Locally

Ensure you are on the PR branch:

```bash
git switch feature/health-endpoint
```

Verify:

```bash
git status
```

Modify the test.

Then:

```bash
git diff
```

Stage:

```bash
git add tests/test_health.py
```

Review:

```bash
git diff --staged
```

Commit:

```bash
git commit -m "Add unhealthy dependency test"
```

Push:

```bash
git push
```

---

# 59. The Pull Request Updates Automatically

Because the pull request tracks the branch, new commits pushed to that branch become part of the open pull request.

Before:

```text
feature/health-endpoint

D --- E
```

After feedback:

```text
feature/health-endpoint

D --- E --- F
```

The PR now includes `F`.

You generally do not create a new PR for every review fix.

---

# 60. Automated Checks May Run Again

Suppose the original PR passed:

```text
Unit Tests       PASS
Security Scan    PASS
```

You push another commit.

The code changed.

Therefore, automated systems may run again.

This is important.

An earlier green check does not necessarily validate a later version of the branch.

The latest proposed state should be validated.

---

# 61. Resolving Review Feedback

A strong feedback workflow is:

```text
Read comment carefully
       |
       v
Understand concern
       |
       v
Decide whether code needs change
       |
       v
Modify locally
       |
       v
Test
       |
       v
Review diff
       |
       v
Commit
       |
       v
Push
       |
       v
Reply when useful
       |
       v
Resolve conversation
       |
       v
Request re-review if needed
```

Do not simply change code until the reviewer stops commenting.

Understand the underlying concern.

---

# 62. When You Disagree With Review Feedback

You do not have to silently implement every suggestion.

Suppose reviewer says:

```text
Use a global variable here.
```

But you believe that creates concurrency problems.

Respond with technical reasoning:

```text
I kept this scoped to the request because the service handles
concurrent requests and a shared mutable value could introduce
cross-request state. Would you be comfortable keeping it local,
or is there another reason you prefer shared state here?
```

Now the team can discuss the design.

Code review is collaboration, not command execution.

# 65. Merge Strategies

Once the pull request is approved, the changes must become part of the base branch.

GitHub commonly supports three important strategies:

```text
Merge commit

Squash and merge

Rebase and merge
```

Repositories can enable or disable particular methods.

Your team should choose intentionally rather than treating the three buttons as interchangeable.

---

# 66. Merge Commit

Suppose:

```text
main:

A --- B --- C


feature:

          D --- E
         /
A --- B --- C
```

A merge-commit strategy produces conceptually:

```text
A --- B --- C -------- M
           \           /
            D --- E ---
```

`M` is a merge commit.

It joins the histories.

---

# 67. What Merge Commit Preserves

The feature commits remain visible:

```text
D

E
```

and Git records an explicit merge point:

```text
M
```

This preserves the branch's commit structure and clearly records that a merge occurred.

---

# 68. Merge Commit Example

Feature branch:

```text
D Add health endpoint
E Add endpoint tests
F Improve validation
```

After merge:

```text
A --- B --- C -------------- M
           \                /
            D --- E --- F --
```

The base branch history contains the feature commits plus the merge commit.

---

# 69. Advantages of Merge Commits

Potential advantages:

```text
Preserves individual feature commits

Preserves explicit branch integration

Shows where feature work joined main

Useful when individual commits have meaning
```

---

# 70. Tradeoffs of Merge Commits

A busy repository can accumulate many merge commits.

History may look like:

```text
* Merge pull request #145
|\
| * Fix validation
| * Add endpoint
|/
* Merge pull request #144
|\
| * Update deployment
|/
* Merge pull request #143
```

Some teams like this explicit structure.

Others prefer a more compact or linear history.

---

# 71. Squash and Merge

Suppose your feature branch contains:

```text
D Add health endpoint

E Fix typo

F Fix test

G Address review

H Remove debug log
```

All five commits represent one logical feature.

With squash and merge, GitHub combines the pull request's changes into one commit on the base branch.

Conceptually:

```text
Feature:

          D --- E --- F --- G --- H
         /
A --- B --- C


Base after squash:

A --- B --- C --- S
```

`S` represents the combined change.

---

# 72. What Squashing Means

Instead of preserving:

```text
D
E
F
G
H
```

as separate commits on the base branch, their combined changes become:

```text
S
```

For example:

```text
S Add API health endpoint
```

This can make the base branch history easier to read.

---

# 73. Advantages of Squash and Merge

Potential advantages:

```text
Cleaner base history

One PR can become one logical commit

Temporary fixup commits disappear from base history

Easy to associate one merged commit with one feature
```

This is useful when feature branches contain commits such as:

```text
Fix typo

Fix test again

Address review

Oops

Remove debug
```

Those commits may have been useful during development but not valuable as permanent individual history on `main`.

---

# 74. Tradeoffs of Squash and Merge

You lose the individual commit structure from the feature branch on the base branch.

Instead of:

```text
Add API

Add tests

Add validation
```

the base receives one combined commit.

If those individual commits carried meaningful independent history, squashing removes that separation from the base branch.

Choose based on how your team wants history to be used.

---

# 75. Rebase and Merge

Now consider:

```text
main:

A --- B --- C


feature:

          D --- E
         /
A --- B --- C
```

A rebase-and-merge style places the feature commits onto the tip of the base branch without creating a merge commit.

Conceptually:

```text
A --- B --- C --- D' --- E'
```

The result is linear.

---

# 76. Why D' and E'?

Rebasing recreates commits in a new historical position.

Because commit identity depends on commit information including parent relationships, recreated commits receive new commit IDs.

Therefore:

```text
D
```

and:

```text
D'
```

may contain equivalent changes but are not the same Git commit object.

This is one reason rebasing requires a strong understanding of history.

We will study rebase deeply in Part 17.

---

# 77. Advantages of Rebase and Merge

Potential advantages:

```text
Linear history

No merge commit

Individual logical commits remain separate

History can be easier to follow sequentially
```

---

# 78. Tradeoffs of Rebase and Merge

Rebasing rewrites commit identity.

Teams must understand the consequences.

Poorly organized commits also remain individually visible.

For example:

```text
Fix

Fix again

Actually fix

Oops

Final fix
```

A linear history is not automatically a good history.

Commit quality still matters.

---

# 79. Comparing the Three Strategies

Suppose the feature contains:

```text
D --- E --- F
```

## Merge commit

```text
A --- B --- C ------------ M
           \              /
            D --- E --- F
```

Result:

```text
Feature commits preserved

Merge point preserved
```

## Squash and merge

```text
A --- B --- C --- S
```

Result:

```text
Feature changes become one commit
```

## Rebase and merge

```text
A --- B --- C --- D' --- E' --- F'
```

Result:

```text
Individual commits remain

History is linear

No merge commit
```

---

# 80. Which Merge Strategy Is Best?

There is no universal answer.

A team may choose:

```text
Squash for feature PRs

Merge commits for long-running integration work

Rebase for carefully structured linear history
```

Another team may enforce only one method.

Repository configuration may disable methods the team does not allow.

As a beginner joining a project:

```text
Do not impose your personal merge preference.
```

Check the project's workflow.

---

# 81. Merge Strategy and History Design

Merge strategy is not just a GitHub button.

It determines what future engineers see when they run:

```bash
git log
```

Consider what you want history to answer:

```text
What feature was added?

What commits created it?

When were branches integrated?

Can I revert one logical PR easily?

Do individual intermediate commits matter?
```

History should serve future troubleshooting and maintenance.

# 82. Practical Production Example

Suppose PR:

```text

```

contains:

```text

E Add dashboard
F Add notification topic
G Fix alarm threshold
H Address review feedback
```

If squashed:

```text

```

Future history is concise.

If merged with a merge commit, all development commits remain visible.

Neither is automatically correct.

The team chooses based on its history policy.

# 83. Merge Conflicts Before a PR Can Merge

Suppose `main` changes while your PR remains open.

Originally:

```text
main:
A --- B --- C

feature:
          D --- E
```

Then another PR changes `main`:

```text
main:
A --- B --- C --- X
```

If `X` conflicts with your feature changes, GitHub may report that the pull request has conflicts.

You learned manual conflict resolution in Part 9.

The principle remains:

```text
Understand both changes

Resolve intentionally

Test final result

Commit resolution if required

Push updated branch

Verify PR
```

Never delete conflict markers blindly just to make Git accept the file.

# 84. Deleting the Feature Branch After Merge

After the pull request is merged, you may no longer need:

```text
feature/health-endpoint
```

GitHub may offer:

```text
Delete branch
```

Some repositories can also automatically delete head branches after pull requests are merged.

Why delete completed feature branches?

Because otherwise remote branch lists accumulate stale branches:

```text
feature/login-2023

feature/old-api

fix/test-thing

feature/finished-six-months-ago
```

Deleting completed short-lived branches keeps the repository easier to navigate.

# 85. Deleting the Remote Branch Does Not Delete Your Local Branch

Suppose GitHub deletes:

```text
feature/health-endpoint
```

Your computer may still have:

```text
feature/health-endpoint
```

These are separate.

Remember:

```text
Local branch
!=
Remote branch
```

You may need to clean up locally as well.

# 86. Return to main After Merge

```bash

```

Then refresh:

```bash

```

Update your local `main`:

```bash

```

Now your local `main` contains the merged work.

# 87. Delete the Local Feature Branch

Once you have verified the feature was merged and your work is safe:

```bash
git branch -d feature/health-endpoint
```

The:

```text
-d
```

requests deletion with Git's merged-work safety check.

If Git believes the branch contains work that has not been merged appropriately, it may refuse.

That refusal is useful.

Investigate before forcing deletion.

---

# 88. Do Not Automatically Use -D

You may encounter:

```bash
git branch -D feature/health-endpoint
```

Capital:

```text
-D
```

forces deletion.

Do not use it merely because:

```text
-d didn't work.
```

First determine why Git believes the branch contains unmerged work.

Remember the safety principle:

```text
Git refuses
     |
     v
Understand why
     |
     v
Then choose action
```

Not:

```text
Git refuses
     |
     v
Add force
```

# 89. Remote-Tracking Cleanup

After a remote branch is deleted, your local remote-tracking information may need pruning.

You can run:

```bash
git fetch --prune origin
```

This updates remote information and removes stale remote-tracking references for branches deleted from that remote.

Again:

```text
Pruning origin/feature/example
```

does not mean Git automatically deletes your local:

```text
feature/example
```

branch.

The most important concept is that a pull request is not simply:

```text
Please put my code into main.
```

It is a controlled collaboration point.

It answers:

```text
What are we changing?

Why are we changing it?

What files changed?

What commits are involved?

Has anyone reviewed it?

What concerns were raised?

Were those concerns resolved?

Did automated validation pass?

How should the history be merged?
```

You also understand the three major merge outcomes:

```text
MERGE COMMIT

A --- B --- C ------------ M
           \              /
            D --- E ------


SQUASH AND MERGE

A --- B --- C --- S


REBASE AND MERGE

A --- B --- C --- D' --- E'
```

These are not merely three buttons.

They produce different Git histories.

Most importantly, you now have the foundation for the professional workflow:

```text
Branch

Develop

   v

   |
   v
Merge
   |
   v
Cleanup
```

This is the point where Git stops being only a personal version-control tool and becomes a team engineering system.
