# Part 13: Firewalls, Network Security, and Access Control

## Learn How Network Traffic Is Allowed, Restricted, and Protected

In Part 12, you followed a web request through DNS, routing, transport, TLS, HTTP, proxies, and applications.

Now consider this situation:

```text
Client
  |
  | TCP 443
  v
Server
```

The client knows the server's IP.

The route exists.

The server is running.

The application is listening on TCP 443.

Yet:

```text
Connection times out.
```

Why?

There may be another decision point in the path:

```text
Client
  |
  v
Network
  |
  v
FIREWALL
  |
  | Allow?
  | Deny?
  v
Server
```

Modern networks do not simply ask:

> Can these two systems technically reach each other?

They also ask:

> Should these two systems be permitted to communicate?

That is the problem firewalls and network access controls help solve.

---

# 1. What Is a Firewall?

A firewall is a security control that evaluates network traffic and decides whether that traffic should be:

```text
Allowed
Denied
Rejected
Dropped
Logged
```

depending on its rules and capabilities.

A simplified firewall decision looks like:

```text
Packet / Connection
       |
       v
Examine traffic
       |
       v
Match security policy
       |
       +---- Allowed ----> Continue
       |
       +---- Denied -----> Stop
```

The firewall sits between traffic and a protected resource or network boundary.

---

# 2. Why Firewalls Exist

Without access controls, any reachable device might potentially attempt to communicate with any exposed service.

Suppose a server runs:

```text
SSH       TCP 22
HTTP      TCP 80
HTTPS     TCP 443
Database  TCP 5432
```

The business may want:

```text
Internet -> HTTPS        ALLOW

Internet -> SSH          DENY

Internet -> Database     DENY

Admin network -> SSH     ALLOW

Application -> Database  ALLOW
```

The fact that a service exists does not mean everyone should be able to access it.

---

# 3. Reachability vs Permission

This distinction is fundamental.

Routing answers:

```text
Where should the packet go?
```

A firewall answers:

```text
Should this traffic be allowed?
```

For example:

```text
Routing table:
Route exists.

Firewall:
DENY TCP 22.
```

The route can be perfectly correct while the connection still fails.

---

# 4. A Firewall Does Not Replace Routing

Suppose:

```text
Client:
10.0.1.50

Server:
10.0.20.50
```

A firewall rule says:

```text
ALLOW
10.0.1.50 -> 10.0.20.50 TCP 443
```

But there is no route to:

```text
10.0.20.0/24
```

The firewall's allow rule does not create the missing route.

You still need:

```text
Correct addressing
Routing
Layer 2 connectivity where appropriate
```

Firewall policy is another layer of the communication path.

---

# 5. A Firewall Does Not Automatically Mean a Separate Appliance

A firewall may exist:

```text
On the endpoint itself

On a router

On a dedicated appliance

Inside a cloud platform

Inside a virtual network

On a hypervisor

Inside a host operating system

At an Internet edge

Between internal network segments
```

One packet may encounter several independent security controls.

---

# 6. Defense in Depth

Consider:

```text
Internet
   |
   v
Edge Firewall
   |
   v
Cloud Security Control
   |
   v
Load Balancer
   |
   v
Host Firewall
   |
   v
Application
```

A connection may need to satisfy multiple policies.

Therefore:

```text
"Security group allows 443."
```

does not necessarily prove:

```text
"Nothing else can block 443."
```

Always inspect the complete path.

---

# 7. Inbound Traffic

Inbound traffic is traffic entering a system, interface, security boundary, or protected network.

For a web server:

```text
Internet
   |
   | TCP 443
   v
Web Server
```

From the server's perspective, this connection is inbound.

A common policy might be:

```text
Inbound TCP 443:
ALLOW

Inbound TCP 22:
ALLOW only from admin network

Everything else:
DENY
```

---

# 8. Outbound Traffic

Outbound traffic leaves a system or protected boundary.

Example:

```text
Application Server
       |
       | TCP 443
       v
External API
```

From the application server's perspective:

```text
Outbound HTTPS
```

is being used.

Organizations may restrict outbound traffic as well as inbound traffic.

---

# 9. Why Outbound Filtering Matters

Beginners often focus entirely on inbound traffic.

But compromised systems frequently need outbound communication.

For example:

```text
Compromised Server
       |
       v
Unauthorized External Destination
```

Restricting unnecessary outbound traffic can reduce certain risks.

Outbound controls can also enforce architectural requirements.

Example:

```text
Database server
   |
   X
Direct Internet access
```

Perhaps the database has no legitimate reason to communicate directly with arbitrary Internet destinations.

---

# 10. Inbound and Outbound Are Relative

Suppose:

```text
Client A
   |
   v
Server B
```

For Client A:

```text
Request = outbound
Response = inbound
```

For Server B:

```text
Request = inbound
Response = outbound
```

Always ask:

> Inbound or outbound relative to what?

---

# 11. What Information Can Firewall Rules Examine?

Basic network firewall rules commonly evaluate fields such as:

```text
Source IP address
Destination IP address
Protocol
Source port
Destination port
Interface
Direction
Connection state
```

More advanced security systems may inspect much more.

But these fields form the foundation.

---

# 12. Source Address

The source address identifies where traffic originates at the IP layer.

Example:

```text
Source:
10.20.30.50
```

A rule could say:

```text
ALLOW TCP 22
FROM 10.20.30.0/24
```

Meaning only clients from that network are permitted by that rule.

---

# 13. Destination Address

The destination address identifies the target.

Example:

```text
Source:
10.20.30.50

Destination:
10.50.10.25
```

A rule may specifically protect:

```text
10.50.10.25
```

or an entire destination subnet.

---

# 14. Protocol

Firewall rules can distinguish protocols.

Common examples:

```text
TCP
UDP
ICMP
ICMPv6
```

For example:

```text
ALLOW TCP 443
```

is not equivalent to:

```text
ALLOW UDP 443
```

This becomes particularly relevant with technologies such as HTTP/3, which uses QUIC over UDP.

---

# 15. Destination Ports

For TCP and UDP, the destination port identifies the service the client wants to reach.

Examples:

```text
TCP 22    SSH
TCP 80    HTTP
TCP 443   HTTPS
UDP 53    DNS
TCP 53    DNS in applicable cases
```

A firewall can allow one service while blocking another.

---

# 16. Source Ports

Clients frequently use ephemeral source ports.

Example:

```text
Client:
10.0.1.50:53124

Server:
10.0.2.20:443
```

The connection is:

```text
10.0.1.50:53124
        ->
10.0.2.20:443
```

The destination port is 443.

The source port is 53124.

Understanding both becomes important when studying stateful filtering.

---

# 17. The Five-Tuple

Network flows are often described using information including:

```text
Source IP
Destination IP
Source port
Destination port
Protocol
```

For example:

```text
Source IP:
10.0.1.50

Source port:
53124

Destination IP:
10.0.2.20

Destination port:
443

Protocol:
TCP
```

This combination helps identify a network flow.

---

# 18. Firewall Rules

A firewall rule expresses a traffic policy.

Conceptually:

```text
IF traffic matches conditions
THEN perform action
```

Example:

```text
Source:
10.10.20.0/24

Destination:
10.10.50.10

Protocol:
TCP

Destination port:
5432

Action:
ALLOW
```

This permits matching PostgreSQL traffic according to that policy.

---

# 19. Allow Rules

An allow rule permits matching traffic.

Example:

```text
ALLOW
Source: 10.0.10.0/24
Destination: 10.0.20.50
Protocol: TCP
Port: 443
```

Conceptually:

```text
10.0.10.0/24
      |
      | TCP 443
      v
10.0.20.50

ALLOW
```

---

# 20. Deny Rules

A deny rule prevents matching traffic.

Example:

```text
DENY
Source: Internet
Destination: Database
Protocol: TCP
Port: 5432
```

Conceptually:

```text
Internet
   |
   | TCP 5432
   X
Database
```

The exact behavior may be a silent drop or an explicit rejection depending on firewall configuration.

---

# 21. Drop vs Reject

Two common firewall behaviors are:

```text
DROP
REJECT
```

A drop typically means:

```text
Discard traffic silently.
```

A reject typically means:

```text
Block traffic and return an error indication.
```

From the client's perspective, these may produce different symptoms.

---

# 22. Firewall Drops and Timeouts

Suppose a TCP SYN is silently dropped:

```text
Client
  |
  | SYN
  v
Firewall
  X
```

The client may retry.

Eventually:

```text
Connection timeout
```

This is one reason a timeout can indicate filtering.

But a timeout alone does **not** prove a firewall is responsible.

---

# 23. Firewall Rejects and Faster Failure

Suppose the firewall explicitly rejects traffic.

The client may receive an error quickly.

That can appear differently from a silent timeout.

However, do not diagnose firewall behavior based only on timing.

Collect evidence from:

```text
Routes
Packet captures
Firewall logs
Server listeners
Cloud controls
```

---

# 24. Rule Order

Some firewall systems evaluate rules sequentially.

Example:

```text
Rule 1:
DENY TCP 22 from anywhere

Rule 2:
ALLOW TCP 22 from 10.0.10.0/24
```

If the system uses first-match processing, Rule 1 may prevent Rule 2 from ever applying.

Order therefore matters in systems with ordered rule evaluation.

---

# 25. Not Every Firewall Uses the Same Rule Model

Do not assume every security system processes rules identically.

Some systems use:

```text
Ordered rules
Priority values
Chains
Tables
Combined allow policies
Stateful abstractions
Stateless ACLs
```

Cloud security groups, Linux nftables, router ACLs, and enterprise firewalls can have different semantics.

Understand the specific control you are troubleshooting.

---

# 26. Default Policies

What happens if no explicit rule matches?

That depends on the default policy.

Example:

```text
Default:
ALLOW
```

or:

```text
Default:
DROP
```

A security-oriented approach commonly aims toward:

```text
Allow what is required.
Deny what is not required.
```

rather than allowing everything and trying to enumerate every possible bad connection.

---

# 27. Default Deny

Conceptually:

```text
Incoming Traffic
      |
      v
Does an allow rule match?
      |
  +---+---+
  |       |
 YES      NO
  |       |
ALLOW    DENY
```

This is often described as:

```text
Default deny
```

It supports least-privilege design.

---

# 28. Least Privilege

Least privilege means granting only the access necessary to perform the required function.

Suppose an application needs:

```text
App Server
    |
    | TCP 5432
    v
Database
```

Poor policy:

```text
ALLOW ANY
FROM ANY
TO ANY
```

Better policy:

```text
ALLOW
Application subnet
->
Database
TCP 5432
```

Better still, where the platform supports appropriate identity/security-group-based controls, policy may be tied more closely to the actual application workload rather than an unnecessarily broad network.

---

# 29. The Problem With `0.0.0.0/0`

You will often encounter:

```text
0.0.0.0/0
```

It represents all IPv4 destinations or sources depending on context.

For a source rule:

```text
Source:
0.0.0.0/0
```

means:

```text
Any IPv4 source
```

This may be appropriate for a public web service on:

```text
TCP 443
```

but extremely dangerous for unnecessary administrative or database services.

---

# 30. Example: Public Web Server

A reasonable simplified inbound policy might be:

```text
TCP 443
Source: 0.0.0.0/0
ALLOW

TCP 80
Source: 0.0.0.0/0
ALLOW
```

if HTTP is required, perhaps for redirection.

But:

```text
TCP 22
Source: 0.0.0.0/0
ALLOW
```

deserves much more scrutiny.

Public SSH exposure should not be the automatic default.

---

# 31. Stateful Firewalls

A stateful firewall tracks information about active network connections or flows.

Suppose a client initiates:

```text
10.0.1.50:53124
      ->
10.0.2.20:443
```

The firewall recognizes that return traffic:

```text
10.0.2.20:443
      ->
10.0.1.50:53124
```

belongs to an established connection.

Conceptually:

```text
Client
  |
  | NEW connection
  v
Stateful Firewall
  |
  v
Server

Server
  |
  | Response belonging
  | to established flow
  v
Stateful Firewall
  |
  v
Client
```

---

# 32. Why Stateful Filtering Is Useful

Without state tracking, policies may need to explicitly account for traffic in both directions based on packet fields.

A stateful firewall can understand:

```text
This response belongs to a connection
that was already permitted.
```

That simplifies many policies.

---

# 33. Connection State

Stateful systems may classify traffic using concepts such as:

```text
NEW
ESTABLISHED
RELATED
INVALID
```

Exact terminology and implementation vary.

The important concept is:

```text
The firewall remembers context.
```

It does not evaluate every packet as if no previous traffic existed.

---

# 34. Stateful TCP Example

Client initiates:

```text
10.0.1.50:53124 -> 10.0.2.20:443
```

The firewall allows the new connection.

TCP handshake:

```text
Client                    Server

SYN --------------------->

    <---------------- SYN-ACK

ACK --------------------->
```

The stateful firewall understands the return SYN-ACK belongs to the permitted connection.

You do not necessarily need an independent broad inbound rule allowing arbitrary traffic toward ephemeral port 53124.

---

# 35. Stateful UDP

UDP does not establish connections using a TCP-style handshake.

However, stateful firewalls can still maintain temporary flow state.

Example:

```text
Client
53124/UDP
   |
   | DNS query
   v
Server
53/UDP
```

The firewall remembers the outbound flow for a period and allows the corresponding response.

Stateful does not mean:

```text
TCP only.
```

---

# 36. Stateless Filtering

A stateless filter evaluates packets without maintaining the same kind of connection-state context.

Each packet is evaluated according to configured rules.

Conceptually:

```text
Packet 1 -> evaluate
Packet 2 -> evaluate
Packet 3 -> evaluate
Packet 4 -> evaluate
```

The device does not simply conclude:

```text
"This packet belongs to the connection
I approved earlier."
```

in the same stateful sense.

---

# 37. Stateless Return Traffic

Suppose a stateless filter allows:

```text
Client -> Server TCP 443
```

You may also need rules that permit appropriate return traffic:

```text
Server TCP 443
        ->
Client ephemeral port
```

This is one reason stateless ACL design requires careful attention to both directions.

---

# 38. Stateful vs Stateless

Simplified comparison:

| Characteristic                  | Stateful                       | Stateless                      |
| ------------------------------- | ------------------------------ | ------------------------------ |
| Tracks flow/connection context  | Yes                            | Generally no                   |
| Understands established traffic | Yes                            | Not in same way                |
| Return traffic handling         | Often automatically associated | Explicit policy often required |
| Packet evaluation               | Uses rules + state             | Primarily packet/rule matching |
| Common use                      | Firewalls, security groups     | ACL-style filtering            |

Do not assume one is universally better.

They solve different architectural requirements.

---

# 39. Host Firewalls

A host firewall runs on or directly protects an individual machine.

Example:

```text
Internet
   |
   v
Linux Server
   |
   +--> Host firewall
   |
   +--> SSH
   +--> Web server
```

The host firewall can decide which traffic is allowed to reach local services.

---

# 40. Why Host Firewalls Matter

Suppose the network firewall accidentally permits:

```text
TCP 5432
```

toward a server.

The host firewall could still block it.

This creates another layer of protection.

```text
Network Firewall
      |
      v
Host Firewall
      |
      v
Application
```

Defense in depth reduces reliance on one control.

---

# 41. Network Firewalls

Network firewalls protect traffic crossing network boundaries.

Example:

```text
Internet
   |
   v
Network Firewall
   |
   v
Corporate Network
```

or:

```text
User Network
   |
   v
Internal Firewall
   |
   v
Database Network
```

They can enforce policy between entire network segments.

---

# 42. Host Firewall vs Network Firewall

Host firewall:

```text
Protects individual host
```

Network firewall:

```text
Protects traffic crossing a network boundary
```

Organizations often use both.

Example:

```text
Internet
   |
   v
Network Firewall
   |
   v
Web Subnet
   |
   v
Host Firewall
   |
   v
Web Server
```

---

# 43. Linux Firewall Architecture

Modern Linux packet filtering is built around the kernel's networking capabilities, particularly Netfilter infrastructure.

User-space tools configure rules that the kernel enforces.

Historically, the most familiar tool has been:

```text
iptables
```

Modern Linux increasingly uses:

```text
nftables
```

Higher-level tools such as:

```text
UFW
firewalld
```

can provide simpler management interfaces.

---

# 44. Netfilter Concept

Think of Linux packet filtering conceptually as:

```text
Packet enters Linux kernel
        |
        v
Netfilter processing
        |
        v
Configured policy/rules
        |
        +--> Accept
        +--> Drop
        +--> Reject
        +--> Other processing
```

Tools such as nftables configure this behavior.

---

# 45. nftables

`nftables` is the modern Linux packet-filtering framework intended to replace many traditional uses of:

```text
iptables
ip6tables
arptables
ebtables
```

Its user-space command is commonly:

```bash
nft
```

To inspect rules, a common command is:

```bash
sudo nft list ruleset
```

This is an excellent read-only starting point.

---

# 46. nftables Concepts

Important nftables concepts include:

```text
Tables
Chains
Rules
Hooks
Expressions
Sets
```

Simplified:

```text
Table
  |
  +--> Chain
         |
         +--> Rule
         +--> Rule
         +--> Rule
```

Do not confuse a firewall table with a routing table.

They solve different problems.

---

# 47. nftables Tables

A table groups related chains and rules.

Conceptually:

```text
table inet filter
```

might contain:

```text
input chain
forward chain
output chain
```

Actual configurations vary.

The `inet` family can be used for both IPv4 and IPv6 filtering.

---

# 48. nftables Chains

Chains contain rules.

Common traffic directions conceptually include:

```text
INPUT
OUTPUT
FORWARD
```

The exact nftables names are administrator-defined, though base chains attach to hooks such as:

```text
input
output
forward
```

---

# 49. INPUT Traffic

Input traffic is destined for the local machine.

Example:

```text
Client
  |
  | SSH
  v
Linux Server
```

Traffic toward the Linux server itself can pass through input filtering.

---

# 50. OUTPUT Traffic

Output traffic originates locally.

Example:

```text
Linux Server
    |
    | HTTPS request
    v
External API
```

Locally generated traffic can be filtered through output processing.

---

# 51. FORWARD Traffic

Forwarded traffic is passing through the Linux system rather than terminating on it.

Example:

```text
Network A
    |
    v
Linux Router
    |
    v
Network B
```

The Linux host is forwarding the traffic.

This is different from traffic addressed to the router itself.

---

# 52. Local vs Forwarded Traffic

This distinction matters enormously.

Suppose Linux acts as a router.

Traffic:

```text
10.0.1.50
    |
    v
Linux Router
    |
    v
10.0.2.50
```

does not terminate on the router.

Therefore troubleshooting only local INPUT policy may miss the relevant filtering path.

---

# 53. Inspecting nftables Safely

A useful observation command:

```bash
sudo nft list ruleset
```

Look for:

```text
Tables
Chains
Hooks
Policies
Source/destination matches
Protocols
Ports
Accept/drop/reject actions
Counters
```

Initially, learn to read rules before learning to change them.

---

# 54. iptables Concepts

`iptables` is the older, widely known Linux firewall administration interface.

You will still encounter it in:

```text
Existing servers
Documentation
Legacy environments
Containers
Troubleshooting guides
Interview questions
```

Even on some modern systems, an `iptables` command may interact with an nftables-backed compatibility layer.

Therefore understanding the concepts remains useful.

---

# 55. Common iptables Chains

Traditional filter-table chains include:

```text
INPUT
OUTPUT
FORWARD
```

Same conceptual distinction:

```text
INPUT
Traffic to this host

OUTPUT
Traffic from this host

FORWARD
Traffic through this host
```

---

# 56. Inspecting iptables Rules

A common command is:

```bash
sudo iptables -L -n -v
```

This can show:

```text
Chains
Policies
Packet counters
Byte counters
Rules
Protocols
Sources
Destinations
Actions
```

The `-n` option avoids name resolution, which can make troubleshooting output faster and clearer.

---

# 57. Why Counters Matter

Suppose a rule shows:

```text
Packets:
0
```

while you repeatedly generate traffic that you expect to match it.

That may suggest:

```text
Traffic is not reaching this rule.

An earlier rule matches.

Wrong chain.

Wrong interface.

Wrong protocol.

Wrong address.

Wrong port.
```

Counters can turn firewall troubleshooting into evidence-based investigation.

---

# 58. UFW

UFW stands for:

```text
Uncomplicated Firewall
```

It provides a simpler interface for firewall management, commonly on Ubuntu systems.

Check status:

```bash
sudo ufw status
```

More detail:

```bash
sudo ufw status verbose
```

This can show:

```text
Whether UFW is active
Default policies
Allowed services
Source restrictions
```

---

# 59. UFW Rule Concept

A rule might conceptually allow:

```text
TCP 22
from trusted admin network
```

rather than:

```text
TCP 22
from anywhere
```

The important skill is understanding what the rule means, not simply memorizing commands.

---

# 60. Never Randomly Modify a Remote Firewall

This deserves special emphasis.

Suppose you are connected through SSH:

```text
Your Laptop
    |
    | TCP 22
    v
Remote Server
```

If you accidentally block TCP 22 before ensuring another safe access path exists:

```text
Your Laptop
    |
    X
Remote Server
```

you can lock yourself out.

On remote production systems:

```text
Inspect first.

Understand existing policy.

Confirm management access.

Use approved change procedures.

Have rollback/recovery access.

Then modify.
```

Do not experiment with firewall policy on a production SSH server.

---

# 61. Cloud Firewalls

Cloud networking introduces virtualized security controls.

Examples include concepts such as:

```text
Instance security groups
Subnet/network ACLs
Cloud firewall services
Load balancer security policies
Managed WAFs
```

These controls may exist even though you cannot see a physical firewall appliance.

---

# 62. Security Groups

In cloud environments, a security group commonly acts as a virtual firewall associated with resources or network interfaces.

A simplified rule might be:

```text
Inbound

Protocol:
TCP

Port:
443

Source:
0.0.0.0/0

Action:
Allow
```

Exact capabilities and semantics depend on the cloud provider.

---

# 63. Security Groups Are Commonly Stateful

Major cloud security-group implementations commonly provide stateful behavior.

Conceptually:

```text
Client
  |
  | Allowed inbound connection
  v
Cloud Resource
  |
  | Return traffic
  v
Client
```

Return traffic belonging to an allowed connection can be handled through the maintained state.

However, always verify the behavior of the specific platform you operate.

---

# 64. Security Group Example

Architecture:

```text
Internet
   |
   | HTTPS
   v
Load Balancer
   |
   | Application traffic
   v
App Server
   |
   | Database traffic
   v
Database
```

A better design is not:

```text
Everything accepts traffic from 0.0.0.0/0.
```

Instead:

```text
Load Balancer:
Allow HTTPS from clients.

Application:
Allow app port from load balancer.

Database:
Allow DB port from application tier.
```

This creates controlled communication paths.

---

# 65. Security Group Chaining Concept

Conceptually:

```text
Internet
   |
   | 443
   v
[Load Balancer SG]
   |
   | 8080
   v
[Application SG]
   |
   | 5432
   v
[Database SG]
```

Each tier exposes only what the next required tier needs.

This is much stronger than making every server directly reachable from everywhere.

---

# 66. Network ACL Concepts

A Network Access Control List, or network ACL, is another filtering mechanism commonly associated with network/subnet boundaries.

A simplified ACL can evaluate:

```text
Source
Destination
Protocol
Port
Direction
Allow/Deny
```

Cloud network ACL implementations are often stateless.

Therefore return traffic may require explicit consideration.

---

# 67. Security Group vs Network ACL

A useful cloud mental model:

```text
Security Group
    |
    +--> Resource/interface-oriented
    +--> Commonly stateful

Network ACL
    |
    +--> Subnet/network-boundary oriented
    +--> Commonly stateless
```

Exact provider behavior matters.

Do not apply AWS terminology blindly to every cloud platform.

---

# 68. Why Stateless ACLs Can Be Tricky

Client:

```text
10.0.1.50:53124
```

Server:

```text
10.0.2.20:443
```

Forward direction:

```text
53124 -> 443
```

Return direction:

```text
443 -> 53124
```

A stateless ACL may need policy that permits both appropriate directions.

If return ephemeral-port traffic is blocked:

```text
Connection may fail
```

even though the inbound server port appears permitted.

---

# 69. Ephemeral Ports and Firewall Troubleshooting

This is where Part 9 becomes important.

Suppose the client chooses:

```text
Source port:
53124
```

and connects to:

```text
Destination port:
443
```

The response is:

```text
Source port:
443

Destination port:
53124
```

Stateless controls need to account for this return path appropriately.

Do not assume both directions use destination port 443.

# 70. Network Segmentation

Instead of:

```text
   |
   v
```

Suppose one employee laptop is compromised.

```text

      |
      +--> Database
      +--> Backup Server
      +--> Admin Server
      +--> Production
```

```text
      |
      v

      X--> Management
```

```text
   |

   |
   v
```

# 74. DMZ Concept

DMZ commonly refers to a network segment used to place externally accessible systems in a controlled zone separated from more sensitive internal networks.

Simplified:

```text

   |
   v

   |
   v
DMZ
   |
   v

   |
   v

```

# 75. Why a DMZ Exists

Suppose a public web server is compromised.

Without segmentation:

```text

        |

```

```text

        |
        v

        |
        X
```

---

# 76. DMZ Does Not Mean Automatically Secure

# 81. Zero Trust Introduction

Traditional network security often assumed:

```text
Inside network = trusted

Outside network = untrusted
```

Modern environments make this assumption increasingly weak.

Users and workloads may exist across:

```text
Cloud
Remote work
SaaS
Data centers
Mobile devices
Multiple regions
Third-party environments
```

Zero Trust challenges implicit trust based only on network location.

---

# 82. Zero Trust Mental Model

A simplified principle is:

```text
Do not automatically trust
a request merely because it
comes from inside the network.
```

Instead, access decisions may consider:

```text
Identity
Device state
Resource
Context
Policy
Authentication
Authorization
Risk
```

---

# 83. Zero Trust Is Not "Trust Nobody"

The phrase can be misleading.

Zero Trust does not mean:

```text
No communication is ever allowed.
```

It means trust should be:

```text
Explicit
Contextual
Continuously evaluated where appropriate
Limited to what is required
```

Network location alone should not grant broad implicit access.

---

# 84. Firewall vs Zero Trust

Traditional firewall question:

```text
Is traffic from this IP/network
allowed to reach this port?
```

A broader Zero Trust architecture might ask:

```text
Who is requesting access?

Which device?

Which workload?

Which resource?

What authentication occurred?

What policy applies?

What context exists?
```

Firewalls can still be part of Zero Trust.

Zero Trust does not eliminate network controls.

# 85. Common Network Attacks


# 86. Reconnaissance

Attackers often begin by gathering information.

They may try to determine:

```text

Which IPs respond?

Which ports appear reachable?

Which services are exposed?

Which technologies are running?
```

Reducing unnecessary exposure decreases the information and attack surface available.

---

# 87. Port Scanning Concept

A port scan tests ports to determine which appear:

```text
Open
Closed
Filtered
```

Conceptually:

```text
Target Server

22   ?
80   ?
443  ?
3306 ?
5432 ?
8080 ?
```

The scanner sends probes and interprets responses.

---

# 88. Why Port Scanning Matters Defensively

Suppose your intended exposure is:

```text
443
```

but an authorized security scan discovers:

```text
22
443
5432
```

Now you know unnecessary services may be reachable.

Defensive scanning can help validate:

```text

Attack surface
Deployment configuration
Network exposure
```

Only scan systems you own or are explicitly authorized to assess.

---

# 89. Open vs Closed vs Filtered

Conceptually:

```text
OPEN
A service appears reachable/listening.

CLOSED
Host responds, but no service accepts the connection.

FILTERED
A filtering device may prevent a clear response.
```

Real scanning interpretation can be more complicated, but this is the useful beginner model.

---

# 90. Spoofing

Spoofing means falsifying identity-related information in communication.

At the network layer, IP spoofing involves forging a packet's source IP address.

Conceptually:

```text
Actual sender:
Attacker

Packet claims source:
Trusted System
```

Firewalls that trust source IP alone may therefore face limitations depending on architecture and protocol.

---

# 91. Why IP Spoofing Is Not Magic

A forged source address does not automatically provide a normal bidirectional TCP connection.

Replies are routed toward the spoofed source.

For TCP:

```text
Attacker sends spoofed SYN
        |
        v
Server
        |
        | SYN-ACK
        v
Spoofed address
```

This makes ordinary interactive TCP communication more difficult.

However, spoofing remains relevant in attacks such as certain denial-of-service and reflection/amplification scenarios.

---

# 92. Anti-Spoofing Controls

Networks can use controls that reject traffic claiming impossible or inappropriate source addresses.

For example:

```text
Internet-facing interface
        |
        v
Packet claims source:
10.0.0.50
```

If that private internal source should never arrive from the Internet-facing side, the packet is suspicious.

Source validation and ingress/egress filtering can help reduce spoofing.

---

# 93. Man-in-the-Middle Concept

A man-in-the-middle attack involves an attacker positioning themselves so they can intercept or manipulate communication between parties.

Conceptually:

```text
Client
  |
  v
Attacker
  |
  v
Server
```

instead of:

```text
Client
  |
  v
Server
```

---

# 94. Why TLS Matters Against MITM

Proper TLS validation helps prevent an attacker from simply impersonating the legitimate HTTPS server.

If the attacker presents an invalid certificate:

```text
Client
  |
  v
Attacker
Certificate does not validate
  |
  X
```

the client should reject the connection.

This is one reason disabling TLS verification is dangerous.

# 95. ARP Spoofing and MITM

You introduced this earlier.

Conceptually:

```text

  |
  v

  |
  v
```

```text
  |
  v
Gateway
```

# 96. Denial of Service

A Denial-of-Service attack attempts to make a service unavailable.

Targets can include:

```text

CPU
Memory
Connection tables
Application workers
Databases
External dependencies
```

The attacker does not necessarily need to compromise the system.

Making it unusable may be enough.

---

# 97. Distributed Denial of Service

DDoS stands for:

```text
Distributed Denial of Service
```

Instead of one source:

```text
Attacker
   |
   v
Target
```

traffic may originate from many systems:

```text
Source A ---\
Source B ----\
Source C -----> Target
Source D ----/
Source E ---/
```

This makes simple source blocking much less effective.

---

# 98. DDoS Can Target Different Layers

DDoS attacks can target:

```text
Network capacity

Transport resources

Protocol behavior

Application resources
```

For example:

```text
Massive traffic volume

Large numbers of connection attempts

Expensive HTTP requests
```

These require different mitigation strategies.

---

# 99. Firewalls Are Not Complete DDoS Protection

A firewall may block unwanted traffic.

But imagine:

```text
Internet link capacity:
1 Gbps

Attack:
20 Gbps
```

If the traffic saturates the connection before reaching your firewall, a local firewall cannot restore bandwidth that has already been exhausted.

Large-scale DDoS defense often requires upstream capabilities such as:

```text
Cloud DDoS protection
CDNs
Anycast networks
Provider filtering
Traffic scrubbing
Rate controls
Scalable infrastructure
```

# 101. Firewall Design Principle

A strong starting question is not:

# 104. Firewall Troubleshooting

Suppose:

```text
Client cannot connect to server TCP 443.
```

Do not immediately add:

```text
ALLOW ANY ANY
```

That destroys useful evidence and may create a security problem.

Instead, troubleshoot systematically.

---

# 105. Step 1: Confirm Addressing

On the client:

```bash
ip addr
```

Confirm:

```text
Source IP
Prefix
Interface
```

On the server, verify its actual IP.

Wrong addressing can look like firewall failure.

---

# 106. Step 2: Confirm Routing

Run:

```bash
ip route get <server-ip>
```

Ask:

```text
Which route?

Which interface?

Which gateway?

Which source IP?
```

If no valid route exists, firewall changes will not solve the fundamental problem.

---

# 107. Step 3: Confirm the Server Is Listening

On Linux server:

```bash
ss -lntp
```

Suppose you expect:

```text
TCP 443
```

but only see:

```text
127.0.0.1:443
```

The service is listening only on loopback.

A firewall allow rule cannot make a loopback-only service externally reachable.

---

# 108. Step 4: Test the Port

From the authorized client:

```bash
nc -vz server.example.com 443
```

or use the application protocol itself:

```bash
curl -v https://server.example.com/
```

Observe whether you receive:

```text
Success
Refused
Timeout
TLS failure
HTTP response
```

These symptoms mean different things.

---

# 109. Step 5: Inspect the Host Firewall

Depending on the system:

```bash
sudo nft list ruleset
```

or:

```bash
sudo ufw status verbose
```

or, in environments using iptables:

```bash
sudo iptables -L -n -v
```

Ask:

```text
Is firewall active?

What is the default policy?

Which rule should match?

Does an earlier rule override it?

Are counters increasing?
```

---

# 110. Step 6: Inspect External Security Controls

In cloud environments, inspect:

```text
Security groups
Network ACLs
Cloud firewall
Load balancer policy
Routing
Subnet configuration
```

A correct Linux host firewall does not prove the cloud network allows the connection.

---

# 111. Step 7: Use Packet Capture

On the server:

```bash
sudo tcpdump -n -i any tcp port 443
```

Generate a connection attempt.

Now ask:

```text
Do packets reach the server?
```

If you see no SYN arriving:

```text
Client
   |
   X
Server capture
```

the problem is likely upstream of the capture point.

---

# 112. SYN Arrives but No Response Leaves

Capture:

```text
Client -> Server
SYN
```

but no SYN-ACK or RST leaves.

Investigate:

```text
Host firewall
Kernel/network stack
Local policy
Service behavior
```

The packet reached the server.

That is important evidence.

---

# 113. SYN and SYN-ACK Are Visible

Suppose server capture shows:

```text
Client -> Server
SYN

Server -> Client
SYN-ACK
```

but client never completes the handshake.

Now investigate the return path.

Possible issues:

```text
Asymmetric routing
Stateless return filtering
Network ACL
Client firewall
Intermediate firewall
```

This is why packet capture is so powerful.

---

# 114. Connection Refused

Suppose:

```text
Connection refused
```

A common explanation is:

```text
Destination reachable,
but nothing is listening on that port.
```

or a device is explicitly rejecting the connection.

Check:

```bash
ss -lntp
```

before changing firewall rules.

---

# 115. Connection Timeout

Suppose:

```text
Connection timed out
```

Possible causes include:

```text
Firewall drop
Network ACL
Routing failure
Wrong IP
Host down
Return-path problem
Security group
Packet loss
```

Timeout does not equal firewall.

It is a symptom requiring investigation.

---

# 116. Ping Failure Does Not Prove the Server Is Down

Suppose:

```bash
ping server
```

fails.

But:

```bash
curl https://server
```

works.

Possible explanation:

```text
ICMP echo is filtered.

TCP 443 is allowed.
```

Different protocols can have different policies.

Never use ping as your only reachability test.

---

# 117. HTTP Works but Ping Fails

Policy:

```text
ICMP Echo
DENY

TCP 443
ALLOW
```

Result:

```text
ping:
fails

HTTPS:
works
```

That can be intentional.

---

# 118. Ping Works but HTTPS Fails

The opposite is also possible.

Policy:

```text
ICMP
ALLOW

TCP 443
DENY
```

Result:

```text
ping:
works

HTTPS:
fails
```

Therefore:

```text
Ping success != application port success.
```

---

# 119. Wrong Source IP Problem

Suppose firewall allows:

```text
10.20.30.0/24 -> TCP 443
```

But client has multiple interfaces and sends traffic using:

```text
10.20.40.25
```

The firewall may correctly deny it.

Check:

```bash
ip route get <destination>
```

The output can reveal the selected source address.

This is especially important on multi-homed systems.

---

# 120. NAT and Firewall Rules

NAT can change addresses before or after certain filtering stages depending on architecture.

Suppose internal client:

```text
10.0.1.50
```

is translated to:

```text
198.51.100.20
```

The remote firewall may see:

```text
198.51.100.20
```

not:

```text
10.0.1.50
```

Always ask:

```text
Which source address does this firewall actually see?
```

---

# 121. Proxy and Load Balancer Source Addresses

Suppose:

```text
Client
  |
  v
Load Balancer
  |
  v
Application
```

The application-side firewall may see the load balancer's address rather than the original client address at the IP layer.

Therefore a rule expecting:

```text
Original client IP
```

may not match.

Understand the actual packet path.

---

# 122. Rule Shadowing

Suppose:

```text
Rule 1:
DENY 10.0.0.0/8

Rule 2:
ALLOW 10.20.30.0/24 TCP 443
```

In an ordered first-match firewall:

```text
Rule 1
```

may match first.

Rule 2 never gets a chance.

This is called rule shadowing in many firewall discussions.

---

# 123. Overly Broad Rules

Example:

```text
ALLOW
0.0.0.0/0
ANY protocol
ANY port
```

This may make troubleshooting temporarily "work," but it destroys the intended security boundary.

Never normalize:

```text
Open everything until it works.
```

Instead identify the exact required flow.

---

# 124. Document Required Flows

For production architecture, maintain something like:

| Source        | Destination   | Protocol | Port | Purpose         |
| ------------- | ------------- | -------- | ---: | --------------- |
| Internet      | Load Balancer | TCP      |  443 | Public HTTPS    |
| Load Balancer | Application   | TCP      | 8080 | App traffic     |
| Application   | Database      | TCP      | 5432 | PostgreSQL      |
| Application   | DNS           | UDP/TCP  |   53 | Name resolution |
| Admin network | Bastion       | TCP      |   22 | Administration  |

This makes firewall policy easier to design, review, and troubleshoot.

---

# 125. Think in Flows

Instead of saying:

```text
"Open port 5432."
```

say:

```text
Source:
Application tier

Destination:
Database tier

Protocol:
TCP

Destination port:
5432

Purpose:
Application database connection
```

A port without source, destination, protocol, and purpose is incomplete security information.

```text
   |
   v
Web
   |
   v
App
   |
   v
Database
```

Policy:

```text
Internet -> Web 443
ALLOW

Web -> App 8080
ALLOW

App -> Database 5432
ALLOW

Internet -> Database
DENY
```

If the database is accidentally given:

```text
Public IP + TCP 5432 from anywhere
```

the segmentation design has been weakened significantly.

# 141. Practical Packet Flow 7: Bastion Access

Policy:

```text
Administrator
      |
      | SSH
      v
Bastion
      |
      | SSH
      v
Private Server
```

Private server allows SSH only from the bastion path.

Direct attempt:

```text

      |
      X
Private Server
```

# 142. Practical Packet Flow 8: Outbound Restriction

Application needs:

```text
api.payment.example
TCP 443
```

```text

        |
        v

        |

        X

```


# 143. Firewalls and DNS

Suppose an application must resolve:

```text
database.internal.example
```

but outbound DNS is blocked.

Application reports:

```text
Name resolution failure
```

The database itself may be healthy.

Required traffic may include:

```text
UDP 53
```

and sometimes:

```text
TCP 53
```

toward the appropriate DNS resolver.

Never troubleshoot only the final application port.

Dependencies matter.

---

# 144. Firewalls and DHCP

DHCP uses specific UDP communication and often begins before a client has a normal configured IP address.

Improper filtering can interfere with DHCP.

Result:

```text
Client receives no lease
```

Then the user may report:

```text
"The Internet is broken."
```

The actual failure occurred during automatic network configuration.

---

# 145. Firewalls and ICMP

Blocking all ICMP blindly can create operational problems.

ICMP is used for more than simple ping.

It supports important network functions and error reporting.

IPv6 relies particularly heavily on ICMPv6 for essential functions such as Neighbor Discovery.

Security policy should understand protocol requirements rather than applying:

```text
ICMP = bad
```

as a blanket rule.

# 146. IPv6 Firewalling

Do not secure only IPv4.

A host may have:

```text
IPv4 address
and
IPv6 address
```

If IPv4 firewall policy is strict but IPv6 policy is wide open:

```text
IPv4:
Protected

IPv6:
Unexpected exposure
```

you may create a serious security gap.

Modern firewall design must account for both protocol families where IPv6 is enabled.

# 156. Complete Firewall Troubleshooting Methodology

When a connection fails:

```text
1. Identify source.

2. Identify destination.

3. Identify protocol.

4. Identify source port if relevant.

5. Identify destination port.

6. Confirm DNS if a hostname is used.

7. Confirm route.

8. Confirm selected source IP.

9. Confirm destination service is listening.

10. Test connectivity.

11. Identify every firewall/control in the path.

12. Determine whether each is stateful or stateless.

13. Inspect inbound policy.

14. Inspect outbound policy.

15. Inspect return-path policy.

16. Check rule order/priority.

17. Check default policy.

18. Check NAT effects.

19. Inspect counters/logs.

20. Capture packets where appropriate.

21. Identify the exact failure point.

22. Make the narrowest justified change.

23. Retest.

24. Document.
```

# 158. Troubleshooting Question: What Does the Firewall See?

Always determine the traffic as observed at the policy point.

Because NAT, proxies, and load balancers may change the effective network identity.

You may think:

```text
Source:
10.0.1.50
```

but the firewall sees:

```text
Source:
198.51.100.20
```

Or the application firewall sees:

```text
Source:
10.0.5.10
```

because that is the load balancer.

Policy must match reality.

---

# 159. Troubleshooting Question: Which Direction?

A rule may look correct:

```text
ALLOW TCP 443
```

but exist in the wrong direction.

Example:

```text
Outbound TCP 443:
ALLOW
```

while you need:

```text
Inbound TCP 443:
ALLOW
```

Direction is part of the policy.

# 160. Troubleshooting Question: Which Interface?

Some firewall rules apply to particular interfaces.

Example:

```text
Allow SSH on:
eth1

Not:
eth0
```

If traffic arrives on the unexpected interface, the rule may not match.

Use routing and packet capture to determine the actual path.

---

# 161. Troubleshooting Question: IPv4 or IPv6?

Hostname:

```text
app.example.com
```

may resolve to:

```text
A
203.0.113.20

AAAA
2001:db8::20
```

Client may prefer IPv6.

If only IPv4 firewall rules are correct:

```text
Some clients may fail.
```

Always know which address family is actually being used.

# 162. Troubleshooting Question: Is the Application Bound Correctly?

Firewall allows:

```text
TCP 8080
```

Application listens:

```text
127.0.0.1:8080
```

Remote connections fail.

Firewall is not the problem.

Compare:

```text
0.0.0.0:8080
```

with:

```text
127.0.0.1:8080
```

and specific-interface binding.

The listener matters.

# 163. Troubleshooting Question: Is the Return Route Correct?

Client sends:

```text
10.0.1.50
   |
   v
Server
10.0.2.20
```

Server response takes an unexpected gateway.

A stateful firewall on the original path may never see the return traffic.

This can create:

```text
Asymmetric routing
```

and connection failure.

Security troubleshooting and routing troubleshooting often overlap.

# 164. Common Beginner Mistake: Firewall = Antivirus

A firewall primarily controls network communication according to policy.

Antivirus/endpoint detection tools focus on malicious software and endpoint behavior.

They may integrate, but they are not the same security control.

# 165. Common Beginner Mistake: Open Port Means Vulnerable

An open port means a service is reachable.

That creates potential attack surface.

But:

```text
Open port
```

does not automatically mean:

```text
Known vulnerability exists.
```

Security depends on:

```text
Service
Version
Configuration
Authentication
Exposure
Application security
Patch state
```

Still, unnecessary open ports should be removed or restricted.

# 166. Common Beginner Mistake: Closed Port Means Completely Secure

A system with few exposed ports can still have vulnerabilities.

Firewalls cannot fix:

```text

SQL injection
Broken authorization
Malicious insiders
Compromised credentials
Application logic flaws
```

Network controls are one part of security.

# 167. Common Beginner Mistake: Internal Means Trusted

Do not assume:


```text

```

It does not prove:

This is one motivation behind Zero Trust principles.

# 168. Common Beginner Mistake: Disable Firewall to Troubleshoot

# 188. Root Cause

The application migration changed the source network, but the database access policy was not updated.

The firewall correctly denied traffic that did not match its existing rule.

This is not:

```text
Random network failure.
```

```text
Application moved

      v
Source identity changed
      |
      v
Firewall rule remained old
      |
      v
Database connection blocked
      |
      v
Application timeout
      |
      v
HTTP 500
```

```text

Retest application.

Verify firewall logs.

Remove obsolete rule if appropriate.

Document the architecture change.
```

When troubleshooting any protected connection, picture this:

```text
APPLICATION
    |
    v
SOCKET
Source IP : Source Port
    |
    v
ROUTING
Where should it go?
    |
    v
OUTBOUND POLICY
May it leave?
    |
    v

    |

    |
    v

    |
```

```text

```

It is:

```text
What exact flow is required?

What is the real source?

What is the real destination?

Which protocol?

Which destination port?

Which direction?

Which route?

Are they stateful or stateless?

Where does the packet stop?

What is the narrowest policy that permits the legitimate flow?
```

Once you begin thinking in **flows, boundaries, state, and evidence**, firewalls stop being mysterious lists of ports and become what they actually are: **policy enforcement points controlling who can communicate with what, how, and under which conditions.**
