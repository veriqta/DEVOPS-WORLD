# Part 16: Route 53, DNS, Domains, and Application Traffic

In the previous parts, you built the infrastructure behind an application.

You now understand how traffic can reach an Application Load Balancer, how the ALB distributes requests to EC2 instances, how Auto Scaling maintains capacity, how RDS provides a managed database, and how CloudWatch gives you operational evidence.

But users should not need to know something like:

```text
my-prod-alb-123456789.us-east-1.elb.amazonaws.com
```

They should be able to type:

```text
app.example.com
```

and reach your application.

That introduces one of the most important foundations of the Internet:

DNS.

In AWS, Amazon Route 53 provides DNS capabilities that allow you to connect human-readable domain names to AWS resources such as Application Load Balancers.

The architecture we are building is:

```text
User
 |
 v
app.example.com
 |
 v
Route 53
 |
 v
Application Load Balancer
 |
 v
Target Group
 |
 +----------+
 |          |
 v          v
EC2 A      EC2 B
```

This part starts DNS from zero.

By the end, you should understand not only how to create a Route 53 record, but what happens from the moment a user enters a domain name until traffic reaches your application.

---

# 1. Why DNS Exists

Computers communicate across IP networks using IP addresses.

An IPv4 address may look like:

```text
203.0.113.25
```

An IPv6 address may look like:

```text
2001:db8:1234::25
```

Humans generally find names easier to remember.

Instead of remembering:

```text
203.0.113.25
```

you can remember:

```text
example.com
```

DNS provides the system that helps translate names into information computers need to locate services.

DNS stands for:

```text
Domain Name System
```

A simplified mental model is:

```text
Human:
app.example.com

        |
        v

DNS lookup

        |
        v

Destination information

        |
        v

Application
```

DNS is sometimes described as the Internet's phone book.

That analogy is useful for beginners, but DNS does considerably more than simply map names to IPv4 addresses.

---

# 2. DNS Does Not Carry Your Application Traffic

This distinction is extremely important.

DNS helps the client discover where it should connect.

DNS does not normally carry the subsequent HTTP or HTTPS application traffic.

Consider:

```text
User wants:
https://app.example.com
```

First:

```text
DNS:
Where should app.example.com go?
```

After DNS resolution, the client connects toward the returned destination.

Conceptually:

```text
Step 1

User
 |
 v
DNS
 |
 v
Find destination


Step 2

User
 |
 v
Application destination
```

For our AWS architecture:

```text
User
 |
 | DNS question
 v
Route 53
 |
 | DNS answer
 v
User
 |
 | HTTPS request
 v
ALB
 |
 v
EC2
```

Do not imagine every web request continuously passing through Route 53.

Route 53 participates in DNS resolution. The ALB handles the application traffic.

---

# 3. What Is a Domain Name?

A domain name is a human-readable name used within DNS.

Examples:

```text
example.com
```

```text
amazon.com
```

```text
github.com
```

You can create names beneath a domain.

For example:

```text
www.example.com
```

```text
app.example.com
```

```text
api.example.com
```

```text
shop.example.com
```

```text
status.example.com
```

These names can identify different services.

---

# 4. Understanding Domain Name Structure

Consider:

```text
app.example.com
```

Read DNS names from right to left when thinking about hierarchy.

```text
app . example . com
 |       |       |
 |       |       +-- Top-level domain
 |       |
 |       +---------- Registered domain label
 |
 +------------------ Subdomain/host label
```

`com` is the top-level domain.

`example.com` is the registered domain in this example.

`app.example.com` is a name beneath that domain.

---

# 5. The DNS Root

DNS is hierarchical.

At the top is the DNS root.

It can conceptually be represented as:

```text
.
```

A fully qualified DNS name technically ends at the root.

For example:

```text
app.example.com.
```

Most people omit the final dot when typing domain names.

The hierarchy looks roughly like:

```text
                  Root
                    .
                    |
          +---------+---------+
          |         |         |
         com       org       net
          |
       example
          |
     +----+----+
     |         |
    www       app
```

Understanding this hierarchy makes DNS troubleshooting much easier.

---

# 6. Top-Level Domains

A top-level domain, or TLD, appears immediately below the DNS root.

Examples include:

```text
.com
.org
.net
```

There are also country-code TLDs and many newer TLDs.

For:

```text
example.com
```

the TLD is:

```text
.com
```

---

# 7. Domain Registration

Before you can normally control a public Internet domain such as:

```text
mycompany.com
```

someone must register it.

Registration establishes the registrant's right to use that domain for a defined registration period, subject to the registrar and registry rules.

This introduces registrars.

---

# 8. What Is a Domain Registrar?

A registrar is a company authorized to provide domain registration services for supported top-level domains.

You use a registrar to:

* Search for available domains
* Register a domain
* Renew registration
* Manage registration information
* Configure which DNS name servers are authoritative for the domain

AWS provides domain registration capabilities through Route 53 for supported domains, but your registrar does not have to be AWS.

A domain can be:

```text
Registered with Provider A
```

while its DNS is:

```text
Hosted by Provider B
```

This distinction is extremely important.

---

# 9. Registrar vs DNS Provider

These are related but separate responsibilities.

## Registrar

Handles domain registration.

Think:

```text
Who manages my ownership/registration of example.com?
```

## DNS provider

Hosts the DNS records and authoritative DNS service.

Think:

```text
Who answers authoritative DNS questions for example.com?
```

They may be the same provider.

They do not have to be.

For example:

```text
Domain registration
        |
        v
Registrar

DNS hosting
        |
        v
Route 53
```

This arrangement is completely valid.

---

# 10. Name Servers

A domain needs authoritative name servers.

These are the DNS servers responsible for authoritative answers about records in the domain's DNS zone.

If Route 53 hosts:

```text
example.com
```

Route 53 assigns name servers to the hosted zone.

Conceptually:

```text
example.com
    |
    v
Delegated to
    |
    +---- Name Server 1
    +---- Name Server 2
    +---- Name Server 3
    +---- Name Server 4
```

The registrar or parent-zone delegation must ultimately point toward the correct authoritative name servers.

If that delegation is wrong, the records you create in Route 53 may be perfectly correct and users may still not reach them.

This is a common DNS troubleshooting lesson:

```text
Correct record
does not guarantee
correct delegation.
```

---

# 11. What Is DNS Resolution?

DNS resolution is the process used to obtain DNS information for a name.

Suppose a user enters:

```text
https://app.example.com
```

The client needs to resolve:

```text
app.example.com
```

A simplified process is:

```text
Browser
   |
   v
Operating System
   |
   v
Recursive DNS Resolver
   |
   v
DNS hierarchy
   |
   v
Authoritative DNS
   |
   v
Answer
```

Let's understand these components.

---

# 12. Stub Resolver

Your computer's operating system contains DNS resolver functionality.

Applications such as browsers generally rely on the operating system's networking capabilities to perform DNS lookups.

The client-side component is commonly called a:

```text
Stub resolver
```

It forwards DNS queries toward a recursive resolver.

---

# 13. Recursive DNS Resolver

A recursive resolver performs DNS resolution on behalf of clients.

Resolvers may be provided by:

* Internet service providers
* Corporate networks
* Cloud environments
* Public DNS services
* Local networking infrastructure

The resolver's job is essentially:

```text
Client:
Where is app.example.com?

Resolver:
I will obtain the answer for you.
```

---

# 14. DNS Caching

Before contacting multiple DNS servers, the resolver may check its cache.

Suppose it recently resolved:

```text
app.example.com
```

If the cached answer remains valid, it can return that answer immediately.

Conceptually:

```text
Client
 |
 v
Resolver
 |
 +---- Cached answer exists?
 |          |
 |          +---- Yes → Return it
 |
 +---- No → Perform resolution
```

Caching makes DNS faster and reduces unnecessary DNS queries.

But caching also explains why DNS changes may not appear everywhere immediately.

We will discuss TTL shortly.

---

# 15. Recursive vs Authoritative DNS

Do not confuse these two roles.

## Recursive resolver

Finds answers for clients.

## Authoritative DNS server

Holds authoritative DNS information for a zone.

Conceptually:

```text
User
 |
 v
Recursive Resolver
 |
 | asks DNS hierarchy
 v
Authoritative Server
 |
 | answer
 v
Recursive Resolver
 |
 v
User
```

Route 53 can provide authoritative DNS hosting for your domains through hosted zones.

---

# 16. DNS Hierarchy During Resolution

Assume the resolver has no cached information.

It wants:

```text
app.example.com
```

Conceptually, resolution may involve:

```text
Recursive Resolver
       |
       v
Root DNS
       |
       v
.com DNS
       |
       v
example.com authoritative DNS
       |
       v
app.example.com answer
```

Let's examine that process.

---

# 17. Step 1: Ask the Root

The resolver needs information about:

```text
app.example.com
```

The DNS root does not normally respond with the final application address.

Instead, it can direct the resolver toward the relevant top-level-domain name servers.

Conceptually:

```text
Resolver:
Where is app.example.com?

Root:
Ask the .com name servers.
```

---

# 18. Step 2: Ask the TLD Name Servers

The resolver then asks the `.com` infrastructure about:

```text
example.com
```

The TLD servers can provide delegation information directing the resolver toward the authoritative name servers for `example.com`.

Conceptually:

```text
Resolver:
Who knows about example.com?

.com:
These name servers are authoritative.
```

---

# 19. Step 3: Ask the Authoritative Server

The resolver asks the authoritative DNS service:

```text
What is app.example.com?
```

If Route 53 is authoritative for the zone, Route 53 answers according to the configured DNS records and routing policy.

The resolver can then return the answer to the client.

---

# 20. Complete DNS Resolution Flow

Put everything together:

```text
User enters:
app.example.com
      |
      v
Local resolver/cache
      |
      v
Recursive resolver
      |
      v
Root
      |
      v
.com
      |
      v
Authoritative DNS
Route 53
      |
      v
DNS answer
      |
      v
Recursive resolver
      |
      v
User
```

Caching may allow several of these steps to be skipped.

---

# 21. What Is Amazon Route 53?

Amazon Route 53 is AWS's DNS web service.

It provides capabilities including:

* Domain registration
* Authoritative DNS
* DNS routing
* Health checking

For our architecture, its main job is:

```text
app.example.com
        |
        v
Route 53
        |
        v
Application Load Balancer
```

Route 53 allows users to use a friendly domain instead of the ALB-generated DNS name.

---

# 22. Why Is It Called Route 53?

DNS commonly uses port:

```text
53
```

DNS can use UDP and TCP depending on the situation.

The `53` in Route 53 refers to DNS port 53.

Do not confuse:

```text
DNS port 53
```

with:

```text
HTTP port 80
HTTPS port 443
SSH port 22
```

Different protocols serve different purposes.

---

# 23. Hosted Zones

A hosted zone is a Route 53 container for DNS records associated with a DNS namespace.

For example, you might create a hosted zone for:

```text
example.com
```

Inside it, you can create records such as:

```text
example.com
www.example.com
app.example.com
api.example.com
```

Conceptually:

```text
Hosted Zone: example.com

 |
 +---- example.com
 |
 +---- www.example.com
 |
 +---- app.example.com
 |
 +---- api.example.com
```

---

# 24. Public Hosted Zones

A public hosted zone contains DNS records intended to be resolved through public DNS.

Example:

```text
app.example.com
```

needs to be reachable by users on the Internet.

You could place its record in a public hosted zone.

Architecture:

```text
Internet User
      |
      v
Public DNS
      |
      v
Route 53 Public Hosted Zone
      |
      v
app.example.com
```

---

# 25. Private Hosted Zones

A private hosted zone provides DNS information within associated VPCs rather than making the records publicly resolvable on the Internet.

Example internal name:

```text
database.internal.example.com
```

or:

```text
api.internal.example.com
```

Conceptually:

```text
Internet
   |
   X
Private DNS name


EC2 inside associated VPC
   |
   v
Route 53 private DNS
   |
   v
Internal resource
```

Private hosted zones are useful for internal service naming.

---

# 26. Public vs Private Hosted Zones

| Feature                                     | Public Hosted Zone              | Private Hosted Zone |
| ------------------------------------------- | ------------------------------- | ------------------- |
| Public Internet DNS                         | Yes                             | No                  |
| Associated with VPCs for resolution         | Not in the same sense           | Yes                 |
| Public website names                        | Yes                             | No                  |
| Internal application names                  | Usually not the primary purpose | Yes                 |
| Internet users can normally resolve records | Yes                             | No                  |

A private hosted zone does not automatically make an application secure.

DNS visibility and network access are different controls.

---

# 27. DNS Does Not Replace Network Security

Suppose:

```text
db.internal.example.com
```

exists only in a private hosted zone.

That is useful.

But you still need:

* Private networking
* Security Groups
* Correct routing
* Authentication
* Database security

DNS naming is not a substitute for access control.

Remember:

```text
DNS tells you where.

Security determines whether you may connect.
```

---

# 28. DNS Records

DNS stores different types of information using record types.

Important record types for beginners include:

* A
* AAAA
* CNAME
* Alias
* MX
* TXT

Each serves a different purpose.

---

# 29. A Record

An A record maps a DNS name to an IPv4 address.

Example:

```text
app.example.com
      |
      v
203.0.113.25
```

Conceptually:

```text
Type: A
Name: app.example.com
Value: 203.0.113.25
```

A stands for:

```text
Address
```

The important beginner rule is:

```text
A record → IPv4 address
```

---

# 30. A Record Example

Suppose a server has public IPv4:

```text
203.0.113.25
```

You could create:

```text
app.example.com A 203.0.113.25
```

Then:

```text
app.example.com
        |
        v
203.0.113.25
```

But for an AWS ALB, you normally should not try to discover and hardcode its underlying IP addresses.

ALBs are managed and addressed through DNS.

That is one reason Route 53 Alias records are important.

---

# 31. AAAA Record

An AAAA record maps a DNS name to an IPv6 address.

Example:

```text
app.example.com
      |
      v
2001:db8::10
```

Remember:

```text
A     → IPv4
AAAA  → IPv6
```

Why four As?

It is simply the DNS record type name defined for IPv6 address records.

Do not interpret it as four separate A records.

---

# 32. CNAME Record

CNAME stands for:

```text
Canonical Name
```

A CNAME makes one DNS name an alias of another DNS name.

Example:

```text
www.example.com
       |
       v
app.example.com
```

Conceptually:

```text
Type: CNAME
Name: www.example.com
Value: app.example.com
```

The important difference is:

```text
A
Name → IPv4 address

CNAME
Name → Another DNS name
```

---

# 33. CNAME Resolution Example

Suppose:

```text
www.example.com
```

is a CNAME for:

```text
app.example.com
```

and `app.example.com` eventually resolves toward the application.

The resolver may follow:

```text
www.example.com
       |
       v
app.example.com
       |
       v
Application destination
```

This creates another level of indirection.

---

# 34. CNAME Limitations

A major DNS rule is that a CNAME cannot coexist at the same owner name with other DNS data in the ordinary way required for a zone apex.

This becomes especially important for the root of your domain.

For example:

```text
example.com
```

is the zone apex.

You cannot treat it exactly like:

```text
www.example.com
```

with an ordinary CNAME if the apex must also contain required records such as SOA and NS.

AWS Alias records help solve this problem for supported AWS resources.

---

# 35. What Is a Route 53 Alias Record?

An Alias record is an AWS Route 53 feature.

It allows a Route 53 record to route traffic to supported AWS resources.

For example:

```text
app.example.com
       |
       v
Alias
       |
       v
Application Load Balancer
```

You can also use Alias records at the zone apex for supported targets.

For example:

```text
example.com
      |
      v
ALB
```

This is extremely useful.

---

# 36. Alias vs CNAME

A beginner-friendly comparison:

| Feature                                     | CNAME                              | Route 53 Alias                |
| ------------------------------------------- | ---------------------------------- | ----------------------------- |
| DNS standard record type                    | Yes                                | AWS Route 53 feature          |
| Points toward another name/resource         | Yes                                | Yes                           |
| Can target supported AWS resources directly | Not AWS-aware                      | Yes                           |
| Can be used at zone apex                    | Generally no                       | Yes, for supported targets    |
| Useful with ALB                             | Possible in some naming situations | Usually preferred in Route 53 |

For an ALB in Route 53, you will commonly create an Alias record.

---

# 37. Why Not Point an A Record at an ALB IP?

Because an Application Load Balancer is an AWS-managed service.

Do not design around manually discovered ALB node IP addresses.

AWS manages the infrastructure behind the ALB.

The ALB provides a DNS name.

Your stable configuration should reference the managed service correctly.

Use:

```text
Route 53 Alias
      |
      v
ALB
```

instead of:

```text
A record
      |
      v
Some IP you observed
```

---

# 38. MX Record

MX stands for:

```text
Mail Exchange
```

MX records specify mail servers responsible for receiving email for a domain.

Example concept:

```text
Email to:
user@example.com
      |
      v
DNS MX lookup
      |
      v
Mail server
```

MX records are not how you connect your website to an ALB.

They relate to email delivery.

---

# 39. TXT Record

TXT records store text information in DNS.

They are widely used for things such as:

* Domain verification
* Email security configurations
* Ownership verification
* Service configuration

You may encounter TXT records when configuring:

* SPF-related email authorization data
* DKIM-related configurations
* Domain verification
* Third-party SaaS services

Do not assume TXT means:

```text
Random notes for humans
```

TXT records are commonly machine-consumed configuration and verification data.

---

# 40. DNS Record Summary

Remember:

```text
A
→ IPv4 address

AAAA
→ IPv6 address

CNAME
→ Another DNS name

Alias
→ Route 53 feature for supported AWS targets

MX
→ Mail routing

TXT
→ Text-based verification/configuration data
```

---

# 41. What Is TTL?

TTL means:

```text
Time To Live
```

TTL tells DNS resolvers how long a record may be cached before it should be considered expired and refreshed.

Suppose:

```text
TTL = 300 seconds
```

That means:

```text
300 seconds = 5 minutes
```

A resolver may cache the answer for up to that TTL period.

---

# 42. Why TTL Matters

Suppose:

```text
app.example.com
```

currently resolves to:

```text
Old destination
```

You change it to:

```text
New destination
```

A resolver may still have the old answer cached.

Therefore some users may temporarily continue using the previous answer.

This is why DNS changes can appear inconsistent during transitions.

---

# 43. High vs Low TTL

Conceptually:

## Lower TTL

Advantages:

* Changes can be picked up sooner after cached data expires
* Useful before planned DNS migrations

Disadvantages:

* More frequent DNS queries
* Less caching efficiency

## Higher TTL

Advantages:

* More caching
* Reduced repeated DNS resolution

Disadvantages:

* Changes may take longer to be observed by clients using cached answers

Choose TTL intentionally.

---

# 44. DNS Propagation Is Often Caching

People frequently say:

```text
DNS is still propagating.
```

Sometimes the real issue is simply:

```text
Different resolvers still have cached answers with unexpired TTLs.
```

Understanding TTL makes DNS behavior less mysterious.

---

# 45. Route 53 Routing Policies

Route 53 can do more than return one static answer.

Routing policies determine how Route 53 responds when multiple resources or endpoints are available.

Important policies include:

* Simple
* Weighted
* Latency-based
* Failover

There are additional Route 53 routing capabilities, but these four give beginners a strong foundation.

---

# 46. Simple Routing

Simple routing is appropriate when you want straightforward DNS behavior without advanced traffic-distribution logic.

Example:

```text
app.example.com
       |
       v
ALB
```

For a beginner application with one ALB, simple routing is often sufficient.

Architecture:

```text
User
 |
 v
app.example.com
 |
 v
Route 53
 |
 v
ALB
```

---

# 47. Simple Routing Example

Suppose your application exists only in:

```text
us-east-1
```

and has one ALB.

You configure:

```text
app.example.com
      |
      v
Alias
      |
      v
prod-alb
```

There is no need for complicated routing logic.

Simple is good when simple solves the requirement.

---

# 48. Weighted Routing

Weighted routing lets you distribute DNS responses among multiple resources according to relative weights.

Example:

```text
                Route 53
                /      \
               /        \
          Weight 90    Weight 10
             |            |
             v            v
        Environment A Environment B
```

Conceptually:

```text
90%
→ Application A

10%
→ Application B
```

The weights are relative values used by Route 53 when choosing responses.

Do not assume each individual user will observe an exact percentage distribution over a tiny sample.

DNS caching and resolver behavior matter.

---

# 49. Weighted Routing Use Cases

Weighted routing can help with:

* Gradual migrations
* Controlled traffic shifts
* Testing a new environment
* Blue/green deployment strategies
* Canary-style exposure

Example:

```text
Old version:
90

New version:
10
```

Then:

```text
Old:
50

New:
50
```

Then:

```text
Old:
0

New:
100
```

This can support gradual transition.

---

# 50. Weighted DNS Is Not Request-Level Load Balancing

This distinction matters.

Route 53 operates at DNS resolution.

An ALB distributes actual HTTP/HTTPS requests among targets.

Compare:

```text
Route 53 weighted routing
→ DNS-level traffic decision
```

with:

```text
ALB
→ Request-level load balancing
```

These are different layers.

---

# 51. Latency-Based Routing

Latency-based routing helps Route 53 select an AWS Region intended to provide lower network latency for the requester among configured resources.

Imagine:

```text
Application
 |
 +---- us-east-1
 |
 +---- eu-west-1
```

Users in different locations may receive different DNS answers.

Conceptually:

```text
US User
   |
   v
Route 53
   |
   v
US Region


European User
   |
   v
Route 53
   |
   v
European Region
```

This is useful for multi-region applications.

---

# 52. Latency Routing Is Not Geographic Distance Alone

Do not think:

```text
Nearest country = selected endpoint
```

Latency-based routing uses AWS latency information to route toward the Region expected to provide lower latency among your configured choices.

Network performance and geographic distance are related, but they are not identical concepts.

---

# 53. Failover Routing

Failover routing supports active-passive architectures.

You define:

```text
Primary
```

and:

```text
Secondary
```

Conceptually:

```text
                 Route 53
                    |
             Is primary healthy?
               /          \
             Yes           No
              |             |
              v             v
           Primary       Secondary
```

This can be used in disaster-recovery designs.

---

# 54. Active-Passive Architecture

Example:

```text
                  Route 53
                     |
                     v
              Health evaluation
                /         \
               /           \
              v             v
      Primary Region   Secondary Region
```

Normally:

```text
Users
  |
  v
Primary
```

If the primary becomes unhealthy according to the configured health logic:

```text
Users
  |
  v
Secondary
```

Failover routing does not magically create your secondary infrastructure.

You must design and maintain the secondary environment.

---

# 55. Route 53 Health Checks

Route 53 health checks can monitor supported endpoints and help Route 53 make routing decisions.

Conceptually:

```text
Route 53
   |
   v
Health Check
   |
   v
Endpoint
```

The health check may determine whether an endpoint appears healthy according to configured criteria.

---

# 56. Health Check Questions

A useful health check should answer something meaningful.

Weak health endpoint:

```text
HTTP 200
```

even when the application cannot use its critical dependencies.

Better health design may distinguish:

```text
Process is alive
```

from:

```text
Application is ready to serve traffic
```

This introduces the broader concepts of:

* Liveness
* Readiness
* Dependency health

You will encounter these concepts again when learning containers and Kubernetes.

---

# 57. Do Not Make Health Checks Too Fragile

Suppose your health endpoint fails whenever a non-critical analytics service is unavailable.

Then:

```text
Analytics issue
       |
       v
Health check fails
       |
       v
Traffic fails over
```

You may turn a small dependency issue into a major traffic event.

Health checks should reflect actual service availability.

---

# 58. Route 53 Health Checks vs ALB Health Checks

These are different.

## ALB health checks

Determine whether ALB targets should receive application traffic.

Architecture:

```text
ALB
 |
 v
EC2 target health
```

## Route 53 health checks

Can help Route 53 evaluate endpoints for DNS routing decisions.

Architecture:


# 60. Prerequisites

Before connecting the domain, verify:

* You control the domain
* The correct Route 53 hosted zone exists
* The domain is delegated correctly
* The ALB exists
* The ALB is internet-facing for a public Internet application
* The ALB has healthy targets
* The ALB Security Group permits the intended traffic
* Target Security Groups permit traffic from the ALB
* The application works through the ALB before adding DNS

This last point is especially important.

# 61. Verify the ALB Before DNS

Do not add DNS to an application that is already broken and then troubleshoot both at once.

Find the ALB DNS name.

It may look conceptually like:

```text

```

Test it.

For HTTP:

```bash
curl -I http://prod-alb-123456.us-east-1.elb.amazonaws.com
```

`curl` is a command-line tool used to transfer data using protocols such as HTTP and HTTPS.

`-I` requests response headers rather than the full response body for HTTP.

Possible output:

```text

```

If the ALB does not work directly, fix that before introducing Route 53.

# 62. Why Test Layers Separately?

# 77. `www` vs Apex

You might have:

```text

```

and:

```text

```

These are separate DNS names.

Possible design:

```text
example.com
      |
      v
ALB

www.example.com
      |
      v
ALB
```

Another design may redirect one hostname to the other at the HTTP/application layer.

DNS itself does not perform an HTTP redirect.

That distinction matters.

---

# 78. DNS Alias Is Not an HTTP Redirect

Suppose:

```text
www.example.com
```

and:

```text
example.com
```

both resolve to the same ALB.

The browser does not necessarily change:

```text
www.example.com
```

into:

```text
example.com
```

in its address bar.

DNS resolution and HTTP redirection are different.

An HTTP redirect may look like:

```text
HTTP 301
```

or:

```text
HTTP 302
```

and is handled at the application/load-balancer HTTP layer.

# 79. Host-Based Routing With Route 53 and ALB

From Part 11, you learned ALB host-based routing.

You can combine DNS names with ALB listener rules.

Example:

```text
api.example.com ----\
                     \
                      > ALB
                     /
app.example.com ----/
```

Then ALB rules:

```text
Host = app.example.com
        |
        v
Application Target Group

Host = api.example.com
        |
        v
API Target Group
```

DNS gets both names to the ALB.

The ALB then examines the HTTP Host header and chooses the appropriate target group.

---

# 80. DNS Layer vs ALB Routing Layer

Understand the separation:

```text
DNS:
app.example.com → ALB
api.example.com → ALB
```

Then:

```text
ALB:
Host app.example.com → App targets

Host api.example.com → API targets
```

DNS determines the destination.

ALB listener rules determine how HTTP/HTTPS requests are routed after reaching the ALB.

---

# 81. Path-Based Routing

You can also have:

```text
example.com/api/*
```

and:

```text
example.com/images/*
```

Both use the same DNS name:

```text
example.com
```

DNS does not care about:

```text
/api/
```

DNS resolves hostnames, not HTTP URL paths.

The ALB can route by path.

Example:

```text
example.com
     |
     v
Route 53
     |
     v
ALB
     |
     +---- /api/* → API Target Group
     |
     +---- /images/* → Web Target Group
```

This distinction is essential.

---

# 82. DNS Does Not See URL Paths

Consider:

```text
https://example.com/products/123
```

DNS resolves:

```text
example.com
```

It does not resolve:

```text
/products/123
```

That path belongs to HTTP.

Think:

```text
DNS:
Which destination handles example.com?

HTTP:
Which resource does /products/123 request?
```

This is one reason DNS is fundamental to dynamic infrastructure.

# 86. DNS and High Availability

DNS can participate in high-availability architectures.

But DNS alone does not create high availability.

For example:

```text

 |
 v

```

still leaves:

```text

```

A more resilient design might be:

```text

 |

 |          |
```

```text
                Route 53
                /      \
               v        v

```

Each layer solves a different problem.

* Wrong name servers

* Typo
* Wrong hosted zone

```bash

```

# 95. Trace DNS Resolution

# 96. Query a Specific DNS Server

You can ask a particular resolver:

```bash

```

The `@` syntax tells `dig` which DNS server to query.

This can help compare resolver behavior.

Do not assume one resolver's cached answer represents every resolver on the Internet.

# 97. Query the Authoritative Server Directly

Suppose one of your authoritative name servers is:

```text

```

Conceptually, you can query it directly:

```bash

```

```text

```

# 98. Troubleshooting With Layers

Use this order:

```text
1. Does the domain exist?
2. Is delegation correct?
3. Does the authoritative server return the expected record?
4. Does the recursive resolver return it?
5. Does the name resolve from the client?
6. Can the client connect to the destination?
7. Does the ALB accept the request?
8. Is the target healthy?
9. Does the application respond?
```

Do not mix every layer together.


# 120. DNS Caching During Weighted Routing

Remember that DNS caching affects weighted routing behavior.

A recursive resolver may cache an answer and serve that answer to multiple clients.

Therefore weighted Route 53 routing is not the same as:

```text

```

That would be request-level traffic behavior.

DNS works differently.

# 145. Common Beginner Mistakes

## Mistake 1

Thinking DNS traffic continuously passes through Route 53.

Correct model:

```text
DNS helps resolve the destination.
Application traffic then goes to the destination.
```

## Mistake 2

Confusing registrar and DNS provider.

They can be different companies.

## Mistake 3

Hardcoding ALB IP addresses.

Use the appropriate Route 53 Alias integration.

## Mistake 4

Creating records in the wrong hosted zone.

Always verify delegation.

## Mistake 5

Thinking a private hosted zone makes a service secure by itself.

It does not replace network security.

## Mistake 6

Blaming DNS when DNS resolution works.

Check the next layer.

## Mistake 7

Thinking DNS Alias equals HTTP redirect.

They are different mechanisms.

## Mistake 8

Forgetting TTL and caching.

Old answers can remain cached.

## Mistake 9

Thinking Route 53 failover creates the backup application.

It does not.

## Mistake 10

Thinking HTTPS is created automatically by adding DNS.

You still need TLS configuration.
