# Part 8: Git Branches From the Ground Up

In Part 7, you learned how to undo changes safely.

You learned that Git can preserve multiple versions of a project through commits:

```text
A -> B -> C -> D
```

So far, however, most of our history has moved in one straight line.

Real software development rarely works that way.

Imagine that your application is currently stable:

```text
A -> B -> C
```

You need to build a new login feature.

But while you are working on it:

* Production must remain stable
* Another engineer may need to fix a bug
* Your feature may take several days
* Your experimental code may temporarily break
* You may eventually decide not to use the feature

You need somewhere to develop without treating every experimental commit as part of the main development line.

This is one of the problems Git branches solve.

In this part, you will learn:

* Why branches exist
* What a Git branch actually is
* What the default branch means
* Why `main` is commonly used
* What branch pointers are
* How HEAD relates to branches

* How to switch branches
* How `git branch` works
* How `git switch` works
* Why older tutorials use `git checkout`
* How commits behave on branches
* What branch divergence means
* How to delete branches
* How to rename branches
* How feature branches work
* Common branch mistakes
* How branches are used in practical DevOps workflows

# 1. Why Branches Exist

Suppose your application has reached this state:

```text
A -> B -> C
```

Commit C is stable.

Now you need to build:

```text
User authentication
```

The feature may require several commits:

```text
Add login page
Add authentication logic
Add session handling
Add tests
```

You could continue directly:

```text
A -> B -> C -> D -> E -> F -> G
```

But what if the authentication work is incomplete at D?

What if production suddenly needs an urgent fix while you are halfway through?

What if the feature is abandoned?

Branches allow development to separate temporarily.

Conceptually:

```text
              D -> E -> F
             /
A -> B -> C
```

The existing development line can remain at C while another line develops independently.

---

# 2. A Real-World Branch Scenario

Imagine VERIQTA has an application with:

```text
main
 |
 v
A -> B -> C
```

The current code works.

You are asked to add:

```text
User profile pages
```

Instead of developing directly on `main`, you create:

```text
feature/user-profile
```

Now:

```text
main
 |
 v
A -> B -> C
          ^
          |
feature/user-profile
```

Initially, both branches identify the same commit.

Then you create a commit on the feature branch:

```text
main
 |
 v
A -> B -> C
          \
           D
           ^
           |
feature/user-profile
```

Another commit:

```text
main
 |
 v
A -> B -> C
          \
           D -> E
                ^
                |
        feature/user-profile
```

Your feature now has its own development history.

---

# 3. Branches Are Not Full Copies of Your Project

A common beginner misunderstanding is:

> Creating a branch creates another complete copy of my repository.

That is not how Git branches should be understood.

You might imagine:

```text
main/
    app.py
    config.yml
    README.md

feature/
    app.py
    config.yml
    README.md
```

But a Git branch itself is not a duplicated project directory.

A branch is fundamentally much smaller.

---

# 4. What a Git Branch Actually Is

At a beginner-friendly level:

> A Git branch is a movable reference to a commit.

Suppose your history is:

```text
A -> B -> C
```

and:

```text
main
```

identifies C.

Conceptually:

```text
A -> B -> C
          ^
          |
         main
```

`main` is not the commits themselves.

It is a reference pointing to one commit.

---

# 5. Branch Pointer Mental Model

Think of a branch as a movable label.

```text
A -> B -> C
          ^
          |
         main
```

If you create another commit:

```text
D
```

while `main` is the active branch, Git moves `main` forward:

```text
A -> B -> C -> D
               ^
               |
              main
```

The branch pointer moves as new commits are created on that branch.

This is why we call branches:

```text
movable references
```

---

# 6. Why This Makes Branches Lightweight

Suppose you create:

```text
feature-login
```

at commit D.

Initially:

```text
A -> B -> C -> D
               ^
              / \
          main   feature-login
```

Git does not need to duplicate every commit.

Both branch references can identify D.

The branch itself is essentially a small reference.

That makes creating Git branches fast and inexpensive.

---

# 7. What Is the Default Branch?

When a repository is created, one branch is normally treated as the initial/default branch.

In many modern repositories, this branch is named:

```text
main
```

You may also encounter:

```text
master
```

especially in older repositories, tutorials, systems, or projects.

The branch name itself does not make the branch technically magical.

It is still a branch reference.

---

# 8. Understanding main

Suppose:

```text
A -> B -> C
          ^
          |
         main
```

`main` is simply the branch named `main`.

Teams often use it as their primary integration branch.

Depending on the organization, `main` might represent:

* The primary development line
* Code expected to remain stable
* Code eligible for deployment
* The branch from which releases are prepared
* The integration point for approved features

But these are workflow policies.

Git itself does not automatically guarantee that `main` is:

```text
safe
production-ready
tested
deployable
protected
```

Those guarantees come from engineering practices and repository configuration.

---

# 9. main Does Not Automatically Mean Production

This distinction matters.

A company might use:

```text
main
```

for production-ready code.

Another might use:

```text
main
develop
release
production
```

in a more complicated workflow.

Git does not decide the team's release model.

Therefore:

```text
main = branch name
```

not:

```text
main = automatically production
```

# 12. Understanding HEAD and Branches

You learned previously that HEAD represents your current checked-out position.

In normal branch-based work:

```text
HEAD
 |
 v
main
 |
 v
C
```

This means:

```text
HEAD -> main -> C
```

HEAD normally refers to the current branch.

The branch identifies a commit.

---

# 13. HEAD Is How Git Knows Where You Are

Suppose your repository contains:

```text
main
feature-login
```

with:

```text
A -> B -> C
          ^
         / \
      main feature-login
```

If:

```text
HEAD -> main
```

you are currently working on `main`.

If you switch:

```text
HEAD -> feature-login
```

you are now working on the feature branch.

HEAD helps Git determine which branch should move when you create a new commit.

# 17. Creating a Branch Does Not Automatically Switch to It

This is extremely important.

You ran:

```bash
git branch feature-login
```

but:

```bash
git branch
```

still shows:

```text
* main
```

Why?

Because:

```bash
git branch feature-login
```

created the branch.

It did not switch HEAD to that branch.

Conceptually:

```text
              HEAD
               |
               v
              main
               |
               v
A -> B -> C
          ^
          |
   feature-login
```

Both branches point to C, but HEAD still refers to `main`.

# 18. Switching Branches With git switch

To switch:

```bash
git switch feature-login
```

You may see:

```text
Switched to branch 'feature-login'
```

Now:

```bash
git branch
```

should show:

```text
* feature-login
  main
```

Conceptually:

```text
              main
               |
               v
A -> B -> C
          ^
          |
   feature-login
          ^
          |
         HEAD
```

---

# 19. What git switch Does

The command:

```bash
git switch feature-login
```

changes your currently checked-out branch.

Git updates:

```text
HEAD
```

to refer to:

```text
feature-login
```

Git also updates the working tree as necessary so your files correspond to the selected branch's state.

At the moment, both branches point to the same commit, so your files may appear unchanged.

# 21. What Happened to the Branch Pointer?

Before the commit:

```text
A -> B
     ^
    / \
 main  feature-login
```

HEAD was attached to:

```text
feature-login
```

When you created commit C:

```text
A -> B -> C
     ^     ^
     |     |
   main  feature-login
```

`feature-login` moved forward.

`main` stayed where it was.

That is the core mechanism behind branches.

Suppose:

```text

 |
 v
C
```

When you create D:

```text
C -> D
```

Git moves:

```text
feature-login
```

to D.

Now:

```text
main
 |
 v
B
 \
  C -> D
       ^
       |
 feature-login
       ^
       |
      HEAD
```

The current branch advances with your new commit.

# 24. Switching Branches Can Change Your Files

This surprises many beginners.

On `feature-login`:

```python
print("Application started")
print("Login feature enabled")
```

On `main`:

```python
print("Application started")
```

When you switch branches, Git updates tracked files in your working tree to reflect the checked-out branch.

Think:

```text
git switch feature-login
        |
        v
Working tree reflects feature-login
```

and:

```text
git switch main
        |
        v
Working tree reflects main
```

Your files are not randomly disappearing.

You are viewing different recorded project states.

---

# 25. Do Not Panic When Files Change During Switching

Suppose:

```text
feature-login
```

contains:

```text
login.py
```

but `main` does not.

When you switch to `main`, `login.py` may disappear from your working tree.

Switch back:

```bash
git switch feature-login
```

and the tracked file returns.

Git is presenting the files associated with the branch's current commit.

# 30. Why Older Tutorials Use git checkout

If you read older Git tutorials, you will often see:

```bash

```

```bash

```

```bash

```


---

# 31. git checkout Historically Did Several Jobs

`git checkout` has historically been used for tasks including:

* Switching branches
* Creating and switching branches
* Checking out commits
* Restoring paths

That made it powerful but sometimes confusing.

For example:

```bash
git checkout main
```

switches branches.

But forms of checkout can also operate on files.

Modern Git introduced more focused commands:

```text
git switch
```

for branch switching, and:

```text
git restore
```

for restoring working-tree/index content.

---

# 32. Old vs Modern Command Comparison

Older tutorials may use:

```bash
git checkout main
```

Modern equivalent:

```bash
git switch main
```

Older:

```bash
git checkout -b feature-login
```

Modern:

```bash
git switch -c feature-login
```

Older path-restoration patterns may use checkout.

Modern Git provides:

```bash
git restore
```

for many restoration tasks.

You should understand both styles because older documentation, Stack Overflow answers, scripts, and existing teams may still use `checkout`.

Suppose:

```text
A -> B -> C
          ^
          |
         main
```

You are on `main`.

Run:

```bash
git switch -c feature-search
```

Git creates:

```text

```

at your current commit.

Now:

```text
A -> B -> C
          ^
         / \
      main  feature-search
```

HEAD moves to `feature-search`.

# 35. Branches Can Start From Different Commits

Branches do not have to start from the latest commit of `main`.

Suppose:

```text
A -> B -> C -> D
               ^
               |
              main
```

You could create a branch from B if you deliberately specify that starting point:

```bash
git branch hotfix-old-version <commit-B>
```

Conceptually:

```text
A -> B -> C -> D
     ^         ^
     |         |
hotfix-old    main
```

This becomes useful in more advanced maintenance and release workflows.

For now, most of your branches will begin from your current branch tip.

# 36. Creating Commits on Different Branches

Suppose:

```text
A -> B
     ^
    / \
 main  feature-login
```

On `feature-login`, create C:

```text
A -> B -> C
     ^     ^
     |     |
   main  feature-login
```

Switch:

```bash
git switch main
```

Then make an unrelated commit D on `main`.

Now history becomes:

```text
        C
       /
A -> B
       \
        D
```

More precisely:

```text
        C
        ^
        |
 feature-login
       /
A -> B
       \
        D
        ^
        |
       main
       ^
       |
      HEAD
```

The branches now have different commits.

# 37. What Is Branch Divergence?

Branches **diverge** when they develop different histories from a common ancestor.

Suppose both started at B.

Then:

```text
feature-login:
B -> C

main:
B -> D
```

Diagram:

```text
        C
       /
A -> B
       \
        D
```

B is the common ancestor.

After B:

* Feature branch contains C
* Main contains D

The histories have diverged.

---

# 38. Why Divergence Happens Naturally

Imagine:

```text
main
```

contains the stable application.

You create:

```text
feature-payment
```

and work on payment integration.

Meanwhile another engineer adds:

```text
Improve logging
```

to `main`.

Now:

```text
               P1 -> P2
              /
A -> B -> C
              \
               L1
```

The branches diverged because independent work occurred.

This is normal.

Git is designed for this.

---

# 39. Divergence Is Not an Error

Beginners sometimes see branch divergence and assume:

> I broke Git.

No.

Branching exists specifically so different lines of development can exist.

The important question becomes:

> How should these histories eventually be combined?

That is the subject of Part 9:

```text
Merging Branches and Resolving Conflicts
```

For now, focus on understanding how divergence forms.

contains:


Show history.


Use compact commit output.


# 43. Read This Graph Carefully

Suppose:

```text

|/

```

This tells you:



# 44. Practical Branch Names

Branches should usually have names that communicate purpose.

Examples:

```text
feature/login
feature/user-profile
fix/api-timeout
fix/health-check
docs/installation
refactor/authentication
```

Teams have different naming conventions.

Git itself does not require these exact prefixes.

The important point is clarity.

---

# 45. Poor Branch Names

Avoid vague names such as:

```text
test
new
stuff
branch1
mine
work
changes
final
final-final
```

Compare:

```text

```

with:

```text

```

The second tells teammates what the branch is for.

---

# 46. Branch Naming Restrictions

Git branch names cannot contain every possible character or pattern.

Rather than memorizing all restrictions now, use simple names built from:

* Letters
* Numbers
* Hyphens
* Forward slashes where your team's convention uses them

Examples:

```text
feature-login
feature/login
fix-api-timeout
fix/api-timeout
```

If Git rejects a branch name, read the error rather than forcing it.

# 48. Common Mistake: Creating a Branch but Not Switching

You intend:

```text
feature-login
```

so you run:

```bash
git branch feature-login
```

Then immediately start coding.

But you forgot to switch.

HEAD remains:

```text
HEAD -> main
```

Your commits therefore move `main`, not `feature-login`.

Prevent this by using:

```bash
git switch -c feature-login
```

when you want to create and immediately work on the new branch.

Then verify:

```bash
git status
```

---

# 49. Common Mistake: Committing on main Accidentally

Suppose:

```bash
git status
```

would have shown:

```text
On branch main
```

but you did not check.

You modify files and commit:

```bash
git commit -m "Add experimental login feature"
```

Now `main` moved.

This is not necessarily unrecoverable.

Part 7 taught you recovery tools.

But prevention is better:

```text
Before editing:
git status

Before committing:
git status

Before pushing:
check your branch
```

---

# 50. Common Mistake: Switching With Uncommitted Changes

Suppose you are on:

```text
feature-login
```

and modify:

```text
app.py
```

without committing.

Then:

```bash
git switch main
```

What happens?

It depends on whether Git can safely carry those working-tree changes across the switch.

Git may allow the switch if the changes do not conflict with the target branch.

Or Git may refuse.

---

# 51. Why Git Sometimes Refuses to Switch

Suppose your uncommitted `app.py` would be overwritten by the version on the target branch.

Git may stop you with a message explaining that local changes would be overwritten.

This is protection.

Do not react with:

```text
How do I force Git to switch?
```

First ask:

```text
What work do I currently have?

Do I need to commit it?

Do I need to keep it temporarily?

Do I need to discard it?
```

Git may be preventing data loss.

---

# 52. Safe Response to a Blocked Switch

Start:

```bash
git status
```

Then:

```bash
git diff
```

Determine what the changes are.

Possible choices include:

* Commit the work if it forms a valid commit
* Restore it if it is definitely unwanted
* Use a temporary-work technique such as stash, which you will learn later
* Finish the current task before switching

Do not blindly force the branch change.

---

# 53. Common Mistake: Assuming Branches Have Separate Physical Folders

You create:

```text
main
feature-login
```

and expect:

```text
project/main/
project/feature-login/
```

Git normally does not work this way in a standard working tree.

You still have one working directory.

Switching branches changes the tracked files in that working directory to reflect the selected branch.

Conceptually:

```text
Repository history
        |
        v
Selected branch
        |
        v
Working tree updated
```

---

# 54. Common Mistake: Assuming a Branch Is a Permanent Snapshot

A branch is not a fixed snapshot.

A commit is a snapshot.

A branch is a movable reference.

Suppose:

```text
feature-login -> C
```

Create D:

```text
feature-login -> D
```

Create E:

```text
feature-login -> E
```

The branch keeps moving.

If you need a fixed historical point, the commit itself provides that identity. Tags, which you will learn later, are also commonly used for named fixed release points.

---

# 55. Deleting Branches

Eventually, branches may no longer be needed.

For example:

```text
feature-login
```

may have completed its purpose.

Git can delete local branches.

A common command is:

```bash
git branch -d feature-login
```

The option:

```text
-d
```

means:

```text
delete
```

# 56. You Cannot Normally Delete the Branch You Are On

Suppose:

```bash
git branch
```

shows:

```text
* feature-login
  main
```

You try:

```bash
git branch -d feature-login
```

Git will not normally let you delete the branch currently checked out.

Switch first:

```bash
git switch main
```

Then:

```bash
git branch -d feature-login
```

# 57. Why Git May Refuse to Delete a Branch

Suppose `feature-login` contains commits not merged into your current branch.

Git may warn that the branch is not fully merged and refuse normal deletion.

This is another safety mechanism.

Git is essentially telling you:

```text
This branch contains history that may become harder to reach
if you delete the branch reference.
```

Do not automatically force deletion.

Inspect first.

---

# 58. Inspect Before Deleting

Run:

```bash
git log --oneline --graph --decorate --all
```

Determine:

* Where the branch points
* Whether its commits are preserved elsewhere
* Whether you still need the work
* Whether the feature has been merged
* Whether deletion is intentional

Only then delete.

---

# 59. Force-Deleting a Branch

Git provides:

```bash
git branch -D feature-login
```

Uppercase:

```text
-D
```

force-deletes the branch.

This can remove a branch reference even when Git considers normal deletion unsafe.

Treat this as a potentially destructive operation.

Do not use:

```bash
git branch -D
```

simply because:

```bash
git branch -d
```

refused.

The refusal may be protecting work.

---

# 60. What Branch Deletion Actually Deletes

Deleting a branch does not necessarily immediately erase all associated commit objects.

It removes the branch reference.

Suppose:

```text
A -> B
     \
      C -> D
           ^
           |
       feature-x
```

Deleting `feature-x` removes the named reference pointing to D.

If no other references make C and D reachable, those commits can become unreachable.

Git may retain unreachable objects temporarily, and reflog or other recovery mechanisms may sometimes help.

But do not depend on that.

Before deleting a branch, verify that you no longer need its unique work.

# 73. Ahead Is Not the Same as Diverged

```text

     ^         ^
     |         |
   main      feature
```

True divergence requires both lines to gain different descendants after their common point.

# 75. Understanding the Common Ancestor

In:

```text
             D -> E
            /
A -> B -> C
            \
             F
```

C is the common ancestor.

Both branches share history through C.

After C:

```text

D -> E
```

while:

```text
main:
F
```

This common-ancestor concept becomes essential for understanding merging in Part 9.

```text

+

```

Sometimes that is easy.

Sometimes both branches changed the same lines and human input is required.

That is merging and conflict resolution.

For now, do not merge yet.

# 81. Branches Are Not Security Boundaries

Do not think:

> My feature is on another branch, so it cannot affect anything.

A branch is a Git history mechanism.

It does not automatically provide:

* Security isolation
* Deployment isolation
* Secret protection
* Access control
* Infrastructure isolation

Those require other systems and policies.

For example, accidentally committing a secret on a feature branch is still a security problem.

---

# 82. Do Not Commit Secrets to “Temporary” Branches

A dangerous thought is:

> This is only a temporary branch, so I can commit the API key and delete the branch later.

No.

Once a secret has been committed and especially if it has been pushed, treat it as potentially exposed.

Never intentionally commit:

```text
AWS access keys
API tokens
Passwords
Private SSH keys
Database credentials
Cloud credentials
Signing keys
```

Branch deletion is not a secret-management strategy.

# 113. A Branch Is a Reference, Not a Container

This is the mental model to keep.

Do not think:

```text
Branch
=
Folder containing commits
```

Think:

```text
Branch
=
Movable reference to a commit
```

Example:

```text
A -> B -> C -> D
               ^
               |
              main
```

When a new commit E is created on `main`:

```text
A -> B -> C -> D -> E
                    ^
                    |
                   main
```

The reference moved.

---

# 114. HEAD Tells Git Which Branch Moves

Suppose:

```text
main -> D
feature -> D
```

and:

```text
HEAD -> feature
```

You create E.

Result:

```text
main -> D
feature -> E
```

Why did `feature` move?

Because HEAD identified `feature` as your current branch.

Conceptually:

```text
HEAD
 |
 v
feature
 |
 v
D
```

Commit:

```text
E
```

becomes:

```text
HEAD
 |
 v
feature
 |
 v
E
```

# 115. Branches Make Parallel Development Possible

Without branches, development would tend toward:

```text
A -> B -> C -> D -> E -> F
```

with every experiment mixed into one line.

Branches allow:

```text
             Feature A
             D -> E
            /
A -> B -> C
            \
             F -> G
             Feature B
```

Later, appropriate changes can be integrated.

This is central to collaborative Git development.

---

# 116. Branches Do Not Replace Good Commits

A feature branch containing:

```text
update
stuff
fix
final
final2
```

still has poor history.

Branches and commits solve different problems.

Branches organize:

```text
lines of development
```

Commits record:

```text
meaningful project states and changes
```

You need both.

---

# 117. Branches Do Not Replace Testing

Creating:

```text
feature/payment
```

does not prove the payment feature works.

The branch still needs:

* Testing
* Review
* Security checks
* Validation
* CI where available
* Correct integration

A branch provides isolation in history, not automatic quality.

# 123. Part 8 Final Recap

The most important idea from this part is:

```text
A GIT BRANCH IS A MOVABLE
REFERENCE TO A COMMIT.
```

Start with:

```text
A -> B -> C
          ^
          |
         main
```

Create:

```bash
git switch -c feature/login
```

Initially:

```text
A -> B -> C
          ^
         / \
      main  feature/login
```

HEAD is now associated with:

```text
feature/login
```

Create a commit:

```text
A -> B -> C
          \
           D
           ^
           |
      feature/login
```

while:

```text
main
```

remains at C.

Create another:

```text
A -> B -> C
          \
           D -> E
                ^
                |
        feature/login
```

If `main` later receives its own commit:

```text
             D -> E
            /
A -> B -> C
            \
             F
```

the branches have diverged.

You can inspect this structure with:

```bash
git log --oneline --graph --decorate --all
```

Your essential branch commands now include:

```bash
git branch
```

List branches.

```bash
git branch feature-name
```

Create a branch without switching.

```bash
git switch feature-name
```

Switch to an existing branch.

```bash
git switch -c feature-name
```

Create and switch.

Older tutorials may use:

```bash
git checkout feature-name
```

or:

```bash
git checkout -b feature-name
```

You should recognize these, even though the clearer modern workflow often uses `git switch`.

For deletion:

```bash
git branch -d feature-name
```

requests normal safe deletion.

Be much more cautious with:

```bash
git branch -D feature-name
```

because it bypasses the normal merged-history safety check.

For renaming:

```bash
git branch -m new-name
```

can rename the current local branch.

Most importantly, develop this habit:

```text
BEFORE WORK
   |
   v
git status
   |
   v
VERIFY CURRENT BRANCH
   |
   v
VERIFY WORKING TREE
   |
   v
CREATE/SWITCH BRANCH
   |
   v
VERIFY AGAIN
   |
   v
MAKE CHANGES
   |
   v
INSPECT
   |
   v
STAGE
   |
   v
REVIEW STAGED DIFF
   |
   v
COMMIT
   |
   v
INSPECT BRANCH HISTORY
```

Branches are the point where Git begins to reveal its real power.

Until now, your history mostly looked like:

```text
A -> B -> C -> D
```

From this point forward, Git history can look like:

```text
             D -> E
            /
A -> B -> C
            \
             F -> G
```

The next engineering problem is obvious:

```text
How do we safely bring those separate lines
of development back together?
```

That is the foundation of Part 9: **Merging Branches and Resolving Conflicts**.
