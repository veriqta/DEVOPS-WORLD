Before learning Git commands, you need to understand why Git exists.

# 1. What Is Version Control?

Version control is a system for recording changes made to files over time.

That definition sounds simple, but it solves an important engineering problem.

Imagine you create a file:

```text
app.py
```

You work on it today.

Tomorrow, you change it.

Next week, another developer changes it.

Later, someone discovers that the application stopped working after one of those changes.

You immediately have several questions:

```text
What changed?

Who changed it?

When was it changed?

Why was it changed?

What did the file look like before?

Can we restore the previous version?
```

Without a version control system, answering these questions can become difficult.

A version control system, often abbreviated as VCS, helps maintain a structured history of changes.

Instead of seeing only the current version:

```text
app.py
```

you can conceptually think of the history as:

```text
Version 1
   |
   v
Version 2
   |
   v
Version 3
   |
   v
Version 4
```

Each meaningful point in that history can describe what changed.

For example:

```text
Version 1
Initial application

Version 2
Added user login

Version 3
Added database connection

Version 4
Fixed login timeout bug
```

Version control therefore gives your project something extremely valuable:

**history.**

It turns a changing collection of files into a project whose evolution can be inspected.

---

# 2. Version Control Is More Than Backup

Beginners sometimes think:

> "Why do I need Git? I already back up my files."

Backup and version control solve different problems.

A backup system primarily helps protect data against loss.

For example:

```text
Laptop fails
     |
     v
Restore files from backup
```

Version control primarily helps you manage changes.

For example:

```text
Working application
       |
       v
Configuration changed
       |
       v
Application fails
       |
       v
Inspect project history
       |
       v
Identify problematic change
```

A good engineering environment may use both.

```text
Backup
    |
    +--> Protects data

Version Control
    |
    +--> Tracks project changes
```

Git should therefore not be viewed simply as another backup mechanism.

It is a system for managing the evolution of a project.

---

# 3. The Problems Version Control Solves

To understand Git, first understand the problems that caused version control systems to become necessary.

## Problem 1: Losing Previous Versions

Suppose you have:

```text
nginx.conf
```

You modify the configuration.

The new configuration breaks your application.

Without recorded history, you may not remember exactly what the previous configuration contained.

You might try keeping copies:

```text
nginx.conf
nginx-old.conf
nginx-working.conf
nginx-final.conf
nginx-final2.conf
nginx-final-real.conf
```

This becomes difficult to manage very quickly.

Version control provides structured history instead.

---

# 4. Problem 2: Not Knowing What Changed

Suppose yesterday your configuration contained:

```text
server_port=8080
```

Today it contains:

```text
server_port=9090
```

If the application suddenly stops working, one of your first troubleshooting questions should be:

**What changed?**

Version control allows engineers to compare versions and identify differences.

Conceptually:

```text
Before
server_port=8080

After
server_port=9090
```

This is extremely useful during troubleshooting.

Instead of relying entirely on memory, you can investigate recorded changes.

---

# 5. Problem 3: Not Knowing Who Changed Something

Consider a team with five engineers.

Someone changes an important infrastructure configuration.

Two days later, the deployment fails.

The team needs context.

They may need to know:

* Who made the change?
* When?
* What files changed?
* What was the purpose?
* Was the change reviewed?

Version control helps create traceability.

This is not mainly about blaming someone.

It is about understanding what happened.

Good incident response depends heavily on evidence.

---

# 6. Problem 4: Multiple People Editing the Same Project

Modern software is rarely created by one person.

Imagine three engineers:

```text
Developer A
Developer B
Developer C
```

All three work on the same application.

Developer A works on authentication.

Developer B fixes a payment bug.

Developer C updates logging.

Without a proper version control workflow, coordinating these changes becomes difficult.

You might end up sending files through email or chat:

```text
project.zip
project-updated.zip
project-updated-john.zip
project-updated-john-fixed.zip
project-final.zip
```

Then someone asks:

> Which one contains Sarah's logging fix?

Nobody is completely sure.

Version control provides a structured way for multiple people to work on the same project.

---

# 7. Problem 5: Experimenting Without Destroying Stable Work

Suppose your application currently works.

You want to experiment with a new feature.

Without version control, you might copy the entire project:

```text
my-app/
my-app-test/
my-app-new/
my-app-backup/
```

This becomes difficult to manage.

Modern version control systems allow developers to create separate lines of development called **branches**.

Conceptually:

```text
Stable project
     |
     +-------------------+
     |                   |
     v                   v
Stable work        New experiment
```

If the experiment works, it can later be combined with the stable work.

If it fails, the stable work can remain unaffected.

Branches will be covered deeply later in this series.

For now, remember:

**Version control makes controlled experimentation possible.**

---

# 8. Problem 6: Understanding Why a Project Changed

A useful history should tell more than:

```text
file changed
```

It should help explain intent.

For example:

```text
Fix database connection timeout
```

or:

```text
Add health check endpoint
```

or:

```text
Update Kubernetes memory limit
```

This gives future engineers context.

Six months later, someone may ask:

> Why was this configuration changed?

Project history may help answer that question.

---

# 9. Problem 7: Recovering From Mistakes

Mistakes happen.

An engineer may:

* Delete important code
* Replace working configuration
* Introduce a bug
* Modify the wrong file
* Make an incorrect infrastructure change

Version control can make many of these situations recoverable because previous project states have been recorded.

However, this requires an important warning.

**Git is not magic.**

If you create work but never record it appropriately, Git may not have a recoverable version of it.

Understanding when Git is actually tracking your work is therefore critical.

We will build that understanding throughout this series.

---

# 10. Life Before Modern Version Control

Before modern version control became standard, developers still needed ways to preserve previous versions.

One basic approach was manual copying.

Imagine a project called:

```text
payment-api
```

You might create:

```text
payment-api-v1
payment-api-v2
payment-api-v3
payment-api-final
payment-api-final-fixed
payment-api-final-fixed-2
```

This works for a small number of changes.

It becomes terrible at scale.

You start asking:

```text
Which version is newest?

Which version actually works?

What changed between v2 and v3?

Who created final-fixed-2?

Can I combine changes from two copies?

Did someone forget to copy a file?
```

Now imagine 30 developers doing this.

The problem becomes much larger.

This is why version control is not simply a convenience.

For modern engineering teams, it is fundamental infrastructure for collaboration.

---

# 11. The Evolution of Version Control

Version control systems can be understood through three broad models:

1. Local version control
2. Centralized version control
3. Distributed version control

Understanding this progression helps explain why Git behaves differently from some older systems.

---

# 12. Local Version Control

A local version control system stores version history on one computer.

Conceptually:

```text
Your Computer
     |
     +-- Project Files
     |
     +-- Version History
```

Instead of manually creating:

```text
project-v1
project-v2
project-v3
```

the version control software manages those versions.

This is an improvement over manual copying.

However, it has an obvious limitation.

The history primarily exists on that machine.

If several developers need to collaborate, a purely local model is not enough.

There is also a risk if the machine and its storage fail without an adequate backup.

---

# 13. Centralized Version Control

Centralized Version Control Systems, or CVCS, introduced a central server.

The model looks approximately like this:

```text
              Central Server
              Repository
                  |
          +-------+-------+
          |       |       |
          v       v       v
       Alice     Bob     Carlos
```

The central server stores the project's authoritative version history.

Developers connect to that server to work with the project.

Examples of centralized version control systems include:

* CVS
* Subversion, commonly called SVN
* Perforce, depending on configuration and workflow

The centralized model greatly improved team collaboration.

Everyone could work from a shared source.

But it also created dependence on the central server.

If access to the server becomes unavailable, some version-control operations may become impossible or limited.

That leads us to distributed version control.

---

# 14. Distributed Version Control

Git is a **distributed version control system**, often abbreviated DVCS.

In a distributed system, developers can have complete repositories locally, including project history.

Conceptually:

```text
                   Remote Repository
                         |
             +-----------+-----------+
             |                       |
             v                       v
      Alice's Repository       Bob's Repository
             |                       |
        Working Files            Working Files
```

Alice does not merely have the latest files.

Her local Git repository can contain project history.

Bob's repository can also contain project history.

This is one of the most important ideas in Git.

When you use Git, many important operations happen locally.

For example, after the repository and required history are available locally, Git can inspect history and create commits without requiring GitHub to perform those operations.

This leads to a critical beginner concept:

**Git does not require GitHub in order to work.**

---

# 15. Local, Centralized, and Distributed Version Control Compared

| Model           | Main idea                                               | Collaboration  | History               |
| --------------- | ------------------------------------------------------- | -------------- | --------------------- |
| Manual copies   | Humans copy files                                       | Very difficult | Separate copies       |
| Local VCS       | Versions managed locally                                | Limited        | Local machine         |
| Centralized VCS | Main history on central server                          | Stronger       | Primarily centralized |
| Distributed VCS | Repositories and history can exist on multiple machines | Strong         | Distributed copies    |

Git belongs to the distributed category.

---

# 16. What Is Git?

Git is a distributed version control system.

It tracks changes to files and helps people manage project history.

Git was created by Linus Torvalds in 2005 during development of the Linux kernel.

Today Git is widely used across software development and infrastructure engineering.

Git allows you to perform tasks such as:

* Create repositories
* Track files
* Record changes
* Inspect history
* Compare versions
* Create branches
* Merge work
* Recover from many mistakes
* Collaborate with other engineers
* Synchronize work with remote repositories

The important word is **Git**.

Git is the version control technology.

It can operate on your computer without GitHub.

---

# 17. What Is GitHub?

GitHub is a platform that hosts Git repositories and provides collaboration features around them.

You can place a Git repository on GitHub so that it can be accessed remotely according to the permissions you configure.

GitHub also provides features such as:

* Pull requests
* Code reviews
* Issues
* Repository permissions
* Project collaboration
* Releases
* Automation through GitHub Actions
* Security features
* Branch protection and rules
* Team and organization management

Conceptually:

```text
Git
|
+--> Version control system

GitHub
|
+--> Platform for hosting and collaborating around Git repositories
```

Git and GitHub are related, but they are not the same thing.

---

# 18. Git vs GitHub

This distinction is one of the first things every beginner should understand.

### Git

Git is software used for version control.

It can run locally.

Example:

```text
Your Laptop
     |
     v
    Git
     |
     v
Local Repository
```

### GitHub

GitHub is an online service where Git repositories can be hosted and collaborated on.

Example:

```text
Your Laptop
     |
     | Internet
     v
   GitHub
     |
     v
Remote Repository
```

A more complete picture is:

```text
Your Computer                         GitHub
+--------------------+               +------------------+
| Working Files      |               | Remote Git       |
|                    |               | Repository       |
| Local Git Repo     | <-----------> |                  |
+--------------------+               +------------------+
```

You use **Git** to manage version history.

You can use **GitHub** to host and collaborate around that repository remotely.

---

# 19. Can You Use Git Without GitHub?

Yes.

You can create a Git repository on your laptop and use Git completely locally.

Conceptually:

```text
Laptop
 |
 +-- project/
      |
      +-- Git repository
```

You can:

* Track files
* Make commits
* Create branches
* Inspect history
* Compare changes
* Merge branches

without creating a GitHub account.

GitHub becomes useful when you want capabilities such as:

* Remote hosting
* Collaboration
* Pull requests
* Code reviews
* Repository sharing
* Cloud-based automation
* Team permissions

# 20. Can You Use GitHub Without Understanding Git?

You can interact with some GitHub features through its website, but if you want to work effectively with Git repositories, understanding Git is essential.

# 21. The Core Git Vocabulary

Before going further, you need five foundational terms:

```text
Repository
Working Directory
Staging Area
Commit
Remote Repository
```

These terms will appear constantly throughout the rest of the series.

---

# 22. What Is a Repository?

A repository, often shortened to **repo**, is a project being managed with version control, together with the Git information needed to track its history.

Imagine this project:

```text
web-application/
├── app.py
├── requirements.txt
├── README.md
└── config/
```

Once the project is initialized as a Git repository, Git maintains information about its history and state.

Conceptually:

```text
Project Files
     +
Git Metadata
     =
Git Repository
```

The metadata is what allows Git to understand things such as:

* Recorded history
* Commits
* Branches
* References
* Configuration

Later, you will learn that a normal Git repository contains a hidden directory called:

```text
.git
```

Do not worry about its internals yet.

The important beginner rule is:

**The repository is not just a folder containing code. It is a project whose changes Git can manage and record.**

---

# 23. What Is the Working Directory?

The **working directory**, also called the **working tree**, is where you work with the checked-out project files.

Suppose your project contains:

```text
app.py
README.md
config.yaml
```

You open:

```text
app.py
```

and change something.

That change exists in your working directory.

Conceptually:

```text
Working Directory
       |
       +-- app.py      <- modified
       +-- README.md
       +-- config.yaml
```

This does not automatically mean that the modification has been recorded permanently in Git history.

This distinction is extremely important.

Editing a file is not the same thing as creating a commit.

---

# 24. What Is the Staging Area?

The **staging area** is where you select changes that you intend to include in the next commit.

Think of it as preparing the next snapshot.

Suppose you modify:

```text
app.py
README.md
config.yaml
```

But you only want the application and documentation changes in your next commit.

You can prepare:

```text
app.py
README.md
```

while leaving:

```text
config.yaml
```

out of that commit.

Conceptually:

```text
Working Directory

app.py          changed
README.md       changed
config.yaml     changed

        |
        | select changes
        v

Staging Area

app.py
README.md

        |
        v

Next Commit
```

The staging area gives you control over what becomes part of a commit.

This is one of Git's most important concepts.

---

# 25. Why Does Git Have a Staging Area?

Imagine you have been working for an hour.

You changed five files.

Three changes belong to a bug fix.

Two belong to an unfinished feature.

You probably do not want one giant commit containing unrelated work.

The staging area lets you organize changes before recording them.

Conceptually:

```text
All current changes
        |
        v
Choose related changes
        |
        v
Staging Area
        |
        v
Create focused commit
```

This helps create clearer project history.

Instead of:

```text
Commit:
changed lots of stuff
```

you can produce:

```text
Commit 1:
Fix database timeout handling

Commit 2:
Update API documentation
```

Clear history is easier to review, troubleshoot, and maintain.

---

# 26. What Is a Commit?

A **commit** is a recorded snapshot of the project changes that you chose to save in Git history.

A commit normally includes information such as:

* The recorded project state
* A unique identifier
* The author
* The timestamp
* A commit message
* A connection to previous history

Conceptually:

```text
Commit A
Initial project
    |
    v
Commit B
Add login page
    |
    v
Commit C
Fix authentication bug
```

Each commit becomes part of the repository's history.

---

# 27. A Commit Is Not Just "Saving a File"

When you press Save in an editor, you save the current file to your filesystem.

That is not the same as making a Git commit.

Consider:

```text
Edit app.py
     |
     v
Save app.py
     |
     v
File changed on disk
```

Git history has not necessarily recorded that change.

A Git workflow adds additional stages:

```text
Edit
  |
  v
Save file
  |
  v
Working Directory
  |
  v
Stage selected change
  |
  v
Create Commit
  |
  v
Git History
```

This distinction prevents a lot of beginner confusion.

---

# 28. What Is a Commit Message?

A commit message describes the purpose of a commit.

Poor example:

```text
changes
```

Another poor example:

```text
stuff
```

Better:

```text
Fix database connection timeout
```

Another:

```text
Add health check endpoint
```

Another:

```text
Update deployment memory limits
```

Good commit messages help other engineers understand why history changed.

They also help you.

Three months later, you are one of the people who may need to understand your own previous work.

---

# 29. Local Repository vs Remote Repository

A **local repository** exists on your computer or another local environment where you are working.

For example:

```text
Laptop
 |
 v
Local Git Repository
```

A **remote repository** exists somewhere else and can be accessed over a network.

For example:

```text
GitHub
 |
 v
Remote Git Repository
```

GitHub is one popular remote repository hosting platform.

The overall relationship might look like:

```text
Developer Laptop                      GitHub
+-----------------------+            +----------------------+
| Working Directory     |            |                      |
|        |              |            | Remote Repository    |
|        v              |            |                      |
| Staging Area          |            |                      |
|        |              |            |                      |
|        v              |            |                      |
| Local Repository      | <--------> |                      |
+-----------------------+            +----------------------+
```

Notice something important:

The staging area is local.

Your local commits are local.

GitHub does not automatically receive every change you make.

Synchronization is a separate action.

---

# 30. Local Does Not Mean Remote

Suppose you make five commits on your laptop.

Those commits can exist in:

```text
Local Repository
```

without existing yet in:

```text
GitHub Repository
```

This is a fundamental Git concept.

Conceptually:

```text
Laptop

Commit A
Commit B
Commit C
Commit D
Commit E

GitHub

Commit A
Commit B
Commit C
```

Your local repository is ahead by two commits.

You later synchronize the appropriate commits with the remote repository.

The exact commands for doing this will be taught later.

# 31. The Basic Git Workflow

Now we can connect the concepts.

A beginner-friendly conceptual workflow is:

```text
Create or modify files
        |
        v
Working Directory
        |
        v
Select changes
        |
        v
Staging Area
        |
        v
Record snapshot
        |
        v
Local Repository
        |
        v
Share/synchronize when needed
        |
        v
Remote Repository
```

This is one of the most important diagrams in this entire series.

Do not memorize commands yet.

Understand the movement.

# 32. A Realistic Example

Imagine you are working on a web application.

The repository contains:

```text
payment-service/
├── src/
├── tests/
├── Dockerfile
├── README.md
└── requirements.txt
```

You need to fix a payment timeout.

You modify:

```text
src/payment.py
```

At this moment:

```text
Working Directory
       |
       +-- payment.py changed
```

You inspect the change and decide that it should become part of the next commit.

You place the relevant change into the staging area.

```text
Working Directory
       |
       v
Staging Area
payment.py
```

You then create a commit describing the change:

```text
Fix payment request timeout
```

Now that snapshot exists in the local repository's history.

Conceptually:

```text
Previous Commit
      |
      v
New Commit
"Fix payment request timeout"
```

Later, the commit may be shared with a remote repository.

That is the basic idea behind Git.

# 33. Git's Three-State Model

Git beginners should understand three important states:

1. Modified
2. Staged
3. Committed

These correspond closely to three important areas.

```text
Working Directory
      |
      | Modified
      v
Staging Area
      |
      | Staged
      v
Local Repository
      |
      | Committed
      v
History
```

Let's examine them carefully.

---

# 34. Modified

A file is **modified** when you have changed it in your working directory compared with the version Git currently has recorded for the relevant state.

Example:

```text
app.py
```

You edit it.

Conceptually:

```text
Repository version:

app.py
Version A

Working directory:

app.py
Version A + new changes
```

Those new changes are currently part of your working state.

They are not automatically a new commit.

---

# 35. Staged

A change is **staged** when you have selected it for inclusion in the next commit.

Conceptually:

```text
Modified Change
      |
      | select
      v
Staged Change
```

The staging area is sometimes called the **index**.

You will see both terms in Git documentation and error messages.

For a beginner:

```text
Staging Area = Index
```

is a useful starting mental model.

---

# 36. Committed

A change becomes **committed** when Git records the staged snapshot in repository history.

Conceptually:

```text
Working Directory
      |
      | modify
      v
Modified
      |
      | stage
      v
Staged
      |
      | commit
      v
Committed
```

This gives us the fundamental cycle:

```text
MODIFY
  |
  v
STAGE
  |
  v
COMMIT
```

You will perform this cycle repeatedly while using Git.

---

# 37. Where Does GitHub Fit Into the Three-State Model?

GitHub is not one of Git's three local states.

This is another important distinction.

The three-state model describes the local Git workflow:

```text
Working Directory
       |
       v
Staging Area
       |
       v
Local Repository
```

A remote repository introduces another destination:

```text
Working Directory
       |
       v
Staging Area
       |
       v
Local Repository
       |
       v
Remote Repository
```

So do not think:

```text
Modified -> Staged -> GitHub
```

Think:

```text
Modified
   |
   v
Staged
   |
   v
Committed locally
   |
   v
Shared remotely when required
```

That mental model will make later commands much easier to understand.

       |

# 49. Common Beginner Misconceptions

## Misconception 1: Git and GitHub are the same thing

They are not.

```text
Git = version control system

GitHub = platform that hosts Git repositories and provides collaboration features
```

---

## Misconception 2: Saving a file creates a Git version

It does not.

Saving modifies the file on your filesystem.

The change must go through the appropriate Git workflow before it becomes a commit.

---

## Misconception 3: Every change automatically goes to GitHub

It does not.

Your working files, staging area, and local repository exist locally.

Remote synchronization is separate.

---

## Misconception 4: Git is only for programmers

It is not.

Git is widely used by:

* Developers
* DevOps engineers
* SREs
* Platform engineers
* Cloud engineers
* Security engineers
* Infrastructure engineers
* Technical writers
* Data professionals

Any workflow involving files that benefit from structured change history may potentially benefit from version control.

---

## Misconception 5: A commit automatically means the change is on GitHub

No.

A commit can exist only in your local repository.

Conceptually:

```text
Commit
  |
  v
Local Repository

NOT automatically:

Commit
  |
  v
GitHub
```

Remote synchronization is another step.

---

## Misconception 6: Git means you can never lose work

Git can protect work that has been appropriately recorded, but uncommitted or otherwise untracked work may still be vulnerable.

Git should also not replace proper backup and disaster-recovery strategies.

# 50. Beginner Troubleshooting Mindset

We have not started using Git commands yet, but you should already begin developing a Git troubleshooting habit.

When something seems wrong, ask:

```text
1. Where am I?
2. What repository am I working in?
3. What files have changed?
4. What state are those changes in?
5. What did I expect to happen?
6. What actually happened?
7. Is the problem local or remote?
```

This produces a useful reasoning flow:

```text
Observe
   |
   v
Identify the current state
   |
   v
Gather evidence
   |
   v
Compare expected vs actual behavior
   |
   v
Form a hypothesis
   |
   v
Test
   |
   v
Fix
   |
   v
Verify
```

Do not build the habit of copying random Git commands from the internet whenever something goes wrong.

Some Git commands can rewrite or discard work.

Understanding the current state should come before attempting a fix.

# 51. Security From the Beginning

Git repositories often contain important project files.

You must develop safe habits early.

Never intentionally commit secrets such as:

```text
Passwords
Private SSH keys
Cloud access keys
API tokens
Database passwords
Production credentials
```

For example, a file containing:

```text
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
```

should not simply be committed to a repository.

Removing a secret from the latest visible file does not necessarily remove it from previous Git history.

This is why secret management matters from the beginning.

Later parts will teach `.gitignore`, authentication, SSH keys, credentials, and repository security in detail.

For now:

**Treat anything committed to Git as something that may persist in history.**

# 53. Mini Scenario: Think Like a DevOps Engineer

Your team stores Kubernetes configuration in Git.

The application currently runs:

Ask yourself:

2. Has Git automatically committed it?
3. Has GitHub automatically received it?
4. What needs to happen before it becomes part of repository history?
5. Why might the team want this change reviewed?

### Answer

The modification initially exists in the engineer's working directory.

Simply editing and saving the YAML file does not create a Git commit.

The local commit is not automatically synchronized with GitHub.

This demonstrates why Git is more than a place to store code.

It can become part of an engineering change-control workflow.

# 57. Part 1 Final Recap

Git becomes much easier when you stop thinking of it as a collection of commands.

Think of it as a system for moving and recording changes.

You begin with files you are working on.

```text
Working Directory
```

You decide which changes belong in the next snapshot.

```text
Staging Area
```

You record that snapshot.

```text
Local Repository
```

You can then collaborate by synchronizing appropriate history with another repository.

```text
Remote Repository
```

Git provides the version-control system that manages this history.

GitHub provides a platform where Git repositories can be hosted and where teams can collaborate around them.

That gives us our foundational model:

```text
FILES
  |
  v
MODIFIED
  |
  v
STAGED
  |
  v
COMMITTED
  |
  v
LOCAL HISTORY
  |
  v
REMOTE COLLABORATION
```

Once this model makes sense, commands such as `git add`, `git commit`, `git push`, and `git pull` stop looking like unrelated commands.

Each command performs a particular job within this workflow.

In Part 2, we can move from the mental model to a real Git environment by installing Git, configuring it correctly, understanding Git's configuration levels, setting identity and defaults, and preparing a safe environment for the hands-on work that follows.
