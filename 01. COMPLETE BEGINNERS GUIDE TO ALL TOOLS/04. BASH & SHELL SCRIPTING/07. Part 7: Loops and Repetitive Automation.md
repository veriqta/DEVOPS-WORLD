# 1. What Is a Loop?

A loop is a programming structure that repeats a block of commands.

Instead of writing:

```bash
printf 'Checking server1\n'
printf 'Checking server2\n'
printf 'Checking server3\n'
```

you can write:

```bash
for server in server1 server2 server3; do
    printf 'Checking %s\n' "$server"
done
```

The loop runs the same block once for each server.

Conceptually:

```text
Start
  |
  v
Get next item
  |
  v
Run commands
  |
  v
More items?
 /       \
Yes       No
 |         |
 +---------+
 |         |
 v         v
Next      End
item
```

A single execution of the loop body is called an **iteration**.

If a loop runs five times, it performs five iterations.

Imagine that an engineer needs to check:

```text

web03
web04
web05
```

Without a loop:

```bash

ping -c 1 web02
ping -c 1 web03
ping -c 1 web04
ping -c 1 web05
```

This is repetitive.

It becomes worse when the number of systems increases.

Imagine:

```text
100 servers
2,000 files
50 containers
300 repositories
25 services
```

Manual repetition becomes:

* slow
* difficult to maintain
* easy to mistype
* difficult to modify
* difficult to scale

Loops allow us to define the operation once and apply it repeatedly.

# 5. Your First `for` Loop

Basic syntax:

```bash
for variable in item1 item2 item3; do
    commands
done
```

Example:

```bash
for server in web01 web02 web03; do
    printf 'Checking %s\n' "$server"
done
```

Expected output:

```text
Checking web01
Checking web02
Checking web03
```

---

# 6. Understanding the `for` Loop

Consider:

```bash
for server in web01 web02 web03; do
    printf 'Checking %s\n' "$server"
done
```

Bash effectively performs:

```text
server=web01
run loop body

server=web02
run loop body

server=web03
run loop body

finish
```

The variable:

```bash
server
```

changes during each iteration.

First:

```text
server = web01
```

Then:

```text
server = web02
```

Then:

```text
server = web03
```

---

# 7. Understanding `do` and `done`

A loop body begins with:

```bash
do
```

and ends with:

```bash
done
```

Example:

```bash
for server in web01 web02 web03
do
    printf 'Checking %s\n' "$server"
done
```

You can also write:

```bash
for server in web01 web02 web03; do
    printf 'Checking %s\n' "$server"
done
```

Both are valid.

The semicolon allows `do` to appear on the same line as the loop declaration.

# 8. Iterating Over Words

The simplest `for` loop iterates over words.

Example:

```bash
for environment in development staging production; do
    printf 'Environment: %s\n' "$environment"
done
```

Output:

```text
Environment: development
Environment: staging
Environment: production
```

This is useful when you have a small known list.

---

# 9. Multiple Commands Inside a Loop

The loop body can contain several commands.

Example:

```bash
for environment in development staging production; do
    printf '--------------------\n'
    printf 'Checking environment: %s\n' "$environment"
    printf 'Validation started\n'
    printf '--------------------\n'
done
```

Every command between:

```bash
do
```

and:

```bash
done
```

runs during every iteration.

---

# 10. Variables Inside Loops

Variables from earlier parts work normally inside loops.

Example:

```bash
prefix="server"

for number in 1 2 3; do
    printf '%s-%s\n' "$prefix" "$number"
done
```

Output:

```text
server-1
server-2
server-3
```

Loops do not replace variables.

They work together.

# 11. Using Conditional Logic Inside Loops

Now combine Part 6 with Part 7.

```bash
for environment in development staging production; do

    if [[ "$environment" == "production" ]]; then
        printf '%s requires strict validation\n' "$environment"
    else
        printf '%s uses standard validation\n' "$environment"
    fi

done
```

This is where scripts become much more powerful.

Each item can receive different treatment.

# 12. Iterating Over Files

Suppose your directory contains:

```text
app.log
api.log
database.log
README.txt
```

You want to process only `.log` files.

Use:

```bash
for file in *.log; do
    printf 'Processing: %s\n' "$file"
done
```

If matching files exist, Bash expands:

```text
*.log
```

into something similar to:

```text
app.log api.log database.log
```

Then the loop processes each one.

---

# 13. This Uses Filename Expansion

Remember Part 3.

The pattern:

```bash
*.log
```

uses filename expansion, also called globbing.

The shell expands it before the loop operates.

Conceptually:

```text
*.log
   |
   v
Shell searches directory
   |
   v
app.log api.log database.log
   |
   v
for loop receives files
```

---

# 14. Always Quote the File Variable

Use:

```bash
"$file"
```

not:

```bash
$file
```

Example:

```bash
for file in *.log; do
    printf 'Processing: %s\n' "$file"
done
```

This matters when filenames contain spaces.

Suppose:

```text
application errors.log
```

The quoted expansion preserves the filename as one argument.

This principle from Part 3 remains extremely important inside loops.

---

# 15. A Subtle Problem: What If No Files Match?

Suppose there are no `.log` files.

You might expect:

```bash
for file in *.log; do
    ...
done
```

to run zero times.

In default Bash behavior, the unmatched pattern may remain literally:

```text
*.log
```

So the loop may process the text `*.log` as if it were a filename.

That can produce misleading behavior.

---

# 16. Safe File Loop with Existence Check

One simple approach is:

```bash
for file in *.log; do
    [[ -e "$file" ]] || continue

    printf 'Processing: %s\n' "$file"
done
```

If the pattern did not match a real path:

```bash
[[ -e "$file" ]]
```

fails.

Then:

```bash
continue
```

skips that iteration.

We will study `continue` fully later in this part.

---

# 17. Bash `nullglob`

Bash also has an option called:

```bash
nullglob
```

When enabled, unmatched glob patterns expand to nothing instead of remaining literal.

Example:

```bash
shopt -s nullglob

for file in *.log; do
    printf 'Processing: %s\n' "$file"
done
```

If no `.log` files exist, the loop runs zero times.

Later:

```bash
shopt -u nullglob
```

disables the option.

This is Bash-specific behavior.

For beginner scripts, an explicit existence check is often easier to understand.

---

# 18. Iterating Over Files in Another Directory

Suppose logs live in:

```text
/var/log/myapp
```

You might write:

```bash
log_directory="/var/log/myapp"

for file in "$log_directory"/*.log; do
    [[ -e "$file" ]] || continue

    printf 'Processing: %s\n' "$file"
done
```

Notice:

```bash
"$log_directory"/*.log
```

The variable part is quoted.

The wildcard remains active.

This allows the directory path to contain spaces while still allowing `*.log` to perform pattern expansion.

---

# 19. Processing Only Regular Files

A directory might contain:

* regular files
* directories
* symbolic links
* other filesystem objects

If you specifically need regular files:

```bash
for file in "$log_directory"/*; do
    [[ -f "$file" ]] || continue

    printf 'Regular file: %s\n' "$file"
done
```

This applies the Part 6 `-f` test inside the loop.

# 20. Iterating Over Directories

Suppose:

```text
projects/
├── api/
├── frontend/
├── worker/
└── README.txt
```

You want only directories.

You could use:

```bash
for directory in projects/*; do
    [[ -d "$directory" ]] || continue

    printf 'Directory: %s\n' "$directory"
done
```

The loop sees everything matching:

```bash
projects/*
```

but:

```bash
[[ -d "$directory" ]] || continue
```

filters out anything that is not a directory.

# 21. Why Filtering Matters

A common automation pattern is:

```text
Discover candidates
       |
       v
Loop through candidates
       |
       v
Validate each candidate
       |
    +--+--+
    |     |
 valid invalid
    |     |
    v     v
process skip
```

Do not assume every matched item is valid for the operation.

Validate inside the loop.

# 22. Iterating Over Command Output

You may encounter code such as:

```bash
for user in $(some_command); do
    printf '%s\n' "$user"
done
```

This uses command substitution.

The command runs first.

Its output becomes the list used by the loop.

For example:

```bash
for shell in $(printf 'bash\nzsh\nsh\n'); do
    printf 'Shell: %s\n' "$shell"
done
```

Output:

```text
Shell: bash
Shell: zsh
Shell: sh
```

But there is an important warning.

---

# 23. Why `for item in $(command)` Can Be Dangerous

Remember Part 3:

Unquoted command substitution is subject to word splitting.

Suppose command output contains:

```text
server one
server two
```

This:

```bash
for server in $(command); do
```

may interpret it as:

```text
server
one
server
two
```

rather than two lines.

Therefore:

```bash
for item in $(command)
```

is only appropriate when you deliberately want shell word splitting and know the output format.

For line-oriented data, use safer methods.

---

# 24. Do Not Parse Arbitrary Lines with `for $(...)`

Avoid:

```bash
for line in $(cat file.txt); do
    ...
done
```

if each line must remain intact.

A line such as:

```text
production server east
```

will be split into separate words.

Instead, use:

```bash
while IFS= read -r line; do
    ...
done < file.txt
```

We will explain every part of this shortly.

# 25. Numeric Ranges

Bash supports brace expansion.

Example:

```bash
for number in {1..5}; do
    printf 'Number: %s\n' "$number"
done
```

Output:

```text
Number: 1
Number: 2
Number: 3
Number: 4
Number: 5
```

This is convenient for fixed numeric ranges.

---

# 26. Descending Ranges

You can also use:

```bash
for number in {5..1}; do
    printf '%s\n' "$number"
done
```

Output:

```text
5
4
3
2
1
```

---

# 27. Range Steps

Bash brace expansion can also use a step.

Example:

```bash
for number in {0..10..2}; do
    printf '%s\n' "$number"
done
```

Output:

```text
0
2
4
6
8
10
```

The general idea is:

```text
{start..end..step}
```

---

# 28. Important Limitation of Brace Expansion

A beginner may try:

```bash
start=1
end=5

for number in {$start..$end}; do
    ...
done
```

This does not behave like a dynamic numeric loop.

Brace expansion happens before normal parameter expansion.

For dynamic numeric boundaries, use a C-style `for` loop.

---

# 29. C-Style `for` Loops

Bash supports arithmetic-style loops similar to languages such as C.

Syntax:

```bash
for (( initialization; condition; update )); do
    commands
done
```

Example:

```bash
for (( i=1; i<=5; i++ )); do
    printf 'Iteration: %s\n' "$i"
done
```

Output:

```text
Iteration: 1
Iteration: 2
Iteration: 3
Iteration: 4
Iteration: 5
```

---

# 30. Understanding the Three C-Style Sections

Consider:

```bash
for (( i=1; i<=5; i++ )); do
```

There are three sections.

## Initialization

```bash
i=1
```

Start the counter at 1.

## Condition

```bash
i<=5
```

Continue while `i` is less than or equal to 5.

## Update

```bash
i++
```

Increase `i` after each iteration.

---

# 31. C-Style Loop Flow

Conceptually:

```text
i=1
 |
 v
i <= 5?
 |
 +-- No --> End
 |
 Yes
 |
 v
Run loop body
 |
 v
i++
 |
 +----------+
            |
            v
         Test again
```

This is useful when you need precise numeric control.

---

# 32. Dynamic Numeric Range

Suppose:

```bash
start=3
end=8
```

You can write:

```bash
for (( i=start; i<=end; i++ )); do
    printf '%s\n' "$i"
done
```

This is more suitable than brace expansion when boundaries come from variables.

---

# 33. Loop Counters

Sometimes you need to know how many items have been processed.

Example:

```bash
count=0

for server in web01 web02 web03; do
    ((count++))
    printf 'Processing server %s: %s\n' "$count" "$server"
done

printf 'Total processed: %s\n' "$count"
```

Expected final output:

```text
Total processed: 3
```

---

# 34. Counters Can Track More Than Total Items

You might maintain:

```bash
processed=0
successes=0
failures=0
skipped=0
```

Then:

```bash
for file in *.log; do

    [[ -e "$file" ]] || continue

    ((processed++))

    if grep -q "ERROR" "$file"; then
        ((failures++))
    else
        ((successes++))
    fi

done
```

Counters make batch automation reports much more useful.

---

# 35. A Note About `((count++))` and Exit Status

There is a subtle Bash behavior worth knowing.

Arithmetic commands themselves return exit statuses.

For:

```bash
((count++))
```

the expression evaluates to the old value of `count`.

If that value is zero, the arithmetic command returns a non-zero status.

This usually does not matter in simple scripts.

But later, when you use strict error-handling patterns such as:

```bash
set -e
```

this can surprise you.

A safer increment pattern in strict scripts is often:

```bash
((count += 1))
```

or:

```bash
((++count))
```

We will study strict error handling properly in Part 14.

For now, understand that Bash arithmetic operations also participate in exit-status behavior.

---

# 36. `while` Loops

A `while` loop repeats commands **while a condition succeeds**.

Basic syntax:

```bash
while condition; do
    commands
done
```

Example:

```bash
count=1

while (( count <= 5 )); do
    printf 'Count: %s\n' "$count"
    ((count += 1))
done
```

Output:

```text
Count: 1
Count: 2
Count: 3
Count: 4
Count: 5
```

---

# 37. How `while` Works

Flow:

```text
Check condition
      |
   +--+--+
   |     |
 true   false
   |     |
   v     v
 run    end
 body
   |
   v
check again
```

The condition is tested **before** each iteration.

If the condition is false immediately, the loop body never runs.

---

# 38. `while` Uses Command Success

Just like `if`, `while` does not require a special Boolean variable.

It can repeatedly execute while a command succeeds.

Example:

```bash
while test -f app.lock; do
    printf 'Lock file still exists\n'
    sleep 2
done
```

As long as:

```bash
test -f app.lock
```

returns `0`, the loop continues.

---

# 39. Using `[[ ]]` with `while`

Example:

```bash
attempt=1

while [[ "$attempt" -le 3 ]]; do
    printf 'Attempt %s\n' "$attempt"
    ((attempt += 1))
done
```

You could also use arithmetic context:

```bash
attempt=1

while (( attempt <= 3 )); do
    printf 'Attempt %s\n' "$attempt"
    ((attempt += 1))
done
```

For numeric counters in Bash, the arithmetic form is usually easier to read.

---

# 40. The Importance of Updating the Loop Condition

Consider:

```bash
count=1

while (( count <= 5 )); do
    printf '%s\n' "$count"
done
```

What changes `count`?

Nothing.

Therefore:

```text
count = 1
```

forever.

The condition:

```text
1 <= 5
```

remains true.

The loop never ends.

This is an accidental infinite loop.

---

# 41. Correcting the Loop

Add:

```bash
((count += 1))
```

Now:

```bash
count=1

while (( count <= 5 )); do
    printf '%s\n' "$count"
    ((count += 1))
done
```

Eventually:

```text
count = 6
```

Then:

```text
6 <= 5
```

is false.

The loop ends.

---

# 42. `until` Loops

An `until` loop is conceptually the opposite of `while`.

A `while` loop means:

> Keep going while this succeeds.

An `until` loop means:

> Keep going until this succeeds.

Syntax:

```bash
until condition; do
    commands
done
```

---

# 43. First `until` Example

```bash
count=1

until (( count > 5 )); do
    printf 'Count: %s\n' "$count"
    ((count += 1))
done
```

The loop continues until:

```bash
(( count > 5 ))
```

becomes successful.

---

# 44. `while` vs `until`

These two examples perform similar work.

Using `while`:

```bash
while (( count <= 5 )); do
    ...
done
```

Using `until`:

```bash
until (( count > 5 )); do
    ...
done
```

Mental model:

```text
while condition
    |
    +--> continue while TRUE
```

```text
until condition
    |
    +--> continue while FALSE
         stop when TRUE
```

Choose whichever communicates the intention more naturally.

---

# 45. Real Use Case for `until`

Imagine an application is starting.

You want to wait until its health check succeeds.

Conceptually:

```text
Application healthy?
      |
      No
      |
      v
Wait
      |
      v
Check again
      |
      +---------+
                |
                v
Application healthy?
      |
     Yes
      |
      v
Continue deployment
```

This is naturally expressed as:

```bash
until health_check_command; do
    sleep 5
done
```

But production scripts need limits.

We will add those shortly.

# 46. Infinite Loops

Sometimes an infinite loop is intentional.

Example:

```bash
while true; do
    printf 'Running\n'
    sleep 5
done
```

The command:

```bash
true
```

always returns exit status `0`.

Therefore the `while` condition always succeeds.

---

# 47. Another Infinite Loop Form

Bash arithmetic can also create:

```bash
while (( 1 )); do
    printf 'Running\n'
    sleep 5
done
```

Because the arithmetic expression `1` is treated as true.

You may also encounter:

```bash
for (( ; ; )); do
    ...
done
```

which is another intentional infinite loop.

---

# 48. When Infinite Loops Are Used

Intentional infinite loops can appear in:

* monitoring scripts
* polling workers
* queue consumers
* daemon-like processes
* development watchers
* container processes
* repeated health checks

But they require careful control.

An infinite loop without:

* delay
* termination condition
* signal handling
* resource limits

can create serious problems.

---

# 49. CPU-Hungry Infinite Loops

Do not casually write:

```bash
while true; do
    command
done
```

If `command` returns immediately, the loop may execute extremely rapidly.

This can consume substantial CPU.

A safer polling design usually includes:

```bash
sleep 5
```

or another deliberate delay.

Example:

```bash
while true; do
    printf 'Checking service\n'
    sleep 5
done
```

---

# 50. Avoiding Accidental Infinite Loops

Before writing a condition-based loop, answer:

```text
What makes this loop continue?

What changes during each iteration?

What eventually makes the condition false or true?

What happens if that event never occurs?

Is there a maximum attempt count?

Is there a timeout?

Is there a delay between attempts?
```

A safe loop needs an exit strategy.

# 51. Reading Files Line by Line

Suppose:

```text
servers.txt
```

contains:

```text
web01
web02
database primary
api01
```

You want each line treated as one item.

Do not use:

```bash
for server in $(cat servers.txt); do
    ...
done
```

because:

```text
database primary
```

may be split into two words.

Use:

```bash
while IFS= read -r line; do
    printf 'Line: %s\n' "$line"
done < servers.txt
```

This is an extremely important Bash pattern.

---

# 52. Understanding `read`

You first encountered `read` in Part 4.

Example:

```bash
read -r line
```

The command reads input and stores it in:

```bash
line
```

The option:

```bash
-r
```

prevents backslashes from being treated as escape characters by `read`.

For general line-oriented file processing, `-r` is usually the safer choice.

---

# 53. What Is `IFS`?

`IFS` means:

**Internal Field Separator**.

Bash uses it when splitting certain input into fields.

The default contains whitespace characters.

In:

```bash
IFS= read -r line
```

we temporarily give `read` an empty `IFS`.

This helps preserve leading and trailing whitespace instead of trimming it according to normal field-splitting behavior.

---

# 54. Understanding the Full Pattern

```bash
while IFS= read -r line; do
    printf '%s\n' "$line"
done < file.txt
```

Breakdown:

```bash
while
```

Repeat while the command succeeds.

```bash
IFS=
```

Use an empty field separator for this `read`.

```bash
read -r line
```

Read one line safely into `line`.

```bash
do
```

Begin loop body.

```bash
printf '%s\n' "$line"
```

Process the line.

```bash
done
```

End loop body.

```bash
< file.txt
```

Redirect the file into the loop's standard input.

---

# 55. Why the Loop Ends at End-of-File

Each time:

```bash
read -r line
```

successfully reads a line, it returns success.

Therefore:

```bash
while IFS= read -r line
```

continues.

Eventually the input reaches the end of the file.

`read` can no longer read another line.

It returns a non-zero status.

The `while` loop stops.

This is another example of exit statuses controlling Bash logic.

---

# 56. Handling a Final Line Without a Newline

Sometimes a text file's last line does not end with a newline character.

A robust pattern is:

```bash
while IFS= read -r line || [[ -n "$line" ]]; do
    printf '%s\n' "$line"
done < file.txt
```

Why?

If `read` reaches end-of-file after receiving some characters but without a terminating newline, it can return non-zero even though `line` contains data.

The additional condition:

```bash
[[ -n "$line" ]]
```

allows that final non-empty line to be processed.

---

# 57. Skipping Empty Lines

Suppose a server file contains blank lines.

You can write:

```bash
while IFS= read -r server; do

    [[ -n "$server" ]] || continue

    printf 'Server: %s\n' "$server"

done < servers.txt
```

If:

```bash
[[ -n "$server" ]]
```

fails, `continue` skips the rest of that iteration.

---

# 58. Skipping Comment Lines

Configuration-style files often contain:

```text
# Production servers
web01
web02

# Database
db01
```

You may skip comments:

```bash
while IFS= read -r server; do

    [[ -n "$server" ]] || continue
    [[ "$server" == \#* ]] && continue

    printf 'Processing: %s\n' "$server"

done < servers.txt
```

The pattern:

```bash
\#*
```

matches values beginning with `#`.

The backslash makes the literal `#` clear in this shell context.

---

# 59. `break`

The command:

```bash
break
```

immediately exits the current loop.

Example:

```bash
for server in web01 web02 web03; do

    printf 'Checking %s\n' "$server"

    if [[ "$server" == "web02" ]]; then
        printf 'Target found\n'
        break
    fi

done
```

Output stops after `web02`.

---

# 60. `break` Flow

Conceptually:

```text
Iteration 1
   |
   v
Continue

Iteration 2
   |
   v
break encountered
   |
   v
Exit loop immediately
   |
   v
Continue after done
```

Commands after `break` inside that loop body do not execute for that iteration.

No further iterations occur.

---

# 61. When `break` Is Useful

Use `break` when:

* the desired item has been found
* a fatal condition occurs
* continuing would be unsafe
* a retry succeeds
* a polling condition is satisfied
* a maximum threshold is reached
* user requests termination

Example:

```bash
for file in *.conf; do

    [[ -f "$file" ]] || continue

    if grep -q "production=true" "$file"; then
        printf 'Production configuration found: %s\n' "$file"
        break
    fi

done
```

Once found, there may be no reason to inspect the remaining files.

---

# 62. `continue`

The command:

```bash
continue
```

does not terminate the entire loop.

It skips the remainder of the **current iteration** and moves to the next iteration.

Example:

```bash
for file in *; do

    if [[ ! -f "$file" ]]; then
        continue
    fi

    printf 'Regular file: %s\n' "$file"

done
```

Directories and other non-regular files are skipped.

---

# 63. `break` vs `continue`

Mental model:

```text
break
  |
  v
Leave loop completely
```

```text
continue
   |
   v
Skip current iteration
   |
   v
Try next iteration
```

This distinction is important.

---

# 64. Guard Conditions with `continue`

A clean loop design often validates an item early.

Example:

```bash
for file in "$log_directory"/*; do

    [[ -f "$file" ]] || continue
    [[ -r "$file" ]] || continue

    printf 'Processing readable file: %s\n' "$file"

done
```

Instead of deeply nesting:

```bash
if [[ -f "$file" ]]; then
    if [[ -r "$file" ]]; then
        ...
    fi
fi
```

you reject unsuitable items early.

This is called a **guard-style** pattern.

# 66. Understanding Nested Loops

The outer loop selects:

```text
development
```

Then the entire inner loop runs:

```text
api
worker
frontend
```

After the inner loop finishes, the outer loop moves to:

```text
production
```

and the inner loop runs again.

Conceptually:

```text
development
    |
    +--> api
    +--> worker
    +--> frontend

production
    |
    +--> api
    +--> worker
    +--> frontend
```

# 67. Nested Loop Iteration Count

Suppose the outer loop has:

```text
3 environments
```

and the inner loop has:

```text
4 services
```

Total combinations:

```text
3 × 4 = 12
```

This matters.

Nested loops can multiply work very quickly.

If:

```text
1,000 outer items
×
1,000 inner items
```

you may perform:

```text
1,000,000 operations
```

Understand the scale before running expensive nested loops.

# 68. `break` in Nested Loops

By default:

```bash
break
```

exits the innermost loop.

Example:

```bash

    for service in api worker frontend; do

        if [[ "$service" == "worker" ]]; then
            break
        fi

        printf '%s %s\n' "$environment" "$service"

    done

done
```

The outer environment loop continues.

# 69. Breaking Multiple Loop Levels

Bash allows:

```bash
break 2
```

to exit two loop levels.

Example:

```bash
for environment in development production; do

    for service in api worker frontend; do

        if [[ "$environment" == "production" && "$service" == "worker" ]]; then
            break 2
        fi

        printf '%s %s\n' "$environment" "$service"

    done

done
```

Use multi-level `break` carefully.

If it makes the script difficult to understand, restructure the logic.

# 70. `continue` in Nested Loops

Similarly:

```bash
continue
```

normally applies to the innermost loop.

Bash also allows:

```bash
continue 2
```

to affect an outer loop level.

Again, readability matters.

Advanced control-flow tricks are not automatically better engineering.

# 71. Loop Conditions

A loop should have a clearly defined continuation condition.

For a `for` loop:

```text
Are there more items?
```

For a `while` loop:

```text
Does condition still succeed?
```

For an `until` loop:

```text
Has condition succeeded yet?
```

Before running a loop, identify exactly what controls termination.

# 72. Safe Loop Design

A production-oriented loop should answer:

```text
What items am I processing?

How many items could there be?

What validates each item?

What happens when one item fails?

Should I continue after failure?

Should I stop immediately?

How long can one iteration take?

Is there a timeout?

Is there a delay?

Can the loop run forever?

Can I safely run it twice?

Does it modify or delete anything?

How will I know what happened?
```

These questions matter more than memorizing loop syntax.

# 88. Retry Loops

Networks fail.

APIs temporarily return errors.

Services take time to start.

Deployments may not become healthy immediately.

Sometimes an operation should be attempted again.

This is called a **retry**.

Conceptually:

```text
Attempt operation
      |
      v
Succeeded?
 /          \
Yes          No
 |            |
 v            v
Done      attempts left?
             /       \
           Yes        No
            |          |
            v          v
           Wait       Fail
            |
            v
        Try again
```

---

# 89. Basic Retry Loop

Suppose we simulate an operation with:

```bash
false
```

which always fails.

A retry structure could be:

```bash
attempt=1
max_attempts=3

while (( attempt <= max_attempts )); do

    printf 'Attempt %s of %s\n' "$attempt" "$max_attempts"

    if false; then
        printf 'Operation succeeded\n'
        break
    fi

    printf 'Operation failed\n'
    ((attempt += 1))
    sleep 2

done
```

Because `false` never succeeds, all attempts are used.

---

# 90. Why Retry Loops Need a Maximum

Dangerous:

```bash
until some_network_command; do
    sleep 5
done
```

What if the remote service is unavailable for three days?

The script could continue indefinitely.

Safer:

```text
Maximum attempts = 5
```

Then:

```text
Attempt 1
Attempt 2
Attempt 3
Attempt 4
Attempt 5
     |
     v
Stop and report failure
```

Retries need boundaries.

---

# 91. Complete Retry Pattern

A clearer pattern:

```bash
attempt=1
max_attempts=5
success=false

while (( attempt <= max_attempts )); do

    printf 'Attempt %s of %s\n' "$attempt" "$max_attempts"

    if some_command; then
        success=true
        break
    fi

    printf 'Attempt failed\n' >&2

    if (( attempt < max_attempts )); then
        sleep 2
    fi

    ((attempt += 1))

done

if [[ "$success" == "true" ]]; then
    printf 'Operation succeeded\n'
else
    printf 'Operation failed after %s attempts\n' "$max_attempts" >&2
    exit 1
fi
```

This distinguishes:

```text
eventual success
```

from:

```text
retry exhaustion
```

---

# 92. Do Not Retry Every Failure

Retries are not automatically appropriate.

Consider:

```text
Temporary network timeout
```

Retry may help.

But:

```text
Invalid password
```

repeating the same request may not help.

Similarly:

```text
Configuration syntax error
```

will not normally fix itself because you waited five seconds.

Before retrying, ask:

> Is this failure likely to be temporary?

Retry transient failures.

Fix permanent failures.

---

# 93. Retry Delay

Retries should usually include a delay.

Example:

```bash
sleep 2
```

Without a delay:

```text
Attempt 1
Attempt 2
Attempt 3
Attempt 4
Attempt 5
```

may happen almost instantly.

That can:

* overload a service
* trigger rate limits
* flood logs
* waste CPU
* worsen an outage

---

# 94. Increasing Retry Delays

A simple increasing delay could be:

```bash
delay=2

for (( attempt=1; attempt<=4; attempt++ )); do

    printf 'Attempt %s\n' "$attempt"

    if some_command; then
        break
    fi

    sleep "$delay"
    ((delay *= 2))

done
```

The delays become:

```text
2 seconds
4 seconds
8 seconds
16 seconds
```

This introduces the idea of **backoff**.

Production retry strategies will be explored more deeply later.

# 95. Polling Loops

Retrying and polling are related but not identical.

A retry usually means:

> Try an operation again because it failed.

Polling usually means:

> Repeatedly check whether a state has changed.

Example:

```text
Deployment started
      |
      v
Check status
      |
      v
Ready?
 /        \
Yes        No
 |          |
 v          v
Continue   Wait
            |
            v
        Check again
```

---

# 96. Simple Polling Example

Suppose a file indicates that a simulated service is ready.

```bash
until [[ -f service.ready ]]; do
    printf 'Waiting for service...\n'
    sleep 2
done

printf 'Service is ready\n'
```

This works, but it can wait forever.

We need a timeout or maximum number of checks.

---

# 97. Bounded Polling Loop

```bash
attempt=1
max_attempts=10

until [[ -f service.ready ]]; do

    if (( attempt >= max_attempts )); then
        printf 'ERROR: service did not become ready\n' >&2
        exit 1
    fi

    printf 'Waiting for service: check %s/%s\n' "$attempt" "$max_attempts"

    ((attempt += 1))
    sleep 2

done

printf 'Service is ready\n'
```

Now the loop has an escape condition.

---

# 98. Polling Is Common in DevOps

You will see polling when waiting for:

* Kubernetes deployments
* cloud instances
* DNS changes
* application health endpoints
* database availability
* CI/CD jobs
* load balancers
* containers
* asynchronous API operations
* infrastructure provisioning

Conceptually:

```text
Start operation
      |
      v
Observe state
      |
      v
Desired state?
   /       \
 Yes       No
  |         |
  v         v
Continue   Wait
            |
            v
        Observe again
```

---

# 99. Polling Needs More Than `sleep`

A production polling loop should consider:

* maximum wait time
* interval between checks
* command timeout
* authentication failures
* unexpected states
* terminal failure states
* logging
* exit status
* cleanup

For example, if a deployment state becomes:

```text
FAILED
```

there is no reason to continue polling for:

```text

```

The script should recognize terminal failure.

# 100. Retry vs Polling

A useful distinction:

```text
Retry
 |
 +--> repeat an operation
```

Example:

```text

```

```text

```

Example:

```text

```

Sometimes the implementation looks similar, but the intention is different.

# 103. Avoid Parsing `ls`

A common beginner pattern is:

```bash
for file in $(ls); do
    ...
done
```

Avoid this.

Why?

`ls` output is designed primarily for display, not safe machine parsing.

Filenames may contain:

* spaces
* tabs
* unusual characters
* newlines

Instead, use shell globbing directly:

```bash
for file in *; do
    ...
done
```

Then validate:

```bash
[[ -f "$file" ]] || continue
```

Use the filesystem objects themselves instead of parsing formatted `ls` output.

---

# 104. Avoid `cat` When Redirection Is Enough

You may see:

```bash
cat servers.txt | while read server; do
    ...
done
```

Often this is unnecessary.

Prefer:

```bash
while IFS= read -r server; do
    ...
done < servers.txt
```

This is clearer and avoids an unnecessary `cat` process.

There is also an important Bash subshell consideration with piped loops, which we will touch on shortly.

---

# 105. The Piped `while` Loop Surprise

Consider:

```bash
count=0

printf 'one\ntwo\nthree\n' |
while IFS= read -r line; do
    ((count += 1))
done

printf 'Count: %s\n' "$count"
```

In Bash, the loop on the right side of the pipeline commonly runs in a subshell.

Changes to:

```bash
count
```

may therefore not exist in the parent shell after the pipeline finishes.

You might unexpectedly see:

```text
Count: 0
```

---

# 106. Why This Happens

Conceptually:

```text
Parent shell
   |
   +--> creates pipeline
           |
           +--> loop runs in child/subshell context
                    |
                    +--> count changes here
```

When that context ends:

```text
parent's count remains unchanged
```

This relates to the subshell concept introduced in Part 5.

---

# 107. Prefer Redirection When Reading a File

Instead of:

```bash
cat file.txt |
while IFS= read -r line; do
    ((count += 1))
done
```

use:

```bash
count=0

while IFS= read -r line; do
    ((count += 1))
done < file.txt

printf 'Count: %s\n' "$count"
```

Now the loop runs in the current shell context and the counter remains available afterward.

---

# 108. Process Substitution Preview

Sometimes you need command output while avoiding a pipeline subshell.

Bash provides **process substitution**.

Example:

```bash
count=0

while IFS= read -r line; do
    ((count += 1))
done < <(printf 'one\ntwo\nthree\n')

printf 'Count: %s\n' "$count"
```

The syntax:

```bash
<(command)
```

provides command output through a file-like input mechanism.

This is an advanced Bash feature.

You do not need to master it yet.

For now, recognize why you may see:

```bash
while ...; do
    ...
done < <(command)
```

in real Bash scripts.

# 126. Complete Multi-File Automation Script

The completed script:

```bash
#!/usr/bin/env bash

log_directory="$HOME/bash-lab/part7/logs"
report_directory="$HOME/bash-lab/part7/reports"
report_file="$report_directory/log-summary.txt"

processed=0
healthy=0
problematic=0
empty_files=0
total_errors=0
total_warnings=0

if [[ ! -d "$log_directory" ]]; then
    printf 'ERROR: log directory does not exist: %s\n' "$log_directory" >&2
    exit 1
fi

if [[ ! -d "$report_directory" ]]; then
    printf 'ERROR: report directory does not exist: %s\n' "$report_directory" >&2
    exit 1
fi

if [[ ! -w "$report_directory" ]]; then
    printf 'ERROR: report directory is not writable: %s\n' "$report_directory" >&2
    exit 1
fi

printf 'VERIQTA LOG PROCESSING REPORT\n' > "$report_file"
printf '=============================\n' >> "$report_file"
printf 'Log directory: %s\n\n' "$log_directory" >> "$report_file"

for file in "$log_directory"/*.log; do

    [[ -e "$file" ]] || continue

    if [[ ! -f "$file" ]]; then
        printf 'SKIP: not a regular file: %s\n' "$file"
        continue
    fi

    if [[ ! -r "$file" ]]; then
        printf 'SKIP: unreadable file: %s\n' "$file" >&2
        continue
    fi

    ((processed += 1))

    if [[ ! -s "$file" ]]; then

        printf 'EMPTY: %s\n' "$file"
        printf 'EMPTY: %s\n' "$file" >> "$report_file"

        ((empty_files += 1))
        ((problematic += 1))

        continue
    fi

    error_count="$(grep -c 'ERROR' "$file")"
    warning_count="$(grep -c 'WARNING' "$file")"

    ((total_errors += error_count))
    ((total_warnings += warning_count))

    if (( error_count > 0 )); then

        printf 'PROBLEM: %s has %s error line(s) and %s warning line(s)\n' \
            "$file" "$error_count" "$warning_count"

        printf 'PROBLEM: %s | errors=%s | warnings=%s\n' \
            "$file" "$error_count" "$warning_count" >> "$report_file"

        ((problematic += 1))

    else

        printf 'OK: %s has no ERROR lines and %s warning line(s)\n' \
            "$file" "$warning_count"

        printf 'OK: %s | errors=%s | warnings=%s\n' \
            "$file" "$error_count" "$warning_count" >> "$report_file"

        ((healthy += 1))

    fi

done

if (( processed == 0 )); then
    printf 'WARNING: no readable .log files were processed\n'
    printf '\nNo readable .log files were processed.\n' >> "$report_file"
fi

{
    printf '\nSUMMARY\n'
    printf '=======\n'
    printf 'Processed files: %s\n' "$processed"
    printf 'Healthy files: %s\n' "$healthy"
    printf 'Problematic files: %s\n' "$problematic"
    printf 'Empty files: %s\n' "$empty_files"
    printf 'Total ERROR lines: %s\n' "$total_errors"
    printf 'Total WARNING lines: %s\n' "$total_warnings"
} >> "$report_file"

printf '\nPROCESSING SUMMARY\n'
printf '==================\n'
printf 'Processed files: %s\n' "$processed"
printf 'Healthy files: %s\n' "$healthy"
printf 'Problematic files: %s\n' "$problematic"
printf 'Empty files: %s\n' "$empty_files"
printf 'Total ERROR lines: %s\n' "$total_errors"
printf 'Total WARNING lines: %s\n' "$total_warnings"
printf 'Report: %s\n' "$report_file"

if (( problematic > 0 )); then
    printf 'RESULT: problems detected\n' >&2
    exit 1
else
    printf 'RESULT: all processed logs passed\n'
    exit 0
fi
```

# 131. Troubleshooting: Loop Never Stops

## Problem

A `while` or `until` loop continues forever.

## Investigate

Ask:

```text
What is the loop condition?

What changes that condition?

Is the counter being updated?

Can the external state ever reach the desired value?

Is break reachable?

Is there a maximum attempt limit?
```

Example mistake:

```bash
count=1

while (( count <= 10 )); do
    printf '%s\n' "$count"
done
```

Fix:

```bash
((count += 1))
```

inside the loop.

# 135. Troubleshooting: Counter Is Zero After Pipeline

Missing delay.

# 138. Troubleshooting: One Bad Item Stops Everything

Sometimes this is intentional.

Sometimes it is not.

Suppose:

```bash
for file in *.log; do
```

The first unreadable file terminates the entire script.


Choose intentionally between:


# 140. Production Thinking: Partial Failure

Batch automation introduces an important question:

> What happens if 1 item fails out of 100?

For others:

```text

   |
   v
record failure
   |
   v
continue remaining 99
   |
   v

```

may be better.

The choice depends on whether operations are:

* independent
* destructive
* transactional
* security-sensitive
* reversible
* production-critical

# 143. Idempotency Introduction

Suppose a loop performs the same operation twice.

Will the second execution produce a safe result?

This introduces the concept of **idempotency**.

A simplified definition:

> An idempotent operation can be repeated without causing unintended additional changes after the desired state has already been reached.

Example concept:

```text
Desired directory exists
        |
        v
mkdir -p directory
        |
        v
Run again
        |
        v
Still one directory
```

Compare that with blindly appending:

```bash
printf 'entry\n' >> config.txt
```

every time the script runs.

Repeated execution may create duplicate entries.

We will revisit idempotency throughout the series.

# 145. Do Not Hide Every Error

You learned about:

```bash
/dev/null
```

in Part 4.

Do not write:

```bash
some_command > /dev/null 2>&1
```

everywhere simply because errors look untidy.

* the exit status is sufficient

# 146. Security and Loops

Loops can multiply security mistakes.

A dangerous operation performed once affects one target.

A dangerous operation inside:

```text
100-server loop
```

can affect 100 targets.

Before batch operations:

* validate targets
* use least privilege
* avoid hardcoded secrets
* protect credentials
* avoid exposing passwords in logs
* test with non-production systems
* use narrow scopes
* consider dry-run behavior
* verify each result
* define stop conditions

* secrets stored in script files
* secrets exposed in process arguments

* secrets copied into shell history

# What You Should Now Understand

After Part 7, you should understand that:

* loops repeat commands
* each execution of a loop body is an iteration
* loops eliminate repetitive manual commands
* `for` loops are useful for collections and known sequences
* loop variables change during each iteration
* `do` begins a loop body
* `done` ends a loop body
* `for` can iterate over words
* shell globbing can provide file lists
* loop variables representing filenames should normally be quoted
* unmatched globs require careful handling
* `nullglob` can make unmatched Bash globs expand to nothing
* filesystem objects should be validated before processing
* `for item in $(command)` can incorrectly split command output
* line-oriented data should normally be read with `while IFS= read -r`
* brace expansion can generate fixed numeric ranges
* C-style `for` loops support dynamic arithmetic ranges
* loop counters can track processed, successful, failed, and skipped items
* `while` repeats while a condition succeeds
* `until` repeats until a condition succeeds
* loop conditions are based on command success and exit status
* infinite loops can be intentional or accidental
* intentional polling loops usually need delays and termination controls
* `read -r` safely reads lines without interpreting backslashes
* `IFS=` helps preserve line contents
* input redirection can feed a file into a `while` loop
* `break` terminates the current loop
* `continue` skips the current iteration
* `exit` terminates the script
* nested loops process combinations of items
* nested loops can multiply the amount of work dramatically
* batch operations amplify both good automation and mistakes
* destructive operations should be previewed and narrowly scoped
* multiple servers can be processed sequentially
* multiple files can be discovered, validated, processed, and summarized
* retry loops repeat operations after appropriate transient failures
* retries need maximum attempts and usually delays
* polling repeatedly checks for a desired state
* polling should normally have a timeout or maximum number of checks
* retries and polling are related but represent different intentions
* parsing `ls` output is generally a poor file-processing strategy
* `cat file | while read` can introduce unnecessary pipeline/subshell behavior
* loop failures need deliberate policy
* scripts may continue after independent failures or stop after critical failures
* loop output should identify the item being processed
* loops should return meaningful final exit statuses
* batch automation should be designed with safety, observability, and idempotency in mind

# Knowledge Check Answers

### Answer 1

A loop repeats a block of commands so you do not have to manually write the same operation for every item.

### Answer 2

An iteration is one execution of the loop body.

### Answer 3

A `for` loop is useful when processing a collection, sequence, list of files, servers, environments, or numeric values.

### Answer 4

`do` begins the commands executed by the loop and `done` ends the loop body.

### Answer 5

It contains the current item being processed.

### Answer 6

Bash performs filename expansion and replaces the pattern with matching filenames when matches exist.

### Answer 7

Quoting preserves the filename as one argument and protects spaces and other characters from unwanted shell splitting.

### Answer 8

The unmatched pattern may remain as literal text such as `*.log`.

### Answer 9

With Bash `nullglob` enabled, an unmatched glob expands to nothing instead of remaining literal.

### Answer 10

Because unquoted command substitution is subject to word splitting, so spaces within individual lines can break one logical item into several words.

### Answer 11

Use:

```bash
while IFS= read -r line; do
    ...
done < file.txt
```

### Answer 12

`read -r` reads input without treating backslashes as escape characters.

### Answer 13

An empty `IFS` helps preserve leading and trailing whitespace rather than applying normal field-splitting behavior to the line.

### Answer 14

It redirects `servers.txt` into the standard input of the loop.

### Answer 15

`read` eventually returns a non-zero exit status, causing a normal `while read` loop to stop.

### Answer 16

It produces the fixed sequence:

```text
1 2 3 4 5
```

through brace expansion.

### Answer 17

Because arithmetic loop boundaries can come from variables and be evaluated dynamically.

### Answer 18

They are:

```text
initialization
condition
update
```

### Answer 19

A `while` loop repeats while its condition succeeds.

### Answer 20

An `until` loop repeats until its condition succeeds.

### Answer 21

`while` continues while a condition is successful. `until` continues while the condition is unsuccessful and stops when it succeeds.

### Answer 22

If nothing inside the loop changes the state required for its continuation condition to eventually stop succeeding.

### Answer 23

It creates an intentional infinite loop because `true` always returns exit status `0`.

### Answer 24

To avoid checking too rapidly, wasting CPU, flooding logs, or overwhelming the external system being checked.

### Answer 25

`break` immediately terminates the current loop.

### Answer 26

`continue` skips the remainder of the current iteration and begins the next iteration.

### Answer 27

`break` leaves the current loop but the script continues afterward. `exit` terminates the script itself.

### Answer 28

A nested loop is a loop placed inside another loop.

### Answer 29

Twenty combinations:

```text
5 × 4 = 20
```

### Answer 30

By default, `break` exits the innermost current loop.

### Answer 31

Counters allow scripts to summarize values such as processed, successful, failed, skipped, or problematic items.

### Answer 32

A retry loop repeats an operation after failure when another attempt may reasonably succeed.

### Answer 33

Without a maximum, the script may retry forever if the operation never succeeds.

### Answer 34

Some failures are permanent, such as invalid configuration or invalid credentials. Repeating the same operation does not solve the root cause.

### Answer 35

Polling means repeatedly checking the state of something until it reaches a desired state or the script reaches a termination condition.

### Answer 36

Retrying repeats an operation that failed. Polling repeatedly observes whether an external state has changed.

### Answer 37

Because `ls` output is formatted for display and filenames containing spaces or unusual characters can be parsed incorrectly.

### Answer 38

Because Bash commonly executes pipeline components in separate process/subshell contexts, so variable modifications may occur outside the parent shell.

### Answer 39

```text
continue = skip this iteration

break = stop this loop

exit = stop this script
```

### Answer 40

Because a mistake inside a loop is repeated across every matching target. A wrongly scoped destructive command can therefore affect many files, servers, or resources very quickly.

# Part 7 Summary

You have now moved from:

```text
Run a command
```

to:

```text
Make a decision
```

and now to:

```text
Repeat an operation intelligently
```

A basic `for` loop is:

```bash
for item in item1 item2 item3; do
    printf '%s\n' "$item"
done
```

A numeric loop can be:

```bash
for (( i=1; i<=10; i++ )); do
    printf '%s\n' "$i"
done
```

A condition-controlled loop can be:

```bash
while condition; do
    commands
done
```

or:

```bash
until condition; do
    commands
done
```

Files can be processed with:

```bash
for file in "$directory"/*.log; do
    [[ -f "$file" ]] || continue

    ...
done
```

Line-oriented files can be processed safely with:

```bash
while IFS= read -r line; do
    ...
done < file.txt
```

Loop execution can be controlled with:

```bash
continue
```

to skip the current item,

```bash
break
```

to leave the loop,

and:

```bash
exit
```

to terminate the script.

Retries should follow a controlled pattern:

```text
Attempt
   |
   v
Success?
 /      \
Yes      No
 |        |
Done   Attempts left?
         /      \
       Yes       No
        |         |
       Wait      Fail
        |
        v
      Retry
```

Polling should follow:

```text
Check state
    |
    v
Ready?
 /     \
Yes     No
 |       |
Done    Wait
         |
         v
      Check again
```

But both need boundaries.

The most important lesson from Part 7 is not simply:

> Bash can repeat commands.

It is:

> Repetition multiplies the effect of your automation.

That can be powerful:

```text
1 correct operation
        ×
100 valid targets
        =
useful automation
```

But it can also be dangerous:

```text
1 incorrect operation
        ×
100 production targets
        =
large incident
```

So good loop design follows:

```text
Identify targets
      |
      v
Validate scope
      |
      v
Iterate
      |
      v
Validate each item
      |
      v
Perform operation
      |
      v
Check result
      |
  +---+---+
  |       |
success failure
  |       |
  |   continue?
  |   retry?
  |   break?
  |   exit?
  |
  +-------+
      |
      v
Record result
      |
      v
Summarize
      |
      v
Return meaningful exit status
```

Keep these engineering rules:

```text
Do not repeat manually what a safe loop can automate.

Do not use a loop until you understand exactly what it will process.

Quote filename and path variables.

Do not parse arbitrary file lines with for $(cat file).

Do not parse ls output for file automation.

Validate every discovered item before acting.

Use continue to reject irrelevant items early.

Use break when further iterations are unnecessary.

Use exit when the entire script must stop.

Know what changes a while-loop condition.

Every potentially endless loop needs an exit strategy.

Retries need maximum attempts.

Polling needs a maximum wait or termination condition.

Use delays when repeatedly contacting external systems.

Do not retry permanent failures blindly.

Track successes and failures during batch operations.

Give each log message enough context to identify its target.

Understand whether partial failures should stop the batch.

Preview destructive operations before executing them.

Test batch operations against safe sample data first.

Do not use production as your first loop test.

Remember that loops multiply mistakes as efficiently as they multiply correct automation.
```
