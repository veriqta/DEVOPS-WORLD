# Part 13: Amazon S3 and Cloud Object Storage

In the previous parts, you built infrastructure around compute and networking.

You learned how an application can run on EC2 instances behind an Application Load Balancer and how an Auto Scaling Group can add, remove, and replace application servers.

The architecture looked roughly like this:

```text
Internet
   |
   v
Application Load Balancer
   |
   v
Target Group
   |
   v
Auto Scaling Group
   |
   +---- EC2
   +---- EC2
```

But applications need more than compute.

They may need somewhere to store:

* Images
* Documents
* Application assets
* Log archives
* Build artifacts
* Database backups
* Reports
* Configuration packages
* Data exports
* Media files

You could place those files on an EC2 instance.

But consider what you learned about Auto Scaling.

An EC2 instance should often be replaceable.

If an instance disappears, important application data should not disappear with it.

This introduces another type of storage:

Amazon Simple Storage Service, commonly called Amazon S3.

By the end of this part, you should understand:

* What object storage is
* How object storage differs from traditional filesystems
* What Amazon S3 is
* Buckets
* Objects
* Object keys
* Prefixes
* Regions
* S3 URLs
* Uploading objects
* Downloading objects
* AWS CLI operations
* `aws s3` commands
* `aws s3api` concepts
* Storage classes
* Versioning
* Delete markers
* Lifecycle policies
* Encryption
* IAM permissions
* Bucket policies
* Block Public Access
* Static website hosting concepts
* Pre-signed URLs
* Replication
* Logging
* Common permission errors
* How applications use S3
* How DevOps engineers use S3
* How to troubleshoot S3 access

Our application architecture can now evolve toward:

```text
                         Internet
                            |
                            v
                           ALB
                            |
                            v
                    Auto Scaling Group
                      /           \

                   EC2 A         EC2 B

          +-----------------+----------------+

       Assets             Logs           Backups
```

The EC2 instances remain replaceable.

Important objects can live independently in S3.

# 1. Start With the Storage Problem

Imagine your application allows users to upload profile pictures.

You have two application servers:

```text
              ALB
             /   \
            v     v
          EC2 A  EC2 B
```

A user uploads:

```text
profile-photo.jpg
```

The request reaches:

```text
EC2 A
```

The application stores the image locally:

```text
/var/www/uploads/profile-photo.jpg
```

Everything appears to work.

Then another request reaches:

```text
EC2 B
```

EC2 B does not have that file.

Now you have a problem.

---

# 2. Local Storage and Horizontally Scaled Applications

Suppose:

```text
EC2 A

/var/www/uploads/
    profile-photo.jpg
```

while:

```text
EC2 B

/var/www/uploads/
    empty
```

The servers no longer have identical application state.

Worse, Auto Scaling may terminate EC2 A.

If the only copy of the image was stored on EC2 A, that data may disappear with the instance.

This conflicts with the replaceable-instance model from Part 12.

Instead, the application could store the object outside the application servers:

```text
                ALB
               /   \
              v     v
           EC2 A   EC2 B
              \     /
               \   /
                v v
                 S3
                  |
                  v
        profile-photo.jpg
```

Both servers can interact with the same object store, subject to their permissions.

---

# 3. What Is Object Storage?

Before learning S3, understand object storage.

There are several major ways data can be stored.

Three important categories are:

* Block storage
* File storage
* Object storage

They solve different problems.

---

# 4. Block Storage

Block storage presents storage as blocks that an operating system can use as a disk.

An example in AWS is:

```text
Amazon EBS
```

Conceptually:

```text
EC2
 |
 v
EBS Volume
 |
 v
Filesystem
 |
 v
Files
```

The operating system may format the volume with a filesystem.

For example:

```text
ext4
```

or:

```text
XFS
```

Then applications interact with paths such as:

```text
/var/lib/app/data
```

Block storage is useful when applications need disk-like storage.

---

# 5. File Storage

File storage organizes data using files and directories.

Conceptually:

```text
/
├── home
├── var
│   └── log
└── app
    ├── config
    └── uploads
```

Applications work with familiar filesystem operations:

```text
open file
read file
write file
rename file
delete file
```

Amazon EFS is one AWS service that provides shared file storage.

---

# 6. Object Storage

Object storage uses a different model.

Instead of thinking primarily in terms of mounted disks and traditional filesystem directories, think:

```text
Bucket
   |
   +---- Object
   +---- Object
   +---- Object
```

Each object generally contains:

```text
Data
+
Metadata
+
Key
```

The key identifies the object within the bucket.

Amazon S3 is an object storage service.

---

# 7. A Simple Comparison

Think of these models like this:

```text
Block storage
     |
     v
Disk-like storage
     |
     v
Filesystem
     |
     v
Files
```

```text
File storage
     |
     v
Shared filesystem
     |
     v
Directories and files
```

```text
Object storage
     |
     v
Bucket
     |
     v
Objects identified by keys
```

Do not treat S3 as if it were simply another Linux directory.

It has a different data model and access model.

---

# 8. What Is Amazon S3?

Amazon S3 stands for:

```text
Amazon Simple Storage Service
```

It is AWS's object storage service.

S3 allows you to store objects inside buckets.

The basic relationship is:

```text
Amazon S3
   |
   v
Bucket
   |
   +---- Object A
   +---- Object B
   +---- Object C
```

For example:

```text
veriqta-production-assets
   |
   +---- logo.png
   +---- handbook.pdf
   +---- app.css
```

---

# 9. What Is a Bucket?

A bucket is a container for objects in Amazon S3.

You do not upload an object into "S3" without a bucket.

You create a bucket and then store objects in it.

Example:

```text
veriqta-app-assets
```

Inside:

```text
veriqta-app-assets
   |
   +---- logo.png
   +---- banner.jpg
   +---- handbook.pdf
```

The bucket provides an administrative boundary for things such as:

* Region
* Access policies
* Versioning
* Lifecycle configuration
* Logging configuration
* Encryption settings
* Replication configuration

---

# 10. Bucket Naming

General purpose S3 bucket names must follow AWS naming rules.

For example, names typically use:

* Lowercase letters
* Numbers
* Periods
* Hyphens

A valid-looking example:

```text
veriqta-production-assets
```

An invalid example:

```text
VERIQTA_Production_Assets
```

Uppercase letters and underscores are not allowed in general purpose bucket names.

---

# 11. Bucket Names Must Be Unique

A beginner may assume:

```text
my-backups
```

only needs to be unique inside their AWS account.

That is incorrect for general purpose S3 buckets.

Bucket names must be unique across the relevant AWS partition.

For example, the commercial AWS partition includes Regions such as:

```text
us-east-1
us-west-2
eu-west-1
```

If another AWS customer already owns the bucket name you want in that partition, you cannot create another general purpose bucket with the same name.

This is why real bucket names often include additional organizational information.

For example:

```text
veriqta-prod-assets-2026
```

Do not blindly copy that exact naming scheme.

Create a consistent naming convention appropriate to your organization.

---

# 12. Bucket Names Can Appear in URLs

Bucket names may appear in S3 endpoints and URLs.

For example, a virtual-hosted-style S3 URL can conceptually look like:

```text
https://BUCKET.s3.REGION.amazonaws.com/OBJECT-KEY
```

Because bucket names can appear in DNS-style names, naming rules matter.

Avoid placing confidential information in bucket names.

A bucket name itself should not contain secrets.

---

# 13. What Is an Object?

An object is the actual item stored in S3.

Examples:

```text
logo.png
```

```text
application.zip
```

```text
backup.sql.gz
```

```text
report.pdf
```

```text
access-log-2026-09-06.json
```

An S3 object consists of the object's data and associated metadata, and it is identified within a bucket by its key.

---

# 14. What Is an Object Key?

The object key is the name that uniquely identifies an object within a bucket.

Suppose the bucket is:

```text
veriqta-assets
```

and the key is:

```text
images/logo.png
```

Together they identify:

```text
s3://veriqta-assets/images/logo.png
```

In this representation:

```text
veriqta-assets
```

is the bucket.

And:

```text
images/logo.png
```

is the key.

---

# 15. Keys Are More Than File Names

A key can look like a filesystem path:

```text
production/logs/app.log
```

But S3's data model is not a normal hierarchical filesystem.

The entire value:

```text
production/logs/app.log
```

is the object's key.

This distinction matters.

---

# 16. S3 Does Not Really Need Traditional Folders

In the S3 console, you may see:

```text
images/
logs/
backups/
artifacts/
```

These look like directories.

But S3 uses a flat object-key namespace within a bucket.

The console presents folder-like organization using key prefixes.

For example:

```text
images/logo.png
images/banner.jpg
images/team/ann.jpg
```

The keys are:

```text
images/logo.png
```

```text
images/banner.jpg
```

```text
images/team/ann.jpg
```

The apparent folder structure comes from the key names.

---

# 17. What Is a Prefix?

A prefix is the beginning portion of an object key used to group or filter objects.

Consider:

```text
logs/2026/09/app.log
logs/2026/09/nginx.log
logs/2026/08/app.log
images/logo.png
```

A useful prefix is:

```text
logs/
```

Another is:

```text
logs/2026/
```

Another:

```text
logs/2026/09/
```

Applications, lifecycle rules, access patterns, and listing operations can make use of prefixes.

---

# 18. Designing Useful Object Keys

Instead of dumping everything into:

```text
veriqta-data
```

with keys such as:

```text
file1
file2
file3
```

use meaningful keys.

Example:

```text
assets/images/logo.png
assets/css/application.css
logs/web/2026/09/06/app.log
backups/database/2026/09/06/database.sql.gz
artifacts/releases/v1.2.0/application.zip
```

This makes objects easier to:

* Identify
* Search
* Filter
* Manage
* Apply lifecycle rules to
* Apply certain access controls to

---

# 19. Buckets and Regions

When creating a bucket, you select an AWS Region.

Example:

```text
us-east-1
```

or:

```text
eu-west-1
```

The bucket's Region matters for architecture.

Consider:

* Application location
* Latency
* Compliance requirements
* Data residency requirements
* Replication design
* Cost
* Other AWS services interacting with the bucket

Do not choose a Region randomly.

---

# 20. Region Example

Suppose your application runs in:

```text
us-east-1
```

and your S3 bucket is also:

```text
us-east-1
```

Conceptually:

```text
AWS Region: us-east-1

EC2
 |
 v
S3 bucket
```

This may be a natural design when the application's data should live in the same Region.

But some architectures intentionally use multiple Regions for specific resilience, compliance, or distribution requirements.

Region choice should come from architecture requirements.

# 25. `aws s3` vs `aws s3api`

The AWS CLI provides two important ways to interact with S3.

High-level commands:

```bash
aws s3 ...
```

Examples:

```bash
aws s3 cp
aws s3 mv
aws s3 sync
aws s3 ls
aws s3 rm
```

These are convenient for common file-style operations.

There is also:

```bash
aws s3api ...
```

This maps more directly to S3 API operations and exposes lower-level configuration and control.

Example:

```bash
aws s3api get-bucket-versioning --bucket BUCKET_NAME
```

As a beginner, you should understand both exist.

Use the high-level `aws s3` interface for common transfers and `aws s3api` when you need more direct API-level operations.

# 33. Synchronizing Directories

Another important command is:

```bash
aws s3 sync
```

Example:

```bash
aws s3 sync project/ s3://veriqta-s3-lab-example/project/
```

`sync` compares source and destination and copies files required to make the destination correspond to the source according to the command's synchronization rules.

This is useful for:

* Static assets
* Build output
* Backup workflows
* Artifact directories

But understand the options before using it in important environments.

---

# 34. Be Careful With `--delete`

A command such as:

```bash
aws s3 sync project/ s3://BUCKET/project/ --delete
```

can delete destination objects that do not exist in the source.

Do not blindly copy this command.

Before destructive synchronization:

* Confirm the bucket.
* Confirm the prefix.
* Confirm the source directory.
* Verify your AWS account.
* Understand versioning status.
* Consider using `--dryrun`.

For example:

```bash
aws s3 sync project/ s3://BUCKET/project/ --delete --dryrun
```

Review what would happen before running the destructive operation without `--dryrun`.

---

# 35. Deleting an Object

Command:

```bash
aws s3 rm s3://veriqta-s3-lab-example/configs/app.txt
```

This removes the specified current object according to the bucket's versioning state.

Be careful.

Deletion behavior differs when versioning is enabled.

We will examine that shortly.

# 36. S3 Storage Classes

Not every object has the same access pattern.

Consider:

```text
Application logo
```

It may be accessed frequently.

A compliance archive may almost never be accessed.

A backup may be needed only during disaster recovery.

Keeping every object in the same storage class may not be appropriate.

S3 provides different storage classes for different access patterns.

---

# 37. Important Storage Classes

Major S3 storage classes include:

* S3 Standard
* S3 Intelligent-Tiering
* S3 Standard-Infrequent Access
* S3 One Zone-Infrequent Access
* S3 Glacier Instant Retrieval
* S3 Glacier Flexible Retrieval
* S3 Glacier Deep Archive

There are also specialized S3 storage options and classes for particular workloads.

For this beginner foundation, focus on understanding the access pattern behind each class.

---

# 38. S3 Standard

S3 Standard is designed for frequently accessed data requiring low-latency, high-throughput access and resilience across multiple Availability Zones.

Examples:

```text
Frequently accessed application assets
```

```text
Active application data
```

```text
Frequently downloaded documents
```

For many beginner projects, Standard is the simplest starting point.

---

# 39. S3 Intelligent-Tiering

S3 Intelligent-Tiering is designed for data whose access patterns are unknown or change over time.

It can automatically move objects between access tiers based on usage.

This can be useful when you cannot confidently predict:

```text
Which objects will stay hot?
```

and:

```text
Which objects will become cold?
```

Do not interpret Intelligent-Tiering as:

```text
Always cheapest.
```

Understand its tiering behavior and pricing before choosing it.

---

# 40. S3 Standard-IA

`IA` means:

```text
Infrequent Access
```

S3 Standard-IA is intended for objects that are accessed less frequently but still need rapid access when requested.

Possible examples:

* Older backups
* Disaster recovery files
* Less frequently accessed content

Storage may cost less than Standard, but retrieval and minimum-storage-duration considerations matter.

Always evaluate the complete access pattern.

---

# 41. S3 One Zone-IA

S3 One Zone-IA stores data in a single Availability Zone rather than using the multi-AZ resilience model of classes such as S3 Standard-IA.

That changes the durability and resilience characteristics of the storage design.

It can make sense for certain recreatable or secondary data.

Do not use it simply because it appears cheaper.

Ask:

```text
Can this data be recreated if the Availability Zone is lost?
```

---

# 42. S3 Glacier Storage Classes

Glacier storage classes are designed for archival use cases.

They include:

```text
S3 Glacier Instant Retrieval
```

```text
S3 Glacier Flexible Retrieval
```

```text
S3 Glacier Deep Archive
```

The major concept is:

```text
Lower-cost archival storage
```

in exchange for different access and retrieval characteristics depending on the class.

Do not place an object into an archival class without understanding how quickly you may need it back and what retrieval will cost.

---

# 43. Storage Class Reasoning

Ask:

```text
How frequently is this object accessed?
```

```text
How quickly must it be retrievable?
```

```text
Can the object be recreated?
```

```text
How long will we keep it?
```

```text
What retrieval charges apply?
```

```text
What minimum storage duration applies?
```

Then choose the class.

Do not choose based only on the lowest storage price displayed.

---

# 44. Versioning

Imagine you have:

```text
configs/application.json
```

Someone accidentally overwrites it with a broken version.

Without version history, recovering the previous content may be difficult unless you have another backup.

S3 Versioning helps preserve multiple versions of an object.

---

# 45. How Versioning Works

Suppose you upload:

```text
config.json
```

Version 1:

```json
{
  "environment": "production",
  "debug": false
}
```

Later you upload another object using the same key:

```text
config.json
```

Version 2:

```json
{
  "environment": "production",
  "debug": true
}
```

With versioning enabled, S3 can retain both object versions.

Conceptually:

```text
config.json

Version A
   |
   +---- debug=false

Version B
   |
   +---- debug=true
```

The newer version becomes the current version.

---

# 46. Why Versioning Matters

Versioning can help protect against:

* Accidental overwrites
* Certain accidental deletions
* Application mistakes
* Human mistakes

But versioning also increases stored data.

If you continually modify large objects, older versions consume storage.

This is why versioning and lifecycle policies often work together.

---

# 47. Enable Versioning With the CLI

Example:

```bash
aws s3api put-bucket-versioning \
  --bucket veriqta-s3-lab-example \
  --versioning-configuration Status=Enabled
```

Check:

```bash
aws s3api get-bucket-versioning \
  --bucket veriqta-s3-lab-example
```

Expected:

```json
{
    "Status": "Enabled"
}
```

---

# 48. Versioning States

A bucket can have versioning:

```text
Unversioned
```

then:

```text
Enabled
```

and later:

```text
Suspended
```

Suspending versioning does not simply erase the versions that already exist.

This is important.

Do not assume:

```text
Suspend versioning
=
delete old versions
```

It does not.

---

# 49. Delete Markers

Versioned buckets introduce an important concept:

```text
Delete marker
```

If you perform a normal delete operation on an object in a versioning-enabled bucket, S3 typically inserts a delete marker as the current version rather than permanently removing every historical version.

Conceptually:

```text
report.pdf

Version 1
Version 2
Delete Marker <- current
```

A normal request for:

```text
report.pdf
```

now behaves as though the object is deleted.

But previous versions may still exist.

---

# 50. Recovering From an Accidental Delete

If a delete marker hides the object, recovery can involve removing the delete marker so a previous version becomes current again.

This is one reason versioning can be valuable.

However, versioning is not a substitute for every backup, retention, or disaster-recovery requirement.

Design those separately.

---

# 51. Lifecycle Policies

Over time, a bucket can accumulate:

```text
Millions of logs
Old backups
Old object versions
Temporary exports
Expired artifacts
```

You may not want to keep all of them in expensive active storage forever.

Lifecycle rules automate object transitions and expiration.

---

# 52. Lifecycle Transition Example

Suppose logs are created daily.

You might design:

```text
Day 0
S3 Standard
```

then:

```text
After a defined period
Lower-cost storage class
```

then eventually:

```text
Archive
```

or:

```text
Expire
```

depending on your requirements.

The actual transition dates must satisfy S3 lifecycle and storage-class rules.

---

# 53. Lifecycle Expiration

A lifecycle rule can automatically expire objects after a defined period.

Example concept:

```text
Temporary exports
       |
       v
Keep 30 days
       |
       v
Expire
```

This is useful for data that has a defined retention period.

But be careful.

Automatic expiration is still deletion behavior.

Do not configure it without understanding the business, compliance, and recovery requirements.

---

# 54. Lifecycle and Versioning

Lifecycle rules can also manage noncurrent object versions.

For example:

```text
Current version
   |
   v
Keep available

Old versions
   |
   v
Transition or expire later
```

This prevents version history from growing forever when long-term retention is unnecessary.

---

# 55. Lifecycle Rules Can Use Prefixes

Suppose:

```text
logs/
```

contains logs.

```text
assets/
```

contains active website images.

```text
backups/
```

contains backups.

You may want different policies.

For example:

```text
logs/
→ archive after a defined period
```

```text
assets/
→ remain readily accessible
```

```text
backups/
→ separate retention policy
```

Good key design makes lifecycle management easier.

---

# 56. Encryption

Encryption protects data by transforming it so it cannot be interpreted without the appropriate cryptographic key and authorization.

For S3, think about two broad states:

```text
Data at rest
```

and:

```text
Data in transit
```

---

# 57. Encryption in Transit

When applications communicate with S3, use secure HTTPS endpoints.

Conceptually:

```text
Application
    |
    | HTTPS
    v
   S3
```

TLS protects the connection while data travels between the client and S3.

---

# 58. Encryption at Rest

Amazon S3 automatically encrypts new object uploads at rest.

S3 provides multiple server-side encryption choices.

Important options include:

* SSE-S3
* SSE-KMS
* DSSE-KMS
* SSE-C

There is also client-side encryption, where data is encrypted before it is sent to S3.

For beginner AWS infrastructure work, focus first on SSE-S3 and SSE-KMS.

---

# 59. SSE-S3

SSE-S3 means server-side encryption using keys managed by Amazon S3.

Conceptually:

```text
Object uploaded
      |
      v
S3 encrypts object
      |
      v
Encrypted data at rest
```

AWS manages the encryption keys for this option.

This provides a simple encryption model without requiring you to manage a KMS key policy.

---

# 60. SSE-KMS

SSE-KMS uses AWS Key Management Service keys.

Conceptually:

```text
Application
    |
    v
S3
    |
    v
AWS KMS
    |
    v
Encryption key controls
```

SSE-KMS provides additional key-management and auditing capabilities.

But it also introduces additional permission requirements and potentially additional cost.

---

# 61. S3 Permission Plus KMS Permission

This is a common troubleshooting issue.

Suppose an IAM role has:

```text
s3:GetObject
```

for an object.

But that object is encrypted with a customer-managed KMS key and the role lacks the required KMS permissions.

The S3 permission alone may not be enough.

Conceptually:

```text
Can access S3 object?
        |
       Yes
        |
        v
Can use required KMS key?
        |
       No
        |
        v
Access fails
```

When troubleshooting encrypted S3 access, investigate both layers.

---

# 62. IAM Access

S3 does not decide access from one policy alone.

Permissions can involve several mechanisms.

Important ones include:

* IAM identity policies
* Bucket policies
* S3 Block Public Access
* Access control lists in legacy or specific scenarios
* AWS Organizations policies
* VPC endpoint policies
* KMS key policies when SSE-KMS is involved

A beginner must learn to think in layers.

---

# 63. Identity-Based IAM Policies

An IAM policy can grant an identity permission to perform S3 actions.

For example:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::veriqta-app-assets/*"
    }
  ]
}
```

This allows `s3:GetObject` against objects covered by that resource ARN, assuming no other applicable control denies access.

---

# 64. Understand the Resource ARN

This:

```text
arn:aws:s3:::veriqta-app-assets/*
```

means objects inside:

```text
veriqta-app-assets
```

The:

```text
/*
```

portion represents object resources beneath the bucket.

But the bucket itself has a different ARN:

```text
arn:aws:s3:::veriqta-app-assets
```

This distinction matters.

---

# 65. Bucket-Level vs Object-Level Permissions

Consider:

```text
s3:ListBucket
```

This is a bucket-level action.

Its resource is typically:

```text
arn:aws:s3:::veriqta-app-assets
```

But:

```text
s3:GetObject
```

is an object-level action.

Its resource can be:

```text
arn:aws:s3:::veriqta-app-assets/*
```

A policy may therefore contain both.

Example:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::veriqta-app-assets"
    },
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::veriqta-app-assets/*"
    }
  ]
}
```

---

# 66. Why `ListBucket` and `GetObject` Are Different

A user might be able to retrieve a known object:

```text
reports/report.pdf
```

without necessarily having permission to list every key in the bucket.

Similarly, listing the bucket does not automatically mean the user can download every object.

Different operations require different permissions.

This distinction explains many confusing beginner errors.

---

# 67. Bucket Policies

A bucket policy is a resource-based policy attached to the bucket.

It can specify:

* Who may access the bucket
* Which actions they may perform
* Which resources they may access
* Conditions that must be true

Basic structure:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {},
      "Action": [],
      "Resource": []
    }
  ]
}
```

Do not copy incomplete examples into production.

Understand each element.

---

# 68. Policy Components

Important fields include:

```text
Effect
```

Usually:

```text
Allow
```

or:

```text
Deny
```

```text
Principal
```

Who the statement applies to.

```text
Action
```

What operations are involved.

```text
Resource
```

Which AWS resources are involved.

```text
Condition
```

Optional conditions controlling when the statement applies.

---

# 69. IAM Policy vs Bucket Policy

A simplified mental model:

```text
IAM policy
    |
    v
Attached to identity
```

```text
Bucket policy
    |
    v
Attached to S3 bucket
```

Both can participate in authorization.

Do not ask only:

```text
Does my IAM role allow this?
```

Also ask:

```text
Is there a bucket policy affecting access?
```

And:

```text
Is there an explicit deny somewhere?
```

---

# 70. Explicit Deny

AWS authorization follows an important principle:

```text
Explicit Deny
```

can override an applicable allow.

Suppose:

```text
IAM policy:
Allow GetObject
```

but another applicable policy says:

```text
Deny GetObject
```

for the request.

The request is denied.

When troubleshooting permissions, finding one `Allow` does not prove access should succeed.

---

# 71. Least Privilege

Do not give an application:

```json
{
  "Effect": "Allow",
  "Action": "s3:*",
  "Resource": "*"
}
```

simply because it makes the error disappear.

Ask what the application actually needs.

For example:

```text
Read application assets?
```

Then perhaps:

```text
s3:GetObject
```

for a specific bucket or prefix is enough.

If it needs to upload logs:

```text
s3:PutObject
```

may be required for a particular prefix.

Grant the minimum permissions required.

---

# 72. Prefix-Based Access

Suppose one bucket contains:

```text
assets/
logs/
backups/
```

Your application may need:

```text
Read assets
```

and:

```text
Write logs
```

but not:

```text
Delete backups
```

Permissions can be scoped accordingly.

Conceptually:

```text
EC2 Application Role
   |
   +---- GetObject → assets/*
   |
   +---- PutObject → logs/*
   |
   X---- DeleteObject → backups/*
```

This is much safer than broad bucket-wide administrative access.

---

# 73. EC2 Should Use an IAM Role

From Part 12, remember:

Do not place long-lived AWS access keys inside your application configuration when an IAM role can be used.

Use:

```text
EC2
 |
 v
IAM Instance Profile / Role
 |
 v
Temporary AWS credentials
 |
 v
S3
```

The AWS SDK or CLI on the instance can use the role's temporary credentials.

---

# 74. Block Public Access

S3 Block Public Access is a major safety control.

It is designed to help prevent S3 buckets and objects from becoming publicly accessible through public policies or ACL-based mechanisms.

AWS provides Block Public Access controls at different levels, including account and bucket levels.

For most application storage, backups, logs, and artifacts:

```text
Keep public access blocked.
```

---

# 75. Private Should Be the Default Mental Model

For:

```text
Backups
Logs
Build artifacts
Internal assets
Customer uploads
Application data
```

your default thought should be:

```text
Private
```

Then explicitly design how authorized users or services access the data.

Do not make a bucket public because permissions are difficult to troubleshoot.

---

# 76. Why Public Buckets Can Be Dangerous

A public bucket or publicly readable objects may expose:

* Customer information
* Internal documents
* Logs
* Backups
* Source artifacts
* Configuration
* Sensitive exports

Even if your current test object is harmless, overly broad public configuration can later expose objects uploaded into the same location.

Treat public access as an architecture decision, not a debugging shortcut.

Examples:

```text

```

S3 does not run server-side application runtimes such as:

```text

Node.js backend
Java application server
```

A static website might contain:

```text
index.html
styles.css
app.js
logo.png
```

# 78. Static Website Architecture

Simple concept:

```text
Browser
   |
   v
S3 Static Website
   |
   +---- index.html
   +---- styles.css
   +---- app.js
   +---- images/
```

# 79. Static Website Does Not Mean Public Bucket Is Always Required

A common beginner tutorial says:

```text
Make bucket public.
Enable website hosting.
Done.
```

That is an oversimplification.

There are multiple architectures for delivering static content.

For production systems, consider:

* HTTPS
* CloudFront
* Private origins
* Access controls
* Caching
* Custom domains
* Security headers

Do not automatically disable Block Public Access just because you want to serve static files.

# 80. What Is a Pre-Signed URL?

Suppose a bucket is private.

You want a user to download:

```text
reports/customer-123/report.pdf
```

You do not want to make the whole bucket public.

A pre-signed URL provides time-limited access to a specific S3 operation using the permissions of the principal that generated it.

Conceptually:

```text
Private S3 Object
       |
       v
Application generates
pre-signed URL
       |
       v
User receives temporary URL
       |
       v
User accesses object
```

---

# 81. Why Pre-Signed URLs Are Useful

Imagine a private application.

User clicks:

```text
Download invoice
```

Instead of making:

```text
invoices/
```

public, the application generates a temporary URL for the authorized invoice.

That URL expires.

This is much better than exposing the entire bucket.

---

# 82. Generate a Pre-Signed Download URL With AWS CLI

Example:

```bash
aws s3 presign \
  s3://veriqta-s3-lab-example/reports/report.pdf \
  --expires-in 300
```

`300` means:

```text
300 seconds
```

which is:

```text
5 minutes
```

The command returns a URL.

Someone with the valid URL can use it until it expires, subject to the underlying signing credentials and request conditions.

Treat pre-signed URLs as temporary credentials.

Do not post sensitive pre-signed URLs publicly.

---

# 83. Pre-Signed Uploads

Applications can also generate pre-signed requests that allow clients to upload objects directly to S3.

Architecture:

```text
User
 |
 v
Application
 |
 | authenticate user
 | authorize upload
 | generate pre-signed request
 v
User
 |
 | uploads directly
 v
S3
```

This can reduce the need for large uploads to pass through the application servers.

But the application must carefully control:

* Key
* Expiration
* Allowed operation
* File restrictions where applicable
* Authorization

---

# 84. Pre-Signed Does Not Mean Public

This is important.

A private object can remain private.

The pre-signed URL grants temporary access to a particular request.

Think:

```text
Private object
+
Temporary signed authorization
```

not:

```text
Public object
```

# 85. Replication

S3 replication can automatically copy objects from one bucket to another according to replication rules.

Two major concepts are:

```text
Same-Region Replication
```

and:

```text
Cross-Region Replication
```

Often abbreviated:

```text
SRR
```

and:

```text
CRR
```

---

# 86. Same-Region Replication

Conceptually:

```text
Bucket A
Region X
   |
   v
Bucket B
Region X
```

Possible reasons include:

* Separate security boundaries
* Separate accounts
* Log aggregation
* Compliance workflows
* Data ownership requirements

---

# 87. Cross-Region Replication

Conceptually:

```text
Region A
Bucket A
   |
   v
Replication
   |
   v
Region B
Bucket B
```

Possible reasons include:

* Geographic data requirements
* Disaster-recovery architecture
* Compliance requirements
* Regional copies of data

Replication is not simply:

```text
Turn it on and every disaster-recovery problem disappears.
```

You must understand what gets replicated, replication timing, versioning requirements, delete behavior, permissions, encryption, and costs.

---

# 88. Versioning and Replication

S3 replication configurations rely on versioning.

For replication, versioning must be enabled on the source and destination buckets as required by S3 replication configuration.

This makes sense because replication needs to understand object versions and changes.

---

# 89. Replication Is Not the Same as Backup

This is an important engineering distinction.

Suppose a bad object is written to the source.

Replication may copy the bad object.

Suppose an application corrupts data.

Replication may reproduce the change depending on the configuration.

Therefore:

```text
Replication
!=
complete backup strategy
```

A backup strategy should consider:

* Recovery points
* Retention
* Immutability requirements
* Versioning
* Access separation
* Restore procedures
* Testing

# 99. S3 Object Lock Introduction

For workloads requiring protection against object deletion or modification for a retention period, S3 provides Object Lock.

* Compliance
* Backup protection
* Ransomware-resilient designs
* Records retention

# 100. Common S3 Error: AccessDenied

One of the most common S3 errors is:

```text
AccessDenied
```

Do not immediately respond by making the bucket public.

Instead investigate.

Ask:

1. Who am I?
2. What action am I trying to perform?
3. Which bucket or object?
4. Does my IAM policy allow it?
5. Does the bucket policy allow or deny it?
6. Is there an explicit deny?
7. Is Block Public Access relevant?
8. Is KMS involved?
9. Is a VPC endpoint policy involved?
10. Is an Organizations policy involved?

---

# 101. Start by Identifying the Caller

Run:

```bash
aws sts get-caller-identity
```

You may discover:

```text
I thought I was using the admin profile.
```

but actually:

```text
I am using a restricted role.
```

Always verify identity before debugging complex permissions.

---

# 102. Check the Exact Operation

Suppose this fails:

```bash
aws s3 ls s3://veriqta-app-assets/
```

The problem may involve:

```text
s3:ListBucket
```

But this:

```bash
aws s3 cp s3://veriqta-app-assets/images/logo.png .
```

requires object-read permissions such as:

```text
s3:GetObject
```

These are different actions.

Troubleshoot the operation that actually failed.

---

# 103. Common Error: Wrong Bucket ARN

Incorrect policy:

```text
Resource:
arn:aws:s3:::veriqta-app-assets/*
```

for an operation requiring access to the bucket resource itself.

For bucket-level actions such as `ListBucket`, you generally need the bucket ARN:

```text
arn:aws:s3:::veriqta-app-assets
```

For object actions:

```text
arn:aws:s3:::veriqta-app-assets/*
```

Understanding resource types prevents many IAM mistakes.

---

# 104. Common Error: Wrong Prefix

Suppose policy allows:

```text
arn:aws:s3:::veriqta-app-assets/images/*
```

But the application requests:

```text
documents/report.pdf
```

The policy does not cover that object.

Compare the exact key against the policy resource.

---

# 105. Common Error: KMS Access

Symptom:

```text
AccessDenied
```

even though S3 permissions appear correct.

Ask:

```text
Is the object encrypted with SSE-KMS?
```

If yes:

```text
Does this identity have the necessary KMS permissions?
```

Also examine the KMS key policy and other applicable controls.

Do not troubleshoot S3 and KMS as though they are unrelated.

---

# 106. Common Error: Wrong Region

You may interact with a bucket while assuming it is in another Region.

Check:

```bash
aws s3api get-bucket-location \
  --bucket veriqta-s3-lab-example
```

Be aware that the response representation for some Regions, especially the historical `us-east-1` case, can be surprising to beginners.

The important lesson is:

```text
Know the bucket's actual Region.
```

---

# 107. Common Error: Object Does Not Exist

Suppose you request:

```text
Images/logo.png
```

but the real key is:

```text
images/logo.png
```

Object keys are case-sensitive.

These are different:

```text
Logo.png
logo.png
LOGO.png
```

Do not assume S3 will correct capitalization.

---

# 108. Common Error: "Folder" Confusion

You think the object is:

```text
logs/app.log
```

but the actual key is:

```text
production/logs/app.log
```

Use:

```bash
aws s3 ls s3://BUCKET/ --recursive
```

to inspect actual keys when appropriate.

Do not reason only from what you remember seeing in the console.

---

# 109. Common Error: Public Access Blocked

Suppose you intentionally attempt to configure public access for a static website lab.

Your bucket policy appears to permit public reads, but access still fails.

Block Public Access may prevent that public configuration.

This is a security feature.

Do not disable it until you understand:

* Why public access is required
* Which Block Public Access setting is preventing it
* What objects would become exposed
* Whether a private S3 plus CloudFront architecture would be better

---

# 110. Common Error: Pre-Signed URL Expired

A pre-signed URL works initially.

Later:

```text
AccessDenied
```

or another authorization-related failure appears.

Check:

```text
Has the URL expired?
```

Also consider:

* Whether the signing credentials are still valid
* Whether permissions changed
* Whether the object still exists
* Whether the request was modified

Pre-signed URLs are deliberately temporary.

---

# 111. Common Error: Application Works Locally but Not on EC2

Your laptop can access S3.

Your EC2 application cannot.

Why?

Your laptop and EC2 instance may use different AWS identities.

Laptop:

```text
IAM user / SSO role / local profile
```

EC2:

```text
IAM instance role
```

The fact that your laptop works proves almost nothing about the EC2 role's authorization.

Check the EC2 role.

# 112. S3 and Private EC2 Instances

A private EC2 instance may need S3 access.

```text

    |
    v
NAT Gateway
    |
    v
S3 public service endpoint
```

For S3, a gateway VPC endpoint can allow resources in a VPC to access S3 without requiring that S3 traffic to traverse an Internet Gateway or NAT Gateway.


# 113. Why an S3 Gateway Endpoint Matters

Recall Part 8.

If large amounts of private-subnet traffic are going to S3 through NAT, a properly designed S3 gateway endpoint can provide architectural and cost benefits.

* Route tables
* Endpoint policies
* IAM policies
* Bucket policies
* DNS and endpoint behavior
* Which traffic the endpoint supports

# 119. Object Size and Multipart Uploads

Large objects should not always be uploaded as one simple request.

S3 supports multipart upload.

Conceptually:

```text
Large file
   |
   +---- Part 1
   +---- Part 2
   +---- Part 3
   +---- Part 4
          |
          v
         S3
          |
          v
     Complete object
```

Benefits include more efficient handling of large uploads and the ability to retry individual failed parts rather than the entire object.

AWS CLI high-level commands can manage multipart behavior automatically for sufficiently large transfers.

---

# 120. Incomplete Multipart Uploads

A multipart upload can be started but never completed.

Those uploaded parts can continue consuming storage.

Lifecycle rules can be configured to abort incomplete multipart uploads after a chosen number of days.

This is an important housekeeping practice for buckets that receive large uploads.

---

# 121. Data Integrity

S3 supports checksums and integrity mechanisms that help validate objects during upload and download workflows.

In production pipelines, consider:

```text
Did we upload the complete artifact?
```

not merely:

```text
Did the command return?
```

For important artifacts and backups, integrity validation should be part of the workflow.

---

# 122. S3 Consistency

Amazon S3 provides strong read-after-write consistency for object PUT and DELETE operations.

This means after a successful write, subsequent reads and listings can reflect the latest state without the old eventual-consistency assumptions found in older S3 tutorials.

Be careful when reading outdated tutorials that still teach old S3 consistency behavior.

---

# 123. S3 Durability and Availability

S3 is designed for extremely high durability.

AWS describes S3 as designed for:

```text
99.999999999% durability
```

for objects across multiple Availability Zones for its regional storage classes that use multi-AZ storage.

Do not confuse:

```text
Durability
```

with:

```text
Availability
```

Durability asks:

```text
Will my stored data remain intact?
```

Availability asks:

```text
Can I access the service/data when needed?
```

They are related but different concepts.

---

# 124. Durability Does Not Eliminate Human Error

Even extremely durable storage cannot automatically protect you from every logical mistake.

For example:

```text
Administrator intentionally deletes object
```

or:

```text
Application overwrites object with bad data
```

Durability alone does not restore the desired previous state.

That is why you may also need:

* Versioning
* Backup strategy
* Replication
* Object Lock
* Least privilege
* Lifecycle management

depending on the workload.

---

# 125. S3 Is Not a Database

Do not use S3 as though it were a relational database.

S3 stores objects.

It does not provide relational database behavior such as:

```text
SQL joins
Foreign keys
Relational transactions
Traditional row-level queries
```

If your application needs relational data, a service such as RDS may be more appropriate.

You will cover RDS separately.

---

# 126. S3 Is Not EBS

Do not confuse:

```text
S3
```

with:

```text
EBS
```

EBS:

```text
Block storage
```

S3:

```text
Object storage
```

An EC2 operating system can mount and use an EBS volume as disk storage.

S3 is normally accessed through APIs, SDKs, CLI tools, or purpose-built integrations.

Choose storage according to application requirements.

---

# 127. S3 Is Not EFS

Do not confuse:

```text
S3
```

with:

```text
EFS
```

EFS provides shared filesystem semantics.

S3 provides object storage semantics.

Ask:

```text
Does my application require filesystem operations?
```

or:

```text
Can my application work with objects through an API?
```

That distinction influences the correct service.

The reverse can also happen.

You may have:

```text

```

```text

```

# 153. Problem: Upload Fails

Check whether the caller has:

```text
s3:PutObject
```

for the destination object ARN.

Also check:

* Bucket policy
* Explicit deny
* Required encryption headers or policy conditions
* KMS permissions
* Object ownership requirements
* Endpoint policies
* Organization controls

Do not solve upload errors by granting full S3 access.

---

# 154. Problem: Delete Fails

Check:

```text
s3:DeleteObject
```

and the exact object resource.

For version-specific deletion, additional version-related actions may be relevant.

Also consider retention controls such as Object Lock.

A deletion failure can be intentional protection.

---

# 155. Problem: Lifecycle Rule Is Not Doing What You Expected

Check:

* Rule enabled?
* Correct prefix/filter?
* Correct object age?
* Current vs noncurrent version?
* Minimum storage duration?
* Transition supported?
* Object size filters?
* Versioning state?
* Lifecycle timing expectations?

Lifecycle actions are asynchronous.

Do not assume a rule runs at exactly midnight at the instant an object reaches the configured age.

---

# 156. Problem: Replication Does Not Work

Check:

* Versioning enabled?
* Destination bucket correct?
* Replication IAM role correct?
* Source rule scope correct?
* Encryption configuration?
* KMS permissions?
* Destination policy?
* Object eligible for replication?
* Replication status?

Do not assume replication failure is a network routing issue.

S3 replication is service-managed.

# 183. Final Mental Model

Do not memorize:

```text
S3 = AWS file storage
```

That explanation is too shallow.

Think:

```text
                         AMAZON S3
                              |
                              v
                            BUCKET
                              |
          +-------------------+-------------------+
          |                   |                   |
          v                   v                   v
       OBJECT              OBJECT              OBJECT
          |                   |                   |
          v                   v                   v
         KEY                 KEY                 KEY
          |                   |                   |
          v                   v                   v
       METADATA            METADATA            METADATA
```

Organization happens through object keys and prefixes:

```text
Bucket
 |
 +---- assets/images/logo.png
 |
 +---- assets/css/app.css
 |
 +---- logs/2026/09/06/app.log
 |
 +---- artifacts/releases/2.4.0/app.zip
 |
 +---- backups/database/2026/09/06.sql.gz
```

Storage management adds another layer:

```text
Object
   |
   +---- Storage Class
   |
   +---- Versioning
   |
   +---- Lifecycle
   |
   +---- Encryption
   |
   +---- Replication
```

Security adds another:

```text
Request
   |
   v
Identity
   |
   v
IAM Policy
   |
   v
Bucket Policy
   |
   v
Block Public Access
   |
   v
Other applicable controls
   |
   v
KMS authorization if required
   |
   v
Allow or Deny
```

Applications interact with S3 like this:

```text
EC2 / ECS / EKS
       |
       v
     IAM Role
       |
       v
   AWS SDK / API
       |
       v
       S3
```

Users can interact through controlled application flows:

```text
User
 |
 v
Application
 |
 | authenticate
 | authorize
 v
Pre-Signed URL
 |
 v
Private S3 Object
```

Your production application can therefore evolve from:

```text
Internet
   |
   v
ALB
   |
   v
Auto Scaling Group
   |
   +---- EC2
   +---- EC2
```

into:

```text
                            Internet
                               |
                               v
                              ALB
                               |
                               v
                       Auto Scaling Group
                        /              \
                       v                v
                     EC2 A            EC2 B
                       \                /
                        \              /
                         +------------+
                               |
                               v
                              S3
              +----------------+----------------+
              |                |                |
              v                v                v
            Assets           Logs           Artifacts
              |                                 |
              v                                 v
           Uploads                           Backups
```

The important architectural lesson is not merely how to run:

```bash
aws s3 cp
```

It is understanding why the application should use object storage in the first place.

EC2 provides compute.

The Auto Scaling Group manages replaceable compute capacity.

The ALB distributes application traffic.

IAM controls what the compute is allowed to do.

S3 provides durable object storage that exists independently of individual application instances.

Versioning protects object history.

Lifecycle policies manage data over time.

Storage classes align storage behavior with access patterns.

Encryption protects stored data.

Bucket policies and IAM policies control access.

Block Public Access helps prevent accidental exposure.

Pre-signed URLs provide temporary controlled access without making private objects permanently public.

Replication can create additional copies according to your resilience or compliance design.

Logging gives you evidence about activity.

And systematic troubleshooting helps you understand why a request was denied instead of solving every problem with dangerous broad permissions.

The mindset should become:

```text
Do not ask:

"Where can I upload this file?"

Ask:

"What kind of data is this?

Who owns it?

Who needs access?

How often is it accessed?

How long must it exist?

How quickly must it be retrieved?

Should previous versions survive?

Should it be replicated?

How should it be encrypted?

Who should be able to delete it?

How will we know who accessed it?

How will we recover it?

What happens to this data when the compute instance disappears?"
```

That is the foundation of using Amazon S3 as an engineer rather than treating it as an online folder.
