# Part 1: AWS Foundations and How the Cloud Actually Works

Before launching an EC2 instance, creating a VPC, or deploying an application, you need to understand what AWS actually provides and how its major pieces fit together.

A common beginner mistake is learning AWS as a collection of service names:

* EC2 = servers
* S3 = storage
* RDS = databases
* Route 53 = DNS
* CloudWatch = monitoring

Those definitions are useful, but they are not enough.

A DevOps engineer needs to understand the system behind those services:

```text
Where does the infrastructure physically exist?

How does a user reach an application?

Who controls access?

Where does networking happen?

Which services belong to a Region?

What happens if a server fails?

What does AWS manage?

What are you responsible for?

How much will the architecture cost?
```

That is what this first part establishes.

By the end of Part 1, you should be able to look at a simple architecture such as:

```text
Users
  |
  v
Internet
  |
  v
Route 53
  |
  v
Load Balancer
  |
  v
EC2
  |
  v
Application
```

and understand what each layer is doing, even though we have not yet configured the individual services.

# 1. What Is Cloud Computing?

Cloud computing is the delivery of computing resources over a network, usually the internet, when you need them.

Those resources can include:

* Servers
* Storage
* Databases
* Networks
* Load balancers
* DNS
* Monitoring systems
* Message queues
* Container platforms
* Security services
* Machine learning services

Before cloud computing became common, organizations often had to purchase and maintain much of this infrastructure themselves.

Suppose a company wants to launch a web application.

Traditionally, it might need to:

1. Purchase physical servers.
2. Find somewhere to host them.
3. Install operating systems.
4. Configure networking.
5. Purchase storage.
6. Configure firewalls.
7. Install database software.
8. Set up backups.
9. Build monitoring.
10. Maintain and replace hardware.

The infrastructure might look roughly like this:

```text
Users
  |
Internet
  |
Company Router
  |
Firewall
  |
Load Balancer
  |
Physical Servers
  |
Database Servers
  |
Storage
```

With cloud computing, much of the underlying physical infrastructure already exists.

A company can request resources from a cloud provider.

For example, with AWS you can request:

```text
Need a virtual server?
        |
        v
      EC2

Need object storage?
        |
        v
       S3

Need a managed relational database?
        |
        v
       RDS

Need DNS?
        |
        v
    Route 53

Need a load balancer?
        |
        v
Elastic Load Balancing
```

Instead of waiting for physical hardware to arrive, infrastructure can often be provisioned in minutes.

## What you should remember

Cloud computing does not mean that servers disappeared.

The servers still physically exist.

The difference is that organizations can consume computing infrastructure as services rather than owning and operating every physical component themselves.

# 2. Traditional Infrastructure vs Cloud Infrastructure

Understanding the difference is important because DevOps practices grew partly from the need to make infrastructure faster, repeatable, automated, and easier to operate.

## Traditional infrastructure

Imagine a company needs ten new application servers.

A traditional process might involve:

```text
Application team requests servers
            |
            v
Infrastructure team approves request
            |
            v
Hardware is purchased
            |
            v
Servers arrive
            |
            v
Servers are installed in racks
            |
            v
Networking is configured
            |
            v
Operating systems are installed
            |
            v
Application is deployed
```

Depending on the organization, this could take days or weeks.

There is another problem.

What happens if the application suddenly becomes extremely popular?

The organization may need more servers.

But physical capacity cannot always appear immediately.

## Cloud infrastructure

In AWS, the process can be much faster.

```text
Application needs servers
          |
          v
AWS API / Console / CLI
          |
          v
Create EC2 instances
          |
          v
Configure automatically
          |
          v
Deploy application
```

Eventually, DevOps engineers can automate the entire process.

For example:

```text
Git Repository
      |
      v
CI/CD Pipeline
      |
      v
Infrastructure Automation
      |
      v
AWS
      |
      +---- Network
      |
      +---- Servers
      |
      +---- Load Balancer
      |
      +---- Database
```

This is one reason cloud computing and DevOps work so well together.

---

# 3. Capital Expenditure vs Operational Expenditure

There is also an important financial difference.

Traditional infrastructure often involves large upfront purchases.

This is commonly associated with capital expenditure, or CapEx.

For example:

```text
Buy servers
Buy networking equipment
Buy storage
Build data center capacity
```

Cloud infrastructure often shifts more spending toward operational expenditure, or OpEx.

Instead of buying every physical server, you pay for services as you consume them.

This does not automatically mean cloud is cheaper.

A poorly designed AWS environment can become very expensive.

Cloud gives you flexibility. Cost efficiency still requires engineering discipline.

# 4. Important Characteristics of Cloud Computing

Cloud environments typically provide several useful capabilities.

## On-demand resources

Resources can be provisioned when needed.

You do not normally need to purchase a physical server before creating an EC2 instance.

## Elasticity

Infrastructure can expand and contract as demand changes.

For example:

```text
Normal traffic

Users
  |
  v
EC2
EC2


Traffic increases

Users
  |
  v
EC2
EC2
EC2
EC2
EC2
```

Later we will use Auto Scaling to understand this properly.

## Automation

Cloud resources are accessible through APIs.

That makes automation possible.

Instead of manually creating infrastructure repeatedly, engineers can define and automate it.

## Metered usage

Many AWS services charge according to usage.

Examples include:

* Compute time
* Storage consumed
* Requests
* Data transfer
* Database capacity

The exact pricing model depends on the service.

## Global reach

AWS operates infrastructure across many geographic locations.

An organization can deploy applications closer to its users or across multiple geographic areas.

# 5. IaaS, PaaS, and SaaS

Cloud services are often described using three broad models:

```text
IaaS
PaaS
SaaS
```

These describe how much of the technology stack you manage versus how much the provider manages.

---

## 5.1 Infrastructure as a Service: IaaS

IaaS gives you infrastructure resources while leaving significant system administration responsibility to you.

Amazon EC2 is a good example.

When you launch an EC2 Linux server, AWS manages the underlying physical infrastructure.

You still manage things such as:

* Operating system configuration
* Packages
* Application installation
* Application configuration
* OS updates
* Many security settings
* Application monitoring

Think of it roughly as:

```text
YOUR RESPONSIBILITY

Application
Runtime
Packages
Operating System
-------------------------
AWS RESPONSIBILITY

Virtualization
Physical Server
Storage Hardware
Networking Hardware
Data Center
```

EC2 therefore gives you considerable control.

But more control also means more responsibility.

---

# 5.2 Platform as a Service: PaaS

PaaS provides a higher-level application platform.

The provider manages more of the underlying infrastructure.

Instead of thinking primarily about individual servers, developers can focus more on applications.

The exact boundary differs between services.

This is why IaaS/PaaS/SaaS should be treated as conceptual models rather than assuming every AWS service fits perfectly into one box.

---

# 5.3 Software as a Service: SaaS

SaaS gives the user access to a finished application.

You normally do not manage:

* Physical servers
* Operating systems
* Runtime
* Application deployment

You simply use the software.

Common examples outside AWS include web-based email, collaboration tools, and customer relationship management systems.

A simplified comparison is:

| Layer             | IaaS       | PaaS       | SaaS     |
| ----------------- | ---------- | ---------- | -------- |
| Application       | You manage | Mostly you | Provider |
| Runtime           | You manage | Provider   | Provider |
| OS                | You manage | Provider   | Provider |
| Virtualization    | Provider   | Provider   | Provider |
| Physical hardware | Provider   | Provider   | Provider |

The main idea is simple:

```text
IaaS
More control
More responsibility

        ↓

PaaS
Less infrastructure management

        ↓

SaaS
Mostly consume the finished software
```

# 8. AWS Global Infrastructure

AWS infrastructure is geographically distributed.

Three terms are especially important:

```text
Region
Availability Zone
Edge Location
```

Do not treat these as interchangeable.

# 9. AWS Regions

A Region is a geographic area in which AWS operates infrastructure.

When creating many AWS resources, you select a Region.

Conceptually:

```text
AWS
 |
 +-- Region A
 |
 +-- Region B
 |
 +-- Region C
```

Why have multiple Regions?

Several reasons:

* Place workloads closer to users
* Meet regulatory or data-location requirements
* Support disaster-recovery strategies
* Access services available in particular Regions
* Design geographically distributed systems

## Region selection matters

When choosing a Region, engineers commonly consider:

1. User location
2. Service availability
3. Cost
4. Compliance requirements
5. Latency
6. Disaster-recovery strategy

Latency means the delay involved in transferring data or completing a request.

If your users are geographically far from your infrastructure, network latency may increase.

---

# 10. Region Codes

AWS Regions have identifiers.

You will encounter these constantly when using the CLI, APIs, Terraform, CloudFormation, and other automation tools.

Examples of the format include:

```text
us-east-1
us-west-2
eu-west-1
```

A beginner should become comfortable recognizing Region identifiers because configuration often includes them.

For example, an AWS CLI command may explicitly specify a Region:

```bash
aws ec2 describe-instances --region us-east-1
```

Do not worry about memorizing the command yet.

The important point is that AWS needs to know **where** you want the operation performed.

---

# 11. Availability Zones

A Region contains multiple Availability Zones.

An Availability Zone, commonly abbreviated as AZ, represents one or more discrete data centers with supporting infrastructure.

Conceptually:

```text
AWS Region
 |
 +-- Availability Zone A
 |
 +-- Availability Zone B
 |
 +-- Availability Zone C
```

Availability Zones are designed so applications can avoid depending on a single location.

Suppose your application runs on only one server in one AZ:

```text
Region
 |
 +-- AZ-A
      |
      EC2
```

If that part of the environment becomes unavailable, your application could fail.

A stronger architecture could distribute workloads:

```text
Region
 |
 +-- AZ-A
 |    |
 |    EC2
 |
 +-- AZ-B
      |
      EC2
```

Now the application has infrastructure in more than one Availability Zone.

This introduces one of the most important cloud concepts:

**High availability.**

High availability means designing a system so that the failure of a component does not necessarily cause the entire service to become unavailable.

We will build this properly later.

---

# 12. Region vs Availability Zone

Remember the hierarchy:

```text
AWS
 |
 +-- Region
      |
      +-- Availability Zone
      |
      +-- Availability Zone
      |
      +-- Availability Zone
```

A Region is the larger geographic area.

Availability Zones exist inside Regions.

This distinction becomes extremely important when we start building VPCs and subnets.

---

# 13. Edge Locations

Edge locations serve a different purpose.

They are points in AWS's global network used by services that benefit from being closer to users, particularly for content delivery, DNS, and related edge capabilities.

Imagine your application is hosted far away from a user.

Without an edge system:

```text
User
 |
 | Long network journey
 |
Application
```

With cached content available closer to the user:

```text
User
 |
Nearby Edge Location
 |
Cached Content
```

The user may receive some content without every request traveling all the way to the application's origin infrastructure.

Amazon CloudFront is an important service associated with this model.

Route 53 also uses AWS's globally distributed infrastructure for DNS.

We will explore Route 53 later in this series.

---

# 14. Regional vs Global AWS Services

Not every AWS service operates with the same geographic scope.

Many resources are regional.

That means you work with them within a particular Region.

For example, an EC2 instance belongs to the Region where it was launched.

You might have:

```text
Region A
 |
 EC2-1
 EC2-2

Region B
 |
 EC2-3
```

EC2-1 does not magically become an instance in Region B.

Other AWS services have global characteristics.

IAM is a major example because identities and permissions are managed at the AWS account level rather than separately as ordinary regional resources.

Route 53 also provides global DNS capabilities.

The important beginner question is:

> Is this resource global, regional, or tied even more specifically to an Availability Zone?

That question will prevent many mistakes later.

# 15. AWS Accounts

An AWS account is a fundamental administrative and security boundary.

When you create AWS resources, they belong to an AWS account.

Conceptually:

```text
AWS Account
 |
 +-- IAM
 |
 +-- VPCs
 |
 +-- EC2
 |
 +-- S3
 |
 +-- RDS
 |
 +-- CloudWatch
```

Organizations often use multiple AWS accounts.

For example:

```text
Organization
 |
 +-- Development Account
 |
 +-- Testing Account
 |
 +-- Production Account
 |
 +-- Security Account
```

Why?

Isolation.

If everything lives in one giant environment, mistakes and security problems can have a much larger impact.

You do not need to design a multi-account enterprise platform yet.

For now, remember:

**Account boundaries matter for ownership, security, billing, and resource isolation.**

# 16. The AWS Root User

When an AWS account is created, it has a root user associated with the account owner credentials.

The root user has extremely powerful access.

That means it should not be used for ordinary daily administration.

A safer principle is:

```text
Root User
   |
   +-- Protect carefully
   +-- Enable MFA
   +-- Avoid daily use

Normal Administration
   |
   v
Appropriate IAM identities / roles
```

MFA means multi-factor authentication.

Instead of authentication depending only on a password, another authentication factor is required.

IAM will receive an entire dedicated part because identity mistakes can create serious security incidents.

# 18. Introduction to the AWS CLI

CLI means Command Line Interface.

The AWS CLI allows you to interact with AWS from a terminal.

Instead of opening the browser and clicking through the console, you can issue commands.

The basic pattern looks like:

```bash
aws <service> <operation> [options]
```

For example:

```bash
aws ec2 describe-instances
```

Break it down:

```text
aws
 |
AWS CLI program

ec2
 |
AWS service

describe-instances
 |
Operation
```

The command asks AWS for information about EC2 instances accessible in the configured account and Region context.

A more explicit example is:

```bash
aws ec2 describe-instances --region us-east-1
```

Here:

```text
--region
```

is an option.

And:

```text
us-east-1
```

is the value supplied to that option.

## Why use the CLI?

Because commands can be:

* Repeated
* Scripted
* Documented
* Combined
* Automated

Eventually you might perform operations such as:

```text
Create resource
      |
Configure resource
      |
Deploy application
      |
Check status
      |
Collect logs
```

without manually navigating through many console pages.

We will learn the actual commands gradually rather than dumping dozens of commands here.

# 22. AWS Shared Responsibility Model

One of the most important AWS security concepts is the Shared Responsibility Model.

Moving to AWS does not mean:

> AWS handles all security.

Security responsibilities are shared between AWS and the customer.

A useful simplified distinction is:

**AWS is responsible for security OF the cloud.**

**The customer is responsible for security IN the cloud.**

---

# 23. AWS Responsibilities

AWS handles areas such as the underlying:

* Physical facilities
* Physical servers
* Physical networking
* Hardware
* Core infrastructure supporting AWS services

You do not normally walk into an AWS data center and replace a failed physical disk.

AWS handles the underlying infrastructure.

---

# 24. Customer Responsibilities

Your responsibilities depend partly on the AWS service being used.

For an EC2 workload, you may be responsible for:

* Operating system updates
* Application security
* IAM permissions
* Security Group configuration
* Data protection
* Installed software
* Credentials
* Application vulnerabilities

Consider this mistake:

```text
EC2 Linux Server
SSH port 22
Source: 0.0.0.0/0
```

AWS did not necessarily make the configuration secure just because the server runs in AWS.

If you configure unnecessarily broad access, that is your configuration.

Similarly:

```text
Weak IAM permissions
Exposed credentials
Unpatched application
Poor network rules
Publicly exposed data
```

can all become customer-side security problems.

---

# 25. Responsibility Changes Depending on the Service

The amount you manage changes depending on the service.

With EC2:

```text
AWS manages physical infrastructure.

You manage much more of the operating system and application stack.
```

With a more managed service:

```text
AWS manages more components.
You manage fewer underlying layers.
```

This is why you should always ask:

> For this AWS service, what exactly does AWS manage and what do I still manage?

That is a much better question than simply asking whether AWS is "secure."

# 28. Route 53

Amazon Route 53 is AWS's DNS service.

DNS means Domain Name System.

Humans prefer names:

```text
app.example.com
```

Computers communicate over networks using IP addresses.

DNS helps connect names with destinations.

Conceptually:

```text
User enters:

app.example.com

        |
        v

DNS lookup

        |
        v

Where should this request go?
```

Route 53 can direct the user toward the application's AWS entry point.

We will dedicate an entire part to DNS and Route 53 later.

# 29. Load Balancer

Imagine your application has three servers:

```text
EC2-1
EC2-2
EC2-3
```

Users should not normally need to decide which server to contact.

A load balancer can sit in front of them:

```text
              Users
                |
                v
         Load Balancer
          /     |     \
         v      v      v
       EC2-1  EC2-2  EC2-3
```

The load balancer receives traffic and forwards requests to appropriate healthy targets.

It can also help detect unhealthy application instances.

For example:

```text
EC2-1 = Healthy
EC2-2 = Healthy
EC2-3 = Unhealthy
```

The load balancer can avoid sending normal traffic to the unhealthy target, depending on configuration.

This helps us build more resilient systems.

# 34. AWS Resources

A resource is an entity you create, configure, or use within AWS.

Examples include:

```text
EC2 instance
VPC
Subnet
Security Group
Load Balancer
S3 bucket
RDS database
IAM role
```

AWS needs ways to identify those resources.

Different resource types have different identifiers.

You may encounter values such as:

```text
i-xxxxxxxxxxxxxxxxx
vpc-xxxxxxxxxxxxxxxxx
subnet-xxxxxxxxxxxxxxxxx
sg-xxxxxxxxxxxxxxxxx
```

The exact values are generated for resources.

The prefixes help indicate the type.

For example:

```text
i-
```

is associated with an EC2 instance ID.

```text
vpc-
```

identifies a VPC.

```text
subnet-
```

identifies a subnet.

```text

```

identifies a Security Group.

Do not memorize fake ID strings.

Learn to recognize what the prefixes represent.

# 35. Amazon Resource Names

Another identifier you will encounter is the ARN.

ARN means:

**Amazon Resource Name**

ARNs provide standardized names for AWS resources.

A typical ARN has a structure resembling:

```text
arn:partition:service:region:account-id:resource
```

For example, conceptually:

```text
arn
 |
 +-- AWS partition
 |
 +-- Service
 |
 +-- Region
 |
 +-- Account
 |
 +-- Resource
```

ARNs become particularly important in IAM policies.

For example, instead of granting access to everything, a policy can reference a particular resource.

We will explore this properly when studying IAM.

---

# 36. Resource IDs vs Human-Friendly Names

Suppose you create an EC2 instance.

AWS might identify it internally with something like:

```text
i-0123456789abcdef0
```

That is useful for AWS.

It is not particularly meaningful to an engineer.

So we often attach metadata such as:

```text
Name = production-web-01
```

Now the engineer can understand what the resource represents.

This introduces tagging.

---

# 37. AWS Tags

Tags are key-value metadata attached to supported AWS resources.

For example:

```text
Key: Name
Value: production-web-01
```

Another:

```text
Key: Environment
Value: Production
```

Another:

```text
Key: Application
Value: payments-api
```

Together:

```text
Name         = production-web-01
Environment  = production
Application  = payments-api
Team         = platform
```

Tags help humans and automation understand resources.

---

# 38. Why Tags Matter

Imagine an account containing 300 EC2 instances.

Without consistent metadata:

```text
i-abc...
i-def...
i-ghi...
i-jkl...
```

Which server belongs to which application?

Which environment?

Which team?

Which cost center?

Which resources can safely be removed?

Good tags can help answer those questions.

Tags can support:

* Resource organization
* Cost allocation
* Automation
* Operations
* Security processes
* Ownership
* Environment identification

---

# 39. Naming Conventions

Naming conventions make infrastructure easier to understand.

A team might use a pattern such as:

```text
<environment>-<application>-<component>
```

Examples:

```text
dev-shop-api
test-shop-api
prod-shop-api
prod-shop-database
```

Or:

```text
<company>-<environment>-<service>-<region>
```

There is no single universal naming standard that every company must use.

The important characteristics are:

* Consistency
* Clarity
* Predictability
* Enough context
* Automation friendliness

Avoid meaningless naming such as:

```text
server-new-final2
test123
myserver
server-real-final
```

Those names become painful in larger environments.

# 40. AWS Pricing Fundamentals

Cloud resources are not automatically free.

AWS uses different pricing models depending on the service.

You may be charged for things such as:

```text
Compute
Storage
Requests
Database capacity
Public IPv4 addresses
Data transfer
NAT Gateway usage
Load balancer usage
Snapshots
Logs
```

This means deleting an EC2 instance does not necessarily guarantee that every related charge disappears.

For example, you may still have other billable resources.

Cost awareness is part of cloud engineering.

---

# 41. Pay-as-You-Go

A major cloud model is paying according to consumption.

Suppose infrastructure usage increases:

```text
More servers
More storage
More network traffic
More database usage
        |
        v
Potentially higher bill
```

And if unnecessary resources remain running:

```text
Unused resource
     |
     v
Still consuming billable capacity
     |
     v
Unnecessary cost
```

Cloud makes infrastructure easy to create.

That also makes it easy to accidentally create waste.

---

# 42. AWS Free Tier

AWS provides Free Tier offers for eligible services and accounts, but you should never interpret "Free Tier" as:

> Everything I create in AWS is free.

Different offers have different:

* Eligibility requirements
* Usage limits
* Time limits
* Service restrictions

A resource can exceed the applicable allowance.

Another service you use alongside it may not be covered by the same offer.

Pricing and Free Tier terms can also change over time.

Therefore, before creating a resource, check the current pricing and Free Tier conditions for that specific service.

---

# 43. Avoiding Unexpected AWS Bills

This matters especially when learning.

## Rule 1: Know what you create

Do not blindly follow a tutorial that tells you to create ten AWS resources without understanding them.

## Rule 2: Clean up labs

When a lab is complete, remove resources that are no longer needed.

## Rule 3: Remember dependent resources

You may create:

```text
EC2
EBS
Load Balancer
NAT Gateway
Elastic IP
RDS
Snapshots
CloudWatch logs
```

Deleting only one component may leave others behind.

## Rule 4: Use AWS Budgets and billing controls

Configure cost monitoring early.

Do not wait until you have built a large environment.

## Rule 5: Read pricing before experimenting with unfamiliar services

Particularly pay attention to resources that can accumulate hourly, storage, request, or data-processing charges.

## Rule 6: Never assume stopped means free

Stopping a compute resource may stop some compute charges while associated storage or other resources continue to generate charges.

## Rule 7: Review your resources across Regions

A common beginner problem is creating something in one Region and later forgetting where it exists.

You might look at:

```text
Region A
"No instances"
```

while your resource is still running in:

```text
Region B
EC2 instance running
```

Always check the selected Region.

# 44. A Beginner Cost-Safety Workflow

Before a lab:

3. Check applicable Free Tier eligibility.
4. Understand which resources continue charging.
5. Create the lab.

# What You Should Now Understand

After Part 1, you should understand that:

* Cloud computing provides computing resources on demand rather than requiring organizations to own every physical component.
* AWS is a cloud platform containing compute, networking, storage, database, security, monitoring, and many other services.
* Cloud infrastructure still runs on physical infrastructure.
* IaaS, PaaS, and SaaS represent different levels of provider management and customer responsibility.
* DevOps engineers use AWS because infrastructure can be programmable, repeatable, scalable, and automatable.
* AWS infrastructure is organized geographically.
* Regions are geographic areas.
* Availability Zones exist within Regions and help engineers design highly available systems.
* Edge locations support globally distributed services and workloads that benefit from proximity to users.
* Some AWS services/resources are regional while others have global characteristics.
* AWS accounts form important administrative, security, ownership, and billing boundaries.
* The root user should be heavily protected and not used for routine work.
* The AWS Management Console is a graphical interface.
* The AWS CLI allows terminal-based interaction.
* SDKs allow software to interact programmatically with AWS.
* These interfaces ultimately interact with AWS service APIs.
* AWS and the customer share security responsibilities.
* AWS resources have identifiers.
* ARNs provide standardized AWS resource names.
* Tags and naming conventions help organize infrastructure.
* Cloud resources can generate costs even when you are only experimenting.
* Free Tier does not mean every AWS resource is free.
* Cleanup and cost verification are part of responsible AWS engineering.
* A real AWS application consists of interconnected services rather than isolated AWS products.
