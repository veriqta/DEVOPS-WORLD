# Part 10: DNS: How Names Become IP Addresses

## Understand One of the Most Important Services on the Internet

In Part 9, you learned that applications communicate using IP addresses and ports.

For example:

```text
203.0.113.20:443
```

could represent a web service.

But humans do not normally want to remember:

```text
203.0.113.20
```

They want to use names such as:

```text
example.com
api.example.com
database.internal.example.com
```

That creates a new problem:

```text
Humans prefer names.

Networks route using IP addresses.
```

DNS solves that problem.

A useful beginner mental model is:

```text
Application wants:

www.example.com
        |
        v
       DNS
        |
        v
Find IP address
        |
        v
203.0.113.20
        |
        v
Routing
        |
        v
TCP/UDP
        |
        v
Application server
```

By the end of Part 10, you should understand how DNS names are organized, how recursive resolution works, what DNS records mean, how caching and TTL work, how Linux chooses resolvers, how DNS works in cloud and Kubernetes environments, and how to troubleshoot DNS failures from the client all the way to the authoritative name server.

---

# 1. Why DNS Exists

Imagine the Internet without DNS.

To visit websites, users might have to type:

```text
203.0.113.20
```

instead of:

```text
example.com
```

To access an API:

```text
198.51.100.40
```

instead of:

```text
api.example.com
```

That would be difficult to remember and difficult to manage.

DNS stands for:

```text
Domain Name System
```

Its core job is to associate names with information.

The most familiar use is:

```text
Domain name
    |
    v
IP address
```

But DNS stores much more than IP addresses.

It can contain information about:

* Mail servers
* Name servers
* Service locations
* Text verification data
* Certificate authority restrictions
* Reverse mappings
* Aliases

---

# 2. DNS Is Not Just a Giant Phone Book

You will often hear:

```text
DNS is the phone book of the Internet.
```

That analogy is useful but incomplete.

DNS is actually a:

```text
Distributed
Hierarchical
Cached
Database system
```

There is not one server containing every Internet DNS record.

Instead, responsibility is distributed across many servers.

Conceptually:

```text
DNS namespace

        .
        |
   +----+----+
   |         |
  com       org
   |
 example
   |
   +--------+
   |        |
 www       api
```

Different DNS servers can be responsible for different parts of this hierarchy.

---

# 3. What Is a Domain Name?

A domain name is a human-readable name within the DNS namespace.

Examples:

```text
example.com
openai.com
github.com
```

A domain name contains labels separated by dots.

For example:

```text
api.example.com
```

contains:

```text
api
example
com
```

Each label represents a position in the DNS hierarchy.

---

# 4. Fully Qualified Domain Name

FQDN stands for:

```text
Fully Qualified Domain Name
```

An FQDN represents the complete DNS name from the host or service label through the DNS hierarchy to the root.

For example:

```text
www.example.com.
```

Notice the final dot.

That final dot represents the DNS root.

In everyday use, people usually omit it:

```text
www.example.com
```

but conceptually the complete DNS name is:

```text
www.example.com.
```

---

# 5. DNS Hierarchy

DNS is hierarchical.

At the top is:

```text
.
```

the DNS root.

Below the root are Top-Level Domains.

Examples:

```text
.com
.org
.net
.gov
.uk
.mx
.ng
```

Below a TLD might be a registered domain:

```text
example.com
```

Below that:

```text
www.example.com
api.example.com
mail.example.com
```

Conceptually:

```text
                    .
                    |
          +---------+---------+
          |                   |
         com                 org
          |
      example
       /   \
      /     \
    www     api
```

---

# 6. Root DNS Servers

At the top of the DNS hierarchy are the DNS root servers.

Their role is not normally to tell you directly:

```text
www.example.com = 203.0.113.20
```

Instead, they help direct resolvers toward the servers responsible for Top-Level Domains.

Conceptually:

```text
Resolver asks:

"Where can I learn about example.com?"

        |
        v
Root
        |
        v
"Ask the .com name servers."
```

The root provides delegation information.

---

# 7. Root Zone

The root servers serve information for the:

```text
Root zone
```

The root zone contains information about Top-Level Domains.

Examples:

```text
.com
.org
.net
.mx
.ng
```

The root servers therefore help resolvers move one step down the hierarchy.

---

# 8. Top-Level Domains

TLD stands for:

```text
Top-Level Domain
```

Examples include:

```text
.com
.org
.net
.edu
.gov
.io
.dev
.mx
.ng
```

Some TLDs are generic.

Examples:

```text
.com
.org
.net
```

Some are country-code TLDs.

Examples:

```text
.mx
.ng
.uk
.de
```

A TLD's authoritative infrastructure knows which name servers are responsible for domains registered beneath that TLD.

---

# 9. Example DNS Delegation

Suppose we need:

```text
www.example.com
```

A resolver may conceptually proceed like this:

```text
Resolver
   |
   | Where is example.com?
   v
Root servers
   |
   | Ask .com
   v
.com servers
   |
   | example.com is delegated to
   | these authoritative servers
   v
Authoritative servers for example.com
   |
   | www.example.com = 203.0.113.20
   v
Resolver
```

This is the hierarchical nature of DNS resolution.

---

# 10. Authoritative Name Servers

An authoritative name server contains or serves authoritative DNS information for a DNS zone.

Suppose:

```text
example.com
```

has DNS records such as:

```text
www.example.com
api.example.com
mail.example.com
```

The authoritative servers for the relevant zone can provide official answers for those names.

Conceptually:

```text
Authoritative server:

"I am responsible for this zone.
Here is the answer."
```

This is different from a recursive resolver that searches on behalf of clients.

---

# 11. Recursive Resolvers

Most user devices do not directly contact root, TLD, and authoritative servers for every lookup.

Instead, they usually ask a recursive resolver.

Examples may include resolvers operated by:

* Internet service providers
* Enterprises
* Cloud providers
* Local network infrastructure
* Public DNS providers

The client asks:

```text
What is the IP for www.example.com?
```

The recursive resolver performs or coordinates the lookup and returns the answer.

---

# 12. Stub Resolvers

Your operating system or application commonly uses a:

```text
Stub resolver
```

A stub resolver is a lightweight DNS client.

It generally does not walk the entire DNS hierarchy itself.

Instead:

```text
Application
     |
     v
Stub resolver
     |
     v
Recursive resolver
```

The recursive resolver does the heavier work.

---

# 13. Complete DNS Resolution Path

Suppose your browser wants:

```text
www.example.com
```

A simplified path:

```text
Browser
   |
   v
Operating system stub resolver
   |
   v
Configured recursive resolver
   |
   v
Root
   |
   v
.com TLD
   |
   v
example.com authoritative server
   |
   v
A/AAAA answer
   |
   v
Recursive resolver
   |
   v
Client
```

However, caching may eliminate many of these steps.

---

# 14. DNS Queries

A DNS query asks for information about a name.

For example:

```text
Name:
www.example.com

Type:
A
```

means:

```text
Give me the IPv4 address record
for www.example.com.
```

Another query:

```text
Name:
example.com

Type:
MX
```

asks:

```text
Which mail servers handle mail
for example.com?
```

The query type matters.

---

# 15. Recursive Queries

A recursive query conceptually says:

```text
Give me the final answer,
or tell me you cannot provide one.
```

A client commonly sends a recursive query to its configured recursive resolver.

Example:

```text
Laptop
   |
   | "Resolve www.example.com for me."
   v
Recursive resolver
```

The resolver performs the necessary work.

---

# 16. Iterative Queries

An iterative query allows a DNS server to respond with the best information it currently has, often including a referral to another DNS server.

Conceptually:

```text
Resolver -> Root

"Where is www.example.com?"
```

Root responds:

```text
"I do not host example.com,
but ask these .com servers."
```

Then:

```text
Resolver -> .com
```

The `.com` server may respond:

```text
"Ask these authoritative servers
for example.com."
```

The resolver keeps following referrals.

---

# 17. Recursive vs Iterative

Simplified:

```text
Recursive:

Client:
"Find the final answer for me."

Resolver:
"Okay."
```

Iterative:

```text
Resolver:
"Where should I go next?"

DNS server:
"Try this server."
```

End-user systems normally rely heavily on recursive resolvers.

Recursive resolvers perform iterative work within the hierarchy when necessary.

---

# 18. DNS Caching

If every query required contacting root servers, TLD servers, and authoritative servers from scratch, DNS would be much less efficient.

DNS therefore uses caching extensively.

Suppose a resolver recently learned:

```text
www.example.com
=
203.0.113.20
```

It can temporarily store that answer.

The next client may receive the cached answer immediately.

Conceptually:

```text
Client A
   |
   v
Resolver
   |
   v
Authoritative lookup
   |
   v
Cache answer
```

Later:

```text
Client B
   |
   v
Resolver cache
   |
   v
Immediate answer
```

---

# 19. Why DNS Caching Matters

Caching helps:

* Reduce DNS traffic
* Reduce latency
* Reduce authoritative-server load
* Improve resilience
* Improve application performance

But caching also creates an important operational consequence:

```text
DNS changes are not necessarily
seen everywhere immediately.
```

That leads us to TTL.

---

# 20. What Is DNS TTL?

TTL stands for:

```text
Time To Live
```

A DNS record's TTL tells caching resolvers approximately how long they may cache the record before needing to refresh it.

Suppose:

```text
www.example.com
A
203.0.113.20
TTL 300
```

`300` means:

```text
300 seconds
```

or:

```text
5 minutes
```

A resolver may cache the answer for that period.

---

# 21. TTL Example

At 10:00:

```text
Resolver learns:

www.example.com
203.0.113.20
TTL 300
```

At 10:02:

A client asks again.

The resolver can use the cached value.

At approximately 10:05 or after expiration:

The resolver needs to refresh the information when needed.

The exact caching behavior can involve implementation details, but the core idea is:

```text
TTL controls cache lifetime.
```

---

# 22. Low vs High TTL

Low TTL:

```text
60 seconds
```

Potential advantage:

```text
Changes can be observed more quickly.
```

Potential disadvantage:

```text
More frequent DNS queries.
```

High TTL:

```text
86400 seconds
```

Potential advantage:

```text
Better cache efficiency.
```

Potential disadvantage:

```text
Old values may remain cached longer
after a change.
```

DNS administrators choose TTLs according to operational needs.

---

# 23. Forward DNS Lookups

A forward lookup maps a name to information, commonly an IP address.

Example:

```text
www.example.com
        |
        v
203.0.113.20
```

Record types commonly involved:

```text
A
AAAA
```

A is for IPv4.

AAAA is for IPv6.

---

# 24. Reverse DNS Lookups

A reverse lookup asks:

```text
Which DNS name is associated with this IP?
```

Example:

```text
203.0.113.20
        |
        v
server.example.com
```

Reverse DNS uses PTR records.

Reverse lookup namespaces are different from ordinary forward DNS zones.

For IPv4, reverse DNS uses:

```text
in-addr.arpa
```

For IPv6:

```text
ip6.arpa
```

---

# 25. A Records

An A record maps a DNS name to an IPv4 address.

Example:

```text
www.example.com.   A   203.0.113.20
```

Meaning:

```text
www.example.com
        |
        v
203.0.113.20
```

This is one of the most common DNS records.

---

# 26. AAAA Records

An AAAA record maps a DNS name to an IPv6 address.

Example:

```text
www.example.com.   AAAA   2001:db8::20
```

Meaning:

```text
www.example.com
        |
        v
2001:db8::20
```

You will sometimes hear AAAA pronounced:

```text
quad-A
```

---

# 27. CNAME Records

CNAME stands for:

```text
Canonical Name
```

A CNAME creates an alias.

Example:

```text
shop.example.com
        |
        v
store.example.net
```

Conceptually:

```text
shop.example.com. CNAME store.example.net.
```

The client then needs the appropriate records for the canonical target.

---

# 28. CNAME Example

Suppose:

```text
app.example.com
```

is a CNAME for:

```text
prod-app.example.net
```

and:

```text
prod-app.example.net
```

has:

```text
A 203.0.113.50
```

Resolution becomes:

```text
app.example.com
      |
      v
prod-app.example.net
      |
      v
203.0.113.50
```

CNAMEs are common in cloud and SaaS environments.

---

# 29. Important CNAME Concept

A CNAME means:

```text
This name is an alias for another DNS name.
```

It does not directly mean:

```text
This name has this IP address.
```

That distinction matters during troubleshooting.

You may need to follow the alias chain.

---

# 30. MX Records

MX stands for:

```text
Mail Exchange
```

MX records identify mail servers responsible for receiving email for a domain.

Example:

```text
example.com. MX 10 mail1.example.com.
example.com. MX 20 mail2.example.com.
```

The numeric value represents priority/preference.

Lower values are generally preferred.

---

# 31. MX Example

Conceptually:

```text
Email to:
user@example.com

        |
        v
DNS query for MX example.com
        |
        v
mail1.example.com
        |
        v
Resolve mail1.example.com IP
        |
        v
SMTP connection
```

DNS does not deliver the email itself.

It tells mail systems which server should receive it.

---

# 32. TXT Records

TXT records store text information.

They are used for many purposes.

Examples include:

* Domain verification
* SPF information
* DKIM-related configuration
* DMARC configuration
* Service verification
* Ownership proofs

Conceptual example:

```text
example.com TXT "some-verification-value"
```

TXT records are extremely common in modern cloud and SaaS systems.

---

# 33. NS Records

NS stands for:

```text
Name Server
```

NS records identify authoritative name servers for a DNS zone.

Example:

```text
example.com. NS ns1.example-dns.net.
example.com. NS ns2.example-dns.net.
```

These records help establish delegation and authority within DNS.

---

# 34. SOA Record

SOA stands for:

```text
Start of Authority
```

Each DNS zone normally has an SOA record.

It contains administrative and zone-management information such as:

* Primary name server
* Responsible party information
* Serial number
* Refresh interval
* Retry interval
* Expiration information
* Negative caching-related values

You do not need to memorize every SOA field immediately.

But you should recognize that SOA provides important zone metadata.

---

# 35. SOA Serial Number

An SOA record includes a serial number.

Historically and operationally, secondary DNS servers use the serial to determine whether zone data has changed.

Conceptually:

```text
Old zone serial:
2026082701

New zone serial:
2026082702
```

A higher serial can indicate newer zone data.

Exact serial formats are administrative conventions.

---

# 36. PTR Records

PTR stands for:

```text
Pointer
```

PTR records are used for reverse DNS.

Example:

```text
203.0.113.20
        |
        v
server.example.com
```

A reverse lookup queries the reverse DNS namespace rather than ordinary `example.com`.

---

# 37. SRV Records

SRV records identify services.

They can include information such as:

* Service name
* Protocol
* Priority
* Weight
* Port
* Target host

A conceptual SRV record:

```text
_service._tcp.example.com
```

could indicate:

```text
Use server.example.com
on TCP port 1234
```

SRV records are useful when applications need more than a simple name-to-IP mapping.

---

# 38. CAA Records

CAA stands for:

```text
Certification Authority Authorization
```

CAA records allow domain owners to specify which certificate authorities are authorized to issue certificates for the domain.

Conceptually:

```text
example.com CAA
        |
        v
Only these certificate authorities
are authorized.
```

CAA relates to certificate issuance policy, not normal web traffic routing.

---

# 39. DNS Record Summary

A useful table:

| Record | Main Purpose                             |
| ------ | ---------------------------------------- |
| A      | Name to IPv4                             |
| AAAA   | Name to IPv6                             |
| CNAME  | Alias to another name                    |
| MX     | Mail server                              |
| TXT    | Text / verification / policy information |
| NS     | Authoritative name server                |
| SOA    | Zone authority metadata                  |
| PTR    | Reverse DNS                              |
| SRV    | Service location                         |
| CAA    | Certificate authority authorization      |

Do not memorize only the letters.

Understand the problem each record solves.

---

# 40. `/etc/hosts`

Linux and Unix-like systems can use:

```text
/etc/hosts
```

for local hostname mappings.

Example:

```text
127.0.0.1 localhost
10.0.0.50 app.internal
```

This allows the local machine to map:

```text
app.internal
```

to:

```text
10.0.0.50
```

without querying DNS, depending on the system's name-service configuration.

---

# 41. Why `/etc/hosts` Matters

Developers frequently use `/etc/hosts` for:

* Local testing
* Temporary overrides
* Development environments
* Troubleshooting

But it can also cause confusion.

Suppose DNS says:

```text
api.example.com
=
10.0.0.20
```

but `/etc/hosts` contains:

```text
10.0.0.99 api.example.com
```

Your local machine may use:

```text
10.0.0.99
```

instead.

This creates the classic symptom:

```text
It works for everyone except me.
```

Always remember local host mappings.

---

# 42. Name-Service Resolution Order

On Linux, the order in which the operating system uses sources such as:

```text
files
dns
```

can be controlled by name-service configuration.

For example, `/etc/nsswitch.conf` may contain:

```text
hosts: files dns
```

Conceptually:

```text
First:
check local files such as /etc/hosts

Then:
query DNS
```

Modern systems may include additional resolver mechanisms.

This is why `dig` results and application behavior can occasionally differ.

---

# 43. `/etc/resolv.conf`

A common Linux DNS configuration file is:

```text
/etc/resolv.conf
```

It may contain:

```text
nameserver 192.168.1.1
nameserver 10.0.0.53
```

These specify DNS resolvers.

It may also contain search configuration.

Example:

```text
search example.internal
```

and options.

---

# 44. Example `/etc/resolv.conf`

```text
search corp.example.com
nameserver 10.10.0.53
nameserver 10.10.0.54
```

This tells the system about DNS resolvers and potentially a search domain.

But modern Linux systems may generate or manage `/etc/resolv.conf` through software such as:

* systemd-resolved
* NetworkManager
* DHCP
* VPN software
* Container platforms

Do not assume manually editing the file is always the correct persistent configuration.

---

# 45. Search Domains

Suppose:

```text
search corp.example.com
```

is configured.

You type:

```text
database
```

The resolver may try a name such as:

```text
database.corp.example.com
```

depending on resolver configuration.

This can make short names convenient.

But it can also create confusion if users do not realize suffixes are being appended.

---

# 46. Inspecting `/etc/resolv.conf`

Run:

```bash
cat /etc/resolv.conf
```

Look for:

```text
nameserver
search
options
```

Ask:

```text
Which DNS server is this host actually using?
```

This should be one of your first DNS troubleshooting questions.

---

# 47. `dig`

One of the best DNS troubleshooting tools is:

```bash
dig
```

For example:

```bash
dig example.com
```

`dig` sends DNS queries and provides detailed output.

It is especially useful for inspecting:

* Answer records
* Query type
* Resolver used
* Response status
* TTL
* Authority information
* Timing

---

# 48. Simple `dig` Query

Run:

```bash
dig example.com A
```

This means:

```text
Query:
example.com

Record type:
A
```

You are asking for IPv4 address records.

For IPv6:

```bash
dig example.com AAAA
```

---

# 49. `dig +short`

For concise output:

```bash
dig +short example.com
```

You may receive:

```text
203.0.113.20
```

This is useful in scripts or quick checks.

But it hides troubleshooting detail.

If DNS is failing, use normal `dig` output instead of relying only on `+short`.

---

# 50. Query a Specific Resolver

You can tell `dig` which DNS server to query.

Syntax:

```bash
dig @<dns-server> example.com
```

Example:

```bash
dig @10.0.0.53 example.com
```

This is extremely useful.

It allows you to compare:

```text
Corporate resolver
vs
Public resolver
vs
Another internal resolver
```

and determine whether the problem is resolver-specific.

---

# 51. Query a Specific Record Type

Examples:

```bash
dig example.com MX
```

```bash
dig example.com NS
```

```bash
dig example.com TXT
```

```bash
dig example.com SOA
```

```bash
dig example.com CAA
```

```bash
dig _service._tcp.example.com SRV
```

Use the query type that matches what you are investigating.

---

# 52. `dig` Response Status

In `dig` output, look for a status such as:

```text
status: NOERROR
```

Other important statuses include:

```text
NXDOMAIN
SERVFAIL
```

The status gives valuable clues.

Do not look only at whether an IP appears in the answer section.

---

# 53. `dig +trace`

A powerful learning tool is:

```bash
dig +trace example.com
```

This allows you to observe DNS delegation more directly, conceptually moving through:

```text
Root
 |
 v
TLD
 |
 v
Authoritative servers
 |
 v
Answer
```

It is useful for understanding where DNS delegation breaks.

However, network policies may prevent direct DNS access required by `+trace`.

---

# 54. `nslookup`

Another common DNS tool is:

```bash
nslookup
```

Example:

```bash
nslookup example.com
```

It can show:

* Resolver used
* Resulting addresses

It is available on many operating systems.

For deep DNS troubleshooting on Unix-like systems, `dig` often provides more detail.

But you should know both.

---

# 55. `host`

Another DNS command is:

```bash
host
```

Example:

```bash
host example.com
```

Possible output conceptually:

```text
example.com has address 203.0.113.20
```

For mail:

```bash
host -t MX example.com
```

`host` is convenient for quick lookups.

---

# 56. `dig` vs `nslookup` vs `host`

A practical beginner model:

```text
dig
-> Detailed DNS investigation

nslookup
-> Common general-purpose resolver testing

host
-> Quick simple queries
```

Learn `dig` deeply.

Recognize the others.

---

# 57. DNS Usually Uses UDP

Most ordinary DNS queries are commonly sent using:

```text
UDP port 53
```

Why UDP?

It has low overhead and works well for many request-response DNS operations.

Conceptually:

```text
Client
  |
  | UDP 53
  v
DNS Resolver
```

But DNS does not use only UDP.

---

# 58. DNS Also Uses TCP

DNS can use:

```text
TCP port 53
```

Examples include situations involving:

* Larger responses
* Truncated UDP responses
* DNS zone transfers
* Certain DNS operations or policies

A correct network design therefore should not blindly assume:

```text
Allow UDP 53 only.
```

DNS can require TCP 53 as well.

---

# 59. Truncated DNS Responses

Suppose a DNS response is too large for the way the UDP exchange is being handled.

The server may indicate truncation.

The client or resolver can retry using TCP.

Conceptually:

```text
Client -- UDP query --> DNS

Client <-- truncated -- DNS

Client -- TCP query --> DNS

Client <-- full answer - DNS
```

Modern DNS also uses EDNS mechanisms to support larger UDP messages, but TCP remains important.

---

# 60. DNS and Firewalls

If DNS fails, check whether the network allows:

```text
UDP 53
TCP 53
```

as required.

A firewall that allows only one can create strange partial failures.

For example:

```text
Small DNS queries work.

Large responses fail.
```

That can point toward TCP 53 or fragmentation/path issues.

---

# 61. DNS Propagation

People often say:

```text
DNS propagation takes time.
```

That phrase usually refers to the time required for:

* Cached old records to expire
* Delegation changes to become visible
* Authoritative data to update
* Recursive resolvers to refresh

DNS does not literally copy every record instantly to every server in the world.

Caching and delegation explain much of what people call propagation.

---

# 62. Propagation Example

Old record:

```text
www.example.com
203.0.113.10

TTL:
3600
```

At 12:00 you change it to:

```text
203.0.113.20
```

A resolver that cached the old value at 11:59 may continue returning the old address until its cache expires.

Another resolver that had no cached answer may immediately see the new value.

That is why:

```text
Person A sees new IP.

Person B still sees old IP.
```

can happen.

---

# 63. Why Lower TTL Before Migration

Suppose you plan to move:

```text
api.example.com
```

from:

```text
203.0.113.10
```

to:

```text
203.0.113.20
```

A common operational technique is to lower the TTL before migration.

Example:

```text
Old TTL:
86400

Lower before migration:
300
```

After enough time for old high-TTL caches to expire, changes can be observed more rapidly.

After the migration is stable, the TTL can be raised again if desired.

---

# 64. NXDOMAIN

NXDOMAIN means:

```text
Non-Existent Domain
```

Conceptually:

```text
The requested DNS name does not exist
according to the DNS response.
```

Example:

```bash
dig does-not-exist.example.com
```

might show:

```text
status: NXDOMAIN
```

This is different from a DNS timeout.

The DNS system responded.

The response says the name does not exist.

---

# 65. NXDOMAIN Troubleshooting

If you receive NXDOMAIN:

Ask:

```text
Is the hostname spelled correctly?

Does the record actually exist?

Am I querying the correct DNS zone?

Am I using the correct resolver?

Is this supposed to be an internal-only name?

Is a search suffix changing the query?
```

Do not immediately blame network connectivity.

You received a DNS response.

---

# 66. SERVFAIL

SERVFAIL means:

```text
Server Failure
```

It tells you the DNS server could not successfully complete the query.

Possible causes can include:

* DNSSEC validation issues
* Broken delegation
* Authoritative server failure
* Upstream resolution problems
* Misconfigured DNS zone
* Resolver problems

SERVFAIL is different from:

```text
NXDOMAIN
```

NXDOMAIN says:

```text
The name does not exist.
```

SERVFAIL says:

```text
I could not successfully answer.
```

---

# 67. DNS Timeout

A DNS timeout means the client waited but did not receive an acceptable DNS response within the expected time.

Possible causes:

* DNS server unreachable
* Firewall dropping UDP/TCP 53
* Wrong resolver IP
* Route failure
* Resolver overloaded
* Network packet loss
* VPN DNS configuration problems

A timeout is a transport/reachability clue.

---

# 68. NXDOMAIN vs SERVFAIL vs Timeout

Remember:

```text
NXDOMAIN
-> DNS replied:
   "That name does not exist."
```

```text
SERVFAIL
-> DNS replied:
   "I failed while resolving it."
```

```text
Timeout
-> No useful response arrived in time.
```

These are very different failure modes.

---

# 69. DNS Failure Can Look Like Internet Failure

Suppose:

```bash
ping 8.8.8.8
```

works.

But:

```bash
ping example.com
```

fails with a name-resolution error.

That tells you:

```text
Basic IP connectivity may work.

DNS may be broken.
```

Do not call it:

```text
The Internet is down.
```

Separate IP connectivity from name resolution.

# 70. DNS Failure Test

A strong first comparison is:

```bash

```

versus:

```bash

```

or better, perform a DNS-specific test:

```bash

```

If IP connectivity works but DNS queries fail, focus on DNS.

# 71. Split-Horizon DNS

Split-horizon DNS means the same DNS name can return different answers depending on where or how the query is made.

For example:

From inside the company:

```text
api.example.com
=
10.0.20.50
```

From the public Internet:

```text
api.example.com
=
203.0.113.50
```

Same name.

Different DNS answer.

---

# 72. Why Split-Horizon DNS Exists

Organizations may use split DNS to provide:

* Private internal addresses to internal clients
* Public addresses to external clients
* Different routing paths
* Internal services
* Security separation

Conceptually:

```text
Internal employee
      |
      v
Internal DNS
      |
      v
api.example.com
10.0.20.50
```

Public user:

```text
Public user
    |
    v
Public DNS
    |
    v
api.example.com
203.0.113.50
```

# 73. Split DNS Troubleshooting

A developer says:

```text
api.example.com works in the office
but not from home.
```

Possible explanation:

```text
Internal DNS has a private record.

Public DNS does not.
```

Or the reverse.

Compare resolvers:

```bash

```

and:

```bash
dig @public-dns api.example.com
```

Use the actual resolver addresses for the environment.

When someone says:

```text

```

```text
       |

       |
       v

       |

       |
       v

       |

       |

       |

       |
```

# 86. Troubleshooting Step 1: Identify the Exact Name

Suppose user says:

```text
The API hostname doesn't work.
```

Ask yourself:

```text
Which exact hostname?
```

For example:

```text
api.example.com
```

Do not troubleshoot vague descriptions.

Write down:

```text
Expected hostname:
api.example.com

Expected record type:
A or AAAA

Expected answer:
203.0.113.50
```

Now you have something testable.

---

# 87. Troubleshooting Step 2: Check `/etc/hosts`

Run:

```bash
grep api.example.com /etc/hosts
```

or inspect:

```bash
cat /etc/hosts
```

If you find:

```text
10.0.0.99 api.example.com
```

that could override normal DNS resolution for applications using the system resolver.

This is especially common on developer machines.

---

# 88. Troubleshooting Step 3: Check Resolver Configuration

Run:

```bash
cat /etc/resolv.conf
```

Identify:

```text
nameserver
```

entries.

For example:

```text
nameserver 10.0.0.53
```

Now test that resolver directly:

```bash
dig @10.0.0.53 api.example.com
```

This separates resolver behavior from other operating-system layers.

---

# 89. Troubleshooting Step 4: Query the Name

Run:

```bash
dig api.example.com
```

Look at:

```text
status
ANSWER SECTION
SERVER
Query time
```

Questions:

```text
Did the DNS query succeed?

Which resolver answered?

What record was returned?

What TTL remains?
```

---

# 90. Troubleshooting Step 5: Check the Record Type

Suppose:

```bash
dig api.example.com A
```

returns nothing useful.

Try:

```bash
dig api.example.com AAAA
```

Maybe the hostname has only IPv6.

Or perhaps it is a CNAME.

Query:

```bash
dig api.example.com CNAME
```

Always verify the actual record type.

---

# 91. Troubleshooting Step 6: Follow CNAMEs

Suppose:

```text
api.example.com
CNAME
prod-app.example.net
```

Now query:

```bash
dig prod-app.example.net A
```

or:

```bash
dig prod-app.example.net AAAA
```

A CNAME can be correct while its target is broken.

Trace the chain.

---

# 92. Troubleshooting Step 7: Compare Resolvers

Suppose internal resolver:

```bash
dig @10.0.0.53 api.example.com
```

returns:

```text
10.0.20.50
```

but another resolver returns:

```text
203.0.113.50
```

This may indicate:

```text
Split-horizon DNS
```

or inconsistent DNS configuration.

Do not assume one answer is wrong until you understand the intended scope.

---

# 93. Troubleshooting Step 8: Check Authoritative Servers

Query the NS records:

```bash
dig example.com NS
```

Then query an authoritative server directly:

```bash
dig @ns1.example-dns.net api.example.com
```

If the authoritative answer is correct but the recursive resolver is returning an old value, investigate caching.

If the authoritative answer itself is wrong, fix the zone.

---

# 94. Troubleshooting Step 9: Check TTL

Suppose authoritative DNS now says:

```text
203.0.113.50
```

but one resolver returns:

```text
203.0.113.20
```

Look at the cached TTL.

The resolver may legitimately still hold the previous answer.

This may be a propagation/caching issue rather than an incorrect authoritative configuration.

---

# 95. Troubleshooting Step 10: Check Delegation

Use:

```bash
dig +trace example.com
```

or inspect:

```text
NS records
```

Ask:

```text
Does the parent zone delegate to the correct name servers?

Do those name servers answer authoritatively?

Are the records consistent?
```

Broken delegation can create SERVFAIL or inconsistent behavior.

---

# 96. Troubleshooting Step 11: Check DNS Server Reachability

Suppose `/etc/resolv.conf` says:

```text
nameserver 10.0.0.53
```

Check the route:

```bash
ip route get 10.0.0.53
```

Check basic reachability if appropriate.

Then test DNS directly:

```bash
dig @10.0.0.53 example.com
```

A DNS problem can actually be:

```text
Routing problem
```

to the DNS resolver.

---

# 97. Troubleshooting Step 12: Check Port 53

Use an appropriate TCP test:

```bash
nc -vz 10.0.0.53 53
```

This tests TCP 53 only.

Remember DNS also uses UDP.

For UDP-specific diagnosis, packet capture or DNS-specific tools are often more useful.

For example:

```bash
sudo tcpdump -n port 53
```

This can show DNS requests and responses.

---

# 98. Capture DNS Traffic

Run:

```bash

```

Then in another terminal:

```bash

```

Look for:

```text
Client -> Resolver query

Resolver -> Client response
```

If the query leaves but no response returns, investigate:

* Resolver
* Firewall
* Route
* Packet loss

If no query leaves, inspect local resolver behavior.

# 112. DNS Security Introduction

DNS is critical infrastructure.

If DNS is compromised or misconfigured, clients can be directed toward incorrect systems.

Important security concepts include:

* DNSSEC
* DNS filtering
* Resolver access control
* DNS logging
* Split DNS
* DNS over encrypted transports
* Protection against cache poisoning

We will not go deeply into DNS attacks here.

The important lesson is:

```text
DNS answers influence where applications connect.
```

Therefore DNS integrity matters.

---

# 113. DNS Over HTTPS and DNS Over TLS

Modern systems may use encrypted DNS transports such as:

```text
DoH
DNS over HTTPS
```

and:

```text
DoT
DNS over TLS
```

These change how DNS traffic is transported.

Traditional DNS:

```text
UDP/TCP 53
```

DoT commonly uses:

```text
TCP 853
```

DoH uses HTTPS transport.

This means packet captures and firewall troubleshooting may differ from traditional DNS.

---

# 114. Why Encrypted DNS Matters for Troubleshooting

Suppose:

```bash
tcpdump port 53
```

shows nothing.

That does not always prove:

```text
No DNS queries are happening.
```

The application or operating system may be using encrypted DNS.

Modern browsers can sometimes use their own DNS mechanisms independent of the system resolver.

This can create situations where:

```text
dig works one way

Browser behaves differently
```

because they may not be using exactly the same resolver path.

---

# 115. Application-Level DNS Caching

The operating system and recursive resolver are not the only places where DNS can be cached.

Applications may cache DNS themselves.

Examples can include:

* Browsers
* Java applications
* Load balancers
* Proxies
* Container runtimes
* Service meshes

So after a DNS change:

```text
Recursive resolver is correct
```

but an application may still use:

```text
Old IP
```

because of its own cache.

Always understand the full resolution path.

---

# 116. DNS Caching Layers

Conceptually:

```text
Application cache
       |
       v
OS resolver cache
       |
       v
Local resolver
       |
       v
Recursive resolver cache
       |
       v
Authoritative DNS
```

Not every system uses all these layers.

But the key idea is:

```text
There can be more than one cache.
```

That is why DNS troubleshooting sometimes requires comparing different tools and processes.

# 126. Common Beginner Mistakes

### Mistake 1: Assuming DNS and HTTP are the same thing

DNS only helps resolve the name.

It does not serve the website.

### Mistake 2: Assuming successful DNS means the application works

No.

You still need routing, transport, TLS, and application functionality.

### Mistake 3: Assuming failed hostname resolution means the Internet is down

IP connectivity may still work.

### Mistake 4: Ignoring `/etc/hosts`

Local overrides can bypass normal DNS.

### Mistake 5: Looking only at A records

A hostname might use AAAA or CNAME records.

### Mistake 6: Assuming NXDOMAIN means timeout

No.

NXDOMAIN is a valid DNS response.

### Mistake 7: Assuming SERVFAIL means the record does not exist

No.

SERVFAIL means resolution failed.

### Mistake 8: Assuming all DNS uses UDP

DNS uses both UDP and TCP.

### Mistake 9: Assuming every resolver returns the same answer

Split DNS and private DNS can intentionally return different answers.

### Mistake 10: Calling every delayed change "propagation"

Check TTL, resolver cache, authoritative data, and delegation first.

# 129. Final DNS Troubleshooting Challenge

You are responsible for this architecture:

```text

      |
      | VPN
      v

      |
      v

      |

      |
      v
```

The developer reports:

```text
"I connected to the VPN,
but api.prod.internal does not work."
```

Do not immediately restart the application.

Work through the DNS path.

---

# 130. Step 1: Test the Name

Run:

```bash
dig api.prod.internal
```

Suppose you receive:

```text
NXDOMAIN
```

Now ask:

```text
Which resolver answered?
```

Look at the `SERVER` field.

```text

```

That is the developer's home resolver.

```text

```

The VPN did not install the expected DNS configuration.

Run:

```bash
dig @10.0.0.53 api.prod.internal
```

Suppose the answer is:

```text
10.20.30.50
```

Now you know:

```text
Corporate DNS works.

The private record exists.

The client is using the wrong resolver.
```

That is evidence.

Run:

```bash
cat /etc/resolv.conf
```

or inspect the system's active resolver configuration.

Confirm whether:

```text
10.0.0.53
```

is installed correctly.

Remember that VPN clients and system resolver software may manage DNS dynamically.

Do not blindly edit `/etc/resolv.conf` unless that is actually the correct persistent mechanism for the system.

# What You Should Now Understand

You should now understand that DNS is not simply:

```text
Name -> IP
```

It is a distributed hierarchical system involving:

```text
DNS root
TLDs
Delegation
Authoritative servers
Recursive resolvers
Stub resolvers
Caching
TTL
Record types
Private/public views
```

You should also understand the meaning of:

```text
A
AAAA
CNAME
MX
TXT
NS
SOA
PTR
SRV
CAA
```

and the purpose of:

```text
/etc/hosts
/etc/resolv.conf
dig
nslookup
host
getent
```

The most important troubleshooting lesson is:

```text
"Hostname does not work"
is not a diagnosis.
```

Break the problem into precise questions:

```text
Is the hostname correct?
        |
        v
Is there a local /etc/hosts override?
        |
        v
Which resolver is being used?
        |
        v
Can that resolver be reached?
        |
        v
What DNS status is returned?
        |
        +--> NXDOMAIN
        |     Name does not exist
        |
        +--> SERVFAIL
        |     Resolver failed
        |
        +--> Timeout
        |     No useful response
        |
        v
What record type exists?
        |
        v
Is there a CNAME chain?
        |
        v
What does authoritative DNS say?
        |
        v
Could caching or TTL explain differences?
        |
        v
Is this private or split-horizon DNS?
        |
        v
Does DNS resolve correctly now?
        |
        v
If yes, move on to routing,
TCP/UDP, TLS, and the application.
```

Once you can follow that path, DNS stops being a mysterious background service. You can determine whether the failure is local configuration, resolver reachability, caching, delegation, authoritative DNS, private DNS, Kubernetes DNS, or something completely outside DNS.
