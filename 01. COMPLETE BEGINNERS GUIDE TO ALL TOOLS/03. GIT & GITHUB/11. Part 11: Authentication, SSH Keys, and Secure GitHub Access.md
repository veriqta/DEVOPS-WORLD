# 1. Why GitHub Authentication Is Required

Imagine GitHub accepted every request without verifying identity.

Someone could potentially attempt:

```text
Delete repositories
Push malicious code
Read private repositories
Modify infrastructure code
Change CI/CD pipelines
Access company projects
Create releases
Modify configuration
```

GitHub therefore needs to establish who is making protected requests.

This is authentication.

A simple definition:

```text
Authentication
=
Proving who you are
```

For example:

```text
Computer
   |
   | Presents credential
   v
GitHub
   |
   | Verifies credential
   v
Identity established
```

---

# 2. Authentication vs Authorization

These terms are related but different.

## Authentication

Authentication asks:

```text
Who are you?
```

## Authorization

Authorization asks:

```text
What are you allowed to do?
```

For example:

```text
You authenticate successfully.

GitHub knows:

You = Engineer A
```

But that does not automatically mean you can modify every repository on GitHub.

GitHub must also determine:

```text
Does Engineer A have write access
to this repository?
```

That is authorization.

Think:

```text
Authentication
      |
      v
Who are you?
      |
      v
Authorization
      |
      v
What can you do?
```

# 5. Your Remote URL Determines the Connection Method

Remember from Part 10:

HTTPS remote:

```text
https://github.com/USERNAME/REPOSITORY.git
```

SSH remote:

```text
git@github.com:USERNAME/REPOSITORY.git
```

```bash
git remote -v
```

You might see:

```text
origin  https://github.com/USERNAME/project.git (fetch)
origin  https://github.com/USERNAME/project.git (push)
```

That repository is configured to communicate using HTTPS.

Or:

```text
origin  git@github.com:USERNAME/project.git (fetch)
origin  git@github.com:USERNAME/project.git (push)
```

That repository is configured to communicate using SSH.

# 6. Why Authentication May Not Be Required for Every Operation

Consider a public repository.

You may be able to run:

```bash
git clone https://github.com/OWNER/REPOSITORY.git
```

without authenticating because the repository is publicly readable.

But attempting:

```bash
git push
```

requires GitHub to determine whether you have permission to modify the repository.

Similarly, accessing a private repository requires authentication because GitHub first needs to determine whether you are allowed to see it.

---

# 7. GitHub Password Authentication Changed

Older Git tutorials may show something like:

```text
Username: your-username
Password: your-github-password
```

for HTTPS Git operations.

That is outdated.

GitHub removed password-based authentication for Git operations over HTTPS.

Your normal GitHub account password is therefore not the credential you should enter when Git requests a password during an HTTPS Git authentication flow.

This is extremely important because beginners often follow old tutorials and think their GitHub account is broken.

# 10. Personal Access Tokens

A personal access token, commonly abbreviated:

```text
PAT
```

is a credential that can be used to authenticate certain operations instead of using your GitHub account password.

Think:

```text
GitHub account password
!=
Personal access token
```

A token is specifically created for programmatic or command-line access.

---

# 11. Why Tokens Are Better Than Reusing Your Password

Tokens provide capabilities that ordinary password reuse does not.

Depending on token type and configuration, tokens can be:

* Limited in scope
* Restricted to specific repositories
* Given selected permissions
* Assigned expiration dates
* Revoked independently

This supports the security principle:

```text
Least privilege
```

Least privilege means:

```text
Give a credential only the access
it actually needs.
```

---

# 12. Fine-Grained Personal Access Tokens

GitHub supports fine-grained personal access tokens.

These allow more precise control over access.

For example, rather than creating a credential with broad access to everything, you may be able to limit a token to:

```text
Selected repositories

Specific permissions

Specific expiration
```

Conceptually:

```text
TOKEN

Repository access:
    devops-lab

Permissions:
    Contents: read/write

Expiration:
    configured date
```

This is much safer than unnecessarily broad credentials.

---

# 13. Token Permissions Matter

Imagine a token only needs to read repository contents.

Giving it broad administrative permissions would violate least privilege.

Think:

```text
TASK

Clone/read repository
       |
       v
NEEDED PERMISSION

Read
```

Do not automatically choose every available permission.

Ask:

```text
What does this credential actually need to do?
```

---

# 14. Personal Access Tokens Are Secrets

A personal access token should be treated like a password.

Never:

```text
Commit it

Paste it into README.md

Put it in a public issue

Post it in screenshots

Store it in source code

Send it in chat

Publish it in documentation
```

If someone obtains a valid token, they may be able to perform actions using the permissions granted to that token.

# 19. What Is SSH?

SSH stands for:

```text
Secure Shell
```

SSH is a protocol for secure communication over a network.

It is commonly associated with remote server access:

```bash
ssh user@server
```

But SSH can also authenticate Git operations.

For GitHub:

```text
Your computer
      |
      | SSH
      v
GitHub
```

SSH can provide secure authentication without repeatedly typing a GitHub token.

---

# 20. SSH Is Bigger Than GitHub

SSH is not a GitHub technology.

You may use SSH to:

```text
Connect to Linux servers

Manage cloud virtual machines

Transfer files

Create secure tunnels

Authenticate Git operations

Run remote commands
```

For a DevOps engineer, SSH is one of the most important foundational technologies to understand.

---

# 21. SSH Authentication With GitHub

GitHub SSH authentication relies on public-key cryptography.

Instead of sending a normal password, you use a cryptographic key pair.

The pair consists of:

```text
Private key

Public key
```

They work together.

---

# 22. Public and Private Keys

Think of the pair as:

```text
PRIVATE KEY
|
| stays on your machine
|
+----------------------+
                       |
                       | mathematically related
                       |
+----------------------+
|
PUBLIC KEY
|
| can be given to GitHub
```

The public key is designed to be shared.

The private key must be protected.

---

# 23. The Most Important SSH Rule

Never share your private key.

Never upload it to GitHub.

Never commit it.

Never email it.

Never paste it into documentation.

Never put it into Slack or chat.

Never place it in a public repository.

The private key represents your side of the authentication relationship.

---

# 24. Which Key Goes to GitHub?

You add:

```text
PUBLIC KEY
```

to GitHub.

Not:

```text
PRIVATE KEY
```

For a common Ed25519 key pair:

```text
~/.ssh/id_ed25519
```

is the private key.

```text
~/.ssh/id_ed25519.pub
```

is the public key.

Notice:

```text
.pub
```

The `.pub` file is the public key.

---

# 25. SSH Authentication Mental Model

Suppose GitHub stores your public key.

Your machine holds the private key.

Conceptually:

```text
YOUR COMPUTER

Private Key
     |
     v
Prove possession
     |
     v
================ NETWORK ================
     |
     v
GITHUB

Stored Public Key
     |
     v
Verify proof
     |
     v
Identity established
```

Your private key does not need to be uploaded to GitHub.

---

# 26. Why This Is Powerful

Suppose an attacker intercepts network traffic.

Your private key is not simply transmitted to GitHub as a password.

SSH uses cryptographic challenge/response mechanisms to prove possession of the private key.

This is one reason SSH key authentication is widely used.

---

# 27. Before Generating a Key

Do not immediately create another key.

First check whether your machine already has SSH keys.

Run:

```bash
ls -la ~/.ssh
```

Break it down.

```text
ls
```

lists directory contents.

```text
-l
```

uses long format.

```text
-a
```

includes hidden entries.

```text
~/.ssh
```

refers to the SSH configuration directory inside your home directory.

---

# 28. Understanding ~

In Unix-like systems:

```text
~
```

usually refers to your home directory.

For example:

```text
/home/ann
```

on Linux.

Or something like:

```text
/Users/ann
```

on macOS.

Therefore:

```text
~/.ssh
```

means:

```text
your-home-directory/.ssh
```

---

# 29. Why Is .ssh Hidden?

Files and directories beginning with:

```text
.
```

are normally hidden from standard directory listings on Unix-like systems.

Therefore:

```text
.ssh
```

is a hidden directory.

This does not mean it is encrypted.

Hidden means it is not normally shown by a basic:

```bash
ls
```

command.

---

# 30. What ~/.ssh Contains

Depending on your system and usage, it may contain files such as:

```text
~/.ssh/
├── id_ed25519
├── id_ed25519.pub
├── config
├── known_hosts
└── authorized_keys
```

Not every machine will contain all of these.

---

# 31. Understanding Common SSH Files

## `id_ed25519`

Common private SSH key filename.

Treat as secret.

## `id_ed25519.pub`

Corresponding public key.

This is the key you may add to GitHub.

## `config`

Optional SSH client configuration.

## `known_hosts`

Stores information about hosts your SSH client has encountered and trusted according to the SSH host-verification process.

## `authorized_keys`

Commonly used on SSH servers to specify public keys allowed to authenticate to an account.

You may not have this file on your laptop simply because you use SSH as a client.

---

# 32. Do Not Delete Unknown SSH Files

Your `.ssh` directory may already contain keys used for:

```text
Cloud servers

EC2 instances

Company infrastructure

Git hosting

Other systems
```

Do not blindly delete or overwrite SSH files.

First understand what they are used for.

---

# 33. Generating a New SSH Key

A commonly recommended modern SSH key type for GitHub is:

```text
Ed25519
```

You can generate one with:

```bash
ssh-keygen -t ed25519 -C "your_email@example.com"
```

Use an email address associated with your context.

---

# 34. Understanding ssh-keygen

Command:

```bash
ssh-keygen -t ed25519 -C "your_email@example.com"
```

Breakdown:

```text
ssh-keygen
```

is the SSH key generation utility.

```text
-t
```

specifies the key type.

```text
ed25519
```

selects the Ed25519 key algorithm.

```text
-C
```

adds a comment.

```text
"your_email@example.com"
```

becomes the comment associated with the key.

The comment can help identify the key.

---

# 35. The Email Comment Is Not the Authentication Secret

The email in:

```bash
ssh-keygen -t ed25519 -C "your_email@example.com"
```

does not make the key secure.

It is primarily a label/comment.

Authentication depends on the cryptographic key material.

---

# 36. Running ssh-keygen

Run:

```bash
ssh-keygen -t ed25519 -C "your_email@example.com"
```

You may see something similar to:

```text
Generating public/private ed25519 key pair.

Enter file in which to save the key:
```

If you accept the default, the key may be stored as:

```text
~/.ssh/id_ed25519
```

with public key:

```text
~/.ssh/id_ed25519.pub
```

---

# 37. Be Careful About Existing Keys

Suppose:

```text
~/.ssh/id_ed25519
```

already exists.

Do not overwrite it without understanding what it is used for.

You may instead choose a descriptive filename such as:

```text
~/.ssh/id_ed25519_github
```

which would produce:

```text
~/.ssh/id_ed25519_github
~/.ssh/id_ed25519_github.pub
```

Multiple-key setups require additional SSH configuration in some situations, but naming keys carefully prevents accidental destruction of existing credentials.

---

# 38. SSH Key Passphrases

During key generation, you may be asked:

```text
Enter passphrase
```

A passphrase provides additional protection for the private key.

Think:

```text
Private key
+
Passphrase
=
Additional protection
```

If someone steals the private-key file, a strong passphrase creates another barrier.

---

# 39. Private Key Passphrase vs GitHub Password

These are not the same thing.

```text
GitHub account password
```

protects your GitHub account login.

```text
SSH key passphrase
```

protects your private key.

When SSH asks for:

```text
Enter passphrase for key...
```

it is asking for the key's passphrase.

It is not asking for your GitHub account password.

# 41. Inspecting the Public Key


# 42. Do Not Run cat on Your Private Key for Sharing


```text

```

```text
.pub
```

when using the standard file naming convention.

# 47. Testing SSH Connectivity

After adding your public key, test the connection:

```bash
ssh -T git@github.com
```

Breakdown:

```text
ssh
```

runs the SSH client.

```text
-T
```

disables pseudo-terminal allocation for this connection.

```text
git@github.com
```

means connect to GitHub's SSH service as the `git` SSH user.

# 48. Why [git@github.com](mailto:git@github.com)?

Beginners sometimes think:

```text
git
```

must be their GitHub username.

It is not.

GitHub's SSH Git connection uses:

```text
git@github.com
```

Your identity is determined through the SSH key used for authentication.

Do not replace:

```text

```

with your GitHub username when using GitHub's standard SSH repository URLs.

# 49. First SSH Connection and Host Verification

On your first connection, SSH may tell you that the authenticity of the host cannot yet be established and display a host-key fingerprint.

Do not blindly type:

```text
yes
```

whenever SSH shows an unknown host.

Host verification protects against connecting to an unexpected system.

For GitHub, compare the displayed fingerprint with GitHub's officially published SSH host fingerprints before trusting a first-time connection.

After successful verification, the host information is normally recorded in:

```text
~/.ssh/known_hosts
```

---

# 50. Successful GitHub SSH Test

A successful test will identify your GitHub account and explain that GitHub does not provide shell access through this connection.

The important information is:

```text
Authentication succeeded.
```

This means your SSH authentication setup is working.

---

# 51. SSH Test May Return a Non-Zero Exit Status

Do not assume every non-zero shell status means authentication failed.

GitHub's SSH endpoint is intended for Git operations rather than interactive shell access.

The actual authentication message is important.

Read the output instead of judging success only from whether you received a shell prompt.

---

# 52. What Is an SSH Agent?

If your private key has a passphrase, typing it for every operation can become repetitive.

An SSH agent is a process that manages private keys for SSH authentication.

Conceptually:

```text
SSH Private Key
      |
      v
SSH Agent
      |
      v
ssh / Git operation
      |
      v
GitHub
```

The agent can keep unlocked key material available during your session so you do not repeatedly enter the passphrase.

---

# 53. Starting ssh-agent

On many Unix-like environments, you may use:

```bash
eval "$(ssh-agent -s)"
```

You may see:

```text
Agent pid 12345
```

Breakdown:

```text
ssh-agent -s
```

starts the agent and prints shell commands needed to configure environment variables.

```text
$(...)
```

captures command output.

```text
eval
```

executes the resulting shell configuration.

The exact setup can vary by operating system and desktop environment.

---

# 54. Adding a Key to the Agent

Run:

```bash
ssh-add ~/.ssh/id_ed25519
```

If the key has a passphrase, you may be asked for it.

After successful addition, the agent can use that key for SSH authentication.

If you used a custom filename:

```bash
ssh-add ~/.ssh/id_ed25519_github
```

Use the private-key filename.

Not:

```text
.pub
```

The agent uses the private key.

---

# 55. Public Key to GitHub, Private Key to ssh-agent

This is worth memorizing:

```text
PUBLIC KEY
id_ed25519.pub
      |
      v
GITHUB
```

while:

```text
PRIVATE KEY
id_ed25519
      |
      v
SSH AGENT
```

Do not reverse them.

# 56. Listing Keys in the Agent

You can inspect identities currently available to the agent with:

```bash
ssh-add -l
```

The lowercase:

```text
-l
```

means list fingerprints of identities.

This can help answer:

```text

```

# 59. Private-Key File Permissions

Your private key must be protected from unauthorized local access.

On Unix-like systems, SSH may reject a private key if its permissions are too open.

A common secure permission is:

```bash
chmod 600 ~/.ssh/id_ed25519
```

You encountered this style of command earlier in the course.

Now let us explain exactly what it means.

---

# 60. Understanding chmod 600

Command:

```bash
chmod 600 ~/.ssh/id_ed25519
```

Breakdown:

```text
chmod
```

means change file mode or permissions.

```text
600
```

represents:

```text
Owner: read + write
Group: no permissions
Others: no permissions
```

Symbolically:

```text
rw-------
```

This means only the file owner can read and modify the private key.

---

# 61. Why Private-Key Permissions Matter

Imagine:

```text
Private key
+
Readable by other local users
```

That increases the risk of credential theft.

SSH may warn:

```text
WARNING: UNPROTECTED PRIVATE KEY FILE!
```

and refuse to use the key.

That behavior is protective.

---

# 62. Verify Key Permissions

Run:

```bash
ls -l ~/.ssh/id_ed25519
```

You might see:

```text
-rw-------  1 user user ... id_ed25519
```

Focus on:

```text
-rw-------
```

The owner can:

```text
read
write
```

Group and others have no permissions.

---

# 63. Directory Permissions

The `.ssh` directory itself should also be protected appropriately.

A commonly used setting is:

```bash
chmod 700 ~/.ssh
```

`700` means:

```text
Owner: read + write + execute
Group: none
Others: none
```

For a directory, execute permission allows traversal/access to entries.

Again, do not randomly change permissions on systems you do not understand.

Verify ownership and environment first.

---

# 64. Public-Key Permissions

Public keys are not secret in the same way.

The important security boundary is:

```text
PRIVATE KEY
```

However, your SSH configuration should still be managed carefully and consistently.

# 66. What git clone Does Here

When you run:

```bash
git clone git@github.com:USERNAME/REPOSITORY.git
```

Git will normally:

```text
Create a local directory

Initialize a Git repository

Download repository history

Download files

Create remote named origin

Configure origin to use the SSH URL

Check out the default branch
```

---

# 67. Verify After Cloning

Move into the repository:

```bash
cd REPOSITORY
```

Then:

```bash
git remote -v
```

You should see an SSH URL similar to:

```text
origin  git@github.com:USERNAME/REPOSITORY.git (fetch)
origin  git@github.com:USERNAME/REPOSITORY.git (push)
```

This proves the repository is configured to communicate with `origin` over SSH.

---

# 68. Test a Real Git Operation

After cloning:

```bash
git fetch origin
```

If SSH authentication works, the fetch should communicate with GitHub.

If you have permission to push and appropriate work to publish, `git push` should also authenticate through SSH.

Remember:

```text
Successful SSH authentication
does not automatically mean
you have write permission.
```

Authentication and authorization remain separate.

---

# 69. Switching an Existing Repository From HTTPS to SSH

Suppose:

```bash
git remote -v
```

shows:

```text
origin  https://github.com/USERNAME/project.git (fetch)
origin  https://github.com/USERNAME/project.git (push)
```

You have already configured SSH and want this repository to use it.

First identify the SSH URL:

```text
git@github.com:USERNAME/project.git
```

Then:

```bash
git remote set-url origin git@github.com:USERNAME/project.git
```

---

# 70. What git remote set-url Does

Command:

```bash
git remote set-url origin <NEW_URL>
```

means:

```text
Find remote:
origin

Replace its URL with:
NEW_URL
```

It does not:

```text
Delete commits

Recreate the repository

Change branches

Upload files
```

It changes remote configuration.

---

# 71. Verify the Change

Run:

```bash
git remote -v
```

Before:

```text
origin  https://github.com/USERNAME/project.git
```

After:

```text
origin  git@github.com:USERNAME/project.git
```

Then test:

```bash
git fetch origin
```

---

# 72. Switching From SSH Back to HTTPS

The opposite is also possible.

Run:

```bash
git remote set-url origin https://github.com/USERNAME/project.git
```

Then verify:

```bash
git remote -v
```

Remote protocols are configuration choices.

You do not need to create a new Git repository just to switch protocols.

# 73. Protecting Credentials

Your Git credentials may provide access to valuable resources.

Treat them as production credentials.

Protect:

```text
Personal access tokens

SSH private keys

API keys

Cloud credentials

Database passwords

Signing keys

Deployment credentials
```

A useful security principle is:

```text
If possession of a value allows someone
to impersonate you or access a system,
treat that value as a secret.
```

---

# 74. Never Commit Secrets

Consider this project:

```text
my-api/
├── app.py
├── README.md
├── .env
└── config.py
```

Suppose `.env` contains:

```text
DATABASE_PASSWORD=real-password
GITHUB_TOKEN=real-token
AWS_SECRET_ACCESS_KEY=real-key
```

Do not commit this file.

---

# 75. Use .gitignore Before Tracking Secret Files

You might add:

```gitignore
.env
*.pem
```

But be careful.

A pattern such as:

```text
*.pem
```

may be too broad for some projects because not every PEM file is necessarily secret.

Ignore rules should reflect your project intentionally.

Do not blindly copy huge `.gitignore` templates without understanding them.

---

# 76. .gitignore Does Not Remove Existing Secrets

Suppose you accidentally do:

```bash
git add .env
git commit -m "Add application configuration"
git push
```

Then later add:

```gitignore
.env
```

The old commit still contains the secret.

Your history may look like:

```text
A
|
+-- .env contains secret
|
v
B
|
+-- .env ignored
```

Commit A still exists.

---

# 77. What to Do After a Secret Is Exposed

The first security question is not:

```text
How do I hide the Git commit?
```

It is:

```text
Is the credential still valid?
```

If a real credential has been exposed, assume it may be compromised.

Depending on the credential:

```text
Revoke it

Rotate it

Create a replacement

Update dependent systems

Investigate where it was exposed
```

Removing the secret from Git history does not make an already exposed credential safe again.

---

# 78. Why Rotation Matters

Suppose an AWS key appears in a public GitHub commit for 30 seconds.

You delete the commit.

Can you prove nobody copied the key?

No.

Therefore:

```text
Exposure
      |
      v
Assume compromised
      |
      v
Revoke/rotate
```

This is an important production security habit.

---

# 79. Do Not Commit SSH Private Keys

Never commit files such as:

```text
id_rsa
id_ed25519
server.pem
private_key.pem
```

if they contain private key material.

An SSH private key in Git history is a serious security incident.

The appropriate response may include:

```text
Revoke/remove corresponding access

Generate replacement keys

Update authorized systems

Investigate exposure

Clean repository history if appropriate
```

# 80. Permission denied (publickey)

One of the most common SSH errors is:

```text
Permission denied (publickey).
```

Beginners often react by generating more keys immediately.

Do not.

Troubleshoot systematically.

---

# 81. What the Error Usually Means

Conceptually:

```text
Your computer
      |
      | Attempts SSH authentication
      v
GitHub
      |
      | No acceptable authentication proof
      v
Permission denied (publickey)
```

Possible causes include:

* No SSH key exists
* Wrong key is being used
* Public key was not added to GitHub
* SSH agent does not have the expected key
* Private key permissions are incorrect
* Wrong GitHub account
* SSH configuration selects another identity
* Organization SSO requirements are not satisfied
* The remote URL or hostname is incorrect

Do not assume one cause.

Gather evidence.

---

# 82. Troubleshooting Step 1: Confirm the Remote Protocol

Run:

```bash
git remote -v
```

If you see:

```text
https://github.com/...
```

then your Git operation is using HTTPS.

An SSH-key problem is probably not the immediate cause of that Git operation failing.

If you see:

```text
git@github.com:...
```

then SSH authentication is relevant.

---

# 83. Troubleshooting Step 2: Test GitHub SSH Directly

Run:

```bash
ssh -T git@github.com
```

If this succeeds but:

```bash
git push
```

fails, the problem may involve:

```text
Repository permissions

Remote URL

Branch permissions

Organization policy
```

rather than basic SSH authentication.

---

# 84. Troubleshooting Step 3: Check for Keys

Run:

```bash
ls -la ~/.ssh
```

Look for likely key pairs:

```text
id_ed25519
id_ed25519.pub
```

or custom names.

Do not assume the first key you see belongs to GitHub.

---

# 85. Troubleshooting Step 4: Check ssh-agent

Run:

```bash
ssh-add -l
```

If the agent reports that it has no identities, your expected key may not be loaded.

Add it:

```bash
ssh-add ~/.ssh/id_ed25519
```

or use the correct custom private-key path.

Then:

```bash
ssh-add -l
```

again.

---

# 86. Troubleshooting Step 5: Check the GitHub Public Key

Display:

```bash
cat ~/.ssh/id_ed25519.pub
```

Compare it with the public key stored under your GitHub SSH settings.

You are checking:

```text
Does GitHub have the public half
of the private key my machine is using?
```

---

# 87. Troubleshooting Step 6: Check File Permissions

Run:

```bash
ls -l ~/.ssh/id_ed25519
```

If the private key is overly permissive on a Unix-like system, correct it when appropriate:

```bash
chmod 600 ~/.ssh/id_ed25519
```

Then test again.

---

# 88. Troubleshooting Step 7: Use Verbose SSH Output

For deeper investigation:

```bash
ssh -vT git@github.com
```

The:

```text
-v
```

option enables verbose diagnostic output.

You may see information about:

```text
Configuration files

Connection establishment

Available identities

Keys being offered

Authentication attempts
```

This is evidence.

Do not randomly change configuration before reading it.

---

# 89. Reading Verbose SSH Conceptually

You may discover:

```text
Offering public key: Key A
```

but GitHub expected:

```text
Key B
```

Now you have a hypothesis:

```text
Wrong identity is being offered.
```

That is far better than:

```text
SSH is broken.
```

Troubleshooting should move from vague symptoms to specific evidence.

---

# 90. Multiple SSH Keys

Engineers sometimes have:

```text
Personal GitHub key

Work GitHub key

AWS server key

GitLab key
```

For example:

```text
~/.ssh/
├── id_ed25519_personal
├── id_ed25519_personal.pub
├── id_ed25519_work
├── id_ed25519_work.pub
└── config
```

In such environments, SSH configuration becomes important.

---

# 91. Basic SSH Config Concept

The file:

```text
~/.ssh/config
```

can define SSH client behavior.

A simple example might look like:

```text
Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519
```

This tells SSH:

```text
When connecting to github.com

Use host:
github.com

Use SSH user:
git

Use identity:
~/.ssh/id_ed25519
```

Do not add configuration unnecessarily if your default setup already works.

---

# 92. Multiple GitHub Accounts Need Careful Configuration

Suppose you use:

```text
Personal GitHub account

Company GitHub account
```

with separate keys.

You may need SSH host aliases and corresponding remote URLs so SSH knows which identity to use.

This is beyond the minimum beginner setup, but the important lesson is:

```text
Multiple accounts
+
Multiple keys
=
Identity selection matters
```

Do not solve this by repeatedly deleting and regenerating keys.

# 93. Common Failure: Wrong GitHub Account

Suppose SSH test identifies:

```text
Account A
```

but the private repository belongs to:

```text
Account B
```

and Account A has no access.

Authentication may be functioning perfectly.

Authorization is the problem.

Ask:

```text
Which GitHub account does this SSH key identify?

Does that account have access to the repository?
```

# 94. Common Failure: Repository Not Found

With HTTPS you might encounter:

```text
Repository not found
```

Possible causes:

```text
Wrong owner

Wrong repository name

Repository deleted

Private repository without access

Wrong authenticated account

Incorrect remote URL
```

Start:

```bash
git remote -v
```

Verify the URL.

Then verify repository access.

---

# 95. Common Failure: Authentication Failed Over HTTPS

Suppose you receive an authentication failure while using:

```text
https://github.com/...
```

Possible causes:

```text
Using normal GitHub password

Expired token

Revoked token

Wrong token

Insufficient token permissions

Cached old credentials

Wrong GitHub account
```

Do not switch to SSH automatically unless you actually want SSH.

Diagnose the HTTPS authentication path first.

---

# 96. Common Failure: Cached Old Credentials

Credential managers can store credentials.

This is useful until the stored credential becomes:

```text
Expired

Revoked

Replaced

Incorrect
```

Then Git may continue presenting an old credential.

The exact removal/update process depends on your operating system and credential manager.

The troubleshooting question becomes:

```text
Which credential is Git actually presenting?
```

not merely:

```text
What credential did I create today?
```

---

# 97. Common Failure: Token Lacks Permission

Authentication can succeed while authorization fails.

For example:

```text
Token valid
      |
      v
Identity recognized
      |
      v
Permission insufficient
      |
      v
Operation denied
```

Remember:

```text
Valid credential
!=
permission to perform every operation
```

---

# 98. Common Failure: Expired Token

Personal access tokens can be configured with expiration.

If a previously working workflow suddenly stops, check whether the token:

```text
Expired

Was revoked

Was rotated

Lost required access
```

Do not simply create unlimited long-lived credentials as the default solution.

Credential lifecycle is part of security.

---

# 99. Common Failure: Organization SSO

Some organizations use SAML single sign-on.

A valid personal access token or SSH key may also need authorization for that organization's SSO environment.

Therefore:

```text
SSH works with personal repository
```

but:

```text
SSH fails for company organization repository
```

can indicate organization-specific access requirements rather than a broken key.

# 100. Common Failure: Wrong Remote URL

Run:

```bash
git remote -v
```

Suppose you intended:

```text
git@github.com:company/platform-api.git
```

but configured:

```text
git@github.com:company/platform-app.git
```

Authentication may work perfectly.

You are simply requesting the wrong repository.

Always verify basic facts before changing security settings.

---

# 101. Common Failure: Private Key Not Found

Suppose your SSH configuration expects:

```text
~/.ssh/id_ed25519
```

but your key is actually:

```text
~/.ssh/id_ed25519_github
```

SSH may not automatically select the expected custom key.

Investigate:

```bash
ssh -vT git@github.com
```

and inspect which identities are being considered.

---

# 102. Common Failure: Passphrase Confusion

You run:

```bash
git push
```

and see:

```text
Enter passphrase for key '/home/user/.ssh/id_ed25519':
```

You enter your GitHub password.

It fails.

Why?

Because SSH is asking for:

```text
SSH PRIVATE KEY PASSPHRASE
```

not:

```text
GitHub account password
```

Understand what each prompt is requesting.

---

# 103. Common Failure: Host Verification Problem

SSH also verifies server identity.

You may encounter messages involving:

```text
Host key verification failed
```

This is different from:

```text
Permission denied (publickey)
```

The first concerns:

```text
Can I trust the server identity?
```

The second concerns:

```text
Can the server authenticate me?
```

Do not treat them as the same problem.

---

# 104. Never Blindly Delete known_hosts Entries

If host verification fails, do not immediately delete:

```text
~/.ssh/known_hosts
```

or disable host checking.

A changed host key can indicate:

```text
Legitimate infrastructure change

Wrong hostname

DNS issue

Proxy/interception

Security problem
```

Investigate before removing trust information.

# 105. Authentication Troubleshooting Model

Use this sequence:

```text
1. Observe exact error
        |
        v
2. Identify protocol
   HTTPS or SSH?
        |
        v
3. Verify remote URL
        |
        v
4. Test authentication
        |
        v
5. Identify credential
        |
        v
6. Verify account identity
        |
        v
7. Verify repository permission
        |
        v
8. Check organization requirements
        |
        v
9. Fix root cause
        |
        v
10. Retest
```

This is far safer than generating random credentials.

# 121. Secure DevOps Context

# 122. What Is Blast Radius?

In security:

```text
Blast radius
```

describes how much can be affected when something goes wrong.

Suppose one private key can access:

```text
GitHub

Production server

Database server

CI server

Monitoring server
```

If that key is stolen, the compromise is much larger.

This is why access should be carefully scoped.

# 123. Least Privilege for Git Credentials

Apply least privilege.

Ask:

```text

Does this automation need access to every repository?

Does this machine need this private key?

Does this user need administrative access?

Does this credential need to live forever?
```

Secure systems intentionally minimize access.

A developer's personal SSH key should not automatically become the credential used by production automation.

For example:

```text

|
+--> Personal authentication

CI/CD
|
+--> Workflow/service identity

Production
|
+--> Deployment identity
```

Separating identities improves auditing and reduces risk.

You will learn these concepts more deeply when studying CI/CD.

The principle for now:

```text
Configuration can be committed.

Secrets should be injected securely.
```

# 131. Part 11 Final Recap

Your GitHub model now expands again.

In Part 10:

```text
Local Repository
      |
      | git push
      v
GitHub
```

But the real interaction contains another layer:

```text
Local Repository
      |
      | git push
      v
Authentication
      |
      v
Authorization
      |
      v
GitHub Repository
```

Authentication asks:

```text
WHO ARE YOU?
```

Authorization asks:

```text
WHAT ARE YOU ALLOWED TO DO?
```

For HTTPS, remember:

```text
Normal GitHub password
!=
Git HTTPS authentication credential
```

Modern HTTPS authentication may use mechanisms such as personal access tokens and credential managers.

For SSH, your model is:

```text
YOUR COMPUTER
      |
      |
PRIVATE KEY
      |
      | cryptographic authentication
      v
GITHUB
      |
      |
PUBLIC KEY
      |
      v
ACCOUNT IDENTITY
      |
      v
AUTHORIZATION
      |
      v
REPOSITORY
```

The most important SSH security rule is:

```text
PRIVATE KEY
=
NEVER SHARE
```

while:

```text
PUBLIC KEY
=
CAN BE ADDED TO GITHUB
```

A common key pair looks like:

```text
~/.ssh/id_ed25519
```

Private.

And:

```text
~/.ssh/id_ed25519.pub
```

Public.

You can generate a modern Ed25519 key with:

```bash
ssh-keygen -t ed25519 -C "your_email@example.com"
```

You can add the private key to an SSH agent:

```bash
ssh-add ~/.ssh/id_ed25519
```

and test GitHub authentication:

```bash
ssh -T git@github.com
```

For a repository using SSH:

```text
git@github.com:USERNAME/REPOSITORY.git
```

Git can use the SSH authentication relationship for:

```text
clone
fetch
pull
push
```

You also learned that:

```text
Permission denied (publickey)
```

should not trigger random commands.

Use evidence:

```text
Check remote
      |
      v
Check protocol
      |
      v
Test SSH
      |
      v
Check keys
      |
      v
Check agent
      |
      v
Check GitHub public key
      |
      v
Check permissions
      |
      v
Use verbose diagnostics
      |
      v
Check authorization
```

And above all:

```text
NEVER COMMIT SECRETS
```

including:

```text
Personal access tokens
SSH private keys
Cloud credentials
Database passwords
API keys
Production secrets
```

If a real credential is exposed, deleting the visible file is not enough.

Think:

```text
Credential exposed
       |
       v
Assume compromise
       |
       v
Revoke / rotate
       |
       v
Replace
       |
       v
Investigate
       |
       v
Prevent recurrence
```
