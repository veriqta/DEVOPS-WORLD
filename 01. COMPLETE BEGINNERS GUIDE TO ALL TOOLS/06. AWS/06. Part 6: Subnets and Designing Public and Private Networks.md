# Part 6: Subnets and Designing Public and Private Networks

In Part 5, you created a VPC:

```text
AWS Region
|
└── VPC 10.0.0.0/16
    |
    ├── Availability Zone A
    |
    └── Availability Zone B
```

The VPC gives you a large private network range:

```text
10.0.0.0/16
```

That range contains:

```text
65,536 total IPv4 addresses
```

But putting every workload into one giant flat network would be poor design.

You may need:

* Internet-facing load balancers
* Application servers
* Databases
* Internal services
* Management systems
* Containers
* Monitoring tools

These resources have different connectivity and security requirements.

That is why we divide a VPC into smaller networks called subnets.

By the end of this part, you should understand:

* What a subnet is
* Why networks are divided
* How subnet CIDR ranges work
* How a subnet relates to a VPC
* Why each subnet belongs to one Availability Zone
* Public subnets
* Private subnets
* What actually makes a subnet public
* Public IP assignment
* AWS-reserved addresses
* IP allocation
* Multi-AZ design
* Web, application, and database subnet patterns
* Common subnet mistakes
* How to design and build a multi-AZ subnet architecture

Our target architecture is:

```text
VPC 10.0.0.0/16
|
├── Availability Zone A
│   ├── Public Subnet
│   └── Private Subnet
│
└── Availability Zone B
    ├── Public Subnet
    └── Private Subnet
```

Later we will add:

```text
Internet Gateway
Route Tables
NAT Gateways
Security Groups
Load Balancers
EC2
RDS
```

But first, we need the subnet structure itself.

---

# 1. What Is a Subnet?

Subnet is short for:

Subnetwork.

A subnet is a smaller IP network created inside a larger network.

In AWS, a subnet is created inside a VPC.

Think:

```text
VPC
10.0.0.0/16
|
+-- Subnet A
    10.0.1.0/24
|
+-- Subnet B
    10.0.2.0/24
```

The VPC provides the larger address space.

The subnet takes a portion of that space.

---

# 2. Why Divide a Network?

Imagine a company building.

Instead of putting everyone in one enormous room, the building is divided into:

```text
Reception
Engineering
Finance
Server Room
Management
```

Each area serves a different purpose.

Networks are divided for similar reasons.

A VPC may contain:

```text
Internet-facing resources
Application servers
Databases
Internal services
Management systems
```

You probably do not want all of these resources treated identically.

Subnetting gives you structure.

---

# 3. Reasons to Create Subnets

Subnets help with:

* Availability design
* Network organization
* Routing
* Security boundaries
* IP address management
* Application-tier separation
* Public/private architecture
* Troubleshooting

For example:

```text
Public Subnet
|
Load Balancer
```

and:

```text
Private Subnet
|
Application Servers
```

give different network roles to different infrastructure components.

---

# 4. Subnet Relationship to a VPC

Suppose your VPC is:

```text
10.0.0.0/16
```

You could divide it into subnets such as:

```text
10.0.1.0/24

10.0.2.0/24

10.0.11.0/24

10.0.12.0/24
```

All of those ranges belong inside:

```text
10.0.0.0/16
```

This is required.

A subnet CIDR must fit inside the VPC address space.

---

# 5. Invalid Subnet Example

Suppose:

```text
VPC
10.0.0.0/16
```

You try to create:

```text
Subnet
10.1.1.0/24
```

This does not belong inside:

```text
10.0.0.0/16
```

The VPC range is:

```text
10.0.0.0
through
10.0.255.255
```

But:

```text
10.1.1.0
```

is outside that range.

Therefore, it cannot be used as a subnet CIDR inside that VPC.

---

# 6. Subnet CIDR Ranges

A subnet also uses CIDR notation.

Example:

```text
10.0.1.0/24
```

This gives:

```text
256 total IPv4 addresses
```

Another:

```text
10.0.2.0/24
```

also gives:

```text
256 total IPv4 addresses
```

The two ranges are separate:

```text
10.0.1.0
through
10.0.1.255
```

and:

```text
10.0.2.0
through
10.0.2.255
```

They do not overlap.

---

# 7. Subnets Must Not Overlap

Suppose you create:

```text
Subnet A
10.0.1.0/24
```

and then try:

```text
Subnet B
10.0.1.128/25
```

Do they overlap?

Yes.

Why?

Because:

```text
10.0.1.0/24
```

already includes:

```text
10.0.1.0
through
10.0.1.255
```

And:

```text
10.0.1.128/25
```

falls inside that range.

AWS will not allow overlapping subnets inside the same VPC.

---

# 8. How Many Addresses Does a `/24` Have?

Remember:

```text
IPv4 = 32 bits
```

For:

```text
/24
```

there are:

```text
32 - 24
=
8 host bits
```

Therefore:

```text
2^8
=
256 total addresses
```

But in AWS, not all 256 are usable by your resources.

We will explain why shortly.

---

# 9. Why Use `/24` for Beginner Subnets?

A `/24` is easy to understand.

It gives:

```text
256 total addresses
```

and has a clear range.

Example:

```text
10.0.10.0/24
```

means:

```text
10.0.10.0
through
10.0.10.255
```

This makes `/24` useful for learning.

Production subnet sizing should be based on actual requirements rather than simply using `/24` everywhere.

---

# 10. Subnets Belong to Availability Zones

This is one of the most important AWS networking rules.

A VPC spans Availability Zones in a Region.

A subnet does not.

A subnet belongs to exactly one Availability Zone.

Think:

```text
VPC
10.0.0.0/16
|
+-- AZ-A
|    |
|    +-- Subnet A
|
+-- AZ-B
     |
     +-- Subnet B
```

Not:

```text
One subnet
spanning
AZ-A and AZ-B
```

That is not how AWS subnets work.

---

# 11. Why Are Subnets AZ-Specific?

Availability Zones represent separate failure domains.

By placing subnets in different AZs, you can distribute workloads.

Example:

```text
AZ-A
|
App Server A
```

and:

```text
AZ-B
|
App Server B
```

If one AZ experiences a failure:

```text
AZ-A
Unavailable
```

the application may still run from:

```text
AZ-B
```

if the architecture was designed correctly.

This supports high availability.

---

# 12. Multi-AZ Design

A multi-AZ architecture uses infrastructure across multiple Availability Zones.

Our beginner VPC will use:

```text
AZ-A

AZ-B
```

Each AZ will have separate subnets.

Example:

```text
VPC 10.0.0.0/16
|
├── AZ-A
│   ├── 10.0.1.0/24
│   └── 10.0.11.0/24
│
└── AZ-B
    ├── 10.0.2.0/24
    └── 10.0.12.0/24
```

This gives us room to place workloads in both AZs.

---

# 13. What Is a Public Subnet?

A public subnet is a subnet whose route table has a route to an Internet Gateway.

This definition is important.

A subnet is not public simply because:

* Its name contains `public`.
* An EC2 instance inside it has a public IP.
* It exists in a VPC.
* It contains an internet-facing server.

The routing is what makes it public.

The core condition is:

```text
Subnet Route Table
|
Destination:
0.0.0.0/0
|
Target:
Internet Gateway
```

We will configure this fully in Part 7.

---

# 14. What Does `0.0.0.0/0` Mean?

`0.0.0.0/0` represents all IPv4 destinations.

Think:

```text
0.0.0.0/0
=
Anywhere in IPv4 address space
```

If a subnet route table contains:

```text
Destination: 0.0.0.0/0
Target: Internet Gateway
```

then internet-bound IPv4 traffic has a route toward the Internet Gateway.

This is a major characteristic of a public subnet.

---

# 15. What Actually Makes a Subnet Public?

This deserves repetition because it is one of the most common AWS networking misunderstandings.

A subnet becomes public when its associated route table contains a route to an Internet Gateway.

Conceptually:

```text
Public Subnet
     |
     v
Route Table
     |
     v
0.0.0.0/0
     |
     v
Internet Gateway
```

But that does not mean every resource inside the subnet is automatically internet reachable.

The resource may still need:

* A public IP or other public addressing mechanism
* Correct Security Group rules
* Correct Network ACL behavior
* A listening service

Public subnet does not mean:

```text
Everything exposed.
```

---

# 16. What Is a Private Subnet?

A private subnet does not have a direct route to an Internet Gateway for internet-bound traffic.

Conceptually:

```text
Private Subnet
     |
     v
No direct IGW route
```

Resources inside may use private IP addresses only.

Examples include:

* Application servers
* Databases
* Internal services

Private subnets are commonly used to reduce direct internet exposure.

---

# 17. Private Does Not Mean "No Internet Access Ever"

This is another common misunderstanding.

A private subnet can still allow outbound internet access through mechanisms such as a NAT Gateway.

Example:

```text
Private EC2
    |
    v
Private Route Table
    |
    v
NAT Gateway
    |
    v
Internet Gateway
    |
    v
Internet
```

This allows the private resource to initiate outbound traffic while avoiding direct public exposure in the normal pattern.

We will study NAT Gateways later.

---

# 18. Public vs Private Subnet

A simplified comparison:

| Public Subnet                                            | Private Subnet                        |
| -------------------------------------------------------- | ------------------------------------- |
| Has a direct route to Internet Gateway                   | No direct route to Internet Gateway   |
| Often contains internet-facing components                | Often contains internal workloads     |
| Resource may have public IP                              | Resource usually uses private IP only |
| Common for load balancers, bastions, some public servers | Common for app servers and databases  |
| Still requires security rules                            | Still requires security rules         |

The key difference is routing.

---

# 19. Public Subnet Does Not Mean Public Resource

Suppose:

```text
Public Subnet
|
EC2
```

The EC2 instance has:

```text
Private IP only
```

and no public address.

Even though the subnet is public, the instance is not directly reachable from the public internet using a public IPv4 address because it has none.

Think:

```text
Public Subnet
does not automatically equal
Public Resource
```

---

# 20. Public IP Assignment

When launching EC2 into a subnet, you may configure automatic public IPv4 assignment.

A subnet can have a setting such as:

```text
Auto-assign public IPv4
```

If enabled, supported EC2 launches may automatically receive a public IPv4 address.

Conceptually:

```text
EC2 Launch
   |
Subnet Setting
   |
Auto-assign public IP?
   |
Yes
   |
EC2 gets public IPv4
```

This is independent from the route-table definition of whether the subnet itself is public.

---

# 21. Route + Public IP + Security

For a public EC2 instance to accept internet traffic, several things generally need to align:

```text
Public IP
+
Public Subnet Route
+
Internet Gateway
+
Security Group
+
Running Service
```

For example:

```text
Internet
   |
Internet Gateway
   |
Public Route Table
   |
Public Subnet
   |
Security Group permits TCP 80
   |
EC2 with public address
   |
Nginx
```

If one required layer fails, connectivity can fail.

---

# 22. Why Use Public Subnets?

Public subnets are useful for resources that need direct or edge-facing internet connectivity.

Common examples include:

* Internet-facing Application Load Balancers
* NAT Gateways
* Bastion hosts in some architectures
* Certain public-facing servers

A public subnet should not become:

```text
Put everything here because it works.
```

Use it where public network connectivity is actually required.

---

# 23. Why Use Private Subnets?

Private subnets are useful for workloads that do not need direct inbound internet access.

Examples:

* Application servers behind a load balancer
* Databases
* Internal APIs
* Worker nodes
* Backend systems

Architecture:

```text
Internet
   |
Load Balancer
   |
Private App Servers
   |
Private Database
```

Only the entry layer needs to face the internet.

The internal layers remain private.

---

# 24. Three-Tier Architecture

A common application pattern is:

```text
Web Tier

Application Tier

Database Tier
```

Each tier has a different purpose.

---

# 25. Web Tier

The web tier receives user-facing traffic.

Modern AWS applications commonly place an internet-facing load balancer in public subnets.

Conceptually:

```text
Internet
   |
Public Load Balancer
```

The actual application servers can remain private behind it.

---

# 26. Application Tier

The application tier runs application logic.

Example:

```text
Load Balancer
     |
     v
Application Servers
```

These servers often do not need direct inbound internet access.

They can live in private subnets.

---

# 27. Database Tier

The database tier stores application data.

Example:

```text
Application Servers
       |
       v
    Database
```

The database generally should not be directly accessible from the public internet unless there is a specific justified design.

A common architecture is:

```text
Internet
   |
Load Balancer
   |
Private App Tier
   |
Private Database Tier
```

---

# 28. Why Separate Application and Database Networks?

Even if both tiers are private, separating them can improve:

* Network organization
* Routing control
* Security design
* Troubleshooting
* Database subnet requirements
* Future policy control

Instead of:

```text
Private Subnet
|
App + Database + Everything
```

you can design:

```text
Private App Subnet

Private DB Subnet
```

for clearer architecture.

---

# 29. Our Beginner Architecture vs Full Three-Tier Architecture

For this part, the required architecture is:

```text
VPC
├── AZ-A
│   ├── Public Subnet
│   └── Private Subnet
│
└── AZ-B
    ├── Public Subnet
    └── Private Subnet
```

That gives four subnets.

Later, we may expand to six:

```text
VPC
├── AZ-A
│   ├── Public Subnet
│   ├── Private App Subnet
│   └── Private DB Subnet
│
└── AZ-B
    ├── Public Subnet
    ├── Private App Subnet
    └── Private DB Subnet
```

The four-subnet model is easier for beginning.

The six-subnet model is more explicit for multi-tier production design.

# 30. Designing Subnet CIDRs

Our VPC is:

```text
10.0.0.0/16
```

We need four `/24` subnets.

One clean design is:

```text
Public AZ-A
10.0.1.0/24

Public AZ-B
10.0.2.0/24

Private AZ-A
10.0.11.0/24

Private AZ-B
10.0.12.0/24
```

This is easy to recognize.

---

# 31. Why Use Structured Numbering?

The pattern:

```text
1
2
```

for public subnets and:

```text
11
12
```

for private subnets makes the role visible.

Example:

```text
10.0.1.0/24
Public A

10.0.2.0/24
Public B

10.0.11.0/24
Private A

10.0.12.0/24
Private B
```

There is no universal rule requiring this.

It is simply a clear naming and addressing convention.

---

# 32. Another Valid Addressing Pattern

You could instead use:

```text
10.0.10.0/24
Public A

10.0.20.0/24
Public B

10.0.110.0/24
Private A

10.0.120.0/24
Private B
```

Or:

```text
10.0.0.0/24
Public A

10.0.1.0/24
Public B

10.0.10.0/24
Private A

10.0.11.0/24
Private B
```

The main requirements are:

* Inside the VPC range
* No overlap
* Enough capacity
* Clear design
* Future expansion considered

---

# 33. Design for Future Growth

Do not allocate every subnet range randomly.

Suppose you later need:

```text
Private Database A
Private Database B
```

If you planned ahead, you can add:

```text
10.0.21.0/24
10.0.22.0/24
```

Architecture:

```text
Public
1, 2

Application
11, 12

Database
21, 22
```

This gives a simple pattern.

VPC 10.0.0.0/16

10.0.1.0/24

10.0.2.0/24

# 35. AWS Reserved IP Addresses in Subnets

AWS reserves five IPv4 addresses in every subnet.

These addresses cannot be assigned to normal resources.

For a subnet:

```text
10.0.1.0/24
```

AWS reserves the first four addresses and the final address.

Specifically:

```text
10.0.1.0
Network address

10.0.1.1
VPC router

10.0.1.2
DNS-related use

10.0.1.3
Reserved by AWS

10.0.1.255
Reserved by AWS
```

Therefore a `/24` does not provide 256 assignable addresses.

---

# 36. Usable Address Count in AWS

A `/24` has:

```text
256 total IPv4 addresses
```

AWS reserves:

```text
5
```

Therefore:

```text
256 - 5
=
251 usable IPv4 addresses
```

for supported resource allocation.

This matters when planning subnet capacity.

---

# 37. Small Subnets and Reserved Addresses

Consider:

```text
/28
```

A `/28` contains:

```text
16 total addresses
```

AWS reserves five.

Therefore:

```text
16 - 5
=
11 usable addresses
```

That is a very small subnet.

If several resources consume addresses, it can fill quickly.

---

# 38. Why Subnet Capacity Matters

Many AWS resources consume subnet IP addresses.

Examples may include:

* EC2 network interfaces
* Load balancers
* RDS
* Container networking
* Kubernetes Pods in some networking models
* VPC endpoints

If you undersize a subnet, you may eventually encounter:

```text
Insufficient free addresses
```

This can prevent:

* Scaling
* Instance launches
* Load balancer growth
* Container scheduling
* Database operations

IP exhaustion can become a production incident.

---

# 39. IP Allocation

When you launch an EC2 instance into a subnet, AWS assigns a private IP from the subnet's available address pool.

Example:

```text
Subnet
10.0.11.0/24
```

EC2 might receive:

```text
10.0.11.25
```

Another EC2 might receive:

```text
10.0.11.38
```

AWS manages address assignment within the subnet.

---

# 40. Primary Private IP

An ENI has a primary private IPv4 address.

Example:

```text
ENI
eni-...
|
Primary private IPv4
10.0.11.25
```

That address belongs to the subnet's CIDR.

The private IP generally remains associated with the network interface while that interface exists.

---

# 41. Secondary Private IP Addresses

Supported ENIs can also have secondary private IP addresses.

Conceptually:

```text
ENI
|
+-- Primary IP
10.0.11.25
|
+-- Secondary IP
10.0.11.26
```

This can support specialized networking designs.

Beginners should not add secondary addresses without a reason.

---

# 42. Public IP Assignment and Subnets

A subnet can be configured to automatically assign public IPv4 addresses to supported newly launched instances.

For a public subnet, this may be convenient during labs.

For a private subnet, you would normally disable automatic public IPv4 assignment.

Conceptually:

```text
Public Subnet
Auto-assign public IPv4:
Enabled, if desired
```

```text
Private Subnet
Auto-assign public IPv4:
Disabled
```

This helps reinforce the intended role of each subnet.

---

# 43. Important: Public IP Does Not Make the Subnet Public

Suppose an EC2 instance receives a public IP.

But its subnet has no route to an Internet Gateway.

The instance still lacks the required internet path.

Therefore:

```text
Public IP
alone
!=
Public subnet
```

You need the routing architecture.

---

# 44. Important: Internet Gateway Does Not Make the Subnet Public

Suppose your VPC has an Internet Gateway attached.

But the subnet route table does not send internet traffic to it.

The subnet is still not public.

Therefore:

```text
Internet Gateway attached
alone
!=
Public subnet
```

Again, the route table matters.

---

# 45. Public Subnet Requirements

A useful beginner model:

```text
Public Subnet
=
Subnet
+
Route Table with IGW route
```

For a resource inside it to be publicly reachable:

```text
Public Resource
=
Public Subnet
+
Public Address
+
Security Rules
+
Running Service
```

This distinction is worth memorizing.

# 46. Designing for Two Availability Zones

Our VPC:

```text
10.0.0.0/16
```

will span:

```text
AZ-A
AZ-B
```

We need one public and one private subnet in each AZ.

Design:

```text
AZ-A
|
+-- Public
10.0.1.0/24

+-- Private
10.0.11.0/24
```

```text
AZ-B
|
+-- Public
10.0.2.0/24

+-- Private
10.0.12.0/24
```

---

# 47. Why Not One Public Subnet for Both AZs?

Because a subnet belongs to one AZ only.

You cannot create:

```text
Public Subnet
10.0.1.0/24
|
AZ-A + AZ-B
```

Instead:

```text
Public Subnet A
|
AZ-A
```

and:

```text
Public Subnet B
|
AZ-B
```

This allows resources to be distributed across failure domains.

---

# 48. Why Multi-AZ Public Subnets?

An internet-facing Application Load Balancer is typically deployed across subnets in multiple Availability Zones.

Conceptually:

```text
Internet
   |
Load Balancer
 /          \
Public A   Public B
AZ-A       AZ-B
```

This helps avoid depending on one AZ.

---

# 49. Why Multi-AZ Private Subnets?

Application servers can also be distributed:

```text
Load Balancer
 /          \
App EC2 A   App EC2 B
Private A   Private B
AZ-A        AZ-B
```

If one AZ fails:

```text
AZ-A
X
```

the other may continue serving traffic:

```text
AZ-B
App EC2 B
```

if the rest of the architecture supports it.

---

# 50. Database Multi-AZ Thinking

Databases also benefit from multi-AZ design.

A database architecture may use database subnets across multiple Availability Zones.

Conceptually:

```text
Private DB Subnet A
AZ-A

Private DB Subnet B
AZ-B
```

Managed services such as RDS can use subnet groups spanning multiple AZs.

We will study that later.

---

# 51. Web, Application, Database Pattern

A strong production mental model is:

```text
Internet
   |
   v
Public Tier
   |
   v
Private Application Tier
   |
   v
Private Database Tier
```

Across two AZs:

```text
VPC
|
├── AZ-A
│   ├── Public A
│   ├── App A
│   └── DB A
│
└── AZ-B
    ├── Public B
    ├── App B
    └── DB B
```

This is a common multi-tier design.

---

# 52. What Belongs in a Public Subnet?

Typical candidates:

* Internet-facing load balancer
* NAT Gateway
* Bastion host in architectures that use one
* Public-facing network appliance

Not every web server needs to be public.

A better pattern is often:

```text
Internet
   |
Public Load Balancer
   |
Private Web/App Servers
```

---

# 53. What Belongs in a Private Application Subnet?

Examples:

* Application EC2 instances
* ECS tasks
* Backend APIs
* Worker services
* Internal services

These workloads can receive traffic from trusted upstream systems rather than the whole internet.

---

# 54. What Belongs in a Private Database Subnet?

Examples:

* RDS database instances
* Internal database services
* Data-tier infrastructure

A database usually receives traffic from application systems.

Example:

```text
App Security Group
     |
     v
Database Security Group
```

The database should not usually be open to:

```text
0.0.0.0/0
```

on its database port.

---

# 55. Subnet Names

Use names that communicate:

* Environment
* Tier
* Availability Zone

Example:

```text
veriqta-dev-public-a

veriqta-dev-public-b

veriqta-dev-private-a

veriqta-dev-private-b
```

For a three-tier design:

```text
veriqta-prod-public-a

veriqta-prod-public-b

veriqta-prod-app-a

veriqta-prod-app-b

veriqta-prod-db-a

veriqta-prod-db-b
```

Good names make architecture easier to understand.

---

# 56. Common Mistake 1: One Subnet for Everything

Architecture:

```text
VPC
|
One Subnet
|
+-- Load Balancer
+-- App
+-- Database
+-- Management
```

This may work technically.

But it gives poor separation and weak architectural clarity.

Better:

```text
Public Tier

Private App Tier

Private DB Tier
```

where requirements justify it.

# 57. Common Mistake 2: One Availability Zone

# 86. Subnet Troubleshooting Scenario: IP Exhaustion

New instances fail to launch.

## Cause

Subnet address space is nearly exhausted.

## Investigation

* Container networking
* Endpoints
* Stale resources

The correct fix may involve:

* Creating larger/new subnets
* Reworking address allocation
* Redesigning workload distribution

Subnet planning matters from the beginning.

# 89. Subnet Capacity Formula

For a subnet prefix:

```text
Total IPv4 addresses
=
2^(32 - prefix)
```

For AWS usable IPv4 addresses in normal subnets:

```text
Usable
=
Total - 5
```

Example `/24`:

```text
256 - 5
=
251 usable
```

Example `/28`:

```text
16 - 5
=
11 usable
```

This is useful for planning.

# What You Should Now Understand

After Part 6, you should understand:

* A subnet is a smaller network inside a VPC.
* Networks are divided to improve structure, routing, security, scalability, and availability.
* Every subnet has its own CIDR block.
* A subnet CIDR must fit inside the VPC CIDR.
* Subnets inside a VPC cannot overlap.
* A subnet belongs to one Availability Zone.
* A VPC can contain subnets across multiple Availability Zones.
* Multi-AZ design reduces dependence on a single failure domain.
* Public and private subnets are primarily distinguished by routing.
* A public subnet has a route to an Internet Gateway.
* A private subnet has no direct route to an Internet Gateway.
* A private subnet can still have outbound internet access through NAT architecture.
* A public IP alone does not make a subnet public.
* An Internet Gateway alone does not make a subnet public.
* Public reachability requires addressing, routing, security, and a listening service.
* Public subnets are commonly used for internet-facing infrastructure.
* Private subnets are commonly used for applications and databases.
* AWS reserves five IPv4 addresses in every subnet.
* A `/24` provides 256 total addresses and 251 normally usable IPv4 addresses in AWS.
* A `/28` provides only 11 normally usable IPv4 addresses.
* Subnet capacity affects scaling.
* IP exhaustion can become a production incident.
* EC2 private IP addresses come from the subnet address range.
* Auto-assigned public IPv4 is a separate subnet/launch behavior from routing.
* Structured subnet CIDRs make environments easier to understand.
* Application tiers can be separated into public, application, and database subnets.
* Multi-AZ architectures normally duplicate relevant subnet roles across AZs.
* Good subnet design considers future EC2, load balancers, RDS, containers, endpoints, and Auto Scaling.
* Clear subnet architecture improves security and troubleshooting.

# Part 6 Complete

You began with one large network:

```text
VPC
10.0.0.0/16
```

You divided it into:

```text
Public
Private
```

across:

```text
AZ-A
AZ-B
```

Your network now has structure:

```text
AWS Region
|
└── VPC 10.0.0.0/16
    |
    ├── AZ-A
    │   ├── Public A
    │   └── Private A
    |
    └── AZ-B
        ├── Public B
        └── Private B
```

The most important lesson is:

```text
A subnet is not public
because of its name.

A subnet is public
because of its route.
```

Part 7 will make this architecture actually move traffic by introducing route tables, local routes, longest-prefix matching, Internet Gateways, public-subnet routing, and the full path an EC2 packet takes from a subnet to the internet.
