# Part 5: Operators, Exit Codes, and Command Execution Logic

In Part 4, you learned how Linux commands exchange data using:

* standard input
* standard output
* standard error
* redirection
* pipes
* `tee`
* here documents
* here strings

You also briefly encountered an important concept:

```bash
echo "$?"
```

This reveals the exit status of the command that just ran.

Exit statuses are one of the foundations of Bash automation.

A command does not communicate only through the text it prints.

It also reports whether it believes it **succeeded or failed**.

For example:

```text
Command
   |
   +----> stdout
   |
   +----> stderr
   |
   +----> exit status
```

These are different forms of information.

A command might print nothing but still succeed.

A command might print useful information and still fail.

A command might produce an error message and return a non-zero exit status.

Bash uses exit statuses to make decisions.

This allows you to create logic such as:

```text
Run health check
      |
      v
Did it succeed?
   /       \
 Yes        No
  |          |
  v          v
Continue    Stop
```

or:

```text
Try primary operation
        |
        v
     Failed?
        |
       Yes
        |
        v
Try fallback operation
```

This is how shell scripts begin to move from simple command sequences into real automation.

By the end of Part 5, you should understand:

* what an exit status is
* why `0` means success
* what non-zero statuses mean
* how to inspect `$?`
* why exit statuses matter in automation
* how to terminate scripts with `exit`
* how to return custom exit codes
* how `;`, `&&`, and `||` control command execution
* logical AND and OR behavior
* how `!` negates a command's status
* how to test whether commands succeeded
* how to run fallback commands
* how to design safer execution workflows
* how CI/CD systems interpret exit codes
* why shell scripts can fail pipelines
* what command lists are
* how `{ }` groups commands
* how `( )` creates a subshell
* when grouping affects redirection and state
* how to build a practical health-check script

# 1. Commands Do More Than Print Output

Consider:

```bash
ls "$HOME"
```

You probably see a list of files and directories.

That is standard output.

But `ls` also finishes with an exit status.

Now try:

```bash
ls /directory-that-does-not-exist
```

You probably see an error.

That error is normally written to standard error.

But again, `ls` also finishes with an exit status.

Conceptually:

```text
                 COMMAND
              +-----------+
              |           |
              |    ls     |
              |           |
              +-----------+
                |   |   |
                |   |   |
                v   v   v
             stdout stderr exit
                            status
```

Output tells you information.

The exit status tells Bash whether the operation succeeded.

---

# 2. What Is an Exit Status?

An **exit status**, often called an **exit code**, is a numeric value returned when a command or process finishes.

The basic convention is:

```text
0       = success

non-zero = failure or another non-success condition
```

This convention is fundamental to Unix and Linux command execution.

For beginners, the most important rule to remember is:

```text
0 = success
```

and:

```text
anything else = something other than success
```

The exact meaning of a non-zero status depends on the command.

---

# 3. Exit Code 0

Run:

```bash
pwd
```

Assuming the command succeeds, immediately run:

```bash
echo "$?"
```

You should see:

```text
0
```

That means the previous command completed successfully.

Try:

```bash
true
```

Then:

```bash
echo "$?"
```

Expected:

```text
0
```

The `true` command deliberately returns success.

---

# 4. Non-Zero Exit Codes

Now run:

```bash
false
```

Immediately check:

```bash
echo "$?"
```

You should see:

```text
1
```

The `false` command deliberately returns failure.

Now try:

```bash
ls /definitely-not-a-real-directory
```

Then:

```bash
echo "$?"
```

You should receive a non-zero value.

The exact value can depend on the command and failure.

The important distinction is:

```text
0
```

versus:

```text
non-zero
```

---

# 5. Exit Codes Are Not All the Same

A beginner might think:

```text
0 = success
1 = failure
```

That is incomplete.

While `1` is commonly used for failure, commands can return many different non-zero statuses.

A program may use different values to distinguish different problems.

Conceptually:

```text
0 = operation succeeded
1 = general failure
2 = different failure condition
3 = another condition
...
```

Do not assume every command gives every number the same meaning.

When the exact code matters, consult the command's documentation.

For example:

```bash
man grep
```

or:

```bash
grep --help
```

---

# 6. `grep` Demonstrates Why Non-Zero Does Not Always Mean "Broken"

Create a small file:

```bash
printf '%s\n' \
  "INFO application started" \
  "ERROR database unavailable" \
  > app.log
```

Now:

```bash
grep "ERROR" app.log
```

Check:

```bash
echo "$?"
```

You should get:

```text
0
```

because a match was found.

Now:

```bash
grep "WARNING" app.log
```

Check immediately:

```bash
echo "$?"
```

You should normally get:

```text
1
```

For `grep`, status `1` commonly means:

> No selected lines were found.

That is different from:

> `grep` itself crashed.

This is an important engineering lesson:

> A non-zero status represents a command-defined non-success condition. You need to understand the command's semantics.

---

# 7. What Is `$?`

Bash provides a special parameter:

```bash
$?
```

It contains the exit status of the **most recently completed foreground pipeline**.

For the simple commands we are using now, think:

```text
Run command
    |
    v
Command finishes
    |
    v
Bash stores status
    |
    v
$?
```

Example:

```bash
mkdir test-directory
echo "$?"
```

If `mkdir` succeeds:

```text
0
```

may be displayed.

---

# 8. `$?` Changes Quickly

This is extremely important.

Run:

```bash
false
```

Then:

```bash
echo "$?"
```

You see:

```text
1
```

But now:

```bash
echo "$?"
```

again.

You may see:

```text
0
```

Why?

Because the first `echo` itself became the most recently executed command, and it succeeded.

Think of `$?` as a temporary status slot:

```text
false
  |
  v
$? = 1

echo "$?"
  |
  v
echo succeeds
  |
  v
$? = 0
```

If you need the previous status later, save it immediately.

---

# 9. Saving an Exit Status

You can write:

```bash
some_command
status=$?
```

Now the value is stored in:

```text
status
```

Example:

```bash
ls /not-real
status=$?

printf 'Exit status: %s\n' "$status"
```

Even though `printf` runs afterward, your variable still contains the saved status.

This pattern can be useful when you need to inspect or log the exact code.

---

# 10. Output and Exit Status Are Different

Consider:

```bash
output="$(some_command)"
```

The variable receives standard output.

The command also returns an exit status.

These are different things.

Conceptually:

```text
some_command
     |
     +------> stdout ------> output variable
     |
     +------> exit status -> $?
```

A common beginner mistake is to judge success only by whether text appeared.

Do not ask only:

> Did the command print something?

Also ask:

> What status did it return?

---

# 11. Why Exit Codes Matter in Automation

Imagine a human runs:

```bash
./deploy.sh
```

and sees:

```text
ERROR: deployment failed
```

The human understands that something went wrong.

But a CI/CD system does not interpret messages like a human.

It needs a machine-readable signal.

That signal is usually the process exit status.

Conceptually:

```text
Script
  |
  v
Exit 0
  |
  v
CI/CD sees SUCCESS
```

or:

```text
Script
  |
  v
Exit non-zero
  |
  v
CI/CD sees FAILURE
```

This is why exit codes are fundamental to automation.

---

# 12. Human Messages Are Not Enough

This script is badly designed:

```bash
#!/usr/bin/env bash

printf 'ERROR: deployment failed\n'
```

Why?

Because printing the word:

```text
ERROR
```

does not automatically make the script fail.

If the script reaches the end successfully after `printf`, its final status may be `0`.

A CI/CD system could therefore see:

```text
SUCCESS
```

even though the message says:

```text
ERROR
```

Your script must communicate failure through its exit status.

---

# 13. The `exit` Command

Bash provides:

```bash
exit
```

to terminate the current shell or script.

In a script, you can specify the exit status:

```bash
exit 0
```

or:

```bash
exit 1
```

For example:

```bash
#!/usr/bin/env bash

printf 'Operation failed\n' >&2
exit 1
```

Now the script explicitly reports failure.

---

# 14. `exit 0`

This means:

```bash
exit 0
```

Terminate the script and report success.

Example:

```bash
#!/usr/bin/env bash

printf 'Health check passed\n'
exit 0
```

Run:

```bash
./health.sh
```

Then:

```bash
echo "$?"
```

Expected:

```text
0
```

---

# 15. `exit 1`

This commonly indicates failure:

```bash
#!/usr/bin/env bash

printf 'Health check failed\n' >&2
exit 1
```

After running:

```bash
./health.sh
```

check:

```bash
echo "$?"
```

You should see:

```text
1
```

Now both humans and automation receive useful information:

```text
Human:
Health check failed

Machine:
exit status = 1
```

---

# 16. Returning Custom Exit Codes

You are not limited to:

```text
0
1
```

A script can return custom codes.

For example:

```text
0 = all checks passed
1 = general failure
2 = configuration missing
3 = required command missing
4 = service unavailable
5 = endpoint unhealthy
```

Then your script might contain:

```bash
printf 'ERROR: configuration file missing\n' >&2
exit 2
```

Another system could inspect that code.

However, do not invent dozens of arbitrary codes unless they provide real value.

Keep the scheme documented and understandable.

---

# 17. Exit Status Range

On Unix-like systems, process exit statuses are represented in a limited range, commonly:

```text
0–255
```

Values outside that range do not behave as unlimited integers.

For beginner scripts, stay with simple documented values such as:

```text
0
1
2
3
```

unless you have a reason to do otherwise.

Also be aware that shells use some statuses for special situations.

For example, you may encounter codes associated with:

* command not found
* command not executable
* termination by signals

You do not need to memorize all of these yet.

---

# 18. `exit` Stops Execution

Consider:

```bash
#!/usr/bin/env bash

printf 'Starting\n'

exit 1

printf 'Finished\n'
```

Run it.

You should see:

```text
Starting
```

but not:

```text
Finished
```

Why?

Because:

```bash
exit 1
```

terminates the script immediately.

Conceptually:

```text
Starting
   |
   v
exit 1
   |
   X
Remaining commands
```

This makes `exit` useful when continuing would be unsafe.

---

# 19. Safe Failure

Suppose a deployment requires a configuration file.

A dangerous workflow might be:

```text
Configuration missing
       |
       v
Continue anyway
       |
       v
Deployment behaves unpredictably
```

A safer workflow is:

```text
Check configuration
       |
       v
Missing?
   /       \
 No         Yes
 |           |
 v           v
Continue   exit non-zero
```

Later, conditional statements will make this pattern much more powerful.

For now, understand the principle:

> When a required prerequisite fails, stopping can be safer than continuing.

---

# 20. Command Chaining

Bash lets you place multiple commands together.

Three important operators are:

```text
;
&&
||
```

They look similar because they connect commands.

But their execution logic is different.

---

# 21. The Semicolon `;`

The semicolon separates commands.

Example:

```bash
pwd; whoami; hostname
```

Bash runs the commands sequentially.

Conceptually:

```text
pwd
 |
 v
whoami
 |
 v
hostname
```

The important point is:

> `;` does not mean "only continue if the previous command succeeded."

The next command is normally attempted regardless of the previous command's status.

---

# 22. Example of `;` After Failure

Run:

```bash
false; echo "Second command executed"
```

You should see:

```text
Second command executed
```

The first command failed.

But the second command still ran.

So:

```text
command1 ; command2
```

means approximately:

> Run command1, then run command2.

It does not create a success dependency.

---

# 23. Why `;` Can Be Dangerous in Automation

Imagine:

```bash
build_application; deploy_application
```

If the build fails, should deployment still happen?

Probably not.

But `;` does not automatically stop the second command.

Conceptually:

```text
Build
 |
 | failed
 v
Deploy anyway
```

That can be unsafe.

You need an operator that makes the second command depend on success.

That operator is:

```text
&&
```

---

# 24. Logical AND with `&&`

The operator:

```text
&&
```

means:

> Run the command on the right only if the command on the left succeeds.

Example:

```bash
mkdir project && cd project
```

Conceptually:

```text
mkdir project
      |
      v
  succeeded?
   /      \
 Yes       No
  |         |
  v         X
cd project
```

If `mkdir project` succeeds, Bash attempts:

```bash
cd project
```

If it fails, the second command is skipped.

---

# 25. Why `&&` Is Called Logical AND

Think:

```text
A && B
```

For the whole sequence to succeed:

```text
A must succeed
AND
B must succeed
```

This creates a dependency.

Example:

```bash
download_file && verify_file
```

means:

> Verify the file only if downloading it succeeded.

---

# 26. Testing `&&`

Run:

```bash
true && echo "Success path"
```

Expected:

```text
Success path
```

Now:

```bash
false && echo "You should not see this"
```

The `echo` command is skipped.

This behavior is called **short-circuit evaluation**.

Bash already knows the AND expression cannot succeed once the left side has failed, so it does not need to execute the right side.

---

# 27. Practical `&&` Example

Suppose you want to create a directory and then create a file inside it.

You might write:

```bash
mkdir -p devops-lab && touch devops-lab/status.txt
```

This means:

1. create or ensure the directory exists
2. only if that succeeds, create the file

This is safer than:

```bash
mkdir -p devops-lab; touch devops-lab/status.txt
```

when the second operation depends on the first.

---

# 28. Logical OR with `||`

The operator:

```text
||
```

means:

> Run the command on the right only if the command on the left fails.

Example:

```bash
some_command || echo "Command failed"
```

Conceptually:

```text
some_command
     |
     v
 succeeded?
  /      \
Yes       No
 |         |
 X         v
       fallback
```

This is useful for:

* fallback actions
* error messages
* recovery attempts
* default behavior
* stopping after failure

---

# 29. Testing `||`

Run:

```bash
true || echo "Failure path"
```

The `echo` command is skipped.

Now:

```bash
false || echo "Failure detected"
```

Expected:

```text
Failure detected
```

The right-hand command runs because the left-hand command failed.

---

# 30. Why `||` Is Called Logical OR

Think:

```text
A || B
```

If A succeeds, Bash already has a successful result.

It does not need B.

If A fails, Bash tries B.

Conceptually:

```text
Try A

A succeeded?
   |
  Yes ----> done

A failed?
   |
  Yes
   |
   v
Try B
```

---

# 31. Difference Between `;`, `&&`, and `||`

This is worth learning clearly.

| Operator | Meaning           | When right side runs                   |            |                         |
| -------- | ----------------- | -------------------------------------- | ---------- | ----------------------- |
| `;`      | command separator | normally regardless of previous status |            |                         |
| `&&`     | logical AND       | only if left side succeeds             |            |                         |
| `        |                   | `                                      | logical OR | only if left side fails |

Example:

```bash
command1 ; command2
```

means:

```text
Run command1
Then run command2
```

Example:

```bash
command1 && command2
```

means:

```text
Run command1
If successful, run command2
```

Example:

```bash
command1 || command2
```

means:

```text
Run command1
If unsuccessful, run command2
```

---

# 32. Chaining Multiple `&&` Commands

You can write:

```bash
command1 && command2 && command3
```

Execution proceeds while commands succeed.

Conceptually:

```text
command1
   |
 success
   |
   v
command2
   |
 success
   |
   v
command3
```

If `command2` fails:

```text
command1
   |
 success
   |
   v
command2
   |
 failure
   |
   X
command3 skipped
```

This is useful for short dependent workflows.

---

# 33. Example: Safe Build Workflow

Imagine:

```bash
prepare_workspace &&
build_application &&
run_tests &&
package_application
```

The intended logic is:

```text
Prepare
  |
  v
Build
  |
  v
Test
  |
  v
Package
```

If testing fails:

```text
Prepare ✓
Build   ✓
Test    ✗
Package skipped
```

This is much safer than blindly running all stages.

---

# 34. Chaining Multiple `||` Commands

You can also create fallback chains:

```bash
primary_command || secondary_command || emergency_command
```

Conceptually:

```text
Try primary
    |
 failed?
    |
    v
Try secondary
    |
 failed?
    |
    v
Try emergency
```

Once a command succeeds, later OR alternatives can be skipped.

---

# 35. Combining `&&` and `||`

You may encounter:

```bash
command && success_action || failure_action
```

It can appear to mean:

```text
if command succeeds:
    success_action
else:
    failure_action
```

Sometimes it behaves that way.

But there is an important trap.

If:

```text
command succeeds
```

but:

```text
success_action fails
```

then:

```text
failure_action
```

can run.

So this should not automatically be treated as a complete replacement for a proper `if` statement.

We will learn `if` in Part 6.

For simple chains, understand the exit-status logic rather than reading `&& ... || ...` as guaranteed if/else syntax.

---

# 36. Negating Commands with `!`

Bash provides:

```text
!
```

to logically negate a command or pipeline's exit status.

Consider:

```bash
true
```

This succeeds.

But:

```bash
! true
```

has a failure status.

Try:

```bash
! true
echo "$?"
```

You should see a non-zero status.

Now:

```bash
! false
echo "$?"
```

You should see:

```text
0
```

because the failure was logically inverted.

---

# 37. Understanding `!`

Think:

```text
Command result
      |
      v
      !
      |
      v
Reverse success/failure
```

So:

```text
success → failure
failure → success
```

This becomes useful when your logic is naturally phrased as:

> Continue if this condition is NOT true.

You will see it more often when we begin conditional testing.

---

# 38. Testing Whether Commands Succeeded

One direct method is:

```bash
some_command
status=$?

if we were manually reasoning:
    0     → success
    other → failure
```

But Bash operators allow shorter patterns.

For example:

```bash
some_command && printf 'Command succeeded\n'
```

or:

```bash
some_command || printf 'Command failed\n' >&2
```

These use the command's actual exit status.

---

# 39. Do Not Parse Human Output When Exit Status Already Exists

Suppose a command already provides meaningful exit codes.

Avoid unnecessarily doing something like:

```text
Run command
Capture output
Search output for word "success"
Guess whether it worked
```

when you could directly inspect its exit status.

Better model:

```text
Command
   |
   +--> output for humans/data
   |
   +--> exit status for execution logic
```

This is often more reliable.

---

# 40. Running Fallback Commands

Suppose an application health endpoint is checked by a command.

You might eventually have:

```bash
check_primary || check_backup
```

This means:

```text
Check primary
     |
     v
  success?
   /    \
 Yes     No
  |       |
 done     v
       Check backup
```

Fallback logic is useful, but it must be designed carefully.

You do not want a fallback to hide a serious underlying failure.

---

# 41. Fallback Is Not the Same as Ignoring Failure

Consider:

```bash
important_command || true
```

If `important_command` fails, `true` runs and succeeds.

The combined list can therefore end successfully.

This may be intentional in some scripts.

But it can also hide a real failure.

Bad habit:

```bash
critical_deployment || true
```

This effectively says:

> Treat deployment failure as acceptable.

That could cause a CI/CD pipeline to appear successful.

Use failure suppression only when failure is genuinely expected and acceptable.

---

# 42. Creating Safe Execution Workflows

A safe workflow identifies dependencies.

Imagine:

```text
Validate configuration
        |
        v
Authenticate
        |
        v
Build
        |
        v
Test
        |
        v
Deploy
        |
        v
Verify
```

Ask:

> Which stages depend on earlier success?

Probably almost all of them.

So blindly writing:

```bash
validate; authenticate; build; test; deploy; verify
```

may be inappropriate.

A better conceptual workflow is:

```text
Validate
   |
 success
   v
Authenticate
   |
 success
   v
Build
   |
 success
   v
Test
   |
 success
   v
Deploy
   |
 success
   v
Verify
```

The more important the automation, the more deliberate your failure behavior should be.

---

# 43. When Should a Script Stop?

A script should usually stop when continuing would:

* produce invalid results
* modify the wrong environment
* deploy untested code
* overwrite important data
* depend on missing prerequisites
* conceal an earlier failure
* create a misleading success result

For example:

```text
Required configuration missing
            |
            v
        STOP
```

is safer than:

```text
Required configuration missing
            |
            v
     Guess defaults
            |
            v
       Deploy anyway
```

unless those defaults are explicitly designed and safe.

---

# 44. Exit Codes in CI/CD

CI/CD platforms run programs and scripts.

A simplified pipeline might look like:

```text
Checkout
   |
   v
Build
   |
   v
Test
   |
   v
Deploy
```

At each stage, the automation needs to know:

```text
Did this operation succeed?
```

Exit statuses provide that signal.

Simplified:

```text
Script exits 0
      |
      v
Stage passes
```

versus:

```text
Script exits non-zero
      |
      v
Stage fails
```

Exact behavior depends on the CI/CD platform and configuration, but this is the core principle.

---

# 45. Example CI/CD Test Script

Suppose a CI job runs:

```bash
./run-tests.sh
```

A correctly designed script might conceptually do:

```text
Tests pass
    |
    v
exit 0
```

or:

```text
Tests fail
    |
    v
exit non-zero
```

The CI runner does not need to understand every test message.

It receives the final status.

---

# 46. Why Scripts Fail Pipelines

Imagine your script contains:

```bash
#!/usr/bin/env bash

printf 'Starting tests\n'

false

exit 1
```

The script explicitly exits with failure.

A CI/CD system will generally mark that step as failed.

That is not a problem with Bash.

That is Bash correctly communicating:

```text
This operation failed.
```

The pipeline can then stop deployment.

---

# 47. A Dangerous Script That Hides Failure

Consider:

```bash
#!/usr/bin/env bash

printf 'Running tests\n'

false

printf 'Tests finished\n'
```

What status does the script finally return?

The last command is:

```bash
printf 'Tests finished\n'
```

If `printf` succeeds, the script may finish with status `0`.

So conceptually:

```text
Tests fail
   |
   v
false returns 1
   |
   v
printf succeeds
   |
   v
script ends
   |
   v
final status 0
```

Your automation may now believe the script succeeded.

This is one reason error handling matters.

---

# 48. The Last Command Matters

Unless you explicitly control the exit behavior, the final status of a script is normally influenced by the last command executed.

Example:

```bash
#!/usr/bin/env bash

false
true
```

Run it:

```bash
./example.sh
```

Then:

```bash
echo "$?"
```

You may receive:

```text
0
```

The earlier failure was not automatically preserved as the script's final status.

---

# 49. Explicit Failure Propagation

One simple pattern is:

```bash
important_command || exit 1
```

Meaning:

```text
Run important_command
        |
        v
     failed?
      /   \
    No     Yes
    |       |
continue   exit 1
```

You may also preserve the command's exact code:

```bash
important_command
status=$?

exit "$status"
```

Whether you want a generic or preserved exit code depends on your script design.

---

# 50. Practical Example: Build Must Succeed Before Deployment

Instead of:

```bash
build_application
deploy_application
```

you might use:

```bash
build_application && deploy_application
```

Now deployment depends on build success.

Or:

```bash
build_application || exit 1
deploy_application
```

Both establish a failure dependency, although they express it differently.

Later, proper `if` statements and structured error handling will make longer workflows clearer.

# 51. Understanding Command Lists

A **command list** is a sequence of commands connected by shell control operators.

Examples include:

```bash
command1 ; command2
```

```bash
command1 && command2
```

```bash
command1 || command2
```

and combinations such as:

```bash
command1 && command2 || command3
```

These are not merely visual separators.

The operators determine execution behavior.

---

# 52. Lists Can Span Multiple Lines

You do not always need everything on one line.

For example:

```bash
mkdir -p devops-lab &&
cd devops-lab &&
touch status.txt
```

This is still a connected AND-list.

Formatting commands across multiple lines can improve readability.

For complex logic, however, proper conditional structures are usually clearer.

---

# 53. Grouping Commands

Sometimes you want several commands treated as a group.

Bash provides important grouping forms:

```text
{ }
```

and:

```text
( )
```

They may look similar, but they behave differently.

---

# 54. Grouping with `{ }`

Example:

```bash
{
    echo "Hostname:"
    hostname
    echo "User:"
    whoami
}
```

This groups multiple commands together.

One major benefit is that you can redirect the entire group at once.

Example:

```bash
{
    echo "Hostname:"
    hostname
    echo "User:"
    whoami
} > system-info.txt
```

Instead of redirecting every command separately, the whole group's stdout goes to:

```text
system-info.txt
```

---

# 55. Why Grouping Is Useful

Without grouping:

```bash
echo "Hostname:" > system-info.txt
hostname >> system-info.txt
echo "User:" >> system-info.txt
whoami >> system-info.txt
```

With grouping:

```bash
{
    echo "Hostname:"
    hostname
    echo "User:"
    whoami
} > system-info.txt
```

The second form can be easier to read.

Conceptually:

```text
{
  command 1
  command 2
  command 3
}
      |
      v
combined stdout
      |
      v
system-info.txt
```

---

# 56. Important `{ }` Syntax

When using braces on one line, Bash syntax requires appropriate separators.

For example:

```bash
{ echo "one"; echo "two"; }
```

Notice:

```text
;
```

before:

```text
}
```

The closing brace must be properly separated from the preceding command.

A multi-line form is often easier to read:

```bash
{
    echo "one"
    echo "two"
}
```

---

# 57. Brace Groups Run in the Current Shell

This is one of the most important differences between:

```text
{ }
```

and:

```text
( )
```

Commands inside a brace group normally execute in the **current shell environment**.

That means changes to shell state can remain afterward.

Example:

```bash
current_value="before"

{
    current_value="inside"
}

printf '%s\n' "$current_value"
```

Output:

```text
inside
```

The variable change remained because the group ran in the current shell.

---

# 58. Grouping with `( )`

Now consider:

```bash
(
    echo "Hostname:"
    hostname
    echo "User:"
    whoami
)
```

This also groups commands.

But parentheses introduce an important concept:

**a subshell environment.**

---

# 59. What Is a Subshell?

A subshell is a separate shell execution environment created from the current shell.

A simplified model:

```text
Current shell
     |
     v
Create subshell
     |
     v
Run grouped commands
     |
     v
Subshell ends
     |
     v
Return to current shell
```

Changes made only inside the subshell generally do not modify the parent shell's state.

---

# 60. Variable Changes in a Subshell

Try:

```bash
environment="development"

(
    environment="production"
    printf 'Inside: %s\n' "$environment"
)

printf 'Outside: %s\n' "$environment"
```

Expected:

```text
Inside: production
Outside: development
```

Why?

The change:

```bash
environment="production"
```

happened inside the subshell.

When the subshell ended, the parent shell still had:

```text
development
```

---

# 61. Directory Changes in a Subshell

This is another useful example.

Run:

```bash
pwd
```

Now:

```bash
(
    cd /tmp
    pwd
)
```

Then:

```bash
pwd
```

Inside the parentheses, the working directory becomes:

```text
/tmp
```

But after the subshell exits, your parent shell remains in its original directory.

This is useful when you want temporary state changes.

---

# 62. Compare `{ }` and `( )`

Brace group:

```bash
{
    cd /tmp
    pwd
}
```

can change the current shell's working directory.

Subshell:

```bash
(
    cd /tmp
    pwd
)
```

changes directory only inside the subshell.

Mental model:

```text
{ }
|
v
current shell
changes may persist
```

versus:

```text
( )
|
v
subshell
changes are isolated
```

---

# 63. `{ }` vs `( )` Summary

| Feature                        | `{ }`       | `( )`                 |
| ------------------------------ | ----------- | --------------------- |
| Groups commands                | Yes         | Yes                   |
| Can redirect entire group      | Yes         | Yes                   |
| Current shell                  | Yes         | No, normally subshell |
| Variable changes persist       | Usually yes | No                    |
| `cd` can affect later commands | Yes         | No                    |
| Useful for temporary isolation | Less so     | Yes                   |

This distinction becomes increasingly important as scripts grow.

---

# 64. Redirecting a Brace Group

Example:

```bash
{
    printf 'Date: '
    date

    printf 'User: '
    whoami

    printf 'Host: '
    hostname
} > report.txt
```

All normal output from the group is redirected into:

```text
report.txt
```

Errors are still separate unless you redirect them too.

For example:

```bash
{
    command1
    command2
} > output.log 2> errors.log
```

---

# 65. Redirecting a Subshell

You can also write:

```bash
(
    printf 'Inside temporary environment\n'
    pwd
    hostname
) > subshell-report.txt
```

The entire subshell's stdout is redirected.

So both grouping forms work well with redirection.

The important difference is shell state.

---

# 66. Exit Status of a Group

Grouped commands also produce an exit status.

For a simple group, the group's status generally reflects the last command executed within that group.

Example:

```bash
{
    true
    false
}
```

Then:

```bash
echo "$?"
```

You should receive a non-zero status because the final command was `false`.

Now:

```bash
{
    false
    true
}
```

Then:

```bash
echo "$?"
```

You should normally receive:

```text
0
```

Again, the earlier failure can be hidden by later success.

This pattern should now look familiar.

---

# 67. Exit Status of a Subshell Group

The same general principle applies to:

```bash
(
    false
    true
)
```

The subshell's final status reflects the command logic executed inside it.

This means grouping does not automatically solve error handling.

You still need deliberate failure logic.

---

# 68. Combining Groups with `&&`

You can write:

```bash
{
    echo "Running checks"
    true
} && echo "Group succeeded"
```

If the group's final status is successful, the right-hand command runs.

Likewise:

```bash
{
    echo "Running checks"
    false
} || echo "Group failed"
```

The fallback runs because the group's final status is non-zero.

---

# 69. Negating a Group

You may encounter:

```bash
! {
    command1
    command2
}
```

or:

```bash
! (
    command1
    command2
)
```

The `!` operator negates the resulting status.

You do not need complex uses yet.

The important concept is that Bash operators can work with:

* individual commands
* pipelines
* grouped command lists

# 70. Exit Status and Pipelines Revisited

From Part 4, remember:

```bash
command1 | command2
```

By default, Bash generally uses the final command's status for the pipeline.

Example:

```bash
false | true
```

Then:

```bash
echo "$?"
```

normally gives:

```text
0
```

even though the first command failed.

This is extremely relevant to CI/CD automation.

---

# 71. `pipefail` Revisited

You learned:

```bash
set -o pipefail
```

With `pipefail`, a failure in an earlier pipeline stage can affect the pipeline's status.

Example:

```bash
set -o pipefail

false | true

echo "$?"
```

Now the result should be non-zero.

Later, Part 14 will cover reliable error handling in much more depth.

For now:

> Never assume that seeing a successful final pipeline command proves every stage succeeded.

---

# 72. Practical Example: Logging with `tee`

Consider:

```bash
./deploy.sh 2>&1 | tee deployment.log
```

If `deploy.sh` fails but `tee` succeeds, the pipeline can appear successful under default behavior.

That could matter in CI/CD.

With appropriate pipeline failure handling:

```bash
set -o pipefail
```

the failure can propagate.

This is a real production reason for understanding exit statuses.

You may be tempted to write every script as:

command2 &&
command3 &&
command4 &&

This can work for simple workflows.

But as scripts become larger, you need:

# 78. Understanding `command -v`

# 80. Use `||` for Failure

# 83. Commands as Questions

# 86. The Health Script's Logic Bug

The script begins:

```bash

```

but never changes it.

So even if:

```text

```

or:

```text
whoami_status
```

or:

```text
home_status
```

is non-zero, the script still ends:

```bash

```

which is:

```text
0
```

This is a classic automation bug.

The script collects failure information but does not propagate it.

# 87. Why This Bug Matters

A human reading:

might notice a problem.

But CI/CD sees only:

```text

```

So the machine concludes:

```text
SUCCESS
```

This demonstrates a critical rule:

> Collecting errors is not enough. Your final script status must represent the result you want automation to act on.

# 90. A Better Operator-Based Fail-Fast Check

For a critical prerequisite, use:

```bash
command -v hostname > /dev/null 2>&1 || {
    printf 'ERROR: hostname command is required\n' >&2
    exit 3
}
```

Read this carefully.

The left side is:

```bash
command -v hostname > /dev/null 2>&1
```

If it succeeds:

```text
||
```

short-circuits and the group is skipped.

If it fails, Bash executes:

```bash
{
    printf 'ERROR: hostname command is required\n' >&2
    exit 3
}
```

This is a useful fail-fast pattern.

---

# 91. Understanding the Fail-Fast Pattern

The flow is:

```text
Check hostname
      |
      v
  succeeded?
   /      \
 Yes       No
  |         |
  |         v
  |     print error
  |         |
  |         v
  |       exit 3
  |
  v
continue
```

This gives both:

```text
human-readable diagnostic
```

and:

```text
machine-readable failure status
```

---

# 99. Using `!` in a Health Check

You could also express a failure test using negation:

```bash
! command -v hostname > /dev/null 2>&1 &&
printf 'hostname is unavailable\n' >&2
```

```text
hostname command resolves successfully
          |
          v
        negate
          |
          v
failure branch does not run
```

If `command -v` fails, `!` turns that result into logical success, allowing the `&&` command to run.

This can become harder to read when logic grows.

Readable automation is more valuable than compressed automation.

# 103. Common Beginner Mistake: Using `;` for Dependent Operations

Risky:

```bash
build; deploy
```

If deployment requires a successful build, use logic that reflects that dependency.

For a simple workflow:

```bash
build && deploy
```

is clearer.

---

# 104. Common Beginner Mistake: Hiding Failure with `|| true`

This:

```bash
critical_command || true
```

can turn a failure into an overall successful command list.

Do this only if the failure is genuinely acceptable and deliberately handled.

Never add `|| true` merely to make a CI pipeline green.

A green pipeline with a hidden failure is worse than an honest failed pipeline.

---

# 105. Common Beginner Mistake: Treating `&& ... || ...` as Perfect If/Else

This:

```bash
command && success_action || failure_action
```

can run `failure_action` when `success_action` itself fails.

For important branching logic, use proper conditionals once you learn them.

Part 6 will address this.

---

# 106. Common Beginner Mistake: Forgetting Pipeline Status Behavior

This:

```bash
failing_command | tee output.log
```

may appear successful because `tee` is the final command.

Understand:

```bash
set -o pipefail
```

before relying on pipelines for failure-sensitive automation.

---

# 107. Common Beginner Mistake: Assuming Grouping Handles Errors

This:

```bash
{
    false
    true
}
```

can finish successfully because the last command succeeds.

Grouping commands does not automatically mean:

> Stop if any command fails.

Grouping and error handling are separate concepts.

---

# 108. Common Beginner Mistake: Confusing `{ }` and `( )`

This:

```bash
{
    cd /tmp
}
```

can change the current shell's directory.

This:

```bash
(
    cd /tmp
)
```

changes directory only inside the subshell.

Use parentheses when temporary isolation is useful.

---

# 109. Common Beginner Mistake: Arbitrary Custom Codes

Avoid designs such as:

```text
17 = missing config
43 = network problem
81 = disk problem
129 = coffee unavailable
```

unless there is a documented reason.

Simple schemes are easier to operate.

For many scripts:

```text
0 = success
1 = general failure
2 = specific known failure
3 = another important known failure
```

may be enough.

---

# 110. Common Beginner Mistake: Continuing After a Critical Failure

Suppose authentication fails.

Do not automatically continue to deployment.

Think:

```text
Authentication failed
        |
        v
Can the next operation safely succeed?
        |
       No
        |
        v
Stop
```

The correct response to failure depends on what the next command assumes.

---

# 111. Troubleshooting: Script Says Success After a Failed Command

## Problem

An earlier command failed, but:

```bash
echo "$?"
```

after the script returns:

```text
0
```

## Possible Cause

A later command succeeded and became the script's final status.

## Investigation

Inspect the command sequence.

Example:

```bash
false
printf 'Finished\n'
```

## Fix

Propagate failure deliberately:

```bash
important_command || exit 1
```

or use structured conditional/error handling.

## Verification

Run the script again and inspect its final status.

---

# 112. Troubleshooting: Fallback Runs Unexpectedly

## Problem

You wrote:

```bash
command && success_action || fallback_action
```

The main command succeeded, but fallback still ran.

## Possible Cause

`success_action` failed.

The OR operator then saw failure and executed the fallback.

## Fix

Do not treat complex AND/OR chains as guaranteed if/else structures.

Use a proper `if` statement when branching logic matters.

---

# 113. Troubleshooting: Variable Changed Inside Group but Not Outside

## Problem

You wrote:

```bash
(
    status="healthy"
)
```

but outside:

```bash
echo "$status"
```

does not contain the expected value.

## Cause

The assignment happened in a subshell.

## Fix

If you intentionally need to modify the current shell state, use appropriate current-shell logic rather than a subshell.

For example:

```bash
{
    status="healthy"
}
```

---

# 114. Troubleshooting: CI Job Is Green Even Though a Command Failed

## Investigate

Look for:

```text
failure followed by successful command
```

or:

```text
pipeline ending in successful command
```

or:

```text
|| true
```

or:

```text
failure swallowed by custom script logic
```

Ask:

```text
What is the final exit status?

Which command produced it?

Was an earlier failure overwritten?

Is a pipeline hiding a failed stage?

Did the script explicitly exit 0?
```

---

# 115. Troubleshooting: Script Stops Earlier Than Expected

If you see:

```bash
command || exit 1
```

and `command` fails, stopping is intentional.

Check the command directly:

```bash
command
```

Then:

```bash
echo "$?"
```

Investigate why the prerequisite failed rather than removing the `exit` merely to make the script continue.

---

# 116. Engineering Reasoning for Command Failures

When automation fails, use this reasoning process:

```text
Observe
   |
   v
Which command failed?
   |
   v
What was its exit status?
   |
   v
What stdout/stderr did it produce?
   |
   v
Was it a standalone command or pipeline?
   |
   v
Was its failure propagated?
   |
   v
What dependency failed?
   |
   v
Fix root cause
   |
   v
Run again
   |
   v
Verify final exit status
```

Do not immediately add:

```bash
|| true
```

Do not immediately redirect:

```bash
2> /dev/null
```

Do not simply force:

```bash
exit 0
```

Those actions can hide evidence instead of fixing the problem.

---

# 117. Security and Safe Automation

Exit logic also has security implications.

Suppose a script checks whether authentication succeeded.

Bad:

```bash
authenticate
deploy
```

Safer:

```bash
authenticate && deploy
```

or:

```bash
authenticate || {
    printf 'ERROR: authentication failed\n' >&2
    exit 1
}

deploy
```

Never continue privileged or production-changing operations after a failed security prerequisite unless the workflow explicitly requires it.

---

# 118. Production Thinking

In production automation, failure should be:

```text
Detected
   |
   v
Communicated
   |
   v
Handled
   |
   v
Logged
   |
   v
Propagated when necessary
```

A dangerous script does this:

```text
Failure
   |
   v
Ignore
   |
   v
Continue
   |
   v
Report success
```

Your goal is to avoid that second pattern.

# 119. What You Should Now Understand

After Part 5, you should understand that:

* every command returns an exit status
* `0` represents success by convention
* non-zero represents a non-success condition
* exact non-zero meanings depend on the command
* `$?` contains the most recent foreground pipeline's exit status
* `$?` changes as new commands execute
* important statuses should be captured immediately
* stdout and exit status are different forms of information
* automation depends heavily on exit statuses
* CI/CD systems use process statuses to determine success and failure
* printing `ERROR` does not automatically make a script fail
* `exit` terminates the current script or shell
* `exit 0` reports success
* `exit 1` commonly reports failure
* scripts can use documented custom exit codes
* `;` separates commands without requiring previous success
* `&&` executes the right side only after success
* `||` executes the right side only after failure
* `&&` represents logical AND behavior
* `||` represents logical OR behavior
* `!` negates command or pipeline status
* fallback commands can be built with `||`
* fallback logic should not accidentally hide critical failures
* `|| true` can suppress failures and must be used deliberately
* dependent operations should not blindly use `;`
* AND/OR chains are not always substitutes for `if/else`
* command lists connect commands through control operators
* `{ }` groups commands in the current shell
* `( )` runs grouped commands in a subshell environment
* variable and directory changes inside a subshell generally do not affect the parent shell
* entire groups can be redirected
* a group's status can depend on its final executed command
* grouping does not automatically provide error handling
* pipeline exit behavior can hide earlier failures
* `pipefail` can make pipeline failures visible
* fail-fast workflows can prevent unsafe continuation
* good scripts communicate useful information to both humans and machines

# Part 5 Summary

You now understand that Bash does not decide success by reading English messages on the screen.

It uses exit statuses.

The core rule is:

```text
0
|
v
SUCCESS
```

and:

```text
non-zero
|
v
NON-SUCCESS / FAILURE CONDITION
```

You can inspect the most recent status with:

```bash
echo "$?"
```

and terminate a script deliberately with:

```bash
exit 0
```

or:

```bash
exit 1
```

You can create execution dependencies using:

```text
command1 ; command2
```

which means:

```text
run command1
then command2
```

without requiring command1 to succeed.

You can use:

```text
command1 && command2
```

for:

```text
command1
   |
 success
   |
   v
command2
```

and:

```text
command1 || command2
```

for:

```text
command1
   |
 failure
   |
   v
command2
```

You can reverse logical status with:

```bash
! command
```

You can group commands in the current shell:

```bash
{
    command1
    command2
}
```

or isolate grouped work in a subshell:

```bash
(
    command1
    command2
)
```

The distinction is:

```text
{ }
 |
 v
Current shell
 |
 v
State changes may remain
```

versus:

```text
( )
 |
 v
Subshell
 |
 v
Temporary state
 |
 v
Subshell ends
 |
 v
Parent state remains
```

Most importantly, you should now understand the automation model:

```text
Run operation
      |
      v
Inspect result
      |
      v
Success?
   /       \
 Yes        No
  |          |
  v          v
Continue    Handle failure
              |
              +--> log
              +--> fallback
              +--> retry later
              +--> stop
              +--> exit non-zero
```

The engineering habits to keep from Part 5 are:

```text
Do not judge success only by printed output.

Remember that 0 means success.

Understand command-specific non-zero codes.

Capture $? immediately when you need it.

Use exit codes to communicate with automation.

Do not print ERROR and then accidentally exit 0.

Use ; only when later execution does not depend on earlier success.

Use && for success-dependent operations.

Use || for deliberate failure handling and fallback behavior.

Do not hide critical failures with || true.

Do not treat && ... || ... as a perfect replacement for if/else.

Understand the final status of command lists.

Know whether grouped commands run in the current shell or a subshell.

Use subshells when temporary state isolation is useful.

Remember that grouping does not automatically handle errors.

Understand pipeline exit behavior.

Use pipefail deliberately when pipeline failures must propagate.

Stop when continuing after a critical failure would be unsafe.

Give humans useful error messages.

Give machines meaningful exit statuses.

Never make automation appear successful merely because failure is inconvenient.
```

IF this condition is true
