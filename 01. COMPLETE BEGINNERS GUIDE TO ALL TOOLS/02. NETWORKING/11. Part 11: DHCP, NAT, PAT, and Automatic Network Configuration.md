# Part 11: DHCP, NAT, PAT, and Automatic Network Configuration

## Understand How Devices Receive Configuration and Share Network Access

In the previous parts, you learned that a device needs several pieces of information before it can communicate effectively:

```text
IP address
Subnet mask / prefix
Default gateway
DNS server
```

You also learned that private IP addresses such as:

```text
10.0.0.25
192.168.1.50
172.20.10.15
```

are not normally routed across the public Internet.

That creates two major networking questions:

```text
Question 1:

How does a new device automatically
receive the network configuration it needs?
```

and:

```text
Question 2:

How can hundreds or thousands of devices
using private addresses communicate
with public Internet services?
```

Two major technologies answer those questions:

```text
DHCP
Dynamic Host Configuration Protocol

NAT
Network Address Translation
```

A third concept, PAT, explains how many private devices can share a single public IPv4 address.

A useful starting mental model is:

```text
New Laptop
    |
    | DHCP
    v
Receives:
192.168.1.50/24
Gateway 192.168.1.1
DNS 192.168.1.1
    |
    v
Sends Internet traffic
    |
    v
Home Router
    |
    | NAT/PAT
    v
Public IP
203.0.113.10
    |
    v
Internet
```

By the end of Part 11, you should understand both processes and be able to troubleshoot them separately.

---

# 1. Why Automatic Network Configuration Is Necessary

Imagine connecting your phone to Wi-Fi and having to manually configure:

```text
IP address
Subnet mask
Default gateway
DNS servers
```

every time.

You would also need to know which addresses were already being used.

If you accidentally configured:

```text
192.168.1.20
```

while another device already had:

```text
192.168.1.20
```

you could create an IP conflict.

Manual configuration becomes extremely difficult at scale.

A company might have:

```text
5,000 laptops
2,000 phones
500 printers
300 servers
Thousands of virtual machines
```

Automatically assigning network configuration solves a major operational problem.

That is one of DHCP's main purposes.

---

# 2. What Is DHCP?

DHCP stands for:

```text
Dynamic Host Configuration Protocol
```

DHCP automatically provides network configuration to clients.

Instead of manually configuring:

```text
IP:       192.168.1.50
Mask:     255.255.255.0
Gateway:  192.168.1.1
DNS:      192.168.1.1
```

the device can request configuration from a DHCP server.

Conceptually:

```text
Client
   |
   | "I need network configuration."
   v
DHCP Server
   |
   | "Use this configuration."
   v
Client
```

---

# 3. DHCP Does More Than Assign an IP Address

A common beginner misunderstanding is:

```text
DHCP gives computers IP addresses.
```

That is true, but incomplete.

DHCP can provide many configuration parameters.

Common ones include:

```text
IP address
Subnet mask
Default gateway
DNS servers
Lease duration
Domain/search information
```

Additional DHCP options can provide other network-specific information.

So think:

```text
DHCP
=
Automatic network configuration
```

not merely:

```text
DHCP
=
IP address generator
```

---

# 4. DHCP Clients

A DHCP client is a device requesting network configuration.

Examples include:

* Laptops
* Desktop computers
* Phones
* Tablets
* Virtual machines
* Printers
* IP phones
* Servers configured for DHCP
* IoT devices

When your laptop joins a network, it may initially know very little about that network.

It needs to discover configuration dynamically.

---

# 5. DHCP Servers

A DHCP server provides configuration to DHCP clients.

Depending on the environment, the DHCP server might be:

```text
Home router
Enterprise DHCP server
Firewall appliance
Network appliance
Cloud DHCP service
```

The server maintains information about addresses it can assign.

For example:

```text
Network:
192.168.1.0/24

DHCP pool:
192.168.1.100 - 192.168.1.200
```

The DHCP server can allocate addresses from that pool.

---

# 6. DHCP Address Pools

A DHCP server commonly has a pool or scope of available addresses.

Example:

```text
Subnet:
10.20.30.0/24

Gateway:
10.20.30.1

DHCP range:
10.20.30.100 - 10.20.30.200
```

A client might receive:

```text
10.20.30.137
```

Another might receive:

```text
10.20.30.138
```

The DHCP server manages these allocations.

---

# 7. DHCP Leases

DHCP addresses are normally leased rather than permanently given to a device.

Suppose:

```text
Client:
Laptop A

Assigned IP:
192.168.1.50

Lease:
8 hours
```

The client is allowed to use that address for the lease period.

Conceptually:

```text
DHCP Server
     |
     | Lease
     v
192.168.1.50
     |
     v
Laptop A
```

The address can later be renewed or eventually returned to the available pool.

---

# 8. Why DHCP Uses Leases

Imagine a hotel Wi-Fi network.

Hundreds of guests connect and disconnect.

If every assigned address remained permanently reserved:

```text
Guest 1 -> address forever
Guest 2 -> address forever
Guest 3 -> address forever
```

the address pool would eventually be exhausted.

Leases allow addresses to be reused.

```text
Device joins
    |
    v
Receives address
    |
    v
Uses address temporarily
    |
    v
Leaves network
    |
    v
Lease eventually expires
    |
    v
Address can be reused
```

---

# 9. DHCP Uses UDP

DHCP commonly uses:

```text
UDP port 67
```

for the server and:

```text
UDP port 68
```

for the client.

A useful memory aid:

```text
Server: UDP 67
Client: UDP 68
```

DHCP has an unusual challenge:

The client may need DHCP because it does not yet have a usable IP configuration.

That affects how the initial messages are sent.

---

# 10. The DORA Process

One of the most important DHCP concepts is:

```text
DORA
```

It represents:

```text
D = Discover
O = Offer
R = Request
A = Acknowledgment
```

The basic DHCP exchange is:

```text
Client                   DHCP Server
  |                           |
  |------ Discover ---------->|
  |                           |
  |<------- Offer ------------|
  |                           |
  |------- Request ---------->|
  |                           |
  |<---- Acknowledgment ------|
  |                           |
```

Memorize DORA, but understand what each step means.

---

# 11. DHCP Discover

A new client joins a network.

It does not necessarily know:

```text
Its IP address
The DHCP server's IP
The network configuration
```

So it sends a DHCP Discover message.

Conceptually:

```text
Client:

"Is there a DHCP server here?
I need configuration."
```

This initial communication commonly relies on broadcast behavior on the local network.

---

# 12. Why DHCP Discover Uses Broadcast Behavior

Consider the client's problem.

It does not know the DHCP server.

Therefore it cannot simply say:

```text
Send directly to DHCP server 10.0.0.10
```

because it may not know that server exists.

Instead, the initial process allows DHCP servers reachable for that network to receive the client's request.

At Layer 2, broadcast communication is therefore important during initial DHCP discovery.

---

# 13. DHCP Offer

A DHCP server receives the Discover.

It may respond with a DHCP Offer.

Conceptually:

```text
Server:

"I can provide configuration.

I am offering you:
IP 192.168.1.50
Mask 255.255.255.0
Gateway 192.168.1.1
DNS 192.168.1.1
Lease 8 hours"
```

The Offer proposes configuration.

---

# 14. Multiple DHCP Offers

It is possible for more than one DHCP server to respond.

Conceptually:

```text
                DHCP Server A
               /
Client Discover
               \
                DHCP Server B
```

Server A:

```text
Offer:
192.168.1.50
```

Server B:

```text
Offer:
192.168.1.80
```

The client can choose an offer and continue the process.

This is also why unauthorized DHCP servers can cause serious problems.

---

# 15. DHCP Request

After receiving an offer, the client sends a DHCP Request.

Conceptually:

```text
Client:

"I would like to use the configuration
offered by this DHCP server."
```

This message also helps indicate which offer the client selected.

The process becomes:

```text
Discover
   |
   v
Offer
   |
   v
Request
```

---

# 16. DHCP Acknowledgment

The selected DHCP server responds with a DHCP acknowledgment, commonly called:

```text
DHCPACK
```

Conceptually:

```text
Server:

"Approved.
You may use this configuration."
```

Now the client can configure its interface.

The completed DORA sequence is:

```text
DISCOVER
   |
   v
OFFER
   |
   v
REQUEST
   |
   v
ACK
```

---

# 17. DHCP NAK

Not every DHCP Request results in an acknowledgment.

A server can send a negative acknowledgment:

```text
DHCPNAK
```

Conceptually:

```text
"You cannot use that configuration
on this network."
```

This can occur when previously remembered configuration is no longer valid for the current network.

The client then needs to obtain valid configuration.

---

# 18. DHCP Packet Flow

A simplified initial exchange:

```text
Laptop
MAC: AA:AA:AA:AA:AA:AA
No usable IPv4 yet
        |
        | DHCP Discover
        v
Broadcast domain
        |
        v
DHCP Server
10.0.0.10
        |
        | DHCP Offer
        v
Laptop
        |
        | DHCP Request
        v
DHCP Server
        |
        | DHCP ACK
        v
Laptop configured:
10.0.0.50/24
Gateway 10.0.0.1
DNS 10.0.0.53
```

Now normal IP communication can begin.

---

# 19. DHCP Options

DHCP options carry additional configuration information.

Important examples include information for:

```text
Subnet mask
Default gateway
DNS servers
Domain/search information
Lease duration
```

The client receives these as part of the DHCP configuration process.

---

# 20. IP Address Assignment

The most obvious DHCP result is the client's IP address.

Example:

```text
10.10.20.137
```

But remember Part 5:

An IP address without a prefix or subnet mask is incomplete network information.

The client must know the network boundary.

---

# 21. Subnet Mask Assignment

DHCP can provide:

```text
255.255.255.0
```

which corresponds to:

```text
/24
```

Now the client knows:

```text
IP:
10.10.20.137

Prefix:
/24

Network:
10.10.20.0/24
```

This allows the client to determine whether destinations are local or remote.

---

# 22. Default Gateway Assignment

DHCP commonly provides the default gateway.

Example:

```text
10.10.20.1
```

This tells the client:

```text
"For destinations that are not local
and for which no more specific route exists,
send traffic toward this router."
```

Without a correct default gateway:

```text
Local communication may work.

Remote communication may fail.
```

---

# 23. DNS Server Assignment

DHCP can also provide DNS server addresses.

Example:

```text
DNS:
10.10.0.53
10.10.0.54
```

Now the host knows where to send DNS queries.

This connects directly to Part 10.

A DHCP problem can therefore appear to users as:

```text
DNS problem
```

if DHCP supplies the wrong DNS server.

---

# 24. One DHCP Configuration Can Affect Multiple Layers

Suppose DHCP gives:

```text
IP:
10.0.10.50

Mask:
/24

Gateway:
10.0.10.1

DNS:
10.0.0.53
```

A mistake in each field causes different symptoms.

Wrong IP:

```text
General connectivity problems
```

Wrong mask:

```text
Incorrect local/remote decisions
```

Wrong gateway:

```text
Remote network failures
```

Wrong DNS:

```text
Names fail while IP connectivity may work
```

This is why you should inspect the entire DHCP configuration.

---

# 25. DHCP Lease Renewal

A DHCP client does not normally wait until the final second of its lease and suddenly lose its address.

It attempts to renew the lease.

Conceptually:

```text
Lease begins
     |
     v
Client uses address
     |
     v
Renewal attempted
     |
     +--> Success
     |       |
     |       v
     |   Lease extended
     |
     +--> Failure
             |
             v
       Further attempts
```

---

# 26. T1 and T2

DHCP lease behavior commonly involves two timers:

```text
T1
Renewal

T2
Rebinding
```

By default, T1 is typically around 50% of the lease duration and T2 around 87.5%, although servers can provide timer values.

At T1, the client normally tries to renew with the server that issued the lease.

If that fails, the client eventually reaches rebinding behavior and can seek help more broadly.

---

# 27. Lease Renewal Example

Suppose:

```text
Lease duration:
8 hours
```

Conceptually:

```text
0h
Lease begins

        |
        v

~4h
Renewal attempt

        |
        v

If successful:
new lease period
```

The user normally notices nothing.

DHCP renewal is designed to happen automatically.

---

# 28. What Happens When a Lease Expires?

If the client cannot renew and the lease eventually expires, it should no longer continue using that leased configuration as though it remains valid.

It needs valid DHCP configuration again.

This can produce symptoms such as:

```text
Network worked earlier.

Then connectivity disappeared.
```

Possible cause:

```text
DHCP renewal failure.
```

---

# 29. DHCP Reservations

DHCP can also be configured so a particular client consistently receives a particular address.

Conceptually:

```text
Client identifier / MAC
AA:BB:CC:DD:EE:FF
        |
        v
DHCP reservation
        |
        v
Always offer:
10.0.0.50
```

This combines centralized DHCP management with predictable addressing.

Reservations are often useful for infrastructure that should retain stable addresses.

---

# 30. Static IP vs DHCP Reservation

These are not the same.

Static configuration:

```text
Host itself configured manually:

IP 10.0.0.50
Gateway 10.0.0.1
DNS 10.0.0.53
```

DHCP reservation:

```text
Host uses DHCP.

DHCP server consistently assigns:
10.0.0.50
```

The final IP may be the same.

The management method is different.

---

# 31. DHCP Is Normally Limited by Broadcast Boundaries

Recall from Part 7:

Routers separate broadcast domains.

Suppose:

```text
VLAN 10
10.0.10.0/24

VLAN 20
10.0.20.0/24
```

and the DHCP server exists in:

```text
Server network
10.0.100.0/24
```

A DHCP Discover broadcast from VLAN 10 does not simply cross the router as an ordinary Layer 2 broadcast.

This creates a problem.

---

# 32. DHCP Relay

DHCP relay solves this problem.

A router or Layer 3 device can receive the local DHCP client request and relay it toward a DHCP server on another network.

Conceptually:

```text
Client
VLAN 10
   |
   | DHCP Discover
   v
Router / L3 Switch
DHCP Relay
   |
   | Relayed DHCP request
   v
DHCP Server
10.0.100.10
```

The server does not need to physically exist in every VLAN.

---

# 33. Why DHCP Relay Matters

Imagine an enterprise with:

```text
100 VLANs
```

Without DHCP relay, you might need DHCP services directly reachable within each broadcast domain.

Instead:

```text
VLAN 10 ----\
VLAN 20 -----\
VLAN 30 ------> Routers/L3 switches
VLAN 40 -----/       |
                    v
             Central DHCP Servers
```

This centralizes DHCP management.

---

# 34. How the DHCP Server Knows Which Subnet to Use

If a central DHCP server serves multiple networks, it needs to know which subnet the client belongs to.

The relay provides information that helps the server identify the originating network.

The server can then choose the appropriate DHCP scope.

Example:

```text
Request came through VLAN 20 gateway:
10.0.20.1
```

Server selects:

```text
10.0.20.0/24 scope
```

rather than:

```text
10.0.10.0/24
```

---

# 35. DHCP Relay Failure

Suppose:

```text
VLAN 10 clients get addresses.

VLAN 20 clients do not.
```

The DHCP server itself may be healthy.

Possible problem:

```text
DHCP relay missing or incorrect
on VLAN 20.
```

This is an important troubleshooting pattern.

If DHCP works in one VLAN but not another, investigate the network-specific path.

---

# 36. DHCP Troubleshooting: First Question

When a user says:

```text
"I have no Internet."
```

first inspect the actual configuration.

Linux:

```bash
ip addr
```

and:

```bash
ip route
```

Windows:

```powershell
ipconfig /all
```

macOS:

```bash
ifconfig
```

and inspect the active network service configuration as appropriate.

Do not immediately restart the router.

---

# 37. DHCP Troubleshooting: Check the Address

Ask:

```text
Does the client have an IP address?
```

Expected:

```text
10.x.x.x
172.16-31.x.x
192.168.x.x
```

depending on the network.

Unexpected example:

```text
169.254.x.x
```

As you learned in Part 4, IPv4 link-local/APIPA addressing can indicate that expected DHCP configuration was not obtained.

---

# 38. DHCP Troubleshooting: Check the Prefix

Suppose expected:

```text
10.0.20.50/24
```

but client has:

```text
10.0.20.50/16
```

The IP itself looks correct.

But the prefix is wrong.

The host may make incorrect local/remote decisions.

Always check:

```text
IP + prefix
```

not just IP.

---

# 39. DHCP Troubleshooting: Check the Gateway

Run:

```bash
ip route
```

You might expect:

```text
default via 10.0.20.1
```

If there is no default route, remote networks may be unreachable.

If the gateway is wrong:

```text
default via 10.0.20.254
```

traffic may be sent to the wrong router.

---

# 40. DHCP Troubleshooting: Check DNS

Inspect:

```bash
cat /etc/resolv.conf
```

or the active system resolver configuration.

Suppose DHCP incorrectly supplied:

```text
DNS:
10.99.99.99
```

Then:

```text
ping 8.8.8.8
```

might work while:

```text
dig example.com
```

fails.

The underlying problem may be DHCP configuration, even though the visible symptom is DNS failure.

---

# 41. DHCP Troubleshooting With Packet Capture

On Linux, you can observe DHCP traffic with a packet capture.

For example:

```bash
sudo tcpdump -n -i eth0 'port 67 or port 68'
```

Then renew or reconnect the client in a safe environment.

You may observe:

```text
Discover
Offer
Request
ACK
```

This lets you identify exactly where DORA stops.

---

# 42. DORA Failure Patterns

### Discover but no Offer

Possible causes:

```text
DHCP server unavailable
DHCP relay problem
VLAN problem
Firewall/policy problem
DHCP pool exhausted
```

### Offer but no Request

Investigate:

```text
Client behavior
Network path
Competing offers
```

### Request but no ACK

Investigate:

```text
Server decision
Requested address validity
Relay/path problems
```

The packet sequence gives you evidence.

---

# 43. DHCP Pool Exhaustion

Suppose DHCP pool:

```text
192.168.1.100 - 192.168.1.110
```

Only 11 addresses are available.

If all addresses are leased, the server may be unable to offer another client a usable address.

Symptoms:

```text
Existing users work.

New users cannot obtain addresses.
```

Check:

```text
Pool size
Active leases
Expired leases
Reservations
Subnet capacity
```

---

# 44. Rogue DHCP Server

A rogue DHCP server is an unauthorized DHCP server responding to clients.

Suppose legitimate DHCP says:

```text
Gateway:
10.0.0.1

DNS:
10.0.0.53
```

but rogue DHCP says:

```text
Gateway:
10.0.0.99

DNS:
10.0.0.99
```

Some clients may receive incorrect or malicious configuration.

Symptoms can appear intermittent because different clients may receive different offers.

Enterprise switches can use protections such as DHCP snooping to help control this risk.

---

# 45. DHCP Troubleshooting Checklist

When DHCP fails, check:

```text
1. Is the interface up?

2. Is the client configured for DHCP?

3. Did the client send Discover?

4. Did a server send Offer?

5. Did the client send Request?

6. Did the server send ACK?

7. Is the DHCP pool exhausted?

8. Is the correct VLAN configured?

9. Is DHCP relay configured?

10. Are UDP 67/68 flows permitted?

11. Is the assigned prefix correct?

12. Is the gateway correct?

13. Are DNS servers correct?

14. Is there a rogue DHCP server?

15. Can the lease renew?
```

---

# 46. Transition From DHCP to NAT

Now our client has:

```text
IP:
192.168.1.50/24

Gateway:
192.168.1.1

DNS:
192.168.1.1
```

It wants to connect to an Internet server.

But:

```text
192.168.1.50
```

is an RFC 1918 private IPv4 address.

It is not globally routed across the public Internet.

So how does the client access Internet services?

This introduces NAT.

---

# 47. What Is NAT?

NAT stands for:

```text
Network Address Translation
```

NAT changes IP addressing information as traffic passes through a NAT device.

A simple example:

```text
Private host
192.168.1.50
      |
      v
NAT Router
      |
      | Translate
      v
Public address
203.0.113.10
      |
      v
Internet
```

The external server sees communication associated with the translated public address rather than the client's RFC 1918 source address.

---

# 48. Why NAT Became Important

IPv4 has approximately:

```text
2^32
```

addresses.

That is roughly:

```text
4.29 billion
```

total possible IPv4 addresses, with many ranges unavailable for ordinary public host addressing.

As Internet usage exploded, globally unique IPv4 addresses became scarce.

Private IPv4 addressing combined with NAT allowed organizations to reuse private ranges internally.

For example:

```text
Company A:
10.0.0.0/8

Company B:
10.0.0.0/8

Home network:
192.168.1.0/24
```

These networks can reuse private addresses because those addresses are not globally unique public Internet addresses.

---

# 49. NAT Is Not the Same as Private Addressing

Private addressing and NAT are related but separate concepts.

Private address:

```text
192.168.1.50
```

NAT:

```text
A translation process performed
by a network device.
```

You can have private networks without Internet NAT.

You can also use NAT for purposes beyond ordinary private-to-public Internet access.

Keep the concepts separate.

---

# 50. Private IPv4 Ranges Review

RFC 1918 private ranges are:

```text
10.0.0.0/8
```

```text
172.16.0.0/12
```

```text
192.168.0.0/16
```

These are commonly used inside:

* Homes
* Offices
* Data centers
* Cloud networks
* Labs
* Virtual environments

They are not intended to be globally routed across the public Internet.

---

# 51. Public IPv4 Addresses

A public IPv4 address can be globally routable when correctly allocated and routed.

For documentation, we will use addresses such as:

```text
203.0.113.10
```

rather than real production addresses.

Suppose your router has:

```text
Inside:
192.168.1.1

Outside:
203.0.113.10
```

It can perform NAT between these environments.

---

# 52. Source NAT

Source NAT changes the:

```text
Source IP address
```

of a packet.

It is often called:

```text
SNAT
```

Example:

Before NAT:

```text
Source:
192.168.1.50

Destination:
198.51.100.20
```

After SNAT:

```text
Source:
203.0.113.10

Destination:
198.51.100.20
```

The destination remains the same.

The source changes.

---

# 53. Source NAT Packet Flow

Suppose:

```text
Laptop:
192.168.1.50

Router public IP:
203.0.113.10

Web server:
198.51.100.20
```

Original packet:

```text
SRC: 192.168.1.50
DST: 198.51.100.20
```

After source translation:

```text
SRC: 203.0.113.10
DST: 198.51.100.20
```

The Internet server therefore sees:

```text
203.0.113.10
```

as the source.

---

# 54. Destination NAT

Destination NAT changes the:

```text
Destination IP address
```

It is commonly called:

```text
DNAT
```

Example:

Before translation:

```text
SRC:
198.51.100.50

DST:
203.0.113.10
```

After DNAT:

```text
SRC:
198.51.100.50

DST:
10.0.0.20
```

This is useful for directing incoming traffic toward internal systems.

---

# 55. SNAT vs DNAT

Remember:

```text
SNAT
Source changes
```

```text
DNAT
Destination changes
```

Example:

```text
Outbound Internet access:
Often SNAT/PAT
```

Example:

```text
Incoming published service:
Often DNAT / port forwarding
```

This distinction is fundamental.

---

# 56. Static NAT

Static NAT creates a fixed mapping.

Conceptually:

```text
10.0.0.20
    |
    | fixed translation
    v
203.0.113.20
```

Whenever that mapping is used, the relationship remains predictable.

Static NAT can be useful when an internal system needs a stable translated address.

---

# 57. Dynamic NAT

Dynamic NAT selects translated addresses dynamically from a pool.

Example:

```text
Private hosts:

10.0.0.10
10.0.0.11
10.0.0.12

        |
        v

Public NAT pool:

203.0.113.20
203.0.113.21
203.0.113.22
```

Mappings are created as needed according to the NAT system's configuration.

Unlike static NAT, a particular private host does not necessarily always receive the same public mapping.

# 58. The Problem With Simple One-to-One NAT

Suppose you have:

```text
1,000 private devices
```

but only:

```text
1 public IPv4 address
```

Simple one-to-one address translation cannot give every device its own public address simultaneously.

Yet your home may have:

```text
Laptop
Phone
Tablet
TV
Console
Camera
Printer
```

all accessing the Internet through one public IPv4 address.

How?

PAT.

---

# 59. What Is PAT?

PAT stands for:

```text
Port Address Translation
```

PAT translates port information as well as addressing information so many internal connections can share a public IPv4 address.

It is sometimes called:

```text
NAT overload
```

In everyday conversation, people often simply call this NAT.

But PAT explains how one public address can represent many simultaneous internal connections.

---

# 60. PAT Example

Suppose:

```text
Laptop:
192.168.1.10:51000

Phone:
192.168.1.20:52000
```

Both connect to:

```text
198.51.100.20:443
```

The NAT router might create:

```text
192.168.1.10:51000
        |
        v
203.0.113.10:40001
```

and:

```text
192.168.1.20:52000
        |
        v
203.0.113.10:40002
```

Same public IP.

Different translated ports.

---

# 61. Why Ports Matter to PAT

From Part 9, remember:

```text
IP address + transport protocol + port
```

helps identify transport endpoints and flows.

PAT can use translated port numbers to distinguish internal connections.

Example:

```text
Public side:

203.0.113.10:40001
203.0.113.10:40002
203.0.113.10:40003
```

These can correspond to different internal connections.

---

# 62. PAT Translation Table

Conceptually, the router maintains state such as:

| Internal           | Translated         |
| ------------------ | ------------------ |
| 192.168.1.10:51000 | 203.0.113.10:40001 |
| 192.168.1.20:52000 | 203.0.113.10:40002 |
| 192.168.1.30:53000 | 203.0.113.10:40003 |

The real implementation may track additional information including:

```text
Protocol
Source
Destination
Ports
Connection state
Timeouts
```

The important idea is that the NAT device remembers the translation.

---

# 63. NAT Tables

A NAT-capable device needs state or rules that describe translations.

Conceptually:

```text
Inside connection
        |
        v
NAT entry
        |
        v
Outside connection
```

For PAT:

```text
192.168.1.10:51000
        <=>
203.0.113.10:40001
```

When the response returns, the device consults its state to determine which internal client should receive it.

---

# 64. Return Traffic Through PAT

Outbound:

```text
Laptop
192.168.1.10:51000
        |
        v
NAT Router
        |
        v
203.0.113.10:40001
        |
        v
Web Server
198.51.100.20:443
```

Return:

```text
Web Server
198.51.100.20:443
        |
        v
203.0.113.10:40001
        |
        v
NAT table lookup
        |
        v
192.168.1.10:51000
```

This state allows the router to return traffic to the correct device.

# 65. Why Unsolicited Inbound Connections Are Different

Suppose an Internet host sends:

```text

203.0.113.10:8080
```

but the NAT device has:

```text

No port-forwarding rule
```

How would it know whether the packet belongs to:

```text

192.168.1.20
192.168.1.30
```

?

It does not automatically know.

That is one reason incoming services behind NAT often require explicit configuration.

# 66. Port Forwarding

Port forwarding creates an explicit rule that sends incoming traffic toward a particular internal host and port.

Example:

```text
Public:
203.0.113.10:443

        |
        v

Internal:
192.168.1.50:443
```

Conceptually:

```text
Internet
   |
   | 203.0.113.10:443
   v
Router
   |
   | DNAT / Port Forward
   v
192.168.1.50:443
```

---

# 67. Port Translation

The external and internal ports do not necessarily need to match.

Example:

```text
Public:
203.0.113.10:8443
```

forwarded to:

```text
Internal:
192.168.1.50:443
```

Conceptually:

```text
203.0.113.10:8443
        |
        v
192.168.1.50:443
```

Both destination address and destination port may be translated.

---

# 68. Port Forwarding Does Not Guarantee the Service Works

Suppose:

```text
203.0.113.10:443
        |
        v
192.168.1.50:443
```

is configured correctly.

The service can still fail because:

```text

Application is not listening
Wrong internal IP
Wrong route
Host firewall blocks traffic
ISP blocks traffic
Upstream NAT exists
```

NAT is only one part of the packet path.

---

# 69. NAT Is Not a Firewall

A very important distinction:

```text
NAT
!=
Firewall
```

NAT performs translation.

A firewall performs traffic filtering according to security policy.

Many devices perform both functions:

```text
Home router
   |
   +--> Routing
   +--> NAT
   +--> Firewall
   +--> DHCP
   +--> DNS forwarding
   +--> Wi-Fi
```

Because these features exist in one box, beginners often confuse their purposes.

Keep them conceptually separate.

# 87. NAT Port Exhaustion

PAT has finite translation resources.

Suppose thousands of workloads share one public IP and create huge numbers of simultaneous connections.

The NAT system must distinguish these translations using available transport state and ports.

At sufficient scale, available translation capacity can become exhausted.

Symptoms may include:

```text
New outbound connections fail.

Existing connections continue working.

Failures appear only under heavy load.
```

This is an important production troubleshooting concept.

---

# 88. NAT State Expiration

NAT entries are not necessarily permanent.

A NAT device tracks connection or flow state and eventually removes stale entries.

Different protocols and connection states can have different timeout behavior.

Conceptually:

```text
Connection created
      |
      v
NAT entry created
      |
      v
Traffic occurs
      |
      v
Connection ends / becomes idle
      |
      v
Timeout
      |
      v
NAT entry removed
```

This prevents NAT tables from growing forever.

# 95. Packet Capture Gives You Translation Evidence

This is a powerful troubleshooting technique.

```text

      |
      v
NAT device
      |
      v
```

Capture both sides.

```text

Did the translated packet leave?

```

# 96. NAT Troubleshooting: Return Route

Suppose outbound translation works.

The server responds.

But the return traffic takes a different path that does not pass through the NAT device holding the translation state.

Conceptually:

```text

  |
  v
NAT A
  |
  v
Internet
```

```text

  |
  v
NAT B
  |
  X
```

Stateful translation often makes path symmetry important.

# 100. NAT and IPv6

NAT became deeply associated with IPv4 partly because of IPv4 address scarcity.

# 117. Common DHCP Beginner Mistakes

### Mistake 1: Thinking DHCP only assigns IP addresses

It can also supply gateway, mask, DNS, and other options.

### Mistake 2: Assuming DHCP works across routers automatically

Broadcast boundaries matter. DHCP relay may be required.

### Mistake 3: Ignoring lease expiration

DHCP configuration is commonly leased.

### Mistake 4: Treating 169.254.x.x as a normal expected enterprise address

It often indicates failure to obtain expected IPv4 DHCP configuration.

### Mistake 5: Checking only the IP address

Check:

```text
IP
Prefix
Gateway
DNS
```

# 118. Common NAT Beginner Mistakes

### Mistake 1: Thinking NAT and routing are the same

Routing chooses paths.

NAT translates addresses.

### Mistake 2: Thinking NAT and firewalling are the same

They are separate functions.

### Mistake 3: Thinking private addresses are automatically secure

Private addressing alone is not a complete security policy.

### Mistake 4: Thinking every device behind NAT needs a unique public IP

PAT allows many connections to share public IPv4 addresses.

### Mistake 5: Assuming NAT is only outbound

DNAT and port forwarding support incoming translation scenarios.

### Mistake 6: Forgetting return traffic

Stateful NAT requires correct return handling.

# 142. Final Mental Model

When a new device joins a network:

```text
DEVICE JOINS
     |
     v
DHCP
     |
     +--> IP address
     +--> Prefix
     +--> Default gateway
     +--> DNS
     |
     v
DEVICE IS CONFIGURED
     |
     v
DNS
Name -> IP
     |
     v
ROUTING DECISION
Local or remote?
     |
     v
REMOTE
     |
     v
DEFAULT GATEWAY
     |
     v
ARP
Gateway IP -> Gateway MAC
     |
     v
PACKET REACHES ROUTER
     |
     v
NAT / PAT
Private source -> translated source
     |
     v
PUBLIC ROUTING
     |
     v
REMOTE SERVER
     |
     v
RESPONSE
     |
     v
NAT STATE LOOKUP
     |
     v
REVERSE TRANSLATION
     |
     v
PRIVATE CLIENT
```

The central lesson from Part 11 is that **DHCP and NAT solve completely different problems**.

DHCP answers:

```text
"What network configuration
should this device use?"
```

NAT answers:

```text
"How should addressing information
be translated as this traffic
crosses this network boundary?"
```

PAT answers:

```text
"How can many simultaneous
private IPv4 connections share
limited public IPv4 addresses?"
```

Once you keep those three responsibilities separate, problems such as **no DHCP lease, wrong gateway, incorrect DNS assignment, missing DHCP relay, broken NAT route, incorrect port forwarding, double NAT, or NAT port exhaustion** become much easier to diagnose systematically.
