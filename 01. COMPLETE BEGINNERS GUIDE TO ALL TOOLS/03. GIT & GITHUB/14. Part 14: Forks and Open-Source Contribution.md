# Part 14: Forks and Open-Source Contribution

In Part 13, you learned how teams collaborate using feature branches and pull requests.

The workflow looked like this:

```text
Shared Repository
       |
       v
     main
       |
       v
Feature Branch
       |
       v
    Commits
       |
       v
      Push
       |
       v
Pull Request
       |
       v
     Review
       |
       v
     Merge
```

That works well when you already have permission to push branches to the shared repository.

But what happens when you find an open-source project on GitHub and want to contribute to it?

You may be able to read the repository.

You may be able to clone it.

But you may not have permission to push your own branch into it.

This creates a new problem:

```text
How can I contribute code to a repository
that I do not control?
```

One common GitHub solution is:

```text
Fork
```

A fork gives you your own GitHub-side copy of another repository.

You can then:

```text
Fork original repository
        |
        v
Clone your fork
        |
        v
Create contribution branch
        |
        v
Make changes
        |
        v
Commit
        |
        v
Push to your fork
        |
        v
Open pull request
        |
        v
Original repository
```

This is one of the foundational workflows of open-source development.

By the end of this part, you should understand:

* What a fork is
* How a fork differs from a clone
* Why forks exist
* What `origin` means
* What `upstream` commonly means
* How to fork a GitHub repository
* How to clone your fork
* How to add the original repository as another remote
* How to keep your fork synchronized
* How to create contribution branches
* Why `CONTRIBUTING.md` matters
* When to open an issue before writing code
* How to make a focused contribution
* How to submit a pull request from a fork
* How to respond to maintainers
* How to update an outdated pull request
* How to behave professionally in open-source communities
* How to complete a full first-contribution workflow

---

# 1. The Problem Forks Solve

Imagine there is a GitHub repository:

```text
github.com/example-org/platform-tool
```

The repository belongs to:

```text
example-org
```

You discover a documentation mistake.

You want to fix it.

You clone the repository:

```bash
git clone https://github.com/example-org/platform-tool.git
```

Now you have a local copy.

You edit the documentation.

You commit the change.

Then you try:

```bash
git push
```

GitHub rejects the push.

Why?

Because being able to read or clone a public repository does not automatically mean you have permission to write to it.

Conceptually:

```text
Original Repository
example-org/platform-tool

        |
        | clone allowed
        v

Your Computer

        |
        | push?
        v

Original Repository

        X
   No write permission
```

You need somewhere on GitHub where you are allowed to push your contribution.

That is where a fork becomes useful.

---

# 2. What Is a Fork?

A fork is a repository on GitHub created from another repository.

Suppose the original repository is:

```text
example-org/platform-tool
```

Your GitHub username is:

```text
ann-dev
```

After forking, you may have:

```text
ORIGINAL

example-org/platform-tool


YOUR FORK

ann-dev/platform-tool
```

The fork exists under your account or another destination where GitHub allows you to create it.

Conceptually:

```text
example-org/platform-tool
          |
          | fork
          v
ann-dev/platform-tool
```

The fork starts from the original project's repository content and history.

But it is now a separate repository on GitHub.

You can work with your fork without needing normal push access to the original repository.

---

# 3. A Fork Is Not Just a Folder Copy

A beginner might think:

```text
Fork = copy and paste repository
```

That mental model is incomplete.

A GitHub fork has a relationship to the repository it was forked from.

GitHub can understand that:

```text
ann-dev/platform-tool
```

was forked from:

```text
example-org/platform-tool
```

That relationship supports workflows such as:

```text
Synchronizing fork changes

Comparing branches

Creating pull requests back to the original project
```

So remember:

```text
Fork
=
GitHub repository created from another repository
and associated with that repository's fork network
```

---

# 4. Fork vs Clone

This is one of the most important distinctions in this part.

A fork and a clone are not the same thing.

## Fork

A fork is created on GitHub.

Example:

```text
GitHub

example-org/platform-tool
          |
          | Fork
          v
ann-dev/platform-tool
```

## Clone

A clone creates a local Git repository from a repository you can access.

Example:

```text
GitHub

ann-dev/platform-tool
          |
          | git clone
          v
Your Computer

~/projects/platform-tool
```

The two operations happen in different places.

---

# 5. Fork vs Clone Diagram

Think of the full workflow like this:

```text
                   GITHUB

          ORIGINAL REPOSITORY

        example-org/platform-tool
                  |
                  | Fork
                  v
             YOUR FORK

          ann-dev/platform-tool
                  |
                  | git clone
                  v

              YOUR COMPUTER

          ~/projects/platform-tool
```

The fork exists remotely on GitHub.

The clone exists locally on your computer.

---

# 6. What git clone Actually Does

From Part 12, recall that:

```bash
git clone <repository-url>
```

does much more than download visible files.

Git creates a local Git repository containing the repository's reachable Git history and references needed for the clone.

It also:

* Creates a working tree
* Creates local repository metadata
* Configures a remote
* Usually names that remote `origin`
* Creates a local branch associated with the cloned repository's default branch

If you clone your fork:

```bash
git clone https://github.com/ann-dev/platform-tool.git
```

then `origin` normally points to:

```text
ann-dev/platform-tool
```

not:

```text
example-org/platform-tool
```

This becomes extremely important later.

---

# 7. Fork vs Clone Summary

| Operation | Where it happens   | Main purpose                                              |
| --------- | ------------------ | --------------------------------------------------------- |
| Fork      | GitHub             | Create your own GitHub repository from another repository |
| Clone     | Your local machine | Create a local Git repository from a remote repository    |

The workflow is often:

```text
Fork
  |
  v
Clone
  |
  v
Develop
```

Not:

```text
Fork = Clone
```

They solve different problems.

---

# 8. Why Forks Exist

Forks are useful because repository owners often should not give every potential contributor direct write access.

Imagine a popular open-source project with:

```text
50,000 users
```

Suppose 2,000 people want to contribute.

It would be dangerous and administratively difficult to give all of them direct push permission to the original repository.

Instead:

```text
Original Repository
        |
        +--> Contributor A fork
        |
        +--> Contributor B fork
        |
        +--> Contributor C fork
        |
        +--> Contributor D fork
```

Each contributor can develop independently.

Then contributors propose selected changes back through pull requests.

---

# 9. Forks Separate Permission From Contribution

This is an important idea.

You may not have permission to do:

```text
Your computer
      |
      | push
      v
Original repository
```

But you may be able to do:

```text
Your computer
      |
      | push
      v
Your fork
      |
      | pull request
      v
Original repository
```

This allows participation without giving every contributor direct write access.

---

# 10. A Typical Open-Source Fork Workflow

The basic workflow is:

```text
Original Repository
        |
        | Fork
        v
Your Fork
        |
        | Clone
        v
Local Repository
        |
        | Create branch
        v
Contribution Branch
        |
        | Edit
        v
Changes
        |
        | Commit
        v
Local Commit
        |
        | Push
        v
Your Fork
        |
        | Pull Request
        v
Original Repository
        |
        | Review
        v
Maintainer Decision
```

This workflow may look complicated initially.

By the end of this part, each step should make sense.

# 11. What Is a Remote Again?

Before learning `origin` and `upstream`, recall what a remote is.

A remote is a named configuration in your local Git repository that refers to another repository location.

You can inspect remotes using:

```bash
git remote
```

Example:

```text
origin
```

For more information:

```bash
git remote -v
```

Example:

```text
origin  https://github.com/ann-dev/platform-tool.git (fetch)
origin  https://github.com/ann-dev/platform-tool.git (push)
```

The name:

```text
origin
```

is simply a local remote name.

It is not a special GitHub account.

---

# 12. What origin Means

When you clone a repository, Git normally creates a remote named:

```text
origin
```

pointing to the repository you cloned.

If you clone:

```text
https://github.com/ann-dev/platform-tool.git
```

then:

```text
origin
```

normally refers to:

```text
ann-dev/platform-tool
```

Conceptually:

```text
LOCAL REPOSITORY

origin
  |
  v

YOUR FORK

ann-dev/platform-tool
```

This is why the order matters.

If you want a standard fork workflow, you usually:

```text
Fork original repository
        |
        v
Clone your fork
```

Then `origin` naturally points to your fork.

---

# 13. origin Is a Convention, Not Magic

Git does not require the name:

```text
origin
```

You could theoretically rename it.

But `origin` is the conventional default created by `git clone`.

This matters because beginners sometimes believe:

```text
origin = original open-source repository
```

That is not necessarily true.

In a fork workflow:

```text
origin
```

usually means:

```text
your fork
```

because your fork is what you cloned.

---

# 14. What upstream Means

Now we need another remote.

Your local repository should know about:

```text
Your fork
```

and:

```text
The original project
```

You already have:

```text
origin
```

for your fork.

A common convention is to call the original repository:

```text
upstream
```

Conceptually:

```text
LOCAL REPOSITORY
      |
      +---- origin ----> YOUR FORK
      |
      +---- upstream --> ORIGINAL REPOSITORY
```

Example:

```text
origin
https://github.com/ann-dev/platform-tool.git

upstream
https://github.com/example-org/platform-tool.git
```

---

# 15. upstream Is Also Just a Name

Like `origin`, the name:

```text
upstream
```

is a convention.

Git does not automatically understand:

```text
upstream = original project
```

You configure that relationship.

You could technically call the remote:

```text
original-project
```

But most tutorials and many developers use:

```text
upstream
```

for the original repository in a fork workflow.

That makes communication easier.

---

# 16. The Most Important Remote Diagram

Memorize this model:

```text
                   ORIGINAL PROJECT
                example-org/platform-tool
                          ^
                          |
                       upstream
                          |
                          |
                   LOCAL REPOSITORY
                          |
                          |
                        origin
                          |
                          v
                      YOUR FORK
                 ann-dev/platform-tool
```

Usually:

```text
upstream
=
repository you receive original project updates from

origin
=
your fork, where you can push your contribution branches
```

# 17. Fetch and Push Are Different Directions

The diagram becomes even clearer when you think about operations.

You commonly fetch project updates from:

```bash
git fetch upstream
```

You commonly push your contribution branch to:

```bash
git push origin feature/example
```

Conceptually:

```text
Original Project
      |
      | fetch
      v
Local Repository
      |
      | push
      v
Your Fork
```

Then GitHub uses your fork branch as the source of a pull request back to the original repository.

You should now see something conceptually like:

# 20. Cloning Your Fork

Now clone:

```text
your fork
```

not the original repository.

Using HTTPS, for example:

```bash
git clone https://github.com/ann-dev/platform-tool.git
```

Then enter the repository:

```bash
cd platform-tool
```

Check:

```bash
git status
```

Then inspect remotes:

```bash
git remote -v
```

Expected conceptually:

```text
origin  https://github.com/ann-dev/platform-tool.git (fetch)
origin  https://github.com/ann-dev/platform-tool.git (push)
```

At this point, your local repository knows only about your fork.

---

# 21. Why Clone Your Fork Instead of the Original?

Suppose you clone the original:

```bash
git clone https://github.com/example-org/platform-tool.git
```

Then:

```text
origin
```

points to the original project.

If you do not have push access, later:

```bash
git push origin feature/my-change
```

may fail.

By cloning your fork:

```text
origin
```

naturally becomes a repository where you normally have permission to push.

That makes the contribution workflow simpler.

---

# 22. Adding the Original Repository as upstream

Your local repository currently knows:

```text
origin -> your fork
```

Now add:

```text
upstream -> original repository
```

Command:

```bash
git remote add upstream https://github.com/example-org/platform-tool.git
```

Let's break this down.

```text
git
```

runs Git.

```text
remote
```

works with remote repository configurations.

```text
add
```

creates a new remote entry.

```text
upstream
```

is the name we are giving the remote.

```text
https://github.com/example-org/platform-tool.git
```

is the original repository URL.

---

# 23. Verify the Remotes

Run:

```bash
git remote -v
```

Expected conceptually:

```text
origin    https://github.com/ann-dev/platform-tool.git (fetch)
origin    https://github.com/ann-dev/platform-tool.git (push)

upstream  https://github.com/example-org/platform-tool.git (fetch)
upstream  https://github.com/example-org/platform-tool.git (push)
```

The fact that Git displays a push URL for `upstream` does not mean GitHub will grant you permission to push there.

Remote configuration tells Git where it could attempt an operation.

Authorization determines whether the server permits it.

---

# 24. Authentication vs Authorization

This distinction is important.

Authentication asks:

```text
Who are you?
```

Authorization asks:

```text
What are you allowed to do?
```

You may authenticate successfully as yourself.

But the original repository may still reject:

```bash
git push upstream main
```

because you do not have write permission.

So:

```text
Successful authentication
!=
Permission to modify every repository
```

# 25. Inspecting One Remote

You can inspect a remote using:

```bash
git remote show origin
```

or:

```bash
git remote show upstream
```

This can provide information about:

* Fetch URL
* Push URL
* Remote branches
* Tracking relationships
* Default branch information

The exact output depends on repository state and connectivity.

# 26. Why Forks Become Outdated

Suppose you fork the project on Monday.

At that moment:

```text
Original:
A --- B --- C

Your fork:
A --- B --- C
```

On Tuesday, maintainers merge two pull requests:

```text
Original:
A --- B --- C --- D --- E

Your fork:
A --- B --- C
```

Your fork is now behind the original project.

Nothing is necessarily wrong.

The original project simply continued evolving.

---

# 27. Why Synchronization Matters

Suppose you create a contribution from your outdated fork:

```text
A --- B --- C
          \
           X --- Y
```

Meanwhile upstream is:

```text
A --- B --- C --- D --- E
```

Your contribution started from an older project state.

This can increase the chance of:

* Conflicts
* Outdated assumptions
* Failed tests
* Duplicating work already completed upstream
* Building against old APIs
* Modifying code that has already changed

Before starting new work, synchronize appropriately.

---

# 28. Fetching upstream Changes

Switch to your local default branch.

Assume the project uses:

```text
main
```

Run:

```bash
git switch main
```

Check:

```bash
git status
```

Then fetch upstream:

```bash
git fetch upstream
```

What does this do?

It contacts the remote named:

```text
upstream
```

and updates your local remote-tracking information.

For example:

```text
upstream/main
```

may move forward.

But:

```text
main
```

does not automatically move merely because you fetched.

---

# 29. Local main vs upstream/main

After fetching:

```text
Local main:

A --- B --- C


upstream/main:

A --- B --- C --- D --- E
```

You now know that the original project has:

```text
D
E
```

but your local `main` has not yet integrated them.

This is exactly the distinction you learned in Part 12.

---

# 30. Inspect Before Integrating

Run:

```bash
git status
```

Then you can inspect:

```bash
git log --oneline main..upstream/main
```

This asks Git to show commits reachable from:

```text
upstream/main
```

that are not reachable from:

```text
main
```

Example:

```text
e92bd1a Fix API timeout handling
7ac418f Update installation documentation
```

Now you know what upstream added.

---

# 31. Updating Local main

If your local `main` should mirror the upstream project's `main` and the update can be fast-forwarded, you can use:

```bash
git merge --ff-only upstream/main
```

Let's break it down.

```text
git merge
```

integrates another line of history into the current branch.

```text
--ff-only
```

means:

```text
Only proceed if Git can update this branch
by moving it forward without creating a merge commit.
```

```text
upstream/main
```

is the remote-tracking branch you want your current branch to catch up to.

Before:

```text
main
   |
   v
A --- B --- C --- D --- E
          ^
          |
     upstream history starts ahead
```

More accurately as references:

```text
main
 |
 v
C --- D --- E
          ^
          |
    upstream/main
```

After:

```text
A --- B --- C --- D --- E
                    ^
                    |
                   main
                    |
              upstream/main
```

---

# 32. Why --ff-only Is Useful Here

Suppose your local `main` has its own unrelated commit:

```text
              X
             /
A --- B --- C
             \
              D --- E
```

Now:

```text
main -> X
upstream/main -> E
```

A fast-forward is impossible.

With:

```bash
git merge --ff-only upstream/main
```

Git refuses instead of silently creating a merge commit.

That refusal tells you:

```text
My local main has diverged.
I need to investigate.
```

This is useful for a beginner who intends local `main` to stay clean and closely follow upstream.

---

# 33. Push the Updated main to Your Fork

After your local `main` is synchronized with upstream, your fork on GitHub may still be behind.

Conceptually:

```text
Original:
A --- B --- C --- D --- E

Local main:
A --- B --- C --- D --- E

Your fork:
A --- B --- C
```

Push:

```bash
git push origin main
```

Now:

```text
Original:
A --- B --- C --- D --- E

Local:
A --- B --- C --- D --- E

Your fork:
A --- B --- C --- D --- E
```

The three are synchronized at this point.

---

# 34. GitHub Can Also Help Synchronize a Fork

GitHub provides fork synchronization features in its interface for eligible fork relationships.

For example, you may see a synchronization option for updating your fork from the upstream repository.

However, learning the Git commands remains valuable because it teaches the underlying model:

```text
Fetch upstream

Update local branch

Push to origin
```

The command-line workflow also helps you understand what is happening when synchronization fails.

---

# 35. Safe Fork Synchronization Workflow

A strong beginner workflow is:

```bash
git switch main
git status
git fetch upstream
git log --oneline main..upstream/main
git merge --ff-only upstream/main
git push origin main
```

Conceptually:

```text
Original Repository
        |
        | git fetch upstream
        v
Local Repository
        |
        | fast-forward main
        v
Updated Local main
        |
        | git push origin main
        v
Your Fork
```

# 36. Do Not Develop Directly on main

Now your fork is synchronized.

Do not immediately begin your contribution directly on:

```text
main
```

Create a contribution branch.

Why?

Because you want:

```text
main
=
clean reference branch following upstream
```

and:

```text
contribution branch
=
your proposed change
```

This separation makes future synchronization much easier.

---

# 37. Creating a Contribution Branch

Suppose you want to fix documentation for SSH setup.

First:

```bash
git switch main
```

Make sure `main` is synchronized.

Then:

```bash
git switch -c docs/fix-ssh-setup
```

Verify:

```bash
git branch --show-current
```

Expected:

```text
docs/fix-ssh-setup
```

Now your work is isolated.

---

# 38. Contribution Branch Naming

Follow the project's conventions if documented.

Possible examples:

```text

fix/null-pointer

test/add-api-tests
chore/update-dependencies
```

Some projects may use issue numbers:

```text

```

Others may have completely different naming rules.

The project's documented convention wins.

# 39. Read CONTRIBUTING.md Before Contributing

This is one of the most important habits in open-source contribution.

Look for:

```text
CONTRIBUTING.md
```

It may exist:

```text
in repository root
```

or in another location such as:

```text
.github/

```

GitHub may also surface contribution guidelines through the repository interface.

Read them before making significant changes.

# 40. What CONTRIBUTING.md Is

`CONTRIBUTING.md` is a project document that explains how maintainers want people to contribute.

It may explain:

* How to set up the development environment
* Branch naming rules
* Coding style
* Testing requirements
* Commit conventions
* Pull request requirements
* Issue workflow
* Documentation standards
* Developer certificate or sign-off requirements
* Contributor license agreement requirements
* Where to ask questions

It is effectively:

```text
The project's contribution instructions
```

---

# 41. Why CONTRIBUTING.md Matters

Imagine the project says:

```text
Run these before submitting:

make lint
make test
```

But you submit without running either.

Your PR fails CI.

Or the project says:

```text
Do not open implementation PRs for major features
without an approved issue first.
```

You spend two weeks building a feature.

Maintainers close the PR because it does not fit the roadmap.

Reading contribution guidelines can save significant time.

# 44. Check the License

```text

```


# 45. Issues Before Pull Requests

Should you always open an issue before creating a pull request?

No.

Should you never open an issue first?

Also no.

The correct answer depends on:

* Project guidelines
* Size of the change
* Whether the problem is already known
* Whether design discussion is required
* Maintainer preferences

---

# 46. When an Issue May Not Be Necessary

Suppose the README says:

```text
Run:
dockre compose up
```

Clearly:

```text
dockre
```

should be:

```text
docker
```

A small typo correction may not require a lengthy issue discussion.

If project guidelines allow direct small PRs, you may simply fix it.

---

# 47. When an Issue Is Often Useful

Suppose you want to:

```text
Replace the project's authentication system
```

That is a major change.

Before writing thousands of lines of code, it may be wise or required to open or find an issue.

Explain:

```text
Problem

Proposed approach

Reason

Alternatives

Potential impact
```

Maintainers may say:

```text
Yes, please proceed.
```

Or:

```text
We are already implementing this differently.
```

Or:

```text
This does not fit the project's roadmap.
```

An issue can prevent wasted work.

---

# 48. Search Existing Issues First

Before creating:

```text
Issue #900
```

search existing issues.

The same problem may already exist as:

```text

```

Maintainers do not benefit from ten duplicate issues describing the same bug.

Search using relevant terms.

For example:

```text

```

or:


or:


# 49. Search Existing Pull Requests Too

Someone may already be fixing the issue.

# 74. What Is an Outdated Pull Request?

Suppose you created your contribution from:

```text
A --- B --- C
          \
           X
```

While your PR was waiting, upstream advanced:

```text
A --- B --- C --- D --- E --- F
          \
           X
```

Your branch is now based on an older upstream state.

The PR may still be mergeable.

Or GitHub/project rules may require it to be updated.

Or new upstream changes may conflict with your work.

```text

Files move
```

The project keeps moving.

```text
* D

* C
* B
```

# 77. Do Not Blindly Update

Before changing history, ask:

```text

Does the maintainer want merge or rebase?
```

# 78. Updating With Merge

One possible workflow is to merge current upstream `main` into your contribution branch.

While on:

```text
docs/fix-ssh-example
```

run:

```bash
git merge upstream/main
```

If there are no conflicts:

```text
A --- B --- C --- D --- E --- F
          \                 /
           X --------------M
```

Your branch now includes upstream changes through a merge.

You can push:

```bash
git push
```

This does not rewrite existing contribution commits.

But it adds a merge commit.

Some projects accept this.

Others prefer rebasing.

Follow project policy.

---

# 79. Updating With Rebase

Another workflow is:

```bash
git rebase upstream/main
```

Conceptually:

Before:

```text
A --- B --- C --- D --- E --- F
          \
           X
```

After:

```text
A --- B --- C --- D --- E --- F --- X'
```

Your contribution commit is recreated on top of the latest upstream history.

This produces a cleaner linear history.

But:

```text
X'
```

has a different commit identity from:

```text
X
```

because rebasing rewrites history.

---

# 80. Important Rebase Warning

We will study rebase deeply in Part 17.

For now, understand:

```text
Rebase
=
rewrite the branch's commit history onto a new base
```

If the contribution branch belongs only to you, rebasing may be appropriate when the project expects it.

But do not casually rebase shared branches other people are building upon.

And do not run rebase commands you do not understand merely because a maintainer says:

```text
Please update your branch.
```

Ask for clarification or follow the documented workflow.

---

# 81. Pushing After Rebase

Because rebase rewrites commit IDs, a normal:

```bash
git push
```

may be rejected.

You may need to update your remote contribution branch with a force push.

A safer form is commonly:

```bash
git push --force-with-lease
```

rather than:

```bash
git push --force
```

But this is an advanced operation.

Do not use it blindly.

`--force-with-lease` adds a safety check intended to reduce the chance of overwriting remote changes you did not know about.

Before using it:

```text
Confirm you are on the correct branch

Confirm the branch is yours to rewrite

Fetch current remote state

Inspect history

Confirm nobody else's work will be overwritten

Follow project guidance
```

Part 17 will cover rebase and history rewriting more deeply.

# 82. Updating With Conflicts

Suppose upstream changed:

```text
docs/setup.md
```

and your contribution changed the same lines.

Git may report a conflict.

You learned conflict resolution in Part 9.

You may see:

```text
<<<<<<< HEAD
ssh -p 22 admin@example-server
=======
ssh admin@example-server
>>>>>>> upstream/main
```

Do not simply delete markers and keep whichever side you like.

Understand:

```text
What did upstream change?

Why?

What did my contribution change?

What should the final documentation say?
```

Then construct the correct final file.

---

# 83. Conflict Resolution Reminder

The safe workflow remains:

```text
Conflict occurs
      |
      v
git status
      |
      v
Open conflicted file
      |
      v
Understand both versions
      |
      v
Create correct final content
      |
      v
Remove conflict markers
      |
      v
Test / validate
      |
      v
git add resolved-file
      |
      v
Continue merge or rebase
      |
      v
Verify
```

For a merge:

```bash
git commit
```

may be used to complete the merge when appropriate.

For a rebase:

```bash
git rebase --continue
```

continues after conflicts are resolved and staged.

Do not mix the workflows.

---

# 84. Aborting an Update

If you begin a merge and realize you are not ready:

```bash
git merge --abort
```

If you begin a rebase and need to return to the pre-rebase state:

```bash
git rebase --abort
```

These are important safety tools.

Before complex history operations, ensure your important work is committed or otherwise safely preserved.

# 141. Common Mistake: Cloning the Original Instead of Your Fork

If your intended workflow is fork-based and you clone:

```text
example-org/project
```

then:

```text
origin
```

normally points to the original.

If you lack push permission, pushing contribution branches to `origin` will fail.

Simpler workflow:

```text
Fork original

Clone fork

origin -> fork

upstream -> original
```

# 142. Common Mistake: Assuming origin Means Original Project

In a standard fork workflow:

```text
origin
```

usually means:

```text
your fork
```

while:

```text
upstream
```

usually means:

```text
original repository
```

Always verify:

```bash
git remote -v
```

Never rely only on memory.

# 143. Common Mistake: Pushing to upstream

You intend:

```bash
git push origin feature/fix
```

but run:

```bash
git push upstream feature/fix
```

If you do not have permission, GitHub should reject it.

If you do have permission for some reason, you might modify a repository you did not intend to modify.

Before pushing:

```bash
git remote -v
git branch --show-current
```

Know:

```text
Where am I pushing?

What branch am I pushing?
```

# 153. Troubleshooting: origin Is Wrong

Problem:

```text
git push origin feature/fix
```

tries to push to the original project.

Investigate:

```bash
git remote -v
```

You may discover:

```text
origin -> original repository
```

If you intended your fork to be `origin`, do not blindly change it until you understand the configuration.

You can change a remote URL with:

```bash
git remote set-url origin <your-fork-url>
```

Then verify:

```bash
git remote -v
```

Make sure the new URL is correct.

# 154. Troubleshooting: upstream Already Exists

# 157. Troubleshooting: Fast-Forward Refused

You run:

```bash
git merge --ff-only upstream/main
```

Git refuses.

This means your current branch cannot simply move forward to the requested commit.

Investigate:

```bash
git status
git log --oneline --graph --decorate --all
```

Do not immediately remove `--ff-only`.

Your local `main` may contain commits that should have been on a contribution branch.

Understand the divergence first.

and inspect the PR's base/head configuration.

# 162. Troubleshooting: I Accidentally Committed to main

Do not panic.

Do not immediately run:

```bash
git reset --hard
```

First inspect:

```bash
git status
git log --oneline --decorate -5
```

If the commit exists only locally, you may be able to preserve it by creating a branch pointing to it before repairing `main`.

For example, depending on your exact state:

```bash
git branch contribution-recovery
```

can preserve the current commit under another branch name.

Then carefully repair `main`.

The correct recovery depends on the exact history.

Use the Part 7 principle:

```text
Preserve work first.

Inspect second.

Repair third.
```
