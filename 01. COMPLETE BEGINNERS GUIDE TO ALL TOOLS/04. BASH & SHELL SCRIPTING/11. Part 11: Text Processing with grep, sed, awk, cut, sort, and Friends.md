# Part 11: Text Processing with grep, sed, awk, cut, sort, and Friends

Linux systems produce text constantly.

Application logs are text.

Configuration files are often text.

Command output is usually text.

CI/CD logs are text.

Web-server access logs are text.

Process listings are text.

Container logs are text.

Infrastructure tools frequently produce text or structured text.

This makes text processing one of the most valuable Bash skills for DevOps, SRE, Platform Engineering, Cloud Engineering, and Linux administration.

Suppose an application produces:

```text
2026-09-02T10:15:01Z INFO user=alice action=login status=success duration_ms=120
2026-09-02T10:15:04Z ERROR user=bob action=payment status=failed duration_ms=940
2026-09-02T10:15:08Z WARNING user=alice action=upload status=slow duration_ms=760
2026-09-02T10:15:11Z ERROR user=carol action=payment status=failed duration_ms=1100
```

An engineer may need to answer:

* How many errors occurred?
* Which users experienced failures?
* Which operation is slowest?
* How many payment failures occurred?
* Which status appears most frequently?
* What happened immediately before an error?
* Can we extract only usernames?
* Can we transform the output into a report?

You could manually open the file and inspect every line.

That works for 20 lines.

It does not work well for:

```text
20,000 lines
2 million lines
hundreds of log files
continuous production output
```

Instead, Linux provides small tools that can be connected together.

For example:

```bash
grep 'ERROR' application.log
```

finds error lines.

Then:

```bash
grep 'ERROR' application.log | wc -l
```

counts them.

Then:

```bash
grep 'ERROR' application.log |
    awk '{print $3}' |
    sort |
    uniq -c
```

can begin turning raw logs into useful information.

The important skill is not memorizing commands.

It is learning how to take:

# 1. The Unix Text-Processing Philosophy

A powerful Unix idea is:

> Build small tools that perform focused tasks, then combine them.

Instead of requiring one enormous program to perform every possible operation, Linux provides tools such as:

```text
grep
sort
uniq
cut
sed
awk
wc
```

Each specializes in certain operations.

You combine them using pipes.

For example:

```bash
grep 'ERROR' application.log | wc -l
```

Here:

```text
grep
 |
 +--> finds matching lines

wc -l
 |
 +--> counts those lines
```

The output of the first command becomes the input of the second.

---

# 2. Why This Matters in DevOps

Consider a production incident.

Users report:

```text
Checkout requests are failing.
```

You inspect:

```text
/var/log/myapp/application.log
```

Instead of manually reading 500,000 lines, you might begin with:

```bash
grep 'ERROR' application.log
```

Then narrow further:

```bash
grep 'ERROR' application.log | grep 'payment'
```

Then count:

```bash
grep 'ERROR' application.log | grep 'payment' | wc -l
```

Then identify affected users:

```bash
grep 'ERROR' application.log |
    grep 'payment' |
    awk '{print $3}'
```

Text-processing tools allow engineers to reduce large amounts of operational data into useful evidence.

```text
stdin  = file descriptor 0
```

# 4. Line-Oriented Processing

Many Unix tools naturally process text one line at a time.

Suppose:

```text
alice
bob
carol
david
```

Each newline separates one record-like unit.

For logs:

```text
2026-09-02 INFO service started
2026-09-02 ERROR database unavailable
2026-09-02 INFO retry started
```

each line often represents one event.

This makes line-oriented tools extremely effective for traditional logs and configuration files.

---

# 5. Important Limitation

Not all data is naturally line-oriented.

For example, JSON may contain nested structures:

```json
{
  "user": {
    "name": "alice",
    "roles": ["admin", "developer"]
  }
}
```

Trying to parse complex JSON using:

```text
grep
cut
awk
```

can become fragile.

For JSON, use a JSON-aware tool such as:

```text
jq
```

when available.

The principle is:

> Use text-processing tools when the data format fits them. Use format-aware tools when structure matters.

# 7. `cat`

`cat` originally comes from the word:

```text
concatenate
```

It can read files and write their contents to standard output.

Example:

```bash
cat application.log
```

The contents appear in your terminal.

---

# 8. What `cat` Actually Does

Conceptually:

```text
application.log
      |
      v
     cat
      |
      v
   stdout
      |
      v
   terminal
```

If stdout is redirected:

```bash
cat application.log > copy.log
```

then:

```text
application.log
      |
      v
     cat
      |
      v
   stdout
      |
      v
   copy.log
```

---

# 9. Concatenating Multiple Files

Suppose:

```bash
printf 'server-a\n' > server-a.txt
printf 'server-b\n' > server-b.txt
```

Run:

```bash
cat server-a.txt server-b.txt
```

Output:

```text
server-a
server-b
```

That is where the name `cat` becomes clearer.

It concatenates the streams from multiple files.

---

# 10. Combine Files

You could run:

```bash
cat server-a.txt server-b.txt > servers.txt
```

Now:

```bash
cat servers.txt
```

returns:

```text
server-a
server-b
```

Be careful with output redirection.

Do not do:

```bash
cat application.log > application.log
```

expecting the file to remain unchanged.

The shell opens and truncates the output file before `cat` reads it, potentially destroying the contents.

---

# 11. `cat` Is Not Always Necessary

Beginners often write:

```bash
cat application.log | grep 'ERROR'
```

This usually works.

But `grep` can read the file directly:

```bash
grep 'ERROR' application.log
```

The second form is simpler.

This does not mean `cat` is bad.

It means:

> Do not add commands to a pipeline when another command can already consume the input directly.

# 12. `less`

`cat` is convenient for small files.

Imagine:

```text
application.log = 500 MB
```

Dumping everything to your terminal is not useful.

Use:

```bash
less application.log
```

`less` provides interactive viewing.

You can move through the file rather than printing everything at once.

Press Enter.

# 14. Why `less` Matters Operationally

During an incident, you may need to inspect a large file manually.

Example:


You can search for:

```text

```

without flooding the terminal.

Use `less` when you need interactive investigation.

Use tools such as `grep`, `awk`, and `sed` when you need automated extraction or transformation.

# 15. `head`

`head` displays the beginning of input.

Example:

```bash
head application.log
```

By default, GNU `head` normally displays the first 10 lines.

Our file contains 10 lines, so you would see the entire file.

Specify a number:

```bash
head -n 3 application.log
```

Output:

```text
2026-09-02T10:15:01Z INFO user=alice service=auth action=login status=success duration_ms=120
2026-09-02T10:15:04Z ERROR user=bob service=payment action=charge status=failed duration_ms=940
2026-09-02T10:15:08Z WARNING user=alice service=storage action=upload status=slow duration_ms=760
```

---

# 16. When `head` Is Useful

Examples:

Inspect the beginning of a generated report:

```bash
head report.txt
```

Preview a dataset:

```bash
head -n 20 users.csv
```

Check a configuration file:

```bash
head -n 15 app.conf
```

Test a pipeline against a small sample:

```bash
head -n 100 huge.log | grep 'ERROR'
```

# 18. Following a Growing Log

One of the most useful operational forms is:

```bash
tail -f application.log
```

`-f` means:

```text
follow
```

Instead of exiting after displaying the end of the file, `tail` waits for new data.

Conceptually:

```text
Application
    |
    v
application.log
    |
    v
 tail -f
    |
    v
Terminal updates as lines arrive
```

Stop with:

```text
Ctrl+C
```

# 19. Following Logs During Deployment

Suppose you deploy an application.

In one terminal:

```bash
tail -f application.log
```

In another terminal you perform the deployment.

You can observe new events as they arrive.

This is useful for:

* application startup
* deployment verification
* service failures
* request errors
* background jobs

In modern environments, logs may instead come through `journalctl`, Kubernetes, container runtimes, or centralized logging systems, but the stream-processing concepts remain useful.

Run:


# 21. Count Lines

Use:


A common pattern:

```bash

```

First:

```bash

```

produces matching lines.

Then:

```bash
wc -l
```

counts those lines.

For our log:

```text

```

There are four `ERROR` lines.

# 25. `grep`

`grep` is one of the most important Linux text-search tools.

Basic syntax:

```text
grep PATTERN FILE
```

Example:

```bash
grep 'ERROR' application.log
```

This prints lines containing:

```text
ERROR
```

---

# 26. How `grep` Thinks

Conceptually:

```text
Read line
   |
   v
Does pattern match?
   |
  / \
Yes  No
 |    |
 v    v
Print Skip
```

It repeats this across the input.

---

# 27. `grep` and Exit Status

`grep` communicates more than output.

For ordinary matching:

```text
0 = at least one match
1 = no match
2 = error
```

Example:

```bash
grep 'ERROR' application.log > /dev/null
echo "$?"
```

If errors exist:

```text
0
```

Search for:

```bash
grep 'CRITICAL' application.log > /dev/null
echo "$?"
```

If no line contains `CRITICAL`:

```text
1
```

That does not necessarily mean `grep` malfunctioned.

It means:

> The search completed, but no match was found.

This distinction is important in scripts.

---

# 28. Quiet Search

If you care only whether a match exists:

```bash
grep -q 'ERROR' application.log
```

`-q` means:

```text
quiet
```

Then:

```bash
if grep -q 'ERROR' application.log; then
    printf 'Errors detected.\n'
fi
```

This avoids generating output just to discard it.

---

# 29. Case-Insensitive Search

Suppose some logs contain:

```text
ERROR
Error
error
```

Use:

```bash
grep -i 'error' application.log
```

`-i` ignores letter case.

Use this only when case should genuinely be ignored.

```bash
grep -n 'ERROR' application.log
```

```text
2:2026-09-02T10:15:04Z ERROR ...
```

# 31. Fixed-String Search

By default, `grep` interprets its pattern using basic regular expressions.

Sometimes you do not want pattern interpretation.

You want literal text.

Use:

```bash
grep -F 'literal text' file
```

`-F` means fixed strings.

Example:

```bash
printf '%s\n' 'price=$5.00' 'price=500' > prices.txt
```

Then:

```bash
grep -F '$5.00' prices.txt
```

asks for the literal characters:

```text
$5.00
```

---

# 32. Why Fixed Strings Matter

Suppose you search for text containing characters that have regex meaning.

If you know you want an exact literal fragment, `grep -F` makes your intention clear.

Examples:

```bash
grep -F 'status=failed' application.log
```

```bash
grep -F 'user=alice' application.log
```

For simple literal searches, this is often easier to reason about than regex.

---

# 33. Regular Expressions

A regular expression describes a text pattern.

For example:

```text
^ERROR
```

could mean:

> lines beginning with ERROR.

Our log lines begin with timestamps, so that particular pattern would not match them.

A useful regex might be:

```text
ERROR.*service=payment
```

This means approximately:

```text
ERROR
followed later by
service=payment
```

---

# 34. Basic Regex Concepts

Some common regex elements:

```text
^       beginning of line
$       end of line
.       any single character
*       zero or more of the previous pattern
[abc]   one character from a set
[0-9]   one digit
```

Do not confuse regex:

```text
*
```

with shell globbing:

```text
*
```

They are interpreted differently.

---

# 35. Extended Regular Expressions

GNU `grep` commonly supports:

```bash
grep -E
```

for extended regular expressions.

This makes constructs such as alternatives easier.

Example:

```bash
grep -E 'ERROR|WARNING' application.log
```

This matches lines containing either:

```text
ERROR
```

or:

```text
WARNING
```

---

# 36. Search for Multiple Severity Levels

Run:

```bash
grep -E ' (ERROR|WARNING) ' application.log
```

Why include spaces?

Because we want the severity field:

```text
ERROR
WARNING
```

rather than those words appearing somewhere else inside another value.

The exact strategy depends on the log format.

---

# 37. Regex vs Fixed Strings

Use fixed strings when you mean:

```text
Find this literal text.
```

Example:

```bash
grep -F 'status=failed' application.log
```

Use regex when you mean:

```text
Find text following this pattern.
```

Example:

```bash
grep -E 'duration_ms=[0-9]+' application.log
```

Do not use regex merely because it looks more advanced.

Choose the simplest tool that correctly expresses the requirement.

---

# 38. Inverting Matches

Sometimes you want lines that do **not** match.

Use:

```bash
grep -v 'INFO' application.log
```

`-v` means invert the match.

This returns lines not containing:

```text
INFO
```

In our example, that leaves errors and warnings.

---

# 39. Combine Inversion with Fixed Strings

Example:

```bash
grep -F -v 'status=success' application.log
```

This asks:

> Show lines that do not contain the literal text `status=success`.

Options can often be combined:

```bash
grep -Fv 'status=success' application.log
```

Readable scripts do not need to compress every option.

---

# 40. Recursive Search

Suppose:

```text
logs/
├── api.log
├── auth.log
└── archive/
    └── payment.log
```

You want to search all files below `logs`.

Use:

```bash
grep -r 'ERROR' logs/
```

`-r` means recursive.

---

# 41. Why Recursive Search Needs Care

Running:

```bash
grep -r 'ERROR' /
```

is usually a poor idea.

You could:

* scan enormous numbers of files
* encounter permissions errors
* search pseudo-filesystems
* consume unnecessary resources
* produce huge output

Scope searches deliberately:

```bash
grep -r 'ERROR' "$HOME/bash-lab/part11/logs"
```

Production investigations should minimize unnecessary system load.

---

# 42. Include Filenames

You can explicitly request:

```bash
grep -H 'ERROR' *.log
```

Example:

```text
api.log:ERROR connection failed
payment.log:ERROR transaction failed
```

This helps identify the source file.

An error line alone may not explain what happened.

Suppose:

```text

```

You may want lines around the error.

Use:

```bash
grep -B 2 'ERROR' file
```

`-B` means:

```text

```

It shows two lines before each match.

---

# 44. After Context

Use:

```bash
grep -A 2 'ERROR' file
```

`-A` means:

```text
after
```

It shows two lines after each match.

---

# 45. Before and After

Use:

```bash
grep -C 2 'ERROR' file
```

`-C` means:

```text
context
```

It shows lines both before and after the match.

This is extremely useful during incident investigation.

# 46. Count Matches with `grep`

You can use:

```bash
grep -c 'ERROR' application.log
```

For our file:

```text

```

This is often simpler than:

```bash
grep 'ERROR' application.log | wc -l
```

But understand both forms.

The pipeline form teaches composition and becomes useful when additional transformations are inserted.

# 47. Match Only the Matching Portion

GNU `grep` supports:

```bash
grep -o
```

which prints only the matched text.

Example:

```bash
grep -o 'user=[^ ]*' application.log
```

Possible output:

```text
user=alice
user=bob
user=alice
user=carol
...
```

Here:

```text
user=
```

matches literally.

```text
[^ ]*
```

means:

> zero or more characters that are not spaces.

# 48. Extract Users with `grep`

# 49. `cut`

`cut` extracts selected sections from lines.

It works especially well when fields have a predictable delimiter.

Create:

```bash
cat > users.csv <<'EOF'
alice,engineering,new-york
bob,operations,london
carol,security,mexico-city
david,platform,toronto
EOF
```

---

# 50. Extract a Delimited Field

Run:

```bash
cut -d',' -f1 users.csv
```

Output:

```text
alice
bob
carol
david
```

Break it down:

```text
cut
```

extract portions.

```text
-d','
```

use comma as delimiter.

```text
-f1
```

print field 1.

---

# 51. Extract Multiple Fields

Run:

```bash
cut -d',' -f1,2 users.csv
```

Output:

```text
alice,engineering
bob,operations
carol,security
david,platform
```

---

# 52. Extract a Range

Example:

```bash
cut -d',' -f2-3 users.csv
```

Output:

```text
engineering,new-york
operations,london
security,mexico-city
platform,toronto
```

---

# 53. `cut` Limitation

Suppose your data is:

```text
alice    engineering
bob          operations
```

with inconsistent whitespace.

Using a single-space delimiter with `cut` can become unreliable because repeated spaces create empty fields.

`awk` handles whitespace-separated data more naturally.

The rule:

> `cut` is excellent when the delimiter is simple and predictable.

---

# 54. Use `cut` on Key-Value Output

Earlier:

```bash
grep -o 'user=[^ ]*' application.log
```

produces:

```text
user=alice
user=bob
...
```

Pipe it to:

```bash
cut -d'=' -f2
```

Full pipeline:

```bash
grep -o 'user=[^ ]*' application.log |
    cut -d'=' -f2
```

Output:

```text
alice
bob
alice
carol
david
alice
bob
carol
david
alice
```

Example:



```text
alice

carol
david
```

# 59. `uniq`

`uniq` removes or reports adjacent repeated lines.

Create:

```bash
cat > services.txt <<'EOF'
api
api
payment
auth
payment
payment
EOF
```

Run:

```bash
uniq services.txt
```

Output:

```text
api
payment
auth
payment
```

Why is `payment` still repeated?

Because the duplicate values were not all adjacent.

---

# 60. Why `sort | uniq` Is Common

First sort:

```bash
sort services.txt
```

Output:

```text
api
api
auth
payment
payment
payment
```

Now:

```bash
sort services.txt | uniq
```

Output:

```text
api
auth
payment
```

Sorting groups identical lines together.

Then `uniq` can collapse adjacent duplicates.

---

# 61. Count Duplicates

Use:

```bash
sort services.txt | uniq -c
```

Output conceptually:

```text
2 api
1 auth
3 payment
```

Now you have frequencies.

---

# 62. Rank Frequencies

Pipe again:

```bash
sort services.txt |
    uniq -c |
    sort -nr
```

Output:

```text
3 payment
2 api
1 auth
```

This pattern is extremely useful:

```text
Extract
  |
  v
Sort
  |
  v
Count duplicates
  |
  v
Sort counts
```

---

# 63. Count Users in the Application Log

Combine what you know:

```bash
grep -o 'user=[^ ]*' application.log |
    cut -d'=' -f2 |
    sort |
    uniq -c |
    sort -nr
```

Expected:

```text
4 alice
2 david
2 carol
2 bob
```

You have transformed raw logs into a frequency report.

```bash
printf '%s\n' alice bob carol > names.txt
```

Run:

```bash
paste names.txt teams.txt
```

Output normally uses a tab:

Output:

This can be useful when assembling simple reports from parallel streams or files.

`paste` can also combine lines serially.

Output:

Here:

```text
-s
```

means serial.


# 67. `tr`

`tr` translates or deletes characters from a stream.

Unlike many commands, traditional `tr` reads standard input rather than taking a normal filename argument.

Example:

```bash
printf 'hello\n' | tr 'a-z' 'A-Z'
```

Output:

```text
HELLO
```

---

# 68. Lowercase Conversion

Example:

```bash
printf 'ERROR\n' | tr 'A-Z' 'a-z'
```

Output:

```text
error
```

This can help normalize simple ASCII text before comparison.

Be aware that character handling and locale can matter for non-ASCII data.

---

# 69. Replace Characters

Example:

```bash
printf 'api:production:healthy\n' |
    tr ':' ','
```

Output:

```text
api,production,healthy
```

Every colon becomes a comma.

---

# 70. Delete Characters

Use:

```bash
printf '123-456-789\n' | tr -d '-'
```

Output:

```text
123456789
```

`-d` means delete matching characters.

---

# 71. Squeeze Repeated Characters

GNU/POSIX-style `tr` supports:

```bash
tr -s
```

to squeeze repeated characters.

Example:

```bash
printf 'api     healthy\n' | tr -s ' '
```

Output:

```text
api healthy
```

This can normalize repeated spaces in simple text.

But do not blindly normalize whitespace in formats where spacing matters.

# 72. `sed`

`sed` means:

```text
stream editor
```

It reads text, applies editing instructions, and writes the result.

A very common use is search and replace.

Example:

```bash
printf 'environment=development\n' |
    sed 's/development/production/'
```

Output:

```text
environment=production
```

---

# 73. Understanding `sed` Substitution

The expression:

```text
s/development/production/
```

means:

```text
s
|
+--> substitute

development
|
+--> search pattern

production
|
+--> replacement
```

The slash separates the parts.

---

# 74. `sed` Does Not Automatically Modify the File

Suppose:

```bash
printf 'environment=development\n' > app.conf
```

Run:

```bash
sed 's/development/production/' app.conf
```

Output:

```text
environment=production
```

But:

```bash
cat app.conf
```

still shows:

```text
environment=development
```

Why?

Because `sed` wrote transformed text to stdout.

It did not modify the original file.

This is a very important safety concept.

---

# 75. Redirect `sed` Output

You could write:

```bash
sed 's/development/production/' app.conf > app.conf.new
```

Now:

```text
app.conf
```

remains untouched.

And:

```text
app.conf.new
```

contains the transformed version.

This is a safe workflow:

```text
Original
   |
   v
Transform
   |
   v
New file
   |
   v
Inspect
   |
   v
Validate
   |
   v
Replace original if appropriate
```

---

# 76. Do Not Redirect Back to the Same File

Dangerous:

```bash
sed 's/development/production/' app.conf > app.conf
```

The shell may truncate `app.conf` before `sed` reads it.

Use a separate output file or intentional in-place editing mechanisms after understanding their behavior.

---

# 77. Global Replacement

By default:

```bash
sed 's/error/warning/'
```

replaces the first match on each line.

For every match on each line:

```bash
sed 's/error/warning/g'
```

The:

```text
g
```

means global within the line.

---

# 78. Case Sensitivity

Suppose:

```text
ERROR error Error
```

A lowercase pattern:

```bash
sed 's/error/failure/g'
```

matches only lowercase `error` unless additional implementation-specific flags or regex strategies are used.

Always know whether case matters.

---

# 79. Different Delimiters

Suppose you want to replace paths:

```text
/opt/app
```

with:

```text
/srv/app
```

This is visually awkward:

```bash
sed 's/\/opt\/app/\/srv\/app/'
```

`sed` allows another delimiter:

```bash
sed 's#/opt/app#/srv/app#'
```

This is easier to read.

The delimiter does not have to be `/`.

---

# 80. Line Addressing

`sed` can operate only on selected lines.

Suppose:

```text
one
two
three
four
five
```

Print line 3:

```bash
sed -n '3p' file.txt
```

Here:

```text
-n
```

suppresses normal automatic printing.

```text
3p
```

means print line 3.

---

# 81. Print a Range of Lines

Use:

```bash
sed -n '2,4p' file.txt
```

This prints lines 2 through 4.

This is useful when you know the approximate line range you need.

---

# 82. Address by Pattern

You can tell `sed` to act on lines matching a pattern.

Example:

```bash
sed -n '/ERROR/p' application.log
```

This prints lines matching `ERROR`.

For simple searches, `grep` is usually clearer.

But pattern addressing becomes useful when combined with editing.

---

# 83. Replace Only Matching Lines

Example:

```bash
sed '/ERROR/s/status=failed/status=investigate/' application.log
```

Interpretation:

```text
For lines matching ERROR
        |
        v
replace status=failed
with status=investigate
```

The original file is still unchanged unless you deliberately perform in-place editing.

---

# 84. Delete Lines from the Output Stream

Example:

```bash
sed '/INFO/d' application.log
```

`d` means delete the matching line from the output stream.

This does not delete lines from the original file unless in-place editing is deliberately requested.

Result:

```text
ERROR...
WARNING...
ERROR...
...
```

---

# 85. In-Place Editing Warning

Many `sed` implementations support:

```bash
sed -i
```

for in-place editing.

But exact `-i` syntax differs between GNU/Linux and BSD/macOS `sed`.

For example, backup-suffix behavior and whether an argument is required can differ.

For beginner automation, a safer portable workflow is often:

```text
Original
   |
   v
sed
   |
   v
Temporary/new file
   |
   v
Validate
   |
   v
Replace intentionally
```

Do not modify important production configuration directly until you have tested the transformation and have a backup.

---

# 86. Safe Configuration Transformation

Example:

```bash
input="app.conf"
output="app.conf.new"

if ! sed 's/environment=development/environment=production/' \
    "$input" > "$output"; then

    printf 'ERROR: transformation failed\n' >&2
    exit 1
fi
```

Then verify:

```bash
grep -F 'environment=production' "$output"
```

Only after validation should you consider replacing the original.

# 87. `awk`

`awk` is a text-processing language.

It is especially powerful for:

* field-based processing
* selecting columns
* filtering records
* calculations
* reports
* conditional processing

A basic pattern is:

```bash
awk '{print $1}' file
```

This prints the first field from every record.

---

# 88. Records and Fields

By default, `awk` treats each input line as a:

```text
record
```

and whitespace-separated pieces within the line as:

```text
fields
```

Suppose:

```text
alice engineering 5
bob operations 3
carol security 8
```

For the first line:

```text
$1 = alice
$2 = engineering
$3 = 5
```

---

# 89. `$0` in `awk`

Inside `awk`:

```text
$0
```

means the complete current record.

Example:

```bash
awk '{print $0}' application.log
```

prints every line.

Important:

This `awk` `$0` is not the same concept as Bash's script `$0`.

Context matters.

---

# 90. Print the First Field

Run:

```bash
awk '{print $1}' application.log
```

Output:

```text
2026-09-02T10:15:01Z
2026-09-02T10:15:04Z
...
```

Because the timestamp is the first whitespace-separated field.

---

# 91. Print Severity

Run:

```bash
awk '{print $2}' application.log
```

Output:

```text
INFO
ERROR
WARNING
ERROR
INFO
ERROR
INFO
WARNING
ERROR
INFO
```

Now:

```bash
awk '{print $2}' application.log |
    sort |
    uniq -c |
    sort -nr
```

produces a severity summary.

Expected:

```text
4 INFO
4 ERROR
2 WARNING
```

---

# 92. Print Multiple Fields

Example:

```bash
awk '{print $1, $2}' application.log
```

Output:

```text
2026-09-02T10:15:01Z INFO
2026-09-02T10:15:04Z ERROR
...
```

By default, `awk` separates printed expressions with its output field separator, usually a space.

---

# 93. Custom Delimiter with `awk`

For CSV:

```bash
awk -F',' '{print $1}' users.csv
```

Here:

```text
-F','
```

means:

> Use comma as the input field separator.

Output:

```text
alice
bob
carol
david
```

---

# 94. `awk` vs `cut`

For:

```text
alice,engineering,new-york
```

both can extract the first field:

```bash
cut -d',' -f1 users.csv
```

or:

```bash
awk -F',' '{print $1}' users.csv
```

Use `cut` when extraction is simple.

Use `awk` when you need logic, calculations, multiple conditions, or more sophisticated formatting.

---

# 95. `NF`

In `awk`:

```text
NF
```

means:

```text
number of fields
```

Example:

```bash
awk '{print NF}' application.log
```

Our log lines should contain a predictable number of whitespace-separated fields.

You can inspect:

```bash
awk '{print NR, NF}' application.log
```

---

# 96. `NR`

In `awk`:

```text
NR
```

means:

```text
current record number
```

For line-oriented input, this often corresponds to the current line number.

Example:

```bash
awk '{print NR, $0}' application.log
```

Output begins:

```text
1 2026-09-02T10:15:01Z INFO ...
2 2026-09-02T10:15:04Z ERROR ...
```

---

# 97. Conditions in `awk`

You can process only records matching a condition.

Example:

```bash
awk '$2 == "ERROR" {print $0}' application.log
```

This means:

```text
If field 2 equals ERROR
        |
        v
print complete record
```

---

# 98. Print Users from Error Records

Our third field is:

```text
user=alice
```

So:

```bash
awk '$2 == "ERROR" {print $3}' application.log
```

produces:

```text
user=bob
user=carol
user=alice
user=david
```

---

# 99. Remove the `user=` Prefix

One way:

```bash
awk '$2 == "ERROR" {print $3}' application.log |
    cut -d'=' -f2
```

Output:

```text
bob
carol
alice
david
```

This is a valid pipeline.

But `awk` can also split data internally.

---

# 100. `split()` in `awk`

Example:

```bash
awk '
$2 == "ERROR" {
    split($3, parts, "=")
    print parts[2]
}
' application.log
```

For:

```text
user=bob
```

`split()` divides the value around:

```text
=
```

Conceptually:

```text
user=bob
   |
 split on =
   |
   +--> parts[1] = user
   +--> parts[2] = bob
```

---

# 101. Conditions with Numeric Values

Suppose we want requests whose duration exceeds 800 ms.

Our final field looks like:

```text
duration_ms=940
```

We need to extract the number.

Example:

```bash
awk '
{
    split($7, duration, "=")

    if (duration[2] > 800) {
        print $0
    }
}
' application.log
```

This prints records with duration above 800.

---

# 102. Why Validate Structure

Our command assumes:

```text
$7
```

contains:

```text
duration_ms=NUMBER
```

What if a malformed line is:

```text
2026-09-02 ERROR unexpected failure
```

Then field 7 does not contain the expected data.

Production log analysis should validate assumptions.

For example:

```bash
awk '
$7 ~ /^duration_ms=[0-9]+$/ {
    split($7, duration, "=")

    if (duration[2] > 800) {
        print $0
    }
}
' application.log
```

Now the script first verifies the expected pattern.

---

# 103. Basic Calculations with `awk`

Suppose we want the total duration.

Run:

```bash
awk '
{
    split($7, duration, "=")

    if (duration[2] ~ /^[0-9]+$/) {
        total += duration[2]
    }
}
END {
    print total
}
' application.log
```

---

# 104. `BEGIN` and `END`

`awk` supports special blocks.

```text
BEGIN
```

runs before input records.

```text
END
```

runs after input processing.

Example:

```bash
awk '
BEGIN {
    print "Starting analysis"
}

{
    count++
}

END {
    print "Records:", count
}
' application.log
```

---

# 105. Calculate Average Duration

Example:

```bash
awk '
{
    split($7, duration, "=")

    if (duration[2] ~ /^[0-9]+$/) {
        total += duration[2]
        count++
    }
}

END {
    if (count > 0) {
        print "Average duration:", total / count, "ms"
    } else {
        print "No valid duration values found"
    }
}
' application.log
```

---

# 106. Why Check `count > 0`?

Without:

```awk
if (count > 0)
```

you could attempt:

```text
total / 0
```

when no valid records exist.

This is the same defensive programming principle used throughout Bash:

```text
Validate assumptions before performing the operation.
```

---

# 107. Find Maximum Duration

Example:

```bash
awk '
{
    split($7, duration, "=")

    if (duration[2] ~ /^[0-9]+$/) {

        value = duration[2] + 0

        if (!found || value > max) {
            max = value
            max_line = $0
            found = 1
        }
    }
}

END {
    if (found) {
        print "Maximum duration:", max, "ms"
        print "Record:", max_line
    }
}
' application.log
```

This demonstrates that `awk` can maintain state while processing records.

---

# 108. Why `+ 0`?

This:

```awk
value = duration[2] + 0
```

makes the numeric intent explicit.

`awk` automatically handles string/number conversions in many situations, but making the expected type clear improves readability.

---

# 109. Count Errors with `awk`

You could write:

```bash
awk '$2 == "ERROR" {count++} END {print count}' application.log
```

Expected:

```text
4
```

Compare with:

```bash
grep -c ' ERROR ' application.log
```

Both can answer the question.

For a simple match count, `grep` is clearer.

For more complex conditions, `awk` becomes more useful.

# 111. Count Requests per Service

# 112. Or Count Directly in `awk`

`awk` can maintain associative counters:

```bash
awk '
{
    split($4, service, "=")
    counts[service[2]]++
}

END {
    for (service in counts) {
        print counts[service], service
    }
}
' application.log
```

Then sort:

```bash
awk '
{
    split($4, service, "=")
    counts[service[2]]++
}

END {
    for (service in counts) {
        print counts[service], service
    }
}
' application.log |
    sort -nr
```

Arrays receive deeper coverage in Bash Part 12, but this is an `awk` array, not a Bash array.

# 113. Choosing Pipelines vs One `awk` Program

You could write:

```bash
awk ... |
sort |
uniq -c |
sort -nr
```

or sometimes perform most processing inside `awk`.

Neither is automatically superior.

Choose based on:

* readability
* maintainability
* performance requirements
* team familiarity
* complexity

For beginner scripts, a clear pipeline can be easier to understand.

For complex record logic, a focused `awk` program may be cleaner.

# 114. Extracting Structured Information

Our logs contain semi-structured fields:

```text

action=login
status=success

```

This is easier to process than arbitrary prose because fields have predictable prefixes.

Suppose we need only failed payment requests.

Use:

```bash
grep -F 'service=payment' application.log |
    grep -F 'status=failed'
```

Output:

```text
2026-09-02T10:15:04Z ERROR user=bob service=payment action=charge status=failed duration_ms=940
2026-09-02T10:15:11Z ERROR user=carol service=payment action=charge status=failed duration_ms=1100
```

Because fields are predictable:

```bash
awk '
$2 == "ERROR" &&
$4 == "service=payment" &&
$6 == "status=failed" {
    print
}
' application.log
```

This is more precise about field positions.

But it depends on the field layout remaining stable.

# 116. Format Assumptions Matter

Suppose developers change the log from:

```text

```

to:

```text

```

A script assuming:

```text

```

may break.

This is an important production lesson:

> Text-processing scripts depend on input contracts.

If the log format is unstable, consider:

* structured logging
* JSON
* dedicated parsers
* centralized observability tools

# 125. Pipeline Exit Status Warning

From Part 5, remember:

```bash
command1 | command2
```

normally reports the status of the final command unless `pipefail` is enabled.

Example:

```bash
grep 'ERROR' missing.log | wc -l
```

`grep` may fail because the file does not exist.

But `wc` may still successfully count zero input.

You could receive:

```text
0
```

and a misleading pipeline status.

---

# 126. Use `pipefail` in Important Scripts

For scripts where pipeline failures matter:

```bash
set -o pipefail
```

Then failures earlier in the pipeline can affect the pipeline status.

A commonly seen stricter Bash setup is:

```bash
set -Eeuo pipefail
```

But each option has behavior and caveats.

Do not copy strict-mode lines blindly without understanding how they affect the script.

Part 14 will examine this deeply.

# 130. Search Multiple Log Files

Search:

```bash
grep -H 'ERROR' logs/*.log
```

Or recursively:

```bash
grep -r 'ERROR' logs/
```

If the directory contains huge archives, recursive search may be expensive.

Scope deliberately.

# 131. Count Errors by File

GNU `grep` can count matches per file:

```bash
grep -c 'ERROR' logs/*.log
```

Possible output:

```text

logs/auth.log:2
logs/payment.log:31
```

This immediately shows where errors are concentrated.

# 132. Excluding Noise

Suppose health checks generate many lines:

```text
INFO healthcheck status=success
```

You could exclude them:

```bash
grep -v 'healthcheck' application.log
```

Then search errors:

```bash
grep -v 'healthcheck' application.log |
    grep 'ERROR'
```

But be careful.

Filtering noise can also hide useful evidence if your pattern is too broad.

# 133. Search Before Transforming

A good troubleshooting sequence is:

```text
Preserve raw source
      |
      v
Search/filter
      |
      v
Inspect result
      |
      v
Transform copy/stream
      |
      v
Summarize
```

Avoid modifying production logs simply to analyze them.

Analysis should normally be read-only.

# 147. Slow Requests Above Threshold

We need to pass a Bash variable into `awk`.

Use:

```bash
awk -v threshold="$slow_threshold" '...'
```

`-v` assigns an `awk` variable before processing.

Add:

```bash
show_slow_requests() {

    printf '\nRequests slower than %s ms:\n' "$slow_threshold"

    awk -v threshold="$slow_threshold" '
    $7 ~ /^duration_ms=[0-9]+$/ {

        split($7, duration, "=")
        value = duration[2] + 0

        if (value > threshold) {
            print $0
        }
    }
    ' "$log_file"
}
```

---

# 148. Why Use `awk -v`?

Do not inject arbitrary shell values directly into an `awk` program like this:

```bash
awk '$7 > '"$value"' { ... }'
```

That becomes difficult to quote correctly and can be unsafe when values are not tightly controlled.

Prefer:

```bash
awk -v threshold="$slow_threshold" '
...
'
```

The shell passes the value as data.

The `awk` program remains separate.

# 151. A Critical Pipeline Reliability Problem

There is an important issue in functions such as:

```bash
awk '...' "$log_file" |
    sort |
    uniq -c |
    sort -nr
```

Without:

```bash
set -o pipefail
```

an early command could fail while the final `sort` succeeds.

The function could appear successful.

For this analyzer, add near the top:

```bash
set -o pipefail
```

So the beginning becomes:

```bash
#!/usr/bin/env bash

set -o pipefail

log_file=""
slow_threshold=800
```

We are intentionally enabling only `pipefail` here rather than introducing all strict-mode options before Part 14 explains their consequences.

---

# 152. Another Reliability Improvement

Even with `pipefail`, a function should propagate pipeline failure.

For example:

```bash
show_errors_by_service() {

    printf '\nErrors by service:\n'

    if ! awk '
    $2 == "ERROR" && $4 ~ /^service=/ {
        split($4, service, "=")

        if (service[2] != "") {
            print service[2]
        }
    }
    ' "$log_file" |
        sort |
        uniq -c |
        sort -nr
    then
        printf 'ERROR: failed to analyze errors by service\n' >&2
        return 1
    fi

    return 0
}
```

Now the function explicitly reports analysis failure.

Apply the same principle to important pipelines.

# 162. Production Logs Are Often Messier

Real logs may contain:

* stack traces spanning multiple lines
* JSON
* quoted values containing spaces
* missing fields
* dynamic field order
* multiline exceptions
* timestamps with spaces
* embedded request IDs
* container prefixes
* ANSI color codes

This means:

```text
awk '{print $4}'
```

is useful only when field position is stable.

Always inspect the data before designing the parser.

---

# 163. Multiline Stack Traces

Consider:

```text
2026-09-02 ERROR application failure
java.lang.RuntimeException: database timeout
    at app.Database.connect(Database.java:42)
    at app.Main.run(Main.java:18)
```

One logical event occupies several physical lines.

A simple:

```bash
grep 'ERROR'
```

finds the first line but not automatically the entire exception.

Context options may help:

```bash
grep -A 5 'ERROR' application.log
```

but this is only an approximation.

For complex multiline logs, dedicated logging systems or parsers are often more appropriate.

---

# 164. Do Not Treat Logs as Trusted Input

Logs may contain:

* user-controlled values
* malicious strings
* terminal escape sequences
* secrets
* tokens
* passwords accidentally logged
* personal information

Do not blindly:

```text
execute values extracted from logs
```

For example, this would be dangerous:

```bash
command=$(awk '{print $5}' untrusted.log)
$command
```

Text extracted from a file should remain data unless deliberately validated for a specific safe use.

---

# 165. Protect Secrets

Suppose a log contains:

```text
Authorization: Bearer SECRET_TOKEN
```

Do not copy the entire log into:

* public bug reports
* Git repositories
* chat messages
* screenshots
* training material

Use filtering or redaction where appropriate.

Example concept:

```bash
sed 's/Bearer [^ ]*/Bearer [REDACTED]/g'
```

But validate redaction rules carefully before assuming sensitive data has been removed.


But scripts should be cautious when parsing human-oriented output.

Many commands provide machine-oriented options.

For example:

```bash
df -P
```

provides a more predictable POSIX-style output format for scripts.

The general principle:

> Prefer stable machine-readable output when available.

# 170. Locale Can Affect Text Processing

Tools such as:

```text
sort
grep
awk
```

may behave differently depending on locale.

Sorting order is a common example.

For predictable byte-oriented sorting in some automation contexts, engineers may use:

```bash
LC_ALL=C sort
```

Do not add locale overrides blindly.

Understand whether language-aware or byte-oriented behavior is required.

# 171. Common Beginner Mistake: Using `cat` Everywhere

Unnecessary:

```bash
cat file | grep ERROR
```

Simpler:

```bash
grep ERROR file
```

Use `cat` when concatenating or when it genuinely improves a stream workflow.

---

# 172. Common Beginner Mistake: Using `grep` for Exact Text Without Considering Regex

If you need a literal string:

```bash
grep -F 'service=payment' application.log
```

is clearer.

Regex is powerful, but unnecessary regex interpretation can create surprising matches.

---

# 173. Common Beginner Mistake: Confusing Shell Globs and Regex

Shell glob:

```text
*.log
```

means:

> filenames ending in `.log`.

Regex:

```text
.*\.log$
```

describes text ending in `.log`.

These are not interchangeable languages.

Ask:

```text
Who interprets this pattern?
```

Possible answers:

```text
Bash
grep
sed
awk
find
```

That question prevents many errors.

---

# 174. Common Beginner Mistake: Forgetting Quotes Around Regex or Patterns

Consider:

```bash
grep *.log file
```

Bash may expand:

```text
*.log
```

as filenames before `grep` sees it.

If the pattern belongs to `grep`, quote it:

```bash
grep '\.log' file
```

Likewise:

```bash
find . -name '*.log'
```

quotes the pattern because `find`, not Bash, should interpret it.

---

# 175. Common Beginner Mistake: Assuming `uniq` Removes All Duplicates

This:

```bash
uniq file
```

only collapses adjacent duplicates.

If identical lines are scattered throughout the file:

```bash
sort file | uniq
```

is often needed.

---

# 176. Common Beginner Mistake: Lexical vs Numeric Sort

This:

```bash
sort numbers.txt
```

sorts text.

This:

```bash
sort -n numbers.txt
```

sorts numerically.

Choose according to the data.

---

# 177. Common Beginner Mistake: Editing the Original Too Early

Avoid beginning with:

```bash
sed -i ...
```

against an important production configuration.

Safer learning workflow:

```text
Read original
   |
   v
Transform to new file
   |
   v
Inspect difference
   |
   v
Validate syntax
   |
   v
Back up original
   |
   v
Replace intentionally
```

# 178. Common Beginner Mistake: Parsing Unstable Field Positions

This:

```bash
awk '{print $7}'
```

assumes field 7 always means the same thing.

If the log format changes, your script may silently produce incorrect results.

Document input assumptions.

Validate them where practical.

# 179. Common Beginner Mistake: Ignoring Pipeline Failures

This:

```bash
grep ERROR missing.log |
    awk '{print $4}' |
    sort
```

may end with a successful `sort`.

Without `pipefail`, the overall status can hide earlier failures.

Important automation should account for this.

# 180. Common Beginner Mistake: Counting Error Text Instead of Error Events

Suppose one log line contains:

```text
ERROR previous_error=ERROR
```

A naive text count may not represent one logical error event.

Know whether you are counting:

```text
matching lines
matching occurrences
structured records
actual incidents
```

These are different measurements.

# 181. Common Beginner Mistake: Searching Huge Trees Without Scope

Avoid casually running:

```bash
grep -r pattern /
```

on production systems.

Start with the most likely directory.

For example:

```bash
grep -r 'connection refused' /var/log/myapp/
```

Scope first.

Expand only when evidence requires it.

# 182. Common Beginner Mistake: Ignoring Stderr

Suppose:

```bash
grep ERROR missing.log > results.txt
```

`results.txt` may be empty.

That does not prove:

```text
There were no errors.
```

`grep` itself may have failed.

Check:

```bash
echo "$?"
```

and inspect stderr.

# 184. Troubleshooting: `cut` Returns Wrong Field

## Problem

You run:

```bash
cut -d' ' -f3 file
```

and receive unexpected output.

## Cause

Repeated spaces may create empty fields.

## Investigate

Inspect:

```bash
cat file
```

or:

```bash
sed -n '1,5p' file
```

If whitespace is variable, consider:

```bash
awk '{print $3}' file
```

because default `awk` field splitting handles runs of whitespace more naturally.

# 185. Troubleshooting: `uniq` Still Shows Duplicates

## Problem

```bash
uniq services.txt
```

still shows the same service multiple times.

## Cause

Duplicates are not adjacent.

## Fix

Try:

```bash
sort services.txt | uniq
```

For counts:

```bash
sort services.txt | uniq -c
```

# 186. Troubleshooting: Numeric Sort Looks Wrong

## Problem

Output:

```text
100
20
3
40
```

## Cause

You performed lexical sorting.

## Fix

```bash
sort -n
```

For largest first:

```bash
sort -nr
```

# 187. Troubleshooting: `sed` Emptied a File

```bash

```

The shell opened and truncated `file` before `sed` could read it.

Safer:

```bash
sed 's/old/new/' file > file.new
```

Then inspect:

```bash

```

This is another example of understanding shell redirection order.

# 191. Security and Text Processing

Text-processing commands are often read-only.

But the surrounding script may not be.

Be especially careful when extracted values are later used as:

* filenames
* commands
* URLs
* usernames
* service names
* SQL fragments
* shell arguments
* deletion targets

Never assume:

```text
It came from a log
```

means:

```text
It is safe.
```

Validate data before using it in sensitive operations.

# 192. Prefer Data Over Code

Suppose a file contains:

```text
service=api
```

Good:

```bash
service=$(awk -F'=' '/^service=/ {print $2}' config.txt)
```

Then validate:

```bash
case "$service" in
    api|auth|payment)
        ;;
    *)
        printf 'ERROR: invalid service\n' >&2
        exit 1
        ;;
esac
```

Do not treat extracted strings as shell code.

Avoid unnecessary:

```bash
eval
```

`eval` can turn untrusted data into commands.

# 193. Production Reasoning: Do You Need a Pipeline?

Before creating:

```text
grep | sed | awk | cut | tr | sort | uniq
```

ask:

```text
Can one tool clearly solve this?

Is the input format stable?

Would a structured parser be safer?

Will another engineer understand this?

Can I test each stage?

What happens on malformed input?

What happens if no matches exist?

What happens if a command fails?
```

The shortest one-liner is not automatically the best production code.

---

# 194. A Readable Pipeline

This:

```bash
grep 'ERROR' application.log | awk '{print $4}' | cut -d= -f2 | sort | uniq -c | sort -nr
```

works.

For a script, this may be easier to review:

```bash
grep 'ERROR' application.log |
    awk '{print $4}' |
    cut -d'=' -f2 |
    sort |
    uniq -c |
    sort -nr
```

Formatting is part of maintainability.

---

# 195. Explain the Pipeline Like an Engineer

Do not memorize:

```bash
grep 'ERROR' application.log |
    awk '{print $4}' |
    cut -d'=' -f2 |
    sort |
    uniq -c |
    sort -nr
```

Understand it:

```text
grep
 |
 +--> keep error records

awk
 |
 +--> select service field

cut
 |
 +--> remove service= prefix

sort
 |
 +--> group identical services

uniq -c
 |
 +--> count adjacent duplicates

sort -nr
 |
 +--> rank highest count first
```

If you can explain every stage, you can troubleshoot it.

# Part 11 Summary

Text processing is one of Bash's strongest capabilities.

Linux frequently gives you:

```text
Logs
Command output
Configuration
Reports
Process information
System information
```

as text.

Your job is often to transform:

```text
Large raw input
```

into:

```text
Useful operational evidence
```

The basic toolkit now includes:

```bash
cat
less
head
tail
wc
cut
paste
tr
sort
uniq
grep
sed
awk
```

Think of them by purpose:

```text
View
 |
 +--> cat
 +--> less
 +--> head
 +--> tail

Count
 |
 +--> wc

Search/filter
 |
 +--> grep

Extract
 |
 +--> cut
 +--> awk

Combine
 |
 +--> paste

Translate characters
 |
 +--> tr

Order
 |
 +--> sort

Count/group duplicates
 |
 +--> uniq

Transform
 |
 +--> sed
 +--> awk

Calculate/report
 |
 +--> awk
```

The power comes from composition:

```text
Raw logs
   |
   v
grep
Filter relevant records
   |
   v
awk / cut
Extract useful fields
   |
   v
sort
Group related values
   |
   v
uniq -c
Count
   |
   v
sort -nr
Rank
   |
   v
Operational insight
```

But do not turn every task into a giant one-liner.

Build pipelines incrementally.

Inspect each stage.

Validate the input format.

Check exit statuses.

Use `pipefail` where pipeline reliability matters.

Do not modify raw production logs merely to analyze them.

Do not treat extracted data as executable code.

Do not use a text parser for a structured format when a proper structured parser is available.

The engineering mindset is:

```text
Observe raw data
      |
      v
Understand its structure
      |
      v
Define the question
      |
      v
Filter only what matters
      |
      v
Extract required fields
      |
      v
Transform carefully
      |
      v
Count/calculate
      |
      v
Verify assumptions
      |
      v
Interpret the result
```

You should now be able to take a realistic application log and answer questions such as:

* How many errors occurred?
* Which services generated them?
* Which users were affected?
* Which actions failed?
* Which requests were slow?
* What was the average duration?
* What was the slowest request?
* What happened around an error?
* Which values occur most frequently?

That is the beginning of practical command-line observability.
