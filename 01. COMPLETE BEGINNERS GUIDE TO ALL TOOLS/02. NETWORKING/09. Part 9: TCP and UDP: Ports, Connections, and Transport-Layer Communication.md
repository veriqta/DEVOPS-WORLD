# Part 9: TCP and UDP: Ports, Connections, and Transport-Layer Communication

## Understand How Applications Actually Communicate

In Part 8, you learned how routing gets an IP packet from one network to another.

You can now answer:

```text
Which network contains the destination?
Which route should the packet use?
Which gateway should receive it?
Which interface should the packet leave through?
```

But reaching the correct computer is only part of the problem.

A server may simultaneously run:

```text
SSH
Web server
Database
DNS
Monitoring agent
Application API
```

If a packet reaches that server, how does the operating system know which application should receive it?

That is where the transport layer, TCP, UDP, and ports become important.

A useful mental model is:

```text
IP address
    |
    | Finds the computer
    v
192.168.10.50
    |
    | Port finds the service
    v
Port 443
    |
    v
HTTPS application
```

By the end of Part 9, you should understand how applications communicate using TCP and UDP, how ports identify services, how TCP establishes and closes connections, how reliability works, how to inspect connections on Linux, and how to diagnose common transport-layer failures.

---

# 1. The Transport Layer

In the OSI model, the transport layer is:

```text
Layer 4
```

Recall the relevant portion of the stack:

```text
Layer 7    Application
Layer 6    Presentation
Layer 5    Session
Layer 4    Transport
Layer 3    Network
Layer 2    Data Link
Layer 1    Physical
```

Layer 3 gives us IP addressing and routing.

Layer 4 provides communication between applications running on hosts.

Two major Layer 4 protocols are:

```text
TCP
UDP
```

---

# 2. Why Do We Need a Transport Layer?

Imagine a server with IP:

```text
10.20.30.40
```

It runs:

```text
SSH
Nginx
PostgreSQL
DNS
```

IP routing can deliver packets to:

```text
10.20.30.40
```

But then we have another question:

```text
Which application should receive the data?
```

The answer involves:

```text
Ports
```

For example:

```text
10.20.30.40:22
```

might represent SSH.

```text
10.20.30.40:443
```

might represent HTTPS.

```text
10.20.30.40:5432
```

might represent PostgreSQL.

The IP address identifies the host.

The port helps identify the application endpoint on that host.

---

# 3. Layer 3 vs Layer 4

Keep this distinction clear:

```text
Layer 3
IP addressing and routing

        ↓

Find the destination host
```

Layer 4:

```text
TCP / UDP and ports

        ↓

Deliver communication to the
appropriate application endpoint
```

Simplified:

```text
IP address
    |
    v
Correct machine
    |
    v
Port
    |
    v
Correct application
```

# 4. What Is TCP?

TCP stands for:

```text
Transmission Control Protocol
```

TCP is a connection-oriented transport protocol.

Before normal application data is exchanged, TCP establishes a logical connection between two endpoints.

TCP provides features including:

* Reliable delivery
* Ordered delivery
* Sequence tracking
* Acknowledgments
* Retransmission
* Flow control
* Congestion control
* Connection establishment
* Connection termination

TCP is used when an application benefits from reliable, ordered byte-stream communication.

---

# 5. What Does "Connection-Oriented" Mean?

Suppose a client wants to communicate with a web server.

TCP does not simply begin sending application data without first establishing TCP state between the endpoints.

Conceptually:

```text
Client                      Server

   |                           |
   | ---- Establish TCP ---->  |
   | <--- Establish TCP -----  |
   |                           |
   | ===== Connection ======   |
   |                           |
   | ---- Application data --> |
   | <--- Application data --- |
```

Both systems maintain information about the TCP connection.

This is why TCP is described as connection-oriented.

---

# 6. What Is UDP?

UDP stands for:

```text
User Datagram Protocol
```

UDP is a connectionless transport protocol.

UDP does not establish a TCP-style connection before sending application datagrams.

Conceptually:

```text
Sender                     Receiver

   |                          |
   | ----- Datagram 1 ------> |
   | ----- Datagram 2 ------> |
   | ----- Datagram 3 ------> |
   |                          |
```

At the UDP transport layer itself, there is no three-way handshake and no TCP-style acknowledgment and retransmission mechanism.

---

# 7. Connectionless Does Not Mean "No Communication"

This distinction matters.

Connectionless does not mean:

```text
The systems are not communicating.
```

It means UDP itself does not create and maintain the kind of connection state TCP does.

An application can still implement:

* Responses
* Retries
* Reliability
* Ordering
* Session logic

above UDP if needed.

The transport protocol itself simply does not provide TCP's mechanisms.

---

# 8. TCP vs UDP

At a beginner level:

| Feature                      | TCP                 | UDP                                      |
| ---------------------------- | ------------------- | ---------------------------------------- |
| Connection-oriented          | Yes                 | No                                       |
| Three-way handshake          | Yes                 | No                                       |
| Reliable delivery mechanism  | Yes                 | No                                       |
| Ordered byte stream          | Yes                 | No                                       |
| Retransmission               | Yes                 | No                                       |
| Flow control                 | Yes                 | No                                       |
| Congestion control           | Yes                 | Not TCP-style transport control          |
| Header overhead              | Higher              | Lower                                    |
| Preserves message boundaries | No, byte stream     | Yes, datagrams                           |
| Common uses                  | Web, SSH, databases | DNS, voice/video, some real-time traffic |

Do not reduce this to:

```text
TCP = slow
UDP = fast
```

That is too simplistic.

The important distinction is the communication behavior and guarantees each protocol provides.

# 9. Why Would an Application Choose TCP?

Imagine transferring a file.

Suppose the file becomes:

```text
Chunk 1
Chunk 2
Chunk 3
Chunk 4
Chunk 5
```

If Chunk 3 disappears in transit, you generally do not want the final file to silently contain:

```text
1
2
4
5
```

Reliable delivery matters.

TCP provides mechanisms for detecting missing data and retransmitting it.

Applications commonly choose TCP when correctness and ordered delivery matter.

---

# 10. Why Would an Application Choose UDP?

Imagine a real-time voice application.

Packets represent tiny pieces of audio.

Suppose one old audio packet disappears.

By the time it could be retransmitted, the conversation may already have moved forward.

For some real-time applications, receiving newer data on time can be more useful than waiting for an old missing piece.

UDP gives applications more control over how they handle these situations.

This does not mean every real-time application simply uses basic UDP directly. Modern application protocols can build sophisticated behavior on top of UDP.

---

# 11. QUIC Is an Important Modern Example

Modern networking gives us a useful reminder that:

```text
UDP does not mean primitive.
```

QUIC operates over UDP and implements sophisticated functionality above it, including reliable streams and congestion control.

HTTP/3 uses QUIC.

So when you learn:

```text
TCP = reliable
UDP = unreliable
```

understand that this describes the transport mechanisms provided directly by TCP and UDP.

Applications and higher-level protocols can build additional guarantees over UDP.

---

# 12. What Is a Port?

A port is a 16-bit number used by TCP or UDP to identify transport-layer endpoints associated with applications.

Port numbers range from:

```text
0
to
65535
```

Why?

Because:

```text
2^16 = 65,536
```

possible values exist.

The values are numbered:

```text
0 through 65535
```

---

# 13. IP Address Plus Port

An IP address tells us:

```text
Which host?
```

A port tells us:

```text
Which application endpoint?
```

For example:

```text
192.168.10.50:443
```

can be read as:

```text
Host:
192.168.10.50

Port:
443
```

The combination is fundamental to transport-layer communication.

---

# 14. One Server Can Run Many Services

Suppose:

```text
Server IP:
10.0.0.50
```

It might have:

```text
10.0.0.50:22
SSH

10.0.0.50:80
HTTP

10.0.0.50:443
HTTPS

10.0.0.50:5432
PostgreSQL
```

The IP address remains the same.

The ports distinguish different transport endpoints.

---

# 15. TCP and UDP Have Separate Port Spaces

This is easy for beginners to miss.

TCP port:

```text
53
```

and UDP port:

```text
53
```

are separate transport endpoints.

A service can therefore use the same numeric port with both TCP and UDP.

DNS is a classic example because DNS commonly uses both:

```text
UDP 53
TCP 53
```

depending on the operation and circumstances.

---

# 16. Source Ports and Destination Ports

Every TCP or UDP communication involves both:

```text
Source port
Destination port
```

Suppose your laptop connects to a web server.

```text
Laptop
192.168.1.50

Server
203.0.113.20
```

The connection might look conceptually like:

```text
192.168.1.50:53124
        |
        v
203.0.113.20:443
```

Here:

```text
Source port:
53124

Destination port:
443
```

---

# 17. Why Does the Client Need a Source Port?

Imagine opening several browser connections simultaneously.

The server needs a way to send traffic back to the correct transport endpoint.

The communication therefore contains both source and destination information.

For example:

```text
Client A

192.168.1.50:53124
        |
        v
203.0.113.20:443
```

Another connection might be:

```text
192.168.1.50:53125
        |
        v
203.0.113.20:443
```

Same client IP.

Same server IP.

Same server port.

Different client source ports.

---

# 18. Ephemeral Ports

Clients commonly use temporary source ports called:

```text
Ephemeral ports
```

The operating system selects them from a configured range.

For example:

```text
Client:
192.168.1.50:52742

Server:
203.0.113.20:443
```

`52742` may be an ephemeral source port.

The exact ephemeral range depends on the operating system and configuration.

Do not assume every operating system uses exactly the same range.

---

# 19. Checking the Linux Ephemeral Port Range

On Linux:

```bash
cat /proc/sys/net/ipv4/ip_local_port_range
```

You may see something such as:

```text
32768    60999
```

This means the kernel is configured to select local ephemeral ports from that range for relevant outbound connections.

Your system may show a different range.

---

# 20. Port Number Categories

IANA groups service port numbers into broad ranges.

### System or well-known ports

```text
0-1023
```

### User or registered ports

```text
1024-49151
```

### Dynamic or private ports

```text
49152-65535
```

These categories help organize port assignments.

Do not assume that every client operating system's ephemeral port configuration exactly matches the IANA dynamic/private range.

---

# 21. Common Ports Beginners Should Recognize

| Service    | Common Port | Transport                                |
| ---------- | ----------: | ---------------------------------------- |
| SSH        |          22 | TCP                                      |
| DNS        |          53 | UDP and TCP                              |
| HTTP       |          80 | TCP                                      |
| HTTPS      |         443 | TCP, while HTTP/3 uses QUIC over UDP 443 |
| SMTP       |          25 | TCP                                      |
| POP3       |         110 | TCP                                      |
| IMAP       |         143 | TCP                                      |
| NTP        |         123 | UDP                                      |
| PostgreSQL |        5432 | TCP                                      |
| MySQL      |        3306 | TCP                                      |

These are defaults or common assignments.

An administrator can often configure a service to listen on a different port.

Therefore:

```text
Port 22 usually suggests SSH.
```

does not mean:

```text
Anything on port 22 must be SSH.
```

# 22. What Is a Socket?

The word socket can mean slightly different things depending on context.

For beginner networking, think of a network socket as an operating-system communication endpoint used by an application.

An application asks the operating system to create and manage sockets for network communication.

For example, a web server may create a TCP socket, bind it to:

```text
0.0.0.0:443
```

and listen for incoming TCP connections.

---

# 23. What Does `0.0.0.0:443` Mean?

Suppose:

```bash
ss -lnt
```

shows:

```text
0.0.0.0:443
```

For an IPv4 listening socket, this generally means the service is listening on port `443` across all local IPv4 addresses rather than one specific IPv4 address.

Suppose the server has:

```text
10.0.0.10
192.168.1.10
```

A service bound appropriately to:

```text
0.0.0.0:443
```

can accept connections addressed to its local IPv4 interfaces, subject to routing, firewall, and other system policies.

---

# 24. Binding to a Specific Address

Suppose instead the service listens on:

```text
127.0.0.1:8080
```

`127.0.0.1` is loopback.

The service is available locally through that loopback binding, not automatically through the machine's external interface addresses.

This creates a classic troubleshooting situation.

The application is running.

The port is listening.

But remote users cannot connect.

Why?

Because it is listening only on:

```text
127.0.0.1
```

---

# 25. Example Binding Problem

Server:

```text
External IP:
10.0.0.50

Application:
127.0.0.1:8080
```

Local test:

```bash
curl http://127.0.0.1:8080
```

works.

Remote test:

```text
Client -> 10.0.0.50:8080
```

fails.

Do not immediately blame:

```text
Firewall
Routing
Cloud security group
```

First inspect what address the application is actually listening on.

# 26. TCP Connections

A TCP connection is identified by transport and endpoint information.

Conceptually, a TCP flow can be represented using:

```text
Protocol
Source IP
Source port
Destination IP
Destination port
```

For example:

```text
TCP

192.168.1.50:52742
        ->
203.0.113.20:443
```

The reverse traffic belongs to the same connection:

```text
203.0.113.20:443
        ->
192.168.1.50:52742
```

---

# 27. Why Ports Let Servers Handle Many Clients

Imagine a web server:

```text
10.0.0.50:443
```

Three clients connect:

```text
Client A
192.168.1.10:51001
       |
       +--------+
                |
Client B        |
192.168.1.11:51002
       |        |
       +--------+----> 10.0.0.50:443
                |
Client C        |
192.168.1.12:51003
       |        |
       +--------+
```

The server can distinguish the connections because their endpoint combinations differ.

# 28. TCP Three-Way Handshake

Before normal application data exchange, TCP establishes a connection.

The famous sequence is:

```text
SYN
SYN-ACK
ACK
```

Diagram:

```text
Client                           Server

  |                                |
  | -------- SYN ----------------> |
  |                                |
  | <------ SYN-ACK -------------- |
  |                                |
  | -------- ACK ----------------> |
  |                                |
  |       CONNECTION READY         |
  |                                |
```

This is the TCP three-way handshake.

---

# 29. Step 1: SYN

The client sends a TCP segment with the:

```text
SYN
```

flag set.

SYN means:

```text
Synchronize
```

Among other things, this begins synchronization of TCP sequence-number state.

Conceptually:

```text
Client:

I want to establish a TCP connection.
Here is my initial sequence information.
```

---

# 30. Step 2: SYN-ACK

If the server accepts the connection attempt at the TCP layer, it responds with:

```text
SYN + ACK
```

Conceptually:

```text
Server:

I received your SYN.
I acknowledge it.
Here is my own initial sequence information.
```

---

# 31. Step 3: ACK

The client responds:

```text
ACK
```

Conceptually:

```text
Client:

I received your synchronization information too.
```

The connection can then enter an established state.

```text
Client                           Server

SYN -------------------------->

    <-------------------- SYN-ACK

ACK -------------------------->

========= ESTABLISHED =========
```

---

# 32. Why Three Steps?

Both sides need to establish and acknowledge the relevant TCP state.

The client needs to know the server received its synchronization request.

The server needs to know the client received the server's response.

The handshake establishes the state required for reliable TCP communication.

---

# 33. TCP Flags

TCP uses control flags to communicate connection state and actions.

Important flags for beginners include:

```text
SYN
ACK
FIN
RST
```

You may later encounter others, including:

```text
PSH
URG
ECE
CWR
```

For now, concentrate on the first four.

---

# 34. Sequence Numbers

TCP provides ordered delivery using sequence numbers.

TCP is fundamentally a byte-stream protocol.

Imagine the application sends bytes:

```text
ABCDEFGHIJ
```

TCP needs a way to track where transmitted data belongs in the byte stream.

Sequence numbers provide that tracking.

A simplified example:

```text
Bytes 1-5:
ABCDE

Bytes 6-10:
FGHIJ
```

Real TCP sequence numbers are 32-bit values and do not simply begin at 1 like this example.

The simplified numbering is only for learning the concept.

---

# 35. Why Sequence Numbers Matter

Networks do not guarantee that every IP packet will:

* Arrive
* Arrive once
* Arrive in order
* Arrive quickly

TCP must handle these realities.

Suppose data associated with an earlier part of the stream is delayed while later data arrives first.

TCP's sequence information helps the receiver identify where bytes belong.

---

# 36. Acknowledgments

TCP receivers acknowledge received data.

Suppose, in a simplified example, the sender transmits bytes:

```text
1 through 100
```

The receiver may acknowledge:

```text
ACK 101
```

Conceptually:

```text
I have received the byte stream through 100.
The next byte I expect is 101.
```

TCP acknowledgment numbers are therefore closely related to sequence numbers.

---

# 37. Reliable Delivery

TCP reliability is not magic.

It is created through mechanisms including:

```text
Sequence numbers
+
Acknowledgments
+
Timers
+
Retransmission
+
Error detection
```

Suppose data is sent:

```text
Sender

Segment A
Segment B
Segment C
```

and part of the expected data is lost.

TCP can detect missing progress and retransmit as appropriate.

---

# 38. Retransmission

Simplified example:

```text
Sender                       Receiver

Data A -------------------->

      <---------------- ACK

Data B -------- X

Data C -------------------->

       Missing data detected

Data B -------------------->

      <---------------- ACK
```

Actual TCP retransmission behavior is more sophisticated than this diagram.

Retransmissions can be triggered by mechanisms involving retransmission timers and acknowledgment patterns.

The beginner concept is:

```text
TCP notices that expected data
has not been successfully acknowledged
and can send it again.
```

---

# 39. Packet Loss and TCP

Suppose a network has significant packet loss.

TCP may repeatedly retransmit.

From the application perspective, you may see:

```text
Slow downloads
Slow API calls
Connections that appear to freeze
Poor throughput
Timeouts
```

The application itself may be healthy.

The underlying network may be losing packets.

This is why transport-layer troubleshooting matters.

---

# 40. Ordered Delivery

Suppose transmitted data logically represents:

```text
A
B
C
```

but network behavior causes arrival like:

```text
A
C
B
```

TCP uses sequence information to reconstruct the ordered byte stream for the receiving application.

The application does not need to manually reorder individual IP packets.

---

# 41. TCP Is a Byte Stream

This deserves special attention.

TCP does not preserve application message boundaries.

Suppose an application writes:

```text
HELLO
```

and then:

```text
WORLD
```

You cannot assume the receiving application will necessarily perform two reads that correspond exactly to:

```text
HELLO
WORLD
```

TCP provides an ordered stream of bytes.

Applications must define their own message framing where needed.

UDP behaves differently because it preserves datagram boundaries.

---

# 42. Flow Control

TCP flow control helps prevent a fast sender from overwhelming a receiver.

Imagine:

```text
Powerful Server
      |
      | sends extremely fast
      v
Small Receiver
```

The receiver has finite buffer capacity.

TCP allows the receiver to advertise how much data it can currently accept.

This is associated with the:

```text
Receive window
```

---

# 43. Flow Control Mental Model

Think:

```text
Receiver:

"I currently have room for this
much more data."
```

The sender adjusts how much unacknowledged data it can have in flight based partly on the receiver's advertised window.

The goal is to protect:

```text
Receiver capacity
```

---

# 44. Flow Control vs Congestion Control

These are related but different.

Flow control asks:

```text
Can the receiver keep up?
```

Congestion control asks:

```text
Can the network path handle the traffic?
```

Keep this distinction.

```text
Flow control
      |
      v
Protect receiver

Congestion control
      |
      v
Respond to network capacity/congestion
```

---

# 45. Congestion Control Introduction

Imagine thousands of systems sending traffic through a limited network path.

```text
Host A ----\
Host B -----\
Host C ------> Network Link ---> Destination
Host D -----/
Host E ----/
```

If senders transmit too aggressively, network devices may become congested and packets may be dropped or delayed.

TCP contains congestion-control mechanisms that adjust sending behavior based on network conditions.

---

# 46. Congestion Window

You may encounter:

```text
cwnd
```

which means:

```text
Congestion window
```

It is part of TCP's mechanism for controlling how much data can be in flight based on perceived network conditions.

You do not need to master congestion-control algorithms yet.

For now remember:

```text
Receive window
-> receiver capacity

Congestion window
-> network conditions
```

Both can influence effective TCP throughput.

---

# 47. TCP Connection Termination

Connections eventually need to close.

A normal TCP close commonly involves:

```text
FIN
ACK
```

exchange.

Unlike connection establishment, connection termination can involve each direction being closed independently.

A simplified graceful close:

```text
Client                           Server

FIN -------------------------->

    <----------------------- ACK

    <----------------------- FIN

ACK -------------------------->

Connection closed
```

---

# 48. What Does FIN Mean?

FIN means the sender has finished sending data in that direction.

Conceptually:

```text
I have no more data to send.
```

TCP is full-duplex.

Therefore, one direction can be closed while the other side may still have data to send.

This is why connection termination is not simply one "disconnect" packet.

---

# 49. FIN and ACK

Suppose the client initiates closure.

```text
Client -> Server
FIN
```

The server acknowledges:

```text
Server -> Client
ACK
```

Later, when the server is ready to close its sending direction:

```text
Server -> Client
FIN
```

The client acknowledges:

```text
Client -> Server
ACK
```

That represents a graceful TCP shutdown in simplified form.

---

# 50. What Is RST?

RST means:

```text
Reset
```

A TCP reset abruptly terminates or rejects a TCP connection or connection attempt.

Conceptually:

```text
Stop this connection immediately.
```

RST differs from the normal graceful FIN-based shutdown.

---

# 51. Common RST Scenario

Suppose a client sends a TCP SYN to:

```text
10.0.0.50:8080
```

The host is reachable, but nothing is listening on TCP port `8080`.

The operating system may respond with:

```text
RST
```

The client can then quickly report:

```text
Connection refused
```

This gives us an important troubleshooting clue.

---

# 52. Connection Refused

Suppose:

```bash
ssh 10.0.0.50
```

returns:

```text
Connection refused
```

A beginner might say:

```text
The network is down.
```

But refusal often tells you something more useful.

You probably reached a host or device capable of actively rejecting that TCP connection.

Common causes include:

* Service is stopped
* Nothing is listening on the requested port
* Service listens on another port
* Service listens only on another address
* Firewall actively rejects the connection

This differs from silent packet loss.

---

# 53. Timeout

Now suppose:

```bash
ssh 10.0.0.50
```

waits for a long time and eventually reports a timeout.

Possible causes include:

* Firewall silently dropping packets
* Security group dropping traffic
* Broken route
* Missing return route
* Host unavailable
* Network ACL
* Wrong IP
* Packet loss
* Intermediate network failure

A timeout provides different evidence from an immediate refusal.

---

# 54. Refused vs Timeout

A useful beginner model:

```text
CONNECTION REFUSED

Client ---- SYN ----> Host
Client <--- RST ----- Host

Something actively rejected the attempt.
```

Versus:

```text
TIMEOUT

Client ---- SYN ----> ?

Client waits...

No useful response arrives.
```

Do not treat this as an absolute diagnostic rule because network devices can alter behavior.

But it is a very useful starting point.

---

# 55. TCP States

Because TCP is connection-oriented, the operating system tracks connection state.

Important states include:

```text
LISTEN
SYN-SENT
SYN-RECEIVED
ESTABLISHED
FIN-WAIT-1
FIN-WAIT-2
CLOSE-WAIT
LAST-ACK
TIME-WAIT
CLOSED
```

You do not need to memorize the full TCP state machine immediately.

Start with:

```text
LISTEN
ESTABLISHED
TIME-WAIT
CLOSE-WAIT
```

---

# 56. LISTEN

`LISTEN` means a TCP socket is waiting for incoming connection attempts.

For example:

```text
0.0.0.0:22
LISTEN
```

means a process is listening for TCP connections on port 22 on the relevant IPv4 wildcard binding.

Conceptually:

```text
Server

Port 22
   |
   v
LISTEN

"Waiting for clients."
```

---

# 57. ESTABLISHED

`ESTABLISHED` means the TCP connection has completed connection establishment and is available for normal data exchange.

Example:

```text
192.168.1.50:52742
        ->
203.0.113.20:443

ESTABLISHED
```

Both endpoints maintain connection state.

---

# 58. TIME_WAIT

`TIME_WAIT` is a normal TCP state associated with the endpoint that performs the active close in typical cases.

It exists for important protocol reasons, including allowing delayed segments from an old connection to expire and allowing retransmission of the final acknowledgment if necessary.

A beginner may run:

```bash
ss -tan
```

and see many:

```text
TIME-WAIT
```

entries.

Do not immediately assume something is broken.

TIME_WAIT is part of normal TCP behavior.

---

# 59. Why TIME_WAIT Can Become Operationally Important

Although TIME_WAIT is normal, extremely high connection churn can make it operationally relevant.

For example:

```text
Application
   |
   | Creates thousands of
   | short-lived connections
   v
Remote Service
```

You may need to investigate:

* Connection reuse
* Application connection pooling
* Ephemeral port availability
* Load balancer behavior
* Client architecture

Do not start changing kernel TCP parameters simply because you see TIME_WAIT.

First understand why so many connections are being created.

---

# 60. CLOSE_WAIT

`CLOSE_WAIT` is particularly useful for application troubleshooting.

It generally means:

```text
The remote side sent FIN.

The local TCP stack acknowledged it.

The local application has not yet fully closed its side.
```

Conceptually:

```text
Remote:
"I'm finished."

        |
        v

Local kernel:
"Received."

        |
        v

Local application:
has not closed socket yet
```

---

# 61. Too Many CLOSE_WAIT Connections

Suppose:

```bash
ss -tan
```

shows thousands of:

```text
CLOSE-WAIT
```

connections associated with an application.

This can indicate an application-side problem where sockets are not being closed correctly after the peer closes its side.

Potential consequences include:

* File descriptor exhaustion
* Resource consumption
* Application degradation

This is different from seeing many normal TIME_WAIT sockets.

---

# 62. TCP State Progression

A simplified client-side view:

```text
CLOSED
   |
   | Send SYN
   v
SYN-SENT
   |
   | Receive SYN-ACK
   | Send ACK
   v
ESTABLISHED
   |
   | Begin close
   v
FIN-WAIT...
   |
   v
TIME-WAIT
   |
   v
CLOSED
```

A simplified server view:

```text
LISTEN
   |
   | Receive SYN
   v
SYN-RECEIVED
   |
   | Handshake completes
   v
ESTABLISHED
```

The complete TCP state machine contains more transitions than these simplified diagrams.

---

# 63. SYN-SENT

If a client has sent:

```text
SYN
```

but has not completed the handshake, it may be in:

```text
SYN-SENT
```

If many connections remain in SYN-SENT, investigate:

* Destination reachability
* Firewalls
* Security groups
* Return routing
* Server availability
* Port correctness

The client is trying to establish connections but is not receiving the expected handshake response.

---

# 64. SYN-RECEIVED

A server that has received a SYN and sent SYN-ACK while waiting for the final ACK can be in:

```text
SYN-RECEIVED
```

Simplified:

```text
Client                  Server

SYN ------------------->

    <------------- SYN-ACK
                      ^
                      |
               SYN-RECEIVED

ACK ------------------->
```

After successful completion, the connection moves to:

```text
ESTABLISHED
```

---

# 65. UDP Communication

UDP works differently.

There is no TCP three-way handshake.

A sender can send a UDP datagram toward:

```text
Destination IP
+
Destination UDP port
```

Conceptually:

```text
Client

10.0.0.10:53000
      |
      | UDP datagram
      v
10.0.0.53:53

DNS Server
```

The server may send a UDP response back.

---

# 66. UDP Does Not Guarantee Delivery

At the UDP layer, the sender does not receive TCP-style acknowledgment that every datagram arrived.

Suppose:

```text
Datagram 1 -> received
Datagram 2 -> lost
Datagram 3 -> received
```

UDP itself does not retransmit Datagram 2.

If retransmission is needed, the application or a higher-level protocol must provide the required behavior.

---

# 67. UDP Does Not Guarantee Ordering

Suppose:

```text
1
2
3
```

are transmitted.

The network might deliver:

```text
1
3
2
```

UDP itself does not reorder the datagrams into:

```text
1
2
3
```

for the application.

Again, applications can implement additional behavior if needed.

---

# 68. UDP Preserves Datagram Boundaries

This is an important difference from TCP.

Suppose an application sends two UDP datagrams:

```text
Datagram A:
HELLO

Datagram B:
WORLD
```

UDP maintains those as separate datagrams.

TCP instead presents applications with a byte stream.

This difference affects application protocol design.

---

# 69. Common UDP Uses

UDP is useful when applications value properties such as:

* Low protocol overhead
* No TCP connection setup
* Message-oriented datagrams
* Application-controlled reliability
* Multicast capability
* Real-time behavior

Common examples include:

```text
DNS queries
NTP
DHCP
Some voice/video traffic
Some gaming traffic
QUIC
```

Again, individual applications and protocols can behave differently.

---

# 70. DNS and UDP

A typical DNS query might look conceptually like:

```text
Client
192.168.1.50:54021
        |
        | UDP
        v
DNS Server
192.168.1.1:53
```

The DNS server responds:

```text
192.168.1.1:53
        |
        v
192.168.1.50:54021
```

But DNS is not "UDP only."

DNS also uses TCP in various situations.

This is why memorizing:

```text

```

is incomplete.

Better:

```text
DNS commonly uses both UDP and TCP port 53.
```

# 86. TCP Success Does Not Mean Application Success

Suppose:

```bash

```

```text

```

```text

Can route there?
Yes.

Layer 4:
Can establish TCP?
Yes.

TLS:
Can negotiate?
Maybe.

HTTP:
Does application respond correctly?

```

This layered reasoning prevents random troubleshooting.

Application is running.

# 92. Security Warning About `0.0.0.0`

Beginners sometimes think:

```text
0.0.0.0 = better because everything works.
```

That is dangerous reasoning.

Binding a service to:

```text

```

can make it listen on all local IPv4 interfaces.

Whether it becomes externally reachable also depends on routing and firewall controls, but the listening scope is broader.

For databases, administrative interfaces, development servers, and internal tools, unnecessary exposure can create serious security risks.

Use the narrowest appropriate binding.

# 98. TCP Handshake Failure Analysis

Suppose the client sends:

```text
SYN
```

but receives nothing.

```text
Client                    Server

SYN --------------------> ?

No SYN-ACK
No RST
```

Possible causes:

* Packet never reached server
* Firewall dropped SYN
* Server unavailable
* Return traffic cannot reach client
* Intermediate network dropped traffic

Now suppose:

```text
Client                    Server

SYN -------------------->

    <------------------- RST
```

That strongly suggests active rejection rather than silent loss.

---

# 99. What If SYN-ACK Returns but Final ACK Fails?

Consider:

```text
Client                    Server

SYN -------------------->

    <--------------- SYN-ACK

ACK -------- X
```

The server may remain waiting for completion until its TCP behavior times out or retries.

Possible causes include:

* Asymmetric routing
* Firewall policy
* Packet loss
* Broken return/forward path
* Stateful filtering problems

This is why packet flow must sometimes be examined in both directions.

```text
     |

     |

```

# 101. Source Port Troubleshooting

Source ports can also become operationally important.

Suppose a system creates huge numbers of outbound short-lived connections.

Each connection may consume an ephemeral source port for some period.

At sufficient scale, the system can experience:

```text
Ephemeral port exhaustion
```

Then new outbound connections may fail even though the destination server is healthy.

---

# 102. Ephemeral Port Exhaustion

Imagine:

```text
Application Server
      |
      | thousands of short-lived
      | outbound connections
      v
Database / API / Proxy
```

Possible contributors:

* No connection pooling
* Extremely high connection churn
* Many sockets in relevant states
* Limited available source-port space
* NAT/proxy constraints

Do not solve this by blindly expanding port ranges.

First understand why the application is creating so many connections.

# 104. Firewall Direction Matters

Suppose an application connects to a database.

The initial TCP SYN is:

```text
Source:
10.0.10.20:49182

Destination:
10.0.20.50:5432
```

A security rule generally needs to allow the intended communication appropriately.

Do not make the beginner mistake of thinking both endpoints communicate using destination port 5432 in both directions.

The response is:

```text

10.0.20.50:5432

Destination:
10.0.10.20:49182
```

Stateful firewalls can automatically recognize return traffic for an established connection.

Stateless filtering requires more explicit reasoning.

Do not expose random development servers publicly just to experiment.

* Prefer VMs
* Prefer private lab networks

* Do not disable firewalls without understanding why
* Do not expose databases directly to the Internet

# 122. Common Beginner Mistakes

### Mistake 1: Thinking IP address and port are the same thing

They solve different problems.

```text
IP -> host/network endpoint
Port -> transport/application endpoint
```

### Mistake 2: Assuming TCP and UDP port 53 are identical

TCP and UDP have separate port spaces.

### Mistake 3: Thinking clients normally use the server port as their source port

Clients commonly use ephemeral source ports.

### Mistake 4: Thinking UDP means "bad"

UDP is intentionally designed for different requirements.

### Mistake 5: Thinking TCP guarantees that the application succeeds

TCP can deliver data successfully while the application returns an error.

### Mistake 6: Thinking LISTEN means everyone can reach the service

Routing, binding, firewalls, and network policy still matter.

### Mistake 7: Thinking TIME_WAIT always means a problem

It is a normal TCP state.

### Mistake 8: Ignoring large numbers of CLOSE_WAIT sockets

Persistent CLOSE_WAIT accumulation can indicate application socket-management problems.

### Mistake 9: Treating refusal and timeout as identical

They provide different clues.

### Mistake 10: Restarting applications before gathering evidence

Inspect the socket and connection state first.

The most important troubleshooting lesson from Part 9 is this:

```text
"Cannot connect"
is not a diagnosis.
```

```text
Route works?
        |
        v

        |
        v

        |
        v
Socket listening?
        |
        v

        |
        v
Connection established?
        |
        v
Application protocol works?
```

Once you learn to separate these stages, errors such as `connection refused`, `timeout`, `CLOSE_WAIT`, a missing listener, a wrong binding address, or a failed TCP handshake stop looking like vague networking problems. They become evidence that tells you where to investigate next.
