# Part 2: IAM Fundamentals, Users, Groups, Roles, and Policies

AWS Identity and Access Management, usually called IAM, controls who can access AWS and what they are allowed to do.

This is one of the most important AWS topics you will learn.

You can build a perfectly designed VPC, configure EC2 correctly, deploy a working application, and still create a serious security problem if IAM is misconfigured.

Many AWS security incidents are not caused by AWS infrastructure failing.

They happen because permissions are too broad, credentials are exposed, or identities are poorly managed.

IAM answers questions such as:

Who is trying to access AWS?

How are they proving who they are?

What are they allowed to do?

Which resources can they access?

Under what conditions are they allowed to perform the action?

A useful mental model is:

```text
Identity
   |
   v
Authentication
   |
   v
Who are you?
   |
   v
Authorization
   |
   v
What are you allowed to do?
   |
   v
AWS Resource
```

By the end of this part, you should understand:

* What IAM is

# 1. What Is IAM?

IAM stands for:

Identity and Access Management.

IAM is the AWS service used to manage identities and permissions.

It helps answer two major questions:

```text
WHO?
 |
Identity

WHAT?
 |
Permissions
```

For example:

```text
Developer Alice
      |
      v
Can start EC2 instances
```

Another:

```text
Application Server
      |
      v
Can read files from S3
```

Another:

```text
Database Administrator
      |
      v
Can manage RDS
but cannot modify IAM
```

IAM lets you control this behavior.

---

# 2. Why IAM Exists

Imagine a company with 100 employees.

If everyone used the AWS root account credentials:

```text
100 Employees
      |
      v
One Root Account
      |
      v
Full AWS Access
```

This would be extremely dangerous.

Someone could accidentally:

* Delete production infrastructure
* Create expensive resources
* Change security settings
* Remove users
* Access sensitive data
* Delete backups

IAM allows access to be separated.

For example:

```text
Developers
   |
   +--> EC2
   +--> CloudWatch

Database Team
   |
   +--> RDS

Security Team
   |
   +--> IAM
   +--> CloudTrail

Applications
   |
   +--> S3
   +--> SQS
```

Each identity receives only the permissions it needs.

This is the foundation of access control in AWS.

---

# 3. Authentication vs Authorization

These two terms are closely related but different.

## Authentication

Authentication answers:

Who are you?

You prove your identity.

Examples include:

* Username and password
* MFA code
* Access key
* Temporary credentials
* Federated identity
* SSO login

Conceptually:

```text
User
 |
 v
Credentials
 |
 v
AWS
 |
 v
Identity verified
```

Authentication is about identity.

---

# 4. Authorization

Authorization answers:

What are you allowed to do?

After AWS knows who you are, AWS evaluates permissions.

Example:

```text
Alice successfully logs in
        |
        v
Authentication succeeded
        |
        v
Alice requests:
Start EC2 instance
        |
        v
AWS evaluates permissions
        |
        v
Allowed or Denied
```

Authentication and authorization are different.

A user can authenticate successfully and still be denied access.

Example:

```text
Login successful
      |
      v
Try to delete S3 bucket
      |
      v
AccessDenied
```

The user exists.

The user is authenticated.

The user simply does not have permission.

---

# 5. Authentication vs Authorization Example

Suppose you enter an office building.

At the entrance:

```text
Security checks your ID
```

That is authentication.

Then you try to enter the server room.

Your badge is checked.

```text
Are you allowed into the server room?
```

That is authorization.

In AWS:

```text
Authentication
"Who are you?"

Authorization
"What can you do?"
```

Remember this distinction.

It will appear constantly in cloud security.

---

# 6. AWS Account Root User

When an AWS account is created, the account owner has root user credentials.

The root user has extremely powerful permissions.

The root user can perform almost every action in the account.

Conceptually:

```text
AWS Account
    |
    v
Root User
    |
    +--> IAM
    +--> EC2
    +--> S3
    +--> RDS
    +--> Billing
    +--> Account Settings
    +--> Almost Everything
```

Because of this power, the root account must be heavily protected.

---

# 7. Why You Should Not Use Root Daily

Suppose your root credentials are stolen.

An attacker may gain extremely broad control over the AWS account.

That is much more dangerous than compromising an identity with limited permissions.

Compare:

```text
Compromised Developer Identity

Can:
- View logs
- Deploy application
- Restart specific servers
```

versus:

```text
Compromised Root User

Potentially:
- Change account configuration
- Modify IAM
- Delete resources
- Access billing
- Remove protections
- Create new privileged identities
```

Root access has a huge blast radius.

Blast radius means:

The amount of damage that can result from a failure, mistake, or compromise.

---

# 8. Root User Security Practices

For an AWS account:

* Use a strong unique password.
* Enable MFA.
* Do not create root access keys unless absolutely required.
* If root access keys exist unnecessarily, remove them.
* Do not use root for normal engineering work.
* Do not share root credentials.
* Store recovery information securely.

Daily work should use appropriate IAM or federated identities instead.

A good pattern is:

```text
Root
 |
Only exceptional account-level tasks

Daily AWS Work
 |
IAM / Federation / Roles
```

---

# 9. What Is an IAM User?

An IAM user represents a long-lived identity inside an AWS account.

Historically, IAM users have often represented:

* Human users
* Administrative users
* Automation identities

An IAM user can have:

* A console password
* Access keys
* Policies
* Group membership

For example:

```text
IAM User: alice
 |
 +-- Console access
 |
 +-- Group: Developers
 |
 +-- Permissions
```

---

# 10. IAM Users Are Account-Specific

An IAM user exists inside an AWS account.

For example:

```text
AWS Account A
 |
 +-- IAM User: alice
```

This is not automatically the same identity as:

```text
AWS Account B
 |
 +-- IAM User: alice
```

Even though the names match.

They belong to different AWS accounts.

Account boundaries matter.

---

# 11. IAM Users and Human Access

IAM users can be useful for learning IAM concepts.

However, in larger modern AWS environments, organizations often prefer centralized identity systems, federation, or AWS IAM Identity Center rather than creating large numbers of long-lived IAM users for every employee.

The important beginner concept is still:

```text
IAM User
 |
Represents an identity inside an AWS account
```

You will encounter IAM users frequently in tutorials, legacy environments, and some automation scenarios.

---

# 12. What Is an IAM Group?

An IAM group is a collection of IAM users.

Instead of assigning the same permissions individually to many users, you can assign permissions to a group.

Example:

```text
Developers Group
 |
 +-- Alice
 +-- Bob
 +-- Maria
```

The group could have permissions such as:

```text
Developers
 |
 +-- View EC2
 +-- Restart development instances
 +-- Read CloudWatch logs
```

Then users in the group inherit those permissions.

---

# 13. Why Groups Are Useful

Imagine five developers:

```text
Alice
Bob
Maria
David
Sarah
```

Without groups, you might manually attach the same policy five times.

```text
Policy --> Alice
Policy --> Bob
Policy --> Maria
Policy --> David
Policy --> Sarah
```

With a group:

```text
                Developers Group
                      |
        +-------------+-------------+
        |             |             |
      Alice          Bob          Maria
        |             |             |
      David         Sarah
```

Attach the policy once:

```text
Developer Policy
       |
       v
Developers Group
```

This makes permission administration easier.

---

# 14. Important IAM Group Limitation

Groups contain users.

Groups do not contain roles.

Groups do not contain other groups.

Think:

```text
IAM Group
 |
 +--> IAM User
 +--> IAM User
 +--> IAM User
```

Not:

```text
IAM Group
 |
 +--> IAM Role
```

And not:

```text
IAM Group A
 |
 +--> IAM Group B
```

---

# 15. What Is an IAM Role?

An IAM role is an AWS identity with permissions that can be assumed temporarily.

This is one of the most important IAM concepts.

Unlike a traditional IAM user, a role is not normally tied permanently to one person.

Different trusted identities or AWS services can assume a role.

Example:

```text
EC2 Instance
     |
     v
Assume IAM Role
     |
     v
Temporary Credentials
     |
     v
Access S3
```

Another example:

```text
Developer
   |
   v
Assume ProductionReadOnly Role
   |
   v
Temporary Access
```

Roles are extremely important for secure AWS architecture.

---

# 16. Why Roles Exist

Suppose an EC2 application needs to download files from S3.

A bad solution would be:

```text
EC2 Server
   |
Hard-coded AWS Access Key
   |
Application
   |
S3
```

Why is this dangerous?

Because the key might be:

* Stored in source code
* Committed to Git
* Written into logs
* Copied into an image
* Forgotten on the server
* Stolen

A better design is:

```text
EC2 Instance
     |
IAM Role
     |
Temporary Credentials
     |
S3
```

AWS manages the temporary credentials.

This avoids manually storing permanent access keys on the server.

---

# 17. IAM User vs IAM Role

A simplified comparison:

| IAM User                                 | IAM Role                                                       |
| ---------------------------------------- | -------------------------------------------------------------- |
| Long-lived identity                      | Assumable identity                                             |
| May have password                        | No normal permanent login password                             |
| May have long-lived access keys          | Usually provides temporary credentials                         |
| Often represents user or legacy workload | Commonly used by workloads, services, and cross-account access |
| Exists directly in account               | Assumed when needed                                            |

The most important distinction:

```text
IAM User
Usually represents a persistent identity

IAM Role
Represents permissions that a trusted identity can assume
```

# 18. What Is an IAM Policy?

An IAM policy is a document that defines permissions.

A policy tells AWS:

```text
What actions are allowed or denied?

On which resources?

Under which conditions?
```

IAM policies are normally written in JSON.

JSON means JavaScript Object Notation.

You do not need JavaScript knowledge to understand IAM JSON.

JSON is simply a structured text format.

---

# 19. A Very Simple IAM Policy

Example:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:ListAllMyBuckets",
      "Resource": "*"
    }
  ]
}
```

Do not worry if this looks unfamiliar.

We will break it down line by line.

---

# 20. JSON Structure Basics

JSON uses structures such as:

```text
{
}
```

for objects.

And:

```text
[
]
```

for arrays or lists.

Key-value pairs look like:

```json
"Effect": "Allow"
```

The key is:

```text
Effect
```

The value is:

```text
Allow
```

Multiple entries are separated by commas.

Example:

```json
{
  "Name": "Alice",
  "Team": "Platform"
}
```

IAM policy syntax becomes easier once you recognize this structure.

---

# 21. IAM Policy Version

You often see:

```json
"Version": "2012-10-17"
```

This is the IAM policy language version.

It does not mean the policy was created in 2012.

Beginners sometimes confuse this.

It identifies the policy syntax version AWS should use when interpreting the document.

---

# 22. Statement

Permissions live inside policy statements.

Example:

```json
"Statement": [
  {
    "Effect": "Allow",
    "Action": "s3:ListAllMyBuckets",
    "Resource": "*"
  }
]
```

A policy can contain one statement or multiple statements.

Conceptually:

```text
Policy
 |
 +-- Statement 1
 |
 +-- Statement 2
 |
 +-- Statement 3
```

Each statement describes permissions.

---

# 23. Effect

Effect tells AWS whether the statement allows or denies actions.

Possible values are:

```text
Allow
Deny
```

Example:

```json
"Effect": "Allow"
```

means the statement grants permission if the rest of the statement matches.

Example:

```json
"Effect": "Deny"
```

means the statement explicitly denies access if it matches.

---

# 24. Action

Action specifies what AWS API operations are being controlled.

Example:

```json
"Action": "s3:GetObject"
```

This refers to retrieving an object from S3.

Another:

```json
"Action": "ec2:StartInstances"
```

This refers to starting EC2 instances.

You may also specify multiple actions:

```json
"Action": [
  "ec2:StartInstances",
  "ec2:StopInstances"
]
```

This means the statement applies to both actions.

---

# 25. Understanding AWS Action Names

AWS actions commonly follow this pattern:

```text
service:Operation
```

For example:

```text
ec2:StartInstances
```

Breakdown:

```text
ec2
 |
AWS service

StartInstances
 |
API operation
```

Another:

```text
s3:GetObject
```

Breakdown:

```text
s3
 |
Amazon S3

GetObject
 |
Retrieve an object
```

IAM permissions are closely connected to AWS APIs.

Remember our Part 1 model:

```text
Console
CLI
SDK
 |
 v
AWS APIs
```

IAM determines whether those API requests are authorized.

---

# 26. Resource

Resource specifies which AWS resources the statement applies to.

Example:

```json
"Resource": "*"
```

The asterisk means:

All applicable resources.

This can be appropriate for some actions but dangerous for others.

A more restrictive example might identify a specific resource using an ARN.

Example structure:

```text
arn:aws:s3:::example-bucket/*
```

Conceptually:

```text
Allow access
     |
Only to
     |
Specific Resource
```

This is much safer than granting unnecessary access everywhere.

---

# 27. Condition

Condition adds additional requirements.

For example, a permission might only apply:

* From a particular network
* When MFA is present
* When specific tags exist
* Under certain request conditions

Conceptually:

```text
Allow action
   |
Only if
   |
Condition matches
```

A policy without a Condition can still be valid.

Condition simply adds more control.

---

# 28. Full IAM Statement Mental Model

Think of an IAM statement as answering four questions:

```text
Effect
 |
Allow or deny?

Action
 |
What operation?

Resource
 |
Which AWS resource?

Condition
 |
Under what circumstances?
```

A useful sentence is:

```text
Allow
Alice
to read
objects
from this S3 bucket
under these conditions.
```

# 29. Identity-Based Policies

Identity-based policies are attached to identities.

Examples:

* IAM user
* IAM group
* IAM role

Conceptually:

```text
IAM Role
   |
   v
Policy
   |
   v
Can read S3
```

Another:

```text
IAM User
   |
   v
Policy
   |
   v
Can describe EC2 instances
```

The policy follows the identity.

---

# 30. Example Identity-Based Policy

Suppose a role should read objects from one S3 bucket.

A simplified policy could look like:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::example-app-bucket/*"
    }
  ]
}
```

Interpretation:

```text
Effect
Allow

Action
Read S3 objects

Resource
Objects inside example-app-bucket
```

This does not automatically allow every S3 operation.

It is narrowly scoped.

---

# 31. Resource-Based Policies

Resource-based policies are attached directly to supported AWS resources.

One common example is an S3 bucket policy.

Instead of attaching the policy to Alice:

```text
Alice
 |
Policy
```

you attach a policy to:

```text
S3 Bucket
 |
Bucket Policy
```

The resource policy can specify which principal is allowed to access the resource.

---

# 32. Principal

In resource-based policies, you often encounter:

```text
Principal
```

Principal answers:

Who is allowed or denied?

Examples include:

* AWS account
* IAM role
* IAM user
* AWS service

Conceptually:

```text
Resource Policy
 |
Principal
 |
Who?
```

Identity-based policies often do not need to specify Principal because the policy is already attached to the identity.

---

# 33. Identity Policy vs Resource Policy

Think of it this way:

Identity-based:

```text
WHO has permission?
 |
Identity
 |
Policy
 |
Can access resource
```

Resource-based:

```text
RESOURCE
 |
Policy
 |
Which principal may access me?
```

Both can participate in AWS permission evaluation.

---

# 34. Managed Policies vs Inline Policies

IAM policies can also be categorized by how they are managed.

Two important forms are:

* Managed policies
* Inline policies

A managed policy exists as a standalone policy that can be attached to multiple identities.

An inline policy exists directly inside one identity.

Conceptually:

```text
Managed Policy
 |
 +--> Role A
 +--> Role B
 +--> User C
```

versus:

```text
Role A
 |
Inline Policy
```

Managed policies are generally easier to reuse and administer consistently.

---

# 35. AWS Managed vs Customer Managed Policies

Managed policies can be:

* AWS managed
* Customer managed

AWS-managed policies are created and maintained by AWS.

Customer-managed policies are created and maintained by you.

Example conceptually:

```text
AWS Managed Policy
 |
Maintained by AWS

Customer Managed Policy
 |
Maintained by your organization
```

AWS-managed policies can be convenient.

However, they may grant broader permissions than your application actually needs.

For production environments, carefully designed customer-managed policies often provide better control.

---

# 36. Allow vs Deny

AWS permission evaluation can appear complicated at first.

Start with one critical rule:

By default, access is denied.

If no permission allows an action:

```text
Request
 |
No Allow
 |
Denied
```

This is called implicit deny.

---

# 37. Implicit Deny

Suppose Alice has no policy allowing:

```text
ec2:TerminateInstances
```

Alice tries:

```text
Terminate EC2
```

AWS evaluates the request.

No permission says Allow.

Result:

```text
Denied
```

Nothing needed to explicitly say Deny.

Access was simply never granted.

That is implicit deny.

---

# 38. Explicit Allow

Suppose Alice receives:

```json
{
  "Effect": "Allow",
  "Action": "ec2:DescribeInstances",
  "Resource": "*"
}
```

Alice requests:

```text
Describe EC2 instances
```

Now there is an Allow.

If no stronger restriction applies, the action can succeed.

---

# 39. Explicit Deny

An explicit deny is powerful.

Suppose one policy says:

```text
Allow deleting S3 objects
```

but another applicable policy says:

```text
Deny deleting S3 objects
```

The explicit deny wins.

Think:

```text
Allow
  +
Explicit Deny
  |
  v
DENIED
```

A useful rule:

```text
Explicit Deny overrides Allow.
```

This becomes extremely important in larger environments involving:

* IAM policies
* Resource policies
* Service Control Policies
* Permission boundaries
* Session policies

We do not need all of those yet.

For now remember:

```text
Default = Denied

Allow can grant access

Explicit Deny overrides Allow
```

---

# 40. Permission Evaluation Mental Model

A simplified beginner model:

```text
Request
   |
   v
Is there an explicit Deny?
   |
   +-- Yes --> DENY
   |
   No
   |
   v
Is there an applicable Allow?
   |
   +-- Yes --> ALLOW
   |
   No
   |
   v
DENY
```

Real AWS policy evaluation has additional layers.

This model is sufficient for your first IAM troubleshooting.

# 41. Principle of Least Privilege

Least privilege means:

Give an identity only the permissions it actually needs to perform its job.

Not more.

Suppose an application only needs to read files from one S3 bucket.

Bad design:

```text
AdministratorAccess
```

The application could potentially access far more AWS resources than necessary.

Better design:

```text
Allow:
s3:GetObject

Resource:
Only required bucket
```

Least privilege reduces blast radius.

---

# 42. Why Least Privilege Matters

Imagine credentials are compromised.

With broad permissions:

```text
Compromised Credential
      |
      +--> EC2
      +--> S3
      +--> RDS
      +--> IAM
      +--> Secrets
      +--> Everything
```

With least privilege:

```text
Compromised Credential
      |
      v
Only read specific S3 objects
```

The compromise is still serious.

But the potential damage is smaller.

---

# 43. Least Privilege Is Not "Give Nothing"

Least privilege does not mean:

```text
No permissions
```

It means:

```text
Exactly enough permissions
for the required task
```

If permissions are too restrictive, applications and engineers cannot work.

If permissions are too broad, security risk increases.

The objective is the smallest appropriate permission set.

---

# 44. MFA

MFA stands for:

Multi-Factor Authentication.

MFA requires more than one factor to authenticate.

For example:

```text
Something you know
Password

+

Something you have
Authenticator device
```

Without MFA:

```text
Password stolen
 |
Potential account access
```

With MFA:

```text
Password stolen
 |
Still requires second factor
```

MFA does not make an account impossible to compromise.

But it significantly strengthens authentication.

---

# 45. Where MFA Is Especially Important

At minimum, pay close attention to:

* Root user
* Privileged administrators
* Sensitive identities

A strong AWS environment should not depend only on passwords for powerful identities.

---

# 46. Password Policies

For IAM users with console passwords, an AWS account can define password policy requirements.

A password policy may control things such as:

* Minimum password length
* Character requirements
* Password reuse
* Whether users can change passwords

Password policy is one layer of protection.

However, even a strong password should not replace MFA for sensitive access.

---

# 47. Console Credentials vs Programmatic Credentials

This distinction matters.

A human might use:

```text
Username
Password
MFA
```

to sign in through the AWS console.

Software often needs programmatic credentials.

Historically, this commonly means:

```text
Access Key ID
Secret Access Key
```

These credentials can be used by tools such as:

* AWS CLI
* SDKs
* Scripts

---

# 48. What Is an Access Key?

An AWS access key normally consists of:

```text
Access Key ID
Secret Access Key
```

Think of them conceptually as:

```text
Access Key ID
 |
Identifier

Secret Access Key
 |
Secret authentication material
```

The secret access key must be protected.

Do not treat it like a username.

It is sensitive.

---

# 49. Access Key Security

Never:

* Put access keys in public GitHub repositories.
* Hard-code them into application source code.
* Send them through insecure chat.
* Put them into Docker images.
* Write them into documentation.
* Store them in public files.
* Reuse them unnecessarily.
* Create them when a role would work instead.

A leaked access key can allow attackers to make AWS API requests using that identity's permissions.

---

# 50. The Dangerous Hard-Coded Credential Pattern

Bad:

```python
ACCESS_KEY = "EXAMPLE"
SECRET_KEY = "EXAMPLE_SECRET"
```

Then:

```text
Application
 |
Hard-coded credentials
 |
AWS
```

If code is shared:

```text
Source Repository
      |
      v
Credentials leaked
      |
      v
Attacker uses AWS API
```

This is a common cloud security failure.

---

# 51. Long-Lived vs Temporary Credentials

Long-lived credentials remain valid until:

* Disabled
* Deleted
* Rotated
* Expired by some external process

Traditional IAM user access keys are examples of long-lived credentials.

Temporary credentials expire automatically.

Temporary credentials are commonly associated with:

* IAM roles
* STS
* EC2 roles
* Federated access

This is a major security improvement.

---

# 52. Why Temporary Credentials Are Better

Suppose permanent credentials are stolen.

They may remain usable until someone notices and disables them.

Temporary credentials have a limited lifetime.

Example:

```text
Temporary Credential
      |
Issued
      |
Valid for limited period
      |
Expires
```

Expiration limits how long the credential can be used.

This does not remove the need for security.

It reduces long-lived credential exposure.

---

# 53. AWS STS Introduction

STS stands for:

AWS Security Token Service.

STS provides temporary security credentials.

A major use of STS is role assumption.

Conceptually:

```text
Identity
   |
   v
Requests role assumption
   |
   v
AWS STS
   |
   v
Temporary credentials
   |
   v
Role permissions
```

STS is fundamental to modern AWS authentication patterns.

---

# 54. Temporary Credential Components

Temporary AWS credentials generally include:

```text
Access Key ID
Secret Access Key
Session Token
```

The session token distinguishes temporary sessions from traditional long-lived key pairs.

Conceptually:

```text
Temporary Session
 |
 +-- Access Key
 +-- Secret Key
 +-- Session Token
 +-- Expiration
```

Applications and tools normally handle these automatically when roles are configured correctly.

---

# 55. What Does "Assume a Role" Mean?

To assume a role means:

A trusted identity temporarily receives the permissions associated with that role.

Example:

```text
Alice
 |
Normal permissions
 |
Assume ProductionReadOnlyRole
 |
Temporary credentials
 |
Read production resources
```

Alice does not permanently become the role.

She receives a temporary session using the role's permissions.

---

# 56. Roles Need Trust

A role needs to define:

Who is allowed to assume me?

This is handled through a trust policy.

Think of two separate questions:

```text
Trust Policy
 |
Who can assume this role?

Permissions Policy
 |
What can the role do after assumption?
```

This distinction is very important.

---

# 57. Trust Policy vs Permissions Policy

Suppose there is a role:

```text
ProductionReadOnlyRole
```

Trust policy:

```text
Alice is allowed to assume this role.
```

Permissions policy:

```text
This role can view EC2 and CloudWatch.
```

Both matter.

If Alice is not trusted:

```text
Cannot assume role
```

If the role has no permissions:

```text
Can assume role
but cannot do useful work
```

# 58. Role Assumption Flow

Conceptually:

```text
User
 |
 v

 |
 v
STS
 |
 v
Check trust policy
 |
 +-- Not trusted --> Denied
 |
 +-- Trusted
       |
       v
Temporary credentials issued
       |
       v

```

This model is extremely important for troubleshooting.

# 59. Cross-Account Roles

Roles are commonly used across AWS accounts.

Imagine:

```text

```

and:

```text

```

Instead of creating another permanent user in production, an engineer may assume a controlled role.

```text

in Account A
      |
      v

      |
      v
Production Account
      |
      v

```

# 60. IAM Roles for AWS Services

AWS services can also assume roles.

For example:

```text

 |
 v
IAM Role
 |
 v
S3
```

The EC2 instance is trusted to use the role.

The role defines what the instance is allowed to do.

# 61. IAM Roles for EC2

Suppose your application runs on EC2 and needs to read:

```text
s3://example-app-config
```

Bad approach:

```text
Create IAM user
      |
Create access key
      |
Copy credentials to EC2
      |
Application uses permanent key
```

Better approach:

```text
Create IAM Role
      |
Allow s3:GetObject
      |
Attach role to EC2
      |
EC2 receives temporary credentials
      |
Application accesses S3
```

No hard-coded access keys are required.

     |

     |

The main thing to remember is:

# 63. How an Application on EC2 Gets Credentials

When an EC2 role is attached, AWS makes temporary role credentials available through the EC2 instance metadata system.

AWS SDKs and the AWS CLI can automatically discover these credentials.

That means your application often does not need code like:

```text

```

Instead:

```text

    |

    |

    |

    |

```

This is significantly safer.

# 64. Example EC2 Role

Suppose the application only needs to read one S3 bucket.

Permissions:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::example-app-config/*"
    }
  ]
}
```

Attach the role to EC2.

Now the application can make an S3 request using temporary credentials.

It cannot automatically:

* Delete EC2 instances
* Create IAM users
* Modify RDS
* Read every S3 bucket

unless additional permissions grant those actions.

That is least privilege.

# 65. Understanding Permission Scope

Compare these policies.

Broad:

```json
{
  "Effect": "Allow",
  "Action": "*",
  "Resource": "*"
}
```

Interpretation:

```text
Allow every applicable action
on every applicable resource
```

This is effectively extremely powerful.

Now compare:

```json
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::example-app-config/*"
}
```

Interpretation:

```text
Allow one type of S3 operation
on objects in one bucket
```

That is much narrower.

# 66. Wildcards

IAM policies frequently use:

```text
*
```

as a wildcard.

Example:

```json
"Action": "s3:*"
```

means:

All S3 actions.

Example:

```json
"Resource": "*"
```

means:

All applicable resources.

Wildcards are convenient.

They can also create excessive permissions.

Every time you see `*`, ask:

```text
Does this actually need to be this broad?
```

# 67. IAM Permission Troubleshooting

One of the most common AWS errors is:

```text
AccessDenied
```

Beginners often respond by attaching:

```text
AdministratorAccess
```

This may make the error disappear.

It is not good troubleshooting.

The correct approach is to understand why permission evaluation failed.

# 68. IAM Troubleshooting Workflow

When you see a permission error:

```text
Observe
   |
   v
Identify identity
   |
   v
Identify action
   |
   v
Identify resource
   |
   v
Inspect policies
   |
   v
Check explicit denies
   |
   v
Check conditions
   |
   v
Fix smallest required permission
   |
   v

```

Do not immediately grant broad administrative access.

---

# 69. Step 1: Identify the Caller

Ask:

Who is making the request?

Possibilities include:

* IAM user
* IAM role
* EC2 role
* Lambda role
* Federated user
* CI/CD role

If you troubleshoot the wrong identity, you may spend hours editing irrelevant policies.

Purpose:

Shows information about the AWS identity currently making the request.

Important fields:

```text

 |
Identity identifier

AWS account ID

```

This command is extremely useful during credential troubleshooting.

# 71. Breaking Down the Command

```bash

```

`aws`

The AWS CLI program.

`sts`

AWS Security Token Service.

`get-caller-identity`

The API operation requesting information about the caller.

This command does not modify infrastructure.

It helps you understand which identity your CLI is currently using.

# 72. Step 2: Identify the Failed Action

An AWS error may tell you something like:

```text
not authorized to perform:
s3:GetObject
```

That tells you the missing or denied operation.

Write it down:

```text
Action = s3:GetObject
```

---

# 73. Step 3: Identify the Resource

The error may identify an ARN such as:

```text
arn:aws:s3:::example-bucket/config.json
```

Now you know:

```text
Identity
Who?

Action
s3:GetObject

Resource
example-bucket/config.json
```

IAM troubleshooting becomes much more precise.

---

# 74. Step 4: Check Applicable Policies

Look at policies attached to:

* User
* Groups
* Role
* Resource

In larger environments you may also need to consider:

* Permission boundaries
* Service Control Policies
* Session policies

But do not jump there first unless the environment uses them.

Start with the simplest applicable permission sources.

---

# 75. Step 5: Look for Explicit Deny

Suppose one policy says:

```text
Allow s3:GetObject
```

but another says:

```text
Deny all S3 actions
```

Result:

```text
Denied
```

Do not keep adding more Allow statements.

An explicit deny must be addressed.

---

# 76. Step 6: Check Resource Matching

Suppose the policy grants:

```text
arn:aws:s3:::bucket-a/*
```

but your application is accessing:

```text
bucket-b
```

The permission does not match.

Another common problem is misunderstanding bucket ARN vs object ARN.

For example:

```text
arn:aws:s3:::example-bucket
```

represents the bucket.

While:

```text
arn:aws:s3:::example-bucket/*
```

represents objects inside the bucket.

Different S3 actions may require different resource forms.

---

# 77. Step 7: Check Conditions

Suppose the policy only allows access if:

```text
MFA is present
```

or:

```text
Source network matches
```

or:

```text
Resource has required tag
```

Then an apparently correct Action and Resource may still fail because the Condition is not satisfied.

---

# 78. Step 8: Make the Smallest Fix

Bad response:

```text
Attach AdministratorAccess
```

Better:

```text
Identify exact missing permission
      |
Add only required action
      |
Scope to required resource
      |
Retest
```

This preserves least privilege.

# 79. Common IAM Security Mistake: Using Root Daily

Problem:

Engineers use root for normal work.

Risk:

A compromised credential has maximum impact.

Better:

```text
Secure Root
   |
Use only when necessary

Daily Work
   |
Limited administrative identity
```

---

# 80. Common IAM Security Mistake: No MFA

Problem:

Powerful identity protected only by password.

Risk:

Password compromise may lead directly to account access.

Better:

Enable MFA.

Especially for privileged identities.

---

# 81. Common IAM Security Mistake: AdministratorAccess Everywhere

Problem:

Every user receives full administrative permission because it is easy.

Example:

```text
Developer
 |
AdministratorAccess
```

Risk:

Mistakes or compromises can affect the entire account.

Better:

Role-specific permissions.

---

# 82. Common IAM Security Mistake: Using `*` Everywhere

Example:

```json
{
  "Effect": "Allow",
  "Action": "*",
  "Resource": "*"
}
```

This is easy.

It is also dangerous.

Ask:

```text
Does this identity truly need every AWS action?
```

Usually the answer is no.

---

# 83. Common IAM Security Mistake: Hard-Coded Access Keys

Problem:

Credentials appear inside:

```text
Git repository
Application code
Shell script
Docker image
Configuration file
```

Risk:

Credentials leak.

Better:

Use roles and temporary credentials whenever possible.

---

# 84. Common IAM Security Mistake: Sharing Credentials

Never have a team use one shared IAM user like:

```text
devteam
```

with one shared password.

Problems include:

* Poor accountability
* Difficult auditing
* Difficult revocation
* Security exposure

Individual identities should be attributable.

---

# 85. Common IAM Security Mistake: Old Access Keys

Unused access keys may remain active for months or years.

If they were copied somewhere unsafe, they can become a hidden vulnerability.

Review and remove unnecessary credentials.

---

# 86. Common IAM Security Mistake: Giving Applications Human Credentials

An application should not normally use a developer's personal IAM access key.

Bad:

```text
Alice's access key
       |
Application server
```

Now if Alice changes jobs or her permissions change, the application may break.

Better:

```text
Application
   |
Dedicated IAM Role
```

Human identity and machine identity should be separated.

---

# 87. Common IAM Security Mistake: Failing to Understand Trust Policies

You may create a role with perfect permissions but still receive:

```text
AccessDenied
```

during `AssumeRole`.

Why?

Because the trust policy does not allow your identity to assume the role.

Remember:

```text
Trust Policy
Who may assume?

Permissions Policy
What may the role do?
```

Different problems.

---

# 88. Common IAM Security Mistake: Keeping Permissions After They Are No Longer Needed

Suppose a developer temporarily needs:

```text
RDS administration
```

Six months later, the access is no longer required.

If nobody removes it, privilege accumulates.

This is called permission creep.

Regularly reviewing permissions is important.

# What You Should Now Understand

After Part 2, you should understand that:

* IAM controls identities and permissions in AWS.
* Authentication proves identity.
* Authorization determines permitted actions.
* The AWS root user is extremely privileged and should not be used for routine work.
* MFA is essential for protecting sensitive identities.
* IAM users are long-lived identities within an AWS account.
* IAM groups organize IAM users and simplify permission management.
* IAM roles provide assumable identities with temporary credentials.
* Roles are preferred over hard-coded access keys for many workloads.
* IAM policies define permissions.
* IAM policies are commonly written in JSON.
* Effect determines Allow or Deny.
* Action identifies AWS API operations.
* Resource identifies what the action applies to.
* Condition adds additional restrictions.
* Identity-based policies attach to identities.
* Resource-based policies attach to resources.
* Trust policies determine who may assume roles.
* Permissions policies determine what a role can do after assumption.
* Default access is denied.
* Explicit Allow can grant access.
* Explicit Deny overrides Allow.
* Least privilege means granting only required permissions.
* Access keys are sensitive credentials.
* Hard-coded access keys create serious security risk.
* Temporary credentials reduce long-lived credential exposure.
* AWS STS issues temporary credentials.
* `AssumeRole` is a fundamental AWS access pattern.
* EC2 instances can use IAM roles rather than permanent credentials.
* `aws sts get-caller-identity` is valuable for permission troubleshooting.
* IAM errors should be diagnosed systematically instead of solved by adding AdministratorAccess.
