# Part 8: NAT Gateways and Private-Subnet Internet Access

By this point, you should already understand:

* What a VPC is
* What public and private subnets are
* How route tables control traffic
* What an Internet Gateway does
* How `0.0.0.0/0` represents all IPv4 destinations
* Why a public subnet normally has a route to an Internet Gateway
* Why a private subnet should not send internet traffic directly to an Internet Gateway

Now we need to solve an important problem.

A server can be private and still need the internet.

That sounds contradictory at first.

If a server is private, why would it need internet access?

Because private does not mean completely disconnected.

A production application server may need to:

* Download Linux package updates
* Install security patches
* Download dependencies
* Contact external APIs
* Retrieve container images
* Send information to external monitoring services
* Validate software licenses
* Download application packages
* Communicate with package repositories
* Reach public AWS service endpoints when private endpoints are not being used

The important distinction is this:

A private server may need to start connections to the internet.

That does not mean the internet should be able to start connections to the server.

This is the problem NAT helps solve.

---

# 1. The Core Problem

Imagine an EC2 instance running inside a private subnet.

```text
VPC: 10.0.0.0/16

Private Subnet
10.0.2.0/24

EC2
Private IP: 10.0.2.25
```

The server needs to run:

```bash
sudo apt update
```

Ubuntu needs to contact package repositories on the internet.

But the EC2 instance:

* Has no public IPv4 address
* Has no Elastic IP
* Lives in a private subnet
* Does not have a direct internet route through an Internet Gateway

So how does it reach the internet?

We introduce a NAT Gateway.

The resulting path becomes:

```text
Private EC2
    |
    v
Private Route Table
    |
    v
NAT Gateway
    |
    v
Public Subnet
    |
    v
Internet Gateway
    |
    v
Internet
```

The private server remains private.

It does not need a public IP address.

The NAT Gateway provides the public-facing translation needed for the outbound connection.

---

# 2. Why Private Servers Still Need Outbound Internet Access

A common beginner misunderstanding is:

"If an EC2 instance is private, it should never communicate with the internet."

That is not necessarily true.

The better rule is:

Private servers should generally avoid direct inbound exposure from the public internet.

They may still require controlled outbound connectivity.

Consider an application server.

```text
Internet
   |
Load Balancer
   |
Private EC2
```

The application server does not need users connecting directly to it.

Users connect to the load balancer.

The load balancer then sends traffic to the application.

But the EC2 server may still need to perform:

```bash
sudo apt update
```

or:

```bash
sudo apt install nginx
```

or:

```bash
curl https://api.example.com
```

or:

```bash
docker pull some-image
```

These operations require outbound connectivity.

This creates two different traffic requirements.

## Inbound requirement

The server should not accept arbitrary connections directly from the internet.

## Outbound requirement

The server should be allowed to initiate certain connections toward the internet.

NAT Gateway helps support that pattern.

---

# 3. What NAT Means

NAT stands for:

Network Address Translation.

Before understanding NAT Gateway, you should understand the translation itself.

Suppose your EC2 instance has:

```text
Private IP:
10.0.2.25
```

Addresses such as `10.x.x.x` are private IPv4 addresses.

They are not globally routable on the public internet.

An internet server cannot normally send traffic directly to:

```text
10.0.2.25
```

because millions of private networks can reuse private address ranges.

Your computer at home might use:

```text
192.168.1.20
```

Someone else's home network could also use:

```text
192.168.1.20
```

Those private addresses only have meaning inside their respective networks.

NAT solves this problem by translating private addressing into public addressing.

---

# 4. A Simple NAT Example

Suppose:

```text
Private EC2 IP:
10.0.2.25

NAT Gateway public IP:
203.0.113.50
```

The EC2 instance wants to connect to:

```text
example.com
```

Assume the destination server is:

```text
93.184.216.34
```

The original packet effectively begins as:

```text
Source:
10.0.2.25

Destination:
93.184.216.34
```

The NAT Gateway translates the source identity for internet-facing communication.

Conceptually:

```text
Before NAT

10.0.2.25
    |
    v
NAT Gateway
```

becomes:

```text
After NAT

203.0.113.50
    |
    v
Internet
```

The internet server sees the NAT Gateway's public address rather than the private EC2 address.

---

# 5. What a NAT Gateway Is

An AWS NAT Gateway is a managed Network Address Translation service.

A common use case is allowing instances in private subnets to connect outward while preventing unsolicited internet connections from being initiated toward those instances.

Instead of managing a NAT server yourself, AWS manages the NAT Gateway infrastructure.

For the public NAT Gateway architecture covered in this article, the NAT Gateway typically:

* Receives traffic from private resources
* Translates their private source addresses
* Sends traffic toward the internet
* Tracks the connection
* Accepts response traffic associated with that connection
* Sends the response back to the original private resource

---

# 6. NAT Gateway Does Not Make the Private EC2 Public

This is critical.

Adding this route:

```text
0.0.0.0/0 → NAT Gateway
```

does not turn a private EC2 instance into a public server.

The EC2 instance still:

* Has its private IP
* Does not require a public IP
* Is not directly reachable through the NAT Gateway
* Cannot normally receive unsolicited inbound internet connections through the NAT Gateway

NAT Gateway is primarily being used here as an outbound path.

---

# 7. Public NAT Gateway Architecture

A standard beginner architecture looks like this:

```text
                    INTERNET
                        |
                        v
                 Internet Gateway
                        |
                        v
                Public Route Table
                        |
                        v
                  Public Subnet
                  10.0.1.0/24
                        |
                   NAT Gateway
                        |
                        v
                Private Route Table
                        |
                        v
                  Private Subnet
                  10.0.2.0/24
                        |
                        v
                       EC2
                   10.0.2.25
```

Logically, outbound traffic travels upward from EC2:

```text
EC2
10.0.2.25
   |
   v
Private Subnet
   |
   v
Private Route Table
   |
0.0.0.0/0
   |
   v
NAT Gateway
   |
   v
Public Subnet
   |
   v
Internet Gateway
   |
   v
Internet
```

AWS requires a zonal public NAT Gateway used for internet access to be placed in a public subnet, associated with an Elastic IP address, with internet traffic from that subnet routed through the VPC's Internet Gateway.

---

# 8. What Makes the NAT Gateway's Subnet Public?

Remember the lesson from route tables.

A subnet is not public merely because we name it:

```text
public-subnet
```

It is public because its route table provides a route toward an Internet Gateway.

For IPv4, the route usually looks like:

```text
Destination       Target

10.0.0.0/16       local
0.0.0.0/0         igw-xxxxxxxx
```

AWS documents this pattern as the route that gives a subnet a path toward the Internet Gateway.

---

# 9. What Is an Elastic IP?

A public NAT Gateway requires a public address for communication with the internet.

AWS commonly provides this through an Elastic IP address.

An Elastic IP, often abbreviated EIP, is a public IPv4 address that you allocate to your AWS account and associate with supported AWS resources.

For our architecture:

```text
Private EC2:
10.0.2.25

NAT Gateway private-side address:
AWS-managed address in public subnet

NAT Gateway Elastic IP:
Public internet-facing IPv4 address
```

The important beginner concept is:

The EC2 instance does not need the public address.

The NAT Gateway owns the public-facing address.

Multiple private workloads can therefore access external systems through the NAT Gateway.

---

# 10. Why a Stable Elastic IP Can Be Useful

Suppose your company communicates with an external API.

The API provider says:

"We only accept requests from approved IP addresses."

Your EC2 instances may have private addresses such as:

```text
10.0.2.15
10.0.2.20
10.0.2.31
```

The external API cannot use those private addresses.

But outbound traffic could appear to come from the NAT Gateway's Elastic IP.

For example:

```text
198.51.100.25
```

The external provider could allowlist that address.

Now several internal workloads can reach the service while presenting a known public source address.

---

# 11. Private Route Tables

The private subnet needs its own routing logic.

Example:

```text
Private Route Table

Destination       Target

10.0.0.0/16       local
0.0.0.0/0         nat-0123456789
```

Let's interpret this carefully.

## Route 1

```text
10.0.0.0/16 → local
```

Traffic destined for addresses within the VPC remains inside the VPC.

For example:

```text
EC2 A:
10.0.2.25

EC2 B:
10.0.3.40
```

Both are inside:

```text
10.0.0.0/16
```

So the VPC-local route applies.

## Route 2

```text
0.0.0.0/0 → NAT Gateway
```

Traffic that does not match a more specific route can use the NAT Gateway.

This is typically internet-bound traffic.

AWS documents this private-subnet route pattern as:

```text
0.0.0.0/0 → nat-gateway-id
```

for IPv4 internet access through NAT.

---

# 12. Understanding 0.0.0.0/0 Properly

You will see this everywhere in AWS networking:

```text
0.0.0.0/0
```

Do not simply memorize it as:

"Internet."

Technically, it represents every possible IPv4 address.

It is the broadest IPv4 CIDR range.

So when a route table contains:

```text
0.0.0.0/0 → NAT Gateway
```

it effectively means:

"If no more-specific route matches this IPv4 destination, send the traffic to this NAT Gateway."

---

# 13. Route Specificity Still Matters

Suppose the route table has:

```text
10.0.0.0/16       local
0.0.0.0/0         NAT Gateway
```

Now the EC2 instance wants:

```text
10.0.4.20
```

AWS does not use:

```text
0.0.0.0/0
```

because:

```text
10.0.0.0/16
```

is a more specific match.

The packet stays within the VPC.

But if the EC2 instance wants:

```text
8.8.8.8
```

the VPC-local route does not match.

The default route does:

```text
0.0.0.0/0
```

So that traffic goes to the NAT Gateway.

This is why understanding routing is more useful than memorizing route entries.

---

# 14. Complete Outbound Connection Flow

Now follow a real connection from start to finish.

Assume:

```text
VPC:
10.0.0.0/16

Public subnet:
10.0.1.0/24

Private subnet:
10.0.2.0/24

Private EC2:
10.0.2.25

NAT Gateway Elastic IP:
198.51.100.50
```

The EC2 instance runs:

```bash
curl https://example.com
```

## Step 1: EC2 creates the connection

The server wants to connect to an internet destination on HTTPS.

HTTPS normally uses TCP port:

```text
443
```

The connection might conceptually begin as:

```text
Source:
10.0.2.25:49152

Destination:
93.184.216.34:443
```

The source port shown here is an example ephemeral port.

---

# 15. Step 2: The Route Table Is Evaluated

The private subnet's route table contains:

```text
10.0.0.0/16       local
0.0.0.0/0         nat-123456
```

The destination:

```text
93.184.216.34
```

is not within:

```text
10.0.0.0/16
```

So AWS uses:

```text
0.0.0.0/0
```

and sends the packet toward the NAT Gateway.

---

# 16. Step 3: NAT Translation Happens

The NAT Gateway receives the traffic.

Conceptually, it translates:

```text
Source:
10.0.2.25
```

into its internet-facing address:

```text
198.51.100.50
```

The external server therefore does not see:

```text
10.0.2.25
```

It sees the public NAT address.

---

# 17. Step 4: Traffic Reaches the Internet Gateway

The NAT Gateway sits in the public network path.

The public subnet route table has:

```text
0.0.0.0/0 → Internet Gateway
```

Traffic continues toward the Internet Gateway.

Then:

```text
Internet Gateway
        |
        v
Internet
```

---

# 18. Step 5: The Internet Server Responds

The external server sends a response back to the NAT Gateway's public address.

Conceptually:

```text
From:
93.184.216.34:443

To:
198.51.100.50
```

The NAT Gateway remembers the connection that originated from:

```text
10.0.2.25
```

It therefore maps the response back to the correct private instance.

---

# 19. Step 6: Return Traffic Reaches EC2

The flow becomes:

```text
Internet Server
      |
      v
Internet Gateway
      |
      v
NAT Gateway
      |
      v
Private EC2
10.0.2.25
```

The application receives the response.

From the application's perspective, it successfully made an HTTPS request.

---

# 20. NAT Gateway Is Stateful for Connection Return Traffic

AWS NAT Gateway permits outbound traffic and response traffic associated with those outbound requests. AWS describes this behavior as stateful.

The easiest beginner way to understand this is:

```text
Private EC2 starts connection
        |
        v
NAT remembers the connection
        |
        v
Internet replies
        |
        v
NAT recognizes the reply
        |
        v
Reply returns to private EC2
```

---

# 21. Why the Internet Cannot Normally Initiate a Connection Through NAT

Now reverse the situation.

Suppose someone on the internet tries to connect directly to the NAT Gateway's Elastic IP:

```text
198.51.100.50
```

and expects the NAT Gateway to forward the request to:

```text
10.0.2.25
```

There is no automatically created outbound connection state telling NAT:

```text
198.51.100.50:443
belongs to
10.0.2.25:443
```

The NAT Gateway is not acting like a public application load balancer.

It is not publishing your EC2 instance as an internet-facing server.

AWS explicitly describes the public NAT Gateway pattern as allowing private instances to connect outward while preventing unsolicited inbound internet connections from being initiated toward them.

This is one reason NAT is useful in private-subnet architecture.

---

# 22. NAT Gateway Is Not a Load Balancer

Do not confuse these services.

A NAT Gateway handles network address translation for connectivity.

A load balancer distributes application connections to registered targets.

Compare:

```text
OUTBOUND

Private EC2
    |
NAT Gateway
    |
Internet
```

versus:

```text
INBOUND APPLICATION TRAFFIC

Internet
    |
Application Load Balancer
    |
Private EC2
```

A common production architecture uses both.

```text
                    Internet
                    /      \
                   /        \
              inbound      outbound
                 |             |
                 v             v
                ALB      NAT Gateway
                 |             ^
                 v             |
              Private EC2 -----
```

---

# 23. NAT Gateway Is Not an Internet Gateway

Another important distinction:

## Internet Gateway

Connects the VPC with the internet routing environment.

## NAT Gateway

Translates addresses and allows resources such as private instances to establish outbound connectivity through the public network path.

A public NAT Gateway still depends on an Internet Gateway for internet-bound traffic in the architecture taught here.

Think of the chain as:

```text
Private EC2
    |
Private Route Table
    |
NAT Gateway
    |
Internet Gateway
    |
Internet
```

The NAT Gateway does not replace the Internet Gateway.

---

# 24. Correct NAT Gateway Placement

For the traditional zonal public NAT Gateway architecture, place the NAT Gateway in a public subnet.

Correct:

```text
VPC
|
├── Public Subnet
│      |
│      NAT Gateway
│      |
│      Route:
│      0.0.0.0/0 → IGW
│
└── Private Subnet
       |
       EC2
       |
       Route:
       0.0.0.0/0 → NAT Gateway
```

Incorrect conceptual design:

```text
Private Subnet
|
NAT Gateway
|
No path to Internet Gateway
```

The NAT Gateway needs a working internet path to provide internet access.

---

# 25. A Common Beginner Mistake

You create:

```text
Private EC2
```

Then create:

```text
NAT Gateway
```

Then wonder why nothing works.

Creating the NAT Gateway alone is not enough.

You need the complete chain.

Check each component:

```text
Private EC2
   |
Private subnet
   |
Private route table
   |
0.0.0.0/0 → NAT Gateway
   |
NAT Gateway
   |
Public subnet
   |
Public route table
   |
0.0.0.0/0 → Internet Gateway
   |
Internet Gateway attached to VPC
   |
Internet
```

One missing piece can break outbound connectivity.

---

# 26. NAT Gateway and Security Groups

A NAT Gateway itself does not use Security Groups in the same way an EC2 instance does.

Instead, control access through things such as:

* Security Groups attached to workloads
* Network ACLs
* Routing
* Application-level security
* Firewall services where required

Your EC2 Security Group must permit the required outbound traffic.

For example, if your private server must access HTTPS endpoints, an outbound rule might permit TCP port:

```text
443
```

to appropriate destinations.

Many beginner environments initially use broader outbound access, but production environments should apply restrictions based on actual requirements.

---

# 27. Network ACLs Can Still Block NAT Traffic

Even when your route tables are correct, Network ACLs can break connectivity.

Remember:

Security Groups are stateful.

Network ACLs are stateless.

If you use custom restrictive NACLs, you need to consider:

* Outbound traffic
* Return traffic
* Appropriate protocols
* Ephemeral ports

AWS specifically recommends checking both the private and public subnet NACLs when troubleshooting NAT internet connectivity.

This explains why:

```text
Route looks correct
```

does not always mean:

```text
network works
```

---

# 28. Single-AZ NAT Architecture

Start with the simplest architecture.

```text
Availability Zone A

Public Subnet A
     |
NAT Gateway A
     |
Internet Gateway

Private Subnet A
     |
EC2
```

Route:

```text
Private RT-A

10.0.0.0/16     local
0.0.0.0/0       NAT-A
```

This works for workloads in one Availability Zone.

But production environments often use multiple Availability Zones.

That changes the design decision.

---

# 29. Multi-AZ Architecture

Suppose your application uses:

```text
Availability Zone A
Availability Zone B
```

You might have:

```text
VPC: 10.0.0.0/16

AZ-A
├── Public Subnet A
└── Private Subnet A

AZ-B
├── Public Subnet B
└── Private Subnet B
```

A resilient zonal NAT architecture commonly looks like:

```text
                 Internet Gateway
                    /       \
                   /         \
              NAT-A         NAT-B
                |             |
          Public A        Public B
                |             |
          Private A       Private B
                |             |
              EC2-A          EC2-B
```

Each private subnet sends outbound traffic toward the NAT Gateway in its own Availability Zone.

AWS recommends this pattern for zonal NAT Gateways when Availability Zone resilience matters.

---

# 30. Why Not Share One Zonal NAT Gateway Across Every AZ?

Technically, resources from multiple Availability Zones can route through one zonal NAT Gateway.

For example:

```text
AZ-A Private
      \
       \
        NAT-A
       /
      /
AZ-B Private
```

But this introduces concerns.

## Availability concern

If Availability Zone A becomes unavailable and NAT-A exists only there, workloads in other zones that depend on NAT-A may lose that outbound path.

AWS specifically notes this risk.

## Cost concern

Cross-AZ traffic can introduce additional data-transfer charges.

AWS therefore recommends considering same-AZ routing or a NAT Gateway per Availability Zone for workloads generating significant traffic.

---

# 31. Per-AZ NAT Design

A cleaner traditional production pattern is:

```text
AZ-A

Private Subnet A
       |
       v
NAT Gateway A
       |
       v
Internet


AZ-B

Private Subnet B
       |
       v
NAT Gateway B
       |
       v
Internet
```

Route Table A:

```text
10.0.0.0/16     local
0.0.0.0/0       NAT-A
```

Route Table B:

```text
10.0.0.0/16     local
0.0.0.0/0       NAT-B
```

Now each Availability Zone has its own outbound NAT path.

---

# 32. Current AWS Note: Regional NAT Gateways

AWS now also supports regional NAT Gateways.

This is important because older AWS tutorials may only discuss zonal NAT Gateways.

A regional NAT Gateway can operate across multiple Availability Zones within a VPC and can automatically expand its footprint based on workloads. AWS also notes that regional public NAT Gateways do not require the traditional public-subnet placement model used by zonal public NAT Gateways.

For beginner learning, you should still understand the zonal model first:

```text
Private subnet
→ zonal NAT Gateway
→ public subnet
→ Internet Gateway
```

Why?

Because this teaches you:

* Routing
* Public vs private subnet design
* Availability Zone boundaries
* Elastic IP usage
* Egress architecture
* Failure-domain thinking

Once you understand that model, regional NAT Gateway becomes much easier to understand.

---

# 33. NAT Availability Considerations

AWS manages NAT Gateway infrastructure.

A zonal NAT Gateway is redundant within its Availability Zone.

But remember:

Redundant inside one AZ does not mean your architecture is automatically multi-AZ resilient.

If your entire design depends on:

```text
NAT Gateway A
```

and its Availability Zone becomes unavailable, another Availability Zone may still be running while lacking the expected outbound route.

Infrastructure engineers therefore think in terms of failure domains.

Ask:

```text
If AZ-A disappears, what stops working?
```

not merely:

```text
Is NAT Gateway managed by AWS?
```

---

# 34. NAT Gateway Cost Model

NAT Gateway is not free.

AWS currently charges for NAT Gateway usage based primarily on:

* Time the NAT Gateway is provisioned and available
* Amount of data processed through it

AWS documents both components in its NAT Gateway pricing guidance.

Exact dollar amounts can vary by Region and can change, so production engineers should check the current AWS pricing page for the Region they intend to use.

The important architecture lesson is:

Leaving NAT Gateways running continuously generates cost even if your lab is barely using them.

---

# 35. NAT Can Become an Unexpected Cost Center

Imagine:

```text
100 application servers
        |
        v
     NAT Gateway
        |
        v
   Large downloads
```

Every gigabyte moving through NAT contributes to processed-data usage.

Now imagine those servers constantly pulling:

* Container images
* Large packages
* S3 objects
* Software artifacts

The architecture may work perfectly while becoming unnecessarily expensive.

DevOps engineering requires thinking about both:

```text
Does it work?
```

and:

```text
Is this the right way to operate it?
```

Instead of:

```text

    |

    |
```

Conceptually:


This is a powerful production lesson:

Do not automatically send every outbound connection through NAT.

# 38. NAT Gateway Troubleshooting Mindset

When internet connectivity fails, beginners often start randomly changing settings.

Do not do that.

Troubleshoot the path.

Use this sequence:

```text
1. Does the EC2 instance work?
2. Does it have a valid private IP?
3. Is its Security Group allowing required outbound traffic?
4. Which subnet is it in?
5. Which route table is associated with that subnet?
6. Does 0.0.0.0/0 point to the NAT Gateway?
7. Is the NAT Gateway available?
8. Is it correctly configured for public connectivity?
9. Can the NAT Gateway reach the Internet Gateway?
10. Is the Internet Gateway attached?
11. Are NACLs blocking traffic?
12. Is DNS working?
13. Is the remote destination itself available?
```

Follow the packet.

---

# 39. Problem: NAT Gateway Shows Failed

Suppose you create a NAT Gateway and its state becomes:

```text
Failed
```

Do not immediately delete everything.

Check the NAT Gateway state message.

AWS lists possible causes such as:

* Insufficient available subnet addresses
* Internet Gateway-related configuration problems
* Invalid Elastic IP allocation
* Resource association problems
* Invalid subnet
* Internal service errors

AWS also notes that failed NAT Gateways are normally removed automatically after a period of time.

Troubleshooting principle:

Read the service's error state before rebuilding infrastructure.

---

# 40. Problem: EC2 Cannot Reach the Internet

You SSH or connect through Systems Manager to the private instance and run:

```bash
curl https://example.com
```

The connection hangs.

Possible causes include:

* NAT Gateway is unavailable
* Wrong route table
* Private subnet associated with wrong route table
* NAT placed/configured incorrectly
* Public subnet lacks Internet Gateway route
* Internet Gateway not attached
* Security Group blocks outbound traffic
* NACL blocks traffic
* DNS failure
* Remote endpoint failure

AWS recommends checking these same routing and security layers when private instances cannot reach the internet through NAT.

---

# 41. Check the Private Route Table

Expected:

```text
Destination       Target

10.0.0.0/16       local
0.0.0.0/0         nat-xxxxxxxx
```

A common mistake is:

```text
0.0.0.0/0 → igw-xxxxxxxx
```

on the private route table.

That is not the NAT architecture we are building.

Another mistake:

```text
0.0.0.0/0 → wrong NAT Gateway
```

Always inspect actual route-table associations.

Do not assume the subnet uses the route table whose name looks correct.

---

# 42. Check the Public Route Table

Expected:

```text
Destination       Target

10.0.0.0/16       local
0.0.0.0/0         igw-xxxxxxxx
```

If the NAT Gateway cannot reach the Internet Gateway, private EC2 traffic stops there.

Think of the path as a chain.

```text
EC2 ✓
 |
Route ✓
 |
NAT ✓
 |
Public route ✗
 |
Internet
```

One failure breaks the complete flow.

---

# 43. Check NAT Gateway State

The NAT Gateway should normally show:

```text
Available
```

If it says:

```text
Pending
```

it may not yet be ready.

If it says:

```text
Failed
```

inspect the failure details.

AWS specifically recommends confirming the `Available` state when diagnosing failed internet connectivity.

---

# 44. Check Security Group Egress

Suppose your EC2 Security Group permits:

```text
Outbound:
TCP 443
```

Your HTTPS request may work.

But:

```bash
ping 8.8.8.8
```

may fail because ping uses ICMP, not TCP 443.

Do not conclude:

"NAT is broken."

Your test method may simply use a protocol your policy does not allow.

---

# 45. Do Not Depend Only on Ping

Ping can be useful, but it is not a complete internet test.

Some internet systems intentionally reject ICMP.

AWS warns about this during NAT troubleshooting.

Better tests include:

```bash
curl -I https://example.com
```

or:

```bash
curl https://checkip.amazonaws.com
```

The second type of test can also show the public source IP that the external service sees.

---

# 46. Verify the NAT Public IP

From the private EC2 instance, you can use a service that reports your source IP.

For example:

```bash
curl https://checkip.amazonaws.com
```

Expected conceptually:

```text
198.51.100.50
```

That should correspond to the internet-facing address being used by your NAT architecture.

AWS recommends this general technique when testing public NAT Gateway connectivity.

# 47. Traceroute Can Help, But Interpret It Carefully

On Linux:

```bash

```

If `traceroute` is not installed:

Ubuntu/Debian:

```bash

```

Amazon Linux/RHEL-family systems may use:

```bash

```

or on older distributions:

```bash

```

AWS notes that traceroute from a private instance can help confirm the NAT path and may show the NAT Gateway's private address as an early hop.

# 48. Problem: DNS Fails

Suppose:

```bash
curl https://example.com
```

fails.

But:

```bash
curl https://93.184.216.34
```

produces some network response.

That suggests your problem may involve DNS rather than NAT itself.

Check:

```bash
cat /etc/resolv.conf
```

Then:

```bash
nslookup example.com
```

or:

```bash
dig example.com
```

Troubleshooting lesson:

"Cannot access website" is a symptom.

It does not identify the broken layer.

---

# 49. Problem: HTTP Works but HTTPS Does Not

If:

```bash
curl http://example.com
```

works

but:

```bash
curl https://example.com
```

fails,

investigate:

* TCP 443 outbound rules
* NACL rules
* TLS issues
* Proxy settings
* Remote service behavior

Do not rebuild the NAT Gateway before checking the evidence.

---

# 50. Problem: Some Destinations Work and Others Fail

If the private EC2 instance can reach:

```text
Site A
Site B
```

but not:

```text
Site C
```

the NAT Gateway itself may be working.

Investigate:

* Destination firewall rules
* Destination IP allowlists
* Protocol behavior
* DNS
* MTU/fragmentation
* Application restrictions

AWS documents certain special cases involving fragmented traffic and remote TCP behavior that can affect NAT connections.

This is an important troubleshooting principle:

Partial connectivity is evidence.

Use it.

---

# 51. Connection Scaling

NAT Gateway can support large numbers of connections, but it is not unlimited.

AWS documents per-destination concurrent-connection considerations and supports additional addresses as one method of increasing connection capacity.

Most beginners will not encounter these limits.

But production engineers should know they exist.

Symptoms can include:

* New connections failing
* Existing connections remaining active
* Failures concentrated toward one destination

At scale, networking capacity becomes an operational consideration.

---

# 52. NAT Gateway Monitoring

Do not wait until an outage to inspect NAT behavior.

CloudWatch exposes NAT Gateway metrics that can help investigate things such as:

* Traffic volume
* Connection attempts
* Connection errors
* Packet drops
* Idle connection timeouts

One metric AWS specifically references during NAT troubleshooting is:

```text
IdleTimeoutCount
```

which can help identify idle-connection behavior.

We will cover CloudWatch much more deeply later.

# 53. VPC Flow Logs

VPC Flow Logs can help investigate network traffic.

They can provide evidence about:

* Source address
* Destination address
* Ports
* Protocol
* Accepted traffic
* Rejected traffic

Suppose:

```text
Private EC2
→ NAT Gateway
```

does not work.

Flow logs can help determine whether traffic is being rejected by network controls.

AWS recommends Flow Logs as one troubleshooting aid for NAT-related connectivity problems.

# 54. Troubleshooting Framework

Use this method whenever the NAT path fails.

## Observe

Example:

```text
apt update hangs
```

## Define the symptom

Is it:

```text
DNS failure?
Timeout?
Connection refused?
TLS failure?
Routing failure?
```

## Check the simplest layer

Can EC2 communicate within the VPC?

## Inspect routing

Which route table is actually attached?

## Inspect NAT

Is it available?

## Inspect public routing

Can NAT reach the IGW?

## Inspect security

Security Groups and NACLs.

## Test DNS

Does the hostname resolve?

## Test another destination

Determine whether the problem is universal.

## Verify after fixing

Repeat the original command.

Do not consider a change successful until the original symptom disappears.

# 75. Break the Lab Intentionally

Do not stop after making it work.

Now learn troubleshooting.

Remove the private route:

```text
0.0.0.0/0 → NAT Gateway
```

Then run:

```bash
curl -I https://example.com
```

It should fail.

Ask:

Why?

Because the private subnet no longer has a matching path for internet-bound traffic.

Restore the route.

Test again.

This teaches more than simply copying configuration.

# 76. Break the Public Route

Temporarily remove:

```text
0.0.0.0/0 → Internet Gateway
```

from the NAT Gateway's public subnet route table.

Test again from the private EC2 instance.

The private route still points to the NAT Gateway.

But the NAT Gateway no longer has the expected internet path.

The connection fails.

Restore the route.

Now you understand why both route tables matter.

# 77. Inspect the Route Instead of Guessing

From the Linux server:

```bash
ip route
```

You may see something similar to:

```text
default via 10.0.2.1 dev eth0
10.0.2.0/24 dev eth0
```

Do not expect Linux itself to display:

```text
NAT Gateway
```

The operating system sends traffic to the VPC networking layer.

AWS then applies subnet route-table logic.

Understanding which layer owns which routing decision prevents confusion.

Putting a zonal public NAT Gateway in a subnet without an Internet Gateway route.


in the private route table.

## Mistake 4

Giving the private EC2 instance a public IP unnecessarily.

Routing the private subnet directly to the Internet Gateway and assuming NAT is still being used.

Sharing a single zonal NAT Gateway across several Availability Zones without considering availability and cross-AZ traffic.

Assuming Security Groups are irrelevant because routing looks correct.

## Mistake 8

Using ping as the only test.

## Mistake 9

Leaving expensive lab infrastructure running after practice.

Sending large volumes of AWS-service traffic through NAT without considering VPC endpoints.


This separation is fundamental to production VPC architecture.

# 86. Final Mental Model

Do not memorize NAT Gateway as:

"NAT Gateway gives private EC2 internet."

Understand the complete mechanism:

```text
PRIVATE SERVER
10.0.2.25
      |
      | wants internet destination
      v
PRIVATE ROUTE TABLE
0.0.0.0/0 → NAT
      |
      v
NAT GATEWAY
translate private source
      |
      v
PUBLIC NETWORK PATH
      |
      v
INTERNET GATEWAY
      |
      v
INTERNET
      |
      | response
      v
NAT GATEWAY
recognizes established flow
      |
      v
PRIVATE EC2
```

And remember the most important principle:

Private does not mean disconnected.

Private means you deliberately control how the resource communicates.

A well-designed private workload does not need to expose itself directly to the internet simply because it needs software updates or outbound connectivity.

That distinction is one of the foundations of secure AWS networking.
