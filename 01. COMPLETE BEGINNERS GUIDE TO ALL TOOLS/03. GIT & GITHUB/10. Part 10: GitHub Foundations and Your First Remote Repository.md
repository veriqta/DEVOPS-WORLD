# 1. Git and GitHub Are Not the Same Thing

This distinction is essential.

Git is a version control system.

GitHub is a platform that hosts Git repositories and adds collaboration, project-management, security, automation, and other development features around them.

You can use Git without GitHub.

For example:

```text
Laptop
 |
 v
Git repository
 |
 v
Commits
```

That repository can exist entirely on your computer.

Git does not require:

```text
GitHub
Internet access
A GitHub account
A web browser
```

for normal local operations such as:

```bash
git init
git status
git add
git commit
git branch
git switch
git merge
git log
```

These are Git operations.

# 3. Git Came Before GitHub

Git is not a GitHub product.

Git is an independent distributed version control system.

This matters because beginners sometimes assume commands such as:

```bash
git commit
```

send information to GitHub.

They do not.

A command like:

```bash
git commit -m "Add login validation"
```

creates a commit in your local Git repository.

It does not automatically upload that commit anywhere.

# 4. Local Commit vs GitHub

Suppose your local history is:

```text
A -> B -> C
          ^
          |
         main
```

You create another commit:

```text
A -> B -> C -> D
               ^
               |
              main
```

Commit D exists locally.

GitHub does not automatically know about D.

Your local repository and GitHub repository can have different states.

To send commits to GitHub, you normally use:

```bash
git push
```

We will examine that carefully later.

# 15. Public vs Private Repositories

When creating a GitHub repository, one of the most important decisions is visibility.

For personal repositories, the two beginner-relevant choices are:

```text
Public

```

---

# 16. Public Repository

A public repository is accessible to people on the internet.

This is useful for:

* Open-source projects
* Public portfolios
* Tutorials
* Example projects
* Public documentation
* Community projects

For example:

```text
Public Repository
       |
       v
Anyone can view
```

However, public does not mean anyone can freely push changes into your repository.

Viewing access and write access are different things.

---

# 17. Private Repository

A private repository restricts repository access to authorized users.

This is commonly appropriate for:

* Proprietary company code
* Internal infrastructure
* Private projects
* Early-stage work
* Sensitive business logic
* Internal automation

Conceptually:

```text
Private Repository
        |
        v
Authorized users
```

---

# 18. Private Does Not Mean Secrets Are Safe to Commit

This deserves special attention.

Do not think:

```text
Repository is private
therefore
I can commit passwords.
```

That is unsafe.

Do not intentionally commit:

```text
Passwords
API keys
Access tokens
Cloud credentials
Private SSH keys
Database passwords
Production secrets
.env files containing secrets
```

even simply because the repository is private.

Private repositories still require proper secret management.

# 28. .gitignore Basics

You learned earlier that Git does not need to track every file.

A `.gitignore` file tells Git which untracked paths should normally be ignored.

Example:

```gitignore
.env
*.log
node_modules/
__pycache__/
```

This might tell Git to ignore:

```text
.env

files ending in .log

node_modules directory

Python __pycache__ directories
```

---

# 29. Why .gitignore Matters

Projects often generate files that should not belong in normal version history.

Examples:

```text
Temporary files
Build output
Dependency directories
IDE metadata
Operating-system files
Log files
Local environment files
Some generated files
```

A `.gitignore` helps prevent accidental tracking of these files.

---

# 30. .gitignore Is Not a Secret Vault

Suppose:

```text
.env
```

contains:

```text
DATABASE_PASSWORD=super-secret-password
```

Adding:

```gitignore
.env
```

is useful before the file is tracked.

But `.gitignore` is not a security mechanism for removing a secret that was already committed.

If a credential has been committed, you may need to:

* Remove it appropriately
* Rotate the credential
* Investigate exposure
* Potentially clean repository history

Never assume:

```text
I added it to .gitignore,
so the old secret disappeared.
```

It did not.

# 34. Repository URLs

A GitHub repository has a location that Git can use to communicate with it.

GitHub supports repository URLs such as HTTPS and SSH URLs.

Conceptually:

```text
Repository URL
=
Address Git uses to locate remote repository
```

For example, an HTTPS URL has a structure similar to:

```text
https://github.com/USERNAME/REPOSITORY.git
```

An SSH URL looks similar to:

```text
git@github.com:USERNAME/REPOSITORY.git
```

Replace the placeholders with actual values.

---

# 35. HTTPS Repository URL

Example structure:

```text
https://github.com/your-username/devops-git-lab.git
```

Break it down:

```text
https://
```

indicates HTTPS.

```text
github.com
```

is the host.

```text
your-username
```

identifies the owner.

```text
devops-git-lab.git
```

identifies the repository.

---

# 36. SSH Repository URL

An SSH-style GitHub URL looks like:

```text
git@github.com:your-username/devops-git-lab.git
```

This uses SSH-based authentication.

To use SSH properly, your machine needs appropriate SSH key configuration.

We will cover that deeply in Part 11.

---

# 37. HTTPS vs SSH

Both can be used to communicate with GitHub repositories.

HTTPS looks like:

```text
https://github.com/USER/REPO.git
```

SSH looks like:

```text
git@github.com:USER/REPO.git
```

The main difference for beginners is authentication and connection setup.

---

# 38. HTTPS Authentication

With HTTPS, Git communicates with GitHub over HTTPS.

For authenticated command-line operations, modern GitHub workflows do not use your normal GitHub account password as the Git password.

Authentication may involve mechanisms such as:

* Credential managers
* Personal access tokens
* GitHub CLI-assisted authentication

The exact setup depends on your environment.

Part 11 will cover authentication in detail.

---

# 39. SSH Authentication

With SSH, authentication uses cryptographic keys.

Conceptually:

```text
Your computer
     |
     | Private key
     |
     v
SSH authentication
     |
     v
GitHub
     |
     | Matches public key
     |
     v
Access decision
```

Your private key stays private.

The corresponding public key can be added to your GitHub account.

Again, Part 11 will build this from the ground up.

# 40. Which One Should a Beginner Use?

Both are legitimate.

HTTPS can be convenient for beginners, particularly when paired with a credential manager.

SSH is extremely common in engineering environments and is valuable to understand.

For this part, you may use whichever authentication method you already have configured.

If you have not configured either one successfully yet, focus on understanding the remote model first.

# 41. What Is a Git Remote?

A remote is a named reference in your local Git repository that stores information about another repository.

This is important.

The remote is not the GitHub repository itself.

It is local configuration describing how Git can reach another repository.

Conceptually:

```text
LOCAL REPOSITORY

Remote name:
origin

Remote URL:
https://github.com/user/project.git

               |
               v

GITHUB REPOSITORY
```

---

# 42. Why Give Remotes Names?

Imagine typing the complete repository URL every time:

```bash
git fetch https://github.com/your-username/project.git
```

Possible, but inconvenient.

Instead, Git lets you associate a name with the location.

For example:

```text
origin
=
https://github.com/your-username/project.git
```

Then you can use:

```bash
git fetch origin
```

The short name is easier to use.

---

# 43. git remote

Run:

```bash
git remote
```

This lists configured remote names.

If your repository has no remotes, the command may display nothing.

That is normal.

Your local Git repository can exist perfectly well without a remote.

# 44. git remote -v

Run:

```bash
git remote -v
```

The `-v` option means verbose.

Example:

```text

origin  https://github.com/your-username/devops-git-lab.git (push)
```

You see two operations:

```text
fetch
push
```

In a simple setup, both normally use the same repository URL.

# 45. What Does origin Mean?

`origin` is a conventional remote name.

It is not a special GitHub server.

It is not a branch.

It is not your GitHub account.

It is not automatically the internet.

It is simply a name commonly used for a remote repository.

Think:

```text
origin
=
nickname for a remote repository location
```

---

# 46. Could You Call It Something Else?

Yes.

You could technically run:

```bash
git remote add github https://github.com/your-username/project.git
```

Then:

```bash
git remote
```

might show:

```text
github
```

You could then use:

```bash
git fetch github
```

or:

```bash
git push github main
```

But `origin` is the conventional default name and is what you will see in most workflows.

---

# 47. Why origin Appears So Often

When you clone a repository, Git normally creates a remote named:

```text
origin
```

pointing to the repository you cloned.

This is why commands such as:

```bash
git push origin main
```

are so common.

But remember:

```text
origin
```

is a remote name, not a magical keyword meaning GitHub.

# 48. Adding a Remote

Suppose your GitHub repository URL is:

```text
https://github.com/your-username/devops-git-lab.git
```

Run:

```bash
git remote add origin https://github.com/your-username/devops-git-lab.git
```

Break it down.

```text
git
```

runs Git.

```text
remote
```

manages remote repository configuration.

```text
add
```

creates a new remote entry.

```text
origin
```

is the name you are assigning.

```text
https://github.com/your-username/devops-git-lab.git
```

is the remote repository URL.

---

# 49. What git remote add Does

This command:

```bash
git remote add origin <REMOTE_URL>
```

does not:

* Upload your files
* Push commits
* Create a GitHub repository
* Merge histories
* Change your project files

It configures your local repository to know:

```text
Remote named origin
is located at
REMOTE_URL
```

That is all.

---

# 50. Verify the Remote

After adding it:

```bash
git remote -v
```

Expected structure:

```text
origin  <REMOTE_URL> (fetch)
origin  <REMOTE_URL> (push)
```

Always verify the URL before pushing.

Why?

Because you do not want to accidentally push a project to the wrong remote repository.

---

# 51. Inspecting a Remote

You can also use:

```bash
git remote show origin
```

This can display more information about the remote and tracked branches.

At this stage, remember:

```text
git remote
```

lists remote names.

```text
git remote -v
```

shows names and URLs.

```text
git remote show origin
```

provides more detailed information.

---

# 52. Removing an Incorrect Remote

Suppose you accidentally add the wrong repository:

```bash
git remote add origin https://github.com/your-username/wrong-project.git
```

You can remove the remote configuration:

```bash
git remote remove origin
```

Then verify:

```bash
git remote -v
```

This removes the remote association from the local repository.

It does not delete the GitHub repository.

---

# 53. Changing a Remote URL

If `origin` exists but points to the wrong URL, you can change it:

```bash
git remote set-url origin <NEW_URL>
```

Then verify:

```bash
git remote -v
```

This is also useful if you later change from HTTPS to SSH.

For example:

```text
HTTPS
   |
   v
Change remote URL
   |
   v
SSH
```

# 54. Local Repository and Remote Repository Are Separate

Suppose:

```text
LOCAL

A -> B -> C
```

and GitHub contains:

```text
REMOTE

A -> B
```

Your local repository is one commit ahead.

Commit C does not exist remotely yet.

The repositories are related, but they are separate.

This is one of the most important mental models in Git.

Beginner version:

```text
=
```

Conceptually:

```text
LOCAL

A -> B -> C
          |
          | git push
          v
REMOTE

A -> B -> C
```

```text
main
```

---

# 57. Push Does Not Mean Save

This distinction is essential.

Saving a file:

```text
Editor
 |
 v
Working Directory
```

Staging:

```bash
git add file
```

moves selected content into the proposed next snapshot.

Committing:

```bash
git commit
```

creates local history.

Pushing:

```bash
git push
```

publishes appropriate local Git history to a remote repository.

The complete sequence is:

```text
EDIT
 |
 v
SAVE
 |
 v
git add
 |
 v
STAGE
 |
 v
git commit
 |
 v
LOCAL COMMIT
 |
 v
git push
 |
 v
REMOTE REPOSITORY
```

---

# 58. A Push Does Not Automatically Include Uncommitted Work

Suppose:

```bash
git status
```

shows:

```text
Changes not staged for commit:
    modified: app.py
```

Then you run:

```bash
git push
```

That uncommitted modification is not magically uploaded as a commit.

Push works with Git history and references.

If the change has not been committed, it is not part of the branch's commit history to push.

# 59. First Push and Upstream Tracking

For a new local branch, you may see:

```bash
git push -u origin main
```

The `-u` is shorthand for:

```text
--set-upstream
```

A fuller version is:

```bash
git push --set-upstream origin main
```

This pushes `main` and configures an upstream relationship for the local branch.

---

# 60. What Is an Upstream Branch?

An upstream branch is the remote-tracking relationship your local branch uses by default for operations such as push and pull.

Conceptually:

```text
LOCAL BRANCH

main
 |
 | tracks
 v
origin/main

REMOTE-TRACKING REFERENCE
```

After:

```bash
git push -u origin main
```

Git knows that local:

```text
main
```

is associated with:

```text
origin/main
```

for normal synchronization workflows.

---

# 61. origin/main Is Not the Same as main

This is very important.

```text
main
```

is your local branch.

```text
origin/main
```

is a remote-tracking reference in your local repository representing your knowledge of the `main` branch at `origin`.

Think:

```text
main
=
my local branch

origin/main
=
my local record of origin's main branch
```

We will explore remote-tracking branches more deeply in Part 12.

# 67. git fetch Downloads Remote Information

A common command is:

```bash

```

Beginner mental model:

```text

   |
   | git fetch
   v
UPDATE MY KNOWLEDGE
OF REMOTE HISTORY
```

It does not automatically merge those changes into your current local branch.

This is a crucial safety property.

# 74. What Is git pull?

`git pull` retrieves changes from another repository and then integrates them into your current branch according to the configured pull behavior.

Beginner mental model:

```text
git pull
=
Get remote changes
+
Integrate them locally
```

A simplified model is often:

```text
git pull
     |
     +--> fetch
     |
     +--> integrate
```

For a beginner using a merge-based pull workflow, you can initially think:

```text
git pull
≈
git fetch
+
git merge
```

But Git can also be configured to use other integration strategies such as rebase, so do not treat that approximation as a universal internal law.

---

# 75. Fetch vs Pull

This distinction is fundamental.

```text
git fetch
```

retrieves remote changes without automatically changing your current local branch.

```text
git pull
```

retrieves remote changes and attempts to integrate them into your current branch.

Think:

```text
FETCH

Remote
  |
  v
Remote-tracking reference

Local branch remains where it is
```

versus:

```text
PULL

Remote
  |
  v
Fetch
  |
  v
Integrate
  |
  v
Local branch updated
```

---

# 76. Why Beginners Should Understand Fetch First

`git pull` is convenient.

But if you only memorize:

```bash
git pull
```

without understanding fetch and integration, remote synchronization can feel mysterious.

Understanding:

```text
Remote repository
        |
        v
git fetch
        |
        v
origin/main
        |
        v
integration
        |
        v
main
```

gives you a stronger mental model.

# 80. A More Complete Local/Remote Model

You now need to expand your Git mental model.

Previously:

```text
Working Directory
       |
       v
Staging Area
       |
       v
Local Repository
```

Now:

```text

       |
       | git add
       v
Staging Area
       |
       | git commit
       v
Local Repository
       |
       | git push
       v
Remote Repository
       ^
       |
       | git fetch / git pull
       |

```

# 81. Commands Operate at Different Layers

Consider:

```bash

```

primarily affects:

```text
Working Directory -> Staging Area
```

```bash

```

records staged content in:

```text
Local Repository
```

```bash
git push
```

communicates:

```text
Local Repository -> Remote Repository
```

```bash
git fetch
```

communicates:

```text
Remote Repository -> Local repository's remote-tracking knowledge
```

```bash
git pull
```

retrieves and integrates remote changes.

Knowing which layer a command affects prevents many beginner mistakes.

# 126. Push Rejection Example


Git may reject the update because blindly moving remote `main` to L could discard R from the branch history.

That rejection is useful.

It is protecting shared work.

# 129. Remote-Tracking Branches

When Git communicates with a remote, it maintains references such as:

```text
origin/main
```

These are called remote-tracking branches or remote-tracking references.

They represent Git's local knowledge of remote branches.

Important:

```text
origin/main
```

is stored locally.

It is not a live network connection.

It updates when you perform operations such as:

```bash
git fetch
```

or other commands that fetch remote information.

---

# 130. Why origin/main Can Become Stale

Suppose GitHub's `main` advances:

```text
REMOTE

A -> B -> C -> D
```

But you have not fetched recently.

Your local repository may still show:

```text
origin/main -> C
```

Your local `origin/main` is your last known state, not necessarily the remote's exact current state.

After:

```bash
git fetch origin
```

it can update:

```text
origin/main -> D
```

This is an extremely important mental model.

# 144. Part 10 Final Recap

Until this part, your Git world mostly ended here:

```text
Working Directory
       |
       v
Staging Area
       |
       v
Local Repository
```

Now the model expands:

```text
Working Directory
       |
       | git add
       v
Staging Area
       |
       | git commit
       v
Local Repository
       |
       | git push
       v
Remote Repository
       |
       v
GitHub
```

And information also flows back:

```text
GitHub
   |
   | git fetch
   v
Remote-Tracking References
   |
   v
Inspect / Integrate
   |
   v
Local Branch
```

The most important distinction is:

```text
Git
!=
GitHub
```

Git handles version control.

GitHub hosts Git repositories and provides a collaboration platform around them.

You learned that:

```text
git commit
```

does not mean:

```text
upload to GitHub
```

Instead:

```text
SAVE FILE
    |
    v
git add
    |
    v
STAGING AREA
    |
    v
git commit
    |
    v
LOCAL HISTORY
    |
    v
git push
    |
    v
REMOTE HISTORY
```

You also learned:

```text
origin
```

is not GitHub itself.

It is simply a conventional remote name.

For example:

```text
origin
   |
   v
https://github.com/user/project.git
```

You learned that:

```bash
git remote add origin <URL>
```

connects a remote name with a repository location.

It does not upload anything.

Then:

```bash
git push -u origin main
```

can publish your local branch and establish an upstream relationship.

You learned to distinguish:

```text
main
```

from:

```text
origin/main
```

where:

```text
main
=
your local branch
```

and:

```text
origin/main
=
your local repository's remote-tracking knowledge
of origin's main branch
```

You also learned the crucial difference between:

```bash
git fetch
```

and:

```bash
git pull
```

Think:

```text
FETCH
=
GET REMOTE INFORMATION
WITHOUT AUTOMATICALLY INTEGRATING
IT INTO MY CURRENT BRANCH
```

while:

```text
PULL
=
GET REMOTE INFORMATION
+
INTEGRATE IT
```

according to the configured pull behavior.

Your complete mental model should now look like:

```text
                 GITHUB
             Remote Repository
                ^       |
                |       |
          git push      | git fetch
                |       |
                |       v
             LOCAL GIT
                ^
                |
           git commit
                |
          STAGING AREA
                ^
                |
            git add
                |
         WORKING DIRECTORY
```

This is the foundation of collaborative Git.

But one major problem remains.

Your computer now needs to prove to GitHub:

```text
Who are you?

Are you allowed to access this repository?

Are you allowed to push?

How can GitHub authenticate this machine securely?
```

That introduces authentication.

In Part 11, you will learn **Authentication, SSH Keys, and Secure GitHub Access**, including HTTPS authentication, personal access tokens, SSH fundamentals, public and private keys, `ssh-keygen`, the `~/.ssh` directory, SSH agents, adding keys to GitHub, testing connections, protecting private keys, and troubleshooting errors such as:

```text
Permission denied (publickey)
```

That will turn the remote model you learned here into a properly authenticated GitHub workflow.
