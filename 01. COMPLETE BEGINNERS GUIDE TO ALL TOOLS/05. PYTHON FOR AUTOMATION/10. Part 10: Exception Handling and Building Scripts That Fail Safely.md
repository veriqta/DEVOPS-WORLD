# Part 10: Exception Handling and Building Scripts That Fail Safely

In the previous parts, you learned how to build increasingly capable Python automation.

You can now work with:

* Variables.
* Strings.
* Collections.
* Conditions.
* Loops.
* Functions.
* Modules.
* Standard-library tools.
* Virtual environments.
* External dependencies.

But there is an important problem.

Real systems fail.

A file may not exist.

A configuration file may contain invalid JSON.

A user may enter:

```text
abc
```

when your program expects:

```text
80
```

A directory may exist, but your process may not have permission to read it.

An API may return:

```text
500 Internal Server Error
```

A server may stop responding.

A Linux command may return a non-zero exit code.

DNS may fail.

A network connection may time out.

A package may receive unexpected data.

If your automation assumes that everything will always work, it is not production-ready automation.

A useful mental model is:

```text
Automation
    |
    v
Perform operation
    |
    +---- Success ----> Continue
    |
    +---- Failure ----> Understand failure
                            |
                            v
                       Handle safely
                            |
             +--------------+--------------+
             |              |              |
             v              v              v
           Retry          Report        Stop safely
```

The goal of exception handling is not:

```text
Prevent every error.
```

That is impossible.

The goal is:

```text
Detect failures.
Understand them.
Handle expected failures.
Preserve useful evidence.
Protect data and systems.
Stop safely when continuing would be dangerous.
```

By the end of this part, you should be able to design Python automation that fails deliberately and clearly rather than crashing unpredictably or hiding important problems.

---

# 1. What Is an Error?

An error is a problem that prevents your program from behaving as intended.

Consider:

```python
print("Checking server")
```

This works.

But:

```python
print("Checking server"
```

does not.

Or:

```python
port = int("HTTPS")
```

The syntax is valid, but Python cannot convert:

```text
HTTPS
```

into an integer.

These are different categories of failure.

Understanding that distinction is essential for troubleshooting.

---

# 2. Two Important Categories

At this stage, distinguish between:

```text
Syntax errors
```

and:

```text
Runtime errors
```

Conceptually:

```text
Python program
     |
     v
Can Python understand the syntax?
     |
  +--+--+
  |     |
 No    Yes
  |     |
  v     v
Syntax  Start running
Error       |
            v
       Something fails
            |
            v
       Runtime error
```

---

# 3. What Is a Syntax Error?

A syntax error means Python cannot correctly parse the code according to Python's grammar.

Example:

```python
print("Checking server"
```

A closing parenthesis is missing.

Python cannot correctly interpret the statement.

You may see an error such as:

```text
SyntaxError
```

---

# 4. Another Syntax Error

Consider:

```python
if server_status == "healthy"
    print("Server is healthy")
```

The colon is missing after the condition.

Correct:

```python
if server_status == "healthy":
    print("Server is healthy")
```

The first version does not represent valid Python syntax.

---

# 5. Syntax Errors Usually Happen Before Normal Execution

Suppose:

```python
print("Starting")

if status == "healthy"
    print("Healthy")
```

Python must first parse the source code.

Because the syntax is invalid, normal execution cannot proceed as intended.

This is different from a problem that appears only after valid code begins running.

---

# 6. What Is a Runtime Error?

A runtime error happens while syntactically valid code is executing.

Example:

```python
port = int("HTTPS")
```

Python understands the syntax.

It begins execution.

Then it tries:

```python
int("HTTPS")
```

and discovers that the string cannot be converted to an integer.

You receive:

```text
ValueError
```

This is a runtime failure.

---

# 7. Syntax vs Runtime

Compare:

```python
print("Hello"
```

This is a syntax problem.

But:

```python
number = int("hello")
```

is syntactically valid.

It fails during execution.

So:

```text
Syntax error
=
Python cannot correctly parse the code.

Runtime error
=
Python understood the code,
started executing it,
and something failed during execution.
```

---

# 8. What Is an Exception?

An exception is an object representing an error or unusual condition that interrupts the normal flow of execution.

For example:

```python
number = int("abc")
```

raises:

```text
ValueError
```

Conceptually:

```text
Normal execution
      |
      v
int("abc")
      |
      v
Operation cannot continue normally
      |
      v
ValueError is raised
      |
      v
Normal flow is interrupted
```

If the exception is not handled, Python normally stops the program and prints a traceback.

---

# 9. Exceptions Are Not Just Error Messages

This distinction matters.

When Python shows:

```text
ValueError: invalid literal for int()...
```

the exception is not merely the text on your screen.

`ValueError` is an exception type.

The exception object can contain information describing the failure.

Python's exception system allows your program to react differently to different categories of failure.

For example:

```text
FileNotFoundError
```

can be handled differently from:

```text
PermissionError
```

because they represent different problems.

---

# 10. Why Exceptions Matter in Automation

Imagine an infrastructure script that:

1. Reads server configuration.
2. Calls an API.
3. Runs health checks.
4. Generates a report.
5. Sends an alert.

Many things can fail:

```text
Read configuration
      |
      +--> file missing
      +--> permission denied
      +--> invalid JSON
      |
      v
Call API
      |
      +--> DNS failure
      +--> timeout
      +--> authentication failure
      +--> server error
      |
      v
Run command
      |
      +--> executable missing
      +--> non-zero exit
      +--> timeout
      |
      v
Write report
      |
      +--> directory missing
      +--> disk issue
      +--> permission denied
```

Production automation must decide what each failure means.

---

# 11. Not Every Failure Should Be Handled the Same Way

Suppose:

```text
Optional report file missing
```

Maybe the script can continue.

But:

```text
Production configuration missing
```

may require immediate termination.

Likewise:

```text
One server unreachable
```

might mean:

```text
Record failure and continue checking other servers.
```

But:

```text
Authentication credentials invalid
```

might mean:

```text
Stop immediately.
```

Good exception handling requires context.

# 12. What Is a Traceback?

When an unhandled exception occurs, Python normally displays a traceback.

A traceback shows the chain of function calls that led to the failure.

Example:

```python
def convert_port(value):
    return int(value)


def load_port():
    return convert_port("HTTPS")


load_port()
```

This eventually raises:

```text
ValueError
```

Python may display a traceback containing several lines.

---

# 13. A Simplified Traceback

It may conceptually resemble:

```text
Traceback (most recent call last):
  File "app.py", line 9, in <module>
    load_port()

  File "app.py", line 6, in load_port
    return convert_port("HTTPS")

  File "app.py", line 2, in convert_port
    return int(value)

ValueError: invalid literal for int() with base 10: 'HTTPS'
```

The exact formatting can vary.

---

# 14. Read the Bottom First

For beginners, a useful strategy is to begin at the bottom.

The bottom tells you:

```text
Exception type
+
exception message
```

For example:

```text
ValueError:
invalid literal for int() with base 10: 'HTTPS'
```

This tells you that Python attempted an invalid integer conversion.

Then work upward to understand where it happened.

---

# 15. Reading a Traceback Step by Step

Given:

```text
Traceback (most recent call last):

File "app.py", line 9, in <module>
    load_port()

File "app.py", line 6, in load_port
    return convert_port("HTTPS")

File "app.py", line 2, in convert_port
    return int(value)

ValueError: ...
```

Read it as:

```text
Program called load_port()
        |
        v
load_port() called convert_port()
        |
        v
convert_port() called int(value)
        |
        v
int() received invalid text
        |
        v
ValueError
```

The traceback is evidence.

Do not treat it as noise.

---

# 16. Tracebacks Tell a Story

Suppose an automation project contains:

```text
main.py
config.py
health.py
api.py
```

A traceback may cross several modules.

Conceptually:

```text
main.py
   |
   v
health.py
   |
   v
api.py
   |
   v
external library
   |
   v
exception
```

This tells you how execution reached the failure.

---

# 17. Do Not Hide Tracebacks Before Understanding Them

Beginners sometimes see a large traceback and immediately try to suppress it.

That is often the wrong response.

A traceback can tell you:

* Which file failed.
* Which line failed.
* Which function was executing.
* Which function called it.
* Which exception occurred.
* What message accompanied it.

Before handling an exception, understand what it means.

# 19. `ValueError`

Example:

```python
port = int("HTTPS")
```

The type of operation is valid:

```text
int(...)
```

but the supplied value is unsuitable.

Therefore:

```text
ValueError
```

---

# 20. `TypeError`

Example:

```python
port = 443

message = "Port: " + port
```

Python cannot concatenate:

```text
str
```

and:

```text
int
```

using that operation.

This can produce:

```text
TypeError
```

Correct approaches include:

```python
message = "Port: " + str(port)
```

or:

```python
message = f"Port: {port}"
```

---

# 21. `FileNotFoundError`

Example:

```python
with open("servers.json", "r") as file:
    data = file.read()
```

If:

```text
servers.json
```

does not exist at the expected path, Python may raise:

```text
FileNotFoundError
```

---

# 22. `PermissionError`

A file may exist, but your process may not be allowed to access it.

Then Python may raise:

```text
PermissionError
```

This is fundamentally different from:

```text
FileNotFoundError
```

One means:

```text
The expected file could not be found.
```

The other means:

```text
The operation was denied by permissions.
```

That difference matters when deciding how to fix the problem.

---

# 23. `KeyError`

Consider:

```python
server = {
    "hostname": "web01",
    "status": "healthy"
}

print(server["region"])
```

The key:

```text
region
```

does not exist.

Python raises:

```text
KeyError
```

---

# 24. `IndexError`

Consider:

```python
servers = [
    "web01",
    "web02"
]

print(servers[10])
```

There is no element at index 10.

Python raises:

```text
IndexError
```

---

# 25. Why Exception Types Matter

Suppose:

```python
with open("config.json", "r") as file:
    data = file.read()
```

Potential failures include:

```text
File does not exist
```

or:

```text
Permission denied
```

These require different responses.

A missing configuration might produce:

```text
Configuration file not found.
```

A permission problem might produce:

```text
Configuration exists but cannot be read.
Check ownership and permissions.
```

Specific exception types allow specific responses.

# 26. What Is `try`?

The `try` statement marks code that may raise an exception you intend to handle.

Basic structure:

```python
try:
    number = int("abc")
except ValueError:
    print("Invalid number")
```

Conceptually:

```text
try
 |
 v
Run risky operation
 |
 +---- success ----> continue
 |
 +---- ValueError ----> except block
```

---

# 27. Understanding the Structure

```python
try:
    number = int("abc")
except ValueError:
    print("Invalid number")
```

The:

```text
try:
```

means:

```text
Attempt this block.
```

The:

```text
except ValueError:
```

means:

```text
If a ValueError is raised from the try block,
handle it here.
```

---

# 28. What Happens Without `try`?

```python
number = int("abc")

print("Finished")
```

The conversion fails.

The program normally stops before:

```python
print("Finished")
```

executes.

---

# 29. What Happens With `try`?

```python
try:
    number = int("abc")
except ValueError:
    print("Invalid number")

print("Finished")
```

Output:

```text
Invalid number
Finished
```

The expected `ValueError` was handled.

Execution continued after the exception-handling structure.

---

# 30. Exception Handling Changes Control Flow

Normally:

```text
Statement 1
    |
    v
Statement 2
    |
    v
Statement 3
```

With an exception:

```text
Statement 1
    |
    v
Risky statement
    |
    +--> exception
            |
            v
        except block
            |
            v
        continue afterward
```

The remainder of the `try` block after the failing statement is skipped.

---

# 31. Statements After the Failure Do Not Run

Consider:

```python
try:
    print("Starting conversion")

    number = int("abc")

    print("Conversion completed")
except ValueError:
    print("Conversion failed")
```

Output:

```text
Starting conversion
Conversion failed
```

This line:

```python
print("Conversion completed")
```

does not execute.

Once the exception occurs, control leaves the remaining portion of the `try` block.

---

# 32. Catching the Exception Object

You can access the exception object:

```python
try:
    number = int("abc")
except ValueError as error:
    print(
        f"Conversion failed: {error}"
    )
```

The:

```text
as error
```

stores the exception object in:

```text
error
```

for use inside the handler.

---

# 33. Why Capture the Exception?

It can provide useful details.

For example:

```python
try:
    port = int("HTTPS")
except ValueError as error:
    print(
        f"Invalid port value: {error}"
    )
```

This provides both:

```text
your context
```

and:

```text
Python's underlying error information
```

---

# 34. User-Friendly Errors vs Technical Errors

A user-facing message might be:

```text
Port must be a number between 1 and 65535.
```

A technical log might contain:

```text
ValueError while converting port input 'HTTPS'
```

Production automation often separates:

```text
What the operator needs to know
```

from:

```text
What engineers need for debugging
```

Do not expose unnecessary internal details to untrusted users.

But do preserve enough evidence in appropriate logs.

---

# 35. What Is `else`?

A `try` statement can include:

```text
else
```

The `else` block runs if the `try` block completes without raising an exception handled by the preceding `except` clauses.

Example:

```python
try:
    port = int("443")
except ValueError:
    print("Invalid port")
else:
    print(
        f"Using port {port}"
    )
```

Output:

```text
Using port 443
```

---

# 36. Why Use `else`?

You could write:

```python
try:
    port = int("443")
    print(
        f"Using port {port}"
    )
except ValueError:
    print("Invalid port")
```

But sometimes it is better to keep the `try` block narrow:

```python
try:
    port = int("443")
except ValueError:
    print("Invalid port")
else:
    print(
        f"Using port {port}"
    )
```

Now only the operation expected to raise the handled exception is inside `try`.

This improves clarity.

---

# 37. Keep `try` Blocks Narrow

Bad:

```python
try:
    port = int(user_input)

    load_configuration()

    connect_to_server()

    update_database()

    send_alert()

    generate_report()

except Exception:
    print("Something failed")
```

Many unrelated operations can fail.

The handler does not tell you which one.

Prefer smaller exception boundaries around operations whose failures you understand.

---

# 38. Narrow `try` Example

```python
try:
    port = int(user_input)
except ValueError:
    print("Port must be numeric")
else:
    connect_to_server(
        port
    )
```

Now the `ValueError` handler clearly relates to input conversion.

---

# 39. What Is `finally`?

The:

```text
finally
```

block is used for cleanup that should run whether the protected operation succeeds or fails.

Example:

```python
try:
    print("Performing operation")
except RuntimeError:
    print("Operation failed")
finally:
    print("Cleanup")
```

Conceptually:

```text
          try
           |
      +----+----+
      |         |
   success   exception
      |         |
      |       except
      |         |
      +----+----+
           |
           v
        finally
```

---

# 40. `finally` Runs on Success

```python
try:
    number = int("443")
except ValueError:
    print("Invalid number")
finally:
    print("Finished conversion attempt")
```

The conversion succeeds.

The `finally` block still runs.

---

# 41. `finally` Runs After a Handled Failure

```python
try:
    number = int("HTTPS")
except ValueError:
    print("Invalid number")
finally:
    print("Finished conversion attempt")
```

Output includes:

```text
Invalid number
Finished conversion attempt
```

---

# 42. Why `finally` Matters

Suppose automation:

1. Acquires a resource.
2. Performs work.
3. Needs to release the resource.

You may need cleanup even when work fails.

Examples include:

* Closing certain resources.
* Releasing locks.
* Removing temporary state.
* Restoring controlled state.
* Recording final status.

However, Python context managers such as:

```python
with open(...)
```

often provide cleaner resource cleanup than manually using `finally`.

Use the appropriate abstraction.

---

# 43. `try`, `except`, `else`, and `finally` Together

```python
try:
    port = int(user_input)
except ValueError as error:
    print(
        f"Invalid port: {error}"
    )
else:
    print(
        f"Valid numeric port: {port}"
    )
finally:
    print(
        "Port validation attempt complete"
    )
```

Flow:

```text
try
 |
 +--> ValueError?
 |       |
 |      yes
 |       |
 |       v
 |     except
 |
 +--> no exception
         |
         v
        else

Either path
    |
    v
 finally
```

---

# 44. Catching Specific Exceptions

Good exception handling normally catches the failures you actually expect.

Example:

```python
try:
    with open(
        "servers.json",
        "r",
        encoding="utf-8"
    ) as file:
        content = file.read()
except FileNotFoundError:
    print(
        "servers.json was not found"
    )
```

This handler has a clear meaning.

---

# 45. Why Specific Exceptions Are Better

Suppose you write:

```python
try:
    with open(
        "servers.json",
        "r"
    ) as file:
        content = file.read()
except Exception:
    print("Configuration problem")
```

What if the failure was caused by:

* Permission denied?
* Invalid encoding?
* An unexpected bug?
* A programming error in additional code inside the block?

You have hidden useful information under:

```text
Configuration problem
```

Specific handlers preserve meaning.

---

# 46. Handling Several Specific Exceptions

You can use multiple `except` blocks:

```python
try:
    with open(
        "servers.json",
        "r",
        encoding="utf-8"
    ) as file:
        content = file.read()

except FileNotFoundError:
    print(
        "Configuration file not found"
    )

except PermissionError:
    print(
        "Permission denied while "
        "reading configuration"
    )
```

Now each failure receives an appropriate response.

---

# 47. Order Can Matter

Exception classes form hierarchies.

Some exceptions are subclasses of broader exceptions.

If you catch a broad parent class before a more specific child class, the specific handler may never be reached.

Conceptually:

```text
Broad exception
      |
      +--> Specific exception A
      |
      +--> Specific exception B
```

Prefer more specific handlers before broader fallback handlers.

---

# 48. Catching Multiple Exception Types Together

If several exception types should receive exactly the same handling:

```python
try:
    perform_operation()
except (
    ValueError,
    TypeError
) as error:
    print(
        f"Invalid data: {error}"
    )
```

The tuple:

```python
(
    ValueError,
    TypeError
)
```

means:

```text
Handle either of these exception types here.
```

---

# 49. When Should Exceptions Be Grouped?

Group them when the recovery action is genuinely the same.

For example:

```python
except (
    FileNotFoundError,
    PermissionError
):
    return None
```

may sometimes be reasonable if:

```text
Either way, this optional resource cannot be used.
```

But if operators need to know whether the file is missing or inaccessible, separate handlers are better.

Do not group exceptions merely to shorten code.

---

# 50. What Does `raise` Mean?

Python can raise exceptions automatically.

You can also raise exceptions deliberately using:

```text
raise
```

Example:

```python
disk_usage = 97

if disk_usage > 95:
    raise RuntimeError(
        "Disk usage is critically high"
    )
```

You are telling Python:

```text
This condition represents a failure
that should interrupt normal execution.
```

---

# 51. Why Raise Exceptions Yourself?

Your program may detect a condition that Python itself does not consider invalid.

For example:

```python
port = 70000
```

Python is perfectly capable of storing:

```text
70000
```

as an integer.

But for a normal TCP/UDP port number, your application may require:

```text
1 through 65535
```

So:

```python
if not 1 <= port <= 65535:
    raise ValueError(
        "Port must be between "
        "1 and 65535"
    )
```

This converts an application rule into an explicit failure.

---

# 52. Python Validity vs Application Validity

This is important.

Python asks:

```text
Can I represent 70000 as an integer?
```

Yes.

Your application asks:

```text
Is 70000 valid for this configuration?
```

No.

Therefore:

```text
Type validation
```

and:

```text
business/application validation
```

are different.

---

# 53. Raising a `ValueError`

Suppose:

```python
def validate_cpu_threshold(
    threshold
):
    if not 0 <= threshold <= 100:
        raise ValueError(
            "CPU threshold must be "
            "between 0 and 100"
        )
```

Then:

```python
validate_cpu_threshold(150)
```

raises:

```text
ValueError
```

with your custom message.

---

# 54. Why Custom Error Messages Matter

Compare:

```text
ValueError
```

with:

```text
ValueError:
CPU threshold must be between 0 and 100
```

The second provides context.

A useful error message should often explain:

* What failed.
* Which value was problematic when safe to show.
* What was expected.
* What the operator can do next.

---

# 55. Good Error Message Example

Weak:

```text
Invalid value
```

Better:

```text
Port must be an integer between 1 and 65535.
Received: 'HTTPS'
```

But be careful when values may contain:

* Passwords.
* API keys.
* Tokens.
* Authorization headers.
* Private information.

Do not leak secrets into errors or logs.

---

# 56. Error Messages Are Operational Interfaces

Engineers often encounter your automation through its failures.

Imagine a 3:00 AM incident.

Which is more useful?

```text
ERROR
```

or:

```text
Failed to load server inventory:
file '/etc/infra/servers.json' was not found.
Verify the deployment configuration.
```

Good failure messages reduce troubleshooting time.

# 57. Re-Raising an Exception

Sometimes you want to perform an action and then allow the exception to continue upward.

Example:

```python
try:
    load_configuration()
except FileNotFoundError:
    print(
        "Configuration could not be loaded"
    )
    raise
```

The bare:

```text
raise
```

inside an active exception handler re-raises the current exception.

---

# 58. Why Re-Raise?

Suppose a lower-level function wants to:

```text
Log useful context
```

but cannot safely recover.

It can record context and then re-raise the failure so a higher level can decide whether the entire application should stop.

Conceptually:

```text
Low-level function
      |
      v
Failure
      |
      +--> Add context/log
      |
      v
Re-raise
      |
      v
Higher-level controller
      |
      v
Decide final action
```

---

# 59. Do Not Log the Same Failure Everywhere

Be careful.

If every function catches, logs, and re-raises the same exception:

```text
Function C logs error
        |
        v
Function B logs same error
        |
        v
Function A logs same error
        |
        v
main logs same error
```

your logs become noisy.

Choose clear ownership for error reporting.

---

# 60. Exception Chaining

Sometimes you catch a low-level exception and raise a more meaningful application-level exception.

Example:

```python
try:
    port = int(value)
except ValueError as error:
    raise ValueError(
        f"Invalid server port: {value}"
    ) from error
```

The:

```text
from error
```

preserves the relationship between the new exception and the original exception.

This is called exception chaining.

---

# 61. Why Exception Chaining Helps

Without context, an operator may only see:

```text
Invalid server configuration
```

But internally the real cause may have been:

```text
ValueError converting 'HTTPS' to integer
```

Exception chaining preserves both levels:

```text
High-level meaning
      |
      v
Invalid server configuration

caused by

Low-level failure
      |
      v
Invalid integer conversion
```

---

# 62. Avoid Overly Broad Exception Handling

This is one of the most important lessons in Part 10.

Avoid patterns such as:

```python
try:
    run_everything()
except:
    pass
```

This is dangerous.

It can hide failures completely.

---

# 63. Why Bare `except` Is Dangerous

A bare:

```python
except:
```

catches an extremely broad range of exceptions, including some signals used for interpreter-level control such as user interrupts and system exits.

For ordinary application error handling, this is usually too broad.

It can make automation:

* Ignore real failures.
* Continue with invalid state.
* Hide bugs.
* Suppress operator interrupts.
* Produce incorrect results.
* Damage production systems.

---

# 64. `except Exception` Is Better, But Still Broad

You may see:

```python
try:
    operation()
except Exception as error:
    print(error)
```

This is narrower than a bare `except`, but it is still broad.

It can be appropriate at carefully chosen application boundaries.

For example:

```text
Top-level worker
```

may need to prevent one failed task from killing an entire worker process.

But broad handling should be deliberate.

---

# 65. A Broad Handler Needs a Policy

If you use:

```python
except Exception as error:
```

ask:

```text
Why am I catching all ordinary application exceptions here?

Can I recover?

Am I logging enough information?

Should I re-raise?

Should the task be marked failed?

Could continuing corrupt state?
```

Never use broad exception handling merely to make red errors disappear.

---

# 66. The Worst Pattern: Silent Failure

Avoid:

```python
try:
    update_production()
except Exception:
    pass
```

Suppose the update fails.

Your script now says nothing.

A pipeline may continue.

Another stage may assume the update succeeded.

You have converted:

```text
Visible failure
```

into:

```text
Hidden incorrect state
```

That can be worse than a crash.

---

# 67. Failing Loudly Can Be Safer

In infrastructure automation:

```text
Stop with clear error
```

can be safer than:

```text
Continue after unknown failure.
```

For example:

```text
Unable to validate production configuration
```

should often block a deployment.

Fail-safe automation prefers a known safe stop over uncertain continuation.

# 69. But First Ask: Is the File Required?

If:

```text
servers.json
```

is essential, continuing may be unsafe.

For example:

```python
from pathlib import Path


def load_configuration(
    path
):

        return Path(path).read_text(

    except FileNotFoundError as error:
        raise RuntimeError(
            f"Required configuration "
```

Now the missing required file becomes a clear application failure.

Consider two files:

```text
servers.json
```

Suppose:


controls which production systems are checked.

It is required.

But:

It may be optional.

Therefore:

# 84. Handling Invalid Input

```python
port_text = input(
    "Enter port: "
)

try:
    port = int(
        port_text
    )
except ValueError:
    print(
        "Port must be a number"
    )
```

This handles conversion failure.

But we still need range validation.

---

# 85. Validate After Conversion

```python
try:
    port = int(
        port_text
    )
except ValueError:
    print(
        "Port must be numeric"
    )
else:
    if not 1 <= port <= 65535:
        print(
            "Port must be between "
            "1 and 65535"
        )
```

There are two separate questions:

```text
Can this become an integer?
```

and:

```text
Is this integer valid for our purpose?
```

---

# 86. Better: Put Validation in a Function

```python
def parse_port(
    value: str
) -> int:
    """Convert and validate a port."""

    try:
        port = int(value)
    except ValueError as error:
        raise ValueError(
            "Port must be an integer"
        ) from error

    if not 1 <= port <= 65535:
        raise ValueError(
            "Port must be between "
            "1 and 65535"
        )

    return port
```

Now:

```python
port = parse_port(
    "443"
)
```

returns:

```text
443
```

But invalid input raises a meaningful exception.

---

# 87. Why Functions Should Often Raise Instead of Print

Suppose:

```python
def parse_port(value):
    try:
        return int(value)
    except ValueError:
        print("Bad port")
        return None
```

This may be acceptable in a tiny script, but reusable functions often should not decide how the entire application communicates errors.

Better:

```python
def parse_port(value):
    try:
        return int(value)
    except ValueError as error:
        raise ValueError(
            "Port must be numeric"
        ) from error
```

Then the caller decides:

* Print.
* Log.
* Retry.
* Exit.
* Ask again.

This improves reuse.

---

# 88. Separation of Responsibilities

A good design may be:

```text
Low-level function
      |
      v
Detect/raise meaningful failure
      |
      v
Higher-level workflow
      |
      v
Decide recovery policy
      |
      v
Top-level application
      |
      v
Report final outcome
```

Do not make every helper function responsible for every layer.

# 89. Handling Connection Failures

* DNS resolution failure.
* Connection refused.
* Timeout.

* TLS problem.
* Proxy issue.
* Remote service unavailable.

The exact exception types depend on the library and operation being used.

Do not assume all network failures use one universal Python exception.

# 90. Connection Failure with a Socket

A standard-library example:

```python
import socket


try:
    connection = socket.create_connection(
        ("example.com", 443),

        f"Connection failed: {error}"
```

```text
Network operation
        |
        v

        |
        v

```

# 91. Timeout Is Different from Immediate Refusal

Suppose:

```text
Connection refused
```

The target host may be reachable but nothing is accepting connections on that port.

A:

```text
timeout
```

may indicate:

* Network filtering.
* Packet loss.
* Unresponsive host.
* Slow service.
* Routing problems.

Do not collapse every network failure into:

```text
Server is down.
```

That conclusion may be unsupported.

---

# 92. Preserve the Actual Network Failure

Bad:

```python
try:
    connect()
except Exception:
    print(
        "Server is down"
    )
```

You do not know that.

Better:

```text
Connection to web01:443 failed:
timed out after 5 seconds.
```

That reports what you actually observed.

# 93. Retryable vs Non-Retryable Failures

Some failures may be temporary.

Example:

```text
Network timeout
```

might succeed on retry.

But:

```text
Invalid authentication credentials
```

probably will not become valid merely because you retry 100 times.

Classify failures.

Conceptually:

```text
Failure
   |
   +--> transient?
   |       |
   |      yes
   |       |
   |       v
   |   limited retry
   |
   +--> permanent/configuration?
           |
           v
       fail/report
```

---

# 94. Never Retry Forever

Bad:

```python
while True:
    try:
        connect()
        break
    except Exception:
        pass
```

This can:

* Loop forever.
* Hide the failure.
* Hammer a broken service.
* Consume resources.
* Delay incident detection.

Retries need limits and visibility.

---

# 95. Basic Limited Retry Pattern

```python
import time


max_attempts = 3

for attempt in range(
    1,
    max_attempts + 1
):
    try:
        perform_health_check()
    except TimeoutError as error:
        print(
            f"Attempt {attempt} "
            f"failed: {error}"
        )

        if attempt == max_attempts:
            raise

        time.sleep(2)
    else:
        break
```

This is only a basic pattern.

Production retry design may also include:

* Exponential backoff.
* Jitter.
* Retryable status codes.
* Idempotency.
* Rate-limit handling.
* Maximum total retry time.

---

# 96. Why Retry Delays Matter

Without delay:

```text
Attempt 1 fails
Attempt 2 immediately
Attempt 3 immediately
Attempt 4 immediately
```

you may worsen an overloaded service.

A delay allows time for recovery.

More advanced systems may use:

```text
1 second
2 seconds
4 seconds
8 seconds
```

rather than a constant delay.

This is called exponential backoff.

---

# 97. What Is Jitter?

If 1,000 clients all retry at exactly:

```text
1 second
2 seconds
4 seconds
```

they can create synchronized traffic spikes.

Jitter introduces some randomness into retry timing.

Conceptually:

```text
Without jitter:

1000 clients
     |
     v
retry simultaneously


With jitter:

clients retry
across a small
time range
```

You do not need to implement sophisticated retry systems yet.

Understand why they exist.

# 99. Return Codes

Operating-system commands commonly return an exit status.

Conventionally:

```text
0
```

means success.

A non-zero value generally indicates some form of failure or alternate status, though exact meanings are command-specific.

Inspect:

```python
print(
    result.returncode
)
```

Do not assume every command uses every non-zero code identically.

Check command documentation.

---

# 100. `check=True`

You can ask `subprocess.run()` to raise an exception when the command returns a non-zero status:

```python
import subprocess


result = subprocess.run(
    [
        "systemctl",
        "is-active",
        "nginx"

    capture_output=True,
    text=True,
    check=True
)
```

If the command fails according to its exit status, Python raises:

```text
subprocess.CalledProcessError
```

---

# 101. Handling `CalledProcessError`

```python
import subprocess


try:
    result = subprocess.run(
        [
            "systemctl",
            "is-active",
            "nginx"
        ],
        capture_output=True,
        text=True,
        check=True

except subprocess.CalledProcessError as error:
    print(
        "Service check command failed"

    print(
        f"Return code: "
        f"{error.returncode}"

```

This turns command failure into an exception-handling workflow.

# 102. Capture `stderr`

With:

```python
capture_output=True
```

you can inspect:

```python
error.stderr
```

when available.

```python
except subprocess.CalledProcessError as error:
```

# 105. Multiple Command Failure Modes

```python
import subprocess


try:
```

# 106. Do Not Use `shell=True` to Fix Command Errors

A beginner may discover that a command behaves differently and try:

```python
subprocess.run(
    command,
    shell=True
)
```

without understanding the consequences.

Using a shell can introduce command-injection risks when untrusted data reaches the command string.

Prefer argument lists where possible:

```python
[
    "systemctl",
    "status",
    service_name
]
```

rather than constructing unsafe shell strings.

---

# 107. Exception Handling Does Not Make Unsafe Commands Safe

This:

```python
try:
    dangerous_operation()
except Exception:
    print("Failed safely")
```

does not mean the operation itself was safe.

The command may have partially changed the system before failing.

Exception handling is not transaction rollback.

This is extremely important.

---

# 108. Partial Failure

Imagine:

```text
Update 10 servers
```

The script succeeds on:

```text
Server 1
Server 2
Server 3
Server 4
```

Then fails on:

```text
Server 5
```

Now the system is partially changed.

An exception tells you something failed.

It does not automatically undo servers 1 through 4.

---

# 109. Fail-Safe Automation Must Consider Partial State

Ask:

```text
If this operation fails halfway,
what state will the system be in?
```

Possible strategies include:

* Validate everything before changes.
* Use transactions where available.
* Use idempotent operations.
* Record completed work.
* Provide rollback mechanisms.
* Stop before dependent actions.
* Resume safely.
* Reconcile desired state afterward.

These are production engineering concerns beyond simple syntax.

---

# 110. What Is Idempotency?

An idempotent operation can be repeated without causing unintended additional changes after the desired state is reached.

Example concept:

```text
Desired state:
directory exists
```

An idempotent operation says:

```text
Ensure directory exists.
```

Running it multiple times should leave the same intended state.

Compare with:

```text
Append this line every time.
```

which may create duplicates on every retry.

Retries are much safer when operations are idempotent.

---

# 111. Retry + Non-Idempotent Operation Can Be Dangerous

Suppose an API call means:

```text
Create invoice
```

The request succeeds on the server, but the network connection breaks before your client receives the response.

Your client thinks:

```text
Request failed.
```

It retries.

Now you may create two invoices.

This is why:

```text
Exception occurred
```

does not always mean:

```text
Operation did nothing.
```

# 113. HTTP Failure vs Network Failure

Suppose a server responds:


```python
except requests.RequestException as error:
```

# 122. API Authentication Failures

Suppose the API returns:

```text
401 Unauthorized
```

or:

```text
403 Forbidden
```

Blind retries may not help.

Possible causes include:

* Missing credentials.
* Expired token.
* Invalid token.
* Insufficient permission.
* Wrong identity.

Do not log the actual secret while reporting the failure.

# 123. API Rate Limiting

An API may return:

```text

```

This is different from:


The correct response may involve:

* Waiting.
* Respecting `Retry-After`.
* Reducing request rate.
* Using exponential backoff.
* Investigating quota limits.

Do not treat every non-2xx status identically.

# 130. Exception Handling Around Loops

# 131. Per-Item Exception Handling

# 162. `loader.py`

```python
import json
from pathlib import Path


def load_json_file(
    path: str
) -> dict:
    """Load JSON configuration."""

    config_path = Path(path)

    try:
        with config_path.open(
            "r",
            encoding="utf-8"
        ) as file:
            return json.load(file)

    except FileNotFoundError as error:
        raise RuntimeError(
            f"Required configuration "
            f"file not found: {path}"
        ) from error

    except PermissionError as error:
        raise RuntimeError(
            f"Permission denied while "
            f"reading: {path}"
        ) from error

    except json.JSONDecodeError as error:
        raise RuntimeError(
            f"Invalid JSON in "
            f"configuration: {path}"
        ) from error
```


The custom messages preserve the reason.

Exception chaining preserves the original cause.

This is one reasonable design.

Another project might choose custom exception classes later.

```python
def validate_config(
    config: dict

    """Validate required configuration."""

    required_keys = [
        "environment",
        "timeout",
```

# 175. `command_runner.py`

```python
import subprocess


def run_command(
    command: list[str],
    timeout: int = 10
) -> str:
    """Run a command safely."""

    try:
        result = subprocess.run(
            command,
            capture_output=True,
            text=True,
            timeout=timeout,
            check=True
        )

    except FileNotFoundError as error:
        raise RuntimeError(
            f"Command not found: "
            f"{command[0]}"
        ) from error

    except subprocess.TimeoutExpired as error:
        raise RuntimeError(
            f"Command timed out after "
            f"{timeout} seconds"
        ) from error

    except subprocess.CalledProcessError as error:
        stderr = (
            error.stderr.strip()
            if error.stderr
            else "No stderr output"
        )

        raise RuntimeError(
            f"Command failed with "
            f"exit code "
            f"{error.returncode}: "
            f"{stderr}"
        ) from error

    return result.stdout.strip()
```

```text
What does this exception mean here?

Can I recover?

If I continue, is the system state safe?

Should I retry?

Should I stop?

Should I report partial failure?

Does the caller need to know?

What evidence should I preserve?
```

Exception handling is engineering judgment.

---

# 186. Common Conditional Mistake: Catching the Wrong Exception

Suppose:

```python
int("abc")
```

raises:

```text
ValueError
```

but you write:

```python
try:
    int("abc")
except TypeError:
    print("Invalid number")
```

The exception is not handled because the type does not match.

Read the traceback.

Do not guess exception names.

---

# 187. Common Mistake: Putting Too Much Inside `try`

Bad:

```python
try:
    config = load_config()
    validate_config(config)
    connect()
    deploy()
    notify()
except ValueError:
    print("Bad config")
```

A `ValueError` could potentially arise from several unrelated operations.

Now:

```text
Bad config
```

may be misleading.

Keep exception boundaries meaningful.

---

# 188. Common Mistake: Catching and Doing Nothing

Avoid:

```python
except FileNotFoundError:
    pass
```

unless the missing file is intentionally optional and the behavior is documented.

Even then, explicit code is often clearer:

```python
except FileNotFoundError:
    config = default_config
```

Now the recovery action is visible.

---

# 189. Common Mistake: Returning `None` Everywhere

Bad:

```python
def load_config():
    try:
        ...
    except Exception:
        return None
```

Then later:

```python
config["servers"]
```

fails with:

```text
TypeError
```

The original failure has been hidden.

If failure is unrecoverable, raising a meaningful exception may be better.

---

# 190. Common Mistake: Printing and Continuing

```python
try:
    authenticate()
except AuthenticationError:
    print(
        "Authentication failed"
    )

deploy()
```

If deployment requires authentication, continuing makes no sense.

Failure handling must match dependencies between operations.

---

# 191. Common Mistake: Retry Every Exception

Do not:

```python
except Exception:
    retry()
```

A retry will not fix:

* Syntax bugs.
* Invalid configuration.
* Missing required files.
* Invalid credentials.
* Programming errors.
* Unsupported values.

Retry only failures reasonably expected to be transient.

---

# 192. Common Mistake: Retry Without Timeout

A retry policy without per-attempt timeout can still hang indefinitely.

You need boundaries around:

```text
Individual attempt
```

and:

```text
Total retry process
```

---

# 193. Common Mistake: Retry Destructive Operations Blindly

Never assume:

```text
No response
=
No change happened.
```

The remote system may have completed the operation before communication failed.

Understand idempotency before retrying mutations.

---

# 194. Common Mistake: Exposing Secrets

Avoid errors such as:

```text
Login failed using password:
MySecretPassword123
```

or:

```text
API request failed:
Authorization: Bearer eyJ...
```

Sanitize sensitive data.

---

# 195. Common Mistake: Replacing the Original Error with a Vague Message

Bad:

```python
except FileNotFoundError:
    raise RuntimeError(
        "Something went wrong"
    )
```

Better:

```python
except FileNotFoundError as error:
    raise RuntimeError(
        "Required inventory file "
        "was not found"
    ) from error
```

Now the application context and underlying cause are preserved.

---

# 196. Common Mistake: Assuming Exceptions Roll Back Work

They do not.

Example:

```text
Create resource A
      |
      v
Create resource B
      |
      v
Exception while creating C
```

Resources A and B may still exist.

Your recovery design must consider partial state.

---

# 197. Common Mistake: Using Exceptions for Ordinary Conditions

Suppose you want to check whether a dictionary contains a key.

You could deliberately trigger:

```text
KeyError
```

but sometimes a normal conditional is clearer:

```python
if "region" in config:
    ...
```

Exceptions are useful for exceptional or failure paths.

Normal expected branching often belongs in conditions.

---

# 198. Exception vs Conditional

Use a conditional when you are checking a normal state:

```python
if disk_usage > 90:
    ...
```

Use exception handling when an operation may fail:

```python
try:
    content = path.read_text()
except FileNotFoundError:
    ...
```

The boundary is not absolute, but this is a useful beginner guideline.

# 213. `automation/config.py`

```python
import json
from pathlib import Path

from automation.errors import (
    ConfigurationError
)


def load_config(
    path: str
) -> dict:
    """Load and validate configuration."""

    config_path = Path(path)

    try:
        with config_path.open(
            "r",
            encoding="utf-8"
        ) as file:
            config = json.load(file)

    except FileNotFoundError as error:
        raise ConfigurationError(
            f"Configuration file "
            f"not found: {path}"
        ) from error

    except PermissionError as error:
        raise ConfigurationError(
            f"Permission denied while "
            f"reading configuration: "
            f"{path}"
        ) from error

    except json.JSONDecodeError as error:
        raise ConfigurationError(
            f"Invalid JSON in "
            f"configuration: {path}"
        ) from error

    validate_config(
        config
    )

    return config
```

# 214. Configuration Validation

Continue:

```python
def validate_config(
    config: dict
) -> None:
    """Validate configuration values."""

    environment = config.get(
        "environment"
    )

    timeout = config.get(
        "timeout"
    )

    targets = config.get(
        "targets"
    )

    if environment not in {
        "development",
        "staging",
        "production"
    }:
        raise ConfigurationError(
            "Environment must be "
            "development, staging, "
            "or production"
        )

    if not isinstance(
        timeout,
        (int, float)
    ):
        raise ConfigurationError(
            "Timeout must be numeric"
        )

    if timeout <= 0:
        raise ConfigurationError(
            "Timeout must be greater "
            "than zero"
        )

    if not isinstance(
        targets,
        list
    ):
        raise ConfigurationError(
            "Targets must be a list"
        )

    if not targets:
        raise ConfigurationError(
            "At least one target "
            "is required"
        )

    for target in targets:
        if not isinstance(
            target,
            str
        ):
            raise ConfigurationError(
                "Every target must "
                "be a string"
            )
```

# 215. `automation/checks.py`

```python
import requests


def check_endpoint(
    url: str,
    timeout: float
) -> dict:
    """Check one HTTP endpoint."""

    try:
        response = requests.get(
            url,
            timeout=timeout
        )

        response.raise_for_status()

    except requests.Timeout as error:
        return {
            "url": url,
            "success": False,
            "category": "timeout",
            "error": str(error)
        }

    except requests.ConnectionError as error:
        return {
            "url": url,
            "success": False,
            "category": "connection",
            "error": str(error)
        }

    except requests.HTTPError as error:
        return {
            "url": url,
            "success": False,
            "category": "http",
            "error": str(error)
        }

    except requests.RequestException as error:
        return {
            "url": url,
            "success": False,
            "category": "request",
            "error": str(error)
        }

    return {
        "url": url,
        "success": True,
        "category": None,
        "error": None,
        "status_code": (
            response.status_code
        )
    }
```

# 217. `main.py`

```python
import sys

from automation.checks import (
    check_endpoint
)

from automation.config import (
    load_config
)

from automation.errors import (
    ConfigurationError
)


def main() -> int:
    """Run infrastructure checks."""

    config = load_config(
        "config/targets.json"
    )

    timeout = config[
        "timeout"
    ]

    targets = config[
        "targets"
    ]

    results = []

    for target in targets:
        result = check_endpoint(
            target,
            timeout
        )

        results.append(
            result
        )

        if result[
            "success"
        ]:
            print(
                f"OK: {target}"
            )
        else:
            print(
                f"FAILED: {target} "
                f"({result['category']})"
            )

    failures = [
        result
        for result in results
        if not result[
            "success"
        ]
    ]

    print()
    print(
        f"Total: {len(results)}"
    )

    print(
        f"Failed: {len(failures)}"
    )

    if failures:
        return 1

    return 0


if __name__ == "__main__":
    try:
        exit_code = main()

    except ConfigurationError as error:
        print(
            f"Configuration error: "
            f"{error}"
        )

        exit_code = 2

    except KeyboardInterrupt:
        print(
            "\nOperation cancelled "
            "by user"
        )

        exit_code = 130

    sys.exit(
        exit_code
    )
```

```text
  |      |
  |      v
  |   stop safely
  |
  v
Verify
  |
  +--> verification fails
  |      |
  |      v
  |   report failure
  |
  v
Report final state
```

```text

finally
```
