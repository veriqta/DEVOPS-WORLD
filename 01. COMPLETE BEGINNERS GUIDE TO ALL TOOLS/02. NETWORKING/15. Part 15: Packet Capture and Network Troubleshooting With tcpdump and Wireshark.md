# Part 15: Packet Capture and Network Troubleshooting With tcpdump and Wireshark

## Learn to Inspect What Is Actually Happening on the Wire

In Part 14, you learned how to interrogate a Linux system using tools such as:

```bash
ip addr
ip route
ip route get
ip neigh
ping
ss
dig
nc
curl
```

Those tools tell you what the operating system knows, what services are listening, which route Linux intends to use, and whether certain connectivity tests succeed.

But eventually you will face a problem where the configuration looks correct and the application logs are not enough.

At that point, you need to ask a more fundamental question:

> What packets are actually being sent and received?

That is where packet capture becomes one of the most powerful networking skills you can learn.

A packet capture can reveal:

```text
Did the client send the SYN?

Did the server receive it?

Did the server send SYN-ACK?

Did the DNS query leave?

Did a DNS response return?

Which IP address answered?

Was the connection reset?

Are packets being retransmitted?

Is ARP resolution working?

Which protocol is actually being used?

Is the problem before TCP, during TCP, during TLS, or inside HTTP?
```

Instead of guessing what happened, you inspect evidence.

The central principle of this part is:

> Configuration tells you what should happen. Packet capture shows you what actually happened.

---

# 1. Why Packet Capture Matters

Consider this architecture:

```text
Client
  |
  v
Firewall
  |
  v
Load Balancer
  |
  v
Application Server
  |
  v
Database
```

The application team reports:

```text
Database connections are timing out.
```

Several explanations are possible:

```text
Application bug
DNS failure
Wrong destination IP
Missing route
Firewall drop
Database not listening
Packet loss
TCP handshake failure
TLS problem
Return-path problem
```

Application logs might simply say:

```text
Connection timed out
```

That tells you the symptom.

It does not necessarily tell you where communication failed.

A packet capture might show:

```text
Client -> Server    SYN
Client -> Server    SYN
Client -> Server    SYN
Client -> Server    SYN
```

with no SYN-ACK returning.

Now you know the TCP handshake is not completing.

That dramatically narrows the investigation.

---

# 2. Packet Capture Is Evidence

Good network troubleshooting should move from assumptions toward evidence.

Weak troubleshooting:

```text
"The firewall is probably blocking it."

"DNS is probably broken."

"Maybe Kubernetes networking is broken."

"Let's restart the server."
```

Better troubleshooting:

```text
What is the source?

What is the destination?

Which protocol?

Which port?

What route was selected?

Did the packet leave?

Did a response return?

What response returned?
```

Packet capture helps answer the last three questions directly.

---

# 3. Packets vs Application Logs

Application logs and packet captures observe different things.

Application logs describe events from the application's perspective.

For example:

```text
2026-08-28 10:15:23
Database connection timeout
```

A packet capture observes network traffic.

It might show:

```text
10.10.1.20:49152 -> 10.10.2.30:5432 SYN
10.10.1.20:49152 -> 10.10.2.30:5432 SYN
10.10.1.20:49152 -> 10.10.2.30:5432 SYN
```

The application says:

```text
I could not connect.
```

The capture says:

```text
TCP connection attempts left this interface,
but no reply was observed here.
```

Those are different levels of evidence.

---

# 4. Packet Capture Does Not Automatically Reveal Root Cause

This distinction is critical.

Suppose a client capture shows:

```text
SYN
SYN
SYN
```

with no reply.

You can conclude:

> No response to those SYNs was observed at this capture point.

You cannot immediately conclude:

> The server firewall dropped them.

Other possibilities include:

```text
Upstream firewall
Routing failure
Wrong destination
Server offline
Return-route failure
Network ACL
Packet loss
Capture taken at the wrong location
```

Packet capture is powerful, but interpretation still requires networking knowledge.

---

# 5. Capture Location Matters

Suppose:

```text
Client
  |
  v
Firewall
  |
  v
Server
```

Capture on the client:

```text
SYN leaves
No response
```

Capture on the server:

```text
No SYN arrives
```

This suggests the packet disappeared somewhere between those observation points.

Now suppose the server capture shows:

```text
SYN arrives
SYN-ACK leaves
```

while the client never sees SYN-ACK.

The investigation changes completely.

Packet captures are observations from specific points in the network.

---

# 6. Think Like a Network Investigator

For every capture, ask:

```text
WHERE am I capturing?

WHAT interface?

WHAT traffic?

WHEN?

WHO are the endpoints?

WHAT question am I trying to answer?
```

Do not capture everything indefinitely and hope the answer appears.

Start with a hypothesis.

Example:

> I want to determine whether TCP SYN packets from the application server reach the database.

Now you can create a narrow capture.

# What Is tcpdump?

## 7. `tcpdump`

`tcpdump` is a command-line packet capture and analysis utility commonly available on Unix-like systems.

It can:

```text
Capture packets
Display packet summaries
Filter traffic
Write captures to files
Read saved captures
Inspect protocol headers
Help troubleshoot live systems
```

It is particularly valuable on servers where no graphical desktop exists.

---

## 8. Why DevOps and SRE Engineers Should Know `tcpdump`

Imagine troubleshooting:

```text
Linux VM
AWS EC2
Kubernetes node
Container host
Reverse proxy
Database server
Load balancer backend
DNS server
```

You may only have SSH access.

There is no desktop environment.

`tcpdump` lets you investigate directly from the terminal.

---

## 9. Is `tcpdump` Always Installed?

No.

Check:

```bash
tcpdump --version
```

If the command is unavailable, installation depends on the distribution and your organization's policies.

For Debian/Ubuntu systems, the package is commonly named:

```text
tcpdump
```

For RHEL-family systems, it is also commonly available as:

```text
tcpdump
```

Production systems may restrict installation or packet-capture privileges.

Follow organizational procedures.

# What Is Wireshark?

## 10. Wireshark

Wireshark is a graphical network protocol analyzer.

It can open packet captures and decode hundreds of protocols.

Its interface allows you to inspect:

```text
Packet list
Protocol hierarchy
Individual header fields
Raw packet bytes
TCP conversations
DNS transactions
HTTP traffic
TLS metadata
ICMP messages
ARP traffic
```

---

## 11. tcpdump vs Wireshark

They complement each other.

| tcpdump                           | Wireshark                               |
| --------------------------------- | --------------------------------------- |
| Command line                      | Graphical interface                     |
| Excellent on remote Linux servers | Excellent for deep interactive analysis |
| Powerful capture filters          | Powerful display filters                |
| Lightweight                       | Rich protocol decoding                  |
| Good for quick live diagnosis     | Good for detailed PCAP investigation    |
| Easy over SSH                     | Better visual conversation analysis     |

A common professional workflow is:

```text
Remote Linux Server
       |
       | tcpdump
       v
    capture.pcap
       |
       v
    Wireshark
       |
       v
Detailed analysis
```

# Choosing an Interface

## 12. Before Capturing, Find the Interface

Run:

```bash
ip link
```

or:

```bash
ip addr
```

You might see:

```text
lo
ens5
docker0
cni0
veth1234
```

You need to determine where the traffic of interest should appear.

---

## 13. List Interfaces Available to tcpdump

Run:

```bash
sudo tcpdump -D
```

This lists interfaces available for capture.

You may see something similar to:

```text
1.ens5
2.lo
3.any
4.docker0
```

Exact output depends on the system.

---

## 14. Capture on a Specific Interface

Example:

```bash
sudo tcpdump -i ens5
```

`-i` means:

```text
interface
```

This tells `tcpdump` where to listen.

---

## 15. The `any` Interface

On Linux, you can often capture across multiple interfaces using:

```bash
sudo tcpdump -i any
```

This is extremely useful when you do not initially know which interface carries the traffic.

But there is a tradeoff.

You may capture much more traffic than necessary.

For precise investigations, the specific interface is often preferable once identified.

---

## 16. Do Not Assume `eth0`

As you learned previously, the primary interface might be:

```text
ens5
ens160
enp0s3
eno1
```

Always inspect first.

# Capturing Traffic

## 17. Basic Capture

Run:

```bash
sudo tcpdump -i ens5
```

Traffic may immediately begin scrolling rapidly.

Stop with:

```text
Ctrl+C
```

At the end, `tcpdump` normally displays capture statistics.

---

## 18. Disable Name Resolution

One of the most useful options is:

```bash
sudo tcpdump -n -i ens5
```

`-n` tells `tcpdump` not to convert IP addresses into names.

Why is this useful?

Because you usually want to see:

```text
10.0.1.20
```

rather than having `tcpdump` attempt to display a hostname.

It also avoids extra name-resolution behavior that can complicate troubleshooting.

---

## 19. Disable Name and Port Resolution

A common troubleshooting command is:

```bash
sudo tcpdump -nn -i ens5
```

Using `-nn` prevents conversion of both addresses and port numbers into names where applicable.

Instead of:

```text
https
```

you see:

```text
443
```

For network troubleshooting, numeric output is often clearer.

---

```text

```

```text

```

```text

```

Direction toward destination.

```text

```

Destination:

```text
IP:   10.0.2.30
Port: 443
```

```text

```

TCP SYN.

# TCP Flags in tcpdump

## 21. Common TCP Flag Representations

You may encounter:

```text
[S]
[S.]
[.]
[F.]
[R]
[R.]
[P.]
```

Simplified:

```text
S   SYN
.   ACK
F   FIN
R   RST
P   PSH
```

Combinations represent multiple flags.

For example:

```text
[S.]
```

means:

```text
SYN + ACK
```

# Capture Filters

## 22. Why Filters Matter

A busy server might process:

```text
Thousands
or
Millions
```

of packets during your investigation.

Capturing everything can create:

```text
Huge files
Noise
Performance overhead
Sensitive-data exposure
Difficult analysis
```

Instead, filter aggressively.

---

## 23. What Is a Capture Filter?

A capture filter determines which packets are captured.

Example:

```bash
sudo tcpdump -i ens5 host 10.0.2.30
```

Only traffic matching the expression is captured/displayed.

`tcpdump` uses packet-filter syntax commonly associated with BPF-style filtering.

---

# Filtering by Host

## 24. Capture Traffic Involving One Host

```bash
sudo tcpdump -nn -i ens5 host 10.0.2.30
```

This captures traffic where the specified address is either source or destination.

Conceptually:

```text
10.0.2.30 -> anything

anything -> 10.0.2.30
```

---

## 25. Filter by Source Host

```bash
sudo tcpdump -nn -i ens5 src host 10.0.1.20
```

This focuses on packets originating from:

```text
10.0.1.20
```

---

## 26. Filter by Destination Host

```bash
sudo tcpdump -nn -i ens5 dst host 10.0.2.30
```

Now only packets destined for that host are selected.

---

# Filtering by Port

## 27. Capture One Port

```bash
sudo tcpdump -nn -i ens5 port 443
```

This captures traffic involving port 443.

---

## 28. Destination Port

```bash
sudo tcpdump -nn -i ens5 dst port 443
```

This focuses on packets whose destination port is 443.

---

## 29. Source Port

```bash
sudo tcpdump -nn -i ens5 src port 53
```

This may be useful when examining responses sourced from DNS port 53, depending on the scenario.

---

# Filtering by Protocol

## 30. TCP

```bash
sudo tcpdump -nn -i ens5 tcp
```

---

## 31. UDP

```bash
sudo tcpdump -nn -i ens5 udp
```

---

## 32. ICMP

```bash
sudo tcpdump -nn -i ens5 icmp
```

For IPv6 ICMP, filtering differs because IPv6 uses ICMPv6.

---

## 33. ARP

```bash
sudo tcpdump -nn -i ens5 arp
```

This is extremely useful for local Layer 2 investigations.

---

# Combining Filters

## 34. TCP 443 to One Host

```bash
sudo tcpdump -nn -i ens5 'host 10.0.2.30 and tcp port 443'
```

Now your capture is much more focused.

---

## 35. Multiple Hosts

You can combine expressions:

```bash
sudo tcpdump -nn -i ens5 'host 10.0.2.30 or host 10.0.2.40'
```

---

## 36. Excluding Traffic

Suppose you are connected over SSH and do not want your own SSH session dominating the output.

You might use:

```bash
sudo tcpdump -nn -i ens5 'not port 22'
```

Be careful with exclusions.

Do not accidentally filter out the traffic you are investigating.

---

## 37. Parentheses and Logical Expressions

More complex filters should be grouped clearly.

Example:

```bash
sudo tcpdump -nn -i ens5 'host 10.0.2.30 and (port 80 or port 443)'
```

This means:

```text
Traffic involving 10.0.2.30

AND

port 80 or 443
```

Clear grouping prevents mistakes.

---

# Capture Filters vs Display Filters

## 38. The Important Difference

This distinction becomes especially important when moving between `tcpdump` and Wireshark.

A capture filter determines:

```text
What gets captured.
```

A display filter determines:

```text
What captured packets are currently shown.
```

---

## 39. Why This Matters

Suppose you capture only:

```text
tcp port 443
```

DNS traffic on port 53 was never captured.

You cannot later change a Wireshark display filter and magically recover those missing DNS packets.

Capture filters discard unwanted traffic before it enters the capture.

Display filters hide traffic from your current view without removing it from the capture file.

---

# TCP Packet Analysis

## 46. Start With the Three-Way Handshake

A normal TCP connection begins:

```text
Client                            Server

SYN ---------------------------->

    <---------------------- SYN-ACK

ACK ---------------------------->

Connection established
```

In a capture, identifying this sequence is fundamental.

---

## 47. SYN

Example:

```text
10.0.1.20.49152 > 10.0.2.30.443: Flags [S]
```

Interpretation:

```text
Client:
10.0.1.20:49152

Server:
10.0.2.30:443

Action:
Client is requesting a TCP connection.
```

---

## 48. SYN-ACK

Response:

```text
10.0.2.30.443 > 10.0.1.20.49152: Flags [S.]
```

Interpretation:

```text
The server side has responded to the connection request.
```

This is powerful evidence.

The SYN reached a TCP endpoint capable of responding, and the return packet reached this capture point.

---

## 49. Final ACK

Client:

```text
10.0.1.20.49152 > 10.0.2.30.443: Flags [.]
```

Now the three-way handshake is complete from the observed packet perspective.

```text
SYN
SYN-ACK
ACK
```

The TCP connection is established.

If the application still fails, investigate what happens after the handshake.

---

# Troubleshooting Connection Timeouts

## 50. Timeout Pattern

Suppose the capture shows:

```text
Client -> Server    SYN

... wait ...

Client -> Server    SYN

... wait ...

Client -> Server    SYN
```

No SYN-ACK.

No RST.

This is a classic packet-level pattern associated with a TCP connection attempt that is receiving no observed response.

---

## 51. What Repeated SYNs Tell You

They suggest:

```text
The client is attempting the connection.

TCP is retrying.

No expected handshake response is being observed at this capture point.
```

Possible causes include:

```text
Firewall silently dropping traffic
Server unavailable
Wrong destination
Routing problem
Return path failure
Network ACL
Packet loss
```

Do not jump directly to one cause.

---

## 52. Capture on Both Ends

Client capture:

```text
SYN
SYN
SYN
```

Server capture:

```text
Nothing
```

This suggests the SYN is disappearing before reaching the server capture point.

Now suppose:

Server capture:

```text
SYN
SYN-ACK
```

Client capture:

```text
SYN
No SYN-ACK
```

Now the forward path worked, but the response is disappearing somewhere on the return path.

This is how packet capture helps localize failures.

---

# TCP Resets

## 53. What Is RST?

TCP RST means:

```text
Reset
```

It abruptly terminates or rejects a TCP connection.

`tcpdump` may show:

```text
Flags [R]
```

or:

```text
Flags [R.]
```

depending on the packet.

---

# Troubleshooting Connection Resets

## 54. SYN Followed by RST

Example:

```text
Client -> Server    SYN
Server -> Client    RST, ACK
```

This differs significantly from:

```text
SYN
SYN
SYN
```

with no response.

A reset indicates something actively responded.

Common possibilities include:

```text
No application listening
Active firewall rejection
Application/network device deliberately resetting
Incorrect service endpoint
```

---

## 55. Reset During an Established Connection

Suppose:

```text
SYN
SYN-ACK
ACK
Application data
Application data
RST
```

The connection initially succeeded.

Something later terminated it abruptly.

Investigate:

```text
Application behavior
Proxy/load balancer behavior
Timeout policies
Protocol mismatch
Middleboxes
Server-side failures
```

The timing of the reset matters.

---

# TCP Retransmissions

## 56. What Is a Retransmission?

TCP provides reliable delivery.

If expected acknowledgment does not arrive, TCP may retransmit data.

Conceptually:

```text
Client                         Server

Data ------------------------>

     X ACK lost

Data ------------------------>   retransmission

     <------------------- ACK
```

---

## 57. Retransmissions Are Clues

Retransmissions can indicate:

```text
Packet loss
Congestion
Path problems
Receiver problems
Severe latency
Filtering
```

But a small number of retransmissions does not automatically prove a catastrophic network problem.

Analyze context and frequency.

---

## 58. tcpdump and Retransmission Analysis

Raw `tcpdump` output gives you packet-level information, sequence numbers, acknowledgments, and timing.

However, Wireshark performs higher-level TCP analysis that can make retransmission investigation easier.

For example, Wireshark may label packets as:

```text
TCP Retransmission
```

or related analysis categories.

These are Wireshark's analytical interpretations based on the packets it observed.

They should be treated as evidence, not unquestionable truth.

---

## 59. Wireshark Retransmission Filter

A useful Wireshark display filter is:

```text
tcp.analysis.retransmission
```

Other `tcp.analysis` filters can help investigate TCP behavior.

Remember that analysis quality depends on the capture point and whether the capture itself missed packets.

---

# Sequence Numbers and ACKs

## 60. Why Sequence Numbers Matter

TCP is an ordered byte stream.

Sequence numbers allow endpoints to track transmitted data.

ACK numbers indicate what data is expected next.

A detailed capture can help determine:

```text
What data was sent
What was acknowledged
What appears missing
What was retransmitted
```

Wireshark commonly uses relative sequence numbers by default to make analysis easier.

---

# TCP Window Information

## 61. TCP Flow Control Visibility

TCP packets also contain receive-window information.

Packet analysis can help identify situations involving:

```text
Receiver window limitations
Zero-window conditions
Window updates
```

These are more advanced investigations.

For now, understand:

> Not every slow TCP connection is caused by packet loss.

The receiving endpoint can also influence transmission behavior through flow control.

# DNS Packet Analysis

## 62. Capturing DNS

A basic capture:

```bash
sudo tcpdump -nn -i any port 53
```

This may capture traditional DNS traffic using UDP or TCP port 53.

---

## 63. DNS Query and Response

Conceptually:

```text
Client                         Resolver

DNS Query
example.com A
----------------------------->

                         DNS Response
                         A = 192.0.2.20
<-----------------------------
```

A capture lets you see whether both sides occurred.

---

## 64. DNS Query Leaves, No Response Returns

Capture:

```text
Client -> Resolver
DNS query

Client -> Resolver
DNS query

Client -> Resolver
DNS query
```

No response observed.

Investigate:

```text
Resolver reachability
Firewall
Routing
DNS service availability
Return path
Packet loss
```

---

## 65. DNS Response With NXDOMAIN

A response may indicate:

```text
NXDOMAIN
```

Meaning the DNS server is reporting that the queried domain name does not exist in DNS.

This is very different from:

```text
No DNS response at all.
```

The network transaction worked enough to receive a DNS answer.

The answer itself indicates nonexistence.

---

## 66. DNS SERVFAIL

A DNS response might indicate:

```text
SERVFAIL
```

This generally means the DNS server encountered a failure while trying to answer the query.

Possible causes may involve:

```text
Upstream DNS problems
DNSSEC validation problems
Authoritative server issues
Resolver failures
Misconfiguration
```

Again:

```text
SERVFAIL
```

is different from a network timeout.

A server responded.

---

## 67. DNS Response Contains Wrong Address

Suppose the application should reach:

```text
10.20.30.50
```

but the capture shows a DNS response containing:

```text
10.20.40.50
```

The networking stack may be behaving correctly.

The problem may be DNS configuration or the particular resolver/view being queried.

Packet capture helps reveal exactly what answer the client received on the wire.

---

# Encrypted DNS Limitation

## 68. Not All DNS Appears as Port 53

Modern environments may use encrypted DNS mechanisms such as:

```text
DNS over HTTPS
DNS over TLS
```

Therefore:

```bash
sudo tcpdump -nn -i any port 53
```

showing nothing does not universally prove:

> This system performed no name resolution.

Understand the resolver architecture.

# ICMP Packet Analysis

## 69. Capture ICMP

Run:

```bash
sudo tcpdump -nn -i any icmp
```

Then, in another terminal:

```bash
ping -c 3 8.8.8.8
```

You may observe:

```text
ICMP echo request
ICMP echo reply
```

---

## 70. ICMP Is More Than Ping

ICMP also communicates network control and error information.

Examples include messages associated with:

```text
Destination unreachable
Time exceeded
Fragmentation/path MTU behavior
```

These can provide valuable diagnostic information.

Do not treat all ICMP as useless traffic that should always be blocked.

---

## 71. ICMP Time Exceeded

Traceroute-style tools often depend on TTL/Hop Limit behavior and ICMP responses.

Conceptually:

```text
Packet TTL reaches zero at router
            |
            v
Router discards packet
            |
            v
ICMP Time Exceeded
            |
            v
Sender
```

Packet capture can reveal these messages.

---

# ARP Packet Analysis

## 72. Capture ARP

Run:

```bash
sudo tcpdump -nn -i ens5 arp
```

Suppose the host needs the MAC address for:

```text
192.168.1.1
```

You may observe a request conceptually equivalent to:

```text
Who has 192.168.1.1?
Tell 192.168.1.50
```

Then a reply:

```text
192.168.1.1 is at aa:bb:cc:dd:ee:ff
```

---

## 73. ARP Request Without Reply

Suppose you repeatedly see:

```text
Who has 192.168.1.1?
Who has 192.168.1.1?
Who has 192.168.1.1?
```

but no reply.

This suggests local neighbor resolution is failing from the perspective of the capture.

Possible causes:

```text
Wrong VLAN
Wrong subnet assumptions
Gateway offline
Layer 2 connectivity problem
Incorrect gateway address
Interface/network issue
```

Do not troubleshoot remote DNS before solving local next-hop reachability.

---

## 74. ARP and `ip neigh` Together

Use:

```bash
ip neigh
```

and:

```bash
sudo tcpdump -nn -i ens5 arp
```

together.

`ip neigh` shows kernel neighbor state.

`tcpdump` shows ARP packets being exchanged.

For example:

```text
ip neigh:
192.168.1.1 FAILED
```

Capture:

```text
ARP request
ARP request
ARP request
No reply
```

The two pieces of evidence reinforce each other.

---

# HTTP Packet Analysis

## 75. Unencrypted HTTP

Traditional HTTP traffic can be visible in plaintext packet captures.

For example:

```text
Client -> Server

GET /health HTTP/1.1
Host: app.example.com
```

Server:

```text
HTTP/1.1 200 OK
```

This can make HTTP troubleshooting straightforward.

---

Example:

```bash
sudo tcpdump -nn -i any tcp port 80
```

For payload-oriented inspection, `tcpdump` has additional output options, but exposing application payloads can reveal sensitive information.

Use them only in authorized lab environments or when operationally justified.

---

For unencrypted HTTP that Wireshark recognizes:

```text
http
```

You can inspect:

```text

Host
Path
Headers
Status code
Response information
```

This is useful for understanding application-layer communication.

---

# TLS Visibility and Limitations

## 78. HTTPS Changes What You Can See

Consider:

```text
HTTP
```

versus:

```text
HTTPS
```

With HTTPS, application data is protected by TLS.

A packet capture can still reveal substantial network metadata, but normally cannot simply display encrypted HTTP application contents as plaintext.

---

## 79. What You Can Still Observe With TLS

Depending on protocol/version and circumstances, you may still observe information such as:

```text
Source IP
Destination IP
Source port
Destination port
TCP handshake
Packet sizes
Packet timing
TCP resets
TCP retransmissions
TLS handshake messages
Certificate-related information in applicable TLS handshakes
Some TLS negotiation metadata
```

Not all TLS versions expose exactly the same metadata.

---

## 80. What TLS Normally Hides

Without appropriate decryption material, encrypted TLS application data prevents you from simply reading things such as:

```text
HTTP request body
Passwords
API response body
Session contents
Most application payload
```

That is the point of encryption.

---

## 81. Do Not Assume Port 443 Means HTTPS

Port 443 commonly carries HTTPS.

But ports do not define protocols.

A service could technically run another protocol on port 443.

Likewise, HTTPS can run on another port.

Protocol analysis should consider actual traffic, not merely port numbers.

---

## 82. HTTP/3 Changes the Transport Picture

HTTP/1.1 and HTTP/2 commonly use TCP for HTTPS.

HTTP/3 uses QUIC over UDP.

Therefore a modern web investigation may involve:

```text
UDP 443
```

rather than:

```text
TCP 443
```

If you capture only:

```text
tcp port 443
```

you can miss HTTP/3 traffic.

This is an excellent example of why filters must match the actual architecture.

# Saving Packet Captures

## 83. Why Save a Capture?

Live terminal output is useful for quick checks.

For deeper analysis, save the packets.

Example:

```bash
sudo tcpdump -i ens5 -w capture.pcap
```

`-w` writes captured packets to a file.

## 84. Do Not Expect Human-Readable Output With `-w`

When using:

```bash
-w capture.pcap
```

`tcpdump` writes packet data in capture-file format rather than printing the normal packet summaries to your terminal.

You analyze the file afterward.

PCAP is a common packet-capture file format.

You may encounter extensions such as:

```text

.pcapng
```

Wireshark commonly works with both, while exact tool support and format details can vary.

A capture file contains packet data and associated capture metadata.

Benefits:

```text
Faster investigation

```


## 92. Packet Length and Snapshots

Packet-capture tools may capture a configured number of bytes from each packet.

This is called the snapshot length or snaplen.

Modern defaults are often sufficient for many investigations, but understanding snaplen matters when payload/header details appear truncated.

With `tcpdump`, `-s` controls snapshot length.

For example:

```bash
sudo tcpdump -s 0 -i ens5
```

historically means capture the full packet according to `tcpdump` semantics.

Use full-packet capture carefully because it increases:

```text
File size
Sensitive-data exposure
Storage requirements
```

# Troubleshooting Packet Loss

## 95. What Packet Loss Looks Like

Packet loss can manifest as:

```text
TCP retransmissions
Duplicate acknowledgments
Delayed communication
Application timeouts
Reduced throughput
```

But packet capture requires careful interpretation.

---

## 96. Capture Loss vs Network Loss

This is extremely important.

Suppose Wireshark says packets appear missing.

Possibility 1:

```text
Packets were actually lost on the network.
```

Possibility 2:

```text
The capture system failed to record them.
```

A busy host can drop packets during capture.

Therefore:

> Missing from the PCAP does not always mean missing from the network.

---

## 97. Check Capture Statistics

When stopping `tcpdump`, inspect its summary.

It may report information about packets:

```text
captured
received by filter
dropped by kernel
```

Exact wording and behavior depend on platform.

If the capture process itself dropped significant traffic, your analysis may be incomplete.

---

## 98. Capture From Multiple Points

For difficult packet-loss investigations:

```text
Client capture
+
Server capture
```

can be much more informative than either alone.

Example:

Client:

```text
Packet A sent
Packet B sent
Packet C sent
```

Server:

```text
Packet A received
Packet C received
```

If the captures are reliable and synchronized sufficiently for the investigation, this suggests Packet B disappeared between those observation points.

# Troubleshooting Connection Timeouts Systematically

## 100. Scenario

Application server:

```text
10.10.1.20
```

Database:

```text
10.10.2.30:5432
```

Application reports:

```text

```

```bash

```



Repeat the failed connection.

You reproduce the application failure.

Capture shows:

```text

```

```text
Wrong capture interface
Wrong destination IP
```

```text
SYN
```

## 103. Pattern C: SYN, RST


## 104. Pattern D: Handshake Completes

```text

SYN-ACK
ACK
```

Then TCP connectivity exists.

```text

Database protocol?
Authentication?
Application request?
```

# Packet Capture in Cloud Environments

## 155. Cloud Networking

On a cloud VM, `tcpdump` can show packets visible to the VM's networking stack.

But cloud networking also includes controls outside the guest OS:

```text
Security groups
Network ACLs
Virtual routers
Load balancers
NAT gateways
Cloud firewalls
```

A packet dropped before reaching the VM cannot appear in a packet capture taken inside that VM.

This is a fundamental limitation.


shows nothing.

That does not prove:

```text
The client sent nothing.
```

It proves:

```text
The packet was not observed at this VM capture point.
```

Capture location matters again.

# Common Beginner Packet Capture Mistakes

## 161. Mistake: Capturing Everything

Running:

```bash
sudo tcpdump -i any
```

on a busy production host can produce overwhelming output.

Filter based on the incident.

---

## 162. Mistake: Choosing the Wrong Interface

You capture:

```text
eth0
```

while traffic uses:

```text
ens5
```

Result:

```text
No packets.
```

You incorrectly conclude:

```text
Application sent nothing.
```

Always verify the interface.

---

## 163. Mistake: Forgetting IPv6

You filter:

```text
host 192.0.2.20
```

but the application actually connects to an IPv6 address from an AAAA record.

Your capture appears empty.

Check:

```bash
dig A example.com
```

and:

```bash
dig AAAA example.com
```

and inspect actual application behavior.

---

## 164. Mistake: Filtering Only TCP 443

Modern browser traffic may use:

```text
QUIC
UDP 443
```

for HTTP/3.

A TCP-only filter can miss it.

---

## 165. Mistake: Assuming No Response Means Firewall

Repeated SYNs without response tell you the expected response was not observed.

They do not identify the exact device responsible.

---

## 166. Mistake: Assuming RST Means Application Failure

A reset can originate from different components depending on the architecture.

Determine:

```text
When did reset occur?

Who appears to send it?

Where was capture taken?

What does capture from other points show?
```

---

## 167. Mistake: Assuming Wireshark Analysis Labels Are Perfect

Wireshark performs sophisticated analysis, but it only knows about packets in the capture.

If the capture missed packets, Wireshark may interpret the conversation differently from what actually occurred on the network.

---

## 168. Mistake: Ignoring Timestamps

Packet order alone is not enough.

Timing can reveal:

```text
Slow handshake
Delayed response
Timeout
Retransmission
Application processing delay
```

---

## 169. Mistake: Capturing After the Failure

The TCP handshake may already be over.

Start capture first.

Then reproduce.

---

## 170. Mistake: Treating Encrypted Traffic as Invisible

TLS hides application contents, but you can still investigate:

```text
TCP establishment
IP endpoints
Ports
Timing
Resets
Retransmissions
Some handshake metadata
```

Encryption does not make packet capture useless.

---

## 171. Mistake: Treating Encryption as Broken Because You Cannot Read Payload

If Wireshark shows:

```text
Application Data
```

instead of readable HTTP, that may simply mean TLS is working as intended.

---

## 172. Mistake: Sharing PCAPs Carelessly

PCAP files can contain sensitive information.

Treat them similarly to:

```text
Production logs
Database exports
Debug dumps
```

and sometimes even more carefully.

# A Complete Investigation Example

## 180. Production Scenario

Architecture:

```text
Users
  |
  v
Load Balancer
  |
  v
Web Server
10.20.1.20
  |
  | HTTPS
  v
API Server
10.20.2.30:443
```

Web server logs:

```text
API connection timeout after 10 seconds
```

Your mission:

> Determine whether the timeout is caused by DNS, routing, TCP, TLS, or the application.

---

## 181. Step 1: DNS

Run:

```bash
dig api.internal.example
```

Response:

```text
10.20.2.30
```

DNS appears to provide the expected address for this test.

---

## 182. Step 2: Routing

Run:

```bash
ip route get 10.20.2.30
```

Suppose Linux returns:

```text
10.20.2.30 via 10.20.1.1 dev ens5 src 10.20.1.20
```

A route exists.

---

## 183. Step 3: Transport Test

Run:

```bash
nc -vz 10.20.2.30 443
```

It times out.

Now packet capture becomes valuable.

---

## 184. Step 4: Capture on Web Server

Run:

```bash
sudo tcpdump -nn -i ens5 'host 10.20.2.30 and tcp port 443'
```

Repeat the connection.

Observed:

```text
10.20.1.20:53001 -> 10.20.2.30:443 SYN

10.20.1.20:53001 -> 10.20.2.30:443 SYN

10.20.1.20:53001 -> 10.20.2.30:443 SYN
```

No reply.

---

## 185. What Can We Conclude?

We know:

```text
Application host has a route.

TCP connection attempts are leaving the observed interface.

No TCP response is observed returning to this capture point.
```

We do **not** yet know exactly where the packets disappear.

---

## 186. Step 5: Capture on API Server

Run on API server:

```bash
sudo tcpdump -nn -i any 'host 10.20.1.20 and tcp port 443'
```

Repeat test.

Suppose:

```text
No matching packets appear.
```

Now the evidence is:

```text
Web Server
SYN observed leaving
      |
      v
Network
      |
      X
      |
API Server
SYN not observed
```

Investigate the network path between them.

---

## 187. Firewall Investigation

You discover a network firewall policy permits:

```text
10.20.1.0/24 -> 10.20.2.0/24 TCP 80
```

but not:

```text
TCP 443
```

After the approved firewall change, repeat the test.

---

## 188. New Capture

Web server:

```text
SYN
SYN-ACK
ACK
```

Then TLS traffic begins.

`curl` succeeds.

Root cause:

```text
Network firewall policy blocked TCP 443
between the web and API networks.
```

---

## 189. Why This Investigation Was Strong

You did not begin by:

```text
Restarting application
Restarting networking
Changing DNS
Disabling host firewall
Changing routes
Rebooting servers
```

You established:

```text
DNS result
Route
TCP behavior
Client capture
Server capture
Firewall evidence
```

Every step narrowed the problem.

That is professional network troubleshooting.

# 215. Final Mental Model

Packet troubleshooting should become a structured investigation:

```text
Define the exact failure
        |
        v
Identify source and destination
        |
        v
Identify protocol and port
        |
        v
Check interface/address
        |
        v
Check route
        |
        v
Choose capture point
        |
        v
Choose interface
        |
        v
Apply narrow capture filter
        |
        v
Start capture
        |
        v
Reproduce failure
        |
        v
Find the first unexpected packet event
        |
        v
Move capture point if necessary
        |
        v
Correlate with logs/configuration
        |
        v
Identify root cause
```

And when reading packets, keep asking:

```text
What did I expect?

What did I observe?

What should have happened next?

Did it happen?

If not, between which two observation points did the expected behavior disappear?
```

That is the real value of `tcpdump` and Wireshark.

They move network troubleshooting from:

```text
"I think the firewall is broken."
```

to:

```text
"The client SYN leaves ens5.

The server never observes that SYN.

Therefore the failure is between these two capture points.

Now we can investigate the routing and filtering controls on that path."
```

That transition from **guessing to packet-level evidence** is one of the most important skills you can develop in networking, Linux administration, DevOps, SRE, cloud engineering, and production incident response.
