# Part 6: Conditional Statements and Decision Making

In Part 5, you learned that every command returns an exit status.

The fundamental convention is:

```text
0        = success
non-zero = non-success or failure condition
```

You also learned how Bash can react to those statuses with:

```bash
command1 && command2
```

and:

```bash
command1 || command2
```

Those operators are useful for short execution decisions.

But real automation quickly becomes more complicated.

Imagine a deployment script that needs to decide:

```text
Is the environment development?
    |
    +-- Yes --> use development configuration
    |
    +-- No --> Is it staging?
                  |
                  +-- Yes --> use staging configuration
                  |
                  +-- No --> Is it production?
                                |
                                +-- Yes --> require extra validation
                                |
                                +-- No --> reject the environment
```

Or imagine a server validation script:

```text
Does configuration file exist?
        |
        v
Is it readable?
        |
        v
Is required directory present?
        |
        v
Is disk usage acceptable?
        |
        v
Is required command installed?
        |
        v
Is environment valid?
```

Writing all of this with long chains of `&&` and `||` would quickly become difficult to read and maintain.

Bash therefore provides structured conditional statements.

The most important are:

```bash
if
then
elif
else
fi
```

Bash also provides testing mechanisms such as:

```bash
[ ]
```

and:

```bash
[[ ]]
```

as well as:

```bash
case
```

for situations where one value may match several possible choices.

By the end of Part 6, you should understand:

* why scripts need conditional logic
* how `if`, `then`, `else`, `elif`, and `fi` work
* how Bash uses command exit statuses as conditions
* what the `test` command is
* how `[ ]` works
* how `[[ ]]` works
* important differences between `[ ]` and `[[ ]]`
* numeric comparisons
* string comparisons
* file and directory tests
* permission tests
* empty and non-empty values
* how to check whether variables exist
* how to combine conditions with `&&` and `||`
* pattern matching
* regular-expression matching with `=~`
* how `case` statements work
* when `case` is clearer than multiple `if` blocks
* how to create menu-based scripts
* how scripts can behave differently in development, staging, and production
* how to build a practical server validation script

# 1. Why Scripts Need Conditional Logic

A simple script can execute commands sequentially:

```bash
command1
command2
command3
```

But this assumes the same commands should always run.

Real systems rarely behave that way.

Your script may need to ask:

```text
Does this file exist?

Is this directory writable?

Did the previous command succeed?

Is the user root?

Is this server production?

Is the supplied argument valid?

Is the disk nearly full?

Is the application configuration missing?

Is this service enabled?

Is the deployment environment staging?

Did the user select option 2?
```

The answer determines what happens next.

This is **conditional logic**.

Conceptually:

```text
Observe condition
       |
       v
    True?
   /     \
 Yes      No
  |        |
  v        v
Action A  Action B
```

Without conditional logic, scripts mostly execute instructions.

With conditional logic, scripts can make decisions based on the state they observe.

Suppose you are writing a deployment script.

You may want:

```text
Application tests pass?
        |
       Yes

        v
Configuration exists?
        |
       Yes
        |
        v

       / \
     Yes  No
      |    |
      v    v
Extra     Normal
checks    deployment
```

Another script might inspect disk usage:

```text
Disk usage > 90%?
      |
   +--+--+
   |     |
  Yes    No
   |     |
   v     v
Alert   Continue
```

Conditional logic appears throughout:

* deployment scripts
* server administration
* CI/CD pipelines
* installation scripts
* health checks
* backup scripts
* cloud automation
* container entrypoints
* monitoring utilities
* configuration validation
* security checks

# 3. Bash Does Not Need a Boolean Value

Many programming languages have explicit Boolean values:

```text
true
false
```

Bash often makes decisions differently.

Remember Part 5:

```text
exit status 0
      |
      v
   success
```

and:

```text
non-zero
   |
   v
non-success
```

Bash conditional structures can directly evaluate commands.

Example:

```bash
if command -v git > /dev/null 2>&1
then
    printf 'Git is available\n'
fi
```

Bash runs:

```bash
command -v git
```

and examines its exit status.

If the command returns `0`, the `then` section executes.

This is one of the most important ideas in Bash.

---

# 4. Your First `if` Statement

The basic structure is:

```bash
if command
then
    commands
fi
```

Example:

```bash
if command -v bash > /dev/null 2>&1
then
    printf 'Bash is installed\n'
fi
```

Read it as:

```text
IF command -v bash succeeds
THEN
    print Bash is installed
END IF
```

The word:

```bash
fi
```

ends the `if` statement.

Notice that `fi` is `if` reversed.

---

# 5. Understanding `if`

Consider:

```bash
if command -v git > /dev/null 2>&1
then
    printf 'Git found\n'
fi
```

Execution flow:

```text
command -v git
      |
      v
exit status?
   /       \
  0       non-zero
  |          |
  v          |
then block   |
  |          |
  +-----+----+
        |
        v
      fi
```

If Git is available, the condition succeeds.

If Git is unavailable, Bash skips the `then` block.

---

# 6. `then`

The keyword:

```bash
then
```

marks the commands that should execute when the condition succeeds.

Example:

```bash
if test -d "$HOME"
then
    printf 'Home directory exists\n'
fi
```

The condition is:

```bash
test -d "$HOME"
```

The action is:

```bash
printf 'Home directory exists\n'
```

---

# 7. `fi`

Every normal Bash `if` statement must eventually be closed with:

```bash
fi
```

Example:

```bash
if command
then
    action
fi
```

A common beginner error is forgetting `fi`.

For example:

```bash
if command -v git > /dev/null
then
    printf 'Git exists\n'
```

Bash reaches the end while still expecting the conditional structure to be completed.

You may receive a syntax error.

---

# 8. Writing `then` on the Same Line

You may also encounter:

```bash
if command -v git > /dev/null 2>&1; then
    printf 'Git exists\n'
fi
```

The semicolon separates the condition from `then`.

Both styles are valid:

```bash
if condition
then
    action
fi
```

and:

```bash
if condition; then
    action
fi
```

For this series, we will often use the second style because it is common in production Bash scripts:

```bash
if condition; then
    action
fi
```

---

# 9. Adding `else`

Often you need one action when the condition succeeds and another when it fails.

Structure:

```bash
if condition; then
    action_if_true
else
    action_if_false
fi
```

Example:

```bash
if command -v git > /dev/null 2>&1; then
    printf 'Git is installed\n'
else
    printf 'Git is not installed\n'
fi
```

Flow:

```text
Is Git available?
     |
   +-+-+
   |   |
  Yes  No
   |   |
   v   v
Print Print
found missing
   |   |
   +---+
     |
     v
    fi
```

---

# 10. `if` Is Clearer Than Complex `&&` and `||`

In Part 5, you saw:

```bash
command && success_action || failure_action
```

This is compact, but it has important edge cases.

Structured logic is usually clearer:

```bash
if command; then
    success_action
else
    failure_action
fi
```

For meaningful decision-making, prefer clarity.

A script may need to be debugged by another engineer during an incident.

Readable code matters.

---

# 11. Adding `elif`

Sometimes there are more than two possibilities.

Suppose:

```text
environment = development
environment = staging
environment = production
```

You could use:

```bash
if [[ "$environment" == "development" ]]; then
    printf 'Development environment\n'
elif [[ "$environment" == "staging" ]]; then
    printf 'Staging environment\n'
elif [[ "$environment" == "production" ]]; then
    printf 'Production environment\n'
else
    printf 'Unknown environment\n'
fi
```

`elif` means:

> Else, if this other condition is true...

---

# 12. How `elif` Flows

Conceptually:

```text
Condition 1?
   |
 +-+-+
 |   |
Yes  No
 |    |
 v    v
 A  Condition 2?
       |
     +-+-+
     |   |
    Yes  No
     |    |
     v    v
     B  Condition 3?
           |
         +-+-+
         |   |
        Yes  No
         |    |
         v    v
         C    D
```

Once one branch succeeds, the remaining branches are skipped.

---

# 13. Full `if` Structure

A complete structure can look like:

```bash
if condition1; then
    commands
elif condition2; then
    commands
elif condition3; then
    commands
else
    commands
fi
```

You do not need every keyword every time.

Valid:

```bash
if condition; then
    commands
fi
```

Also valid:

```bash
if condition; then
    commands
else
    commands
fi
```

Also valid:

```bash
if condition1; then
    commands
elif condition2; then
    commands
else
    commands
fi
```

# 14. The `test` Command

How do you ask questions such as:

> Does this file exist?

> Is this number greater than 10?

> Is this string empty?

Bash provides the `test` command.

Example:

```bash
test -d "$HOME"
```

This tests whether:

```bash
"$HOME"
```

refers to a directory.

The command usually prints nothing.

Instead, it communicates through its exit status.

Try:

```bash
test -d "$HOME"
echo "$?"
```

You should normally receive:

```text
0
```

Now:

```bash
test -d /definitely-not-a-real-directory
echo "$?"
```

You should receive a non-zero status.

---

# 15. `test` Works Naturally with `if`

Instead of manually inspecting `$?`:

```bash
test -d "$HOME"
status=$?
```

you can write:

```bash
if test -d "$HOME"; then
    printf 'Home directory exists\n'
fi
```

Bash evaluates the exit status directly.

This is an important Bash pattern:

```text
Command performs test
       |
       v
Returns exit status
       |
       v
if evaluates status
       |
   +---+---+
   |       |
success  failure
```

---

# 16. The `[ ]` Test Syntax

Bash and other shells commonly use:

```bash
[ condition ]
```

Example:

```bash
if [ -d "$HOME" ]; then
    printf 'Home directory exists\n'
fi
```

This is closely related to the `test` command.

These:

```bash
test -d "$HOME"
```

and:

```bash
[ -d "$HOME" ]
```

perform equivalent tests in this example.

---

# 17. `[ ]` Is Not Decorative Punctuation

Beginners often think:

```bash
[ condition ]
```

works like parentheses in mathematics.

It does not.

`[` is effectively a command form of `test`, and the closing `]` is required syntax for that form.

This is why spaces matter.

Correct:

```bash
[ "$environment" = "production" ]
```

Incorrect:

```bash
["$environment" = "production"]
```

Correct:

```text
[ SPACE condition SPACE ]
```

Those spaces are essential.

---

# 18. Verify `[` Yourself

Run:

```bash
type [
```

Depending on your shell, you may see that `[` is available as a shell builtin.

You can also try:

```bash
help [
```

in Bash.

This helps reinforce that `[` is not merely visual punctuation.

# 19. The `[[ ]]` Conditional Expression

Bash also provides:

```bash
[[ condition ]]
```

Example:

```bash
if [[ "$environment" == "production" ]]; then
    printf 'Production environment\n'
fi
```

`[[ ]]` is a Bash conditional construct.

It provides safer and more powerful behavior for many Bash-specific scripts.

It supports features such as:

* easier string comparisons
* logical operators
* pattern matching
* regular-expression matching

---

# 20. `[ ]` vs `[[ ]]`

At first they look almost identical:

```bash
[ "$environment" = "production" ]
```

versus:

```bash
[[ "$environment" == "production" ]]
```

But they are not identical.

A useful beginner distinction is:

```text
[ ]
|
+--> traditional test syntax
+--> broadly portable across POSIX-style shells
+--> quoting is especially important
```

and:

```text
[[ ]]
|
+--> Bash/Ksh-style conditional construct
+--> more expressive
+--> safer for many string operations
+--> supports pattern matching
+--> supports =~ regular expressions
```

If you are deliberately writing Bash scripts, `[[ ]]` is often preferable for conditional expressions.

If you need strict POSIX `sh` portability, `[ ]` is more portable.

---

# 21. Why Quoting Still Matters

From Part 3, remember that variables can contain:

* spaces
* empty values
* wildcard characters
* special characters

With `[ ]`, quoting variable expansions is especially important.

Prefer:

```bash
[ "$name" = "Ann Felix" ]
```

rather than:

```bash
[ $name = "Ann Felix" ]
```

With `[[ ]]`, Bash handles word splitting and filename expansion differently, making many variable comparisons safer.

Still, consistent readable quoting is often useful.

# 22. Numeric Comparisons

Suppose:

```bash
disk_usage=75
```

You want to determine whether it exceeds a threshold.

With `[ ]`, numeric operators include:

```text
-eq   equal
-ne   not equal
-lt   less than
-le   less than or equal
-gt   greater than
-ge   greater than or equal
```

Example:

```bash
if [ "$disk_usage" -gt 70 ]; then
    printf 'Disk usage is above 70%%\n'
fi
```

Notice:

```bash
%%
```

inside `printf`.

That prints a literal `%`.

---

# 23. Numeric Operator Meanings

| Operator | Meaning                  |
| -------- | ------------------------ |
| `-eq`    | equal to                 |
| `-ne`    | not equal to             |
| `-lt`    | less than                |
| `-le`    | less than or equal to    |
| `-gt`    | greater than             |
| `-ge`    | greater than or equal to |

Example:

```bash
users=5

if [ "$users" -eq 5 ]; then
    printf 'Exactly five users\n'
fi
```

---

# 24. Greater Than

Example:

```bash
memory_usage=82

if [ "$memory_usage" -gt 80 ]; then
    printf 'WARNING: memory usage is high\n'
fi
```

Flow:

```text
82 > 80?
   |
  Yes
   |
   v
Print warning
```

---

# 25. Less Than

Example:

```bash
free_space=15

if [ "$free_space" -lt 20 ]; then
    printf 'WARNING: free space is low\n'
fi
```

---

# 26. Greater Than or Equal

Example:

```bash
disk_usage=90

if [ "$disk_usage" -ge 90 ]; then
    printf 'CRITICAL: disk threshold reached\n'
fi
```

This succeeds when the value is:

```text
90
```

or greater.

---

# 27. Numeric Ranges

Suppose:

```bash
disk_usage=75
```

You want:

```text
0–69    healthy
70–89   warning
90+     critical
```

You can write:

```bash
if [ "$disk_usage" -ge 90 ]; then
    printf 'CRITICAL\n'
elif [ "$disk_usage" -ge 70 ]; then
    printf 'WARNING\n'
else
    printf 'HEALTHY\n'
fi
```

Why does the second condition not need:

```text
less than 90
```

Because Bash reaches the second branch only if the first condition was false.

So by the time:

```bash
elif [ "$disk_usage" -ge 70 ]
```

runs, you already know the value is below 90.

# 28. Arithmetic Conditions with `(( ))`

Because you learned arithmetic expansion in Part 3, you should also know that Bash provides arithmetic evaluation:

```bash
(( expression ))
```

For numeric logic, this can be easier to read.

Example:

```bash
disk_usage=75

if (( disk_usage > 70 )); then
    printf 'Disk usage is high\n'
fi
```

Inside arithmetic context, familiar operators can be used:

```text
==
!=
<
<=
>
>=
```

Example:

```bash
if (( disk_usage >= 90 )); then
    printf 'CRITICAL\n'
fi
```

For Bash-specific numeric logic, `(( ))` is often very readable.

# 29. Do Not Confuse Numeric and String Comparisons

This is important.

Numeric:

```bash
[ "$number" -eq 10 ]
```

String:

```bash
[ "$name" = "server01" ]
```

Do not casually interchange them.

Bash needs to know whether you are comparing numbers or text.

# 30. String Comparisons

Suppose:

```bash
environment="production"
```

You can test:

```bash
if [[ "$environment" == "production" ]]; then
    printf 'Production mode\n'
fi
```

String equality:

```text
==
```

within `[[ ]]`.

String inequality:

```text
!=
```

Example:

```bash
if [[ "$environment" != "production" ]]; then
    printf 'Not production\n'
fi
```

---

# 31. String Comparison with `[ ]`

Traditional syntax:

```bash
if [ "$environment" = "production" ]; then
    printf 'Production mode\n'
fi
```

For portability, single `=` is commonly used with `[ ]`.

In Bash, `==` may also work inside `[ ]`, but:

```bash
=
```

is the portable choice for traditional test syntax.

# 32. Empty Strings

Suppose:

```bash
username=""
```

You can check whether it is empty:

```bash
if [[ -z "$username" ]]; then
    printf 'Username is empty\n'
fi
```

`-z` means the string has zero length.

Think:

```text
-z
 |
 v
zero-length string?
```

---

# 33. Non-Empty Strings

Use:

```bash
-n
```

to test whether a string is non-empty.

Example:

```bash
username="ann"

if [[ -n "$username" ]]; then
    printf 'Username provided: %s\n' "$username"
fi
```

Think:

```text
-n
 |
 v
non-zero string length?
```

# 34. Empty vs Unset Variables

These are related but different.

An empty variable:

```bash
environment=""
```

exists but contains an empty value.

An unset variable:

```bash
unset environment
```

does not currently have a value assigned in the shell.

These situations can behave similarly during simple expansion:

```bash
printf '<%s>\n' "$environment"
```

may print:

```text
<>
```

for both.

But sometimes your script needs to distinguish them.

---

# 35. Checking Whether a Variable Exists

In Bash, one useful approach is the `-v` conditional operator.

Example:

```bash
if [[ -v environment ]]; then
    printf 'environment variable is set\n'
else
    printf 'environment variable is unset\n'
fi
```

Notice that with `-v`, you are asking whether the variable itself is set.

Now:

```bash
environment=""
```

and:

```bash
[[ -v environment ]]
```

still succeeds because the variable exists even though its value is empty.

---

# 36. Set vs Non-Empty

These questions are different:

```text
Does the variable exist?
```

versus:

```text
Does the variable contain a non-empty value?
```

Example:

```bash
environment=""
```

Then:

```bash
[[ -v environment ]]
```

is true.

But:

```bash
[[ -n "$environment" ]]
```

is false.

This distinction is useful for configuration validation.

# 37. Parameter Expansion for Required Values

From Part 3, you also learned parameter expansion.

For example:

```bash
${VARIABLE:-default}
```

Conditional logic and parameter expansion often work together.

Suppose:

```bash
environment="${APP_ENV:-development}"
```

If `APP_ENV` is unset or empty, the script uses:

```text
development
```

Then you can validate:

```bash
if [[ "$environment" == "production" ]]; then

fi
```

# 38. File Tests

Scripts frequently need to inspect filesystem state.

Common file tests include:

```text
-e   exists
-f   regular file
-d   directory
-r   readable
-w   writable
-x   executable
-s   exists and has size greater than zero
-L   symbolic link
```

These tests allow scripts to validate prerequisites before acting.

---

# 39. Testing Whether Something Exists

Example:

```bash
config_file="app.conf"

if [[ -e "$config_file" ]]; then
    printf 'Configuration path exists\n'
fi
```

`-e` asks whether the path exists.

But it does not specifically require a regular file.

---

# 40. Testing for a Regular File

Use:

```bash
-f
```

Example:

```bash
config_file="app.conf"

if [[ -f "$config_file" ]]; then
    printf 'Configuration file exists\n'
else
    printf 'Configuration file missing\n' >&2
fi
```

This is usually better when your script specifically requires a regular file.

---

# 41. File Existence vs File Type

Suppose:

```text
app.conf
```

exists, but it is actually a directory.

Then:

```bash
[[ -e app.conf ]]
```

may succeed.

But:

```bash
[[ -f app.conf ]]
```

will not consider it a regular file.

Ask the most specific question your script actually needs.

Do not merely ask:

> Does something exist at this path?

if the real requirement is:

> Is there a readable regular configuration file at this path?

---

# 42. Directory Tests

Use:

```bash
-d
```

Example:

```bash
log_directory="/var/log"

if [[ -d "$log_directory" ]]; then
    printf 'Log directory exists\n'
else
    printf 'Log directory missing\n' >&2
fi
```

This is common in:

* backup scripts
* deployment scripts
* log processors
* installation scripts
* application startup scripts

---

# 43. Read Permission Test

Use:

```bash
-r
```

Example:

```bash
config_file="app.conf"

if [[ -r "$config_file" ]]; then
    printf 'Configuration is readable\n'
else
    printf 'Configuration cannot be read\n' >&2
fi
```

This asks whether the current process can read the path according to the test semantics.

---

# 44. Write Permission Test

Use:

```bash
-w
```

Example:

```bash
output_directory="$HOME/bash-lab/output"

if [[ -w "$output_directory" ]]; then
    printf 'Output directory is writable\n'
else
    printf 'Output directory is not writable\n' >&2
fi
```

This can help prevent an operation from failing later when it attempts to create output.

---

# 45. Executable Test

Use:

```bash
-x
```

Example:

```bash
script="./deploy.sh"

if [[ -x "$script" ]]; then
    printf 'Deployment script is executable\n'
else
    printf 'Deployment script is not executable\n' >&2
fi
```

This relates directly to Part 2, where you learned:

```bash
chmod +x script.sh
```

---

# 46. Non-Empty File Test

Use:

```bash
-s
```

Example:

```bash
log_file="app.log"

if [[ -s "$log_file" ]]; then
    printf 'Log file contains data\n'
else
    printf 'Log file is empty or unavailable\n'
fi
```

This can be useful when merely existing is not enough.

---

# 47. Symbolic Link Test

A symbolic link is a filesystem object that points to another path.

You will encounter symlinks frequently on Linux.

A common test is:

```bash
-L
```

Example:

```bash
if [[ -L "$HOME/current-app" ]]; then
    printf 'current-app is a symbolic link\n'
fi
```

You do not need advanced symlink administration yet.

For now, know that Bash can distinguish filesystem object types.

---

# 48. Combining File Conditions

Suppose a configuration file must:

1. exist as a regular file
2. be readable

You could test both:

```bash
if [[ -f "$config_file" && -r "$config_file" ]]; then
    printf 'Configuration file is ready\n'
fi
```

Read this as:

```text
regular file
    AND
readable
```

Both must be true.

---

# 49. Logical AND Inside `[[ ]]`

Example:

```bash
if [[ -f "$config_file" && -r "$config_file" ]]; then
    printf 'Configuration is usable\n'
fi
```

Flow:

```text
Is regular file?
       |
      Yes
       |
       v
Is readable?
       |
      Yes
       |
       v
Run then block
```

If either condition is false, the combined AND condition is false.

---

# 50. Logical OR Inside `[[ ]]`

Suppose either environment is acceptable:

```bash
if [[ "$environment" == "development" || "$environment" == "staging" ]]; then
    printf 'Non-production deployment mode\n'
fi
```

Read:

```text
environment is development
          OR
environment is staging
```

Only one needs to match.

---

# 51. `&&` and `||` Have More Than One Context

You have now seen:

```bash
command1 && command2
```

at the command-list level.

You can also use logical operators inside:

```bash
[[ condition1 && condition2 ]]
```

Example:

```bash
if [[ -f "$config_file" && -r "$config_file" ]]; then
    ...
fi
```

The concepts are related, but the syntax context is different.

Be careful not to treat every occurrence as identical punctuation.

---

# 52. Grouping Conditions

Suppose you need:

> Environment is staging OR production, AND configuration file exists.

You can make the logic explicit:

```bash
if [[ ( "$environment" == "staging" || "$environment" == "production" ) && -f "$config_file" ]]; then
    printf 'Environment and configuration are valid\n'
fi
```

The parentheses clarify how conditions are grouped inside `[[ ]]`.

Readable logic is especially important as conditions grow.

---

# 53. Avoid Overly Complex Conditions

This may technically be possible:

```bash
if [[ condition1 && condition2 || condition3 && condition4 || condition5 ]]; then
    ...
fi
```

But ask whether another engineer can understand it quickly.

Sometimes this is clearer:

```bash
if condition1; then
    ...
elif condition2; then
    ...
else
    ...
fi
```

Or calculate meaningful intermediate values.

The goal is maintainable automation, not maximum compression.

---

# 54. Pattern Matching

Suppose you have:

```bash
hostname="web-prod-01"
```

You want to know whether it begins with:

```text
web-
```

Inside `[[ ]]`, Bash supports pattern matching.

Example:

```bash
if [[ "$hostname" == web-* ]]; then
    printf 'Web server detected\n'
fi
```

The pattern:

```text
web-*
```

means:

```text
starts with "web-"
followed by zero or more characters
```

---

# 55. Important Pattern Quoting Rule

Compare:

```bash
[[ "$hostname" == web-* ]]
```

with:

```bash
[[ "$hostname" == "web-*" ]]
```

These are not equivalent.

Unquoted:

```text
web-*
```

acts as a pattern.

Quoted:

```text
"web-*"
```

is treated literally.

So the quoted version looks for the actual characters:

```text
web-*
```

including the asterisk.

This is a situation where quoting changes semantics.

---

# 56. Pattern Matching Examples

Suppose:

```bash
server="api-prod-03"
```

Starts with `api-`:

```bash
if [[ "$server" == api-* ]]; then
    printf 'API server\n'
fi
```

Ends with `-03`:

```bash
if [[ "$server" == *-03 ]]; then
    printf 'Server number 03\n'
fi
```

Contains `prod`:

```bash
if [[ "$server" == *prod* ]]; then
    printf 'Production-style hostname detected\n'
fi
```

---

# 57. Pattern Matching Is Not Regex

This is important.

Bash patterns such as:

```text
web-*
```

are **globbing patterns**.

They are not regular expressions.

For example, in glob patterns:

```text
*
```

means:

> match any sequence of characters

Regular expressions use different rules.

Do not assume glob syntax and regex syntax are interchangeable.

---

# 58. Regular Expressions with `=~`

Bash `[[ ]]` supports regular-expression matching with:

```bash
=~
```

Example:

```bash
server="web-prod-01"

if [[ "$server" =~ ^web- ]]; then
    printf 'Hostname starts with web-\n'
fi
```

The regex:

```text
^web-
```

means:

```text
^      beginning of string
web-   literal characters
```

---

# 59. Basic Regex Example

Suppose server names follow:

```text
web-01
web-02
web-123
```

You might validate:

```bash
server="web-01"

if [[ "$server" =~ ^web-[0-9]+$ ]]; then
    printf 'Valid web server name\n'
else
    printf 'Invalid web server name\n'
fi
```

Breakdown:

```text
^
```

start of string

```text
web-
```

literal prefix

```text
[0-9]
```

one digit

```text
+
```

one or more of the preceding pattern

```text
$
```

end of string

So:

```text
^web-[0-9]+$
```

means approximately:

> The entire string must be `web-` followed by one or more digits.

---

# 60. Regex Matching and Quoting

With Bash:

```bash
[[ "$value" =~ regex ]]
```

the regex is normally left unquoted when you want its regex metacharacters to operate as a regular expression.

For example:

```bash
[[ "$server" =~ ^web-[0-9]+$ ]]
```

Quoting the entire regex can change matching behavior.

This is different from ordinary variable-safety rules.

Again, context matters.

---

# 61. Store Complex Regex in a Variable

For readability, you can store a regex:

```bash
server_pattern='^web-[0-9]+$'
```

Then:

```bash
if [[ "$server" =~ $server_pattern ]]; then
    printf 'Valid server name\n'
fi
```

This is often easier to maintain than placing a long regex directly inside the condition.

---

# 62. Capturing Regex Matches with `BASH_REMATCH`

When `=~` succeeds, Bash stores matching information in:

```bash
BASH_REMATCH
```

Example:

```bash
server="web-42"

if [[ "$server" =~ ^([a-z]+)-([0-9]+)$ ]]; then
    printf 'Full match: %s\n' "${BASH_REMATCH[0]}"
    printf 'Role: %s\n' "${BASH_REMATCH[1]}"
    printf 'Number: %s\n' "${BASH_REMATCH[2]}"
fi
```

Expected idea:

```text
Full match: web-42
Role: web
Number: 42
```

Arrays will be covered fully in Part 12.

For now, simply recognize that regex matching can extract pieces of data as well as validate it.

---

# 63. When to Use Pattern Matching vs Regex

Use simple Bash patterns when the requirement is simple:

```text
starts with web-
ends with .log
contains prod
matches app-*
```

Use regex when structure needs stronger validation:

```text
web- followed by digits
version number format
structured server name
specific identifier format
```

Do not use regex when a simple equality or glob test is clearer.

---

# 64. `case` Statements

Suppose a variable can contain:

```text
start
stop
restart
status
```

You could write:

```bash
if [[ "$action" == "start" ]]; then
    ...
elif [[ "$action" == "stop" ]]; then
    ...
elif [[ "$action" == "restart" ]]; then
    ...
elif [[ "$action" == "status" ]]; then
    ...
else
    ...
fi
```

This works.

But Bash provides a cleaner structure for matching one value against multiple patterns:

```bash
case
```

---

# 65. Basic `case` Syntax

Structure:

```bash
case "$value" in
    pattern1)
        commands
        ;;
    pattern2)
        commands
        ;;
    *)
        default_commands
        ;;
esac
```

Notice:

```bash
esac
```

ends the structure.

Like `fi`, it is the opening keyword reversed:

```text
case
esac
```

---

# 66. First `case` Example

```bash
action="status"

case "$action" in
    start)
        printf 'Starting application\n'
        ;;
    stop)
        printf 'Stopping application\n'
        ;;
    restart)
        printf 'Restarting application\n'
        ;;
    status)
        printf 'Checking application status\n'
        ;;
    *)
        printf 'Unknown action: %s\n' "$action" >&2
        ;;
esac
```

Bash compares:

```bash
"$action"
```

against each pattern.

---

# 67. Understanding `;;`

In a basic `case` statement:

```bash
;;
```

ends that branch.

Example:

```bash
start)
    printf 'Starting\n'
    ;;
```

Think:

```text
Pattern matched
     |
     v
Run commands
     |
     v
End this case branch
```

---

# 68. The Default `*` Pattern

The pattern:

```bash
*)
```

matches anything not handled earlier.

It acts similarly to an `else`.

Example:

```bash
*)
    printf 'Invalid option\n' >&2
    ;;
```

This is useful for unexpected input.

---

# 69. Multiple Patterns in One `case` Branch

You can match several alternatives using:

```bash
pattern1|pattern2)
```

Example:

```bash
case "$answer" in
    yes|y|Y)
        printf 'Confirmed\n'
        ;;
    no|n|N)
        printf 'Cancelled\n'
        ;;
    *)
        printf 'Invalid response\n'
        ;;
esac
```

This is much cleaner than repeating several string comparisons.

---

# 70. When `case` Is Better Than Multiple `if` Blocks

Use `case` when:

* one variable is compared against several known values
* one command argument can be one of several actions
* a menu has several numbered choices
* file names need pattern-based handling
* environment names need dispatch logic
* user responses have multiple accepted forms

For example:

```text
action
 |
 +--> start
 +--> stop
 +--> restart
 +--> status
```

is a natural `case` problem.

---

# 71. When `if` Is Better

Use `if` when conditions involve different kinds of tests.

Example:

```text
Does file exist?
AND
Is disk usage below threshold?
AND
Is user allowed?
```

These are not simply different values of one variable.

An `if` statement is usually clearer.

---

# 72. `case` Supports Patterns

`case` patterns are not limited to exact words.

Example:

```bash
filename="application.log"

case "$filename" in
    *.log)
        printf 'Log file detected\n'
        ;;
    *.conf)
        printf 'Configuration file detected\n'
        ;;
    *.sh)
        printf 'Shell script detected\n'
        ;;
    *)
        printf 'Other file type\n'
        ;;
esac
```

This is pattern matching, not regex.

# 77. Environment-Aware Logic

One of the most important DevOps uses of conditional logic is changing behavior according to environment.

Typical environments include:

```text
development
staging
production
```

These are often shortened to:

```text
dev
staging
prod
```

A simplified deployment flow might be:

```text
                Deployment
                    |
                    v
              Which environment?
             /        |        \
           dev     staging     prod
            |          |         |
            v          v         v
         relaxed     realistic   strict
         testing      testing    safeguards
```

The exact controls vary by organization.

The important point is that production usually deserves stronger safeguards.

---

# 78. Development Environment

Development environments are usually used while engineers build and test software.

A script might allow:

* verbose debugging
* test data
* frequent deployments
* local dependencies
* less restrictive workflows

Example:

```bash
if [[ "$environment" == "development" ]]; then
    debug="true"
    replicas=1
fi
```

The exact values are application-specific.

---

# 79. Staging Environment

Staging often attempts to resemble production closely enough to validate changes before release.

Example:

```bash
elif [[ "$environment" == "staging" ]]; then
    debug="false"
    replicas=2
```

A staging environment may be used for:

* integration testing
* release validation
* smoke testing
* production-like configuration checks
* deployment rehearsals

---

# 80. Production Environment

Production serves real users or real business workloads.

Production automation should normally be treated more carefully.

Example:

```bash
elif [[ "$environment" == "production" ]]; then
    debug="false"
    replicas=3
```

Production logic may additionally require:

* explicit confirmation
* approved configuration
* correct credentials
* backup verification
* health checks
* change controls
* rollback capability
* stronger logging
* stricter validation

Do not simply assume production is "development with more servers."

---

# 81. Environment Decision with `if`

Example:

```bash
environment="${APP_ENV:-development}"

if [[ "$environment" == "development" ]]; then
    printf 'Using development configuration\n'
elif [[ "$environment" == "staging" ]]; then
    printf 'Using staging configuration\n'
elif [[ "$environment" == "production" ]]; then
    printf 'Using production configuration\n'
else
    printf 'ERROR: unsupported environment: %s\n' "$environment" >&2
    exit 2
fi
```

This prevents unknown environment values from silently continuing.

---

# 82. Environment Decision with `case`

Because this compares one variable against several known values, `case` may be cleaner:

```bash
case "$environment" in
    development)
        printf 'Using development configuration\n'
        ;;
    staging)
        printf 'Using staging configuration\n'
        ;;
    production)
        printf 'Using production configuration\n'
        ;;
    *)
        printf 'ERROR: unsupported environment: %s\n' "$environment" >&2
        exit 2
        ;;
esac
```

This is a good example of when `case` is preferable.

---

# 83. Production-Specific Safeguards

Suppose production requires a configuration file:

```bash
production_config="./config/production.conf"
```

You can write:

```bash
if [[ "$environment" == "production" ]]; then
    if [[ ! -f "$production_config" ]]; then
        printf 'ERROR: production configuration missing\n' >&2
        exit 3
    fi
fi
```

This is a **nested conditional**.

An `if` statement appears inside another `if`.

---

# 84. Nested Conditions

Structure:

```bash
if outer_condition; then

    if inner_condition; then
        action
    fi

fi
```

Conceptually:

```text
Outer condition true?
        |
       Yes
        |
        v
Inner condition true?
        |
       Yes
        |
        v
      Action
```

Nested logic is sometimes necessary.

But too much nesting makes scripts difficult to understand.

---

# 85. Reduce Unnecessary Nesting

Instead of deeply nesting many checks:

```text
if A
    if B
        if C
            if D
```

sometimes fail-fast validation is clearer:

```bash
[[ condition_a ]] || exit 1
[[ condition_b ]] || exit 1
[[ condition_c ]] || exit 1
```

or structured separate `if` blocks.

Choose the form that communicates intent most clearly.

---

# 86. Negating Conditions

From Part 5:

```bash
!
```

negates success/failure.

You can use it inside `[[ ]]`.

Example:

```bash
if [[ ! -f "$config_file" ]]; then
    printf 'Configuration file does not exist\n'
fi
```

Read:

```text
-f file
 |
 v
is regular file?

!
 |
 v
NOT a regular file
```

---

# 87. Negative Logic vs Positive Logic

Compare:

```bash
if [[ ! -f "$config_file" ]]; then
    printf 'Missing\n'
else
    printf 'Present\n'
fi
```

with:

```bash
if [[ -f "$config_file" ]]; then
    printf 'Present\n'
else
    printf 'Missing\n'
fi
```

Both work.

Prefer whichever makes the operational intent clearer.

For fail-fast validation, negative checks are often natural:

```bash
if [[ ! -f "$config_file" ]]; then
    printf 'ERROR: configuration missing\n' >&2
    exit 1
fi
```

Then the rest of the script assumes the prerequisite exists.

Check 3 fails --> record
Check 4 passes
       |
       v
Show complete report
```

Useful when the user benefits from seeing everything that needs fixing.

Our server validator uses the second approach for most checks.

# 101. Check Disk Usage

```

Example output:

```text
37%
```

Remove `%`:

```bash
disk_usage="$(df -P "$base_directory" | awk 'NR==2 {print $5}' | tr -d '%')"
```

Now:

```bash
disk_usage
```

contains a number such as:

```text
37
```

# 102. Validate Disk Usage

Add:

```bash
printf '\nChecking disk usage...\n'

    printf 'FAIL: disk usage is critical: %s%%\n' "$disk_usage" >&2
    ((errors++))
elif (( disk_usage >= 75 )); then
    printf 'WARNING: disk usage is elevated: %s%%\n' "$disk_usage"
    ((warnings++))
else
    printf 'PASS: disk usage is healthy: %s%%\n' "$disk_usage"
fi
```

Decision tree:

```text
disk >= 90?
   |
  Yes --> FAIL
   |
   No
   v
disk >= 75?
   |
  Yes --> WARNING
   |
   No
   v
PASS
```

# 103. Validate the Numeric Data Before Trusting It

Production-quality scripts should not blindly assume command output is valid.

We can validate:

```bash
if [[ "$disk_usage" =~ ^[0-9]+$ ]]; then
    printf 'PASS: disk usage value is numeric\n'
else
    printf 'FAIL: invalid disk usage value: %s\n' "$disk_usage" >&2
    ((errors++))
fi
```

This demonstrates regex validation.

However, there is another design issue.

We should validate the value **before** performing arithmetic with it.

So the better order is:

```bash
if [[ "$disk_usage" =~ ^[0-9]+$ ]]; then

    if (( disk_usage >= 90 )); then
        ...
    elif (( disk_usage >= 75 )); then
        ...
    else
        ...
    fi

else
    printf 'FAIL: unable to determine valid disk usage\n' >&2
    ((errors++))
fi
```

Validate first.

Use second.

# 118. Common Beginner Error: Using String Operators for Numbers

Avoid treating numeric comparisons like ordinary strings.

For traditional tests:

```bash
if [ "$count" -gt 10 ]; then
```

For Bash arithmetic:

```bash
if (( count > 10 )); then
```

Choose numeric semantics intentionally.

---

# 119. Common Beginner Error: Comparing Numbers with `<` Inside `[ ]`

A beginner may write:

```bash
[ "$number" < 10 ]
```

This is not the correct traditional numeric comparison.

Use:

```bash
[ "$number" -lt 10 ]
```

or in Bash arithmetic context:

```bash
(( number < 10 ))
```

# 120. Common Beginner Error: Quoting a Glob Pattern

Suppose:

```bash
server="web-01"
```

This pattern test works:

```bash
[[ "$server" == web-* ]]
```

But:

```bash
[[ "$server" == "web-*" ]]
```

asks for the literal string:

```text
web-*
```

Do not quote pattern syntax when you intend it to act as a pattern.

---

# 121. Common Beginner Error: Treating Glob Patterns as Regex

This:

```text
*.log
```

is a glob pattern.

This:

```text
^[a-z]+\.log$
```

is a regular expression.

They belong to different matching systems.

Understand which one your conditional construct expects.

# 122. Common Beginner Error: Trusting Command Output Before Validation

Suppose:

```bash
disk_usage="$(some_command)"
```

Do not immediately assume it contains a valid integer.

Validate first:

```bash
if [[ "$disk_usage" =~ ^[0-9]+$ ]]; then
    ...
else
    ...
fi
```

External command output is data.

Data should be validated before sensitive use.

# 123. Common Beginner Error: Checking Only Existence

Suppose your script needs a readable configuration file.

This is incomplete:

```bash
[[ -e "$config_file" ]]
```

The path could exist but:

* be a directory
* be unreadable
* be empty
* be the wrong type

Ask the condition that matches the real requirement.

For example:

```bash
[[ -f "$config_file" && -r "$config_file" ]]
```

# 124. Common Beginner Error: Assuming Permission Tests Replace Security Design

A test such as:

```bash
[[ -w "$directory" ]]
```

can help determine whether a path is writable.

But it does not replace proper security practices.

You still need:

* least privilege
* correct ownership
* carefully designed permissions
* safe file locations
* appropriate service accounts
* avoidance of unnecessary root execution

Conditional tests observe state.

They do not automatically make that state secure.

# 125. Common Beginner Error: Deeply Nested `if` Statements

Code like:

```text
if
    if
        if
            if
                if
```

quickly becomes hard to follow.

Consider:

* early validation
* fail-fast checks
* `case`
* helper functions later
* simpler intermediate variables

Readable control flow is an operational advantage.

# 126. Common Beginner Error: Accepting Unknown Environments

Dangerous:

```bash
if [[ "$environment" == "production" ]]; then
    production_logic
else
    development_logic
fi
```

What happens if:

```text
environment = prodction
```

because of a typo?

It falls into the `else` branch and may be treated as development.

Safer:

```bash
case "$environment" in
    development)
        ...
        ;;
    staging)
        ...
        ;;
    production)
        ...
        ;;
    *)
        printf 'ERROR: invalid environment\n' >&2
        exit 1
        ;;
esac
```

Reject unknown values explicitly.

# 127. Common Beginner Error: Defaulting Production Unsafely

Be careful with defaults.

This is dangerous design:

```bash
environment="${APP_ENV:-production}"
```

If `APP_ENV` is missing, the script automatically targets production.

A safer default for a learning environment might be:

```bash
environment="${APP_ENV:-development}"
```

For real production deployment tools, requiring the environment explicitly may be even safer.

The correct choice depends on the risk.

# 137. Security: Never Trust User Input Blindly

A menu value or script argument is external input.

Treat it as data requiring validation.

For example:

```bash
case "$environment" in
    development|staging|production)
        ;;
    *)
        printf 'ERROR: invalid environment\n' >&2
        exit 2
        ;;
esac
```

Whitelisting known values is often safer than trying to guess what an unexpected value means.

# 138. Security: Production Should Usually Fail Closed

Suppose a production prerequisite cannot be verified.

Unsafe philosophy:

```text
Could not verify
      |
      v
Continue anyway
```

Safer philosophy:

```text
Could not verify
      |
      v
Stop
      |
      v
Investigate
```

This is often called **failing closed** in security-sensitive contexts.

The exact behavior depends on the system, but production automation should not casually bypass unknown states.

# 139. Choosing the Right Conditional Tool

Use:

```bash
if
```

when you need general decision logic.

Use:

```bash
[ ]
```

when you need traditional portable test syntax.

Use:

```bash
[[ ]]
```

for richer Bash-specific conditional expressions.

Use:

```bash
(( ))
```

for Bash arithmetic conditions.

Use:

```bash

```

when one value must be matched against multiple values or patterns.

```text
General decision?
    |
    v
   if

Traditional test?
    |
    v
  [ ]

Bash string/file/pattern condition?
    |
    v
 [[ ]]

Arithmetic decision?
    |
    v

    |

```

# 140. Production Thinking

Conditional logic is not merely syntax.

It represents operational decisions.

A production script should make questions explicit:

```text
What must be true before this action runs?

What states are acceptable?

What states are invalid?

Should failure stop execution?

Should the script collect all errors?

What should happen for unknown input?

Which conditions are warnings?

Which conditions are fatal?

Should production behave differently?

```

The syntax is the easy part.

The engineering skill is choosing the correct decision.

# What You Should Now Understand

After Part 6, you should understand that:

* scripts need conditional logic to respond to changing situations
* Bash conditions are fundamentally connected to exit statuses
* `if` evaluates whether a command or conditional expression succeeds
* `then` begins the success branch
* `else` provides an alternative branch
* `elif` allows additional conditions
* `fi` ends an `if` statement
* `test` performs conditional tests through exit statuses
* `[ ]` is traditional test syntax
* spaces around `[ ]` matter
* `[[ ]]` is a richer Bash conditional construct
* `[ ]` is generally more portable
* `[[ ]]` supports useful Bash-specific behavior
* numeric comparisons with `[ ]` use `-eq`, `-ne`, `-lt`, `-le`, `-gt`, and `-ge`
* `(( ))` provides readable Bash arithmetic conditions
* string equality and inequality are different from numeric comparisons
* `-z` checks for empty strings
* `-n` checks for non-empty strings
* an empty variable is different from an unset variable
* `[[ -v variable ]]` can test whether a Bash variable is set
* `-e` checks path existence
* `-f` checks for a regular file
* `-d` checks for a directory
* `-r` checks readability
* `-w` checks writability
* `-x` checks executability
* `-s` checks whether a file has non-zero size
* `-L` can test for symbolic links
* conditions can be combined with `&&` and `||`
* complex conditions should remain readable
* `[[ ]]` supports glob-style pattern matching
* quoting a pattern can make it literal
* glob patterns and regex are different
* `=~` performs regular-expression matching in `[[ ]]`
* regex can validate structured input
* `BASH_REMATCH` can hold matched regex groups
* `case` matches one value against several patterns
* `;;` ends a normal `case` branch
* `*` can provide a default `case` branch
* `case` is often clearer than many `elif` comparisons against one variable
* menus can use `read` plus `case`
* user input should be validated before acting
* development, staging, and production can require different behavior
* unknown environments should normally be rejected explicitly
* production should receive stronger safeguards where appropriate
* validation can fail fast or collect multiple errors
* validation results should ultimately produce meaningful exit statuses

# Part 6 Summary

You have moved from simple command execution into structured decision-making.

The basic Bash decision model is:

```text
Observe something
       |
       v
Evaluate condition
       |
    +--+--+
    |     |
  true   false
    |     |
    v     v
Action A Action B
```

The fundamental `if` structure is:

```bash
if condition; then
    action
else
    alternative
fi
```

For several conditions:

```bash
if condition1; then
    action1
elif condition2; then
    action2
elif condition3; then
    action3
else
    fallback
fi
```

You can test filesystem and string state using:

```bash
[[ ... ]]
```

For example:

```bash
[[ -f "$config_file" ]]
```

asks whether the path is a regular file.

```bash
[[ -d "$directory" ]]
```

asks whether it is a directory.

```bash
[[ -r "$file" ]]
```

asks whether it is readable.

```bash
[[ -w "$directory" ]]
```

asks whether it is writable.

```bash
[[ -x "$script" ]]
```

asks whether it is executable.

```bash
[[ -z "$value" ]]
```

asks whether a string is empty.

```bash
[[ -n "$value" ]]
```

asks whether it is non-empty.

You can combine conditions:

```bash
[[ condition1 && condition2 ]]
```

or:

```bash
[[ condition1 || condition2 ]]
```

You can perform pattern matching:

```bash
[[ "$server" == web-* ]]
```

and regular-expression matching:

```bash
[[ "$server" =~ ^web-[0-9]+$ ]]
```

When one value has several possible choices, you can use:

```bash
case "$value" in
    option1)
        ...
        ;;
    option2)
        ...
        ;;
    *)
        ...
        ;;
esac
```

Most importantly, you should now think of conditional logic as more than syntax.

It is how automation answers operational questions:

```text
Is the input valid?

Does the prerequisite exist?

Can I read the configuration?

Can I write to the destination?

Did the previous operation succeed?

Is this development, staging, or production?

Is this condition only a warning?

Is this condition dangerous enough to stop?

Should I continue?

Should I reject the request?

What should the final exit status be?
```

The engineering habits to keep from Part 6 are:

```text
Validate before acting.

Reject unknown values explicitly.

Use the most specific test for the requirement.

Distinguish files from directories.

Distinguish existence from readability and writability.

Distinguish empty variables from unset variables.

Use numeric operators for numbers.

Use string comparisons for strings.

Validate external command output before trusting it.

Understand when patterns are active and when quoting makes them literal.

Do not confuse shell globs with regular expressions.

Use regex only when simpler matching is insufficient.

Use case when one value has many possible choices.

Use if for general decision logic.

Avoid deeply nested conditions when simpler control flow is possible.

Give production stronger safeguards when risk requires them.

Do not bypass failed security or configuration checks merely to keep automation running.

Give humans useful diagnostics.

Give machines meaningful exit statuses.

Make the script's decision process understandable to the engineer who will troubleshoot it later.
```

In **Part 7: Loops and Repetitive Automation**, you will take these decisions and apply them repeatedly.

Instead of checking only one file, one server, one service, or one command, Bash will begin processing collections and repeating operations with:

```bash
for
while
until
break
continue
```

You will learn how to iterate through files, directories, ranges, command results, and server lists, how to safely read files line by line, how nested loops work, and how real DevOps scripts implement retries, polling, batch operations, and repetitive automation.
