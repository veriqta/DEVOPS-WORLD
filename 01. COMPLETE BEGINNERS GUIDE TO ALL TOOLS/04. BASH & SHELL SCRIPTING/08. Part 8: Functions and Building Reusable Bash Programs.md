# Part 8: Functions and Building Reusable Bash Programs

In Part 7, you learned how loops eliminate repeated commands.

Instead of writing:

```bash
check web01
check web02
check web03
```

you learned to write:

```bash
for server in web01 web02 web03; do
    check "$server"
done
```

That solves one kind of repetition.

But consider a larger Bash script.

You may repeatedly need to:

* print formatted messages
* validate files
* check directories
* check services
* calculate disk usage
* verify commands exist
* perform health checks
* write log entries
* handle errors

If you copy and paste the same group of commands throughout the script, the script becomes difficult to maintain.

Bash provides **functions** to solve this problem.

A function allows you to give a reusable block of commands a name.

Instead of repeating:

```bash
printf 'Checking disk usage...\n'
df -h
```

throughout your script, you could create:

```bash
check_disk() {
    printf 'Checking disk usage...\n'
    df -h
}
```

Then run:

```bash
check_disk
```

whenever you need that operation.

Functions allow Bash scripts to move from:

```text
long sequence of commands
```

toward:

```text
small reusable components
        |
        +--> validation
        +--> logging
        +--> disk checks
        +--> service checks
        +--> reporting
        +--> error handling
```

By the end of Part 8, you should understand:

* why functions matter
* how to create functions
* how to call functions
* how to name functions clearly
* how functions receive arguments
* `$1`, `$2`, and other positional parameters
* `$@`
* `$*`
* `$#`
* local variables
* the `local` command
* global variables
* function scope
* function return statuses
* the `return` command
* how functions return data through output
* the difference between output and return status
* how command substitution captures function output
* how to organize scripts into functions
* how to reuse functions
* how function libraries work
* how `source` works
* how the `.` command relates to `source`
* how to import common functions
* how to design maintainable Bash scripts
* how the `main` function pattern works
* how to build a practical reusable system utility

# 1. What Is a Bash Function?

A Bash function is a named group of shell commands.

Example:

```bash
show_date() {
    date
}
```

The function is named:

```text
show_date
```

The commands belonging to the function appear between:

```text
{
}
```

Defining the function does not automatically execute it.

You must call it:

```bash
show_date
```

Then Bash executes:

```bash
date
```

---

# 2. Why Functions Matter

Imagine a script that performs this operation several times:

```bash
printf '================================\n'
printf 'SYSTEM HEALTH CHECK\n'
printf '================================\n'
```

You could copy the block everywhere.

But now imagine you want to change the separator.

You would need to find every copy and modify it.

That creates duplication.

Instead:

```bash
print_header() {
    printf '================================\n'
    printf 'SYSTEM HEALTH CHECK\n'
    printf '================================\n'
}
```

Then:

```bash
print_header
```

Wherever you need it.

If the formatting changes, modify the function once.

Every caller automatically uses the new implementation.

---

# 3. Functions Reduce Duplication

Without functions:

```text
Script
 |
 +--> validation commands
 |
 +--> disk commands
 |
 +--> validation commands again
 |
 +--> service commands
 |
 +--> validation commands again
```

With functions:

```text
Script
 |
 +--> validate_input()
 |
 +--> check_disk()
 |
 +--> check_service()
 |
 +--> main()
```

The repeated implementation lives in one place.

---

# 4. Functions Improve Readability

Compare:

```bash
if [[ ! -f "$config_file" ]]; then
    printf 'ERROR: configuration file missing\n' >&2
    exit 1
fi

if [[ ! -r "$config_file" ]]; then
    printf 'ERROR: configuration file unreadable\n' >&2
    exit 1
fi
```

with:

```bash
validate_config "$config_file"
```

The second version tells you the intention immediately.

You can inspect the implementation separately when necessary.

Functions therefore allow scripts to communicate at different levels.

High-level logic:

```text
validate configuration
check dependencies
perform health checks
generate report
```

Low-level implementation:

```text
exact commands required for each operation
```

---

# 5. Functions Help Maintenance

Suppose ten parts of a script need to check whether a command exists.

Without a function, you may repeat:

```bash
if ! command -v curl > /dev/null 2>&1; then
    printf 'ERROR: curl not installed\n' >&2
    exit 1
fi
```

With a function:

```bash
require_command() {
    ...
}
```

you can call:

```bash
require_command curl
require_command grep
require_command awk
```

The checking logic exists only once.

Functions commonly represent operations such as:

```text
log_info()

require_command()
validate_file()
check_service()
check_disk()
check_memory()
check_endpoint()
deploy_application()
rollback_application()
create_backup()
cleanup()
send_notification()
```

A deployment script might eventually look like:

```text
main()

 +--> validate_environment()
 |
 +--> check_dependencies()
 |
 +--> run_tests()
 |
 +--> build_application()
 |
 +--> deploy_application()
 |
 +--> verify_deployment()
```

This is easier to reason about than hundreds of unrelated commands in one block.

# 7. Creating Your First Function

The most common Bash function syntax is:

```bash
function_name() {
    commands
}
```

Example:

```bash
greet() {
    printf 'Hello from Bash\n'
}
```

At this point Bash knows about the function.

But nothing has been printed yet.

Now call:

```bash
greet
```

Output:

```text
Hello from Bash
```

---

# 8. Function Definition vs Function Call

These are different operations.

Definition:

```bash
greet() {
    printf 'Hello\n'
}
```

Call:

```bash
greet
```

Think of the definition as:

```text
Teach Bash what "greet" means
```

and the call as:

```text
Execute "greet" now
```

---

# 9. Functions Must Usually Be Defined Before They Are Called

Consider:

```bash
greet

greet() {
    printf 'Hello\n'
}
```

When Bash reaches:

```bash
greet
```

the function has not yet been defined.

The shell may try to find an external command named `greet`.

You may receive:

```text
greet: command not found
```

Instead:

```bash
greet() {
    printf 'Hello\n'
}

greet
```

Bash learns the function first and calls it afterward.

---

# 10. Another Function Syntax

You may also encounter:

```bash
function greet {
    printf 'Hello\n'
}
```

or:

```bash
function greet() {
    printf 'Hello\n'
}
```

Bash supports these forms.

For this series, we will normally use:

```bash
greet() {
    ...
}
```

It is clean, familiar, and does not require the `function` keyword.

---

# 11. Function Naming

Function names should describe what the function does.

Good examples:

```text
check_disk
check_service
validate_file
print_report
require_command
create_backup
log_error
```

Poor examples:

```text
doit
thing
x
stuff
func1
test123
```

A reader should be able to see:

```bash
check_disk
```

and immediately understand the intention.

---

# 12. Use Consistent Naming

A useful convention is:

```text
verb_noun
```

Examples:

```text
check_disk
check_memory
validate_file
validate_directory
create_backup
remove_temp_files
print_summary
```

Consistency improves readability.

---

# 13. Avoid Function Names That Hide Familiar Commands

You could technically create:

```bash
ls() {
    printf 'Not the real ls\n'
}
```

Then:

```bash
ls
```

may call your function instead of the external `ls` command.

That can be extremely confusing.

Avoid function names that unnecessarily conflict with common commands such as:

```text
ls
cd
grep
curl
ssh
docker
kubectl
terraform
```

Use descriptive names instead.

# 14. Inspecting Functions

Remember the `type` command from Part 1.

Define:

```bash
check_disk() {
    df -h
}
```

Then:

```bash
type check_disk
```

Bash should report that:

```text
check_disk is a function
```

You can also use:

```bash
declare -f check_disk
```

to display the function definition.

# 15. Calling a Function Multiple Times

Functions are reusable.

```bash
show_time() {
    date
}

show_time
sleep 2
show_time
```

The same function executes twice.

You do not need to redefine it.

---

# 16. Functions Can Call Other Functions

Example:

```bash
print_separator() {
    printf '============================\n'
}

print_header() {
    print_separator
    printf 'SYSTEM REPORT\n'
    print_separator
}
```

Then:

```bash
print_header
```

One function can build on another.

This allows larger scripts to be composed from smaller operations.

---

# 17. Functions Need Input

A function such as:

```bash
check_file() {
    ...
}
```

needs to know:

> Which file?

Functions receive values through **arguments**.

Call:

```bash
check_file "/etc/hosts"
```

Inside the function, Bash makes that argument available as:

```bash
$1
```

---

# 18. `$1` Inside a Function

Example:

```bash
show_file() {
    printf 'File: %s\n' "$1"
}

show_file "/etc/hosts"
```

Output:

```text
File: /etc/hosts
```

Inside the function:

```text
$1 = /etc/hosts
```

---

# 19. Multiple Function Arguments

Call:

```bash
show_service "nginx" "production"
```

Define:

```bash
show_service() {
    printf 'Service: %s\n' "$1"
    printf 'Environment: %s\n' "$2"
}
```

Inside:

```text
$1 = nginx
$2 = production
```

---

# 20. Function Arguments Are Positional Parameters

The values are assigned according to position.

Call:

```bash
deploy_app "api" "production" "v2.4.1"
```

Inside the function:

```text
$1 = api
$2 = production
$3 = v2.4.1
```

If you change the order:

```bash
deploy_app "production" "api" "v2.4.1"
```

then:

```text
$1 = production
$2 = api
$3 = v2.4.1
```

Bash does not understand what the values mean.

Your function design determines their meaning.

---

# 21. Positional Parameters Beyond `$9`

For arguments 1 through 9:

```bash
$1
$2
$3
...
$9
```

For argument 10 and beyond, use braces:

```bash
${10}
${11}
```

Do not rely on:

```bash
$10
```

to mean argument 10.

It may be interpreted as:

```text
$1 followed by 0
```

Use:

```bash
"${10}"
```

---

# 22. Quote Function Arguments

Use:

```bash
"$1"
```

not:

```bash
$1
```

Example:

```bash
show_file() {
    printf 'File: %s\n' "$1"
}

show_file "application errors.log"
```

Quoting preserves the argument as one value.

This continues the quoting discipline you learned in Part 3.

---

# 23. Assign Arguments to Named Variables

Large functions become easier to read when positional parameters are immediately assigned meaningful names.

Instead of:

```bash
deploy_app() {
    printf 'Deploying %s to %s using %s\n' "$1" "$2" "$3"
}
```

prefer:

```bash
deploy_app() {
    local application="$1"
    local environment="$2"
    local version="$3"

    printf 'Deploying %s to %s using version %s\n' \
        "$application" "$environment" "$version"
}
```

Now the function communicates meaning.

---

# 24. `$#`: Number of Arguments

Inside a function:

```bash
$#
```

contains the number of arguments passed to that function.

Example:

```bash
show_count() {
    printf 'Argument count: %s\n' "$#"
}

show_count one two three
```

Output:

```text
Argument count: 3
```

---

# 25. Validating Argument Count

Suppose a function requires exactly two arguments.

```bash
check_service() {
    if (( $# != 2 )); then
        printf 'ERROR: check_service requires 2 arguments\n' >&2
        return 2
    fi

    local service="$1"
    local environment="$2"

    printf 'Checking %s in %s\n' "$service" "$environment"
}
```

Call correctly:

```bash
check_service nginx production
```

Call incorrectly:

```bash
check_service nginx
```

The function detects the missing argument.

---

# 26. Why Validate Function Arguments?

Without validation:

```bash
check_service nginx
```

may leave:

```text
$2 = empty
```

The function could then perform an incorrect operation.

Good reusable functions should validate assumptions.

Ask:

```text
How many arguments are required?

Can arguments be empty?

Does the path exist?

Is the value allowed?

Does the caller have permission?

Is the environment valid?
```

Functions should not blindly trust their inputs.

---

# 27. `$@`: All Arguments

Inside a function:

```bash
"$@"
```

represents all arguments while preserving each argument as a separate value.

Example:

```bash
show_arguments() {
    for argument in "$@"; do
        printf 'Argument: <%s>\n' "$argument"
    done
}
```

Call:

```bash
show_arguments "web01" "database primary" "api01"
```

Output:

```text
Argument: <web01>
Argument: <database primary>
Argument: <api01>
```

The argument:

```text
database primary
```

remains one argument.

---

# 28. Why `"$@"` Is Important

Suppose a function needs to pass its arguments to another command.

Example:

```bash
run_command() {
    printf 'Running command...\n'
    "$@"
}
```

Call:

```bash
run_command printf '%s\n' "hello world"
```

The function executes the arguments as a command while preserving their boundaries.

This pattern must still be used carefully, especially when arguments come from untrusted sources.

But it demonstrates why:

```bash
"$@"
```

is extremely useful.

---

# 29. `$*`: All Arguments as a Combined Expansion

Bash also provides:

```bash
$*
```

Like `$@`, it represents all positional parameters.

But the behavior differs when quoted.

Compare:

```bash
"$@"
```

with:

```bash
"$*"
```

The distinction matters.

---

# 30. `"$@"` vs `"$*"`

Suppose arguments are:

```text
one
two words
three
```

With:

```bash
"$@"
```

Bash preserves them as three separate arguments:

```text
<one>
<two words>
<three>
```

With:

```bash
"$*"
```

Bash combines them into one string, separated by the first character of `IFS`.

Typically:

```text
<one two words three>
```

---

# 31. Demonstrating `$@`

Create:

```bash
demo_at() {
    for argument in "$@"; do
        printf '<%s>\n' "$argument"
    done
}
```

Call:

```bash
demo_at "one" "two words" "three"
```

Output:

```text
<one>
<two words>
<three>
```

---

# 32. Demonstrating `$*`

Create:

```bash
demo_star() {
    for argument in "$*"; do
        printf '<%s>\n' "$argument"
    done
}
```

Call:

```bash
demo_star "one" "two words" "three"
```

Output is effectively one iteration:

```text
<one two words three>
```

---

# 33. Which Should You Usually Use?

When you need to preserve the original arguments, prefer:

```bash
"$@"
```

This is especially important when arguments contain:

* spaces
* wildcard characters
* empty values
* unusual characters

Use:

```bash
"$*"
```

when you intentionally want all arguments combined into one string.

Do not treat them as interchangeable.

---

# 34. Function Arguments Are Separate from Script Arguments

Suppose your script is called:

```bash
./utility.sh production
```

At the top level:

```bash
$1
```

is:

```text
production
```

Now define:

```bash
show_value() {
    printf '%s\n' "$1"
}
```

Call:

```bash
show_value "staging"
```

Inside the function:

```text
$1 = staging
```

The function receives its own positional parameters during the call.

This is important.

# 35. Variables and Scope

**Scope** describes where a variable is visible or usable.

Bash has some behavior that may surprise beginners.

By default, variables created inside functions are not automatically isolated from the rest of the script.

Example:

```bash
set_name() {
    name="VERIQTA"
}

set_name

printf '%s\n' "$name"
```

You may see:

```text
VERIQTA
```

The function changed a variable visible outside the function.

---

# 36. Global Variables

A variable available throughout the shell/script context is often described as global.

Example:

```bash
environment="production"

show_environment() {
    printf 'Environment: %s\n' "$environment"
}

show_environment
```

The function can access:

```bash
environment
```

even though the variable was created outside the function.

---

# 37. Functions Can Modify Global Variables

Example:

```bash
status="unknown"

set_status() {
    status="healthy"
}

set_status

printf 'Status: %s\n' "$status"
```

Output:

```text
Status: healthy
```

This can be useful.

It can also create hard-to-debug scripts.

---

# 38. Why Too Many Global Variables Become Dangerous

Imagine:

```text
main()
 |
 +--> function_a modifies status
 |
 +--> function_b modifies status
 |
 +--> function_c assumes old status
 |
 +--> unexpected behavior
```

If many functions silently modify shared global state, understanding the script becomes difficult.

Prefer local variables for temporary function-specific data.

---

# 39. The `local` Command

Inside a Bash function:

```bash
local
```

creates a variable local to that function invocation.

Example:

```bash
show_user() {
    local username="ann"

    printf 'Inside: %s\n' "$username"
}
```

The variable belongs to the function's scope.

---

# 40. Local Variable Example

```bash
name="global"

show_name() {
    local name="local"

    printf 'Inside function: %s\n' "$name"
}

show_name

printf 'Outside function: %s\n' "$name"
```

Output:

```text
Inside function: local
Outside function: global
```

The local variable did not overwrite the global variable.

---

# 41. Declare and Assign Local Variables

Common:

```bash
local file="$1"
```

You can also write:

```bash
local file
file="$1"
```

Both are valid.

For simple parameter assignment:

```bash
local file="$1"
```

is convenient.

---

# 42. A Subtle `local` Assignment Problem

Consider:

```bash
local output="$(some_command)"
```

This looks reasonable.

But `local` itself is a command.

The exit status you inspect afterward may be the status of `local`, not necessarily the failure you intended to detect from `some_command`.

When command success matters, separate declaration and assignment:

```bash
local output

if ! output="$(some_command)"; then
    printf 'ERROR: command failed\n' >&2
    return 1
fi
```

This preserves explicit error handling.

---

# 43. Use Local Variables for Function Internals

Example:

```bash
check_file() {
    local file="$1"
    local size

    size="$(wc -c < "$file")"

    printf '%s has %s bytes\n' "$file" "$size"
}
```

`file` and `size` are implementation details.

Other functions should not need to know about them.

---

# 44. Bash Uses Dynamic Scope for Local Variables

Bash function scope has an important behavior.

A local variable can be visible to functions called from the function where that variable is local.

Example:

```bash
child() {
    printf 'Value: %s\n' "$message"
}

parent() {
    local message="hello from parent"
    child
}

parent
```

The child function can see the parent's local variable.

This is called **dynamic scope**.

It differs from the lexical scoping used by many other programming languages.

For beginners, the practical rule is:

> Do not depend unnecessarily on invisible variables from calling functions.

Pass important values explicitly as arguments when possible.

---

# 45. Prefer Explicit Data Flow

Less clear:

```bash
check_service() {
    printf 'Checking %s\n' "$service_name"
}
```

Where did:

```bash
service_name
```

come from?

Better:

```bash
check_service() {
    local service_name="$1"

    printf 'Checking %s\n' "$service_name"
}

check_service "nginx"
```

Now the data flow is obvious.

# 46. Functions Have Exit Statuses

Commands have exit statuses.

Functions do too.

A function can communicate:

```text
success
```

or:

```text
failure
```

to its caller.

This is essential for reusable automation.

---

# 47. Default Function Exit Status

If you do not explicitly use `return`, the function's exit status is normally the exit status of the last command executed in the function.

Example:

```bash
check_hosts_file() {
    [[ -f /etc/hosts ]]
}
```

If `/etc/hosts` exists, the test returns:

```text
0
```

and therefore the function returns:

```text
0
```

If it does not exist, the function returns a non-zero status.

---

# 48. Testing Function Success

You can use a function directly with `if`.

```bash
check_hosts_file() {
    [[ -f /etc/hosts ]]
}

if check_hosts_file; then
    printf 'Hosts file exists\n'
else
    printf 'Hosts file missing\n' >&2
fi
```

This works because `if` evaluates the function's exit status.

---

# 49. The `return` Command

Inside a function:

```bash
return
```

ends the function and returns an exit status to the caller.

Example:

```bash
validate_file() {
    local file="$1"

    if [[ ! -f "$file" ]]; then
        printf 'ERROR: file not found: %s\n' "$file" >&2
        return 1
    fi

    return 0
}
```

---

# 50. `return 0`

Convention:

```bash
return 0
```

means:

```text
function succeeded
```

Example:

```bash
check_directory() {
    local directory="$1"

    if [[ -d "$directory" ]]; then
        return 0
    fi

    return 1
}
```

---

# 51. Non-Zero Return Status

A non-zero return status indicates failure or another defined condition.

Example:

```bash
validate_file() {
    local file="$1"

    if [[ -z "$file" ]]; then
        return 2
    fi

    if [[ ! -e "$file" ]]; then
        return 3
    fi

    if [[ ! -r "$file" ]]; then
        return 4
    fi

    return 0
}
```

You might define:

```text
0 = valid
2 = missing argument
3 = path does not exist
4 = unreadable
```

Document custom statuses if callers depend on them.

---

# 52. `return` vs `exit`

This distinction is critical.

Inside a function:

```bash
return 1
```

means:

```text
Stop this function
Return status 1 to caller
Continue script unless caller decides otherwise
```

But:

```bash
exit 1
```

means:

```text
Terminate the entire script/shell process
```

---

# 53. Example: `return`

```bash
check_file() {
    if [[ ! -f "$1" ]]; then
        return 1
    fi

    return 0
}

check_file "/missing/file"

printf 'Script is still running\n'
```

The function fails, but the script can continue.

---

# 54. Example: `exit`

```bash
check_file() {
    if [[ ! -f "$1" ]]; then
        exit 1
    fi
}

check_file "/missing/file"

printf 'You may never see this\n'
```

The function terminates the script.

That makes the function less reusable because it decides that the entire program must stop.

---

# 55. Prefer `return` in Reusable Functions

A reusable function should usually report failure and allow its caller to decide what to do.

Function:

```bash
validate_config() {
    local file="$1"

    [[ -r "$file" ]]
}
```

Caller:

```bash
if ! validate_config "$config_file"; then
    printf 'Configuration validation failed\n' >&2
    exit 1
fi
```

Now responsibility is separated:

```text
Function
   |
   +--> determine whether operation succeeded

Caller
   |
   +--> decide whether failure is fatal
```

This improves reusability.

---

# 56. `return` Is Not for Returning Arbitrary Data

A common beginner mistake is:

```bash
get_disk_usage() {
    return 45
}
```

thinking that `45` is ordinary data.

`return` communicates an exit status.

It is not the normal mechanism for returning arbitrary text or general numeric data.

Use output instead.

---

# 57. Returning Data Through Standard Output

Example:

```bash
get_hostname() {
    hostname
}
```

Capture it:

```bash
system_hostname="$(get_hostname)"
```

Then:

```bash
printf 'Hostname: %s\n' "$system_hostname"
```

The function writes data to standard output.

Command substitution captures that output.

---

# 58. Function Output vs Function Status

A function can communicate through two different channels.

```text
Function
   |
   +--> stdout --------> data
   |
   +--> exit status ---> success/failure
```

Example:

```bash
get_hostname() {
    hostname
    return 0
}
```

The hostname is data.

The return status tells the caller whether the function succeeded.

---

# 59. A Better Data-Returning Function

```bash
get_file_size() {
    local file="$1"

    if [[ ! -f "$file" ]]; then
        printf 'ERROR: file does not exist: %s\n' "$file" >&2
        return 1
    fi

    wc -c < "$file"
}
```

Call:

```bash
if size="$(get_file_size "/etc/hosts")"; then
    printf 'Size: %s bytes\n' "$size"
else
    printf 'Could not determine file size\n' >&2
fi
```

This is a powerful pattern.

---

# 60. Understanding That Pattern

The function:

```bash
get_file_size
```

uses:

```text
stdout
```

for the actual size.

It uses:

```text
stderr
```

for errors.

It uses:

```text
exit status
```

for success or failure.

Conceptually:

```text
get_file_size()
      |
      +--> stdout --> "245"
      |
      +--> stderr --> error message if needed
      |
      +--> status --> 0 or non-zero
```

This clean separation is extremely useful in automation.

---

# 61. Do Not Mix Human Messages with Data Output Carelessly

Consider:

```bash
get_hostname() {
    printf 'Getting hostname...\n'
    hostname
}
```

Then:

```bash
result="$(get_hostname)"
```

The variable contains both:

```text
Getting hostname...
actual-hostname
```

That may be undesirable.

If the function's stdout is intended as machine-readable data, keep informational messages away from stdout.

For example:

```bash
get_hostname() {
    printf 'Getting hostname...\n' >&2
    hostname
}
```

Now command substitution captures only the hostname.

---

# 62. Output Contract

A well-designed function should have a predictable contract.

For example:

```text
Function: get_file_size

Input:
    file path

stdout:
    file size

stderr:
    error messages

return status:
    0 = success
    non-zero = failure
```

Thinking this way makes functions easier to reuse.

---

# 63. Functions Can Use Loops

Everything from Part 7 still applies.

Example:

```bash
check_files() {
    local directory="$1"
    local file

    for file in "$directory"/*.log; do
        [[ -f "$file" ]] || continue

        printf 'Checking %s\n' "$file"
    done
}
```

Call:

```bash
check_files "$HOME/bash-lab/logs"
```

---

# 64. Functions Can Use Conditionals

Example:

```bash
classify_environment() {
    local environment="$1"

    if [[ "$environment" == "production" ]]; then
        printf 'critical\n'
    else
        printf 'standard\n'
    fi
}
```

Capture:

```bash
level="$(classify_environment production)"
```

---

# 65. Functions Can Call Commands

Example:

```bash
check_disk() {
    df -h
}
```

Functions can contain:

* builtins
* external commands
* pipelines
* redirections
* loops
* conditions
* other functions

A function is essentially a reusable command block.

---

# 66. Functions Can Accept Multiple Files

Example:

```bash
show_files() {
    local file

    for file in "$@"; do
        printf 'File: %s\n' "$file"
    done
}
```

Call:

```bash
show_files "/etc/hosts" "/etc/passwd" "application errors.log"
```

Using:

```bash
"$@"
```

preserves every original argument.

---

# 67. Validate Before Processing `$@`

Example:

```bash
show_existing_files() {
    local file

    if (( $# == 0 )); then
        printf 'ERROR: provide at least one file\n' >&2
        return 2
    fi

    for file in "$@"; do

        if [[ ! -f "$file" ]]; then
            printf 'SKIP: not a regular file: %s\n' "$file" >&2
            continue
        fi

        printf 'File: %s\n' "$file"

    done
}
```

Reusable functions should defend their assumptions.

---

# 68. Function Design: One Clear Responsibility

Avoid functions that attempt to do everything.

For example:

```text
do_everything()
```

that:

* validates arguments
* checks disk
* checks memory
* checks services
* deletes files
* performs deployment
* sends notifications
* generates reports

becomes difficult to test and maintain.

Prefer focused functions.

---

# 69. Better Decomposition

Instead:

```text
validate_environment()
check_dependencies()
check_disk()
check_memory()
check_service()
generate_report()
```

Then:

```bash
main() {
    validate_environment
    check_dependencies
    check_disk
    check_memory
    check_service
    generate_report
}
```

Each function has a clear purpose.

---

# 70. Think in Responsibilities

Ask:

> What is this block of commands responsible for?

If the answer is:

```text
verify a required command exists
```

create something like:

```bash
require_command()
```

If the answer is:

```text
check whether a service is active
```

create:

```bash
check_service()
```

If the answer requires five unrelated sentences, the function may be doing too much.

# 71. Organizing Scripts into Functions

```text

```

# 72. Why `main()` Helps

Small Bash scripts do not require a `main` function.

This is valid:

```bash
#!/usr/bin/env bash

printf 'Hello\n'
```

But as scripts grow, `main()` gives you an obvious entry point.

Example:

```bash
main() {
    validate_environment
    check_dependencies
    run_health_checks
    print_summary
}

main "$@"
```

A reader can immediately understand the script's high-level workflow.

---

# 73. The Main Function Pattern

A common pattern is:

```bash
main() {
    local environment="$1"

    validate_environment "$environment"
    run_checks "$environment"
    generate_report "$environment"
}

main "$@"
```

The script's original arguments are passed to `main` through:

```bash
"$@"
```

This keeps the top-level script clean.

---

# 74. Why `main "$@"`?

Suppose the script is run as:

```bash
./utility.sh production verbose
```

At script level:

```text
$1 = production
$2 = verbose
```

When you call:

```bash
main "$@"
```

the arguments are passed to `main` while preserving their boundaries.

Inside `main`:

```text
$1 = production
$2 = verbose
```

---

# 75. Main Function Validation

Example:

```bash
main() {
    if (( $# != 1 )); then
        printf 'Usage: %s <environment>\n' "$0" >&2
        return 2
    fi

    local environment="$1"

    printf 'Environment: %s\n' "$environment"
}

main "$@"
```

The `main` function can validate the script's external interface.

---

# 76. Capturing Main's Status

You may simply use:

```bash
main "$@"
```

as the final command.

The script will normally finish with the status returned by `main`.

Or make it explicit:

```bash
main "$@"
exit $?
```

However, there is an even clearer pattern when you want explicit handling:

```bash
if ! main "$@"; then
    exit 1
fi
```

The exact approach depends on whether you need to preserve specific custom statuses.

---

# 77. Preserving Main's Exact Status

If `main` may return several meaningful statuses:

```bash
main "$@"
status=$?

exit "$status"
```

This preserves the exact result.

For example:

```text
0 = success
2 = invalid usage
3 = missing dependency
4 = failed validation
```

# 78. Reusing Functions Within One Script

Suppose:

```bash

    local file="$1"

    if [[ ! -f "$file" ]]; then
        printf 'ERROR: missing file: %s\n' "$file" >&2
        return 1
    fi
}
```

You can reuse it:

```bash
require_file "/etc/hosts"
require_file "/etc/passwd"
require_file "$HOME/app.conf"
```

The implementation is written once.

---

# 79. What If Multiple Scripts Need the Same Function?

Suppose you have:

```text
backup.sh
deploy.sh
health-check.sh
cleanup.sh
```

and all need:

```text
log_info()
log_error()
require_command()
```

You could copy the functions into every script.

But then you create multiple copies to maintain.

Instead, put common functions in a **function library**.

---

# 80. What Is a Function Library?

A Bash function library is simply a file containing reusable function definitions.

Example:

```text
lib/common.sh
```

could contain:

```bash
log_info() {
    printf 'INFO: %s\n' "$*"
}

log_error() {
    printf 'ERROR: %s\n' "$*" >&2
}

require_command() {
    local command_name="$1"

    if ! command -v "$command_name" > /dev/null 2>&1; then
        log_error "Required command not found: $command_name"
        return 1
    fi
}
```

Other scripts can load these functions.

---

# 81. The `source` Command

Bash provides:

```bash
source
```

to read commands from another file into the current shell.

Example:

```bash
source ./lib/common.sh
```

After this command, functions defined in:

```text
./lib/common.sh
```

are available to the current script.

---

# 82. The `.` Command

The command:

```bash
.
```

can also source a file.

These are similar in Bash:

```bash
source ./lib/common.sh
```

and:

```bash
. ./lib/common.sh
```

The dot form is historically associated with POSIX shell syntax.

For Bash-focused scripts, `source` is often more immediately readable to beginners.

---

# 83. `source` Is Not the Same as Running Another Script

This distinction is extremely important.

Suppose:

```text
common.sh
```

contains:

```bash
greet() {
    printf 'Hello\n'
}
```

If you execute:

```bash
bash common.sh
```

Bash starts another shell, reads the file there, then that shell exits.

Your current shell does not necessarily receive the function.

But:

```bash
source common.sh
```

reads the file into the current shell context.

Then:

```bash
greet
```

is available.

---

# 84. Execution vs Sourcing

Conceptually:

```text
bash common.sh
      |
      v
new Bash process
      |
      v
define functions there
      |
      v
process ends
```

Compared with:

```text
source common.sh
      |
      v
current Bash process
      |
      v
definitions become available here
```

That is why libraries are sourced.

---

# 85. Sourced Files Can Modify Your Current Shell

This is also a security consideration.

When you run:

```bash
source some_file.sh
```

you are not merely importing harmless function definitions.

You are executing the contents of that file in your current shell context.

It can:

* define functions
* change variables
* change directories
* modify shell options
* create aliases
* unset variables
* run commands
* exit the shell/script

Therefore:

> Never source untrusted shell files.

Inspect them first.

# 88. Relative Path Problem with `source`

There is an important problem with:

```bash
source ./lib/common.sh
```

It depends on the current working directory.

Suppose your script lives in:

```text
/home/ann/bash-lab/part8/test-library.sh
```

but you run it while standing in:

```text
/tmp
```

The path:

```text
./lib/common.sh
```

means:

```text
/tmp/lib/common.sh
```

not:

```text
directory containing the script
```

This can cause:

```text
No such file or directory
```

---

# 89. Script Directory Pattern

A common Bash solution is:

```bash
script_dir="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)"
```

Then:

```bash
source "$script_dir/lib/common.sh"
```

This makes the library path relative to the script itself rather than the user's current directory.

This line looks complicated, so let us break it down.

---

# 90. `${BASH_SOURCE[0]}`

In Bash:

```bash
${BASH_SOURCE[0]}
```

usually identifies the current script or sourced file.

This is often more useful for locating Bash source files than:

```bash
$0
```

especially when sourcing is involved.

---

# 91. `dirname`

The command:

```bash
dirname
```

extracts the directory portion of a path.

Example:

```bash
dirname "/home/ann/project/script.sh"
```

returns something similar to:

```text
/home/ann/project
```

---

# 92. `cd` and `pwd`

This section:

```bash
cd -- "$(dirname -- "${BASH_SOURCE[0]}")"
```

moves into the directory containing the script.

Then:

```bash
pwd
```

prints the resulting absolute directory path.

Command substitution captures it:

```bash
script_dir="$(...)"
```

---

# 93. Why `--` Appears

Many commands use:

```text
--
```

to indicate:

> Stop interpreting following values as command options.

This is useful when a filename or path begins with:

```text
-
```

It is a defensive scripting habit.

Not every command handles `--` identically, but commands such as `cd` and `dirname` support the pattern used here.

---

# 94. Safer Library Import

Now:

```bash
script_dir="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)"

source "$script_dir/lib/common.sh"
```

works based on the script location.

Conceptually:

```text
Find this script
      |
      v
Find its directory
      |
      v
Build library path
      |
      v
Source common.sh
```

---

# 95. Validate a Library Before Sourcing

You can check:

```bash
library="$script_dir/lib/common.sh"

if [[ ! -r "$library" ]]; then
    printf 'ERROR: library not readable: %s\n' "$library" >&2
    exit 1
fi

source "$library"
```

This provides a clearer failure message.

---

# 96. Sourcing Can Fail

`source` itself returns an exit status.

Therefore:

```bash
if ! source "$library"; then
    printf 'ERROR: failed to load library: %s\n' "$library" >&2
    exit 1
fi
```

can detect a sourcing failure.

However, library design also matters.

A sourced file should avoid unexpected top-level actions.

---

# 97. Good Library Design

A library file should generally focus on definitions.

For example:

```bash
log_info() {
    ...
}

log_error() {
    ...
}

require_command() {
    ...
}
```

Avoid surprising behavior such as:

```bash
printf 'Deleting temporary files...\n'
rm -rf ...
```

at top level.

The act of importing a library should not unexpectedly perform unrelated operations.

---

# 98. Libraries Should Not Usually Call `main`

Suppose:

```text
common.sh
```

contains:

```bash
main() {
    ...
}

main "$@"
```

When another script sources `common.sh`, the `main` function immediately executes.

That is usually undesirable for a reusable library.

Libraries generally define functionality.

Executable scripts decide what to run.

# 100. Do Not Split Tiny Scripts Too Early

Modularity is useful.

Overengineering is not.

A 15-line script does not necessarily need:

* clarity
* reuse
* testing
* maintenance

Do not create complexity merely to look sophisticated.

# 101. Designing Maintainable Functions

A good function should usually have:

```text
Clear name
   |
   v
Clear inputs
   |
   v
Input validation
   |
   v
Focused responsibility
   |
   v
Predictable stdout/stderr
   |
   v
Meaningful return status
```

The caller should know what to expect.

---

# 102. Function Contract Example

Consider:

```bash
check_file_readable() {
    local file="$1"

    if [[ -z "$file" ]]; then
        printf 'ERROR: file argument required\n' >&2
        return 2
    fi

    if [[ ! -f "$file" ]]; then
        printf 'ERROR: not a regular file: %s\n' "$file" >&2
        return 3
    fi

    if [[ ! -r "$file" ]]; then
        printf 'ERROR: file is not readable: %s\n' "$file" >&2
        return 4
    fi

    return 0
}
```

Contract:

```text
Input:
    one file path

stdout:
    nothing

stderr:
    validation errors

status:
    0 valid
    2 missing argument
    3 not regular file
    4 unreadable
```

This is predictable.

# 103. Logging Functions

Logging is an excellent use case for reusable functions.

Example:

```bash
log_info() {
    printf 'INFO: %s\n' "$*"
}

log_warning() {
    printf 'WARNING: %s\n' "$*" >&2
}

log_error() {
    printf 'ERROR: %s\n' "$*" >&2
}
```

Now:

```bash
log_info "Health check started"
log_warning "Disk usage above threshold"
log_error "Database unavailable"
```

provides consistent formatting.

---

# 104. Timestamped Logging

Improve it:

```bash
log_info() {
    printf '%s INFO: %s\n' "$(date '+%Y-%m-%d %H:%M:%S')" "$*"
}
```

Output:

```text
2026-09-02 12:30:00 INFO: Health check started
```

The exact time will depend on when you run the script.

---

# 105. Avoid Repeating Timestamp Logic

Without a function:

```bash
printf '%s INFO: starting\n' "$(date ...)"
printf '%s INFO: checking\n' "$(date ...)"
printf '%s ERROR: failed\n' "$(date ...)"
```

With functions:

```bash
log_info "Starting"
log_info "Checking"
log_error "Failed"
```

The timestamp format is controlled in one place.

---

# 106. Dependency Checking Function

A reusable utility often needs commands such as:

```text
df
grep
awk
systemctl
curl
```

Create:

```bash
require_command() {
    local command_name="$1"

    if [[ -z "$command_name" ]]; then
        log_error "require_command needs a command name"
        return 2
    fi

    if ! command -v "$command_name" > /dev/null 2>&1; then
        log_error "Required command not found: $command_name"
        return 1
    fi

    return 0
}
```

---

# 107. Use the Dependency Function

```bash
if ! require_command grep; then
    exit 1
fi
```

Or check several commands:

```bash
for command_name in df grep awk; do
    if ! require_command "$command_name"; then
        exit 1
    fi
done
```

This combines:

* functions
* loops
* conditions
* exit statuses

---

# 108. Function That Returns Data

Create:

```bash
get_hostname() {
    local value

    if ! value="$(hostname)"; then
        log_error "Could not determine hostname"
        return 1
    fi

    printf '%s\n' "$value"
}
```

```bash

```

Then:

```bash

```

# 109. Function That Returns Status Only

Example:

```bash
is_root() {
    (( EUID == 0 ))
}
```

Call:

```bash
if is_root; then
    printf 'Running as root\n'
else
    printf 'Not running as root\n'

```

The function does not need to print data.

Its purpose is to answer a yes/no question through exit status.

# 110. Predicate Functions

Functions such as:

```text
is_root

is_service_active
file_exists
port_is_open
```

are often called **predicate functions** because they represent a condition.

They are useful with:

```bash
if
```

```bash
while
```

and:

```bash
until
```

Example:

```bash

    ...

```

This can make logic highly readable.

# 111. Environment Validation Function

```bash
is_valid_environment() {
    local environment="$1"

    case "$environment" in
        development|staging|production)
            return 0
            ;;
        *)
            return 1
            ;;
    esac
}
```

Then:

```bash
if ! is_valid_environment "$environment"; then
    log_error "Invalid environment: $environment"
    exit 2
fi
```

This reuses the `case` logic from Part 6.

# 112. Functions and Safe Production Decisions

Suppose production requires extra confirmation or stricter validation.

You could create:

```bash
is_production() {
    [[ "$1" == "production" ]]
}
```

Then:

```bash
if is_production "$environment"; then
    log_warning "Production environment detected"
fi
```

The high-level code communicates intention clearly.

---

# 113. Avoid Hidden Side Effects

A function named:

```text
get_disk_usage
```

should probably not:

* delete files
* restart services
* change permissions

A name should reflect behavior.

If a function modifies the system, use a name that communicates the action:

```text
remove_old_logs
restart_service
update_permissions
create_backup
```

Predictability is a major part of maintainability.

---

# 114. Functions Should Not Silently Depend on Working Directory

Fragile:

```bash
read_config() {
    cat config/app.conf
}
```

This assumes the caller is in the correct directory.

Better:

```bash
read_config() {
    local config_file="$1"

    cat "$config_file"
}
```

Or construct the path from a known script directory.

Hidden working-directory assumptions cause many automation failures.

---

# 115. Functions Should Validate Destructive Inputs

Suppose a future cleanup function accepts a directory.

Dangerous:

```bash
cleanup_directory() {
    rm -rf "$1"/*
}
```

If `$1` is empty or incorrect, consequences may be severe.

A production-quality destructive function would require extensive validation.

At minimum, before destructive operations, consider:

* argument present?
* absolute expected path?
* path exists?
* path is directory?
* path is within allowed location?
* not `/`?
* not `$HOME` accidentally?
* dry-run available?
* backups required?
* confirmation policy?
* least privilege?

We will continue strengthening these safety patterns later.

---

# 116. Never Use `eval` Just to Make Functions Flexible

Beginners sometimes encounter:

```bash
eval "$command"
```

and use it to dynamically execute strings.

This can create serious quoting and command-injection problems.

For example, if untrusted input becomes part of that string, Bash may interpret shell syntax contained in the input.

Prefer explicit arguments and:

```bash
"$@"
```

where appropriate.

Do not reach for `eval` unless you deeply understand why it is necessary and the security implications.

---

# 117. Function Libraries and Naming Collisions

If two libraries define:

```bash
log_info()
```

the later definition may replace the earlier one.

Large Bash projects sometimes use naming prefixes.

Example:

```text
veriqta_log_info
veriqta_log_error
veriqta_require_command
```

or project-specific prefixes.

For small projects, this may be unnecessary.

For shared libraries, namespacing can reduce collisions.

calls:

The command:


The option:



# 134. Create Dependency Validation

Add:

```bash
check_dependencies() {
    local command_name
    local failed=0

    for command_name in \
        date \
        whoami \
        hostname \
        uname \
        df \
        free \
        pgrep
    do
        if ! require_command "$command_name"; then
            failed=1
        fi
    done

    if (( failed != 0 )); then
        return 1
    fi

    return 0
}
```

This function reuses:

```text
require_command()
```

from the imported library.

---

# 135. Why Continue Checking Dependencies?

Notice that we did not immediately return after the first missing command.

Instead:

```bash
failed=1
```

records that something failed.

The loop continues.

This allows the user to see all missing dependencies in one run.

At the end:

```bash
if (( failed != 0 )); then
    return 1
fi
```

reports overall failure.

This is the partial-failure reasoning from Part 7.

# 138. Why Return `10` for Exit?

For this learning project, we use:

```text

```

as an internal signal meaning:

```text
user selected Exit
```

This is not a universal Bash standard.

It is simply a documented status chosen for this program.

The caller can distinguish:

```text
0 = operation succeeded
1 = operation failed
2 = invalid input
10 = user requested exit
```

In a larger application, constants or clearer control structures could make this even more explicit.

```bash
case "$status" in
```

# 156. Common Mistake: Calling Before Definition

Problem:

```bash
check_disk

check_disk() {
    df -h
}
```

Bash has not seen the function definition when the first line executes.

Move the definition above the call.

# 157. Common Mistake: Missing Arguments

Function:

```bash
check_file() {
    local file="$1"

    [[ -f "$file" ]]
}
```

Call:

```bash
check_file
```

Now `$1` is empty.

Fix by validating:

```bash
if (( $# < 1 )); then
    printf 'ERROR: file argument required\n' >&2
    return 2
fi
```

# 158. Common Mistake: Using Global Variables Accidentally

Problem:

```bash
calculate() {
    result="something"
}
```

The function may modify a global `result`.

Better:

```bash
calculate() {
    local result="something"
}
```

Use globals intentionally, not accidentally.

# 159. Common Mistake: Using `exit` Inside Every Function

Problem:

```bash
validate_file() {
    if [[ ! -f "$1" ]]; then
        exit 1
    fi
}
```

Now the function cannot be reused in situations where the caller wants to recover.

Prefer:

```bash
return 1
```

and let the caller decide.

---

# 160. Common Mistake: Trying to Return Text with `return`

Wrong concept:

```bash
get_environment() {
    return "production"
}
```

`return` expects a numeric status.

Use:

```bash
get_environment() {
    printf '%s\n' "production"
}
```

Capture:

```bash
environment="$(get_environment)"
```

---

# 161. Common Mistake: Polluting Captured Output

Problem:

```bash
get_value() {
    printf 'Calculating...\n'
    printf '42\n'
}

value="$(get_value)"
```

`value` contains both lines.

If only `42` is data:

```bash
get_value() {
    printf 'Calculating...\n' >&2
    printf '42\n'
}
```

---

# 162. Common Mistake: Using `$*` When `$@` Is Needed

If arguments need to remain separate:

```bash
for argument in "$@"; do
    ...
done
```

Do not replace it blindly with:

```bash
for argument in "$*"; do
```

because quoted `$*` combines arguments.

---

# 163. Common Mistake: Unquoted `$@`

Prefer:

```bash
"$@"
```

not:

```bash
$@
```

Unquoted positional parameters may undergo unwanted word splitting and filename expansion.

---

# 164. Common Mistake: Source Path Depends on Current Directory

Fragile:

```bash
source ./lib/common.sh
```

if the script can be launched from different directories.

Use a script-relative path:

```bash
script_dir="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)"
source "$script_dir/lib/common.sh"
```

---

# 165. Common Mistake: Sourcing Untrusted Files

Problem:

```bash
source "$user_supplied_file"
```

without understanding its contents.

Because sourcing executes the file in the current shell context, this can allow arbitrary shell commands to execute.

Only source trusted code.

---

# 166. Common Mistake: Library Performs Work During Import

Library:

```bash
log_info() {
    ...
}

rm -rf /some/path
```

Simply sourcing the library executes the `rm` command.

Libraries should generally avoid surprising top-level actions.

---

# 167. Common Mistake: Function Does Too Much

If a function is hundreds of lines long and responsible for:

```text
validation
networking
deployment
logging
cleanup
reporting
```

it may be difficult to understand.

Break it into meaningful operations.

But do not split every two lines into a separate function either.

Aim for useful boundaries.

# 168. Common Mistake: Ignoring Return Status

Suppose:

```bash

deploy_application
```

If `create_backup` fails but you ignore its status, deployment may continue.

Instead:

```bash
if ! create_backup; then
    log_error "Backup failed. Deployment stopped."

deploy_application
```

Reusable functions only help if callers respond correctly to failures.

```bash
printf
```

which probably succeeds.

Therefore the function may return:

```text
0
```

even though:

```bash
false
```

failed.

---

# 173. Fixing Lost Failure Status

Handle the command explicitly:

```bash
do_work() {
    if ! false; then
        printf 'Operation failed\n' >&2
        return 1
    fi

    printf 'Finished\n'
    return 0
}
```

Do not assume an earlier failure automatically becomes the function's final status.

## Problem

```bash

```

contains informational messages.

## Cause

The function wrote both data and human messages to stdout.

## Fix

Keep:

```text
stdout = data
stderr = diagnostics
```

when the function is designed for command substitution.

# 175. Troubleshooting: Custom Status Disappears After `!`

Problem:

```bash
if ! some_function; then
    printf 'Status: %s\n' "$?"
fi
```

You expected the original custom failure status.

But `!` negates command success/failure.

If exact status matters:

```bash
some_function
status=$?

if (( status != 0 )); then
    printf 'Status: %s\n' "$status"
fi
```

# What You Should Now Understand

After Part 8, you should understand that:

* a function is a named reusable block of commands
* defining a function does not execute it
* functions are called by their names
* functions reduce duplicated code
* functions improve readability and maintenance
* function names should describe their responsibilities
* consistent names such as `verb_noun` are useful
* functions can call other functions
* functions receive arguments through positional parameters
* `$1` is the first function argument
* `$2` is the second
* `${10}` is the correct form for argument 10
* `$#` contains the number of function arguments
* `"$@"` preserves all arguments as separate arguments
* `"$*"` combines all positional parameters into one string when quoted
* `"$@"` is usually preferable when forwarding or iterating over original arguments
* positional parameters should normally be quoted
* assigning positional parameters to descriptive local variables improves readability
* Bash variables are global unless made local in the relevant function context
* functions can read and modify global variables
* excessive shared global state makes scripts harder to reason about
* `local` creates function-local variables
* Bash local variables use dynamic scope
* explicit function arguments are usually clearer than hidden dependencies
* functions have exit statuses
* a function normally inherits the status of its last executed command unless explicitly controlled
* `return` ends a function
* `return 0` indicates success
* non-zero return statuses indicate failure or another defined condition
* `return` is different from `exit`
* `return` leaves the function
* `exit` terminates the script or shell process
* reusable functions should usually return failure rather than terminating the whole program themselves
* arbitrary data should normally be returned through stdout
* command substitution can capture function stdout
* stderr should be used for diagnostics when stdout is machine-readable data
* a function can communicate both data and status
* function output should have a predictable contract
* functions can contain loops, conditions, pipelines, and other functions
* functions should generally have focused responsibilities
* scripts can be organized into validation, logging, operational, reporting, and main functions
* `main()` gives larger scripts a clear entry point
* `main "$@"` passes script arguments into the main function
* shared functions can be stored in library files
* `source` reads another shell file into the current shell context
* `.` is another way to source a file
* sourcing differs from executing a script in another Bash process
* sourced files can modify the current shell and must therefore be trusted
* library paths should not blindly depend on the current working directory
* `${BASH_SOURCE[0]}` can help locate the current Bash source file
* reusable libraries should generally define functions rather than unexpectedly execute operations
* function libraries reduce duplication across multiple scripts
* dependencies between libraries should be clear
* functions should validate dangerous inputs before making system changes
* functions should avoid unnecessary hidden side effects
* reusable Bash programs should expose predictable interfaces
* functions make larger automation easier to test and troubleshoot
