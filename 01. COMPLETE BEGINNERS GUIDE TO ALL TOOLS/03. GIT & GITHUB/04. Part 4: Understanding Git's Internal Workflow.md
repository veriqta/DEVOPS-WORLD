# 1. Start With the Big Picture

Before looking inside Git, remember the basic workflow:

```text
WORKING TREE
     |
     | git add
     v
STAGING AREA / INDEX
     |
     | git commit
     v
LOCAL REPOSITORY
```

This model is simple, but it is extremely important.

Most everyday Git operations involve relationships between these three areas.

Let's define them properly.

---

# 2. The Three Main Areas

Git beginners should become comfortable thinking about three major areas:

```text
1. Working Tree

2. Staging Area / Index

3. Local Repository
```

They are related, but they are not the same thing.

Imagine you are working on:

```text
veriqta-git-lab/
├── README.md
├── app.py
└── config/
    └── app.conf
```

The files you open and edit are part of your working tree.

When you select changes using `git add`, Git updates the staging area.

When you run `git commit`, Git records the staged snapshot in the local repository.

Conceptually:

```text
Files you edit
     |
     v
WORKING TREE
     |
     | git add
     v
STAGING AREA
     |
     | git commit
     v
LOCAL REPOSITORY
```

Understanding these boundaries will make many later Git commands easier to understand.

---

# 3. What Is the Working Tree?

The **working tree**, sometimes called the **working directory**, is the checked-out version of your project that you can actually work with.

It contains files such as:

```text
README.md
app.py
config/app.conf
```

These are the files you:

* Open
* Read
* Edit
* Delete
* Rename
* Execute
* Test

If you open `app.py` in Visual Studio Code and change:

```python
print("Application started")
```

to:

```python
print("VERIQTA application started")
```

you changed the working-tree version of the file.

Git has not automatically committed that change.

You have simply changed the file on disk.

---

# 4. Working Tree Does Not Mean the Entire Computer

The term can sound confusing.

Your working tree is not:

```text
your entire filesystem
```

It refers to the checked-out files belonging to the repository you are currently working with.

Suppose you have:

```text
Projects/
├── payment-api/
│   └── .git/
│
└── monitoring-dashboard/
    └── .git/
```

These are separate Git repositories.

Each repository has its own working tree and Git metadata.

Changes in:

```text
payment-api/
```

do not automatically become changes in:

```text
monitoring-dashboard/
```

---

# 5. Why Is It Called a Working Tree?

You can think of it as the project state where you perform your actual work.

For example:

```text
Repository history
        |
        | Git checks out a version
        v
Working Tree
        |
        | You edit files
        v
Modified Working Tree
```

The word **tree** also relates to the hierarchical structure of directories and files.

For example:

```text
project/
|
+-- README.md
|
+-- src/
|   |
|   +-- app.py
|
+-- config/
    |
    +-- app.conf
```

Your project has a tree-like structure.

---

# 6. What Is the Staging Area?

You learned in Part 3 that the staging area is where you prepare the next commit.

Suppose you modify:

```text
README.md
app.py
config/app.conf
```

But only the changes in:

```text
README.md
app.py
```

belong to the feature you are currently recording.

You can stage those two:

```bash
git add README.md app.py
```

while leaving:

```text
config/app.conf
```

unstaged.

Conceptually:

```text
WORKING TREE

README.md       modified
app.py          modified
app.conf        modified

       |
       | git add README.md app.py
       v

STAGING AREA

README.md
app.py

NEXT COMMIT

README.md
app.py
```

The configuration change remains outside the next commit.

---

# 7. Staging Area and Index

You will frequently encounter two terms:

```text
Staging Area
```

and:

```text
Index
```

For the purposes of learning Git:

```text
Staging Area = Index
```

They refer to the mechanism Git uses to prepare the contents of the next commit.

"Staging area" is easier to understand conceptually.

"Index" is the terminology you will often encounter in Git documentation and advanced discussions.

Do not assume they are two separate places.

---

# 8. Why the Index Matters

The index gives you control over the next snapshot.

Imagine you spent one hour working and accidentally mixed three tasks:

```text
Task A:
Fix application timeout

Task B:
Update README

Task C:
Experiment with logging
```

Your working tree contains changes for all three.

Without careful selection, you might create one messy commit:

```text
Fix timeout and docs and logging stuff
```

Instead, the staging area allows you to organize history.

You could stage only the timeout fix:

```bash
git add src/api.py
```

Then commit it:

```bash
git commit -m "Fix API timeout handling"
```

Later, stage the documentation:

```bash
git add README.md
```

and create another commit:

```bash
git commit -m "Document API timeout configuration"
```

This produces cleaner history.

---

# 9. The Staging Area Is a Proposed Snapshot

A powerful way to think about the staging area is:

> The staging area represents what you are currently proposing as the next commit.

Suppose your current commit contains:

```text
app.py version 1
README.md version 1
config.yml version 1
```

You modify `app.py` and stage it.

Conceptually:

```text
CURRENT COMMIT

app.py       version 1
README.md    version 1
config.yml   version 1


STAGING AREA

app.py       version 2
README.md    version 1
config.yml   version 1
```

The next commit is being prepared with:

```text
app.py       version 2
README.md    version 1
config.yml   version 1
```

This becomes important when understanding snapshots.

---

# 10. What Is the Local Repository?

The local repository is the Git database associated with your project.

Its metadata normally lives inside:

```text
.git/
```

The local repository contains information about things such as:

* Commits
* Git objects
* Branches
* Tags
* References
* Configuration
* Repository history

It exists on your computer.

You do not need GitHub to create a local repository.

This workflow:

```text
Working Tree
     |
     | git add
     v
Staging Area
     |
     | git commit
     v
Local Repository
```

can happen completely offline.

---

# 11. Local Repository vs GitHub

This distinction must remain clear.

Your local Git repository might exist at:

```text
/Users/ann/projects/payment-api/.git/
```

A GitHub repository exists remotely on infrastructure operated by GitHub.

They are different repositories that can later exchange Git data.

Conceptually:

```text
YOUR COMPUTER

Working Tree
     |
     v
Staging Area
     |
     v
Local Git Repository


        NETWORK
           |
           v

REMOTE GIT REPOSITORY
       GitHub
```

At this point in the series, our focus remains primarily on the local side.

---

# 12. What Is a Commit?

A commit is a recorded point in your repository's history.

Suppose your project begins with:

```text
README.md
app.py
```

You create:

```bash
git commit -m "Create initial application"
```

Later you modify `app.py` and create:

```bash
git commit -m "Add health check endpoint"
```

Later:

```bash
git commit -m "Document local setup"
```

Your history now contains multiple recorded states:

```text
Commit A
Create initial application
        |
        v
Commit B
Add health check endpoint
        |
        v
Commit C
Document local setup
```

Each commit represents a meaningful recorded state of the project.

---

# 13. A Commit Is More Than a Message

Beginners sometimes think a commit is mainly:

```text
commit message
```

It is not.

The message is metadata describing the commit.

A commit is connected to information including:

* A project snapshot
* Author information
* Committer information
* Timestamp information
* Commit message
* Parent commit or commits
* A unique object identifier

Conceptually:

```text
COMMIT
|
+-- project tree
|
+-- parent
|
+-- author
|
+-- committer
|
+-- message
|
+-- identifier
```

---

# 14. Git Thinks in Snapshots

One of the most important ideas in Git is that Git's model is based on snapshots.

Imagine your project at three moments.

## Commit A

```text
README.md
app.py
```

## Commit B

```text
README.md
app.py
config.yml
```

## Commit C

```text
README.md
app.py
config.yml
deploy.sh
```

You can think of each commit as representing a snapshot of the project at that point.

Conceptually:

```text
Commit A
[Project State A]

      |
      v

Commit B
[Project State B]

      |
      v

Commit C
[Project State C]
```

This mental model is more accurate than thinking that Git history is simply a pile of patch files.

---

# 15. Snapshots vs File Differences

This distinction often confuses beginners.

You frequently see Git display differences like:

```diff
- PORT=8080
+ PORT=9090
```

So it is natural to think:

> Git commits must just store the difference between the old file and the new file.

But that is not the best mental model for Git's object model.

Git fundamentally records project states through objects and snapshots.

It can then efficiently determine differences between those states.

Conceptually:

```text
Snapshot A
     |
     | compare
     v
Snapshot B
     |
     v
Difference
```

rather than thinking only:

```text
Difference
=
entire meaning of the commit
```

Git can show you differences because it can compare states.

---

# 16. Example: Snapshot vs Difference

Suppose `app.conf` initially contains:

```text
PORT=8080
ENVIRONMENT=development
```

Later it contains:

```text
PORT=9090
ENVIRONMENT=development
```

Git can show:

```diff
- PORT=8080
+ PORT=9090
```

That is the **difference** between versions.

But the project snapshot at the later commit conceptually includes the complete state:

```text
PORT=9090
ENVIRONMENT=development
```

Think:

```text
Snapshots = recorded project states

Diffs = comparisons between states
```

This distinction will help enormously when you later use:

```text
git diff
git show
git log
git restore
git reset
```

---

# 17. Does Git Waste Space by Copying Everything?

The snapshot model may make you wonder:

> If every commit represents the whole project, does Git create a completely separate physical copy of every unchanged file?

No.

Git uses its object database efficiently.

When file content has not changed, Git can reuse existing objects rather than creating unnecessary duplicate content objects.

Conceptually:

```text
Commit A

app.py ------> Blob X
README ------> Blob Y


Commit B

app.py ------> Blob X
README ------> Blob Z
```

Here:

```text
app.py
```

did not change.

Git can continue referring to the same underlying content object.

`README.md` changed, so new content is represented.

You therefore get a snapshot model without needing to think of every commit as a completely duplicated project folder.

# 18. Introduction to Git Objects

Now we can go one level deeper.

Git stores repository data using objects.

At a beginner level, three especially important object types are:

```text
Blob
Tree
Commit
```

There is also another object type called a tag object, which we will encounter when we study tags.

For now:

```text
Git Object Database
|
+-- Blob
|
+-- Tree
|
+-- Commit
```

Each object serves a different purpose.

---

# 19. Why Learn Git Objects?

You do not need to manually create Git objects during normal beginner work.

But understanding them answers important questions such as:

* What does Git actually store?
* How does a commit represent files?
* Why does a commit have a hash?
* How does Git connect commits together?
* Why can Git reconstruct old project states?

This knowledge also makes advanced Git troubleshooting easier later.

---

# 20. What Is a Blob?

A **blob** is a Git object used to store file content.

Blob means:

```text
Binary Large Object
```

But do not let the name make the concept sound more complicated than it is.

For beginner purposes:

```text
Blob
=
file content stored by Git
```

Suppose:

```text
README.md
```

contains:

```text
# VERIQTA Git Lab
```

Git can store that content as a blob object.

Conceptually:

```text
README.md
    |
    v
File content
    |
    v
Blob object
```

---

# 21. A Blob Does Not Primarily Store the Filename

This is an important internal concept.

A blob represents file content.

The filename is associated through the tree structure rather than being the fundamental identity of the blob itself.

Think:

```text
Blob
|
+-- content
```

not:

```text
Blob
|
+-- README.md filename
+-- folder path
+-- content
```

The directory structure and names are represented through tree objects.

---

# 22. Identical Content Can Be Reused

Suppose two files contain exactly the same content:

```text
file-a.txt
file-b.txt
```

Both contain:

```text
production-ready
```

Because Git identifies objects based on their content and object representation, identical content can correspond to the same blob object.

Conceptually:

```text
file-a.txt ----\
                \
                 > Blob X
                /
file-b.txt ----/
```

The names can be different while the underlying content object is the same.

This helps illustrate why filenames and file content are separate concepts internally.

---

# 23. What Is a Tree Object?

A **tree** object represents directory-like structure.

It connects names to Git objects.

A tree can contain references to:

* Blob objects
* Other tree objects

Suppose your project is:

```text
project/
├── README.md
├── app.py
└── config/
    └── app.conf
```

Conceptually, Git can represent this as:

```text
ROOT TREE
|
+-- README.md ---> Blob A
|
+-- app.py ------> Blob B
|
+-- config ------> Tree C
                    |
                    +-- app.conf ---> Blob D
```

This is the basic relationship.

---

# 24. Blob vs Tree

A simple distinction:

```text
BLOB
stores file content

TREE
organizes names and directory structure
```

Example:

```text
Tree
|
+-- README.md ---> Blob
|
+-- src ---------> Tree
                    |
                    +-- app.py ---> Blob
```

You can think of a tree as describing:

> Which names exist here, and which objects do those names refer to?

---

# 25. What Is a Commit Object?

A commit object connects a recorded project state to history and metadata.

Conceptually:

```text
Commit Object
|
+-- Tree
|
+-- Parent commit
|
+-- Author
|
+-- Committer
|
+-- Message
```

The tree identifies the root project snapshot.

The parent connects the commit to earlier history.

The metadata explains who created the commit and why.

---

# 26. Connecting the Three Objects

Now put everything together.

Suppose your project contains:

```text
README.md
src/app.py
```

Git's internal model can be simplified as:

```text
COMMIT
  |
  v
ROOT TREE
  |
  +-- README.md ---> BLOB A
  |
  +-- src ---------> TREE B
                       |
                       +-- app.py ---> BLOB C
```

The commit identifies a tree.

The tree represents the project structure.

The blobs represent file contents.

This is one of the most useful beginner-friendly models of Git's object database.

---

# 27. A More Complete Commit Diagram

Now add history:

```text
COMMIT C
|
+-- Tree C
|
+-- Parent ---> COMMIT B
|
+-- Author
|
+-- Message
```

Commit B:

```text
COMMIT B
|
+-- Tree B
|
+-- Parent ---> COMMIT A
|
+-- Author
|
+-- Message
```

Commit A:

```text
COMMIT A
|
+-- Tree A
|
+-- No parent
|
+-- Author
|
+-- Message
```

Now history begins to appear.

# 28. What Is a Commit Hash?

When you run:

```bash
git log --oneline
```

you may see:

```text
9b3c41a Add health check endpoint
4f71d28 Create initial application
```

The values:

```text
9b3c41a
4f71d28
```

are abbreviated object identifiers for the commits.

You will often hear engineers call them:

* Commit hashes
* Commit IDs
* SHA values
* SHA identifiers

In everyday conversation, these terms are often used loosely to refer to a commit's object ID.

---

# 29. Why Does Git Need Identifiers?

Imagine your history contains:

```text
Create application
Fix application
Fix application
Update application
Fix application
```

Messages are not guaranteed to be unique.

Git needs a reliable way to identify objects.

That is where object identifiers come in.

Instead of saying:

> Give me the commit called "Fix application."

you can refer to a specific identifier.

For example:

```bash
git show 9b3c41a
```

The identifier points Git to a specific object.

---

# 30. What Does SHA Mean?

Historically, Git repositories used SHA-1 for object names.

SHA stands for:

```text
Secure Hash Algorithm
```

A hash function takes input and produces a fixed-size output.

Conceptually:

```text
Input data
    |
    v
Hash function
    |
    v
Identifier
```

Git has also introduced support for SHA-256 repositories.

As a beginner, the most important point is not memorizing cryptographic details.

Remember:

> Git objects have content-derived object identifiers that Git uses to identify and connect repository data.

---

# 31. Full vs Short Object IDs

A full SHA-1 object ID is much longer than what you normally see with:

```bash
git log --oneline
```

You may see something like:

```text
9b3c41a
```

instead of a full identifier.

Git often allows an unambiguous shortened form.

Conceptually:

```text
Full identifier
9b3c41a..........................

Short form
9b3c41a
```

The shortened version is easier for humans to work with.

---

# 32. Important: The Hash Is Not Random

A Git object ID is not simply a random number assigned to a commit.

It is derived from the object's contents and representation.

That means changing the commit information changes the resulting commit object and therefore its identifier.

For a commit, relevant content includes information such as:

* Tree
* Parent information
* Author
* Committer
* Message

This is one reason Git history has strong internal relationships.

---

# 33. What Is a Parent Commit?

Most commits point to an earlier commit called their **parent**.

Suppose you create:

```text
Commit A
```

Then create:

```text
Commit B
```

Commit B points back to Commit A.

```text
Commit A
    ^
    |
 parent
    |
Commit B
```

We often draw history in the easier reading direction:

```text
Commit A
    |
    v
Commit B
```

But internally, the newer commit contains the reference to its parent.

---

# 34. The First Commit Is Special

Your first commit has no parent.

Why?

Because nothing came before it.

Conceptually:

```text
Commit A
Initial commit

Parent: none
```

The next commit:

```text
Commit B

Parent: Commit A
```

The next:

```text
Commit C

Parent: Commit B
```

This creates a chain.

---

# 35. How Commits Form History

Suppose you create three commits:

```text
A = Create project
B = Add configuration
C = Add health check
```

The relationship is:

```text
A
|
v
B
|
v
C
```

Internally, think backward:

```text
C
|
+-- parent --> B
               |
               +-- parent --> A
```

Git can follow parent relationships backward through history.

This is fundamental to:

* `git log`
* Branches
* Merges
* Rebasing
* Reverting
* History inspection

---

# 36. History Is Not Based on Timestamps Alone

It would be easy to assume Git simply sorts commits by date.

But the important structure comes from parent relationships.

Conceptually:

```text
Commit C
parent -> Commit B

Commit B
parent -> Commit A
```

These relationships form the history graph.

This becomes especially important when branches and merges create histories that are not simply one straight line.

Later you will see histories like:

```text
A---B---C---F
     \     /
      D---E
```

For now, a straight history is enough.

---

# 37. What Is HEAD?

HEAD is one of the most important Git concepts.

At a beginner level:

> HEAD tells Git where you currently are in the checked-out history.

In normal branch-based work, HEAD usually points to the current branch, and that branch points to a commit.

For example:

```text
HEAD
 |
 v
main
 |
 v
Commit C
```

This means:

* You are currently on `main`
* `main` currently identifies Commit C
* Commit C is the current tip of that branch

---

# 38. HEAD Is Not Usually the Branch Itself

Be precise with the relationship.

Normal state:

```text
HEAD
 |
 v
refs/heads/main
 |
 v
Commit C
```

Simplified:

```text
HEAD
 |
 v
main
 |
 v
C
```

HEAD tells Git which branch is currently checked out.

The branch reference identifies the current commit at the tip of that branch.

This distinction becomes extremely important later.

---

# 39. Inspect HEAD

Inside your practice repository, run:

```bash
cat .git/HEAD
```

You may see:

```text
ref: refs/heads/main
```

This tells you HEAD currently refers to:

```text
refs/heads/main
```

Conceptually:

```text
HEAD
 |
 v
main
```

Do not manually edit `.git/HEAD`.

We are inspecting it only to understand the concept.

---

# 40. What Happens to HEAD After a Commit?

Suppose history is:

```text
A
|
v
B

main -> B
HEAD -> main
```

You create another commit.

Git creates:

```text
C
```

and advances the branch reference:

```text
A
|
v
B
|
v
C

main -> C
HEAD -> main
```

HEAD still refers to `main`.

But `main` now identifies the new commit.

This is how the branch moves forward as you commit.

---

# 41. HEAD Helps Define "Current"

Many Git commands need to know what you mean by:

```text
current version
current commit
current branch position
```

HEAD plays a major role in that.

You will later use expressions such as:

```text
HEAD
HEAD~1
HEAD~2
```

For now:

```text
HEAD
```

means your current checked-out position.

---

# 42. Current Commit, Index, and Working Tree

We can now expand our earlier model.

Git often needs to compare:

```text
HEAD
Index
Working Tree
```

Conceptually:

```text
HEAD
Current committed snapshot
        |
        | compare
        v
INDEX
Staged snapshot
        |
        | compare
        v
WORKING TREE
Files currently on disk
```

This model explains a large part of everyday Git behavior.

---

# 43. Example: Everything Matches

Suppose:

```text
HEAD version of app.py:
Version A

Index version:
Version A

Working tree version:
Version A
```

Everything matches.

```text
HEAD        A
INDEX       A
WORKING     A
```

Then:

```bash
git status
```

reports a clean working tree.

---

# 44. Example: File Is Modified

Now edit `app.py`.

Working tree:

```text
Version B
```

But HEAD and the index still represent:

```text
Version A
```

Now:

```text
HEAD        A
INDEX       A
WORKING     B
```

Git sees:

```text
Index != Working Tree
```

So the file appears as:

```text
modified
```

and not yet staged.

---

# 45. Example: File Is Staged

Now run:

```bash
git add app.py
```

The index is updated to represent the new content.

Now:

```text
HEAD        A
INDEX       B
WORKING     B
```

Git sees:

```text
HEAD != Index
```

That difference is prepared for the next commit.

`git status` reports the file under:

```text
Changes to be committed
```

---

# 46. Example: File Is Committed

Now run:

```bash
git commit -m "Update application output"
```

The new commit records the staged state.

Now conceptually:

```text
HEAD        B
INDEX       B
WORKING     B
```

Everything matches again.

Result:

```text
working tree clean
```

This is one of the most important Git state models you can learn.

---

# 47. The State Table

| State     | HEAD | Index | Working Tree |
| --------- | ---- | ----- | ------------ |
| Clean     | A    | A     | A            |
| Modified  | A    | A     | B            |
| Staged    | A    | B     | B            |
| Committed | B    | B     | B            |

Do not memorize the letters.

Understand what they represent.

```text
A = old content
B = new content
```

# 48. What Actually Happens During git add?

Now we can answer this more accurately.

Suppose:

```text
app.py
```

contains new content in your working tree.

You run:

```bash
git add app.py
```

At a beginner-friendly internal level, Git:

1. Reads the current file content
2. Creates or reuses the appropriate content object
3. Updates the index so it represents that content for the next snapshot

Conceptually:

```text
Working Tree
app.py
Version B
     |
     | git add
     v
Blob representing Version B
     |
     v
Index updated
```

The important point is:

> `git add` updates Git's proposed next snapshot.

Because of the word "add," beginners sometimes imagine:

```text
=

```

It does not.

Everything we are discussing is still local.

```text

    |
    | git add
    v

```

No GitHub connection is required.

No internet connection is required.

# 50. git add Does Not Mean "Commit"

Another common misunderstanding:

```text

```

does not permanently record a commit.

It prepares content.

Think:

```text

=

```

and:

```text

=

```

The distinction matters because you can change the staging area before committing.

# 51. What Actually Happens During git commit?

Suppose the index represents:

```text

app.py
config/app.conf
```

You run:

```bash

```

At a simplified internal level, Git:

1. Uses the staged/index state to build the project tree
2. Creates the necessary tree objects
3. Creates a commit object
4. Connects the commit to its parent, if one exists
5. Records author/committer metadata
6. Records the commit message
7. Generates the commit object's identifier
8. Moves the current branch reference to the new commit

Conceptually:

```text
INDEX
 |
 v
TREE SNAPSHOT
 |
 v
COMMIT OBJECT
 |
 +-- parent
 +-- author
 +-- message
 |
 v
NEW COMMIT ID
 |
 v
CURRENT BRANCH MOVES FORWARD
```

# 63. Git File States

A beginner should recognize four major terms:

```text
Untracked
Modified
Staged
Committed
```

Let's define each carefully.

---

# 64. Untracked

An untracked file exists in the working tree but is not currently part of Git's tracked file history.

Example:

```text
notes.txt
```

You just created it.

Git says:

```text
Untracked files:
  notes.txt
```

Conceptually:

```text
File exists
+
Git sees it
+
Not tracked yet
=
UNTRACKED
```

---

# 65. Modified

A modified file is already tracked, but the working-tree version differs from the staged/recorded state.

Example:

```text
app.py
```

was committed.

You edit it.

Git now sees:

```text
MODIFIED
```

Conceptually:

```text
Tracked file
+
Working copy changed
+
Change not staged
=
MODIFIED
```

---

# 66. Staged

A staged change has been added to the index and is prepared for the next commit.

Example:

```bash
git add app.py
```

Conceptually:

```text
Current working content
        |
        | git add
        v
Index
        |
        v
Prepared for next commit
```

State:

```text
STAGED
```

---

# 67. Committed

A committed state has been recorded in repository history.

Conceptually:

```text
Index
   |
   | git commit
   v
Repository history
```

The recorded file content is now represented through Git's object and commit structure.

# 79. Common Beginner Confusion: "Where Did My File Go After git add?"

It did not disappear from your working tree.

Running:

```bash
git add app.py
```

does not move the physical file out of your project directory.

The file remains:

```text
project/app.py
```

Git reads its content and updates repository/index information.

Conceptually, when we draw:

```text
Working Tree
     |
     v
Staging Area
```

we are describing Git state transitions.

We are not saying the operating system physically moves `app.py` into a folder called "staging area."

---

# 80. Common Beginner Confusion: "Where Is the Staging Folder?"

There normally is no project directory called:

```text
staging/
```

The staging area is represented internally by Git's index.

It is not a folder where you manually drag files.

Use Git commands to interact with it.

For example:

```bash
git add app.py
```

updates the staged state.

---

# 81. Common Beginner Confusion: "Does Git Store Only Changes?"

Git often **shows** changes as differences.

Example:

```diff
- PORT=8080
+ PORT=9090
```

But Git's conceptual storage model is based on snapshots and objects.

Remember:

```text
Snapshots
=
recorded states

Diffs
=
comparisons between states
```

Do not confuse how Git displays changes with the fundamental model of repository history.

---

# 82. Common Beginner Confusion: "Is HEAD My Latest Commit?"

Often, in a simple repository, HEAD ultimately resolves to the latest commit on your currently checked-out branch.

But the more accurate model is:

```text
HEAD
 |
 v
Current branch
 |
 v
Commit
```

Later, you will learn situations where HEAD can point directly to a commit instead of through a branch.

That is called a detached HEAD state.

Do not worry about it yet.

For now, remember the normal case.

---

# 83. Common Beginner Confusion: "Is the Commit Hash the File Hash?"

No.

Different Git objects have their own object identifiers.

A commit object has an identifier.

A blob object has an identifier.

A tree object has an identifier.

Conceptually:

```text
Blob A
 -> object ID

Tree B
 -> object ID

Commit C
 -> object ID
```

When engineers casually say:

```text
commit hash
```

they mean the object ID identifying that commit object.

# 85. Troubleshooting: My New Edits Are Missing From the Commit

Scenario:

1. You edited `app.py`
2. You ran:

```bash

```

3. You edited `app.py` again
4. You ran:


The commit did not "lose" your work.

# 106. Part 4 Final Recap

You began with the simple Git model:

```text
Working Tree
     |
     | git add
     v
Staging Area
     |
     | git commit
     v
Local Repository
```

You can now see what lies underneath it.

The working tree contains the files you actively edit.

The index represents the proposed next snapshot.

The local repository stores Git's object database and history.

Git represents file content with:

```text
BLOBS
```

It represents directory structure using:

```text
TREES
```

And it represents recorded history using:

```text
COMMITS
```

The relationship can be simplified as:

```text
COMMIT
  |
  +-- TREE
  |    |
  |    +-- BLOB
  |    +-- BLOB
  |    +-- TREE
  |         |
  |         +-- BLOB
  |
  +-- PARENT COMMIT
  |
  +-- AUTHOR / COMMITTER
  |
  +-- MESSAGE
```

Commits are connected through parent relationships:

```text
A
|
v
B
|
v
C
```

Your current branch points to the current commit:

```text
main
 |
 v
C
```

and HEAD normally refers to the current branch:

```text
HEAD
 |
 v
main
 |
 v
C
```

The most important state model from this part is:

```text
HEAD
Current committed snapshot
        |
        v
INDEX
Proposed next snapshot
        |
        v
WORKING TREE
Current files on disk
```

When everything matches:

```text
HEAD       A
INDEX      A
WORKING    A
```

the repository is clean.

After editing:

```text
HEAD       A
INDEX      A
WORKING    B
```

the file is modified.

After staging:

```text
HEAD       A
INDEX      B
WORKING    B
```

the change is staged.

After committing:

```text
HEAD       B
INDEX      B
WORKING    B
```

everything matches again.

And if you stage a file and then edit it again:

```text
HEAD       A
INDEX      B
WORKING    C
```

the same file can contain both staged and unstaged changes.

That single model explains a surprisingly large amount of Git.

You now understand not only **which commands to type**, but what Git is doing when you type them.
